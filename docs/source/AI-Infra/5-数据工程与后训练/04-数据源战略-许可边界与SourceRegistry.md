# 数据源战略、许可边界与 Source Registry

## 1. 本文要解决的工程问题

采集任务把公开可访问误当成可训练、可再分发，直到数据已经进入多个版本才发现许可、robots 与退出联系人从未登记。

本文围绕一个可执行判断展开：怎样在采集前把许可、用途、撤回和责任边界写进 Source Registry？读完应能给出自己的系统边界、输入输出、版本关系和验收证据，而不是只复述工具名称或公式。

## 2. 本文交付物与判定标准

本文的核心决定是：在抓取前建立 Source Registry，把来源身份、许可依据、用途、保留期、退出方式和责任人写成机器可判定的准入合同。

完成学习和实验后，应当交付一份最小可复现记录，至少包含输入快照、配置、代码版本、运行状态、原始输出和结论边界。验收证据是：每个采集对象都能命中一个有效来源记录；缺许可、超用途或退出中的来源会在进入解析层前被拒绝。

围绕“数据源战略、许可边界与 Source Registry”的验收不接受三类替代品：把模拟输出写成真实 GPU 结果；只展示成功样本而隐藏失败与 `SKIPPED`；只给总分，不保存能复算总分的对象级记录。

## 3. 前置知识与实验边界

“数据源战略、许可边界与 Source Registry”的机制实验使用 Python 3.10 及以上版本和标准库，重点验证对象、算法或状态转换。真实硬件路径使用 PyTorch；检测不到 CUDA 时必须输出结构化 `SKIPPED`，不得静默改跑 CPU 后仍标成 GPU 实测。

技术门禁保存和执行已批准的政策，不替法律意见或合同解释作最终判断。

### 3.1 业务背景与失败模式

模型数据问题往往在清洗之后才被发现：某批内容无法证明来源，某个站点要求退出，某个代码仓库许可证改变，某个产品日志没有获得训练用途授权，或者训练集规模很大却被少数不稳定来源支配。此时再回到海量 Shard 中寻找原始关系，成本远高于入口登记。

Source Strategy 解决的不是“去哪里下载更多文件”，而是组织为什么需要某类数据、允许以什么方式取得、怎样证明使用边界、如何持续更新、出现撤回时怎样退出，以及每单位独特可训练 Token 是否值得长期维护。Source Registry 则把这些决策变成机器可查询、可审批和可传播的资产。

来源公开可访问，不代表自动允许抓取、训练、再分发或商业使用；标注了许可证，也不代表每个子对象都由同一权利人提供；robots、服务条款、合同、隐私、版权和内部政策解决不同问题，不能压缩成一个 `license=public` 字段。这里提供工程化记录与门禁方法，不构成针对具体司法辖区或项目的法律意见。真实项目应由具备权限的法务、隐私与安全角色确认。

本文建立从业务目标到 Source Portfolio 的完整链路：能力缺口转成来源需求；候选来源经过身份、获取、许可、隐私、质量、独特性、稳定性和成本评审；通过的来源生成 Source、Agreement、Capture、Policy 与退出合同；采集和训练只消费明确版本；来源变化触发重新审批与影响分析。

### 3.2 学习目标与能力清单

完成后应当能够：

1. 区分 Source、Provider、Owner、Publisher、Capture、Agreement 与 Data Object。
2. 把模型能力目标转成语言、领域、难度、时间与交互类型的来源需求。
3. 为网页、代码、论文、内部日志、人工标注、合成数据和在线反馈设计不同入口合同。
4. 解释许可证、服务条款、robots、隐私同意、合同和组织 Policy 的不同作用。
5. 设计可查询的 Source Registry Schema，而不是只保存 URL 列表。
6. 为来源定义允许用途、禁止用途、再分发、保留、地域、模型阶段和撤回规则。
7. 评估来源的独特 Token 转换率、质量、覆盖、稳定性、成本和供应链风险。
8. 设计 Onboarding、Capture、监控、变更、暂停、撤回和退休状态机。
9. 通过机制实验实现 Policy Decision 与退出影响，通过 CUDA 实验证明训练前可以按 Source Policy 编译不可变 Mixture。
10. 明确自动化 Policy Engine 能做什么，以及哪些判断必须由有权限的人完成。

### 3.3 实验准备与责任边界

需要理解前几篇的数据对象、版本、Manifest 与血缘。机制实验使用 Python 标准库实现 Source Registry、用途 Policy、审批和 Capture Manifest，不连接外部网站，也不判断真实许可证是否合法。

真实硬件实验使用至少一张可用 CUDA GPU 和 PyTorch DDP。程序读取三个受控来源的 Token Shard，根据训练用途、地域、再分发和审批状态编译允许集合，再训练小型自回归模型。一个被禁止来源会在 CUDA 初始化前被拒绝。该实验验证 Policy 与真实训练入口的连接，不提供任何真实来源的法律结论。

所有示例中的来源、合同和政策均为虚构工程数据。程序输出 `allow`、`deny` 或 `review` 只是依据输入规则的机械结果；环境不足输出结构化 `skipped`。本文不会把网页可访问性、robots 允许或某个许可证标签单独解释为训练合法性。

## 4. 来源对象模型怎样建立

来源不是 URL，抓取事件需要关联取得依据与对象身份。

### 4.1 Source 不是一个 URL

URL 是定位信息，会重定向、过期或被复用。Source 表示稳定的内容供应关系，例如某个网站集合、代码组织、数据供应商、企业系统、标注项目、Teacher 生成服务或产品反馈管道。

一个 Source 至少有稳定 ID、类型、Provider、Owner/联系人、获取方式、用途、Policy、时间范围、更新节奏、身份验证、退出通道和状态。URL、Bucket、API 和数据库表是 Location，可以随版本变化。

### 4.2 Provider、Publisher 与权利主体

Provider 是向组织交付数据的一方；Publisher 是发布内容的平台或机构；内容作者、上传者、数据主体和权利人可能不同。一个社区平台作为 Provider，并不自动拥有所有用户内容的全部权利。

Registry 应能表达已知角色和证据，而不是强行把它们合成 `owner`。不确定关系标记 `unknown/review`，不能用空字段默认允许。

### 4.3 Agreement 描述依据与边界

Agreement 可以是许可证声明、采购合同、内部授权、隐私同意、数据共享协议或其他经批准依据。它包含证据、版本、有效期、地域、允许用途、禁止用途、再分发、保留、删除、审计和责任人。

同一 Source 可能同时受多个 Agreement 约束。最终 Policy 是多个条件与组织规则的组合，不是随便选择最宽松的一条。

### 4.4 Capture 表示一次取得事件

Source 是长期关系，Capture 是某次抓取、导出、购买批次或生成运行。Capture 记录时间窗口、工具、请求、认证身份、原始清单、响应证据、对象哈希和状态。

相同 Source 每月 Capture 形成不同版本。来源 Policy 后续改变时，可以准确区分变更前后对象，而不是把历史全部视为一个不可解释集合。

### 4.5 Object 是实际进入数据湖的对象

Object 指网页响应、文件、数据库记录、对话、代码 Blob、标注结果或生成输出。它关联 Source 与 Capture，拥有原始定位、内容哈希、媒体类型、时间和 Policy Snapshot。

Policy Snapshot 很重要：训练需要知道对象进入时依据和当前状态。当前 Policy 收紧时，系统通过 Source/Agreement 关系找到历史对象并重新评估。

### 4.6 Source Family 与 Variant

同一组织可能提供网页、API、批量导出和商业数据包。可以用 Source Family 连接，Variant 分别记录获取与权利。不要因为品牌相同就合并 Policy；免费网页与付费 API 的合同可能不同。

### 4.7 Source Version

Source 的描述、联系人、Location 和 Policy 会变化。每次影响获取或用途的变化创建 Source Version，旧 Capture 继续引用旧版本；目录展示当前版本和历史。

### 4.8 Source Identity 的稳定规则

ID 不使用可变域名作为唯一部分。域名转让、镜像和品牌改名会破坏身份。可以使用组织命名空间随机 UUID，并把域名、证书、账户、合同 ID 和其他身份作为证据属性。

### 4.9 Source Relationship

来源之间存在 Mirror、Fork、Syndication、Derived、Purchased-from、Generated-by、Successor 和 Replaces。关系帮助去重、许可传播和供应集中分析。

十个域名转载同一上游，不应在 Portfolio 中被误认为十个独立来源。关系带证据与置信度，自动推断和人工确认分开。

### 4.10 Policy Snapshot 与当前 Policy

历史证据解释取得过程，当前决策决定是否继续消费。

Capture 保存当时决策，当前 Policy 决定能否继续使用。历史允许不代表永久允许，当前禁止也不能抹去曾经发生的训练事实。目录同时提供 `policy_at_capture`、`current_policy` 和 `reevaluation_status`。

## 5. 来源战略怎样从模型目标反推

### 5.1 先定义能力缺口

来源选择应从目标模型与评测切片出发。若需要代码调试能力，需求不只是更多代码 Token，还包括错误代码、测试、日志、修复过程和版本环境；若需要长上下文，需求包含长文结构、跨段依赖和目标信息位置；若需要 Agent，需求包含环境、工具结果和状态转移。

### 5.2 建立需求向量

可以把来源需求表示为语言、领域、能力、难度、时间、格式和反馈类型向量。每一维定义当前覆盖、目标区间和证据。需求不是采购数量清单，而是可验证缺口。

### 5.3 通用锚点与目标增强

只收集目标域会造成能力变窄和遗忘。Source Portfolio 应同时包含通用锚点、目标增强、稀缺长尾和安全/反例。每类来源设置作用和最大暴露，而不是全部按规模自然混合。

### 5.4 独特性优先于名义规模

候选来源与现有资产执行精确、近似、Span 和语义重叠。一个 TB 新数据若 95% 是已有镜像，独特 Train-ready Token 成本可能很高。Registry 保存重叠 Measurement，而不是只写供应商宣称规模。

### 5.5 来源组合要降低集中风险

若大多数关键能力依赖一个 Provider，价格、政策、访问或质量变化会中断训练。计算各域来源集中、上游传播和替代能力。多个域名若同属同一上游，不能当作分散。

### 5.6 新鲜度与历史深度

软件、法规和产品需要持续更新，数学和经典文献需要历史深度。Source Strategy 为不同类型定义 Capture 频率与时间窗口；不是所有来源都按日抓取，也不是只保留最新版本。

### 5.7 真实、人类与合成数据的组合

真实世界数据提供自然分布，人类标注提供目标信号，合成数据提高任务密度和可控性。三类来源有不同偏差和血缘。Teacher 输出不因为“合成”就没有来源；它依赖 Prompt、模型权重和种子。

### 5.8 预算应按独特可训练 Token 计算

来源成本包括获取、网络、存储、解析、OCR、去重、评分、人工、合规、撤回和训练处理。核心指标可以是每百万合格独特 Token 成本、每个能力覆盖单元成本和代理训练收益成本。

### 5.9 先做试采样再签长期依赖

候选来源先取得允许范围的小样本，验证解析、重叠、质量、Policy 和成本。试采样本身也需依据，不能以“仅评估”为由绕过限制。通过后再建立正式 Capture 与 SLA。

### 5.10 退出能力是来源战略的一部分

Onboarding 时就验证 Provider 能否接收退出请求、如何定位对象、是否有稳定 ID、组织能否清除缓存和派生。无法退出的来源会形成长期风险和技术债。

## 6. 不同来源类型需要哪些专门合同

### 6.1 公开网页

记录域名与身份、URL 范围、robots 快照、服务条款版本、抓取频率、User-Agent、速率、退出联系、内容权利不确定性和再评估。robots 是自动访问协议的一部分，不等于内容许可证或隐私同意。

### 6.2 公共数据集

记录数据集版本、数据卡、许可证、上游来源、已知撤回、文件哈希和再分发条件。聚合数据集的顶层许可证可能不能替代每个子来源证据，需要评估 Provenance 覆盖。

### 6.3 代码仓库

记录仓库、Commit、文件路径、许可证文件、子模块、Vendor 依赖、Fork 和生成文件。仓库级许可证可能不覆盖第三方目录；Commit 历史还可能包含已删除密钥和大文件。

### 6.4 论文与图书

区分元数据、摘要、正文、图表和补充材料的使用边界；记录版本、出版方、开放许可、作者稿与最终版。公开可下载不等于允许任意再分发。

### 6.5 企业内部文档

记录系统 Owner、访问分级、雇佣/客户关系、机密级别、保留、地域、用途批准和离职/合同退出。内部可访问不等于允许用于模型训练。

### 6.6 产品日志与用户反馈

记录数据主体、告知/同意或其他依据、产品用途、训练用途、敏感字段、脱敏、地域、年龄和删除 SLA。训练与产品运维是不同用途，需要明确 Policy。

### 6.7 人工标注

记录任务合同、标注规范、数据输入权利、标注者隐私、成果权属、质量、地域和再使用。外包标注平台还需要供应商与子处理方信息。

### 6.8 合成数据

记录 Prompt Source、Teacher Bundle、Tokenizer、推理服务、采样、工具、环境、验证器和人工修订。还要检查 Teacher 输出政策、输入内容权利和生成内容中的记忆风险。

### 6.9 第三方商业数据

记录合同版本、席位/计算限制、模型训练、衍生模型、评测、再分发、期限、审计、删除和终止后处理。采购订单不能替代数据用途条款。

### 6.10 在线环境与工具轨迹

记录环境 Owner、API 条款、工具输入输出、秘密、外部账户、执行地域和结果保留。Agent 轨迹可能把多个来源混入同一上下文，需要逐 Observation 保存来源关系。

## 7. 许可、条款、robots、隐私与组织政策怎样区分

### 7.1 许可证回答内容权利的一部分

许可证通常说明复制、修改、分发、商业使用、署名或相同方式共享等条件。不同许可证适用对象、版本和司法背景不同。Registry 保存原文或权威证据、标识、版本、适用范围和评审结论，不从简称猜测完整权利。

### 7.2 服务条款约束服务访问关系

平台服务条款可能规定自动访问、账户、API、内容使用、再分发和争议。即使单个内容有开放许可证，取得方式仍可能受服务条款影响；反之，允许 API 访问也不自动授予内容训练与再分发权利。

### 7.3 robots 描述自动抓取偏好

允许抓取与允许训练是不同判断，不能互相代替。

robots.txt 通常面向爬虫访问路径与 User-Agent，不是版权许可证，也不证明个人数据可以训练。采集系统保存请求时生效的 robots 快照和解析器版本，遵循组织 Policy；后续变化触发重新评估。

### 7.4 隐私依据关注个人数据处理

个人数据处理涉及告知、同意或其他依据、目的限制、数据最小化、保留、地域、主体权利和安全。内容公开不意味着个人合理预期与训练用途自动一致。Source Registry 需标识可能个人数据与隐私评审状态。

### 7.5 合同可以增加或限制默认权利

商业合同、数据共享协议、劳动/客户协议可能明确模型训练、衍生模型、期限和退出。合同证据受权限保护，目录可展示结构化结论与有效期，不向所有工程师开放全文。

### 7.6 组织 Policy 是最终执行入口

Policy 把法律、合同、安全、伦理、产品和风险偏好组合成工程决策。即使外部条件允许，组织仍可禁止某类用途；外部禁止则不能由内部 Policy 放宽。Policy 版本与审批者进入决策证据。

### 7.7 允许抓取不等于允许训练

获取、存储、分析、训练、评测、再分发、展示样本和发布衍生模型是不同 Action。Policy 矩阵逐项决定，不能只存一个 `allowed=true`。

### 7.8 商业使用与内部研究要分开

研究试验、内部生产、对外 API、模型权重发布和数据再分发可能有不同条件。训练 Run 声明 Purpose 与 Distribution Plan，Policy 根据 Source Agreement 编译允许集合。

### 7.9 衍生模型与衍生数据要区分

某些条款对修改数据、生成标注、模型输出或权重有不同要求。Registry 分别记录 Raw 再分发、派生数据、统计、Embedding、模型权重和服务输出，不能用一个“可衍生”字段覆盖。

### 7.10 署名义务需要可实现

若使用要求署名，组织需要保留作者、来源、许可证和展示方式，并判断模型发布如何满足。无法追踪 Attribution 的聚合数据不应因为“许可证看起来开放”自动进入发布配方。

### 7.11 相同方式共享与模型发布

ShareAlike 等条件如何适用于具体数据处理和发布，需要授权角色判断。工程系统只保存评审结论、适用 Artifact 类型和义务，不自行推导法律答案。

### 7.12 非商业限制

NonCommercial 不能用布尔值粗略映射“公司内部”。项目商业属性、资金、服务和分发需要评审。Policy 把批准用途精确列出，默认不把未知解释为允许。

### 7.13 禁止演绎或修改

NoDerivatives 等限制对清洗、格式转换、标注、混合和再分发的影响需要评审。Raw 归档、内部索引和训练不是自动等价动作。Registry 保存范围结论和证据。

### 7.14 多许可证与可选择许可证

同一内容可能提供多个许可选项，必须记录选择的具体版本和满足条件。依赖文件可能采用不同许可证，不能把仓库顶层选择传播给全部对象。
