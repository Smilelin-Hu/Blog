# Rollout 引擎、权重同步、重分片与资源放置

## 1. 本文要解决的工程问题

生成阶段需要 KV Cache，训练阶段需要参数、梯度和优化器；简单地把两者固定占满不同 GPU，会产生长时间空闲，强行共置又会触发反复装载与 OOM。

本文围绕一个可执行判断展开：怎样在共置与分离架构中完成权重同步、重分片和资源放置？读完应能给出自己的系统边界、输入输出、版本关系和验收证据，而不是只复述工具名称或公式。

## 2. 本文交付物与判定标准

本文的核心决定是：按阶段内存、通信拓扑和权重更新频率选择共置、分离或混合布局，并把权重同步与重分片纳入调度。

完成学习和实验后，应当交付一份最小可复现记录，至少包含输入快照、配置、代码版本、运行状态、原始输出和结论边界。验收证据是：布局报告计算占用、空闲、峰值显存、同步字节与阶段耗时；新权重在 Rollout 前通过版本校验。

围绕“Rollout 引擎、权重同步、重分片与资源放置”的验收不接受三类替代品：把模拟输出写成真实 GPU 结果；只展示成功样本而隐藏失败与 `SKIPPED`；只给总分，不保存能复算总分的对象级记录。

## 3. 前置知识与实验边界

“Rollout 引擎、权重同步、重分片与资源放置”的机制实验使用 Python 3.10 及以上版本和标准库，重点验证对象、算法或状态转换。真实硬件路径使用 PyTorch；检测不到 CUDA 时必须输出结构化 `SKIPPED`，不得静默改跑 CPU 后仍标成 GPU 实测。

容量模型用于排除不可能方案，最终吞吐和同步开销必须在目标 GPU 与互联上实测。

## 4. Rollout 语义与失败模式

### 4.1 输入与输出

输入不仅是 Prompt，还包含 policy_version、采样参数、最大 Token、工具 Schema、环境 ID、随机种子、截止时间和优先级。输出是带版本的序列、Token log-prob、终止原因、时延、资源与轨迹指针。任何缺少策略版本的 Rollout 都无法判断陈旧度，也无法精确重放。

### 4.2 与普通推理服务的差异

普通在线服务优化用户延迟和可用性，模型版本相对稳定；RL Rollout 允许批量离线、长序列与多候选，但权重频繁变化、需返回训练统计并与环境交互。服务不能只暴露文本 API，还要保证 Tokenization、采样概率、版本切换和取消语义适合训练。

### 4.3 Prefill 与 Decode

Prefill 处理 Prompt，可形成大矩阵乘；Decode 逐 Token，受 KV Cache 和调度影响。Agent 轨迹多次工具交互形成短 Prefill 与断续 Decode。容量模型要拆 Prompt Token、生成 Token、暂停时间和环境等待。仅用 tokens/s 均值无法解释 GPU 空闲与队列积压。

### 4.4 Continuous Batching

动态把新请求加入正在运行的 Batch，提高 Decode 利用率。训练数据要求每条序列的模型版本与采样语义稳定，因此切权重时不能让同一 Episode 跨版本生成而不标记。引擎需支持排空、版本命名空间或显式跨版本策略。

### 4.5 KV Cache

只计算权重无法判断长序列高并发是否可运行。

KV 占用随层数、头、精度和上下文增长，决定并发。Rollout 还可能保留多分支或工具暂停会话。引擎记录每请求 KV Token、块、抢占、重算和前缀命中。权重切换后旧 KV 通常不能与新权重混用，必须排空或绑定版本。

### 4.6 Token log-prob

PPO、GRPO、重要性修正和诊断常需行为策略 log-prob。引擎返回与实际采样分布一致的 Token 概率，包含温度、top-k、top-p 和约束解码后的归一语义。若只返回原始模型 logit 而采样经过截断，行为概率会错。Mask、EOS 和精度要对拍。

### 4.7 取消与超时

训练控制器可能在任务已满足、环境失败、版本过旧或预算耗尽时取消生成。引擎要幂等取消，释放 KV 并返回部分轨迹与原因。取消 Token 是否进入训练由算法定义。静默丢请求会让队列账本和采样分布不一致。

### 4.8 确定性与重放

固定随机种子、模型、引擎、并行和采样配置仍可能受 Kernel 与批调度影响。系统定义重放等级：逐 Token 一致、分布一致或结果一致。关键调试可使用确定性路径，生产吞吐路径记录所有条件。不能承诺不存在的逐位复现。

## 5. 数据面与控制面

### 5.1 数据面

承载 Prompt、Token、KV、权重块、轨迹、log-prob 和验证结果，追求吞吐与低开销。大对象尽量点对点或共享存储，消息队列传引用与摘要。每个对象内容寻址并带租约，避免控制消息承载 GB 级权重。

### 5.2 控制面

负责策略版本、角色注册、资源租约、同步状态、路由、健康、背压、回滚和终止。控制面可以知道某个 Worker“已下载”，但只有数据面加载并完成 Canary 后才标记“可服务”。状态机不能用一个布尔 ready 简化所有阶段。

### 5.3 版本状态机

任务要记录实际行为版本，不能直接拷贝期望值。

策略版本经历 created、materialized、distributed、loaded、validated、serving、draining、retired 与 failed。每个状态有幂等转换、超时和证据。控制器只路由到 validated 版本，失败版本不能自动覆盖稳定指针。回滚重用已验证旧版本。

### 5.4 请求账本

每个 request_id 关联任务、目标策略版本、实际版本、种子、Worker、开始结束、Token 和结果。至少一次队列会重复，写入按 ID 幂等。账本用于守恒核对：提交、完成、取消、作废和待定之和一致。

### 5.5 Worker 注册

Worker 上报 GPU、内存、拓扑、引擎版本、并行布局、已加载策略和健康。注册有租约与心跳，过期后停止新路由。不能只看进程活着；固定 Canary 验证 Tokenization、log-prob 和生成语义。

### 5.6 背压

当验证、环境或训练消费慢于生成，队列增长会增加数据陈旧和存储。按版本、任务和年龄限制入队，动态降低候选 $N$ 或暂停 Rollout。背压传播到任务生产者，不以无限磁盘掩盖失衡。

### 5.7 多租户

租户有 GPU、Token、队列、权重和成本配额，策略与数据命名空间隔离。公平调度考虑长序列和工具等待，不能只按请求数。高风险任务路由到专用环境和模型。资源借用可抢占但保留最小保障。

### 5.8 可观测性

统一 trace_id 贯穿任务、Rollout、环境、验证和训练消费。指标按 policy_version、Worker、任务、长度和终止原因切片。日志正文受控，面板使用摘要。一次奖励异常能追到实际权重 hash 与 Token 概率。

## 6. 权重同步与版本加载

### 6.1 版本身份

一个策略版本由训练 Run、global_step、参数摘要、Tokenizer、模板、Adapter、精度和配置共同定义。只用 Step 号会在重跑或分支时碰撞。发布 ID 不可变，latest 只是可移动别名且不进入轨迹真值字段。

### 6.2 全量检查点

训练器将所有参数物化为推理可读格式，写临时位置，逐分片校验后原子发布 manifest。优点简单可恢复，缺点写盘、网络和加载成本高。同步周期短时可能还没加载完下一版已产生，必须合并或跳过中间版本。

### 6.3 增量与 Adapter

LoRA 只传小 Adapter 可大幅减流量，前提是推理基座完全一致。增量差分需要父版本、应用顺序和数值校验，链过长会增加恢复风险。周期生成完整基线，增量版本不能脱离父 hash 加载。合并前后固定 logit 对拍。

### 6.4 内存直传

共置或高速互联可从训练参数直接复制到推理 Worker，绕过对象存储。必须协调训练写与推理读，使用版本缓冲而非原地修改正在服务的权重。传输完成后计算摘要和 Canary，再原子切路由。快路径不能降低一致性。

### 6.5 双缓冲

Worker 保留 serving 和 loading 两套权重，新版本后台加载并验证，切换指针后旧版本排空。内存需求接近双份，显存不足可用主机内存、分层加载或停止世界。容量模型必须包含切换峰值，不只稳态模型大小。

### 6.6 Stop-the-world

暂停新请求、排空旧请求、卸载旧权重、加载新权重再恢复。实现简单且版本纯净，产生停顿和 GPU 空闲。适合小集群、长同步周期或内存不足。停顿进入训练墙钟与成本，不能从吞吐报表删除。

### 6.7 一致性级别

强一致要求一批轨迹都来自指定版本；最终一致允许 Worker 逐步切换，但每条轨迹标实际版本；Episode 一致要求多轮同一版本。算法对陈旧敏感时用更强协议。平台不能在不告知训练器的情况下选择便宜级别。

### 6.8 Canary 加载

新权重先在一个 Worker 加载，固定输入对比预期 logit、Token、log-prob、EOS 和延迟。通过后分批扩散。Canary 失败保留旧服务并标记版本 failed。验证样本覆盖短长、特殊 Token 和 Adapter，不只检查能生成文字。

## 7. 重分片

逻辑参数身份不变，物理分片与路由需要转换。

### 7.1 为什么需要重分片

训练可能使用 FSDP、ZeRO 或 Tensor/Pipeline 并行，参数按优化器需求分布；推理可能用另一 Tensor Parallel 度数、量化和布局。权重同步不是复制同名文件，而是把全局张量从训练分片映射到推理分片，并保持 Tie、转置、Padding 和量化语义。

### 7.2 全局参数视图

为每个参数定义全局 shape、dtype、逻辑轴、训练分片规则与推理布局。重分片计划从元数据生成，不能根据文件名猜。每个输出块记录来源区间与摘要。小模型先物化全量作为 Oracle，对分布式输出逐元素或统计对拍。

### 7.3 Tensor Parallel 转换

列并行权重沿输出维切，行并行沿输入维切，Attention 的 QKV 与 GQA 头布局还可能交错。TP 度改变需 all-gather 旧块、重排再 split 新块。偏置、归一化和词表通常有不同规则。错误轴可让 shape 合法但行为完全错误，必须 logit 对拍。

### 7.4 Pipeline Parallel 转换

PP 改变层到 Rank 映射，参数内容不变但目标 Worker 不同。非均匀层、Embedding、输出头和共享权重需特殊处理。计划先构建层归属，再调度传输，避免所有 Rank 同时汇聚到单节点。目标阶段加载完成后独立校验层清单。

### 7.5 FSDP 与 ZeRO

扁平参数可能把多个逻辑张量拼接，并含 Padding。恢复元数据用于解平坦，不能按模型 state_dict 顺序猜。ZeRO 优化器分片与推理权重不同，通常只需参数。保存时保留参数名、范围、原 shape 和版本，升级框架要桥接。

### 7.6 词表与 Embedding

词表 Padding、Tie 权重和 Tokenizer 扩展容易出错。重分片后确认实际 vocab_size、特殊 Token 行、输入输出 Tie 与 Padding 行。固定 Token 做 Embedding 与最终 logit 对拍。只比较张量均值无法发现行错位。

### 7.7 量化

可以先聚合高精度再按推理分片量化，语义清晰、传输大；也可在训练侧分块量化后传输，需保证量化组与目标分片边界一致。Scale、zero point、group size 和 Kernel 布局属于版本。量化后测 logit、排序、生成和奖励翻转。

### 7.8 流水化重分片

不必等整个检查点物化：参数块从训练 Rank 读取、转换、传输、目标写入并校验，形成流水。峰值内存受窗口控制。失败按块幂等重试，版本只有全部块和 Canary 完成才可服务。中间块不能被其他版本混用。

### 7.9 拓扑感知

尽量在 NVLink 或同节点聚合，再跨节点发送，避免同一参数多次穿越慢链路。计划结合训练和推理 Rank 物理位置，测实际带宽而非标称。控制流量优先级，权重传输不能拖垮训练 collective 和环境网络。

### 7.10 校验

结构校验参数集合、shape、dtype、分片覆盖无重叠缺口；数值校验摘要、抽样元素、范数与全量小模型；行为校验固定 logit 与生成。三层都通过才发布。摘要一致证明字节一致，不证明 Tokenizer 和推理 Kernel 语义一致。

## 8. 资源放置

只有完全卸载非活动角色时，共置峰值才近似两阶段最大值。

### 8.1 分离放置

可运行计划仍需用有效吞吐和质量比较。

Trainer、Rollout、Reward 与 Reference 使用独立 GPU，易隔离和并行，资源需求高。适合大集群和各角色长期忙碌。权重同步跨池，需高带宽与版本协议。利用率按角色监控，某池瓶颈时其他池可能空闲。

### 8.2 共置放置

同一 GPU 在训练和 Rollout 阶段切换，减少 GPU 总数和权重传输，阶段间有卸载、缓存与停顿。适合小规模或交替算法。必须控制显存峰值，确保旧 KV、优化器和推理权重不会同时驻留超限。阶段时间比例决定利用率。

### 8.3 混合放置

部分训练 GPU 在 Rollout 阶段复用，另有常驻推理池吸收连续任务；Reward 可与 Reference 共置或独立。混合提高弹性，也让调度和版本更复杂。用时间线和资源账本模拟，不凭静态 GPU 数量选方案。

### 8.4 角色资源画像

Trainer 需要参数、梯度、优化器和高带宽 collective；Rollout 需要权重、KV 和动态 Batch；Reward 多为 Prefill 评分；环境偏 CPU 与隔离。分别测计算、显存、网络、磁盘和延迟。资源请求基于高分位与切换峰值。

### 8.5 拓扑

TP 通信频繁，应优先同高速域；PP 可跨较慢链路但受激活传输；权重同步是大吞吐突发；环境调用是小消息长延迟。调度器使用 GPU 型号、互联、NUMA 和网络标签。错误放置可能比少一张 GPU 更伤吞吐。

### 8.6 弹性

Rollout 可按队列与版本扩缩，Trainer 通常拓扑固定。新 Worker 加载权重与 Canary 有冷启动，扩容决策要提前。缩容先排空 Episode 和 KV，不能丢部分轨迹。资源变化写入 Run 事件并影响容量指标。

### 8.7 抢占

低优先级 Rollout 可被抢占，保存部分轨迹或取消原因；训练 collective 中途抢占恢复成本高。抢占策略按角色设计。高风险环境和不可逆工具任务不随意中断。被抢占 Episode 不自动算失败。

### 8.8 成本归属

GPU 小时按角色、策略版本、任务和租户归属，权重同步、空闲排空与失败也计入。每条有效轨迹成本包含生成、环境、验证和陈旧淘汰。只看 Trainer MFU 会把 Rollout 浪费隐藏到系统外。

## 9. 容量模型：有效样本固定时的各阶段计算预算

容量模型可以从负载侧补一笔账：生成样本数与进入更新的样本数是两回事。保留 $n_{\mathrm{keep}}$ 条、平均保留比例 $a$，需生成 $n_{\mathrm{generate}}\approx n_{\mathrm{keep}}/a$：留 16 条、比例一半要生成 32 条，降到四分之一要 64 条——**生成与评分处理全部回答，更新只处理保留样本**，保留率下降增加前两段工作而不扩大更新 batch。筛选规则也要看信号：组内相对优势下，同组回答奖励全同则减均值后优势全零、策略梯度为零——生成评分更新都跑了却没学到东西，只有奖励差异提供非零优势；损失若要对全 batch 有效 token 求平均，累计 micro-batch 梯度时分母要用全 batch 有效 token 总数，先各 micro-batch 取均值再平均会让短 micro-batch 的 token 权重偏大。

固定目标算例（Qwen3-8B，八题各四份回答，P=1024、G=256，保留 16 条，参考模型同构、无教师）：rollout prefill 32 条 465.143 TFLOPs、decode 255 步/条 129.056、参考模型对 32 份各一次教师强制前向 634.944、策略更新 16 条一次遍历 952.416，合计 2181.559 TFLOPs。一般式

$$
F_{\mathrm{cycle}}(n)=n(f_g+f_r)+F_u,
$$

保留率从 1/2 降到 1/4、仍要 16 条则生成 64 条：生成与参考计算翻倍、更新不变，总量增到 3410.701 TFLOPs（+56.3%），每保留样本分摊从 136.347 增到 213.169——**增量全部来自额外回答的生成与评分**。运算量相加后仍要分阶段记矩阵形状：decode 逐 token 小 batch 受带宽限制，评分与训练能教师强制一次处理多个已知 token，工具验证还要 CPU 与沙箱，分别估耗时再按生成→反馈→更新→同步排依赖（OPD 多教师蒸馏则把教师前向加进反馈段）。权重同步：$r$ 个生成副本各收完整权重则传输 $rM_W$，Qwen3-8B BF16 四副本约 65.526 GB，优化器状态留学习器、副本只需前向权重，广播/分层分发可共用路径减重复发送（共享出口的下界见主题四 13 篇第 6 节，策略版本与异步周期见主题一 23 篇第 4 节）。
