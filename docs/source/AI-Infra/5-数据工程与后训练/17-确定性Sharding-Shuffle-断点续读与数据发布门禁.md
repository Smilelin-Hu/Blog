# 确定性 Sharding、Shuffle、断点续读与数据发布门禁

## 1. 本文要解决的工程问题

训练中断后 DataLoader 从文件开头继续，虽然随机种子相同，Worker 数和预取队列已改变，导致样本重复或遗漏。

本文围绕一个可执行判断展开：怎样让 Sharding、Shuffle、断点续读和发布门禁在恢复后保持等价？读完应能给出自己的系统边界、输入输出、版本关系和验收证据，而不是只复述工具名称或公式。

![确定性数据流与恢复语义](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y5_l17_01.png)

## 2. 本文交付物与判定标准

本文的核心决定是：用稳定样本 ID、确定性 Shard/Shuffle、消费游标和发布 Manifest 定义恢复语义，并区分逐位一致与统计等价。

完成学习和实验后，应当交付一份最小可复现记录，至少包含输入快照、配置、代码版本、运行状态、原始输出和结论边界。验收证据是：不中断运行与中断恢复运行能够比较完整样本序列、重复量、遗漏量和分片校验和。

围绕“确定性 Sharding、Shuffle、断点续读与数据发布门禁”的验收不接受三类替代品：把模拟输出写成真实 GPU 结果；只展示成功样本而隐藏失败与 `SKIPPED`；只给总分，不保存能复算总分的对象级记录。

## 3. 前置知识与实验边界

“确定性 Sharding、Shuffle、断点续读与数据发布门禁”的机制实验使用 Python 3.10 及以上版本和标准库，重点验证对象、算法或状态转换。真实硬件路径使用 PyTorch；检测不到 CUDA 时必须输出结构化 `SKIPPED`，不得静默改跑 CPU 后仍标成 GPU 实测。

本地恢复验证只覆盖指定并发和运行时；世界大小或数据框架变化后需要重新验收。

### 3.1 业务背景与失败模式

模型参数、优化器和学习率都能正确恢复，训练仍可能因为数据流从头开始、换了分片、Shuffle 缓冲丢失或 Worker 数变化而偏离。大规模训练里，“数据集相同”并不意味着“样本序列相同”；“样本数相同”也不意味着没有重复或遗漏。若没有明确交付语义，训练故障恢复会把不一致藏在正常 Loss 噪声里。

本文把数据流视为一台可检查点化的确定性状态机。输入是不可变 Manifest、逻辑样本 ID、配方与随机规范；输出是一系列全局逻辑批次。Sharding 决定对象归属，Shuffle 决定顺序，Worker 与 Rank 只执行已定义的逻辑工作，Checkpoint 保存足以恢复的位置与未决状态，发布门禁证明清单、预算、治理、格式、吞吐和恢复全部合格。

这里的“确定性”不是承诺不同 GPU 和浮点内核产生逐位相同参数，而是对相同数据规范，能重建训练读取的逻辑样本与 Token 序列；对于允许弹性世界大小的系统，则能按照声明的至少一次、至多一次或恰好一次语义解释重复与遗漏。没有这个边界，成本、能力、删除与事故复盘都缺少事实基础。

### 3.2 记录身份

记录 ID 代表语义来源对象，如文档、会话或代码文件。它跨物理移动稳定，用于血缘、去重和退出。记录版本标识内容变化，内容摘要验证字节或规范化产物。

### 3.3 逻辑样本身份

样本 ID 代表训练构造，如文档窗口、对话模板或长上下文组合。它引用一个或多个记录及 Token 区间。构造规则、Tokenizer 或 Mask 变化会产生新样本 ID，即使原文不变。

### 3.4 物理分片身份

Shard ID 代表存储与传输单元，包含多个逻辑样本。重打包可改变 Shard 而不改变样本；退出一条记录可能重建受影响 Shard。训练顺序不应永久依赖对象路径或 Tar 成员自然顺序。

### 3.5 逻辑批次身份

全局批次 ID 代表一次应被优化器提交的数据集合。它与物理 Rank、Attempt 和 Step 分开：失败重试仍是同一逻辑批次，新采样才是新 ID。账本用它判断重复与确认。

### 3.6 小文件问题

海量小对象增加元数据请求、网络往返与文件句柄，训练器很难获得顺序吞吐。将样本打包成较大 Shard 可以顺序读取、缓存和校验，也适合对象存储范围读取。

### 3.7 Shard 不是随机桶

物理分片要平衡大小、样本数、Token、长度、领域、治理域和增量重编译。只按文件数会让长文 Shard 过大；只追求字节相等可能使某 Shard 全是一个来源；全局最优装箱又会让一次删除重写大量对象。

### 3.8 目标大小

Shard 过小带来请求与索引开销，过大则缓存粒度、故障重试和删除放大严重。通过对象存储吞吐、网络延迟、Worker 数和平均样本大小 Profile 选择区间，不存在通用唯一值。发布门禁设置最小、目标和最大，而不是每片必须精确相同。

### 3.9 稳定分区

不能使用跨进程不稳定的默认哈希充当发布协议。

先以稳定样本 ID 哈希分到较多逻辑分区，再在分区内按目标大小生成物理 Shard。新增或删除主要影响一个分区，减少全局重排。哈希函数、种子、分区数和规范输入属于版本。

### 3.10 治理隔离

不同租户、地域、权利或敏感级别通常不能共享 Shard，否则删除、访问和跨区复制困难。安全边界优先于装箱利用，物理隔离在 Manifest 中显式。

## 4. Shard Manifest

### 4.1 根 Manifest

根对象记录数据产品 ID、版本、父版本、Tokenizer、样本构造、配方、Shard 列表摘要、总记录、总样本、总 Token、状态和签名。训练只引用不可变版本，不解析 `latest` 目录。

### 4.2 Shard 条目

每条含 Shard ID、URI、内容摘要、字节、样本数、Token、索引 URI、治理域、统计和成员清单摘要。URI 是位置，ID 与摘要是身份；复制到新区域不改变内容身份。

### 4.3 样本索引

索引将样本 ID 映射到 Shard 内 Offset、长度、Token、记录父节点和编译摘要。流式全读可以不用随机访问，但删除、抽查、恢复和故障定位需要索引。索引自身有摘要并与 Shard 原子发布。

### 4.4 Merkle 或分层摘要

百万 Shard 的根清单可用分层 Manifest 和摘要树。根摘要验证子清单集合，单个 Shard 可局部替换并生成新根。实现明确叶排序和规范序列化，否则相同集合会因顺序得到不同根。

## 5. 确定性 Shard 编译

### 5.1 输入先冻结

候选样本清单、状态与统计固定后才能分片。边编译边接收新样本会让 Shard 边界依赖任务完成时序。增量数据进入下一发布版本。

### 5.2 规范排序

按稳定分区、样本 ID 和明确 Tie-break 排序，不依赖数据库返回、文件系统或并发 Worker 顺序。排序键进入编译版本。若需要预 Shuffle，应生成单独索引，不破坏成员身份排序。

### 5.3 流式写与原子提交

写入临时内容寻址对象，边写边计算摘要、计数和索引；完成后验证，再将对象加入候选 Manifest。最终根指针原子提交。半成 Shard 永远不出现在已发布清单。

### 5.4 可重入与幂等

任务 ID 由输入分区和编译版本派生。重复执行相同任务产生同摘要，已存在对象可校验复用。失败重试不追加到旧 Shard，也不覆盖不同内容。

### 5.5 增量发布

新版本复用未受影响 Shard，只重编译变化分区。根 Manifest 显示新增、删除、复用与替换 Token。复用不等于继承资格：治理状态仍在发布时重新验证。

## 6. Shuffle 的不同层次

### 6.1 Shard 级 Shuffle

改变 Shard 读取顺序，成本低、适合对象存储，但 Shard 内部局部相关仍存在。若 Shard 按来源或长度分组，仅 Shard 乱序不足以消除长连续同类样本。

### 6.2 样本级全局 Shuffle

为所有样本生成随机排序键，理论混合好，可离线构建 Shuffle 索引。代价是索引、随机读取和缓存局部性。大规模训练常在 Shard 级与缓冲级之间折衷。

### 6.3 缓冲 Shuffle

流式读取时维护大小 $B$ 的缓冲，新样本进入后随机弹出。它只在局部窗口近似随机，缓冲越大混合越好、内存和恢复状态越大。缓冲内容、RNG 和输入游标都是检查点。

### 6.4 分层 Shuffle

先打乱 Shard，再在 Shard 内按离线索引或局部缓冲打乱，最后批次调度。每层随机种子和顺序独立派生，避免 Worker 数变化改变全局随机流。

### 6.5 Epoch 与无限流

有限无放回遍历可定义 Epoch：每个样本一次；上采样与多域流通常使用循环或放回，不再有统一自然 Epoch。此时用全局有效 Token 和逻辑批次推进，`epoch` 只是日志窗口，不能暗示无重复覆盖。

### 6.6 Resampling 不是 Shuffle

放回重采样 Shard 可以均衡无限流，但天然会重复并遗漏某些对象。它满足概率分布，不满足每 Epoch 恰好一次。接口与监控必须区分，不能用总样本数相同证明完整覆盖。

## 7. 随机规范

### 7.1 主种子不够

保存一个整数却更改库、算法、Worker 和并行度，序列仍不同。随机规范包含 PRNG 算法、版本、域分隔、种子派生、Shuffle 层、缓冲、世界大小策略和测试向量。

### 7.2 域分隔

从主种子和明确标签派生 Shard Shuffle、域选择、样本 Shuffle、窗口裁剪与增强种子，避免一个组件多消费随机数后改变其他组件。派生可用稳定哈希，而非 Python 进程随机哈希。

### 7.3 按对象派生

随机裁剪或增强使用样本 ID 与轮次派生种子，不依赖 Worker 执行顺序。这样换 Worker 数仍能对同一逻辑样本得到相同变换。

### 7.4 测试向量

发布随机规范时保存前若干 Shard 顺序、样本选择和对象裁剪结果。实现升级必须复现或明确创建新版本，避免“同 Seed”产生不同轨迹。

## 8. Rank、Worker 与数据归属

拓扑变化后要重新分配未消费集合，不能简单复制旧游标。

### 8.1 物理 Rank 不是永久身份

Rank 由本次作业拓扑决定。若用 `hash(sample_id) % world_size` 分配，世界大小变化会重排几乎全部样本。可以禁止世界大小改变，或使用稳定逻辑分区再将分区动态映射到 Rank。

### 8.2 Worker 再分片

DataLoader Worker 需要在 Rank 已分配集合内继续不重叠划分。框架常同时自动分 Rank 与 Worker，手工再切一次会漏样本；两层都不切则重复。启动时用黄金 Manifest 验证归属并集与交集。

### 8.3 模型并行副本

Tensor、Pipeline 或 Context 并行 Rank 属于同一数据并行副本，通常应看到同一逻辑批次或由一个 Rank 广播。数据状态按纯 Data Parallel Rank 保存，不能把所有全局 Rank 当独立数据消费者。

### 8.4 全局批次计划

协调器可生成全局逻辑批次，再分发给 DP 副本。这样领域、长度和 Token 预算全局可控，恢复也按批次 ID。代价是控制面和计划存储，需要避免单点瓶颈。

### 8.5 去中心化计划

每个 DP Rank 从相同随机规范和自己的逻辑分区独立生成，可扩展但对世界大小和恢复更敏感。只在数学和实现都能证明不重不漏时使用。

## 9. 断点续读到底保存什么

预取进度与完成更新的进度必须分开。

### 9.1 不可变输入身份

数据产品、根 Manifest、配方、Tokenizer 和读取器摘要必须与检查点一致。若恢复时 `latest` 已指向新版本，系统应失败而非自动升级。

### 9.2 Shard 与样本游标

保存当前 Shard 顺序位置、Shard 内样本或字节 Offset、当前循环轮次。若使用索引，可直接定位；流式压缩格式可能只能重开并跳过，恢复成本需计量。

### 9.3 Shuffle 缓冲

保存缓冲中每个样本的恢复键、顺序和 RNG，或保存足够早的周期快照并确定性重放到当前位置。只保存缓冲大小不够。

### 9.4 Packing 与组批状态

在线 Packing 等待池、长度桶队列、尚未完成的微批和领域债务都会影响下一批。它们必须保存或能确定性重放。

### 9.5 随机状态

保存各层 PRNG 状态或可推导逻辑计数。Python、NumPy、PyTorch CPU 与 CUDA 随机是不同状态；数据流最好使用独立 PRNG，避免模型随机消费影响数据。

### 9.6 已确认与未决批次

数据发出不等于优化提交。检查点要有最后已确认全局批次和未决集合。恢复选择重放未决或回滚模型到此前一致点，不能让加载器独自前进。

### 9.7 过滤与异常状态

若恢复依赖重放，样本编码和过滤必须确定。上游规则变化导致某样本这次被跳过，会使计数错位。恢复读取旧容器与规则，或保存完整恢复键而非只按“跳过 N 个”定位。

## 10. 三种交付语义

重复计算可以接受，重复学习是否允许必须由合同定义。

### 10.1 至多一次

样本发出后立即标记消费，失败可能丢失，但不重复。适合某些低价值流，不适合严格训练预算，因为故障会系统缺数据。

### 10.2 至少一次

只有优化确认后提交游标，失败重放未决批次，可能重复。实现相对稳健，但账本必须能量化重复，模型效果和 Token 预算承认实际值。

### 10.3 恰好一次的工程含义

真正端到端恰好一次需要模型参数、优化器、数据游标与账本在同一一致性点提交。分布式存储中很昂贵。常见做法是检查点事务加确定性重放，在已保存边界提供等价恰好一次；边界之间故障则回滚模型和数据一起重放。

### 10.4 不要混用口号

若恢复后可能重复几个微批，就不是无限精度恰好一次，但可以声明“检查点边界一致、区间回放”。语义用状态机与故障测试定义，而不是文档写一个词。
