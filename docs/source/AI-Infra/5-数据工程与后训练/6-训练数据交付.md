# 训练数据交付：Sharding、断点续读与 SFT 协议

数据在「训得动」之前要先「发得出去」：分片可校验、顺序可复现、中断能续、门禁能拦。这一篇把这些交付层的东西讲清，再看 CPT 与 SFT 的数据设计。

## 1. Shard 设计：四个目标互相拉扯

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y5_l17_01.png" width="78%" alt="确定性 Sharding" />
  <p>图 1：物理分片要同时平衡大小、样本、Token、领域与治理域</p>
</div>

物理分片不是「随机切成 N 份」。要同时平衡：

- **大小与字节**：只按文件数会让长文 Shard 过大；
- **样本数与 Token**：只追字节相等可能让某个 Shard 全是一个来源；
- **领域与长度**：影响混洗质量与 batch 内浪费；
- **治理域**：租户、地域、权利、敏感级别通常**不能共享 Shard**，否则删除、访问与跨区复制都变难——**安全边界优先于装箱利用**；
- **增量重编译**：全局最优装箱会让一次删除重写大量对象。

**目标大小没有通用唯一值**：过小带来请求与索引开销，过大让缓存粒度、故障重试与删除放大变严重。发布门禁应设「最小 / 目标 / 最大」区间，而不是要求每片精确相同。

## 2. 稳定分区：两层哈希

```text
样本 ID → 稳定哈希 → 逻辑分区（较多） → 分区内按目标大小生成物理 Shard
```

好处是新增/删除只影响一个分区，避免全局重排。三条纪律：

1. **不能用跨进程不稳定的默认哈希**当发布协议；
2. 哈希函数、种子、分区数、规范输入都属于**版本**；
3. 排序键也要进版本：按稳定分区 + 样本 ID + 明确 tie-break，**不依赖数据库返回顺序、文件系统顺序或并发 Worker 到达顺序**。

## 3. Manifest 的三层

| 层 | 内容 |
|---|---|
| 根 Manifest | 数据产品 ID、版本、父版本、Tokenizer、样本构造、配方、Shard 列表摘要、总记录/样本/Token、状态、签名 |
| Shard 条目 | Shard ID、URI、内容摘要、字节、样本数、Token、索引 URI、治理域、统计、成员清单摘要 |
| 样本索引 | `sample_id → Shard + offset + 长度 + Token + 父节点 + 编译摘要` |

两条铁律：**URI 是位置，ID 与摘要才是身份**（复制到新区域不改变身份）；**训练只引用不可变版本，不解析 `latest` 目录**。

百万 Shard 可用分层 Manifest + 摘要树（Merkle），根摘要验证子清单集合；但**必须明确叶排序与规范序列化**，否则相同集合会因顺序不同得到不同根。

## 4. 确定性编译的五步

1. **输入先冻结**：候选清单、状态、统计固定后才分片。边编译边收新样本，会让 Shard 边界依赖任务完成时序；增量数据进下一版本；
2. **规范排序**：见上；
3. **流式写 + 原子提交**：写临时内容寻址对象，边写边算摘要/计数/索引；完成后验证，再进候选 Manifest，根指针原子提交。**半成 Shard 永不出现在已发布清单**；
4. **可重入与幂等**：任务 ID 由「输入分区 + 编译版本」派生；重复执行产生同摘要，已存在对象可校验复用；失败重试不追加、不覆盖；
5. **增量发布**：新版本复用未受影响 Shard，只重编译变化分区；根 Manifest 展示新增/删除/复用/替换的 Token 数。**复用不等于继承资格**——治理状态仍要在发布时重新验证。

## 5. Shuffle 的五个层次

| 层 | 做法 | 边界 |
|---|---|---|
| Shard 级 | 打乱读取顺序 | 成本低，但 Shard 内局部相关仍在 |
| 样本级全局 | 给所有样本随机排序键 | 混合最好，代价是索引、随机读与缓存局部性 |
| 缓冲（buffer） | 流式维护大小 \(B\) 的缓冲，随机弹出 | 只在局部窗口近似随机；**缓冲内容、RNG、游标都是检查点** |
| 分层 | Shard 打乱 → Shard 内打乱 → 批次调度 | 每层种子独立派生，避免 Worker 数变化改变全局随机流 |
| Epoch | 有限无放回遍历 | 上采样/多域流通常是循环或放回，不再有「自然 Epoch」 |

两个容易混的概念：

- **Resampling ≠ Shuffle**：放回重采样能均衡无限流，但天然重复并可能遗漏某些对象——它满足概率分布，**不满足「每 Epoch 恰好一次」**；
- **`epoch` 只是日志窗口**：无限流下它不代表完整覆盖，监控要按全局有效 Token 与逻辑批次推进。

## 6. 随机规范：一个种子不够

保存一个整数却换了库、算法、Worker 数或并行度，序列仍会不同。完整的随机规范包含：PRNG 算法与版本、域分隔、种子派生、Shuffle 层、缓冲、世界大小策略、**测试向量**。

三条实践：

1. **域分隔**：从主种子 + 明确标签派生「Shard 洗牌 / 域选择 / 样本洗牌 / 窗口裁剪 / 增强」的种子，避免一个组件多消费随机数影响其他组件；
2. **按对象派生**：裁剪与增强用「样本 ID + 轮次」派生，不依赖 Worker 执行顺序——换卡数也能得到相同变换；
3. **测试向量**：发布随机规范时保存前若干 Shard 顺序、样本选择与裁剪结果；实现升级必须复现，否则就是新版本。

## 7. 断点续读的最小检查点

- 当前 Shard 与游标（offset / record index）；
- **缓冲 Shuffle 的缓冲内容**；
- **RNG 状态**（含域分隔后的子种子）；
- 已消费的有效 Token 计数（用于预算与配比对账）；
- 数据版本（Manifest 摘要）与 Reader Plan 版本。

只存「第几个 batch」是不够的：Packing 或 buffer 一变，恢复后消费序列就与原来不同。

## 8. CPT 与 Mid-training：介于预训练和 SFT 之间

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y5_l18_01.png" width="78%" alt="CPT 与 Mid-training" />
  <p>图 3：持续预训练补能力，mid-training 补分布与长上下文，SFT 补行为</p>
</div>

| 阶段 | 目标 | 数据特征 | 主要风险 |
|---|---|---|---|
| 预训练 | 通用能力 | 海量、广覆盖 | 成本 |
| CPT | 领域/语言/代码增量 | 领域集中、质量高 | **灾难性遗忘**、过拟合小语料 |
| Mid-training | 分布与上下文形态 | 长文档、指令化前的高质量语料 | 与后续 SFT 重复、格式提前污染 |
| SFT | 行为与格式 | 指令-回答、多轮、工具 | 模板不一致、监督错位 |

CPT 的四条纪律：

1. **保留通用回放**：CPT 数据里混入一定比例通用语料，评估通用能力是否回退；
2. **评估要双向**：领域能力提升 + 通用能力不退化，两个方向的指标都要报；
3. **学习率与步数保守**：小语料上大 LR + 多 epoch 最容易过拟合；
4. **数据要清洗到位**：CPT 通常不做过强过滤，但重复、模板、PII 仍要处理。

## 9. SFT 的数据协议

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y5_l19_01.png" width="78%" alt="SFT Schema" />
  <p>图 4：从原始字段到规范 Sample，再到模板渲染与 Token 级 Mask</p>
</div>

### 9.1 五种原始形式 → 一个规范 Sample

原始数据常见：单字段 `text`、`prompt/completion`、`instruction/input/output`、OpenAI `messages`、`conversations`、`chosen/rejected`、工具调用、图片+文本、自定义字段。

不要写一堆 if-else 支持所有形态，**先转换到规范 Sample**，最小字段：

```text
sample_id / Source 与父 Document / Messages / 目标 Turn
工具定义 / 附件引用 / 质量与能力标签 / Schema Version
```

原始字段留在血缘层，不必全进训练 Shard。**规范化不是把所有任务压成一段 Text**——那会丢角色与边界。

### 9.2 Message 中间表示

一条 Message 至少：`role`、`content`、稳定 `message_id`。Content 可以是文本，也可以是类型化 Parts：Text / Image Reference / Audio / Tool Call / Tool Result / Structured Object。

Tool Call 应含**调用 ID + 工具名 + 参数对象**，Tool Result 引用调用 ID——这样才能验证「每个结果有对应调用、顺序正确、并发不串线」。只存渲染后的 JSON 字符串，分不清原始参数与转义问题。

规范层还要标 `supervision`：`target` / `context` / `ignore`（可带权重）。它表达**策划意图**，最终 Token Mask 由模板与 Tokenizer 解释——**两层分开，才能发现「策划说监督，但截断后没有目标」**。

### 9.3 监督哪些 Turn

- `all_assistant`：监督所有 Assistant 内容；
- `last_assistant`：只监督最后一轮，前面作为上下文。

两种都不能靠「找最后一个 Assistant 标记」隐式决定，要写进 Schema 或 Recipe。多轮数据里若前面回答质量低，全监督会传播错误；只监督最后一轮又浪费高质量历史答案。

角色控制 Token（`<|assistant|>`、结束符）是否监督要单独决定，边界测试必须**逐 Token 展示**。

### 9.4 Chat Template 是协议，不是展示层

它决定角色 Header、分隔、BOS/EOS、换行、工具声明与 Generation Prompt。**训练与推理模板不一致会造成分布偏移**——训练用一种 Token 序列写 Assistant Header，服务端用另一种，模型的遵循与停止表现会退化。

模板版本应绑定：模板文本摘要 + Tokenizer 版本 + 特殊 Token 映射 + 渲染库版本。**只记模型名不够**，同一权重可被不同模板包装。

`add_generation_prompt` 的坑：

- 训练样本已含目标 Assistant Message → 通常**不再**添加空的 Generation Prompt，否则出现重复 Header；
- Prompt-only 在线生成 → 应启用；
- 测试三种结尾：最后是 User / Assistant / Tool Result，逐一核对渲染末尾与推理服务一致。

### 9.5 BOS、EOS 与 Padding

- 重复 BOS：模板显式写了 BOS，Tokenizer 又自动加；
- 缺少 EOS：模型学不到「何时停」；
- 把 EOS 当 Padding：**Attention Mask 与 Label 必须让填充位置的 EOS 不贡献 Loss**——真实结尾 EOS 要监督，填充 EOS 要忽略，两者 Token ID 相同，语义由 Mask 区分。

检查要看**最终 ID 序列**，不是可读字符串。

### 9.6 特殊 Token 的原子性

模板里写着 `<|assistant|>`，不代表 Tokenizer 把它编码成**一个** Special Token。没注册就会被拆成多个普通 Token，边界定位直接失效。

验证四件事：词表中 Token ID、`all_special_tokens`、Encode 长度、Skip Special Tokens 解码。新增特殊 Token 后要**扩 Embedding 并训练对应行**，不能只改 Tokenizer 文件。

### 9.7 Tokenizer 边界合并

对 BPE/SentencePiece：

$$
\mathrm{encode}(\text{prompt}) + \mathrm{encode}(\text{answer}) \ne \mathrm{encode}(\text{prompt} + \text{answer})
$$

前导空格、换行、相邻字符都会影响子词合并。**正确做法是对完整渲染文本一次 Tokenize，再用 Offset Mapping 或模板给出的 Mask 定位 Assistant 跨度。**

若用 Sentinel 标记定位，必须证明：Sentinel 不出现在用户内容、不被模板转义、编码序列唯一。对抗样本要包含**伪造角色标记**，防止用户文本改变监督边界。

### 9.8 Loss Mask 是数据资产

Loss Mask 由「监督意图 + 模板 + Tokenizer + 截断 + Packing」共同决定，应保存在 Train-ready Sequence 中或可确定重建，并带版本。

质量报告至少给：有效目标 Token 数、比例、按角色/任务分布、**零目标样本**、仅 EOS 样本、截断损失、每样本监督 Turn 数。平均比例正常仍可能掩盖某个切片全零。

训练 Run 要记**有效 Token**，而不是只报 Input Token——全序列与 Assistant-only 用同样名义 batch，梯度信号量完全不同。

### 9.9 Label Shift 的经典错误

Causal LM 通常在 Forward 内部把 Labels 左移一位（位置 \(t\) 的 logits 预测 \(t+1\)）。若预处理**提前左移**，模型再移一次，就变成预测两步之后的 Token。

另一个错误是 Mask 打在**输入位置**而不是**目标位置**：Assistant 第一个 Token 由前一个 Header 位置的 logits 预测，所以 Label 数组中该 Token 所在位置应有效。用一个 5 Token 的手算例子最容易验证。

Padding 方向也影响位置：左 Padding 常用于生成，训练可能右 Padding，Position IDs 与 Attention Mask 处理不当会改变相对位置。

### 9.10 截断不是简单切片

- 取前 \(L\) 个：可能保留全部 Prompt、删除答案 → **零监督样本**；
- 取后 \(L\) 个：可能丢失 System 与任务定义；
- 中间截断：可能切断工具 JSON 或角色 Header。

策略按类型设计：单轮 SFT 预留最小 Completion 预算；多轮删最早完整 Turn、保留 System 与最后目标；工具轨迹按 Step 边界；长文问答保留问题与相关证据。

**任何截断都要记录**原始 Token、保留 Token、删除的角色与目标、是否切断结构；截断后重新验证至少一个目标 Token、结束符、工具配对与模板合法。

Answer 截断更危险：硬切后追加 EOS，等于教模型在半个 JSON 或半句处结束。统计 Answer 截断率、受影响能力与长度分位——大量截断说明数据与上下文预算不匹配。

## 写在最后

交付层的所有细节都指向一件事：**训练读到的字节、顺序与 Mask 必须能被证明。** 证明不了，实验就不可比。
