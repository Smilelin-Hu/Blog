# WARC、HTML、PDF、代码与对话数据解析

## 1. 本文要解决的工程问题

同一篇文章在 WARC、HTML 和 PDF 中各有一份，解析器却只输出正文字符串。页码、DOM 路径、响应头和失败原因消失后，后续清洗无法复核。

本文围绕一个可执行判断展开：怎样把 WARC、HTML、PDF、代码和对话解析成保留证据的统一记录？读完应能给出自己的系统边界、输入输出、版本关系和验收证据，而不是只复述工具名称或公式。

## 2. 本文交付物与判定标准

本文的核心决定是：为 WARC、HTML、PDF、代码和对话分别保留可回指证据，再归一到统一 Document Schema，而不是强迫所有来源共享同一种解析过程。

完成学习和实验后，应当交付一份最小可复现记录，至少包含输入快照、配置、代码版本、运行状态、原始输出和结论边界。验收证据是：抽样记录能返回原始字节位置；解析失败有结构化状态；不同解析器版本可以对同一固定集做差异比较。

围绕“WARC、HTML、PDF、代码与对话数据解析”的验收不接受三类替代品：把模拟输出写成真实 GPU 结果；只展示成功样本而隐藏失败与 `SKIPPED`；只给总分，不保存能复算总分的对象级记录。

## 3. 前置知识与实验边界

“WARC、HTML、PDF、代码与对话数据解析”的机制实验使用 Python 3.10 及以上版本和标准库，重点验证对象、算法或状态转换。真实硬件路径使用 PyTorch；检测不到 CUDA 时必须输出结构化 `SKIPPED`，不得静默改跑 CPU 后仍标成 GPU 实测。

解析成功只表示结构可用，不表示内容已满足质量、版权或训练价值门槛。

### 3.1 业务背景与失败模式

数据采集解决的是字节如何到达对象存储，解析解决的则是这些字节如何被解释成可验证、可定位、可复现的内容单元。网页抓取结果可能带有 HTTP 响应头、重定向链、压缩传输和错误编码；HTML 同时包含正文、导航、脚本、评论、隐藏区域与结构信息；PDF 保存的是页面绘制指令而不一定是自然阅读顺序；代码仓库包含语言、依赖、提交历史、生成文件与许可证边界；对话记录还包含角色、轮次、工具调用、附件和状态转换。把它们统一调用一个 `extract_text()`，往往会把最重要的工程语义抹掉。

训练系统关心的不是“抽出了多少字符”，而是抽出的每个片段能否回答：来自哪个不可变原始对象，由哪个解析器版本产生，对应原对象的哪个位置，结构和顺序是否可信，失败或降级发生在哪里，是否携带来源与用途约束，以及能否在解析器升级后比较变化。若这些问题无法回答，下游去重、质量评分、隐私清洗、样本构造和训练回归都只能在不可解释的文本堆上工作。

解析也是一条安全边界。文档格式可能包含压缩炸弹、递归容器、超大页面、恶意字体、脚本、外部引用与解析器漏洞。生产系统不能让一个损坏文件拖垮整个分区，更不能把不可信内容交给具有网络、凭据和写权限的进程。正确的解析平台必须同时处理内容保真、吞吐、资源隔离、确定性、可观测性与故障证据。

本文把 WARC、HTML、PDF、代码和对话放在同一套抽象中讲解。目标不是记住五套库的调用方式，而是建立一个“原始字节—容器记录—结构节点—内容单元—训练文档”的分层模型，并用统一契约连接不同解析器。完成后应能设计一个不会因格式变化、库升级或坏样本而失控的数据解析流水线。

### 3.2 学习目标与能力清单

### 2.1 能力目标

第一，理解 WARC 记录、HTTP 消息和网页内容之间的层级，正确处理 response、request、revisit、metadata 与 conversion 等记录类型。第二，理解 HTML 解析、DOM 构建、正文抽取和语义分块是不同阶段，能够保留标题、列表、代码、链接和节点路径。第三，理解 PDF 字符定位、阅读顺序、字体映射、扫描页 OCR 和版面分区的困难，避免把页内绘制顺序误当成自然语言顺序。

第四，能把代码仓库解析为文件、语法树、符号、注释、依赖和提交上下文，同时识别生成物、二进制、大文件和秘密。第五，能把对话解析为带角色、轮次、工具调用、状态与附件关系的事件序列，而不是用换行符拼接。第六，能定义跨格式的中间表示、错误分类、质量指标、资源预算和版本发布门禁。

### 2.2 工程验收

一个合格解析任务必须固定输入 Manifest、解析 Recipe、容器镜像与依赖版本；每个输入对象产生成功、部分成功、隔离或失败状态；每个输出 Content Unit 带原始对象 ID、位置、解析器和内容摘要；相同输入与 Recipe 重复执行时，结果集合和顺序在约定范围内一致；坏文件不会导致整个 Worker 或分区无界消耗；解析升级能够生成对象级和切片级差异报告。

真实硬件实验以至少一张可用 CUDA GPU 为目标：CPU 进程完成格式解析，GPU 进程消费固定解析 Manifest 做轻量编码与吞吐验证。若环境没有可用 CUDA 设备，程序必须输出结构化 `skipped`，不得把 CPU 结果冒充 CUDA 单卡实测。本文不会虚构任何吞吐、显存或准确率数字，所有数字由读者在自己的机器上运行后产生。

### 2.3 不在本文展开的内容

本文不把网页采集合规判断替换成解析规则，来源与用途决定属于前一篇的 Source Registry；不深入讲语言识别、规范化、质量过滤与去重，它们在后续篇目分别展开；不把 OCR 模型训练、视觉语言模型训练和分布式数据框架调优作为中心。解析器只负责在明确资源与安全边界内，把原始对象变成带证据的结构化资产。

### 3.3 实验准备与责任边界

### 3.1 Raw Object 层

Raw Object 是采集后不可变的字节对象，至少包含对象 ID、内容哈希、长度、媒体类型声明、取得时间、Source ID 和存储位置。这里的媒体类型只是主张，不能完全信任扩展名或 HTTP 头。解析前可以用魔数、容器结构和安全扫描生成 Detected Format，但不要覆盖原声明。保留两者能发现上游配置错误和伪装文件。

原始对象是重放锚点。任何解析结果都必须能回到它，任何退出或安全事件也从它向下游传播。为节省空间而只保存抽取文本，会失去修复解析错误的机会；但原始对象的保留期限与权限应由来源 Policy 决定，不能因为技术便利永久保存。

### 3.2 Container Record 层

WARC、ZIP、TAR、邮件包、代码仓库和对话导出都可能在一个对象中承载多个记录。Container Record 描述容器内的逻辑成员，包括类型、偏移、长度、校验和、父记录与成员路径。解析器先验证边界，再把成员交给格式专用阶段。这样一个成员失败时无需把整个容器标成不可用，也能防止路径穿越、递归解压和成员数量爆炸。

WARC 记录尤其需要区分记录头、HTTP 负载和实体正文。一个 WARC response 记录的 Content-Length 是 WARC 记录内容块长度，不等于 HTTP 实体长度；HTTP 还可能有 transfer/content encoding。revisit 记录可能没有完整负载，而是引用先前记录。若在容器层直接搜 HTML 标签，偏移和血缘会立即混乱。

### 3.3 Structural Node 层

Structural Node 是格式解析器识别的结构：HTML DOM 节点、PDF 页面/文本框/行/字形、代码语法树节点、对话消息/工具调用。节点带类型、父子关系、源位置和解析置信度。结构层应尽量保真，不急于决定哪些内容用于训练，因为后续不同 Recipe 可能需要不同视图。

结构节点不一定一一对应源字节区间。HTML 解析器会修复不合法标记，DOM 可能包含浏览器规则生成的结构；PDF 文字可能由多个绘制操作合成；OCR 文本由图像区域推断；语法树可能包含错误恢复节点。因此位置要允许字节偏移、页码坐标、行列范围、时间区间和“无精确映射”等不同表示，并记录产生方式。

### 3.4 Content Unit 层

Content Unit 是下游可独立选择、过滤、去重和退出的最小内容单元。网页可按标题、段落、列表项、代码块、表格单元或评论分区；PDF 可按标题、段落、列表、公式说明或页面区域；代码可按文件、符号、注释、函数与测试；对话可按消息、回合、轨迹和工具 Observation。每个 Unit 包含规范化前原文、结构类型、顺序键、语言候选、位置、父节点、链接和质量信号。

单元不能过小。逐字符或逐 DOM 文本节点会让上下文丢失、对象数量爆炸；也不能过大。整本 PDF 或整个仓库成为一个字符串会使去重、隐私删除和训练分块无法定位。合适粒度由下游用途决定，因此平台可以保存细粒度结构节点，并用版本化 Assembler 生成不同 Content Unit 视图。

### 3.5 Training Document 层

Training Document 是为清洗、采样和样本构造准备的逻辑文档。它由一个或多个 Content Unit 按明确顺序组成，包含标题、正文、代码、角色等类型化字段，以及完整血缘。此层仍不是最终 Token 样本；后续可以规范化、过滤、去重、Packing。训练文档 ID 应由来源对象、Recipe 和逻辑路径稳定派生，不能用处理时间或随机 UUID，否则重跑无法对齐差异。

五层模型的关键价值是把“保存事实”与“选择视图”分开。Raw 与 Structure 尽量记录发生了什么，Content Unit 和 Training Document 说明当前 Recipe 选择了什么。更换正文抽取算法时，可以复用同一 Raw Object 并产生新视图，而不是假装来源数据发生了变化。

## 4. 解析契约与中间表示

输出文本应能回到原始容器位置，不能只留清洗后字符串。

### 4.1 输入契约

解析任务不接收“某个目录”，而接收不可变 Manifest。每一行明确 object_id、content_hash、byte_length、declared_media_type、source_id、capture_id 和 location。Worker 读取前验证哈希或使用对象存储的可信校验字段，读取后记录实际字节数。Manifest 摘要进入 Job ID，确保失败重试和结果对账针对同一集合。

输入契约还包含 Budget：最大对象字节、最大解压比、最大成员数、最大页面数、最大 DOM 节点、最大代码文件数、单对象 CPU 时间和内存。不同 Source/Format 可有不同预算，但所有预算都必须有限。超过预算是 `resource_limit` 状态，不是普通解析失败，更不能无限重试。

### 4.2 输出契约

推荐把输出拆成 Document、Unit、Edge、Diagnostic 和 Metric 五类记录。Document 描述逻辑文档及状态；Unit 保存内容与结构；Edge 保存父子、引用、回复、定义—使用和原始—派生关系；Diagnostic 保存错误阶段、错误码、库版本、截断与降级；Metric 保存数量、字节、字符、节点、耗时与资源峰值。

输出记录都包含 recipe_id、parser_name、parser_version、schema_version 和 created_at，但稳定内容 ID 不能依赖 created_at。文本摘要在明确编码后的 Unicode 字节上计算，结构摘要则对排序后的规范 JSON 计算。浮点坐标需规定舍入，集合需规定排序，避免同一 PDF 因字典顺序或线程完成顺序产生不同 ID。

### 4.3 状态模型

`success` 表示所有强制阶段完成且未触发截断；`partial` 表示仍有可用输出，但存在明确的页、成员、节点或字段失败；`quarantined` 表示安全、资源或策略风险阻止内容进入普通候选区；`failed` 表示没有满足最小契约的输出；`skipped` 表示环境或 Recipe 明确不处理该类型。状态必须配机器可聚合的 reason_code，不能只存异常字符串。

部分成功非常重要。一本一千页的 PDF 只有一页字体损坏，不一定要丢掉其余内容；一个仓库有一个二进制文件，不等于代码解析失败；一段对话有未知工具结果，可以保留其他消息。但部分输出进入训练前需要 Policy 决定可接受哪些 Diagnostic，不能由解析 Worker 自行隐瞒。

### 4.4 Schema 演进

中间表示采用向后兼容字段扩展、显式 Schema 版本和迁移测试。删除、改名或改变字段语义需要新主版本。消费者声明支持范围，未知主版本安全失败。不要让不同格式各自产生完全不同 JSON，公共字段统一，格式专用信息放在受版本控制的 `attributes` 命名空间中。

解析器升级不原地覆盖结果。新 Recipe 写入新前缀，通过差异与质量门禁后再发布视图指针。旧结果按保留策略存在，训练 Run 仍可重放。若升级修复安全漏洞，旧视图可被撤销，但审计关系仍保留。

## 5. WARC：先理解记录语义，再谈网页正文

### 5.1 WARC 的作用

WARC 是一种把多个记录串接到归档文件中的格式，可以保存协议负载、请求、响应、元数据、转换结果和重复检测事件。工程上应把 WARC 看作“带关系的记录日志”，而不是“装了很多网页的压缩包”。标准支持记录完整性、压缩和记录间引用，这些能力恰好适合大规模网页采集的重放与审计。

常见 `WARC-Type` 包括 `warcinfo`、`response`、`request`、`resource`、`metadata`、`revisit`、`conversion` 和 `continuation`。训练正文通常主要来自 response/resource，但 request 对重放和访问上下文很重要，metadata 包含分类与采集信息，revisit 则表示重复负载引用。只处理 response 并丢弃关系，会在去重、重定向、错误页判断和退出定位时失去证据。

### 5.2 记录边界

解析 WARC 首先读取版本行和 WARC 头，严格按 `Content-Length` 定位内容块，然后验证记录分隔。不能通过搜索下一个 `WARC/1.1` 字符串切分，因为该字节序列可能出现在负载内。头字段大小、单行长度和总字段数都需上限，重复字段与不合法换行要记录 Diagnostic。

压缩 WARC 常见逐记录 gzip 成员，这使随机定位和并行切分更容易，但实现不能假设所有 `.warc.gz` 都严格逐记录压缩。索引通常保存压缩偏移、压缩长度、目标 URI、日期、记录 ID 和摘要。Worker 读取一个范围后仍要验证 WARC 记录头与校验，防止索引漂移或对象被替换。

### 5.3 WARC 头与 HTTP 头是两层

各层有独立长度与编码，截断错误要定位到对应层。

WARC 头描述归档记录，HTTP 头描述被采集的协议消息。`WARC-Target-URI` 是目标标识，HTTP 响应中的最终内容类型、内容编码、状态码和重定向位置属于负载。二者不一致时都保留，并由规则判断。比如 WARC 记录声明 `application/http; msgtype=response`，真正的 HTML 类型在 HTTP `Content-Type` 中。

HTTP 解析要处理状态行、重复头、折叠历史格式、chunked transfer encoding、gzip/br 内容编码与字符集声明。采集系统可能已解码传输分块却保留头，也可能保存原始字节；Recipe 必须基于具体采集器契约，不能盲目二次解码。每一步记录输入/输出长度与摘要，遇到不一致置为 partial 或 quarantined。

### 5.4 Revisit 记录

revisit 用于记录重复检测事件，常通过 `WARC-Refers-To` 或目标 URI/日期引用已有记录。它可能包含 HTTP 头但省略实体正文。解析平台需要先构建记录 ID 索引，再解析引用；若引用跨 WARC 文件，索引必须覆盖 Capture 集合。找不到基记录时输出 `unresolved_revisit`，不能生成空网页假装成功。

同一负载在不同时间访问可能有不同 HTTP 状态、响应头和来源上下文。复用实体字节不等于复用整个 Document。正确结果是新 Capture Record 引用旧 Payload Object，并保留当前访问元数据；下游可选择按内容去重，但时间与 URL 血缘不丢失。

### 5.5 重定向、错误页与非 HTML 响应

去导航不能连同代码、列表或关键上下文一起删除。

三百状态响应通常没有目标正文，但重定向边可连接 URL 规范化和抓取链。四百、五百状态页面有可读文本，却多数不是目标内容；解析器可以抽取以供采集质量分析，训练视图默认排除或单独分类。两百状态也可能是软 404、验证码、同意页或机器人挑战，需要内容分类而非只看状态码。

WARC 里还会有 PDF、图片、JSON、音视频和任意二进制。路由器依据魔数、HTTP 类型和内容探测选择解析器，不应把所有 response 送进 HTML 库。探测冲突进入 Diagnostic，恶意伪装文件走沙箱。

### 5.6 WARC 切分与并行

大文件不能按任意字节平均切片，否则 Worker 会从记录中间开始。常见方法是预先构建 CDX 类索引，按记录压缩范围分配；或顺序扫描生成安全边界后形成 Shard Manifest。分片权重不只看压缩字节，还要估算解压大小、媒体类型和历史解析成本，避免一个包含巨型 PDF 的 Shard 拖慢全局。

输出顺序按输入对象 ID、WARC 记录偏移和 Unit 顺序稳定排序。Worker 可以乱序完成，但 Commit 阶段归并。每个 Shard 有输入记录数、各状态数和输出摘要；总账必须满足成功、部分、隔离、失败与跳过之和等于输入记录数。

## 6. HTML：DOM 正确不代表正文正确

### 6.1 字节到 Unicode

HTML 解析前必须决定编码。信号可能来自 HTTP `charset`、BOM、文档早期 meta、探测器和来源默认。优先级应接近浏览器规则，但数据流水线还要保存原始信号、最终选择与替换字符数量。用 UTF-8 强解所有网页会把大量非英语内容变成乱码，而完全信任 meta 也会被错误或恶意声明欺骗。

解码结果需要记录 replacement ratio、控制字符比例和往返可逆性。若多个候选接近，可保存候选与置信度并设 partial；后续语言识别能提供辅助，但不要形成循环覆盖。原始字节永远保留为事实，Unicode 文本是 Recipe 派生。

### 6.2 Tokenization 与 DOM 树构建

HTML 不是严格 XML。现实网页标签不闭合、嵌套错误、脚本包含特殊文本，标准解析器会按 HTML 规则修复并构造 DOM。正则删除标签无法正确处理这些情况，也会破坏 `script/style` 边界、实体解码和块级结构。生产系统应使用成熟 HTML 解析器，并固定库版本和配置。

DOM 是内存节点树，包含 Element、Text、Comment 等节点。浏览器执行 JavaScript 后得到的 DOM 可能与静态响应不同。大规模训练采集通常优先解析静态响应，以降低成本和攻击面；对确有价值的动态站点可在隔离浏览器中渲染，但必须把浏览器版本、脚本执行、网络请求、等待条件和最终 DOM 快照作为另一条 Recipe，不能与静态结果混为一谈。

### 6.3 Boilerplate 与正文抽取

网页正文抽取要区分导航、页眉页脚、推荐、广告、评论、表单和主要文章。常见特征包括文本密度、链接密度、标签类型、节点深度、标点、段落长度、视觉/类名提示和相邻节点。规则算法透明且便宜，模型算法对复杂布局更强但需要校准和版本管理。最佳工程实践通常是候选生成、规则硬排除、模型/评分排序与站点切片监控的组合。

正文不是永远只有一个区域。论坛有主题与回复，文档站有正文、导航目录和代码示例，电商页有规格、描述与评论。中间表示应保留区域类型，训练 Recipe 再选择。把评论拼到文章结尾会混淆作者与事实层级；把代码示例当普通段落会破坏缩进。

### 6.4 标题层级、列表与表格

纯文本抽取常丢掉标题层级和列表边界，导致训练模型无法学习文档组织。Unit 应保留 `heading_level`、列表有序性、列表项路径和定义关系。HTML 表格需要保留 caption、行列标题、rowspan/colspan 和单元格坐标；简单按行拼接会让跨列含义错位。复杂嵌套表格可降级为结构 JSON 或明确标记，不要生成看似自然但语义错误的句子。

隐藏文本要结合 HTML 属性、样式与渲染 Recipe 判断。静态解析无法完全计算 CSS，但可以识别 `hidden`、`aria-hidden`、常见 display 规则与无尺寸模板。无障碍文本、alt 和 screen-reader 内容不应一概删除，它们可能提供重要语义；同时也可能被 SEO 滥用，需要切片质量评估。
