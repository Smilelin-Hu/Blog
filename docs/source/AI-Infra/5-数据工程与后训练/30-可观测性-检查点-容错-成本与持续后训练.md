# 可观测性、检查点、容错、成本与持续后训练

## 1. 本文要解决的工程问题

一次持续后训练任务可以自动恢复，却无法回答恢复了哪些状态、丢了多少轨迹、花了多少有效 GPU 小时，也无法在奖励异常时回到一致版本。

本文围绕一个可执行判断展开：怎样用可观测性、联合 Checkpoint、故障演练和成本归因运营持续后训练系统？读完应能给出自己的系统边界、输入输出、版本关系和验收证据，而不是只复述工具名称或公式。

## 2. 本文交付物与判定标准

本文的核心决定是：建立跨数据、Rollout、Reward、Trainer 和发布面的可观测性、联合检查点、故障演练与单位有效更新成本。

完成学习和实验后，应当交付一份最小可复现记录，至少包含输入快照、配置、代码版本、运行状态、原始输出和结论边界。验收证据是：故障演练验证 RPO/RTO、幂等和语义连续性；成本报告区分原始 GPU 时间、空闲、重试与最终有效 Token。

围绕“可观测性、检查点、容错、成本与持续后训练”的验收不接受三类替代品：把模拟输出写成真实 GPU 结果；只展示成功样本而隐藏失败与 `SKIPPED`；只给总分，不保存能复算总分的对象级记录。

## 3. 前置知识与实验边界

“可观测性、检查点、容错、成本与持续后训练”的机制实验使用 Python 3.10 及以上版本和标准库，重点验证对象、算法或状态转换。真实硬件路径使用 PyTorch；检测不到 CUDA 时必须输出结构化 `SKIPPED`，不得静默改跑 CPU 后仍标成 GPU 实测。

本文提供可执行基线和生产配置入口，不承诺在未测试集群上的恢复时间或成本数字。

### 3.1 进程健康只能回答最表层问题

Kubernetes Pod Running、Ray Actor 心跳正常、GPU 利用率非零，只能说明计算进程仍存活。模型可能加载错版本，Response Mask 可能全零，Reward Worker 可能把异常当正确，Trainer 可能重复消费相同 Experience。这些语义错误不会自动让进程退出。

健康必须分层。基础设施健康关注节点、GPU、网络和存储；服务健康关注请求成功、延迟和队列；数据健康关注 Schema、Mask、组完整与版本；算法健康关注 Reward、KL、Entropy、Ratio、梯度和固定评测；治理健康关注来源、权限、安全和审计。上层异常可以在下层完全绿色时发生。

### 3.2 为什么平均 Reward 最容易误导

平均 Reward 上升可能来自模型能力，也可能来自采样器逐渐选择容易题、输出格式收敛、Judge 偏长、Parser 漏洞、超时样本被排除或 Reward Version 切换。聚合值没有条件分布与版本就不能解释。

任何训练曲线至少与 Prompt 域、难度、来源、响应长度、终止原因、Policy Version、Reward Version 和格式状态联动。固定锚点评测独立于训练采样，用同一版本与预算周期运行。训练 Reward 是优化信号，不是产品成绩。

### 3.3 为什么恢复能力也是健康的一部分

一个连续运行十天却从未验证恢复的系统，不算可靠。Checkpoint 可能缺优化器分片、Sampler 游标或控制账本；只有真正加载、重放并比较不变量才能确认。恢复演练和回放通过率应进入 SLO。

健康不是没有故障，而是故障被及时检测、影响被限制、状态能恢复、证据可追溯。系统设计从“如何避免所有失败”转为“每种失败发生时如何确定性处理”。

### 3.4 四个核心问题

第一，学习信号是否有效：Reward、优势、KL、Entropy、Clip、梯度和评测怎样变化。第二，数据是否可信：来源、版本、Mask、Group、污染、错误码和有效率。第三，系统是否稳定：队列、吞吐、利用率、延迟、故障和恢复。第四，成本是否值得：每个有效 Token、Experience、Checkpoint 与能力增量花费什么。

每个问题都需要指标、日志、Trace 与制品。指标发现异常，Trace 定位阶段，日志解释事件，制品和固定回放提供复核。只建设 Dashboard 而没有 ID 与 Manifest，发现异常后无法下钻。

### 3.5 五个观测平面

训练平面记录 Loss、Reward、Advantage、KL、Entropy、Ratio、Clip Fraction、梯度和参数；数据平面记录 Prompt、Response、Group、Mask、长度、状态和来源；系统平面记录 GPU、CPU、内存、网络、存储、队列和阶段时间；版本平面记录 Policy、Reference、Reward、Tokenizer、Template、Runtime 与 Environment；成本平面把资源和失败归属到 Run、项目、域与结果。

这些平面以共同身份连接：`run_id`、`iteration_id`、`group_id`、`experience_id`、`update_id`、`checkpoint_id` 与 `policy_version`。没有共同键，团队只能在多个看板靠时间猜测。

### 3.6 观测数据自身也需要质量

Metric 丢失、Clock 偏移、重复事件、字段语义变化和采样偏差会让看板误判。每个指标定义单位、分母、采集位置、版本与缺失处理。零值与未采集分开，`NaN` 不静默转零。

观测 Pipeline 监控自身延迟、丢弃、重复和 Schema。关键提交事件写持久账本，不能只依赖尽力而为的日志采集。高频性能指标允许抽样，Exactly-once 证据不允许抽样。

### 3.7 Reward 分布

同时记录总 Reward 与分量、均值、分位数、零分率、满分率和非有限数。对组算法记录 Zero-variance Group 比例与有效组率。按任务域和 Reward Version 分桶。

若均值上升但满分率不变，可能连续风格分量提高；若满分率上升同时格式拒绝下降，先区分格式与内容；若版本切换产生阶跃，运行固定回放迁移矩阵。单条曲线无法完成这些判断。

### 3.8 KL 与 Reference

KL 衡量 Policy 相对 Reference 的偏移，但估计方式不同数值不可直接比较。记录计算公式、Token Mask、Reduction、Reference Version 与分桶。响应长度增加可能改变 Token 平均与序列平均。

KL 突降可能是 Mask 缩短、Reference 加载错版或大量短响应；突升可能学习率、Reward 尺度、Policy Lag 或引擎 Logprob 偏差。与 Valid Response Tokens、Initial Ratio、长度和版本一起定位。

### 3.9 Entropy

Entropy 反映分布不确定性。过快下降可能策略塌缩、Reward 过强或采样过窄；上升可能优化不稳或任务变难。生成端采样参数也影响观测，训练 Logits Entropy 与实际采样 Entropy 区分。

全词表 Entropy 计算昂贵时可抽样 Batch 或记录 Top-k 近似，但定义清楚。只看采样响应多样性会混入 Prompt 变化。

### 3.10 Ratio 与 Clip Fraction

Ratio 是 Current 与 Old Policy 在行为 Token 上的概率比。更新前 Initial Ratio 应接近一；更新中分布逐渐扩散。Clip Fraction 过高说明大量 Token 进入截断区，可能更新过激或数据过旧。

按正负 Advantage 分开 Clip，按 Policy Lag 与响应位置分桶。序列尾部异常可能训练—推理数值累积；某 Worker 独有异常可能权重同步失败。均值会掩盖两端大偏差。

### 3.11 梯度与参数

记录全局 Norm、分层 Norm、非有限数、被 Clip 比例和 Optimizer Step 是否跳过。LoRA 训练确认只有 Adapter 参数变化；冻结层抽样哈希。MoE 还观察 Expert 负载和路由。

梯度为零可能 Zero-variance Reward、Mask 全零、参数未加入优化器或 Loss Detach；梯度巨大可能 Reward 尺度、长度 Reduction、混合精度和异常样本。指标要能下钻到 Batch ID。

## 4. 数据指标为什么决定曲线能否解释

### 4.1 输入组成

每轮记录数据域、来源、难度、Prompt 长度、任务类型和采样权重。Dynamic Sampler 同时记录期望概率与实际份额。若分布改变，评估聚合 Reward 前先做条件分析。

去污染、许可、隐私与安全状态进入数据版本。被撤回对象在训练队列和 Checkpoint 血缘中可定位。数据量指标区分原始、生成、通过门禁和最终提交。

### 4.2 Response 与终止

记录生成 Token、有效响应 Token、Padding、Stop Reason、Truncated、Tool Steps、Parser Status 和语言。平均长度之外看分布与极端值。强制截断和模型 EOS 分开。

长度是能力、成本和 Mask 的交点。平均 Reward 随长度上升时，做条件正确率与成本分析；不要直接加长度惩罚。超长失败可能模型策略，也可能 Runtime 上限。

### 4.3 Group 健康

记录计划组大小、完成、失败、重试、超时、混版本、Zero-variance 和完成时间。有效组成本为所有尝试生成 Token 除以最终进入训练的组数。

Group 完成率下降会让 Trainer 饥饿，即使 Rollout Token/s 很高。按 Worker、任务和环境分桶，定位是系统长尾还是任务难度。

### 4.4 Mask 与 Token 对齐

统计 Prompt Mask、Response Mask、Tool Observation Mask、有效 Token 比例和空 Mask。抽样渲染 Token、文本与 Mask。Template 或 Packing 变更后运行金色样本逐位比较。

Mask 错误通常不会使训练报错，却改变所有 KL、Loss 与成本分母，因此应作为发布门禁，而不是事故后临时检查。

## 5. 系统指标怎样连接到有效学习

### 5.1 队列不是越短越好

每个队列记录 Token、对象数、字节、Age 分位数、到达率、完成率和版本分布。空队列可能阶段平衡，也可能下游饥饿；深队列可能吸收突发，也可能持续过载。

队列指标与 Policy Lag、过期率和 GPU 空闲联动。生成队列增长但有效提交下降，说明更多计算没有转化为学习。

### 5.2 吞吐的分母

区分 Generated Token/s、Rewarded Token/s、Train-ready Token/s、Committed Token/s 与每 GPU Token/s。Prompt Token 与 Response Token 分开。端到端吞吐包含等待、同步、Checkpoint 和失败。

任何性能比较给相同模型、长度分布、组、Reward 和门禁。峰值阶段吞吐不能替代稳态有效吞吐。

### 5.3 资源与阶段时间

GPU 指标包括利用率、显存、功耗、温度、时钟、ECC 或 Xid；CPU 包括利用、内存、Page Fault 与负载；网络包括吞吐、重传和 Collective；存储包括带宽、IOPS、延迟与容量。

Trace 将 Rollout、Reward、Batch Build、Forward、Backward、Optimizer、Checkpoint 和 Publish 分段。GPU 低利用只有与等待原因对齐才可行动。

### 5.4 故障与重试

按稳定错误码统计 Worker Restart、Task Retry、OOM、Timeout、Artifact Missing、Version Reject、Duplicate、Late 与 Quarantine。失败率与浪费 Token、恢复时间关联。

只统计最终成功会隐藏重试风暴。每个成功 Experience 的 Attempt 数和总资源是成本的重要组成。

## 6. 版本指标为什么是持续后训练的一等公民

### 6.1 Active 与 Desired

每个 Worker 报告 Desired Policy、Active Policy、Bundle Hash、最后切换时间和错误。队列显示 Behavior Policy 分布，Trainer 显示 Current Policy。版本差与 Logprob Lag 同时观察。

Reward、Template、Tokenizer、Runtime 和 Environment 也有 Active/Desired。一次滚动升级允许受控窗口，多版本超出窗口报警。

### 6.2 Checkpoint 与发布版本

Checkpoint ID、Policy Version 和 Optimizer Step 关系明确。一个 Checkpoint 可能还未通过评测，不能成为 Production Approved；一个 Policy Bundle 可能用于 Rollout 但未发布给用户。状态分离为 Training、Candidate、Approved、Serving 与 Retired。

发布指针只引用完整并验证的制品。回滚创建新发布事件，不删除历史。

### 6.3 Reward Version 迁移

新旧 Reward 对固定回放集双跑，记录一致、上升、下降和无法评分。队列按版本分桶，切换策略明确 Drain、重评或隔离。

发现 Hacking 时，按版本与证据定位历史高分、受影响 Update 和 Checkpoint。版本指标让事件响应从猜测变为范围分析。

## 7. 成本指标为什么不能只看 GPU 小时

被拒绝和失败工作仍产生费用，不能从成本分子删掉。

### 7.1 端到端成本对象

成本包括 Rollout GPU、Trainer GPU、Reward Model 或 API、CPU 沙箱、存储、网络、Checkpoint、失败重试与人工评审。共同归属到 Run、项目、域、Policy Version 和结果状态。

GPU 小时高不一定低效，若长轨迹带来高价值；GPU 小时低也不一定好，若大量廉价错误数据污染训练。成本要与有效信号和评测连接。
