# 大模型数据与后训练基础设施全景

## 1. 本文要解决的工程问题

接手一个已经训练出多个检查点的团队。训练任务能跑，模型也能评测，但没人能从检查点反查语料版本，也没人说得清失败轨迹是怎样回到下一轮训练的。

本文围绕一个可执行判断展开：怎样把数据获取、治理、训练、评测与反馈组织成可追踪的工程系统？读完应能给出自己的系统边界、输入输出、版本关系和验收证据，而不是只复述工具名称或公式。

![数据与后训练基础设施全景](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y5_l01_01.png)

## 2. 本文交付物与判定标准

本文的核心决定是：建立一套贯穿 Source、Document、Sample、Sequence、Trajectory、Experience 与 Checkpoint 的对象合同，并把数据流、控制流和版本流放进同一张系统地图。

完成学习和实验后，应当交付一份最小可复现记录，至少包含输入快照、配置、代码版本、运行状态、原始输出和结论边界。验收证据是：任取一个检查点，可以正向追到训练输入，也可以反向追到原始来源、处理配方、Reward 与策略版本。

围绕“大模型数据与后训练基础设施全景”的验收不接受三类替代品：把模拟输出写成真实 GPU 结果；只展示成功样本而隐藏失败与 `SKIPPED`；只给总分，不保存能复算总分的对象级记录。

## 3. 前置知识与实验边界

“大模型数据与后训练基础设施全景”的机制实验使用 Python 3.10 及以上版本和标准库，重点验证对象、算法或状态转换。真实硬件路径使用 PyTorch；检测不到 CUDA 时必须输出结构化 `SKIPPED`，不得静默改跑 CPU 后仍标成 GPU 实测。

本文验证对象和血缘关系，不用单机模拟结果替代多节点吞吐或模型能力结论。

### 3.1 业务背景与失败模式

本文建立整个系列统一使用的数据与后训练系统地图。学习重点不是记住一串工具名称，而是理解一条数据从进入组织开始，如何经过解析、治理、清洗、筛选、去重、混合、分词、训练、采样、奖励、评测和回流，最终改变模型行为。后续篇目会分别深入每个环节，但所有环节都必须落回同一组数据对象、版本关系、质量证据和运行状态。

一个大模型项目如果只有训练代码，却无法回答“这个模型究竟使用了哪些数据、这些数据经历了什么处理、为什么保留这些样本、某条来源被撤回后会影响哪些检查点、某次能力提升来自哪一版配方”，它就还不具备工程意义上的数据基础设施。一个后训练项目如果只有 GRPO 或 DPO 的损失函数，却无法回答“轨迹由哪个策略版本生成、奖励由哪个 Verifier 计算、训练端看到的概率是否与生成端一致、失败样本如何回流”，它同样不是完整的后训练系统。

本文把两部分连接起来：前半部分关注“原始内容怎样成为可训练数据资产”，后半部分关注“模型交互怎样成为新的训练信号”。二者组成一个持续循环，而不是两条互不相干的流水线。

### 3.2 学习目标与能力清单

完成后应当能够：

1. 解释 Source、Document、Sample、Sequence、Batch、Trajectory 和 Experience 的区别。
2. 画出从原始数据到训练检查点，再到反馈回流的数据流、控制流与版本流。
3. 区分预训练、Continued Pretraining、Mid-training、SFT、偏好优化、Reward Modeling、RLHF、RLVR 和蒸馏的数据需求。
4. 为每个数据对象设计最小可追踪元数据，而不是只保存一个无法解释的 JSONL 文件。
5. 区分离线数据流水线与在线后训练流水线，并说明两者为何最终必须共享资产目录和质量门禁。
6. 解释数据质量、数据多样性、数据独特性、数据难度与数据时效性之间的冲突。
7. 设计一个可以恢复、回放、审计和删除传播的最小数据供应链。
8. 通过机制实验验证数据对象的转换与血缘记录，通过真实 GPU 实验观察数据效率如何影响有效 Token 吞吐。

### 3.3 实验准备与责任边界

学习本文只需要掌握 Python 基础、文件读写、JSON 和命令行。机制实验仅依赖 Python 标准库。真实硬件实验依赖 PyTorch；有 CUDA GPU 时运行 GPU 路径，没有 GPU 时脚本必须明确输出 `skipped`，不能静默退回 CPU 后仍把结果称为 GPU 实测。

本文不会重新讲解 CUDA Kernel、数据并行、张量并行或推理引擎内部实现。出现 GPU、训练进程和 Rollout 引擎，是为了说明数据对象如何在系统中流动，以及不同角色如何绑定版本。

## 4. 数据怎样从来源走到训练

### 4.1 为什么“数据”不是一个文件夹

在个人实验中，人们经常把下载到的文件放进 `data/`，写一个清洗脚本，再把结果保存为 `train.jsonl`。这种做法在一次性实验里可以工作，但它隐藏了至少十类重要信息：

- 原始内容从哪里来，什么时候取得，依据什么许可使用。
- 原始文件是否完整，是否发生过解析失败或编码损坏。
- 哪一版清洗规则处理了它。
- 哪些文档被删除，删除的具体原因是什么。
- 去重时哪些文档互为重复，最终保留了哪一个，为什么保留它。
- 数据属于什么语言、领域、难度和质量区间。
- 数据是否与验证集、测试集或安全红队集重叠。
- 分词器版本是什么，特殊 Token 和文档边界怎样处理。
- 训练时采用什么混合比例、采样顺序和随机种子。
- 哪个模型检查点实际消费了哪些 Shard，以及训练中断后从哪里恢复。

因此，工程里的“数据”至少包含三部分：内容本身、描述内容的元数据、描述处理过程和关系的血缘事件。只有内容而没有元数据，无法做筛选、审计和复现；只有内容与元数据而没有处理事件，无法解释当前版本是怎样产生的。

可以把一个数据资产写成：

$$A = (C, M, L, V)$$

其中：

- $C$ 是 Content，即文本、图片、音频、代码或交互轨迹等实际内容。
- $M$ 是 Metadata，包括来源、语言、领域、长度、许可、质量分和安全标签。
- $L$ 是 Lineage，记录输入、处理步骤、输出、运行和父子关系。
- $V$ 是 Version，标识这组内容、元数据和处理关系的不可变快照。

版本不是文件名末尾的 `final_v3_really_final`。一个有效版本需要稳定标识、内容校验和、父版本、生成配方、代码版本、参数和创建时间。只有这样，训练运行引用的才是确定对象。

### 4.2 七个核心数据对象

对象转换必须携带父对象身份，Batch 是一次消费而非新的来源。

### Source：来源

Source 描述数据为什么会进入系统。它可能是 Common Crawl 的某次抓取、某个公开代码仓库、企业内部工单系统、人工标注任务、Teacher 模型的合成输出或在线产品反馈。

Source 不等于 URL。URL 只是定位信息之一。Source 还应包含：

- 稳定的 `source_id`。
- 来源类型和所有者。
- 获取时间与时间窗口。
- 许可、使用范围和再分发条件。
- robots、opt-out 或合同约束。
- 保留期、删除联系人和撤回策略。
- 抓取或导出工具版本。
- 原始对象清单和校验和。

同一网页在不同月份被抓取，通常应当视为同一逻辑来源下的不同 Capture。把 Source 与 Capture 分开，可以同时表达“它们来自同一站点”和“内容发生过变化”。

### Document：文档

Document 是从原始对象解析出来、仍然保留自然边界的内容单元。网页正文、PDF 文章、代码文件、论坛主题和一段完整对话都可以成为 Document。

Document 应尽量保留回到原始内容的能力。例如网页 Document 需要记录原始 WARC 位置、URL、抓取时间和解析器版本；PDF Document 需要记录页码、文本块坐标和 OCR 状态；代码 Document 需要记录仓库、Commit、路径、语言和许可证文件关联。

文档层适合做来源治理、解析质量、文档级去重、语言识别和粗粒度质量判断。它不一定能直接用于训练，因为一个文档可能过长、包含多个任务、需要切段，或必须转换成对话结构。

### Sample：训练语义样本

Sample 是面向某种训练目标整理出的语义单元。它可能是：

- 一段预训练文本。
- 一个指令与答案。
- 一段多轮对话。
- 一个 `chosen/rejected` 偏好对。
- 一个问题与可验证答案。
- 一条带工具调用的 Agent 轨迹。

同一个 Document 可以派生多个 Sample。例如一篇技术文档可以产生连续预训练段落、问答 SFT 样本、术语解释样本和代码修复任务。Document 与 Sample 必须通过父子关系连接，避免派生后失去来源。

### Sequence：Token 序列

Sequence 是分词器处理后的模型输入单位。它包含 `input_ids`、`labels`、Attention Boundary、Position 信息、Loss Mask 和可能存在的多模态代用标记符。

Sample 与 Sequence 不是一一对应。一个长 Sample 可能被切成多个 Sequence；多个短 Sample 也可能被 Packing 到一个 Sequence。只记录 Sequence 而不记录 Sample 边界，会使训练者无法解释 Loss 来自哪些样本，也容易在 Packing 时产生跨样本注意力泄漏。

### Batch：一次计算消费的数据集合

Batch 是运行时概念。它受序列长度、显存、并行规模、梯度累积和动态批处理影响。相同 Sample 集合在不同硬件或并行策略下可能形成不同 Batch，但应保持统计意义上的采样一致性。

在后训练中，Batch 的定义更复杂。一个 Prompt 可以生成一组响应；GRPO 会按组计算相对优势；PPO 还会把一批 Rollout 切成多个 Mini-batch 并重复若干 Epoch。因此需要区分：

- Prompt Batch。
- Rollout Group。
- Experience Batch。
- Update Mini-batch。
- Global Update Batch。

如果日志里只写 `batch_size=64`，却不说明指的是哪一层，就无法比较实验。

### Trajectory：交互轨迹

Trajectory 描述策略与环境之间的一次完整交互。单轮问答的轨迹可能只有 Prompt 和 Response；工具 Agent 的轨迹会包含多次观察、动作、工具调用、工具结果和最终状态。

一个最小轨迹通常包含：

- 任务和初始状态。
- 策略版本。
- 每一步输入上下文。
- 动作或生成 Token。
- 工具调用与环境观察。
- 终止原因。
- 奖励及其分解。
- Verifier、Judge 或 Reward Model 版本。
- 生成时的 Logprob、采样参数和引擎信息。

轨迹是后训练数据基础设施的核心对象，因为它既可以转化为 SFT 数据，也可以形成偏好对、Reward Model 数据或在线 RL Experience。

### Experience：用于更新策略的训练经验

Experience 是从 Trajectory 计算出来、能够直接进入优化器的数据。它通常额外包含 Old Logprob、Reference Logprob、Reward、Return、Advantage、Mask、Policy Version 和有效 Token 范围。

Trajectory 是发生过什么，Experience 是这次经历如何被训练算法解释。相同轨迹在不同算法、Reward 配置或 Advantage 估计下，会产生不同 Experience。因此不能只保存处理后的 Advantage 而丢失原轨迹，也不能只保存轨迹却不记录生成 Experience 的算法版本。

### 4.3 从原始来源到可训练数据的离线链路

离线数据流水线通常按以下方向推进：

1. 注册来源与使用条件。
2. 获取原始对象并生成不可变清单。
3. 解析成 Document。
4. 做编码修复、正文抽取和结构规范化。
5. 统计语言、长度、领域和质量特征。
6. 执行规则过滤、模型过滤和安全处理。
7. 执行精确、模糊、段落、子串或语义去重。
8. 与评测集、安全集和保留集做去污染。
9. 按能力目标构建 Sample。
10. 设计 Mixture、采样权重和课程顺序。
11. 绑定 Tokenizer，构建 Sequence、Loss Mask 和 Packing。
12. 生成 Shard、索引、校验和、Dataset Card 和发布 Manifest。

这里的“离线”不代表只运行一次，而是指训练更新不与数据生成同步发生。数据可以每天新增，也可以持续重建，但每次发布给训练任务的版本应当是确定快照。

### Raw、Bronze、Silver、Gold 与 Train-ready

为了隔离不同处理责任，可以把数据分为若干层：

- Raw：原始字节或原始导出，不修改内容。
- Bronze：完成基本解析，保留尽可能多的原始结构和定位信息。
- Silver：完成清洗、语言识别、质量特征和基础治理。
- Gold：完成去重、去污染、能力标签、质量门禁，具备明确用途。
- Train-ready：绑定 Tokenizer、模板、Packing、Shard 和采样配方，可被具体训练框架直接消费。

这些名称不是强制标准，关键是层之间的责任不能混乱。尤其不要直接覆盖 Raw，也不要把 Tokenized 数据作为唯一保存版本。Tokenizer 会变化，训练目标也会变化；如果没有 Sample 层，就无法低成本重建新的 Sequence。

### 4.4 从模型交互到新训练信号的在线链路

后训练数据链路从 Prompt 或 Task 开始：

1. 从任务池选择 Prompt，并记录采样原因。
2. 把 Prompt 发送给某个 Policy Version。
3. Rollout 引擎生成一个或多个响应。
4. 环境执行工具调用并返回 Observation。
5. Verifier、规则、Reward Model 或 Judge 计算奖励。
6. 将轨迹转换为 SFT、偏好或 RL Experience。
7. 训练器更新策略，生成新的 Policy Version。
8. 运行能力、安全和回归门禁。
9. 把失败样本、低置信度样本、分歧样本和真实产品反馈送回任务池。

这条链路与离线流水线的最大区别是策略本身参与数据分布的形成。模型更新后，未来生成的数据也会变化，因而数据不再独立同分布。若继续使用很旧的轨迹，训练数据可能来自已经过时的策略；若只保留高奖励样本，又可能快速降低多样性并造成模式收缩。

因此在线链路必须显式记录 Policy Version、生成引擎、采样配置、Reward Version、环境版本和生成时间。没有这些信息，就不能判断数据是 On-policy、Near-policy 还是明显 Off-policy。

### 4.5 训练阶段不是按名称堆叠，而是按数据作用划分

### Pretraining

预训练让模型从大规模 Token 序列中学习语言、知识、模式和一般能力。数据重点是覆盖、质量、独特性、混合、Token 效率和长尾。训练目标通常是下一 Token 预测，因此大多数数据没有显式任务标签。

### Continued Pretraining

Continued Pretraining 从已有 Base Checkpoint 继续使用语言建模目标训练，常用于领域适配、知识更新、多语种扩展、数学代码强化或长上下文扩展。它与从零预训练使用相似数据结构，但数据比例、学习率、通用回放和遗忘控制更敏感。

### Mid-training

Mid-training 不是一个严格统一的行业术语，通常表示 Base 预训练与最终对齐之间的能力塑形阶段。它可能引入高质量数学、代码、长上下文、阅读理解、合成推理或接近指令形式的数据。工程上应根据“训练目标和数据 Schema”描述具体做法，而不是只写一个模糊标签。

### SFT

SFT 用明确的输入—目标输出训练模型。重点从“文档是否高质量”转向“任务是否有价值、答案是否正确、模板是否一致、Loss Mask 是否正确、能力混合是否平衡”。同样一条对话，如果把 User Token 也计入 Loss，训练含义就会改变。

### Preference Optimization

DPO、IPO、KTO、ORPO、SimPO 等方法使用偏好或好坏反馈塑造输出分布。重点是候选响应从哪里来、Chosen/Rejected 差异是否真实、Judge 是否有偏差、数据是否与当前策略匹配、长度是否成为伪特征。

### Reward Modeling

Reward Model 学习把人类或 AI 偏好转成可计算信号。数据需要 Prompt、候选响应和偏好标签，还要有切片、分歧、标注者、规则与置信度。Reward Model 不是“标准答案模型”，它只是在特定数据分布和标注规范下拟合偏好。
