# 后训练系统：Rollout、同步异步与陈旧度

SFT/DPO 是「离线喂数据」，RL 后训练是「边生成边学」。系统复杂度立刻上升一个量级：**同一批数据既是被优化的对象，又是被策略生产的产物**。

## 1. 四个角色与三条流

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y5_l27_01.png" width="78%" alt="RLHF 数据流" />
  <p>图 1：Trainer、Rollout、Reward/Verifier、Reference 四角色，加上控制器与支撑服务</p>
</div>

| 角色 | 职责 | 变体 |
|---|---|---|
| Policy Trainer | 消费 Experience、反向传播、提交更新 | 需要 Critic（PPO）或组内统计（GRPO/RLOO） |
| Rollout Engine | 按策略生成响应与轨迹 | 长尾主来源 |
| Reward / Verifier | 打分或执行验证 | RM / Judge / 可执行 Verifier（RLVR） |
| Reference Model | KL 约束基线 | 部分方法省掉 |

**控制器不承担大张量计算**，它负责创建任务、放置角色、分配 Prompt、聚合 Group、触发权重发布、决定更新与处理故障。Checkpoint Manager、Artifact Store、Metric Collector、数据目录是支撑服务——省略它们，恢复与审计看起来就像免费的。

三条流不能混画：

- **数据流**：Prompt、Response、Token、Logprob、Reward、Advantage、Batch；
- **版本流**：Policy、Reference、Reward、Tokenizer、Template、Runtime、Environment 的不可变标识；
- **控制流**：启动、心跳、背压、同步、暂停、提交、取消、恢复。

`Policy Bundle` 不是「一串参数」，而是**模型/Adapter 制品 + 版本 + 哈希 + Tokenizer + Template + 生成兼容信息**的集合；`Checkpoint / 账本` 也不只存模型，还存消费游标、已提交 Experience、采样器状态与控制器状态。

### 1.1 Experience 的双向血缘

给定 `experience_id`，要能查到每一阶段的输入、输出、状态、时间、重试次数与制品版本；给定一个 Checkpoint，要能反查哪些 Experience 被提交。

**没有双向血缘，系统只能说「某个任务失败」，无法解释影响范围。**

## 2. 三个平面

| 平面 | 追求 | 关键设计 |
|---|---|---|
| 数据面 | 大吞吐 | 批 Prompt、KV Cache、Token、Logprob、Reward、梯度走共享内存/对象存储/张量通信；**别让每条响应都回到 Controller 的 Python 堆** |
| 控制面 | 确定语义 | 消息小但决定正确性：Job ID、Role、Lease、Policy Version、Group Deadline、Watermark、Barrier、Commit ID；**幂等、可重试、带状态机** |
| 证据面 | 可追溯 | Manifest、日志、指标、事件、内容哈希、回放与审计；冷热分层 |

控制面的三条纪律：

1. **超时不等于没执行**：给任务唯一 ID 与租约，Worker 完成后按 ID 提交，重复提交由账本去重；
2. **取消不是删消息**，而是写期望状态，Worker 在安全点响应；
3. 区分「期望状态」与「观察状态」——否则超时重试会演化成重复生成与重复更新。

## 3. 同步控制：最容易理解，不一定最省资源

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y5_l29_01.png" width="78%" alt="同步与异步" />
  <p>图 2：同步用 Barrier 换清晰边界，异步用重叠换吞吐，代价是陈旧</p>
</div>

### 3.1 状态机

```text
ROLLOUT → REWARD → ASSEMBLE → TRAIN → PUBLISH → COMMIT
```

只有当前状态完成才能进下一状态，失败则重试或从最近 Barrier 恢复。

### 3.2 优点

Group 成员版本一致、行为概率易验证、队列短、恢复边界明确、实验可重复——**团队刚建平台时，先跑通同步闭环比直接追异步利用率更重要**：没有可信基线，就测不出异步偏差。

### 3.3 代价

$$
T_{iter} = T_r + T_w + T_t + T_p
$$

Rollout 长尾让其他 Worker 等最慢任务；Reward 里的工具与 Judge 时延更不稳定；进入 Train 后专用 Rollout GPU 可能空闲；同一批 GPU 在阶段间重分片还要迁移权重与优化器状态。

### 3.4 可信基线五件事

1. 每轮生成 `iteration_id` 与**冻结的 Policy Bundle**；
2. 定义 **Group Timeout**：超时是丢整组、补采样还是允许变长组——由算法决定，不能由队列临时定；
3. Train 前跑完整性与版本门禁，把本轮可训练集合写成**不可变清单**；
4. Publish 只有在「模型 + 优化器 + 数据游标 + 提交账本」共同 Checkpoint 成功后才可见；
5. 发布用临时路径 + 原子指针切换，读者只看到完整 Bundle。

**若只上传权重而账本失败，恢复时就会用新权重重复消费旧数据。**

## 4. 异步控制：更快，也更难证明正确

### 4.1 吞吐上限

$$
\lambda_{\max} \le \min\left(\mu_r,\ \mu_w,\ \mu_t\right)
$$

但这个结论**依赖队列稳定**：到达率长期超过某阶段服务率，积压与 Lag 就会无界增长。异步必须用**背压**调整采样或暂停上游，不能把对象存储当无限缓冲。

### 4.2 Policy Lag 的两种门禁

- **版本差**：\(u - v \le L_{\max}\)，好实现，但不同更新幅度下「差 1 版」并不等价；
- **Trainer 侧重算**：重算 current logprob，观察 Ratio、近似 KL、Clip Fraction，按异常程度拒绝或降权。

拒绝旧 Experience 浪费昂贵 Rollout，接受过旧 Experience 伤害 on-policy。可动态调发布频率、队列深度与 Trainer 更新步数，把「浪费率」与「学习稳定」控制在预算内。**Lag 指标要按 Token、Prompt 域、响应长度、Worker 分桶**，否则均值会掩盖某个慢 Worker。

### 4.3 异步组聚合的陷阱

GRPO 的组成员若由不同 Policy Version 生成，**组内相对 Reward 不再对应同一行为分布**。即使版本差只有 1，温度或模板变化也会破坏可比性。

正确做法：控制器分配时**固定 Group 的 Policy Bundle**，所有成员携带相同 `group_policy_version`；成员超时补采样也必须用原版本，原 Bundle 被回收则整组失效（不能用最新策略补一条）。

组状态机：`Planned → Running → Partial → Complete / Expired / Invalid`，**只有 Complete 且版本一致才进优势计算**。

## 5. 混合控制：用重叠换时间，但守住边界

### 5.1 微批次流水线

把一轮大 Rollout 拆成多个 Microbatch：第一个进 Reward 时，Rollout 生成第二个；第一个进 Train 时，Reward 处理第二个。**所有 Microbatch 绑定同一 Policy Version**，轮末统一发布。

代价：后续 Microbatch 若仍按旧策略生成，会逐渐离策略——要么累积梯度只更新一次，要么允许有限更新并监控 Ratio。**选择必须写进 Objective Contract。**

### 5.2 有界异步

允许 Rollout 与 Trainer 同时跑，但限制：**最大 Policy Lag、最大队列 Token、最大 Group Age、每版最大更新数**。任一超限就暂停上游、强制发布或清理过期数据。

阈值要靠测量校准：版本差 2 不一定安全、差 5 也不一定危险；关键是 Ratio 分布、Clip Fraction、KL 与固定评测。先在同步基线上得到正常区间，再逐步扩大窗口。

### 5.3 Partial Rollout

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y5_l29_02.png" width="78%" alt="Partial Rollout" />
  <p>图 3：在固定 Token/时间/步骤处截断，用 Bootstrap 价值补未来回报</p>
</div>

长 Agent 轨迹可能跑几分钟。Partial Rollout 把轨迹切段：Trainer 先消费已完成片段，后续续生成。

**它不是把 `max_new_tokens` 调小**——算法必须知道「序列没有自然终止」。

四种终止原因要显式编码，对应不同 Mask 与回报：

| 原因 | 含义 | 误处理后果 |
|---|---|---|
| EOS | 策略选择结束 | 把截断当 EOS → 教模型提前结束 |
| 长度上限 | 外部截断 | 同上 |
| 工具暂停 | 等待环境 | 当成结束 → 丢掉后续 |
| 取消 | 控制事件 | 当成失败 → 惩罚无关 Token |

Bootstrap 回报：

$$
G_t = \sum_{k=t}^{T-1}\gamma^{k-t}r_k + \gamma^{T-t}V(s_T)
$$

价值偏差会直接进优势。没有可靠 Critic 或可验证未来时，Partial 样本只适合过程监督、离线数据或等待续跑，**不能假装是完整终局轨迹**。

三种预算各有偏向：

- **Token 预算**：易调度，可能在关键推理中间截断，训练偏向短任务；
- **时间预算**：符合 SLO，但原因混杂（环境慢 vs 模型长推理），硬件版本会改变数据分布；
- **步骤预算**：Agent 按工具步截断，便于快照与续跑，但步骤成本差异大，安全/事务动作必须在完整边界结束。

## 6. 异步的三个现实问题

| 问题 | 表现 | 对策 |
|---|---|---|
| 乱序 | 短任务先完成，Trainer 按到达顺序消费 → 偏向短/易任务 | 按任务/版本/年龄/优先级调度，给长任务最小份额；迟到结果有状态 |
| 重复 | 至少一次投递 + 租约超时 + 重试 → 重复执行 | `request_id`/`trajectory_id`/`group_id`/`update_commit_id` 各自幂等；**不能因文本相同判重复**（合法多候选可能相似） |
| 迟到 | 任务过期后结果才到 | 记 `late` 并决定离线用途，**不重新打开已提交 Group**，也不无痕删除 |

恢复方面：角色可独立重启，但语义状态必须落在耐久账本（租约、版本、队列位置、Group、验证、训练提交）。控制器接管时先重建「期望 vs 观察」，冻结新更新，核对重复与在途，再恢复。

## 7. RLVR 与数据飞轮

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y5_l26_01.png" width="78%" alt="RLVR 与数据飞轮" />
  <p>图 5：可验证奖励把「打分」换成「执行」，飞轮把训练产物变回数据</p>
</div>

- **RLVR**：奖励来自可执行验证（单测、数学答案、SQL 结果、形式证明），比 RM 更客观，但**只覆盖可验证任务**，且要防「作弊式通过」（硬编码、读测试、绕过沙箱）；
- **环境**：Agentic RL 需要一个可重置、可快照、可并行的环境；环境版本也是数据版本；
- **拒绝采样**：从当前策略采样多次，只保留通过验证的样本用于 SFT/DPO——简单有效，但会带来**难度偏置**（只留「当前能做对」的题）；
- **飞轮**：训练 → 评测 → 失败样本 → 新数据 → 再训练。飞轮必须防止「自我强化偏差」，并保留人工与外部基准做对照。

## 8. 北极星指标

一句最重要的话：**北极星是「有效且新鲜的 Experience 吞吐与学习收益」，不是组件利用率。**

各角色都追求局部吞吐时：Trainer 加速 → 版本差变大；Rollout 加速 → 队列变长；Reward 长尾 → 任务构成偏移。最后 GPU 都很忙，训练却在消费陈旧、偏置的数据。

## 9. 设计对照表

| 维度 | 同步 | 有界异步 | 完全异步 |
|---|---|---|---|
| 版本边界 | 清晰 | 受阈值限制 | 模糊 |
| 资源利用 | 受 Barrier 限制 | 较高 | 最高（理论） |
| 正确定义 | 容易验证 | 需 Ratio/KL 门禁 | 需强门禁 + 血统 |
| 恢复 | 边界明确 | 中等 | 复杂（在途状态多） |
| 适用 | 建基线、小规模 | 大多数生产 | 极大规模且证据充分 |

## 写在最后

后训练系统的难点不在算法公式，而在**「哪一版策略生成了哪条经验、它被哪次更新消费」这件事能不能被证明**。

最后一篇收口：五个后训练平台的工程项目——可版本化数据湖、配方工厂、合成与偏好工厂、可按显存缩放的 SFT→DPO→GRPO/RLVR 流水线，以及可恢复的异步 Agentic RL 平台。
