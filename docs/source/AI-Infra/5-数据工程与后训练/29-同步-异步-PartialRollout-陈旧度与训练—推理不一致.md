# 同步、异步、Partial Rollout、陈旧度与训练—推理不一致

## 1. 本文要解决的工程问题

异步系统吞吐更高，但 Rollout 使用的 Policy、Trainer 更新的 Policy 和重算 Logprob 的实现逐渐分离。时间延迟很小，也可能已经跨过多个策略版本。

本文围绕一个可执行判断展开：怎样控制同步、异步与 Partial Rollout 的陈旧度、旧 logits 和训练—推理不一致？读完应能给出自己的系统边界、输入输出、版本关系和验收证据，而不是只复述工具名称或公式。

## 2. 本文交付物与判定标准

本文的核心决定是：用 Policy Version、Token Age、Update Distance 和兼容窗口定义陈旧度，并把 Partial Rollout 与训练—推理不一致分别治理。

完成学习和实验后，应当交付一份最小可复现记录，至少包含输入快照、配置、代码版本、运行状态、原始输出和结论边界。验收证据是：每条 Experience 带生成与消费版本；按陈旧度切片报告奖励、重要性比率、丢弃率和吞吐。

围绕“同步、异步、Partial Rollout、陈旧度与训练—推理不一致”的验收不接受三类替代品：把模拟输出写成真实 GPU 结果；只展示成功样本而隐藏失败与 `SKIPPED`；只给总分，不保存能复算总分的对象级记录。

## 3. 前置知识与实验边界

“同步、异步、Partial Rollout、陈旧度与训练—推理不一致”的机制实验使用 Python 3.10 及以上版本和标准库，重点验证对象、算法或状态转换。真实硬件路径使用 PyTorch；检测不到 CUDA 时必须输出结构化 `SKIPPED`，不得静默改跑 CPU 后仍标成 GPU 实测。

异步策略没有通用最优窗口，允许范围取决于算法、模型、任务与生成系统。

### 3.1 业务背景与失败模式

### 1.1 行为策略与目标策略

轨迹由行为策略 $\mu$ 采样，Trainer 希望更新当前策略 $\pi_\theta$。严格 On-policy 时二者相同；分布式流水中，$\mu$ 通常是若干 Step 之前的策略或不同推理运行时。若直接把旧轨迹当当前采样，梯度估计可能偏。系统必须保存行为版本和 Token 概率，不能只保存回答文本。

### 1.2 重要性比

对状态动作或 Token，可定义：

$$\rho_t=\frac{\pi_\theta(a_t|s_t)}{\mu(a_t|s_t)}$$

当 $\rho_t$ 远离一，样本对当前策略的代表性下降，乘积形式还会随序列长度产生极端方差。PPO 裁剪限制单步更新影响，却不能修复错误的行为概率、模板或环境状态。初始 Ratio 异常首先是系统一致性问题，不应立即调 Clip 掩盖。

### 1.3 Policy Lag

若轨迹由版本 $v$ 生成，Trainer 当前版本为 $u$，版本滞后 $L_v=u-v$。它便宜易监控，却不是行为差的精确度量：多个小更新与一个大更新差异很大。还应测墙钟年龄、实际 Token Ratio、KL 代理、奖励分布和任务环境版本。

### 1.4 数据年龄

数据从 Prompt 采样、生成、环境、Reward、Group 聚合到训练消费经历多个阶段。墙钟年龄反映队列与外部状态变化，版本年龄反映策略更新，两者都可能使数据失效。任务、Reward 和环境也有版本，因此“模型版本新”不自动说明整条 Experience 新鲜。

### 1.5 训练—推理不一致

Tokenizer、精度、内核与采样处理都可能造成差异。

即使权重 Step 相同，训练与 Rollout 仍可能因 Tokenizer、Chat Template、精度、量化、RoPE、Kernel、Logits Processor、温度、top-p、EOS 和约束解码不同而产生不同分布。必须把运行时协议纳入复合策略版本，并在固定 Token 上对拍行为 log-prob。

### 1.6 优化目标与系统合同

算法公式隐含输入合同：PPO 需要行为 log-prob 与 Value，GRPO 需要同策略同 Prompt 的完整 Group，RLVR 需要环境证据，Partial Rollout 需要截断与 Bootstrap。控制面只有满足合同后才提交 Experience。消息到达不等于可训练。

### 3.2 学习目标与能力清单

### 2.1 同步轮次

![同步轮次与异步流水对比](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y5_l29_02.png)

分别读左右两侧，检查它们回答的问题与采用的分母。重叠提高资源利用，也引入策略陈旧与在途状态。

冻结策略 $v$，生成规定 Prompt 和候选，完成 Reward 与优势，Trainer 更新并发布 $v+1$，再进入下一轮。状态可写为 ROLLOUT、REWARD、ASSEMBLE、TRAIN、PUBLISH、COMMIT。每个 Barrier 提供清晰版本边界，适合建立正确性基线和小硬件实验。

### 2.2 同步的优势

Group 成员版本一致，行为概率易验证，队列短，恢复边界明确，实验重复性较好。算法异常更容易与输入 Batch 关联。对于团队初建后训练平台，先跑通同步闭环比立即追求异步利用率更重要，因为没有可信基线就无法测量异步偏差。

### 2.3 同步的长尾

最慢生成、环境或 Judge 决定 Barrier。已完成 Worker 空闲，专用 Rollout 与 Trainer 池在对方阶段闲置。若每轮时间由阶段之和构成，系统利用率受串行比例限制。长度分桶、任务超时、组级补采样和阶段内部并行可改善，但必须保持算法语义。

### 2.4 Group 超时

同 Prompt 八个候选只返回七个时，可丢整组、补采样、使用变长组或以 Mask 处理。每种选择改变优势统计。补采样必须使用同一冻结策略和环境合同；新版候选不能补旧组。规则写入算法配置，不能由队列临时决定。

### 2.5 同步恢复

Checkpoint 不只保存模型，还要保存轮次状态、Prompt 清单、已完成轨迹、Group、消费与发布账本。故障后可以重用已验证轨迹或按相同版本与种子补齐。若模型更新提交而数据账本未提交，恢复可能重复消费，需原子 Barrier 或两阶段提交。

### 2.6 同步何时更优

任务长尾可控、权重同步成本高、算法对 On-policy 敏感、GPU 规模有限或证据能力不足时，同步往往是更好的工程点。性能比较必须用达到质量门槛的墙钟与总成本，而不是认为异步组件同时忙就必然更优。

### 3.3 实验准备与责任边界

### 3.1 基本结构

Rollout 持续读取可用策略，Reward 持续处理轨迹，Trainer 持续消费 Experience 并周期发布。长期吞吐接近最慢阶段服务率，而非各阶段时间之和。代价是同一队列包含多个行为版本，任务可能乱序、重复、迟到或在消费前过期。

### 3.2 有界异步

控制最大版本差、墙钟年龄、队列 Token、Group 完整和在途版本数。超限时背压 Rollout、暂停 Trainer、排空队列或淘汰数据。有界异步把性能问题转为可测参数，比完全开放异步更适合作为从同步基线向生产演进的中间点。

### 3.3 完全异步的风险

各角色只追求局部吞吐时，Trainer 加速会增加版本差，Rollout 加速会增加队列，Reward 长尾会改变任务构成。最终 GPU 都很忙，训练却消费陈旧、偏置数据。系统北极星必须是有效新鲜 Experience 和学习收益，而非组件利用率。

### 3.4 乱序

后生成的短任务可能先完成，早期长任务晚到。Trainer 按到达顺序消费会偏向短、易和低环境延迟任务。需要按任务、版本、年龄与优先级调度，保留长任务最小份额。迟到结果有状态，不静默丢弃或错误补组。

### 3.5 重复

队列至少一次、租约超时和控制器重试会重复执行。request_id、trajectory_id、group_id 和 update_commit_id 分别幂等。重复轨迹不能因文本相同判断，因为合法多候选可能相似；身份与采样种子决定是重试还是独立样本。

### 3.6 迟到

任务过期后结果仍可能到达。系统记录 late 并决定离线用途，不重新打开已提交 Group。迟到不等于失败，也不能无痕删除。它帮助定位长尾、错误 TTL 和环境瓶颈，并计入生成成本。

### 3.7 异步恢复

角色可独立重启，但语义状态必须在耐久账本：任务租约、版本、队列位置、Group、验证和训练提交。控制器接管先重建期望与观察，冻结新更新，核对重复和在途，再恢复。多副本不自动带来正确高可用。

## 4. Partial Rollout

### 4.1 什么是 Partial Rollout

在固定 Token、时间、步骤或安全点截断未完成轨迹，使用部分序列进行训练或保存到下一阶段继续。目标是减少长尾、提高响应和资源利用。它不是简单把 `max_new_tokens` 调小，因为算法必须知道序列未自然终止，并处理未来回报与状态。

### 4.2 截断与终止

EOS 表示策略选择结束，长度上限表示外部截断，工具暂停表示等待环境，取消表示控制事件。这些终止原因对应不同 Mask 和回报。把截断当 EOS 会教模型提前结束；把系统取消当失败会惩罚无关 Token。Schema 必须显式编码。

### 4.3 Bootstrap

若在状态 $s_T$ 截断，可用价值估计 $V(s_T)$ 补未来回报：

$$G_t=\sum_{k=t}^{T-1}\gamma^{k-t}r_k+\gamma^{T-t}V(s_T)$$

价值偏差会进入优势。没有可靠 Critic 或可验证未来时，Partial 样本可能仅用于过程监督、离线数据或等待续跑，不应假装完整终局轨迹。

### 4.4 Token 预算 Partial

按固定 Token 切分容易调度，可能在关键推理中间截断。截断点分布与任务长度相关，训练会偏向短任务。报告完整率、截断位置、任务覆盖和最终成功。可在句子、工具边界或可恢复状态寻找更安全切点。

### 4.5 时间预算 Partial

按墙钟控制长尾，环境慢与模型长推理都会触发，原因混杂。应扣分或作废基础设施等待，记录生成与环境时间。时间预算更符合服务 SLO，却可能随硬件变化改变数据分布，因此运行时和硬件版本进入配置。

### 4.6 步骤预算 Partial

Agent 按工具步截断便于状态快照与续跑。不同步骤成本差异大，不能只按数量。安全和事务动作必须在完整边界结束。部分轨迹保存环境 snapshot、父 Episode 与 continuation token，续跑时验证版本兼容。

### 4.7 Partial Group

GRPO 组内有些完整、有些截断时，奖励尺度和长度不同。可只用完整成员、按 Mask 计算、为 Partial 估值或丢组，每种都有偏差。必须通过合成任务和真实任务消融，不能因“有 Token 就训练”随意混合。

### 4.8 Partial 的适用边界

适合长尾显著、状态可保存、过程信号或 Critic 可靠、算法明确支持截断的系统。不适合最终奖励极稀疏且无法 Bootstrap、环境不可恢复或安全动作不能中断的任务。先作为数据与调度功能验证，再决定是否进入梯度。

## 5. 陈旧度建模

![陈旧度的多个维度](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y5_l29_03.png)

Policy Lag 不是单一时钟差，而是策略、运行时、奖励和环境版本共同形成的兼容性问题。下面把这些维度拆开，避免用一个模糊阈值掩盖失配。

同样版本差在不同更新频率下代表不同时间与参数变化。

### 5.1 多维陈旧

至少包括 policy_version_lag、wall_clock_age、runtime_age、reward_version_age 和 environment_version_age。一个标量无法覆盖。训练门禁先检查协议兼容，再看行为距离。环境语义变化时，即使策略版本相同，旧轨迹也可能不可用。

### 5.2 Ratio 分布

均值接近一不足以说明 On-policy。报告中位、分位、最大、绝对对数 Ratio 和 Clip Fraction，按 Token 位置、长度、任务与版本切片。序列长时小单步差异累积，应避免直接乘全序列 Ratio 造成数值爆炸。

### 5.3 KL 代理

在轨迹状态上重算当前分布与行为分布，或用采样 Token log-ratio 估计。明确方向、截断与精度。它比版本差直接，但计算成本高，可对边界、风险和抽样数据运行。检测到不一致先排系统，再讨论算法容忍。

### 5.4 奖励漂移

Reward 或 Verifier 升级后，同一轨迹分数改变。旧奖励可能不适合当前目标，重算又可能与当时策略选择机制不同。保留原始证据和多版本 evaluation，训练 Run 绑定选择的版本。严重验证漏洞需重判并追踪已训练影响。

### 5.5 环境漂移

工具 Schema、依赖、网页和模拟器变化会让旧动作结果不同。任务尽量使用快照与不可变环境；真实动态任务记录时间和状态。环境桥接翻转率决定旧轨迹能否复用。不能只依据 Prompt 文本判断兼容。

### 5.6 陈旧数据处置

可拒绝、降权、重要性修正、重放重评或转离线用途。策略取决于算法、行为距离和成本。任何降权函数先用真实数据校准，不能凭版本差线性设置。被拒数据仍保存原因与成本，帮助容量优化。

## 6. 训练—推理一致性

### 6.1 Tokenizer

比较消息渲染后的 Token ID、特殊 Token、Padding 和 EOS。训练与推理若分别在线下载 Tokenizer，浮动 revision 会漂移。制品随 Bundle 固定，固定样本逐 Token 测试。轨迹保存原 Token ID，文本只作审计视图。

### 6.2 Chat Template

System、角色、工具定义和 Assistant 起始符的微小差异会改变全部条件概率。模板实现与版本进入 Bundle。训练重算使用实际 Token 或完全相同渲染器。升级模板创建新 Run 或明确桥接，不重新解释旧轨迹。

### 6.3 Logits Processor

重复惩罚、禁词、语法、温度、top-k 和 top-p 顺序影响行为概率。服务返回处理后分布的采样 Token log-prob，并保存 processor 链。Trainer 若只用原始模型 softmax，重要性比无意义。固定 logits 单元测试每个处理器。

### 6.4 精度与量化

训练 BF16、推理 INT4 的差异在低 Margin 和长序列放大。桥接实际 Token Ratio、KL、EOS、长度、奖励和安全切片。量化收益与学习损失形成 Pareto。不能用离线困惑度单指标批准 On-policy Rollout。

### 6.5 Kernel 与并行

不同 Attention、TP 归约和融合 Kernel 可能产生浮点差异，批调度也影响确定性。定义容差与重放等级，优先保证分布和关键决策一致。异常若集中某硬件或序列长度，按运行时版本隔离。性能升级需要行为 Canary。

### 6.6 Old log-prob

最可信来源是 Rollout 引擎在采样时记录实际行为概率。若事后用行为权重重算，必须复现 Tokenizer、模板、处理器、精度和运行时；重算差异作为指标。缺可靠 old log-prob 的轨迹不能用于需要 Ratio 的目标，可转其他用途。

### 6.7 Reward 输入一致

Reward 可能使用不同模板、截断或工具状态。训练使用的奖励必须绑定实际可见输入和版本。若策略回答在 Reward 侧被截断，分数不再对应全轨迹。记录 Reward Token、截断和证据，不能只传标量。
