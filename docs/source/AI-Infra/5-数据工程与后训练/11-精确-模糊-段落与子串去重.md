# 精确、模糊、段落与子串去重

## 1. 本文要解决的工程问题

去重报告显示删除率很高，团队把它当成节省训练预算的成功；抽查后发现模板页被正确合并，但代码许可证和短事实也被错误吞掉。

本文围绕一个可执行判断展开：怎样组合精确、MinHash、段落和子串去重并控制误删？读完应能给出自己的系统边界、输入输出、版本关系和验收证据，而不是只复述工具名称或公式。

## 2. 本文交付物与判定标准

本文的核心决定是：按精确、MinHash、段落和子串关系分层建簇，先定义保留策略、冲突处理与可解释证据，再决定删除。

完成学习和实验后，应当交付一份最小可复现记录，至少包含输入快照、配置、代码版本、运行状态、原始输出和结论边界。验收证据是：黄金重复集和非重复近邻集同时验收；每个删除对象都能指出代表样本、相似证据、阈值和保留理由。

围绕“精确、模糊、段落与子串去重”的验收不接受三类替代品：把模拟输出写成真实 GPU 结果；只展示成功样本而隐藏失败与 `SKIPPED`；只给总分，不保存能复算总分的对象级记录。

## 3. 前置知识与实验边界

“精确、模糊、段落与子串去重”的机制实验使用 Python 3.10 及以上版本和标准库，重点验证对象、算法或状态转换。真实硬件路径使用 PyTorch；检测不到 CUDA 时必须输出结构化 `SKIPPED`，不得静默改跑 CPU 后仍标成 GPU 实测。

高删除率不是质量指标，局部相似也不等于训练贡献完全重复。

### 3.1 业务背景与失败模式

本文系统讲解大模型数据工程中的去重。目标不是记住 Exact Hash、MinHash、LSH、Suffix Array 等名称，而是能够根据重复的形成方式、数据规模、允许误差、内存与网络预算，设计一条可解释、可回放、可抽检的多层去重流水线。

训练语料中的重复并不只有“两个文件完全相同”。网页镜像可能只改导航栏与日期，文章转载可能插入广告，代码仓库可能复制依赖，论坛引用会把旧回复嵌入新页面，合成数据可能共享长模板，指令数据则可能问题不同但答案主体完全相同。任何单一算法都只能捕捉其中一部分。

去重的价值也不只是减少磁盘。重复会改变来源权重、放大高频模板、增加记忆与污染风险、浪费训练 Token，并让评测重叠更隐蔽。但过度去重会删除合法复述、多语对齐、代码样板和同题不同解法。因此工程目标不是追求最高删除率，而是在明确的相似语义下控制召回、误删、成本与下游收益。

### 3.2 学习目标与能力清单

完成后应当能够：

1. 区分字节级、规范化文本级、文档级、段落级、句子级、子串级与语义级重复。
2. 设计规范化与内容指纹，解释为什么比较视图不应直接覆盖训练文本。
3. 从集合相似度推导 MinHash 碰撞概率，并用 LSH 的 Band 与 Row 参数计算候选概率。
4. 设计全局去重、分桶去重和增量去重，判断分桶带来的召回损失。
5. 使用外部排序、Bloom Filter、哈希分区和并查集控制大规模精确去重成本。
6. 解释段落、句子与子串去重的收益和结构破坏风险。
7. 为每个重复簇选择代表文档，并保存删除理由、簇关系与回滚证据。
8. 通过机制实验比较不同算法的 Precision、Recall、候选缩减率和阈值敏感性。
9. 通过真实 CUDA 实验测量批量签名比较的吞吐、显存与候选密度；无 GPU 时明确输出 `skipped`。
10. 把离线去重指标与固定训练预算下的模型效果、记忆风险和数据多样性连接起来。

### 3.3 实验准备与责任边界

需要理解哈希、集合、概率和基本复杂度，能够运行 Python。机制实验仅依赖标准库和 NumPy，核心算法刻意保留可读实现。生产规模可使用 DataTrove、NeMo Curator、Spark、Ray、Dask 或自建 C++/CUDA 任务，但工具不会替代相似语义与验收设计。

真实硬件实验依赖 PyTorch CUDA。实验基准以单张或至少一张可用 CUDA GPU 为目标，只测量已经生成的 MinHash 签名之间的候选比较，不声称完成互联网规模端到端 GPU 去重。若 CUDA、PyTorch 或足够显存不存在，脚本返回结构化 `skipped`。

## 4. 重复对象与候选算法怎样定义

### 4.1 先定义“重复”

重复是一种相对于表示、粒度和用途的关系。两个压缩文件的字节不同，解压后的正文可能相同；两个网页正文只差一个日期，从训练语义看可能近似重复；两篇独立新闻报道描述同一事件，语义相近但表达与事实细节不同，未必应该删除。

因此每条去重规则都要回答四个问题：比较什么表示，在哪个对象粒度比较，用什么相似函数，达到什么阈值算同簇。缺少任一项，“已去重”都不是可复现结论。

字节级重复适合发现完全相同原始对象，能够避免重复解析和存储。规范化文本级重复忽略编码、换行、Unicode 和部分标点差异。模糊文档级重复关注大部分内容重合。段落与子串重复处理文档内部或跨文档的局部拷贝。语义重复关注改写和同义表达，但误删知识互补内容的风险更高。

用途会改变判断。预训练可能希望删除大段转载，却保留同一概念的多种自然表达；SFT 可能要保留同题不同高质量解法；偏好数据必须保留同 Prompt 的不同响应，因为差异正是监督信号；评测去污染则宁愿提高召回，再对命中进行受控复核。

### 4.2 去重不是一条过滤规则

成熟流水线通常按成本从低到高分层。先做字节摘要和规范化精确哈希，再做低成本模板与段落统计，然后生成 Shingle 与 MinHash 候选，最后只对少量候选做精确 Jaccard、编辑距离、长子串或语义模型复核。

这种级联设计有两个理由。第一，全量两两比较是平方复杂度，规模稍大就不可行。第二，昂贵算法不一定更可靠，把所有文档直接送入语义 Embedding 既贵，又可能把主题相近但内容互补的文档错误合并。

每层都要记录输入量、候选量、确认簇、删除量、耗时、资源和抽检。若只保存最终保留集，就无法判断某条文档在哪一层消失，也无法在阈值调整时复用上游特征。

级联还需要明确短路条件。精确哈希相同的文档可直接同簇，不必再跑 MinHash；但若许可与来源优先级需要决定代表样本，仍需把全部成员送入代表选择。低质量文档也不应在记录重复关系前随意删除，因为它可能帮助识别其他来源的模板簇。

### 4.3 比较视图与训练视图

去重通常对文本做规范化：Unicode 归一、大小写折叠、空白合并、控制字符删除、数字或 URL 代用标记。规范化越强，越容易发现形式差异下的重复，也越容易把本来不同的内容合并。

比较视图应当是训练文档的派生字段，而不是覆盖原文。代码大小写、数学符号、空格缩进和标点都可能有语义；为了指纹方便而修改训练内容，会把去重操作变成不可逆清洗。

规范化 Recipe 需要版本化。至少记录 Unicode 形式、语言相关大小写规则、空白定义、标点处理、HTML 实体、数字与 URL 策略。哈希必须绑定 Recipe ID，否则两个使用不同规范化的摘要不可直接比较。

规范化还要抵抗异常输入。超长重复字符、混合方向文本、非法代理字符、零宽字符和组合字符可能让看似相同的内容产生不同表示，或让正则处理耗时异常。应设置长度与时间上限，并在失败时保留状态，而不是把异常统一映射为空串。

### 4.4 精确哈希的正确用法

比较视图变化会改变重复定义，不能无版本覆盖旧哈希。

精确去重最常见做法是对规范化内容计算加密摘要或高速非加密哈希。加密摘要碰撞风险极低，适合跨系统稳定标识；高速哈希吞吐高，适合分区和内存表。工程上可以用高速哈希做候选键，再用字节长度、第二摘要或原文比较确认。

不能把语言运行时默认哈希作为持久 ID。许多运行时会随机化哈希种子，不同进程结果不同；某些算法版本与端序也可能变化。稳定 ID 应明确算法、编码和输入 Recipe。

完全相同摘要仍不意味着代表样本可以随意选。一个内容可能同时出现在原创站点、聚合站、低质量镜像和许可未知来源。去重簇应保存所有成员元数据，再按来源可信度、许可、解析质量、时间、结构完整性和稳定规则选代表。

精确去重的分布式实现通常先按摘要前缀分桶，让相同摘要必然进入同一分区。分区内排序或哈希聚合。若某个空文档、通用模板或异常常量形成超大热桶，需要单独检测与拆分，否则一个 Worker 会成为长尾。

### 4.5 外部排序与哈希聚合

当摘要与元数据可以放入内存时，哈希表聚合简单高效。规模超过内存后，可以分区写盘，或使用外部排序。外部排序先生成若干有序 Run，再多路归并；相同摘要相邻，内存只需保存当前组和归并缓冲。

哈希分区的优点是天然并行，缺点是分桶倾斜和大量中间文件。外部排序更容易生成稳定全局顺序，也便于后续合并，但会产生多轮磁盘 I/O。选择取决于数据规模、存储带宽、分区数和是否需要有序输出。

分区数太少会让单分区过大，太多会产生小文件和调度开销。可以先采样摘要前缀分布，估算每桶字节和最大桶，针对热点键使用单独路径。不要只按平均值规划，因为去重数据常有极端模板簇。

任务重试必须幂等。分区输出以输入版本、Recipe 和分区 ID 派生稳定路径，写完校验后提交。重复任务不应追加第二份结果。全局 Manifest 只引用全部成功并通过计数校验的分区。

### 4.6 Bloom Filter 适合回答什么

Bloom Filter 是空间高效的概率集合结构，能回答某个键“肯定不存在”或“可能存在”。它有假阳性，没有假阴性，前提是实现、容量与哈希没有错误。它适合在昂贵远程查询前过滤明显新键，或做流式精确重复的第一道门。

对预计插入数 $n$、位数组大小 $m$ 和哈希数 $k$，假阳性率近似为：

$$p \approx \left(1-e^{-kn/m}\right)^k$$

给定位预算时，最优哈希数约为 $k=(m/n)\ln 2$。容量超过设计值后，位数组趋于饱和，假阳性会快速上升。因此监控插入数与位密度，不能把一个固定 Filter 无限复用。

Bloom Filter 不能独立证明重复。命中后仍需查精确摘要存储或比较内容。如果直接把“可能存在”当成重复删除，假阳性就会变成永久数据损失。删除元素还需要 Counting Bloom Filter 或重新构建，普通 Bloom Filter 不支持安全删除。

分布式场景可以按摘要前缀维护多个 Filter，减少广播体积；也可以定期发布只读快照，让 Worker 本地查询。快照版本与精确索引版本必须匹配，否则会出现新旧状态不一致。

### 4.7 Shingle 把文本变成集合

窗口大小改变重复敏感度，集合会丢失重复次数信息。

模糊文档去重通常先把文本切成连续的 Token 或字符 N-gram，称为 Shingle。文档 $A$ 的 Shingle 集合记作 $S_A$。两个文档的 Jaccard 相似度为：

$$J(A,B)=\frac{|S_A\cap S_B|}{|S_A\cup S_B|}$$

Shingle 长度决定敏感性。过短会让常见词和短语产生大量偶然重叠，过长则对微小编辑过于敏感。词级 Shingle 对自然语言直观，但依赖分词与语言；字符级 Shingle 可跨语言统一，却受空白与编码规范化影响。

集合会丢失重复次数。一个模板句在文档出现十次，与出现一次对集合贡献相同。如果频次有意义，可以使用 Multiset Jaccard、加权 MinHash 或单独模板比例特征。生产系统要明确使用集合还是多重集合。

短文档是特殊情况。一个只有数个词的标题产生不了足够 Shingle，Jaccard 估计方差大。可以对短文本使用规范化精确匹配、编辑距离或单独阈值，避免把所有短句塞进与长文相同参数。

### 4.8 为什么不能全量计算 Jaccard

若有 $N$ 个文档，全量两两比较需要 $N(N-1)/2$ 对。即使单次集合交并很快，百万文档也接近五千亿对，网络与调度远超可接受范围。模糊去重必须先做候选生成。

候选生成的目标是高召回地保留可能相似的少量 Pair。候选缩减率与候选召回是核心指标。只报告最终簇 Precision，不报告漏掉多少真实重复，会掩盖分桶或 LSH 参数造成的盲区。

粗分桶可使用语言、长度区间、来源、时间、首段哈希或 Shingle 数量。长度过滤有数学依据：若两个集合大小差异过大，它们不可能达到高 Jaccard。但按域名分桶会漏掉跨站转载，按语言分桶会漏掉翻译与语言识别错误。

因此安全分桶应来自相似度上界或仅用于资源规划，并保留跨桶策略。业务分区不能未经评估就当作去重边界。

### 4.9 MinHash 的概率含义

签名碰撞是概率证据，不是两个文档相同的证明。

MinHash 利用一个关键性质：对集合 $S_A$ 与 $S_B$ 使用同一随机排列，两个集合最小元素相同的概率等于 Jaccard 相似度。直观上，并集里最先出现的元素如果落在交集，两个集合的最小值相同；它落在交集的概率就是交集占并集比例。

实际不会保存宇宙集合的随机排列，而使用一组近似独立哈希函数。对每个哈希函数，取文档所有 Shingle 哈希后的最小值，得到长度为 $h$ 的签名。两个签名相同位置的比例是 Jaccard 的无偏估计。

若真实相似度为 $s$，每个签名位置近似是成功概率 $s$ 的 Bernoulli 变量，估计方差为 $s(1-s)/h$。增加签名数能降低方差，却线性增加计算、存储和比较成本。参数应由目标阈值附近允许误差反推，而不是照抄默认值。

哈希函数独立性不足、整数溢出、模数选择和 Shingle 预哈希碰撞都会影响估计。机制实现可以使用线性哈希族演示，生产应选择经过验证的实现并用已知集合校准。

### 4.10 LSH 的 Banding 推导

候选遗漏与误报由参数控制，不能跳过核验就删除。

只有 MinHash 签名仍需比较所有签名对。LSH Banding 把长度 $h=b r$ 的签名分成 $b$ 个 Band，每个 Band 有 $r$ 行。两个文档只要任一 Band 完全相同，就成为候选。

若单个签名位置相同概率为 $s$，一个 Band 的 $r$ 行全同概率为 $s^r$，该 Band 不同概率为 $1-s^r$。所有 $b$ 个 Band 都不同的概率为 $(1-s^r)^b$，所以候选概率为：

$$P(\text{candidate}|s)=1-(1-s^r)^b$$

这个函数呈 S 形。增加 $r$ 会要求单个 Band 更严格，降低低相似 Pair 的候选率；增加 $b$ 提供更多命中机会，提高召回同时增加候选。所谓“阈值”不是硬切线，阈值附近仍有假阴性与假阳性。

参数选择应先写目标。例如希望相似度 0.8 的 Pair 至少有 0.98 候选概率，同时相似度 0.3 的 Pair 候选概率低于 0.01，再搜索满足条件的整数 $(b,r)$，并计算签名长度与存储成本。

### 4.11 从候选 Pair 到重复簇

LSH 输出的是候选 Pair，不是最终重复。先对候选计算真实或更精确相似度，超过确认阈值后形成图的边。重复簇通常取连通分量，可用并查集或分布式连通分量算法。

连通关系可能产生链式效应：A 与 B 相似，B 与 C 相似，但 A 与 C 低于阈值，三者仍在同一连通分量。对转载链这可能合理，对严格近重复则可能过度合并。应抽检簇直径、中心相似度和成员跨度，必要时采用中心聚类或完全链接约束。

候选 Pair 数可能因超大 Bucket 爆炸。如果一个 Band Key 对应十万文档，生成所有 Pair 不可行。它可能来自空文本、通用模板、哈希错误或真实超大簇。应对 Bucket 大小设阈值，单独分析热点；不能简单丢弃，因为这会造成系统性漏检。

并查集输出应保持确定性。根节点随并行合并顺序变化时，不应直接用根 ID 当簇 ID。可以对簇成员稳定 ID 排序，用最小 ID 或成员摘要生成稳定 Cluster ID。

### 4.12 精确确认与二阶段阈值

LSH 阈值负责候选召回，确认阈值负责最终 Precision。两者不应相同地理解。候选阶段通常偏宽松，让目标重复有较高概率进入；确认阶段用完整 Shingle 集合、编辑距离、覆盖率或任务规则做确定判断。

Jaccard 对短新增与长原文的包含关系不敏感。若短文完全包含在长文中，交集等于短文集合，并集接近长文集合，Jaccard 可能不高。可以同时计算 Containment：

$$C(A\rightarrow B)=\frac{|S_A\cap S_B|}{|S_A|}$$

它表达 $A$ 有多少被 $B$ 包含。转载摘要、引用和模板清理常需要 Jaccard 与双向 Containment 联合规则。

编辑距离适合字符级修改较少的中短文本，但长文动态规划成本高。可以先用长度差上界、分块哈希或 Bit-parallel 算法缩小范围。语义余弦适合改写候选，不能替代内容重合确认。

阈值要按语言、长度和文档类型校准。代码文件、新闻、论坛与数学解答的重复结构不同。统一阈值操作简单，却可能在某些切片过度删除。分切片阈值增加复杂性，必须有足够标注与持续监控支持。

## 5. 怎样把相似度算法变成可治理流水线

### 5.1 Precision、Recall 与删除风险

去重评估需要一组带真值的 Pair 或簇。Precision 表示系统确认的重复中有多少真重复，Recall 表示真重复中有多少被发现。高 Precision 保护数据多样性，高 Recall 减少冗余与污染。不同用途对二者权重不同。

训练语料去重的误删是不可见风险：被删除内容不再进入后续统计，若没有审计样本，很容易只看到存储减少。评测去污染的漏检风险更高，因此可以宽松命中后人工复核。在线数据流可能更关心低延迟，允许周期全局任务补召回。

Pair 指标也会被簇大小主导。一个万成员模板簇包含近五千万 Pair，可能让总体分数看起来很好，却不能代表普通簇。应同时报告按 Pair、按簇、按文档和按 Token 加权的结果，并单独观察大簇。

标注集需要包含难负例：同主题不同报道、同问题不同解法、代码模板与真实复制、短引用与整篇转载。随机采样的大多数 Pair 完全无关，无法检验阈值边界。

### 5.2 候选召回的分解

最终 Recall 是多个阶段召回的乘积或上界约束。规范化可能把信息删除，分桶可能把 Pair 分开，MinHash 有估计误差，LSH 有概率漏检，热点保护可能丢候选，确认阈值也可能拒绝。只评估最后分类器看不到前面漏掉的 Pair。

应对标注重复 Pair 记录它在哪一步消失。跨语言 Pair 被语言桶分开，长短包含 Pair 被长度过滤，短文本无法生成 Shingle，模板热点被上限截断，这些需要不同修复。

可以建立漏斗指标：总真重复、可规范化、进入同分桶、至少一 Band 命中、生成候选、通过确认、进入正确簇。每次 Recipe 变更比较漏斗，而不仅是最终删除率。

候选召回评估必须使用与生产相同的分布式分区和热点策略。单机小样本没有大 Bucket 和跨分区边界，结果往往过于乐观。

### 5.3 代表样本选择是独立问题

先排除不可使用对象，再按确定规则选择代表。

重复检测回答哪些文档属于一簇，代表选择回答保留谁。把第一个到达的文档作为代表会让并发顺序影响数据版本，也可能保留低质量镜像。

代表评分可以综合来源优先级、许可可用性、原始时间、正文完整性、解析质量、广告比例、语言置信度、结构标记和下游用途。硬约束先排除禁止来源，软指标再排序。最终加入稳定 ID 作为 Tie-breaker，确保确定性。

“最早来源”不一定等于原创，因为抓取时间不是发布时间，聚合站也可能保留更早的错误元数据。“最长文档”可能保留更多广告。“最高质量分”可能偏向改写镜像。代表规则需要通过簇抽检，而不是凭单一启发式。

有时一簇可以保留多个代表。例如同一文章的不同语言、不同许可版本、包含独特评论的转载或同一代码库不同有效版本。去重策略可以设置每簇配额与多样性约束，不必强制只剩一个对象。

### 5.4 删除还是降权

确认重复后有三种常见动作：删除非代表、保留但降低采样权重、按重复次数校正权重。完全删除节省存储与计算，降权保留结构和来源多样性，校正权重则让一簇总贡献近似固定。

网页预训练常删除高相似镜像；代码数据可能希望保留不同仓库上下文，但避免常见库文件重复贡献；SFT 中相同答案模板可以降权，同时保留不同 Prompt；后训练轨迹则按策略版本和奖励语义判断，不能仅文本去重。

动作应由下游 Mixture 配方消费。数据平台可以输出 Cluster ID、Cluster Size、Representative Rank 与建议权重，由训练配方决定是否删除。这样算法改动不必立即物理重写所有内容。

物理删除与逻辑排除分开。逻辑视图便于回滚和消融，物理回收在保护期后执行。涉及隐私或许可撤回时则必须按治理要求真正删除，不能只降权。

### 5.5 段落去重的对象定义

文档去重不能完全消除跨文档局部复制。

段落去重先把 Document 切成 Paragraph，再对规范化段落做精确或模糊比较。它能删除跨网页反复出现的页眉、免责声明、导航、版权、引用块和转载段落，也能处理两篇文档只有部分主体重叠的情况。

难点首先是段落边界。网页 DOM、Markdown 空行、PDF 版面、论坛楼层和代码块都有不同结构。简单按换行切分会把硬换行 PDF 切成许多短片，也会把列表每项视为独立段落。解析器应尽量保留结构类型、父节点和原始位置。

短段落如“联系我们”“下一页”高度重复但信息量低，可以用长度与停用模式过滤；短而关键的代码、公式、标题却不应同样处理。段落去重规则要按类型区分，并设置最小信息量而非单一字符数。

删除重复段落后，文档可能失去上下文、指代对象和语法连贯性。训练数据若保留残缺句子，节省 Token 可能换来质量下降。因此要在删除后运行结构修复与可读性检查，必要时按整个文档降权而不是切掉局部。

### 5.6 Boilerplate 与真实重复

Boilerplate 是跨页面重复的站点模板，它与正文转载不同。模板删除通常希望保留每个页面的独特正文，而文档去重可能只保留整篇代表。两者的动作和证据应分开。

基于 DOM 的模板检测可以利用相同 XPath、节点类、链接密度与站点频率。纯文本数据失去 DOM 后，可以按段落哈希统计来源内文档频率。某段在同一域名大比例页面出现，很可能是模板；但新闻站的突发公告、法规固定条款和教程公共前言可能仍有语义。

频率阈值要结合站点规模。一个只有三页的小站，两页相同段落不一定是模板；大型站点百分之一出现的段落也可能有数万次。可以同时设置最小文档数、占比、段落长度与位置特征。

站内模板去除应先于跨站模糊文档去重。否则共享导航与版权会抬高 Jaccard，产生大量假候选。顺序变化会改变结果，必须写入 Recipe 并做消融。
