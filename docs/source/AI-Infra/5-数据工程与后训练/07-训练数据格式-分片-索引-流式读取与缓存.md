# 训练数据格式、分片、索引、流式读取与缓存

## 1. 本文要解决的工程问题

训练吞吐下降时，数据侧只知道文件数量，训练侧只知道 DataLoader 等待。分片过小、索引失效、缓存抖动和跨节点读取因此混成一个问题。

本文围绕一个可执行判断展开：怎样设计分片、索引、缓存与流式读取，使吞吐优化不破坏确定性？读完应能给出自己的系统边界、输入输出、版本关系和验收证据，而不是只复述工具名称或公式。

## 2. 本文交付物与判定标准

本文的核心决定是：把格式、分片、索引、预取、缓存与 Shuffle 设计成同一个读取合同，并让断点保存消费位置而不只保存文件名。

完成学习和实验后，应当交付一份最小可复现记录，至少包含输入快照、配置、代码版本、运行状态、原始输出和结论边界。验收证据是：固定样本集在冷缓存、热缓存和恢复运行后保持样本身份与顺序可解释，同时输出 I/O 等待、有效 Token 吞吐和缓存命中。

围绕“训练数据格式、分片、索引、流式读取与缓存”的验收不接受三类替代品：把模拟输出写成真实 GPU 结果；只展示成功样本而隐藏失败与 `SKIPPED`；只给总分，不保存能复算总分的对象级记录。

## 3. 前置知识与实验边界

“训练数据格式、分片、索引、流式读取与缓存”的机制实验使用 Python 3.10 及以上版本和标准库，重点验证对象、算法或状态转换。真实硬件路径使用 PyTorch；检测不到 CUDA 时必须输出结构化 `SKIPPED`，不得静默改跑 CPU 后仍标成 GPU 实测。

本文只比较数据供给路径；模型计算、网络拓扑和并行策略需要在目标训练环境单独测量。

### 3.1 业务背景与失败模式

训练数据已经完成解析、清洗和选择后，仍然可能因为物理布局让 GPU 长时间等待。数十亿条 JSON 小文件会被对象存储请求延迟和元数据淹没；单个数 TB 压缩流无法随机恢复；Parquet 列裁剪很强，却不一定适合按样本随机读取已 Tokenize 序列；Tar Shard 对连续流式读取友好，但成员更新困难；二进制 Token 文件吞吐高，却容易丢失样本边界、来源与版本；本地缓存能隐藏网络，却可能在多 Rank 间返回不同版本或被退出事件遗漏。

格式不是“文件扩展名”，而是一组读写契约：逻辑 Schema 如何映射到字节，记录/Batch/页/成员的边界在哪里，压缩在什么粒度发生，索引能定位什么，如何切分给 Node/Rank/Worker，如何验证完整性，失败后从哪里恢复，如何演进 Schema，Source 退出怎样定位，以及训练实际消费如何对账。只有这些契约闭合，才能同时获得吞吐、确定性和治理。

大模型训练还有特殊压力。预训练通常顺序扫描海量 Token，强调大块连续 IO、低 CPU 解码和确定性 Shuffle；SFT/偏好数据字段复杂、长度重尾，强调 Schema、随机访问和 Packing；多模态数据包含图片/音频/视频字节，强调成员共置与大对象流；RL Experience 持续生成，强调时间窗、版本和消费陈旧度。一个万能格式往往让至少一种负载付出高代价。

本文从逻辑样本、物理 Shard、Index、Reader、Shuffle、Cache 和 Consumption Receipt 七层展开，比较 JSONL、Parquet、Arrow IPC、Tar/WebDataset、Token Bin/Idx 等形式，设计对象存储到通用 CUDA 训练的完整数据面。核心目标不是记住格式优劣，而是依据访问模式选择物理产品，并能证明训练 Rank 不重不漏地读取了固定版本。

### 3.2 能力目标

应能区分逻辑 Schema、序列化格式、容器、压缩、Shard 和 Dataset Manifest；理解 Parquet File—Row Group—Column Chunk—Page 层次，Arrow RecordBatch/IPC Stream/IPC File 差异，Tar 成员与 WebDataset 式 Shard，JSONL 的可观测性与局限，Token Bin/Idx 的偏移和 dtype；能设计全局/Shard/记录/字段级索引。

还应能确定 Shard 目标大小与成本，设计 Node—Rank—Worker 层次分片，执行确定性 Shuffle、Epoch 重采样与断点续读；理解对象存储 Range、多段预取、并发、backpressure、本地 SSD Cache 和缓存一致性；能计算有效 Token 吞吐、IO 放大、缓存命中、Padding/Packing 与 GPU 等待。

### 3.3 工程验收

每个 Dataset Release 有不可变 Manifest、Schema/Recipe、Shard 列表、对象版本/摘要、逻辑记录/Token 总账与索引版本；每个 Shard 可独立校验，Reader 只从 Manifest 读取；多 Rank/Worker 分配在约定 Epoch 内不重不漏；断点恢复后消费序列或允许的统计语义一致；损坏/缺失/版本漂移失败关闭；Cache 命中仍验证 Dataset 身份和 Source Policy。

CPU 机制实验将实现自描述 Shard、偏移索引、Range 读取、确定性分片/Shuffle 与断点；CUDA 实验在至少一张可用 CUDA GPU 上用 `torchrun` 消费同一 Token Shard，测数据等待、吞吐、显存和消费覆盖。若单 GPU 不可用，结构化输出 `skipped`，不虚构实测。

### 3.4 边界

本文不深入 Tokenizer 训练、Packing 算法质量和长上下文样本构造，它们在后续篇目展开；不重复后续篇目的全局确定性发布门禁，但会为其建立格式基础；不讨论对象存储厂商具体计费价格，因为价格会变化，应以运行时账单与官方配置为准。

### 3.5 Logical Sample

Logical Sample 是训练语义单位：预训练文档/片段、SFT 对话、偏好对、图文对或 RL 轨迹。它有稳定 sample_id、Source/Unit 血缘、字段、长度和选择权重。逻辑样本不等于物理文件记录；一个样本可跨多个内容 Unit 组装，物理重分片也不应改变 sample_id。

### 3.6 Encoded Record

Encoded Record 是 Schema 映射后的可序列化记录，例如 JSON 对象、Arrow/Parquet 行、Tar 中同 Key 成员组、已 Tokenize 的整数序列。编码必须明确 Null、字段类型、Unicode、二进制、列表/嵌套与版本。字段默认值不能由不同 Reader 随意决定。

### 3.7 Physical Shard

Shard 是存储、并发、重试、缓存和分发单位。一个 Shard 包含多 Record，具有 shard_id、byte length、record/token count、content digest、compression 和 location。Shard 不可变；增加样本生成新 Shard/Release，不能 append 已发布对象后保持同 ID。

### 3.8 Index

Index 把 sample_id/ordinal 映射到 Shard 与 offset/row group/member，或把 Shard 映射统计用于裁剪。索引是派生资产，必须绑定 Dataset/Shard 摘要和版本。损坏或漂移时应重建/失败，不能读到错误样本。不同格式可使用 Footer、Sidecar 或全局 Catalog。

### 3.9 Dataset Manifest

Manifest 列出 Schema、Recipe、所有 Shard/Index、总账、顺序/分区规则、父 Release 与 Policy。Reader 不列目录、不猜最新版本。Manifest 自身内容寻址或签名，训练 Run 保存摘要。物理 Location 可有多个 Replica，但对象版本/摘要一致。

### 3.10 Reader Plan

Reader Plan 在给定 world_size、rank、worker、epoch、seed、缓存和访问模式下，把 Shard/Record 分配与预取。它是运行派生但可重建；改变 world_size 可能允许不同物理顺序，但逻辑 Epoch 语义要定义。Plan 不能依赖进程到达顺序或默认 Hash。

### 3.11 Consumption Receipt

训练侧记录实际打开的 Shard、校验、样本/Token、跳过/错误、epoch/seed 和 Checkpoint 位置。期望 Manifest 与实际 Receipt 对账，发现 Reader 少读、重复或损坏。Receipt 以 Rank/Worker 局部聚合后全局合并，不为每 Token 写远程日志。

## 4. Schema 设计

### 4.1 强制字段

任何训练记录至少包含 sample_id、payload 或其结构字段、source references、recipe/schema version 和逻辑长度。训练热路径可以把血缘压缩成整数/sidecar 引用，但 Dataset 仍能从 sample_id 查回。只存 text/token 而无身份，会使退出、去污染和故障难以定位。

### 4.2 嵌套与扁平

对话、偏好和工具轨迹天然嵌套。JSON/Arrow/Parquet 可表达列表/Struct，Tar 可用多个成员，Token Bin 通常需 Sidecar。完全扁平会重复 conversation 元数据并破坏关系；过深嵌套又让某些引擎/UDF 难处理。逻辑 Schema 保真，训练热视图可单独序列化成扁平 Token 样本。

### 4.3 可空与 Unknown

Null 表示字段已知为空，缺失表示 Schema/来源未提供，Unknown 治理状态最好显式枚举。不要把空字符串、零和 Null 混用。Parquet/Arrow validity bitmap、JSON 字段缺失和二进制 sentinel 映射要统一，跨 Reader 契约测试。

### 4.4 数字类型

Token ID 最大值决定 uint16/int32/int64 等 dtype；选择太宽浪费 IO/缓存，太窄溢出。长度、offset 和 Token 总数使用足够宽整数，文件超过 4GB 时 32 位偏移危险。浮点权重/Reward 明确 FP32/FP16 和 NaN 策略。写 Reader 时验证范围，不做静默截断。

### 4.5 字符串与二进制

原文使用规范 UTF-8，非法输入应在上游得到状态；图片/音频等是 binary 或对象引用，不 Base64 塞入 JSON 造成约三分之一放大与额外解码。大二进制可与元数据共 Tar Shard 或独立对象，但成员关系/摘要保留。

### 4.6 Schema 演进

新增可选字段可向后兼容；修改语义、类型或必填需要新主版本。Reader 声明支持范围，未知主版本失败。Dataset Release 固定 Schema，不让同目录不同 Shard 随机字段类型。迁移写新 Shard/Manifest，旧训练仍可读旧版。

### 4.7 热路径与冷路径

冷路径保存完整 Text、结构、血缘和诊断；热路径保存训练所需 Token、边界、Mask 与紧凑引用。热数据可重建，并绑定父 Dataset/Tokenizer/Pack Recipe。不要用训练优化格式取代长期可解释资产，也不要让热 Reader 解析复杂冷 Schema 浪费 CPU。

## 5. JSON 与 JSONL

### 5.1 优点

JSON 可读、生态广、调试方便；JSONL 每行一个记录，顺序扫描、分段恢复和流式 Writer 简单。早期数据交换、失败样本、Manifest 和中等规模 SFT 数据常适合。稳定字段/排序后可计算记录摘要。

### 5.2 限制

字段名重复、数值/字符串冗长、Base64 放大；逐行解析 CPU 成本高；Schema 常靠约定；嵌套长行使 Range 切分困难；压缩整个 `.jsonl.gz` 后通常难随机定位。小文件再叠加对象存储请求开销，训练吞吐会很差。

### 5.3 分割

未压缩 JSONL 可在 Range 中寻找下一换行作为安全起点，但必须限制最大行长并处理字符串中的换行已经被转义的前提。Shard Builder 更应在写出时记录每行 offset/length 和摘要。压缩时使用独立 Shard 或可分块压缩，不把整个 Dataset 做单 gzip 流。

### 5.4 类型契约

JSON 数字没有统一物理宽度，Reader 可能将大整数转浮点；必须 Schema 验证。JSON 对象 Key 顺序不影响语义但影响字节摘要，Canonical Digest 对规范序列化计算。不要用 Python 默认 `str(dict)` 作长期身份。

### 5.5 使用边界

适合可读交换、控制面和规模可控复杂样本；不适合直接承载数万亿 Token 热训练数据。可从 JSONL 冷资产编译为 Parquet/Arrow 或 Token Shard，编译过程有 Manifest 和总账。

## 6. Parquet

### 6.1 物理层次

Parquet File 包含多个 Row Group；每 Row Group 为每列存一个连续 Column Chunk；Column Chunk 进一步由 Page 组成。Footer File Metadata 记录 Schema 和各 Column Chunk 位置/大小，Reader 通常先读文件尾部元数据，再定位需要的列。Row Group 是常见并行/裁剪单位，Page 是编码/压缩更细单位。

这种列式布局适合只读部分列、基于统计跳过 Row Group 以及批量扫描。对 Dataset 画像、Join、过滤、质量特征和复杂 Schema 非常有效。训练若最终只需 tokens/labels/mask，也可投影这些列，但逐样本随机访问可能反复读 Page/Row Group，需按访问模式评估。

### 6.2 Row Group 大小

大 Row Group 提高顺序 IO 和压缩，减少 Footer 元数据，却需要 Writer 缓冲、更粗裁剪和失败/随机读放大；小 Row Group 相反。目标依据对象存储 Range、列宽、并发、Worker 内存和查询选择率实测，不直接照搬旧 HDFS 建议。每 File 含适量 Row Group，避免一 File/RowGroup 极端。

### 6.3 Column Projection

Reader 只选择 ID、长度和 quality 时无需读正文 Column Chunk，适合先筛选再取 Payload。若 Python UDF 要求整行，会破坏投影优势。将大 text/binary 与常用元数据分列，统计/过滤可显著少 IO。Explain/实际 Range 验证，不从 API 意图推断。

### 6.4 Predicate 与统计

Row Group/Page 统计、Column Index、Bloom Filter 等可帮助跳过数据，但统计可用性取决于 Writer/类型/实现。Min/max 对随机 ID 筛选未必有效；按 Source/日期排序可提升裁剪却引入写出 Shuffle。统计是优化，不替代逐行 Policy/正确性。

### 6.5 嵌套数据

Parquet 用定义/重复层级表达嵌套，Arrow/Spark 等 Reader 可映射 List/Struct。不同实现对 Map、空列表、Null 列表和时间逻辑类型可能有差异，需要跨语言 Golden。复杂对话写入后检查往返，不只 Schema 字符串。

### 6.6 Compression 与 Encoding

列可按类型使用字典、RLE/位打包、Delta 等 Encoding，再用压缩 Codec。低基数字符串字典有效，高基数长文本可能字典膨胀；Token 整数分布也需实测。压缩节省网络/存储但消耗 CPU，GPU 等待时优先看端到端 Token/s。

### 6.7 Footer 与对象存储

Reader 为取 Footer 先读尾部 Range，再读 Column Chunk。大量小 File 导致请求多，Footer 过大也有延迟。缓存 Footer/元数据必须绑定对象版本/摘要。若对象被 append/覆盖，旧 Footer 与新数据会灾难性错配，因此 Shard 不可变。

### 6.8 适用场景

适合数据湖分析、列裁剪、过滤/Join/统计、SFT/偏好复杂记录冷/中间层。预训练热 Token 顺序扫描可比较 Parquet token list 与专用 Bin/Idx；谁更优由 CPU 解码、IO、随机/断点和生态决定。

## 7. Arrow 与 IPC

### 7.1 内存列式格式

Arrow 定义跨语言的列式内存布局，常用 validity、offset 和 value buffers 表达数组，RecordBatch 携带同一 Schema 的一批行。它减少 DataFrame/进程/语言间逐对象转换，是 Ray Data、Pandas/Parquet 等生态的重要交换层。零拷贝是条件性能力，不是所有转换都零拷贝。

### 7.2 IPC Stream

IPC Stream 通常先发送 Schema，再发送 Dictionary/RecordBatch 消息，按序读取，适合管道/网络和未知长度流；它不提供文件尾部随机访问索引，通常从头消费。EOS/流关闭与消息边界必须处理，截断产生明确错误。
