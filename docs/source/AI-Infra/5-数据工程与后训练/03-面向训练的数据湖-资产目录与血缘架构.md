# 面向训练的数据湖、资产目录与血缘架构

## 1. 本文要解决的工程问题

某个来源要求退出后，团队在最终 JSONL 里搜索 URL，却发现样本经过解析、拼接、合成和 Tokenization，原始标识早已丢失。

本文围绕一个可执行判断展开：怎样让任一训练样本都能回溯到来源、配方、处理任务和发布版本？读完应能给出自己的系统边界、输入输出、版本关系和验收证据，而不是只复述工具名称或公式。

## 2. 本文交付物与判定标准

本文的核心决定是：把数据湖的物理快照、资产目录的逻辑身份与事件化血缘分开设计，并让删除墓碑沿派生关系传播。

完成学习和实验后，应当交付一份最小可复现记录，至少包含输入快照、配置、代码版本、运行状态、原始输出和结论边界。验收证据是：随机抽取样本能回到原始对象；给一个 source_id 写入退出事件后，影响分析能列出派生数据集、训练运行和检查点。

围绕“面向训练的数据湖、资产目录与血缘架构”的验收不接受三类替代品：把模拟输出写成真实 GPU 结果；只展示成功样本而隐藏失败与 `SKIPPED`；只给总分，不保存能复算总分的对象级记录。

## 3. 前置知识与实验边界

“面向训练的数据湖、资产目录与血缘架构”的机制实验使用 Python 3.10 及以上版本和标准库，重点验证对象、算法或状态转换。真实硬件路径使用 PyTorch；检测不到 CUDA 时必须输出结构化 `SKIPPED`，不得静默改跑 CPU 后仍标成 GPU 实测。

血缘能定位影响范围，是否删除、下架、重训或接受风险仍由治理责任主体决定。

### 3.1 业务背景与失败模式

很多训练项目从一个共享目录开始：原始文件放在 `raw/`，清洗结果放在 `clean/`，分词结果放在 `tokenized/`，训练脚本读取一个名为 `final` 的路径。项目规模较小时，这种目录约定能够工作；当来源、处理版本、模型团队和训练运行增加后，同一个文件名会出现多个含义，覆盖、复制和局部失败会让团队无法回答最基本的问题。

一次模型回归发生后，工程师需要知道它使用了哪个数据版本；某个来源撤回授权后，治理团队需要知道哪些文档、样本、Shard、Checkpoint 和线上模型受到影响；Tokenizer 升级后，训练团队要重建 Sequence，却不希望重新下载和解析所有 Raw；数据过滤器升级后，评审者要比较新旧版本中谁进入、谁退出、原因是什么。仅靠对象存储路径无法可靠完成这些任务。

数据湖解决大规模、低成本保存多种数据的问题，但“把文件放进对象存储”只是数据平面的一部分。面向模型训练的数据基础设施还需要资产身份、不可变版本、目录、Recipe、运行、血缘、事务发布、访问策略、删除传播和训练消费回执。它们共同把松散文件转化为可以被引用、复现、审计和回滚的数据产品。

本文从训练任务的需求反推架构。重点不是比较某个云厂商产品，而是建立一组独立于具体工具的对象合同：Blob 表示不可变内容，Asset 表示有语义的数据集合，Manifest 列出版本包含的对象，Recipe 描述怎样从输入生成输出，Run 记录一次执行，Lineage Edge 连接父子，Alias 为人提供可变入口，Release 决定什么能够进入训练。

### 3.2 学习目标与能力清单

完成后应当能够：

1. 区分对象存储、数据湖、Lakehouse、资产目录、元数据存储和血缘系统的职责。
2. 解释为什么数据内容、逻辑资产、版本、快照和别名必须使用不同 ID。
3. 使用内容寻址、Manifest 与不可变提交构建可复现数据版本。
4. 设计 Raw、Parsed、Silver、Gold、Train-ready 等层次，同时避免层名成为含糊文件夹。
5. 为 Source、Document、Sample、Sequence、Shard 和 Dataset Release 建立最小资产 Schema。
6. 区分静态列级血缘、运行级血缘、样本级血缘和模型反向血缘。
7. 将代码、参数、容器、Tokenizer、评分器和输入版本封装成可重放 Recipe。
8. 设计候选、验证、发布、别名切换和回滚的事务流程。
9. 处理删除请求、Tombstone、代表重选、派生资产失效与模型影响分析。
10. 通过 CPU 机制实验实现内容寻址目录和影响查询，通过 CUDA 实验证明训练运行可以锁定并验证数据 Manifest。

### 3.3 实验准备与责任边界

本文需要理解文件、目录、JSON、哈希、关系数据库基础和训练数据的一般流程。机制实验使用 Python 标准库、SQLite 与本地文件系统模拟对象存储、目录和血缘。SQLite 只是为了把事务与查询讲清楚，不表示生产规模的数据目录必须使用单机数据库。

真实硬件实验使用 PyTorch DistributedDataParallel，在至少一张可用 CUDA GPU 上读取由 Manifest 锁定的 Token Shard，校验内容哈希，执行真实前向、反向和 AllReduce，并把数据提交 ID 写入 Checkpoint。实验会故意修改一个工作副本，验证训练在哈希不一致时拒绝启动。

没有至少一张 CUDA GPU、依赖不足或显存不满足时，程序输出结构化 `skipped`。CPU 目录实验不能冒充数据湖生产基准，CUDA 单卡小模型实验也不能证明对象存储在大集群上的吞吐、元数据扩展性或跨区域一致性。

## 4. 数据湖、Lakehouse、目录与血缘分别解决什么

### 4.1 对象存储负责保存字节

对象存储以 Bucket、Key 和 Object 保存字节，通常提供高耐久、水平扩展、按对象读写和元数据标签。它适合 WARC、Parquet、压缩 JSONL、音频、图片、Token Shard 和 Checkpoint 等大对象。

对象存储不是传统 POSIX 文件系统。重命名目录可能实际意味着复制与删除；列出大量小对象成本高；原子操作通常以单对象为边界；强一致语义和版本能力取决于实现。训练系统不应假设 `mv directory_a directory_b` 是低成本原子事务，也不应依赖全量 `list` 来发现正式数据版本。

对象 Key 是位置，不是稳定身份。相同内容可以复制到多个 Key；同一个 Key 也可能被覆盖。若训练只记录路径，之后无法证明当时读取的字节。需要在 Key 之外记录内容哈希、大小、对象版本和 Manifest。

### 4.2 数据湖负责组织多层原始与派生数据

数据湖允许以接近原始形式保存大量结构化、半结构化和非结构化数据，再由不同计算引擎处理。它为模型数据提供低成本历史保留、跨格式处理和重新构建能力。

数据湖的关键价值不是“什么都往里放”，而是保存不可逆处理之前的证据，使解析器、过滤器、Tokenizer 和训练目标变化后可以重算。没有目录、Schema 和治理的数据湖会退化为 Data Swamp：文件存在，但不知道含义、质量、所有者和用途。

### 4.3 Lakehouse 为表型数据增加事务与快照

Parquet 等列式文件适合批量统计，但一组 Parquet 文件本身不提供表级事务。Lakehouse 表格式通常通过元数据文件、Manifest、Snapshot 和乐观并发控制，为对象存储上的数据增加原子提交、Schema 演进、分区演进、时间旅行和增量读取。

这类能力适合 Document 元数据、质量特征、过滤决策、样本索引和运行统计。大型 WARC、媒体和 Token 二进制 Shard 可以继续作为对象，由表保存引用与属性。不要为了“统一”把每个任意二进制都强行塞进表，也不要让表里只有路径却没有内容哈希。

### 4.4 资产目录负责发现与解释

目录回答“组织拥有哪些数据资产”。它保存名称、稳定 ID、版本、Schema、所有者、用途、标签、许可、质量摘要、位置、上下游和发布状态。搜索“中文代码 SFT、允许商业训练、2026 年更新”应返回候选资产，而不是要求用户遍历 Bucket。

目录中的描述性元数据可以更新，例如负责人、说明和标签；被训练引用的版本内容不能随描述更新而变化。目录需要明确区分可变描述与不可变版本事实。

### 4.5 血缘系统负责解释怎样产生以及影响谁

真实图可能多对多，不能把单条示意链当作完整影响集合。

血缘连接输入、处理和输出。它至少回答：某个 Gold 数据版本由哪些 Parsed 版本和 Recipe 生成；某个 Shard 包含哪些 Sample；某次训练消费哪些 Shard；某个 Checkpoint 由哪个数据版本和代码产生。

血缘既支持正向追踪，也支持反向影响分析。正向追踪从来源走到模型，解释生产过程；反向追踪从问题对象找所有派生资产和模型，支持撤回、事故和重建。

### 4.6 元数据存储不是把所有信息复制一遍

上层保存引用，下层保存内容，不要求每层复制全文。

内容、热路径属性、统计、目录描述、血缘边和运行日志有不同访问模式。把所有内容放在一个关系数据库会昂贵且难扩展；只把元数据写在对象旁边的 JSON 又难以全局查询。

合理架构让对象存储保存大内容，表或索引保存可查询元数据，图或关系边保存血缘，日志系统保存运行事件，目录提供统一视图。它们通过稳定 ID 关联，而不是复制整份内容。

## 5. 资产身份应该怎样设计

### 5.1 路径、名称与身份不能混为一谈

人类喜欢 `latest-clean-data` 这样的名称，但机器训练需要不可变引用。建议区分：

- `blob_id`：由内容哈希和算法确定，标识一段不可变字节。
- `object_id`：标识来源对象或逻辑文档，可跨多次内容修订。
- `asset_id`：标识一类数据产品，例如“中文技术文档 Gold”。
- `version_id` 或 `commit_id`：标识该资产一次不可变提交。
- `snapshot_id`：标识表或视图在某时刻的一致快照。
- `alias`：如 `candidate`、`stable`、`production`，指向某个提交，可原子切换。

训练配置可以写 `asset_id + commit_id`，不能只写 Alias。Alias 适合启动前解析，解析结果连同 Commit 写入运行；运行中 Alias 改变不应影响已启动任务。

### 5.2 内容寻址怎样工作

内容寻址把字节哈希作为身份的一部分：

$$blob_id=algorithm:hash(bytes)$$

例如 `sha256:...`。上传内容前计算哈希，相同字节可以复用 Blob；Manifest 记录 Blob、大小、逻辑路径和媒体类型。读取时重新校验哈希，发现静默损坏或错误覆盖。

哈希相同证明字节相同，不证明语义、许可或安全相同。同一公开内容从两个许可来源取得，Blob 可以相同，但 Source Relationship 和使用条件仍要分别保存。Blob 去重不能覆盖来源治理。

### 5.3 Manifest 是提交的内容边界

一个数据版本不能由“某前缀下当前有哪些文件”定义，因为目录会继续变化。Manifest 显式列出版本包含的对象：

```json
{
  "asset_id": "asset-tech-zh-gold",
  "commit_id": "commit-2026-09-0017",
  "parent_commit_id": "commit-2026-08-0012",
  "schema_version": "document-v4",
  "recipe_id": "recipe-gold-filter-v8",
  "objects": [
    {
      "logical_path": "shards/00000.parquet",
      "blob_id": "sha256:...",
      "size_bytes": 734003200,
      "row_count": 1200000
    }
  ]
}
```

Manifest 自身也应规范序列化并计算哈希，形成 Commit。列表顺序、字段默认值和时间格式需要确定，否则同一逻辑内容会产生不同哈希。

### 5.4 逻辑对象为什么还需要稳定 ID

文档重新解析后字节会改变，Blob ID 也改变，但治理团队仍希望知道“这是同一个抓取对象的新解析版本”。因此 Object ID 来自来源定位、Capture 和稳定规则，而 Blob ID 来自内容。

Sample 从 Document 派生时也需要稳定或可解释 ID。可以用父对象、Recipe 和局部选择器生成：

$$sample_id=H(document_id,recipe_id,selector)$$

`selector` 可以是段落范围、对话轮次、代码符号或任务生成索引。这样同一 Recipe 重跑得到同 ID，Recipe 改变则产生新 Sample。

### 5.5 ID 设计需要避免什么

不要使用数据库自增 ID 作为跨系统唯一身份；迁移或重建数据库后 ID 会改变。不要直接把长路径作为 ID；路径重组会造成血缘断裂。不要把可识别个人信息放入 ID；哈希也可能被字典攻击。

ID 应带类型或命名空间，避免 Document ID 与 Run ID 碰撞。哈希算法要显式记录，不能假定永远是 SHA-256。随机 UUID 适合 Run、人工任务等事件身份，内容对象更适合确定性 ID。

## 6. 数据湖分层怎样避免成为文件夹命名游戏

### 6.1 每一层必须定义不变量

Raw、Bronze、Silver、Gold、Train-ready 是常用名称，但行业没有统一含义。团队需要为每层写出允许输入、输出 Schema、可执行处理、不可逆操作、质量门禁、责任人和保留策略。

如果 `silver/` 里同时有原始 HTML、清洗文本和 Token ID，分层没有提供边界。层的价值来自不变量，而不是颜色名称。

### 6.2 Raw 层保存来源证据

Raw 保存取得的原始字节、Source Capture、协议头、导出清单、校验和和许可证据。默认不可原地修改。若源系统只允许短期保留，至少保存允许范围内的哈希、元数据和删除证明。

Raw 不保证内容适合训练。它可能包含恶意文件、PII、损坏编码和重复对象，访问权限通常比 Gold 更严格。训练任务不应直接读取 Raw。

### 6.3 Parsed 或 Bronze 层保存可解释结构

Parsed 将 WARC、HTML、PDF、代码仓库和对话导出转换为 Document，保留原始定位、块结构和解析错误。它应尽量可逆或可回到 Raw，不进行大量不可解释删除。

解析器升级会生成新版本。旧版本在保留期内继续可用，以便比较回归。解析失败也是资产，需要记录错误类型和原对象，而不是只留下成功输出。

### 6.4 Silver 层保存特征与治理状态

Silver 通常完成规范化、语言识别、基础质量特征、PII 检测、安全标签和许可决策。建议保留原文视图与规范视图，所有不可逆修改生成新字段或新对象。

规则命中不等于立即删除。Silver 可以保存 `accept`、`quarantine`、`reject` 和 `repair` 决策，使评审者看到每条规则的证据和版本。

### 6.5 Gold 层表示特定用途下的可选数据

Gold 完成去重、去污染、质量门禁、能力标签和来源治理，适合某类训练用途。一个 Document 可以进入预训练 Gold，却不进入医疗 SFT Gold；Gold 不是全组织唯一的“最好数据”。

Gold 版本需要附带统计、已知限制、重复簇和删除传播状态。它仍未绑定具体 Tokenizer 和训练框架。

### 6.6 Train-ready 层绑定训练合同

Train-ready 将 Gold 转换为 Sample 和 Sequence，绑定 Tokenizer、Chat Template、Loss Mask、最大长度、Packing、Shard、索引和 Mixture。相同 Gold 可以产生多个 Train-ready 版本，用于不同模型或训练阶段。

训练任务只需读取 Manifest 与 Shard，不在热路径临时重新清洗。这样训练复现和性能更稳定，也能精确统计 Label Token 与消费游标。

### 6.7 层之间为何不能覆盖写

覆盖写会破坏重放、版本比较和删除传播。处理输出先写临时不可见位置，全部分区完成后生成 Manifest 并提交新 Commit。旧 Commit 保留，Alias 在事务中切换。

垃圾回收可以在保留期后删除没有任何 Commit 引用的 Blob，但必须检查血缘、审计、法律保留和运行中的训练租约。垃圾回收不是简单删除旧目录。
