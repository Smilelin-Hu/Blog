# Prefix、Session 与 KV-Locality Routing

## 1. 课程定位

“如何在缓存命中与副本负载之间求解跨副本路由决策？”贯穿本文。先把 Prefix Cache、Session Affinity 及其状态边界讲清楚，再讨论计算、实现和上线证据。在 Prefix、Session 与 KV-Locality Routing 中，算法选择只是决策的一部分；负载分布、模型修订、调度、显存、并发和服务等级都会改变结论。每项收益都需要对应可观察的事件与适用范围。

个人电脑即可完成本文的双路径验证：CPU 模拟负责检验 Prefix Cache 到 Session Affinity 的方向，CUDA 实验负责测量真实执行代价。模拟、实测和外部资料不会混用。围绕 Prefix Cache 得出的结果只对记录的模型、软件、设备和负载负责，同时给出失败原因与回滚入口。

## 2. 学习目标

1. 准确解释 Prefix Cache、Session Affinity 和 KV Locality 之间的状态与资源关系。
2. 使用“route_value_i = reusable_tokens*prefill_cost - queue_penalty_i - staleness_penalty_i”建立可计算的收益边界并解释全部变量。
3. 围绕可复用 Token、Prefill 节省、缓存命中率和 TTFT 设计可复现实验。
4. 识别高命中率副本严重排队、缓存键忽略模板或模型版本和目录显示命中但数据已驱逐等典型失败模式。
5. 对“如何在缓存命中与副本负载之间求解跨副本路由决策？”给出包含适用条件、证据、风险和回滚的工程答案。

## 3. 前置知识与环境

阅读 Prefix、Session 与 KV-Locality Routing 需要理解自回归生成、Tokenizer、Prefill、Decode、KV Cache、批处理和分位延迟的基本含义。涉及 Prefix Cache 时，所有缩写都会在正文首次出现处定义；没有某个特定框架经验不妨碍理解机制。实验需要 Python 3.11 或兼容版本。围绕 Prefix Cache 的机制模拟只依赖 CPU；真实路径需要任意可用的 CUDA GPU、与驱动兼容的 PyTorch，以及自行准备的本地小模型或兼容制品。

验证 Prefix Cache 前必须记录 GPU 名称、数量、可用显存、驱动、CUDA、PyTorch、推理框架、模型摘要、精度、批量、序列长度和完整命令。脚本根据可用显存缩放模型、批量、上下文和样本数，并把 Prefix Cache 状态写入报告；可选 CUDA 入口不下载未经确认的大模型。

## 4. 工程问题

Prefix、Session 与 KV-Locality Routing 没有脱离环境的统一加速数字。评审记录应包含模型修订、长度分布、到达过程、并发、采样、缓存、可复用 Token 定义、服务等级和硬件；随后才能比较“定义缓存键与身份”和“估算前缀节省”。缺少这些信息时，局部速度无法换算成系统收益。

需要纳入同一证据链的对象包括：Prefix Cache、Session Affinity、KV Locality、可复用 Token、缓存目录、负载惩罚、模型修订、缓存驱逐。它们并不处在同一个组件中，却会一起改变驱逐率和 TTFT。正文按 Prefix Cache 的生命周期、状态归属、测量位置和失败条件展开，再将同一方法应用到其他对象。

## 5. 知识串讲

### 5.1 核心直觉：少做一次昂贵加载/重算，有时比去最空的 Replica 更值

Locality Routing 的本质不是“粘住请求”，而是在排队成本与状态复用收益之间动态比较。

### 5.2 Prefix Locality

Replica A 已缓存某个长 system prompt 的 prefix state。

同类请求送 A 可以减少重复 Prefill。

### 5.3 Session Locality

多轮对话历史状态在 Replica B。

下一轮继续送 B，可能复用已有状态。

### 5.4 Adapter Locality

LoRA X 已加载在 Replica C。

送 C 可以避免动态加载。

### 5.5 Model Locality

冷门 Model Y 只驻留在 Replica D。

请求 Y 最好直接路由 D，而不是随机发到别处后再加载。

### 5.6 Locality 与 Load 的冲突

假设：

![Prefix 命中 vs 队列负载：算总账再路由](https://raw.gitcode.com/weixin_42917352/image-host/raw/main/images/aiinfra_y3_l18_02.png)

A 不是最优。

可以定义：

$$Score_i=QueueCost_i+MissCost_i+LoadCost_i$$

其中：

$$MissCost_i=PrefillTime(UncachedTokens_i)$$

选择最小：

$$i^*=\arg\min_i Score_i$$

Locality 只是一项成本，不应凌驾于所有负载信息之上。

### 5.7 Cache Affinity 不是 Sticky Forever

“同一 Session 永远固定一个 Replica”实现简单，但会出现：

- Replica 宕机后无法迁移；
- 长 session 把某个实例绑死；
- 热门租户造成热点；
- 缓存已被驱逐但 Router 仍认为有 locality。

更合理的是 soft affinity：

```text
命中优先
但负载差距超过阈值时允许迁移
```

### 5.8 Locality Metadata

Router 可能维护：

```text
replica_id
model_ids
adapter_ids
prefix_fingerprints
session_handles
last_update
capacity/load
```

问题是 Prefix 数量可能巨大，不能把全部 cache key 同步到所有 Router。

可以使用：

- Bloom filter；
- prefix summary；
- event stream；
- sampled hot keys；
- hierarchical router。

目标是：用有限元数据获得足够好的 routing signal。

### 5.9 一致性：Router 看到的状态可能已经失效

例如：

1. A 报告持有 prefix P；
2. Cache pressure 导致 P 被驱逐；
3. Router 尚未收到事件；
4. 新请求仍被发到 A。

这种 stale metadata 不应导致 correctness error，只应导致性能 miss。

因此：

locality metadata 必须设计成“提示”，而不是正确性前提。

真正的 Cache 命中仍由 Replica 本地确认。

### 5.10 多租户安全

- 不允许通过 route decision 泄漏别的租户是否存在某个 prefix；
- 不能跨安全域共享 session affinity；
- adapter/model residency 信息的可见范围需要控制。

性能信息也可能形成侧信道，所以平台接口不应返回过细的其他租户缓存状态。

### 5.11 Adapter/Model Locality 与缓存有什么不同

Prefix locality 是“可重算状态”；Adapter/Model locality 是“Artifact 已驻留”。

Miss cost 不同：

$$Cost_{prefix-miss}\approx PrefillRecompute$$

$$Cost_{adapter-miss}\approx AdapterLoad$$

$$Cost_{model-miss}\approx ModelLoad/ColdStart$$

Model miss 可能远大于 Prefix miss，因此多模型环境里 Residency 通常拥有更高路由权重。

### 5.12 Smart Router 模拟器扩展

在 Smart Router 模拟器中加入：

- prefix hit saved_ms；
- session affinity；
- adapter load cost；
- stale metadata probability。

比较：

1. Load-only；
2. Locality-only；
3. Weighted cost；
4. Soft affinity。

观察 P99 和 load imbalance。

### 5.13 Prefix Cache

解释 Prefix Cache 时，先列出它接收什么、产生什么、由谁维护以及状态何时结束。Prefix、Session 与 KV-Locality Routing 的请求可能在这些交界处增加等待、计算或复制。与 Session Affinity 交互的字段必须携带版本身份，便于回放时找到同一配置。

围绕 Prefix Cache 建立资源模型，需要把计算量、显存占用、内存流量、主机工作和等待时间单独记账。会话亲和维持跨轮 KV 状态会移动关键路径，却很少让所有资源同比例变化。请求事件负责说明顺序，资源曲线负责解释瓶颈转移。

平衡亲和与负载是否合适，取决于 Prefix Cache 所面对的长度分布、并发、到达过程、采样和任务域。实验在低载、接近饱和、过载三段保留同口径证据。固定长度与固定批量的结果用于解释机制，不承担完整容量结论。

Prefix Cache 带来的速度变化仍需满足模型输出合同，包括 Token 序列、采样分布、结构合法性、结束原因和错误传播。出现会话亲和在副本故障后丢失时，质量门禁应停止性能发布；回退目标是已验证配置，并保留问题请求用于复现。

Prefix Cache 的观测记录包含请求身份、模型版本、策略版本、阶段时间、资源状态与失败原因。副本队列没有单位、统计窗口和分母时不参与决策。完整记录用于复查“如何在缓存命中与副本负载之间求解跨副本路由决策？”在具体负载下是否成立。

### 5.14 Session Affinity

Session Affinity 在 Prefix、Session 与 KV-Locality Routing 中的生命周期需要落到组件接口：输入从哪里来，状态由谁持有，输出交给谁，失败如何传播。它与 KV Locality 之间的身份和版本若未绑定，请求时间线就可能混入旧配置。

缓存收益应按节省时间而非命中率估计对 Session Affinity 的影响会分散到计算、显存、内存带宽、主机处理和同步等待。某一阶段变短时，被遮蔽的成本可能随即暴露。为确认 Session Affinity 的变化来自哪里，本文对齐请求时间线与资源采样，而非只看整段运行的 GPU 平均值。

Session Affinity 的边际价值会随输入长度、输出长度、并发、流量突发、采样和任务域变化。验证设置热点分流阈值时分别运行低载、接近饱和与过载区间，并使用代表性分布。单一长度、批量或短窗口只能说明该测试点。

正确性门禁覆盖 Session Affinity 影响到的 Token、采样、结构、结束状态与错误。若检测到攻击者构造热点前缀，当前性能结果不进入候选评审，并立即切回已验证配置。失败样本与版本信息要一并保存。

为 Session Affinity 建立证据链时，统一保存请求 ID、模型及策略修订、关键时间点、资源快照和错误。热点分流率的定义随报告存档，包括单位、窗口和分母。这样才能按同一条件重放“如何在缓存命中与副本负载之间求解跨副本路由决策？”。

### 5.15 KV Locality

对 KV Locality 做边界检查，要覆盖输入、输出、状态归属和销毁时点。Prefix、Session 与 KV-Locality Routing 的等待、计算及复制都能沿这些节点定位。KV Locality 传给可复用 Token 的数据还应附带模型或策略版本，使测量结果可以对应到唯一配置。

KV Locality 的资源账要拆成计算、显存、内存带宽、主机开销和同步等待。热点亲和会把请求集中到少数副本通常只先改变其中几项，其他资源随后可能进入关键路径。KV Locality 的请求时间线和资源曲线可以呈现这种转移，平均 GPU 利用率只作为辅助信号。

工作负载一变，KV Locality 对系统的贡献也会变化。传播缓存目录应覆盖长短输入、不同输出、并发、突发、采样与任务域，并保留低载、稳定高载和过载记录。容量判断不能从一次固定批量的短运行外推。

对 KV Locality 的优化只有在输出合同不变时才有效。Token 序列、采样分布、结构合法性、结束原因和错误传播均需对账。只统计命中率不统计节省时间会触发停止与回退，系统恢复到已有证据支持的配置。

KV Locality 相关事件要能关联到稳定请求身份、模型与策略版本、开始结束时间、阶段耗时、资源采样和失败原因。驱逐率必须附带口径。缺少这些信息时，关于“如何在缓存命中与副本负载之间求解跨副本路由决策？”的判断无法在上线后复核。

### 5.16 可复用 Token

在 Prefix、Session 与 KV-Locality Routing 中，可复用 Token 的边界由输入、输出、状态和拥有者共同确定。把生命周期写清楚，才能定位请求在哪个阶段等待、计算或复制。可复用 Token 连接缓存目录时还要传播身份和版本，避免把另一套配置的结果归到当前实验。

测量可复用 Token 时分别记录算力、显存、带宽、CPU 开销与同步。发生“模型和模板修订决定缓存身份”后，缩短的阶段可能让另一项资源成为瓶颈。分析因此对齐可复用 Token 的阶段事件和资源轨迹，不让单个平均利用率代替因果证据。

评估可复用 Token 需要把负载分布写入实验：输入输出长度、并发、到达突发、采样方式和业务域都可能移动收益边界。选择驱逐与失效策略至少比较低载、临近容量与过载，结论只覆盖实际运行过的区间。

可复用 Token 进入候选路径后，输出校验继续检查 Token、采样、结构、结束原因和错误传递。高命中率副本严重排队一旦出现，质量结果优先于速度数字；发布停止，流量回到已验证修订，相关请求留作重放。

观察可复用 Token 需要稳定请求身份、模型与策略修订、起止时间、阶段耗时、资源快照和失败原因。TTFT 同时注明单位、窗口和分母。这些字段使“如何在缓存命中与副本负载之间求解跨副本路由决策？”可以在发布后按原条件回放。

评估缓存驱逐需要把负载分布写入实验：输入输出长度、并发、到达突发、采样方式和业务域都可能移动收益边界。设置热点分流阈值至少比较低载、临近容量与过载，结论只覆盖实际运行过的区间。

缓存驱逐进入候选路径后，输出校验继续检查 Token、采样、结构、结束原因和错误传递。攻击者构造热点前缀一旦出现，质量结果优先于速度数字；发布停止，流量回到已验证修订，相关请求留作重放。

观察缓存驱逐需要稳定请求身份、模型与策略修订、起止时间、阶段耗时、资源快照和失败原因。目录新鲜度同时注明单位、窗口和分母。这些字段使“如何在缓存命中与副本负载之间求解跨副本路由决策？”可以在发布后按原条件回放。
