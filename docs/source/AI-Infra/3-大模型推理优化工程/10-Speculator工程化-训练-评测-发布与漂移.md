# Speculator 工程化：训练、评测、发布与漂移

本文回答的问题是「如何把 Speculator 当作独立制品管理，并用真实流量持续选择策略？」。先把 Speculator 独立制品、训练数据版本及其状态边界讲清楚，再讨论计算、实现和上线证据。算法选择只是决策的一部分：负载分布、模型修订、调度、显存、并发和服务等级都会改变结论，每项收益都需要对应可观察的事件与适用范围。

个人电脑即可完成双路径验证：CPU 模拟负责检验从独立制品到训练数据版本的方向，CUDA 实验负责测量真实执行代价。模拟、实测和外部资料不会混用。围绕独立制品得出的结果只对记录的模型、软件、设备和负载负责，同时给出失败原因与回滚入口。

## 1. 内容概览

- Speculator 独立制品、训练数据版本与离线评测矩阵之间的状态与资源关系。
- 用 $PolicyValue(x,s) = ExpectedSavedTime(x,s) - DraftCost(s) - CapacityPenalty(s)$ 建立可计算的收益边界并解释全部变量。
- 围绕兼容组合通过率、域级接受长度、策略命中率和制品加载成本设计可复现实验。
- 识别 Drafter 与 Target 修订错配、离线集合过度代表单一域、在线选择器使用不可观测特征等典型失败模式。
- 对中心问题给出包含适用条件、证据、风险和回滚的工程答案。

## 2. 核心直觉：Speculator 不是模型附件，而是需要独立生命周期的 Serving 组件

真正工程化后，Speculator 的问题不再只是「能不能产生候选」，而是训练数据来自哪里、如何评测、怎样与 Target revision 绑定、何时灰度、何时回退。前面几篇依次解决了草拟结构、条件特征、树验证与动态调度，本文把它们收拢到同一条制品生命周期上。

新一代 Speculation 的演化主线：

```text
减少 Target 串行轮数
      ↓
AR Drafter 自己成为瓶颈
      ↓
更强 EAGLE / MTP
      ↓
Parallel Drafting
      ↓
Block Diffusion DFlash
      ↓
更强 conditioning / DFlare
      ↓
Diffusion Draft Tree
      ↓
Confidence / Load-aware 动态验证
      ↓
Speculator Policy 成为 Serving 系统组件
```

这条主线比背算法名称更重要：每一步都在把「更多决策」从 checkpoint 移到运行时，而最后一步要求这些决策具备制品身份、评测证据与回滚路径。

## 3. 前置知识与实验环境

需要理解自回归生成、Tokenizer、Prefill、Decode、KV Cache、批处理和分位延迟的基本含义，并已掌握前几篇的整轮时间口径（$T_V$、$T_O$、Bonus Token、$C=E[A]+1$）。所有缩写都会在正文首次出现处定义；没有某个特定框架经验不妨碍理解机制。实验需要 Python 3.11 或兼容版本。机制模拟只依赖 CPU；真实路径需要任意可用的 CUDA GPU、与驱动兼容的 PyTorch，以及自行准备的本地小模型或兼容制品。

验证前必须记录 GPU 名称、数量、可用显存、驱动、CUDA、PyTorch、推理框架、模型摘要、精度、批量、序列长度和完整命令。脚本根据可用显存缩放模型、批量、上下文和样本数，并把制品状态写入报告；可选 CUDA 入口不下载未经确认的大模型。

评审记录应包含模型修订、长度分布、到达过程、并发、采样、缓存、兼容组合通过率定义、服务等级和硬件；随后才能比较「定义制品元数据」和「构建训练与评测数据谱系」。缺少这些信息时，局部速度无法换算成系统收益。

## 4. 训练数据：分布决定接受率

### 4.1 五类候选源与谱系

候选源：

1. 通用 instruction 数据；
2. coding/math 专项数据；
3. 真实匿名化 serving trace；
4. online teacher rollout；
5. 结构化输出/工具调用数据。

对 Speculator 而言数据分布的优先级非常高，因为 acceptance 直接依赖 $P_{serve}(x_{future}\mid context)$。如果训练和 Serving 分布偏移：

$$D_{KL}(P_{serve}\,\|\,P_{train})\uparrow$$

通常会表现为 position-wise acceptance 下降。注意 KL 的方向：是「服务分布相对训练分布」的偏移，而不是反过来。用训练分布去覆盖服务分布的采样方式会低估偏移程度。

谱系必须逐层可追溯：`dataset_id → snapshot → mixture_recipe → training_run → speculator_id`。任何一层缺失，发布记录就无法关联训练数据，漂移发生时也无法判断该重训还是该重校准。

### 4.2 域衰减的解析形式

设 Drafter 在训练域内的逐位置条件接受概率为 $p_k$，服务域与训练域不一致时每个位置乘以域衰减因子 $\rho<1$。由于 $s_k=\prod_{i\le k}p_i$，域外存活概率有干净的解析形式：

$$s_k^{OOD}=\rho^{k}\,s_k^{ID}$$

指数 $k$ 意味着**域偏移的代价随深度指数放大**：单位置只降 20%，第 8 个位置的存活概率就降到 $0.8^8=0.168$ 倍。这解释了为什么域漂移总是先表现为「深位置接受率塌陷」，而 top-1 accuracy 看起来只降了一点。

取两个域的专家曲线（推导设定，非实测）：

```text
位置 k:      1     2     3     4     5     6     7     8
code  p_k: 0.97  0.94  0.89  0.83  0.76  0.68  0.60  0.52
chat  p_k: 0.85  0.72  0.58  0.45  0.33  0.24  0.17  0.12
```

按 $E[A]=\sum_{j\le B}s_j$、$C=E[A]+1$ 算得 $B=8$ 时：code 域 $E[A]=4.544$、$C=5.544$；chat 域 $E[A]=2.044$、$C=3.044$。沿用前几篇口径 $T_{draft}=1.40$ ms、$T_V(B)=3+0.25B+0.01B^2$ ms、$T_O=0.3$ ms，则 $T_{round}(8)=7.34$ ms，自回归基线每 Token 3.56 ms。

### 4.3 专家 Drafter 与混合 Drafter 的交叉点

两种训练配方（推导设定，非实测）：

- **code 专家**：只用 code 数据训练，code 域 $\rho=1.0$，chat 域 $\rho=0.80$；
- **混合 Drafter**：code/chat 混合训练，相对各域专家曲线 $\rho=0.96$（略逊于专家，但远好于跨域专家）。

代入 $s_k^{OOD}=\rho^k s_k^{ID}$ 得（推导值，非实测）：

| 配方 | 域 | $E[A]$ | $C$ | $T_{eff}$ |
| --- | --- | --- | --- | --- |
| code 专家 | code | 4.544 | 5.544 | 1.324 ms |
| code 专家 | chat | 1.340 | 2.340 | 3.137 ms |
| 混合 | code | 3.987 | 4.987 | 1.472 ms |
| 混合 | chat | 1.884 | 2.884 | 2.545 ms |

专家在 chat 域的 $T_{eff}$ 是 3.137 ms，比自回归基线 3.56 ms 只好 11.9%——**跨域使用专家 Drafter 几乎等于关掉 speculation**。

按流量混合比例计算平均 $T_{eff}$（推导值，非实测）：

| code 占比 | code 专家 | 混合 Drafter | 混合相对专家 |
| --- | --- | --- | --- |
| 90% | **1.505 ms** | 1.579 ms | +4.9%（更差） |
| 80% | 1.687 ms | 1.687 ms | 0%（交叉点） |
| 70% | 1.868 ms | **1.794 ms** | −4.0% |
| 50% | 2.231 ms | **2.009 ms** | −9.9% |
| 30% | 2.593 ms | **2.223 ms** | −14.3% |

交叉点可以解析求出。设 code 占比 $x$，专家均值 $=3.137-1.813x$，混合均值 $=2.545-1.073x$，令两者相等：

$$x^*=\frac{3.137-2.545}{1.813-1.073}=\frac{0.592}{0.740}=0.80$$

**当线上主域占比超过 80% 时用域专家 Drafter，否则用混合训练 Drafter。** 这个阈值不是经验值，而是由两条 $T_{eff}$ 直线的斜率差决定的，域衰减因子变化时它会移动。因此训练配方的选择必须绑定线上流量结构，而流量结构变化本身就是需要监控的漂移信号。

## 5. 离线评测矩阵：四类指标与矩阵裁剪

### 5.1 离线评测不能只有 Accuracy

至少需要四类指标：

| 类别 | 指标 | 口径要求 |
| --- | --- | --- |
| Token | top-1 accuracy | 按位置分桶，注明是否含 Bonus |
| Token | position-wise accuracy | 逐位置 $p_k$，而非平均值 |
| Token | prefix survival | $s_k$，注明连乘起点 |
| Token | mean accepted length | $E[A]$，注明 $B$ 与域 |
| Cost | draft forward count | 每轮草拟前向次数 |
| Cost | draft ms | 每轮草拟耗时，注明是否含条件特征传输 |
| Cost | extra memory | Drafter 常驻显存，注明是否含双版本 |
| Cost | verification nodes/tokens | 每轮验证位置数或树节点数 |
| End-to-End | TPOT | 每输出 Token 时间，注明窗口与分位 |
| End-to-End | output token/s | 单请求与批次分别报 |
| End-to-End | batch throughput | 注明并发与到达过程 |
| End-to-End | P50/P99 | TPOT 与整轮时间分别报 |
| End-to-End | GPU-hour / output token | 注明是否含草拟与加载摊销 |
| Quality | 输出合同对账 | Token 序列、采样分布、结构合法性、结束原因、错误传播 |

Lossless speculative 仍需验证实现没有改变 Target semantics。Structured Output、LoRA、量化、stop sequence 等组合路径都要测试。**质量门禁优先于速度数字**：任何一类 Quality 指标不通过，性能结果不进入候选评审。

### 5.2 矩阵规模与两阶段裁剪

评测矩阵维度（推导设定）：域 5 × 上下文长度桶 4 × 并发档 3 × 算法 6 × 采样方式 2 = **720 组合**。

每组合 200 请求 × 256 输出 Token = 51200 Token，按自回归基线 3.56 ms/Token 估算需 $51200\times3.56=182272$ ms $=182.27$ s（推导值，非实测）。于是：

| 方案 | 组合数 | GPU-hour |
| --- | --- | --- |
| 全矩阵一次跑完 | 720 | 36.45 h |
| 粗筛（域 × 算法，固定中并发/中长度/greedy） | 30 | 1.52 h |
| 粗筛淘汰一半后精评（360 × 24 倍展开） | 360 | 18.23 h |
| 两阶段合计 | 390 | **19.75 h** |

两阶段裁剪节省 45.8%。代价是粗筛可能误杀「只在高并发或长上下文下才占优」的算法，因此粗筛必须保留每个算法至少一个非默认工况，且淘汰决策要记录依据。

### 5.3 单域过度代表的量化后果

设离线集合 80% code / 20% chat，而线上 30% code / 70% chat，使用混合 Drafter、$B=8$（推导值，非实测）：

| 集合 | 加权 $C$ | $T_{eff}$ | 预测加速比 |
| --- | --- | --- | --- |
| 离线（80/20） | 4.566 | 1.607 ms | 2.22× |
| 线上（30/70） | 3.515 | 2.088 ms | 1.70× |

离线把加速比高估 **29.9%**。原因是 $C$ 对域权重是线性的，而高接受域与低接受域的 $C$ 相差 1.7 倍，权重错配的误差被直接放大。

因此离线门禁必须**按域分别设阈值**，而不是只设一个全局 $E[A]$ 下限；同时报告离线集合的域权重与线上域权重的差，作为「结论适用范围」的一部分。

## 6. Speculator Registry 与制品元数据

### 6.1 元数据字段

建议元数据：

```yaml
speculator_id: dflash-qwen3-8b-code-v3
target_model: qwen3-8b
model_revision: ...
tokenizer_revision: ...
algorithm: dflash
max_draft_tokens: 16
training_domain: code
runtime_min_version: ...
verified_hardware:
  - H100
  - B200
compatibility:
  lora: conditional
  structured_output: tested
status: canary
```

Registry 的价值是：

- 防止 Target 升级后继续错误复用旧 Speculator；
- 支持 Canary / Rollback；
- Router 根据 workload 选择；
- 保留真实性能证据。

`status` 至少要有 `draft / canary / stable / deprecated / quarantined` 五态。`quarantined` 与 `deprecated` 必须分开：前者是「证据显示有问题、禁止路由」，后者是「不再演进、仍可回滚」。把两者混为一谈会导致回滚时找不到可用制品。

### 6.2 兼容矩阵规模与验证成本

制品数（推导设定）：Target 模型 4 × Target 修订 3 × 算法 6 × 训练域 3 = **216 个 Speculator 制品**。每个制品的兼容维度：LoRA 3 档 × Structured Output 2 档 × 量化 3 档 × 硬件 2 档 = 36，合计 **7776 个兼容组合**。

两类验证的成本相差一个数量级（推导值，非实测）：

| 验证类型 | 单组合规模 | 单组合耗时 | 全量 GPU-hour |
| --- | --- | --- | --- |
| 逐位输出对账（正确性） | 20 请求 × 128 Token | 9.11 s | 19.7 h |
| 完整性能评测 | 200 请求 × 256 Token | 182.27 s | 393.7 h |

正确性对账可以全量跑（19.7 GPU-h 换 7776 个组合的确定性结论），性能评测不行。按线上活跃组合占 8%（622 个）裁剪后为 31.5 GPU-h。**「兼容组合通过率」的分母必须是实际会被路由到的组合，而不是笛卡尔积总数**——用 7776 做分母会把通过率稀释到毫无意义。

### 6.3 Compatibility hash 与证据失效

把 `target_model + model_revision + tokenizer_revision + algorithm + speculator_revision + dtype + runtime_min_version` 拼成 Compatibility hash。任何一项变更都会使 hash 改变，旧的性能证据随之失效，但**正确性对账证据可以按字段分级复用**：tokenizer 未变时逐位对账结论仍成立，量化变更时则必须重跑。

这条分级规则决定了 Target 升级的实际成本：若升级只改权重不改 tokenizer，可复用大部分对账证据；若同时换 tokenizer，则全部制品的对账与性能证据都要重建。

### 6.4 制品加载成本

以 DFlash 四层 Drafter 为例，参数量对应 1.50 GiB（fp16，沿用前一篇 DFlare 的估算口径）。加载耗时（推导值，非实测）：

| 来源 | 带宽 | 传输耗时 | 加 SHA256 校验（1 GiB/s） | 合计 |
| --- | --- | --- | --- | --- |
| 本地 NVMe 缓存 | 3 GB/s | 0.50 s | 1.50 s | **2.00 s** |
| 对象存储 | 200 MB/s | 8.05 s | 1.50 s | 9.55 s |
| 远端 Registry | 50 MB/s | 32.21 s | 1.50 s | 33.71 s |

「制品加载成本」必须按缓存命中/未命中分别统计，并注明单位（秒/次切换）、窗口与分母。只报一个平均加载时间会掩盖「回滚时恰好未命中」这一最坏情况。

## 7. Target 兼容关系与修订错配

### 7.1 错配的四种形态

Drafter 与 Target 修订错配不是单一故障，而是四类：

| 错配类型 | 直接后果 | 是否改变输出合同 |
| --- | --- | --- |
| 权重修订变更 | 接受率下降，速度退化 | 否（仍 lossless） |
| Tokenizer 修订变更 | 候选 Token 序列语义错位 | **是** |
| 量化方案变更 | 分布偏移，深位置接受率塌陷 | 可能 |
| LoRA / adapter 变更 | 域偏移，等价于 $\rho<1$ | 否 |

只有 Tokenizer 错配会直接破坏正确性，其余三类表现为性能退化。但**性能退化同样需要门禁**：一个接受率降到接近 0 的 Drafter 仍在消耗草拟算力与验证预算，等于给系统加了纯开销。

### 7.2 错配的量化门槛

沿用第 4 节的 chat 域专家曲线（$C=2.340$、$T_{eff}=3.137$ ms）。若错配进一步把 $\rho$ 从 0.80 压到 0.60，则 $s_k$ 再乘 $(0.60/0.80)^k=0.75^k$：

$$E[A]_{0.60}=\sum_{k\le8}0.75^k\,s_k^{0.80}$$

逐项计算（推导值）：$0.75\times0.68=0.510$、$0.5625\times0.39168=0.2203$、$0.4219\times0.18174=0.0767$、$0.3164\times0.06543=0.0207$、$0.2373\times0.01727=0.0041$、$0.1780\times0.003316=0.0006$，后两项可忽略。合计 $E[A]\approx0.832$，$C\approx1.832$，$T_{eff}=7.34/1.832=4.007$ ms。

**4.007 ms 已经慢于自回归基线 3.56 ms（+12.6%）**。这给出一个可直接落地的门槛：当某制品在某域的 $T_{eff}$ 超过基线时，Registry 应自动把它在该域标记为不可路由，而不是等人工发现。

### 7.3 解耦发布的代价

独立版本允许 Target 与 Speculator 解耦发布，但扩大兼容矩阵。第 6.2 节的 7776 组合就是代价的具体形态：解耦让两边可以各自迭代，却让「已验证组合」的集合以乘积速度增长。工程上的平衡点是**限制活跃制品数**：同一 Target 修订下每个域最多保留 1 个 stable + 1 个 canary + 1 个 rollback 目标，其余进入 deprecated。这样活跃组合数被约束在可评测的规模内。

## 8. 动态 Speculator Policy

### 8.1 候选、输入与输出

可以定义候选：

```text
No speculation
MTP
EAGLE-3
P-EAGLE
DFlash
DSpark
```

Policy 输入：model id、adapter id、request domain、prompt length、expected output、current concurrency、recent acceptance、SLO tier。

Policy 输出：algorithm、draft depth / block size、verification budget。

### 8.2 PolicyValue 与 Score

收益边界写作：

$$PolicyValue(x,s) = ExpectedSavedTime(x,s) - DraftCost(s) - CapacityPenalty(s)$$

各项与前几篇口径对齐：$ExpectedSavedTime=C(x,s)\cdot T_{AR}$（$T_{AR}=3.56$ ms）；$DraftCost=T_{draft}+T_O$；$CapacityPenalty=T_V(K)+LoadPenalty\cdot K$。于是 $PolicyValue$ 就是上一篇的 $NetGain$ 再减去负载惩罚，最大化它对应**净收益判据**。

带权重的评分形式：

$$Score_j=PredictedSavedTime_j-\lambda_1 VerifyCost_j-\lambda_2 MemoryCost_j$$

$$j^*=\arg\max_j Score_j$$

如果所有 $Score_j\le0$，直接关闭 speculation。$\lambda_1$ 表达服务承诺对验证容量的重视程度，$\lambda_2$ 把 Drafter 显存折算成被挤占的 KV cache 机会成本。

### 8.3 六候选评分表

为便于横向比较，下表统一采用第 4.3 节混合 Drafter 在 code/chat 两域的存活概率曲线，仅让草拟成本、可用深度与接受率折减随算法变化；真实评测中各算法的接受曲线必须分别测量。流量取 50/50，低载 $LoadPenalty=0$（推导设定与推导值，非实测）：

| 算法 | $K$ | $T_{draft}$ | 接受率折减 | $T_{eff}$ code | $T_{eff}$ chat | 混合 $T_{eff}$ |
| --- | --- | --- | --- | --- | --- | --- |
| No speculation | 0 | 0 | — | 3.560 ms | 3.560 ms | 3.560 ms |
| MTP | 4 | 0.50 ms | $\rho=0.85$ | 1.581 ms | 2.097 ms | 1.839 ms |
| EAGLE-3 | 4 | 2.00 ms | 无 | 1.590 ms | 2.283 ms | 1.937 ms |
| P-EAGLE | 8 | 1.10 ms | 无 | 1.412 ms | 2.441 ms | 1.926 ms |
| DFlash | 4 | 1.40 ms | 无 | 1.443 ms | 2.071 ms | 1.757 ms |
| DSpark | 7 / 3 | 1.40 ms | 无 | 1.414 ms | 2.056 ms | **1.735 ms** |

MTP 的折减 $\rho=0.85$ 反映原生多头未独立训练、深位置接受率更弱；EAGLE-3 的 $T_{draft}=2.00$ ms 来自 4 步自回归草拟（每步 0.5 ms），与前一篇 AR 对照一致。

对应的 $PolicyValue$（ms/轮，推导值，非实测）：

| 算法 | 低载 PV | 高载 PV（0.40 ms/位置） | 低载排名 | 高载排名 |
| --- | --- | --- | --- | --- |
| No speculation | 0 | 0 | — | — |
| MTP | 4.835 | 3.235 | 5 | 5 |
| EAGLE-3 | 5.808 | 4.208 | 4 | 3 |
| P-EAGLE | 6.971 | 3.771 | **2** | **4** |
| DFlash | 6.408 | 4.808 | 3 | 2 |
| DSpark | **7.292** | **5.292** | 1 | 1 |

两个关键现象：

1. **P-EAGLE 从低载第 2 掉到高载第 4**。它的 $K=8$ 使容量惩罚翻倍（3.20 ms vs 1.60 ms），深草拟在共享 verifier 上的机会成本被放大。
2. **PV 排名与 $T_{eff}$ 排名不同**。$T_{eff}$ 最优是 DSpark（1.735），PV 最优也是 DSpark，但第 2–5 名的顺序完全不一样：$T_{eff}$ 视角 MTP 第 2，PV 视角 MTP 第 5。这正是上一篇「净收益判据 vs 比率判据」的延续——**策略必须声明自己优化的是哪一个**。

### 8.4 关闭条件何时触发

chat 域高负载下 P-EAGLE 的 PV 为 $2.884\times3.56-7.04-3.20=0.027$ ms，几乎为零。$LoadPenalty$ 再升 0.05 ms/位置就转负（$-0.373$ ms），此时应直接关闭 speculation 而不是继续草拟。

$\lambda_1$ 扫描给出更一般的关闭边界。取 $\lambda_2=1$、显存折算 0.30 ms/GiB（MTP 0.20 GiB、EAGLE-3 0.375 GiB、其余 0.75 GiB），$Score=PV_{low}-(\lambda_1-1)\overline{T_V}-MemoryCost$（推导值，非实测）：

| 算法 | $\lambda_1=1.0$ | $1.5$ | $2.0$ | $2.5$ | 转负阈值 $\lambda_1^*$ |
| --- | --- | --- | --- | --- | --- |
| MTP | 4.775 | 2.695 | 0.615 | −1.465 | 2.15 |
| EAGLE-3 | 5.695 | 3.615 | 1.535 | −0.545 | 2.37 |
| P-EAGLE | 6.746 | 3.926 | 1.106 | −1.714 | 2.20 |
| DFlash | 6.183 | 4.103 | 2.023 | −0.057 | 2.49 |
| DSpark | **7.067** | **4.797** | **2.527** | **0.257** | **2.56** |

$\lambda_1$ 从 1.0 升到 2.5，MTP 与 P-EAGLE 最先转负，DSpark 因平均验证长度最短而最后转负。**「所有 Score ≤ 0 则关闭」不是理论兜底，而是在延迟/容量优先的服务档下会真实触发的分支**，必须实现并测试。

### 8.5 不可观测特征的门禁

八项输入里有一项在决策时不可得：**expected output**。离线评测可以用真实输出长度，在线只能用预测值。若策略在离线用了真实值，线上必然退化。

量化后果沿用前一篇 DFlash 的短输出摊销结论：净节省 2.094 ms/Token、初始化成本 $T_{init}=50$ ms 时盈亏平衡点为 24 Token。若预测输出 256 Token 而实际只有 16 Token：

$$16\times2.094-50=33.50-50=-16.50\ \text{ms}$$

净亏损 16.5 ms。因此在线策略必须改用可观测代理（prompt 类型、SLO 档、同域历史输出长度分位数），并保留「预测不确定时关闭 speculation」的通道。**离线特征集与在线特征集的差集必须显式列出并逐项论证**，这是「在线选择器使用不可观测特征」这一失败模式的唯一防线。

## 9. Acceptance Drift 与分桶监控

### 9.1 五类诱因与五个切分维度

Speculator 上线后可能出现：模型版本变化、用户业务域变化、新 LoRA 上线、Prompt template 改变、Sampling 参数改变，导致 $Acceptance_{online}\downarrow$。

因此监控至少按 model、adapter、tenant/domain、concurrency bucket、algorithm 切分。只有全局平均 acceptance，可能完全看不出某个大客户已经退化。

### 9.2 平均值掩盖单租户塌陷

设五个租户的流量占比与 $E[A]$（$B=8$，推导设定，非实测）：

| 租户 | 流量占比 | 基线 $E[A]$ | 漂移后 $E[A]$ | 相对变化 |
| --- | --- | --- | --- | --- |
| A | 50% | 4.20 | 4.20 | 0% |
| B | 20% | 3.80 | 3.80 | 0% |
| C | 15% | 3.50 | 1.20 | **−65.7%** |
| D | 10% | 3.20 | 3.20 | 0% |
| E | 5% | 3.00 | 3.00 | 0% |
| 全局加权 | 100% | 3.855 | 3.510 | −9.0% |

若告警阈值设为「全局下降 10%」，则**不触发**（9.0% < 10%），而租户 C 已经退化 65.7%。按租户设 15% 阈值则立即触发。这就是「漂移告警只看平均接受率」的具体代价。

### 9.3 流量结构变化造成的假漂移

反过来，若没有任何模型退化，只是租户 C 的流量占比从 15% 升到 30%（其余租户等比缩放），全局加权 $E[A]$ 变为 3.793，相对基线下降 1.6%（推导值，非实测）。

这 1.6% 是**纯结构变化**，不是漂移。若只看全局均值就触发重训，会浪费一次完整的训练与评测周期。因此漂移分数必须定义为「固定流量权重下的分域接受长度变化」，即把权重固定在基线期，只让各域的 $E[A]$ 变动：

$$DriftScore=\sum_d w_d^{base}\cdot\frac{E[A]_d^{now}-E[A]_d^{base}}{E[A]_d^{base}}$$

这样结构变化被权重固定吸收，真实退化被保留。同时必须单独报告流量结构本身的变化，因为它会移动第 4.3 节的专家/混合交叉点。

### 9.4 漂移分数的口径

「漂移分数」没有单位、统计窗口和分母时不参与决策。建议口径：无量纲相对变化，窗口不短于该域最小样本量所需时间（第 10.2 节），分母为该域基线期 $E[A]$，并按上下文长度桶与并发桶二次切分。全局漂移分数只作为汇总视图，不作为告警依据。

## 10. Canary 发布与回滚

### 10.1 灰度流程与停止条件

上线新 Speculator 不需要直接 100%：

```text
5% traffic
  ↓
检查正确性 / P99 / acceptance / GPU cost
  ↓
25%
  ↓
50%
  ↓
100%
```

Rollback 条件可以是：accepted length 低于基线；TPOT 恶化；verifier waste 超阈值；error/correctness 异常；显存抬高导致稳定并发下降。

五条里只有第四条是正确性问题，其余四条都是性能问题。**性能回滚条件必须预先写成数值阈值并绑定域**，否则灰度期间「看起来还行」会让不合格制品一路升到 100%。

### 10.2 灰度样本量与时长

要检测全局 $E[A]$ 从 3.855 降到 3.510（$\Delta=0.345$），设单请求 $E[A]$ 标准差 $\sigma=1.2$，双侧 $\alpha=0.05$、power $=0.8$，每组样本量：

$$n=\frac{2\sigma^2(z_{\alpha/2}+z_\beta)^2}{\Delta^2}=\frac{2\times1.44\times(1.96+0.84)^2}{0.345^2}=\frac{22.579}{0.119}=190$$

即每组约 190 请求。设总流量 100 req/s，达到该样本量所需时间（推导值，非实测）：

| 灰度比例 | canary 流量 | 全局 190 请求 | chat 域（30%） | 长尾租户（1%） |
| --- | --- | --- | --- | --- |
| 5% | 5 req/s | 38 s | 127 s | **3800 s（63 min）** |
| 25% | 25 req/s | 7.6 s | 25 s | 760 s（13 min） |
| 50% | 50 req/s | 3.8 s | 13 s | 380 s（6.3 min） |

**5% 灰度对主域足够（约 2 分钟），对长尾租户需要 1 小时以上。** 因此长尾租户不能靠统一灰度比例保护：要么单独延长灰度、要么按域设独立门禁、要么对长尾域直接沿用 stable 制品不参与灰度。把「灰度错误率」按域拆开报告，才能看出哪一档比例 actually 提供了保护。

### 10.3 回滚时间预算与制品驻留

回滚 SLO 设 10 s，在途请求排空 1.5 s（推导设定）。结合第 6.4 节的加载成本：

| 旧制品位置 | 加载 | 排空 | 合计 | 是否满足 10 s |
| --- | --- | --- | --- | --- |
| 本地缓存命中 | 2.00 s | 1.5 s | **3.50 s** | 是 |
| 对象存储 | 9.55 s | 1.5 s | 11.05 s | 否（超 10.5%） |
| 远端 Registry | 33.71 s | 1.5 s | 35.21 s | 否（超 2.5 倍） |

「回滚时旧 Drafter 已被逐出」正是第三行的场景。解决办法是常驻上一版制品：两版 DFlash Drafter 共 3.00 GiB，占 80 GiB 卡的 3.75%，若 KV cache 预算为 60 GiB 则挤占 5.0%。

**用 3.75% 显存把回滚时间从 35.21 s 压到 3.50 s（10 倍），是明显划算的交易。** 但常驻策略必须写进 Registry 的容量规划，否则「显存抬高导致稳定并发下降」这条回滚条件会被自己触发。

### 10.4 审计链

回滚与审计要求每次切换都能回答：切的是哪个 `speculator_id`、从哪个 revision 到哪个 revision、触发条件是哪一条阈值、决策时的分域指标是什么、在途请求如何处理、资源是否释放。缺任何一项，事后都无法判断回滚是否正确。「回滚时间」必须附带口径：起点是告警触发还是切换指令下发，终点是流量完全切回还是最后一个旧请求完成。

## 11. Benchmark Matrix 与证据口径

Speculator Benchmark 项目使用统一矩阵，每一个结果必须同时记录环境：GPU、Runtime 版本、Target revision、Speculator revision、dtype/quantization、prompt set。

在此之上还需固定两类标签：

- **来源标签**：`source=fixture`（机制模拟）与 `source=measured`（真实测量）分开存档，不得混用，模拟值不得写成实测数字。
- **口径标签**：$C$ 是否含 Bonus、$T_V$ 用线性还是树口径、$T_{draft}$ 是否含条件特征传输与 sequential 成本、$E[A]$ 的域权重、P99 的窗口与请求集。

矩阵的每一行都是一个「制品 × 兼容组合 × 负载区间」的三元组，而不是一个算法名。只按算法名汇总的排行榜无法回答「这个制品在我的 Target 修订、我的域、我的并发下是否划算」，而那才是路由决策真正需要的问题。

## 12. 八个对象的边界与失败模式

需要纳入同一证据链的对象包括：Speculator 独立制品、训练数据版本、离线评测矩阵、在线策略选择、Target 兼容关系、灰度发布、漂移检测、回滚与审计。它们并不处在同一个组件中，却会一起改变回滚时间和制品加载成本。

### 12.1 统一检查框架

每个对象都按同一组问题展开：边界与生命周期（输入、输出、状态归属、销毁时点、失败传播）、资源账（计算、显存、内存带宽、主机开销、同步等待分别记账）、负载区间（低载、接近饱和、过载三段同口径）、正确性门禁（Token 序列、采样分布、结构合法性、结束原因、错误传播）、观测字段（请求身份、模型与策略修订、起止时间、阶段耗时、资源快照、失败原因）。跨对象传递的数据必须携带版本身份。

### 12.2 Speculator 独立制品

边界由输入、输出、状态和拥有者共同确定；与训练数据版本交互的字段必须携带版本身份，便于回放时找到同一配置。独立版本允许 Target 与 Speculator 解耦发布但扩大兼容矩阵，这会移动关键路径，却很少让所有资源同比例变化：请求事件负责说明顺序，资源曲线负责解释瓶颈转移。

「设计离线门禁」是否合适，取决于长度分布、并发、到达过程、采样和任务域，实验在三段负载保留同口径证据。典型失败是**漂移告警只看平均接受率**：第 9.2 节显示全局下降 9.0% 时单租户已退化 65.7%，阈值不触发。质量结果优先于速度数字，发布停止并保留问题请求用于复现。**漂移分数**没有单位、统计窗口和分母时不参与决策。

### 12.3 训练数据版本

生命周期落到组件接口：输入从哪里来，状态由谁持有，输出交给谁，失败如何传播。与离线评测矩阵之间的身份和版本若未绑定，请求时间线就可能混入旧配置。离线接受率必须连接到真实服务成本，其影响分散到五项资源；某一阶段变短时，被遮蔽的成本可能随即暴露。

「选择在线策略特征」的验证分别运行三段负载并使用代表性分布。典型失败是**回滚时旧 Drafter 已被逐出**：第 10.3 节显示未命中缓存时回滚需 35.21 s，超预算 2.5 倍。当前性能结果不进入候选评审，立即切回已验证配置，失败样本与版本信息一并保存。**灰度错误率**的定义随报告存档，包括单位、窗口和分母。

### 12.4 离线评测矩阵

边界检查覆盖输入、输出、状态归属和销毁时点；传给在线策略选择的数据应附带模型或策略版本。在线选择器根据请求特征和容量决定策略，通常只先改变资源账中的几项，其他资源随后可能进入关键路径；平均 GPU 利用率只作为辅助信号。

「设置漂移阈值」应覆盖长短输入、不同输出、并发、突发、采样与任务域，容量判断不能从一次固定批量的短运行外推。典型失败是**发布记录无法关联训练数据**：谱系断链后无法判断该重训还是重校准。触发停止与回退，系统恢复到已有证据支持的配置。**回滚时间**必须附带口径。

### 12.5 在线策略选择

边界由输入、输出、状态和拥有者共同确定；连接 Target 兼容关系时还要传播身份和版本，避免把另一套配置的结果归到当前实验。数据漂移会改变位置接受率与域收益，缩短的阶段可能让另一项资源成为瓶颈。

「制定灰度和回滚流程」至少比较低载、临近容量与过载，结论只覆盖实际运行过的区间。典型失败是**Drafter 与 Target 修订错配**：第 7.2 节显示 $\rho$ 降到 0.60 时 $T_{eff}=4.007$ ms，已慢于基线 12.6%。质量结果优先于速度数字，发布停止、流量回到已验证修订，相关请求留作重放。**制品加载成本**同时注明单位、窗口和分母。

### 12.6 Target 兼容关系

与灰度发布交互的字段必须携带版本身份。灰度和回滚需要保留可复现制品身份，这会移动关键路径，却很少让所有资源同比例变化。

「定义制品元数据」是否合适，取决于长度分布、并发、到达过程、采样和任务域。典型失败是**离线集合过度代表单一域**：第 5.3 节显示 80/20 离线集合对 30/70 线上流量把加速比高估 29.9%。质量门禁应停止性能发布，回退目标是已验证配置。**兼容组合通过率**没有单位、统计窗口和分母时不参与决策，分母必须是实际可路由组合。

### 12.7 灰度发布

生命周期落到组件接口，与漂移检测之间的身份和版本若未绑定，请求时间线就可能混入旧配置。Drafter 收益由模型、域、采样和负载共同决定，其影响分散到五项资源。

「构建训练与评测数据谱系」的验证分别运行三段负载并使用代表性分布。典型失败是**在线选择器使用不可观测特征**：第 8.5 节显示 expected output 预测错误会让短请求净亏损 16.5 ms。当前性能结果不进入候选评审，立即切回已验证配置。**域级接受长度**的定义随报告存档，包括单位、窗口和分母。

### 12.8 漂移检测

边界检查覆盖输入、输出、状态归属和销毁时点；传给回滚与审计的数据应附带模型或策略版本。数据漂移会改变位置接受率与域收益，通常只先改变资源账中的几项。

「设置漂移阈值」应覆盖长短输入、不同输出、并发、突发、采样与任务域。典型失败是**把流量结构变化误判为漂移**：第 9.3 节显示纯结构变化即可造成 1.6% 的全局下降，触发一次无谓的重训周期。触发停止与回退后系统恢复到已有证据支持的配置。**策略命中率**必须附带口径：命中指策略选择与事后最优一致，分母为参与决策的请求数。

### 12.9 回滚与审计

边界由输入、输出、状态和拥有者共同确定；与 Speculator 独立制品之间必须传播身份和版本。灰度和回滚需要保留可复现制品身份，缩短的阶段可能让另一项资源成为瓶颈。

「制定灰度和回滚流程」至少比较低载、临近容量与过载。典型失败是**审计链缺少决策输入**：只记录了切换动作而没有触发阈值与分域指标，事后无法判断回滚是否正确。质量门禁应停止性能发布，回退目标是已验证配置并保留问题请求。**制品加载成本**与**回滚时间**都要按缓存命中/未命中分别统计，注明单位、窗口和分母。

## 13. 六个机制的因果分析

核心关系写作 $PolicyValue(x,s)=ExpectedSavedTime(x,s)-DraftCost(s)-CapacityPenalty(s)$。它是一项组织变量的近似模型，不代表供应商基准。建模时把制品版本与训练数据配方设为可控因素，工作负载、模型及硬件作为条件，兼容组合通过率、域级接受长度、策略命中率与制品加载成本作为结果。时间量统一单位，概率限定在零到一，吞吐量明确计数对象。框架队列、Kernel 启动、分配器、网络、客户端与取消不在近似中，真实实验需要补齐；方向冲突通常意味着变量或测量口径遗漏。

### 13.1 机制 1：独立版本允许 Target 与 Speculator 解耦发布，但扩大兼容矩阵

这一机制会改写请求的阶段顺序。画出变化前后的关键路径，标明并行、串行和跨请求合批位置；制品元数据给出状态条件，兼容组合通过率验证结果是否传到请求端。第 6.2 节显示解耦把已验证组合推到 7776 个，正确性对账 19.7 GPU-h 可全量覆盖，性能评测 393.7 GPU-h 必须裁剪到活跃组合。

单请求数据不足以评价：低载用于测量固定成本，接近容量时观察批处理与共享资源，过载时确认拒绝和尾延迟。离线集合过度代表单一域若只在并发后出现，优先检查候选路径对正常请求资源的挤占。

数据格式、张量形状、缓存身份、版本兼容和错误传播共同构成实现边界；「定义制品元数据」需要在合同冻结后测试正常、无效、极端和资源受限输入。证据需要成对的原因和结果字段：原因包括制品 revision、Compatibility hash 与域权重，结果包括兼容组合通过率、错误、取消和资源快照。发布时配置独立开关、灰度身份、停止条件和暖回滚目标；Drafter 与 Target 修订错配触发后只撤回相关变化。

### 13.2 机制 2：离线接受率必须连接到真实服务成本

把前后两条请求时间线对齐，逐段标出可并行、必须串行和允许合批的工作。训练数据版本说明机制何时生效，域级接受长度负责确认关键路径是否真的缩短。第 5.3 节显示离线 $E[A]$ 与线上 $E[A]$ 可以相差 29.9%，只报离线数字等于报了一个不属于任何真实流量的加速比。

分别施加轻载、稳定高载和过载流量，可以分辨同步开销、队列增长、合批变化与资源竞争。检测到回滚时旧 Drafter 已被逐出后，沿共享执行资源检查局部收益为何没有进入系统 Goodput。

确定接口时同时规定数据与 Shape、缓存和版本身份、错误及回退，随后以无效输入、极端长度和资源不足验证「构建训练与评测数据谱系」。观测时原因侧保存数据 snapshot、mixture recipe 与域权重，结果侧保存 GPU-hour/output token、错误、取消与资源。该机制通过独立开关进入灰度，出现发布记录无法关联训练数据时撤回本项候选，并核对在途请求、缓存状态与资源是否释放。

### 13.3 机制 3：在线选择器根据请求特征和容量决定策略

请求执行该机制后，阶段边界和依赖关系会发生变化。先记录原路径，再记录候选路径中的串行、并行与合批段，同时保存策略命中率与制品加载成本。第 8.3 节显示 P-EAGLE 在低载 PV 排名第 2、高载掉到第 4，说明「最优算法」是负载的函数而不是常量。

容量评估放在三个负载区间中运行。在线选择器使用不可观测特征意味着候选工作可能消耗了服务正常请求所需的容量——短请求被误判为长请求后白付初始化成本。

实现时明确数据格式、张量形状、缓存身份、版本兼容和错误回退；执行「选择在线策略特征」前冻结接口合同，并加入无效输入、极端长度与资源不足测试。Trace 同时记录决策输入与执行结果，后者含域级接受长度、错误、取消和资源变化。上线合同写明灰度范围、停止条件、开关和暖回滚目标；Drafter 与 Target 修订错配发生后，系统恢复相关稳定配置，并持续观察请求排空、缓存切换和资源回收。

### 13.4 机制 4：数据漂移会改变位置接受率与域收益

这一机制会改写请求的阶段顺序。画出变化前后的关键路径，标明并行、串行和跨请求合批位置；漂移检测给出状态条件，漂移分数验证结果是否传到请求端。第 4.2 节的 $s_k^{OOD}=\rho^k s_k^{ID}$ 说明漂移代价随深度指数放大，因此逐位置接受率比 top-1 accuracy 更早暴露问题。

单请求数据不足以评价：低载测量固定成本，接近容量时观察批处理与共享资源，过载时确认拒绝和尾延迟。漂移告警只看平均接受率若只在并发后出现，优先检查候选路径对正常请求资源的挤占。

数据格式、张量形状、缓存身份、版本兼容和错误传播共同构成实现边界；「设置漂移阈值」需要在合同冻结后测试正常、无效、极端和资源受限输入。证据需要成对字段：原因包括域标签、adapter 修订、prompt template 版本与采样参数，结果包括分域 $E[A]$、P99、错误、取消和资源快照。发布时配置独立开关、灰度身份、停止条件和暖回滚目标；把流量结构变化误判为漂移触发后只撤回相关变化。

### 13.5 机制 5：灰度和回滚需要保留可复现制品身份

把前后两条请求时间线对齐，逐段标出可并行、必须串行和允许合批的工作。灰度发布说明机制何时生效，回滚时间负责确认关键路径是否真的缩短。第 10.3 节显示常驻上一版制品用 3.75% 显存换回滚时间 10 倍改善，这是该机制最直接的量化证据。

分别施加轻载、稳定高载和过载流量，可以分辨同步开销、队列增长、合批变化与资源竞争。检测到审计链缺少决策输入后，沿共享执行资源检查局部收益为何没有进入系统 Goodput。

确定接口时同时规定数据与 Shape、缓存和版本身份、错误及回退，随后以无效输入、极端长度和资源不足验证「制定灰度和回滚流程」。观测时原因侧保存切换指令、触发阈值与分域指标，结果侧保存制品加载成本、错误、取消与资源。该机制通过独立开关进入灰度，出现回滚时旧 Drafter 已被逐出时撤回本项候选，并核对在途请求、缓存状态与资源是否释放。

### 13.6 机制 6：Drafter 收益由模型、域、采样和负载共同决定

请求执行该机制后，阶段边界和依赖关系会发生变化。先记录原路径，再记录候选路径中的串行、并行与合批段，同时保存策略命中率与域级接受长度。第 4.3 节的专家/混合交叉点 $x^*=0.80$ 说明「哪个 Drafter 更好」取决于流量结构，而流量结构本身会漂移。

容量测试覆盖低载、稳定高载和过载。若出现在线选择器使用不可观测特征，说明局部延迟没有变成有效容量，需要核对候选工作占用的公共资源。

接口合同包括格式、Shape、缓存键、版本与回退语义；「设计离线门禁」进入评审前，使用非法输入、边界长度和资源不足场景检验保护路径。采集证据时把数据配方、域权重、判据类型与兼容组合通过率、错误、取消及资源事件放进同一请求链。发布单元包含灰度身份、门禁、停止动作和已预热回滚路径；检测到离线集合过度代表单一域后执行局部撤回。

## 14. 工程决策与取舍

### 14.1 决策 1：定义制品元数据

候选做法是最小字段集（id + target + algorithm）、完整字段集（含 tokenizer/硬件/兼容状态）、再加 Compatibility hash 与证据分级。第 6.3 节显示 hash 分级复用能把 Target 升级的对账成本大幅降低，因此完整字段集加 hash 是默认选择。取舍在于维护负担：字段越多，登记与校验的自动化要求越高。判据是兼容组合通过率与错配拦截次数，并附「Drafter 与 Target 修订错配」的自动隔离动作（$T_{eff}$ 超基线即标记不可路由）。

### 14.2 决策 2：构建训练与评测数据谱系

候选做法是只记 dataset 名、记到 snapshot、记到 mixture recipe 与 training run 全链。第 4.1 节要求全链可追溯，否则漂移时无法定位该重训还是重校准。取舍在于存储与合规成本：serving trace 需匿名化且保留期受限。判据是谱系完整率与漂移归因耗时，并明确匿名化后是否仍能按域分桶。域权重必须与线上权重一起存档，作为结论适用范围的一部分。

### 14.3 决策 3：设计离线门禁

候选做法是单一全局 $E[A]$ 下限、按域设阈值、按域 × 上下文桶设阈值、再加质量对账硬门禁。第 5.3 节显示全局阈值会被域权重错配掩盖，因此按域设阈值是下限要求。取舍在于评测成本：第 5.2 节的两阶段裁剪节省 45.8%，但可能误杀只在特定工况占优的算法。判据是四类指标全部通过、粗筛保留非默认工况、以及离线/线上域权重差被显式报告。

### 14.4 决策 4：选择在线策略特征

候选做法是用全部八项输入、剔除不可观测项、用可观测代理替代、再加不确定时关闭通道。第 8.5 节显示 expected output 不可观测且误判代价为净亏损 16.5 ms，因此必须剔除或替代。取舍在于代理精度：同域历史输出长度分位数比单请求预测稳，但对新域无历史。判据是策略命中率与离线/在线特征差集清单，并保留「所有 Score ≤ 0 则关闭」分支的实现与测试。

### 14.5 决策 5：设置漂移阈值

候选做法是全局均值阈值、按租户阈值、固定基线权重的分域漂移分数、再加分桶 ECE。第 9.2/9.3 节显示全局阈值既漏报（9.0% < 10% 而单租户 −65.7%）又误报（纯结构变化 −1.6%），因此固定权重的分域分数是默认选择。取舍在于告警噪声：分桶越细，小样本桶的波动越大。判据是每桶最小样本量（第 10.2 节的 190 请求口径）与未达样本量桶的抑制规则，并同时报告流量结构变化。

### 14.6 决策 6：制定灰度和回滚流程

候选做法是直接 100%、固定比例阶梯、按域分层阶梯、再加长尾域不参与灰度。第 10.2 节显示 5% 灰度对长尾租户需 63 min 才有足够样本，因此统一阶梯不足以保护长尾。取舍在于发布速度：分层与延长灰度会拉长上线周期。判据是分域灰度错误率、回滚时间（按缓存命中/未命中分别报）与制品驻留显存，并明确常驻上一版制品的容量预算（3.75% 显存换 10 倍回滚速度）。

## 15. 实验设计与双路径验证

实验复用 Speculator Benchmark 项目的统一矩阵，在其上增加制品登记、谱系追溯、策略评分与漂移分桶四个模块。本文给出设计规格与指标口径，不含可执行代码。

**路径 A：机制模拟（`source=fixture`）。** 只依赖 CPU。输入：域专家接受曲线、域衰减因子 $\rho$、训练配方、流量域权重、各算法的 $K$ 与 $T_{draft}$、$T_V$/$T_O$ 口径、$LoadPenalty$、$\lambda_1/\lambda_2$、显存折算系数、灰度比例、租户流量结构、漂移注入幅度。输出：$s_k$、$E[A]$、$C$、$T_{eff}$、$PolicyValue$、$Score$、专家/混合交叉点、关闭分支触发次数、分域漂移分数、灰度样本量与时长、回滚时间预算。扫描维度为 $\rho\in\{1.0,0.96,0.85,0.80,0.60\}$、code 占比 $\in\{0.3,0.5,0.7,0.8,0.9\}$、$\lambda_1\in\{1.0,1.5,2.0,2.5\}$、负载档 $\in\{$低, 中, 高$\}$、灰度比例 $\in\{5\%,25\%,50\%\}$。

**路径 B：真实测量（`source=measured`）。** 在可用 CUDA GPU 上运行同一组配置，采集八项必测指标：

| 指标 | 口径要求 |
| --- | --- |
| 兼容组合通过率 | 分母为实际可路由组合数，注明 LoRA/结构化/量化/硬件档位 |
| 域级接受长度 | 按域 × 上下文桶 × 并发桶的 $E[A]$，注明是否含 Bonus |
| 策略命中率 | 选择与事后最优一致的请求占比，注明事后最优的判据类型 |
| 制品加载成本 | 秒/次切换，按缓存命中与未命中分别统计 |
| 漂移分数 | 固定基线权重的分域相对变化，注明窗口与每桶样本量 |
| 灰度错误率 | 按域拆分的正确性/性能异常率，注明灰度比例与窗口 |
| 回滚时间 | 注明起点（告警/指令）与终点（流量切回/末请求完成） |
| GPU-hour / output token | 注明是否含草拟、加载与双版本驻留摊销 |

外加 $T_{eff}$、P99（TPOT 与整轮时间分别报）、verifier 浪费率与稳定并发上限。每次运行记录完整环境与 Target revision、Speculator revision、Compatibility hash、数据 snapshot、mixture recipe、判据类型。

**双路径对账。** 同一配置下比较模拟与实测的域级 $E[A]$、$T_{eff}$ 排名与关闭分支触发点：方向一致但数值偏离时优先补齐批次 padding、Kernel 启动、CPU 调度、制品加载与同步项；方向相反时先核对口径（$C$ 是否含 Bonus、$T_V$ 用线性还是树口径、域权重是否一致、判据是 PV 还是 $T_{eff}$），再检查是否触发未建模的自动隔离或长尾抑制。模拟结果不得写成实测数字，实测结果不得外推到未运行过的负载区间与未覆盖的域。

**门禁与回滚。** 任何制品进入候选前必须通过逐位输出对账与四类离线指标；策略变更必须声明判据类型并保留一键关闭 speculation 的路径；回滚目标制品必须常驻本地缓存，且其显存占用已计入容量规划。发布记录无法关联训练数据时不进入评审。

## 16. 常见错误与排查

| 现象 | 可能原因 | 排查动作 |
| --- | --- | --- |
| Target 升级后速度退化 | 继续复用旧 Speculator，修订错配 | 校验 Compatibility hash，按域重测 $T_{eff}$ |
| 输出 Token 序列异常 | Tokenizer 修订错配 | 立即隔离制品，重跑逐位对账 |
| 某域 $T_{eff}$ 超过基线 | 域衰减 $\rho$ 过低（第 7.2 节 4.007 ms） | Registry 自动标记该域不可路由 |
| 离线加速比线上兑现不了 | 离线集合过度代表单一域 | 按线上域权重重算，分域设门禁 |
| 评测跑不完 | 兼容矩阵笛卡尔积爆炸 | 正确性全量、性能按活跃组合裁剪 |
| 兼容通过率看起来极低 | 分母用了 7776 而非可路由组合 | 改分母，注明活跃组合定义 |
| 策略在离线好线上差 | 使用了不可观测的 expected output | 列出特征差集，改用可观测代理 |
| 短请求反而变慢 | 输出长度误判，初始化成本未摊销 | 加「预测不确定则关闭」通道 |
| 高并发下深草拟算法掉队 | 容量惩罚随 $K$ 线性放大 | 按负载重算 PV，声明判据类型 |
| 所有算法 Score 为负 | $\lambda_1$ 过高或域接受率过低 | 触发关闭分支，检查是否实现并测试 |
| 漂移告警不触发但客户投诉 | 只看全局平均接受率 | 按租户/域分桶，固定基线权重 |
| 无退化却触发重训 | 流量结构变化被误判为漂移 | 分离结构变化与分域接受率变化 |
| 回滚耗时超预算 | 旧 Drafter 已被逐出缓存 | 常驻上一版制品，计入显存预算 |
| 事后无法判断回滚对错 | 审计链缺少决策输入 | 成对记录触发阈值、分域指标与切换动作 |

## 17. 常见追问与解答

**问：Speculator 为什么不能当作 Target 的附件一起发布？**
答：因为两者的迭代节奏与失效模式不同。Target 升级不一定要求 Drafter 重训，但必须重新验证兼容；Drafter 重训也不一定要求 Target 变更。解耦发布让两边各自迭代，代价是兼容矩阵扩大（本文推导为 7776 组合），需要用活跃制品数约束来平衡。

**问：训练数据分布真的比模型结构更重要吗？**
答：对接受率而言是的。本文推导中域衰减 $\rho=0.80$ 就让 chat 域 $T_{eff}$ 从 2.545 ms 恶化到 3.137 ms，$\rho=0.60$ 时更是慢于基线。结构改进通常带来百分之几的收益，域错配带来的是百分之几十甚至收益归零。

**问：什么时候该用域专家 Drafter，什么时候用混合 Drafter？**
答：看线上主域占比。本文推导的交叉点是 80%：高于它用专家，低于它用混合。交叉点由两条 $T_{eff}$ 直线的斜率差决定，域衰减因子变化时会移动，因此必须随流量结构定期重算。

**问：离线评测为什么不能只报一个加速比？**
答：因为加速比对域权重是线性敏感的。离线 80/20、线上 30/70 时，同一个制品的加速比从 2.22× 变成 1.70×，高估 29.9%。必须分域报指标，并同时报离线与线上的域权重差。

**问：PolicyValue 和 $T_{eff}$ 该用哪个选策略？**
答：取决于服务承诺。PV 最大化对应净收益判据（吞吐/成本视角），$T_{eff}$ 最小化对应比率判据（延迟视角）。本文推导中两者的第 2–5 名顺序完全不同，策略必须显式声明用的是哪一个。

**问：「所有 Score ≤ 0 则关闭」真的会触发吗？**
答：会。chat 域高负载下 P-EAGLE 的 PV 只有 0.027 ms，$LoadPenalty$ 再升 0.05 ms 就转负；$\lambda_1$ 升到 2.5 时除 DSpark 外全部转负。这个分支必须实现并测试，不能只写在文档里。

**问：灰度 5% 够不够？**
答：对主域够（约 2 分钟达到 190 请求样本量），对占 1% 流量的长尾租户需要 63 分钟。长尾域要么延长灰度、要么独立门禁、要么不参与灰度直接沿用 stable 制品。

**问：回滚为什么要常驻旧制品？**
答：因为加载成本差异是 10 倍量级。本地缓存命中 3.50 s 满足 10 s 预算，远端 Registry 35.21 s 超预算 2.5 倍。代价是 3.75% 显存，这笔交易在绝大多数场景下划算，但必须计入容量规划。

## 写在最后

把 Speculator 当作独立制品管理，意味着接受一个事实：**算法收益只是结论的一半，另一半由域权重、负载、兼容组合与制品身份决定**。本文的推导给出的几个可落地阈值——专家/混合交叉点 80%、离线高估 29.9%、错配隔离线 $T_{eff}>3.56$ ms、长尾灰度 63 min、常驻旧制品换 10 倍回滚速度——都不是算法参数，而是工程制度参数。它们必须写进 Registry、门禁与告警配置，并随流量结构变化定期重算。
