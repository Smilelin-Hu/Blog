# DDTree：Diffusion Draft Tree 与树验证

本文回答的问题是「如何在固定节点预算下构造候选树并控制树验证成本？」。分析沿概念边界、性能关系、实现证据和发布条件四条线展开，其中 Diffusion Draft Tree 与树节点预算是最先核对的状态。工作负载、模型修订、运行时、资源余量和服务承诺共同决定「用共享前缀表达多个并行候选序列」是否值得采用，后续每个结论都会注明这些条件。

实验采用两条证据路径：CPU 机制模拟隔离候选树与节点预算的因果关系，真实 CUDA 路径记录实现、框架和硬件开销。报告分别标记两类结果，节点利用率的模拟值不充当 GPU 基准，单台设备的绝对速度也不外推。最终结论必须能够复现、诊断并回滚。

## 1. 内容概览

- Diffusion Draft Tree、树节点预算与分支因子之间的状态与资源关系。
- 用 $Value(node)=P(\text{prefix survives})\cdot P(token)\cdot SavedTargetTime-VerifyMarginalCost$ 建立可计算的收益边界并解释全部变量。
- 围绕节点利用率、路径存活概率、覆盖率和单位节点收益设计可复现实验。
- 识别宽树包含大量低概率节点、深树在前部拒绝后全部浪费、验证掩码构造占据 CPU 关键路径等典型失败模式。
- 对中心问题给出包含适用条件、证据、风险和回滚的工程答案。

## 2. 核心直觉：把被丢掉的第二名候选重新利用

假设块扩散 Drafter 输出每个位置的分布：

```text
位置1: A 0.70 / B 0.20
位置2: C 0.60 / D 0.30
位置3: E 0.55 / F 0.35
```

线性 Draft 只会验证一条路径：

```text
A → C → E
```

但如果 Target 在第 2 个位置更偏好 D，整条线性后缀很快被截断。树可以覆盖多条分支：

```text
        A
      /   \
     C     D
    / \   / \
   E  F  E   F
```

只要真实 Target path 落在树中，就可能继续接受更多 token。树的本质是**用共享前缀把「被丢掉的第二名候选」重新纳入验证**，代价是节点数上升与掩码、KV 布局复杂化。

## 3. 前置知识与实验环境

需要理解自回归生成、Tokenizer、Prefill、Decode、KV Cache、批处理和分位延迟的基本含义，并已掌握前一篇块扩散草拟的整轮时间口径。所有缩写都会在正文首次出现处定义；没有某个特定框架经验不妨碍理解机制。实验需要 Python 3.11 或兼容版本。机制模拟只依赖 CPU；真实路径需要任意可用的 CUDA GPU、与驱动兼容的 PyTorch，以及自行准备的本地小模型或兼容制品。

验证前必须记录 GPU 名称、数量、可用显存、驱动、CUDA、PyTorch、推理框架、模型摘要、精度、批量、序列长度和完整命令。脚本根据可用显存缩放模型、批量、上下文和样本数，并把候选树状态写入报告；可选 CUDA 入口不下载未经确认的大模型。

决定是否采用树验证前，先冻结模型版本、长度分布、流量到达、并发、采样、缓存状态、节点利用率口径、服务等级和硬件配置。评审「分配树宽与深」和「选择扩展节点」时，由这些记录解释收益分子、成本分母及共享资源竞争。

## 4. 候选树不是笛卡尔积

### 4.1 节点量爆炸推导

如果每个位置保留 $b$ 个 token，深度 $K$ 的完整树节点量为：

$$N=\sum_{d=1}^{K}b^d=\frac{b(b^K-1)}{b-1}$$

逐项算得（推导值，非实测）：

| $b$ | $K$ | 节点数 $N$ |
| --- | --- | --- |
| 2 | 4 | 30 |
| 2 | 6 | 126 |
| 2 | 8 | 510 |
| 3 | 6 | 1092 |
| 4 | 4 | 340 |
| 4 | 6 | 5460 |
| 4 | 8 | **87380** |

$b=4,K=8$ 已经不可接受：单请求一轮就要验证 8.7 万个节点，而前一篇的线性块验证预算只有个位数到十几。若节点预算 $B=64$，覆盖率仅 $64/87380\approx0.073\%$。因此 DDTree 必须在有限 Node Budget 下选择「最值得验证」的分支，而不是枚举笛卡尔积。

### 4.2 路径分数与 best-first 扩展

一条路径的 surrogate probability 定义为各位置分布的乘积：

$$Score(path)=\prod_k q_k(x_k),\qquad \log Score(path)=\sum_k\log q_k(x_k)$$

用第 2 节的示例分布，八条深度 3 路径的分数为（推导值，非实测）：

| 排序 | 路径 | $Score$ | 累计概率质量 |
| --- | --- | --- | --- |
| 1 | A-C-E | 0.2310 | 0.2310 |
| 2 | A-C-F | 0.1470 | 0.3780 |
| 3 | A-D-E | 0.1155 | 0.4935 |
| 4 | A-D-F | 0.0735 | 0.5670 |
| 5 | B-C-E | 0.0660 | 0.6330 |
| 6 | B-C-F | 0.0420 | 0.6750 |
| 7 | B-D-E | 0.0330 | 0.7080 |
| 8 | B-D-F | 0.0210 | 0.7290 |

总质量 $0.90\times0.90\times0.90=0.729$，即三个位置各取 top-2 时笛卡尔积能覆盖的概率上限。用 best-first / heap 按 $\log Score$ 逐步扩展高分路径，直到耗尽节点预算，就得到一棵「概率优先」的树。

### 4.3 节点预算与覆盖率推导

扩展时节点是共享的：加入 A-C-F 只需新增 1 个节点（A、AC 已存在）。按上表顺序累计（推导值，非实测）：

| 节点预算 $B$ | 覆盖的完整路径 | 路径概率质量 | 单位节点覆盖收益 |
| --- | --- | --- | --- |
| 3（线性 A-C-E） | 1 条 | 0.2310 | 0.0770 |
| 7 | 4 条 | 0.5670 | **0.0810** |
| 10 | 5 条 | 0.6330 | 0.0633 |
| 14（全树） | 8 条 | 0.7290 | 0.0521 |

单位节点覆盖收益在 $B=7$ 达到峰值后单调下降：从 7 到 14，节点翻倍而概率质量只增 28.6%。这就是「宽树包含大量低概率节点」的定量形式——预算继续加大时，新增节点几乎都落在不会被走到的分支上。

## 5. Diffusion Marginal 与 AR Prefix 的错位

这里有一个很重要的概念边界。Diffusion Drafter 的每位置分布更多反映「在整个 block 条件下这个位置像什么」，而 Target AR verifier 的接受是严格 prefix-based：

```text
第3个 token 是否有效
必须建立在第1、2个 token 都属于同一正确前缀
```

因此 marginal probability 不是完美的路径概率。把 marginal 直接当 conditional 连乘会系统性高估深路径：设真实条件接受概率为 0.70 / 0.55 / 0.45，则真实三位存活概率为 $0.70\times0.55\times0.45=0.17325$，而 marginal 乘积给出 0.231，**高估 33.3%**（推导值，非实测）。

高估的后果是预算偏向深处：深路径分数被抬高，best-first 会先扩展它们，而真实接受率撑不住。两种修正方式：

- 用少量真实验证回放校准 conditional survival，把校准后的条件概率用于 scoring；
- 在 log 分数上加深度惩罚 $\log Score(path)-\lambda\cdot depth$。取 $\lambda=0.15$ 时，A（深度 1）的惩罚后分数为 −0.507、AC 为 −1.168、B 为 −1.759、ACE 为 −1.915，扩展顺序自动变成「先补浅层分支、再延长深路径」，与后文的节点价值贪心高度一致。

这也是后续 PRESTO / CaDDTree 类工作继续优化 tree scoring 与 cost-aware budget 的原因。

## 6. 节点价值与 cost-aware 选择

### 6.1 Value(node) 的定义与逐项计算

源文给出的节点价值模型是：

$$Value(node)=P(\text{prefix survives})\cdot P(token)\cdot SavedTargetTime-VerifyMarginalCost$$

四项含义：前缀存活概率、该节点 token 的概率、接受一个 Token 所省下的 Target 前向时间、以及为该节点多付的验证边际成本。沿用前一篇的自回归基线，$SavedTargetTime=3.56$ ms/Token。树验证的边际成本取 $T_V^{tree}$ 与 $T_{tree}$ 的导数之和（推导设定，见第 8.1 节），在 $B=7$ 附近约 0.132 ms/节点。

于是每个节点的价值就是「节点概率 × 3.56 − 0.132」（推导值，非实测）：

| 节点 | 深度 | 节点概率 | 期望贡献 | $Value$ |
| --- | --- | --- | --- | --- |
| A | 1 | 0.7000 | 2.492 ms | +2.360 ms |
| AC | 2 | 0.4200 | 1.495 ms | +1.363 ms |
| ACE | 3 | 0.2310 | 0.822 ms | +0.690 ms |
| AD | 2 | 0.2100 | 0.748 ms | +0.616 ms |
| B | 1 | 0.2000 | 0.712 ms | +0.580 ms |
| ACF | 3 | 0.1470 | 0.523 ms | +0.391 ms |
| BC | 2 | 0.1200 | 0.427 ms | +0.295 ms |
| ADE | 3 | 0.1155 | 0.411 ms | +0.279 ms |
| ADF | 3 | 0.0735 | 0.262 ms | +0.130 ms |
| BCE | 3 | 0.0660 | 0.235 ms | +0.103 ms |
| BD | 2 | 0.0600 | 0.214 ms | +0.082 ms |
| BCF | 3 | 0.0420 | 0.150 ms | +0.018 ms |
| BDE | 3 | 0.0330 | 0.117 ms | −0.015 ms |
| BDF | 3 | 0.0210 | 0.075 ms | −0.057 ms |

注意节点概率是「前缀存活 × 本位概率」的乘积，因此深度 2 的 AD（0.21）比深度 3 的 ACE（0.231）只低一点，而深度 1 的 B（0.20）远高于深度 3 的 ADF（0.0735）。**浅层分支的价值密度天然高于深层尾巴**。

### 6.2 两种 7 节点方案的对照

按路径分数 best-first 取 7 个节点得到 $\{A,AC,ACE,ACF,AD,ADE,ADF\}$；按 $Value$ 贪心（并遵守祖先约束：加 AC 前必须已有 A）取 7 个节点得到 $\{A,AC,ACE,AD,B,ACF,BC\}$。两者的期望接受长度按「各深度被覆盖节点概率之和」计算（推导值，非实测）：

| 方案 | 深度 1 覆盖 | 深度 2 覆盖 | 深度 3 覆盖 | $E[A]$ | 每轮提交 $C$ |
| --- | --- | --- | --- | --- | --- |
| 路径分数 best-first | 0.700 | 0.630 | 0.567 | 1.897 | 2.897 |
| 节点价值贪心 | 0.900 | 0.750 | 0.378 | **2.028** | **3.028** |

同样 7 个节点，价值贪心的 $E[A]$ 高 6.9%。原因很直接：路径分数把预算花在 A 分支的深度 3 尾巴（ADE、ADF）上，而价值贪心用同样两个节点换来 B（深度 1，+0.20）与 BC（深度 2，+0.12），浅层覆盖的收益远大于深层尾巴。

这给出一条可执行结论：**树评分不能只用路径概率，必须把节点边际价值与验证边际成本一起算**。纯 best-first 在预算紧张时会系统性浪费节点。

## 7. Tree Verification 与 ancestor-only mask

Target 一次 forward 需要让每个节点只能看到自己的祖先，不能看兄弟分支。因此构造 ancestor-only attention mask：

```text
Root
├─ A
│  ├─ C
│  └─ D
└─ B
   ├─ E
   └─ F
```

节点 `D` 可以看 `Root, A, D`，不能看 `C`。如果 mask 错误让一个分支看见兄弟节点，会破坏 causal semantics，验证结果不再对应真实自回归路径——这类错误不会抛异常，只会让接受率与输出分布悄悄偏离，因此必须用「与逐 token 自回归逐位对账」的方式验证，而不是只看是否报错。

mask 的规模是 $B\times B$。它可以在 CPU 上构造后拷贝到 GPU，也可以用节点祖先索引在 Kernel 内直接判定。两种实现的 CPU 成本与显存成本相差很大，第 10.1 节给出量化对照。

## 8. Node Budget 的性能模型

### 8.1 树验证的成本口径

树越大覆盖率通常越高，$E[A(B)]\uparrow$；但验证成本也增加，$T_V(B)\uparrow$。真正的目标是：

$$Throughput(B)=\frac{E[A(B)]}{T_D+T_{tree}(B)+T_V(B)}$$

这解释了为什么固定「大树」并不合理，后续 cost-aware tree 会直接以 throughput 而不是 accepted length 作为目标。

口径必须与前一篇区分清楚：前一篇的 $T_V(B)=3+0.25B+0.01B^2$ ms 描述**线性块验证**；树验证因为共享前缀 KV 与 ancestor mask，单节点边际成本更低但掩码与索引成本更高，本文改用（推导设定，非实测）：

$$T_V^{tree}(B)=3+0.08B+0.002B^2\ \text{ms},\qquad T_{tree}(B)=0.1+0.01B+0.001B^2\ \text{ms}$$

$T_D=1.40$ ms 沿用前一篇块扩散草拟延迟，收尾 $T_O=0.3$ ms 单列。整轮时间 $T_{round}=T_D+T_{tree}(B)+T_V^{tree}(B)+T_O$，每 Token 时间 $T_{eff}=T_{round}/C$，$C=E[A]+1$。两套 $T_V$ 不可混用，报告中必须注明使用的是哪一套。

### 8.2 预算扫描推导

用第 6.2 节的价值贪心顺序扩展节点，逐档算得（推导值，非实测）：

| $B$ | $E[A]$ | $C$ | $T_{tree}$ | $T_V^{tree}$ | $T_{round}$ | $T_{eff}$ | 节点利用率 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 3（线性） | 1.351 | 2.351 | 0.139 ms | 3.258 ms | 5.097 ms | 2.168 ms | 45.0% |
| 5 | 1.761 | 2.761 | 0.175 ms | 3.450 ms | 5.325 ms | 1.929 ms | 35.2% |
| 7 | 2.028 | 3.028 | 0.219 ms | 3.658 ms | 5.577 ms | 1.842 ms | 29.0% |
| 10 | 2.283 | 3.283 | 0.300 ms | 4.000 ms | 6.000 ms | **1.828 ms** | 22.8% |
| 12 | 2.385 | 3.385 | 0.364 ms | 4.248 ms | 6.312 ms | 1.865 ms | 19.9% |
| 14（全树） | 2.439 | 3.439 | 0.436 ms | 4.512 ms | 6.648 ms | 1.933 ms | 17.4% |

三个读数：

1. 最优预算是 $B=10$，$T_{eff}=1.828$ ms，相对自回归基线 3.56 ms 加速 $3.56/1.828\approx1.95\times$，相对线性 draft 的 2.168 ms 改善 15.7%。
2. 从 10 到 14，$E[A]$ 只增 6.8% 而整轮时间增 10.8%，$T_{eff}$ 反而恶化 5.7%——**全笛卡尔积不是最优解**。
3. 若改用路径分数 best-first，$B=7$ 的 $T_{eff}$ 为 $5.577/2.897=1.925$ ms，比价值贪心的 1.842 ms 差 4.5%。评分方式本身就值 4.5% 的性能。

### 8.3 节点利用率

节点利用率定义为 $E[A]/B$，即「平均有多少比例的验证节点落在最终被接受的路径上」。它随 $B$ 单调下降：45.0% → 17.4%。这意味着树验证天然要为覆盖率支付浪费，而浪费的比例必须与覆盖率一起报告。

只看接受长度会得出「树越大越好」的错误结论；只看节点利用率会得出「线性最好」的错误结论。两者与 $T_{eff}$ 一起看，才能定位真正的最优预算。

## 9. 固定预算下的宽深分配

同样 14 个节点，可以分配成不同形状。用第 2 节分布并把各位置 top-3 概率补为 0.70/0.20/0.06、0.60/0.30/0.07、0.55/0.35/0.06，推导三种形状（非实测）：

| 形状 | 结构 | 深度 1 | 深度 2 | 深度 3 | $E[A]$ | 节点利用率 |
| --- | --- | --- | --- | --- | --- | --- |
| 深窄 | $b=1$，一条路径延长到 14 层 | 0.700 | 0.420 | 0.231 | 1.478 | 10.6% |
| 宽浅 | $b=3,K=2$（12 节点）+ 2 个深度 3 节点 | 0.960 | 0.931 | 0.378 | 2.269 | 16.2% |
| 均衡 | $b=2,K=3$ 全树（14 节点） | 0.900 | 0.810 | 0.729 | **2.439** | **17.4%** |

深窄形状把全部预算压在一条路径上，$E[A]$ 只有 1.478：因为存活概率连乘衰减极快，第 4 位之后贡献已不足 0.1，第 8 位之后不足 0.001，后面 6 个节点几乎是纯浪费。这就是「深树在前部拒绝后全部浪费」的极端形式——一旦第 1 位被拒（概率 0.30），14 个节点全部作废。

宽浅形状补足了浅层覆盖，但深度 3 只剩 2 个节点，$E[A]$ 降到 2.269。均衡形状在本例中最优。

工程结论：固定预算下应当**先保证浅层分支覆盖，再向深处延伸**，且延伸深度以「该深度的边际节点价值仍为正」为界（第 6.1 节表中 BDE、BDF 已转负）。宽深比例不是常量，它随概率分布的陡峭程度移动：分布越平坦（top-1 概率越低），越值得宽；分布越尖锐，越值得深。

## 10. 掩码构造与 KV 重排的实现成本

### 10.1 掩码构造的 CPU 关键路径

ancestor-only mask 有 $B^2$ 项。若在 CPU 上逐项构造（设每项 100 ns）再拷贝到 GPU，推导得（非实测）：

| $B$ | mask 项数 | 单请求构造耗时 | 并发 32、8 核并行的墙钟 |
| --- | --- | --- | --- |
| 14 | 196 | 0.020 ms | 0.078 ms |
| 64 | 4096 | 0.410 ms | 1.64 ms |
| 126 | 15876 | 1.588 ms | 6.35 ms |
| 510 | 260100 | 26.01 ms | 104.0 ms |

单请求下掩码构造看似便宜，但它是 CPU 工作：并发上升时按核数排队，$B=126$、并发 32 时墙钟达 6.35 ms，与整轮 GPU 时间同量级，直接成为关键路径。这就是「验证掩码构造占据 CPU 关键路径」的来源。

三种缓解手段：用祖先索引在 Kernel 内判定而不物化 $B\times B$ 矩阵；把掩码构造与上一轮 GPU 计算重叠；对固定树形预计算并缓存掩码模板。三者都要单独计量，不能只报「掩码构造时间」一个总数。

### 10.2 KV 重排与内存连续性

树验证后只有一条路径被接受，需要把该路径的 KV 搬到连续位置并丢弃兄弟分支。设 32 层、8 个 KV 头、head_dim 128、fp16，则每 token 每层 KV 为 $2\times8\times128\times2=4$ KiB，32 层合计 128 KiB/token。推导两种实现（非实测）：

| 实现 | $B=510$、接受路径长 8 时的搬运量 | HBM 800 GB/s 耗时 | 并发 32 耗时 |
| --- | --- | --- | --- |
| 只 gather 接受路径 | $8\times128$ KiB = 1 MiB | 1.31 µs | 0.042 ms |
| 压缩整段节点 KV | $510\times128$ KiB = 63.75 MiB | 83.6 µs | 2.68 ms |

相差 64 倍。「节点重排破坏内存连续性」的代价几乎完全由实现选择决定：gather 只搬被接受的节点，compact 则把全部废弃分支也搬一遍。因此 KV 布局必须与树形一起设计——按深度优先排列节点可以让接受路径更接近连续，进一步减少 gather 的离散访问。

## 11. DDTree 与 EAGLE Tree 的区别

EAGLE 类 tree 往往来自 autoregressive / feature drafter 的分支 rollout；DDTree 利用 block diffusion 一次得到的 per-position distributions 构树。

共同点：

- 都要在有限节点下覆盖高概率路径；
- 都要 Target tree verification；
- 都需要严格 causal / ancestor mask。

差异：

| 维度 | EAGLE Tree | DDTree |
| --- | --- | --- |
| 候选概率语义 | 条件概率，沿 rollout 逐步生成 | 块内 marginal，需校准为路径概率 |
| Draft cost 结构 | 随分支 rollout 次数增长 | 一次前向得到全部分布，构树在 CPU |
| 路径 scoring 可靠性 | 较高（天然 prefix-based） | 较低（存在第 5 节的错位） |
| 主要额外成本 | Drafter 多次前向 | 掩码构造、节点重排、评分校准 |

因此两者的最优预算不能互相套用：EAGLE Tree 的瓶颈常在 Drafter 侧，DDTree 的瓶颈常在 CPU 掩码与评分侧。选择时仍回到同一个目标函数——满足 SLO 前提下的 Goodput / GPU-hour。

## 12. 八个概念的边界与失败模式

分析范围由八个可观察概念组成：Diffusion Draft Tree、树节点预算、分支因子、前缀共享、树验证、节点存活概率、候选覆盖率、KV 与掩码布局。虽然它们分属不同系统层级，接受长度和单位节点收益会同时受到这些状态影响。

### 12.1 统一检查框架

每个概念都按同一组问题展开：边界与生命周期（输入、输出、状态归属、销毁时点、失败传播）、资源账（计算、显存、内存带宽、主机开销、同步等待分别记账）、负载区间（低载、接近饱和、过载三段同口径）、正确性门禁（Token 序列、采样分布、结构合法性、结束原因、错误传播）、观测字段（请求身份、模型与策略修订、起止时间、阶段耗时、资源快照、失败原因）。跨概念传递的数据必须携带版本身份。每项说明谁维护状态、在哪里计量、什么情况下失效，以及结果怎样传到请求端。

### 12.2 Diffusion Draft Tree

边界检查覆盖输入、输出、状态归属和销毁时点；传给树节点预算的数据应附带模型或策略版本，使测量结果可以对应到唯一配置。固定节点预算在深度与宽度之间分配通常只先改变资源账中的几项，其他资源随后可能进入关键路径。

「构造验证掩码」应覆盖长短输入、不同输出、并发、突发、采样与任务域，并保留三段负载记录。典型失败是**节点重排破坏内存连续性**：接受路径的 KV 分散在兄弟分支之间，gather 退化为大量离散访问。触发停止与回退后系统恢复到已有证据支持的配置。**掩码构造时间**必须附带口径。

### 12.3 树节点预算

边界由输入、输出、状态和拥有者共同确定；连接分支因子时还要传播身份和版本。节点存活概率沿路径相乘并快速衰减，缩短的阶段可能让另一项资源成为瓶颈，分析要对齐阶段事件和资源轨迹。

「设置节点预算」至少比较低载、临近容量与过载，结论只覆盖实际运行过的区间。典型失败是**候选缺少多样性**：预算全压在单一分支上，覆盖率等同线性 draft 却付了树的成本。质量结果优先于速度数字，发布停止并保留问题请求。**KV 重排时间**同时注明单位、窗口和分母。

### 12.4 分支因子

与前缀共享交互的字段必须携带版本身份，便于回放时找到同一配置。树验证可复用 Target 前向但会增加掩码与索引成本，这一机制会移动关键路径，却很少让所有资源同比例变化。

「设计剪枝与回退」是否合适，取决于长度分布、并发、到达过程、采样和任务域。典型失败是**树预算静态而负载动态**：低并发下调出的最优 $B$ 在高并发下挤占 verifier 容量。质量门禁应停止性能发布，回退目标是已验证配置。**接受长度**没有单位、统计窗口和分母时不参与决策。

### 12.5 前缀共享

生命周期落到组件接口，与树验证之间的身份和版本若未绑定，请求时间线就可能混入旧配置。候选覆盖率取决于分支多样性，其影响分散到五项资源；为确认变化来自哪里，要对齐请求时间线与资源采样。

「选择适合的请求分布」的验证分别运行三段负载并使用代表性分布。典型失败是**宽树包含大量低概率节点**：单位节点覆盖收益从 0.0810 跌到 0.0521。当前性能结果不进入候选评审，立即切回已验证配置。**单位节点收益**的定义随报告存档。

### 12.6 树验证

边界检查覆盖输入、输出、状态归属和销毁时点；传给节点存活概率的数据应附带版本。KV 布局影响树节点重排和显存访问，通常只先改变资源账中的几项，其他资源随后可能进入关键路径。

「分配树宽与深」应覆盖长短输入、不同输出、并发、突发、采样与任务域。典型失败是**深树在前部拒绝后全部浪费**：第 1 位被拒时整棵树作废，深窄形状下 14 个节点利用率仅 10.6%。触发停止与回退后系统恢复到已有证据支持的配置。**节点利用率**必须附带口径。

### 12.7 节点存活概率

边界由输入、输出、状态和拥有者共同确定；连接候选覆盖率时还要传播身份和版本。树结构用共享前缀表达多个并行候选序列，缩短的阶段可能让另一项资源成为瓶颈。

「选择扩展节点」至少比较低载、临近容量与过载。典型失败是**验证掩码构造占据 CPU 关键路径**：$B=126$、并发 32 时 CPU 墙钟达 6.35 ms。质量结果优先于速度数字，发布停止并保留问题请求用于重放。**路径存活概率**同时注明单位、窗口和分母，尤其要声明是 marginal 乘积还是校准后的条件概率。

### 12.8 候选覆盖率

与 KV 与掩码布局交互的字段必须携带版本身份。固定节点预算在深度与宽度之间分配会移动关键路径，却很少让所有资源同比例变化：请求事件负责说明顺序，资源曲线负责解释瓶颈转移。

「构造验证掩码」是否合适，取决于长度分布、并发、到达过程、采样和任务域。典型失败是**节点重排破坏内存连续性**：compact 实现比 gather 多搬 64 倍数据。质量门禁应停止性能发布，回退目标是已验证配置。**覆盖率**没有单位、统计窗口和分母时不参与决策。

### 12.9 KV 与掩码布局

生命周期落到组件接口，与 Diffusion Draft Tree 之间的身份和版本若未绑定，请求时间线就可能混入旧配置。节点存活概率沿路径相乘并快速衰减，其影响分散到五项资源。

「设置节点预算」的验证分别运行三段负载并使用代表性分布。典型失败是**候选缺少多样性**：布局按宽度优先排列但评分按深度优先扩展，导致接受路径高度离散。当前性能结果不进入候选评审，立即切回已验证配置。**验证节点数**的定义随报告存档，包括单位、窗口和分母。

## 13. 六个机制的因果分析

![DDTree 的机制与证据闭环](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y3_l08_01.png)

*机制流程：把候选树构造、节点预算分配、树验证与证据闭环连接起来。*

核心关系写作 $Value(node)=P(\text{prefix survives})\cdot P(token)\cdot SavedTargetTime-VerifyMarginalCost$。Diffusion Draft Tree 与树节点预算进入决策变量，模型、负载和硬件限定结果，节点利用率、验证节点数与单位节点收益承担验证。公式只表达这些变量的关系；时间单位、概率取值和节点利用率分母必须在运行配置中显式记录。框架调度、Kernel 启动、内存分配、网络、客户端和取消传播仍由真实路径计量；模拟与实测方向不一致时，检查遗漏变量和指标口径。

### 13.1 机制 1：树结构用共享前缀表达多个并行候选序列

从请求关键路径入手，变化前后每个阶段的顺序、并行性和合批条件均需标注，Diffusion Draft Tree 作为启用条件，节点利用率作为端到端结果。共享前缀让 $B$ 个节点表达多于 $B/K$ 条路径，但接受路径只有一条，因此利用率天然低于线性 draft。

容量测试覆盖低载、稳定高载和过载：低载显示固定与同步成本，高载显示队列、批处理及共享资源竞争。若出现深树在前部拒绝后全部浪费，说明局部延迟没有变成有效容量，需要核对候选工作占用的公共资源。

接口合同包括格式、Shape、缓存键、版本与回退语义；「构造验证掩码」进入评审前，使用非法输入、边界长度和资源不足场景检验保护路径。采集证据时把策略输入、阈值、候选集合与验证节点数、错误、取消及资源事件放进同一请求链。发布单元包含灰度身份、门禁、停止动作和已预热回滚路径；检测到候选缺少多样性后执行局部撤回，并确认在途工作、缓存与资源回到稳定状态。

### 13.2 机制 2：固定节点预算在深度与宽度之间分配

这一机制会改写请求的阶段顺序。画出变化前后的关键路径，标明并行、串行和跨请求合批位置；树节点预算给出状态条件，路径存活概率验证结果是否传到请求端。第 9 节的三形状对照是这一机制的定量形式：同样 14 节点，$E[A]$ 从 1.478 到 2.439 相差 65%。

单请求数据不足以评价：低载用于测量固定成本，接近容量时观察批处理与共享资源，过载时确认拒绝和尾延迟。验证掩码构造占据 CPU 关键路径若只在并发后出现，优先检查候选路径对正常请求资源的挤占。

数据格式、张量形状、缓存身份、版本兼容和错误传播共同构成实现边界；「设置节点预算」需要在合同冻结后测试正常、无效、极端和资源受限输入。证据需要成对的原因和结果字段：原因包括决策特征、阈值和候选，结果包括掩码构造时间、错误、取消和资源快照。发布时配置独立开关、灰度身份、停止条件和暖回滚目标；树预算静态而负载动态触发后只撤回相关变化。

### 13.3 机制 3：节点存活概率沿路径相乘并快速衰减

把前后两条请求时间线对齐，逐段标出可并行、必须串行和允许合批的工作。分支因子说明机制何时生效，覆盖率负责确认关键路径是否真的缩短。连乘衰减意味着深节点的边际价值迅速转负（第 6.1 节表中 BDE、BDF），因此剪枝阈值应当由价值而非深度硬性决定。

分别施加轻载、稳定高载和过载流量，可以分辨同步开销、队列增长、合批变化与资源竞争。检测到节点重排破坏内存连续性后，沿共享执行资源检查局部收益为何没有进入系统 Goodput。

确定接口时同时规定数据与 Shape、缓存和版本身份、错误及回退，随后以无效输入、极端长度和资源不足验证「设计剪枝与回退」。观测时原因侧保存策略输入、阈值和候选集合，结果侧保存 KV 重排时间、错误、取消与资源。该机制通过独立开关进入灰度，出现宽树包含大量低概率节点时撤回本项候选，并核对在途请求、缓存状态与资源是否释放。

### 13.4 机制 4：树验证可复用 Target 前向但会增加掩码与索引成本

请求执行该机制后，阶段边界和依赖关系会发生变化。先记录原路径，再记录候选路径中的串行、并行与合批段，同时保存前缀共享状态和验证节点数。复用前向是树验证的收益来源，掩码与索引是它的新增成本，两者必须分开记账才能判断净方向。

容量评估放在三个负载区间中运行。候选缺少多样性意味着候选工作可能消耗了服务正常请求所需的容量——付了 $B$ 个节点的验证成本却只覆盖一条路径。

实现时明确数据格式、张量形状、缓存身份、版本兼容和错误回退；执行「选择适合的请求分布」前冻结接口合同，并加入无效输入、极端长度与资源不足测试。Trace 同时记录决策输入与执行结果，后者含接受长度、错误、取消和资源变化。上线合同写明灰度范围、停止条件、开关和暖回滚目标；深树在前部拒绝后全部浪费发生后，系统恢复相关稳定配置，并持续观察请求排空、缓存切换和资源回收。

### 13.5 机制 5：候选覆盖率取决于分支多样性

从请求关键路径入手，变化前后每个阶段的顺序、并行性和合批条件均需标注，树验证作为启用条件，掩码构造时间作为端到端结果。覆盖率不是节点数的函数而是分支分布的函数：第 6.2 节显示同样 7 节点，价值贪心比路径分数多覆盖 6.9% 的期望接受长度。

容量测试覆盖低载、稳定高载和过载。若出现树预算静态而负载动态，说明局部延迟没有变成有效容量，需要核对候选工作占用的公共资源。

接口合同包括格式、Shape、缓存键、版本与回退语义；「分配树宽与深」进入评审前，使用非法输入、边界长度和资源不足场景检验保护路径。采集证据时把策略输入、阈值、候选集合与单位节点收益、错误、取消及资源事件放进同一请求链。发布单元包含灰度身份、门禁、停止动作和已预热回滚路径；检测到验证掩码构造占据 CPU 关键路径后执行局部撤回。

### 13.6 机制 6：KV 布局影响树节点重排和显存访问

这一机制会改写请求的阶段顺序。画出变化前后的关键路径，标明并行、串行和跨请求合批位置；节点存活概率给出状态条件，KV 重排时间验证结果是否传到请求端。第 10.2 节显示 gather 与 compact 两种实现相差 64 倍搬运量，布局设计因此不是细节而是主要成本项。

单请求数据不足以评价：低载测量固定成本，接近容量时观察批处理与共享资源，过载时确认拒绝和尾延迟。节点重排破坏内存连续性若只在并发后出现，优先检查离散访问对 HBM 有效带宽的折损。

数据格式、张量形状、缓存身份、版本兼容和错误传播共同构成实现边界；「选择扩展节点」需要在合同冻结后测试正常、无效、极端和资源受限输入。证据需要成对字段：原因包括树形、布局与剪枝阈值，结果包括 KV 重排时间、显存占用、错误与取消。发布时配置独立开关、灰度身份、停止条件和暖回滚目标；候选缺少多样性触发后只撤回相关变化，并确认在途请求、缓存和资源释放。

## 14. 工程决策与取舍

### 14.1 决策 1：设置节点预算

候选做法是固定 $B$、按并发分档、按请求熵分档、运行时按边际价值自适应。第 8.2 节给出固定预算的最优点（本例 $B=10$），但该点随概率分布与验证成本移动。判据是 $T_{eff}$、节点利用率与单位节点收益的成对记录，并附「树预算静态而负载动态」的门禁。评审需运行基线（线性 draft）、单变量候选与暖回退三组，共享同一请求集合与随机种子。

### 14.2 决策 2：分配树宽与深

深窄、宽浅、均衡三种形状在第 9 节的 $E[A]$ 分别为 1.478 / 2.269 / 2.439。取舍原则是先保证浅层分支覆盖再向深处延伸，延伸以边际节点价值为正为界。判据是路径存活概率、覆盖率与节点利用率，并说明分布陡峭程度如何移动最优宽深比。若运行时不支持动态树形，则按主力负载的概率分布选一个折中形状并记录适用范围。

### 14.3 决策 3：选择扩展节点

纯路径分数 best-first、节点价值贪心、带深度惩罚的 log 分数、cost-aware 预算分配。第 6.2 节显示价值贪心比路径分数在 7 节点下多 6.9% 的 $E[A]$、在 $T_{eff}$ 上好 4.5%。取舍在于实现复杂度：价值贪心需要祖先约束与边际成本估计，深度惩罚只需一个超参。判据是单位节点收益与掩码构造时间，且必须声明 scoring 用的是 marginal 还是校准后的条件概率。

### 14.4 决策 4：构造验证掩码

CPU 物化 $B\times B$ 矩阵、Kernel 内按祖先索引判定、预计算模板缓存。第 10.1 节显示 CPU 物化在 $B=126$、并发 32 时墙钟达 6.35 ms。取舍在于显存与 CPU 的互换：物化占显存但 Kernel 简单，索引判定省显存但 Kernel 复杂。判据是掩码构造时间与节点利用率，并附「验证掩码构造占据 CPU 关键路径」的停止动作。正确性必须用与逐 token 自回归逐位对账验证，不能只看是否报错。

### 14.5 决策 5：设计剪枝与回退

按深度硬截断、按路径分数阈值、按节点价值阈值、按负载动态收缩。价值阈值最贴合收益模型但需要校准；深度截断最简单但会误剪高价值浅分支。判据是覆盖率、单位节点收益与接受长度，并说明剪枝后树形变化对 KV 布局与掩码模板的影响。回退路径必须能在不重新下载制品的情况下恢复线性 draft。

### 14.6 决策 6：选择适合的请求分布

树验证的收益高度依赖分布形状：top-1 概率低（分支不确定）时收益大，top-1 概率接近 1 时树几乎等同线性却多付掩码成本。因此应按请求类型与预估熵分流，高确定性请求走线性 draft，低确定性请求走树验证。判据是按域分桶的接受长度、节点利用率与高低并发 Goodput，并把「候选缺少多样性」作为停止条件。启用范围与实际证据范围保持一致。

## 15. 实验设计与双路径验证

实验复用前一篇块扩散草拟的模拟框架，在其上增加树形构造与 ancestor mask 验证两个模块。

**路径 A：机制模拟（`source=fixture`）。** 只依赖 CPU，输入每位置 top-$b$ 分布、节点预算 $B$、评分方式、$T_D$、$T_{tree}(B)$、$T_V^{tree}(B)$、$T_O$，输出树形、$E[A]$、$C$、$T_{eff}$、节点利用率、覆盖率、单位节点收益与 $Value(node)$ 分布。扫描维度为 $B\in\{3,5,7,10,12,14,30,64\}$、$b\in\{1,2,3,4\}$、$K\in\{2,3,4,6,8\}$、评分方式 $\in\{$路径分数, 节点价值, 深度惩罚$\}$、并发档 $\in\{1,16,64\}$。模拟必须显式区分 marginal 乘积与校准后条件概率两套口径。

**路径 B：真实测量（`source=measured`）。** 在可用 CUDA GPU 上运行同一组配置，采集八项必测指标：

| 指标 | 口径要求 |
| --- | --- |
| 验证节点数 | 每轮实际进入 Target 前向的节点数，注明是否含 root |
| 节点利用率 | $E[A]/B$，注明 $E[A]$ 是否含 Bonus |
| 路径存活概率 | 按深度分桶，注明 marginal 还是校准条件概率 |
| 覆盖率 | 真实 Target 路径落在树中的比例，注明样本量与窗口 |
| 单位节点收益 | 净收益毫秒 / 节点数，注明成本口径 |
| 掩码构造时间 | 毫秒/轮，区分 CPU 构造、H2D 拷贝与 Kernel 内判定 |
| KV 重排时间 | 毫秒/轮，区分 gather 与 compact，注明搬运字节数 |
| 接受长度 | 每轮接受 draft token 数，注明是否含 Bonus |

外加端到端 TPOT、P99、总吞吐与有效单位成本。每次运行记录完整环境与模型、Drafter、树形参数、评分方式、Compatibility hash。

**双路径对账。** 同一配置下比较模拟与实测的 $E[A]$、$T_{eff}$ 与掩码/KV 成本：方向一致但数值偏离时优先补齐 Kernel 启动、离散访问带宽折损、CPU 排队与同步项；方向相反时先核对口径（$T_V$ 用线性还是树口径、$C$ 是否含 Bonus、覆盖率分母是路径数还是请求数），再检查是否触发未建模的剪枝或回退。模拟结果不得写成实测数字，实测结果不得外推到未运行过的负载区间。

**门禁与回滚。** ancestor mask 必须通过与逐 token 自回归的逐位对账；输出合同任一项不通过即停止性能发布。性能候选带独立开关、灰度身份、停止阈值与已预热回滚修订，回退目标为线性 draft 路径。

## 16. 常见错误与排查

| 现象 | 可能原因 | 排查动作 |
| --- | --- | --- |
| 树比线性 draft 更慢 | 预算过大或概率分布过于尖锐 | 扫 $B$ 并记录节点利用率与单位节点收益 |
| 接受长度上升但吞吐下降 | 验证与掩码成本超过接受收益 | 用 $Throughput(B)$ 而非 $E[A]$ 作目标 |
| 深路径评分高但实际接受低 | marginal 当 conditional 用，高估约 33% | 用真实验证回放校准条件概率或加深度惩罚 |
| 同预算下覆盖率偏低 | 路径分数 best-first 把节点花在深层尾巴 | 改节点价值贪心，先补浅层分支 |
| 高并发下 CPU 打满 | 逐轮物化 $B\times B$ 掩码 | 改 Kernel 内祖先判定或与 GPU 计算重叠 |
| KV 重排耗时异常 | compact 实现搬运全部废弃分支 | 改 gather，按深度优先排列节点 |
| 输出分布与自回归不一致 | ancestor mask 泄漏兄弟分支 | 与逐 token 自回归逐位对账，检查 mask 构造 |
| 第 1 位拒绝后整轮浪费 | 深窄形状，节点集中在深处 | 按第 9 节调整宽深比，浅层优先 |
| 低并发最优预算上线后变差 | 树预算静态而负载动态 | 三档并发重扫，按并发下发预算 |
| 模拟与实测方向相反 | $T_V$ 口径混用（线性 vs 树） | 统一口径后再补未建模变量 |

## 17. 常见追问与解答

**问：树验证为什么能比线性 draft 接受更多 token？**
答：线性 draft 只覆盖一条路径，一旦某位置的第二名才是 Target 偏好，后缀全部作废。树用共享前缀同时覆盖多条分支，只要真实路径落在树中就能继续接受。

**问：为什么不直接把所有候选都验证？**
答：节点量按 $b^K$ 爆炸，$b=4,K=8$ 就是 87380 个节点。验证成本与掩码成本随之上升，而新增节点几乎都落在低概率分支上。

**问：最优节点预算怎么定？**
答：以 $Throughput(B)$ 为目标扫描，而不是以接受长度为目标。本文推导下最优 $B=10$，全树 14 反而更慢，且最优点随概率分布与并发移动。

**问：路径分数排序为什么不够？**
答：它忽略节点边际价值与验证边际成本。同样 7 个节点，价值贪心比路径分数多 6.9% 的期望接受长度、$T_{eff}$ 好 4.5%。

**问：Diffusion 的 marginal 概率能直接当路径概率吗？**
答：不能。Target 接受是严格 prefix-based，marginal 乘积会高估深路径（本文示例高估 33.3%）。需要校准或加深度惩罚。

**问：ancestor mask 错了会怎样？**
答：不会抛异常，但分支看见兄弟节点会破坏因果语义，验证结果不再对应真实自回归路径。必须与逐 token 自回归逐位对账。

**问：树验证的 CPU 成本为什么重要？**
答：掩码构造是 CPU 工作，并发上升时按核数排队。$B=126$、并发 32 时墙钟达 6.35 ms，与整轮 GPU 时间同量级。

**问：DDTree 与 EAGLE Tree 的最优预算能互相套用吗？**
答：不能。EAGLE Tree 瓶颈常在 Drafter 多次前向，DDTree 瓶颈常在 CPU 掩码与评分校准，成本结构不同。

## 写在最后

树验证把「被丢掉的第二名候选」重新利用起来，但它同时引入三项新成本：节点预算的分配、评分与真实前缀语义的错位、掩码与 KV 布局的实现开销。本文的推导给出的最重要结论不是「树比线性好」，而是「以 throughput 而非接受长度为目标、以节点价值而非路径分数排序、以浅层覆盖优先分配预算」——这三条决定了树验证是净收益还是净亏损。
