# EAGLE-3：Training-Time Test 与直接 Token 预测

本文把 EAGLE-3 放回真实请求链路中讨论，中心问题是「EAGLE-3 如何通过直接预测与多层特征融合提高接受长度？」。EAGLE-3 Drafter 和直接 Token 预测提供分析入口，计算模型负责说明方向，实验和发布门禁负责限定结论。评审时需要同时查看模型版本、负载、调度、显存、并发与服务等级，避免把 Drafter 的局部理想收益直接当成端到端结果。

方法上先用 CPU 模拟控制 Drafter 与直接 Token 预测的关系，再用真实 CUDA 路径检查这些关系进入实现后增加了哪些成本。每份结果都要标明数据来源、运行环境和适用边界。这样得到的是可复查的工程判断，而非依赖某个框架版本的参数口诀。

## 1. 内容概览

- EAGLE-3 Drafter、直接 Token 预测和 Target 多层特征融合之间的状态与资源关系。
- 用 $P(A\ge j)=\prod_{i=1}^{j}p_i$ 与 $E[A]=\sum_{j=1}^{K}P(A\ge j)$ 建立可计算的收益边界并解释全部变量。
- 围绕位置级 Token 准确率、平均接受长度、树节点利用率和域外退化设计可复现实验。
- 识别平均准确率掩盖后部位置崩塌、训练期教师特征与服务期递归特征不一致、特征层选择增加带宽而收益有限等典型失败模式。
- 对中心问题给出包含适用条件、证据、风险和回滚的工程答案。

## 2. 核心直觉：从「预测未来特征」到「预测可验证 Token」

假设 Target Model 在当前上下文 $x_{1:t}$ 下产生隐藏状态：

$$h_t^{(l)}=f_l(x_{1:t})$$

早期思路希望 Drafter 预测未来隐藏状态：

$$\hat h_{t+1}\approx h_{t+1}$$

再从预测特征映射到 Token。问题是：Feature 空间的距离变小，并不保证最终 Token 排名一定更接近 Target。对于 speculative decoding，真正产生收益的是 Target 最终接受多少 Token，而不是 hidden vector 的欧氏距离有多漂亮。

因此可以把训练目标更直接地写成未来 Token 的交叉熵：

$$\mathcal{L}_{draft}=-\sum_{j=1}^{K}\log q_\theta(x_{t+j}\mid \text{features},\ \text{draft context})$$

这里 $q_\theta$ 是 Drafter。目标从「回归一个向量」变成「预测会被验证的离散 Token」，评价口径也随之从特征距离变成位置级准确率与接受长度。

## 3. 前置知识与实验环境

需要理解自回归生成、Tokenizer、Prefill、Decode、KV Cache、批处理和分位延迟的基本含义。所有缩写都会在正文首次出现处定义；没有某个特定框架经验不妨碍理解机制。实验需要 Python 3.11 或兼容版本。机制模拟只依赖 CPU；真实路径需要任意可用的 CUDA GPU、与驱动兼容的 PyTorch，以及自行准备的本地小模型或兼容制品。

验证前必须记录 GPU 名称、数量、可用显存、驱动、CUDA、PyTorch、推理框架、模型摘要、精度、批量、序列长度和完整命令。脚本根据可用显存缩放模型、批量、上下文和样本数，并把 Drafter 状态写入报告；可选 CUDA 入口不下载未经确认的大模型。

性能问题要从测量条件开始：模型与修订、输入输出分布、请求到达、并发、采样、缓存、位置级 Token 准确率统计方式、服务等级和硬件均需保持可追溯。「选择注入的 Target 层」和「确定 Drafter 宽度与深度」只有在同一证据口径下才可比较。

## 4. 为什么需要 Target 的多层特征

### 4.1 不同层的信息分工

Transformer 不同层包含的信息不同：

- 较浅层更接近词法与局部信息；
- 中间层形成组合语义；
- 深层更接近最终 next-token 决策。

如果 Drafter 只接最终一层，可能丢失一些对未来 rollout 有帮助的中间信号。

### 4.2 融合表达与工程代价

一种抽象表达是把多层特征融合成条件向量：

$$z_t=\phi\left(h_t^{(l_1)},h_t^{(l_2)},\dots,h_t^{(l_m)}\right)$$

再由 Drafter 提出候选：

$$q_\theta(x_{t+1:t+K}\mid z_t)$$

$\phi$ 可以是拼接、投影、加权或专门的 fusion 模块。工程上真正要关注的不是公式形态，而是 **Target feature 获取本身会不会增加数据存储、通信和训练开销**。多层特征提高候选质量的同时，也按比例放大了特征张量的体积。

### 4.3 特征存储量推导

Offline 特征体积可以按 $N_{token}\times m\times d_{model}\times B_{dtype}$ 估算。取 $d_{model}=4096$、语料 $10^8$ Token（推导设定，非实测）：

| 注入层数 $m$ | 精度 | 每 Token 特征字节 | $10^8$ Token 总量 |
| --- | --- | --- | --- |
| 1 | fp16 | 8 KiB | 约 0.75 TiB |
| 3 | fp16 | 24 KiB | 约 2.24 TiB |
| 3 | fp32 | 48 KiB | 约 4.47 TiB |

这张表解释了为什么「特征层选择增加带宽而收益有限」是一个真实风险：从 1 层扩到 3 层，存储与 I/O 变成三倍，而接受长度的提升未必成正比。层选择必须与第 7 节的接受长度推导一起评估，而不是只看 validation loss 下降。

## 5. Training-Time Test：训练期就运行 Drafter

### 5.1 exposure mismatch

普通蒸馏往往先构造「正确答案」，再让学生模型逼近。Speculator 的特殊点在于：训练时最好让 Drafter 看到自己推出来的状态，而不是永远只在完美 teacher prefix 上学习。因为上线后 Drafter 的第 2、3、4 个候选是建立在它自己前面预测的候选之上。

如果训练只看 ground-truth prefix，就会出现 exposure mismatch：

```text
训练：永远从正确前缀继续
上线：经常从自己猜出的前缀继续
```

### 5.2 训练期递归状态

Training-Time Test 可以理解为：训练阶段主动运行/测试 Drafter，让训练样本更接近真实 speculative rollout 分布。工程含义是训练管线里必须包含一次真实的草拟 rollout，并把 rollout 产生的状态回灌为后续位置的输入条件，而不是全部使用教师强制（teacher forcing）的前缀。

这也带来一个可检验的失败模式：训练期教师特征与服务期递归特征不一致。若训练时每个位置都拿到 Target 的真实 hidden states，而服务时第 2 个位置之后只能拿到 Drafter 自己递推的状态，位置级准确率会在深层位置显著低于训练期读数。核对方法是比较同一 Drafter 在「教师前缀」与「自递归前缀」两种输入下的逐位置准确率曲线。

## 6. 性能模型与训练期指标

### 6.1 统一性能模型

沿用前一篇建立的统一模型：

$$T_{effective}=\frac{T_{draft}+T_{verify}+T_{other}}{E[A]}$$

EAGLE-3 优化的重点不是让 $T_{draft}$ 变成 0，而是用更好的候选质量提高 $E[A]$，同时保持 Drafter 足够小。换言之，分子上的草拟成本允许增加，只要分母上的接受长度增加得更快。

### 6.2 训练期至少同时记录七项

训练一个 Speculator 时，不要只看 validation loss。至少同时记录：

- top-1 token accuracy；
- position-wise accuracy；
- mean accepted length；
- tree acceptance；
- draft ms/round；
- verify ms/round；
- end-to-end TPOT。

前四项属于候选质量，后三项属于成本与端到端结果。只报告质量项会漏掉「质量提高但草拟更慢」的情形；只报告成本项会漏掉「更快但接受长度下降」的情形。

## 7. Position-wise Accuracy 与 Prefix Survival

### 7.1 公式

假设未来 5 个位置准确率是：

```text
pos1: 90%
pos2: 75%
pos3: 58%
pos4: 40%
pos5: 25%
```

如果验证要求最长正确前缀，第 4/5 位置的低准确率未必能转化为多少收益。更重要的是 prefix survival：

$$P(A\ge k)=P(d_1\ \text{accepted},\dots,d_k\ \text{accepted})$$

在各位置接受事件独立的近似下：

$$P(A\ge j)=\prod_{i=1}^{j}p_i$$

平均 accepted length 可写为：

$$E[A]=\sum_{j=1}^{K}P(A\ge j)$$

这比「所有位置平均准确率」更接近真实加速收益。

### 7.2 五位置算例

把上面的准确率当作 $p_i$ 代入（推导值，非实测；独立假设只是近似）：

| 位置 $j$ | $p_j$ | $P(A\ge j)$ |
| --- | --- | --- |
| 1 | 0.90 | 0.9000 |
| 2 | 0.75 | 0.6750 |
| 3 | 0.58 | 0.3915 |
| 4 | 0.40 | 0.1566 |
| 5 | 0.25 | 0.0392 |

$$E[A]=0.9000+0.6750+0.3915+0.1566+0.0392\approx2.16$$

若计入验证全接受时的 Bonus Token，则每轮提交约 $3.16$ 个 Token。

对比一个常见误算：五个位置的平均准确率为 $(90+75+58+40+25)/5=57.6\%$，若用「平均准确率 × 位置数」估计接受长度会得到 $0.576\times5=2.88$，比正确值 $2.16$ 高估约 33%。原因是平均准确率把后部位置的贡献线性计入，而 prefix survival 是连乘，后部位置必须在前部全部存活的条件下才有意义。

### 7.3 前部位置与后部位置的边际收益

在同一算例上分别做两组改动（推导值，非实测）：

| 改动 | 新的 $E[A]$ | 相对基线增量 |
| --- | --- | --- |
| 基线（90/75/58/40/25） | 2.162 | — |
| pos2 从 75% 提到 85% | 2.331 | +0.168（约 +7.8%） |
| pos4、pos5 从 40%/25% 提到 55%/40% | 2.268 | +0.106（约 +4.9%） |

后两位置的准确率提升幅度更大（+15 与 +15 个百分点），带来的接受长度增量却更小。这定量说明了「位置级准确率决定深层候选的存活概率」：优化资源应优先投向前部位置与深层候选的前缀依赖，而不是平均地拉高所有位置。

## 8. 训练数据工程：Offline 与 Online Features

EAGLE-3 类训练通常需要 Target 输出的隐藏状态，因此工程管线可以分两种。

### 8.1 Offline Features

先跑 Target，把特征保存到磁盘。优点是 Drafter 训练时不需要持续加载 Target。缺点：

- 特征数据可能巨大（见第 4.3 节推导）；
- 数据集、Target revision、层选择改变后需要重建；
- I/O 可能变成训练瓶颈。

### 8.2 Online Features

训练时按需运行 Target 产生 feature。优点是数据新鲜、流程简单、易做在线采样；缺点是 Target forward 显著增加训练成本。

### 8.3 选择依据

选择取决于训练规模、存储、Target 大小和迭代速度。一个实用的判断顺序是：先估算特征体积与可用存储带宽，再估算 Target forward 的额外 GPU 时间，最后看迭代频率——如果层选择与 Target 修订还在频繁变动，Offline 特征的重建成本可能超过 Online 的 forward 成本。

无论哪种管线，特征都必须绑定 Target 修订、层索引、归一化方式与精度；否则训练出的 Drafter 无法证明与服务期特征同源。

## 9. 八个观察对象的边界与失败模式

决策所需的八个观察对象为：EAGLE-3 Drafter、直接 Token 预测、Target 多层特征融合、Training-Time Test、位置级准确率、特征归一化与投影、树候选与验证、训练域和服务域。它们横跨算法、运行时和平台，共同作用于显存增量与域外退化。每个对象都要标出拥有者、状态、计量点和失败边界，局部变化才能与端到端结果对上。

### 9.1 统一检查框架

每个对象都按同一组问题展开：边界与生命周期（接收什么、产生什么、谁维护、何时结束、失败如何传播）、资源账（计算、显存、内存带宽、主机开销、同步等待分别记账）、负载区间（低载、接近饱和、过载三段同口径）、正确性门禁（Token 序列、采样分布、结构合法性、结束原因、错误传播）、观测字段（请求身份、模型与策略修订、起止时间、阶段耗时、资源快照、失败原因）。跨对象传递的数据必须携带版本身份，否则请求时间线会混入旧配置。

### 9.2 EAGLE-3 Drafter

生命周期需要落到组件接口，并与直接 Token 预测绑定身份和版本。直接预测 Token 减少未来特征回归误差的级联，其影响分散到计算、显存、内存带宽、主机处理和同步等待；某一阶段变短时，被遮蔽的成本可能随即暴露，因此要对齐请求时间线与资源采样，而非只看整段运行的 GPU 平均值。

边际价值随输入长度、输出长度、并发、流量突发、采样和任务域变化。典型失败是 Drafter 版本与 Target 修订不匹配：此时性能结果不进入候选评审，立即切回已验证配置，失败样本与版本信息一并保存。Target 验证延迟的定义随报告存档，包括单位、窗口和分母。

### 9.3 直接 Token 预测

边界检查覆盖输入、输出、状态归属和销毁时点；传给 Target 多层特征融合的数据应附带模型或策略版本。资源账拆成五项，训练阶段模拟推理期递归状态以缩小暴露偏差通常只先改变其中几项，其他资源随后可能进入关键路径。

「按域训练或共享 Drafter」的验证应覆盖长短输入、不同输出、并发、突发、采样与任务域，并保留三段负载记录；容量判断不能从一次固定批量的短运行外推。典型失败是代码域收益无法迁移到开放聊天，此时触发停止与回退。端到端加速比必须附带口径。

### 9.4 Target 多层特征融合

边界由输入、输出、状态和拥有者共同确定；连接 Training-Time Test 时要传播身份和版本。测量时分别记录算力、显存、带宽、CPU 开销与同步。位置级准确率决定深层候选的存活概率，缩短的阶段可能让另一项资源成为瓶颈，因此分析要对齐阶段事件和资源轨迹，不让单个平均利用率代替因果证据。

「设置树宽和验证预算」至少比较低载、临近容量与过载，结论只覆盖实际运行过的区间。典型失败是只复述论文速度比而没有本机基线：质量与端到端结果优先于速度数字，发布停止，流量回到已验证修订。显存增量同时注明单位、窗口和分母。

### 9.5 Training-Time Test

先列出它接收什么、产生什么、由谁维护以及状态何时结束；与位置级准确率交互的字段必须携带版本身份。资源模型把计算量、显存占用、内存流量、主机工作和等待时间单独记账：Drafter 容量与延迟共同决定端到端收益，会移动关键路径，却很少让所有资源同比例变化。

「制定模型与 Drafter 兼容矩阵」是否合适，取决于所面对的长度分布、并发、到达过程、采样和任务域。典型失败是平均准确率掩盖后部位置崩塌，质量门禁应停止性能发布，回退目标是已验证配置并保留问题请求。域外退化没有单位、统计窗口和分母时不参与决策。

### 9.6 位置级准确率

生命周期落到组件接口，并与特征归一化与投影绑定身份和版本。服务域漂移会改变接受长度分布，其影响分散到计算、显存、内存带宽、主机处理和同步等待。「选择注入的 Target 层」的验证分别运行三段负载并使用代表性分布，单一长度、批量或短窗口只能说明该测试点。

典型失败是训练期教师特征与服务期递归特征不一致：当前性能结果不进入候选评审，立即切回已验证配置。位置级 Token 准确率的定义随报告存档，包括单位、窗口和分母。

### 9.7 特征归一化与投影

边界检查覆盖输入、输出、状态归属和销毁时点；传给树候选与验证的数据应附带版本。多层 Target 特征为未来 Token 提供不同抽象层次的条件，通常只先改变资源账中的几项，其他资源随后可能进入关键路径。

「确定 Drafter 宽度与深度」应覆盖长短输入、不同输出、并发、突发、采样与任务域。典型失败是特征层选择增加带宽而收益有限，触发停止与回退，系统恢复到已有证据支持的配置。平均接受长度必须附带口径。

### 9.8 树候选与验证

边界由输入、输出、状态和拥有者共同确定；连接训练域和服务域时要传播身份和版本。测量分别记录算力、显存、带宽、CPU 开销与同步。直接预测 Token 减少误差级联后，缩短的阶段可能让另一项资源成为瓶颈。

「构造 Training-Time Test 样本」至少比较低载、临近容量与过载。典型失败是 Drafter 版本与 Target 修订不匹配：质量结果优先于速度数字，发布停止，流量回到已验证修订，相关请求留作重放。树节点利用率同时注明单位、窗口和分母。

## 10. 六个机制的因果分析

*机制流程：把 EAGLE-3 的输入、关键决策、执行与证据闭环连接起来。*

用于推演的性能关系为 $P(A\ge j)=\prod_{i=1}^{j}p_i$ 与 $E[A]=\sum_{j=1}^{K}P(A\ge j)$。它帮助评审 Drafter 与直接 Token 预测怎样作用于位置级 Token 准确率、Drafter 延迟和域外退化，没有预设具体设备的基准值。代入数据前先统一时间单位，检查概率范围，并注明吞吐量计算的是请求、Token 还是满足 SLO 的有效完成。公式与实测产生矛盾时，处理顺序是检查假设、遗漏项和统计方式。

### 10.1 机制 1：多层 Target 特征为未来 Token 提供不同抽象层次的条件

请求执行后阶段边界和依赖关系会发生变化。先记录原路径，再记录候选路径中的串行、并行与合批段；同时保存 Drafter 状态和位置级 Token 准确率，便于把原因与结果关联起来。

容量评估放在三个负载区间中运行：固定开销通常在低载突出，队列和资源争用会在高载显现。实现时明确数据格式、张量形状、缓存身份、版本兼容和错误回退；执行「构造 Training-Time Test 样本」前冻结接口合同，并加入无效输入、极端长度与资源不足测试。

Trace 同时记录决策输入与执行结果：前者含阈值和候选，后者含 Drafter 延迟、错误、取消和资源变化。上线合同写明灰度范围、停止条件、开关和暖回滚目标；「代码域收益无法迁移到开放聊天」发生后，系统恢复相关稳定配置，并持续观察请求排空、缓存切换和资源回收。

### 10.2 机制 2：直接预测 Token 减少未来特征回归误差的级联

从请求关键路径入手，变化前后每个阶段的顺序、并行性和合批条件均需标注，直接 Token 预测作为启用条件，平均接受长度作为端到端结果。

容量测试覆盖低载、稳定高载和过载：低载显示固定与同步成本，高载显示队列、批处理及共享资源竞争。若出现特征层选择增加带宽而收益有限，说明局部延迟没有变成有效容量，需要核对候选工作占用的公共资源。

接口合同包括格式、Shape、缓存键、版本与回退语义。「按域训练或共享 Drafter」进入评审前，使用非法输入、边界长度和资源不足场景检验保护路径。采集证据时把策略输入、阈值、候选集合与 Target 验证延迟、错误、取消及资源事件放进同一请求链。发布单元包含灰度身份、门禁、停止动作和已预热回滚路径；检测到只复述论文速度比而没有本机基线后执行局部撤回，并确认在途工作、缓存与资源回到稳定状态。

### 10.3 机制 3：训练阶段模拟推理期递归状态以缩小暴露偏差

这一机制会改写请求的阶段顺序。画出变化前后的关键路径，标明并行、串行和跨请求合批位置；Target 多层特征融合给出状态条件，树节点利用率验证结果是否传到请求端。

单请求数据不足以评价该机制：低载用于测量固定成本，接近容量时观察批处理与共享资源，过载时确认拒绝和尾延迟。「Drafter 版本与 Target 修订不匹配」若只在并发后出现，优先检查候选路径对正常请求资源的挤占。

数据格式、张量形状、缓存身份、版本兼容和错误传播共同构成实现边界；「设置树宽和验证预算」需要在合同冻结后测试正常、无效、极端和资源受限输入。证据需要成对的原因和结果字段：原因包括决策特征、阈值和候选，结果包括端到端加速比、错误、取消和资源快照。发布时配置独立开关、灰度身份、停止条件和暖回滚目标；「平均准确率掩盖后部位置崩塌」触发后只撤回相关变化，并继续检查在途请求、缓存和资源释放。

### 10.4 机制 4：位置级准确率决定深层候选的存活概率

把前后两条请求时间线对齐，逐段标出可并行、必须串行和允许合批的工作。Training-Time Test 说明机制何时生效，Drafter 延迟负责确认关键路径是否真的缩短。

分别施加轻载、稳定高载和过载流量，可以分辨同步开销、队列增长、合批变化与资源竞争。检测到代码域收益无法迁移到开放聊天后，沿共享执行资源检查局部收益为何没有进入系统 Goodput。

确定接口时同时规定数据与 Shape、缓存和版本身份、错误及回退，随后以无效输入、极端长度和资源不足验证「制定模型与 Drafter 兼容矩阵」。观测时原因侧保存策略输入、阈值和候选集合，结果侧保存显存增量、错误、取消与资源；两侧对齐后可以区分收益不足、选择错误、实现开销偏大和工作负载漂移。该机制通过独立开关进入灰度，出现训练期教师特征与服务期递归特征不一致时撤回本项候选。

### 10.5 机制 5：Drafter 容量与延迟共同决定端到端收益

先记录原路径，再记录候选路径中的串行、并行与合批段，同时保存位置级准确率状态和 Target 验证延迟。容量评估放在三个负载区间中运行；「只复述论文速度比而没有本机基线」意味着候选工作可能消耗了服务正常请求所需的容量。

实现时明确数据格式、张量形状、缓存身份、版本兼容和错误回退；执行「选择注入的 Target 层」前冻结接口合同，并加入无效输入、极端长度与资源不足测试。Trace 同时记录决策输入与执行结果，后者含域外退化、错误、取消和资源变化。上线合同写明灰度范围、停止条件、开关和暖回滚目标；特征层选择增加带宽而收益有限发生后，系统恢复相关稳定配置。

### 10.6 机制 6：服务域漂移会改变接受长度分布

从请求关键路径入手，标注变化前后每个阶段的顺序、并行性和合批条件，特征归一化与投影作为启用条件，端到端加速比作为结果。

容量测试覆盖低载、稳定高载和过载。若出现平均准确率掩盖后部位置崩塌，说明局部延迟没有变成有效容量，需要核对候选工作占用的公共资源。接口合同包括格式、Shape、缓存键、版本与回退语义；「确定 Drafter 宽度与深度」进入评审前，使用非法输入、边界长度和资源不足场景检验保护路径。

采集证据时把策略输入、阈值、候选集合与位置级 Token 准确率、错误、取消及资源事件放进同一请求链。发布单元包含灰度身份、门禁、停止动作和已预热回滚路径；检测到 Drafter 版本与 Target 修订不匹配后执行局部撤回，并确认在途工作、缓存与资源回到稳定状态。

## 11. 工程决策与取舍

### 11.1 选择注入的 Target 层

候选做法是只取深层、取浅中深三层、或取更多层。判据不是 validation loss，而是「接受长度增量 / 特征体积与带宽增量」。第 4.3 节给出了体积随层数线性增长的关系，第 7 节给出了接受长度的连乘结构；两者一起才能判断多加一层是否值得。层索引必须写入制品元数据，Target 修订变化后需要重新验证层语义是否仍然对齐。

### 11.2 确定 Drafter 宽度与深度

宽度影响单步草拟成本与候选质量，深度影响串行草拟步数。沿用 $T_{effective}$ 模型：宽度增大通常提高 $p_i$ 但抬高 $T_{draft}$，深度增大提高 $K$ 但接受长度趋于饱和。决策应在低载与高载分别扫描，取两个区间都能接受的范围，而不是只取低载最优点。

### 11.3 设置树宽与验证预算

树候选用更多节点换取更高的前缀存活概率，代价是验证位置数与 attention mask 复杂度上升。树节点利用率（被接受节点 / 总验证节点）是核心指标：利用率低说明大量验证算力被浪费。预算应以单轮可验证位置数为硬上限，并按并发动态收缩，避免挤占正常请求容量。

### 11.4 制定模型与 Drafter 兼容矩阵

Drafter 与 Target 是一对绑定制品。兼容矩阵至少记录 Target 修订、Tokenizer、Chat Template、注入层索引、归一化方式、精度与 Drafter 修订。任何一项变化都视为新组合，需要重新评测而不是沿用旧结论。矩阵缺失时，最常见的事故是 Drafter 版本与 Target 修订不匹配却仍被路由命中。

### 11.5 按域训练或共享 Drafter

按域训练能提高该域接受率，但增加制品数量与路由复杂度；共享 Drafter 降低维护成本，却在域外退化。决策依据是流量构成：若某域占比高且接受率差异显著，按域训练值得；若流量高度混合，共享 Drafter 加按域动态禁用阈值更稳妥。两种方案都必须在目标域与域外同时评测。

### 11.6 构造 Training-Time Test 样本

样本构造要覆盖真实 rollout 分布：包含自递归前缀、不同温度、不同任务域与不同上下文长度。只用教师前缀构造的样本会高估深层位置准确率。样本集合同样需要版本化，并记录生成时使用的 Target 修订与 Drafter 修订，便于复现训练期读数与服务期读数的差异。

## 12. 实验设计与双路径验证

### 12.1 机制模拟

CPU 模拟输入逐位置准确率序列、草拟成本、验证成本与树结构，输出 $P(A\ge j)$、$E[A]$、$T_{effective}$、树节点利用率与浪费比例。运行方式沿用统一约定：默认 Fixture，`--check-only` 只做预检，`--real` 进入实测路径。

模拟至少覆盖：教师前缀与自递归前缀两种准确率曲线、不同注入层数对应的成本、不同树宽与验证预算。验收要求方向可解释——前部位置提升带来更大接受长度增量、层数增加时收益增速低于成本增速、树宽超过某点后利用率下降。

### 12.2 真实 CUDA 路径

真实路径测量草拟与验证耗时、显存增量、特征读取带宽与端到端 TPOT。预检记录 GPU、驱动、CUDA、PyTorch、框架版本、Target 与 Drafter 修订、精度、批量、序列长度和完整命令；显存不足时按约定缩放并给出可识别退出码。

测量至少记录第 6.2 节七项指标，外加峰值显存、特征 I/O 时间、错误与取消。每个配置先预热再测量，保留原始请求级记录。只有 `source=measured` 可以支撑性能或发布结论。

### 12.3 域外与漂移验证

除目标域外，必须在域外负载上重复同一测量，报告域外退化幅度。服务域漂移的检验方式是固定 Drafter 与 Target 修订，替换输入分布，观察逐位置准确率与接受长度分布的变化；若变化显著，需要重新训练或调整启用阈值，而不是沿用旧结论。

## 13. 常见错误与排查

| 现象 | 可能原因 | 排查方向 |
| --- | --- | --- |
| validation loss 下降但接受长度不涨 | 特征距离改善未转化为 Token 排名改善 | 改看位置级准确率与 prefix survival |
| 平均准确率不错但深层候选几乎不被接受 | 后部位置崩塌被平均掩盖 | 报告逐位置准确率与 $P(A\ge j)$ |
| 训练期准确率高、服务期明显偏低 | 教师特征与自递归特征不一致 | 对比两种前缀下的逐位置曲线 |
| 特征读取成为训练瓶颈 | Offline 特征体积随层数线性增长 | 估算体积与带宽，减少层数或改 Online |
| 显存增量超预期 | 多层特征、树候选与 mask 同时增大 | 分阶段记录峰值显存，限制验证预算 |
| 换 Target 修订后收益消失 | 兼容矩阵缺失或层语义错位 | 校验制品绑定，重新评测 |
| 代码域很快、开放聊天变慢 | 域外退化 | 按域分桶评测，按域启用或禁用 |
| 只引用论文加速比 | 缺少本机基线 | 建立同环境同负载基线后再比较 |
| 树节点利用率低 | 树宽过大、候选质量不足 | 收缩树宽，优先提升前部位置准确率 |
| 端到端加速比无法复核 | 口径缺失 | 补齐单位、统计窗口与分母 |

## 14. 常见追问与解答

**问：EAGLE-3 为什么放弃预测未来特征？**
答：特征空间距离变小不保证 Token 排名更接近 Target，而投机解码的收益只由被接受的 Token 数决定。直接以未来 Token 交叉熵为目标，使训练目标与验收指标一致。

**问：多层特征融合一定更好吗？**
答：不一定。它提高候选质量的同时按层数放大特征体积与带宽。判据是接受长度增量与成本增量之比，需要在本机负载下测量。

**问：Training-Time Test 解决的是什么问题？**
答：exposure mismatch。训练若只在正确前缀上进行，服务期自递归前缀下的深层位置准确率会显著下降。训练期主动运行 Drafter 可缩小这一偏差。

**问：为什么平均准确率不能用来估计接受长度？**
答：接受长度是前缀连乘的结果，后部位置只在前部全部存活时才有贡献。用平均准确率乘以位置数会系统性高估，第 7.2 节算例中高估约 33%。

**问：Offline 与 Online 特征怎么选？**
答：比较特征体积与存储带宽、Target forward 的额外 GPU 时间、以及层选择与修订的变动频率。变动频繁时 Offline 的重建成本可能更高。

**问：Drafter 应该多大？**
答：没有固定答案。宽度与深度共同决定 $T_{draft}$ 与 $E[A]$，应在低载与高载分别扫描，取两个区间都可接受的范围。

**问：怎样判断域外退化是否可接受？**
答：在域外负载上用同一口径测量接受长度与端到端 TPOT，并与关闭投机的基线比较。若为负收益，应按域禁用而不是全局启用。

**问：上线前必须准备什么？**
答：兼容矩阵、独立开关、灰度身份、停止阈值、已预热回滚修订，以及覆盖目标域与域外的证据。撤回后还要确认在途请求、缓存与资源释放。

## 16. 验收 Checklist

- [ ] Target 修订、Drafter 修订、Tokenizer、Chat Template、注入层索引、归一化方式与精度全部记录。
- [ ] 逐位置准确率与 $P(A\ge j)$ 分别报告，不使用平均准确率替代。
- [ ] 教师前缀与自递归前缀两种条件下的准确率曲线均已测量。
- [ ] 七项训练期指标齐全，且标明单位、窗口与分母。
- [ ] 特征体积与 I/O 时间被记录，层选择有成本收益依据。
- [ ] 树节点利用率与验证预算上限被记录。
- [ ] 低载、接近饱和、过载三段使用同一口径证据。
- [ ] 目标域与域外负载分别评测，域外退化幅度明确。
- [ ] 本机基线存在，不依赖外部论文加速比。
- [ ] 输出合同校验通过：Token 序列、采样分布、结构合法性、结束原因、错误传播。
- [ ] 峰值显存与显存增量发生阶段被记录。
- [ ] 失败与前提失败状态可解释，退出码可识别。
- [ ] 独立开关、灰度身份、停止阈值与已预热回滚修订就位。
- [ ] 撤回后核对在途请求、缓存状态与资源释放。
- [ ] 结论限定在实际证据覆盖的环境、修订与负载区间。

## 写在最后

EAGLE-3 的关键转变是把训练目标从「预测未来特征」改为「预测可验证 Token」，并用多层特征与 Training-Time Test 支撑深层候选的存活概率。判断收益时，逐位置准确率与 prefix survival 比平均准确率更接近真实加速，而特征体积与草拟成本决定了这份收益能否落地。
