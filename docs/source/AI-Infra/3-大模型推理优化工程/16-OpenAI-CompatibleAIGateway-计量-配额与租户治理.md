# OpenAI-Compatible AI Gateway：计量、配额与租户治理

理解 OpenAI-Compatible AI Gateway，需要先回答「怎样建立模型无关入口，同时精确执行 Token 配额、权限和回退？」。本文沿着概念边界、性能关系、实现证据和发布条件四条线展开，其中 OpenAI-Compatible API 与 AI Gateway 是最先核对的状态。工作负载、模型修订、运行时、资源余量和服务承诺共同决定兼容 API 把多后端暴露为统一请求合同是否值得采用，后续每个结论都会注明这些条件。

实验采用两条证据路径：CPU 机制模拟隔离 OpenAI-Compatible API 与 AI Gateway 的因果关系；真实 CUDA 路径记录实现、框架和硬件开销。报告分别标记两类结果，入口成功率的模拟值不充当 GPU 基准，单台设备的绝对速度也不外推。最终结论必须能够复现、诊断并回滚。

## 1. 内容概览

- OpenAI-Compatible API、AI Gateway 与模型能力路由之间的状态与资源关系。
- 用 $available\_quota=limit-reserved-settled+released$ 与 $\text{route only if } capability\supseteq request$ 建立可计算的收益边界并解释全部变量。
- 围绕入口成功率、路由命中率、计量对账差异和租户有效成本设计可复现实验。
- 识别宣称兼容但忽略流式结束语义、预估 Token 与最终计量严重偏差和回退模型能力不等价等典型失败模式。
- 对中心问题给出包含适用条件、证据、风险和回滚的工程答案。

## 2. 核心直觉：Gateway 是请求治理边界，不是 GPU Scheduler

Gateway 最重要的工作是统一协议、身份、配额、usage 与模型入口；它可以触发路由决策，但不应把 GPU 热路径的每轮调度逻辑搬到 API 层。

这条边界不是风格偏好，而是可量化的容量约束。第 15 节会证明：Gateway 若参与每 Token 决策，其容量需求与 **GPU 数量 × 输出长度**成正比；若只做入口决策，则只与**请求数**成正比。两者在 $O=300$ 时相差 300 倍。一个本应无状态轻量的层，会因此变成必须按 GPU 规模线性扩容的新集中瓶颈。

上一篇 Compound AI Serving 建立的任务级成本口径与跨层身份传播，在本文变成 Gateway 的两项核心职责：**计量必须落在每次调用上再按 task 聚合，身份必须从入口贯穿到 Replica**。没有这两条，配额、计费与排障都无从谈起。

## 3. 前置知识与实验环境

需要理解自回归生成、Tokenizer、Prefill、Decode、KV Cache、批处理和分位延迟的基本含义，并已掌握前几篇的成本口径（$c_{tok}=0.625$ GPU-ms、$F_{other}=450$ GPU-ms、Prefill 0.05 GPU-ms/token、TPOT 20 ms、GPU 单价 \$2.40/h）。涉及 OpenAI-Compatible API 时所有缩写都会在正文首次出现处定义；没有某个特定框架经验不妨碍理解机制。实验需要 Python 3.11 或兼容版本。机制模拟只依赖 CPU；真实路径需要任意可用的 CUDA GPU、与驱动兼容的 PyTorch，以及自行准备的本地小模型或兼容制品。

验证前必须记录 GPU 名称、数量、可用显存、驱动、CUDA、PyTorch、推理框架、模型摘要、精度、批量、序列长度和完整命令。脚本根据可用显存缩放模型、批量、上下文和样本数，并把 OpenAI-Compatible API 状态写入报告；可选 CUDA 入口不下载未经确认的大模型。

决定是否采用前，先冻结模型版本、长度分布、流量到达、并发、采样、缓存状态、入口成功率、服务等级和硬件配置。评审「定义兼容字段边界」和「选择路由与回退规则」时，由这些记录解释收益分子、成本分母及共享资源竞争。

## 4. 三层路由的职责分离

### 4.1 Gateway / API Routing

决定：

```text
/v1/chat/completions
model = "reasoning-pro"
```

对应哪个逻辑服务。

### 4.2 Model Routing

逻辑模型 alias：

```text
reasoning-pro
  ├─ model-v3 90%
  └─ model-v4 10%
```

负责版本、Canary、fallback。

### 4.3 Replica Routing

一个模型有多个 Replica：

```text
model-v3
  ├─ replica A
  ├─ replica B
  └─ replica C
```

决定请求去哪台实例。

这三层职责不同。把所有逻辑塞进一个 Router，后续很难演化。

### 4.4 三层的变更频率与回滚代价

分层的实际收益体现在变更频率与回滚代价上（推导设定）：

| 层 | 决策依据 | 变更频率 | 回滚动作 | 回滚耗时 |
| --- | --- | --- | --- | --- |
| API Routing | 路径 + alias | 月级 | 改路由表 | ≈5 s |
| Model Routing | 版本权重 + 能力 | 周级 / Canary | 改 alias 指向 | ≈5 s + 排空 |
| Replica Routing | 负载 + 队列 + KV  locality | 秒级 | 剔除实例 | ≈1 s |

三层的回滚耗时相差一个数量级，且**只有 Replica 层需要秒级反应**。若混在一个 Router 里，为了 Replica 层的秒级需求就必须让整层保持热更新能力，而 Model 层的版本权重变更会被迫走同一条高频路径，Canary 与回滚的审计链随之混乱。

Replica 层的负载与 KV locality 决策会在后续 Distributed Replica Routing 与 Prefix、Session 与 KV-Locality Routing 两篇展开，本文只负责把请求正确交到该层入口。

## 5. 兼容字段边界与统一 Request Identity

### 5.1 八字段契约

兼容协议不是为了「模仿某个产品」，而是建立稳定的调用契约：

- model；
- messages/input；
- sampling；
- tools；
- structured output；
- stream；
- usage；
- error。

底层可以替换：

```text
vLLM
SGLang
TensorRT-LLM
Ray Serve
KServe
自研 Runtime
```

客户端不需要同时学习多套协议。

### 5.2 兼容的深度：字段存在 ≠ 语义等价

「宣称兼容但忽略流式结束语义」是最常见的浅兼容。八个字段中，前六个是**请求侧**（相对容易对齐），后两个是**响应侧**（语义复杂）：

| 字段 | 浅兼容表现 | 深兼容要求 |
| --- | --- | --- |
| stream | 能返回 SSE 流 | 结束事件、`finish_reason`、中途断开的 usage 结算 |
| usage | 完成时返回 token 数 | 流式增量 usage、取消/失败也结算、幂等写入 |
| error | 返回 HTTP 500 | 区分能力不支持、配额不足、后端故障、超时，且错误码可重试性明确 |
| tools | 接受 tools 字段 | 工具调用的结构化输出与并行调用语义一致 |
| structured output | 接受 schema | 语法保证与语义校验边界一致（见前面 Structured Output 一篇） |

**兼容性的验收必须落在响应侧语义，而不是请求侧字段列表。** 一个能接受全部请求字段但在流式取消时不结算 usage 的 Gateway，会让计量对账差异达到平台级配额的数倍（第 9 节量化）。

### 5.3 统一 Request Identity

每个请求进入时生成：

```text
request_id
trace_id
tenant_id
user_id(optional)
model_alias
model_revision
adapter_id(optional)
slo_tier
budget
```

后面所有日志/metric/usage 都使用同一 ID。否则当用户投诉一次请求「慢/错/贵」时，很难跨 Gateway、Router、Replica 找到完整证据。

其中 `user_id` 标注为 optional，但第 13 节会证明它在成本归属上实际是必需的：共享密钥下均摊成本会让重度用户补贴 30% 给轻度用户，且无法定位滥用。`budget` 与 `slo_tier` 则是上一篇 deadline/budget propagation 的入口锚点——**没有入口锚点，下游各层的预算传播就无从起算**。

## 6. 五维限流：为什么 requests/min 与 tokens/min 都不够

### 6.1 两个极端请求

请求 A：100 input + 100 output。

请求 B：20K input + 20K reasoning/output。

都是一个 request，GPU 成本差异巨大。按本文口径（推导值，非实测）：

$$C_A=450+100\times0.05+100\times0.625=517.5\ \text{GPU-ms}$$
$$C_B=450+20000\times0.05+20000\times0.625=13950\ \text{GPU-ms}$$

比值 **26.96 倍**（未计长上下文的 KV 带宽反噬，计入后更高）。

### 6.2 三种限流口径的偏差

设限额分别为 60 req/min、100 万 token/min、60000 GPU-ms/min（= 1 GPU）：

| 限流口径 | 全 A 时可过请求 | 全 A 时 GPU 占用 | 全 B 时可过请求 | 全 B 时 GPU 占用 | 偏差 |
| --- | --- | --- | --- | --- | --- |
| requests/min = 60 | 60 | 0.52 GPU | 60 | **13.95 GPU** | **26.96×** |
| tokens/min = 100 万 | 5000 | **43.1 GPU** | 25 | 5.81 GPU | 7.42×（反向） |
| **cost credits = 60000 GPU-ms/min** | 115.9 | **1.00 GPU** | 4.3 | **1.00 GPU** | **1.00×** |

两个反直觉结论：

1. **按 requests/min 限流会让 GPU 需求差 27 倍**。按全 A 配 1 张卡，全 B 时需要 14 张。
2. **按 tokens/min 限流反而偏向长请求**。因为固定开销 $F_{other}=450$ GPU-ms 被摊薄：A 的每 Token 成本 $517.5/200=2.5875$ GPU-ms，B 只有 $13950/40000=0.34875$ GPU-ms，A 贵 7.42 倍。短请求多的租户会被同一 token 限额压得更死。

因此 Gateway 至少支持五维：requests/min、input tokens/min、output tokens/min、concurrent requests、cost credits。**五维不是冗余，而是各自封堵一类偏差**：前四维防突发与长尾，cost credits 防形态差异。只有 cost credits 能让不同请求形态占用相同资源。

### 6.3 input 与 output 必须分开限

input token 在入口已知，output token 未知。若合并成一个 token 限额，则：

- 长输入短输出（RAG，20000 input + 100 output）与短输入长输出（Reasoning，100 input + 20000 output）被同等对待；
- 但前者成本 $450+1000+62.5=1512.5$ GPU-ms，后者 $450+5+12500=12955$ GPU-ms，**差 8.57 倍**。

分开限流后，可对 output 用预估值（第 7 节），对 input 用精确值，两者的不确定性完全不同，混在一起会让配额策略无法调优。

## 7. Token 计量生命周期：预估、保留、结算、释放

### 7.1 基本式

用户提交时通常只知道输入 token，输出 token 还未知。最终 usage：

$$Tokens_{total}=Tokens_{input}+Tokens_{output}$$

如果有 Reasoning/Tool/Embedding 等，还可以扩为：

$$Usage=\sum_j w_j\cdot Tokens_j$$

其中 $w_j$ 反映不同模型/阶段成本。配额可用量：

$$available\_quota=limit-reserved-settled+released$$

四个量对应四个生命周期事件：`limit` 是租户额度，`reserved` 在接受请求时按预估写入，`settled` 在请求结束时按实际写入，`released` 释放预留与实际的差额。

### 7.2 三种预估策略

设请求 input 1000、`max_tokens` 4096，历史实际 output P50 = 300、P95 = 1200、均值 400（推导设定），租户 $limit=10^7$ 加权 Token/天：

| 预估策略 | reserved | 实际 settled | 偏差 | 可接受并发请求数 | 配额利用率 |
| --- | --- | --- | --- | --- | --- |
| 按 max_tokens | 5096 | 1400 | 高估 3.64× | 1962 | **27.5%** |
| 按 P95 | 2200 | 1400 | 高估 1.57× | 4545 | 63.6% |
| 按 P50 | 1300 | 1400 | **低估 7.1%** | 7692 | 107.7%（超卖） |
| 理论上限（按均值） | 1400 | 1400 | 0 | 7142 | 100% |

**按 `max_tokens` 预留会把配额利用率压到 27.5%**——这是「预估 Token 与最终计量严重偏差」最常见的形态，且它不是错误而是过度保守。按 P50 预留则超卖 7.7%，在租户集中跑长请求时会突破额度。

正确做法是**按 P95 预留 + 及时释放差额**：利用率 63.6% 起步，随着 `released` 及时写回而趋近 100%。这就把问题从「预估准不准」转成了「释放及不及时」。

### 7.3 released 的语义

$$released=\max(0,\ reserved-settled)$$

必须注意三点：

1. **取消与失败也要释放**：请求未完成时 `settled` 为已生成部分，差额仍需释放，否则预留永久泄漏；
2. **释放必须幂等**：同一 `request_id` 的释放只能生效一次，否则重复释放会让配额虚增；
3. **超卖时的处理**：若 `settled > reserved`（P50 策略下会发生），不能释放负数，而应追加扣减并记录超卖事件，用于回调预估分位。

第 3 点是配额系统的闭环：超卖事件率应当作为预估策略的反馈信号。设超卖率持续 >5%，则把预估分位从 P50 上调到 P75；设利用率持续 <50%，则下调分位。**静态分位必然在某一侧失效**。

## 8. 结算延迟与配额虚占

### 8.1 虚占的稳态量

设请求速率 $\lambda=100$ req/s、结算延迟（请求结束到 `released` 写回）为 $t_{settle}$、单请求预留与实际差额 $\Delta=reserved-settled$。稳态下被虚占的配额：

$$Quota_{phantom}=\lambda\cdot t_{settle}\cdot\Delta$$

按 max_tokens 策略 $\Delta=5096-1400=3696$：

| $t_{settle}$ | 虚占量 | 占 $limit=10^7$ | 后果 |
| --- | --- | --- | --- |
| 0.1 s | 36960 | 0.37% | 可忽略 |
| 2 s | 739200 | 7.39% | 轻度压缩 |
| 10 s | 3696000 | 36.96% | 明显压缩 |
| **27.06 s** | $10^7$ | **100%** | **新请求全部被拒** |
| 60 s（批量对账） | $2.22\times10^7$ | 222% | 配额完全失效 |

### 8.2 结算延迟的硬上限

由 $Quota_{phantom}<limit$ 得：

$$\boxed{t_{settle}<\frac{limit}{\lambda\cdot\Delta}}$$

| 预估策略 | $\Delta$ | $t_{settle}$ 上限 |
| --- | --- | --- |
| max_tokens | 3696 | **27.06 s** |
| P95 | 800 | 125 s |
| P50 | −100 | 无虚占（但有超卖风险） |

**按 `max_tokens` 预留时，结算延迟必须小于 27 秒**；若采用每小时批量对账（3600 s），配额会在 27 s 后完全失效，表现为「租户明明没用完额度却全部被拒」。

这条约束把两个看似无关的设计绑在一起：**预估越保守，对结算实时性的要求越高**。因此「按 max_tokens 预留 + 异步批量对账」是一个自相矛盾的组合，而它恰恰是最容易实现的组合。

### 8.3 计量对账差异

「计量对账差异」必须附带口径：分子为 $|Usage_{gateway}-Usage_{backend}|$，分母为 $Usage_{backend}$，窗口为日结，并按差异来源分列：

| 来源 | 方向 | 量级（第 9 节推导） |
| --- | --- | --- |
| 流式断开未结算 | Gateway 少计 | 8.64e7 Token/天 |
| usage 写入重试无幂等 | Gateway 多计 | 6.05e7 Token/天 |
| 预估残留未释放 | 配额虚占（非 usage 差异） | 视 $t_{settle}$ |
| Reasoning Token 未计入 | Gateway 少计 | 视模型 |

**四类来源方向不同，混在一个总差异率里会互相抵消**，看起来对账平了实际上两侧都在错。因此必须分列并各自设阈值。

## 9. 流式 Usage 与幂等结算

### 9.1 状态机

流式响应在结束前不知道最终 output tokens。需要状态：

```text
REQUEST_ACCEPTED
→ STREAMING
→ COMPLETED / CANCELLED / FAILED
→ FINAL_USAGE
```

用户中途断开时，也要结算已实际生成的 token，不能只有「完整完成」才记录。Usage 记录需要幂等：同一个 `request_id` 重试写入时不能重复扣费。

### 9.2 断开未结算的漏计量

设流式请求平均 output 400 Token、用户在 50% 处断开、断开率 5%、$\lambda=100$ req/s（推导设定）：

$$\text{漏计}=100\times0.05\times200=1000\ \text{Token/s}=8.64\times10^7\ \text{Token/天}$$

折算 GPU 成本 $1000\times0.625=625$ GPU-ms/s，即 **0.625 张 GPU 持续白跑**，按 \$2.40/h 计为 \$15/天、\$450/月。相对单租户日配额 $10^7$，漏计量是它的 **8.64 倍**（平台级）。

关键点在于：这 0.625 GPU 的成本**已经真实发生**（Token 已生成、KV 已占用、带宽已消耗），只是没被记账。因此它不是「少收了钱」，而是「成本归属完全丢失」——无法知道该由哪个租户承担。

### 9.3 无幂等写入的多计量

设 usage 写入成功但 ack 丢失的概率 0.5%，客户端重试 → 重复扣费：

$$\text{多计}=100\times0.005\times1400=700\ \text{Token/s}=6.05\times10^7\ \text{Token/天}$$

**漏计 8.64e7 与多计 6.05e7 方向相反、量级相同**，都源于结算路径不可靠。若两者同时存在，总差异率看起来只有 2.59e7（净额），掩盖了两侧各 6～8 千万的错误。

幂等键应为 `request_id + usage_version`，配合唯一约束与 upsert：**同一 `request_id` 的 `FINAL_USAGE` 只生效一次**。注意不能用 `attempt_id` 做键，否则重试会被当成新 usage。

### 9.4 流式增量 usage 的必要性

若只在结束时上报 usage，则 `STREAMING` 阶段配额完全不收紧。设一个流式请求 `max_tokens`=32768、实际跑到 30000 Token 才断开：

- 预留按 P95（2200）→ 实际 30000，超卖 27800 Token；
- 若同时有 100 个这样的请求 → 超卖 278 万 Token，占 $limit$ 的 27.8%。

因此流式必须**增量上报 usage 并增量扣减配额**，设每 500 Token 上报一次，则最大超卖被限制在 500 Token/请求，100 个请求共 5 万 Token（0.5%）。**增量粒度直接决定超卖上限**，这是一个可以精确配置的旋钮，而不是「尽量实时」这类模糊要求。

## 10. 能力路由：capability ⊇ request

### 10.1 路由判据

$$\text{route only if } capability\supseteq request$$

请求需要的能力集合必须被模型能力集合完全包含。设四个模型的能力矩阵（推导设定）：

| 模型 | chat | tools | struct | vision | reasoning | stream | 上下文 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| chat-fast | ✓ | ✓ | ✓ | ✗ | ✗ | ✓ | 32k |
| reasoning-pro | ✓ | ✓ | ✓ | ✗ | ✓ | ✓ | 128k |
| vision | ✓ | ✓ | ✗ | ✓ | ✗ | ✓ | 32k |
| embed | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | 8k |

### 10.2 无模型可路由的请求

设请求类型分布：

| 请求类型 | 需要能力 | 占比 | 可路由模型 |
| --- | --- | --- | --- |
| 纯 chat | chat, stream | 40% | 三个 |
| 工具调用 | chat, tools, struct, stream | 25% | chat-fast / reasoning-pro |
| 长思考 | chat, reasoning, stream | 15% | reasoning-pro |
| 图文 | chat, vision, stream | 15% | vision |
| **图文 + 工具** | chat, vision, tools, stream | **5%** | **无** |

**5% 的请求在当前模型集合下无解。** 若 Gateway 不做能力校验，会把它们路由到 vision 模型，然后工具调用失败 → 重试 → 成本放大。

代价对比（推导值）：

| 处置 | 单请求 GPU-ms | 5% 请求的平均浪费 |
| --- | --- | --- |
| 入口拒绝（capability_not_supported） | ≈0 | **0** |
| 路由到 vision 后失败 + 重试 2 次 | $3\times112.5=337.5$ | 16.9 GPU-ms/请求 |

其中 112.5 = Prefill 50 + 已生成 100 Token 的 62.5（沿用上一篇的故障浪费口径）。

**能力校验前置是零成本优化**：它把 16.9 GPU-ms/请求的浪费直接归零，且给用户明确错误而不是神秘失败。这也是「回退模型能力不等价」的预防手段——回退前必须先校验能力包含关系。

### 10.3 路由命中率的口径

「路由命中率」分子为路由到满足全部能力模型的请求数，分母为全部入口请求数。上例为 95%。

剩下 5% 必须计入**入口拒绝**而非路由失败，两者分列。若混在一起，路由命中率 95% 看起来是「路由算法不够好」，实际是「模型集合缺能力」——处置方式完全不同：前者调路由策略，后者补模型或明确产品边界。

## 11. 回退链与首字节边界

### 11.1 流式开始后回退语义受限

关键约束：**流式响应一旦发出首字节，就不能透明回退到另一个模型**，因为客户端已收到部分 Token，换模型会产生不连续内容。

设首字节时间 $TTFB=100$ ms（Prefill），故障检测时间 $t_{detect}$：

| 条件 | 可否透明回退 | 处置 |
| --- | --- | --- |
| $t_{detect}<TTFB$ | 可以 | 换后端重跑，客户端无感 |
| $t_{detect}>TTFB$ | **不可以** | 中断 + 错误，或续写（内容不一致） |

设后端故障中 90% 在 Prefill 阶段暴露（$t_{detect}=50$ ms），10% 在 Decode 中途暴露（$t_{detect}=2$ s）（推导设定）。则**回退成功率的理论上限是 90%**，把它当 100% 来设计 SLO 必然失配。

### 11.2 不可回退部分的代价

10% 的故障请求已生成 $2000/20=100$ Token，浪费 $100\times0.625+50=112.5$ GPU-ms，且任务失败。若客户端整体重试（上一篇口径），浪费再乘放大系数。

因此回退链的全部决策必须**在首字节前完成**，这要求四项前置：

1. 健康检查前置：路由时剔除不健康 Replica；
2. 能力校验前置：$capability\supseteq request$（第 10 节）；
3. 配额校验前置：$available\_quota>0$（第 7 节）；
4. 预算可行性前置：$T_{estimate}\le D_{remain}$（上一篇口径）。

**四项前置把「可回退故障」的比例从 90% 推向接近 100%**，因为它们把大部分故障拦在首字节之前。这是回退链设计的核心，而不是「准备多少个备选模型」。

### 11.3 回退链的能力等价

「回退模型能力不等价」是回退链的独有失败模式。设主模型 reasoning-pro（含 reasoning），回退到 chat-fast（不含）：

- 能力校验会直接拒绝（$capability\not\supseteq request$），回退链失效；
- 若强行回退并忽略 reasoning 需求，则质量从 Reasoning 一篇的 $Q(B{=}16000)=0.80$ 掉到 chat-fast 的水平，任务成功率不可比。

因此回退链必须**按能力等价类构建**，而不是按「模型列表顺序」。等价类内的回退是透明的，跨等价类的回退必须显式降级并告知客户端（返回 `degraded` 标记与降级原因），否则客户端会把质量下降当成模型故障。

「回退成功率」必须附带口径：分子为回退后成功完成且能力等价的请求数，分母为触发回退的请求数，并注明是否含首字节后故障。三个口径混用会让同一系统看起来有 90%、100% 或 0% 三种回退成功率。

## 12. Model Alias、Canary 与回滚

### 12.1 Alias 的价值

客户端不应该硬编码底层 revision：

```text
model=qwen3-...-build-20260812-abc
```

更适合：

```text
model=chat-fast
model=reasoning-pro
model=vision
```

Control Plane 决定 alias 指向：

```text
chat-fast → qwen3-x-v17
```

这样可以做版本升级、Canary、回滚、区域路由、成本优化。

### 12.2 Canary 的错误率放大

设 alias `reasoning-pro` 指向 model-v3 90% / model-v4 10%，v3 错误率 1%：

| v4 错误率 | 全局错误率 | 相对基线 |
| --- | --- | --- |
| 1% | 1.0% | 0% |
| 5% | 1.4% | +40% |
| 10% | 1.9% | +90% |
| 20% | **2.9%** | **+190%** |

**10% 的 Canary 流量能把全局错误率放大近 3 倍**。因此 Canary 比例不是「越小越安全」——它同时决定了检出时间。

### 12.3 Canary 样本量与检出时间

用二元比例检验（$\alpha=0.05$、$\beta=0.2$，$z_{\alpha/2}=1.96$、$z_\beta=0.8416$）：

$$n=\frac{\left(z_{\alpha/2}\sqrt{2\bar p(1-\bar p)}+z_\beta\sqrt{p_3(1-p_3)+p_4(1-p_4)}\right)^2}{(p_4-p_3)^2}$$

代入 $p_3=0.01$、$p_4=0.05$、$\bar p=0.03$：分子 $(0.47285+0.20163)^2=0.45492$，分母 $0.0016$，得 $n=284.3\Rightarrow$ **285 请求/组**（推导值，非实测）。

设 $\lambda=100$ req/s：

| Canary 比例 | v4 流量 | 检出时间 |
| --- | --- | --- |
| 10% | 10 req/s | **28.5 s** |
| 5% | 5 req/s | 57 s |
| 1% | 1 req/s | 285 s（4.75 min） |
| 0.1% | 0.1 req/s | 2850 s（47.5 min） |

**Canary 比例从 10% 降到 0.1%，检出时间从 28.5 s 涨到 47.5 min（100 倍）**，而期间累积的错误请求数相同（都是 285 个）。小比例 Canary 并不减少受害用户总数，只是把伤害摊薄到更长时间——对持续性故障这反而更糟。

### 12.4 Alias 回滚 vs 制品回滚

| 回滚方式 | 动作 | 耗时 |
| --- | --- | --- |
| Alias 切换 | 改路由表 | ≈5 s |
| 制品回滚（本地 NVMe） | 重新加载 1.50 GiB + 校验 | 2.00 s |
| 制品回滚（对象存储） | 同上 | 9.55 s |
| 制品回滚（远端 50 MB/s） | 同上 | **33.71 s** |

制品回滚数据沿用 Speculator 工程化一篇。**Alias 回滚不涉及制品加载，因此耗时与存储位置无关**，这是 alias 层的核心价值：把「换版本」从数据面操作变成控制面操作。

但 alias 回滚只影响新请求，已在跑的请求仍用旧 revision。设平均请求 6 s、长思考请求 200 s（Reasoning 一篇口径），则完全生效时间 = 传播 5 s + 最长在跑请求剩余时间，最坏 **205 s**。因此「5 秒回滚」的说法必须附带排空条件，否则长思考负载下回滚实际要 3 分半。

## 13. 租户有效成本与身份归属

### 13.1 加权用量

$$Usage=\sum_j w_j\cdot Tokens_j$$

沿用上一篇权重：大模型 $w=1.0$、小模型 $w=0.20/0.625=0.32$。设租户 A 全用 chat-fast、租户 B 全用 reasoning-pro，两者都消耗 $10^6$ 原始 Token/天：

| 租户 | 原始 Token | 加权 Token | GPU-ms | 日成本 |
| --- | --- | --- | --- | --- |
| A（小模型） | $10^6$ | 320000 | 200000 | \$0.133 |
| B（大模型） | $10^6$ | 1000000 | 625000 | \$0.417 |

**原始 Token 相同，真实成本差 3.125 倍。** 按原始 Token 计费会让 A 补贴 B，且 B 没有动力优化用量。

### 13.2 共享密钥的归属失效

「租户共享密钥无法归属成本」是 OpenAI-Compatible API 对象的独有失败模式。设一个 key 下 10 个用户，用量呈重尾分布，top-1 占 40%（推导设定）：

| 归属方式 | top-1 承担 | 其余 9 人各承担 | 偏差 |
| --- | --- | --- | --- |
| 真实用量 | 40% | 6.67% | — |
| 按 key 均摊 | 10% | 10% | top-1 **少计 30 个百分点** |

**均摊让重度用户把 30% 的成本转嫁给轻度用户**，且无法定位滥用来源。当 top-1 是失控的 Agent 循环（上一篇的 retry storm）时，均摊会让整个租户的配额被一个用户耗尽，而其他 9 个用户看不到任何异常。

因此 `user_id` 虽标注 optional，实际是成本归属的必需字段；API key 应当 per-user，或至少支持 sub-key 归属与用量下钻。

### 13.3 租户有效成本

「租户有效成本」必须附带口径：

$$EffectiveCost_u=\frac{\sum_{r\in u}C_r}{\text{成功任务数}_u}$$

分子是该租户全部请求的 GPU 成本（含失败与重试），分母是**成功任务数**而非请求数。这与前几篇的每成功任务成本一致。

设租户 A 请求成功率 95%、租户 B 因 Agent 重试成功率 60%，两者单请求成本相同（517.5 GPU-ms）：

| 租户 | 成功率 | 每请求成本 | 每成功任务成本 |
| --- | --- | --- | --- |
| A | 95% | 517.5 | 544.7 |
| B | 60% | 517.5 | **862.5** |

**B 的有效成本比 A 高 58.3%，而按请求计费的账单完全相同。** 这就是为什么配额与计费必须落在有效成本口径上：否则重试放大严重的租户在账单上看起来「很划算」，实际在消耗最多资源。

## 14. 凭证保护与敏感日志

### 14.1 敏感日志的暴露面

「日志记录请求敏感内容」是模型能力路由对象的独有失败模式。设 Gateway 为调试记录完整 prompt，日均 $10^6$ 请求 × 1000 Token × 4 B = 4 GB/天，保留 30 天 → **120 GB 日志**；含 PII 比例 5% → 6 GB 敏感数据暴露面。

处置与效果（推导值）：

| 策略 | 日志量 | 敏感暴露面 | 相对默认 |
| --- | --- | --- | --- |
| 全量 prompt + 30 天 | 120 GB | 6 GB | 1× |
| 全量 prompt + 1 h TTL | 0.167 GB | 8.3 MB | **1/720** |
| 只记 hash + 长度 + 30 天 | ≈0.1 GB | 0 | 敏感面归零 |
| 按需开启 + 租户隔离 + 1 h + 访问审计 | 视开启量 | 受控 | 可审计 |

**TTL 从 30 天降到 1 小时就把暴露面降低 720 倍**，而排障能力几乎不受影响（绝大多数排障发生在请求后数分钟内）。默认应当只记 hash 与长度，完整内容需显式开启并带审计。

### 14.2 凭证泄露的损失封顶

设 API key 泄露后平均发现时间 24 h、滥用速率 100 req/s、单请求 517.5 GPU-ms：

$$\text{损失}=24\times3600\times100\times517.5\ \text{GPU-ms}=4.47\times10^9\ \text{GPU-ms}=1242\ \text{GPU-hour}$$

按 $2.40/h 计为 **$2981**。若 key 设有 cost credits 上限（如 $100/天），损失封顶 $100，**降低 29.8 倍**。

因此配额不仅是治理手段，也是**泄露损失的封顶机制**。这给「设置租户配额与突发额度」增加了一条安全论据：即使不考虑公平性，每个 key 也必须有绝对成本上限，且突发额度不得突破该上限。

### 14.3 凭证与配额的绑定

凭证必须绑定到 `tenant_id` 与配额账户，而不是只绑定到「是否合法」。设一个合法但无配额绑定的 key，则 $available\_quota$ 无从计算，第 7 节的整套生命周期失效。

同时凭证 TTL 与配额周期应当解耦：凭证可以短期轮换（1 h），配额按日/月累计。若把配额状态存在凭证里，轮换就会重置配额——这是一个容易被忽略的绕过路径。

## 15. Gateway 不应该做什么

不要把每 token 热路径全部放 Gateway：

- token sampling；
- KV block 管理；
- Engine scheduler；
- 每轮 Decode 决策。

Gateway 应保持尽可能轻、无状态或可外部化状态，否则它会成为新的集中瓶颈。

### 15.1 每 Token 参与的容量代价

设 Gateway 单实例处理 10000 RPC/s，一个 Replica 产出 1600 Token/s（$32/0.020$），10 个 Replica：

| 参与粒度 | RPC 需求 | Gateway 实例数 | 相对入口决策 |
| --- | --- | --- | --- |
| 每 Token 一次决策 | $10\times1600=16000$/s | **2**（且需随 GPU 扩容） | 300× |
| 每请求一次决策 | $10\times1600/300=53$/s | 1（余量 189 倍） | 1× |

**每 Token 参与让 Gateway 容量需求与 GPU 数量成正比，入口决策只与请求数成正比**，两者相差 $O=300$ 倍。一个本应无状态轻量的层变成必须按 GPU 规模线性扩容的有状态瓶颈。

### 15.2 延迟代价

设每 Token 一次 Gateway RPC：

| RPC 位置 | 单次延迟 | TPOT 变化 | $O=300$ 的额外延迟 |
| --- | --- | --- | --- |
| 同机 | 0.5 ms | 20 → 20.5 ms（+2.5%） | 150 ms |
| 跨机 | 2 ms | 20 → 22 ms（+10%） | **600 ms** |

跨机时每请求多 600 ms，相对方案 3 的 1580 ms 端到端是 **38% 的纯开销**。而 Gateway 提供的治理价值（身份、配额、路由）在入口一次就能全部完成，没有任何理由按 Token 重复。

### 15.3 状态外部化

Gateway 需要持有的状态只有三类：配额计数（`reserved`/`settled`/`released`）、alias 路由表、健康与熔断状态。三者都应外部化：

| 状态 | 存储 | 一致性要求 |
| --- | --- | --- |
| 配额计数 | 内存 KV（如 Redis）+ 持久化 | 强一致（否则超卖） |
| alias 路由表 | 控制面下发 + 本地缓存 | 最终一致（5 s 传播可接受） |
| 健康/熔断 | 本地 + gossip | 最终一致 |

**配额计数是唯一需要强一致的状态**，因此它也是 Gateway 唯一的性能瓶颈点。第 8 节的 $t_{settle}$ 约束本质上就是这个强一致写入的延迟约束。把配额写入做成异步批量，就会违反 27 s 上限。

## 16. 八个对象的边界与失败模式

跟踪的八个概念为：OpenAI-Compatible API、AI Gateway、模型能力路由、Token Metering、租户配额、身份与策略、回退链、流式响应。它们分属不同系统层级，取消传播时间和租户有效成本会同时受到这些状态影响。

### 16.1 统一检查框架

1. **边界与生命周期**：输入从哪里来、状态由谁持有、输出交给谁、失败如何传播；跨层字段是否携带版本身份。
2. **资源账五项**：计算、显存、内存带宽、主机开销、同步等待分别记账。
3. **三段负载区间**：低载、接近饱和、过载各留同口径证据。
4. **正确性门禁**：Token 序列、采样分布、结构合法性、结束原因、错误传播五项对账。
5. **观测字段**：请求身份、模型与策略修订、阶段时间、资源快照、失败原因；每个指标带单位、窗口与分母。

### 16.2 OpenAI-Compatible API

边界是「客户端请求 → 统一契约对象」，拥有者是 Gateway 入口，生命周期结束于响应返回。它传给 AI Gateway 的数据必须附带模型与策略版本。

独有失败模式是**租户共享密钥无法归属成本**：协议完全兼容，但 top-1 用户把 30% 成本转嫁给其余 9 人（第 13.2 节）。决策短语是「设计 Token 计量生命周期」，指标为回退成功率。

### 16.3 AI Gateway

边界是「契约对象 → 治理决策 + 转发」，拥有者是入口层，状态应外部化。它连接模型能力路由时必须传播身份与版本。

独有失败模式是**取消未传播造成无效工作**：Gateway 收到客户端断开但后端继续生成，浪费已真实发生的 GPU 成本（第 9.2 节 0.625 GPU 持续白跑）。决策短语是「设置租户配额与突发额度」，指标为首字节时间。

### 16.4 模型能力路由

边界是「请求能力集合 → 候选模型集合」，拥有者是 Model Routing 层，产物是 alias 到 revision 的映射。它与 Token Metering 交互的字段必须携带版本身份。

独有失败模式是**日志记录请求敏感内容**：路由决策正确，但调试日志把 6 GB PII 暴露 30 天（第 14.1 节）。决策短语是「传播截止时间和取消」，指标为取消传播时间。

### 16.5 Token Metering

边界是「Token 计数 → 加权 Usage → 结算记录」，拥有者是计量服务，生命周期跨请求且需幂等。它与租户配额之间的版本身份若未绑定，结算就会记到错误账户。

独有失败模式是**宣称兼容但忽略流式结束语义**：请求侧字段全兼容，但流式取消不结算，漏计 8.64e7 Token/天（第 9.2 节）。决策短语是「保护凭证与敏感日志」，指标为租户有效成本。

### 16.6 租户配额

边界是「$limit$ 与 $reserved/settled/released$ 的账本」，拥有者是配额服务，是唯一需要强一致的状态。它传给身份与策略的数据必须附带模型与策略版本。

独有失败模式是**预估 Token 与最终计量严重偏差**：按 `max_tokens` 预留使利用率仅 27.5%，配合批量对账则 27 s 后配额完全失效（第 8 节）。决策短语是「定义兼容字段边界」，指标为入口成功率。

### 16.7 身份与策略

边界是「凭证 → tenant/user/slo_tier/budget 的解析」，拥有者是 Auth 与 Tenant Resolver，生命周期结束于请求身份生成。它是所有下游治理的锚点。

独有失败模式是**策略版本与凭证生命周期耦合**：配额状态存于凭证内，轮换即重置配额，形成绕过路径（第 14.3 节）。另一形态是 `user_id` 缺失导致成本无法下钻。决策短语是「选择路由与回退规则」，指标为路由命中率。

### 16.8 回退链

边界是「主模型故障 → 能力等价备选 → 重跑或降级」，拥有者是 Model Routing 层，决策必须在首字节前完成。它与流式响应之间的版本身份若未绑定，回退后的 usage 就会记到错误 revision。

独有失败模式是**回退模型能力不等价**：reasoning-pro 回退到 chat-fast 时能力校验失败或质量静默崩塌（第 11.3 节）。决策短语是「传播截止时间和取消」，指标为计量对账差异。

### 16.9 流式响应

边界是「SSE 增量 → 结束事件 → FINAL_USAGE」，拥有者是 Streaming Proxy，生命周期可能长于普通请求数倍。它传给 Token Metering 的数据必须附带增量序号与幂等键。

独有失败模式是**首字节后无法透明回退**：10% 的后端故障发生在 Decode 中途，回退成功率理论上限只有 90%（第 11.1 节）。另一形态是增量 usage 缺失导致超卖 27.8%（第 9.4 节）。指标为入口成功率与首字节时间。

## 17. 六个机制的因果分析

### 17.1 Gateway 在入口执行身份、策略和计量

机制链条是「入口一次决策 → 生成 Request Identity → 下游全部沿用」。它把治理成本从 $O(\text{Token})$ 降到 $O(\text{请求})$，第 15.1 节量化为 300 倍差异。

资源账上它只增加主机 CPU 与一次强一致写入（配额），不占 GPU。因此 Gateway 的扩容依据是请求速率与配额写入延迟，而不是 GPU 数量——这是判断 Gateway 是否越界的直接指标。

该机制的边界是「决策必须在首字节前完成」。身份、能力、配额、预算四项前置校验缺一不可，否则故障会落到不可回退区间（第 11.2 节）。

### 17.2 能力路由根据模型模态与工具支持筛选候选

机制链条是「$capability\supseteq request$ → 候选集合 → 权重选择」。它把「模型能不能做」从运行时失败前移到入口拒绝。

第 10.2 节显示 5% 的请求在当前模型集合下无解，入口拒绝可省 16.9 GPU-ms/请求的平均浪费，且给用户明确错误。这是零成本优化，唯一代价是必须维护准确的能力矩阵。

该机制还约束回退链：备选模型必须在同一能力等价类内，否则回退本身会触发能力校验失败或质量静默下降。能力矩阵因此不是文档，而是路由与回退共用的运行时数据。

### 17.3 Token 配额需要区分预估、保留与最终结算

机制链条是「接受时 reserved → 结束时 settled → 差额 released」。三个量对应三个时间点，任一缺失都会让账本失衡。

预估策略决定利用率与超卖的权衡：max_tokens 利用率 27.5%、P95 为 63.6%、P50 超卖 7.7%。而释放及时性决定虚占：$t_{settle}<limit/(\lambda\Delta)$，max_tokens 策略下上限仅 27.06 s。

**两个设计点互相约束**：预估越保守，对结算实时性要求越高。因此「保守预估 + 异步批量对账」是自相矛盾的组合，必须避免。

### 17.4 流式开始后回退语义受到限制

机制链条是「首字节发出 → 客户端已收到内容 → 换模型产生不连续 → 只能中断」。它把回退窗口硬性截断在 TTFB。

第 11.1 节量化：90% 故障在 Prefill 暴露（可回退），10% 在 Decode 中途（不可回退），故回退成功率上限 90%。四项前置校验的作用就是把更多故障拦到首字节之前，从而推高这个上限。

该机制还决定 usage 结算形态：流式必须增量上报，否则 `STREAMING` 阶段配额不收紧，超卖可达 27.8%。增量粒度（如每 500 Token）直接给出超卖上限，是可精确配置的旋钮。

### 17.5 租户治理把共享资源转化为可执行份额

机制链条是「共享 GPU 池 → 五维限额 + cost credits → 每租户可执行份额」。它把「谁该用多少」从协商变成运行时强制。

五维各自封堵一类偏差：requests/min 防突发、input/output tokens/min 防形态差异、concurrent 防长尾占用、cost credits 防成本不等价。第 6.2 节显示单用 requests/min 偏差 27 倍、单用 tokens/min 反向偏差 7.42 倍，只有 cost credits 偏差为 1。

治理还承担安全职能：cost credits 上限把凭证泄露损失从 $2981 封顶到 $100（29.8 倍）。因此配额不是可选的公平性工具，而是必需的损失封顶机制。

### 17.6 兼容 API 把多后端暴露为统一请求合同

机制链条是「八字段契约 → 后端可替换 → 客户端零改动」。它使 vLLM/SGLang/TensorRT-LLM/Ray Serve/KServe/自研 Runtime 可以互换。

但兼容的深度在响应侧而非请求侧：stream 的结束语义、usage 的取消结算与幂等、error 的可重试性分类，才是真正决定能否互换的部分。第 5.2 节列出五类浅兼容表现。

该机制的验收因此必须落在语义等价测试上：同一请求在不同后端下的 Token 序列、采样分布、结构合法性、结束原因与错误传播五项对账，而不是「字段都能接受」的冒烟测试。

## 18. 工程决策与取舍

### 18.1 定义兼容字段边界

八字段契约全部支持，且响应侧语义必须等价：流式结束事件与 `finish_reason`、取消/失败也结算 usage、幂等写入、error 分类与可重试性。验收用五项输出合同对账，不用字段冒烟测试。

### 18.2 设计 Token 计量生命周期

四事件齐备：接受时按 P95 预留、结束时按实际结算、差额及时释放、取消/失败同样释放。释放幂等，超卖追加扣减并作为预估分位的反馈信号。流式增量上报，粒度按可接受超卖上限反解（每 500 Token → 超卖 ≤0.5%）。

### 18.3 设置租户配额与突发额度

五维同时启用，cost credits 为主约束。结算延迟满足 $t_{settle}<limit/(\lambda\Delta)$。每 key 设绝对成本上限作为泄露损失封顶，突发额度不得突破该上限。配额状态与凭证生命周期解耦。

### 18.4 选择路由与回退规则

三层路由分离：API Routing 定逻辑服务、Model Routing 定版本与 Canary、Replica Routing 定实例。能力校验前置（$capability\supseteq request$），回退链按能力等价类构建，跨类回退显式标记降级。四项前置校验把故障拦在首字节前。

### 18.5 传播截止时间和取消

入口生成 `budget` 与 `slo_tier` 作为锚点，下游按 $D_{remain}$ 动态收紧。客户端断开必须传播到后端并停止生成，同时结算已生成 Token。取消传播时间需带单位、窗口与分母上报。

### 18.6 保护凭证与敏感日志

默认只记 hash 与长度；完整内容需显式开启 + 租户隔离 + 短 TTL（1 h）+ 访问审计。凭证短期轮换但不携带配额状态。`user_id` 实际必需，API key per-user 或支持 sub-key 下钻。

### 19.5 验收判据

- 五维限流下不同请求形态的 GPU 占用偏差 $\le1.1\times$；
- P95 预估 + 及时释放时配额利用率 $\ge90\%$，超卖率 $\le1\%$；
- $t_{settle}$ 满足 $limit/(\lambda\Delta)$ 上限，批量对账不得用于 reserved 释放；
- 流式断开与失败均结算，计量对账四类来源各自 $\le0.5\%$；
- usage 写入幂等，重复 `request_id` 不产生二次扣费；
- 能力校验前置，无解请求入口拒绝率 100%，后端因此失败率 0；
- 回退链能力等价，跨类回退带 `degraded` 标记；
- Canary 检出时间与比例匹配，回滚传播 $\le5$ s 且排空条件已记录；
- 取消传播时间 $\le100$ ms，断开后后端无残留生成；
- 敏感日志默认关闭，开启时 TTL $\le1$ h 且有访问审计。

## 21. 常见追问与解答

**问 1：为什么不能只按 requests/min 限流？**
因为请求形态差异达 27 倍。100+100 的请求成本 517.5 GPU-ms，20K+20K 的成本 13950 GPU-ms。同一 60 req/min 限额下前者占 0.52 GPU、后者占 13.95 GPU。必须五维同时启用，以 cost credits 为主约束。

**问 2：按 token 限流总该公平了吧？**
反而偏向长请求。固定开销 450 GPU-ms 被摊薄后，短请求每 Token 成本 2.5875 GPU-ms、长请求 0.34875，差 7.42 倍。同一 token 限额下短请求租户会被压得更死。

**问 3：配额预留该用 max_tokens 还是历史分位？**
用 P95 加及时释放。max_tokens 预留使利用率仅 27.5%，且要求结算延迟 <27 s；P50 预留超卖 7.7%。P95 起步利用率 63.6%，随释放及时而趋近 100%，结算延迟上限放宽到 125 s。

**问 4：流式取消为什么必须结算？**
因为成本已真实发生。5% 断开率下漏计 8.64e7 Token/天，相当于 0.625 张 GPU 持续白跑（\$450/月），且成本归属完全丢失。只记 COMPLETED 会让这部分成本无法归到任何租户。

**问 5：回退成功率为什么达不到 100%？**
因为首字节后不能透明回退。10% 的后端故障发生在 Decode 中途，理论上限 90%。提高上限的办法不是加备选模型，而是把健康、能力、配额、预算四项校验前置，把故障拦在首字节之前。

**问 6：Canary 比例越小越安全吗？**
不是。比例从 10% 降到 0.1%，检出时间从 28.5 s 涨到 47.5 min，而累积受害请求数相同（285 个）。小比例只是把伤害摊薄到更长时间，对持续性故障反而更糟。

**问 7：Gateway 能不能参与调度？**
可以做入口一次决策，不能做每 Token 决策。后者让 Gateway 容量需求与 GPU 数量成正比（相差 300 倍），跨机时每请求多 600 ms（端到端的 38%）。token sampling、KV block 管理、Engine scheduler、每轮 Decode 决策必须留在引擎。

**问 8：配额只是公平性工具吗？**
还是安全工具。凭证泄露平均 24 h 才发现，滥用损失可达 \$2981；设 \$100/天的 cost credits 上限可封顶到 \$100，降低 29.8 倍。因此每个 key 必须有绝对成本上限，突发额度不得突破。

## 22. 延伸练习

1. 把 $F_{other}$ 从 450 改为 100 GPU-ms，重算第 6.2 节三种限流口径的偏差，判断 token 限流的反向偏差如何变化。
2. 推导流式增量粒度 $g$ 与最大超卖量的关系式，并求使超卖 $\le0.1\%$ 的 $g$（设并发 100、$limit=10^7$）。
3. 设结算路径改为异步批量（周期 $T$），推导配额失效的临界 $T$，并给出「保守预估 + 批量对账」可行的唯一条件。
4. 为五维限额设计联合校验顺序，说明哪一维应先检查才能最早拒绝，并量化不同顺序下的平均拒绝延迟。
5. 把 Canary 检验改为序贯检验（SPRT），推导期望检出时间与比例的关系，并与固定样本量 285 对比。
6. 设租户内用户用量服从 Zipf($s$)，推导按 key 均摊的成本转嫁比例随 $s$ 的变化，并给出必须启用 user 级归属的 $s$ 阈值。
7. 推导「首字节前四项前置校验」各自能拦下的故障比例，并说明叠加后回退成功率上限如何从 90% 提升。
8. 为多区域 Gateway 设计配额一致性方案，说明强一致写入的跨区延迟如何影响第 8 节的 $t_{settle}$ 上限，并给出分区配额的折中。

- [ ] $available\_quota=limit-reserved-settled+released$ 四事件齐备。
- [ ] 取消与失败同样释放预留，释放幂等。
- [ ] $t_{settle}<limit/(\lambda\Delta)$ 已验证，reserved 释放不走批量对账。
- [ ] 流式增量上报 usage，粒度按超卖上限反解。
- [ ] usage 写入幂等，键为 `request_id + usage_version`。
- [ ] 计量对账按四类来源分列，各自设阈值，不做净额抵消。
- [ ] 能力矩阵为运行时数据，$capability\supseteq request$ 前置校验。
- [ ] 无解请求入口拒绝，不计入路由失败。
- [ ] 回退链按能力等价类构建，跨类回退带 `degraded` 标记与原因。
- [ ] 健康、能力、配额、预算四项前置校验齐备。
- [ ] Canary 比例与检出时间匹配，回滚传播 $\le5$ s 且排空条件已记录。
- [ ] 取消传播到后端并停止生成，传播时间 $\le100$ ms。
- [ ] 租户有效成本按成功任务数为分母，分子含失败与重试。
- [ ] 敏感日志默认关闭，开启时租户隔离 + TTL $\le1$ h + 访问审计。
- [ ] 每 key 设绝对成本上限，突发额度不突破；配额状态与凭证解耦。
- [ ] Gateway 不参与每 Token 决策，配额计数为唯一强一致状态且已外部化。

## 写在最后

Gateway 的价值不在转发，而在把「谁能用、用多少、用了多少、出错怎么办」变成入口一次就能完成的治理决策。本文的判据链条是：五维限流封堵请求形态偏差 → 四事件计量生命周期配合结算延迟上限保证配额真实可用 → 流式增量与幂等结算保证成本不丢不重 → 能力校验与四项前置把故障拦在首字节之前 → alias 让回滚变成控制面操作 → 有效成本口径让重试放大在账单上可见。任一环缺失，都会出现「协议完全兼容、账目完全对不上」的现象。
