# P-EAGLE：并行 Drafter 与长上下文训练

理解 P-EAGLE 需要先回答「并行多 Token 草拟如何降低串行草拟延迟并保持可扩展训练？」。本文沿着概念边界、性能关系、实现证据和发布条件四条线展开，其中并行 Drafter 与多深度 Token 预测头是最先核对的状态。工作负载、模型修订、运行时、资源余量和服务承诺共同决定「多个深度预测头并行产生候选以移除串行草拟链」是否值得采用，后续每个结论都会注明这些条件。

实验采用两条证据路径：CPU 机制模拟隔离并行 Drafter 与多深度预测头的因果关系；真实 CUDA 路径记录实现、框架和硬件开销。报告分别标记两类结果，各深度准确率的模拟值不充当 GPU 基准，单台设备的绝对速度也不外推。最终结论必须能够复现、诊断并回滚。

## 1. 内容概览

- P-EAGLE 并行 Drafter、多深度 Token 预测头和共享前缀表示之间的状态与资源关系。
- 用 $T_{parallel}=T_{shared}+\max_j(T_{head_j})$ 与 $Gain=T_{serial\_draft}-T_{parallel}-\Delta T_{verify}$ 建立可计算的收益边界并解释全部变量。
- 围绕各深度准确率、候选多样性、并行草拟延迟和净 Goodput 设计可复现实验。
- 识别并行头输出高度相关、深位置准确率快速下降、共享层成为带宽瓶颈等典型失败模式。
- 对中心问题给出包含适用条件、证据、风险和回滚的工程答案。

## 3. 前置知识与实验环境

需要理解自回归生成、Tokenizer、Prefill、Decode、KV Cache、批处理和分位延迟的基本含义。所有缩写都会在正文首次出现处定义；没有某个特定框架经验不妨碍理解机制。实验需要 Python 3.11 或兼容版本。机制模拟只依赖 CPU；真实路径需要任意可用的 CUDA GPU、与驱动兼容的 PyTorch，以及自行准备的本地小模型或兼容制品。

验证前必须记录 GPU 名称、数量、可用显存、驱动、CUDA、PyTorch、推理框架、模型摘要、精度、批量、序列长度和完整命令。脚本根据可用显存缩放模型、批量、上下文和样本数，并把并行 Drafter 状态写入报告；可选 CUDA 入口不下载未经确认的大模型。

决定是否采用之前，先冻结模型版本、长度分布、流量到达、并发、采样、缓存状态、各深度准确率、服务等级和硬件配置。评审「确定并行头数量」和「选择共享层与独立层」时，由这些记录解释收益分子、成本分母及共享资源竞争。

## 4. 把 Draft Depth 看成多任务

### 4.1 多头损失与深度权重

设要预测未来 $K$ 个位置：

$$q_k(x_{t+k}\mid h_t),\quad k=1,\dots,K$$

最简单的多头训练是把各深度损失加权求和：

$$\mathcal{L}=\sum_{k=1}^{K}w_k\mathcal{L}_k$$

其中深位置通常更难，可以使用不同权重 $w_k$。权重设计是一个真实决策：提高深位置权重可能改善后部准确率，却挤占前部位置的学习容量，而前部位置对 prefix survival 的影响更大。

### 4.2 用分布信息做条件

如果每个 $q_k$ 只看同一个 $h_t$，就缺少中间 Token 条件。COD 类思想可以用前一个或前几个位置的**分布信息**而不是离散采样 Token 作为条件，从而保留可并行训练与推理的空间。抽象地写：

$$q_k(x_{t+k}\mid h_t, q_1,\dots,q_{k-1})$$

关键是这些条件可以以张量形式并行构造，而不要求真实走完 $k-1$ 次完整 autoregressive forward。这也是「并行」与「盲猜」的分界：条件信息仍然存在，只是以分布而非离散 Token 的形式传递。

## 5. Parallel Draft 的两个主要风险

### 5.1 Suffix Accuracy Decay

越靠后的位置条件越弱，准确率通常下降。如果定义条件接受概率：

$$p_k=P(\text{position }k\text{ accepted}\mid 1\dots k-1\text{ accepted})$$

那么前缀存活概率为：

$$P(A\ge k)=\prod_{i=1}^{k}p_i$$

一个位置稍微下降，长前缀存活概率会快速下降。这是连乘结构的直接后果，也是并行路线必须面对的核心约束。

### 5.2 Verification Waste

一次并行预测很便宜，容易诱惑把 $K$ 开得很大。但 Target 仍需验证这些位置。假设 verifier cost 为：

$$T_V(K)=a+bK+cK^2_{mask}$$

即使 Draft cost 近似常数，过大的 $K$ 仍可能把浪费转移到 verifier。二次项来自候选树或 mask 的构造与 attention 复杂度，它在 $K$ 较大时不可忽略。

## 6. 并行 Drafter 的真正优势在哪里

### 6.1 草拟延迟的两种增长形态

AR Drafter 的草拟延迟随深度线性增长：

$$T_D^{AR}(K)\approx K\cdot t_d$$

Parallel Drafter 的草拟延迟近似固定加一个缓慢增长项：

$$T_D^{P}(K)\approx t_{base}+\Delta(K)$$

如果 $\Delta(K)$ 增长较慢，就可以在相似 Draft latency 下提出更多候选。

### 6.2 收益条件

最终收益条件仍是有效速率的比较：

$$\frac{E[A_P]}{T_D^P+T_V^P}>\frac{E[A_{AR}]}{T_D^{AR}+T_V^{AR}}$$

也就是说，并行路线不需要「更准」，只需要在单位时间里留下更多被接受的 Token。

### 6.3 AR 与 Parallel 的对照推导

取一组推导设定（非实测）：AR 每步草拟 $t_d=1.0$ ms；Parallel $t_{base}=1.0$ ms、$\Delta(K)=0.05K$ ms；验证成本 $T_V(K)=2+0.1K+0.002K^2$ ms；条件接受率 AR 为 $p_k=0.9\times0.98^{k-1}$（衰减慢），Parallel 为 $p_k=0.9\times0.88^{k-1}$（衰减快）。

先算期望接受长度 $E[A]=\sum_{j=1}^{K}\prod_{i=1}^{j}p_i$：

| $K$ | AR $E[A]$ | Parallel $E[A]$ |
| --- | --- | --- |
| 1 | 0.900 | 0.900 |
| 2 | 1.694 | 1.613 |
| 4 | 2.961 | 2.414 |
| 8 | 4.394 | 2.702 |

再算每轮时间与单位有效 Token 时间（提交数按 $E[A+1]$ 计，含 Bonus Token）：

| $K$ | AR $T_{round}$ | AR $T_{effective}$ | Parallel $T_{round}$ | Parallel $T_{effective}$ |
| --- | --- | --- | --- | --- |
| 1 | 3.102 ms | 1.633 ms | 3.152 ms | 1.659 ms |
| 2 | 4.208 ms | 1.562 ms | 3.308 ms | 1.266 ms |
| 4 | 6.432 ms | 1.624 ms | 3.632 ms | 1.064 ms |
| 8 | 10.928 ms | 2.026 ms | 4.328 ms | 1.169 ms |

在这组假设下可以看到三件事：

- $K=1$ 时 AR 略优，因为并行的固定开销 $t_{base}$ 还没有被摊销。
- $K\ge2$ 后 Parallel 明显占优，尽管它的接受长度始终低于 AR。
- 两者最优点不同：AR 在 $K=2$（1.562 ms），Parallel 在 $K=4$（1.064 ms）。

以不启用投机时每 Token 需 $T_V(1)=2.102$ ms 为基线，Parallel 最优点的加速比约 $2.102/1.064\approx1.98$ 倍，AR 最优点约 $2.102/1.562\approx1.35$ 倍（推导值，非实测）。改变 $t_d$、$t_base$ 或衰减速率，交叉点与最优点都会移动，因此必须在真实负载上重新扫描。

### 6.4 验证浪费对照

同一组设定下，每轮浪费的验证位置数为 $K-E[A]$：

| $K$ | AR 浪费位置 | AR 浪费比例 | Parallel 浪费位置 | Parallel 浪费比例 |
| --- | --- | --- | --- | --- |
| 2 | 0.306 | 15.3% | 0.387 | 19.4% |
| 4 | 1.039 | 26.0% | 1.586 | 39.6% |
| 8 | 3.606 | 45.1% | 5.298 | 66.2% |

Parallel 的浪费比例始终更高，但单位有效 Token 时间更短。这说明「验证浪费」本身不是判据，浪费必须与草拟节省一起放进 $T_{effective}$ 才有意义；只有在高并发下浪费挤占了共享验证容量时，它才成为独立约束。

## 7. 并行延迟的构成：共享层与最慢头

并行草拟延迟由共享部分与最慢头决定：

$$T_{parallel}=T_{shared}+\max_j\left(T_{head_j}\right)$$

收益则为：

$$Gain=T_{serial\_draft}-T_{parallel}-\Delta T_{verify}$$

其中 $\Delta T_{verify}$ 是并行路线因为提出更多候选而额外增加的验证成本。若两条路线验证同样多的位置，$\Delta T_{verify}=0$；若并行路线把 $K$ 从 4 提到 8，就要按 $T_V(K)$ 补上差额。

用一组推导设定说明 $\max$ 的含义（非实测）：设 $T_{shared}=1.0$ ms，四个头耗时分别为 0.20、0.25、0.30、0.35 ms，则 $T_{parallel}=1.35$ ms，而同样这些头串行执行需要 $1.0+0.20+0.25+0.30+0.35=2.10$ ms。若其中一个头恶化到 1.20 ms，$T_{parallel}$ 立刻变成 2.20 ms，其余三个头的任何优化都不再产生影响。

这解释了「共享层成为带宽瓶颈」为什么是典型失败模式：共享部分与最慢头共同封顶，头数量增加并不自动带来延迟下降，反而可能因为共享表示被更多头读取而放大带宽压力。

## 8. 长上下文训练与 KV 访问成本

长上下文改变两件事：特征分布与 KV 访问成本。Drafter 每步草拟都要读取自身上下文 KV，读取量与上下文长度成正比，而草拟计算量近似不变，因此长上下文下草拟会从计算受限转向带宽受限，$t_d$ 与 $\Delta(K)$ 都不再是常数。

以一个单层、8 个 KV 头、head_dim 128、fp16 的 Drafter 为例，每 Token KV 为 $2\times1\times8\times128\times2=4096$ 字节即 4 KiB。按有效带宽 800 GB/s 估算（推导设定，非实测）：

| 上下文长度 $S$ | KV 总量 | 每步读取时间 |
| --- | --- | --- |
| 2048 | 8 MiB | 约 10.5 µs |
| 8192 | 32 MiB | 约 41.9 µs |
| 32768 | 128 MiB | 约 167.8 µs |
| 131072 | 512 MiB | 约 671.1 µs |

到 128K 上下文时，单步 KV 读取已进入数百微秒量级，与 $t_{base}$ 同量级。这意味着短上下文下测得的并行收益不能直接外推到长上下文，必须按上下文长度分桶重测；也意味着「决定是否为长上下文单独训练」是一个真实决策，而不是可选项。

训练侧的对应问题是长上下文训练样本不足：若训练语料以短序列为主，Drafter 在长上下文下的特征分布与接受率都会偏移，表现为深位置准确率快速下降。

## 9. 训练数据与域适配

Parallel drafter 对 workload 分布非常敏感。代码补全常有强局部结构；数学推理可能有固定模式；开放创作的不确定性更高。因此 Speculator 训练数据应覆盖真实 serving workload，而不是只在通用语料上追求平均 Token accuracy。

训练评测至少分为五类，并对每类分别报告 position-wise acceptance：

- coding；
- math/reasoning；
- general chat；
- structured/template；
- bilingual/multilingual。

分桶报告的意义在于：并行路线的收益高度依赖深位置条件是否充分，而不同域的深位置可预测性差异很大。一个在 coding 上表现优异的并行 Drafter，可能在 general chat 上深位置准确率崩塌，全局平均值会把这件事完全掩盖。

## 10. 八个概念的边界与失败模式

跟踪的八个概念为：P-EAGLE 并行 Drafter、多深度 Token 预测头、共享前缀表示、位置条件与深度条件、并行草拟延迟、长上下文训练、草拟头相关性、动态 Depth。虽然它们分属不同系统层级，长上下文退化和净 Goodput 会同时受到这些状态影响。

### 10.1 统一检查框架

每个概念都按同一组问题展开：边界与生命周期（输入从哪里来、状态由谁持有、输出交给谁、失败如何传播、何时销毁）、资源账（计算、显存、内存带宽、主机开销、同步等待分别记账）、负载区间（低载、接近饱和、过载三段同口径）、正确性门禁（Token 序列、采样分布、结构合法性、结束原因、错误传播）、观测字段（请求身份、模型与策略修订、起止时间、阶段耗时、资源快照、失败原因）。跨概念传递的数据必须携带版本身份，否则请求时间线会混入旧配置。

### 10.2 P-EAGLE 并行 Drafter

边界检查覆盖输入、输出、状态归属和销毁时点；传给多深度 Token 预测头的数据应附带模型或策略版本。资源账拆成五项：共享表示降低重复计算但会耦合不同深度任务，通常只先改变其中几项，其他资源随后可能进入关键路径。

「设计深度损失权重」应覆盖长短输入、不同输出、并发、突发、采样与任务域，并保留三段负载记录。典型失败是长上下文训练样本不足，触发停止与回退，系统恢复到已有证据支持的配置。接受长度必须附带口径。

### 10.3 多深度 Token 预测头

边界由输入、输出、状态和拥有者共同确定；连接共享前缀表示时要传播身份和版本。测量分别记录算力、显存、带宽、CPU 开销与同步。越深位置依赖更长未知前缀而预测难度上升，缩短的阶段可能让另一项资源成为瓶颈，因此分析要对齐阶段事件和资源轨迹。

「采样或剪枝并行候选」至少比较低载、临近容量与过载。典型失败是并行草拟减少延迟却增加显存峰值：质量结果优先于速度数字，发布停止，流量回到已验证修订，相关请求留作重放。显存峰值同时注明单位、窗口和分母。

### 10.4 共享前缀表示

先列出接收什么、产生什么、由谁维护以及状态何时结束；与位置条件与深度条件交互的字段必须携带版本身份。长上下文改变特征分布与 KV 访问成本会移动关键路径，却很少让所有资源同比例变化：请求事件负责说明顺序，资源曲线负责解释瓶颈转移。

「按负载调整 Depth」是否合适，取决于长度分布、并发、到达过程、采样和任务域。典型失败是静态 Depth 在负载变化时失效，质量门禁应停止性能发布，回退目标是已验证配置并保留问题请求。长上下文退化没有单位、统计窗口和分母时不参与决策。

### 10.5 位置条件与深度条件

生命周期落到组件接口，并与并行草拟延迟绑定身份和版本。预测头相关性过高会降低候选多样性，其影响分散到计算、显存、内存带宽、主机处理和同步等待；某一阶段变短时，被遮蔽的成本可能随即暴露，因此要对齐请求时间线与资源采样，而非只看整段运行的 GPU 平均值。

「决定是否为长上下文单独训练」的验证分别运行三段负载并使用代表性分布。典型失败是并行头输出高度相关：当前性能结果不进入候选评审，立即切回已验证配置，失败样本与版本信息一并保存。净 Goodput 的定义随报告存档，包括单位、窗口和分母。

### 10.6 并行草拟延迟

边界检查覆盖输入、输出、状态归属和销毁时点；传给长上下文训练的数据应附带版本。在线负载决定并行草拟节省是否能覆盖验证成本，通常只先改变资源账中的几项，其他资源随后可能进入关键路径。

「确定并行头数量」应覆盖长短输入、不同输出、并发、突发、采样与任务域。典型失败是深位置准确率快速下降，触发停止与回退。各深度准确率必须附带口径，否则上线后无法复核判断。

### 10.7 长上下文训练

边界由输入、输出、状态和拥有者共同确定；连接草拟头相关性时要传播身份和版本。测量分别记录算力、显存、带宽、CPU 开销与同步。多个深度预测头并行产生候选以移除串行草拟链后，缩短的阶段可能让另一项资源成为瓶颈。

「选择共享层与独立层」至少比较低载、临近容量与过载。典型失败是共享层成为带宽瓶颈：质量结果优先于速度数字，发布停止，流量回到已验证修订。候选多样性同时注明单位、窗口和分母。

### 10.8 草拟头相关性

先列出接收什么、产生什么、由谁维护以及状态何时结束；与动态 Depth 交互的字段必须携带版本身份。共享表示降低重复计算但会耦合不同深度任务，会移动关键路径，却很少让所有资源同比例变化。

「设计深度损失权重」是否合适，取决于长度分布、并发、到达过程、采样和任务域。典型失败是长上下文训练样本不足，质量门禁应停止性能发布。并行草拟延迟没有单位、统计窗口和分母时不参与决策。

### 10.9 动态 Depth

生命周期落到组件接口，并与并行 Drafter 绑定身份和版本。越深位置依赖更长未知前缀而预测难度上升，其影响分散到五项资源；为确认变化来自哪里，要对齐请求时间线与资源采样。

「采样或剪枝并行候选」的验证分别运行三段负载并使用代表性分布。典型失败是并行草拟减少延迟却增加显存峰值：当前性能结果不进入候选评审，立即切回已验证配置。验证节点数的定义随报告存档，包括单位、窗口和分母。

## 11. 六个机制的因果分析

![P-EAGLE 的机制与证据闭环](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y3_l04_01.png)

*机制流程：把并行草拟的输入、关键决策、执行与证据闭环连接起来。*

分析采用近似式 $T_{parallel}=T_{shared}+\max_j(T_{head_j})$ 与 $Gain=T_{serial\_draft}-T_{parallel}-\Delta T_{verify}$。并行 Drafter 与多深度预测头进入决策变量，模型、负载和硬件限定结果，各深度准确率、验证节点数与净 Goodput 承担验证。公式只表达这些变量的关系；时间单位、概率取值和各深度准确率分母必须在运行配置中显式记录。框架调度、Kernel 启动、内存分配、网络、客户端和取消传播仍由真实路径计量；模拟与实测方向不一致时，检查遗漏变量和指标口径。

### 11.1 机制 1：多个深度预测头并行产生候选以移除串行草拟链

从请求关键路径入手，变化前后每个阶段的顺序、并行性和合批条件均需标注，并行 Drafter 作为启用条件，各深度准确率作为端到端结果。

容量测试覆盖低载、稳定高载和过载：低载显示固定与同步成本，高载显示队列、批处理及共享资源竞争。若出现深位置准确率快速下降，说明局部延迟没有变成有效容量，需要核对候选工作占用的公共资源。

接口合同包括格式、Shape、缓存键、版本与回退语义。「设计深度损失权重」进入评审前，使用非法输入、边界长度和资源不足场景检验保护路径。采集证据时把策略输入、阈值、候选集合与验证节点数、错误、取消及资源事件放进同一请求链。发布单元包含灰度身份、门禁、停止动作和已预热回滚路径；检测到并行草拟减少延迟却增加显存峰值后执行局部撤回，并确认在途工作、缓存与资源回到稳定状态。

### 11.2 机制 2：共享表示降低重复计算但会耦合不同深度任务

这一机制会改写请求的阶段顺序。画出变化前后的关键路径，标明并行、串行和跨请求合批位置；多深度 Token 预测头给出状态条件，候选多样性验证结果是否传到请求端。

单请求数据不足以评价该机制：低载用于测量固定成本，接近容量时观察批处理与共享资源，过载时确认拒绝和尾延迟。「共享层成为带宽瓶颈」若只在并发后出现，优先检查候选路径对正常请求资源的挤占。

数据格式、张量形状、缓存身份、版本兼容和错误传播共同构成实现边界；「采样或剪枝并行候选」需要在合同冻结后测试正常、无效、极端和资源受限输入。证据需要成对的原因和结果字段：原因包括决策特征、阈值和候选，结果包括接受长度、错误、取消和资源快照。发布时配置独立开关、灰度身份、停止条件和暖回滚目标；「静态 Depth 在负载变化时失效」触发后只撤回相关变化，并继续检查在途请求、缓存和资源释放。

### 11.3 机制 3：越深位置依赖更长未知前缀而预测难度上升

把前后两条请求时间线对齐，逐段标出可并行、必须串行和允许合批的工作。共享前缀表示说明机制何时生效，并行草拟延迟负责确认关键路径是否真的缩短。

分别施加轻载、稳定高载和过载流量，可以分辨同步开销、队列增长、合批变化与资源竞争。检测到长上下文训练样本不足后，沿共享执行资源检查局部收益为何没有进入系统 Goodput。

确定接口时同时规定数据与 Shape、缓存和版本身份、错误及回退，随后以无效输入、极端长度和资源不足验证「按负载调整 Depth」。观测时原因侧保存策略输入、阈值和候选集合，结果侧保存显存峰值、错误、取消与资源；两侧对齐后可以区分收益不足、选择错误、实现开销偏大和工作负载漂移。该机制通过独立开关进入灰度，出现并行头输出高度相关时撤回本项候选。

### 11.4 机制 4：长上下文改变特征分布与 KV 访问成本

先记录原路径，再记录候选路径中的串行、并行与合批段，同时保存位置条件与深度条件状态和验证节点数。容量评估放在三个负载区间中运行；「并行草拟减少延迟却增加显存峰值」意味着候选工作可能消耗了服务正常请求所需的容量。

实现时明确数据格式、张量形状、缓存身份、版本兼容和错误回退；执行「决定是否为长上下文单独训练」前冻结接口合同，并加入无效输入、极端长度与资源不足测试。Trace 同时记录决策输入与执行结果，后者含长上下文退化、错误、取消和资源变化。上线合同写明灰度范围、停止条件、开关和暖回滚目标；深位置准确率快速下降发生后，系统恢复相关稳定配置，并持续观察请求排空、缓存切换和资源回收。

### 11.5 机制 5：预测头相关性过高会降低候选多样性

从请求关键路径入手，标注变化前后每个阶段的顺序、并行性和合批条件，并行草拟延迟作为启用条件，接受长度作为结果。

容量测试覆盖低载、稳定高载和过载。若出现静态 Depth 在负载变化时失效，说明局部延迟没有变成有效容量，需要核对候选工作占用的公共资源。接口合同包括格式、Shape、缓存键、版本与回退语义；「确定并行头数量」进入评审前，使用非法输入、边界长度和资源不足场景检验保护路径。

采集证据时把策略输入、阈值、候选集合与净 Goodput、错误、取消及资源事件放进同一请求链。发布单元包含灰度身份、门禁、停止动作和已预热回滚路径；检测到共享层成为带宽瓶颈后执行局部撤回，并确认在途工作、缓存与资源回到稳定状态。

### 11.6 机制 6：在线负载决定并行草拟节省是否能覆盖验证成本

这一机制会改写请求的阶段顺序。画出变化前后的关键路径，标明并行、串行和跨请求合批位置；长上下文训练给出状态条件，显存峰值验证结果是否传到请求端。

单请求数据不足以评价：低载用于测量固定成本，接近容量时观察批处理与共享资源，过载时确认拒绝和尾延迟。「并行头输出高度相关」若只在并发后出现，优先检查候选路径对正常请求资源的挤占。

数据格式、张量形状、缓存身份、版本兼容和错误传播共同构成实现边界；「选择共享层与独立层」需要在合同冻结后测试正常、无效、极端和资源受限输入。这一机制也是动态 Depth 的直接依据：低载时放长深度追求单请求延迟，高载时收缩深度保住验证容量与净 Goodput。

## 12. 工程决策与取舍

### 12.1 确定并行头数量

头数量决定 $K$ 的上限，也决定共享表示被读取的次数。判据是 $T_{effective}$ 与验证浪费比例的联合曲线，而不是头数越多越好。第 6.3 节的推导显示最优点通常出现在中等深度，且随成本参数移动。

### 12.2 选择共享层与独立层

共享层减少重复计算，但让不同深度任务耦合在同一表示上，并可能成为带宽瓶颈；独立层提高各深度的表达能力，代价是参数、显存与草拟延迟上升。决策应按上下文长度分桶评测：短上下文下共享更划算，长上下文下共享层的带宽压力可能抵消收益。

### 12.3 设计深度损失权重

深位置更难，提高其权重看似合理，但前部位置对 prefix survival 的贡献更大。权重设计应以「接受长度增量」为目标函数，而不是以各深度 loss 均衡为目标；调整后必须重新报告逐位置准确率曲线。

### 12.4 按负载调整 Depth

固定 $K$ 最容易实现，但不同请求的可预测性不同，且 verifier 负载随时间变化。动态 Depth 的依据包括前几个位置 confidence、最近 acceptance 历史、request domain、verifier 当前负载与 SLO。调整需要迟滞与上下限，避免深度抖动带来的图重捕获与缓存失效。这也是后续 DSpark 与动态 Speculator Policy 的接口。

### 12.5 采样或剪枝并行候选

并行头一次产生多个位置的分布，可以按置信度剪掉低质量尾部候选，减少验证浪费。剪枝阈值必须与验证预算联动：低载时放宽以争取接受长度，高载时收紧以保住批处理容量。剪枝策略本身需要版本化并进入观测。

### 12.6 决定是否为长上下文单独训练

若服务负载包含大量长上下文请求，且短上下文训练的 Drafter 在长上下文下深位置准确率显著下降，则需要单独训练或混合训练。判据是分桶后的接受长度与端到端 TPOT，而不是训练集上的平均准确率。单独训练会增加制品数量与兼容矩阵复杂度，需要一并计入维护成本。

## 13. 实验设计：复用投机解码边界实验框架

本主题不另建实验入口，复用前一篇投机解码性能边界的实验框架，加入两个模型：

1. **AR**：Draft latency 随 $K$ 线性增加，但 $p_k$ 衰减慢。
2. **Parallel**：Draft latency 近似固定，但 $p_k$ 衰减更快。

扫描 $K=1\dots16$，比较四项结果：accepted length、effective token latency、verification waste、最优 $K$。运行方式沿用统一约定：默认 Fixture，`--check-only` 只做预检，`--real` 进入实测路径。

最终应看到的现象是：Parallel Drafter 的优势不是「永远更准」，而是用低 Draft latency 换取更多候选空间，再由质量决定能留下多少。第 6.3 与 6.4 节的推导表给出了这一结论的定量形式，真实路径需要用自己的成本参数与准确率曲线重新计算。

真实 CUDA 路径额外记录：共享层与各头耗时、峰值显存、长上下文分桶下的草拟延迟、验证节点数、错误与取消。预检记录完整环境与制品修订，显存不足时按约定缩放并给出可识别退出码。只有 `source=measured` 可以支撑性能或发布结论。

## 14. 常见错误与排查

| 现象 | 可能原因 | 排查方向 |
| --- | --- | --- |
| 并行头很多但接受长度不涨 | 深位置缺少条件信息，近似盲猜 | 检查是否传入前序分布条件，报告逐位置准确率 |
| 深位置准确率快速下降 | Suffix Accuracy Decay | 收缩 $K$，或改进深位置条件与损失权重 |
| 头数增加后延迟不降 | $T_{parallel}$ 由共享层与最慢头封顶 | 分别计时共享层与各头，定位最慢头 |
| 并发升高后共享层变慢 | 共享表示成为带宽瓶颈 | 记录带宽与读取量，考虑独立层或减少头数 |
| 显存峰值上升导致 OOM | 并行候选与 mask 同时增大 | 分阶段记录峰值显存，限制验证预算 |
| 长上下文下收益消失 | KV 读取量随 $S$ 线性增长 | 按上下文长度分桶重测，必要时单独训练 |
| 各头输出几乎相同 | 预测头相关性过高，候选多样性不足 | 统计头间相关性与候选去重后数量 |
| 低载很快、高载 Goodput 下降 | 验证浪费挤占共享容量 | 观测 $B_{verify}$ 与队列，启用动态 Depth |
| 静态 $K$ 在流量变化后失效 | 缺少负载感知 | 引入 confidence、acceptance 历史与 verifier 负载 |
| coding 很好、chat 很差 | 训练域与服务域不匹配 | 五类分桶评测，按域启用或重新训练 |

## 15. 常见追问与解答

**问：并行 Drafter 为什么不需要更准也能更快？**
答：判据是 $E[A]/(T_D+T_V)$。并行把 $T_D$ 从 $K\cdot t_d$ 降到近似 $t_{base}+\Delta(K)$，即使 $E[A]$ 略低，比值仍可能更高。

**问：并行头之间的条件信息怎么传？**
答：用前序位置的分布信息而非离散采样 Token 作为条件，以张量形式并行构造，避免真实走完 $k-1$ 次自回归前向。

**问：$K$ 能不能开得很大？**
答：不能无条件开大。验证成本含 $bK$ 与 $cK^2_{mask}$ 项，且深位置接受率衰减使浪费比例上升；高并发下还会挤占共享验证容量。

**问：$T_{parallel}$ 为什么取 max 而不是求和？**
答：各头并行执行，整轮延迟由最慢头决定。因此优化非最慢头没有收益，共享层与最慢头才是关键路径。

**问：长上下文为什么会让并行收益消失？**
答：草拟每步读取的 KV 与上下文长度成正比，长上下文下带宽项进入百微秒到毫秒量级，$t_{base}$ 与 $\Delta(K)$ 不再是常数，短上下文的结论不能外推。

**问：头相关性过高有什么后果？**
答：候选多样性下降，多个头提出几乎相同的候选，验证节点被浪费而接受长度不增。需要统计头间相关性与去重后候选数。

**问：动态 Depth 依据哪些信号？**
答：前几个位置 confidence、最近 acceptance 历史、request domain、verifier 当前负载与 SLO，并配合迟滞与上下限避免抖动。

**问：训练评测为什么要分五类域？**
答：并行路线对深位置可预测性高度敏感，不同域差异很大。全局平均准确率会掩盖某个域的深位置崩塌。

## 写在最后

并行 Drafter 的价值不在「更准」，而在用近似固定的草拟延迟换取更多候选空间，再由深位置质量决定能留下多少。共享层与最慢头封顶了并行延迟，验证成本的二次项与长上下文 KV 读取封顶了可用深度，这两条约束一起决定了并行路线的适用区间。
