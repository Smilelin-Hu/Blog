# Multi-Model Serving：热冷模型与稀疏流量

## 1. 课程定位

理解 Multi-Model Serving：热冷模型与稀疏流量，需要先回答“怎样决定模型常驻、休眠、逐出和恢复策略以降低空闲成本？”。本文沿着概念边界、性能关系、实现证据和发布条件四条线展开，其中多模型服务池与 Hot Model 是最先核对的状态。工作负载、模型修订、运行时、资源余量和服务承诺共同决定热模型常驻换取低延迟但增加空闲成本是否值得采用，后续每个结论都会注明这些条件。

实验采用两条证据路径。CPU 机制模拟隔离多模型服务池与 Hot Model 的因果关系；真实 CUDA 路径记录实现、框架和硬件开销。报告分别标记两类结果，模型常驻率的模拟值不充当 GPU 基准，单台设备的绝对速度也不外推。最终结论必须能够复现、诊断并回滚。

## 2. 学习目标

1. 准确解释多模型服务池、Hot Model 和 Cold Model 之间的状态与资源关系。
2. 使用“KeepResident if expected_requests*horizon*latency_saved > idle_cost + eviction_externality”建立可计算的收益边界并解释全部变量。
3. 围绕模型常驻率、冷启动时间、缓存命中率和有效 GPU 成本设计可复现实验。
4. 识别逐出后立刻再次加载形成抖动、并发加载占满存储带宽和显存总量足够却因碎片加载失败等典型失败模式。
5. 对“怎样决定模型常驻、休眠、逐出和恢复策略以降低空闲成本？”给出包含适用条件、证据、风险和回滚的工程答案。

## 3. 前置知识与环境

阅读 Multi-Model Serving：热冷模型与稀疏流量需要理解自回归生成、Tokenizer、Prefill、Decode、KV Cache、批处理和分位延迟的基本含义。涉及多模型服务池时，所有缩写都会在正文首次出现处定义；没有某个特定框架经验不妨碍理解机制。实验需要 Python 3.11 或兼容版本。围绕多模型服务池的机制模拟只依赖 CPU；真实路径需要任意可用的 CUDA GPU、与驱动兼容的 PyTorch，以及自行准备的本地小模型或兼容制品。

验证多模型服务池前必须记录 GPU 名称、数量、可用显存、驱动、CUDA、PyTorch、推理框架、模型摘要、精度、批量、序列长度和完整命令。脚本根据可用显存缩放模型、批量、上下文和样本数，并把多模型服务池状态写入报告；可选 CUDA 入口不下载未经确认的大模型。

## 4. 工程问题

决定是否采用 Multi-Model Serving：热冷模型与稀疏流量前，先冻结模型版本、长度分布、流量到达、并发、采样、缓存状态、模型常驻率、服务等级和硬件配置。评审“划分热温冷层级”和“选择常驻与逐出阈值”时，由这些记录解释收益分子、成本分母及共享资源竞争。

本文跟踪八个概念：多模型服务池、Hot Model、Cold Model、模型常驻、模型逐出、模型恢复、稀疏流量、显存碎片。虽然它们分属不同系统层级，冷请求 P99 和有效 GPU 成本会同时受到这些状态影响。后文从多模型服务池开始，逐项说明谁维护状态、在哪里计量、什么情况下失效，以及结果怎样传到请求端。

## 5. 知识串讲

### 核心直觉与基础关系

### 核心直觉：低频模型的主要成本往往是“常驻等待”，不是推理本身

当模型数量远大于稳定热门模型数量时，Dedicated Deployment 会让大量 GPU 为稀疏流量空转。Multi-Model Serving 要把模型本身也变成可装载、可驱逐的资源。

假设 20 个模型，每个至少 2 张 GPU 保证高可用：

$$GPU_{reserved}=20\times2=40$$

其中 15 个模型一天只有少量请求，GPU 大部分时间空闲。

Multiplexing 允许：

```text
Replica Pool
├─ 当前驻留 Model A
├─ 当前驻留 Model B
└─ 按需加载 Model C/D/...
```

用少量共享容量承载稀疏流量。

### Hot / Warm / Cold

### Hot

常驻 GPU，SLO 最好，成本最高。

### Warm

权重在本地 NVMe/Host cache，GPU 需要加载但不需要远程下载。

### Cold

只在远程存储/Registry，首次请求需要完整下载和初始化。

一个模型的状态可以动态变化：

```text
Cold → Warm → Hot → Warm → Cold
```

### 热度模型

可用滑动窗口估计：

$$Heat_m=\alpha ReqRate_m+\beta RecentRequests_m+\gamma BusinessPriority_m$$

再决定：

- 是否常驻；
- 常驻多少 Replica；
- 是否预热；
- 是否驱逐。

但纯历史热度对突然 burst 不够，需要结合事件/预测。

### Model Load Cost

模型加载成本不只是文件大小：

$$T_{load}=T_{download}+T_{deserialize}+T_{H2D}+T_{runtime-init}+T_{warmup}$$

相同 20GB 权重：

- 本地 NVMe vs 网络对象存储；
- FP16 vs 量化；
- 单文件 vs shards；
- Runtime 是否需要编译/Graph capture；

启动时间都可能差很多。

所以 Model Multiplexing 的 cache 策略应使用真实 load cost。

### Eviction

显存不足时驱逐哪个模型？

简单 LRU：

$$Evict=\arg\min LastUsed$$

更好的 cost-aware：

$$Score_m=\frac{PredictedReuse_m\cdot LoadCost_m}{Memory_m}$$

优先保留单位显存能节省更多未来加载成本的模型。

### Model Router

请求到来：

1. 查哪些 Replica 已驻留模型；
2. 如果有，结合 load 选一个；
3. 如果没有，选择可加载实例；
4. 可能触发 scale-out；
5. 在 SLO 不允许等待时使用 fallback model。

例如：

```text
reasoning-pro cold
→ fallback reasoning-balanced
```

Model Alias 让客户端不需要知道内部切换。

### Sparse Traffic 的核心矛盾

如果模型流量很稀疏：

- 常驻：浪费 GPU；
- 不常驻：每次 Cold Start。

最优方案取决于：

$$IdleCost \quad vs \quad ColdStartPenalty\times RequestRate$$

可以用阈值：

$$C_{idle}<\lambda\cdot C_{cold}$$

时常驻更划算，反之允许冷却。

### Multi-Model 与 Multi-LoRA 的边界

Multi-LoRA：共享 Base，切换小 Adapter。

Multi-Model：Base 权重本身不同，load cost/显存通常高得多。

因此不要把 Adapter Multiplexing 的经验直接套到完整 Model Multiplexing。

### 多模型服务池

对多模型服务池做边界检查，要覆盖输入、输出、状态归属和销毁时点。Multi-Model Serving：热冷模型与稀疏流量的等待、计算及复制都能沿这些节点定位。多模型服务池传给 Hot Model 的数据还应附带模型或策略版本，使测量结果可以对应到唯一配置。

多模型服务池的资源账要拆成计算、显存、内存带宽、主机开销和同步等待。冷模型按需加载降低常驻成本却引入启动延迟通常只先改变其中几项，其他资源随后可能进入关键路径。多模型服务池的请求时间线和资源曲线可以呈现这种转移，平均 GPU 利用率只作为辅助信号。

工作负载一变，多模型服务池对系统的贡献也会变化。设置 Warm Pool 应覆盖长短输入、不同输出、并发、突发、采样与任务域，并保留低载、稳定高载和过载记录。容量判断不能从一次固定批量的短运行外推。

对多模型服务池的优化只有在输出合同不变时才有效。Token 序列、采样分布、结构合法性、结束原因和错误传播均需对账。热度统计窗口反应过慢会触发停止与回退，系统恢复到已有证据支持的配置。

多模型服务池相关事件要能关联到稳定请求身份、模型与策略版本、开始结束时间、阶段耗时、资源采样和失败原因。显存碎片率必须附带口径。缺少这些信息时，关于“怎样决定模型常驻、休眠、逐出和恢复策略以降低空闲成本？”的判断无法在上线后复核。

### Hot Model

在 Multi-Model Serving：热冷模型与稀疏流量中，Hot Model 的边界由输入、输出、状态和拥有者共同确定。把生命周期写清楚，才能定位请求在哪个阶段等待、计算或复制。Hot Model 连接 Cold Model 时还要传播身份和版本，避免把另一套配置的结果归到当前实验。

测量 Hot Model 时分别记录算力、显存、带宽、CPU 开销与同步。发生“模型大小和分配顺序造成显存碎片”后，缩短的阶段可能让另一项资源成为瓶颈。分析因此对齐 Hot Model 的阶段事件和资源轨迹，不让单个平均利用率代替因果证据。

评估 Hot Model 需要把负载分布写入实验：输入输出长度、并发、到达突发、采样方式和业务域都可能移动收益边界。限制并发加载至少比较低载、临近容量与过载，结论只覆盖实际运行过的区间。

Hot Model 进入候选路径后，输出校验继续检查 Token、采样、结构、结束原因和错误传递。冷模型请求阻塞共享队列一旦出现，质量结果优先于速度数字；发布停止，流量回到已验证修订，相关请求留作重放。

观察 Hot Model 需要稳定请求身份、模型与策略修订、起止时间、阶段耗时、资源快照和失败原因。模型切换次数同时注明单位、窗口和分母。这些字段使“怎样决定模型常驻、休眠、逐出和恢复策略以降低空闲成本？”可以在发布后按原条件回放。

### Cold Model

解释 Cold Model 时，先列出它接收什么、产生什么、由谁维护以及状态何时结束。Multi-Model Serving：热冷模型与稀疏流量的请求可能在这些交界处增加等待、计算或复制。与模型常驻交互的字段必须携带版本身份，便于回放时找到同一配置。

围绕 Cold Model 建立资源模型，需要把计算量、显存占用、内存流量、主机工作和等待时间单独记账。请求热度变化需要迁移常驻集合会移动关键路径，却很少让所有资源同比例变化。请求事件负责说明顺序，资源曲线负责解释瓶颈转移。

整理显存与进程生命周期是否合适，取决于 Cold Model 所面对的长度分布、并发、到达过程、采样和任务域。实验在低载、接近饱和、过载三段保留同口径证据。固定长度与固定批量的结果用于解释机制，不承担完整容量结论。

Cold Model 带来的速度变化仍需满足模型输出合同，包括 Token 序列、采样分布、结构合法性、结束原因和错误传播。出现只优化 GPU 空闲而忽略启动体验时，质量门禁应停止性能发布；回退目标是已验证配置，并保留问题请求用于复现。

Cold Model 的观测记录包含请求身份、模型版本、策略版本、阶段时间、资源状态与失败原因。冷请求 P99 没有单位、统计窗口和分母时不参与决策。完整记录用于复查“怎样决定模型常驻、休眠、逐出和恢复策略以降低空闲成本？”在具体负载下是否成立。

### 模型常驻

模型常驻在 Multi-Model Serving：热冷模型与稀疏流量中的生命周期需要落到组件接口：输入从哪里来，状态由谁持有，输出交给谁，失败如何传播。它与模型逐出之间的身份和版本若未绑定，请求时间线就可能混入旧配置。

恢复路径依赖权重缓存和加载并发对模型常驻的影响会分散到计算、显存、内存带宽、主机处理和同步等待。某一阶段变短时，被遮蔽的成本可能随即暴露。为确认模型常驻的变化来自哪里，本文对齐请求时间线与资源采样，而非只看整段运行的 GPU 平均值。

模型常驻的边际价值会随输入长度、输出长度、并发、流量突发、采样和任务域变化。验证为稀疏模型定义服务等级时分别运行低载、接近饱和与过载区间，并使用代表性分布。单一长度、批量或短窗口只能说明该测试点。

正确性门禁覆盖模型常驻影响到的 Token、采样、结构、结束状态与错误。若检测到逐出后立刻再次加载形成抖动，当前性能结果不进入候选评审，并立即切回已验证配置。失败样本与版本信息要一并保存。

为模型常驻建立证据链时，统一保存请求 ID、模型及策略修订、关键时间点、资源快照和错误。有效 GPU 成本的定义随报告存档，包括单位、窗口和分母。这样才能按同一条件重放“怎样决定模型常驻、休眠、逐出和恢复策略以降低空闲成本？”。

显存碎片在 Multi-Model Serving：热冷模型与稀疏流量中的生命周期需要落到组件接口：输入从哪里来，状态由谁持有，输出交给谁，失败如何传播。它与多模型服务池之间的身份和版本若未绑定，请求时间线就可能混入旧配置。

模型大小和分配顺序造成显存碎片对显存碎片的影响会分散到计算、显存、内存带宽、主机处理和同步等待。某一阶段变短时，被遮蔽的成本可能随即暴露。为确认显存碎片的变化来自哪里，本文对齐请求时间线与资源采样，而非只看整段运行的 GPU 平均值。

显存碎片的边际价值会随输入长度、输出长度、并发、流量突发、采样和任务域变化。验证限制并发加载时分别运行低载、接近饱和与过载区间，并使用代表性分布。单一长度、批量或短窗口只能说明该测试点。

正确性门禁覆盖显存碎片影响到的 Token、采样、结构、结束状态与错误。若检测到冷模型请求阻塞共享队列，当前性能结果不进入候选评审，并立即切回已验证配置。失败样本与版本信息要一并保存。

为显存碎片建立证据链时，统一保存请求 ID、模型及策略修订、关键时间点、资源快照和错误。加载带宽的定义随报告存档，包括单位、窗口和分母。这样才能按同一条件重放“怎样决定模型常驻、休眠、逐出和恢复策略以降低空闲成本？”。

### 性能模型与变量

分析采用近似式 KeepResident if expected_requests*horizon*latency_saved > idle_cost + eviction_externality。多模型服务池与 Hot Model 进入决策变量，模型、负载和硬件限定结果，模型常驻率、加载带宽与有效 GPU 成本承担验证。公式只表达这些变量的关系；时间单位、概率取值和模型常驻率分母必须在运行配置中显式记录。

这项近似主要回答方向问题：发生“热模型常驻换取低延迟但增加空闲成本”时先观察哪一项，出现“冷模型按需加载降低常驻成本却引入启动延迟”时成本如何摊销。框架调度、Kernel 启动、内存分配、网络、客户端和取消传播仍由真实路径计量。模拟与实测方向不一致时，检查遗漏变量和指标口径。

### 机制 1：热模型常驻换取低延迟但增加空闲成本

理解“热模型常驻换取低延迟但增加空闲成本”要从请求关键路径入手。变化前后每个阶段的顺序、并行性和合批条件均需标注，多模型服务池作为启用条件，模型常驻率作为端到端结果。

“热模型常驻换取低延迟但增加空闲成本”的容量测试覆盖低载、稳定高载和过载。低载显示固定与同步成本，高载显示队列、批处理及共享资源竞争。若出现并发加载占满存储带宽，说明局部延迟没有变成有效容量，需要核对候选工作占用的公共资源。

“热模型常驻换取低延迟但增加空闲成本”的接口合同包括格式、Shape、缓存键、版本与回退语义。设置 Warm Pool 进入评审前，使用非法输入、边界长度和资源不足场景检验保护路径，确保实现不会只在理想样本上成立。
