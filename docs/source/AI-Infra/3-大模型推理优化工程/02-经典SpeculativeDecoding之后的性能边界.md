# 经典 Speculative Decoding 之后的性能边界

「何时投机解码会加速，何时验证成本和批处理竞争会抵消收益？」是贯穿本文的问题。先把 Draft Model 与 Target Model 的职责边界、候选 Token 块与草拟深度及其状态边界讲清楚，再讨论计算、实现和上线证据。在经典 Speculative Decoding 之后，算法选择只是决策的一部分；负载分布、模型修订、调度、显存、并发和服务等级都会改变结论。每项收益都需要对应可观察的事件与适用范围。

个人电脑即可完成双路径验证：CPU 模拟负责检验从职责边界到候选深度的方向，CUDA 实验负责测量真实执行代价。模拟、实测和外部资料不会混用。围绕职责边界得出的结果只对记录的模型、软件、设备和负载负责，同时给出失败原因与回滚入口。

## 1. 内容概览

- Draft Model 与 Target Model 的职责边界、候选 Token 块与草拟深度、接受长度与接受率之间的状态与资源关系。
- 用 $T_{round}=T_{draft}(k)+T_{verify}(k)+T_{sample}+T_{sync}$ 与 $R_{eff}=E[A+1]/T_{round}$ 建立可计算的收益边界，并解释全部变量。
- 围绕平均接受长度、位置接受率、草拟耗时和每有效 Token 成本设计可复现实验。
- 识别接受率高但草拟延迟过大、单请求加速但系统 Goodput 下降、验证批次膨胀导致显存压力等典型失败模式。
- 对「何时投机解码会加速」给出包含适用条件、证据、风险和回滚的工程答案。

## 3. 前置知识与实验环境

需要理解自回归生成、Tokenizer、Prefill、Decode、KV Cache、批处理和分位延迟的基本含义。涉及职责边界时，所有缩写都会在正文首次出现处定义；没有某个特定框架经验不妨碍理解机制。实验需要 Python 3.11 或兼容版本。机制模拟只依赖 CPU；真实路径需要任意可用的 CUDA GPU、与驱动兼容的 PyTorch，以及自行准备的本地小模型或兼容制品。

验证前必须记录 GPU 名称、数量、可用显存、驱动、CUDA、PyTorch、推理框架、模型摘要、精度、批量、序列长度和完整命令。脚本根据可用显存缩放模型、批量、上下文和样本数，并把职责边界状态写入报告；可选 CUDA 入口不下载未经确认的大模型。

评审记录还应包含模型修订、长度分布、到达过程、并发、采样、缓存、平均接受长度定义、服务等级和硬件；随后才能比较「是否启用 Speculator」和「选择候选深度」。缺少这些信息时，局部速度无法换算成系统收益。

## 4. 一轮时间的记账口径

### 4.1 四段分解与单位有效 Token 时间

设一轮提出 $K$ 个候选，平均提交 $A$ 个 Token，把一轮时间拆成四段：

$$T_{round}=T_{draft}(K)+T_{prepare}(K)+T_{verify}(K)+T_{commit}(K)$$

则单位有效 Token 时间近似为：

$$T_{effective}=\frac{T_{round}}{E[A]}$$

真正追求的是 $\min T_{effective}$，而不是单独最大化 $E[A]$。四段分解的价值在于把「准备候选形状、构造 mask、提交与回退」这些容易被忽略的主机工作单独记账，它们经常是草拟深度增大后最先暴露的成本。

### 4.2 采样与同步单列的性能模型

工程分析中常用另一种口径，把采样与同步显式列出：

$$T_{round}=T_{draft}(k)+T_{verify}(k)+T_{sample}+T_{sync}$$

$$R_{eff}=\frac{E[A+1]}{T_{round}}$$

两个式子并不矛盾，差别只在 $A$ 的定义：

- 若 $A$ 表示「一轮实际提交的 Token 数」（已含验证全接受时目标模型额外产出的 Bonus Token），则用 $T_{effective}=T_{round}/E[A]$。
- 若 $A$ 表示「被接受的草稿 Token 数」，则提交数为 $A+1$，有效速率为 $R_{eff}=E[A+1]/T_{round}$。

口径混用会让同一份数据算出相差一个 Token 的结论，在 $K$ 较小时误差尤其明显。报告中必须写明 $A$ 的定义、时间单位、统计窗口和分母。

式中职责边界与候选深度是可调因素，负载、模型和硬件组成适用条件，观测端记录平均接受长度、验证耗时及每有效 Token 成本。这是一种工程近似：关系式可以预测方向变化，无法替代真实运行时测量。调度、Kernel 启动、内存分配、网络传输、客户端行为和取消传播均可能改变关键路径。若实测与推演相反，先补充这些变量并核对口径。

### 4.3 一个常见反例：接受长度更高反而更慢

方案 A：

- accepted length = 5；
- draft = 10 ms；
- verify + others = 5 ms。

$$T_{effective}=15/5=3\ \mathrm{ms/token}$$

方案 B：

- accepted length = 4；
- draft = 2 ms；
- verify + others = 5 ms。

$$T_{effective}=7/4=1.75\ \mathrm{ms/token}$$

方案 B 的 acceptance 更低，却可能更快。原因是草拟成本进入分子，而接受长度只进入分母；当草拟路径本身成为最长阶段时，继续提高接受长度的边际收益会被草拟耗时吃掉。

### 4.4 期望接受长度的推导

若假设各位置接受事件独立且接受概率同为 $p$，则被接受的草稿数期望为等比数列求和：

$$E[A]=\sum_{i=1}^{K}p^{i}=\frac{p\,(1-p^{K})}{1-p},\qquad E[A+1]=\frac{1-p^{K+1}}{1-p}$$

代入不同 $p$ 与 $K$（推导值，非实测）：

| 位置接受率 $p$ | $K=1$ | $K=2$ | $K=4$ | $K=8$ |
| --- | --- | --- | --- | --- |
| 0.6 | 1.60 | 1.96 | 2.31 | 2.47 |
| 0.7 | 1.70 | 2.19 | 2.77 | 3.20 |
| 0.8 | 1.80 | 2.44 | 3.36 | 4.33 |
| 0.9 | 1.90 | 2.71 | 4.10 | 6.13 |

这张表说明两件事：接受长度随 $K$ 增长但存在饱和上限 $1/(1-p)$；$p$ 越低，增大 $K$ 的收益越小。真实文本的位置接受率通常随位置下降，独立同分布假设只是上界直觉，实际必须用逐位置接受率测量，不能用一个平均 $p$ 外推长草拟深度。

### 4.5 最优草拟深度的推导

沿用方案 B 的成本结构，设每步草拟 $t_d=0.5$ ms（$K=4$ 时草拟共 2 ms），验证与采样同步合计 $T_{verify}+T_{sample}+T_{sync}=4+0.25K$ ms（$K=4$ 时为 5 ms），取 $p=0.8$。均为推导设定，非实测：

| 候选深度 $K$ | $T_{draft}$ | 验证等 | $T_{round}$ | $E[A+1]$ | $T_{effective}$ |
| --- | --- | --- | --- | --- | --- |
| 1 | 0.5 ms | 4.25 ms | 4.75 ms | 1.80 | 2.64 ms |
| 2 | 1.0 ms | 4.50 ms | 5.50 ms | 2.44 | 2.25 ms |
| 4 | 2.0 ms | 5.00 ms | 7.00 ms | 3.36 | 2.08 ms |
| 8 | 4.0 ms | 6.00 ms | 10.00 ms | 4.33 | 2.31 ms |
| 16 | 8.0 ms | 8.00 ms | 16.00 ms | 4.89 | 3.27 ms |

在这组假设下最优深度为 $K=4$，$T_{effective}\approx2.08$ ms；不启用投机时每个 Token 需要 $4.25$ ms，加速比约 $4.25/2.08\approx2.04$ 倍。深度继续增大反而变慢，因为草拟串行成本线性增长而接受长度趋于饱和。改变 $t_d$、验证增量成本或 $p$，最优点会移动——这正是「批处理形状变化会移动最优草拟深度」的定量表达。

## 5. 八个必须一起记账的对象

需要纳入同一证据链的对象包括：Draft Model 与 Target Model 的职责边界、候选 Token 块与草拟深度、接受长度与接受率、并行验证与 Bonus Token、采样一致性与分布校正、低并发关键路径、高并发 Verifier Capacity、工作负载分布与批处理。它们并不处在同一个组件中，却会一起改变 Goodput 和每有效 Token 成本。

### 5.1 统一的五个检查问题

每个对象都按同一组问题展开，避免只记录成功路径：

1. **边界与生命周期**：接收什么、产生什么、由谁维护、状态何时结束；输入从哪里来，输出交给谁，失败如何传播。交界处可能增加等待、计算或复制。
2. **资源账**：计算量、显存占用、内存流量、主机工作和等待时间分别记账。某一阶段变短时，被遮蔽的成本可能随即暴露；平均 GPU 利用率只作为辅助信号。
3. **负载区间**：低载、接近饱和、过载三段保留同口径证据，覆盖长短输入、不同输出、并发、突发、采样与任务域。固定长度与固定批量的结果用于解释机制，不承担完整容量结论。
4. **正确性门禁**：Token 序列、采样分布、结构合法性、结束原因和错误传播都要对账。质量结果优先于速度数字；门禁失败即停止发布并切回已验证配置，保留问题请求用于复现。
5. **观测字段**：请求身份、模型版本、策略版本、起止时间、阶段耗时、资源快照与失败原因。跨对象传递的数据必须携带版本身份，否则请求时间线会混入旧配置。

### 5.2 Draft Model 与 Target Model 的职责边界

职责边界决定谁持有草拟状态、谁持有验证状态、hidden states 是否需要跨模型传递。Target 一次前向能够并行验证多个候选位置会移动关键路径，却很少让所有资源同比例变化：请求事件负责说明顺序，资源曲线负责解释瓶颈转移。

选择独立或共享 Drafter 是否合适，取决于所面对的长度分布、并发、到达过程、采样和任务域。典型失败是采样参数不一致破坏分布正确性——此时性能数字再好也不能发布。观测端 TTFT 没有单位、统计窗口和分母时不参与决策。

### 5.3 候选 Token 块与草拟深度

候选块的生命周期需要落到组件接口，并与接受长度、接受率绑定身份和版本。拒绝位置会截断本轮收益并触发回退采样，其影响分散到计算、显存、内存带宽、主机处理和同步等待。为确认变化来自哪里，应对齐请求时间线与资源采样，而非只看整段运行的 GPU 平均值。

边际价值随输入长度、输出长度、并发、流量突发、采样和任务域变化。典型失败是短输出没有足够轮次摊销启动成本：请求只生成十几个 Token 时，草拟器加载、图捕获与预热的固定开销无法被摊薄。逐 Token 延迟的定义（单位、窗口、分母）随报告存档。

### 5.4 接受长度与接受率

边界检查要覆盖输入、输出、状态归属和销毁时点；传给并行验证与 Bonus Token 的数据应附带模型或策略版本。资源账拆成计算、显存、内存带宽、主机开销和同步等待五项。

典型失败是高并发时草拟请求与正常 Decode 竞争验证容量：单请求看起来更快，系统排队却更长。因此需要设置动态禁用阈值，并保留低载、稳定高载和过载记录；容量判断不能从一次固定批量的短运行外推。另一类失败是指标只统计接受率而忽略端到端时间。Goodput 必须附带口径。

### 5.5 并行验证与 Bonus Token

边界由输入、输出、状态和拥有者共同确定；连接采样一致性与分布校正时还要传播身份和版本，避免把另一套配置的结果归到当前实验。测量时分别记录算力、显存、带宽、CPU 开销与同步。

典型失败是接受率由模型域、温度和上下文共同决定：同一 Speculator 在代码补全上接受率高，在开放创作上可能显著下降。发布门禁至少比较低载、临近容量与过载，结论只覆盖实际运行过的区间；接受率高但草拟延迟过大一旦出现，质量与端到端结果优先于速度数字。每有效 Token 成本同时注明单位、窗口和分母。

### 5.6 采样一致性与分布校正

投机解码必须保持目标分布不变，这依赖草拟与验证使用一致的采样参数与校正规则。围绕它建立资源模型时，同样把计算量、显存占用、内存流量、主机工作和等待时间单独记账。

典型失败是批处理形状变化会移动最优草拟深度：验证批次从 8 位置变成 64 位置后，原本合适的 $K$ 可能不再最优。是否启用 Speculator 取决于长度分布、并发、到达过程、采样和任务域；单请求加速但系统 Goodput 下降时，质量门禁应停止性能发布。平均接受长度没有单位、统计窗口和分母时不参与决策。

### 5.7 低并发关键路径

低并发下目标是最小化一个用户的 TPOT，关键路径由草拟串行深度、验证一次前向和同步开销组成。它与高并发 Verifier Capacity 之间的身份和版本若未绑定，请求时间线就可能混入旧配置。

典型失败是草拟路径随候选深度累积额外计算，以及验证批次膨胀导致显存压力。验证「选择候选深度」时分别运行低载、接近饱和与过载区间，并使用代表性分布；单一长度、批量或短窗口只能说明该测试点。位置接受率的定义随报告存档，包括单位、窗口和分母。

### 5.8 高并发 Verifier Capacity

高并发下验证容量是共享资源，边界检查要覆盖输入、输出、状态归属和销毁时点，传给工作负载分布与批处理的数据应附带版本。资源账同样拆成五项，Target 一次前向并行验证多个候选位置通常只先改变其中几项，其他资源随后可能进入关键路径。

选择独立或共享 Drafter 应覆盖长短输入、不同输出、并发、突发、采样与任务域。采样参数不一致破坏分布正确性会触发停止与回退，系统恢复到已有证据支持的配置。草拟耗时必须附带口径，否则上线后无法复核判断。定量分析见第 7 节。

### 5.9 工作负载分布与批处理

工作负载分布与批处理的边界由输入、输出、状态和拥有者共同确定；连接职责边界时要传播身份和版本。拒绝位置截断本轮收益并触发回退采样后，缩短的阶段可能让另一项资源成为瓶颈，因此分析要对齐阶段事件和资源轨迹，不让单个平均利用率代替因果证据。

评估需要把负载分布写入实验：输入输出长度、并发、到达突发、采样方式和业务域都可能移动收益边界。为交互与批处理请求分流时至少比较低载、临近容量与过载。短输出没有足够轮次摊销启动成本一旦出现，发布停止，流量回到已验证修订，相关请求留作重放。验证耗时同时注明单位、窗口和分母。

## 6. 四类新 Drafter 路线

### 6.1 Autoregressive Feature Drafter

代表路线：EAGLE 系列。优势是候选存在显式前缀依赖，通常有较好的 draft quality；缺点是需要逐步 rollout，草拟耗时随深度线性累积。

### 6.2 Parallel Multi-Token Drafter

代表：P-EAGLE、部分并行 MTP 路线。目标是一次预测多个未来位置，减少 Draft 串行深度。问题变成：不同位置的预测如果彼此缺少条件依赖，越靠后的 Token 置信度可能下降。

### 6.3 Native MTP

目标模型本身带未来 Token prediction heads/modules。它避免维护一个完整独立小模型，但部署与特定模型结构绑定，模型修订升级时需要同步验证预测头兼容性。

### 6.4 Block-Diffusion Drafter

代表：DFlash。把多个 mask 位置作为一个 block，在同一次或少量并行推断中产生整块草稿，再由目标 AR 模型验证。它把问题从「怎样更快地 rollout」改成「怎样在没有完整前缀依赖时保持候选质量」。

四条路线的共同点是都在重新分配 $T_{draft}$ 与 $E[A]$ 的比例：AR Feature Drafter 用串行深度换质量，Parallel 与 Block-Diffusion 用并行度换深度，Native MTP 用结构绑定换独立模型的维护成本。

## 7. 高并发：验证容量成为共享资源

离线单请求里，目标是最小化一个用户的 TPOT。在线高并发里，Target Verify 的额外候选也会占用 Token batch：

$$B_{verify}=\sum_i K_i$$

如果 64 个请求都一次验证 8 个候选，Verifier 这一轮要处理 512 个候选位置。即使每个请求 latency 下降，也可能挤压其他请求的计算预算。

反过来看同一份预算：若单轮可验证位置数为 512，$K=8$ 时最多容纳 64 个请求同批，$K=4$ 时可容纳 128 个（推导值，非实测）。草拟深度因此直接改变可并发驻留的请求数，而不只是改变单请求速度。

系统目标更接近：

$$\max \frac{AcceptedTokens}{GPUTime}$$

而不是：

$$\max\ AcceptedLength$$

这也是后面 DSpark「根据置信度和系统负载调整验证长度」的动机之一：低载时可以放长草拟深度追求单请求延迟，高载时应收缩深度以保住批处理容量与 Goodput。

## 8. Speculator 的五维评估法

| 维度 | 观察项 |
| --- | --- |
| Draft Quality | acceptance rate；mean accepted length；prefix survival probability |
| Draft Cost | forward pass 数；每次 forward 的 FLOPs；是否需要 Target hidden states；是否增加额外权重/KV |
| Verify Cost | 验证 Token 数；候选树节点数；attention mask 复杂度；高并发下的 batch occupancy |
| Memory / Deployment Cost | Speculator 权重；额外 cache/buffer；模型兼容性；checkpoint 管理 |
| Workload Fit | 代码、数学、模板文本、开放创作、长推理的可预测性差异 |

五维必须一起看：Draft Quality 高但 Draft Cost 也高，可能不如质量略低而成本极小的方案；Verify Cost 在低载不显眼，在高载直接决定容量。不存在一个 Speculator 对所有 workload 都固定最优。

## 9. 机制的因果分析

![投机解码的机制与证据闭环](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y3_l02_01.png)

*机制流程：把投机解码的输入、关键决策、执行与证据闭环连接起来。*

### 9.1 机制 1：草拟路径会随候选深度累积额外计算

分析时把前后两条请求时间线对齐，逐段标出可并行、必须串行和允许合批的工作。职责边界说明机制何时生效，平均接受长度负责确认关键路径是否真的缩短。

分别施加轻载、稳定高载和过载流量，可以分辨同步开销、队列增长、合批变化与资源竞争。检测到单请求加速但系统 Goodput 下降后，沿共享执行资源检查局部收益为何没有进入系统 Goodput。

确定接口时同时规定数据与 Shape、缓存和版本身份、错误及回退，随后以无效输入、极端长度和资源不足验证「选择独立或共享 Drafter」，使失败路径与成功路径拥有同样清晰的证据。观测时原因侧保存策略输入、阈值和候选集合，结果侧保存验证耗时、错误、取消与资源；两侧对齐后可以区分收益不足、选择错误、实现开销偏大和工作负载漂移。

该机制通过独立开关进入灰度，发布记录包含流量身份、停止阈值和可立即启用的回滚修订。出现短输出没有足够轮次摊销启动成本时撤回本项候选，随后核对在途请求、缓存状态与资源是否释放。

### 9.2 机制 2：Target 一次前向能够并行验证多个候选位置

请求执行后阶段边界和依赖关系会发生变化。先记录原路径，再记录候选路径中的串行、并行与合批段；同时保存候选 Token 块与草拟深度状态和位置接受率，便于把原因与结果关联起来。

容量评估把该机制放在三个负载区间中运行。固定开销通常在低载突出，队列和资源争用会在高载显现；验证批次膨胀导致显存压力意味着候选工作可能消耗了服务正常请求所需的容量。

实现时明确数据格式、张量形状、缓存身份、版本兼容和错误回退。执行「为交互与批处理请求分流」前冻结接口合同，并加入无效输入、极端长度与资源不足测试；成功样本之外的保护行为也属于验收范围。

Trace 同时记录决策输入与执行结果：前者含阈值和候选，后者含 TTFT、错误、取消和资源变化，这样能判断问题来自机制、选择器、实现成本还是流量变化。上线合同写明灰度范围、停止条件、开关和暖回滚目标；「指标只统计接受率而忽略端到端时间」发生后，系统恢复相关稳定配置，并持续观察请求排空、缓存切换和资源回收。

### 9.3 机制 3：拒绝位置会截断本轮收益并触发回退采样

理解这一机制要从请求关键路径入手。变化前后每个阶段的顺序、并行性和合批条件均需标注，接受长度与接受率作为启用条件，草拟耗时作为端到端结果。

一轮中第一个被拒绝的位置之后，所有后续候选都不再提交，本轮草拟成本却已经付出。因此位置接受率比平均接受率更能解释浪费：若拒绝集中在前几个位置，增大 $K$ 只会增加无效草拟；若拒绝集中在尾部，说明前缀质量尚可，可以考虑树形候选或收缩深度。

回退采样必须保证目标分布不变。拒绝后从校正分布重新采样，而不是直接取目标模型 argmax，否则在温度大于零时输出分布会被悄悄改变。验证这一点的方法是对同一提示与种子比较启用与关闭投机的输出分布，而不是只比较单次文本是否相同。

资源账上，回退采样增加主机侧分支与同步，拒绝率高时还会让验证批次的有效产出下降。观测需要同时记录草拟 Token、验证 Token、接受 Token 与浪费 Token 四类计数，只记录总 Token 数无法区分这四种情况。

### 9.4 机制 4：接受率由模型域、温度和上下文共同决定

同一 Speculator 在不同任务域上的接受率差异可能大于不同 Speculator 之间的差异。代码与模板文本的可预测性高，开放创作与长推理链的可预测性低；温度升高会放大目标分布的熵，使草拟分布更难匹配。

因此接受率必须按任务域、温度、上下文长度分桶报告，不能用一个全局平均值决定开关。分桶后常见的情形是：某些桶收益显著、某些桶为负，此时正确做法是按桶启用而不是全局启用或全局禁用。

上下文长度还会改变草拟成本结构：长上下文下 Drafter 自身的 KV 与 attention 成本上升，$t_d$ 不再是常数，第 4.5 节的线性假设需要按长度分段修正。

### 9.5 机制 5：批处理形状变化会移动最优草拟深度

验证批次的形状由并发数与各自 $K_i$ 共同决定。低并发时批次小，验证接近固定开销，放长 $K$ 有利；高并发时批次接近预算上限，$K$ 增大会挤掉其他请求的槽位，最优点向更小的 $K$ 移动。

这解释了为什么静态配置一个全局草拟深度很难同时满足交互与批处理负载。可行的工程做法是把深度作为调度器可调节的变量，依据当前批次占用、队列长度与位置接受率在线调整，并为调整设置迟滞与上下限，避免深度抖动带来的图重捕获与缓存失效。

## 10. 实验设计与双路径验证

### 10.1 机制模拟

CPU 模拟负责检验方向与边界：给定 $t_d$、验证成本函数、位置接受率序列、并发与到达过程，扫描 $K$ 并输出 $T_{round}$、$E[A+1]$、$T_{effective}$、验证位置占用与浪费 Token 比例。运行方式沿用统一约定：默认 Fixture，`--check-only` 只做预检，`--real` 进入实测路径。

模拟至少覆盖三类场景：低并发长输出（预期投机收益最大）、高并发混合长度（预期收益被验证容量抵消）、短输出（预期固定开销无法摊销）。验收不要求固定数字，而要求方向可解释：最优点随成本参数移动、高并发下收益收缩、短输出场景出现负收益。

模拟不能证明真实 Kernel 耗时、真实接受率分布和真实调度行为，这些必须留给实测。

### 10.2 真实 CUDA 路径

真实路径测量草拟与验证的实际耗时、显存占用与同步开销。预检记录 GPU 名称、数量、可用显存、驱动、CUDA、PyTorch、推理框架版本、模型修订或本地校验、精度和最终解析配置；显存不足时按约定缩小模型、批量、上下文与样本量，并给出可识别退出码。

测量至少记录：逐位置接受率、平均接受长度、草拟耗时、验证耗时、采样与同步耗时、每有效 Token 时间、峰值显存、错误与取消。每个配置先预热再测量，保留原始请求级记录以便重算分位数。只有 `source=measured` 可以支撑性能或发布结论，`source=fixture` 只验证控制逻辑。

比较基线与候选时只改变一个研究因素（例如只改 $K$，或只改 Drafter 路线），其余变量冻结。同时记录输出合同校验结果：Token 序列、采样分布、结构合法性、结束原因与错误传播。

### 10.3 结果解释

先检查实验是否有效，再比较性能：预热与测量分开、请求实际达到目标速率、客户端未成为瓶颈、错误与取消被计入、Token 口径一致。若实测与第 4 节推演相反，优先核对 $A$ 的定义、草拟耗时是否包含主机准备、验证耗时是否包含 mask 构造与同步。

结论只覆盖实际运行过的环境、模型修订与负载区间，并记录下一轮需要补证的范围。

## 11. 常见错误与排查

| 现象 | 可能原因 | 排查方向 |
| --- | --- | --- |
| 接受率很高但端到端没变快 | 草拟耗时进入分子，串行深度成为新关键路径 | 分段计时 $T_{draft}$/$T_{verify}$/$T_{sample}$/$T_{sync}$ |
| 单请求 TPOT 下降但系统 Goodput 下降 | 验证位置挤占批处理容量 | 统计 $B_{verify}=\sum_i K_i$ 与队列长度、按并发分桶 |
| 增大 $K$ 后显存 OOM | 验证批次膨胀、候选树节点与 mask 增大 | 记录峰值显存发生阶段，限制单轮验证位置预算 |
| 输出分布与关闭投机时不一致 | 采样参数不一致或回退未做分布校正 | 对齐温度/top-p/种子，检查拒绝后采样路径 |
| 短请求反而更慢 | 固定开销无法被足够轮次摊销 | 按输出长度分桶，设置最小输出长度启用阈值 |
| 平均接受长度看起来很好但尾延迟差 | 位置接受率随位置快速衰减 | 报告逐位置接受率与分位延迟，而非单一均值 |
| 不同任务域收益差异大 | 接受率由模型域、温度和上下文决定 | 按域/温度/上下文分桶，按桶启用 |
| 实测与模拟方向相反 | 口径不一致或漏记主机与同步成本 | 核对 $A$ 定义、时间单位、窗口与分母 |
| 换模型修订后收益消失 | Drafter 与 Target 版本未绑定 | 校验制品身份，重新训练或重新评测 |
| 灰度期间指标抖动 | 深度频繁调整导致图重捕获与缓存失效 | 为动态深度设置迟滞与上下限 |

## 12. 常见追问与解答

**问：接受率多高才值得启用投机解码？**
答：没有统一阈值。判据是 $T_{effective}$ 是否下降，以及在高并发下 Goodput 是否不降。接受率只是影响 $E[A+1]$ 的一个因素，草拟成本与验证容量同样进入判据。

**问：为什么 $E[A+1]$ 里要加 1？**
答：当一轮 $K$ 个候选全部被接受时，目标模型在同一次前向中还能额外产出一个 Bonus Token，因此提交数为 $A+1$。若把 $A$ 定义为已含 Bonus 的提交数，就不再加 1，两种口径不能混用。

**问：草拟深度是不是越大越好？**
答：不是。接受长度存在饱和上限 $1/(1-p)$，而 AR 草拟成本随深度线性增长，因此 $T_{effective}$ 存在最优点；高并发下验证容量约束会把最优点进一步推向更小的 $K$。

**问：独立 Drafter 和共享 Drafter 怎么选？**
答：取决于长度分布、并发、到达过程、采样和任务域。独立 Drafter 便于版本管理与隔离，但增加权重与显存；共享路线减少制品数量，却与目标模型结构绑定。两者都必须在三段负载下用同口径证据比较。

**问：投机解码会不会改变输出质量？**
答：正确实现不应改变目标分布。若拒绝后未做分布校正，或草拟与验证采样参数不一致，分布就会被改变。质量门禁优先于性能数字，出现不一致即停止发布并回退。

**问：为什么平均 GPU 利用率不能作为判据？**
答：利用率高可能是在处理被拒绝的候选或已取消请求。必须把草拟、验证、接受、浪费四类 Token 分开计数，再结合请求时间线判断有效工作。

**问：Native MTP 与独立 Drafter 的部署差别在哪？**
答：Native MTP 的预测头属于目标模型制品的一部分，模型升级即需要同步验证；独立 Drafter 可以单独发布与回滚，但需要维护两套制品的版本绑定关系。

**问：怎样把结论写成可上线的形式？**
答：给出适用条件（模型修订、负载区间、并发范围、温度与任务域）、证据（分段计时与分桶指标）、风险（显存、分布正确性、Goodput）和回滚入口（独立开关与已验证修订）。

## 13. 延伸练习

1. 用第 4.4 节公式计算 $p=0.75$、$K=1,2,4,8,16$ 时的 $E[A+1]$，并说明饱和上限。
2. 固定 $p=0.8$，把每步草拟成本从 0.5 ms 改为 0.2 ms 与 1.0 ms，重算第 4.5 节表格，观察最优深度如何移动。
3. 把验证成本函数改为 $4+0.5K$ ms，说明为什么最优点会前移。
4. 给定单轮验证位置预算 512，分别计算 $K=2,4,8,16$ 时可同批的请求数，并讨论对 KV 容量的影响。
5. 设计一个按输出长度分桶的启用阈值实验，说明如何避免短请求负收益。
6. 设计一个分布一致性校验：同一提示、同一温度、同一种子，比较启用与关闭投机的输出分布，写出判定标准。
7. 为动态草拟深度设计迟滞规则，说明上下限、调整周期与触发指标。
8. 把五维评估法填成一张具体 Speculator 的评估表，标出哪些项是推导值、哪些项待测。

## 14. 验收 Checklist

- [ ] 模型修订、Tokenizer、框架版本、CUDA 与驱动、GPU 型号数量、精度、并行策略全部记录。
- [ ] $A$ 的定义、时间单位、统计窗口与分母在报告中写明。
- [ ] 逐位置接受率与平均接受长度分别报告，并按任务域、温度、上下文分桶。
- [ ] 草拟、验证、采样、同步四段耗时分别可查。
- [ ] 草拟 Token、验证 Token、接受 Token、浪费 Token 四类计数齐全。
- [ ] 低载、接近饱和、过载三段使用同一口径证据。
- [ ] $B_{verify}$ 与队列长度、并发驻留请求数一并观测。
- [ ] 输出合同校验通过：Token 序列、采样分布、结构合法性、结束原因、错误传播。
- [ ] 峰值显存与 OOM 发生阶段被记录。
- [ ] 失败与前提失败状态可解释，退出码可识别。
- [ ] 客户端完成数与服务端完成数能够对账。
- [ ] 独立开关、停止阈值与可立即启用的回滚修订已就位。
- [ ] 撤回候选后核对在途请求、缓存状态与资源释放。
- [ ] 结论限定在实际证据覆盖的环境与负载区间，并列出待补证范围。

## 写在最后

经典投机解码的边界不在算法本身，而在「草拟成本、验证容量、接受长度」三者的比例关系，以及这个比例随负载与任务域的移动。把一轮时间拆成可记账的四段、把接受率拆成逐位置分布、把验证容量当成共享资源之后，后续各种新 Drafter 路线才有统一的比较口径。
