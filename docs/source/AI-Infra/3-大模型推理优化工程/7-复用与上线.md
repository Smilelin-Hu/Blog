# 复用与上线：Multi-LoRA、多模型、权重分发与冷启动

推理平台上有两类「贵」：贵的显存，和贵的时间。前者靠共享基座、热温冷分层与缓存解决；后者靠权重分发与冷启动优化压下来。

## 1. Multi-LoRA：一套基座，多个 Adapter

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y3_l19_01.png" width="78%" alt="Multi-LoRA serving" />
  <p>图 1：共享 Base，按请求挂载不同 Adapter</p>
</div>

### 1.1 显存账

朴素做法是每个定制模型一份副本：

$$
Memory_{naive} = N \cdot M_{base}
$$

Multi-LoRA 只保留一份基座：

$$
Memory_{multi} = M_{base} + \sum_{a \in resident} M_{adapter,a} + Runtime
$$

因为 Adapter 远小于 Base，节省巨大。但**不能无限加载**：adapter 本身占显存、metadata 与 kernel workspace 随数量增长，太多还会让 cache 抖动。

### 1.2 Adapter Registry

```text
adapter_id / base_model_revision / adapter_revision
rank·alpha·config / dtype / storage_uri / checksum / tenant / status
```

最重要的字段是 **`base_model_revision`**：同一个 Adapter 不能随便挂到不兼容的 Base revision 上。少了这个绑定，升级基座后会出现「能加载、但输出不对」的隐形故障。

### 1.3 三层缓存与淘汰

```text
Hot adapters   → GPU
Warm adapters  → CPU / local SSD
Cold adapters  → Object Storage
```

淘汰策略三种：LRU（时间局部性强）、LFU（热门集合稳定）、Cost-aware（考虑重新加载成本）：

$$
EvictScore(a) = f\left(\mathrm{Recency}, \mathrm{Frequency}, \mathrm{LoadCost}, \mathrm{Size}\right)
$$

大 Adapter 占空间多，但如果加载极慢且马上还会复用，**未必该先被淘汰**。

### 1.4 Adapter Load 会进 TTFT

```text
Request → Route → Adapter not resident → Download/Load/Materialize → Inference
```

$$
\mathrm{TTFT} = T_{queue} + T_{adapter\text{-}load} + T_{prefill}
$$

所以 Router 应该优先选已加载该 Adapter 的副本——但仍要与 queue cost 权衡（第 6 篇的 \(Score_i\) 就是干这个的）。

### 1.5 一个容易被低估的成本

同一批里出现多个 Adapter 时，Kernel 需要在多个权重之间切换：批内切换次数、adapter 权重搬运、以及「一个 Batch 里不同请求走不同 LoRA」带来的额外访存，都会让吞吐下降。Multi-LoRA 的容量规划必须按「同时活跃的 adapter 数」而不是「注册的 adapter 数」来算。

## 2. 多模型：热、温、冷

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y3_l20_01.png" width="78%" alt="Multi-model serving" />
  <p>图 2：少量共享容量承载稀疏流量</p>
</div>

### 2.1 为什么需要多路复用

20 个模型、每个至少 2 张 GPU 保高可用：

$$
GPU_{reserved} = 20 \times 2 = 40
$$

其中 15 个模型一天只有少量请求，GPU 大部分时间空闲。Multiplexing 用少量共享容量承载稀疏流量：

```text
Replica Pool
├─ 当前驻留 Model A
├─ 当前驻留 Model B
└─ 按需加载 Model C/D/...
```

### 2.2 三档状态

| 档位 | 状态 | SLO | 成本 |
|---|---|---|---|
| Hot | 常驻 GPU | 最好 | 最高 |
| Warm | 权重在本地 NVMe/Host cache | 中（需加载，不需下载） | 中 |
| Cold | 只在远程存储/Registry | 差（完整下载 + 初始化） | 低 |

状态会来回迁移：`Cold → Warm → Hot → Warm → Cold`。

### 2.3 热度模型

$$
Heat_m = \alpha\,ReqRate_m + \beta\,RecentRequests_m + \gamma\,BusinessPriority_m
$$

据此决定是否常驻、常驻几副本、是否预热、是否驱逐。**纯历史热度对突发不够**，要与事件（发布会、营销）和预测结合。

### 2.4 加载成本远不止文件大小

$$
T_{load} = T_{download} + T_{deserialize} + T_{H2D} + T_{runtime\text{-}init} + T_{warmup}
$$

同样 20 GB 权重，本地 NVMe 与网络对象存储、FP16 与量化、单文件与 shards、Runtime 是否要编译/Graph capture，启动时间能差好几倍。缓存策略要用**真实 load cost**，而不是文件名大小。

## 3. Model Registry 与部署生命周期

Registry 的核心不是「存文件」，而是**不可变修订**：权重、配置、Tokenizer、Chat Template、量化信息与校验和打包成一个制品，并给一个不可变 revision。

```text
register → verify(checksum/格式) → load 就绪 → 最小真实 Canary
        → 逐步放量 → drain 旧版本 → retire
```

三个不变量：

1. 逻辑模型名（alias）与不可变 revision 必须分开记录；
2. 没有通过真实路径 Canary 的 revision 不允许被路由；
3. 删除副本前必须停止接新请求并等待在途请求完成或迁移。

健康状态分三层：**进程存活 / 模型就绪 / 真实推理路径可用**——只有第一层通过就导流，是发布事故的经典来源。

## 4. 权重分发：启动的关键路径

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y3_l22_01.png" width="78%" alt="权重分发" />
  <p>图 3：下载、校验、反序列化、H2D、Runtime init、warmup 串成启动关键路径</p>
</div>

### 4.1 下载下限

$$
T_{download} \ge \frac{S}{B_{eff}}
$$

100 GB 模型、有效带宽 2 GB/s：**至少 50 秒**。这还没算连接建立、校验、解压、metadata、文件系统、反序列化与 H2D。

所以「秒级扩容」对大模型通常要靠提前缓存/预热，而不是临时从远端拉全量。

### 4.2 单文件 vs 多 Shard

- 单文件：metadata 少，但单流可能吃不满带宽，失败重试代价大；
- 多 Shard：可并行，\(T \approx \max_i T_{shard,i}\)，但 shard 太多会带来 list/stat、open/close、小文件开销与元数据压力。

最优 shard size 取决于存储系统，需要实测。

### 4.3 并发不是越多越快

$$
B_{total}(n) = \min\left(nB_{stream},\ B_{network},\ B_{storage},\ B_{disk}\right)
$$

超过瓶颈后再加并发只会增加连接数、抢带宽、制造抖动，还影响别的节点扩容。

### 4.4 惊群（Thundering Herd）

100 个副本同时下载 100 GB：

$$
TotalData = 10\ \mathrm{TB}
$$

即使单节点带宽足够，中央对象存储出口也会被打满。对策：节点本地缓存、机架内镜像、P2P 分发、预取、错峰 rollout、共享高吞吐文件系统。

## 5. 冷启动：三层 Warm 与经济性

### 5.1 三层

| 层级 | 状态 | 成本 |
|---|---|---|
| Node Warm | 镜像已拉、权重在本地 NVMe | 分钟级 |
| Process/Runtime Warm | 容器与进程已起，模型未 Ready | 数十秒 |
| Serving Warm | 模型已在 GPU、已完成 warmup | 立即可接 |

### 5.2 Warm Pool 是经济问题

$$
C_{idle} = N_w \cdot C_g,\qquad
E[C_{cold}] = P(\mathrm{Burst}) \cdot C_{miss}
$$

只有当 \(C_{idle} < E[C_{cold}]\) 时，保留 Warm Pool 才划算。**这不是纯性能结论，而是成本结论。**

### 5.3 预测式预热

流量有周期性时（8:50 预热、9:00 高峰），可以提前：拉镜像 → 拉模型 → 启动 worker → load → warmup → 注册 Ready。预测错误会增加 idle 成本，所以要按「预测准确率 × 违约成本」定策略。

### 5.4 组合拳

```text
最冷：remote model → node → GPU
本地缓存：node NVMe → GPU
Warm pool：model 已在 GPU → 直接路由
```

多数平台三层同时存在：平时靠本地缓存把「冷启动」压成「温启动」，峰值前靠预热把「温启动」变成「秒级」，突发时靠 warm pool 兜底。

## 6. 一个模型上线的完整关键路径

```text
调度 → 镜像拉取 → 权重下载/校验 → H2D → Runtime init → warmup → 注册 Ready → 导流
```

每一段都要能被单独度量，否则「启动慢」会变成一个无法归因的黑箱。经验做法：给每段打 NVTX 或埋点，把冷启动拆成可比较的柱状图——优化哪一段，用数据说话。
