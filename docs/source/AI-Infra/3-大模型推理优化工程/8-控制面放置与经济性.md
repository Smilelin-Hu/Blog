# 控制面、放置与运营：从单个副本到 GPU Fleet

单副本优化决定「一台机器多快」，控制面决定「整池机器有多少有效容量」。这一篇把控制循环、异构放置、装箱、扩缩容、容量规划与单位经济连起来。

## 1. 控制面：Desired State 与 Observed State

```text
Desired:  min=2  max=16
Observed: READY=2  LOADING=1  FAILED=1
Action = Reconcile(Desired, Observed)
```

持续把期望收敛为实际，比写一次性部署脚本可靠，因为故障与资源变化是持续的。

通用控制循环：

```text
Observe → Decide → Act → Wait/Measure → (回到 Observe)
```

**核心难点是 Action 有延迟**：大模型冷启动很慢，控制器不能假设「扩容命令发出后容量立刻出现」。所以必须把 Loading Pending 计入决策，并给控制器加冷却时间。

三种控制面的抽象差异：

| 方案 | 定位 | 适合 |
|---|---|---|
| Ray Serve | 应用级分布式 Serving（Deployment / Replica / Handle / autoscaling / multiplexing） | LLM 与 Python 服务、DAG 组合 |
| KServe | K8s-native 模型服务控制面（声明式） | 多团队、标准交付 |
| Dynamo | 面向 LLM 推理的分布式编排（路由 + KV 感知） | 大规模 LLM 平台 |

关键不是背 API，而是理解「它如何把模型服务变成可扩缩的 Deployment/Replica」。

## 2. 异构放置：能力、拓扑与隔离

三层约束：

1. **设备能力**：显存、算力、精度支持（FP8/FP4）、NVLink 与否——不是所有卡都能跑同一个配置；
2. **拓扑亲和**：TP 必须落在同一 NVLink 域；EP 要在超节点内；PP/DP 才允许跨机；
3. **隔离与配额**：MIG/时间片、租户配额、GPU 型号混部带来的性能差异。

异构池的价值是成本：小模型跑在老卡、大模型跑在新卡；风险是一致性：同一 alias 落到不同型号会得到不同 TTFT/TPOT，SLO 需要用**分型号的容量曲线**来算。

## 3. 装箱：并行组是不可分割的单位

一个 TP=8 的副本需要 8 张同节点 GPU，不能拆成 4+4。于是装箱问题变成「按组装箱」：

$$
\text{Group} = \text{TP} \times \text{PP}, \qquad
\text{DP 副本数} = \left\lfloor \frac{\text{可用组数}}{\text{每副本组数}} \right\rfloor
$$

常见碎片来源：节点剩余 7 卡但需要 8 卡组；跨代混插；大模型与小模型混部。

三种做法：首次适应（简单，碎片多）、最佳适应（省空间，易留小洞）、**按拓扑分层的 bin packing**（先按机架/节点分组，再在组内装）。评估指标不是「利用率」，而是**可用组数与碎片分布**。

## 4. 自动扩缩容：容量曲线 + 队列工作 + SLO

### 4.1 副本容量不是固定 QPS

```text
短输入短输出 → 20 req/s
长 reasoning → 2 req/s
```

所以容量应写成 workload-conditioned：

$$
\mu = f\left(\mathrm{ISL}, \mathrm{OSL}, \mathrm{Concurrency}, \mathrm{CacheHit}, \mathrm{Speculation}, \mathrm{Hardware}\right)
$$

需要靠 profile 得到服务曲线，而不是套一个固定阈值。

### 4.2 队列工作不是请求数

$$
W_q = \sum_{r \in queue} EstimatedWork(r),\qquad
EstimatedWork = \alpha\,InputTokens + \beta\,ExpectedOutputTokens
$$

控制目标：

$$
\frac{W_q}{Capacity_{ready}} < Target
$$

### 4.3 SLA-aware 反推

若要求 TTFT P99 < 1 s，则 \(QueueDelay + ServiceTime \le SLO\)，据此反推：

$$
N \ge \frac{PredictedWork}{CapacityPerReplica \cdot Window},\qquad
N_{target} = \left\lceil N(1+h) \right\rceil
$$

### 4.4 Pending capacity 必须计入

```text
目标 10：Ready 6 / Loading 3 / Pending 1
```

如果只看 Ready=6 就再扩 4 个，等它们全部就绪时会超配。正确做法：决策用 `Ready + Loading + Pending`，并用冷却窗口避免抖动。

## 5. 容量规划：预测、Headroom 与 Fleet

三件事：

1. **流量预测**：按业务日历、活动、增长趋势拆到「模型 × 区域 × 时段」；
2. **Headroom**：为突发、故障转移与长度误差留余量（常见 20%–30%，按 SLO 严格度调整）；
3. **Fleet 结构**：Hot（常驻）/ Warm（可秒级）/ Cold（需分钟级）三档容量比例。

一个常见错误是「按峰值留 100% 余量」，结果是低峰大量 idle；另一个极端是「完全按均值」，一次突发就雪崩。合理做法是用**排队模型 + 分型号容量曲线**算「在 SLO 内的最大负载」，再乘 headroom。

## 6. 可观测与可靠性

四类证据各有分工：

| 类型 | 回答 | 例子 |
|---|---|---|
| Trace | 一次请求卡在哪个阶段 | Gateway→Route→Queue→Prefill→Decode 各段耗时 |
| Metrics | 趋势与分布 | TTFT/P99、队列长度、KV 使用率、acceptance |
| Logs | 离散事实 | 加载失败、权重校验失败、超时 |
| Events | 状态变化 | 扩容、drain、canary 推进、驱逐 |

发布与故障的三件套：**Canary**（小流量验证真实路径）、**Drain**（摘流 → 等在途完成 → 释放）、**隔离**（坏节点/坏副本立即隔离，不参与路由）。演练要覆盖：副本崩溃、节点失联、共享存储变慢、权重下载失败。

## 7. 单位经济：从 GPU 忙到钱花得值

第一层：

$$
C_{infra} = N \cdot H \cdot C_g,\qquad
\mathrm{CostPer1MOutput} = \frac{C_{infra}}{T_{out}} \times 10^6
$$

但这只是开始。真正该算的是**有效 token**：

$$
Efficiency_{useful} = \frac{UsefulTokens}{ComputedTokens}
$$

无效 token 来自：投机被拒的候选、用户取消后继续生成、失败重试、warmup 合成请求、重复 Prefill、超时后没人消费的结果。

三类成本要一起看：

- **Idle cost**：\(C_{idle} = GPUHours_{idle}\cdot C_g\)——缩容越狠不一定越省，冷启动与 SLO 违约会反噬；
- **Cold start cost**：\(C_{cold} = C_{compute} + C_{bandwidth} + C_{SLO}\)，与 warm pool 的 idle cost 比较；
- **Speculation ROI**：

$$
ROI_{spec} = \frac{BaselineGPUTime - OptimizedGPUTime}{ExtraSpeculatorCost}
$$

更直接的口径是 **Cost per Accepted Token**，而不是「speedup ×」。

## 8. 一页图：从请求到 Fleet

```text
Gateway（身份/配额）
  → Router（负载 / 局部性 / ECT）
    → Replica Pool（Hot / Warm / Cold）
      → Engine（Prefill / Decode / KV）
        ↑ Controller：Observe → Decide → Act（含 Pending）
        ↑ Planner：容量曲线 + 队列工作 + SLO + Headroom
        ↑ Evidence：Trace / Metrics / Logs / Events
        ↑ Economics：有效 token / idle / cold start / ROI
```

每一层都能单独回答「我这一层的瓶颈是什么」，整条链路才能被优化——否则所有问题最后都会归结为一句「GPU 不够」。
