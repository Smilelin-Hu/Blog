# Structured Output Serving：Grammar、FSM 与 XGrammar

本文回答的问题是「约束解码如何保证结构合法，同时控制编译、缓存和逐步掩码成本？」。分析从 Grammar 与有限状态机 FSM 的关系开始，随后落到计算模型、实现路径和发布验收。Structured Output Serving 会同时受到工作负载、模型修订、运行时调度、显存容量、并发状态与服务等级约束，正文把相关机制还原成 Grammar 等可观察实体，再据此划定收益条件与额外成本。

证据分为机制模拟和真实 CUDA 测量两条路径。前者用可控变量观察 Grammar 怎样影响有限状态机 FSM，后者把框架、Kernel、内存和硬件成本计入结果。两条路径使用不同来源标签，并保留 Grammar 相关环境与限制；参数组合可以随版本改变，证据链仍要支持复现、定位和回退。

## 1. 内容概览

- Grammar、有限状态机 FSM 与 XGrammar 之间的状态与资源关系。
- 用 $T_{total}=T_{compile}(\text{cache miss})+\sum(T_{decode}+T_{mask})$ 与 $Net=RetrySaved-ConstraintOverhead$ 建立可计算的收益边界并解释全部变量。
- 围绕编译延迟、缓存命中率、每 Token 掩码延迟和重试节省设计可复现实验。
- 识别首次编译造成 TTFT 尖峰、缓存键忽略 Schema 版本和复杂递归导致状态爆炸等典型失败模式。
- 对中心问题给出包含适用条件、证据、风险和回滚的工程答案。

## 2. 核心直觉：不是「生成后修 JSON」，而是「非法 Token 根本不能被采样」

普通采样：

$$p(x)=\mathrm{softmax}(logits)$$

约束采样先构建合法集合 $A_s$，其中 $s$ 是 grammar 当前状态：

$$logits'_i=\begin{cases}logits_i,&i\in A_s\\-\infty,&i\notin A_s\end{cases}$$

再采样：

$$p'(x)=\mathrm{softmax}(logits')$$

因此生成路径始终满足 grammar。这与「生成完整 JSON 再解析修复」有本质区别：后者把合法性交给事后校验，失败就要重试整段输出；前者把合法性前移到每一步采样，**失败在 Token 级就被消除，而不是在请求级被补救**。

上一篇 Agentic Inference 已经量化过请求级重试的代价：整体重试把放大系数从 1.0525 抬到 1.5623，并可能触发 retry storm。约束解码正是从源头削减这类重试的手段，但它自身引入编译与掩码两项新成本，净收益必须显式计算（第 9 节）。

## 3. 前置知识与实验环境

需要理解自回归生成、Tokenizer、Prefill、Decode、KV Cache、批处理和分位延迟的基本含义，并已掌握前两篇建立的成本口径。涉及 Grammar 时所有缩写都会在正文首次出现处定义；没有某个特定框架经验不妨碍理解机制。实验需要 Python 3.11 或兼容版本。围绕 Grammar 的机制模拟只依赖 CPU；真实路径需要任意可用的 CUDA GPU、与驱动兼容的 PyTorch，以及自行准备的本地小模型或兼容制品。

验证 Grammar 前必须记录 GPU 名称、数量、可用显存、驱动、CUDA、PyTorch、推理框架、模型摘要、精度、批量、序列长度和完整命令。脚本根据可用显存缩放模型、批量、上下文和样本数，并把 Grammar 状态写入报告；可选 CUDA 入口不下载未经确认的大模型。

评估时先不要回答「打开以后能快多少」。需要固定模型与修订、输入输出长度分布、到达过程、并发、采样、缓存状态、编译延迟口径、服务等级和硬件环境，再评审「选择 JSON Schema 或 Grammar」和「缓存编译结果」。这些条件共同决定收益、成本和资源竞争。

## 4. 统一口径与成本模型

后续推导统一使用以下设定（推导设定，非实测）：

| 量 | 取值 | 说明 |
| --- | --- | --- |
| 词表大小 $\lvert V\rvert$ | 128000 | 主流开源模型量级 |
| 批内单请求 TPOT | 20 ms/token | 沿用前两篇，$B_{slot}=32$ |
| 摊销每 Token GPU 时间 $c_{tok}$ | 0.625 GPU-ms | $=20/32$ |
| 每请求固定开销 $F$ | 500 GPU-ms | Prefill + 调度 |
| 输出长度 $O$ | 300 Token | 工具参数典型长度 |
| Prefill wall-clock $T_{pre}$ | 100 ms | 输入 1000 Token |
| KV 每 Token | 128 KiB | 沿用前几篇口径 |
| GPU 单价 | \$2.40 / GPU-hour | $1$ GPU-ms $=6.667\times10^{-7}$ 美元 |
| CPU wall → GPU-ms 折算 | 1 ms = 1 GPU-ms | 沿用上一篇设定 |

总时间模型：

$$T_{total}=T_{compile}\cdot\mathbb{1}[\text{cache miss}]+\sum_{i=1}^{O}\left(T_{decode}+T_{mask}\right)$$

净收益模型：

$$Net=RetrySaved-ConstraintOverhead$$

其中 $RetrySaved$ 是「因为输出必然合法而省下的重试成本」，$ConstraintOverhead$ 是「摊销编译 + 逐步掩码 + 状态维护」。**约束解码不是无条件划算的优化，而是一笔需要算账的交易**：分子来自重试率，分母来自缓存命中率与掩码实现质量。

单请求成本与墙钟时间沿用前两篇：

$$C(O)=c_{tok}\,O+F,\qquad T(O)=T_{pre}+O\cdot TPOT$$

$O=300$ 时 $C=687.5$ GPU-ms、$T=6.1$ s。这个 687.5 就是「一次完整重试」的代价，后面所有收益都以它为单位。

## 5. Schema → Grammar → FSM → 词表映射

### 5.1 从 Schema 到状态机

例如 JSON Schema：

```text
object
├─ name: string
└─ age: integer
```

编译后可形成状态机：

![ai3-13-L87](https://raw.gitcode.com/weixin_42917352/image-host/raw/main/images/aiinfra_y3_l13_01.png)

这条链共 12 个状态（推导设定）。真实 tokenizer 不是字符级，因此还要把 grammar 允许的字符/字节序列映射为合法 token IDs。**这一步是 Structured Output 性能工程的关键**，也是编译成本的主要来源。

### 5.2 词表映射为什么不是单步转移

一个 token 往往对应多个字节（UTF-8 中文占 3 字节，常见英文词占 4～6 字节）。FSM 工作在字节级，因此判断「token $t$ 在状态 $s$ 是否合法」不是查一次转移表，而是：

$$\text{Allowed}(s,t)=\exists\ \text{路径}\ s\xrightarrow{bytes(t)}s'$$

即从 $s$ 出发能否消费完 $t$ 的全部字节。设平均每 token 3 字节、每次字节转移检查 50 ns，则单次判定约 150 ns（推导设定）。

由此得到编译期的朴素工作量：

$$Work_{compile}=|S|\times|V|\times150\ \text{ns}$$

| Schema 复杂度 | 状态数 $\lvert S\rvert$ | 朴素编译耗时 |
| --- | --- | --- |
| 扁平两字段 | 12 | 230.4 ms |
| 中等工具 schema（10 字段、2 层嵌套） | 200 | **3.84 s** |
| 深递归（深度 6、分支 4） | 4096 | 78.6 s |
| 深递归（深度 10、分支 4） | $1.05\times10^6$ | 5.6 h |

最后一行已经不只是慢：$1.05\times10^6$ 个状态各需一份 $\lvert V\rvert/8=16000$ B 的 bitset，合计 **16 GiB**，占 60 GiB KV 预算的 26.7%。这就是「复杂递归导致状态爆炸」的定量形态——它同时吃掉编译时间与显存。

### 5.3 三类状态的合法集合规模差异巨大

掩码成本不是常量，而强烈依赖当前状态类型（推导设定）：

| 状态类型 | 典型 $\lvert A_s\rvert$ | 占词表比例 | 掩码形态 |
| --- | --- | --- | --- |
| 结构态（等待 `{`、`,`、字段名、`:`） | 1～50 | $<0.04\%$ | 极稀疏 |
| 整数值态 | 10～15 | 0.01% | 极稀疏 |
| 枚举值态 | 枚举项数 | $<0.1\%$ | 极稀疏 |
| 字符串值态 | $\approx0.9\lvert V\rvert$ | 90% | 近稠密 |

**字符串值态是掩码成本的主要来源**：它几乎允许整个词表，稀疏表示反而更贵。因此实现必须按状态类型选择表示法（稀疏列表 vs bitset），而不是统一用一种。设一个 300 Token 的工具参数输出中字符串值占 70%、结构态占 30%，则 210 步走近稠密路径、90 步走极稀疏路径。

## 6. 编译成本：朴素全量与 trie 剪枝

### 6.1 三条编译路径

朴素全量遍历 $\lvert S\rvert\times\lvert V\rvert$ 的问题在于：绝大多数 (state, token) 组合根本不可达。用 token trie 做前缀剪枝，只遍历「从 $s$ 出发存在合法字节前缀」的 token 子树，可把有效检查数压到 $\alpha\lvert S\rvert\lvert V\rvert$。设剪枝率 $\alpha=2\%$（推导设定，结构态大多只允许极少前缀）：

| 编译路径 | 有效检查数（$\lvert S\rvert=200$） | $T_{compile}$ |
| --- | --- | --- |
| 朴素全量 | $2.56\times10^7$ | 3.84 s |
| trie 前缀剪枝（$\alpha=2\%$） | $5.12\times10^5$ | **76.8 ms** |
| 增量编译（复用已编译子自动机） | $\approx5\times10^4$ | 7.5 ms |

**50 倍的编译加速不是微优化，而是决定约束解码是否可用的分水岭**（第 9 节会给出盈亏平衡命中率的对比）。

### 6.2 编译产物应当常驻 GPU

编译产物包含每个状态的 allowed bitset。若只存在主机内存，每步都要 H2D 传输：

$$T_{H2D}=\frac{B\cdot|V|/8}{BW_{PCIe}}=\frac{32\times16000}{32\times10^9}=16.0\ \mu s$$

若编译期直接把 bitset 上传并常驻显存，每步只需传「状态索引」（$32\times4$ B $=128$ B），传输成本可忽略。显存代价为 $\lvert S\rvert\times16000$ B：$\lvert S\rvert=200$ 时 3.2 MiB，$\lvert S\rvert=4096$ 时 64 MiB（占 60 GiB 的 0.104%）。

因此缓存键必须包含 `BackendVersion`：编译产物的布局与设备驻留方式随后端版本变化，跨版本复用会读到错误格式。

### 6.3 编译期可达性检查

不可满足的 schema（如 `minLength > maxLength`、互斥的 `allOf`）会编译出「无出边状态」或「无法到达 END 的状态」。运行期表现为每步 $A_s=\varnothing$，请求挂死直到 `max_tokens`。

编译期做一次图可达性检查即可拦截，成本 $O(|S|+|E|)$，$\lvert S\rvert=200$ 时为微秒级。而运行期死锁的代价是 $O\cdot TPOT=300\times20=6$ s 的无效槽位占用，外加 $162.5$ MiB KV 被白占 6 s。**编译期检查比运行期死锁便宜约六个数量级**，没有理由不做。

## 7. 每步掩码成本：四条实现路径

### 7.1 成本拆分

每生成一个 token 需要：根据当前 FSM state 找 allowed set → 生成/应用 token mask → 采样 → 更新 state。故

$$T_{structured}=T_{model}+T_{mask}+T_{state}$$

其中

$$T_{mask}(B)=T_{lookup}(B)+T_{transfer}(B)+T_{apply}(B)$$

当模型很小、batch 很大或 token 很短时，CPU mask overhead 可能不再可忽略。

### 7.2 四条路径的定量对照

设 $B=32$、$\lvert V\rvert=128000$、HBM 带宽 2 TB/s、CPU 单核有效带宽 20 GB/s（推导设定）：

| 路径 | 每步工作量 | 每步耗时 | 相对 TPOT 20 ms |
| --- | --- | --- | --- |
| 朴素 CPU 逐 token FSM 检查（单核） | $32\times128000\times50$ ns | **204.8 ms** | **10.24×** |
| 同上，32 核并行 | $128000\times50$ ns | 6.4 ms | +32% |
| 预计算 bitset + 每步 H2D | 索引 3.2 µs + 传输 16.0 µs + apply 16.4 µs | 35.6 µs | +0.178% |
| **预计算 bitset 常驻 GPU** | 索引 3.2 µs + apply 16.4 µs | **19.6 µs** | **+0.098%** |

GPU apply 的推导：读 logits $B\lvert V\rvert\times4$ B $=16.384$ MB，写回同量，合计 32.77 MB，除以 2 TB/s 得 16.4 µs。

结论有两层：

1. **朴素实现是灾难性的**：单核路径让每步耗时变成 TPOT 的 10.24 倍，吞吐从 $32/0.020=1600$ Token/s 掉到 $32/0.2048=156$ Token/s（**−90.2%**）。即使 32 核并行也损失 24.2% 吞吐（$32/0.0264=1212$ Token/s）。
2. **优化后掩码几乎免费**：常驻 GPU 的 bitset 路径只增加 0.098% 的每步时间。所谓「约束解码拖慢生成」在正确实现下并不成立，成立的是「错误实现拖慢生成」。

高性能实现依赖的手段包括：稀疏 allowed set、precomputed transition、bitset、trie、batched mask kernel、backend-specific compiler。它们的共同点是**把每步的工作从「遍历词表」降为「查表 + 一次批量 apply」**。

### 7.3 掩码成本对净收益的影响

把每步掩码成本乘以 $O=300$，与第 9 节的重试节省对照（编译用 trie 剪枝、$h=86.1\%$）：

| 掩码实现 | 300 Token 合计 | $Net$（GPU-ms/请求） |
| --- | --- | --- |
| 朴素 CPU 单核 | 61440 ms | **−61343.9** |
| CPU 32 核并行 | 1920 ms | −1823.9 |
| bitset + 每步 H2D | 10.68 ms | +97.2 |
| bitset 常驻 GPU | 5.88 ms | **+102.0** |

**掩码实现的选择对净收益的影响远大于缓存命中率**：命中率从 50% 提到 99% 只改变几十 GPU-ms，而掩码路径选错直接改变几万 GPU-ms。排查顺序应当是先确认掩码路径，再优化缓存。

## 8. 编译缓存：键、容量与命中率

### 8.1 缓存键

如果大量请求使用同一个工具 schema：

```text
Tenant A: weather schema
Tenant B: weather schema
Tenant C: weather schema
```

可以使用 cache key：

$$Key=\mathrm{Hash}(NormalizedSchema,\ TokenizerRevision,\ BackendVersion)$$

而不是只 hash 原始字符串。原因：

- whitespace / 字段顺序可能不同但语义相同；
- tokenizer 变化会改变 token mapping；
- backend 编译格式可能升级。

三个分量各自对应一类静默错误：漏掉 `NormalizedSchema` 会让语义相同的 schema 重复编译（命中率虚低）；漏掉 `TokenizerRevision` 会在换 tokenizer 后复用错误映射（**合法 token 被拒**）；漏掉 `BackendVersion` 会在升级后读到不兼容的 bitset 布局（掩码错乱）。后两者不是性能问题而是正确性事故，因此「缓存键忽略 Schema 版本」必须列为发布阻断项。

### 8.2 容量与命中率

设中等 schema 的编译产物为 $\lvert S\rvert\times16000=3.2$ MiB，从 60 GiB KV 预算中划 1 GiB 给 grammar cache，则可容纳 $1024/3.2=320$ 个 schema（推导值，非实测）。

设平台共 1000 个不同 schema，访问呈重尾分布：top-20 承载 80% 请求，其余 980 个均匀分摊 20%。LRU 容量 320 时：

$$h=0.80+0.20\times\frac{320-20}{980}=0.80+0.20\times0.306=86.1\%$$

| 命中率 $h$ | $E[TTFT]$（trie 编译 76.8 ms） | $E[TTFT]$（朴素编译 3.84 s） |
| --- | --- | --- |
| 0% | 176.8 ms | 3940 ms |
| 50% | 138.4 ms | 2020 ms |
| 86.1% | 110.7 ms | 633.8 ms |
| 99% | 100.8 ms | 138.4 ms |
| 100% | 100 ms | 100 ms |

### 8.3 平均 TTFT 掩盖 P99 尖峰

关键洞察：**只要 miss 比例超过 1%，P99 TTFT 就等于一次完整编译**。

| $h$ | miss 比例 | $E[TTFT]$（朴素） | P99 TTFT（朴素） |
| --- | --- | --- | --- |
| 86.1% | 13.9% | 633.8 ms | **3940 ms** |
| 99% | 1% | 138.4 ms | **3940 ms** |
| 99.9% | 0.1% | 103.8 ms | 100 ms |

$h$ 从 86.1% 提到 99%，平均 TTFT 改善 4.6 倍，**P99 完全不变**。要让 P99 摆脱编译尖峰，必须 $h\ge99.9\%$，或者把编译移出请求关键路径（预热 / 异步编译 + 首次请求降级为无约束生成后校验）。

这解释了「首次编译造成 TTFT 尖峰」为什么是最常见的上线事故：离线评测通常反复用同一 schema（$h\approx100\%$），线上却持续有新 schema 涌入。**离线 TTFT 与线上 P99 TTFT 可以相差 39 倍，而两者的平均吞吐量看起来一样。**

### 8.4 LRU 会被一次性 schema 冲刷

设一次批量任务提交 500 个一次性 schema。LRU 容量 320，这批 schema 会把 top-20 热 schema 全部驱逐。批量任务结束后，后续热请求全部 miss，命中率从 86.1% 骤降到接近 0，直到热 schema 重新被加载。

因此缓存必须分池：

- **常驻池（pinned）**：工具 schema、系统 prompt 相关 schema，容量按 top-K 设定，不参与 LRU 驱逐；
- **流动池（LRU）**：租户临时 schema，容量受限，且**按租户隔离配额**，防止单租户冲刷全局。

设常驻池 64 个（204.8 MiB）、流动池 256 个（819.2 MiB），则上述批量任务最多冲刷流动池，top-20 热 schema 的命中率保持 100%，全局 $h$ 从 86.1% 只降到 $0.80+0.20\times0=80\%$（推导值）。**分池把命中率跌幅从 86.1 个百分点压到 6.1 个百分点。**

## 9. 净收益判据与盈亏平衡命中率

### 9.1 重试节省

设无约束时输出语法合法率 $p_{valid}=0.85$（推导设定，非实测），失败后最多重试 2 次，每次重试代价为完整重新生成 $C_{retry}=c_{tok}O+F=687.5$ GPU-ms。期望重试次数：

$$E[R]=p_f+p_f^2,\qquad p_f=1-p_{valid}$$

$$RetrySaved=E[R]\times687.5$$

$p_{valid}=0.85$ 时 $E[R]=0.15+0.0225=0.1725$，$RetrySaved=118.59$ GPU-ms/请求。

### 9.2 约束开销

$$ConstraintOverhead=(1-h)\cdot T_{compile}+O\cdot T_{mask}$$

取 trie 剪枝编译 76.8 ms、常驻 GPU 掩码 19.6 µs/步：$O\cdot T_{mask}=300\times0.0196=5.88$ ms。

### 9.3 盈亏平衡命中率

令 $Net=0$：

$$(1-h^*)=\frac{RetrySaved-O\cdot T_{mask}}{T_{compile}}\ \Longrightarrow\ h^*=1-\frac{RetrySaved-5.88}{T_{compile}}$$

| 编译实现 | $T_{compile}$ | $h^*$（$p_{valid}=0.85$） |
| --- | --- | --- |
| 朴素全量 | 3840 ms | **97.06%** |
| trie 剪枝 | 76.8 ms | 无解（全区间净赚） |
| 增量编译 | 7.5 ms | 无解（全区间净赚） |

朴素编译下 $(118.59-5.88)/3840=0.02935$，故 $h^*=97.06\%$——**命中率低于 97% 时约束解码反而更贵**。trie 剪枝下 $(118.59-5.88)/76.8=1.468>1$，意味着即使 $h=0$（每请求都编译）仍然净赚。

**编译优化把约束解码从「需要 97% 命中率才划算」变成「无条件划算」。** 这是本文最重要的工程结论：决定约束解码经济性的不是「要不要开」，而是「编译实现够不够快」。

### 9.4 净收益随命中率与合法率变化

$Net$（GPU-ms/请求，掩码固定为常驻 GPU 路径）：

| $p_{valid}$ | $RetrySaved$ | 朴素编译 $h$=50% | 朴素 $h$=86.1% | 朴素 $h$=99% | trie $h$=50% | trie $h$=86.1% | trie $h$=99% |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 0.95 | 36.09 | −1889.8 | −497.8 | −8.2 | −8.2 | +24.3 | +29.4 |
| 0.85 | 118.59 | −1807.3 | −421.1 | +74.3 | +74.3 | **+102.0** | +111.9 |
| 0.70 | 268.13 | −1657.8 | −271.5 | +223.9 | +223.9 | +251.6 | +261.5 |
| 0.60 | 385.00 | −1540.9 | −154.7 | +340.7 | +340.7 | +368.4 | +378.4 |
| 0.40 | 660.00 | −1265.9 | +120.3 | +615.7 | +615.7 | +643.4 | +653.4 |

规律：**模型越弱、schema 越复杂（$p_{valid}$ 越低），约束解码越划算**。$p_{valid}=0.95$ 时朴素编译几乎全区间亏损，$p_{valid}=0.40$ 时即使 $h=50\%$ 也净赚 120 GPU-ms。因此「是否开启约束解码」应当按模型能力与 schema 复杂度分档，而不是全局一个开关。

### 9.5 重试节省在长链路里被低估

上表只算了单请求重试。若重试触发的是整个 Agent 任务重试（上一篇口径 $Amp=1.5623$、10 步链路），则一次语法失败的实际代价是 $687.5\times1.5623\times$ 链路放大，远高于 687.5。此外重试还会推高 $\lambda_m$，在负载相关失败率下可能进入 retry storm。

因此 Agent 场景的 $RetrySaved$ 应当用**任务级**而非请求级口径重算，本文表格给出的是保守下界。

## 10. 状态爆炸与不可信 Schema 隔离

### 10.1 递归深度与状态数

递归 grammar 本质上是下推自动机而非有限状态机。若用 FSM 近似展开，状态数随深度指数增长：

$$|S|\approx b^d$$

设分支因子 $b=4$（推导设定）：

| 递归深度 $d$ | $\lvert S\rvert$ | bitset 显存 | 朴素编译 | trie 编译（$\alpha$=2%） |
| --- | --- | --- | --- | --- |
| 4 | 256 | 4 MiB | 4.92 s | 98.3 ms |
| 6 | 4096 | 64 MiB | 78.6 s | 1.57 s |
| 8 | 65536 | 1 GiB | 1258 s | 25.2 s |
| 10 | $1.05\times10^6$ | **16 GiB** | 5.6 h | 6.7 min |

深度从 6 到 10，状态数涨 256 倍、显存涨 256 倍。**「限制 Schema 复杂度」不是保守建议，而是显存与编译时间的硬约束。**

### 10.2 上限设定

建议三重上限（推导设定）：

| 上限 | 取值 | 依据 |
| --- | --- | --- |
| 状态数 $\lvert S\rvert_{max}$ | 4096 | bitset 64 MiB，占 60 GiB 的 0.104% |
| 递归深度 $d_{max}$ | 6 | 覆盖绝大多数业务嵌套需求 |
| 单 schema 编译超时 | 2 s | trie 路径下 4096 状态需 1.57 s，留 27% 余量 |

超限时的处置不是「硬编译」而是**降级**：改用「无约束生成 + 事后 JSON 校验 + 有限重试」，并把降级原因写进结束原因字段。降级路径的代价可用第 9 节公式反算：$p_{valid}=0.85$ 时多花 118.59 GPU-ms/请求，但避免了 16 GiB 显存占用与 6.7 min 编译阻塞。

### 10.3 编译是 DoS 面

多租户下租户可提交任意 schema，编译因此成为拒绝服务面。设编译线程池 4 个线程，正常 trie 编译 76.8 ms → 容量 $4/0.0768=52$ 编译/s。

一个 $\lvert S\rvert=1.05\times10^6$ 的恶意 schema 在朴素路径下需 5.6 h：

| 恶意并发数 | 占用线程 | 剩余编译容量 | 正常请求编译排队 |
| --- | --- | --- | --- |
| 1 | 1/4 | 39 编译/s（−25%） | 轻度 |
| 2 | 2/4 | 26 编译/s（−50%） | 明显 |
| 4 | 4/4 | **0** | **完全阻塞** |

因此「隔离不可信 Schema」必须落实为四件事：**状态数与深度上限、编译超时、每租户编译配额、编译在独立进程或沙箱中执行**。仅靠超时不够——超时前线程已被占用；仅靠配额不够——配额内的合法编译仍可能因状态数过大而吃满显存。

## 11. 结构合法 ≠ 语义合法

### 11.1 两层合法率

「只验证 JSON 语法却忽略业务语义」是 XGrammar 类后端最容易被误读的能力边界。grammar 保证的是**语法**合法，不保证字段值域、枚举归属、引用完整性等**语义**合法。

设语法合法率 $p_{syn}$、语义合法率（在语法合法条件下）$p_{sem}=0.90$（推导设定）：

| 方案 | $p_{syn}$ | 总体合法率 | $p_f$ | $E[R]$ | 重试成本 GPU-ms |
| --- | --- | --- | --- | --- | --- |
| 无约束 | 0.85 | 0.765 | 0.235 | 0.2902 | 199.53 |
| 仅语法 grammar | 1.00 | 0.900 | 0.100 | 0.1100 | 75.63 |
| 语法 + 枚举/值域编入 grammar | 1.00 | 0.980 | 0.020 | 0.0204 | 14.03 |

仅语法 grammar 的 $RetrySaved=199.53-75.63=123.90$ GPU-ms；把枚举与值域也编进去可再省 $75.63-14.03=61.60$ GPU-ms。

### 11.2 语义约束的编译代价

把 10 个字段各 10 个枚举编入 grammar，状态数从 200 涨到约 1200（6 倍，推导设定），trie 编译从 76.8 ms 涨到 460.8 ms，增量 384 ms。

额外净收益：

$$\Delta Net=61.60-384\times(1-h)$$

| $h$ | 额外编译摊销 | $\Delta Net$ |
| --- | --- | --- |
| 50% | 192.0 ms | **−130.4** |
| 84.0% | 61.4 ms | ≈0（盈亏平衡） |
| 86.1% | 53.4 ms | +8.2 |
| 99% | 3.8 ms | +57.8 |

盈亏平衡命中率 $h^*=1-61.60/384=83.96\%$。

结论：**语义约束是否编入 grammar 取决于命中率**。工具 schema 高度复用（$h\approx100\%$）时应当编入，可再省 57.8 GPU-ms/请求；租户临时 schema（$h<84\%$）时应当留在业务校验层，用一次轻量校验换编译成本。这也是「选择 JSON Schema 或 Grammar」决策的定量依据。

## 12. 受约束采样的顺序与空集死锁

### 12.1 掩码与采样参数的顺序

约束采样必须明确 mask 与 temperature / top-p / top-k 的先后。两种顺序的结果不同：

| 顺序 | 行为 | 风险 |
| --- | --- | --- |
| top-p → mask | 先按概率截断，再排除非法 token | **可能把合法集合整个截掉 → 空集** |
| **mask → temperature → top-p → sample** | 先在合法集合内重归一化，再截断 | 永不空集（除非 $A_s$ 本身为空） |

空集概率可估算：设 top-p=0.9 时平均保留 50 个 token，结构态占输出的 30%，结构态唯一合法 token 落在保留集外的概率 0.20（推导设定），则

$$P(\varnothing)=0.30\times0.20=6\%$$

**6% 的请求会在某个步骤陷入空集**。若实现把空集静默处理为「放开掩码」，则约束失效且不可察觉；若处理为「挂起等待」，则请求死锁。正确处置是立即终止并返回结构错误，同时记录 state 与 $A_s$ 便于复现。

### 12.2 空集死锁的代价

FSM 进入无出边状态后，每步 $A_s=\varnothing$。若实现选择「跳过掩码继续生成」，输出必然非法；若选择「重试采样直到合法」，则永远循环。设 `max_tokens=300`、TPOT=20 ms，请求会占用槽位 $300\times20=6$ s，KV $162.5$ MiB 被白占，且最终仍以失败告终。

因此必须有两道门禁：

1. **编译期**：可达性检查（第 6.3 节），拦截不可满足 schema；
2. **运行期**：$A_s=\varnothing$ 即刻终止，返回 `structural_error` 结束原因，不重试采样。

两道门禁缺一不可：编译期检查覆盖不了「schema 可满足但 tokenizer 映射遗漏」的情形，运行期终止则保证任何遗漏都不会演变成 6 s 的无效占用。

### 12.3 词表映射与 Tokenizer 修订脱钩

「Tokenizer 映射错误拒绝合法 Token」的根因通常是缓存键漏掉 `TokenizerRevision`。换 tokenizer 后旧 bitset 仍被命中，合法 token 被判非法，表现为**合法输出率骤降但编译延迟与命中率看起来完全正常**。

这类故障的隐蔽性在于：所有性能指标都健康，只有质量指标恶化。因此发布门禁必须把「合法输出率」与「语义合法率」作为一等指标，且**在 tokenizer 修订变更时强制清空 grammar cache**，而不是依赖键自然失效。

## 13. 与投机解码的组合

### 13.1 Drafter 不感知 grammar 的代价

Speculator 提出的候选也必须满足 grammar。如果 Drafter 不知道 grammar：

![ai3-13-L463](https://raw.gitcode.com/weixin_42917352/image-host/raw/main/images/aiinfra_y3_l13_02.png)

沿用前几篇口径：$T_V(B)=3+0.25B+0.01B^2$ ms、$T_O=0.3$ ms、$T_{draft}=1.40$ ms、AR 基线 3.56 ms/Token、$s_j=\prod_{i\le j}p_i$、$E[A]=\sum_{j\le B}s_j$、$C=E[A]+1$、$T_{eff}=T_{round}/C$。

设无约束时逐位置接受率 $p=0.85$；有约束但 Drafter 不感知时，结构态位置几乎必错（$p=0.10$），值位置仍为 0.85。按每 3 个位置含 1 个结构态排列（推导设定）：

| 位置 $j$ | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 无约束 $s_j$ | 0.850 | 0.7225 | 0.6141 | 0.5220 | 0.4437 | 0.3771 | 0.3206 | 0.2725 |
| 不感知约束 $s_j$ | 0.850 | 0.7225 | 0.0723 | 0.0614 | 0.0522 | 0.0052 | 0.0044 | 0.0038 |

第 3 个位置一旦落到结构态，$s_3$ 从 0.6141 崩到 0.0723（**−88.2%**），后续位置全部被前缀性质拖垮。

### 13.2 四种方案的对照

$T_{round}=T_{draft}+T_V(B)+T_O$，结果如下（推导值，非实测）：

| 方案 | $B$ | $E[A]$ | $C$ | $T_{round}$ ms | $T_{eff}$ ms | 相对无约束 |
| --- | --- | --- | --- | --- | --- | --- |
| 无约束（参照） | 4 | 2.7086 | 3.7086 | 5.860 | 1.580 | — |
| 无约束（参照） | 8 | 4.1226 | 5.1226 | 7.340 | **1.433** | — |
| 不感知约束 | 4 | 1.7062 | 2.7062 | 5.860 | 2.165 | +37.0% |
| 不感知约束 | 8 | 1.7718 | 2.7718 | 7.340 | 2.648 | **+84.8%** |
| 不感知约束 | 2 | 1.5725 | 2.5725 | 5.240 | 2.037 | +28.9% |
| **Drafter 也应用约束** | 4 | 2.7086 | 3.7086 | 5.938 | 1.601 | +1.3% |
| **Drafter 也应用约束** | 8 | 4.1226 | 5.1226 | 7.497 | **1.464** | **+2.2%** |

Drafter 应用约束后每步增加 19.6 µs 掩码成本，$B=8$ 时 $T_{draft}=1.40+8\times0.0196=1.557$ ms。

三条结论：

1. **Drafter 感知约束几乎完全恢复收益**：$B=8$ 时 $T_{eff}$ 从 2.648 降到 1.464（改善 44.7%），只比无约束慢 2.2%。掩码成本 0.157 ms 相对 7.34 ms 的轮次时间可忽略。
2. **不感知时最优 depth 从 8 掉到 2**：$B=2$ 的 2.037 优于 $B=4$ 的 2.165 优于 $B=8$ 的 2.648。这与前面 DSpark 一篇的负载感知 $K$ 选择同理——**约束强度改变了最优投机深度，静态配置必然失配**。
3. **Target verify 前快速过滤不能替代 Drafter 感知**：过滤在首个非法位置截断，有效 depth 退化为 2，但草拟仍花了 8 个位置的成本，$T_{round}$ 与直接降 depth 相同而 $T_{draft}$ 更高，严格劣于方案 4。过滤的价值只在于避免把非法候选送进验证 Kernel，不在于恢复接受率。

因此 structured workload 应当单独选择 Speculator 配置，并单独 Benchmark，不能沿用自由文本域的最优 $B$。

## 14. 与 Tool Calling / Agent 链路的关系

Agent 的工具调用通常要求固定 schema，因此 Structured Output 不是单纯「格式美观」，而是 Agent Runtime 的协议边界：

![ai3-13-L506](https://raw.gitcode.com/weixin_42917352/image-host/raw/main/images/aiinfra_y3_l13_03.png)

非法参数会直接变成失败/retry，引发更高总成本。

工具 schema 的一个天然优势是**高度复用**：设 Agent 工具集 20 个 schema 全部常驻缓存，则 $h\approx100\%$，$Net=118.59-0-5.88=112.71$ GPU-ms/请求（推导值）。

按上一篇口径，一个任务含 6 次模型调用，其中 4 次 branch 调用带工具 schema，则每任务节省 $4\times112.71=450.8$ GPU-ms。该任务总 GPU 成本约 $9500\times0.625+15200\times0.20+6\times500=11977.5$ GPU-ms，故直接节省 **3.8%**。

但 3.8% 是保守下界。真正的价值在于：语法失败率从 15% 降到 0，意味着上一篇推导的 retry storm 正反馈少了一个触发源。设每步失败率 $p_f$ 中语法失败占一半，则 $p_f$ 从 0.05 降到 0.025，任务级失败率从 $1-0.95^{10}=0.4013$ 降到 $1-0.975^{10}=0.2237$，整体重试放大系数从 1.5623 降到 1.2735（**−18.5%**）。**约束解码对 Agent 链路的主要贡献是打断重试放大，而不是省下那 3.8% 的 Token 成本。**

## 15. 八个对象的边界与失败模式

分析范围由八个可观察概念组成：Grammar、有限状态机 FSM、XGrammar、Token Mask、Grammar 编译缓存、结构合法性、词表映射、受约束采样。算法层的变化会经运行时和平台层传到吞吐损失与重试节省。

### 15.1 统一检查框架

八个对象共用五问，避免逐个重复模板化叙述：

1. **边界与生命周期**：输入从哪里来、状态由谁持有、输出交给谁、何时销毁；跨组件传递是否携带模型与策略版本身份。
2. **资源账五项**：算力、显存、内存带宽、主机 CPU 开销、同步等待分别记账，不用单一平均 GPU 利用率代替因果证据。
3. **三段负载区间**：低载、临近容量、过载各保留同口径证据；固定长度与固定批量的结果只解释机制，不承担容量结论。
4. **正确性门禁**：Token 序列、采样分布、结构合法性、结束原因、错误传播五项对账；质量恶化优先于速度收益，触发即停止发布并回退到已验证修订。
5. **观测字段**：请求身份、模型与策略修订、起止时间、阶段耗时、资源快照、失败原因；每个指标附带单位、统计窗口与分母。

### 15.2 Grammar

边界是「schema 文本 → 规范化语法对象」，拥有者是编译前端，生命周期结束于编译产物入缓存。它向 FSM 传递的必须包含 `NormalizedSchema` 身份，否则字段顺序不同但语义相同的 schema 会被当成两个对象重复编译。

独有失败模式是**掩码处理成为 CPU 瓶颈**：grammar 本身正确，但每步遍历词表的实现让 CPU 成为关键路径（第 7.2 节单核 204.8 ms/步）。决策短语是「限制 Schema 复杂度」，对应指标为合法输出率与吞吐损失。

### 15.3 有限状态机 FSM

边界是「编译产物 → 每请求状态实例」，拥有者是调度器侧的 per-request 状态槽，生命周期与请求一致。状态实例必须与请求身份绑定，batch 内不同请求处于不同 state 是常态。

独有失败模式是**Tokenizer 映射错误拒绝合法 Token**：FSM 结构正确但字节到 token 的映射有误，表现为合法输出率骤降而性能指标全部健康。决策短语是「选择 CPU 或 GPU 掩码路径」，对应指标为 TTFT（必须带单位、窗口与分母）。

### 15.4 XGrammar

边界是「后端编译器接口」，输入 grammar 对象、输出设备可用的掩码表，拥有者是推理框架的 structured output 后端。它与 Token Mask 之间的版本身份若未绑定，请求时间线就会混入旧配置。

独有失败模式是**只验证 JSON 语法却忽略业务语义**：把后端能力误读为端到端合法性保证，导致语义错误流入工具执行器（第 11 节）。决策短语是「设置非法结构回退」，对应指标为吞吐损失。

### 15.5 Token Mask

边界是「state → allowed set → logits 修改」，拥有者是采样前置阶段，生命周期只有一个 Token。它传给编译缓存的查询必须附带模型与策略版本。

独有失败模式是**首次编译造成 TTFT 尖峰**：掩码本身廉价，但 cache miss 时的编译被计入首 Token 路径（第 8.3 节 P99 3940 ms）。决策短语是「隔离不可信 Schema」，对应指标为重试节省。

### 15.6 Grammar 编译缓存

边界是「Key → 编译产物」，拥有者是平台级缓存服务，生命周期跨请求且需分池管理。它向结构合法性校验传递产物时必须带 `BackendVersion`。

独有失败模式是**缓存键忽略 Schema 版本**：tokenizer 或后端升级后复用旧产物，掩码错乱且所有性能指标正常。决策短语是「选择 JSON Schema 或 Grammar」，对应指标为编译延迟与缓存命中率。

### 15.7 结构合法性

边界是「输出 Token 序列 → 合法/非法判定」，拥有者是输出校验层，生命周期结束于响应返回或重试触发。它与词表映射交互的字段必须携带版本身份。

独有失败模式是**复杂递归导致状态爆炸**：$\lvert S\rvert$ 指数增长吃满显存与编译时间（第 10.1 节深度 10 需 16 GiB）。决策短语是「缓存编译结果」，对应指标为缓存命中率。

### 15.8 词表映射

边界是「字节级 grammar → token 级 allowed set」，拥有者是编译期的映射阶段，产物随缓存驻留。它与受约束采样之间的身份若未绑定，采样就会用到错误映射。

独有失败模式是**多字节 Token 跨状态游走遗漏**：只检查首字节转移就判定合法，导致含中文或长英文词的合法输出被拒。资源账上它主要影响编译时间与掩码表内存，而非每步算力。

### 15.9 受约束采样

边界是「masked logits → 采样参数 → token」，拥有者是采样器，生命周期一个 Token。它是唯一直接决定输出分布的环节，因此顺序错误的影响是分布级而非性能级。

独有失败模式是**掩码与 top-p 顺序错误导致空集**：6% 的请求在某步陷入 $A_s=\varnothing$（第 12.1 节），静默放开掩码会让约束失效且不可察觉。指标为合法输出率与结束原因分布。

## 16. 六个机制的因果分析

### 16.1 每步 Token Mask 排除不合法候选

机制链条是「grammar state → allowed set → logits 掩码 → 采样必然合法」。它把合法性从请求级事后校验前移到 Token 级事前排除，因此重试率从 $p_f$ 降到接近 0。

但收益不是免费的：每步增加 $T_{mask}$，且实现路径决定这一项是 19.6 µs 还是 204.8 ms（相差 10449 倍）。资源账上它先增加主机 CPU 开销与同步等待，优化后才转为少量 HBM 带宽。

因此该机制的适用条件是「掩码实现已优化到查表 + 批量 apply」。在此条件下 $O\cdot T_{mask}=5.88$ ms 相对 $RetrySaved=118.59$ ms 可忽略；不满足时净收益为 −61343.9 GPU-ms，机制方向正确但实现不可用。

### 16.2 词表到语法终结符的映射影响编译与内存

机制链条是「字节级 FSM + 多字节 token → 逐 (state, token) 可达性判定 → 编译时间与 bitset 内存」。它解释了为什么编译成本与 $\lvert S\rvert\lvert V\rvert$ 成正比，而不是与 schema 文本长度成正比。

关键路径转移发生在两处：编译期从 CPU 算力转为 trie 剪枝效率；运行期从主机内存转为显存驻留容量。$\lvert S\rvert=4096$ 时 bitset 64 MiB 尚可接受，$\lvert S\rvert=10^6$ 时 16 GiB 直接挤占 KV 预算的 26.7%。

因此该机制给出的工程边界是状态数上限，而不是「schema 写简单点」这类无法执行的劝告。上限 4096 对应 0.104% 的 KV 预算占用，是可核算的取舍。

### 16.3 缓存复用能够摊销重复 Schema 编译

机制链条是「相同 Key 命中 → 跳过编译 → TTFT 回到 $T_{pre}$」。摊销效果为 $(1-h)T_{compile}$，因此命中率的边际价值与编译成本成正比。

这带来一个反直觉结论：**编译越慢，缓存越重要；编译足够快时缓存反而不再是关键**。朴素编译 3840 ms 下 $h^*=97.06\%$，trie 编译 76.8 ms 下全区间净赚。把工程 effort 投在编译优化上的回报高于投在缓存调优上。

但缓存仍不可省略，原因是 P99：只要 miss 比例 >1%，P99 TTFT 就等于一次完整编译。平均指标改善 4.6 倍而 P99 完全不变，这是缓存命中率最容易被误读的地方。

### 16.4 复杂递归结构扩大状态和分支

机制链条是「递归深度 $d$、分支因子 $b$ → $\lvert S\rvert\approx b^d$ → 编译时间与 bitset 内存指数增长」。它把「schema 复杂度」这一模糊概念变成可核算的显存与时间预算。

资源账上它同时压三项：编译 CPU 时间、掩码表显存、编译线程池占用。三者会互相放大——显存不足触发驱逐，驱逐降低命中率，命中率下降又增加编译次数，最终占满线程池。

因此该机制的处置必须是**入口限制 + 降级路径**，而不是运行期扩容。深度上限 6、状态上限 4096、编译超时 2 s，超限转「无约束生成 + 事后校验」，代价 118.59 GPU-ms/请求，远小于 16 GiB 显存与 6.7 min 阻塞。

### 16.5 约束减少无效重试但增加逐步处理

机制链条是「$p_f\downarrow$ → $RetrySaved\uparrow$；$T_{mask}\uparrow$ → $ConstraintOverhead\uparrow$」，净效果由 $Net=RetrySaved-ConstraintOverhead$ 决定。这是本文全部取舍的总公式。

它的负载依赖性体现在两端：$RetrySaved$ 随模型能力与 schema 复杂度变化（$p_{valid}$ 从 0.95 到 0.40，$RetrySaved$ 从 36.09 到 660.00），$ConstraintOverhead$ 随命中率与掩码实现变化（从 5.88 到 61440+）。**两端都可变，所以不存在全局最优开关。**

在 Agent 链路里该机制还有一层放大：重试不仅花 687.5 GPU-ms，还推高 $\lambda_m$ 并可能触发 retry storm。因此 $p_f$ 从 0.05 降到 0.025 带来的整体重试放大系数下降 18.5%，价值高于单请求节省。

### 16.6 语法约束被编译为可推进的状态机

机制链条是「schema → 自动机 → per-request state → 每步转移」。它使合法性判定变成 $O(1)$ 查表而非 $O(\lvert V\rvert)$ 遍历，是掩码成本从 204.8 ms 降到 19.6 µs 的根本原因。

但「可推进」是有条件的：状态必须有出边、必须能到达 END、必须与 tokenizer 映射一致。三者任一破坏都会导致空集死锁或合法 token 被拒，而这两类故障在性能指标上完全不可见。

因此该机制的正确性门禁必须独立于性能门禁：编译期可达性检查 + 运行期空集即终止 + tokenizer 修订变更强制清缓存。三道门禁覆盖的是「性能全绿但输出全错」这一最危险的象限。

## 17. 工程决策与取舍

### 17.1 选择 JSON Schema 或 Grammar

JSON Schema 表达力受限但状态少、编译快；自定义 Grammar（EBNF/GBNF）可描述递归与上下文相关约束，但状态爆炸风险高。判据是第 10.1 节的状态数表：需求若能落在 $\lvert S\rvert\le4096$ 内则两者皆可，超出则必须降级或拆分 schema。语义约束（枚举、值域）是否编入按第 11.2 节的 $h^*=83.96\%$ 判断。

### 17.2 缓存编译结果

必须缓存，且键为 $\mathrm{Hash}(NormalizedSchema,TokenizerRevision,BackendVersion)$。分常驻池与流动池，常驻池放工具 schema，流动池按租户配额隔离。目标不是平均命中率而是 **P99 不受编译影响**，即 $h\ge99.9\%$ 或把编译移出关键路径。

### 17.3 限制 Schema 复杂度

三重上限：$\lvert S\rvert\le4096$、$d\le6$、编译超时 2 s。超限降级为「无约束生成 + 事后校验 + 有限重试」，并记录降级原因。上限的依据是显存占比 0.104% 与 trie 编译 1.57 s，不是经验口诀。

### 17.4 选择 CPU 或 GPU 掩码路径

默认 GPU 路径 + bitset 常驻显存。CPU 路径只在 $\lvert V\rvert$ 很小或 batch 极小时考虑，且必须并行化——单核朴素路径损失 90.2% 吞吐。字符串值态走近稠密 bitset，结构态走稀疏列表，按状态类型分派而非统一表示。

### 17.5 设置非法结构回退

运行期 $A_s=\varnothing$ 即刻终止并返回 `structural_error`，不重试采样、不静默放开掩码。编译期做可达性检查拦截不可满足 schema。回退目标是已验证的 backend 修订，问题请求保留用于重放。

### 17.6 隔离不可信 Schema

四件事同时做：状态数与深度上限、编译超时、每租户编译配额、编译在独立进程或沙箱执行。仅靠超时不够（超时前线程已占用），仅靠配额不够（配额内仍可能吃满显存）。编译线程池被 4 个恶意 schema 占满即完全阻塞，这是可核算的 DoS 面。

- $h\ge99.9\%$ 或编译异步化后 P99 TTFT $\le1.1\times T_{pre}$；
- 语法合法率 100%，语义合法率按第 11.1 节分档记录；

## 20. 常见追问与解答

**问 1：约束解码一定比「生成后修 JSON」好吗？**
不一定。第 9.3 节给出判据：朴素编译下需 $h\ge97.06\%$ 才净赚，trie 剪枝下全区间净赚。若模型本身 $p_{valid}=0.95$ 且编译实现朴素，约束解码在 $h=86.1\%$ 时净亏 497.8 GPU-ms/请求，此时事后校验更划算。

**问 2：为什么掩码成本在不同实现下相差一万倍？**
因为工作量级不同。朴素路径每步做 $B\lvert V\rvert$ 次 FSM 查询（$32\times128000=4.1$M 次），优化路径每步做 $B$ 次查表加一次批量 apply（32 次 + 32.77 MB 内存流量）。前者是 $O(B\lvert V\rvert)$ 的 CPU 串行工作，后者是 $O(B)$ 索引 + $O(B\lvert V\rvert)$ 的 GPU 并行带宽工作，硬件与复杂度都不同。

**问 3：命中率从 86% 提到 99% 值得投入吗？**
对平均 TTFT 值得（朴素编译下 633.8→138.4 ms），对 P99 完全无效（两者都是 3940 ms）。若目标是 P99，必须做到 99.9% 或把编译移出关键路径；若目标是净收益，trie 编译下两者的 $Net$ 只差 9.9 GPU-ms，投入产出比很低。

**问 4：递归 schema 一定要拒绝吗？**
不是拒绝而是降级。深度 6 以内（$\lvert S\rvert\le4096$、64 MiB）可以正常编译；超出则转「无约束生成 + 事后校验」，代价 118.59 GPU-ms/请求。这比硬编译吃 16 GiB 显存并阻塞 6.7 min 好得多。

**问 5：约束解码和投机解码能同时开吗？**
能，但 Drafter 必须感知 grammar。第 13.2 节显示不感知时 $B=8$ 的 $T_{eff}$ 从 1.433 恶化到 2.648 ms（+84.8%），感知后回到 1.464 ms（+2.2%）。若无法让 Drafter 感知，则应把 depth 降到 2（2.037 ms），而不是维持大 depth。

**问 6：为什么语义约束不全部编进 grammar？**
因为编译成本随状态数线性增长。第 11.2 节算出盈亏平衡命中率 83.96%：工具 schema 高度复用时编入可再省 57.8 GPU-ms/请求，租户临时 schema 命中率低时编入反而净亏 130.4 GPU-ms。应当按 schema 复用度分档。

**问 7：空集发生时为什么不重试采样？**
因为 $A_s=\varnothing$ 是状态级事实，不是采样随机性导致的。重采样不会改变 allowed set，只会无限循环。正确处置是立即终止并返回 `structural_error`，同时记录 state 供编译期修复。

**问 8：多租户下怎么防止编译被滥用？**
四件事同时做：状态数与深度上限、编译超时、每租户编译配额、独立进程或沙箱。第 10.3 节量化了后果——4 个恶意 schema 可占满 4 线程池使正常编译容量归零。单靠任何一项都不够。

3. 推导常驻池容量 $K$ 与全局命中率的关系式，假设 top-$K$ 承载流量比例 $f(K)$，求使 $h\ge99.9\%$ 的最小 $K$。
4. 把第 11.2 节的语义约束扩展到 20 字段各 50 枚举，重算 $\lvert S\rvert$、编译增量与盈亏平衡命中率。
5. 设 Drafter 感知约束后掩码成本升到 0.2 ms/步（而非 19.6 µs），重算第 13.2 节 $B$=4/8 的 $T_{eff}$，判断是否仍优于降 depth 到 2。
6. 推导「异步编译 + 首请求降级」策略的净收益表达式，并与同步编译在 $h$=86.1% 时对比，给出异步化划算的条件。
7. 设 retry storm 场景（上一篇 $p_f$ 负载相关式），把语法失败从 $p_f$ 中移除，重算四次迭代的 $\lambda$ 轨迹，判断是否仍发散。
8. 为「编译产物跨设备迁移」设计缓存键扩展，说明需要增加哪些分量，以及不增加时会出现什么静默错误。

## 22. 验收 Checklist

- [ ] 缓存键包含 `NormalizedSchema`、`TokenizerRevision`、`BackendVersion` 三个分量。
- [ ] Schema 规范化覆盖字段顺序与空白差异，语义等价类只编译一次。
- [ ] 编译路径为 trie 剪枝或增量，实测 $T_{compile}$ 与 $\lvert S\rvert$ 的关系已记录。
- [ ] 编译产物 bitset 常驻显存，每步只传状态索引。
- [ ] 掩码按状态类型分派：结构态稀疏列表、字符串态 bitset。
- [ ] 每步掩码延迟按状态类型分桶上报，单位 µs。
- [ ] 编译期可达性检查已启用，不可满足 schema 在 parse 阶段被拒。
- [ ] 运行期 $A_s=\varnothing$ 即刻终止并返回 `structural_error`，不重试采样。
- [ ] 采样顺序固定为 mask → temperature → top-p/top-k → sample。
- [ ] 状态数上限 4096、递归深度上限 6、编译超时 2 s 三项均已配置。
- [ ] 超限 schema 走降级路径并记录降级原因，无一例硬编译。
- [ ] 缓存分常驻池与流动池，常驻池 pinned 不参与 LRU 驱逐。
- [ ] 流动池按租户配额隔离，单租户无法冲刷全局热 schema。
- [ ] tokenizer 修订变更时强制清空 grammar cache。
- [ ] TTFT 按 hit/miss 分列上报，P99 单独设门禁。
- [ ] 语法合法率与语义合法率分列统计，语义校验层已就位。
- [ ] 投机解码场景下 Drafter 感知 grammar，或 depth 已按约束强度下调。
- [ ] $Net$ 按任务级口径计算，注明 $p_{valid}$、$h$、编译与掩码实现。
- [ ] 编译线程池配额、超时与沙箱隔离三项均已落实，恶意并发 4 个时容量下降 $\le25\%$。

## 写在最后

约束解码把「输出是否合法」从概率问题变成结构问题，代价是编译与掩码两项新成本。本文的核心判据是 $Net=RetrySaved-ConstraintOverhead$：编译实现决定它是否无条件划算，掩码实现决定它是否会灾难性亏损，缓存命中率决定 P99 而非平均值，schema 复杂度上限决定显存与编译线程池是否安全。四者缺一，约束解码就会从优化变成事故。
