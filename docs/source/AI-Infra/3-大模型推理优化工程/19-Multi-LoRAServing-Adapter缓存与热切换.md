# Multi-LoRA Serving：Adapter 缓存与热切换

## 1. 课程定位

本文把 Multi-LoRA Serving：Adapter 缓存与热切换放回真实请求链路中讨论，中心问题为“如何在共享基座模型上多路复用 Adapter，并控制加载抖动和版本一致性？”。LoRA Adapter 和共享基座模型提供分析入口，计算模型负责说明方向，实验和发布门禁负责限定结论。评审时需要同时查看模型版本、负载、调度、显存、并发与服务等级，避免把 LoRA Adapter 的局部理想收益直接当成端到端结果。

本文先用 CPU 模拟控制 LoRA Adapter 和共享基座模型，再用真实 CUDA 路径检查这些关系进入实现后增加了哪些成本。每份结果都要标明数据来源、运行环境和适用边界。这样得到的是可复查的工程判断，而非依赖某个框架版本的参数口诀。

## 2. 学习目标

3. 围绕 Adapter 命中率、加载延迟、切换延迟和每 Adapter 成本设计可复现实验。
4. 识别 Adapter 与基座版本不兼容、高基数流量导致加载抖动和不同 Adapter 请求无法有效合批等典型失败模式。
5. 对“如何在共享基座模型上多路复用 Adapter，并控制加载抖动和版本一致性？”给出包含适用条件、证据、风险和回滚的工程答案。

## 3. 前置知识与环境

阅读 Multi-LoRA Serving：Adapter 缓存与热切换需要理解自回归生成、Tokenizer、Prefill、Decode、KV Cache、批处理和分位延迟的基本含义。涉及 LoRA Adapter 时，所有缩写都会在正文首次出现处定义；没有某个特定框架经验不妨碍理解机制。实验需要 Python 3.11 或兼容版本。围绕 LoRA Adapter 的机制模拟只依赖 CPU；真实路径需要任意可用的 CUDA GPU、与驱动兼容的 PyTorch，以及自行准备的本地小模型或兼容制品。

验证 LoRA Adapter 前必须记录 GPU 名称、数量、可用显存、驱动、CUDA、PyTorch、推理框架、模型摘要、精度、批量、序列长度和完整命令。脚本根据可用显存缩放模型、批量、上下文和样本数，并把 LoRA Adapter 状态写入报告；可选 CUDA 入口不下载未经确认的大模型。

## 4. 工程问题

关于 Multi-LoRA Serving：Adapter 缓存与热切换的性能问题，要从测量条件开始。模型与修订、输入输出分布、请求到达、并发、采样、缓存、Adapter 命中率统计方式、服务等级和硬件均需保持可追溯。“选择缓存容量与驱逐”和“决定同批多 Adapter”只有在同一证据口径下才可比较。

## 5. 知识串讲

### 核心直觉与基础关系

### 核心直觉：共享 Base Model，把 Adapter 当成可调度缓存对象

Multi-LoRA 的收益不是 LoRA 本身更小，而是多个租户不必各自复制完整 Base Model。Serving 系统需要进一步管理 Adapter 的加载、驻留、淘汰和路由。

如果每个租户启动完整 Base：

$$Memory_{naive}=N\cdot M_{base}$$

Multi-LoRA：

$$Memory_{multi}=M_{base}+\sum_{a\in resident}M_{adapter,a}+Runtime$$

由于 Adapter 通常远小于 Base，节省巨大。

但这不意味着可以无限加载 Adapter：

- GPU 仍有 adapter memory；
- metadata / kernel workspace；
- adapter 数量太多会增加 cache thrash。

### Adapter Registry

至少包含：

```text
adapter_id
base_model_revision
adapter_revision
rank/alpha/config
dtype
storage_uri
checksum
tenant
status
```

最重要的字段是：

`base_model_revision`

同一个 Adapter 不能随便挂在不兼容的 Base revision 上。

### Adapter Cache

GPU/Host 侧可以维护有限容量：

```text
Hot adapters   → GPU
Warm adapters  → CPU/local SSD
Cold adapters  → Object Storage
```

淘汰策略：

### LRU

最近最少使用先淘汰。

适合时间局部性强。

### LFU

长期低频先淘汰。

适合热门集合稳定。

### Cost-Aware

考虑重新加载成本：

$$EvictScore(a)=f(Recency,Frequency,LoadCost,Size)$$

大 Adapter 虽占空间多，但如果加载极慢且马上还会复用，未必该先淘汰。

### Adapter Load 进入 TTFT

Cache miss 时：

```text
Request
 ↓
Route
 ↓
Adapter not resident
 ↓
Download / Load / Materialize
 ↓
Inference
```

TTFT 近似：

$$TTFT=T_{queue}+T_{adapter-load}+T_{prefill}$$

因此 Router 应优先选择已加载 Adapter 的 Replica，但仍需与 queue cost 权衡。

### Multiplexing 与 Routing

假设：

```text
Replica A: LoRA 1,2,3
Replica B: LoRA 4,5
Replica C: LoRA 1,6
```

请求 LoRA1：A/C 有 locality。

请求 LoRA7：所有 Replica miss，需要选：

- 哪个实例 load 最低；
- 哪个 cache 有可淘汰空间；
- 加载后是否值得保留；
- 是否需要预热一个新 Replica。

这与前一篇的 Adapter Locality 直接连接。

### Batch 中多个 Adapter

一个 batch 可能：

```text
Req A → LoRA1
Req B → LoRA2
Req C → LoRA1
Req D → LoRA3
```

如果 Runtime 每个请求单独执行 adapter GEMM，会产生大量小 kernel。

高性能实现会：

- 按 adapter group；
- 使用 batched/multi-LoRA kernel；
- 合并相同 adapter 请求；
- 对 rank/shape 做约束。

Multi-LoRA 的 Serving 效率依赖 Runtime 是否真正支持混合 Adapter Batch，而不是只支持“请求时换权重”。

### 热门 Adapter 预测与预热

如果某个租户每天 9:00 流量激增，可以提前：

- load adapter；
- pin cache；
- 增加 compatible replicas。

相比 miss 后再加载，可以显著降低首批请求 TTFT。

这属于后续 Cold Start 与 Autoscaling 篇目的联动。

### LoRA Adapter

LoRA Adapter 在 Multi-LoRA Serving：Adapter 缓存与热切换中的生命周期需要落到组件接口：输入从哪里来，状态由谁持有，输出交给谁，失败如何传播。它与共享基座模型之间的身份和版本若未绑定，请求时间线就可能混入旧配置。

Adapter 缓存避免重复存储读取对 LoRA Adapter 的影响会分散到计算、显存、内存带宽、主机处理和同步等待。某一阶段变短时，被遮蔽的成本可能随即暴露。为确认 LoRA Adapter 的变化来自哪里，本文对齐请求时间线与资源采样，而非只看整段运行的 GPU 平均值。

LoRA Adapter 的边际价值会随输入长度、输出长度、并发、流量突发、采样和任务域变化。验证设置预取与常驻时分别运行低载、接近饱和与过载区间，并使用代表性分布。单一长度、批量或短窗口只能说明该测试点。

正确性门禁覆盖 LoRA Adapter 影响到的 Token、采样、结构、结束状态与错误。若检测到缓存逐出热点制品，当前性能结果不进入候选评审，并立即切回已验证配置。失败样本与版本信息要一并保存。

为 LoRA Adapter 建立证据链时，统一保存请求 ID、模型及策略修订、关键时间点、资源快照和错误。缓存占用的定义随报告存档，包括单位、窗口和分母。这样才能按同一条件重放“如何在共享基座模型上多路复用 Adapter，并控制加载抖动和版本一致性？”。

### 共享基座模型

对共享基座模型做边界检查，要覆盖输入、输出、状态归属和销毁时点。Multi-LoRA Serving：Adapter 缓存与热切换的等待、计算及复制都能沿这些节点定位。共享基座模型传给 Adapter Cache 的数据还应附带模型或策略版本，使测量结果可以对应到唯一配置。

共享基座模型的资源账要拆成计算、显存、内存带宽、主机开销和同步等待。同批不同 Adapter 需要运行时多路复用通常只先改变其中几项，其他资源随后可能进入关键路径。共享基座模型的请求时间线和资源曲线可以呈现这种转移，平均 GPU 利用率只作为辅助信号。

工作负载一变，共享基座模型对系统的贡献也会变化。绑定基座和 Adapter 版本应覆盖长短输入、不同输出、并发、突发、采样与任务域，并保留低载、稳定高载和过载记录。容量判断不能从一次固定批量的短运行外推。

对共享基座模型的优化只有在输出合同不变时才有效。Token 序列、采样分布、结构合法性、结束原因和错误传播均需对账。租户加载未授权 Adapter 会触发停止与回退，系统恢复到已有证据支持的配置。

Adapter 装载带来的速度变化仍需满足模型输出合同，包括 Token 序列、采样分布、结构合法性、结束原因和错误传播。出现租户加载未授权 Adapter 时，质量门禁应停止性能发布；回退目标是已验证配置，并保留问题请求用于复现。

Adapter 装载的观测记录包含请求身份、模型版本、策略版本、阶段时间、资源状态与失败原因。同批多路复用率没有单位、统计窗口和分母时不参与决策。完整记录用于复查“如何在共享基座模型上多路复用 Adapter，并控制加载抖动和版本一致性？”在具体负载下是否成立。

### 性能模型与变量

用于推演的性能关系为：Benefit = avoided_base_replicas - adapter_load_cost - multiplex_overhead - cache_miss_penalty。它帮助评审 LoRA Adapter、共享基座模型怎样作用于 Adapter 命中率、同批多路复用率和每 Adapter 成本，没有预设具体设备的基准值。代入 LoRA Adapter 数据前先统一时间单位，检查概率范围，并注明吞吐量计算的是请求、Token 还是满足 SLO 的有效完成。

推演重点是判断多个 Adapter 共享基座权重降低常驻成本发生后哪些量应变化，以及 Adapter 缓存避免重复存储读取的收益在什么负载下被摊销。实现中的调度、Kernel、内存、网络、客户端和取消成本另行记录。公式与实测产生矛盾时，以检查假设、遗漏项和统计方式为处理顺序。

### 机制 1：多个 Adapter 共享基座权重降低常驻成本

请求执行“多个 Adapter 共享基座权重降低常驻成本”后，阶段边界和依赖关系会发生变化。先记录原路径，再记录候选路径中的串行、并行与合批段；同时保存 LoRA Adapter 状态和 Adapter 命中率，便于把原因与结果关联起来。

容量评估把“多个 Adapter 共享基座权重降低常驻成本”放在三个负载区间中运行。固定开销通常在低载突出，队列和资源争用会在高载显现；高基数流量导致加载抖动意味着候选工作可能消耗了服务正常请求所需的容量。

实现“多个 Adapter 共享基座权重降低常驻成本”时明确数据格式、张量形状、缓存身份、版本兼容和错误回退。执行设置预取与常驻前冻结接口合同，并加入无效输入、极端长度与资源不足测试。成功样本之外的保护行为也属于验收范围。

“多个 Adapter 共享基座权重降低常驻成本”的 Trace 同时记录决策输入与执行结果：前者含阈值和候选，后者含同批多路复用率、错误、取消和资源变化。这样能判断问题来自机制、选择器、实现成本还是流量变化。
