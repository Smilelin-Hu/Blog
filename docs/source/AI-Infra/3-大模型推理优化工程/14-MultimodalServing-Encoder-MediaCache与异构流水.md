# Multimodal Serving：Encoder、Media Cache 与异构流水

「如何拆分媒体预处理、编码和 LLM 解码以控制端到端延迟？」贯穿本文。先把媒体预处理、Vision Encoder 及其状态边界讲清楚，再讨论计算、实现和上线证据。在 Multimodal Serving 中算法选择只是决策的一部分，负载分布、模型修订、调度、显存、并发和服务等级都会改变结论，每项收益都需要对应可观察的事件与适用范围。

双路径验证在个人电脑上即可完成：CPU 模拟负责检验媒体预处理到 Vision Encoder 的方向，CUDA 实验负责测量真实执行代价。模拟、实测和外部资料不会混用。围绕媒体预处理得出的结果只对记录的模型、软件、设备和负载负责，同时给出失败原因与回滚入口。

## 1. 内容概览

- 媒体预处理、Vision Encoder 与 Media Token 之间的状态与资源关系。
- 用 $T_{e2e}=T_{fetch}+T_{preprocess}+T_{encode}+T_{queue}+T_{prefill}+T_{decode}$ 建立可计算的收益边界并解释全部变量。
- 围绕媒体获取时间、预处理延迟、Encoder 延迟和端到端成功率设计可复现实验。
- 识别媒体下载或解码阻塞入口、缓存键遗漏裁剪与模型版本和 Encoder 批处理导致交互长尾等典型失败模式。
- 对中心问题给出包含适用条件、证据、风险和回滚的工程答案。

## 2. 核心直觉：为什么「同样一个请求」成本可以差 100 倍

请求 A：一张 224×224 图片。

请求 B：20 秒 1080p 视频，抽 64 帧。

外部 API 都可能是 1 request，但内部工作量完全不同。可以定义 multimodal work：

$$W=\alpha B_{media}+\beta N_{frames}+\gamma N_{visionTokens}+\delta N_{llmTokens}$$

其中各项系数由实际硬件/模型 profile 得到。这说明：**多模态平台按 request count 做容量规划尤其危险**。

但本文会进一步指出一个容易被忽略的反面：按「总 GPU 成本」规划同样会低估媒体侧压力，因为媒体侧成本大量落在**网络与 CPU**，而不是 LLM 的 GPU 时间。第 5 节的资源账显示，A 与 B 的网络工作量差 683 倍、CPU 差 256 倍，而 LLM Decode 的 GPU 成本完全相同。只看一个总量指标，无论它是请求数还是 GPU-ms，都会漏掉真正的瓶颈。

## 3. 前置知识与实验环境

需要理解自回归生成、Tokenizer、Prefill、Decode、KV Cache、批处理和分位延迟的基本含义，并已掌握前几篇建立的成本口径。涉及媒体预处理时所有缩写都会在正文首次出现处定义；没有某个特定框架经验不妨碍理解机制。实验需要 Python 3.11 或兼容版本。围绕媒体预处理的机制模拟只依赖 CPU；真实路径需要任意可用的 CUDA GPU、与驱动兼容的 PyTorch，以及自行准备的本地小模型或兼容制品。

验证媒体预处理前必须记录 GPU 名称、数量、可用显存、驱动、CUDA、PyTorch、推理框架、模型摘要、精度、批量、序列长度和完整命令。脚本根据可用显存缩放模型、批量、上下文和样本数，并把媒体预处理状态写入报告；可选 CUDA 入口不下载未经确认的大模型。

评审记录应包含模型修订、长度分布、到达过程、并发、采样、缓存、媒体获取时间定义、服务等级和硬件，随后才能比较「选择图像分辨率或视频采样率」和「部署独立或共置 Encoder」。缺少这些信息时，局部速度无法换算成系统收益。

## 4. 统一口径与六段延迟模型

### 4.1 口径

后续推导统一使用以下设定（推导设定，非实测）：

| 量 | 取值 | 说明 |
| --- | --- | --- |
| 批内单请求 TPOT | 20 ms/token | 非带宽受限时的基线，$B_{slot}=32$ |
| 摊销每 Token GPU 时间 $c_{tok}$ | 0.625 GPU-ms | $=20/32$ |
| 固定开销 $F_{other}$ | 450 GPU-ms | 调度、聚合、采样前置 |
| Prefill GPU 成本 | 0.05 GPU-ms/token | 沿用前几篇 |
| Prefill wall-clock | 0.1 ms/token | 同上 |
| Decode 输出长度 $O$ | 300 Token | 与前两篇一致 |
| 文本输入 | 1000 Token | 同上 |
| KV 每 Token | 128 KiB | 32 层 8 KV 头 head_dim 128 fp16 |
| HBM 带宽 | 2 TB/s | 用于第 9 节带宽受限判定 |
| PCIe 带宽 | 32 GB/s | 同机跨卡传 feature |
| 对象存储下载带宽 | 50 MB/s | 沿用 Speculator 工程化一篇的远端口径 |
| GPU 单价 | \$2.40 / GPU-hour | $1$ GPU-ms $=6.667\times10^{-7}$ 美元 |

前几篇把固定开销记为 $F=500$ GPU-ms，其中已含 1000 Token 的 Prefill（50 GPU-ms）。本文把它拆成 $F_{other}=450$ 加按实际 Token 数计的 Prefill，**口径等价**，因为多模态的输入长度不再固定为 1000。

### 4.2 六段模型

$$T_{e2e}=T_{fetch}+T_{preprocess}+T_{encode}+T_{queue}+T_{prefill}+T_{decode}$$

六段分属四种不同资源：$T_{fetch}$ 属网络、$T_{preprocess}$ 属 CPU、$T_{encode}$ 属 Encoder GPU、$T_{prefill}+T_{decode}$ 属 LLM GPU，$T_{queue}$ 则是各段之间的等待。**把它们加成一个总时间会掩盖瓶颈归属**，因此本文始终按资源分列。

首 Token 延迟只含前五段：

$$TTFT=T_{fetch}+T_{preprocess}+T_{encode}+T_{queue}+T_{prefill}$$

### 4.3 两个参照请求

| 量 | 请求 A（图片） | 请求 B（视频） |
| --- | --- | --- |
| 媒体 | 224×224 JPEG | 20 s 1080p H.264 @ 4 Mbps |
| $B_{media}$ | 15 KB | 10 MB |
| $N_{frames}$ | 1 | 64 |
| 每帧视觉 Token $V$ | 256（patch 14，16×16） | 256（抽帧后 resize 到 224×224） |
| $N_{vision}$ | 256 | 16384 |
| LLM 输入总 Token | 1256 | 17384 |

帧数与采样率的关系：

$$N_{frames}=fps_{sample}\cdot duration,\qquad N_{vision}=N_{frames}\cdot V$$

$64=3.2\times20$，即采样率 3.2 fps。即使 LLM 输出很短，Prefill 也可能巨大——这是视频负载的全部麻烦来源。

## 5. 四类瓶颈与完整资源账

### 5.1 四种瓶颈类型

- **Download Bound**：远程 URL、对象存储或 CDN 慢。
- **CPU Decode/Preprocess Bound**：JPEG/PNG/video decode、resize、normalize 占 CPU。
- **Encoder Bound**：Vision/Audio Encoder 占用 GPU 计算，可能与 LLM 竞争。
- **LLM Bound**：Encoder 输出变成大量 multimodal tokens，进入 LLM 上下文，扩大 Prefill/KV。

只有看完整 trace 才知道瓶颈在哪里。

### 5.2 分资源账

各段单位成本设定（推导设定）：下载 50 MB/s；JPEG 解码+resize 2 ms/张；视频帧解码+resize 8 ms/帧（CPU）；ViT 单帧 12 GPU-ms，batch 8 摊薄到 6 GPU-ms/帧；Prefill 0.1 ms/token wall。

| 资源 | 请求 A | 请求 B | B/A |
| --- | --- | --- | --- |
| 网络下载 | 0.3 ms / 15 KB | 200 ms / 10 MB | **683×**（字节） |
| CPU 预处理 | 2 ms | 512 ms | **256×** |
| Encoder GPU | 12 ms | 384 ms | 32× |
| LLM Prefill GPU | 62.8 ms | 869.2 ms | 13.8× |
| LLM Decode GPU | 187.5 ms | 187.5 ms | **1×** |
| KV 显存 | 157 MiB | 2173 MiB | 13.8× |

Decode 成本相同是因为输出长度相同（第 9 节会修正这一假设）。**媒体侧差异集中在网络与 CPU，而这两项在传统 LLM Serving 的监控里往往根本不存在。**

### 5.3 TTFT 差 23 倍，端到端只差 1.5 倍

$T_{queue}=0$ 时（推导值，非实测）：

| 指标 | 请求 A | 请求 B | B/A |
| --- | --- | --- | --- |
| TTFT | 139.9 ms | 3218.4 ms | **23.0×** |
| $T_{e2e}$ | 6139.9 ms | 9218.4 ms | 1.50× |

$TTFT_A=0.3+2+12+125.6=139.9$ ms，$TTFT_B=200+512+768+1738.4=3218.4$ ms（此处 Encoder 未 batch，按单帧 12 ms 计 64 帧为 768 ms）。

**只看端到端平均延迟会完全掩盖多模态的入口瓶颈**：6 s 的 Decode 把 3 s 的入口差异稀释成 1.5 倍。因此多模态 SLO 必须把 TTFT 单列，且按媒体类型分桶——图片与视频混在一个 TTFT 分布里，P99 会被视频完全支配而图片的问题不可见。

### 5.4 并发上限

60 GiB KV 预算下（推导值）：

| 请求类型 | 总输入 Token | KV | 并发上限 |
| --- | --- | --- | --- |
| 纯文本 | 1300 | 162.5 MiB | 378 |
| 图片 A | 1256 | 157 MiB | 391 |
| 视频 B | 17384 | 2173 MiB | **28** |

视频请求的并发上限只有图片的 **7.2%**。按请求数估容量会高估 13.8 倍，必须按 KV 占用或 Token·秒估。这与 Reasoning Serving 一篇的结论同构：那里的分母是思考 Token，这里是视觉 Token。

## 6. CPU/GPU 异构流水：重叠的收益上限

### 6.1 最差实现与合理实现

最差实现：

```text
CPU 下载
等待
CPU 解码
等待
GPU Encoder
等待
LLM
```

更合理：

```text
Req A: Download → Decode → Encoder → LLM
Req B:          Download → Decode → Encoder → LLM
Req C:                   Download → Decode → Encoder → LLM
```

目标是用异步 I/O、线程池和独立 GPU/stream，把不同请求阶段重叠。这不是重新讲 CUDA stream，而是把它放到多模态 Serving 的资源编排中。

### 6.2 重叠收益由瓶颈资源决定

设各阶段资源独立（网络、CPU 池、Encoder GPU、LLM GPU），三个请求 A/B/C 同时到达（推导值，非实测）：

| 阶段资源 | 三请求总占用 |
| --- | --- |
| 网络 | 200.6 ms |
| CPU 预处理 | 516 ms |
| Encoder GPU | 792 ms |
| **LLM GPU** | **19989.6 ms** |

串行总时长 $2\times6139.9+9218.4=21498.2$ ms；流水重叠后 makespan 由 LLM 决定，约 $14.3+19989.6=20003.9$ ms，**改善仅 7.0%**。

换成 8 个视频请求、输出缩短到 $O=50$：

| 方案 | 总时长 | 改善 |
| --- | --- | --- |
| 串行 | $8\times4218.4=33747.2$ ms | — |
| 流水重叠 | $1480+8\times2738.4=23387.2$ ms | **30.7%** |

结论：**流水重叠的收益上限等于「非瓶颈阶段占总时间的比例」**。当 LLM 占 93% 时最多省 7%；当输出短、媒体重时能省 30%。因此「上异步流水」不是无条件优化，必须先确认瓶颈在哪一段。

### 6.3 视频负载的真正瓶颈是 Prefill 而非 Encoder

直觉上视频负载的瓶颈应该是 Vision Encoder，但数字不支持：

$$T_{encode}=768\ \text{ms},\qquad T_{prefill}=1738.4\ \text{ms}\quad\Rightarrow\quad \frac{T_{prefill}}{T_{encode}}=2.26$$

**16384 个视觉 Token 的 Prefill 比编码它们贵 2.26 倍。** 这直接改变了优化顺序：降低视觉 Token 数（减帧或降分辨率）比加速 Encoder 更有效，因为前者同时削减 Encoder 与 Prefill 两项，后者只削减一项。第 8 节给出最优 Token 预算的闭式解。

## 7. 视频帧采样与上下文挤压

### 7.1 帧数上限由上下文长度反解

设模型上下文 32768 Token，文本输入 1000、输出 300，则可用视觉 Token 为 $32768-1300=31468$：

$$N_{frames}^{max}=\left\lfloor\frac{31468}{V}\right\rfloor$$

| 每帧 $V$ | 最大帧数 | 20 s 视频的 $fps_{sample}$ 上限 | 60 s 视频的上限 |
| --- | --- | --- | --- |
| 256 | 122 | 6.1 | 2.03 |
| 512 | 61 | 3.05 | 1.02 |
| 1024 | 30 | 1.5 | 0.5 |

**分辨率提高 4 倍（$V$ 从 256 到 1024）会把最大帧数从 122 压到 30。** 这就是「帧数过多挤压文本上下文」的定量形态：分辨率与帧数在同一个上下文预算里竞争，不能各自独立配置。

### 7.2 帧数对 KV 与并发的影响

| 帧数 | $N_{vision}$ | 总输入 | 占 32768 | KV | 60 GiB 并发 |
| --- | --- | --- | --- | --- | --- |
| 16 | 4096 | 5096 | 15.6% | 637 MiB | 96 |
| 32 | 8192 | 9192 | 28.1% | 1149 MiB | 53 |
| 64 | 16384 | 17384 | 53.0% | 2173 MiB | 28 |
| 122 | 31232 | 32232 | 98.4% | 4029 MiB | **15** |

122 帧时上下文占用 98.4%，几乎没有留给多轮对话的余量，且并发上限掉到 15。**「最大帧数」不应按上下文刚好填满来设，而应按「留出多轮余量 + 并发不低于某阈值」反解。** 若要求并发 $\ge28$，则帧数上限就是 64。

### 7.3 平台需要的六项控制

因此平台需要：sampling policy、max frames、resolution tier、duration limit、preprocess queue、encoder pool。六项不是并列的可选项，而是一条约束链：duration limit 与 sampling policy 决定 $N_{frames}$，resolution tier 决定 $V$，两者乘积受 max frames 与上下文预算约束，preprocess queue 与 encoder pool 则决定这个乘积能否被按时消化。

## 8. Vision Token 预算的最优解

### 8.1 成本与质量口径

Encoder 摊薄成本折算到每视觉 Token：$6/256=0.0234375$ GPU-ms。加上 Prefill 的 0.05，得每视觉 Token 的边际成本 $c_v=0.0734375$ GPU-ms。固定部分为 $F_{other}+0.05\times1000+c_{tok}O=450+50+187.5=687.5$ GPU-ms。故

$$C(N)=0.0734375\,N+687.5$$

质量沿用 Reasoning Serving 一篇的双曲饱和形式（推导设定，非实测）：

$$Q(N)=Q_\infty\frac{N}{N+K_v},\qquad Q_\infty=0.90,\ K_v=4000$$

### 8.2 闭式最优

每成功任务成本 $f(N)=C(N)/Q(N)$，与上一篇同构，故

$$\boxed{N^*=\sqrt{\frac{687.5\times K_v}{c_v}}}=\sqrt{\frac{687.5\times4000}{0.0734375}}\approx6119\ \text{视觉 Token}$$

$f(N^*)=2088.9$ GPU-ms。对应 **24 帧 × 256**（$24\times256=6144$），而不是源直觉里的 64 帧。

| $N_{vision}$ | 帧×$V$ | $C$ GPU-ms | $Q$ | $C/Q$ | 相对最优 |
| --- | --- | --- | --- | --- | --- |
| 2048 | 32×64 | 837.9 | 0.3048 | 2749.0 | +31.6% |
| 4096 | 16×256 | 988.3 | 0.4553 | 2170.7 | +3.9% |
| **6144** | **24×256** | **1138.7** | **0.5451** | **2089.0** | **0%** |
| 8192 | 32×256 | 1289.1 | 0.6045 | 2132.5 | +2.1% |
| 16384 | 64×256 | 1890.7 | 0.7232 | 2614.4 | +25.1% |

从 6144 到 16384：质量涨 32.7%，成本涨 66.0%，每成功任务成本涨 25.1%。**「多抽帧总是更准」在成本口径下不成立。**

### 8.3 同预算下优先减帧而非降分辨率

固定 $N_{vision}=8192$，两种切分方式（推导值）：

| 方案 | 帧 | $V$ | Encoder GPU-ms | CPU 预处理 | $C$ | $C/Q$ | TTFT |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 少帧高分辨率 | 32 | 256 | 192 | 256 ms | 1289.1 | 2132.5 | **1567.2 ms** |
| 多帧低分辨率 | 64 | 128 | 192 | 512 ms | 1289.1 | 2132.5 | 1823.2 ms |

Encoder 成本相同（$32\times6=64\times3=192$），GPU 总成本与质量相同，但**少帧方案的 CPU 预处理少一半、TTFT 低 14.0%**。

因此在视觉 Token 预算固定时应优先减帧。唯一的例外是任务依赖时序密度（动作识别、事件定位），此时减帧的质量损失无法用 $Q(N)$ 表达，必须单独建模并实测——本文的 $Q$ 只按 Token 数建模，是简化而非结论。

## 9. 长上下文对 Decode 的反噬

### 9.1 KV 读取带宽成为瓶颈

前面假设视频请求的 Decode 成本与图片相同（187.5 GPU-ms），这在长上下文下不成立。Decode 每步都要读取全部历史 KV：

$$T_{step}^{KV}=\frac{B\cdot N_{total}\cdot128\ \text{KiB}}{BW_{HBM}}$$

| 负载 | batch | 每步 KV 读取 | $T_{step}$ | 是否带宽受限 |
| --- | --- | --- | --- | --- |
| 纯文本（1300 Token） | 32 | 5.08 GiB | 2.60 ms | 否（20 ms 由权重与计算决定） |
| 视频（17384 Token） | 28 | 60.05 GiB | **31.9 ms** | **是** |

视频负载下 TPOT 从 20 ms 涨到 31.9 ms（**+59.5%**），每 Token GPU 成本从 0.625 涨到 $31.9/28=1.139$ GPU-ms（**+82%**）。**视觉 Token 不只扩大 Prefill，还按输出长度倍数放大 Decode 的带宽成本。**

### 9.2 折算到每视觉 Token

每视觉 Token 在整个 Decode 阶段引发的额外 GPU 时间：

$$c_{kv}=O\times\frac{128\ \text{KiB}}{BW_{HBM}}=300\times\frac{131072}{2\times10^{12}}\ \text{s}=0.01966\ \text{GPU-ms}$$

带宽项超过基线 Decode 成本的临界点：$0.01966(N+1000)=187.5\Rightarrow N=8537$。**视觉 Token 超过约 8500 后，Decode 进入带宽受限区，成本斜率从 0.0734 跳到 0.0931 GPU-ms/Token。**

### 9.3 修正后的成本表

| $N_{vision}$ | Decode GPU-ms | $C$ GPU-ms | $C/Q$ | 相对基础口径 |
| --- | --- | --- | --- | --- |
| 4096 | 187.5 | 988.3 | 2170.7 | 0% |
| 6144 | 187.5 | 1138.7 | 2089.0 | 0% |
| 8192 | 187.5 | 1289.1 | 2132.5 | 0% |
| 12288 | 261.2 | 1663.6 | 2449.7 | +4.6% |
| 16384 | 341.8 | 2045.0 | **2827.7** | **+8.2%** |

最优点仍在 6100 附近（因为它落在临界点以下），但**大预算的惩罚被显著加重**：16384 的每成功任务成本从 2614.4 升到 2827.7。这进一步支持第 8 节的结论——默认 64 帧是过度配置。

「峰值显存」必须附带口径：区分 KV 峰值、Encoder 激活峰值与 feature 缓存峰值，注明统计窗口与分母（并发请求数）。三者峰值不同时出现，用一个「显存利用率」无法判断该扩 KV 还是该扩 Encoder 池。

## 10. 跨模态位置与 Prefix 复用

### 10.1 位置编码方案影响质量而非速度

视觉 Token 插入 LLM 序列时需要位置编码。一维连续 id 会丢失图像的空间结构，三维（时间/高/宽）方案保留结构但实现更复杂。这一项的质量影响无法用解析式给出，**标记为待测**，门禁是：位置编码方案变更必须做质量对账（同一媒体、同一问题、同一采样种子下的输出一致性），性能收益不得替代质量结论。

### 10.2 位置方案决定 Prefix Cache 能否命中

资源账上它有一个可量化的后果：若视觉 Token 的 position id 依赖媒体在序列中的**绝对偏移**，则同一张图片出现在不同位置会产生不同 KV，Prefix Cache 无法复用。

设图片位于 prompt 开头的比例为 80%（推导设定），则 20% 的请求必须重新 Prefill 视觉部分：

| 请求类型 | 视觉 Prefill GPU-ms | 20% 未命中的期望额外成本 | 占 $C$ 比例 |
| --- | --- | --- | --- |
| 图片 A | 12.8 | 2.56 GPU-ms | 0.36% |
| 视频 B | 819.2 | **163.84 GPU-ms** | **8.7%** |

**视频负载下位置方案不当会白扔 8.7% 的 GPU 成本。** 因此跨模态位置方案应保证「同一媒体在同一相对位置产生同一 KV」，或统一把媒体前置。这一约束会在后续 Prefix、Session 与 KV-Locality Routing 一篇里再次出现，那里讨论的是路由层如何配合。

## 11. 三层缓存：Media / Preprocessed / Feature

### 11.1 三层各缓存什么

**Media Cache** 缓存原始下载后的 bytes，Key 可以是：

$$\mathrm{Hash}(URL,ETag,ContentDigest)$$

**Preprocessed Cache** 缓存 resize/normalize 后的 Tensor，Key 还要包含 preprocess config。

**Encoder Feature Cache** 缓存 encoder output：

$$Key=\mathrm{Hash}(MediaDigest,EncoderRevision,PreprocessRevision)$$

如果同一张图片被多个问题重复引用，Feature Cache 可以直接跳过 Encoder。

### 11.2 三层的体积与收益密度

设 hidden 4096、feature fp16、预处理 Tensor 为 $3\times224\times224$ fp32（推导设定）：

| 层 | 请求 A 体积 | 请求 B 体积 | 命中节省（B） |
| --- | --- | --- | --- |
| Media（raw bytes） | 15 KB | 10 MB | 200 ms |
| Preprocessed（Tensor） | 588 KiB | 36.75 MiB | 712 ms |
| Feature（encoder out） | 2 MiB | **128 MiB** | 1480 ms |

**Feature 体积是 raw bytes 的 12.8 倍**（视频），因此收益密度反而最低：

| 层 | 节省 ms/MiB（视频 B） | 节省 ms/MiB（图片 A） |
| --- | --- | --- |
| Media | **20.97** | **20.5** |
| Preprocessed | 19.37 | 4.01 |
| Feature | 11.56 | 7.15 |

1 GiB 缓存预算能容纳的条目数（推导值）：

| 层 | 视频条目 | 图片条目 |
| --- | --- | --- |
| Media | 107 | ≈69900 |
| Preprocessed | 27 | 1783 |
| Feature | **8** | 512 |

**只缓存 Feature 时 1 GiB 只能存 8 个视频**，命中率必然极低。正确做法是分层缓存并按「节省时间 × 访问频率 / 字节」排序，而不是统一缓存最贵的那一层。图片场景 raw bytes 的收益密度最高且体积极小，应当优先全量缓存。

### 11.3 分层命中率与期望 TTFT

设 Feature 命中率 $h_f=0.50$；在 Feature miss 的请求中 Preprocessed 命中率 0.40（整体 0.20）；在两者都 miss 的请求中 Media 命中率 0.60（整体 0.18）；全 miss 0.12（推导设定）。

$$E[TTFT]=T_{prefill}+0.20\,T_{enc}+0.18\,(T_{enc}+T_{prep})+0.12\,(T_{enc}+T_{prep}+T_{fetch})$$

| 请求 | 无缓存 TTFT | Feature 全命中 | 分层期望 TTFT | 改善 |
| --- | --- | --- | --- | --- |
| A | 139.9 ms | 125.6 ms（−10.2%） | 132.24 ms | −5.5% |
| B | 3218.4 ms | 1738.4 ms（−46.0%） | **2300.0 ms** | **−28.5%** |

**Feature Cache 对视频 TTFT 的改善（46%）远大于对图片（10%）**，因为视频的媒体侧成本占比高。缓存策略必须按媒体类型分档：图片优先 Media Cache，视频优先 Feature Cache，且视频 Feature Cache 需要独立的大容量预算。

## 12. 缓存键的五个分量与陈旧率

### 12.1 为什么不能只用 URL 做 Key

同一个 URL 内容可能变化；同一图片在不同 encoder revision 下 feature 也不同。安全 Key 至少包含：

- content digest；
- encoder revision；
- preprocess config；
- projector/model revision；
- tenant isolation（视业务要求）。

### 12.2 遗漏各分量的后果

| 遗漏分量 | 后果 | 定量形态（推导设定） |
| --- | --- | --- |
| content digest | 陈旧内容 | 内容变更率 5%/h、TTL 24 h → $1-0.95^{24}=70.8\%$ 条目可能陈旧 |
| preprocess config | 取错分辨率/裁剪 | 3 个 resolution tier → **2/3 概率取错** |
| encoder revision | feature 空间不兼容 | 升级后 projector 无法消费，输出乱码或崩溃 |
| projector/model revision | 同上 | 与 encoder 升级同类，但更隐蔽（encoder 未变） |
| tenant isolation | 跨租户命中 | 同 digest 的私有媒体被他人命中 → **数据泄露** |

**70.8% 的陈旧率与 2/3 的取错率都不是性能问题，而是正确性与合规事故。** 它们的共同特征是：命中率、编译延迟、吞吐全部正常，只有输出质量恶化。因此「缓存键遗漏裁剪与模型版本」必须列为发布阻断项，且门禁指标是输出质量而非任何性能指标。

### 12.3 与 Grammar 缓存的同构性

上一篇 Structured Output 的缓存键是 $\mathrm{Hash}(NormalizedSchema,TokenizerRevision,BackendVersion)$，本文是 $\mathrm{Hash}(MediaDigest,EncoderRevision,PreprocessRevision,ProjectorRevision,Tenant)$。两者结构完全相同：**内容身份 + 所有会改变产物语义的版本身份 + 隔离边界**。这不是巧合，而是「缓存编译产物」这类优化的通用键设计法则，后续 Weight Distribution 与 Cold Start 两篇的制品缓存仍会沿用。

## 13. Encoder 共卡与分池的经济性

### 13.1 两种部署形态

**共卡**优点是架构简单、不需要跨 GPU 传 feature；缺点是 Encoder burst 会干扰 LLM、GPU memory 生命周期更复杂。

**分池**：

```text
Media → Encoder Pool → Feature → LLM Pool
```

优点是可独立扩缩容和选择硬件；缺点是需要网络/IPC，增加故障面。是否拆分必须根据 $T_{encoder}$、TrafficMix、FeatureSize、SLO 实测。

### 13.2 共卡的干扰量化

设 Encoder batch 8 帧需 $8\times6=48$ GPU-ms。video-heavy 流量为 2 视频请求/s × 64 帧 = 128 帧/s → 16 批/s → Encoder 占用 $16\times48=768$ ms/s，即 $u_e=76.8\%$。

共卡时 LLM 只能使用剩余 $1-u_e$ 的 GPU 时间：

$$TPOT_{shared}=\frac{20}{1-u_e}=\frac{20}{0.232}=86.2\ \text{ms}$$

吞吐从 1600 Token/s 掉到 $32/0.0862=371$ Token/s（**−76.8%**）。**一次 48 ms 的 Encoder 批会让同 batch 内 32 个交互请求的该步延迟从 20 ms 变成 68 ms**，这就是「Encoder 批处理导致交互长尾」的机制。

### 13.3 分池的传输成本

视频 feature 128 MiB $=134.2$ MB：

| 互联 | 带宽 | 传输时间 | 占 TTFT 3218 ms |
| --- | --- | --- | --- |
| NVLink | 600 GB/s | 0.224 ms | 0.007% |
| PCIe（同机跨卡） | 32 GB/s | 4.19 ms | 0.13% |
| 25 GbE（跨节点） | 3.125 GB/s | 42.9 ms | 1.33% |

**即使跨节点，传输成本也只占 TTFT 的 1.33%**，远小于共卡带来的 76.8% 吞吐损失。「分池会增加网络开销」在这一量级下不构成反对理由。

### 13.4 每 Token 成本与盈亏平衡

按 GPU 单价 \$2.40/h（每 GPU-second $6.667\times10^{-4}$）：

| 方案 | GPU 数 | LLM 吞吐 | \$/1000 Token |
| --- | --- | --- | --- |
| 无媒体基线 | 1 | 1600 Token/s | $4.167\times10^{-4}$ |
| 共卡（$u_e$=76.8%） | 1 | 371 Token/s | $1.797\times10^{-3}$ |
| 分池 | 2 | 1600 Token/s | $8.333\times10^{-4}$ |

**分池多用一张卡，但每 Token 成本反而比共卡低 2.16 倍。** 共卡省的是硬件台数，不是钱。

盈亏平衡条件：设 Encoder 占用比例 $u_e$，分池需 $\lceil u_e\rceil$ 张额外卡，则分池划算当且仅当

$$1+\lceil u_e\rceil<\frac{1}{1-u_e}$$

| $u_e$ | 共卡 TPOT | 共卡 $/1k tok | 分池 $/1k tok | 更优 |
| --- | --- | --- | --- | --- |
| 0.10 | 22.2 ms | $4.630\times10^{-4}$ | $8.333\times10^{-4}$ | 共卡 |
| 0.30 | 28.6 ms | $5.952\times10^{-4}$ | $8.333\times10^{-4}$ | 共卡 |
| **0.50** | 40.0 ms | $8.333\times10^{-4}$ | $8.333\times10^{-4}$ | **临界** |
| 0.768 | 86.2 ms | $1.797\times10^{-3}$ | $8.333\times10^{-4}$ | 分池 |
| 0.90 | 200 ms | $4.167\times10^{-3}$ | $8.333\times10^{-4}$ | 分池 |

**Encoder 占用超过 50% 时分池才划算**（单卡 Encoder 池）。低于此阈值时共卡的统计复用收益更大。这条阈值必须按实际 TrafficMix 重算，而不是按「多模态就该分池」的直觉配置。

「帧级吞吐」必须附带口径：单位为帧/s，分母为 Encoder GPU 数，窗口为稳态区间，并注明 $V$ 与 batch。本例单卡 $1/0.006=166.7$ 帧/s（$V=256$、batch 8），换分辨率或 batch 后该数字不可比。

## 14. 预处理并发、背压与降级

### 14.1 CPU 预处理容量

设预处理池 16 线程、每帧 8 ms，则容量 $16/0.008=2000$ 帧/s（推导值）。

| 视频到达率 | 帧需求（64 帧/请求） | 利用率 |
| --- | --- | --- |
| 2 req/s | 128 帧/s | 6.4% |
| 20 req/s | 1280 帧/s | 64% |
| 31.25 req/s | 2000 帧/s | 100% |
| 40 req/s | 2560 帧/s | **128%（过载）** |

### 14.2 无背压时队列等待线性发散

40 req/s 时净积压 $(40-31.25)\times64=560$ 帧/s：

| 持续时间 | 积压帧数 | 新请求预处理等待 |
| --- | --- | --- |
| 10 s | 5600 | 2.8 s |
| 30 s | 16800 | 8.4 s |
| 60 s | 33600 | **16.8 s** |

**等待时间随过载持续时间线性增长，没有稳态。** 这与 Reasoning Serving 一篇的长请求排队不同：那里队列会自然排空，这里只要到达率不降就永远发散。

### 14.3 背压 + 降级采样率

设预处理队列上限 4000 帧（约 2 s 处理时间）。超限时不是拒绝请求，而是**降级采样率**：64 帧 → 16 帧，则需求变为 $40\times16=640$ 帧/s，远低于 2000，队列立即排空。

代价可用第 8 节公式算：$N_{vision}$ 从 16384 降到 4096，$Q$ 从 0.7232 降到 0.4553（−37.0%），但每成功任务成本从 2827.7 降到 2170.7（−23.2%）。**降级不仅避免了延迟发散，还降低了每成功任务成本**——因为原始 64 帧本就处于过度配置区。

因此「为预处理设置并发与背压」的正确形态是：并发上限按 CPU 核数与单帧成本推算，队列上限按可接受等待时间推算，超限触发采样率降级而非拒绝，并把降级原因写进结束原因字段。

## 15. 媒体错误回退与槽位泄漏

### 15.1 损坏媒体触发无限重试

设媒体损坏率 1%、到达率 40 req/s，则 0.4 req/s 进入重试。若重试无上限且每次必失败，请求永不释放槽位：

$$T_{slot\ exhaustion}=\frac{32\ \text{槽}}{0.4\ \text{req/s}}=80\ \text{s}$$

**80 秒后全部 32 个槽位被死请求占满，服务完全停摆。** 而监控上看到的只是「重试次数上升」，吞吐与延迟在最初 80 s 内甚至可能看起来正常。

### 15.2 三道防线

| 防线 | 设定 | 作用 |
| --- | --- | --- |
| 重试上限 | 2 次 | 单请求最多消耗 3 轮，不会无限占用 |
| digest 级黑名单 | TTL 1 h | 同一损坏 URL 不再重复消耗下载与解码 |
| 失败即释放槽位 | 立即 | 槽位占用与重试解耦 |

三者缺一不可：只设重试上限仍会让同一损坏 URL 被不同请求反复触发；只设黑名单仍会让首次遇到的损坏媒体耗尽重试；只释放槽位则会把压力转成无界的重试流量（上一篇的 retry storm）。

### 15.3 媒体下载阻塞入口

「媒体下载或解码阻塞入口」是另一类形态：下载与解码若发生在请求处理主线程，一个 200 ms 的下载会阻塞整个入口。设入口单线程、40 req/s，其中视频占 10%（4 req/s × 200 ms = 800 ms/s），则入口 **80% 的时间在下载**，图片请求即使只需 0.3 ms 也要排队。

处置是把下载与解码移入独立异步 I/O 与线程池（第 6 节的流水），并对下载设超时（如 5 s）与并发上限（按入口带宽推算：1 Gbps = 125 MB/s → 12.5 个 10 MB 视频/s）。**入口带宽是视频负载的硬上限，且它与 GPU 数量无关**——加 GPU 不会提高下载容量。

「端到端成功率」必须附带口径：分子为成功返回且输出合法的请求数，分母为全部入口请求数（含被背压拒绝与媒体失败），并注明媒体类型分桶。只统计「进入 LLM 的请求」的成功率会把入口失败全部隐藏。

## 16. 八个对象的边界与失败模式

需要纳入同一证据链的对象包括：媒体预处理、Vision Encoder、Media Token、Media Cache、异构流水、视频帧采样、跨模态位置、LLM Decode。它们并不处在同一个组件中，却会一起改变帧级吞吐和端到端成功率。

### 16.1 统一检查框架

八个对象共用五问：

1. **边界与生命周期**：接收什么、产生什么、由谁维护、状态何时结束；跨组件字段是否携带版本身份。
2. **资源账五项**：计算量、显存占用、内存流量、主机工作、等待时间分别记账。
3. **三段负载区间**：低载、接近饱和、过载各留同口径证据；固定长度与固定批量只解释机制。
4. **正确性门禁**：Token 序列、采样分布、结构合法性、结束原因、错误传播五项对账；质量恶化即停止发布并回退。
5. **观测字段**：请求身份、模型与策略修订、阶段时间、资源快照、失败原因；每个指标带单位、窗口与分母。

### 16.2 媒体预处理

边界是「原始 bytes → 归一化 Tensor」，拥有者是 CPU 预处理池，生命周期结束于 Tensor 交给 Encoder。它与 Vision Encoder 交互的字段必须携带 preprocess config 版本。

独有失败模式是**帧数过多挤压文本上下文**：预处理本身成功，但产出的视觉 Token 超出上下文预算（第 7.1 节 122 帧上限）。决策短语是「设计 Media Cache 键」，指标为首 Token 延迟。

### 16.3 Vision Encoder

边界是「Tensor → feature」，拥有者是 Encoder GPU 池，生命周期结束于 feature 交给 projector 或缓存。它与 Media Token 之间的版本身份若未绑定，请求时间线就会混入旧配置。

独有失败模式是**CPU 预处理成为隐藏瓶颈**：Encoder GPU 利用率看起来不高，实际是上游供不上数据（第 14 节 2000 帧/s 上限）。决策短语是「为预处理设置并发与背压」，指标为峰值显存（须区分 KV/激活/feature 三类）。

### 16.4 Media Token

边界是「feature → LLM 序列中的视觉 Token」，拥有者是 projector 与 tokenizer 拼接层，生命周期与请求上下文一致。它传给 Media Cache 的数据必须附带模型与策略版本。

独有失败模式是**损坏媒体触发无限重试**：Token 化之前的媒体失败若没有重试上限，会在 80 s 内耗尽全部槽位（第 15.1 节）。决策短语是「分配 Encoder 和 Decode 设备」，指标为帧级吞吐。

### 16.5 Media Cache

边界是「Key → 三层产物之一」，拥有者是平台缓存服务，生命周期跨请求。它连接异构流水时必须传播身份与版本。

独有失败模式是**媒体下载或解码阻塞入口**：缓存未命中时下载发生在主线程，入口 80% 时间被占用（第 15.3 节）。决策短语是「定义媒体错误回退」，指标为端到端成功率。

### 16.6 异构流水

边界是「四段资源的编排与背压」，拥有者是调度层，生命周期覆盖请求全程。它与视频帧采样交互的字段必须携带版本身份。

独有失败模式是**缓存键遗漏裁剪与模型版本**：流水各段都「成功」，但复用了错误配置下的产物（第 12.2 节 2/3 取错率）。决策短语是「选择图像分辨率或视频采样率」，指标为媒体获取时间。

### 16.7 视频帧采样

边界是「duration + fps → 帧序列」，拥有者是采样策略层，生命周期结束于帧交给预处理。它与跨模态位置之间的版本身份若未绑定，时间维位置编码就会错位。

独有失败模式是**Encoder 批处理导致交互长尾**：为吞吐而攒 batch 会让单个交互请求等待整批（第 13.2 节 20→68 ms）。决策短语是「部署独立或共置 Encoder」，指标为预处理延迟。

### 16.8 跨模态位置

边界是「视觉 Token 的 position id 分配」，拥有者是位置编码层，产物影响 KV 布局与 Prefix 复用。它传给 LLM Decode 的数据必须附带模型与策略版本。

独有失败模式同样是**帧数过多挤压文本上下文**，但作用点不同：这里表现为位置 id 空间与文本 Token 冲突，以及绝对偏移导致 Prefix Cache 失效（第 10.2 节视频白扔 8.7% GPU 成本）。指标为 Encoder 延迟。

### 16.9 LLM Decode

边界是「含视觉 Token 的上下文 → 输出 Token 流」，拥有者是 LLM GPU 池，生命周期最长。它是唯一同时受视觉 Token 数与输出长度双重放大的阶段。

独有失败模式是**长 Decode 与 Encoder 争用设备和内存**：共卡时 Encoder burst 把 TPOT 从 20 推到 86.2 ms（第 13.2 节），长上下文时 KV 读取带宽又把 TPOT 推到 31.9 ms（第 9.1 节）。两类干扰叠加时交互请求的尾延迟不可预测，因此必须按第 13.4 节的 $u_e$ 阈值决定是否分池。

## 17. 六个机制的因果分析

### 17.1 Encoder 将媒体转换为可供 LLM 消费的表示

机制链条是「bytes → Tensor → feature → 视觉 Token」。它把非 Token 输入引入 LLM 的上下文预算，因此所有下游成本都按 $N_{vision}$ 放大。

关键路径转移发生在三处：从网络到 CPU（下载完成后）、从 CPU 到 Encoder GPU（预处理完成后）、从 Encoder 到 LLM（feature 就绪后）。每次转移都伴随一次数据形态变化与体积变化，视频 feature 128 MiB 是 raw bytes 的 12.8 倍。

因此该机制的工程边界是 $N_{vision}$ 而非「模型支持多模态」。第 8 节给出最优 6119，第 7 节给出上下文上限 122 帧，两者共同构成可核算的配置区间。

### 17.2 媒体缓存按内容与处理配置复用编码结果

机制链条是「Key 命中 → 跳过对应阶段 → TTFT 下降」。三层缓存分别跳过 fetch、fetch+prep、fetch+prep+encode，节省量递增但体积也递增。

收益密度与节省量方向相反：Media 层 20.97 ms/MiB 最高，Feature 层 11.56 ms/MiB 最低。因此缓存预算分配不能按「哪层省得多」而应按「哪层单位字节省得多 × 访问频率」。

该机制的正确性前提是键包含全部五个分量。遗漏任一分量都会让「复用」变成「复用错误产物」，且所有性能指标正常——这是它区别于普通性能优化的地方。

### 17.3 视频帧数同时改变质量、Encoder 成本和上下文长度

机制链条是「$N_{frames}\uparrow$ → $N_{vision}\uparrow$ → 质量↑、Encoder↑、Prefill↑、KV↑、Decode 带宽↑」。一个旋钮同时推动五项，且方向不全一致。

质量按双曲饱和增长（$K_v=4000$），成本按线性增长，因此存在闭式最优 $N^*=\sqrt{F'K_v/c_v}$。超过临界点 8537 后 Decode 进入带宽受限区，成本斜率再跳一档。

这解释了为什么「帧数」不能由业务方随意指定：它是一个同时决定质量、显存、并发与每成功任务成本的全局变量，必须平台侧统一设上限并按任务类型分档。

### 17.4 异构 CPU 与 GPU 阶段需要背压

机制链条是「四段资源速率不匹配 → 队列积压 → 等待线性发散」。CPU 预处理 2000 帧/s、Encoder 166.7 帧/s、网络 12.5 视频/s，三者容量相差一个数量级以上。

无背压时过载不会自愈：第 14.2 节显示 60 s 后等待达 16.8 s 且持续增长。有背压时超限触发采样率降级，把延迟爆炸转成质量损失，且因为原始配置本就过度，每成功任务成本反而下降 23.2%。

因此背压不是「限流保护」这么简单，而是**把不可控的延迟发散换成可控的质量降级**，前提是降级路径本身经过成本核算。

### 17.5 长 Decode 会与 Encoder 争用设备和内存

机制链条是「共卡 → 时间片竞争 → TPOT 按 $1/(1-u_e)$ 放大」。$u_e=76.8\%$ 时 TPOT 放大 4.31 倍，同 batch 的 32 个交互请求全部受影响。

分池消除争用但引入 feature 传输，传输成本在 PCIe 下仅 4.19 ms（占 TTFT 0.13%），跨节点 42.9 ms（1.33%）。因此争用成本远大于传输成本，$u_e>50\%$ 时分池必然更优。

该机制还有一层内存争用：Encoder 激活与 LLM KV 共享显存，视频 feature 缓存又占 128 MiB/条目。三者峰值不同时出现，必须分别设预算，否则「显存够用」的平均值会掩盖瞬时 OOM。

### 17.6 媒体解码和预处理位于 GPU 推理之前

机制链条是「入口串行 → 下载/解码阻塞 → 所有请求排队」。它在 GPU 之前，因此**加 GPU 完全无效**：第 15.3 节入口 80% 时间在下载时，GPU 利用率可能只有 20%。

资源账上它属网络与 CPU，而传统 LLM Serving 的监控通常只覆盖 GPU。这是多模态平台最容易漏掉的一整类瓶颈，也是「CPU 预处理成为隐藏瓶颈」这一失败模式的根源。

处置必须是异步 I/O + 独立线程池 + 下载超时与并发上限，并把网络与 CPU 指标纳入与 GPU 同等级别的观测。否则容量规划会持续加错资源。

## 18. 工程决策与取舍

### 18.1 选择图像分辨率或视频采样率

按第 8 节闭式最优 $N^*\approx6119$ 视觉 Token 配置默认档（24 帧 × 256），按第 7 节上下文与并发上限设硬顶。同预算下优先减帧而非降分辨率（第 8.3 节 TTFT 低 14.0%），时序敏感任务单独实测。分辨率与帧数共享同一上下文预算，不可独立配置。

### 18.2 部署独立或共置 Encoder

按第 13.4 节阈值：$u_e>50\%$ 分池，否则共卡。分池时优先同机跨卡（PCIe 4.19 ms），跨节点仅在 Encoder 需独立扩缩容或选异构硬件时采用。共卡必须限制 Encoder batch 与插入频率，避免交互长尾。

### 18.3 设计 Media Cache 键

五分量齐备：content digest、encoder revision、preprocess config、projector/model revision、tenant isolation。三层分别缓存，预算按收益密度分配（图片偏 Media、视频偏 Feature）。版本变更强制清对应层，不依赖键自然失效。

### 18.4 为预处理设置并发与背压

并发上限按 CPU 核数 / 单帧成本推算（16 线程 → 2000 帧/s），队列上限按可接受等待推算（4000 帧 ≈ 2 s）。超限触发采样率降级而非拒绝，降级原因写入结束原因字段。下载与解码必须在独立异步 I/O 与线程池，不得占用入口主线程。

### 18.5 分配 Encoder 和 Decode 设备

三类显存分别设预算：LLM KV、Encoder 激活、Feature 缓存。视频负载下 KV 是主约束（28 并发），Feature 缓存是次约束（1 GiB 仅 8 条）。跨模态位置方案须保证 Prefix 可复用，否则白扔 8.7% GPU 成本。

### 18.6 定义媒体错误回退

重试上限 2 次 + digest 级黑名单（TTL 1 h）+ 失败即释放槽位，三者同时落实。下载超时 5 s、并发上限按入口带宽推算。端到端成功率的分母必须含入口失败，否则 80 s 槽位耗尽事故在监控上不可见。

### 19.4 容量规划对照

实验必须同时输出两种规划口径的容量估计并对比：

- 按 QPS：$\text{Replica}=\lceil\lambda/\text{QPS}_{capacity}\rceil$；
- 按 stage work：$\text{Replica}=\lceil\sum_s W_s/\text{Capacity}_s\rceil$，其中 $s$ 遍历网络、CPU、Encoder、LLM 四类资源。

第 5.4 节已给出差异量级：视频负载下按请求数会高估 13.8 倍。实验需在三种 trace 上分别验证这一偏差，并确认按 stage work 规划后四类资源利用率均落在合理区间。

### 19.5 验收判据

- 默认档 $N_{vision}\approx6144$，每成功任务成本 $\le2100$ GPU-ms（推导预期 2089.0）；
- 视频 TTFT P99 按媒体类型单独设门禁，不与图片混合；
- 三层缓存命中时 TTFT 改善与第 11.3 节推导一致（视频 −28.5%、图片 −5.5%）；
- $u_e>50\%$ 时分池，且每 Token 成本低于共卡；
- 过载 120% 持续 60 s 时预处理等待 $\le2$ s（背压 + 降级生效）；
- 损坏率 5% 时槽位占用不随时间增长（三道防线生效）；
- 缓存键五分量齐备，版本变更后无跨版本命中；
- 跨模态位置方案变更后 Prefix 命中率不下降。

## 21. 常见追问与解答

**问 1：多模态容量到底该按什么规划？**
按四类资源分别规划：网络（入口带宽）、CPU（帧/s）、Encoder GPU（帧/s）、LLM GPU（Token 与 KV）。第 5.4 节显示按请求数会高估 13.8 倍，第 15.3 节显示入口带宽与 GPU 数量无关。任何单一总量指标都会漏掉至少一类瓶颈。

**问 2：视频默认抽多少帧合适？**
本文口径下最优约 24 帧 × 256 = 6144 视觉 Token（$N^*=\sqrt{687.5\times4000/0.0734375}\approx6119$），每成功任务成本 2089.0 GPU-ms。64 帧（16384）成本高 25.1%，计入 KV 带宽后高 35.2%。时序敏感任务需单独实测，不能直接套用。

**问 3：Encoder 和 LLM 一定要分池吗？**
不一定。判据是 $u_e>50\%$：低于此值共卡的统计复用更划算，高于此值分池即使多用一张卡也更便宜（$u_e=76.8\%$ 时每 Token 成本低 2.16 倍）。分池的传输成本在 PCIe 下仅占 TTFT 0.13%，不构成反对理由。

**问 4：Feature Cache 省得最多，为什么不全缓存它？**
因为体积也最大。视频 feature 128 MiB 是 raw bytes 的 12.8 倍，1 GiB 只能存 8 条，命中率必然极低。收益密度 Media 层 20.97 ms/MiB 高于 Feature 层 11.56 ms/MiB。应按「节省 × 频率 / 字节」分层分配预算。

**问 5：流水重叠能带来多少收益？**
上限等于非瓶颈阶段占比。LLM 占 93% 时最多省 7.0%；输出短、媒体重时能省 30.7%。因此必须先定位瓶颈再决定是否投入异步编排，否则复杂度上去了收益几乎没有。

**问 6：为什么视觉 Token 会拖慢 Decode？**
因为 Decode 每步读取全部历史 KV。17384 Token × 128 KiB × batch 28 = 60.05 GiB，除以 2 TB/s 得 31.9 ms/步，超过 20 ms 基线。临界点是视觉 Token 约 8500，超过后成本斜率从 0.0734 跳到 0.0931 GPU-ms/Token。

**问 7：背压为什么选降级而不是拒绝？**
因为原始 64 帧配置本就处于过度配置区。降到 16 帧后质量降 37.0%，但每成功任务成本反而降 23.2%，且队列立即排空。拒绝会损失全部任务价值，降级只损失部分质量——前提是降级档位经过成本核算。

**问 8：缓存键漏一个分量会怎样？**
不会报错，只会静默出错。漏 content digest → 70.8% 条目可能陈旧；漏 preprocess config → 2/3 概率取错分辨率；漏 revision → 输出乱码；漏 tenant → 数据泄露。所有性能指标正常，因此门禁必须落在输出质量与合规审计上。

## 22. 延伸练习

1. 把 $V$ 从 256 换成 1024，重算第 8 节的最优 $N^*$ 与对应帧数，并判断上下文上限是否先于成本最优成为约束。
2. 设 HBM 带宽从 2 TB/s 降到 1 TB/s，重算第 9 节的临界视觉 Token 数与修正成本表，判断最优点是否移动。
3. 推导 Encoder 池需要 $n_e>1$ 张卡时的分池盈亏平衡条件，并给出 $u_e=1.5$ 时的最优方案。
4. 设图片访问服从 Zipf 分布，推导 Media 层缓存容量与命中率的关系，求使 $h\ge99\%$ 的最小容量。
5. 把第 14 节的背压模型改为「拒绝」而非「降级」，推导端到端成功率与每成功任务成本，并与降级方案对比。
6. 为时序敏感任务设计 $Q(N_{frames},V)$ 的双变量质量模型，说明需要哪些实测数据才能标定，并指出本文单变量 $Q(N)$ 的适用边界。
7. 设 feature 需跨节点传输且带宽仅 1 GB/s，重算分池的 TTFT 与经济性，判断阈值 $u_e$ 如何移动。
8. 推导「媒体统一前置」对 Prefix 命中率的提升上限，并说明它与多轮对话中媒体位置变化之间的冲突如何处理。

- [ ] 版本变更强制清对应缓存层，不依赖键自然失效。
- [ ] Encoder 部署按 $u_e>50\%$ 阈值决定分池，并记录实测 $u_e$。
- [ ] 共卡时 Encoder batch 与插入频率受限，交互 TPOT 尖峰有门禁。
- [ ] 分池 feature 传输路径与带宽已记录，跨节点方案有 TTFT 占比核算。
- [ ] 预处理并发上限按 CPU 核数推算，队列上限按可接受等待推算。
- [ ] 背压超限触发采样率降级而非拒绝，降级原因写入结束原因字段。
- [ ] 下载与解码在独立异步 I/O 与线程池，入口主线程不被阻塞。
- [ ] 下载超时与并发上限按入口带宽配置。
- [ ] 媒体重试上限 2 次 + digest 黑名单 TTL 1 h + 失败即释放槽位，三者齐备。
- [ ] 端到端成功率分母含入口失败，峰值显存按 KV / 激活 / feature 三类分列。

## 24. 量化补充：三种表示与实时时间线

第 11 节的三层缓存可以落到具体字节。视觉 token 数 $n_v=H_{\mathrm{img}}W_{\mathrm{img}}/(p_{\mathrm{patch}}^2r^2)$：Qwen3-VL-4B 的 640×640 图按 16×16 patch 切 1600 块、2×2 合并得 400 token；最终特征 [400,2560] BF16 只 2 MB，但 DeepStack 另取三个中间层特征拼接成 [400,10240] 共 **7.8125 MiB**——特征宽度翻四倍、语言序列仍只增 400 token。同一张图三种表示对应三个交接位置与复用条件：压缩截图 0.8 MB（同文件内容）、EC 7.8125 MiB（图＋预处理＋编码器＋格式一致）、视觉 token 语言 KV 56.25 MiB（还依赖先前上下文与位置）——**问题放图前，换问题会改视觉 token 的 KV；放图后，因果注意力使此前视觉 KV 不变**。四图＋400 文本 token 的输入逻辑 KV 共 281.25 MiB；分辨率宽高各翻倍，token 数、EC、KV 都翻四倍，编码内部交互另按注意力结构算。输出是声音或图像时循环结构又不同：Fish Audio S2 Pro 每帧一次慢速前向建状态＋九次码本预测，一帧十次前向——语言 token/s、声学帧/s、每秒音频时长是三个速度；Qwen-Image 1024×1024 形成 4096 latent 位置、50 去噪步×true CFG 两支共 100 次 DiT 前向约 $7.83\times10^{15}$ FLOPs，总量 $n_sn_bF_{\mathrm{step}}(n_v)$：文本生成逐 step 追加上下文、访问量递增，去噪反复更新同一组 latent、固定分辨率下随步数线性增长。

实时播放要算缓冲曲线而非平均速率：$B_{\mathrm{audio}}(t)=A(t)-P(t)$，余量归零而下一块未到即中断。实测两次语音交互用户停说至首块到达约 400/370 ms，后续块间隔中位约 94 ms；教学时间线（每块 20 ms 960 B、处理 12 ms、发送 1 ms、传播 5 ms）首块 38 ms 到达、缓冲 40 ms 后 78 ms 首播，第三块传播抖到 50 ms 就晚到 5 ms 后续顺延；缓冲改 60 ms 停顿消失但首播推迟到 98 ms——**缓冲吸收短时抖动，长期到达速率低于播放速率时有限缓冲终究耗尽**。打断要分三个时刻：教学时序 123 ms 发打断、控制延迟 5 ms、设备每 10 ms 执行一次故 130 ms 静音（用户感受 7 ms），后端停生成与缓冲释放另走控制路径——停播放、停计算、释存储各自计时。输入端同样有时间约束：只在动作后观察会漏掉一闪而过的弹窗，AOI 类持续观测把采集与执行分开，但关键帧存多会挤占上下文，观测要配筛选。任务类型决定时间要求：语音要持续流畅，RAW 精修要尽早拿到完整成片（EC 替代不了原图），截图 Agent 要逐轮依赖尽早推进（完整链路账见 42 篇）。

## 写在最后

多模态 Serving 的核心不是「把 Encoder 接上 LLM」，而是承认一个请求的工作量分布在四种互不相同的资源上，且视觉 Token 会同时放大 Prefill、KV、Decode 带宽与上下文占用。本文的判据链条是：六段延迟分资源记账 → 视觉 Token 预算按闭式最优配置 → 缓存键五分量保证复用正确 → Encoder 部署按 $u_e$ 阈值决定 → 背压把延迟发散换成质量降级。任一环缺失，都会出现「GPU 利用率很低但请求排长队」这类加机器也解决不了的现象。
