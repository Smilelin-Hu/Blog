# MTP Serving：原生多 Token 预测头的部署

本文回答的问题是「如何把训练期 MTP 头转化为可测量、可回滚的推理加速路径？」。分析从原生 MTP 预测头与训练目标、服务目标的关系开始，随后落到计算模型、实现路径和发布验收。MTP Serving 会同时受到工作负载、模型修订、运行时调度、显存容量、并发状态与服务等级约束，因此需要把相关机制还原成可观察实体，再据此划定收益条件与额外成本。

证据分为机制模拟和真实 CUDA 测量：前者用可控变量观察原生 MTP 预测头怎样影响训练目标与服务目标，后者把框架、Kernel、内存和硬件成本计入结果。两条路径使用不同来源标签，并保留相关环境与限制；参数组合可以随版本改变，证据链仍要支持复现、定位和回退。

## 1. 内容概览

- 原生 MTP 预测头、训练目标与服务目标、MTP Depth 之间的状态与资源关系。
- 用 $Utility(d)=Saved\_target\_time(d)-MTP\_cost(d)-Verify\_overhead(d)$ 建立可计算的收益边界并解释全部变量。
- 围绕 MTP 头准确率、位置接受率、服务加速比和回退率设计可复现实验。
- 识别训练指标提升但接受长度不变、MTP 头与主干权重错配、代码任务有效而对话退化等典型失败模式。
- 对中心问题给出包含适用条件、证据、风险和回滚的工程答案。

## 2. 核心直觉：MTP 为什么适合当 Speculator

如果目标模型内部已经有未来 Token 预测模块：

![Target hidden 复用：主 head 与 MTP head 各预测一位](https://raw.gitcode.com/weixin_42917352/image-host/raw/main/images/aiinfra_y3_l05_03.png)

优势是：

- 不需要再部署一个完整独立小语言模型；
- 可能复用 Target 的 embedding 与 hidden state；
- 模型作者已经在训练阶段注入未来 Token supervision；
- checkpoint 与 Target 结构天然关联。

但注意：「模型有 MTP 模块」不等于「线上打开一个参数就一定获得加速」。必须看 Runtime 是否支持、MTP head 质量、验证路径、并发与硬件。

## 3. 前置知识与实验环境

需要理解自回归生成、Tokenizer、Prefill、Decode、KV Cache、批处理和分位延迟的基本含义。所有缩写都会在正文首次出现处定义；没有某个特定框架经验不妨碍理解机制。实验需要 Python 3.11 或兼容版本。机制模拟只依赖 CPU；真实路径需要任意可用的 CUDA GPU、与驱动兼容的 PyTorch，以及自行准备的本地小模型或兼容制品。

验证前必须记录 GPU 名称、数量、可用显存、驱动、CUDA、PyTorch、推理框架、模型摘要、精度、批量、序列长度和完整命令。脚本根据可用显存缩放模型、批量、上下文和样本数，并把原生 MTP 预测头状态写入报告；可选 CUDA 入口不下载未经确认的大模型。

评估时先不要回答「打开以后能快多少」。需要固定模型与修订、输入输出长度分布、到达过程、并发、采样、缓存状态、MTP 头准确率口径、服务等级和硬件环境，再评审「选择可部署的 MTP 深度」和「是否微调 MTP 头」。这些条件共同决定收益、成本和资源竞争。

## 4. MTP Training 与 MTP Serving 不是同一件事

训练阶段可能使用带 MTP 辅助损失的联合目标：

$$\mathcal{L}=\mathcal{L}_{next}+\lambda\sum_{k=1}^{K}\mathcal{L}_{mtp,k}$$

它的目的可能包括改善 representation、提高 sample efficiency、为未来 speculative inference 提供 head。

Serving 阶段关注的则是：

$$Speedup=f(HeadQuality,\ HeadCost,\ VerifyCost,\ Concurrency)$$

一个训练上有益的 MTP head，如果推理时额外计算很重或 acceptance 不高，未必适合 Serving。这是「训练损失改善不保证服务净收益」的根源：训练目标里的 $\lambda$ 权衡的是表示质量，服务目标权衡的是每轮净节省时间，两者不是同一个函数。

## 5. MTP Depth 的选择

### 5.1 存活概率与扫描

假设有 $K$ 个未来 heads。更深的 head 通常预测更难，因此可以定义：

$$a_k=P(\text{head }k\text{ survives prefix verification})$$

在线上不应默认全部开启，而应根据真实数据扫描。一组示例读数如下（示意口径，非本机实测）：

![ai3-05-L68](https://raw.gitcode.com/weixin_42917352/image-host/raw/main/images/aiinfra_y3_l05_02.png)

最优点由实际性能决定，而不是由 head 数量决定。

### 5.2 Utility 模型

把一轮的净收益写成：

$$Utility(d)=Saved\_target\_time(d)-MTP\_cost(d)-Verify\_overhead(d)$$

三项含义分别是：相比自回归少执行的 Target 前向所节省的时间、MTP 头自身带来的额外成本、以及因为验证更多候选而增加的验证开销。只有 $Utility(d)>0$ 才值得启用该深度。

一轮总成本可抽象为：

$$T_{MTP}=T_{feature}+T_{heads}(K)+T_{verify}(K)+T_{commit}$$

如果多个 head 真正并行，$T_{heads}(K)$ 增长可能较慢；如果实现仍然串行或触发多个小 Kernel，则优势会被 Runtime overhead 抵消。

### 5.3 深度扫描推导

取一组推导设定（非实测）：自回归每 Token 需 $8.31$ ms；$T_{feature}=0.5$ ms、$T_{commit}=0.3$ ms；并行 heads 成本 $T_{heads}(d)=0.4+0.1d$ ms；验证成本 $T_{verify}(d)=8+0.3d+0.01d^2$ ms；每轮提交 Token 数沿用第 5.1 节示例读数。

| Depth $d$ | 每轮提交 | $T_{heads}$ | $T_{verify}$ | $T_{MTP}$ | $T_{effective}$ | 加速比 | $Utility$ |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 1.8 | 0.5 ms | 8.31 ms | 9.61 ms | 5.34 ms | 1.56× | 5.35 ms |
| 2 | 2.5 | 0.6 ms | 8.64 ms | 10.04 ms | 4.02 ms | 2.07× | 10.74 ms |
| 4 | 3.0 | 0.8 ms | 9.36 ms | 10.96 ms | 3.65 ms | 2.27× | 13.97 ms |
| 8 | 3.1 | 1.2 ms | 11.04 ms | 13.04 ms | 4.21 ms | 1.98× | 12.72 ms |

在这组假设下最优深度为 4：深度从 4 增到 8，每轮提交只多 0.1 个 Token，而验证成本增加 1.68 ms、heads 成本增加 0.4 ms，净收益反而下降。这正是「深度增加会提升候选数量也会累积低置信位置」的定量形式。

### 5.4 串行 head 实现的对照

若实现未能真正并行，heads 成本变为 $T_{heads}(d)=0.5d$ ms，其余设定不变（推导值，非实测）：

| Depth $d$ | $T_{MTP}$ | $T_{effective}$ | 加速比 | $Utility$ |
| --- | --- | --- | --- | --- |
| 1 | 9.61 ms | 5.34 ms | 1.56× | 5.35 ms |
| 2 | 10.44 ms | 4.18 ms | 1.99× | 10.34 ms |
| 4 | 12.16 ms | 4.05 ms | 2.05× | 12.77 ms |
| 8 | 15.84 ms | 5.11 ms | 1.63× | 9.92 ms |

最优点仍在 4，但净收益从 13.97 ms 降到 12.77 ms，深度 8 的收益从 12.72 ms 降到 9.92 ms。同一个模型、同一组头，仅因为实现方式不同就损失了可观收益——因此「Runtime 是否真正并行执行 heads」必须作为测量项，而不是假设。

### 5.5 额外显存的量级推导

MTP 头的显存增量取决于是否共享词表投影。取 $d_{model}=4096$、词表 $V=128000$、fp16（推导设定，非实测）：

| 头结构 | 单头参数量 | 单头显存 | $K=4$ | $K=8$ |
| --- | --- | --- | --- | --- |
| 独立词表投影 $d\times V$ | 约 $5.24\times10^8$ | 约 0.98 GiB | 约 3.9 GiB | 约 7.8 GiB |
| 共享词表投影 + $d\times d$ 变换 | 约 $1.68\times10^7$ | 约 32 MiB | 约 128 MiB | 约 256 MiB |

两者相差约 32 倍。若每个头都带独立词表投影，8 个头的显存增量可能直接挤掉 KV Cache 容量，表现为「深度增加造成验证和显存反噬」；若共享词表投影，增量则在百 MiB 量级。因此 extra VRAM 必须与头结构一起报告，不能只报一个总数。

## 6. 域适配：为什么同一个 MTP 在代码上很好，在开放聊天上可能一般

MTP 学到的是未来 Token 条件分布。如果上线 workload 与训练分布不同：

$$P_{train}(x)\neq P_{serve}(x)$$

则 acceptance 可能明显下降。因此可以针对 code、math、reasoning、customer-service、JSON/tool call 分别做轻量 MTP finetune 或 calibration。

但必须同时确认一个前提：**只微调 MTP 模块是否保持 Target 主模型输出分布不变？** Speculator 可以改变候选，但最终 Target verification 仍需保证结果正确。若微调过程触及主干权重或共享 embedding，就不再是「只调 Speculator」，必须按主模型变更走完整发布门禁。

## 7. MTP Checkpoint 生命周期

一个生产平台至少要记录：

```text
Target model revision
Target tokenizer revision
MTP speculator revision
MTP depth
Training dataset/version
Runtime version
Compatibility hash
```

不能只把文件名写成：

```text
mtp_final.pt
```

因为 Target 升级后，旧 MTP 可能直接不兼容或 acceptance 下降。Compatibility hash 应由上述字段共同计算，加载时校验；校验失败必须拒绝启用 MTP 并回退到普通自回归路径，而不是尝试加载后观察输出是否异常。

## 8. MTP 与 Multi-LoRA 的组合

### 8.1 四种策略

这是生产环境里很容易遗漏的组合问题。如果 Base Model 上叠加不同 LoRA：

```text
Base + LoRA A
Base + LoRA B
```

Target 输出分布已经发生变化。原来针对 Base 训练的 MTP speculator 是否仍然有高 acceptance，需要单独验证。可能的策略：

1. Base 共用 MTP，接受 acceptance 下降；
2. 热门 LoRA 单独适配 MTP；
3. 低流量 LoRA 关闭 MTP；
4. Router 根据 adapter id 选择 speculator policy。

四种策略不是互斥的：常见做法是按 adapter 流量分层，热门 LoRA 单独适配，长尾 LoRA 共用或直接关闭，并由 Router 按 adapter id 下发策略。

### 8.2 acceptance 下降的定量影响与关闭阈值

沿用第 5.3 节 Depth 4 的并行设定（$T_{MTP}=10.96$ ms，自回归每 Token 8.31 ms），观察每轮提交 Token 数下降时的结果（推导值，非实测）：

| 每轮提交 Token | $T_{effective}$ | 加速比 | $Utility$ |
| --- | --- | --- | --- |
| 3.0（Base） | 3.65 ms | 2.27× | 13.97 ms |
| 2.2（LoRA 轻度退化） | 4.98 ms | 1.67× | 7.32 ms |
| 1.5（LoRA 明显退化） | 7.31 ms | 1.14× | 1.51 ms |
| 1.2（LoRA 严重退化） | 9.13 ms | 0.91× | −0.99 ms |

关闭阈值可以直接解出：当每轮提交 Token 数低于 $T_{MTP}/8.31=10.96/8.31\approx1.32$ 时，$Utility$ 转负，MTP 反而更慢。这给「低流量 LoRA 关闭 MTP」提供了可计算依据，而不是凭经验设定。阈值随 $T_{MTP}$ 与基线延迟变化，需要按实际测量重算。

## 9. 性能模型与必测指标

真实测试至少采集七项：

- MTP forward latency；
- Target verify latency；
- mean accepted length；
- per-position acceptance；
- TPOT；
- total throughput；
- extra VRAM。

前两项对应 $T_{heads}$ 与 $T_{verify}$，中间两项对应候选质量，后三项对应端到端结果与资源代价。缺少 extra VRAM 会漏掉显存反噬；缺少 per-position acceptance 会漏掉深位置崩塌；缺少 TPOT 与 throughput 则无法判断收益是否进入系统层面。

所有指标都要注明单位、统计窗口和分母。加载时间、Adapter 切换延迟、回退率、域内外差异同样需要口径，否则上线后无法复核。

## 10. 八个概念的边界与失败模式

分析范围由八个可观察概念组成：原生 MTP 预测头、训练目标与服务目标、MTP Depth、Target 主干复用、Checkpoint 绑定、域适配、多 LoRA 条件、服务引擎接口。算法层的变化会经运行时和平台层传到 Adapter 切换延迟与回退率。每个概念都绑定具体状态、责任边界、观测字段和故障表现。

### 10.1 统一检查框架

每个概念都按同一组问题展开：边界与生命周期（输入、输出、状态归属、销毁时点、失败传播）、资源账（计算、显存、内存带宽、主机开销、同步等待分别记账）、负载区间（低载、接近饱和、过载三段同口径）、正确性门禁（Token 序列、采样分布、结构合法性、结束原因、错误传播）、观测字段（请求身份、模型与策略修订、起止时间、阶段耗时、资源快照、失败原因）。跨概念传递的数据必须携带版本身份。

### 10.2 原生 MTP 预测头

边界由输入、输出、状态和拥有者共同确定；连接训练目标与服务目标时要传播身份和版本。测量分别记录算力、显存、带宽、CPU 开销与同步。训练损失改善不保证服务净收益，缩短的阶段可能让另一项资源成为瓶颈，因此分析要对齐阶段事件和资源轨迹，不让单个平均利用率代替因果证据。

「如何绑定制品版本」至少比较低载、临近容量与过载。典型失败是多 LoRA 热切换后缓存污染：质量结果优先于速度数字，发布停止，流量回到已验证修订，相关请求留作重放。加载时间同时注明单位、窗口和分母。

### 10.3 训练目标与服务目标

先列出接收什么、产生什么、由谁维护以及状态何时结束；与 MTP Depth 交互的字段必须携带版本身份。深度增加会提升候选数量也会累积低置信位置，会移动关键路径，却很少让所有资源同比例变化。

「按域启用或禁用」是否合适，取决于长度分布、并发、到达过程、采样和任务域。典型失败是引擎只支持部分模型架构，质量门禁应停止性能发布，回退目标是已验证配置并保留问题请求。域内外差异没有单位、统计窗口和分母时不参与决策。

### 10.4 MTP Depth

生命周期落到组件接口，并与 Target 主干复用绑定身份和版本。Checkpoint 与分词器及主干修订必须一致，其影响分散到计算、显存、内存带宽、主机处理和同步等待；某一阶段变短时，被遮蔽的成本可能随即暴露。

「为 Adapter 共享还是专用 MTP」的验证分别运行三段负载并使用代表性分布。典型失败是深度增加造成验证和显存反噬：当前性能结果不进入候选评审，立即切回已验证配置。Adapter 切换延迟的定义随报告存档，包括单位、窗口和分母。

### 10.5 Target 主干复用

边界检查覆盖输入、输出、状态归属和销毁时点；传给 Checkpoint 绑定的数据应附带版本。域适配改变未来 Token 的可预测性，通常只先改变资源账中的几项，其他资源随后可能进入关键路径。

「选择引擎回退路径」应覆盖长短输入、不同输出、并发、突发、采样与任务域。典型失败是训练指标提升但接受长度不变，触发停止与回退。回退率必须附带口径。

### 10.6 Checkpoint 绑定

边界由输入、输出、状态和拥有者共同确定；连接域适配时要传播身份和版本。多 LoRA 会让共享 MTP 的条件分布发生变化，缩短的阶段可能让另一项资源成为瓶颈。

「选择可部署的 MTP 深度」至少比较低载、临近容量与过载。典型失败是 MTP 头与主干权重错配：质量结果优先于速度数字，发布停止，流量回到已验证修订。MTP 头准确率同时注明单位、窗口和分母。

### 10.7 域适配

先列出接收什么、产生什么、由谁维护以及状态何时结束；与多 LoRA 条件交互的字段必须携带版本身份。MTP 头复用 Target 表示预测未来多个位置会移动关键路径，却很少让所有资源同比例变化。

「是否微调 MTP 头」是否合适，取决于长度分布、并发、到达过程、采样和任务域。典型失败是代码任务有效而对话退化，质量门禁应停止性能发布。位置接受率没有单位、统计窗口和分母时不参与决策。

### 10.8 多 LoRA 条件

生命周期落到组件接口，并与服务引擎接口绑定身份和版本。训练损失改善不保证服务净收益，其影响分散到五项资源；为确认变化来自哪里，要对齐请求时间线与资源采样，而非只看整段运行的 GPU 平均值。

「如何绑定制品版本」的验证分别运行三段负载并使用代表性分布。典型失败是多 LoRA 热切换后缓存污染：当前性能结果不进入候选评审，立即切回已验证配置。服务加速比的定义随报告存档，包括单位、窗口和分母。

### 10.9 服务引擎接口

边界检查覆盖输入、输出、状态归属和销毁时点；传给原生 MTP 预测头的数据应附带版本。深度增加会提升候选数量也会累积低置信位置，通常只先改变资源账中的几项。

「按域启用或禁用」应覆盖长短输入、不同输出、并发、突发、采样与任务域。典型失败是引擎只支持部分模型架构，触发停止与回退，系统恢复到已有证据支持的配置。额外显存必须附带口径。

## 11. 六个机制的因果分析

![MTP Serving 的机制与证据闭环](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y3_l05_01.png)

*机制流程：把 MTP 部署的输入、关键决策、执行与证据闭环连接起来。*

核心关系写作 $Utility(d)=Saved\_target\_time(d)-MTP\_cost(d)-Verify\_overhead(d)$。它是一项组织变量的近似模型，不代表供应商基准。建模时把原生 MTP 预测头和训练目标与服务目标设为可控因素，工作负载、模型及硬件作为条件，MTP 头准确率、额外显存和回退率作为结果。时间量统一单位，概率限定在零到一，吞吐量明确计数对象。框架队列、Kernel 启动、分配器、网络、客户端与取消不在近似中，真实实验需要补齐；方向冲突通常意味着变量或测量口径遗漏。

### 11.1 机制 1：MTP 头复用 Target 表示预测未来多个位置

这一机制会改写请求的阶段顺序。画出变化前后的关键路径，标明并行、串行和跨请求合批位置；原生 MTP 预测头给出状态条件，MTP 头准确率验证结果是否传到请求端。

单请求数据不足以评价：低载用于测量固定成本，接近容量时观察批处理与共享资源，过载时确认拒绝和尾延迟。「MTP 头与主干权重错配」若只在并发后出现，优先检查候选路径对正常请求资源的挤占。

数据格式、张量形状、缓存身份、版本兼容和错误传播共同构成实现边界；「如何绑定制品版本」需要在合同冻结后测试正常、无效、极端和资源受限输入。证据需要成对的原因和结果字段：原因包括决策特征、阈值和候选，结果包括额外显存、错误、取消和资源快照。发布时配置独立开关、灰度身份、停止条件和暖回滚目标；「引擎只支持部分模型架构」触发后只撤回相关变化，并继续检查在途请求、缓存和资源释放。

### 11.2 机制 2：训练损失改善不保证服务净收益

把前后两条请求时间线对齐，逐段标出可并行、必须串行和允许合批的工作。训练目标与服务目标说明机制何时生效，位置接受率负责确认关键路径是否真的缩短。

分别施加轻载、稳定高载和过载流量，可以分辨同步开销、队列增长、合批变化与资源竞争。检测到代码任务有效而对话退化后，沿共享执行资源检查局部收益为何没有进入系统 Goodput。

确定接口时同时规定数据与 Shape、缓存和版本身份、错误及回退，随后以无效输入、极端长度和资源不足验证「按域启用或禁用」。观测时原因侧保存策略输入、阈值和候选集合，结果侧保存加载时间、错误、取消与资源；两侧对齐后可以区分收益不足、选择错误、实现开销偏大和工作负载漂移。该机制通过独立开关进入灰度，出现深度增加造成验证和显存反噬时撤回本项候选。

### 11.3 机制 3：深度增加会提升候选数量也会累积低置信位置

先记录原路径，再记录候选路径中的串行、并行与合批段，同时保存 MTP Depth 状态和服务加速比。容量评估放在三个负载区间中运行；「多 LoRA 热切换后缓存污染」意味着候选工作可能消耗了服务正常请求所需的容量。

实现时明确数据格式、张量形状、缓存身份、版本兼容和错误回退；执行「为 Adapter 共享还是专用 MTP」前冻结接口合同，并加入无效输入、极端长度与资源不足测试。Trace 同时记录决策输入与执行结果，后者含域内外差异、错误、取消和资源变化。上线合同写明灰度范围、停止条件、开关和暖回滚目标；训练指标提升但接受长度不变发生后，系统恢复相关稳定配置，并持续观察请求排空、缓存切换和资源回收。

### 11.4 机制 4：Checkpoint 与分词器及主干修订必须一致

从请求关键路径入手，标注变化前后每个阶段的顺序、并行性和合批条件，Target 主干复用作为启用条件，额外显存作为端到端结果。

容量测试覆盖低载、稳定高载和过载。若出现引擎只支持部分模型架构，说明局部延迟没有变成有效容量，需要核对候选工作占用的公共资源。接口合同包括格式、Shape、缓存键、版本与回退语义；「选择引擎回退路径」进入评审前，使用非法输入、边界长度和资源不足场景检验保护路径。

采集证据时把策略输入、阈值、候选集合与 Adapter 切换延迟、错误、取消及资源事件放进同一请求链。发布单元包含灰度身份、门禁、停止动作和已预热回滚路径；检测到 MTP 头与主干权重错配后执行局部撤回，并确认在途工作、缓存与资源回到稳定状态。

这一机制会改写请求的阶段顺序。画出变化前后的关键路径，标明并行、串行和跨请求合批位置；Checkpoint 绑定给出状态条件，加载时间验证结果是否传到请求端。

## 12. 工程决策与取舍

### 12.1 选择可部署的 MTP 深度

以 $Utility(d)$ 最大化为目标，在真实负载上扫描 $d=1,2,4,8$，并同时记录 extra VRAM 与验证成本。低载最优点与高载最优点可能不同：高载下验证容量共享，最优深度通常更小。最终配置应取两个区间都可接受的深度，或交由动态策略按负载调整。

### 12.2 是否微调 MTP 头

当服务域与训练域差异显著、且该域流量占比高时，轻量 finetune 或 calibration 值得投入。前提是只改 MTP 模块、不动主干与共享 embedding，并重新校验输出分布不变。微调后必须重新绑定 Compatibility hash，不能沿用旧制品身份。

### 12.3 如何绑定制品版本

采用第 7 节的七字段清单加 Compatibility hash，加载时强校验。校验失败即拒绝启用 MTP 并回退自回归路径，同时记录失败原因。制品身份需要进入请求级 Trace，使任何一次加速比都能追溯到唯一配置。

### 12.4 按域启用或禁用

按域分桶测量 acceptance 与 $Utility$，对负收益域直接禁用。禁用策略应可热更新，并记录生效时间与流量身份，便于回滚与复核。域划分本身需要版本化，避免域定义变化导致历史结论不可比。

### 12.5 为 Adapter 共享还是专用 MTP

按 adapter 流量分层：热门 LoRA 单独适配 MTP，长尾 LoRA 共用 Base MTP 或关闭。判据是第 8.2 节的关闭阈值与该 adapter 的流量权重——专用 MTP 的维护成本只有在流量足够大时才被摊薄。

### 12.6 选择引擎回退路径

引擎只支持部分模型架构是常态。回退路径必须事先定义并测试：MTP 不可用时退回普通自回归，而不是报错或静默降级到未验证配置。回退率是核心观测指标，回退率突增通常意味着制品错配、引擎版本变化或显存不足。

## 13. 实验设计：Level 0 模拟与 Level 2 实测

本主题复用 Speculator Benchmark 项目的 MTP 路径，先做 Level 0 模拟：

- 设置 1/2/4/8 个 heads；
- 为更深 head 设置不同 acceptance；
- 设置并行与串行两种 head cost；
- 扫描并发。

模拟应能复现第 5.3 与 5.4 节的方向：最优深度出现在中等值、串行实现削弱收益、深度过大时验证与显存反噬。运行方式沿用统一约定：默认 Fixture，`--check-only` 只做预检，`--real` 进入实测路径。

Level 2 使用实际支持 MTP 的模型与 Runtime 时，必须记录具体模型 revision 和 Runtime 版本，不把一个模型结果泛化到所有 MTP 模型。真实路径采集第 9 节七项指标，外加加载时间、Adapter 切换延迟、回退率与域内外差异。预检记录完整环境，显存不足时按约定缩放并给出可识别退出码。只有 `source=measured` 可以支撑性能或发布结论。

## 14. 常见错误与排查

| 现象 | 可能原因 | 排查方向 |
| --- | --- | --- |
| 打开 MTP 参数后没有加速 | Runtime 未真正支持或未并行执行 heads | 分别计时 MTP forward 与 Target verify |
| 训练 loss 改善但接受长度不变 | 训练目标与服务目标不一致 | 改看 per-position acceptance 与 $Utility$ |
| 深度增大后反而更慢 | 低置信位置累积，验证与显存反噬 | 扫描 $Utility(d)$，记录 extra VRAM |
| 显存增量远超预期 | 每头带独立词表投影 | 核对头结构，考虑共享词表投影 |
| 加载后输出异常或崩溃 | MTP 头与主干权重错配 | 校验 Compatibility hash，拒绝启用并回退 |
| Target 升级后 acceptance 下降 | 制品绑定缺失 | 重新绑定修订并重新评测 |
| code 很快、对话变慢 | 域适配不足 | 按域分桶评测，按域启用或微调 |
| 挂上 LoRA 后收益消失 | 共享 MTP 条件分布变化 | 按 adapter 测量，套用关闭阈值 |
| Adapter 切换后结果串味 | 热切换缓存污染 | 校验缓存键含 adapter 与制品身份，切换时失效 |
| 回退率突增 | 引擎版本变化或显存不足 | 检查回退原因分类与资源快照 |
| 加速比无法复核 | 口径缺失 | 补齐单位、统计窗口与分母 |

## 15. 常见追问与解答

**问：模型自带 MTP 模块就一定能加速吗？**
答：不一定。还要看 Runtime 是否支持、heads 是否真正并行、head 质量、验证路径、并发与硬件。任一环节不满足都可能没有净收益。

**问：训练时 MTP 损失下降，为什么服务没变快？**
答：训练目标权衡的是表示质量与 sample efficiency，服务目标权衡的是每轮净节省时间。两者不是同一个函数，必须用 $Utility(d)$ 与接受长度重新评价。

**问：MTP 深度怎么选？**
答：在真实负载上扫描并取 $Utility$ 最大的深度，同时检查 extra VRAM 与验证容量。低载与高载最优点可能不同，需要分别记录。

**问：为什么 heads 串行执行会削弱收益？**
答：$T_{heads}$ 从近似固定变成随深度线性增长，直接抬高 $T_{MTP}$。第 5.4 节推导显示同一模型仅因实现方式不同就损失可观净收益。

**问：只微调 MTP 头安全吗？**
答：前提是主干与共享 embedding 不变，且 Target verification 仍保证输出分布。若触及主干，就必须按主模型变更走完整门禁。

**问：Multi-LoRA 下 MTP 怎么处理？**
答：按 adapter 流量分层：热门单独适配、长尾共用或关闭，Router 按 adapter id 下发策略。关闭阈值可由 $Utility$ 转负的条件解出。

**问：Checkpoint 需要记录哪些字段？**
答：Target 模型修订、Target tokenizer 修订、MTP speculator 修订、MTP depth、训练数据集版本、Runtime 版本与 Compatibility hash。只写文件名不足以证明兼容性。

**问：回退路径应该怎么设计？**
答：MTP 不可用时退回普通自回归，并记录回退原因与回退率。回退必须是已验证配置，不能静默降级到未测试组合。

- [ ] 低载、接近饱和、过载三段使用同一口径证据。
- [ ] 域内外分别评测，负收益域已禁用。

- [ ] 输出合同校验通过：Token 序列、采样分布、结构合法性、结束原因、错误传播。

- [ ] 独立开关、灰度身份、停止阈值与已预热回滚修订就位。
- [ ] 撤回后核对在途请求、缓存状态与资源释放。

## 写在最后

原生 MTP 头把 Speculator 的制品成本降到很低，但「模型自带模块」与「线上获得净收益」之间还隔着 Runtime 支持、头质量、验证成本、显存结构与域适配五道关。用 $Utility(d)$ 把节省与成本放在同一口径下，再用 Compatibility hash 与按 adapter 的策略把配置绑定住，MTP 才能成为可测量、可回滚的加速路径。
