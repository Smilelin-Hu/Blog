## 5. 知识串讲

### 核心直觉与基础关系

### 核心直觉：模型启动首先是大规模数据分发问题

百 GB 权重在几十或上百个节点同时启动时，对象存储、网络和本地缓存会形成新的“启动数据面”。先算数据搬运下限，再谈框架启动优化。

模型文件总大小 $S$，有效带宽 $B_{eff}$：

$$T_{download}\ge \frac{S}{B_{eff}}$$

100GB 模型，实际有效下载 2GB/s：

$$T\ge50s$$

还没算：

- connection setup；
- checksum；
- decompression；
- metadata；
- filesystem；
- deserialization；
- H2D。

所以“秒级扩容”对大模型通常需要提前缓存/预热，而不是临时从远端完整拉取。

### Single Large File vs Shards

### 单文件

优点：metadata 少。

缺点：单流可能吃不满带宽，失败重试成本大。

### 多 Shard

```text
model-00001
model-00002
...
```

可以并行下载：

$$T\approx \max_i T_{shard,i}$$

但 shard 太多会增加：

- list/stat；
- open/close；
- small file overhead；
- checksum；
- filesystem metadata pressure。

最优 shard size 依赖存储系统。

### 并行下载不是线程越多越快

有效吞吐：

$$B_{total}(n)=\min(nB_{stream},B_{network},B_{storage},B_{disk})$$

并发超过瓶颈后，只会：

- 增加连接数；
- 抢占带宽；
- 造成抖动；
- 影响别的节点扩容。

需要在真实对象存储/网络上扫并发。

### Thundering Herd：一次扩100个 Replica

如果 100 个节点同时下载 100GB：

$$TotalData=10TB$$

即使单节点带宽足够，中央对象存储出口可能被打满。

解决思路：

- node-local cache；
- rack/local mirror；
- peer-to-peer distribution；
- prefetch；
- staggered rollout；
- shared high-throughput filesystem。

### Node-Local Cache

节点本地 NVMe 保存常用模型：

![ai3-22-L123](https://raw.gitcode.com/weixin_42917352/image-host/raw/main/images/aiinfra_y3_l22_02.png)

之后扩容：

$$T_{remote-download}\rightarrow T_{local-read}$$

但要解决：

- cache size；
- eviction；
- checksum；
- revision；
- security；
- disk wear；
- namespace isolation。

### Weight Cache Key

必须以 immutable artifact identity 为基础：

$$Key=Hash(ModelRevision,ArtifactDigest)$$

不能只按 `model_name`，否则模型同名升级后会读取旧缓存。

### Deserialize / Map 也可能很慢

权重下载到磁盘后，还可能：

- Python/框架解析 config；
- mmap；
- tensor metadata；
- CPU page fault；
- dtype conversion；
- quantization de/packing；
- H2D。

所以 Startup Trace 应包含：

```text
resolve
fetch
verify
deserialize
host_map
gpu_load
engine_init
warmup
```

而不是只有一个 `model_load_ms`。

### Overlap

有些步骤可以流水化：

![权重加载流水线：下载与加载重叠](https://raw.gitcode.com/weixin_42917352/image-host/raw/main/images/aiinfra_y3_l22_03.png)

理想启动时间接近最慢流水阶段，而不是所有阶段简单相加。

但前提是 Runtime 支持分 shard 流式加载，不能假设所有框架都可自动 overlap。

评估启动关键路径需要把负载分布写入实验：输入输出长度、并发、到达突发、采样方式和业务域都可能移动收益边界。安排校验与解压至少比较低载、临近容量与过载，结论只覆盖实际运行过的区间。

启动关键路径进入候选路径后，输出校验继续检查 Token、采样、结构、结束原因和错误传递。GPU 等待串行 CPU 读取一旦出现，质量结果优先于速度数字；发布停止，流量回到已验证修订，相关请求留作重放。

观察启动关键路径需要稳定请求身份、模型与策略修订、起止时间、阶段耗时、资源快照和失败原因。校验时间同时注明单位、窗口和分母。这些字段使“如何定位存储、并发读取、分片布局和 GPU 装载中的启动瓶颈？”可以在发布后按原条件回放。

### 机制 1：大模型权重按分片从远端或本地存储读取

分析“大模型权重按分片从远端或本地存储读取”时，把前后两条请求时间线对齐，逐段标出可并行、必须串行和允许合批的工作。权重分片说明机制何时生效，下载吞吐负责确认关键路径是否真的缩短。

对“大模型权重按分片从远端或本地存储读取”分别施加轻载、稳定高载和过载流量，可以分辨同步开销、队列增长、合批变化与资源竞争。检测到小分片导致请求开销过大后，沿共享执行资源检查局部收益为何没有进入系统 Goodput。

观测“大模型权重按分片从远端或本地存储读取”时，原因侧保存策略输入、阈值和候选集合，结果侧保存校验时间、错误、取消与资源。两侧对齐后，可以区分大模型权重按分片从远端或本地存储读取收益不足、选择错误、实现开销偏大和工作负载漂移。
