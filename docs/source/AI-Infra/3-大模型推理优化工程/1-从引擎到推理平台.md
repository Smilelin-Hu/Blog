# 从推理引擎性能到生产级推理平台

同一块 GPU 上「怎么让 Token 出得更快」只是问题的一小部分。真实服务面对的是持续到达、形态不一的请求，变化的并发，不同长度，多模型版本、多租户、跨副本缓存、发布与故障。单引擎每秒 Token 再高，只要流量被送到错的副本、模型启动太慢、长请求堵住交互请求、取消没有传下去，用户体验与单位成本依然很难看。

## 1. 三个平面

### 1.1 数据面

承载高频热路径：协议解析、请求调度、模型执行、KV Cache、Token 流与必要的数据传输。目标是**低延迟、可预测、可背压**。

两个纪律：热路径不同步访问慢速控制数据库，也不依赖不稳定的远程配置；路由规则、模型元数据、配额快照以可更新的本地结构进入热路径。

数据面的状态分两类：请求队列、采样器属于**短暂状态**；模型权重、CUDA Graph、KV Cache、媒体特征缓存属于**昂贵状态**。恢复策略取决于状态价值——能丢的丢，能转的转，需要就靠版本与校验重建。把所有状态都当无状态 Web 服务，会严重低估恢复成本。

### 1.2 控制面

负责低频高影响的决策：注册模型、创建部署、选并行策略、分配 GPU、扩缩容、发布、回滚、排空、故障替换。它必须接受观测延迟与最终一致性：Pod 已经 Running，不代表权重加载完、引擎预热完。

健康状态至少要分三层：**进程存活、模型就绪、真实推理路径可用**。

控制面最重要的不是 API 数量，而是**状态机与不变量**：

- 一个修订版在被路由前必须通过制品校验 → 加载 → 预热 → Canary；
- 一个副本在删除前必须停止接新请求，并等待在途请求完成或迁移；
- 一次扩容决策必须把「已创建但尚未就绪」的容量算进去，否则会重复扩容。

### 1.3 证据面

收集请求级 Trace、引擎指标、队列与缓存事件、部署状态、版本信息、成本归属与实验记录。它和「监控面板」的区别在于：能从用户症状反查到模型修订、路由选择、工作器状态与具体执行阶段；也能把优化前后放在同一个工作负载下比较。

指标看趋势、日志记事实、Trace 表达跨组件因果、事件流重建控制器与缓存状态——四者不可互相替代。

## 2. 请求生命周期

```text
客户端 → Gateway 校验/规范化 → 全局路由 → 工作器排队 → 预处理 → Prefill
      → 首 Token → 循环 Decode → 流式传输 → 结束处理 → 计量落账
```

$$
T_{e2e} = T_{gateway} + T_{route} + T_{queue} + T_{preprocess} + T_{prefill} + T_{decode} + T_{stream} + T_{post}
$$

这个求和式的价值是**检查清单**，不是物理定律：流式返回时服务端仍在 Decode（重叠），媒体预处理与 Tokenizer 会争 CPU（共享），路由到有前缀缓存的副本会减少 Prefill（改变后续成本）。真实分析要用 Trace 识别重叠与等待。

三个指标口径必须分开：

- **TTFT** 不等于 Prefill Kernel 耗时——它还包含 Gateway、路由、排队、预处理与首 Token 执行；
- **逐 Token 间隔**要看分位数、最大间隔与连续卡顿长度，平均值会骗人；
- **吞吐**要说明是请求/s、输入 Token/s 还是输出 Token/s；长输出负载可能输出 Token 吞吐很高，却让短交互请求大量超时。

**Goodput** 只计满足服务等级的有效工作：

$$
\mathrm{Goodput} = \frac{\sum_i w_i\,\mathbf{1}(T_i \le D_i)\,U_i}{\Delta t}
$$

请求被取消、输出无效或违反质量门禁时 \(U_i = 0\)。生产优化应优先解释 Goodput 的变化，因为它把性能与用户承诺连在一起。

## 3. 工作负载不是平均值

推理负载至少由这些维度定义：到达过程、输入长度、输出长度、采样参数、模型/Adapter、优先级、截止时间、前缀复用、工具调用、媒体数量、失败重试。

- **到达过程**决定瞬时并发：固定间隔适合调试，泊松可模拟独立请求，回放真实时间戳才能保留业务节律与爆发。**开放环**按预定速率发送（适合观察过载），**闭合环**等上一个完成再发（系统变慢时自动降压强，会掩盖排队崩溃）。
- **输入长度**主要影响 Prefill 与 TTFT；**输出长度**影响驻留时间、KV 增长与 Decode 调度。长思考模型让输出长度直接变成计算预算；Agentic 请求会把一次用户任务摊成多次模型调用——平台容量不能只看外部 QPS。
- **前缀复用率**决定路由价值：大量请求共享系统提示与长文档时，KV locality 很值钱；提示高度随机时，维护全局缓存索引可能得不偿失。

## 4. 目标函数与约束

先写目标：

$$
\max\ \mathrm{Throughput}(x)
$$

\(x\) 包含批量、并发、并行策略、缓存、路由与硬件配置。但这个目标不够——无限加大排队能提高利用率，却让用户等到不可接受。加入服务等级后用 Goodput，加入成本：

$$
\min\ C_{valid} = \frac{C_{gpu}+C_{cpu}+C_{storage}+C_{network}+C_{failure}}{N_{valid\ token}}
$$

分母是**满足质量与服务等级的有效输出 Token**，不是所有算过的 Token；分子除 GPU 时间，还含权重存储分发、CPU 预处理、网络、观测以及失败重试的浪费。

可靠性作为约束：

$$
P\left(T_i \le D_i \ \land\ Q_i \ge Q_{min}\right) \ge \mathrm{SLO}
$$

这三条一起定义了可接受区域：不能靠截断长输出换延迟，也不能靠削弱验证让投机解码改变目标分布。

## 5. 排队与饱和

利用率 \(\rho = \lambda/\mu\) 接近 1 时，任何抖动都会造成长时间排队。LLM 比固定服务时间的队列更复杂：Prefill 与 Decode 消耗不同资源；连续批处理让多请求共享一步；KV 容量限制可驻留请求数；取消与抢占改变工作量；投机验证一次处理多个候选且接受长度随机。

两个结论：

1. **GPU 利用率 100% 不是无条件目标**——要留 Headroom 吸收突发、故障转移与长度误差；
2. **服务能力不是一个 QPS 数字**——同一模型在短进短出下可支持很高 QPS，长上下文长输出时显著下降。容量曲线要按「输入长度 × 输出长度 × 并发 × 命中率」分桶。

## 6. 局部优化如何传播

- **投机解码**：接受长度提高 → 低并发逐 Token 延迟下降；但草拟器占显存与算力，高并发时挤占批处理槽位。路由器不知道某些副本启用了不同 Speculator，就会把活送错。
- **前缀缓存**：命中提高减少 Prefill，但缓存条目占 KV 容量，可能挤压 Decode；跨副本索引增加事件与网络开销；模型版本或 Tokenizer 变化让旧缓存失效。
- **权重快速加载**：并行读取缩短启动，但多个副本同时扩容会形成下载风暴；本地缓存省时间却要磁盘、校验与淘汰策略。

所以每个优化都要记录**它改变的资源和故障模式**，不能只记成功路径的时间。

## 7. 可复现：冻结什么

模型修订、Tokenizer、框架版本与提交、CUDA 与驱动、GPU 型号与数量、精度、并行策略、引擎参数、工作负载样本、到达过程、随机种子、预热、测量窗口、客户端实现。

三个易错点：

- **模型名不是标识**：同一分支会更新，Chat Template 变化会改变 Token 数；
- **自动选择要落盘**：Attention Backend、量化 Kernel、并行方式的选择结果要写进报告；
- **冷启动与稳态必须分开**：首次请求会触发页缓存、Tokenizer 初始化、Kernel 编译、Graph 捕获——混进平均值后两边都不代表。

## 8. 四个真实失败模式

| 案例 | 现象 | 根因 |
|---|---|---|
| 平均值改善、长尾恶化 | 平均 TTFT 420→360 ms，P99 1.8→3.2 s | 短请求合并更紧，长输入被持续推迟（饥饿） |
| 吞吐提高、有效成本上升 | 输出 Token 吞吐上升，取消率也上升 | 客户端超时断开，服务端未传播取消，仍在给「没有消费者的请求」Decode |
| 扩容引发存储拥塞 | 10 个副本同时启动，全部变慢，扩容器继续加 | 未把「未就绪容量」计入决策，也没限制并发加载 |
| 发布健康但真实路径失败 | 探针通过、导流后报错 | 被动健康只证明进程能响应，不证明 Tokenizer/引擎/流式路径可用 |

对应的四条规则：给长请求独立队列与等待补偿；让取消从 Gateway 传到调度器与 KV Manager；扩容器带冷却与预测；发布门禁分层（制品校验 → 加载就绪 → 最小真实 Canary → 代表性负载 → 逐步放量）。
