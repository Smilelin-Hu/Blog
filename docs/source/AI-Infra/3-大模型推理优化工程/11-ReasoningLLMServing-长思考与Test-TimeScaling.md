# Reasoning LLM Serving：长思考与 Test-Time Scaling

本文把长思考请求放回真实请求链路中讨论，中心问题为「如何为长思考请求建立预算、公平性和服务等级？」。Reasoning Token 和 Test-Time Scaling 提供分析入口，计算模型负责说明方向，实验和发布门禁负责限定结论。评审时需要同时查看模型版本、负载、调度、显存、并发与服务等级，避免把 Reasoning Token 的局部理想收益直接当成端到端结果。

分析先用 CPU 模拟控制 Reasoning Token 与 Test-Time Scaling，再用真实 CUDA 路径检查这些关系进入实现后增加了哪些成本。每份结果都要标明数据来源、运行环境和适用边界，这样得到的是可复查的工程判断，而非依赖某个框架版本的参数口诀。

## 1. 内容概览

- Reasoning Token、Test-Time Scaling 与思考预算之间的状态与资源关系。
- 用「选择 $b$ 最大化 $Q(b)-\lambda T(b)-\mu C(b)$，受 deadline 与 fairness 约束」建立可计算的收益边界并解释全部变量。
- 围绕思考 Token 数、任务成功率、质量增益斜率和每成功任务成本设计可复现实验。
- 识别无限提高预算却没有质量收益、长请求饿死交互短请求、平均完成时间掩盖超时尾部等典型失败模式。
- 对中心问题给出包含适用条件、证据、风险和回滚的工程答案。

## 2. 核心直觉：输出长度不再只是结果，而是计算预算

普通 Serving 常把 `max_tokens` 当作安全上限。Reasoning 场景里，可以把它理解成：

$$Budget_{compute}\approx N_{reasoning\ tokens}\times Cost_{token}$$

更长推理可能带来更高质量，但收益不是线性的：

$$Quality(B+\Delta B)-Quality(B)$$

往往随预算增加出现边际递减。因此平台问题变成：

$$\max\ Quality(B)-\lambda\,Cost(B)$$

subject to latency / user tier / business value。

这个式子与前一篇 Speculator Policy 的 $PolicyValue$ 结构相同，但变量含义完全变了：那里的决策是「验证多少个候选位置」，这里的决策是「让模型思考多少个 Token」。前者收益来自减少 Target 串行轮数，后者收益来自任务成功率提升，而**成本从毫秒级变成分钟级**，因此公平性、截止时间与取消传播第一次成为一等公民。

## 3. 前置知识与实验环境

需要理解自回归生成、Tokenizer、Prefill、Decode、KV Cache、批处理和分位延迟的基本含义。所有缩写都会在正文首次出现处定义；没有某个特定框架经验不妨碍理解机制。实验需要 Python 3.11 或兼容版本。机制模拟只依赖 CPU；真实路径需要任意可用的 CUDA GPU、与驱动兼容的 PyTorch，以及自行准备的本地小模型或兼容制品。

验证前必须记录 GPU 名称、数量、可用显存、驱动、CUDA、PyTorch、推理框架、模型摘要、精度、批量、序列长度和完整命令。脚本根据可用显存缩放模型、批量、上下文和样本数，并把 Reasoning Token 状态写入报告；可选 CUDA 入口不下载未经确认的大模型。

关于性能问题要从测量条件开始：模型与修订、输入输出分布、请求到达、并发、采样、缓存、思考 Token 数统计方式、服务等级和硬件均需保持可追溯。「设置默认思考预算」和「按任务难度分配预算」只有在同一证据口径下才可比较。

## 4. 成本与质量的统一口径

### 4.1 成本口径

后续推导统一使用以下设定（推导设定，非实测）：

| 量 | 取值 | 说明 |
| --- | --- | --- |
| 批内单请求 TPOT | 20 ms/token | Replica 稳定并发 $B_{slot}=32$ |
| 摊销后每 Token GPU 时间 $c_{tok}$ | 0.625 GPU-ms | $=TPOT/B_{slot}=20/32$ |
| 每任务固定开销 $F$ | 500 GPU-ms | Prefill + planner + 聚合 |
| Prefill wall-clock | 100 ms | 输入 1000 Token |
| GPU 单价 | \$2.40 / GPU-hour | 用于把 GPU-ms 折算成金额 |

用 GPU-ms 而不是美元作为主单位，是为了让结论与硬件单价解耦；换算关系为 $1\ \text{GPU-ms}=2.4/3.6\times10^6=6.667\times10^{-7}$ 美元。

单轨迹成本与墙钟时间：

$$C(B)=c_{tok}\,B+F,\qquad T(B)=T_{pre}+B\cdot TPOT$$

### 4.2 质量口径

任务成功率用双曲饱和形式建模（推导设定，非实测）：

$$Q(B)=Q_\infty\frac{B}{B+K},\qquad Q_\infty=0.90,\ K=2000\ \text{token}$$

$K$ 是半饱和预算：$B=K$ 时质量达到上限的一半。边际质量增益斜率为：

$$Q'(B)=\frac{Q_\infty K}{(B+K)^2}$$

| $B$ | $Q(B)$ | $Q'(B)$（每 Token） | 相对 $B=1000$ 的斜率 |
| --- | --- | --- | --- |
| 1000 | 0.300 | $2.00\times10^{-4}$ | 1.00× |
| 2000 | 0.450 | $1.13\times10^{-4}$ | 0.56× |
| 4000 | 0.600 | $5.00\times10^{-5}$ | 0.25× |
| 8000 | 0.720 | $1.80\times10^{-5}$ | 0.09× |
| 16000 | 0.800 | $5.56\times10^{-6}$ | **0.028×** |

从 1000 到 16000，预算涨 16 倍、质量涨 2.67 倍，而**边际斜率掉到 1/36**。这就是「更多思考 Token 可能改善任务质量但收益递减」的解析形态：不是收益变负，而是收益增速远慢于成本增速（成本对 $B$ 是线性的）。

「质量增益斜率」必须附带单位（成功率增量/Token）、统计窗口与分母（该难度桶内的任务数）。只报质量差值不报斜率，无法判断该不该继续加预算。

## 5. 长驻留任务：KV、槽位与并发上限

### 5.1 驻留时间

设一个 Replica 同时处理 $N$ 个请求，每个请求输出长度 $O_i$，请求在 Decode 阶段的驻留时间近似：

$$T_i\approx O_i\cdot TPOT_i$$

普通请求 $O=300$，Reasoning 请求 $O=10000$，即使 TPOT 一样，后者在实例中停留时间也可高出一个数量级以上：$300\times20=6$ s 对 $10000\times20=200$ s，**33.3 倍**。

结果：

- 占用 KV 更久；
- 占用 scheduler slot 更久；
- 更容易与短请求形成资源不公平；
- 用户中途取消时浪费 token 更多；
- Autoscaler 看到的「当前并发数」不再能代表剩余工作量。

### 5.2 KV 占用与并发上限

沿用前一篇 DDTree 的 KV 口径：32 层、8 个 KV 头、head_dim 128、fp16，每 Token 128 KiB。输入固定 1000 Token（推导值，非实测）：

| 请求类型 | 总 Token | KV 占用 | 60 GiB 预算下并发上限 |
| --- | --- | --- | --- |
| 普通（$O=300$） | 1300 | 162.5 MiB | 378 |
| Reasoning（$O=10000$） | 11000 | 1375 MiB | 44 |

同样显存下 Reasoning 的并发上限只有普通请求的 **11.8%**。这直接改变了容量规划的分母：按「请求数」估容量会高估 8.5 倍，必须按「Token·秒」或 KV 占用估。

### 5.3 长请求饿死短请求

设 FCFS 单队列、32 个 Decode 槽位，流量为 90% 短请求（6 s）+ 10% 长请求（200 s），到达率 1.0 req/s。按 Little's law 稳态槽位需求：

$$\text{短}=0.9\times6=5.4\ \text{槽},\qquad \text{长}=0.1\times200=20\ \text{槽}$$

长请求占用了 **78.7%** 的槽位时间（$20/25.4$），却只占 10% 的请求数。一旦长请求集中到达把 32 槽占满，短请求必须等待某个长请求结束；若长请求剩余寿命均匀分布在 $[0,200]$ s，期望等待 100 s——**是短请求自身服务时间 6 s 的 16.7 倍**。

隔离队列（短 8 槽 / 长 24 槽）后：短请求利用率 $5.4/8=67.5\%$，长请求 $20/24=83.3\%$，两者都有余量，短请求等待回到接近 0。代价是长请求峰值吞吐被限制在 $24/200=0.12$ req/s，突发时需要排队或降级预算。

**隔离不是免费的**：它把「共享池的统计复用收益」换成了「可预测的尾延迟」。选择依据是短请求的 SLO 是否硬承诺——若是，隔离必选；若短请求也可容忍排队，共享池利用率更高。

## 6. 思考预算的四种形式

### 6.1 Token Budget

最直接：

```text
max_reasoning_tokens = 4096 / 8192 / 16384
```

适合做硬上限。优点是计量简单、与计费口径一致；缺点是不反映实际速度——同样 8192 Token 在不同并发下墙钟时间可以差数倍。

### 6.2 Wall-Time Budget

例如 20 秒内必须返回。需要维护：

$$RemainingTime=Deadline-Now$$

系统根据当前速度决定是否继续推理。由 $T(B)=T_{pre}+B\cdot TPOT$ 反解可得可行预算上限：

$$B_{max}(D)=\frac{D-T_{pre}}{TPOT}$$

| Deadline | $B_{max}$ | 对应 $Q(B_{max})$ |
| --- | --- | --- |
| 5 s | 245 | 0.098 |
| 10 s | 495 | 0.179 |
| 20 s | 995 | 0.299 |
| 30 s | 1495 | 0.385 |
| 60 s | 2995 | 0.540 |
| 300 s | 14995 | 0.794 |

Wall-Time 预算必须随实测 TPOT 动态重算：并发上升使 TPOT 从 20 ms 涨到 30 ms 时，30 s deadline 的可行预算从 1495 掉到 995，质量从 0.385 掉到 0.299。**静态配置的 wall-time 预算在负载变化时会静默失效**。

### 6.3 Cost Budget

例如每个请求最多花费 $Cost_{request}\le C_{max}$，适合 API 计费、企业 Agent 和批量任务。由 $C(B)=c_{tok}B+F$ 反解：

$$B_{max}(C_{max})=\frac{C_{max}-F}{c_{tok}}$$

$C_{max}=1125$ GPU-ms 时 $B_{max}=1000$；$C_{max}=3000$ 时 $B_{max}=4000$。Cost 预算与 Token 预算在 $c_{tok}$ 固定时等价，但 $c_{tok}$ 随并发变化，因此 Cost 预算实际上比 Token 预算更严格——它自动把「高并发时更贵」计入约束。

### 6.4 Quality/Confidence Budget

如果模型/Verifier 已达到足够置信度，可以提前结束；否则继续分配更多 test-time compute。这需要额外 quality estimator，不是纯 Serving 可以凭空得到。

四种预算的关系不是互斥而是**层层收紧**：Token 上限是硬边界，Wall-Time 与 Cost 在运行时动态收紧，Quality 预算则可能提前放开边界。实现上必须明确「谁先触发谁生效」，并把触发原因写进结束原因字段，否则事后无法区分「达到质量目标提前结束」与「超时被截断」。

## 7. 每成功任务成本的最优预算

### 7.1 解析最优点

单看质量会倾向大预算，单看成本会倾向小预算。把两者合成「每成功任务成本」：

$$f(B)=\frac{C(B)}{Q(B)}=\frac{(c_{tok}B+F)(B+K)}{Q_\infty B}=\frac{1}{Q_\infty}\left(c_{tok}B+c_{tok}K+F+\frac{FK}{B}\right)$$

对 $B$ 求导并令其为零：

$$f'(B)=\frac{1}{Q_\infty}\left(c_{tok}-\frac{FK}{B^2}\right)=0\ \Longrightarrow\ \boxed{B^*=\sqrt{\frac{FK}{c_{tok}}}}$$

代入 $F=500$、$K=2000$、$c_{tok}=0.625$：

$$B^*=\sqrt{\frac{500\times2000}{0.625}}=\sqrt{1.6\times10^6}\approx1265\ \text{token}$$

这是一个**只依赖固定开销、半饱和预算与单 Token 成本**的闭式解，与 $Q_\infty$ 无关（质量上限只缩放 $f$ 的绝对值，不移动最优点）。

### 7.2 预算扫描

$f(B^*)=3701.3$ GPU-ms。扫描结果（推导值，非实测）：

| $B$ | $Q(B)$ | $C(B)$ GPU-ms | $C/Q$ GPU-ms | 相对最优 |
| --- | --- | --- | --- | --- |
| 500 | 0.180 | 812.5 | 4513.9 | +21.9% |
| 1000 | 0.300 | 1125.0 | 3750.0 | +1.3% |
| **1265** | **0.349** | **1290.6** | **3701.3** | **0%** |
| 2000 | 0.450 | 1750.0 | 3888.9 | +5.1% |
| 4000 | 0.600 | 3000.0 | 5000.0 | +35.1% |
| 8000 | 0.720 | 5500.0 | 7638.9 | +106.4% |
| 16000 | 0.800 | 10500.0 | 13125.0 | +254.6% |

从 1265 到 16000：质量从 0.349 升到 0.800（+129%），预算涨 12.6 倍，**每成功任务成本涨 3.55 倍**。这就是「无限提高预算却没有质量收益」的准确含义——不是质量不涨，而是涨的质量不值那个价钱。

### 7.3 最优点如何移动

$B^*=\sqrt{FK/c_{tok}}$ 给出三条可直接用于容量规划的规律：

1. **固定开销 $F$ 越大，最优预算越大**。$F$ 从 500 涨到 2000（更长的 prompt、更重的 planner），$B^*$ 从 1265 涨到 2530。因此长 prompt 场景天然适合更深思考。
2. **半饱和预算 $K$ 越大，最优预算越大**。难题（$K$ 大）应当分配更多预算，这是「按任务难度分配预算」的解析依据。
3. **单 Token 成本 $c_{tok}$ 越高，最优预算越小**。高并发使 $c_{tok}$ 上升时，最优预算自动收缩——**预算策略必须与负载联动，而不是静态配置**。

第 3 条尤其重要：$c_{tok}=TPOT/B_{slot}$，若并发从 32 降到 8（低载时批不满），$c_{tok}$ 从 0.625 涨到 2.5，$B^*$ 从 1265 掉到 632。低负载时单请求更贵，反而应该少思考。

## 8. 截止时间把质量优化变成受限决策

### 8.1 两种目标给出不同答案

同一个 deadline 下，「最大化质量」与「最小化每成功任务成本」会选择不同预算：

- 目标 A（质量优先）：$B=B_{max}(D)$，用满时间；
- 目标 B（成本优先）：$B=\min(B_{max}(D),\ B^*)$。

两者只在 $B_{max}(D)\ge B^*$ 时重合，即 $D\ge T_{pre}+B^*\cdot TPOT=100+1265\times20=25400$ ms $=25.4$ s。

按目标 A 扫描（推导值，非实测）：

| Deadline | $B$ | $Q$ | $C/Q$ GPU-ms | 相对无约束最优 |
| --- | --- | --- | --- | --- |
| 5 s | 245 | 0.098 | 6649.7 | **+79.7%** |
| 10 s | 495 | 0.179 | 4532.9 | +22.5% |
| 20 s | 995 | 0.299 | 3752.1 | +1.4% |
| 30 s | 1495 | 0.385 | 3725.9 | +0.7% |
| 60 s | 2995 | 0.540 | 4395.3 | +18.8% |
| 120 s | 5995 | 0.675 | 6293.0 | +70.0% |
| 300 s | 14995 | 0.794 | 12431.7 | +235.9% |

**每成功任务成本在 deadline 轴上也是 U 形的**：太紧（5 s）落在曲线左侧上升段，太松（300 s）落在右侧上升段。给更多时间并不总是更好——它只是把决策推向质量更高但性价比更差的区域。

### 8.2 超时率与尾延迟

「平均完成时间掩盖超时尾部」可以量化。设 90% 请求在 6 s 完成、10% 请求在 200 s 完成：

$$\bar T=0.9\times6+0.1\times200=25.4\ \text{s}$$

平均值 25.4 s 看起来「都还行」，但 P99 落在长请求段，接近 200 s。若 SLO 是「P99 < 30 s」，则**平均指标完全无法暴露违约**，必须直接报分位数与超时率。

超时率口径必须明确三件事：分子是「超过 deadline 才返回」还是「被截断返回」；分母是否含被取消请求；deadline 是全局任务级还是单次调用级。三者任一不同，数字就不可比。

## 9. Test-Time Scaling：fan-out 与 verifier

### 9.1 平台含义

一种常见思路是同一个问题生成多个 reasoning candidates，再选择最优：

![长推理链：逐步 Reasoning，Verifier 把关后出答案](https://raw.gitcode.com/weixin_42917352/image-host/raw/main/images/aiinfra_y3_l11_02.png)

如果并行生成 $M$ 条轨迹，总成本近似：

$$C\propto\sum_{m=1}^{M}Tokens_m$$

这会产生新的平台问题：fan-out 并发、candidate aggregation、verifier 服务、预算共享、一个用户能否瞬间占用大量 GPU。因此 Test-Time Scaling 需要与租户配额和成本控制打通。

### 9.2 成功率与成本模型

设单轨迹成功率 $q(B)=Q(B)$，verifier 在存在正确轨迹时选中它的概率为 $p_v$（$M=1$ 时无需选择，$p_v=1$；$M>1$ 时取 $p_v=0.85$，推导设定）。则：

$$Q_M(B)=p_v\left[1-(1-q(B))^M\right]$$

$$C_M(B)=c_{tok}\,M\,B+F+100(M-1),\qquad T_M(B)=T_{pre}+B\cdot TPOT+200\cdot\mathbb{1}[M>1]$$

其中 $100(M-1)$ 是每增加一条分支的 Prefill 与 verifier 增量开销，200 ms 是聚合墙钟成本。

### 9.3 固定预算下增加 M 并不划算

取 $B=1265$（$q=0.349$），扫描 $M$（推导值，非实测）：

| $M$ | $Q_M$ | $C_M$ GPU-ms | $C_M/Q_M$ |
| --- | --- | --- | --- |
| 1 | 0.349 | 1290.6 | **3701.3** |
| 2 | 0.489 | 2181.3 | 4456.7 |
| 4 | 0.697 | 3962.5 | 5684.6 |
| 8 | 0.822 | 7525.0 | 9149.2 |

固定预算下 $M$ 越大性价比越差：verifier 的 15% 折损加上分支固定开销，超过了概率叠加的收益。**「多采样几条」不是免费的质量提升**。

### 9.4 固定质量目标下存在最优 M

正确的比较方式是**锁定目标质量，反解各 $M$ 所需预算**。目标 $Q=0.60$（推导值，非实测）：

| 方案 | 所需 $B$ | $C$ GPU-ms | $C/Q$ | 相对单轨迹 |
| --- | --- | --- | --- | --- |
| $M=1$ | 4000 | 3000.0 | 5000.0 | 0% |
| $M=2$ | 2069 | 3186.8 | 5311.3 | +6.2% |
| **$M=4$** | **828** | **2870.8** | **4784.6** | **−4.3%** |
| $M=8$ | 374 | 3071.0 | 5118.3 | +2.4% |

目标 $Q=0.80$：

| 方案 | 所需 $B$ | $C$ GPU-ms | $C/Q$ | 相对单轨迹 | 墙钟时间 |
| --- | --- | --- | --- | --- | --- |
| $M=1$ | 16000 | 10500.0 | 13125.0 | 0% | 320.1 s |
| $M=2$ | 6862 | 9277.5 | 11596.9 | −11.6% | 137.5 s |
| $M=4$ | 2586 | 7265.5 | 9081.9 | −30.8% | 52.0 s |
| **$M=8$** | **991** | **6156.0** | **7695.0** | **−41.4%** | **20.1 s** |
| $M=16$ | 440 | 6400.0 | 8000.0 | −39.0% | 9.1 s |

两个结论：

1. **目标质量越高，最优 fan-out 越大**（$Q=0.60$ 时 $M=4$，$Q=0.80$ 时 $M=8$）。原因是高质量单轨迹必须进入收益递减段（$B=16000$ 时斜率只有 $5.56\times10^{-6}$），而多轨迹用「概率叠加」替代「预算堆叠」更划算。
2. **fan-out 同时改善成本与延迟**。$Q=0.80$ 时 $M=8$ 把墙钟从 320.1 s 压到 20.1 s（16 倍），每成功任务成本还降 41.4%。代价是瞬时并发需求 8 倍——一个用户任务瞬间占用 8 个 Decode 槽位。

第 2 条解释了为什么 Test-Time Scaling 必须与租户配额打通：**它对单任务是双赢，对平台是峰值冲击**。若不限制 fan-out，少量 Deep 档用户就能把 Replica 槽位占满，触发第 5.3 节的短请求饿死。

## 10. Reasoning Tier 的后端映射与定价

### 10.1 Tier 不应只是前端标签

生产平台可以定义：

```text
Fast      : 1x budget
Balanced  : 4x budget
Deep      : 16x budget
```

但 Tier 不应该只写成前端标签。后端需要映射到：max reasoning tokens、max wall time、candidate count、model size、priority、cost cap。这样用户购买的是可解释的资源级别。

取基准预算 1000 Token，完整映射如下（推导值，非实测）：

| Tier | 倍数 | $B$ | $M$ | 墙钟上限 | $Q_M$ | 每请求成本 GPU-ms | $C/Q$ |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Fast | 1× | 1000 | 1 | 20.1 s | 0.300 | 1125 | 3750 |
| Balanced | 4× | 4000 | 2 | 80.3 s | 0.714 | 5600 | 7843 |
| Deep | 16× | 16000 | 4 | 320.3 s | 0.849 | 40800 | 48077 |

### 10.2 定价陷阱

每请求成本比为 $1125:5600:40800=1:4.98:36.27$，而标称预算倍数是 $1:4:16$。

**Deep 档的实际成本是标称倍数的 2.27 倍**（$36.27/16$），Balanced 档是 1.24 倍。原因是 fan-out 让成本超线性增长：$C_M$ 里既有 $M\times B$ 的乘积项，又有 $100(M-1)$ 的分支固定项。

若按预算倍数定价，Deep 档会系统性亏损。正确做法是按**每成功任务成本**定价：Deep 的 $C/Q$ 是 Fast 的 12.8 倍（$48077/3750$），而质量只有 2.83 倍（$0.849/0.300$）。因此 Deep 档的合理溢价上限约为 12.8 倍，超过就没有用户价值；低于成本比 36.3 倍则平台亏损。**这两个数字之间的区间才是可定价空间**，而它比「1×/4×/16×」的直觉窄得多。

### 10.3 优先级映射

Tier 还必须映射到调度优先级，且方向与直觉相反：**Fast 档优先级最高，Deep 档最低**。因为 Fast 档服务时间短（6–20 s），优先放行几乎不占用槽位时间；Deep 档服务时间长（320 s），一旦抢占就长时间锁住资源。按「最短作业优先」的变体调度，可以在不牺牲 Deep 档完成率的前提下把 Fast 档 P99 压到最低。

## 11. 长任务公平性与计量

### 11.1 按 Token 而非按请求数

可以使用：

$$Usage_u=\sum_{r\in u}OutputTokens_r\cdot Weight_{model}$$

做 tenant compute accounting，而不是只数 request 数。

量化偏差：设租户 A 发 1000 个短请求（各 300 Token），租户 B 发 100 个长请求（各 10000 Token）。

| 计量方式 | A | B | A/B |
| --- | --- | --- | --- |
| 请求数 | 1000 | 100 | 10.0 |
| 输出 Token | 300,000 | 1,000,000 | 0.30 |

**按请求数计量会把配额压力错误地加在短请求租户上，偏差达 33.3 倍**（$10/0.30$）。A 实际只用了 B 的 30% 算力，却看起来是 B 的 10 倍。任何基于请求数的限流、配额与计费在 Reasoning 场景下都会产生这种反向激励。

### 11.2 权重与 fan-out

$Weight_{model}$ 用于区分不同模型的单 Token 成本（大模型更贵）。但 Agent 与 Test-Time Scaling 场景还需计入 fan-out：一个用户任务的真实用量是 $\sum_m Tokens_m$，而不是最终答案的 Token 数。若只按最终输出计量，$M=8$ 的 Deep 任务会被少计 8 倍。

因此计量点必须落在**每次模型调用**上，再按 `task_id` 聚合，而不是落在任务返回时。「任务成功率」的分母也必须是原始用户任务数，而不是内部模型调用数——否则 fan-out 越大成功率看起来越高。

## 12. 取消传播与无效计算

### 12.1 超时后仍持续生成的代价

设 deadline 30 s（可完成 1495 Token），但引擎未收到取消信号，继续生成到 $B=16000$：

$$\text{无效 Token}=16000-1495=14505$$

$$\text{无效计算}=14505\times0.625=9065.6\ \text{GPU-ms}=9.07\ \text{GPU-s}$$

折算金额 $9.07/3600\times2.40=\$0.00604$ / 请求。若每天 10 万请求、10% 超时且未取消，则每天浪费 $\$60.4$、每月约 $\$1813$（推导值，非实测）。

这笔钱只是直接算力成本，更大的代价是**槽位被无效占用 290 s**，等价于挤掉了 48 个短请求的服务机会（$290/6$）。

### 12.2 取消传播的路径与延迟

取消必须沿完整链路传播：用户 → Gateway → Agent Runtime → 每次 LLM 调用 → 引擎 scheduler → 正在运行的 batch。任一环断开都会出现「超时后模型仍持续生成」。

传播延迟 $\Delta$ 造成的额外浪费为 $\Delta/TPOT$ 个 Token。$\Delta=2$ s 时额外 100 Token（62.5 GPU-ms），相对 9065.6 GPU-ms 只是零头——**主要风险不是传播慢，而是传播断**。因此验收必须逐环注入取消信号并确认引擎侧停止，而不是只测端到端延迟。

### 12.3 中途取消与计费

用户主动取消时，已生成部分是否计费需要明确合同。设取消时刻均匀分布在 $[0,T]$，期望浪费为已生成 Token 的 50%；Reasoning 请求 $O=10000$ 时期望浪费 5000 Token（3125 GPU-ms）。

若按「已生成 Token 计费」，用户取消仍付一半钱，会抑制合理使用；若按「成功任务计费」，平台承担全部取消风险，需要在定价里计入取消率。两种合同都可行，但**必须与「任务成功率」的口径绑定**：被取消的任务算不算失败，直接改变每成功任务成本的分母。

## 13. Autoscaler 的剩余工作量信号

「当前并发数」在 Reasoning 场景下不再能代表剩余工作量。构造两个并发数相同的时刻（推导设定，非实测）：

| 时刻 | 组成 | 平均剩余 Token | 剩余工作量（Token） |
| --- | --- | --- | --- |
| 1 | 32 个短请求（各已完成一半） | 150 | 4,800 |
| 2 | 20 长（各剩 5000）+ 12 短（各剩 150） | — | 101,800 |

**同样 32 并发，剩余工作量相差 21.2 倍**。按并发数扩容会在时刻 1 严重过扩、时刻 2 严重欠扩。

正确信号是剩余 Token 总量或剩余槽位·秒：

$$WorkRemaining=\sum_i\left(O_i-o_i^{done}\right),\qquad SlotsNeeded=\frac{WorkRemaining\cdot TPOT}{T_{drain}}$$

设目标排空时间 $T_{drain}=60$ s，时刻 2 需要 $101800\times0.020/60=33.9$ 槽，即扩容到 34；时刻 1 只需 $4800\times0.020/60=1.6$ 槽，可以大幅缩容。两者的扩缩方向完全相反，而并发数指标给出的信号一模一样。

这条结论把 Reasoning Serving 与后续的 SLA-aware Autoscaling 直接连起来：**扩缩容的输入必须是工作量而不是请求数**，否则长思考流量会让 autoscaler 系统性失准。

## 14. 八个对象的边界与失败模式

决策所需的八个观察对象为：Reasoning Token、Test-Time Scaling、思考预算、完成截止时间、长输出队列、推理质量曲线、优先级与公平性、预算终止策略。它们横跨算法、运行时和平台，共同作用于队列年龄与每成功任务成本。

### 14.1 统一检查框架

每个对象都按同一组问题展开：边界与生命周期（输入从哪里来、状态由谁持有、输出交给谁、失败如何传播、何时销毁）、资源账（计算、显存、内存带宽、主机开销、同步等待分别记账）、负载区间（低载、接近饱和、过载三段同口径）、正确性门禁（Token 序列、采样分布、结构合法性、结束原因、错误传播）、观测字段（请求身份、模型与策略修订、起止时间、阶段耗时、资源快照、失败原因）。跨对象传递的数据必须携带版本身份。每个对象都要标出拥有者、状态、计量点和失败边界，局部变化才能与端到端结果对上。

### 14.2 Reasoning Token

生命周期落到组件接口，与 Test-Time Scaling 之间的身份和版本若未绑定，请求时间线就可能混入旧配置。长输出占用 Decode 槽位并放大队列等待，其影响分散到五项资源；某一阶段变短时，被遮蔽的成本可能随即暴露。为确认变化来自哪里，需对齐请求时间线与资源采样，而非只看整段运行的 GPU 平均值。

「隔离长短请求队列」的验证分别运行三段负载并使用代表性分布。典型失败是**超时后模型仍持续生成**：第 12.1 节显示单次无效计算达 9065.6 GPU-ms，并挤掉 48 个短请求的服务机会。当前性能结果不进入候选评审，立即切回已验证配置，失败样本与版本信息一并保存。**完成延迟**的定义随报告存档，包括单位、窗口和分母。

### 14.3 Test-Time Scaling

边界检查覆盖输入、输出、状态归属和销毁时点；传给思考预算的数据应附带模型或策略版本。截止时间把质量优化转化为受限决策，通常只先改变资源账中的几项，其他资源随后可能进入关键路径；平均 GPU 利用率只作为辅助信号。

「选择质量与延迟门禁」应覆盖长短输入、不同输出、并发、突发、采样与任务域，容量判断不能从一次固定批量的短运行外推。典型失败是**难度估计错误分配过多资源**：简单题拿到 Deep 档预算，$C/Q$ 从 3750 涨到 48077。触发停止与回退，系统恢复到已有证据支持的配置。**超时率**必须附带口径。

### 14.4 思考预算

边界由输入、输出、状态和拥有者共同确定；连接完成截止时间时还要传播身份和版本，避免把另一套配置的结果归到当前实验。不同难度请求需要不同预算，缩短的阶段可能让另一项资源成为瓶颈。

「设计截止时间传播」至少比较低载、临近容量与过载，结论只覆盖实际运行过的区间。典型失败是**质量评测与线上任务不一致**：离线用基准题库拟合 $Q(B)$，线上任务难度分布不同导致 $K$ 估计偏差，$B^*$ 随之错位。质量结果优先于速度数字，发布停止、流量回到已验证修订，相关请求留作重放。**队列年龄**同时注明单位、窗口和分母。

### 14.5 完成截止时间

与长输出队列交互的字段必须携带版本身份。取消传播决定超时后的无效计算，这会移动关键路径，却很少让所有资源同比例变化：请求事件负责说明顺序，资源曲线负责解释瓶颈转移。

「控制超时后的取消与计费」是否合适，取决于长度分布、并发、到达过程、采样和任务域。典型失败是**无限提高预算却没有质量收益**：第 7.2 节显示预算涨 12.6 倍只换来质量 +129%，每成功任务成本涨 3.55 倍。质量门禁应停止性能发布，回退目标是已验证配置。**每成功任务成本**没有单位、统计窗口和分母时不参与决策。

### 14.6 长输出队列

生命周期落到组件接口，与推理质量曲线之间的身份和版本若未绑定，请求时间线就可能混入旧配置。预算终止器依据进展信号提前收敛，其影响分散到五项资源。

「设置默认思考预算」的验证分别运行三段负载并使用代表性分布。典型失败是**长请求饿死交互短请求**：第 5.3 节显示长请求占 78.7% 槽位时间却只占 10% 请求数，FCFS 下短请求期望等待 100 s。当前性能结果不进入候选评审，立即切回已验证配置。**思考 Token 数**的定义随报告存档，包括单位、窗口和分母。

### 14.7 推理质量曲线

边界检查覆盖输入、输出、状态归属和销毁时点；传给优先级与公平性的数据应附带模型或策略版本。更多思考 Token 可能改善任务质量但收益递减，通常只先改变资源账中的几项。

「按任务难度分配预算」应覆盖长短输入、不同输出、并发、突发、采样与任务域。典型失败是**平均完成时间掩盖超时尾部**：第 8.2 节显示均值 25.4 s 而 P99 接近 200 s，平均指标完全无法暴露 SLO 违约。触发停止与回退后系统恢复到已有证据支持的配置。**任务成功率**必须附带口径，分母为原始用户任务数。

### 14.8 优先级与公平性

边界由输入、输出、状态和拥有者共同确定；连接预算终止策略时还要传播身份和版本。长输出占用 Decode 槽位并放大队列等待，缩短的阶段可能让另一项资源成为瓶颈。

「隔离长短请求队列」至少比较低载、临近容量与过载。典型失败是**按请求数计量掩盖算力不公平**：第 11.1 节显示偏差达 33.3 倍，配额压力被反向加在短请求租户上。质量结果优先于速度数字，发布停止并保留问题请求用于重放。**质量增益斜率**同时注明单位、窗口和分母。

### 14.9 预算终止策略

与 Reasoning Token 交互的字段必须携带版本身份。截止时间把质量优化转化为受限决策，会移动关键路径，却很少让所有资源同比例变化。

「选择质量与延迟门禁」是否合适，取决于长度分布、并发、到达过程、采样和任务域。典型失败是**终止器误判进展导致提前收敛**：把「输出变短」当作「已收敛」，在质量尚未达标时截断，任务成功率下降而成本指标看起来改善。质量门禁应停止性能发布，回退目标是已验证配置。**TTFT** 没有单位、统计窗口和分母时不参与决策。

## 15. 六个机制的因果分析

![Reasoning Serving 的机制与证据闭环](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y3_l11_01.png)

*机制流程：把长思考与 Test-Time Scaling 的输入、关键决策、执行与证据闭环连接起来。*

用于推演的性能关系为：选择 $b$ 最大化 $Q(b)-\lambda T(b)-\mu C(b)$，受 deadline 与 fairness 约束。它帮助评审 Reasoning Token、Test-Time Scaling 怎样作用于思考 Token 数、TTFT 和每成功任务成本，没有预设具体设备的基准值。代入数据前先统一时间单位，检查概率范围，并注明吞吐量计算的是请求、Token 还是满足 SLO 的有效完成。

推演重点是判断「更多思考 Token 可能改善任务质量但收益递减」发生后哪些量应变化，以及「长输出占用 Decode 槽位并放大队列等待」的收益在什么负载下被摊销。实现中的调度、Kernel、内存、网络、客户端和取消成本另行记录。公式与实测产生矛盾时，以检查假设、遗漏项和统计方式为处理顺序。

### 15.1 机制 1：更多思考 Token 可能改善任务质量但收益递减

请求执行该机制后，阶段边界和依赖关系会发生变化。先记录原路径，再记录候选路径中的串行、并行与合批段；同时保存 Reasoning Token 状态和思考 Token 数，便于把原因与结果关联起来。第 4.2 节给出解析斜率 $Q'(B)=Q_\infty K/(B+K)^2$，第 7.1 节由此导出闭式最优预算 $B^*=\sqrt{FK/c_{tok}}$。

容量评估把该机制放在三个负载区间中运行。固定开销通常在低载突出，队列和资源争用会在高载显现；长请求饿死交互短请求意味着候选工作可能消耗了服务正常请求所需的容量。

实现时明确数据格式、张量形状、缓存身份、版本兼容和错误回退。执行隔离长短请求队列前冻结接口合同，并加入无效输入、极端长度与资源不足测试，成功样本之外的保护行为也属于验收范围。Trace 同时记录决策输入与执行结果：前者含阈值和候选，后者含 TTFT、错误、取消和资源变化。上线合同写明灰度范围、停止条件、开关和暖回滚目标；难度估计错误分配过多资源发生后，系统恢复相关稳定配置，并持续观察请求排空、缓存切换和资源回收。

### 15.2 机制 2：长输出占用 Decode 槽位并放大队列等待

把前后两条请求时间线对齐，逐段标出可并行、必须串行和允许合批的工作。第 5.2 节显示 Reasoning 请求的 KV 占用使并发上限降到普通请求的 11.8%，第 5.3 节显示长请求以 10% 的请求数占据 78.7% 的槽位时间。

分别施加轻载、稳定高载和过载流量，可以分辨同步开销、队列增长、合批变化与资源竞争。检测到短请求等待时间达到自身服务时间 16.7 倍后，沿共享执行资源检查局部收益为何没有进入系统 Goodput。

确定接口时同时规定数据与 Shape、缓存和版本身份、错误及回退，随后以无效输入、极端长度和资源不足验证「隔离长短请求队列」。观测时原因侧保存请求类型、预算档与槽位分配，结果侧保存队列年龄、错误、取消与资源。该机制通过独立开关进入灰度，出现长请求饿死交互短请求时撤回本项候选，并核对在途请求、缓存状态与资源是否释放。

### 15.3 机制 3：截止时间把质量优化转化为受限决策

这一机制会改写请求的阶段顺序。画出变化前后的关键路径，标明并行、串行和跨请求合批位置；思考预算给出状态条件，超时率验证结果是否传到请求端。第 8.1 节显示每成功任务成本在 deadline 轴上呈 U 形，5 s 与 300 s 两端分别比最优高 79.7% 与 235.9%。

单请求数据不足以评价：低载用于测量固定成本，接近容量时观察批处理与共享资源，过载时确认拒绝和尾延迟。平均完成时间掩盖超时尾部若只在并发后出现，优先检查候选路径对正常请求资源的挤占。

数据格式、张量形状、缓存身份、版本兼容和错误传播共同构成实现边界；「设计截止时间传播」需要在合同冻结后测试正常、无效、极端和资源受限输入。证据需要成对的原因和结果字段：原因包括 deadline、剩余时间与实测 TPOT，结果包括超时率、P99、错误、取消和资源快照。发布时配置独立开关、灰度身份、停止条件和暖回滚目标；无限提高预算却没有质量收益触发后只撤回相关变化。

### 15.4 机制 4：取消传播决定超时后的无效计算

把前后两条请求时间线对齐，逐段标出可并行、必须串行和允许合批的工作。完成截止时间说明机制何时生效，每成功任务成本负责确认关键路径是否真的缩短。第 12.1 节显示单次未取消的超时请求浪费 9065.6 GPU-ms，并挤掉 48 个短请求的服务机会。

分别施加轻载、稳定高载和过载流量，可以分辨同步开销、队列增长、合批变化与资源竞争。检测到超时后模型仍持续生成后，沿共享执行资源检查局部收益为何没有进入系统 Goodput。

确定接口时同时规定数据与 Shape、缓存和版本身份、错误及回退，随后以无效输入、极端长度和资源不足验证「控制超时后的取消与计费」。观测时原因侧保存取消发起点、传播路径与各环确认时间，结果侧保存无效 Token 数、错误、取消与资源。该机制通过独立开关进入灰度，出现传播断链时撤回本项候选，并核对在途请求、缓存状态与资源是否释放。

### 15.5 机制 5：不同难度请求需要不同预算

请求执行该机制后，阶段边界和依赖关系会发生变化。先记录原路径，再记录候选路径中的串行、并行与合批段，同时保存质量增益斜率与任务成功率。第 7.3 节给出 $B^*$ 对 $F$、$K$、$c_{tok}$ 的三条依赖规律，其中 $K$ 正是难度的解析代理。

容量测试覆盖低载、稳定高载和过载。若出现质量评测与线上任务不一致，说明离线拟合的 $K$ 不适用于线上难度分布，需要按域重新标定而不是调整全局默认值。

接口合同包括格式、Shape、缓存键、版本与回退语义；「按任务难度分配预算」进入评审前，使用非法输入、边界长度和资源不足场景检验保护路径。采集证据时把难度估计、预算档、判据类型与队列年龄、错误、取消及资源事件放进同一请求链。发布单元包含灰度身份、门禁、停止动作和已预热回滚路径；检测到难度估计错误分配过多资源后执行局部撤回。

### 15.6 机制 6：预算终止器依据进展信号提前收敛

这一机制会改写请求的阶段顺序。画出变化前后的关键路径，标明并行、串行和跨请求合批位置；预算终止策略给出状态条件，TTFT 与完成延迟验证结果是否传到请求端。第 6.4 节指出 Quality/Confidence 预算需要额外 estimator，不是纯 Serving 可以凭空得到。

单请求数据不足以评价：低载测量固定成本，接近容量时观察批处理与共享资源，过载时确认拒绝和尾延迟。终止器误判进展导致提前收敛若只在并发后出现，优先检查进展信号是否被批次 padding 或流式缓冲污染。

数据格式、张量形状、缓存身份、版本兼容和错误传播共同构成实现边界；「选择质量与延迟门禁」需要在合同冻结后测试正常、无效、极端和资源受限输入。证据需要成对字段：原因包括进展信号、置信度估计与阈值，结果包括任务成功率、结束原因、错误、取消和资源快照。发布时配置独立开关、灰度身份、停止条件和暖回滚目标；质量评测与线上任务不一致触发后只撤回相关变化。

## 16. 工程决策与取舍

### 16.1 决策 1：设置默认思考预算

候选做法是固定 Token 上限、按 $B^*=\sqrt{FK/c_{tok}}$ 计算、按 Tier 分档、再按负载动态调整。第 7.3 节显示 $c_{tok}$ 随并发变化会让 $B^*$ 移动一倍（并发 32→8 时 1265→632），因此静态默认值只在单一工况下正确。取舍在于实现复杂度：动态 $B^*$ 需要实时 TPOT 与并发信号。判据是每成功任务成本与任务成功率，并附「无限提高预算却没有质量收益」的停止动作。默认值必须标注它对应的 $F$、$K$、$c_{tok}$ 假设。

### 16.2 决策 2：按任务难度分配预算

候选做法是不分配、按请求类型静态分档、按难度估计器动态分配、按历史同域成功率反馈分配。第 7.3 节给出 $B^*\propto\sqrt{K}$，难度越大最优预算越大，这是分配的解析依据。取舍在于估计器成本与误差：难度估计错误会把简单题送进 Deep 档，$C/Q$ 涨 12.8 倍。判据是分难度桶的质量增益斜率与每成功任务成本，并明确估计不确定时的回退档位。质量评测集必须与线上任务分布对齐，否则 $K$ 标定失效。

### 16.3 决策 3：设计截止时间传播

候选做法是只设全局 deadline、逐层分配子 deadline、按剩余时间动态重算、再加不可行时提前拒绝。第 6.2 节显示 wall-time 预算必须随实测 TPOT 重算，静态配置在负载变化时静默失效。取舍在于拒绝率：提前拒绝不可行请求会改善尾延迟但降低任务成功率。判据是超时率、P99 完成延迟与拒绝率，三者必须同时报。deadline 必须传播到 sub-agent、LLM call、tool call、reranker/embedding 与 final synthesis 全链路。

### 16.4 决策 4：控制超时后的取消与计费

候选做法是不取消（跑完为止）、软取消（当前 step 结束后停）、硬取消（立即中止 batch）、再加按已生成 Token 或按成功任务计费。第 12.1 节显示不取消的代价是 9065.6 GPU-ms 加 48 个短请求的服务机会，因此硬取消是默认选择。取舍在于计费合同：按已生成 Token 计费抑制用户合理使用，按成功任务计费要求平台承担取消风险。判据是无效 Token 数、取消传播各环确认时间与槽位释放延迟，并明确被取消任务是否计入成功率分母。

### 16.5 决策 5：隔离长短请求队列

候选做法是共享 FCFS、按长度分队列、按 Tier 分队列、再加加权公平队列。第 5.3 节显示共享池下短请求期望等待 100 s（自身服务时间的 16.7 倍），隔离后回到接近 0。取舍在于统计复用损失：隔离把长请求峰值吞吐限制在 $24/200=0.12$ req/s。判据是分队列的队列年龄、P99 完成延迟与槽位利用率，并按短请求 SLO 是否硬承诺决定隔离强度。隔离比例必须随流量结构定期重算。

### 16.6 决策 6：选择质量与延迟门禁

候选做法是只设质量下限、只设延迟上限、两者联合、再加每成功任务成本上限。第 8.1 节显示质量与成本在 deadline 轴上呈 U 形关系，单设任一门禁都会把决策推向另一侧的上升段。取舍在于门禁数量：越多越安全但越容易互相冲突导致无可行解。判据是任务成功率、P99 完成延迟、超时率与每成功任务成本四项同时达标，并明确冲突时的优先级（正确性 > 质量 > 延迟 > 成本）。fan-out 上限必须作为独立门禁，防止单任务峰值冲击。

## 17. 实验设计与双路径验证

实验复用新型推理工作负载基准平台的 workload generator，在其上增加 Reasoning 模式：可控思考预算分布、难度分桶、fan-out 分支数、deadline 与取消注入。本文给出设计规格与指标口径，不含可执行代码。

**路径 A：机制模拟（`source=fixture`）。** 只依赖 CPU。输入：$Q_\infty$、$K$、$F$、$c_{tok}$、$T_{pre}$、$TPOT$、$B_{slot}$、KV 每 Token 占用、流量长短比例与到达率、deadline 分布、$M$ 与 $p_v$、取消传播延迟、Tier 映射。输出：$Q(B)$、$Q'(B)$、$C(B)$、$T(B)$、$B^*$、$C/Q$、$B_{max}(D)$、$Q_M$、$C_M$、并发上限、槽位占用比、短请求等待、无效 Token、剩余工作量与所需槽位。扫描维度为 $B\in\{250..32000\}$、$M\in\{1,2,4,8,16\}$、$D\in\{5,10,20,30,60,120,300\}$ s、$K\in\{1000,2000,4000\}$、$F\in\{250,500,1000,2000\}$、并发 $\in\{8,16,32,64\}$、长请求占比 $\in\{5\%,10\%,20\%\}$。

**路径 B：真实测量（`source=measured`）。** 在可用 CUDA GPU 上运行同一组配置，采集八项必测指标：

| 指标 | 口径要求 |
| --- | --- |
| 思考 Token 数 | 区分 reasoning 与 answer 段，注明是否含被截断部分 |
| 任务成功率 | 分母为原始用户任务数，注明取消与超时是否计为失败 |
| 质量增益斜率 | $\Delta Q/\Delta B$，按难度桶报告，注明样本量 |
| 每成功任务成本 | GPU-ms 或美元，注明是否含 fan-out、verifier 与无效计算 |
| TTFT | 首 Token 时间，注明是否含 planner 与工具等待 |
| 完成延迟 | P50/P95/P99 分别报，注明窗口与请求集 |
| 超时率 | 分子区分「超时返回」与「被截断」，分母注明是否含取消 |
| 队列年龄 | 按长短队列分别报，注明统计窗口与分母 |

外加 KV 占用峰值、槽位利用率、fan-out 峰值与 burstiness、无效 Token 数、剩余工作量估计误差。每次运行记录完整环境与模型修订、预算策略版本、Tier 映射、难度估计器版本。

**双路径对账。** 同一配置下比较模拟与实测的 $Q(B)$ 曲线、$B^*$ 位置与 $C/Q$ 排名：方向一致但数值偏离时优先补齐批次 padding、Kernel 启动、CPU 调度、verifier 服务与取消传播项；方向相反时先核对口径（成功率分母、$c_{tok}$ 是否含 fan-out 摊销、$K$ 标定数据集），再检查是否触发未建模的截断或降级。模拟结果不得写成实测数字，实测结果不得外推到未运行过的负载区间与未标定的难度域。

**门禁与回滚。** 任何预算策略变更必须通过与基线策略的任务成功率对账（不劣化）与每成功任务成本对账（在门禁内）；取消传播必须逐环注入验证；fan-out 上限与 Tier 映射作为独立配置项支持灰度与一键回退。质量评测集与线上分布不一致时不进入评审。

## 18. 常见错误与排查

| 现象 | 可能原因 | 排查动作 |
| --- | --- | --- |
| 加预算质量不涨 | 已进入收益递减段（斜率降至 1/36） | 报质量增益斜率，按 $B^*$ 收敛预算 |
| 每成功任务成本持续上升 | 预算越过 $B^*$ 或 fan-out 过大 | 用 $\sqrt{FK/c_{tok}}$ 复核，锁定质量目标反解 $M$ |
| 短请求 P99 突然恶化 | 长请求占满槽位（78.7% 槽位时间） | 隔离长短队列，按 SLO 设隔离比例 |
| 并发上限远低于预期 | 按请求数而非 KV 估容量 | 改用 Token·秒与 KV 占用，重算 11.8% 折减 |
| 超时后 GPU 仍在跑 | 取消传播断链 | 逐环注入取消，确认引擎侧停止 |
| 每月算力账单异常 | 无效计算未计入（\$1813/月量级） | 统计无效 Token，纳入成本口径 |
| 平均延迟达标但客户投诉 | 均值掩盖 P99（25.4 s vs 200 s） | 直接报分位数与超时率 |
| 配额限制了短请求租户 | 按请求数计量（偏差 33.3 倍） | 改按 Token × 模型权重计量 |
| Deep 档亏损 | 按预算倍数定价（成本低 2.27 倍） | 按每成功任务成本定价，核对 12.8× 上限 |
| wall-time 预算静默失效 | TPOT 随并发上升未重算 | 用实测 TPOT 动态反解 $B_{max}(D)$ |
| Autoscaler 方向反了 | 用并发数而非剩余工作量 | 改用 $\sum(O_i-o_i^{done})$，两时刻差 21.2 倍 |
| 终止器提前收敛 | 把输出变短误判为已收敛 | 校验进展信号，按任务成功率门禁 |
| 离线最优预算线上不适用 | $K$ 标定集与线上难度分布不一致 | 按域重新标定 $K$，分桶报斜率 |
| fan-out 打满 Replica | 单任务瞬时占用 8 槽无上限 | 设 fan-out 门禁与租户配额联动 |

## 19. 常见追问与解答

**问：Reasoning Serving 与普通 Serving 的本质差别是什么？**
答：输出长度从「结果」变成「计算预算」。普通请求 6 s、Reasoning 请求 200 s，驻留时间差 33.3 倍，KV 占用差 8.5 倍，并发上限差 8.5 倍。因此公平性、截止时间、取消传播与工作量信号第一次成为一等公民。

**问：思考预算应该设多大？**
答：没有通用值，但有闭式解 $B^*=\sqrt{FK/c_{tok}}$。本文设定下为 1265 Token。它随固定开销 $F$ 与难度 $K$ 增大而增大，随单 Token 成本 $c_{tok}$ 增大而减小，因此必须与负载联动。

**问：为什么给更多时间反而可能更差？**
答：每成功任务成本在 deadline 轴上是 U 形的。5 s 时被迫用 245 Token，成本比最优高 79.7%；300 s 时用满 14995 Token，成本高 235.9%。质量最大化与成本最优化的答案不同，必须先声明目标。

**问：Test-Time Scaling 多采样几条总是更好吗？**
答：不是。固定预算下 $M$ 越大性价比越差（$M=8$ 时 $C/Q$ 从 3701 涨到 9149）。只有在锁定质量目标反解预算时，才存在最优 $M$：$Q=0.60$ 对应 $M=4$，$Q=0.80$ 对应 $M=8$。

**问：fan-out 对平台是好事还是坏事？**
答：对单任务双赢（$Q=0.80$ 时延迟降 16 倍、成本降 41.4%），对平台是峰值冲击（瞬时 8 槽）。因此必须与租户配额和 fan-out 门禁打通，否则少量 Deep 用户就能饿死短请求。

**问：Tier 按 1×/4×/16× 定价有什么问题？**
答：实际每请求成本比是 $1:4.98:36.27$，Deep 档成本是标称倍数的 2.27 倍，因为 fan-out 让成本超线性。合理溢价上限由每成功任务成本比 12.8 倍决定，可定价空间比直觉窄得多。

**问：为什么不能按请求数做配额？**
答：本文例子中短请求租户用了长请求租户 30% 的算力，却看起来是 10 倍的请求数，偏差 33.3 倍。必须按 $Usage_u=\sum OutputTokens_r\cdot Weight_{model}$ 计量，且计量点落在每次模型调用而非任务返回。

**问：Autoscaler 该看什么信号？**
答：剩余工作量而不是并发数。两个并发数同为 32 的时刻，剩余 Token 可以相差 21.2 倍，扩缩方向完全相反。用 $\sum(O_i-o_i^{done})$ 结合目标排空时间反解所需槽位。

## 20. 延伸练习

1. 把 $Q(B)$ 换成幂律形式 $Q_\infty(1-e^{-B/B_0})$，重新推导每成功任务成本的最优预算，并比较两种质量模型给出的 $B^*$ 差异。
2. 推导 $B^*=\sqrt{FK/c_{tok}}$ 对三个参数的弹性（相对变化率），并据此判断哪个参数的估计误差对预算决策影响最大。
3. 把第 9.4 节的目标质量扫描扩展到 $Q\in\{0.4,0.5,0.6,0.7,0.8,0.85\}$，画出最优 $M$ 随目标质量的变化曲线，并解释为何 $Q>Q_\infty p_v$ 时无解。
4. 推导 verifier 准确率 $p_v$ 的盈亏平衡值：在给定 $M$ 与 $B$ 下，$p_v$ 低于多少时 fan-out 不如单轨迹。
5. 为第 5.3 节的隔离方案推导最优槽位分配：在短请求 P99 硬约束下，求使长请求吞吐最大的分配比例，并说明流量结构变化时如何重算。
6. 设计取消传播的逐环验收方案：列出每一环的注入点、确认信号与最大允许延迟，并推导传播延迟对无效 Token 的贡献。
7. 把第 13 节的剩余工作量信号扩展为带预测的 autoscaler 输入：考虑到达率预测与预算分布，推导目标排空时间下的所需槽位公式。
8. 为 Fast/Balanced/Deep 三档设计完整定价表：给出每成功任务成本、质量、墙钟上限与合理溢价区间，并说明 fan-out 上限如何影响定价空间。

## 写在最后

长思考把 Serving 的决策变量从「毫秒级的验证长度」换成「分钟级的计算预算」，于是三个此前可以忽略的问题变成核心：质量收益递减使最优预算存在闭式解、长驻留使公平性必须按 Token 而非请求数计量、截止时间与取消传播决定了无效计算的规模。本文推导给出的几个数字——$B^*\approx1265$、并发上限折减到 11.8%、短请求等待 16.7 倍、Deep 档成本超线性 2.27 倍、剩余工作量差 21.2 倍——都指向同一件事：**Reasoning 场景下按请求数做的任何决策都会失准**。
