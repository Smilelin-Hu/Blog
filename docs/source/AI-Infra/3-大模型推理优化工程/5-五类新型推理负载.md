# 五类新负载：Reasoning、Agentic、Structured、Multimodal、Compound

「一次请求 = 一次 Prefill + 一段 Decode」这个假设，在五类新负载下逐一失效。它们的共同点是：**容量与延迟的决定因素从「token/s」变成了「阶段结构」**。

## 1. Reasoning：长驻留任务

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y3_l11_01.png" width="78%" alt="Reasoning serving" />
  <p>图 1：长思考把「输出长度」变成计算预算，也让请求驻留时间放大一个数量级</p>
</div>
### 1.1 预算曲线不是线性的

$$
\max_B\ \mathrm{Quality}(B) - \lambda\,\mathrm{Cost}(B)
$$

受 latency / user tier / business value 约束。质量随预算增加的边际收益递减，所以「给更多思考时间」不是免费的正确率。

### 1.2 驻留时间放大

$$
T_i \approx O_i \cdot \mathrm{TPOT}_i
$$

普通请求 \(O=300\)、推理请求 \(O=10000\)，即使 TPOT 相同，后者在实例里待的时间也高一个数量级。五个连锁后果：

- KV 占用更久；
- scheduler slot 被占更久；
- 与短请求形成资源不公平；
- 用户中途取消时浪费的 token 更多；
- **Autoscaler 看到的「当前并发数」不再代表剩余工作量**。

最后一条最容易出事：并发数一样，剩余工作量可能是 30 倍。

### 1.3 四种预算

| 形式 | 做法 | 适用 |
|---|---|---|
| Token budget | `max_reasoning_tokens` 4096/8192/16384 | 硬上限，最直接 |
| Wall-time budget | \(Remaining = Deadline - Now\)，按当前速度决定是否继续 | 交互场景 |
| Cost budget | 每请求成本 \(\le C_{max}\) | API 计费、企业 Agent、批量任务 |
| Quality/Confidence budget | 达到足够置信度就提前结束 | 需要额外的 quality estimator |

### 1.4 Test-Time Scaling 的平台代价

```text
Question → Reasoning 1..M → Verifier/Judge → Answer
```

$$
C \propto \sum_{m=1}^{M} \text{Tokens}_m
$$

fan-out 会带来并发瞬时放大、Verifier 成本、以及「M 条轨迹里失败的算不算浪费」的计量问题。

## 2. Agentic：流量放大与状态机

```text
一次用户任务
  → Planner → Tool A / Tool B / Tool C → Aggregator → 继续 LLM
  → 工具等待期间不消耗 GPU，但占着会话与 deadline
```

### 2.1 Traffic amplification

$$
\lambda_m = \lambda_u \cdot E[F]
$$

一次请求平均 fan-out 8 次：外部 20 req/s → 内部 160 model calls/s。而且它们不是平滑到达，而是 Planner 决策后**同时爆发**。

### 2.2 生命周期不是一个持续 Decode

```text
RUNNING_LLM → WAITING_TOOL → RUNNING_LLM → WAITING_USER/APP → RUNNING_LLM → DONE
```

工具等待时要回答四个问题：

1. 会话状态保留多久？
2. KV 是否继续占 GPU？
3. 多久后 offload / recompute 更划算？
4. 工具超时后，是否取消下游模型调用？

第 4 个问题最容易被漏掉：上游超时、下游还在跑，就是典型的「GPU 在给没有消费者的请求发 token」。

### 2.3 Fan-out 的延迟与成本

$$
T_{fanout} \approx \max_i T_i + T_{merge},\qquad
C_{fanout} \approx \sum_i C_i
$$

并行降低 wall-clock，却增加瞬时资源压力与总成本。

### 2.4 Deadline 必须传播

$$
D_{remain} = D_{global} - Now,\qquad D_i \le D_{remain}
$$

用户给整个 Agent 30 秒，不代表每一步都能用 30 秒。某个 Tool 已经花了 25 秒，再启动一个预期 20 秒的深度推理调用，大概率只是浪费资源。Gateway / Agent Runtime 应把 deadline 传播到 sub-agent、tool call、模型调用与重试。

## 3. Structured Output：把采样限制在合法集合里

### 3.1 机制

约束采样先按 grammar 当前状态 \(s\) 求出合法集合 \(A_s\)，把不合法 token 的 logits 置为 \(-\infty\)：

$$
logits'_i =
\begin{cases}
logits_i, & i \in A_s \\
-\infty, & i \notin A_s
\end{cases}
,\qquad
p'(x) = \mathrm{softmax}(logits')
$$

这样生成路径始终满足 grammar。

### 3.2 从 Schema 到状态机

```text
JSON Schema → object{name: string, age: integer}
        ↓
FSM：START → { → "name" → : → STRING → , → "age" → : → INTEGER → } → END
```

**真实 tokenizer 不是字符级**：还要把 grammar 允许的字符/字节序列映射为合法 token ID。这一步才是 Structured Output 性能工程的关键——映射表的大小直接决定每步 mask 的成本。

### 3.3 两个成本

$$
T_{structured} = T_{model} + T_{mask} + T_{state}
$$

- **编译成本 \(T_{compile}\)**：新 Schema 要 parse、normalize、建自动机、做 tokenizer 映射、再缓存。每个请求都换 Schema 又不缓存，TTFT 会明显变差。
- **每步 mask 成本**：查 allowed set、生成/应用 mask、采样、更新状态。模型小、batch 大、输出短的时候，**CPU mask overhead 不再可以忽略**。

工程对策：Schema cache（按 schema 哈希 + tokenizer 版本）、按需编译、把 mask 计算下推到 GPU kernel、对高频 schema 预编译。

## 4. Multimodal：四种瓶颈与三层缓存

### 4.1 工作量不能按请求数算

$$
W = \alpha B_{media} + \beta N_{frames} + \gamma N_{visionTokens} + \delta N_{llmTokens}
$$

两个「1 request」的工作量可能差 100 倍。**按请求数做容量规划尤其危险。**

### 4.2 四种瓶颈

| 瓶颈 | 表现 | 对策 |
|---|---|---|
| Download bound | 远程 URL / 对象存储 / CDN 慢 | 缓存、就近拉取、预签 URL |
| CPU decode / preprocess | JPEG/PNG/视频解码、resize、normalize 吃 CPU | 线程池、硬件解码、降分辨率 |
| Encoder bound | Vision/Audio Encoder 占 GPU，与 LLM 竞争 | 独立 stream/池、feature cache |
| LLM bound | 视觉 token 进入上下文，Prefill 与 KV 膨胀 | 控制 token 数、压缩、裁剪 |

只看总耗时永远不知道瓶颈在哪里，必须看完整 trace。

### 4.3 流水线错峰

```text
最差：CPU 下载 → 等 → CPU 解码 → 等 → GPU Encoder → 等 → LLM
更好：A: Download→Decode→Encoder→LLM
      B:         Download→Decode→Encoder→LLM
      C:                Download→Decode→Encoder→LLM
```

用异步 I/O、线程池与独立 stream，把不同请求的阶段重叠起来。

### 4.4 三层缓存

| 层 | 缓存什么 | Key |
|---|---|---|
| Media cache | 原始 bytes | `Hash(URL, ETag, ContentDigest)` |
| Preprocessed cache | resize/normalize 后的 Tensor | 上面 + preprocess config |
| Encoder feature cache | encoder 输出 | `Hash(MediaDigest, EncoderRevision, PreprocessRevision)` |

**不能用 URL 当唯一 key**：同一 URL 的内容会变，同一图片在不同 encoder revision 下 feature 也不同。缓存 key 少一个版本维度，就会在升级后静默返回旧特征。

## 5. Compound AI：只有关键路径上的优化才算数

  <p>图 2：Embedding → Search → Rerank → LLM → Safety 的跨阶段依赖</p>
</div>

### 5.1 串行与并行

$$
T_{e2e} = \sum_i T_i\ (\text{串行}),\qquad
T_{parallel} = \max_i T_i\ (\text{并行})
$$

复杂 DAG 的用户延迟由最长依赖路径决定。

### 5.2 一个反直觉的例子

```text
Embedding 10ms → Search 20ms → Rerank 100ms → LLM 2000ms → Safety 50ms
```

- 把 Embedding 从 10 ms 优化到 2 ms，端到端只省 8 ms；
- 如果 Reranker 把 LLM 的 Prompt 从 8000 token 压到 2000 token，即使它自己花 100 ms，整体也可能更快更省。

量化方式：

$$
\mathrm{Value}_i = \mathrm{DownstreamCostSaved}_i - \mathrm{Cost}_i
$$

**不能只看某一阶段的 latency 判断值不值得。**

### 5.3 Stage budget 与降级

$$
\sum_i B_i \le D_{global}
$$

静态均分通常不合理，应按历史 P95、业务重要性与 fallback 能力分配。某阶段超预算时的降级手段：timeout、skip、用 cache、降级模型、减少候选数。

### 5.4 Bulkhead：别让一个阶段拖死全部

Embedding、Reranker、LLM 共用一个无限队列，一次突发会传播到所有阶段。正确做法是各自独立资源池：

```text
Embedding Pool | Reranker Pool | LLM Pool | Judge Pool
```

每个池有自己的并发上限、队列长度、超时与熔断——这才叫隔离。

## 6. 五类负载的对比

| 负载 | 容量单位 | 关键约束 | 最容易踩的坑 |
|---|---|---|---|
| Reasoning | 输出 token × 并发 | 长驻留、KV 与 slot 占用 | 用并发数估算剩余工作量 |
| Agentic | 内部 model calls/s | fan-out 突发、工具等待、deadline | 取消不传播，下游空转 |
| Structured | 每 token mask 成本 | 编译开销、CPU mask | 每请求新 Schema 不缓存 |
| Multimodal | 加权工作量 \(W\) | 四段瓶颈、三层缓存 | 按请求数规划容量 |
| Compound | 关键路径 | 阶段预算与降级 | 优化了不在关键路径的环节 |

## 写在最后

五类负载的共同结论：**先把请求拆成阶段，再谈优化**。谁的阶段结构最复杂，谁就最容易被「局部变快、整体没变」骗到。
