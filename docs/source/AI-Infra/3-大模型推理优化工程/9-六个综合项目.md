# 六个综合项目：验收标准与失败模式

第三期的六个项目不是六份代码，而是六次「把系统跑起来并证明它成立」。每个项目都有自己的验收条件，这些条件本身就是最好的设计清单。

## 1. 项目全景

| # | 项目 | 目标 | 核心验收 |
|---|---|---|---|
| 1 | 新一代 Speculator Benchmark | 同一工作负载成对比较禁用/启用 | 成对到达、身份一致、输出等价、部署归因 |
| 2 | 新负载基准平台 | 五类工作负载按到达时间重放 | 五类都跑通、保持到达顺序、结构化输出校验、多跳链路 |
| 3 | 生产级 Gateway + Smart Router | 配额预留、负载选路、前缀亲和、故障转移 | 每请求有决策、失败副本被排除、亲和有状态、预留全部结算 |
| 4 | Multi-Tenant / Multi-Model / Multi-LoRA | 加权公平调度 + 配额 + 选路 + 驻留淘汰 | ≥2 租户/模型/Adapter、adapter 显式、公平调度被触发 |
| 5 | GPU Fleet Planner + Autoscaler | 容量证据驱动的选型装箱与扩缩容 | 拒绝 fixture 容量、放置满足约束、表示启动延迟、探测当前端点 |
| 6 | 生产级 Inference Platform | 把注册、Canary、选路、配额、回退、扩缩容、成本串成一次运行 | 非法状态迁移失败、候选被 shadow 对比、失败回落、预留结算 |

## 2. 项目一：Speculator Benchmark

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y3_l31_01.png" width="76%" alt="Speculator benchmark" />
  <p>图 1：成对 A/B 的四个证据来源：工作负载哈希、制品/部署证据、成对端点记录、指标快照</p>
</div>

**必须成对**：每个请求同时打到 baseline 与 candidate，否则比较的是两个世界。四条验收：

1. 每个请求都到达两个端点；
2. target / sampling / workload 身份一致；
3. candidate 输出等于 baseline（lossless 的意义）；
4. 部署证据把 candidate 绑定到具体制品（artifact sha + launch command sha）。

漏掉第 4 条，会出现「换了版本却还用旧结论」的经典错误。

## 3. 项目二：新负载基准平台

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y3_l32_01.png" width="76%" alt="新负载基准平台" />
  <p>图 2：五类工作流统一重放，分类核算 SLO</p>
</div>

要求：按**到达时间**重放 Reasoning、Agentic、Structured、Multimodal、Compound 五类工作流，并分别核算端到端 SLO。

验收要点：

- 五个 handler 全部跑通；
- **到达顺序被保留**（否则排队行为不可比）；
- 结构化输出真的被校验（不是只看字符串）；
- compound/agentic 路径确实产生多次关联调用（subcall lineage）。

产出：分类指标、SLO 违规、子调用谱系、指标快照。

## 4. 项目三：Gateway 与 Smart Router

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y3_l33_01.png" width="76%" alt="Gateway 与 Smart Router" />
  <p>图 3：配额预留 → 负载选路 → 前缀亲和 → 失败反馈 → 故障转移</p>
</div>

四条验收：

1. 每个被接受的请求都有一次明确的选路决策（可审计）；
2. 主端点失败后，重试时**排除该端点**（而不是再撞一次）；
3. prefix 亲和是**有状态**的（能证明命中与未命中的差异）；
4. 所有预留（quota reservation）最终都被结算（成功、失败、取消三条路径都要结清）。

第 4 条最容易被忽略：预留不结算就是账目黑洞，跑一天后配额对不上。

## 5. 项目四：多租户 / 多模型 / 多 LoRA

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y3_l34_01.png" width="76%" alt="多租户多模型" />
  <p>图 4：加权公平顺序 + Token 配额 + Adapter 驻留与淘汰</p>
</div>

要求：以**加权公平**顺序处理多租户请求，执行 Token 配额、模型/Adapter 选路、驻留淘汰，并调用真实端点。

验收：

- 至少两个租户、两个模型、两个 Adapter；
- 每笔被接受的预留都结算；
- **每个 LoRA 请求都显式声明 adapter**（不能靠默认值）；
- 公平调度器确实被触发（有排队与交错证据）。

产出：公平排程序列、租户账目、Adapter 命中/淘汰轨迹、逐 ID 指标。

## 6. 项目五：Fleet Planner 与 Autoscaler

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y3_l35_01.png" width="76%" alt="Fleet Planner" />
  <p>图 5：带原始证据哈希的容量点 → 装箱 → 带启动延迟/滞后/冷却的扩缩容</p>
</div>

两个阶段：先做**选型与装箱**（带原始证据哈希的实测容量点），再对需求时间序列跑**带启动延迟、滞后与冷却**的扩缩容状态机。

验收：

1. fixture 容量被拒绝（必须用实测证据，不能拿假数据过关）；
2. 放置满足显存 / 库存 / SLO 约束；
3. 启动延迟被显式表示（不是假设瞬时可用）；
4. 当前端点被真实探测（不是读配置猜）。

## 7. 项目六：生产级推理平台

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y3_l36_01.png" width="76%" alt="生产级平台" />
  <p>图 6：注册 → Canary → 选路 → 配额 → 故障回退 → 扩缩容 → 成本证据</p>
</div>

把前五个项目合成一次完整运行，验收五条：

1. **非法状态迁移必须失败**（例如未 Ready 就导流、未 drain 就删除）；
2. **候选被 shadow 对比**（真实流量旁路验证，而不是只看健康检查）；
3. **候选失败后流量回到 stable**（有回退证据）；
4. **所有预留结算**；
5. **最终状态是显式的**（不是「大概跑完了」）。

产出：端到端 trace、发布决策、故障恢复记录、容量与成本报告。

## 8. 五个通用失败模式

| 失败模式 | 表现 | 根因与对策 |
|---|---|---|
| 不成对比较 | baseline 与 candidate 跑在不同负载上 | 强制成对 + 工作负载哈希 |
| 身份漂移 | 模型/tokenizer/采样参数不一样却当作同一实验 | 请求身份与版本字段贯穿全链路 |
| 预留不结算 | 配额越用越少但没人失败 | 成功/失败/取消三路都 settle |
| 假设瞬时容量 | 扩容后立刻按新容量决策 | 用 Ready+Loading+Pending，加冷却 |
| 只测健康不测真实路径 | 探针通过、用户报错 | Canary 走完整 Tokenizer→引擎→流式链路 |

第三期到这里收尾：从指标与三个平面，到下一代生成加速、五类新负载、入口与路由、复用与上线、控制面与经济学，最后用六个项目证明「这整套东西能跑」。
