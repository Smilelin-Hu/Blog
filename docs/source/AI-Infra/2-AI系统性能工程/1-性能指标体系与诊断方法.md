# 性能工程：指标体系与诊断方法

性能工程最危险的情况不是「没有数据」，而是**大家拿着同一个数字，却在讨论不同的东西**。

两个团队都声称模型跑到 10,000 tokens/s，可能分别说的是：单用户单并发的输出速度、100 并发合计的系统吞吐、输入与输出相加的总吞吐、离线批处理峰值、只统计 Decode 不含排队与 Prefill、或者生成长度 16 对比 512。数字都算对了，但不可比。

## 1. 一个指标该带多少上下文

一个完整指标应当写成：

```text
Metric = 数值 + 单位 + 工作负载 + 负载模型 + 统计口径 + 正确性/SLO + 环境
```

缺任何一项，这个数字就只能用来「感觉」，不能用来「决策」。

## 2. 端到端时间分解

先把一次训练 Step 或一次请求拆开：

$$
T_{e2e} = T_{input} + T_{transfer} + T_{compute} + T_{communication} + T_{runtime} + T_{idle} + T_{recovery}
$$

- \(T_{input}\)：读取、解码、分词、组批；
- \(T_{transfer}\)：CPU↔GPU、GPU↔GPU 搬运；
- \(T_{compute}\)：前向/反向/采样；
- \(T_{communication}\)：AllReduce、AllGather、ReduceScatter、All-to-All；
- \(T_{runtime}\)：Python、Dispatcher、Kernel Launch、分配与同步；
- \(T_{idle}\)：气泡、负载不均、锁与排队；
- \(T_{recovery}\)：重启、回滚与重算摊销到有效工作的成本。

加法模型适合「没有重叠」的直觉分析。若各阶段能流水化，稳态更接近：

$$
T_{steady} \approx \max(T_{input}, T_{transfer}, T_{compute}, T_{communication}) + T_{unhidden}
$$

预取、异步拷贝、通信重叠，本质上都是把「相加的等待」变成「被别的活藏起来的等待」。这也解释了为什么优化要挑占比大的环节——Amdahl 定律给出上限：

$$
S_{total} = \frac{1}{(1-p) + p/s}
$$

一个占总时间 10% 的 Kernel 即使优化到无穷快，端到端也只有 \(1/(1-0.1) = 1.11\times\)。

## 3. 有效产出：Goodput 而不是 GPU-Util

$$
\mathrm{Goodput}_{abs} = \frac{\text{正确且满足 SLO 的工作量}}{\text{总墙钟时间}},\qquad
\mathrm{Goodput}_{ratio} = \frac{\text{实测有效吞吐}}{\text{参考有效吞吐}}
$$

训练里，只有真正推进进度且没因失败丢失的 Step 才算有效工作；在线推理里，超时、失败、被取消的请求即使吃满了 GPU，也不计入业务 Goodput。**GPU-Util 高不代表产出高**——它只说明卡在忙。

## 4. 延迟：平均值会骗人

### 4.1 为什么必须看尾延迟

99 个请求 100 ms、1 个请求 10 s，平均约 199 ms——报告看不出「大多数很快」，也看不出「有一个极慢」。所以在线系统要同时报：P50（典型体验）、P90/P95（较慢）、P99/P99.9（SLO 风险）、Max（排障用）。

百分位必须配样本数：只有 100 个样本时，P99 几乎由最慢的那一个决定。

### 4.2 LLM 请求的时间拆解

```text
请求发出 ── 排队/调度/网络/Prefill/首次采样 ──▶ 第一个 Token ── gap ── Token2 ...
│<-------------- TTFT --------------->│
│<------------------ E2E Latency ------------------>│
```

- **TTFT**：\(t_{\text{first token}} - t_{\text{request sent}}\)，含网络、排队、调度、Prompt 预处理、Prefill 与首次 Decode；
- **ITL**：相邻 Token 事件间隔 \(t_{j+1} - t_j\)，反映「是否流畅」，必须看分布（平均 30 ms 可能是每步稳定 30 ms，也可能是多数 10 ms、偶尔 500 ms）；
- **TPOT**：\((L_{e2e} - \text{TTFT}) / (N_{out} - 1)\)，即排除首 Token 后每个输出 Token 的平均时间；
- **每用户 Tokens/s**：\(\approx 1/\text{TPOT}\)，TPOT 50 ms 即约 20 tok/s/user。

注意口径陷阱：若服务端一次流式事件返回多个 Token，TPOT 与 ITL 不是同一个东西；某个请求的 TPOT 等于它自己的 ITL 均值，但全局 TPOT 分布与全局 ITL 分布并不必然相同。

### 4.3 症状 → 归因

| 现象 | 更可能的原因 | 优先检查 |
|---|---|---|
| TTFT 高、TPOT 正常 | 排队、长 Prompt、Prefill、冷启动 | Scheduler、Prompt 长度、Prefill Batch、Prefix Cache |
| TTFT 正常、TPOT 高 | Decode 慢、KV Cache、带宽、批次过大 | Decode Batch、KV Cache、量化、带宽与 Kernel |
| 两者都高 | 系统过载、模型/硬件不匹配 | 到达率、并发、资源、并行与服务配置 |
| P50 正常、P99 很差 | 长短请求干扰、队头阻塞、抖动 | 请求分布、调度策略、GC、共享资源、网络 |

## 5. 吞吐：单位决定含义

- **RPS / QPS / Samples/s**：一次请求不等于一个查询、也不等于一个样本，报告必须写清单位；
- **失败与超时**是否计入分母要说清，生产容量只统计「成功且满足质量要求」的请求。

LLM 有三种 Tokens/s，容易被混用：

$$
\mathrm{TPS}_{in} = \frac{\sum_i N_{in,i}}{T},\quad
\mathrm{TPS}_{out} = \frac{\sum_i N_{out,i}}{T},\quad
\mathrm{TPS}_{total} = \frac{\sum_i (N_{in,i}+N_{out,i})}{T}
$$

输入吞吐主要反映 Prefill 工作量；输出吞吐反映 Decode 容量；总吞吐可能被长 Prompt 完全主导（4096 输入 + 16 输出 与 128 输入 + 512 输出，总量不可比）。

**系统吞吐与用户体验是矛盾的**：提高并发与批处理会提升系统总输出 Tokens/s，却降低每用户速度、抬高 TPOT。所以容量要写成「在 P99 TTFT 与 P99 TPOT 都满足 SLO 时的最大吞吐」。

## 6. 并发、队列与 Little 定律

稳定系统中：

$$
L = \lambda W
$$

\(L\) 为系统内平均请求数（排队 + 处理），\(\lambda\) 为到达/完成速率，\(W\) 为平均停留时间。它不能直接指导优化，但能做一致性校验：若仪表盘显示 100 req/s、平均延迟 2 s，而「在途请求」只有 10，那么至少有一个统计口径是错的。

负载曲线分三段：

```text
低负载：吞吐随到达率近线性增长，延迟平稳
拐点：利用率上升、批处理更有效，尾延迟开始抬升
过载：吞吐接近上限，延迟与超时急剧恶化
```

所以「压到系统不再变快」测到的是**离线峰值**，不等于在线可用容量。

## 7. 训练指标：Step Time、Tokens/s、MFU/HFU

### 7.1 吞吐与全局 Batch

$$
\text{Training Tokens/s} = \frac{B_{global} \times S}{T_{step}},\qquad
B_{global} = B_{micro} \times N_{DP} \times N_{grad\_accum}
$$

这里有个高频错误：**TP 与 PP 切的是同一个模型/同一个 Batch，不能乘进全局样本数**。把所有 GPU 数都乘进去会虚增吞吐。

### 7.2 模型 FLOPs 的 6P 近似

$$
F_{model/token} \approx 6P
$$

前向约 \(2P\)、反向对权重与激活约 \(4P\)。但这是近似，边界要记住：Attention 的序列相关项可能不可忽略；Embedding 与输出层的计数口径不同；MoE 不能用总参数，要按每 Token 实际激活的专家与共享层算；FMA 计 1 还是 2 FLOPs 必须统一。

### 7.3 MFU 与 HFU

$$
\mathrm{MFU} = \frac{F_{model/token} \times \text{Tokens/s}}{N_{device} \times \text{Peak FLOPs/device}},\qquad
\mathrm{HFU} = \frac{\text{实际执行 FLOPs/s}}{N_{device} \times \text{Peak FLOPs/device}}
$$

差别只有分子：MFU 只算「模型算法必需」的 FLOPs，HFU 算「硬件实际执行」的 FLOPs。开了激活重计算后，多出来的前向计算计入 HFU 而不计入 MFU，所以常见 \(\mathrm{HFU} > \mathrm{MFU}\)。

两点提醒：HFU 高不等于高效（大量无效重算也能让硬件很忙）；MFU 低也不告诉你原因——它只是「离峰值有多远」。可能的原因有一长串：GEMM 形状不友好、HBM 带宽打满、流水线气泡、DataLoader 等待、通信没重叠、Python/Kernel Launch 开销、把 checkpoint 与评估算进了窗口、峰值分母选错。

## 8. 六类瓶颈与实验规范

| 类型 | 常见信号 | 首先验证 |
|---|---|---|
| 计算 | 大 GEMM/Attention 占关键路径 | 数据类型、Tensor Core、形状、实际 FLOPs/s |
| 显存 | OOM、频繁分配、碎片、换入换出 | 峰值显存、张量生命周期、激活/KV Cache/优化器占用 |
| 带宽/访存 | GPU 很忙但计算单元吞吐低 | 算术强度、HBM 流量、合并访存、数据复用 |
| Runtime/Launch | 大量极短 Kernel、时间线有空洞 | Python 开销、Launch 数、同步、Fusion、CUDA Graph |
| 输入/系统 | GPU 周期性空闲、CPU 或存储先满 | DataLoader、解码、页锁定内存、NUMA、IO、预取 |
| 通信/调度 | 多卡扩展效率下降、长尾 Rank | Collective 时间、拓扑、Bucket、负载均衡、网络热点 |

一份合格的 Benchmark 至少记录：硬件与 Compute Capability；驱动/CUDA/PyTorch/Python 版本；模型、精度、Batch、序列长度与输入分布；Warmup 与正式迭代次数、同步方式；均值/中位数/P95/P99、吞吐与峰值显存；是否启用编译、AMP、TF32、CUDA Graph、FlashAttention；正确性容差；功耗与干扰；原始日志、命令、代码版本与随机种子。

`torch.cuda.Event` 计时、`torch.cuda.synchronize()` 同步、跳过 Warmup——这些细节决定了数字能不能被别人复现。
