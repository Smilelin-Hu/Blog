# 大模型分布式训练体系

本篇系统理解数据、张量、流水线与专家并行，学会为不同模型规模选择合适的分布式训练方案。

单卡训练像一个人完成整套装修：设计、搬料、施工、验收都在同一处。模型继续变大后，问题不再只是「多买几张 GPU」，而是怎样分工：数据怎样分、参数怎样分、层怎样分、长序列怎样分、MoE 专家怎样分，以及这些分工产生的数据交换是否值得。目标不是背诵 DP、TP、PP 等缩写，而是拿到模型规模、序列长度、GPU 数量与互联拓扑后，先判断「放不下、算不完、还是传不动」，再选择最少且最合适的并行维度。

## 1. 内容概览

- rank、world size、process group、local rank 与 DeviceMesh 的关系。
- 数据并行、分片数据并行、张量并行、流水线并行、序列并行、上下文并行与专家并行的区别。
- 全局 Batch、环形 All-Reduce、流水线气泡与 ZeRO 显存模型的初步估算。
- Sequence Parallel 与 Context Parallel 为什么不是同一个概念。
- 按容量、计算、通信与拓扑瓶颈设计混合并行方案。
- CPU/GPU 通用的 DDP 实验，以及强扩展与弱扩展效率的测量。

## 2. 核心直觉：先分清是哪一种「不够」

分布式训练通常在解决四类问题：**容量不够**（参数、梯度、优化器状态与激活无法同时放进一张卡）、**计算不够**（模型能放下但一次训练要几个月）、**通信太多**（等待 All-Reduce、All-Gather、Reduce-Scatter、All-to-All 或点对点传输的时间超过新增算力收益）、**系统不稳**（节点、网络、数据读取或检查点任何一层的长尾都会拖慢整个同步作业）。

不同策略切的是不同维度：

| 策略 | 主要切分对象 | 首要收益 | 主要代价 |
| --- | --- | --- | --- |
| DP / DDP | Batch 样本 | 提高吞吐 | 梯度同步 |
| ZeRO / FSDP | 模型状态 | 降低单卡状态显存 | 参数/梯度通信 |
| TP | 层内矩阵 | 单层也能跨卡 | 高频层内 Collective |
| PP | 网络深度 | 分摊层和参数 | 流水线气泡与激活传输 |
| SP | 部分序列维激活 | 配合 TP 降低激活冗余 | 额外切分/聚合 |
| CP | 完整上下文序列 | 支持超长序列 | Attention 通信与负载均衡 |
| EP | MoE 专家 | 分摊专家参数和计算 | Token All-to-All 与负载不均 |

最重要的工程原则：**能用较简单的策略达到目标，就不要过早叠加更多并行维度**。每增加一个维度，都会增加通信组、配置约束、检查点格式与故障排查复杂度。

## 3. 分布式训练的坐标系

- `world_size`：参与默认进程组的总进程数，常见配置是一块 GPU 对应一个进程。
- `rank`：进程在全局进程组中的唯一编号，范围 `0 ... world_size-1`。
- `local_rank`：进程在当前节点内的编号，常用于绑定本机 GPU。
- `process_group`：执行一组 Collective 的进程集合，DP、TP、PP、CP、EP 往往各有自己的组。

两台机器、每台 8 张 GPU 时通常 `world_size=16`；节点 1 的第 3 个本地进程可能是 `local_rank=3, rank=11`，它不一定同时属于同样大小的 DP、TP 和 PP 组。`torchrun` 负责启动进程并提供环境变量，不决定模型怎样切分；DDP 负责梯度同步，也不会自动把输入 Batch 切开，因此真实训练仍应使用 `DistributedSampler` 或等价的数据分片方案。

**DeviceMesh** 把一维 rank 重排成多维网格。16 张 GPU 采用 `TP=4, PP=2, DP=2` 时：

```text
world_size = DP × PP × TP = 2 × 2 × 4 = 16

(dp=0, pp=0, tp=0..3)  第一组层内并行
(dp=0, pp=1, tp=0..3)  第二个流水线阶段
(dp=1, pp=0, tp=0..3)  另一份数据副本
(dp=1, pp=1, tp=0..3)
```

实际框架可能采用不同的维度顺序与 rank 映射，不能根据乘积猜通信组，必须读取框架配置或打印 group 成员。

## 4. 七种并行策略

### 4.1 数据并行：模型复制，数据分开

DDP 在每个数据并行 rank 上保存一份完整模型，各 rank 读取不同样本，反向传播时聚合梯度，同步完成后每份模型保持一致。全局 Batch：

$$
B_{global} = B_{micro} \times N_{acc} \times D
$$

其中 $B_{micro}$ 是每个数据并行 rank 每个微步的 Batch、$N_{acc}$ 是梯度累积步数、$D$ 是**数据并行度**。混合并行时不能把总 GPU 数直接当作 $D$。优点是实现简单、计算量均匀、吞吐扩展直观；缺点是每张卡都保存完整模型状态，且每步都要同步梯度。

### 4.2 ZeRO / FSDP：让模型状态也分片

经典混合精度 Adam 训练常按每参数约 16 Bytes 估算模型状态：FP16/BF16 参数 2 B、梯度 2 B、FP32 主参数 4 B、Adam 一阶与二阶矩 8 B。设某个 TP×PP 分区内仍有 $P_{local}$ 个参数、数据并行度为 $D$，忽略 padding、临时缓冲、碎片与激活：

$$
M_{DDP} \approx 16 P_{local}
$$

$$
M_{ZeRO1} \approx 4P_{local} + \frac{12P_{local}}{D}, \qquad
M_{ZeRO2} \approx 2P_{local} + \frac{14P_{local}}{D}, \qquad
M_{ZeRO3} \approx \frac{16P_{local}}{D}
$$

ZeRO-1 分片优化器状态，ZeRO-2 再分片梯度，ZeRO-3 再分片参数。越彻底的分片越省静态模型状态，但前向与反向需要更频繁地聚合/散布参数与梯度。公式只是容量规划的起点，不是显存承诺：激活、通信 Bucket、CUDA Context、Allocator 碎片与 Kernel Workspace 仍需实测。

### 4.3 张量并行：一层矩阵也由多张卡共同计算

以 $Y=XW$ 为例：列并行切 $W$ 的输出列，每个 rank 计算一部分输出；行并行切 $W$ 的输入行，各 rank 得到部分和再归约。TP 能解决「单层都放不下」，但通常每层都产生 Collective，通信频率高，工程上常把 TP 组放在 NVLink/NVSwitch 等最快互联域内。两张只能通过 PCIe 通信的消费卡仍可验证正确性与观察通信，但其 TP 扩展性不能代表 A100/H100/B200 的高速互联系统。

### 4.4 流水线并行：按网络深度切成阶段

PP 把连续层放到不同设备：阶段 0 输出激活给阶段 1，反向时再反向传递梯度。为避免只有一个阶段工作，Batch 被拆成多个微批次，采用 GPipe、1F1B 或交错式调度。对最简单、阶段计算时间相等的 GPipe 模型，设阶段数 $p$、微批次数 $m$，只看填充与排空的气泡比例：

$$
Bubble \approx \frac{p-1}{m+p-1}
$$

增加 $m$ 可降低气泡，但会影响激活显存、调度开销与有效 Batch。阶段间层数相同也不保证计算相同：Attention、MoE、Embedding、输出头与重计算都可能造成 stage imbalance。

### 4.5 序列并行：减少 TP 区域里的激活冗余

Sequence Parallel 通常与 TP 配合，将 LayerNorm、Dropout 等原本在 TP rank 间重复保存/计算的激活沿序列维切分。它不是「任意长序列并行」的统称，也不是 Context Parallel 的旧名字。

### 4.6 上下文并行：把完整长上下文跨卡分担

Context Parallel 把输入序列沿 token 维分到多个 rank，并在 Attention 中交换必要的 Key/Value 或中间结果，以分摊长上下文激活与计算。它解决的是完整序列长度过大，通信模式与 SP 不同。可变长度样本还会引入负载不均，需要位置、mask、数据打包与通信调度共同配合。

### 4.7 专家并行：把 MoE 专家放到不同 Rank

EP 把专家参数与计算分布到多张 GPU：Router 选择专家后，token 通过 All-to-All 发往专家所在 rank，计算完成再返回。首要风险不是「专家数量不够」，而是路由不均——最忙 rank 决定同步步骤的尾延迟。MoE 的并行组关系依赖框架实现，不能总写成 `world=DP×TP×PP×CP×EP`，一些实现中 EP 与数据并行维度发生折叠或重新分组。配置前应让框架打印每个 process group 并验证每个 rank 的成员资格。

## 5. 混合并行：从可行解走向高效解

稳健的选型顺序：

1. 先测单卡容量与单步时间，能放下时先用 DDP。
2. 模型状态 OOM，优先尝试激活重计算、混合精度与 FSDP/ZeRO。
3. 单层或单个矩阵无法落在一张卡上，再引入 TP。
4. 层数很多、需要跨节点分摊深度时，引入 PP。
5. 超长上下文使激活或 Attention 计算成为瓶颈时，引入 CP/SP。
6. 模型是 MoE 且专家无法放下或需要扩大专家吞吐时，引入 EP。
7. 最后依据拓扑重排 rank，并调通信重叠、Bucket 与微批次数。

| 观察到的问题 | 首选方向 | 先验证什么 |
| --- | --- | --- |
| 完整模型能放下但训练太慢 | DDP | 弱扩展、数据管线、All-Reduce |
| 参数/梯度/优化器状态 OOM | ZeRO/FSDP | 模型状态与峰值激活占比 |
| 单层矩阵无法放下 | TP | 层内通信是否有高速互联 |
| 模型深度大、跨节点较多 | PP | stage balance 与气泡 |
| 长序列激活 OOM | CP/SP/重计算 | Attention 与激活内存 |
| MoE 专家参数或计算过大 | EP | token 分布与 All-to-All |

**拓扑感知**：通信频率越高越应靠近最快互联。TP 通常每层通信，优先放在单机 NVLink/NVSwitch 域；EP 的 token dispatch 对 All-to-All 敏感，关注双向带宽与拥塞；PP 主要在相邻阶段间传激活，适合清晰的链路映射；DP 梯度同步数据量大但可 Bucket 化并与反向计算重叠，常跨越更大范围。最优映射不是固定口诀，仍要以实际模型、拓扑与 Profiler 结果为准。

## 6. 关键性能模型

**环形 All-Reduce 通信量**：$D$ 个数据并行 rank、梯度大小 $G$ Bytes，理想环形 All-Reduce 每个 rank 的收发总量约

$$
V_{ring} \approx 2\frac{D-1}{D}G, \qquad
T_{comm} \approx n_{step}\alpha + \frac{V}{B_{effective}}
$$

$\alpha$ 是每个通信步骤的启动延迟，$B_{effective}$ 是包含协议、拓扑与争用后的有效带宽。小 Bucket 更容易提前启动并重叠，但消息过碎会放大延迟；大 Bucket 带宽利用好，却可能等到反向末尾才开始。

**通信重叠不是简单相加**：没有重叠时 $T_{step}\approx T_{compute}+T_{comm}+T_{input}$；理想重叠时

$$
T_{step} \approx \max(T_{compute}, T_{comm}) + T_{unhidden} + T_{input,critical}
$$

「通信被隐藏」并非通信消失，而是通信与计算占用不同资源并发执行。若 GPU Kernel、DMA、PCIe、NVLink 或网络共享瓶颈，二者也可能互相拖慢。

**扩展效率**：

$$
E_N = \frac{Throughput_N}{N \times Throughput_1}
$$

强扩展指总问题规模不变、增加设备，每卡工作变小、通信占比往往升高；弱扩展指每卡问题规模不变、总规模随设备增加，更容易得到较好效率，但全局 Batch 改变了优化语义。因此「两卡比一块卡快 1.8 倍」必须同时说明是强扩展还是弱扩展、全局 Batch 是否相同、精度与数据是否一致。

## 7. 瓶颈分析方法

1. **先问容量还是速度**：记录至少四类显存——参数/梯度/优化器状态、保存用于反向的激活、通信与临时 Workspace、Allocator reserved/fragmentation。只看 `nvidia-smi` 无法区分它们。
2. **分解 Step 时间**：`Data wait → H2D → Forward → Backward compute → Gradient communication → Optimizer → Checkpoint/logging`。观察每个 rank 的时间而不是只看 rank 0，同步训练的步耗时由最慢 rank 决定。
3. **检查通信是否在关键路径**：DDP Bucket 是否在反向过程中逐步启动；Collective 前是否出现长时间空白或 CPU Launch Gap；某个 rank 是否因数据、频率、温度或 MoE 路由更慢；通信是否落在预期网卡、PCIe Root Complex、NVLink 或 InfiniBand 上；梯度累积时非最后微步是否用了 `no_sync()`。
4. **区分算法瓶颈与拓扑瓶颈**：同一份代码在两张 PCIe 消费卡上扩展差，不能证明 DDP 算法无效；也不能用单机 NVLink 结果外推跨机网络。需要同时保存 GPU 型号、互联拓扑、NCCL 日志、消息大小与软件版本。

## 8. Level 0：纯 Python 并行方案规划器

保存为 `parallelism_planner.py`：

```python
#!/usr/bin/env python3
import argparse, json

GIB = 1024 ** 3

def model_state_bytes(params, dp, zero_stage):
    # 经典混合精度 Adam 粗略模型：参数 2B、梯度 2B、主参数 4B、动量 8B
    if zero_stage == 0:
        return 16 * params
    if zero_stage == 1:
        return 4 * params + 12 * params / dp
    if zero_stage == 2:
        return 2 * params + 14 * params / dp
    if zero_stage == 3:
        return 16 * params / dp
    raise ValueError("zero_stage 必须为 0、1、2 或 3")

def main():
    p = argparse.ArgumentParser(description="分布式训练并行度与静态显存规划器")
    p.add_argument("--params-b", type=float, default=7.0)
    p.add_argument("--world-size", type=int, default=8)
    p.add_argument("--tp", type=int, default=1)
    p.add_argument("--pp", type=int, default=1)
    p.add_argument("--micro-batch", type=int, default=1)
    p.add_argument("--grad-accum", type=int, default=8)
    p.add_argument("--pipeline-microbatches", type=int, default=None)
    p.add_argument("--zero-stage", type=int, default=0)
    p.add_argument("--sequence-length", type=int, default=4096)
    p.add_argument("--hidden-size", type=int, default=4096)
    p.add_argument("--layers", type=int, default=32)
    a = p.parse_args()
    if min(a.world_size, a.tp, a.pp, a.micro_batch, a.grad_accum,
           a.sequence_length, a.hidden_size, a.layers) <= 0:
        raise ValueError("并行度、Batch 和模型形状必须为正数")
    mp = a.tp * a.pp
    if a.world_size % mp != 0:
        raise ValueError("world_size 必须能被 tp × pp 整除")

    dp = a.world_size // mp
    total = a.params_b * 1e9
    local = total / mp
    m = a.pipeline_microbatches or a.grad_accum
    grad_bytes = 2 * local
    print(json.dumps({
        "degrees": {"world": a.world_size, "dp": dp, "tp": a.tp, "pp": a.pp},
        "global_batch": a.micro_batch * a.grad_accum * dp,
        "local_partition_params_b": local / 1e9,
        "zero_stage": a.zero_stage,
        "approx_model_state_gib_per_rank": model_state_bytes(local, dp, a.zero_stage) / GIB,
        "simple_pipeline_bubble_fraction": 0.0 if a.pp == 1 else (a.pp - 1) / (m + a.pp - 1),
        # 仅用于比较形状规模，不等同于真实激活显存
        "activation_elements_proxy": a.micro_batch * a.sequence_length * a.hidden_size * (a.layers / a.pp),
        # 仅是普通 DDP 梯度环形 All-Reduce 的粗略通信量
        "ddp_ring_gradient_traffic_gib_per_rank": (0.0 if dp == 1 else 2 * (dp - 1) / dp * grad_bytes) / GIB,
        "warnings": ["显存估算不含激活、通信缓冲、临时Workspace和碎片",
                     "activation_elements_proxy不是激活显存公式",
                     "ZeRO/FSDP的真实通信模式不能用普通DDP流量替代"],
    }, ensure_ascii=False, indent=2))

if __name__ == "__main__":
    main()
```

```bash
python parallelism_planner.py \
  --params-b 7 --world-size 8 --tp 2 --pp 2 \
  --micro-batch 2 --grad-accum 8 --zero-stage 2 \
  --sequence-length 4096 --hidden-size 4096 --layers 32
```

预期现象：`DP=2, TP=2, PP=2`，乘积等于 8；全局 Batch 为 `2×8×2=32`，不是 `2×8×8=128`；7B 参数先被 TP×PP 分为每 rank 约 1.75B，再由 ZeRO-2 对部分状态按 DP 分片；增大 PP 阶段数而保持微批次数不变时简单气泡比例上升；结果不能直接判断某张卡是否一定可跑，因为激活与临时内存尚未计入。

## 9. Level 1：CPU/GPU 通用 DDP Benchmark

保存为 `ddp_train_lab.py`：

```python
#!/usr/bin/env python3
import argparse, contextlib, json, os, time
import torch
import torch.distributed as dist
import torch.nn as nn
import torch.nn.functional as F
from torch.nn.parallel import DistributedDataParallel as DDP

def parse_args():
    p = argparse.ArgumentParser()
    p.add_argument("--hidden", type=int, default=1024)
    p.add_argument("--layers", type=int, default=4)
    p.add_argument("--local-batch", type=int, default=32)
    p.add_argument("--grad-accum", type=int, default=1)
    p.add_argument("--warmup", type=int, default=3)
    p.add_argument("--steps", type=int, default=20)
    p.add_argument("--bucket-mb", type=float, default=25.0)
    return p.parse_args()

def make_model(hidden, layers):
    modules = []
    for _ in range(layers):
        modules += [nn.Linear(hidden, hidden), nn.GELU()]
    modules.append(nn.Linear(hidden, hidden))
    return nn.Sequential(*modules)

def sync(device):
    if device.type == "cuda":
        torch.cuda.synchronize(device)

def main():
    args = parse_args()
    use_cuda = torch.cuda.is_available()
    backend = "nccl" if use_cuda else "gloo"
    dist.init_process_group(backend=backend)
    rank, world = dist.get_rank(), dist.get_world_size()
    local_rank = int(os.environ.get("LOCAL_RANK", "0"))
    if use_cuda:
        torch.cuda.set_device(local_rank)
        device = torch.device("cuda", local_rank)
    else:
        device = torch.device("cpu")
        # 多进程 CPU 实验避免每个进程都占满全部 CPU 线程
        torch.set_num_threads(max(1, (os.cpu_count() or 2) // world))

    torch.manual_seed(2026)          # 各 rank 初始参数一致
    model = make_model(args.hidden, args.layers).to(device)
    ddp = DDP(model, device_ids=[local_rank] if use_cuda else None,
              bucket_cap_mb=args.bucket_mb, gradient_as_bucket_view=True)
    optimizer = torch.optim.SGD(ddp.parameters(), lr=1e-3)
    params = sum(p.numel() for p in ddp.parameters())

    generator = torch.Generator(device=device)
    generator.manual_seed(1000 + rank)   # 数据种子按 rank 区分，模拟不同分片

    def train_step():
        optimizer.zero_grad(set_to_none=True)
        loss_value = 0.0
        for micro in range(args.grad_accum):
            # 非最后微步不做梯度同步；forward 也必须位于 no_sync 内
            ctx = ddp.no_sync() if micro < args.grad_accum - 1 else contextlib.nullcontext()
            with ctx:
                x = torch.randn(args.local_batch, args.hidden, device=device, generator=generator)
                target = torch.randn(args.local_batch, args.hidden, device=device, generator=generator)
                loss = F.mse_loss(ddp(x), target) / args.grad_accum
                loss.backward()
                loss_value += float(loss.detach())
        optimizer.step()
        return loss_value

    for _ in range(args.warmup):
        train_step()
    sync(device); dist.barrier()
    if use_cuda:
        torch.cuda.reset_peak_memory_stats(device)

    start, last_loss = time.perf_counter(), None
    for _ in range(args.steps):
        last_loss = train_step()
    sync(device); dist.barrier()
    elapsed = time.perf_counter() - start

    # 同步训练应使用最慢 rank 的耗时计算端到端吞吐
    t = torch.tensor(elapsed, dtype=torch.float64, device=device)
    dist.all_reduce(t, op=dist.ReduceOp.MAX)
    max_elapsed = float(t.item())
    global_samples = args.steps * args.local_batch * args.grad_accum * world

    if rank == 0:
        print(json.dumps({
            "world_size": world, "backend": backend, "device": str(device),
            "torch_version": torch.__version__, "parameters": params,
            "local_batch_per_microstep": args.local_batch, "grad_accum": args.grad_accum,
            "global_batch_per_optimizer_step": args.local_batch * args.grad_accum * world,
            "max_elapsed_s": max_elapsed, "step_ms": max_elapsed * 1000 / args.steps,
            "global_samples_per_s": global_samples / max_elapsed,
            "peak_allocated_gib_rank0": (torch.cuda.max_memory_allocated(device) / 1024**3) if use_cuda else None,
            "last_loss_rank0": last_loss,
        }, indent=2))
    dist.destroy_process_group()

if __name__ == "__main__":
    main()
```

CPU 回退（保持全局 Batch 约 32，属于简化强扩展对照）：

```bash
torchrun --standalone --nproc-per-node=1 ddp_train_lab.py \
  --hidden 512 --layers 3 --local-batch 32 --steps 10
torchrun --standalone --nproc-per-node=2 ddp_train_lab.py \
  --hidden 512 --layers 3 --local-batch 16 --steps 10
```

CPU 多进程可能因内存带宽与线程竞争而变慢，这是有效实验现象，不代表 GPU DDP 的结论。

GPU 运行：

```bash
# 单卡基线
CUDA_VISIBLE_DEVICES=0 torchrun --standalone --nproc-per-node=1 \
  ddp_train_lab.py --hidden 1024 --layers 4 --local-batch 64 --steps 30
# 双卡强扩展：全局 Batch 保持 64
CUDA_VISIBLE_DEVICES=0,1 torchrun --standalone --nproc-per-node=2 \
  ddp_train_lab.py --hidden 1024 --layers 4 --local-batch 32 --steps 30
# 双卡弱扩展：每卡 Batch 保持 64，全局 Batch 变成 128
CUDA_VISIBLE_DEVICES=0,1 torchrun --standalone --nproc-per-node=2 \
  ddp_train_lab.py --hidden 1024 --layers 4 --local-batch 64 --steps 30
# 梯度累积与 no_sync()
CUDA_VISIBLE_DEVICES=0,1 torchrun --standalone --nproc-per-node=2 \
  ddp_train_lab.py --hidden 1024 --layers 4 --local-batch 16 --grad-accum 4 --steps 30
```

预期现象与分析：GPU 模式使用 NCCL、CPU 回退使用 Gloo；两个 rank 使用不同随机数据，但 DDP 同步后参数更新保持一致；强扩展中每卡矩阵变小，计算效率可能下降、通信占比上升；弱扩展通常更容易获得较高吞吐，但全局 Batch 变化后不能直接比较收敛；`grad_accum>1` 时代码只在最后一个微步同步梯度，移除 `no_sync()` 后每个微步都可能触发通信；没有 NVLink 的双卡通信经过 PCIe，扩展效率受主板拓扑、PCIe 代际与 CPU Root Complex 影响。本实验是合成 MLP，结果只代表当次环境，不能替代真实 Transformer、真实序列长度与真实数据管线的 Benchmark。
