# 模型架构资源消耗量化

40 篇的估算框架里，$F$、$R$、$M$ 都是代入值；本文回答这些数字从哪里来：从模型配置逐矩阵推出运算量，从注意力结构推出每 token 存多少、每步读多少，从 MoE 路由推出批内实际访问的权重集合。贯穿口径：一次乘法加一次加法计 2 FLOPs，BF16 每元素 2 字节，GB 十进制、GiB 二进制。基线模型 Qwen3-8B：$L=36$ 层、$d=4096$、FFN 中间维 $f=12288$、32 个 Q 头／8 个 KV 头、头维 $d_h=128$、词表 151936，共约 81.9 亿参数。

## 1. 计算图：哪些等待能消除

计算图用节点表示运算、边表示数据依赖，边的方向决定哪些运算必须先后执行。两种结构的依赖完全不同：

- **RNN**：$h_t=f(x_t,h_{t-1})$，同层必须等前一 token，输入全到齐也无法并行。
- **因果 Transformer**：第 $l$ 层某位置只读上一层中该位置及之前的表示；上一层完成后，同层已知输入 token 可并行。因果掩码限制信息来源，不要求逐个执行。深度方向依赖仍在，生成时还多一条跨调用串行依赖：下一次输入由本次输出确定。

记号约定：$B$ 请求数、$P$ 本次每请求输入 token 数、$S$ 已有上下文长度，$m=BP$ 是本次参与投影的总行数（普通 decode 时 $P=1$，$m=B$）。投影输入 $X\in\mathbb{R}^{m\times d}$：prefill 形成大行数矩阵，decode 在小 batch 下接近矩阵向量乘。**权重相同，输入形状截然不同**——这是两阶段性能差异的根源。

## 2. 逐矩阵推运算量

对 $[m,k]\times[k,n]$ 投影：$N_W=kn$，$F=2mkn$，$M_W=b_Wkn$。行数 $m$ 翻倍运算量翻倍、权重不变；宽度 $n$ 翻倍两者都翻倍。

Qwen3-8B 一层：Q／O 投影各 $4096\times4096$，K／V 各 $4096\times1024$，SwiGLU 三矩阵各 $4096\times12288$：

$$
N_{\mathrm{proj}}=2\times4096^2+2\times4096\times1024\approx4194\ \text{万},\quad N_{\mathrm{FFN}}=3\times4096\times12288\approx1.51\ \text{亿}.
$$

FFN 占主要投影参数约 78%，短上下文时计算份额最大。注意力交互另算：$P$ 个新 token、$S$ 个旧 token 的有效因果查询—键配对是一个长方形加三角形：

$$
N_{\mathrm{pair}}=B\left(PS+\frac{P(P+1)}{2}\right),\qquad F_{\mathrm{attn}}=4n_Qd_hN_{\mathrm{pair}}.
$$

每对一个 Q 头，$QK^{\mathsf T}$ 与 $AV$ 各约 $2d_h$ FLOPs。全模型主要矩阵运算：

$$
F_{\mathrm{matrix}}=36\left(385{,}875{,}968\,m+16{,}384\,N_{\mathrm{pair}}\right)+2m_{\mathrm{out}}\times4096\times151936.
$$

词表头只按实际输出的 $m_{\mathrm{out}}$ 行算（生成下一 token 时每请求只需末尾一行）。代入：8192 token 的 prefill 约 **133.6 TFLOPs**；已有 8192 上下文再补一个 token 约 **20.0 GFLOPs**，相差约 6700 倍。两个增长规律要分开：投影／FFN 随 $m$ 线性增长，全注意力随 $P(P+1)/2$ 增长——序列加倍，投影行数翻倍、配对数约翻四倍。保持 $BP$ 不变只能保持投影行数，不能保持上下文交互；把长输入拆成独立短请求会消失跨分界的配对，前缀复用省掉的正是这部分。

## 3. KV 缓存：存储量与累计读取量差几个数量级

因果模型中旧 token 看不到后来的 token，权重与位置不变时其 K／V 可保留复用——缓存把「重算旧 token 表示」换成「保存并访问旧 token 状态」。长期保存的是 K 和 V，旧 Q 已完成任务。每上下文 token 的 KV：

$$
c_{\mathrm{KV}}=2Ln_{\mathrm{KV}}d_hb_{\mathrm{KV}}=2\times36\times8\times128\times2=144\ \mathrm{KiB}.
$$

8192 token 即 1.125 GiB，每步追加 144 KiB；层数或 KV 头减半增速减半，独立请求各增一份。

**累计读取远超存储**。固定 $B=1$、前缀 $S$、输入 $P$、返回 $G$，令 $H=S+P$、$n_d=G-1$，第 $j$ 次 decode 前上下文长 $H+j$：

$$
R_{\mathrm{old}}=c_{\mathrm{KV}}\left[n_dH+\frac{n_d(n_d-1)}{2}\right].
$$

取 $P=8192$、$G=1025$：累计读取约 **1224 GiB**，而最终保存仅约 1.27 GiB——近千倍差距，因为已进入上下文的 token 每次 decode 都要再读一遍。输出变长时固定项随 $n_d$ 线性增长，新增上下文使部分运算按步数平方增长。

**上下文读取何时超过权重读取**：每批共享权重读一遍约 15.14 GB，各请求上下文独立，两者相等时 $B_*=R_W/(c_{\mathrm{KV}}H)$。8K 上下文时 $B_*=13$，2K 时 51——上下文越长，批内权重复用收益越早受限。40 篇的 148 转折点只计权重，这里补上了状态项。

## 4. 上下文状态机制：每 token 存多少、每步读多少

比较上下文成本要同时给三个量：每 token 平均存储增量、长度 $N$ 时的实际驻留、一次 decode 的逻辑读取。除以上下文长度取平均会掩盖不同增长规律。

**KV 共享（MHA／GQA／MQA）**：减少每 token 的 KV 组数，token 数不变。Qwen3-8B 每 4 个 Q 头共用一组 KV：改 MHA 容量翻四倍，改 MQA 缩到八分之一。关键区分：**KV 投影与存储按组数减少，$QK^{\mathsf T}$／$AV$ 交互仍按 Q 头数累计**——共享的是被查询的数据，不是查询本身。MQA 论文的动机直接就是增量推理的内存带宽。

**MLA 潜变量压缩**：先把输入投影为低维潜变量 $c$ 保存，上投影位置由结合律决定：

$$
qK^{\mathsf T}=q(cU_k)^{\mathsf T}=(qU_k^{\mathsf T})c^{\mathsf T}.
$$

展开路径先为每个上下文 token 恢复 K／V；紧凑路径只变换当前查询、直接与潜变量点积，值汇总后再上投影。Kimi K3 的 Gated MLA 保存 512 维潜变量＋64 维 RoPE 分支（NoPE 层不旋转但仍缓存），24 层 8K 上下文紧凑缓存 **216 MiB**，展开缓存约 **11.25 GiB**——差异只在缓存位于线性变换哪一侧。上下文越长紧凑路径省得越多，越短查询变换开销占比越高。

**局部窗口＋压缩＋稀疏索引**：三个对象分开计量——SWA 只读最近一段（窗口 128）；全局主 KV 是可能已合并多位置的长期表示；索引 K 是供检索打分的小表示，**筛选本身也要读索引算分数，不能只统计选中的主状态**。DeepSeek V4-Flash 组合两种压缩：CSA 压缩比 4（相邻块重叠、每条目汇总 8 token）＋top-k 索引，HCA 压缩比 128、读全部粗粒度条目。8K 上下文下 43 层窗口＋压缩＋索引共 59.125 MiB，加 FP32 压缩缓冲合计约 70.8 MiB；一次查询主注意力最多读窗口＋512 条目，索引却仍扫描全部 2048 个压缩条目。压缩还引入与查询不同的更新节奏：每 4／128 个 token 才完成一块。

**线性注意力与有限状态递推**：不再逐 token 保存，而是把贡献合入固定大小状态：

$$
\mathcal S_t=\mathcal S_{t-1}+k_tv_t^{\mathsf T},\qquad o_t=q_t^{\mathsf T}\mathcal S_t.
$$

状态恒为 $d_kd_v$ 个元素，序列运算量线性增长。Kimi K3 的 KDA 加门控与 delta 修正（按当前预测误差写入修正量），96 头各 $128\times128$ 矩阵，FP32 下 69 层共 414 MiB，每步一读一写 828 MiB——**不随上下文增长**：短上下文是显著固定开销，长上下文避免扫描量持续增加。prefill 用块式并行算法，块内中间量使峰值内存无法仅凭最终状态预测。

**混合结构容量模型**：

$$
M_{\mathrm{state}}(H)=M_{\mathrm{fixed}}+c_{\mathrm{state}}H,\qquad H_*=\frac{M_{\mathrm{fixed}}}{c_{\mathrm{state}}}.
$$

Qwen3.6-35B-A3B（30 线性层＋10 全注意力层）固定 61.875 MiB、每 token 20 KiB，$H_*=3168$；Kimi K3（69 KDA＋24 MLA）固定约 433.4 MiB、每 token 27 KiB，交点约 16.4K。低于交点缩短上下文省不了多少，高于交点减小每 token 宽度更有效。8K 上下文状态对照：Qwen3-8B 1152 MiB、Qwen3.6 约 221.9 MiB、Kimi K3 约 649.4 MiB、V4-Flash 约 70.8 MiB（BF16 参考格式）。

## 5. 跨层共享与 CED：层数不等于缓存份数

DeepSeek V4.1 Flash 把 40 层主干分成前 20 层因果编码器＋后 20 层解码器（CED）：全局 KV 由编码器末层表示投影生成，大部分输入 token 不必经过解码器主体；解码器局部 SWA 靠提示末尾最多 128 token 的编码器输出重放构建；生成新 token 仍走全部 40 层。8K prefill 从参考全层前向的 282.39 TFLOPs 降到 **143.95 TFLOPs**，省的主要是解码器主体的 140.2 TFLOPs。注意这是 prefill 侧收益，decode 两部分都要执行，不能直接套用节省比例。

缓存缩小靠跨层共享＋低精度而非更高压缩比：40 层中只有第 2、8、14 层（2:1 压缩）与第 20 层（1:1）保存独立全局 KV，其余共享。主记录 512 值 FP4＋每 16 值 1 字节 scale 合 288 B，索引 68 B，平均增量

$$
\left(\frac{3}{2}+1\right)(288+68)=890\ \mathrm{B/token},
$$

对照 V4-Flash 的 $21\times(584+68)/4+20\times584/128=3514.25$ B/token，约 3.95 倍差距。共享层仍有独立 Q 与局部 SWA，可对共享条目算不同权重——**共享减少重复保存，不减少各层读取**。

条目选择分层组织：38 个全局注意力层分 4 Full（生成缓存与索引、全局扫描选最多 16384 候选）＋4 Reindex（候选池内各自重选 top-512）＋30 Reuse（连同选择一起复用）。候选池给后续层搜索量封顶，但首轮全局扫描仍随上下文增长，且池外条目本次查询无法再选入——训练需适应这一搜索范围。

## 6. MoE：运算量看分派，读取量看覆盖

MoE 把「保存多少参数」与「每 token 激活多少参数」解耦。单专家 $N_e$ 参数、每 token 选 $k_{\mathrm{top}}$ 个，单 token 专家运算约 $2k_{\mathrm{top}}N_e$；增大专家总数 $E$ 只扩容量，不直接增单 token 运算。一批 token 的运算与读取要分开：

$$
F_{\mathrm{expert}}=2N_e\sum_e t_e=2N_eBk_{\mathrm{top}},\qquad R_{\mathrm{expert}}=b_WN_eU,
$$

$U$ 是本批实际访问的不同专家数。**同样 512 次分派，读取可差 32 倍**：Qwen3.6 一层 256 专家、$B=64$ 各选 8 个，均匀分派覆盖全部 256 专家（每层读 1.5 GiB），集中到同一组 8 个专家只读 48 MiB——每份权重供 2 行还是 64 行使用，同时改变权重复用与分组 GEMM 形状。这就是大 EP 下路由 skew 的系统代价（主题三 40 篇展开）。

共享专家处理全部 $m$ 行：一层专家运算 $2mN_s+2\sum_e t_eN_e$，容量却要存全部路由专家。Kimi K3 把专家计算移入 3584 维潜空间（主干 7168 维），缩小专家矩阵但增加进出两次投影。专家跨卡放置时，通信量取决于专家与输入各在哪里。

## 7. 网络形状与辅助计算

- **深度与宽度**：稠密主干参数约正比 $Ld^2$；宽度减半层数翻四倍可保参数量，但依赖链拉长四倍、每层各存一份状态。专家粒度同理：$E$ 减半、$f$ 加倍、$k_{\mathrm{top}}$ 减半，总参数 $3Edf$ 与单 token 运算 $6k_{\mathrm{top}}df$ 都不变，变的只是分组矩阵形状与每专家接收行数。
- **跨层连接**：普通残差 $x_{\ell+1}=x_\ell+f_\ell(x_\ell)$ 要求子层计算期间保留输入。V4-Flash 的 mHC 扩成 4 路残差（混合矩阵非负、行列和近 1，Sinkhorn 迭代归一化），8192 输入额外约 555 GFLOPs 混合投影；Kimi K3 的 AttnRes 沿深度对浅层表示加权选择。这类跨层表示只在一次前向内保留，与跨调用保留的 KV 生命周期不同。
- **MTP 与推测解码**：辅助块预生成多个候选交主模型验证。设普通 decode 耗时 $T_d$、一轮草稿＋验证 $T_s+T_v$、平均有效输出 $\bar g$，有收益的条件：

$$
\bar g>\frac{T_s+T_v}{T_d}.
$$

20 ms decode、30 ms 一轮：$\bar g=2$ 时每输出 15 ms 有收益，$\bar g=1$ 时 30 ms 反而更慢。V4-Flash 单 token 一次 MTP 辅助约 1.80 GFLOPs，共享词表头占一半以上。

## 8. 全模型比较与容量预算

五个模型同条件（$B=1$，8K prefill／8K 上下文 decode，词表头只算末尾 token）：

| 模型 | 8K prefill（TFLOPs） | 8K 状态（GiB） | 1M 上下文交互（GFLOPs） |
|---|---:|---:|---:|
| Qwen3-8B（36 GQA，稠密） | 133.59 | 1.125 | 618.48 |
| Qwen3.6-35B-A3B（30 线性＋10 全注意力，MoE） | 52.09 | 0.217 | 171.80 |
| DeepSeek V4-Flash（CSA＋HCA，MoE） | 231.13 | 0.069 | 113.80 |
| Kimi K3（69 KDA＋24 MLA，2.78T 参数） | 1863.46 | 0.634 | 5257.04 |
| DeepSeek V4.1 Flash（CED＋CSA2＋Engram） | 143.95 | 0.029 | 25.23 |

三个量各由不同结构决定：**总容量看全部专家**（Kimi K3 路由专家占参数约 98%），**单步运算看选中专家与注意力路径**（Qwen3.6 权重约为 8B 四倍、单步运算反而更少），**状态看上下文机制**（压缩＋跨层共享使 V4.1 的 1M 状态仅 3.1 GiB）。长上下文下索引扫描与固定状态读写仍增长，「压缩」不等于「免费」。

容量预算两个方向。正向求并发上界：

$$
B_{\max}=\left\lfloor\frac{M_{\mathrm{device}}-M_{\mathrm{weight}}-M_{\mathrm{workspace}}}{M_{\mathrm{state/request}}}\right\rfloor.
$$

4090（24 GB）跑 Qwen3-8B BF16、预留 2 GiB、8K 上下文：$B_{\max}=4$；16K 降到 2，4K 升到 9——请求数按整数跳变，装下半份状态没有意义。反向求参数上界：$N_{\max}=(C-M_0-BK)/b_W$，同一张 4090 先留 4 条 8K 请求与工作区，BF16 最多约 85.1 亿参数。70B 模型 4-bit 分组量化约 39.5 GB（含高精度保留参数与 scale 开销，比一律半字节折算更大），H100 上 8K 可放 14 条、32K 只剩 3 条。**压缩权重释放的空间换成更多并发，上下文越长并发越少**——模型规模、状态结构、卡数要一起选。

## 9. 谬误与陷阱

- **参数更多每 token 计算就更大**：总参数定容量，选中专家、注意力类型与调用形状定当前工作。
- **KV 容量降四分之一注意力计算同比降**：GQA 共享表示但 Q 头仍分别评分；MLA 还改变上投影执行位置。先找被改变的矩阵与状态，再算其余工作。
- **状态固定访问开销就可忽略**：递推矩阵每步仍要一读一写，prefill 还有临时块状态。容量、累计访问、峰值工作区是三个问题。
- **同 token 数就能公平比模型**：token 数适合比资源结构；比能力要固定文本与评分标准，允许不同分词器产生不同长度。
