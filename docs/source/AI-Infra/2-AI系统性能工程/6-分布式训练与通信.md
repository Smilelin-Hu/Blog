# 分布式训练与通信

单卡优化到顶之后，分布式是唯一的路；而分布式的收益几乎总是被同步点吃掉。这一篇讲三件事：先分清「哪种不够」，再让通信不进关键路径，最后看 FSDP 如何用容量换吞吐。

## 1. 先分清是哪一种「不够」

### 1.1 坐标系

- **Rank**：全局进程编号；
- **World Size**：全局进程数；
- **Local Rank**：节点内编号，决定绑哪张卡；
- **DeviceMesh**：把一维 Rank 重新排成多维网格，让「DP 沿哪个维、TP 沿哪个维」成为显式配置。

DeviceMesh 的价值在于把拓扑意图写进代码：TP 组落在同一节点，DP 组跨机，而不是靠环境变量碰运气。

### 1.2 七种并行策略

| 策略 | 切什么 | 解决什么 | 主要代价 |
|---|---|---|---|
| DP | 数据 | 训练太慢 | 梯度 AllReduce |
| ZeRO / FSDP | 模型状态 | 装不下 | AllGather + ReduceScatter |
| TP | 单层矩阵 | 单层太大 | 每层多次通信，必须靠 NVLink |
| PP | 网络深度 | 层数太多 | 气泡 + 激活跨阶段 |
| SP（序列并行） | TP 区域里的激活 | TP 下激活冗余 | 与 TP 同域的通信 |
| CP（上下文并行） | 完整长上下文 | 长序列装不下 | K/V 交换，通信量大 |
| EP（专家并行） | MoE 专家 | 专家规模 | All-to-All 与负载不均 |

判据很朴素：**单卡装得下就是 DP 问题；单层装不下才上 TP；整体层数多上 PP；激活爆炸上 SP/CP；专家多上 EP。**

## 2. 通信为什么进了关键路径

### 2.1 三条原因

**梯度等待**：反向从后往前算，最后一层先就绪。若等全部反向结束才 AllReduce，就浪费了整个反向窗口——DDP 的做法是进 Bucket，桶满即异步通信。

**启动延迟与碎片**：\(K\) 个消息、总字节 \(S\)：

$$
T_{comm} \approx K\alpha + \frac{S}{B}
$$

融合能压 \(K\alpha\)，但消息越大就绪越晚、重叠窗口越短——这就是 Bucket 调优的根本矛盾。

**资源争用**：NCCL Kernel 也吃 SM、HBM、Copy Engine、NVLink/PCIe 与 NIC。时间线上「并发」不代表互不干扰：GEMM 与通信可能抢 HBM，通信 CTA 可能抢 SM。**要看 Step Time，而不是重叠面积**。

### 2.2 Bucket 的取舍

| Bucket 较小 | Bucket 较大 |
|---|---|
| 更早就绪、重叠窗口大 | 启动次数少、带宽利用高 |
| 启动与调度开销大 | 发起晚、尾巴可能长 |
| 小消息带宽利用低 | Buffer 与峰值显存上升 |
| 大量短 NCCL Kernel | 参数顺序不佳时长期等待 |

`bucket_cap_mb` 只是上限提示，实际桶受注册顺序与梯度就绪顺序影响。`gradient_as_bucket_view=True` 可省一次拷贝与一份峰值显存，但会改变梯度存储关系，且首轮可能重建桶，需要 Warmup。

扫参建议：4 / 8 / 16 / 25 / 50 / 100 MiB 各测一遍，比较 Collective 数、首个 NCCL 发起时刻、最后结束时刻、通信尾巴、峰值显存与端到端 Step。

### 2.3 异步不等于重叠

`async_op=True` 只返回一个 Work handle。真重叠还需要：输入在正确 Stream 就绪；通信尽早发起；后面存在不依赖结果的计算；消费结果前正确等待；通信与计算没有严重资源争用。

对第 \(i\) 个桶，梯度就绪 \(r_i\)、通信耗时 \(c_i\)：

$$
s_i = \max(r_i, e_{i-1}),\qquad e_i = s_i + c_i,\qquad
T_{tail} = \max(0,\ e_K - T_{backward})
$$

优化目标是让尾巴 \(T_{tail}\) 归零，而不是让「重叠面积」好看。常见的破坏者：热路径 `torch.cuda.synchronize()`、`.item()`、打印 CUDA Tensor、通信未完成就复用 Buffer、多 Communicator 乱序发起、只测 CPU API 返回时间。

### 2.4 降频与降字节

**梯度累积**：DDP 下前 \(A-1\) 个微步要用 `no_sync()`，只在最后同步，否则等于没省。

$$
B_{global} = B_{micro} \times A \times D
$$

**避免冗余通信**：不重复 AllReduce；小标量统计融合或降频；常量不要每步 Broadcast；不在训练循环里重建 Process Group；日志与 checkpoint 不该由单个 Rank 阻塞全局。

**低精度与压缩**：FP32→BF16 理论字节减半，但要评估 Cast、累加精度与最终质量。INT8/稀疏/Top-k 只有满足下式才可能赚：

$$
T_{compress} + \frac{rS}{B} + T_{decompress} < \frac{S}{B}
$$

\(r\) 为压缩后比例。在 NVSwitch 这种高速域内，压缩往往不划算；慢网络 + 大消息才更可能收益。任何压缩都要验证收敛。

### 2.5 各并行策略的优化重点

- **DP**：桶化梯度、与反向重叠、累积期 `no_sync()`、盯最慢 Rank；
- **FSDP/ZeRO**：ReduceScatter 与反向重叠，下一层 AllGather 预取；预取太激进会 OOM，Wrap Unit 太小则通信碎片；
- **TP**：每层通信、延迟敏感，必须放最快互联域，配合序列并行，验证 Collective 与 GEMM 的重叠；
- **PP**：相邻 Stage 的 Send/Recv、微批次与 1F1B、Stage 均衡，避免 Host staging；
- **EP**：All-to-All 同时受带宽与 Token 不均影响，要监控每专家/每 Rank 的 Token 数、All-to-All 的 P50/P99 与 Rail 拥塞。

### 2.6 慢 Rank 与三组基线

同步训练的 Step 时间由最慢者决定：

$$
T_{step} = \max_i T_i
$$

慢 Rank 可能来自数据长度、DataLoader、降频、NUMA/NIC 亲和性、网络重传、MoE 路由、资源争用，甚至某个 Rank 在独自打日志。**不要只记录 Rank 0**：按 Rank 采集 Data / Forward / Backward / Collective / Optimizer / Barrier，并报告 Max、P95、Median 与 Max−Median。

三组基线是排查的起点：

1. **Compute-only**：单 Rank 或关闭同步之后的计算近似；
2. **Comm-only**：`nccl-tests` 或 Collective 微基准；
3. **End-to-end**：真实模型 Step。

若纯通信很快而训练仍慢，问题通常不在 NCCL，而在发起时机、Bucket、数据或慢 Rank。

## 3. NCCL 侧的抓手

不用背变量，记住四个动作就够：

1. **确认走对了链路**：`NCCL_SOCKET_IFNAME` / `NCCL_IB_HCA` 选对网卡，`NCCL_DEBUG=INFO` 看 path type；
2. **确认选对了算法**：大消息 Ring / NVLS，小消息 Tree / LL，必要时用 `NCCL_ALGO` / `NCCL_PROTO` 覆盖；
3. **确认按拓扑分组**：同 NVLink 域内做 TP，跨机做 DP/PP；`NCCL_GRAPH_DUMP_FILE` 核对；
4. **确认调优可复现**：一次只改一个变量，先 `nccl-tests` 再上业务。

## 4. FSDP：分片保存，按需借用

### 4.1 常驻状态与峰值

| 方案 | 参数 | 梯度 | 优化器状态 |
|---|---|---|---|
| DDP / ZeRO-0 | 复制 | 复制 | 复制 |
| ZeRO-1 | 复制 | 复制 | 分片 |
| ZeRO-2 | 复制 | 分片 | 分片 |
| ZeRO-3 / FULL_SHARD | 分片 | 分片 | 分片 |

理想常驻：

$$
M_{sharded} \approx \frac{M_{state}}{N}
$$

真实峰值还要加临时聚合出来的完整参数组、预取缓冲、激活、通信缓冲与碎片：

$$
M_{peak} \approx \frac{M_{state}}{N} + M_{active\ group} + M_{prefetch} + M_{act} + M_{comm} + M_{fragment}
$$

这解释了一个常见困惑：**分片到 1/N，并不等于显存降到 1/N。**

### 4.2 一次 FSDP2 迭代

以 Transformer Block 为分片组、`reshard_after_forward=True`：

```text
前向：分片 --All-Gather--> 完整 Block --计算--> 释放完整参数
反向：分片 --All-Gather--> 完整 Block --算梯度
      完整梯度 --Reduce-Scatter--> 本 rank 梯度分片 --释放完整参数
优化：本 rank 只更新自己的参数与优化器状态分片
```

为什么前向要做两次 All-Gather（前向一次、反向再一次）？因为前向后立刻释放能拿到最低峰值，但反向必须重新聚合。若选择「前向后保留」，就少一次聚合、多占一段显存：

| 选择 | 峰值显存 | 参数通信 | 适合 |
|---|---|---|---|
| 前向后立即 Reshard | 低 | 较高 | 模型逼近显存上限 |
| 前向后保留完整参数 | 高 | 较低 | 模型较小、通信是主瓶颈 |

### 4.3 通信量对比

$$
V_{AG} \approx V_{RS} \approx \frac{N-1}{N}S
$$

FSDP 每步两次 All-Gather + 一次 ReduceScatter：

$$
V_{FSDP} \approx 3\frac{N-1}{N}P b_{comm}
$$

DDP 每步一次 AllReduce（等价 RS + AG）：

$$
V_{DDP} \approx 2\frac{N-1}{N}P b_{g}
$$

所以「模型明明能放进单卡」时，FSDP 未必更快——**FSDP 的首要价值是容量，吞吐要靠分组、低精度通信与重叠去争**。

### 4.4 FSDP1 与 FSDP2

- **FSDP1**：`FullyShardedDataParallel` 包装 Module，参数展平成 FlatParameter 再切片；配置项包括 `ShardingStrategy`、`MixedPrecision`、`auto_wrap_policy`、`BackwardPrefetch`、`CPUOffload`、`limit_all_gathers`。老项目必须会读。
- **FSDP2**：`fully_shard(module)` 原地改写，参数表示为沿第 0 维切分的 DTensor，不再依赖 FlatParameter，参数名稳定、更易与其他 DTensor 并行组合。

最关键的接口变化不是名字，而是**通信分组显式化**：

```python
# bottom-up：每个 block 一组，最后根模块一组
for block in model.blocks:
    fully_shard(block, mesh=mesh)
fully_shard(model, mesh=mesh)
```

只对根模型调用一次，所有参数会形成一个巨大的组：前向前一次大 AllGather，反向尾一次大 ReduceScatter，几乎没有层间重叠空间。

### 4.5 分片粒度：最重要的旋钮

$$
T_{group} \approx \alpha + \frac{G}{B}
$$

组太小：Collective 次数多，启动延迟与调度开销累积；组太大：峰值显存高、通信晚启动、难与逐层计算重叠。

实践起点是「一层 Block 一组」，再按 Profile 调整：Block 很小就合并相邻块；Block 很大可按 Attention/MLP 再分，但要防碎片；Embedding 与 LM Head 共用权重时要验证分片与 checkpoint 行为。

### 4.6 组合优化

**混合精度**：常驻分片参数与优化器状态保持 FP32；AllGather 后的计算参数用 BF16；ReduceScatter 用 BF16 省带宽、用 FP32 保稳定。BF16 是否可用应以 `torch.cuda.is_bf16_supported()` 检测，不要按型号猜。

**激活重计算**：FSDP 只减模型状态，激活仍随 batch、序列长度、hidden 与层数增长——长序列模型里，激活会重新变成第一瓶颈。

**CPU Offload**：最后手段。省显存，吃 PCIe，吞吐通常明显下降。
