# 八个综合项目：交付标准与常见坑

前面的原理是知识，八个项目是证据。它们的共同要求只有一句：**每个结论都要能被别人用同一套命令复现。**

## 1. 项目全景

| # | 项目 | 核心能力 | 主要交付物 |
|---|---|---|---|
| 1 | GPU 性能分析实验 | 三级证据链：基准 → 系统时间线 → Kernel 计数器 | 诊断报告 + 可复现脚本 |
| 2 | CUDA Kernel 优化项目 | 访存、Occupancy、融合 | 优化前后 Benchmark 与正确性对照 |
| 3 | PyTorch 训练性能优化 | DataLoader、AMP、compile、通信 | 优化清单 + 回归数据 |
| 4 | 7B 训练性能 Benchmark | 并行配置、MFU、扩展效率 | 基线表 + 配置矩阵 |
| 5 | vLLM 推理优化 | 连续批、KV、量化 | TTFT/TPOT/Goodput 对比 |
| 6 | KV Cache 优化实验 | 容量模型、Paged、前缀缓存 | 命中率与显存曲线 |
| 7 | Disaggregated 系统设计 | 容量规划、KV 传输预算、状态机 | 设计文档 + 规划器 |
| 8 | 综合项目 | 端到端收敛 | 完整方案 + 验收口径 |

## 2. 项目一：GPU 性能分析实验

**核心纪律**：不要凭 GPU 利用率猜瓶颈。

三级证据链：

```text
业务指标异常
  → 基准测试（有没有变慢、慢多少）
    → 系统时间线（nsys：CPU/GPU/通信谁在等谁）
      → Kernel 计数器（ncu：带宽、occupancy、Tensor Core 活动）
```

**交付物**：`reports/` 下的诊断报告，必须包含冻结的工作负载（输入尺寸、dtype、随机种子）、环境记录（PyTorch/CUDA/驱动版本）、中位数与 P95/P99、加速比与有效带宽、以及「改了什么 → 改善哪个区间 → 损害哪个区间」。

**诊断矩阵**（这张表比任何经验都可靠）：

| 现象 | 优先查看 | 可能原因 |
|---|---|---|
| 时间线大量短 Kernel 与空隙 | nsys | Launch-bound、同步过多 |
| GPU 长时空闲、CPU 繁忙 | Profiler OSRT | 数据准备、日志、锁、线程调度 |
| 单 Kernel 很长且 DRAM 吞吐高 | ncu Memory | Memory-bound，减少中间张量 |
| 单 Kernel 很长且计算管线高 | ncu SOL | Compute-bound，精度/Tiling/算法 |
| Occupancy 低但吞吐不低 | Occupancy + Stall | 可能是合理的资源交换，别乱改 |
| 每轮出现同步锯齿 | CUDA API / NVTX | `.item()`、隐式同步、阻塞拷贝 |
| 多卡只有一个 Rank 落后 | 各 Rank 时间线 | 负载不均、拓扑、I/O、日志 |

## 3. 项目二：CUDA Kernel 优化

**验收标准**：同输入、同精度、同输出语义下，与 PyTorch/cuBLAS 对照正确性（容差写明），再给加速比。

**推荐路径**：naive 实现 → 合并访存 → 向量化 → 共享内存 Tiling → 减少寄存器压力 → 融合。每一步都要有单独的数据点，报告里能看出「哪一步拿到了多少」。如果某一步收益为零甚至为负，那本身就是有价值的结论（说明瓶颈不在那里）。

**常见坑**：只测一次（没 Warmup、没同步）、只报最好成绩、把 5% 的时间优化到极致却说成「整体提速 5 倍」。

## 4. 项目三：PyTorch 训练性能优化

按「低风险 → 高约束」推进：删同步 → `inference_mode`/预分配 → DataLoader（worker、`pin_memory`、`prefetch_factor`、`persistent_workers`）→ AMP → `torch.compile` → CUDA Graph。

**交付要求**：每项优化单独成行，记录 step time、tokens/s、峰值显存、以及是否影响收敛（同 seed、同数据顺序、看 loss 曲线）。

## 5. 项目四：7B 训练性能 Benchmark

要产出的不是「一个 MFU 数字」，而是一张**配置矩阵**：

| 维度 | 取值 |
|---|---|
| 并行 | DP / ZeRO 阶段 / TP×PP |
| micro batch | 1 / 2 / 4 / 8 |
| 梯度累积 | 1 / 4 / 8 |
| 精度 | BF16 / FP16(+scaling) |
| 重计算 | 关 / 选择性 / 全开 |

每行记录 tokens/s、MFU、峰值显存、扩展效率（\(X_N/(N X_1)\)）。**必须声明 MFU 口径**：模型 FLOPs 用 \(6P\) 还是含 Attention 项、峰值是 Dense 还是 Sparse。

## 6. 项目五：vLLM 推理优化

指标要一起报：TTFT、TPOT、系统输出 tokens/s、每用户 tokens/s、以及 **SLO 约束下的 Goodput**。

典型对照：并发数扫描（1 → 2 → 4 → …）、max_num_seqs、chunked prefill 开关、量化（FP8/INT8）前后、prefix caching 开关。

**常见坑**：只报峰值吞吐不报 P99；用固定 16 token 输出测 Prefill 性能却当成通用结论；不同输入长度分布之间直接比较总 tokens/s。

## 7. 项目六：KV Cache 优化实验

三个必测项：

1. **容量模型校验**：用 \(M_{token} = 2 L H_{kv} D_{head} B\) 估算，与 `nvidia-smi` / 框架日志实测对齐（差多少、差在哪）；
2. **碎片对比**：连续预留的 \(Waste_{contiguous}\) 与 Paged 的 \(Waste_{paged}\)，以及不同 Block Size 的尾部浪费；
3. **前缀缓存命中率**：多轮对话/共享系统提示场景下命中率与 TTFT 收益，以及驱逐策略对命中率的影响。

## 8. 项目七：Disaggregated Inference 系统设计

这个项目的产物是**一份可落地的设计**，不是一张架构图。

**延迟模型**：

$$
TTFT = T_{queue,p} + T_{prefill} + T_{transfer} + T_{queue,d} + T_{first\ decode}
$$

**KV 传输字节与链路预算**：

$$
Bytes_{KV} = S_{input} \times 2 \times L \times H_{kv} \times D_{head} \times B_{dtype}
$$

$$
T_{xfer} \approx T_{setup} + \frac{Bytes_{KV}}{BW_{eff}},\qquad
BW_{required} \ge \frac{Bytes_{KV}}{T_{budget} - T_{setup} - T_{sync}}
$$

**排队稳定性**（Erlang-C 的前提）：

$$
\rho_p = \frac{\lambda S_p}{c_p},\qquad \rho_d = \frac{\lambda S_d}{c_d}
$$

任何阶段 \(\rho \ge 1\) 时，稳态延迟不存在——规划器应当输出「不可行」，而不是给一个好看的有限平均值。

**必须写清的五件事**：

1. **状态机**：`RECEIVED → PREFILL_ASSIGNED → PREFILL_RUNNING → KV_TRANSFERRING → DECODE_RUNNING → DONE`，以及每一步的取消与超时；
2. **幂等与重试**：Request ID、KV Handle、重复 Prefill 的处理；
3. **控制面/数据面分离**：元数据走控制面，KV 走 P2P/RDMA/共享存储；
4. **回退路径**：链路拥塞或短 Prompt 时退回本地 Prefill；
5. **观测指标**：P/D 各自队列、KV 传输 P50/P99、每阶段利用率、SLO Goodput。

## 9. 项目八：综合项目

把前七个串起来：选一个真实场景（训练或推理），给出当前基线 → 瓶颈证据 → 优化方案 → 验收数据 → 回归门禁。

**回归门禁**是它区别于前七个项目的地方：把「性能基线 + 阈值 + 触发条件」写进 CI，让性能不再靠人盯。最小可行版本：固定 workload、跑三次取中位数、超过阈值即失败。

## 10. 五个通用坑

| 坑 | 表现 | 对策 |
|---|---|---|
| 没有 Warmup | 首次运行包含编译/初始化，数字虚高 | 固定 Warmup 步数并丢弃 |
| 不同步计时 | 测到的是 CPU 提交时间 | `torch.cuda.Event` + `synchronize` |
| 工作负载漂移 | 输入长度/分布变了还在比 | 冻结 workload 与 seed |
| 只报均值 | 尾延迟问题被平均掉 | 报 P50/P95/P99 |
| 口径不一致 | MFU/带宽/tokens/s 定义各异 | 报告里写死公式与峰值来源 |
