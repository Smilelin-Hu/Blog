# AI 系统性能指标体系

本篇建立统一的性能指标语言，把延迟、吞吐、利用率、Goodput 与 Roofline 之间的关系理清楚。

## 1. 内容概览

性能工程最危险的情况不是「没有数据」，而是**大家都拿着一个数字，却在讨论不同的东西**。

两个团队都声称模型达到 `10,000 tokens/s`，可能分别指：单用户单并发的输出速度；100 个并发请求合计的系统输出吞吐；输入与输出 Token 相加的总吞吐；离线批处理、不受延迟约束的峰值吞吐；只统计 Decode、不含排队与 Prefill；或者生成长度 16 与 512 的两种场景。

这些数字都可能「计算正确」，但不能直接比较。所以指标体系要回答三个问题：

1. **指标的分子和分母分别是什么？**
2. **测量窗口包含了什么，又排除了什么？**
3. **这个指标能证明什么，不能证明什么？**

## 2. 本篇要点

1. 区分平均延迟、P50、P95、P99，并解释在线系统为何更关心尾延迟。
2. 区分 QPS、RPS、Samples/s、Sequences/s、Input/Output/Total Tokens/s。
3. 正确解释 TTFT、TPOT、ITL、E2E Latency 与每用户 Tokens/s。
4. 用 Little 定律连接并发数、吞吐和平均响应时间。
5. 从 Step Time 推导训练 Tokens/s，并估算 Dense Transformer 的 MFU。
6. 解释 MFU 与 HFU 的差异，特别是 Activation Recomputation 为什么让 HFU 高于 MFU。
7. 按 SLO、正确性和失败重试定义 Goodput，而不把 GPU-Util 当作有效产出。
8. 用 Roofline 判断 Kernel 更可能受计算峰值还是内存带宽限制。

## 3. 阅读前提

已完成上一篇，理解端到端关键路径与 Goodput 的直觉；知道训练含前向反向、推理含 Prefill 与逐 Token Decode；会运行 Python；可选了解矩阵乘法 FLOPs 的基本算法。

## 4. 核心直觉：没有上下文的性能数字几乎没有意义

假设一家快递公司说自己「速度是 1000 件/秒」，至少还要问：是整个仓库还是每个工人？是完成配送还是只完成扫码？包裹大小相同吗？高峰期和空闲期一样吗？超时、损坏和退件算不算？

AI 系统的数字同样要绑定上下文。一个完整指标可以写成：

```text
Metric = 数值 + 单位 + 工作负载 + 负载模式 + 统计口径 + 正确性/SLO + 环境
```

例如「8×A100，Llama-2-7B，输入 512/输出 128，Poisson 到达，并发 64，P99 TTFT 800 ms 内，输出 820 tok/s」——这比单独写「820 tok/s」更有解释力，也更可复现。

## 5. 指标全景图

```text
用户体验
├── E2E Latency
├── TTFT：多久看到第一个 Token
├── TPOT / ITL：后续 Token 是否流畅
└── P50 / P95 / P99：普通用户与尾部用户体验

系统容量
├── QPS / RPS / Samples/s
├── Input Tokens/s
├── Output Tokens/s
├── Total Tokens/s
└── Concurrency 与队列长度

训练效率
├── Step Time
├── Samples/s / Tokens/s
├── MFU：模型所需 FLOPs 相对理论峰值
├── HFU：硬件实际执行 FLOPs 相对理论峰值
└── Scaling Efficiency

有效产出
├── SLO-compliant Goodput
├── Effective Training Time Ratio
├── 成本/百万 Token
└── Token/Joule

硬件瓶颈
├── Peak Compute
├── Memory Bandwidth
├── Arithmetic Intensity
└── Roofline 上限
```

这些指标不是互相替代，而是从不同高度观察同一系统。

## 6. Latency：用户等了多久

### 6.1 平均延迟为什么不够

$$
L_{avg} = \frac{1}{N}\sum_{i=1}^{N} L_i
$$

平均值容易被少数极端值拉高，也会掩盖尾部用户。例如 99 个请求耗时 100 ms、一个请求耗时 10 s，平均约 199 ms——报告只写「平均 199 ms」，看不出大多数用户很快，也看不出那个用户极慢。

因此在线系统通常同时报告：**P50**（50% 请求不超过，接近典型体验）、**P90/P95**（观察较慢请求）、**P99/P99.9**（观察尾延迟与 SLO 风险）、**Max**（辅助排障，但对样本量极敏感）。

百分位必须配合样本数：只有 100 个请求时，P99 几乎由最慢的一个样本决定；严谨的尾延迟评估需要足够长的时间与足够多的样本。

### 6.2 LLM 请求的时间拆解

![LLM 请求时间拆解：TTFT 与 E2E Latency](https://raw.gitcode.com/weixin_42917352/image-host/raw/main/images/aiinfra_y2_l02_01.png)

**TTFT（Time to First Token）**：

$$
\mathrm{TTFT} = t_{first\ token} - t_{request\ sent}
$$

它通常包含客户端到服务端网络、排队、调度、Prompt 预处理、Prefill 和第一次 Decode。对聊天系统「是否立即响应」非常关键。

**ITL（Inter-Token Latency）**：相邻流式 Token 事件的间隔，

$$
\mathrm{ITL}_j = t_{j+1} - t_j
$$

它反映生成过程是否流畅。应报告分布，因为平均 30 ms 可能是每个 Token 稳定 30 ms，也可能是大多 10 ms、偶尔卡 500 ms。

**TPOT（Time per Output Token）**：常见口径排除第一个 Token，

$$
\mathrm{TPOT}_i = \frac{L_{e2e,i} - \mathrm{TTFT}_i}{N_{out,i} - 1}
$$

当服务端每次流式事件只返回一个 Token 时，一个请求的 TPOT 等于其 ITL 平均值；但全局 TPOT 分布与所有 Token 间隔的 ITL 分布并不必然相同。某些服务端一次事件可能返回多个 Token，更要明确口径。

**每用户输出 Tokens/s**：对足够长的输出，$\mathrm{TPS}_{user} \approx 1/\mathrm{TPOT}$。若 TPOT 为 50 ms，稳态约 20 tok/s/user。这是单个用户看到的速度，不是集群总吞吐。

### 6.3 何时 TTFT 高，何时 TPOT 高

| 现象 | 更可能的原因 | 优先检查 |
| --- | --- | --- |
| TTFT 高、TPOT 正常 | 排队、长 Prompt、Prefill、冷启动 | Scheduler、Prompt 长度、Prefill Batch、Prefix Cache |
| TTFT 正常、TPOT 高 | Decode 慢、KV Cache、显存带宽、批次过大 | Decode Batch、KV Cache、量化、带宽与 Kernel |
| TTFT 和 TPOT 都高 | 系统过载、模型/硬件不匹配 | 到达率、并发、资源、模型并行和服务配置 |
| P50 正常、P99 很差 | 长短请求干扰、队头阻塞、抖动 | 请求分布、调度策略、GC、共享资源和网络 |

## 7. Throughput、QPS 与 RPS：系统完成了多少工作

### 7.1 Throughput

$$
\mathrm{Throughput} = \frac{\text{Completed Work}}{\text{Measurement Duration}}
$$

关键在于 Completed Work 的单位：图片任务是 images/s；语音任务是 audio seconds/s；训练是 samples/s 或 tokens/s；LLM 推理是 requests/s、input tokens/s、output tokens/s 或 total tokens/s。

### 7.2 QPS、RPS 与 Samples/s

- **RPS**：每秒完成的请求数。
- **QPS**：每秒查询数。
- **Samples/s**：每秒完成的样本数。

在「一次请求等于一个查询、且查询只含一个样本」的简单 API 中三者可能相同；但一个请求可能携带一个 Batch，一个 Query 也可能含多个 Sample。报告必须定义单位。

$$
\mathrm{RPS} = \frac{N_{successful\ requests}}{T}
$$

失败请求是否计入分母、超时请求是否算完成，都要写清楚。生产容量通常只统计成功且满足质量要求的请求。

### 7.3 LLM 的三种 Tokens/s

$$
\mathrm{TPS}_{input} = \frac{\sum_i N_{input,i}}{T},\quad
\mathrm{TPS}_{output} = \frac{\sum_i N_{output,i}}{T},\quad
\mathrm{TPS}_{total} = \frac{\sum_i (N_{input,i} + N_{output,i})}{T}
$$

输入吞吐主要反映 Prefill 工作量，但不同模型、Attention 实现和 Prefix Cache 命中率会改变实际成本；输出吞吐常用于衡量 Decode 容量。

**总 Tokens/s 不是输出 Tokens/s**：若测试使用 4096 Token Prompt、只输出 16 Token，总 Tokens/s 主要由 Prefill 贡献；另一个测试输入 128、输出 512，两者不能只看总数比较。

### 7.4 系统 Tokens/s 与每用户 Tokens/s 的矛盾

提高并发和 Continuous Batching 往往能提高系统总输出 Tokens/s，却可能降低每用户 Tokens/s 并增加 TPOT，因为同一轮 Decode 要服务更多序列。

![ai2-02-L182](https://raw.gitcode.com/weixin_42917352/image-host/raw/main/images/aiinfra_y2_l02_02.png)

一个有效的容量数字应写成「在 P99 TTFT 和 P99 TPOT 均不超过 SLO 时的最大吞吐」——这就是 SLO 约束下的 Goodput 思想。

## 8. 并发、队列与 Little 定律

稳定系统中：

$$
L = \lambda W
$$

$L$ 是系统中的平均请求数（含排队与处理中），$\lambda$ 是平均到达/完成速率，$W$ 是平均请求停留时间。

例如系统稳定完成 20 req/s、平均 E2E Latency 0.5 s，则平均约有 $20 \times 0.5 = 10$ 个请求处于排队或执行中。

Little 定律不告诉你怎样优化，却能做一致性检查：如果仪表盘显示 100 req/s、平均延迟 2 s，但平均在途请求只有 10，至少有一个口径不一致。

**饱和点**：

```text
低负载区：吞吐随到达率近线性增加，延迟平稳
拐点附近：设备利用提高，Batch 更有效，尾延迟开始上升
过载区：吞吐接近上限，延迟和超时急剧恶化
```

所以「压到系统不再变快」为止测到的是离线峰值，不一定是在线可用容量。

## 9. 训练指标：Step Time、Tokens/s、MFU 与 HFU

### 9.1 Step Time 与训练 Tokens/s

$$
\mathrm{Training\ Tokens/s} = \frac{B_{global} \times S}{T_{step}}
$$

$$
B_{global} = B_{micro} \times N_{data\ parallel} \times N_{grad\ accumulation}
$$

TP 或 PP 切分的是同一模型/Batch，通常不直接乘进全局样本数。重复把所有 GPU 数量都乘进去，是常见统计错误。

### 9.2 Dense Transformer 的模型 FLOPs 近似

一个常用的一阶估算：每 Token 的模型 FLOPs 约为

$$
F_{model/token} \approx 6P
$$

$P$ 为参数量。直觉上前向约需 $2P$ 次浮点操作，反向对权重和激活的梯度约再需 $4P$。

但这只是近似：Attention 的序列长度相关项可能不可忽略；Embedding、输出层等计数口径不同；MoE 不能直接用总参数量，应按每 Token 实际激活的专家与共享层计算；参数共享、稀疏性会改变模型 FLOPs；不同论文对一次 FMA 计 1 FLOP 还是 2 FLOPs 必须一致。严谨比较应使用同一公式并公开公式。

### 9.3 MFU：Model FLOPs Utilization

$$
\mathrm{MFU} = \frac{F_{model/token} \times \mathrm{Tokens/s}}{N_{device} \times \mathrm{Peak\ FLOPs/device}}
$$

MFU 回答的是：**按模型算法完成这些有效 Token 所需的理论 FLOPs，占硬件对应精度理论峰值的多少？**

它适合跨训练系统比较模型有效计算效率，但前提是：模型 FLOPs 定义一致；Peak FLOPs 对应实际主要精度；稀疏/非稀疏峰值口径一致；分母包含正确的设备数量；Tokens/s 为端到端稳态吞吐（含数据、通信与优化器时间）。

### 9.4 HFU：Hardware FLOPs Utilization

$$
\mathrm{HFU} = \frac{\text{Actual executed hardware FLOPs/s}}{N_{device} \times \mathrm{Peak\ FLOPs/device}}
$$

HFU 关注硬件实际执行了多少 FLOPs，可能包含模型算法之外的额外计算，例如 Activation Recomputation。如果为省显存在反向阶段重新执行部分前向：

- MFU 的分子仍按完成模型训练所需的「有效模型 FLOPs」计算。
- HFU 的分子包含重新计算的额外 FLOPs。
- 因此常见 $\mathrm{HFU} > \mathrm{MFU}$。

HFU 高不一定说明更高效——大量无效重算也能让硬件很忙。MFU 更接近模型有效计算，HFU 更接近硬件算力占用，两者结合才能定位问题。

### 9.5 为什么 MFU 不能替代 Profiler

MFU 低可能来自：GEMM 太小或形状不友好、HBM 带宽瓶颈、Pipeline Bubble、DataLoader 等待、通信没有被重叠、Python/Kernel Launch 开销、Checkpoint 或评估被计入窗口、Peak FLOPs 分母选错。

MFU 只告诉你「离理论峰值有多远」，不告诉你为什么远。根因仍需时间线、硬件计数器和分层剖析。
