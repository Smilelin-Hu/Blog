# 通信与集群互连

并行度一旦上去，训练时间就不再由单卡算力决定，而由「最慢的那次同步」决定。这一篇从集合通信原语讲到 NCCL 的算法选择，再到集群拓扑与通信亲和性，最后看国产芯片的通信栈。

## 1. 四个集合通信原语

### 1.1 一个两维度的分类框架

理解原语先建坐标系：横轴是数据流向（一对多 / 多对多），纵轴是是否做归约（Reduction）。

| 原语 | 数据流向 | 是否归约 | 典型用途 |
|---|---|---|---|
| Broadcast | 一对多 | 否 | 参数初始化、超参下发 |
| Reduce | 多对一 | 是 | 汇总到主节点 |
| AllReduce | 多对多 | 是 | DP 梯度同步 |
| AllGather | 多对多 | 否 | 收集分片、ZeRO 参数聚合 |
| ReduceScatter | 多对多 | 是 | 归约后按片分发、ZeRO 梯度分片 |

AllReduce 可以看作 ReduceScatter + AllGather 的组合，这也是 Ring 算法的实现基础。

### 1.2 Broadcast：一对多分发

Broadcast 把一个节点（Root）上的数据发到通信域内所有节点，最终每个节点持有一份完全相同的副本。典型场景是 Rank 0 加载预训练权重后同步到全部 GPU，保证初始状态一致。

```python
import torch.distributed as dist

if rank == 0:
    tensor = torch.tensor([1.0, 2.0, 3.0]).cuda()
else:
    tensor = torch.zeros(3).cuda()

dist.broadcast(tensor, src=0)
```

底层通常用二叉树或环形拓扑优化：树形的时间复杂度是 \(O(\log N)\)，环形是 \(O(N)\)。

### 1.3 AllReduce：数据并行的基石

AllReduce 对所有节点上的数据做归约（求和、求平均、求最大），再把结果分发回所有节点。DDP 每一步都在做这件事。

环形实现分两阶段，每阶段各 \(N-1\) 轮：

1. **ReduceScatter**：把梯度张量切成 \(N\) 份，经过 \(N-1\) 轮环形传递后，每张卡持有其中一份的全局累加和；
2. **AllGather**：把各自持有的已完成归约的分片继续沿环传递，再经 \(N-1\) 轮，所有卡拥有完整梯度。

每张卡的总通信量约为：

$$
V_{\text{per GPU}} \approx \frac{2(N-1)}{N} S
$$

其中 \(S\) 是梯度张量大小。\(N\) 较大时 \(V \approx 2S\)——**通信量与卡数几乎无关**，这正是 Ring 能扩展到大规模的原因。

### 1.4 AllGather 与 ReduceScatter

- **AllGather**：每张卡贡献自己的分片，最终所有卡拿到全部分片拼成的完整张量。ZeRO-3 在计算前聚合参数就是 AllGather。
- **ReduceScatter**：先归约再按片分发，每张卡只留下自己负责的那一片。ZeRO-2 的梯度分片依赖它。

## 2. NCCL 的算法选择

NCCL 会根据集合通信类型、消息大小与网络拓扑**动态选择算法**。常见算法有 Ring、Tree、CollNet Direct、CollNet Chain、NVLS、NVLS Tree：Ring 支持所有集合通信，Tree 只支持 AllReduce。

### 2.1 Ring：小规模集群的黄金标准

Ring 把 GPU 逻辑上排成一个环，每个 GPU 只有前驱与后继两个邻居，数据单向传递、边走边归约。

```text
总通信时间 ≈ 2 × (N - 1) × (tensor_size / (N × bandwidth))
```

特性很清晰：

- **通信成本恒定**：总通信量几乎与 \(N\) 无关；
- **带宽利用率高**：所有链路并行工作；
- **延迟随 \(N\) 线性增长**：需要 \(2(N-1)\) 轮。

因此 Ring 适合单机 8 卡或几十卡、NVLink/PCIe 高带宽互联的场景；到千卡规模时，环形轮数带来的延迟会成为主要成本。

### 2.2 Tree 与 CollNet / NVLS

- **Tree**：把通信组织成树，延迟为 \(O(\log N)\)，但每层链路负载不均。适合小消息的 AllReduce。
- **CollNet**：把归约卸载到交换机（SHARP），网络设备直接做加法，减少主机侧数据搬运；Direct / Chain 是两种拓扑组织方式。
- **NVLS**：基于 NVLink SHARP 的机内归约，在 NVLink 域内可以显著降低 AllReduce 的往返次数。

### 2.3 为什么调优能差出 30%

一个配置不当的 NCCL，可能让千卡集群的训练效率从 80% 掉到 50%。主要变量有三个：算法选择是否与消息大小匹配、通道数（`NCCL_NCHANNELS`、`NCCL_MAX_NCHANNELS`）是否打满链路、拓扑探测是否选对了网卡与网络面（多网卡、多 rail 时尤其明显）。

工程做法是先看 NCCL 的拓扑探测结果与单次集合通信的带宽，再调通道数与算法，而不是盲目加环境变量。

## 3. 集群拓扑与通信亲和性

### 3.1 分层拓扑

单机内 8 卡通过 NVLink 全互联，通信对所有人都是均匀的；大规模集群则完全不同：

- 服务器内 GPU：NVLink，带宽可达约 900 GB/s，延迟微秒级；
- 同机柜不同服务器的 GPU：经 Leaf 交换机，带宽通常 400 Gbps（约 50 GB/s），延迟数十微秒；
- 跨机柜：再经 Spine，带宽进一步下降，延迟更高。

如果通信调度不感知这种差异，就会出现跨交换机通信——本该在机柜内完成的高速交换被迫绕行上层网络，带宽降级、延迟飙升。

### 3.2 通信亲和性

原则只有一条：**把通信最频繁、数据量最大的操作放在物理上最近的 GPU 之间**。

| 并行维度 | 通信形态 | 数据量 | 放置建议 |
|---|---|---|---|
| TP | 每层多次 AllReduce | TB 级 | 节点内 NVLink |
| EP | All-to-All | TB 级 | 同一超节点内 |
| PP | 点对点激活传递 | GB 级 | 可跨服务器 |
| DP | 每步一次 AllReduce | 中等 | 可跨机柜 |

### 3.3 收益与案例

研究表明物理拓扑对 LLM 预训练有显著影响，拓扑感知的通信调度可以把通信组的最大扩散范围降低最高 1.67 倍。

一个真实案例：1024 张 H800A 上跑 Megatron-LM（DP=8 / TP=4 / PP=32），初次上线 MFU 只有 71%，而预期是 85%。Profiler 显示 25% 的时间花在 AllReduce 上，P99 尾延迟是 P50 的 4 倍——根因是 NCCL 默认拓扑探测把 32 卡的 pipeline group 放到了同一个 Spine 下，导致 AllReduce 频繁跨 Spine。

## 4. 国产芯片的通信与训练栈

### 4.1 CANN：昇腾的「CUDA」

CANN（Compute Architecture for Neural Networks）是昇腾 AI 处理器的异构计算架构，连接上层 PyTorch、TensorFlow、MindSpore 与底层芯片。它通过 AscendCL 提供 Device、Context、Stream、内存、模型加载与执行等 API，开发者不必直接处理芯片细节。

生态方面，CANN 8.0 新增 200 多个基础算子、80 多个融合算子与 100 多个 Ascend C API，官方称典型算子开发周期从 2 人月缩短到 1.5 人周；2025 年宣布开源开放，并支持 PyTorch、MindSpore、TensorFlow、飞桨、ONNX、OpenCV、OpenMMLab 等框架。

### 4.2 MindSpeed：昇腾的分布式训练套件

**MindSpeed-LLM**（原 ModelLink）覆盖分布式预训练、SFT、RLHF/DPO、数据预处理、权重转换、在线推理与基线评估，已支持百余个 Dense 与 MoE 模型，包括 DeepSeek-V3-671B 与 DeepSeek-R1 系列。

**MindSpeed MM** 面向多模态，兼容 FSDP、TP、PP、CP。例如 Lumina-DiMOO 训练中用 `npu_fusion_attention`、RoPE 融合、RMSNorm 融合等优化，总显存下降 27.7%。

### 4.3 从 NVIDIA 迁移到昇腾

最短路径是自动迁移，靠 `torch_npu` 的 `transfer_to_npu` 把 CUDA 调用重定向到 NPU：

```python
import torch_npu
from torch_npu.contrib import transfer_to_npu
```

工程上需要保留的三条检查：算子是否都有 NPU 实现、通信后端（HCCL）与集合通信行为是否等价、显存与执行流语义差异是否被覆盖。迁移不是「改一行 import」，而是逐层验证数值、性能与稳定性。
