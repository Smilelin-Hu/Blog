# 通信与集群互连

并行度上去之后，训练时间往往不再由单卡算力决定，而由「最慢的那次同步」决定。这一篇从集合通信原语讲到 NCCL 调优，再到集群拓扑、梯度压缩与国产芯片适配。

## 1. 四个集合通信原语

### 1.1 一张分类表

| 原语 | 数据流向 | 是否归约 | 训练中的典型用途 |
|---|---|---|---|
| Broadcast | 一对多 | 否 | 参数初始化、超参下发 |
| AllReduce | 多对多 | 是 | DP 梯度同步 |
| AllGather | 多对多 | 否 | TP 输出拼接、ZeRO-3 参数聚合 |
| ReduceScatter | 多对多 | 是 | 归约后各取一片、ZeRO-2 梯度分片 |

AllReduce 恰是 ReduceScatter + AllGather 的组合，这也是 Ring 算法的结构。

### 1.2 通信量：先分清「每卡」与「全网」

设通信域有 \(N\) 个节点、每节点初始数据量 \(M\)：

| 原语 | 每卡发送 | 每卡接收 | 备注 |
|---|---|---|---|
| Broadcast | \(M\)（root） | \(M\) | 树形延迟 \(O(\log N)\)，环形 \(O(N)\) |
| ReduceScatter | \(\approx M\) | \(\approx M/N\) | 只完成归约的一半工作 |
| AllGather | \(\approx M\) | \(\approx M\) | 环形实现下每卡收发各约 \(M\) |
| AllReduce | \(\approx 2M\) | \(\approx 2M\) | 环形下总量与 \(N\) 几乎无关 |

这里有个必须澄清的口径：**环形 AllGather 每卡的收发量各约 \(M\)，与 \(N\) 无关；但「广播式」实现的总流量是 \(O(N^2)M\)**。讲义里同时出现「AllGather 复杂度 \(O(N)\)」和「总通信量 \(O(N^2)\)」两种说法，区别就在是否按环形实现计。工程结论只有一条：**TP 组内的 AllGather 必须走环形/树形，不能退化成广播**。

### 1.3 AllReduce = ReduceScatter + AllGather

```text
输入：每个节点持有 T_i
      ↓ 阶段 1：ReduceScatter
节点 k 持有 Σ T_i^k（全局归约结果中的第 k 片）
      ↓ 阶段 2：AllGather
每个节点持有完整的 Σ T_i（由各片拼接）
```

这也解释了为什么 ZeRO-2 的通信形态是 ReduceScatter + AllGather：它本来就不需要「每人都有完整梯度」。

## 2. 通信时间模型

### 2.1 两个参数

任何一次通信都可以近似成：

$$
T = \alpha + \frac{M}{\beta}
$$

\(\alpha\) 是启动延迟（协议握手、kernel 启动、同步），\(\beta\) 是有效带宽。小消息（几 KB）由 \(\alpha\) 主导，属于延迟敏感；大消息（几 GB）由 \(M/\beta\) 主导，属于带宽敏感。

NCCL 的 \(\alpha\) 通常在 1–10 μs，但 PyTorch 的 kernel 启动开销可能到几十 μs——这就是 DDP 必须分桶的物理原因：把 \(N\) 次 \(\alpha\) 合成 1 次。

### 2.2 一次实战估算

8 张 A100 训练 70B 模型（纯 DDP，FP16）：每卡梯度 \(M = 140\) GB，NVLink 有效带宽取 600 GB/s。

$$
T \approx \frac{2M}{\beta} = \frac{280\ \text{GB}}{600\ \text{GB/s}} \approx 0.47\ \text{s}
$$

如果单步计算是 1.5 s，通信就占约 24%——这正是必须引入模型并行或 ZeRO 分片的量化理由。

### 2.3 什么时候该分桶

| 消息大小 | 主导项 | 对策 |
|---|---|---|
| < 1 MB | 延迟 \(\alpha\) | 分桶、合并小张量、减少同步点 |
| 1 MB – 100 MB | 两者混合 | 调通道数、选协议 |
| > 100 MB | 带宽 | 层次化 AllReduce、梯度压缩、换拓扑 |

## 3. 通信与计算重叠

### 3.1 前提是硬件路径独立

计算 Kernel 跑在 SM 上，NCCL 通信走 RDMA 引擎与 NVLink 控制器，路径不同才能真并行。若两者争用同一资源，重叠就只是「看起来异步」。

### 3.2 用 Stream 把通信藏起来

- 计算流（默认流）：矩阵乘、卷积等；
- 通信流（NCCL 内部流）：AllReduce 等集合操作。

反向传播算完一层梯度就立刻在通信流发起同步，计算流继续算下一层，于是「计算 → 通信 → 计算」被流水化。

### 3.3 Megatron 的做法

TP 的每层前向/反向各需一次 AllReduce。Megatron 把 AllReduce 与 GeLU 这类**不需要同步数据**的逐元素操作重叠：通信发起后先算本地 GeLU，等通信回来正好衔接，能隐藏约 30% 以上的 TP 通信开销。

### 3.4 判断重叠是否生效

看 profiler 时间线三件事：

1. CUDA 计算 Kernel 与 NCCL Kernel 是否**交叠**；
2. 通信流活跃时计算流有没有「空洞」；
3. 端到端 step time 是否下降（通信总量不变，但从关键路径上消失了）。

失效常见原因：`torch.cuda.synchronize()` 等显式同步、数据依赖太强（必须等通信结果才能继续）、桶太小导致通信时长不足以覆盖计算。

## 4. NCCL 调优

### 4.1 算法

NCCL 会按消息大小与拓扑动态选择算法，常见的几类：

| 算法 | 适用 | 特点 |
|---|---|---|
| Ring | 所有集合通信 | 通信量恒定，延迟随卡数线性增长 |
| Tree | 仅 AllReduce | 延迟 \(O(\log N)\)，适合小消息 |
| CollNet | 交换机内归约（SHARP） | 把加法卸载到网络设备，减少主机搬运 |
| NVLS | NVLink SHARP | 机内归约，降低往返次数 |
| PAT | 特定拓扑 | 面向大规模交换结构的并行聚合 |

### 4.2 协议

`NCCL_PROTO` 三档：`Simple`（大数据）、`LL`（低延迟小数据）、`LL128`（128 位优化版）。算法与协议的组合受硬件限制，不是任意搭配都可用。

### 4.3 关键环境变量

| 变量 | 作用 | 典型场景 |
|---|---|---|
| `NCCL_SOCKET_IFNAME` | 指定 IP 网卡（`=eth0`、`^docker`） | 多网卡机器必设，避免选错接口 |
| `NCCL_IB_HCA` | 指定 IB 网卡（`mlx5_0:1`） | 多 HCA 时选对端口 |
| `NCCL_ALGO` / `NCCL_PROTO` | 强制算法/协议 | 自动选择次优时手动覆盖 |
| `NCCL_MIN/MAX_NCHANNELS` | 通信通道数 | 提高并行度，代价是资源占用 |
| `NCCL_BUFFSIZE` | 通信缓冲（字节） | 大消息吞吐调优，如 4 MB |
| `NCCL_IB_QPS_PER_CONNECTION` | 每连接 QP 数 | IB 并行度；部分国产网卡要求特殊取值 |
| `NCCL_DEBUG` / `NCCL_DEBUG_SUBSYS` | 日志级别与子系统 | 排查用 `INFO`/`TRACE` + `COLL`/`GRAPH` |
| `NCCL_GRAPH_DUMP_FILE` | 导出拓扑 XML | 验证拓扑识别是否正确 |
| `NCCL_P2P_LEVEL` | P2P 允许的最远距离 | 避免走性能差的路径 |

### 4.4 调优方法论

1. **基线**：`nccl-tests` 的 `all_reduce_perf -b 8 -e 128M -f 2 -g 1` 测不同消息大小的带宽与延迟；
2. **识别**：`NCCL_DEBUG=INFO` 看它选了哪个算法/协议、走了哪张网卡；
3. **单变量**：一次只改一个环境变量；
4. **组合**：单变量最优后再组合；
5. **生产验证**：小规模先验证再推广。

公开数据里，精细的 NCCL 参数调优可把训练时间再降约 12.5%——量不大，但属于「免费」的收益。

## 5. 三类典型故障

### 5.1 Watchdog 超时

```text
Watchdog caught collective operation timeout:
WorkNCCL(SeqNum=12345, OpType=ALLREDUCE, Timeout(ms)=600000)
```

它是「全能型」错误，凡是让某个 rank 在集合通信上无限等待的情况都会报。五类常见原因：

1. 各 rank 数据量不一致（`len(dataset)` 不能被 world size 整除且 `drop_last=False`）；
2. Sampler 配置错误（`shuffle` 混用、忘调 `sampler.set_epoch`）；
3. 网卡选错（选到 docker 虚拟网卡）；
4. 某个 GPU 因 OOM 挂起；
5. IB 的 GID index 等通信配置不当。

排查顺序：核对各 rank 步数 → 检查 sampler → 开 `NCCL_DEBUG=INFO` → 查网络配置 → 用 PyTorch Flight Recorder 抓超时瞬间的 rank 状态。

### 5.2 死锁

现象是「完全卡住、无报错、GPU 功耗接近空闲」。根因通常是**集合通信调用不匹配**：不同 rank 走的分支不同，调用的操作数量、顺序或类型不一致。对策是保证所有 rank 的集合通信序列严格一致，并临时用 `NCCL_BLOCKING_WAIT=1` 把异步错误变成同步错误来定位。

### 5.3 性能下降

无报错但慢，四个高频原因：拓扑识别错误（跨交换机被塞进同一通信组）、算法选择次优、PCIe 亲和性没绑对、GDR（GPUDirect RDMA）没启用。

处理手段：`NCCL_GRAPH_DUMP_FILE` 导出拓扑图核对、`NCCL Inspector` 看按通信器/按操作拆分的性能、确认日志里有 GDR 初始化记录。

## 6. 大规模集群：拓扑、调度与压缩

### 6.1 拓扑感知与通信亲和性

集群是分层的：节点内 NVLink（约 900 GB/s、微秒级）→ 机柜内 Leaf（400 Gbps 级）→ 跨机柜 Spine → 数据中心 Core。

放置原则只有一句：**把通信最频繁、数据量最大的维度放在最近的位置**。TP 与 EP 留在节点/超节点内，PP 可跨机，DP 放最外层。拓扑感知调度可以把通信组的最大扩散范围降低最高 1.67 倍。

### 6.2 层次化 AllReduce

先节点内归约，再由每个节点的代表参与跨节点归约，最后把结果广播回节点内。跨节点通信量从 \(2G\) 降到 \(2G/N\)（\(G\) 为梯度总量）——这是规模变大后唯一还成立的优化方向之一。

### 6.3 多维层次化与 HiPIPE

万卡集群往往有四层网络（NVLink → Leaf → Spine → Core）。二维环面、超立方体等拓扑各有对应的层次化方案；2025 年提出的 HiPIPE 把分块大小建模成线性规划，在所有网络维度上同时分块并动态调整块数，论文数据是平均减少通信时间 28.85%、带宽利用率 98.11%。

### 6.4 梯度压缩

层次化优化的是「怎么通信」，梯度压缩优化的是「通信什么」。

| 方法 | 机制 | 收益 | 风险 |
|---|---|---|---|
| 量化 | FP32→FP16→INT8→4/1 bit | 通信量按位宽线性下降，1-bit 可降 32 倍 | 精度损失，需误差补偿 |
| 稀疏化 | 只传 Top-K 大幅值梯度 | Top-5% 可减 90% 通信量 | 丢小梯度，收敛受影响 |
| 低秩近似 | PowerSGD 用低秩矩阵近似 | 压缩率高且与 SGD 性能相当 | 额外计算（幂迭代） |
| 误差补偿 | 缓存压缩误差，下轮补回 | 保证期望无偏 | 实现复杂、需额外状态 |

工程上三者可叠加：DeepSeek 的 DGC v2.0 用「自适应量化（FP8/INT4）+ Top-5% 稀疏 + 误差补偿」，把通信量压到约 1/20。三者叠加的整体效果据讲义数据，可把通信开销从 40%–60% 降到 10%–20%，算力利用率从 42% 提到 80% 以上。

## 7. 国产芯片与异构计算

### 7.1 软件栈

**CANN** 是昇腾的异构计算架构（对应 CUDA），通过 AscendCL 提供 Device/Context/Stream/内存/模型执行等 API；**MindSpeed-LLM**（原 ModelLink）覆盖预训练、SFT、RLHF/DPO、权重转换与推理，**MindSpeed MM** 面向多模态并兼容 FSDP/TP/PP/CP。

同理，寒武纪是 Neuware、壁仞是 BIRENSUPA——每家的「CUDA」都不一样，这是异构最根本的成本。

### 7.2 三条迁移路径

1. **自动迁移**：`import torch_npu` + `from torch_npu.contrib import transfer_to_npu`，两行代码把 CUDA 调用映射到 NPU，最轻量；
2. **工具迁移**：PyTorch GPU2Ascend 自动分析并转换脚本，适合代码量大的场景；
3. **手工迁移**：自定义 CUDA 算子必须重写。硬核路线用 Ascend C，工作量相当于重写；偷懒路线用 Triton——昇腾的策略是拥抱生态，符合规范的 Triton 代码由编译器后端翻译到 NPU。

### 7.3 五个高频坑

| 坑 | 表现 | 对策 |
|---|---|---|
| 算子不兼容 | 某些算子无 NPU 实现，甚至梯度丢失 | 用 msprobe 做精度对比，逐层定位后替换或手写 |
| 混合精度适配 | Apex 不可直接用 | 换 Apex for Ascend |
| Triton Block Size | GPU 上 1024 可行，NPU 上撑爆 UB | 先降到 256/128 跑通再优化 |
| 原子操作差异 | `tl.atomic_add` 支持有限 | 改用 `tl.reduce` 等更通用指令 |
| 非连续访存 | NPU 偏好连续对齐，复杂 Mask 效率骤降 | 简化 Mask、Padding 到对齐形状 |

迁移的三条最佳实践：**先跑通再优化**、**版本配套优先**（昇腾软件栈对版本组合极其敏感，版本不匹配是最常见失败原因）、**精度对比工具先行**（msprobe 逐层对比）。

### 7.4 多厂商混合训练

动机有三：算力供给的结构性矛盾、存量资产盘活、供应链安全。三大挑战与对应手段：

1. **通信协议不兼容**（NCCL/HCCL/CNCL 互不通用）→ 建异构通信抽象层，如商汤 DeepLink；
2. **算力不均衡的拖尾**（最慢的卡决定整批速度）→ 异构感知的并行策略：重 Stage 给强卡，按算力动态分配批次；
3. **软件栈碎片化** → 容器化封装 + 统一调度。

公开进展：异构流水线下 NVIDIA + 壁仞可达 99.77% 混训效率，NVIDIA + 天数 + 壁仞三方 99.03%；异构数据并行 NVIDIA + 壁仞约 92.88%；RoCEv2 网络互通的三芯混训达到单一芯片集群的 90%。规律很清楚：**流水线并行对异构最友好，数据并行对异构最敏感**。

## 写在最后

通信这条线的三层已经打通：原语决定数据怎么走，NCCL 决定走几轮、走哪张网卡，拓扑与压缩决定物理链路上的开销。接下来回到单卡内部——显存装不下、精度不够、访存跑不满，这些才是并行之后的第二战场。
