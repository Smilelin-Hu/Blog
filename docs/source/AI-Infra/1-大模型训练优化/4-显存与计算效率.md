# 显存与计算效率

并行解决「装不下」，这一篇解决「装不下的另一半」：显存到底被谁吃掉、怎么用分片与重计算换空间、精度怎么降、算子怎么少搬一次数据。

## 1. 显存账本

### 1.1 四类消耗

训练显存主要被四类数据占据：

1. **模型参数**：显存占用 = 参数量 × 每参数字节数。7B 模型 FP16 约 14 GB。
2. **梯度**：每个参数对应一个梯度，大小通常与参数相同（7B/FP16 约 14 GB）。
3. **优化器状态**：以 Adam 为例，每个参数额外保存 FP32 的一阶动量与二阶方差，共 8 字节/参数——是全量训练里最容易被低估的一项。
4. **激活值**：前向的每层输出，反向时要用，占用与 batch size、序列长度成正比。

除了这四项，还有框架开销与 CUDA 上下文（常见 5–10 GB 量级）以及临时缓冲。

### 1.2 12Φ 还是 16Φ：先把口径对齐

混合精度 + Adam 的核心显存有两种常见写法：

$$
\text{核心显存} \approx 2\Phi + 2\Phi + 8\Phi = 12\Phi \quad\text{（不含 FP32 主参数副本）}
$$

$$
\text{核心显存} \approx 2\Phi + 2\Phi + 8\Phi + 4\Phi = 16\Phi \quad\text{（含 FP32 主参数副本）}
$$

差异来自是否把「FP32 主权重」单独计入。DeepSpeed、Megatron 的文档里两种口径都能见到，做容量规划时建议统一按 16Φ 保守估算：7B 模型约 \(16 \times 7 = 112\) GB，还没算激活。

### 1.3 激活值：随序列长度平方增长的部分

单层激活的粗略量级：

$$
\text{每层激活} \approx b \times s \times h \times 4\ \text{bytes}
$$

当 \(b=64\)、\(s=2048\)、\(h=4096\) 时单层就可能超过 1 GB，70 层模型就是 70 GB 以上——比模型参数本身还大。序列一长，注意力分数矩阵还会叠加 \(O(s^2)\) 项，128K 上下文下这一项往往成为主导。

### 1.4 怎么观测

- `nvidia-smi` 看总量与进程占用，但看不到分配细节；
- `torch.cuda.memory_allocated()` / `memory_reserved()` 区分「真实张量」与「缓存池」；
- `nsys` / `ncu` 看时间线上的分配峰值、碎片与 HBM 带宽。

一个常见误判：显存「看起来够」但一跑就 OOM，通常是碎片化或峰值出现在反向刚开始（此时所有层激活都还在）。

## 2. ZeRO：把冗余分片

### 2.1 冗余从哪里来

DDP 中每张卡都完整保存参数、梯度、优化器状态。既然大家存的是同一份，就可以各存一部分。ZeRO 按「优化器状态 → 梯度 → 参数」的顺序逐步扩大分片范围。

### 2.2 三个阶段

| 阶段 | 分片对象 | 单卡模型状态（16Φ 口径，\(N\) 卡） | 通信 |
|---|---|---|---|
| DDP | 无 | \(16\Phi\) | 每步 AllReduce |
| ZeRO-1 | 优化器状态 + FP32 主参 | \(4\Phi + 12\Phi/N\) | AllReduce |
| ZeRO-2 | 再加梯度 | \(2\Phi + 14\Phi/N\) | ReduceScatter + AllGather |
| ZeRO-3 | 再加参数 | \(16\Phi/N\) | 计算前 AllGather、用后释放 |

以 \(N=8\) 计，ZeRO-1 把模型状态压到 \(4\Phi + 1.5\Phi = 5.5\Phi\)，约为原来的 34%；ZeRO-3 则线性下降到 \(2\Phi\)。

讲义的收益推导值得校正一处：文中给出「参数 \(P\)、优化器状态 \(2P\)、梯度 \(P\)，合计 \(4P\)；ZeRO-1 后为 \((2 + 2/N)P\)，\(N=8\) 时从 \(4P\) 降到 \(2.25P\)，减少 62.5%」——同一口径下的降幅应为 \((4-2.25)/4 = 43.75\%\)。62.5% 这个数字更接近「把 12Φ 的优化器状态与 FP32 主参一起分片」的另一套口径（\(16\Phi \to 5.5\Phi\) 约 65.6%）。结论不变：**ZeRO-1 的收益在 4 成左右，写百分比前必须声明口径**。

### 2.3 代价

分片换来的空间是通信换的：ZeRO-2 把 AllReduce 拆成 ReduceScatter + AllGather，ZeRO-3 还要在每次前向/反向按需聚合参数。ZeRO-3 在小 batch、深层模型上容易出现「通信等待」，这也是为什么大集群更常用「ZeRO-1 + TP/PP」而不是盲目上 ZeRO-3。

## 3. 激活重计算

激活值太多，就丢掉再算一遍——**以计算换空间**。

```text
传统方式：前向保存 A1…AN → 反向逐层读取
峰值显存：A1 + A2 + … + AN

重计算：前向只保留边界（checkpoint）→ 反向时从最近边界重算该段
峰值显存：约 √N 段激活（分段策略下）
```

代价是反向多一次前向计算，端到端通常增加 20%–30% 时间（取决于重算粒度）。工程上常用 `torch.utils.checkpoint` 或框架自带的 selective checkpoint，只对显存占比大的层（如 Attention）做重算。

## 4. 卸载：把状态挪到 CPU

ZeRO-3 之后如果单卡还是不够（例如只有 1–2 张 80 GB 卡要训 10B 模型），可以把优化器状态甚至参数放到主机内存。

**ZeRO-Offload** 的分工：

- GPU 侧：FP16 参数、当前批次激活、少量临时缓冲；
- CPU 侧：FP32 主参数、FP16 梯度、Adam 动量与方差。

两个关键优化：

1. **DeepSpeedCPUAdam**：相比 PyTorch 原生 CPU 实现快 5–7 倍，避免 CPU 成为新瓶颈；
2. **一步延迟更新**：GPU 不等 CPU 完成参数更新就进入下一批次，把 CPU 计算藏在 GPU 计算后面。

代价是 PCIe 带宽：卸载量越大，对 PCIe 的压力越明显，训练速度下降通常比显存收益更「痛」。

## 5. 混合精度

### 5.1 三种格式的定位

| 格式 | 符号/指数/尾数 | 动态范围 | 特点 |
|---|---|---|---|
| FP32 | 1 + 8 + 23 | ±3.4×10³⁸ | 精度充足，带宽与显存成本高 |
| FP16 | 1 + 5 + 10 | 约 6.1×10⁻⁵ – 65504 | 精度较高但范围小，必须配 loss scaling |
| BF16 | 1 + 8 + 7 | 与 FP32 相同 | 范围足够、无需 loss scaling，大模型训练首选 |
| TF32 | 1 + 8 + 10 | 与 FP32 相同 | 只是 Tensor Core 的**计算**格式，不省显存 |

几个容易踩的点：

- **TF32 不省显存**：数据仍以 FP32 存储，只加速矩阵计算，属于「即插即用」的算力提升。
- **BF16 精度低于 FP16 但更稳**：深度学习实践里动态范围通常比尾数精度更重要，溢出比舍入更致命。
- **FP16 必须配 loss scaling**：小梯度下溢为 0 会直接让训练「停滞」，动态 loss scaling 是标准做法。

### 5.2 混合精度的收益从哪来

显存：参数与梯度减半（16Φ → 12Φ 的核心差异在参数/梯度两项）；
带宽：HBM 读写量减半，对受内存墙限制的算子收益更大；
算力：Tensor Core 在 FP16/BF16 下的峰值通常是 FP32 的数倍。

## 6. 算子融合与图优化

### 6.1 内存墙

Tensor Core 每秒可以完成大量浮点运算，而 HBM 带宽只有每秒几 TB。如果算子频繁读写 HBM，计算单元大部分时间在等数据——这就是内存墙。

```text
不融合：算子A 计算 → 写 HBM → 算子B 读 HBM → 计算
融合后：算子A 计算 → 中间结果留在寄存器/共享内存 → 算子B 直接算 → 只写一次 HBM
```

### 6.2 两种融合方向

- **水平融合**：把同层中并行、独立的算子合并，例如把 Q、K、V 三个投影合成一个大 GEMM；
- **垂直融合**：把有数据依赖的串联算子合并，例如 MatMul + GeLU + Dropout 融合成一个 Kernel。

收益来自两处：少的 Kernel 启动次数（单次启动是微秒级固定开销，几百个算子累积可占 5%–10%），以及少的 HBM 往返。实际场景中融合常带来 1.3×–2.0× 的局部加速。

### 6.3 约束与工具

融合需要更多寄存器与共享内存，融合过度会压低 occupancy，性能反而下降。工具链上：

- `torch.compile`：按图捕获、算子融合与后端代码生成，适合把「一堆小算子」压成少量 Kernel；
- TensorRT / TensorRT-LLM：面向推理的图优化与量化融合；
- 手写：Triton/CUDA 处理编译器覆盖不到的融合模式。

## 7. CUDA 与 Triton 入门

### 7.1 线程层级

- **Thread**：最小执行单元，靠 `threadIdx` 处理不同数据；
- **Block**：一组线程，可通过共享内存交换数据、用 `__syncthreads()` 同步；常见 128 / 256 / 512 线程；
- **Grid**：一组 Block，决定整体并行规模。

一维索引与二维索引：

```cpp
int idx = blockIdx.x * blockDim.x + threadIdx.x;

int row = blockIdx.y * blockDim.y + threadIdx.y;
int col = blockIdx.x * blockDim.x + threadIdx.x;
int idx2 = row * width + col;
```

### 7.2 Warp 与分支分歧

一个 Warp 是 32 个线程，它们在同一个 SM 上以 SIMT 方式执行相同指令。由此带来两个硬约束：

- **合并访存**：同一 Warp 的线程访问连续地址才能合并成一次事务；
- **Warp Divergence**：Warp 内线程走不同分支时，分支被串行执行，有效算力打折。

### 7.3 Triton 的定位

手写 CUDA 能拿到极限性能，但线程层级、共享内存、bank conflict 都要手工管理。Triton 用 Python DSL 把「块级」抽象暴露出来：写 `tl.load` / `tl.dot` / `tl.store`，由编译器负责线程映射、向量化与流水，开发者主要思考 tile 大小与访存模式。

它适合的场景很明确：融合类算子（RMSNorm、SwiGLU、RoPE）、Attention 变体、以及需要快速试错的自定义 Kernel。极致手调仍要落到 CUDA/CUTLASS。
