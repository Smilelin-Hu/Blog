# 显存与计算效率

并行解决「装不下模型」，这一篇解决「装不下状态」与「算不满硬件」：显存被谁吃掉、如何用分片/重计算/卸载换空间、精度怎么降、算子怎么少搬一次数据，最后落到 CUDA 与 Triton 的入门路径。

## 1. 显存账本

### 1.1 四类消耗

以 175B 模型（FP32）为例，显存总需求可超过 2000 GB。四类消耗分别是：

1. **模型参数** = 参数量 × 每参数字节数（7B/FP16 ≈ 14 GB）；
2. **梯度**：每个参数一个梯度，量级与参数相同（7B/FP16 ≈ 14 GB）；
3. **优化器状态**：Adam 为每个参数存 FP32 的一阶动量与二阶方差，共 8 字节/参数——它是模型参数（2 字节）的 4 倍，全量训练中可占总显存 60%；
4. **激活值**：前向的每层输出，反向要用，与 batch size、序列长度成正比，可占总显存 30%（长序列下更高）。

另外还有框架与 CUDA 上下文开销（常见 5–10 GB）与临时缓冲。

### 1.2 12Φ 还是 16Φ

$$
\text{核心显存} \approx 2\Phi + 2\Phi + 8\Phi = 12\Phi \quad(\text{不含 FP32 主参})
$$

$$
\text{核心显存} \approx 2\Phi + 2\Phi + 8\Phi + 4\Phi = 16\Phi \quad(\text{含 FP32 主参})
$$

差别只在是否单独计入 FP32 主权重副本。同一个问题上 12Φ 与 16Φ 两种口径都常见，做容量规划建议按 16Φ 保守估，讲收益时先声明口径。

### 1.3 一个 7B 的实算

$$
12 \times 7 = 84\ \text{GB}\ (\text{12Φ 口径}),\qquad 16 \times 7 = 112\ \text{GB}\ (\text{16Φ 口径})
$$

再叠加数十 GB 激活与 5–10 GB 框架开销——这就是「单卡 80 GB 装不下 7B 全量训练」的算术来源。

### 1.4 观测

- `nvidia-smi`：总量与进程占用；`watch -n 1 nvidia-smi` 看动态；`nvidia-smi pmon` 看进程级利用率；
- `nsys profile -o report python train.py`：Kernel、拷贝、分配的完整时间线；加 `--cuda-memory-usage=true` 追踪分配释放，加 `--capture-range` 只采目标步；
- PyTorch 侧用 `memory_allocated()` / `memory_reserved()` / `max_memory_allocated()` 区分真实张量与缓存池。

常见误判：显存「看起来够」却 OOM，通常是碎片化，或峰值出现在反向刚开始（所有层激活都在）。

## 2. ZeRO：用通信换显存

### 2.1 三个阶段

| 阶段 | 分片对象 | 单卡模型状态（16Φ 口径，\(N\) 卡） | 主要通信 |
|---|---|---|---|
| DDP | 无 | \(16\Phi\) | AllReduce |
| ZeRO-1 | 优化器状态 + FP32 主参 | \(4\Phi + 12\Phi/N\) | AllReduce |
| ZeRO-2 | 再加梯度 | \(2\Phi + 14\Phi/N\) | ReduceScatter + AllGather |
| ZeRO-3 | 再加参数 | \(16\Phi/N\) | 按需 AllGather + 用后释放 |

\(N=8\) 时 ZeRO-1 约 \(5.5\Phi\)、ZeRO-3 为 \(2\Phi\)。常见的「4P → 2.25P 减少 62.5%」说法口径不自洽：同口径应为 **43.75%**；62.5% 更接近「优化器 + FP32 主参一起分片」的另一套算法。

### 2.2 ZeRO-3 的 Hook 生命周期

ZeRO-3 的本质是一套 Hook：参数平时以 \(1/N\) 分片存放，**用时 AllGather、用完立即 Partition**。

一次前向的时序：

1. **Pre-Forward Hook**：发起本层参数的异步 AllGather；
2. **等待就绪**：计算流等待通信完成（未完成就是气泡）；
3. **前向计算**：用完整参数算，产出激活；
4. **Post-Forward Hook**：立即释放完整参数，回到分片；
5. **预取**：算第 N 层时提前发起第 N+1 层的 AllGather，把通信藏进计算。

反向完全对称：Pre-Backward 聚合参数 → 算梯度 → Post-Backward 释放 → 梯度按 ReduceScatter 归约到各自分片。

### 2.3 DeepSpeed 配置与调优原则

DeepSpeed 的设计哲学是「改配置不改代码」：`deepspeed --num_gpus=8 train.py --deepspeed ds_config_zero3.json`，训练循环里只需改成 `model_engine.backward(loss)` / `model_engine.step()`。

ZeRO-3 中真正影响性能的几个开关：

```json
"zero_optimization": {
  "stage": 3,
  "overlap_comm": true,
  "contiguous_gradients": true,
  "reduce_bucket_size": 5e8,
  "stage3_prefetch_bucket_size": 5e8,
  "stage3_param_persistence_threshold": 1e6,
  "stage3_max_live_parameters": 1e9,
  "stage3_max_reuse_distance": 1e9,
  "stage3_gather_16bit_weights_on_model_save": true
}
```

调优三条原则：**显存够就用低 Stage**（Stage 越低通信越少）、**不够再逐级升**、**Offload 是最后手段**（CPU 带宽远低于 HBM）。桶大小是权衡：桶大 → 通信次数少但触发晚；桶小 → 触发早但次数多，常从 500 MB 起步试。

## 3. 激活重计算

激活太多就丢掉重算——用计算换空间。

```text
常规：前向保存 A1…AN → 反向逐层读取，峰值 ≈ 全部激活
重算：前向只留边界 → 反向从最近边界重算该段，峰值大幅下降
```

代价是反向多一次前向，端到端通常增加 20%–30%。实践里用 `torch.utils.checkpoint` 或框架的 selective checkpoint，只对 Attention 等显存大户重算——这也解释了 MFU 与 HFU 的差：重计算让实际 FLOPs 高于模型理论 FLOPs。

## 4. 卸载

ZeRO-3 之后仍不够（如 1–2 张卡训 10B），就把优化器状态甚至参数放到主机内存。

**ZeRO-Offload** 的分工：GPU 留 FP16 参数 + 当前激活 + 小缓冲；CPU 承担 FP32 主参、FP16 梯度、Adam 动量与方差。两个关键优化是 `DeepSpeedCPUAdam`（比 PyTorch CPU 实现快 5–7 倍）与**一步延迟更新**（GPU 不等 CPU 更新完就进入下一批）。公开数据称可在有限显存上训练到 130 亿参数级。

**ZeRO-Infinity** 进一步把权重卸载到 CPU 甚至 NVMe，靠更高效的带宽调度与重叠来减少「卸载税」。代价始终是 PCIe/NVMe 带宽。

## 5. 混合精度

| 格式 | 符号/指数/尾数 | 动态范围 | 定位 |
|---|---|---|---|
| FP32 | 1+8+23 | ±3.4×10³⁸ | 精度标准，成本高 |
| FP16 | 1+5+10 | 约 6.1×10⁻⁵ – 65504 | 精度较好、范围小，必须配 loss scaling |
| BF16 | 1+8+7 | 同 FP32 | 大模型训练首选，通常无需缩放 |
| TF32 | 1+8+10 | 同 FP32 | 只是 Tensor Core 计算格式，**不省显存** |

三个常踩的坑：TF32 只加速不省显存；BF16 尾数少但动态范围大，溢出比舍入更致命，因此更稳；FP16 必须配动态 loss scaling，否则小梯度下溢为 0、训练「假死」。

收益来源三条：显存（参数与梯度减半）、带宽（HBM 读写减半，访存密集算子受益最大）、算力（Tensor Core 在低精度下峰值更高）。

## 6. 算子融合与图优化

### 6.1 内存墙与两种融合

Tensor Core 的算力远高于 HBM 带宽，算子频繁读写 HBM 就会「饿死」计算单元。

- **水平融合**：合并同层独立算子，如 Q/K/V 三个投影合成一个大 GEMM；
- **垂直融合**：合并有依赖的串行算子，如 MatMul + GeLU（中间结果留在寄存器）。

收益来自少的 kernel 启动（单次微秒级，几百个算子可占 5%–10%）与少的 HBM 往返。约束是片上资源：融合过度会压低 occupancy。

### 6.2 `torch.compile`

按图捕获 + 编译，零代码改动。三个常见问题：

- **图断裂（Graph Break）**：遇到 Dynamo 无法捕获的第三方调用或动态控制流，优化被打断；
- **重编译**：输入形状变化触发重新编译；
- **调试复杂**：可用 `TORCH_TRACE` 开跟踪、`tlparse` 分析。

### 6.3 TensorRT 与 TensorRT-LLM

TensorRT 走**离线编译**：先解析动态图，再转静态图做融合与内存重用。

典型融合模式：Conv+BN+ReLU 三合一；LayerNorm+GELU；MHA 由十几个算子合成 3 个融合算子。TensorRT-LLM 在 A100 上对 LLaMA-2 70B 的吞吐提升可达 2.3 倍，并把显存占用降低 30% 以上。

选型：训练优先 `torch.compile`；推理追求极致选 TensorRT；大模型推理优先 TensorRT-LLM。

### 6.4 FlashAttention：融合思想的最佳案例

标准 Attention 的瓶颈不是算力而是访存：\(S = QK^\top\) 与 \(P=\mathrm{softmax}(S)\) 都是 \(N\times N\)，序列 4096 时约 67 MB、16K 时超过 1 GB，反复进出 HBM。

两项核心技术：

1. **Tiling**：把 Q/K/V 切块搬进 SRAM，逐块计算，避免物化完整的 S/P；
2. **Online Softmax**：边算边维护最大值 \(m\) 与指数和 \(l\)，发现新最大值就修正历史累加，结果与标准 Softmax **完全等价**（不是近似）。

公开数据：序列 1K–4K 端到端约 2.4 倍加速，GPT-2（1K）上约 3 倍。演进路线是 v1（IO-aware）→ v2（减少非 MatMul 开销、更好并行）→ v3（面向 Hopper 的 TMA/WGMMA）。集成方式：PyTorch 的 `scaled_dot_product_attention`、HF 的 `attn_implementation="flash_attention_2"`、vLLM 默认 FA-2。

## 7. CUDA 与 Triton 入门

### 7.1 线程层级

- **Thread**：最小执行单元，靠 `threadIdx` 处理不同数据；
- **Block**：一组线程，共享内存通信，`__syncthreads()` 同步，常见 128/256/512；
- **Grid**：一组 Block。

```cpp
int idx = blockIdx.x * blockDim.x + threadIdx.x;

int row = blockIdx.y * blockDim.y + threadIdx.y;
int col = blockIdx.x * blockDim.x + threadIdx.x;
```

### 7.2 Warp

32 个线程一个 Warp，同一 Warp 以 SIMT 执行相同指令。两个硬约束：合并访存（同 Warp 连续地址才能合成一次事务）、Warp Divergence（分支分歧被串行化）。

### 7.3 Triton：块级抽象

Triton 用 `tl.load/tl.store/tl.dot` 写块级逻辑，编译器负责线程映射与向量化。以 Fused Softmax 为例，整行一次载入 SRAM，在片上完成 max/exp/sum/除法：

```python
@triton.jit
def softmax_kernel(output_ptr, input_ptr, input_row_stride, output_row_stride,
                   n_rows, n_cols, BLOCK_SIZE: tl.constexpr):
    row_idx = tl.program_id(0)
    row_start_ptr = input_ptr + row_idx * input_row_stride

    offsets = tl.arange(0, BLOCK_SIZE)
    mask = offsets < n_cols
    row = tl.load(row_start_ptr + offsets, mask=mask, other=-float("inf"))

    row = row - tl.max(row, axis=0)
    numerator = tl.exp(row)
    denominator = tl.sum(numerator, axis=0)

    out_ptr = output_ptr + row_idx * output_row_stride
    tl.store(out_ptr + offsets, numerator / denominator, mask=mask)
```

朴素 PyTorch 版 Softmax 要读 5MN+2M、写 3MN+2M 个元素，融合后只需一次读一次写，常见 4 倍级加速。矩阵乘法则用 `tl.make_block_ptr` 组织块指针，靠**程序重排序**提升 L2 命中（A100 上从 220 到 245 TFLOPS）。

### 7.4 五层优化路径

| 层 | 手段 | 适用 |
|---|---|---|
| 1 | PyTorch 原生 | 原型与冷路径 |
| 2 | `torch.compile` | 零改动拿收益 |
| 3 | Triton 内核 | 访存密集、融合类算子 |
| 4 | CUDA C++ | 需要硬件特性（TMA 等）或极致调优 |
| 5 | PTX/SASS | 极少数场景 |

决策顺序很朴素：先问 PyTorch 够不够，再问 `torch.compile` 够不够，再判断是否适合 Triton，最后才考虑手写 CUDA——不要一上来就写 Kernel。
