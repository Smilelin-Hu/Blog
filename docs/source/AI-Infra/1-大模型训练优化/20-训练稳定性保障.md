# 训练稳定性保障

## 1. 损失爆炸（Loss Spike）的检测与恢复

### 1.1 什么是 Loss Spike：从「小波动」到「灾难性发散」

Loss Spike 指训练过程中损失值出现的**突然、极端的急剧上升**。这不仅是暂时的性能下降，更可能引发灾难性发散（Catastrophic Divergence），需要人工从早期检查点恢复训练。

在 PaLM 的训练中，研究人员在 540B 参数模型的训练过程中观察到**超过 20 次 Loss Spike**，每次都需要回退检查点并跳过几百个 Batch。更麻烦的是，**触发 Spike 的同一个 Batch 重新播放时，并不总能复现问题**——这暗示 Loss Spike 源于优化器状态与特定输入 Batch 之间的**罕见交互**，是一种脆弱且难以预测的组合。

Loss Spike 的影响不只是时间成本：训练 65B 模型时，处理 Loss Spike 额外消耗了 **30 天时间和 129.3 MWh 的电力**。

### 1.2 根本原因：多种因素的「交汇」

Loss Spike 没有单一的「罪魁祸首」，通常由**多种异质因素的共同作用**触发，常见来源包括：

- **优化器状态**：二阶动量异常、更新方向突变。
- **数据**：罕见的输入批次、脏数据、重复样本。
- **数值精度**：FP16 下溢/上溢、低精度下的累积误差。
- **并行策略**：梯度同步、重计算与通信重叠引入的时序问题。
- **硬件**：静默数据错误（SDC）、链路抖动。

学术界把 Loss Spike 分为两类：

- **良性 Spike（Benign Spike）**：训练可自然恢复，不造成永久损害。
- **恶性 Spike（Malignant Spike）**：导致不可逆发散，必须干预。

关键挑战在于：**在 Spike 发生的瞬间，如何区分良性与恶性？** 如果等到确认是恶性再干预，可能已经错过最佳恢复时机。

### 1.3 检测方法：从人工观察到自动化异常检测

**传统方法：人工监控与手动干预**。实践中应用最广的做法是从之前的检查点重启训练，并跳过受 Spike 影响的 Batch。这种方法资源密集、效率低下，在大规模长时间训练中不可持续。

**自动化检测：Z-Score 异常检测**。**ZClip** 提出基于 **Z-Score** 的自适应异常检测：动态跟踪梯度范数的统计特性（均值与标准差），当梯度范数的 Z-Score 超过阈值时判定为异常 Spike。与固定阈值相比，ZClip **主动适应训练动态**，无需对梯度范数的尺度和时间演化做先验假设。

**Post-Mortem 调试：trainscope**。**trainscope** 是专为 LLM 训练 Loss Spike 设计的**事后调试器**：记录**每层的梯度、权重分布和激活值的峰度（Kurtosis）**——其中峰度是**最早的 Spike 信号**——然后允许在浏览器 UI 中回溯事件。其 GPU 开销仅约 **1%–4%**。

**SPAM：动量重置**。**SPAM（Spike-Aware Adam with Momentum Reset）** 提出优化器层面的解决方案。研究发现梯度 Spike 可以比正常梯度**大 1000 倍**；SPAM 通过**动量重置**和 Spike 感知的梯度裁剪对抗梯度 Spike。

### 1.4 恢复策略：从回退到自适应缓解

**策略一：检查点回退 + Batch 跳过**。最经典的方法——检测到 Spike 后回退到 Spike 发生前约 **100 步**的检查点，然后**跳过 200–500 个 Batch** 继续训练。有效但代价高昂：回退 100 步意味着丢失 100 步进度。

**策略二：自适应梯度裁剪（AdaGC）**。**AdaGC** 提出**按张量（Per-Tensor）的自适应梯度裁剪**：根据历史裁剪值的指数移动平均动态调整每个张量的裁剪阈值，在消除训练不稳定的同时，把下游准确率提升 **1.27%–2.48%**。

**策略三：SPAM 的动量重置**。检测到梯度 Spike 时**重置 Adam 的一阶和二阶动量**，切断异常梯度对优化器状态的「污染」。这种方法不需要回退检查点，可以在**同一个训练步骤内完成恢复**。

**策略四：ZClip 的实时缓解**。ZClip 检测到异常梯度后**动态调整裁剪阈值**抑制大梯度尖峰，同时不干扰正常收敛——这是**主动预防**而非被动恢复。

## 2. 断点续训（Checkpoint & Resume）的实现

### 2.1 为什么 Checkpoint 如此重要

在大规模分布式训练中，**Checkpoint 是稳定性保障的最后一道防线**。无论 Spike 检测多智能、故障排查多迅速，总有一些故障无法预防——硬件突然掉卡、节点宕机、电力中断。这时唯一能依赖的就是定期保存的 Checkpoint。

一个残酷的现实是：对万亿参数模型，**保存一次 Checkpoint 可能需要几分钟到几十分钟**。频率过高会显著拖慢训练；频率过低则故障恢复时丢失的进度太多。

### 2.2 Checkpoint 的核心内容

1. **模型参数（Model State）**：所有网络层的权重和偏置。
2. **优化器状态（Optimizer State）**：Adam 的动量和方差等（混合精度训练中这部分往往最大）。
3. **训练元数据（Training Metadata）**：当前 epoch、step 数、学习率、随机数生成器状态。
4. **分布式训练状态**：ZeRO、FSDP 等分片训练中，各分片的参数与梯度状态。

### 2.3 PyTorch 的 Checkpoint 实现

**单卡场景**：

```python
# 保存
checkpoint = {
    'epoch': epoch,
    'model_state_dict': model.state_dict(),
    'optimizer_state_dict': optimizer.state_dict(),
    'loss': loss,
}
torch.save(checkpoint, 'checkpoint.pth')

# 恢复
checkpoint = torch.load('checkpoint.pth')
model.load_state_dict(checkpoint['model_state_dict'])
optimizer.load_state_dict(checkpoint['optimizer_state_dict'])
epoch = checkpoint['epoch']
```

**分布式场景：PyTorch Distributed Checkpoint（DCP）**。分布式训练中参数和梯度被切分到多个 Rank，保存与恢复更复杂，DCP 专门解决这个问题：

- **按分片保存**：每个 Rank 只保存自己负责的参数分片。
- **按需加载**：加载时只加载所需的 Checkpoint 分片。
- **弹性训练支持**：恢复时的 GPU 数量与保存时不同也能正确加载。

**DeepSpeed 的 Universal Checkpoint**：把 ZeRO 分片的 Checkpoint 转换为**与并行策略无关的通用格式**，因此可以：

- 用不同数量的 GPU 恢复训练（如从 64 卡恢复到 128 卡）。
- 在不同并行配置间迁移（如从 ZeRO-2 迁移到 ZeRO-3）。
- 在不同硬件平台间迁移。

### 2.4 高级 Checkpoint 技术

**JIT Checkpointing（即时检查点）**。周期性 Checkpoint 存在「脆弱窗口」——两次保存之间发生故障会丢失大量进度。**JIT Checkpointing** 在收到终止信号的**瞬间**保存训练状态，而不是等下一个调度间隔。Red Hat 的实践中 JIT Checkpointing 每年可节省**数十万美元**；Kubeflow Training SDK 已内置支持，且**无需修改训练代码**。

**EasyCkpt：阿里巴巴的零开销 Checkpoint**。PAI 团队开发的 **EasyCkpt** 实现了**接近零开销的模型存储机制**：

- **异步分层 Checkpoint**：把保存操作分层，减少对训练主流程的干扰。
- **Checkpoint-计算重叠**：训练的同时异步保存。
- **网络感知的异步 Checkpoint**：根据网络状况动态调整策略。

它使大模型训练可以在**接近零成本**的情况下实现**全过程进度无损的存储与恢复**。

### 2.5 断点续训的工程实践

一个工业级方案的骨架是「从 `start_epoch`/`start_step` 起继续，并按固定步数保存」：

```python
for epoch in range(start_epoch, args.num_epochs):
    for step, batch in enumerate(dataloader, start=start_step):
        # 训练代码...

        # 定期保存Checkpoint
        if step % args.save_interval == 0:
            model.save_checkpoint(args.save_dir, epoch, step)
```

**最佳实践**：

1. **Checkpoint 频率**：建议每 **1000–5000 步**保存一次，或在每个 Epoch 结束时保存。
2. **存储位置**：同时保存到本地与远端（如 S3），防止单点故障。
3. **Checkpoint 清理**：只保留最近 N 个，避免存储耗尽。
4. **原子保存**：先写临时文件，完成后重命名为最终文件名，防止出现损坏的 Checkpoint。

## 3. 训练悬停、OOM 等常见故障的排查

### 3.1 训练悬停（Training Hang）

**现象**：训练进程仍在运行，GPU 利用率掉到 0% 或极低，没有任何错误输出，训练进度停滞。

**根本原因**：大规模分布式训练中，**通信异常是导致 Hang 的最常见原因**，具体包括：

- **NCCL 通信超时**：某个 Rank 在集合通信中无限等待。
- **Rank 提前退出**：某个进程或线程提前退出，其他 Rank 在同步点无限等待。
- **网络分区**：部分节点间的网络连接中断。
- **GPU 掉卡**：某张 GPU 因硬件故障失去响应。

**排查步骤**：

**第 1 步：检查 NCCL 日志**。

```bash
export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=ALL
```

关注通信初始化日志，检查各 Rank 使用的传输类型是否符合预期。如果出现非预期的 path type，需要怀疑节点内链路状态或网络问题。

**第 2 步：导出拓扑图分析**。

```bash
export NCCL_TOPO_DUMP_FILE=topo.xml
export NCCL_GRAPH_DUMP_FILE=graph.xml
```

检查拓扑图是否反映了实际物理连接。

**第 3 步：使用 Flight Recorder（PyTorch 2.0+）**。它可以在 Hang 发生时捕获各 Rank 的状态。NCCL Watchdog Timeout 是一个 **「全能型」错误**——任何可能导致某个 Rank 在集合通信上无限等待的情况都可能触发。

**第 4 步：CCL-D 诊断系统**。大规模集群可用 **CCL-D** 做**Rank 级实时探测**与智能决策分析，在**6 分钟内**精确定位故障 Rank。它已在 **4000 张 GPU 的集群**上部署一年，对已知 Slow/Hang 异常实现近乎全覆盖。

### 3.2 显存溢出（OOM）

**现象**：训练过程中抛出 `CUDA out of memory`，训练中断。

**根本原因**：GPU 显存需求超过物理限制，具体可能来自：

1. **模型规模与显存容量不匹配**：参数 + 梯度 + 优化器状态 + 激活值超过显存。
2. **Batch Size 设置不当**：Batch Size 过大导致激活值爆炸。
3. **内存碎片化**：总显存有剩余，但没有足够大的连续内存块。
4. **残留进程占用**：之前的训练进程没有正常退出，占着显存。

**排查步骤**：

**第 1 步：确认显存占用**。用 `nvidia-smi` 查看显存总容量、已用容量与每个进程的占用；发现残留进程用 `kill -9 PID` 清理。

**第 2 步：分析显存分布**。用 `torch.cuda.memory_summary()` 或 Nsight Systems 分析具体分配情况，确认是模型状态（参数/梯度/优化器）还是激活值占了主要空间。

**第 3 步：调整并行策略**。如果 OOM 发生在分布式训练中，可以增加 **TP** 或 **PP** 的值，把模型切到更多 GPU；注意约束 `TP × PP ≤ GPU 数量`且需整除。

**第 4 步：启用显存优化技术**：降低 Batch Size；启用激活值重计算；用 ZeRO-Offload 把优化器状态卸载到 CPU；换用更高效的算子（如 FlashAttention）。

### 3.3 其他常见故障

**NaN/Inf 值**：训练中 Loss 变为 NaN 或 Inf。原因通常是梯度爆炸（常与 Loss Spike 相关）、学习率过高、数值精度问题（FP16 下溢）。排查时用 trainscope 等工具记录每层梯度范数与 NaN/Inf 比例，定位异常层。

**GPU 硬件故障**：大规模集群中 GPU 硬件故障是常态。字节跳动的 **ByteRobust** 通过三条手段应对：

- **高容量容错**：利用 LLM 训练的并行特性实现故障容忍。
- **快速故障界定与定位**：数据驱动的方法快速定位故障。
- **自动故障恢复**：在常规训练流程中自动检测和恢复。

ByteRobust 在 **9600 张 GPU** 上运行**3 个月**的训练任务，实现了 **97% 的有效训练时间比（ETTR）**。
