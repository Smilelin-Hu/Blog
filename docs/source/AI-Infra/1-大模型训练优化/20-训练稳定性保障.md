# 训练稳定性保障

### 1.1. 什么是Loss Spike：从“小波动”到“灾难性发散”
Loss Spike是指训练过程中损失值出现的**突然、极端的急剧上升**。这不仅是暂时的性能下降，更可能引发灾难性发散（Catastrophic Divergence），需要人工从早期检查点恢复训练。
在PaLM的训练中，研究人员在540B参数模型的训练过程中观察到了**超过20次Loss Spike**，每次都需要回退检查点并跳过几百个Batch。更令人困扰的是，**触发Spike的同一个Batch重新播放时，并不总能复现问题**——这暗示了Loss Spike源于优化器状态与特定输入Batch之间的**罕见交互**，是一种脆弱且难以预测的组合。
Loss Spike的影响不只是时间成本。训练65B模型时，处理Loss Spike额外消耗了**30天时间和129.3 MWh的电力**。

有趣的是，学术界将Loss Spike分为两种类型：
- **良性Spike（Benign Spike）**：训练可以自然恢复，不造成永久性损害
- **恶性Spike（Malignant Spike）**：导致不可逆的发散，必须干预
关键挑战在于：**在Spike发生的瞬间，如何区分良性和恶性？** 如果等到确认是恶性再干预，可能已经错过了最佳恢复时机。
### 1.3. 检测方法：从人工观察到自动化异常检测
**传统方法：人工监控与手动干预**
实践中，最广泛采用的方法是**人工干预**——从之前的检查点重启训练，并跳过受Spike影响的Batch。这种方法资源密集、效率低下，且在大规模长时间训练中不可持续。
**自动化检测：Z-Score异常检测**
**ZClip**提出了一种基于**Z-Score**的自适应异常检测方法。其核心思想是：动态跟踪梯度范数的统计特性（均值和标准差），当梯度范数的Z-Score超过阈值时，判定为异常Spike。与传统固定阈值方法不同，ZClip**主动适应训练动态**，无需对梯度范数的尺度和时间演化做出先验假设。
**Post-Mortem调试：trainscope**
**trainscope**是一个专门为LLM训练Loss Spike设计的**事后调试器**。当Spike发生时，通常知道它发生了，但不知道为什么。trainscope记录了**每层的梯度、权重分布和激活值的峰度（Kurtosis）** ——其中峰度是**最早的Spike信号**——然后允许在浏览器UI中回溯事件。其GPU开销仅约**1-4%**。
**SPAM：动量重置**
**SPAM（Spike-Aware Adam with Momentum Reset）** 提出了一种优化器层面的解决方案。研究发现，梯度Spike可以比正常梯度**大1000倍**。SPAM通过**动量重置**和**Spike感知的梯度裁剪**来对抗梯度Spike。
### 1.4. 恢复策略：从回退到自适应缓解
**策略一：检查点回退 + Batch跳过**
这是最经典的恢复方法：当检测到Spike后，回退到Spike发生前约**100步**的检查点，然后**跳过200-500个Batch**继续训练。这种方法有效但代价高昂——回退100步意味着丢失了100步的训练进度。
**策略二：自适应梯度裁剪（AdaGC）**
**AdaGC**提出了一种**按张量（Per-Tensor）的自适应梯度裁剪**方案。它根据历史裁剪值的指数移动平均来动态调整每个张量的裁剪阈值，在消除训练不稳定的同时，将下游准确率提升了**1.27%-2.48%**。
**策略三：SPAM的动量重置**
SPAM的动量重置机制在检测到梯度Spike时，**重置Adam的一阶和二阶动量**，切断异常梯度对优化器状态的“污染”。这种方法不需要回退检查点，可以在**同一个训练步骤中完成恢复**。
**策略四：ZClip的实时缓解**
ZClip在检测到异常梯度后，**动态调整裁剪阈值**来抑制大梯度尖峰，同时不干扰正常收敛。这是一种**主动预防**而非被动恢复的策略。
### 2.1. 为什么Checkpoint如此重要
在大规模分布式训练中，**Checkpoint是稳定性保障的最后一道防线**。无论Loss Spike检测多么智能、故障排查多么迅速，总有一些故障是无法预防的——硬件突然掉卡、节点宕机、电力中断。在这些情况下，唯一能依赖的就是定期保存的Checkpoint。
一个残酷的现实是：对于万亿参数模型，**保存一次Checkpoint可能需要几分钟到几十分钟**。如果Checkpoint频率过高，训练效率会大幅下降；如果频率过低，故障恢复时丢失的进度太多。
### 2.2. Checkpoint的核心内容
一个完整的训练Checkpoint需要保存以下状态：
1. **模型参数（Model State）**：所有网络层的权重和偏置
2. **优化器状态（Optimizer State）**：Adam的动量和方差等（在混合精度训练中，这部分往往是最大的）
3. **训练元数据（Training Metadata）**：当前epoch、step数、学习率、随机数生成器状态等
4. **分布式训练状态**：在ZeRO、FSDP等分片训练中，需要保存各分片的参数和梯度状态
### 2.3. PyTorch的Checkpoint实现
**单卡场景**：
```text
# 保存
checkpoint = {
    'epoch': epoch,
    'model_state_dict': model.state_dict(),
    'optimizer_state_dict': optimizer.state_dict(),
    'loss': loss,
}
torch.save(checkpoint, 'checkpoint.pth')

# 恢复
checkpoint = torch.load('checkpoint.pth')
model.load_state_dict(checkpoint['model_state_dict'])
optimizer.load_state_dict(checkpoint['optimizer_state_dict'])
epoch = checkpoint['epoch']
```
**分布式场景：PyTorch Distributed Checkpoint（DCP）**
在分布式训练中，参数和梯度被切分到多个Rank上，Checkpoint的保存和恢复变得更加复杂。PyTorch的**Distributed Checkpointing（DCP）** 专门解决了这个问题：
- **按分片保存**：每个Rank只保存自己负责的参数分片
- **按需加载**：加载时只加载所需的Checkpoint分片
- **弹性训练支持**：即使恢复时的GPU数量与保存时不同，也能正确加载
**DeepSpeed的Universal Checkpoint**
DeepSpeed提供了**Universal Checkpoint**格式，可以将ZeRO分片的Checkpoint转换为**与并行策略无关的通用格式**。这意味着：
- 用不同数量的GPU恢复训练（如从64卡恢复到128卡）
- 在不同并行配置间迁移（如从ZeRO-2迁移到ZeRO-3）
- 在不同硬件平台间迁移
### 2.4. 高级Checkpoint技术
**JIT Checkpointing（即时检查点）**
传统的周期性Checkpoint存在一个“脆弱窗口”——两次Checkpoint之间如果发生故障，会丢失大量进度。**JIT Checkpointing**在收到终止信号的**瞬间**保存训练状态，而不是等待下一个调度间隔。在Red Hat的实践中，JIT Checkpointing每年可为企业节省**数十万美元**的成本。Kubeflow Training SDK已内置支持JIT Checkpointing，且**无需修改训练代码**。
**EasyCkpt：阿里巴巴的零开销Checkpoint**
阿里巴巴PAI团队开发的**EasyCkpt**实现了**接近零开销的模型存储机制**。它通过以下技术实现：
- **异步分层Checkpoint**：将Checkpoint操作分层，减少对训练主流程的干扰
- **Checkpoint-计算重叠**：在训练的同时异步保存Checkpoint
- **网络感知的异步Checkpoint**：根据网络状况动态调整Checkpoint策略
EasyCkpt使得大模型训练可以在**接近零成本**的情况下实现**全过程进度无损的模型存储与恢复**。
### 2.5. 断点续训的工程实践
一个工业级的断点续训方案应包含以下要素：
```text

    for epoch in range(start_epoch, args.num_epochs):
        for step, batch in enumerate(dataloader, start=start_step):
            # 训练代码...

            # 定期保存Checkpoint
            if step % args.save_interval == 0:
                model.save_checkpoint(args.save_dir, epoch, step)
```
**最佳实践**：
1. **Checkpoint频率**：建议每**1000-5000步**保存一次，或在每个Epoch结束时保存
2. **存储位置**：同时保存到本地和远端存储（如S3），防止单点故障
3. **Checkpoint清理**：只保留最近N个Checkpoint，避免存储空间耗尽
4. **原子保存**：先保存到临时文件，完成后重命名为最终文件名，防止损坏的Checkpoint
### 3.1. 训练悬停（Training Hang）
**现象**：训练进程仍在运行，GPU利用率掉到0%或极低，但没有任何错误输出，训练进度停滞。
**根本原因**：
在大规模分布式训练中，**通信异常是导致Hang的最常见原因**。具体包括：
- **NCCL通信超时**：某个Rank在集合通信中无限等待
- **Rank提前退出**：某个进程或线程提前退出，其他Rank在同步点无限等待
- **网络分区**：部分节点间的网络连接中断
- **GPU掉卡**：某张GPU因硬件故障失去响应
**排查步骤**：
**第1步：检查NCCL日志**
```bash
export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=ALL
```
关注通信初始化日志，检查各Rank使用的传输类型是否符合预期。如果出现非预期的path type，需要怀疑节点内链路状态或网络问题。
**第2步：导出拓扑图分析**
```bash
export NCCL_TOPO_DUMP_FILE=topo.xml
export NCCL_GRAPH_DUMP_FILE=graph.xml
```
检查拓扑图是否反映了实际的物理连接。
**第3步：使用Flight Recorder（PyTorch 2.0+）**
PyTorch引入的Flight Recorder可以在Hang发生时捕获各Rank的状态。NCCL Watchdog Timeout是一个 **“全能型（Catch-All）”错误**——任何可能导致某个Rank在集合通信上无限等待的情况都可能触发。
**第4步：CCL-D诊断系统**
对于大规模集群，**CCL-D**提供了**Rank级别的实时探测**和**智能决策分析**，可在**6分钟内**精确定位故障Rank。CCL-D已在**4000张GPU的集群**上部署一年，实现了对已知Slow/Hang异常的**近乎全覆盖**。
### 3.2. 显存溢出（OOM）
**现象**：训练过程中抛出`CUDA out of memory`异常，训练中断。
**根本原因**：
OOM的本质是**GPU显存需求超过物理限制**。具体可能来自：
1. **模型规模与显存容量不匹配**：模型参数+梯度+优化器状态+激活值超过显存
2. **Batch Size设置不当**：Batch Size过大导致激活值爆炸
3. **内存碎片化**：虽然总显存有剩余，但没有足够大的连续内存块
4. **残留进程占用**：之前的训练进程没有正常退出，占用了显存
**排查步骤**：
**第1步：确认显存占用**
```bash
nvidia-smi
```
查看显存总容量、已用容量，以及每个进程的显存占用。如果发现残留进程，使用`kill -9 PID`清理。
**第2步：分析显存分布**
使用`torch.cuda.memory_summary()`或Nsight Systems分析显存的具体分配情况，确认是模型状态（参数/梯度/优化器）还是激活值占用了主要空间。
**第3步：调整并行策略**
如果OOM发生在分布式训练中，可以尝试：
- 增加**TP（张量并行）** 或**PP（流水线并行）** 的值，将模型切分到更多GPU上
- 注意约束：`TP × PP ≤ GPU数量`，且需要被整除
**第4步：启用显存优化技术**
- 降低Batch Size
- 启用激活值重计算（Gradient Checkpointing）
- 使用ZeRO-Offload将优化器状态卸载到CPU
- 使用更高效的算子（如FlashAttention）
### 3.3. 其他常见故障
**NaN/Inf值**
**现象**：训练过程中Loss变为NaN或Inf。
**原因**：
- 梯度爆炸（通常与Loss Spike相关）
- 学习率过高
- 数值精度问题（FP16下溢）
**排查**：使用trainscope等工具记录每层的梯度范数和NaN/Inf比例，定位异常层。
**GPU硬件故障**
在大规模集群中，GPU硬件故障是常态。字节跳动的ByteRobust系统通过以下方式应对：
- **高容量容错**：利用LLM训练的并行特性实现故障容忍
- **快速故障界定与定位**：数据驱动的方法快速定位故障
- **自动故障恢复**：在常规训练流程中自动检测和恢复故障
ByteRobust在**9600张GPU**上运行**3个月的训练任务**，实现了**97%的有效训练时间比（ETTR）**。
