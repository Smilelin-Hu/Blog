# 数据、稳定性与可观测性

训练跑不起来是显存问题，跑不快是并行与通信问题，而**跑不完**通常是数据、稳定性与运维问题。这一篇覆盖数据供给、Loss Spike、指标监控、高可用，以及两个特殊负载：RLHF 训练与长上下文训练。

## 1. 数据供给：别让 GPU 等数据

### 1.1 停等效应

```python
train_loader = DataLoader(dataset, batch_size=32)   # num_workers=0
```

`num_workers=0` 时数据加载是同步的：主进程读盘、预处理，然后才能把 batch 递给 GPU，期间 GPU 完全空闲。这就是 Stall。

### 1.2 四个关键参数

| 参数 | 作用 | 经验值 |
|---|---|---|
| `num_workers` | 多进程预加载 | 从 CPU 物理核数或 \(4 \times\) GPU 数起步，预处理越重越需要加 |
| `pin_memory` | 锁页内存，让 DMA 直接读 | 训练时恒开 |
| `prefetch_factor` | 每个 worker 预取的批次数 | 默认 2；GPU 利用率周期性掉坑时加大 |
| `persistent_workers` | worker 跨 epoch 存活 | 多 epoch 训练必开，避免反复创建进程 |

`pin_memory=True` 必须和 `non_blocking=True` 配合，才能真正让 H2D 拷贝与计算重叠：

```python
inputs = inputs.to(device, non_blocking=True)
labels = labels.to(device, non_blocking=True)
```

### 1.3 一个可用的配置

```python
train_loader = DataLoader(
    dataset,
    batch_size=256,
    shuffle=True,
    num_workers=8,
    pin_memory=True,
    prefetch_factor=4,
    persistent_workers=True,
)
```

注意 worker 数在分布式下的口径：总 worker 数是**每个 rank 之和**，8 卡 × 8 worker = 64 个进程在抢同一块盘的 IO。

## 2. 存储与格式

选格式看三件事：行式还是列式、随机访问还是顺序访问、能不能从对象存储流式读。

| 格式 | 优势 | 局限 | 适用 |
|---|---|---|---|
| TFRecord | 支持 GZIP/ZSTD，适合流式读取，与 TF 生态深度集成 | 偏 TensorFlow，Schema 隐式，随机访问弱 | TF / GCP 上的大规模训练 |
| Parquet | 列裁剪、自描述 Schema、生态广（Spark/Pandas/PyArrow/HF） | 随机访问差，多模态大对象受 row group 限制，无原生版本控制 | 结构化训练数据与数据湖 |
| Lance | 为 AI 负载设计，文件格式 + 表格式 + 二级索引 | 生态相对新 | 多模态、需要随机访问与版本管理的场景 |

训练打乱需要随机访问，这与列式格式的顺序读优势天然冲突；因此大规模训练的常见做法是「离线重排成若干 shard，训练时按 shard 顺序流式读，shard 内再打乱」。

## 3. 训练稳定性：Loss Spike

### 3.1 现象与量级

Loss Spike 是损失突然、极端上升，可能引发灾难性发散。PaLM 540B 的训练中观察到 20 多次 Spike，每次都要回退检查点并跳过数百个 Batch；同一 Batch 重放不一定复现，说明 Spike 来自优化器状态与特定输入的罕见交互。训练 65B 模型时，处理 Spike 额外消耗了 30 天与 129.3 MWh 电力。

### 3.2 良性还是恶性

- **良性 Spike**：训练能自然恢复，处理成本是「等一等」；
- **恶性 Spike**：不可逆发散（常见伴随 NaN/Inf），必须回退。

关键是在 Spike 发生后的几十步内快速区分二者，这决定了是继续跑还是立刻回滚。

### 3.3 检测手段

- **固定阈值**：简单但误报多，不同模型、不同阶段的梯度范数量级不同；
- **ZClip**：动态跟踪梯度范数的均值与标准差，用 Z-Score 判异常：

$$
z_t = \frac{\lVert g_t \rVert - \mu_t}{\sigma_t}
$$

  超过阈值即判为异常并裁剪，能适应训练阶段的变化；
- **trainscope**：记录每层梯度、权重分布与激活峰度，用于事后回溯；峰度往往比 Loss 更早出现异常；
- **SPAM**（Spike-Aware Adam with Momentum Reset）：检测到大梯度后重置动量并做 Spike 感知裁剪，避免异常值污染 Adam 状态。

### 3.4 恢复策略

1. **检查点回退 + Batch 跳过**：回到 Spike 前约 100 步，跳过 200–500 个 Batch；
2. **AdaGC**：按张量维护历史裁剪值的 EMA，动态设阈值；
3. **SPAM 类方法**：不回退，直接清理优化器状态后继续。

## 4. 可观测性：训练指标

### 4.1 三类核心指标

- **Loss**：同时看训练 Loss、验证 Loss 与异常波动。训练降而验证升提示过拟合；Loss 突增时按「显存 → 数据批次 → 学习率 → 检查点恢复」的顺序排查。
- **梯度范数**：突增 10 倍以上怀疑梯度爆炸；长期贴近 0 怀疑梯度消失或学习率问题；与 Loss 同步跳变多半是坏数据。
- **学习率**：监控优化器实际学习率与调度器目标是否一致、Warmup 是否按计划从 0 上升、衰减时机是否对。

### 4.2 更早的信号

**Spectral Alignment（谱对齐）** 监控层输入与权重主奇异向量的分布对齐情况，可以在 Loss 爆炸之前给出预警——从「事后检测」走向「事前预测」。

### 4.3 采集频率是硬约束

大模型单步常在 100 ms 到 1 s，核心训练指标必须与迭代同步、每步采集、端到端延迟控制在 100 ms 以内。五分钟级的通用监控无法支撑实时干预。

### 4.4 GPU Util 不等于 MFU

- Util > 90%：说明 GPU 持续工作，但仍要区分「有效计算」与「访存/通信 Kernel」；
- 长期 < 70%：查数据加载、通信等待、大量小 Kernel。

判断是否「真的高效」要结合 SM 效率、Tensor Core 活动、HBM 带宽与 step time，而不是只看一个百分比。

## 5. 高可用：故障是常态

### 5.1 故障的三类来源

- **硬件**：GPU Xid、ECC、NVLink 错误、过热降频、显存错误、PCIe 不稳定、电源与散热；
- **软件与运行时**：NCCL 超时/死锁、CUDA 与驱动崩溃、OOM、Loss Spike 产生 NaN；
- **运维事件**：节点维护、内核升级、网络分区、Spot 抢占。

同步训练下，任何一个节点故障都可能阻塞所有 Rank——这就是高可用要解决的问题。

### 5.2 三层检测

1. **硬件层**：IPMI 与健康代理采集温度、功耗、ECC、NVLink 计数器，建健康度模型并做主动健康检查；
2. **通信层**：比较集合操作完成时间，找出显著慢于同组其他 Rank 的 straggler；
3. **任务层**：守护进程监控进程致命异常、step 停滞、数据与存储路径可达性。

### 5.3 三种迁移策略

| 策略 | 做法 | 代价 |
|---|---|---|
| 检查点回退 + 节点替换 | 隔离坏节点、拉起健康节点、回退到最近 checkpoint | 进度损失取决于 checkpoint 间隔 |
| 实时迁移（如 TrainMover） | 备用机 + 两阶段增量通信组重建 + 无通信沙箱影子迭代 | 实现复杂；周期 10 分钟重平衡场景下可维持约 99% 效率 |
| 弹性缩容继续训练 | 减少 world size 继续跑，资源恢复后再扩容 | 需要框架支持弹性并行（如 DLRover 在 K8s 上的 Pod 替换与自动扩缩） |

字节跳动的 ByteRobust 是万卡级容错实践的代表，核心思路是把「检测—隔离—重建—恢复」做成平台能力，而不是靠人工值守。

## 6. RLHF 训练：系统视角

### 6.1 为什么 RLHF 比 SFT 难

预训练与 SFT 只优化「下一个 token 的似然」，而 RLHF 要优化「人类偏好」。标准流程分三步：

1. **SFT**：用高质量问答对做监督微调，让模型从「续写」转向「回答」；
2. **奖励模型（RM）**：用人类偏好对比数据训练一个打分器，输入 prompt + response，输出标量偏好分数；
3. **RL 微调**：以 RM 的分数为奖励，用 PPO 等算法继续优化 SFT 模型。

### 6.2 PPO 的四个模型

PPO 训练时同时维护四个模型：

| 模型 | 作用 |
|---|---|
| Actor | 当前策略，生成回答 |
| Reference | 冻结的参考策略，用于 KL 约束，防止跑偏 |
| Critic | 价值估计，计算优势 |
| Reward | 奖励模型，给回答打分 |

显存压力很直观：70B 模型四份 BF16 权重就是 \(4 \times 70\text{B} \times 2 \approx 560\) GB，单卡放不下，必须 TP/PP + ZeRO 分布式部署。

### 6.3 系统挑战

RLHF 是「生成 → 评分 → 训练」的串行流水，三个阶段的并行形态不同（生成是推理负载、训练是训练负载），资源利用率天然低于纯训练。因此工程上关注三件事：阶段间的权重同步开销、生成阶段的 KV Cache 与批处理、以及 PPO 的样本新鲜度（rollout 与 policy 版本的偏差）。

## 7. 长上下文训练

### 7.1 二次方复杂度

标准 Self-Attention 要计算 \(N \times N\) 的注意力矩阵，显存与计算都是 \(O(N^2)\)。序列从 4K 到 128K（32 倍），注意力矩阵增长 1024 倍；到 1M 时矩阵本身就要 TB 级显存。

此外前向还要缓存反向所需的 K、V 与中间激活。一个可参考的数字：Qwen2.5-3B 在不用序列并行时单卡显存可达 75.35 GiB，8 卡 Ulysses + Ring Attention 可降到 17.92 GiB，降幅 76%。

### 7.2 三重瓶颈

- **显存**：128K 序列的朴素注意力分数矩阵超过单卡容量；
- **计算**：序列翻倍，标准 Attention 计算量增长 4 倍；
- **通信**：序列切到多卡后，K/V 或激活交换成为新瓶颈，百万 token、数十卡时通信可占总时间 40% 以上。

### 7.3 为什么传统并行不够

- **DP**：每卡仍处理完整序列；
- **TP**：单卡显存下降，但长序列下层内通信更频繁；
- **PP**：按层切分，不解决单层 Attention 的 \(N^2\) 问题。

因此需要第四种维度：**序列并行（SP/CP）**，沿序列维度把输入切到多个设备。

### 7.4 两条主流路线

- **DeepSpeed-Ulysses**：Attention 前做 All-to-All，把「序列切分」布局转成「Head 切分」布局，使每卡拥有完整序列但只算部分 Head。通信量在序列长度与设备数同比增加时可保持相对稳定，但并行度受 Head 数量限制。
- **Ring Attention**：保留本地 Q 块，让 K/V 块沿环传递，分块计算并累加结果。它不要求 Head 数可整除，适合更长的序列，但对链路带宽与流水重叠要求更高。
