# 数据、稳定性与可观测性

训练跑不起来是显存问题，跑不快是并行与通信问题，而**跑不完**通常是数据、稳定性与运维问题。这一篇覆盖数据供给、检查点与断点续训、Loss Spike、指标监控、高可用与弹性训练，以及两个特殊负载：RLHF 与长上下文。

## 1. 数据供给：别让 GPU 等数据

`num_workers=0` 时数据加载是同步的：读盘、预处理完成后才把 batch 递给 GPU，期间 GPU 空转，这就是 Stall。

| 参数 | 作用 | 经验 |
|---|---|---|
| `num_workers` | 多进程预加载 | 从 CPU 物理核数或 \(4\times\)GPU 起步；预处理越重越要加 |
| `pin_memory` | 锁页内存，DMA 直接读 | 训练恒开；不开时 H2D 可能慢 30%–50% |
| `prefetch_factor` | 每 worker 预取批次数 | 默认 2；GPU 利用率周期性掉坑就加大 |
| `persistent_workers` | worker 跨 epoch 存活 | 多 epoch 必开 |

```python
train_loader = DataLoader(
    dataset, batch_size=256, shuffle=True,
    num_workers=8, pin_memory=True,
    prefetch_factor=4, persistent_workers=True,
)
```

配合 `non_blocking=True` 才能真正重叠。注意分布式口径：总 worker 数是**各 rank 之和**，8 卡 × 8 worker 就是 64 个进程抢同一块盘。

## 2. 存储与格式

选格式看三件事：行式/列式、随机访问/顺序读、能否从对象存储流式读。

| 格式 | 优势 | 局限 | 适用 |
|---|---|---|---|
| TFRecord | 支持 GZIP/ZSTD，流式读，TF 生态 | Schema 隐式、随机访问弱 | TF / GCP 大规模训练 |
| Parquet | 列裁剪、自描述、生态广 | 随机访问差、多模态受 row group 限制、无版本控制 | 结构化数据与数据湖 |
| Lance | AI 负载设计，格式 + 表 + 二级索引 | 生态较新 | 多模态、需随机访问与版本管理 |

训练打乱要随机访问，列式格式擅长顺序读——两者天然冲突。通行做法是**离线重排成 shard，训练按 shard 顺序流式读，shard 内再打乱**。

## 3. 稳定性：Loss Spike

### 3.1 现象与代价

PaLM 540B 训练中出现 20 多次 Spike，每次都要回退检查点、跳过数百 batch；同一 batch 重放不一定复现，说明它来自优化器状态与特定输入的罕见交互。训练 65B 模型时，处理 Spike 额外消耗约 30 天与 129.3 MWh 电力。

两类要分开：**良性 Spike**（能自愈，等一等就好）与**恶性 Spike**（NaN/Inf，不可逆）。关键是在几十步内判断出是哪一类。

### 3.2 检测

- **固定阈值**：简单但误报多；
- **ZClip**：跟踪梯度范数的均值与标准差，用 Z-Score 判异常：

$$
z_t = \frac{\lVert g_t\rVert - \mu_t}{\sigma_t}
$$

- **trainscope**：记录每层梯度、权重分布与激活峰度，峰度往往比 Loss 更早报警；
- **SPAM**：检测到大梯度后重置动量 + Spike 感知裁剪，防止异常污染 Adam 状态。

### 3.3 恢复

检查点回退（约 100 步）+ 跳过 200–500 个 batch 是最稳的做法；AdaGC 按张量维护历史裁剪值的 EMA 动态设阈值；SPAM 一类方法则不清空进度，直接清理优化器状态继续跑。

## 4. 检查点与断点续训

### 4.1 分布式检查点

参数被切到多个 rank 后，保存/恢复都变复杂：

- **PyTorch DCP**：按分片保存、按需加载，支持恢复时卡数变化；
- **DeepSpeed Universal Checkpoint**：把 ZeRO 分片转成与并行策略无关的格式，可在 64 卡 ↔ 128 卡之间、ZeRO-2 ↔ ZeRO-3 之间迁移。

### 4.2 降低检查点成本

- **JIT Checkpointing**：收到终止信号瞬间保存，而不是等下一个周期——填补「两次检查点之间的脆弱窗口」；
- **EasyCkpt（阿里 PAI）**：异步分层 + 与计算重叠 + 网络感知，做到接近零开销的全过程无损存储。

### 4.3 工程规范

1. 频率：每 1000–5000 步或每 epoch；
2. 位置：本地 + 远端（S3 等）双写，避免单点；
3. 清理：只保留最近 N 个，防止打满存储；
4. **原子保存**：先写临时文件再重命名，避免半写坏的检查点。

## 5. 可观测性

### 5.1 三类核心指标

- **Loss**：训练/验证同时看。训练降而验证升是过拟合；突增按「显存 → 数据 → 学习率 → 恢复策略」顺序排查。
- **梯度范数**：突增 10 倍以上怀疑爆炸；长期贴 0 怀疑消失或学习率问题；与 Loss 同步跳变多半是坏数据。
- **学习率**：核对实际值与调度器目标是否一致、Warmup 是否按计划、衰减时机是否正确。

### 5.2 更早的信号与采样频率

**Spectral Alignment** 监控层输入与权重主奇异向量的分布对齐，可在 Loss 爆炸前预警。采样频率是硬约束：单步 100 ms–1 s，核心指标需每步采集、端到端延迟 < 100 ms，五分钟级监控无法支撑实时干预。

### 5.3 GPU Util 不等于 MFU

| 观察 | 可能含义 |
|---|---|
| Util > 90% | 卡在忙，但要看忙的是计算还是访存/通信 kernel |
| 长期 < 70% | 数据加载、通信等待或大量小 kernel |

判断效率要联合 SM 效率、Tensor Core 活动、HBM 带宽与 step time。

## 6. 高可用与弹性训练

### 6.1 故障是常态

硬件（Xid、ECC、NVLink、过热、PCIe、电源）、软件（NCCL 超时、驱动崩溃、OOM、NaN）、运维（维护、升级、网络分区、Spot 抢占）——同步训练下任何一个节点出问题都会阻塞全部 rank。

### 6.2 Hang 与 OOM 的排查

**Hang**（进程在跑、GPU 0%、无报错）：先开 `NCCL_DEBUG=INFO` + `NCCL_DEBUG_SUBSYS=ALL` 看初始化与 path type，再导 `NCCL_TOPO_DUMP_FILE` / `NCCL_GRAPH_DUMP_FILE` 核对拓扑，再用 PyTorch Flight Recorder 抓各 rank 状态。大规模集群可用 CCL-D 做 rank 级实时探测——公开数据是 6 分钟内定位故障 rank，已在 4000 卡集群运行一年。

**OOM** 四条根因：规模与容量不匹配、batch 过大导致激活爆炸、碎片化、残留进程。处理顺序：确认占用（`nvidia-smi`、`memory_summary()`）→ 分析分布 → 调 TP/PP（注意 `TP × PP ≤ GPU 数` 且需整除）→ 降 batch / 开重计算 / Offload。

### 6.3 弹性训练

**TorchElastic / torchrun** 用动态 rendezvous 组网：节点故障视为「缩容」，替换节点视为「扩容」，成员变化触发重新组网，`--max-restarts` 控次数。

```bash
torchrun --nnodes=4 --nproc-per-node=8 --max-restarts=5 \
         --rdzv-id=job_001 --rdzv-backend=c10d \
         --rdzv-endpoint=etcd:2379 train.py
```

**DLRover** 在 K8s 上做得更完整：故障隔离 + Pod 替换 + 自动缩容/扩容 + FSDP reshard。公开数据是千卡训练的有效训练时间从 32.9% 提到 58.9%。

**Lazarus** 针对 MoE：自适应专家副本、最优专家放置、灵活 token 分发，在频繁故障下比现有系统快 5.7 倍（真实 Spot 轨迹 3.4 倍）。

**ByteRobust** 是万卡级实践：9600 张 GPU 跑 3 个月训练，有效训练时间比（ETTR）达 97%。

### 6.4 自动扩缩容

- **HPA**：按 GPU 利用率或队列长度扩 Pod；
- **Cluster Autoscaler**：扩节点，配合云上弹性实例池；
- **Kueue + KEDA**：按作业队列积压预判扩容，队列空可缩到 0；
- **训练感知**：按 Loss 收敛速度、训练阶段（预热/稳定/收尾）调规模。

弹性训练 + 自动扩缩容闭合成环：队列积压 → 扩节点 → TorchElastic 重新组网 → 继续训练（不重启作业）；低谷期反向缩容。

## 7. RLHF 训练的系统视角

### 7.1 三阶段

1. **SFT**：让模型从「续写」转向「回答」；
2. **奖励模型**：用人类偏好对比数据训练打分器（prompt + response → 标量）；
3. **RL 微调**：以 RM 分数为奖励，用 PPO 优化。

### 7.2 PPO 的四模型与显存

| 模型 | 作用 |
|---|---|
| Actor | 当前策略，生成回答 |
| Reference | 冻结参考策略，KL 约束 |
| Critic | 价值估计，算优势 |
| Reward | 奖励模型，打分 |

70B 四份 BF16 权重即 \(4 \times 70\text{B} \times 2 \approx 560\) GB，必须 TP/PP + ZeRO 分布式部署。

### 7.3 系统挑战

「生成 → 评分 → 训练」三阶段并行形态不同（推理负载 vs 训练负载），利用率天然低于纯训练。工程关注三点：阶段间权重同步开销、生成阶段的 KV Cache 与批处理、PPO 的样本新鲜度（rollout 与 policy 版本偏差）。

## 8. 长上下文训练

### 8.1 二次方复杂度

标准 Attention 显存与计算都是 \(O(N^2)\)：序列 4K→128K（32 倍），注意力矩阵涨 1024 倍；到 1M 时矩阵本身就要 TB 级。前向还要缓存 K/V 与中间激活——Qwen2.5-3B 不用序列并行时单卡可达 75.35 GiB，8 卡 Ulysses + Ring Attention 可降到 17.92 GiB（降 76%）。

### 8.2 三重瓶颈

- **显存**：128K 的朴素分数矩阵超单卡；
- **计算**：序列翻倍，计算量 4 倍；
- **通信**：序列切多卡后 K/V 或激活交换成为新瓶颈，百万 token、数十卡时通信可占 40% 以上。

DP/TP/PP 都解决不了单层 Attention 的 \(N^2\)：DP 每卡仍是完整序列，TP 层内通信更频繁，PP 只切层。于是需要第四维度——**序列并行（SP/CP）**。

### 8.3 两条路线

- **DeepSpeed-Ulysses**：Attention 前做 All-to-All，把「序列切分」转成「Head 切分」，并行度受 Head 数限制；
- **Ring Attention**：保留本地 Q 块，K/V 块沿环传递分块计算，不要求 Head 整除，适合更长序列，但对带宽与流水重叠要求高。
