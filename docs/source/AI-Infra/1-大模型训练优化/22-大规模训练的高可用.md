# 大规模训练的高可用（High Availability）

### 1.1. 故障的普遍性与多源性
在大规模训练集群中，故障的来源极其多样，远不止“硬件坏了”这么简单。
**硬件层故障**：
- GPU Xid错误、ECC（纠错码）错误、NVLink错误
- GPU温度过高导致降频
- 显存硬件错误、PCIe链路不稳定
- 电源、散热、主板等基础设施问题
**软件与运行时故障**：
- NCCL通信超时或死锁
- CUDA错误、驱动崩溃
- 训练进程OOM（显存溢出）
- Loss Spike导致的NaN/Inf值
**管理与运维事件**：
- 节点维护、内核升级
- 网络分区、交换机故障
- 资源抢占（尤其是在云环境中使用Spot实例时）
这些故障有一个共同特点：**任何一个节点的故障都可能导致整个训练任务中断**。在数据并行中，梯度同步的AllReduce要求所有节点同时参与——一个节点掉线，所有节点都在等待。
### 1.2. 多层级故障检测
一个成熟的故障检测体系需要在多个层级同时工作：
**硬件级检测：主动探测与被动监控**
硬件层故障检测的核心是**实时监控硬件的健康状态**。字节跳动的ByteRobust系统通过以下方式实现硬件故障的早发现：
- **IPMI协议监控**：实时采集GPU温度、功耗、显存错误等硬件指标
- **健康度模型**：基于历史数据训练的健康度预测模型，**提前预测**故障节点
- **主动健康检查**：Amazon SageMaker HyperPod的运行状况监控代理在集群中所有GPU节点上持续运行，监视GPU或NVLink错误计数器等硬件问题
**通信层检测：识别“慢节点”**
硬件故障往往不是突然“死亡”，而是先表现为性能下降。字节跳动的实践表明，**拖尾节点（Straggler）并不总是由硬件故障简单引起，而是多种复杂因素共同作用的结果**。通信层检测通过监控NCCL集合操作的完成时间，识别那些响应明显慢于同组其他节点的“慢节点”。
**任务层检测：应用感知的故障发现**
最接近训练任务的检测方式是在训练过程中植入健康检查逻辑。DLRover的弹性训练方案中，当守护进程发现训练进程输出致命异常时，会将该进程的状态设置为Error并报告控制节点。控制节点触发故障排查流程，检测软件栈适配性、硬件设备可用性、数据存储路径访问权限等。
### 1.3. 故障后的任务迁移策略
检测到故障后，下一步是如何将训练任务从故障节点迁移到健康节点。
**策略一：检查点回退 + 节点替换（最经典）**
这是最成熟的方案：定期保存Checkpoint（如每10分钟保存一次模型参数、优化器状态及随机数种子）。当检测到节点故障时：
1. 隔离故障节点
2. 启动一个健康节点作为替换
3. 所有节点回退到最近的Checkpoint
4. 从Checkpoint恢复训练
这个方案的优点是实现简单、成熟可靠。缺点是**恢复时间取决于Checkpoint间隔**——如果Checkpoint每10分钟保存一次，故障时最多可能丢失10分钟的训练进度。
**策略二：TrainMover的实时迁移（Live Migration）**
TrainMover代表了故障恢复技术的前沿方向。它通过**备用机器（Standby Machines）** 实现故障时的**秒级恢复**，且**零内存开销**。
TrainMover的两项核心技术：
- **两阶段、基于增量的通信组设置（Two-phase, delta-based communication group setups）**：新节点加入时只需传输通信组的增量变化，而非重建整个通信拓扑
- **无通信的沙箱影子迭代（Communication-free sandboxed shadow iterations）**：在备用节点上预先“预热”训练状态，迁移时无需额外通信
TrainMover在实际评估中实现了**迁移期间秒级停机时间**，在周期性10分钟重平衡中维持了**99%的训练效率**。
**策略三：弹性缩容继续训练**
当没有备用节点可用时，另一种策略是**缩容继续训练**——减少节点数量，在较小的集群上继续训练。DLRover在Kubernetes上实现了这一功能：节点故障导致可用机器少于作业配置时，**自动缩容来继续训练**，待集群新增机器后再自动扩容恢复节点数量。
### 1.4. 字节跳动的ByteRobust：万卡集群的容错实践
ByteRobust是字节跳动部署在**超过20万张GPU**生产平台上的大规模GPU基础设施管理系统。它的设计理念值得深入理解：
**核心理念**：利用LLM训练过程的**独特并行特性**来实现高容量容错，而非简单地依赖Checkpoint恢复。
**关键能力**：
- **高容量容错（High-capacity fault tolerance）**：利用LLM训练的并行特性容忍故障
- **快速故障界定与定位（Prompt fault demarcation and localization）**：数据驱动的方法快速定位故障根因
- **例行化故障恢复（Routine failure recovery）**：在常规训练流程中自动检测和恢复故障
**效果**：ByteRobust在9,600张GPU上运行3个月的训练任务，实现了**97%的有效训练时间比（ETTR）**。
### 2.1. 什么是弹性训练
**弹性训练（Elastic Training）** 是指训练任务能够在**节点数量动态变化**的情况下继续运行，无需人工干预。
弹性训练与传统容错的关键区别在于：
- **传统容错**：节点故障后，替换节点、恢复Checkpoint、继续训练——节点数量不变
- **弹性训练**：节点可以**增加或减少**，训练任务自动适应新的节点数量——节点数量可变
弹性训练的价值不仅在于容错，还在于**资源效率**——可以根据训练进度动态调整资源规模，在需要时扩容加速，在不需要时缩容节省成本。
### 2.2. TorchElastic：PyTorch原生的弹性训练框架
**TorchElastic**是PyTorch在1.9版本之后默认加入的弹性训练组件，通过`torchrun`提供支持。
**核心机制：Rendezvous（会合）**
弹性训练的基础是**动态组网（Dynamic Rendezvous）** ——训练进程能够自动根据动态变化的节点数量来组网集合通信，无需固定指定各个节点的rank和world_size。
TorchElastic的工作原理：
- 节点故障被视为 **“缩容”事件**
- 调度器替换故障节点时，被视为 **“扩容”事件**
- 成员变化时，TorchElastic触发**重新动态组网**
- `--max-restarts`参数控制允许的总重启次数
**启动方式**：
```bash
torchrun --nnodes=4 --nproc-per-node=8 \
         --max-restarts=5 \
         --rdzv-id=job_001 \
         --rdzv-backend=c10d \
         --rdzv-endpoint=etcd-server:2379 \
         train.py
```
**关键参数**：
- `--max-restarts`：允许的最大重启次数
- `--rdzv-backend`：会合后端（etcd、c10d等）
- `--rdzv-endpoint`：会合服务的地址
训练脚本需要实现`save_checkpoint`和`load_checkpoint`接口，以在成员变更或恢复时持久化/还原训练进度。
### 2.3. DLRover：Kubernetes上的弹性训练实践
**DLRover**是蚂蚁集团在Kubernetes上基于TorchElastic开发的弹性训练方案。
**核心功能**：
1. **故障自动恢复**：出现故障后快速执行节点健康检测，定位故障机并隔离，然后重启Pod替换故障节点
2. **自动缩容**：节点故障导致可用机器少于作业配置时，自动缩容继续训练
3. **自动扩容**：集群新增机器后，自动扩容恢复节点数量
4. **FSDP优化**：支持根据实际卡数reshard模型参数，缩短Checkpoint保存和加载时间
**实际效果**：
- 上线前：千卡训练有效训练时间仅**32.9%**
- 上线后：有效训练时间提升至**58.9%**——**提升近一倍**
**云原生落地**：在Kubernetes上结合DLRover与TorchElastic，可实现故障机隔离与Pod替换、缩容继续训练、扩容自动加回，**将故障恢复时间从小时级降至分钟级**。
### 2.4. Lazarus：MoE模型的弹性训练
**Lazarus**是专为**MoE（混合专家）模型**设计的弹性训练系统。
**为什么MoE需要专门的弹性训练？**
MoE模型采用**专家并行（Expert Parallelism）** 策略——不同的专家分布在不同的GPU上。现有的容错方案要么缺乏弹性，要么依赖于流水线并行的容错机制——这些都无法直接应用于MoE架构。
Lazarus的核心创新：
- **自适应专家副本分配**：根据专家工作负载的不平衡动态调整专家副本
- **最优专家放置算法**：最大化故障恢复概率
- **灵活Token分发器**：故障后充分利用所有可用节点，不让任何GPU闲置
**效果**：Lazarus在频繁节点故障下比现有MoE训练系统**快5.7倍**，在真实Spot实例轨迹上**快3.4倍**。
### 3.1. 为什么需要自动扩缩容
弹性训练解决的是“节点数量变化后训练还能继续”的问题。而**自动扩缩容**解决的是“**什么时候**应该改变节点数量”的问题——根据训练需求**主动**调整资源规模。
自动扩缩容的价值体现在：
- **成本优化**：在训练低谷期缩容，减少GPU闲置
- **加速训练**：在需要加速时扩容，缩短训练周期
- **资源效率**：让GPU利用率从40%提升至85%以上
### 3.2. Kubernetes原生的扩缩容机制
在云原生环境中，Kubernetes提供了两种核心的自动扩缩容机制：
**Horizontal Pod Autoscaler（HPA）**
HPA根据资源利用率（CPU、内存）或自定义指标自动调整Pod副本数量。
在大模型训练中，可以基于**GPU利用率**或**队列长度**等自定义指标触发扩缩容。例如，某自动驾驶企业通过自定义指标扩展（Custom Metrics API），将训练任务资源利用率从58%提升至82%，**单次训练成本降低40%**。
**Cluster Autoscaler**
HPA调整的是Pod数量，而Cluster Autoscaler调整的是**节点数量**——当集群中没有足够的资源来调度新Pod时，自动增加节点；当节点长期利用率低时，自动缩减节点。
在GPU集群中，Cluster Autoscaler与云服务商（AWS、GCP、Azure）的弹性实例池配合，实现**GPU节点的按需创建和销毁**。
### 3.3. 基于队列的智能扩缩容：Kueue + KEDA
传统的HPA基于**当前资源利用率**触发扩缩容，但对于训练任务来说，更智能的方式是基于**作业队列长度**来预测资源需求。
**Kueue**是Kubernetes的作业队列管理组件，**KEDA**（Kubernetes Event-Driven Autoscaler）是事件驱动的自动扩缩容组件。
两者的协作模式：
1. Kueue管理GPU作业的排队和调度
2. KEDA监控Kueue的指标，特别是**GPU作业队列的长度**
3. 当队列积压增加时，KEDA触发扩容
4. 当队列为空时，KEDA触发缩容（甚至缩到零节点）
这种基于队列的扩缩容方案的优势在于**预测性**——不是等GPU用满了才扩容，而是根据等待的作业量提前扩容。
### 3.4. 训练感知的智能扩缩容
除了基于队列的扩缩容，更前沿的方案是基于**训练状态**的智能扩缩容：
**基于Loss收敛速度的扩缩容**
当训练进入平台期（Loss下降缓慢）时，可以适当缩容——更多的GPU并不能加速收敛；当训练处于快速下降阶段时，可以扩容加速。
**基于训练阶段的扩缩容**
预训练的不同阶段对算力的需求不同。例如：
- **预热阶段**：需要更多GPU来快速达到稳定的训练状态
- **稳定训练阶段**：可以适当缩容
- **收尾阶段**：可以进一步缩容
**弹性训练 + 自动扩缩容的闭环**
将弹性训练与自动扩缩容结合，形成一个完整的闭环：
1. 自动扩缩容系统检测到训练队列积压 → 触发扩容
2. Kubernetes启动新的GPU节点
3. TorchElastic检测到新节点加入 → 触发动态组网
4. 训练任务在新节点上继续，无需重启作业
这个闭环使得训练集群可以在**负载高峰期自动扩容、在低谷期自动缩容**，实现资源利用率和成本的最优平衡。
### 3.5. 云服务商的弹性训练方案
各大云服务商正在将弹性训练作为核心能力推出：
**Amazon SageMaker HyperPod**支持弹性训练，使ML工作负载能够**根据资源可用性自动扩缩容**，在保持训练质量的同时最大化GPU利用率、降低成本。结合Karpenter，HyperPod可以实现**即时预置**，在低需求时段缩到零节点。
**Red Hat OpenShift AI**通过Kueue和KEDA的集成，实现了GPU资源的**按需自动扩展和缩减**。
