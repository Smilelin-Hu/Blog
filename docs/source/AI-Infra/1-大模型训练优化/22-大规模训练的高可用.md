# 大规模训练的高可用（High Availability）

## 1. 节点故障的自动检测与任务迁移

### 1.1 故障的普遍性与多源性

在大规模训练集群中，故障来源极其多样，远不止「硬件坏了」这么简单。

**硬件层故障**：GPU Xid 错误、ECC（纠错码）错误、NVLink 错误；GPU 温度过高导致降频；显存硬件错误、PCIe 链路不稳定；电源、散热、主板等基础设施问题。

**软件与运行时故障**：NCCL 通信超时或死锁；CUDA 错误、驱动崩溃；训练进程 OOM；Loss Spike 导致的 NaN/Inf 值。

**管理与运维事件**：节点维护、内核升级；网络分区、交换机故障；资源抢占（尤其在云环境使用 Spot 实例时）。

这些故障有一个共同特点：**任何一个节点的故障都可能导致整个训练任务中断**。数据并行中，梯度同步的 AllReduce 要求所有节点同时参与——一个节点掉线，所有节点都在等待。

### 1.2 多层级故障检测

一个成熟的故障检测体系需要在多个层级同时工作。

**硬件级检测：主动探测与被动监控**。核心是**实时监控硬件健康状态**，比如：

- **IPMI 协议监控**：实时采集 GPU 温度、功耗、显存错误等硬件指标。
- **健康度模型**：基于历史数据训练的健康度预测模型，**提前预测**故障节点。
- **主动健康检查**：Amazon SageMaker HyperPod 的运行状况监控代理在集群所有 GPU 节点上持续运行，监视 GPU 或 NVLink 错误计数器等硬件问题。

**通信层检测：识别「慢节点」**。硬件故障往往不是突然「死亡」，而是先表现为性能下降。实践表明，**拖尾节点（Straggler）并不总是由硬件故障简单引起，而是多种复杂因素共同作用的结果**。通信层检测通过监控 NCCL 集合操作的完成时间，识别那些响应明显慢于同组其他节点的「慢节点」。

**任务层检测：应用感知的故障发现**。最接近训练任务的检测方式是在训练过程中植入健康检查逻辑。DLRover 的弹性训练方案中，守护进程发现训练进程输出致命异常时，会把该进程状态设为 Error 并报告控制节点；控制节点触发故障排查流程，检测软件栈适配性、硬件设备可用性、数据存储路径访问权限等。

### 1.3 故障后的任务迁移策略

**策略一：检查点回退 + 节点替换（最经典）**。定期保存 Checkpoint（如每 10 分钟保存模型参数、优化器状态及随机数种子）。检测到节点故障时：

1. 隔离故障节点。
2. 启动一个健康节点作为替换。
3. 所有节点回退到最近的 Checkpoint。
4. 从 Checkpoint 恢复训练。

优点是实现简单、成熟可靠；缺点是**恢复时间取决于 Checkpoint 间隔**——每 10 分钟保存一次，故障时最多丢失 10 分钟进度。

**策略二：TrainMover 的实时迁移（Live Migration）**。它通过**备用机器（Standby Machines）**实现故障时的**秒级恢复**，且**零内存开销**。两项核心技术：

- **两阶段、基于增量的通信组设置**：新节点加入时只传通信组的增量变化，而非重建整个拓扑。
- **无通信的沙箱影子迭代**：在备用节点上预先「预热」训练状态，迁移时无需额外通信。

评估中 TrainMover 实现了**迁移期间秒级停机**，在周期性的 10 分钟重平衡中维持了 **99% 的训练效率**。

**策略三：弹性缩容继续训练**。没有备用节点可用时，另一种策略是**缩容继续训练**——减少节点数量，在较小集群上继续。DLRover 在 Kubernetes 上实现了这一功能：节点故障导致可用机器少于作业配置时**自动缩容继续训练**，待集群新增机器后再自动扩容恢复节点数量。

### 1.4 万卡集群的容错实践：ByteRobust

**ByteRobust** 是字节跳动部署在**超过 20 万张 GPU** 生产平台上的大规模 GPU 基础设施管理系统。它的设计理念是：利用 LLM 训练过程的**独特并行特性**实现高容量容错，而非简单依赖 Checkpoint 恢复。关键能力包括：

- **高容量容错**：利用 LLM 训练的并行特性容忍故障。
- **快速故障界定与定位**：数据驱动的方法快速定位根因。
- **例行化故障恢复**：在常规训练流程中自动检测和恢复。

效果：在 9600 张 GPU 上运行 3 个月的训练任务，实现了 **97% 的有效训练时间比（ETTR）**。

## 2. 弹性训练（Elastic Training）的原理与实践

### 2.1 什么是弹性训练

**弹性训练**指训练任务能够在**节点数量动态变化**的情况下继续运行，无需人工干预。它与传统容错的关键区别在于：

- **传统容错**：节点故障后替换节点、恢复 Checkpoint、继续训练——节点数量不变。
- **弹性训练**：节点可以**增加或减少**，训练任务自动适应新的节点数量——节点数量可变。

弹性训练的价值不仅在容错，还在于**资源效率**——可按训练进度动态调整规模，需要时扩容加速、不需要时缩容省成本。

### 2.2 TorchElastic：PyTorch 原生的弹性训练框架

**TorchElastic** 是 PyTorch 1.9 之后默认加入的弹性训练组件，通过 `torchrun` 提供支持。基础是**动态组网（Dynamic Rendezvous）**——训练进程能根据动态变化的节点数量自动组网集合通信，无需固定指定各节点的 rank 与 world_size。

工作原理：

- 节点故障被视为**「缩容」事件**。
- 调度器替换故障节点时视为**「扩容」事件**。
- 成员变化时触发**重新动态组网**。
- `--max-restarts` 控制允许的总重启次数。

```bash
torchrun --nnodes=4 --nproc-per-node=8 \
         --max-restarts=5 \
         --rdzv-id=job_001 \
         --rdzv-backend=c10d \
         --rdzv-endpoint=etcd-server:2379 \
         train.py
```

**关键参数**：`--max-restarts`（最大重启次数）、`--rdzv-backend`（会合后端，如 etcd、c10d）、`--rdzv-endpoint`（会合服务地址）。训练脚本需实现 `save_checkpoint` 与 `load_checkpoint` 接口，以在成员变更或恢复时持久化/还原进度。

### 2.3 DLRover：Kubernetes 上的弹性训练实践

**DLRover** 是蚂蚁集团在 Kubernetes 上基于 TorchElastic 开发的弹性训练方案。核心功能：

1. **故障自动恢复**：出现故障后快速执行节点健康检测，定位故障机并隔离，然后重启 Pod 替换。
2. **自动缩容**：可用机器少于作业配置时自动缩容继续训练。
3. **自动扩容**：集群新增机器后自动扩容恢复节点数量。
4. **FSDP 优化**：支持根据实际卡数 reshard 模型参数，缩短 Checkpoint 保存与加载时间。

**实际效果**：上线前千卡训练有效训练时间仅 **32.9%**，上线后提升至 **58.9%**——提升近一倍。在 Kubernetes 上结合 DLRover 与 TorchElastic，可实现故障机隔离与 Pod 替换、缩容继续、扩容自动加回，**把故障恢复时间从小时级降到分钟级**。

### 2.4 Lazarus：MoE 模型的弹性训练

**Lazarus** 是专为 **MoE（混合专家）模型**设计的弹性训练系统。

**为什么 MoE 需要专门的弹性训练？** MoE 采用**专家并行（EP）**策略——不同专家分布在不同 GPU 上。现有容错方案要么缺乏弹性，要么依赖流水线并行的容错机制，都无法直接套用到 MoE 架构上。

Lazarus 的核心创新：

- **自适应专家副本分配**：根据专家工作负载的不平衡动态调整副本。
- **最优专家放置算法**：最大化故障恢复概率。
- **灵活 Token 分发器**：故障后充分利用所有可用节点，不让任何 GPU 闲置。

效果：在频繁节点故障下比现有 MoE 训练系统**快 5.7 倍**，在真实 Spot 实例轨迹上**快 3.4 倍**。

## 3. 训练任务的自动扩缩容

### 3.1 为什么需要自动扩缩容

弹性训练解决「节点数量变化后训练还能继续」，**自动扩缩容**解决「**什么时候**应该改变节点数量」——按训练需求**主动**调整资源规模。价值体现在：

- **成本优化**：训练低谷期缩容，减少 GPU 闲置。
- **加速训练**：需要加速时扩容，缩短周期。
- **资源效率**：让 GPU 利用率从 40% 提升至 85% 以上。

### 3.2 Kubernetes 原生的扩缩容机制

**Horizontal Pod Autoscaler（HPA）**：根据资源利用率（CPU、内存）或自定义指标自动调整 Pod 副本数。大模型训练中可以基于 **GPU 利用率**或**队列长度**等自定义指标触发。例如某自动驾驶企业通过自定义指标扩展（Custom Metrics API），把训练任务资源利用率从 58% 提升至 82%，**单次训练成本降低 40%**。

**Cluster Autoscaler**：HPA 调整的是 Pod 数量，Cluster Autoscaler 调整的是**节点数量**——集群没有足够资源调度新 Pod 时自动加节点，节点长期利用率低时自动缩减。在 GPU 集群中，它与云服务商的弹性实例池配合，实现**GPU 节点的按需创建与销毁**。

### 3.3 基于队列的智能扩缩容：Kueue + KEDA

传统 HPA 基于**当前资源利用率**触发，而训练任务更智能的方式是基于**作业队列长度**预测资源需求。

**Kueue** 是 Kubernetes 的作业队列管理组件，**KEDA**（Kubernetes Event-Driven Autoscaler）是事件驱动的自动扩缩容组件。协作模式：

1. Kueue 管理 GPU 作业的排队与调度。
2. KEDA 监控 Kueue 的指标，特别是**GPU 作业队列长度**。
3. 队列积压增加时，KEDA 触发扩容。
4. 队列为空时，KEDA 触发缩容（甚至缩到零节点）。

优势在于**预测性**——不是等 GPU 用满才扩容，而是根据等待的作业量提前扩容。

### 3.4 训练感知的智能扩缩容

**基于 Loss 收敛速度的扩缩容**：训练进入平台期（Loss 下降缓慢）时可适当缩容——更多 GPU 并不能加速收敛；处于快速下降阶段时可扩容加速。

**基于训练阶段的扩缩容**：预训练不同阶段对算力需求不同——预热阶段需要更多 GPU 快速达到稳定状态，稳定训练阶段可适当缩容，收尾阶段可进一步缩容。

**弹性训练 + 自动扩缩容的闭环**：

1. 自动扩缩容系统检测到训练队列积压 → 触发扩容。
2. Kubernetes 启动新的 GPU 节点。
3. TorchElastic 检测到新节点加入 → 触发动态组网。
4. 训练任务在新节点上继续，无需重启作业。

这个闭环使集群可以在**负载高峰期自动扩容、低谷期自动缩容**，实现资源利用率与成本的最优平衡。

### 3.5 云服务商的弹性训练方案

**Amazon SageMaker HyperPod** 支持弹性训练，使 ML 工作负载能**根据资源可用性自动扩缩容**，在保持训练质量的同时最大化 GPU 利用率、降低成本；结合 Karpenter 可实现**即时预置**，在低需求时段缩到零节点。

**Red Hat OpenShift AI** 通过 Kueue 与 KEDA 的集成，实现 GPU 资源的**按需自动扩展与缩减**。
