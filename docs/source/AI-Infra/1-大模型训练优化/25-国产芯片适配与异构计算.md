# 国产芯片适配与异构计算

## 1. 昇腾（Ascend）CANN 生态与 MindSpeed 训练套件

### 1.1 CANN：昇腾的「CUDA」

**CANN**（Compute Architecture for Neural Networks，神经网络异构计算架构）是华为昇腾 AI 处理器的异构计算架构，角色是把上层 AI 训练框架（PyTorch、TensorFlow、MindSpore）与底层昇腾芯片连接起来。通俗地说，**CANN 之于昇腾，就像 CUDA 之于 NVIDIA GPU**。

CANN 并非单点技术，而是一个完整的**软件栈**，包含驱动、运行时、编译器、算子库、编程语言（Ascend C）、图引擎与工具链等多层组件。它通过 **AscendCL**（Ascend Computing Language）对外提供 Device 管理、Context 管理、Stream 管理、内存管理、模型加载与执行等 API，开发者无需关心芯片底层细节。

截至 2025 年，CANN 已升级到 **8.0 版本**，新增 200 多个深度优化的基础算子、80 多个融合算子、100 多个 Ascend C API，典型算子开发周期从 **2 人月缩短至 1.5 人周**。

### 1.2 生态开放战略

2025 年 8 月，华为宣布 CANN 全面开源开放，核心目标是**扩大生态、降低开发者迁移成本**。目前 CANN 已支持 PyTorch、MindSpore、TensorFlow、飞桨、ONNX、计图、OpenCV 和 OpenMMLab 等框架与第三方库，应用迁移时**无需大规模修改代码，只需少量适配乃至零改动**。

但不可否认，与发展了 18 年的 CUDA 生态相比，起步六七年的 CANN 在易用性与生态丰富度上仍有差距。华为正在效仿 NVIDIA 最初推广 CUDA 的策略，向百度、科大讯飞、腾讯等头部企业派遣工程团队，帮助它们在 CANN 环境中重现和优化现有的 CUDA 训练代码。

### 1.3 MindSpeed：昇腾生态的大模型训练套件

**MindSpeed** 是昇腾生态中的**大语言模型分布式训练套件**，为目标客户提供端到端训练方案。

**MindSpeed-LLM**（原 ModelLink）的核心能力：

- **分布式预训练**：在昇腾集群上进行大规模预训练。
- **分布式指令微调**：支持 SFT 等微调任务。
- **分布式偏好对齐**：支持 RLHF/DPO 等对齐训练。
- **开发工具链**：数据预处理、权重转换、在线推理、基线评估。

MindSpeed-LLM 已内置支持**百余个业界常用稠密与 MoE 大模型**的预训练、微调和偏好对齐，DeepSeek-V3-671B、DeepSeek-R1 系列等主流模型均已支持。

**MindSpeed MM** 面向**多模态大模型**训练，兼容 FSDP、TP、PP、CP 等主流分布式策略。在 Lumina-DiMOO 多模态模型训练中，它采用 npu_fusion_attention（性能优化 5%）、RoPE 融合算子（优化 4%）、RMSNorm 融合算子（优化 7.6%）等融合算子，**总计显存占用减少 27.7%**。

### 1.4 昇腾硬件与训练优化

昇腾 AI 处理器是 **NPU（神经网络处理单元）** 架构，与 NVIDIA GPU 有本质不同，硬件与 CANN 形成软硬双引擎。

实际训练中需要针对其架构特点专门优化。例如华为团队通过算法与系统的协同优化，把 MoE 训练中的 Host-Bound 占比控制在 **2% 以下**。Hermes 系统——一套面向昇腾芯片的大模型训练性能诊断与优化系统——源于团队 3 年、面向 40 多个客户、解决 223 个性能问题、沉淀 135 个关键案例的真实经验。

## 2. 从 NVIDIA 到昇腾的代码迁移实战

### 2.1 三条迁移路径

将基于 PyTorch 的训练脚本迁移到昇腾，目前有三种方式：自动迁移（推荐）、工具迁移、手工迁移。迁移前需保证脚本能在 GPU/CPU 上正常运行。

**路径一：自动迁移（推荐）**。在训练脚本中导入两行库代码即可完成迁移：

```python
import torch_npu
from torch_npu.contrib import transfer_to_npu
```

这两行会自动把 PyTorch 的 GPU 操作映射到昇腾 NPU 上，迁移后脚本可直接运行——这是**最轻量、成本最低**的方式。

**路径二：工具迁移（PyTorch GPU2Ascend）**。该工具能把 GPU 训练脚本**自动分析并转换**为支持昇腾的脚本，适用于代码量较大、自动迁移无法完全覆盖的场景。

**路径三：手工迁移**。对包含自定义 CUDA 算子或深度依赖特定 GPU 库的代码，需要手工重写，有两条子路径：

- **硬核路**：把 CUDA 代码重写为 **Ascend C**（昇腾底层编程语言）。性能最强，但工作量巨大。
- **偷懒路**：使用 **Triton**。昇腾官方策略是「拥抱生态」——只要 Triton 代码符合规范，编译器后端就能翻译成 NPU 指令。

### 2.2 迁移中的常见「坑」

**坑 1：算子不兼容**。最核心的问题。某些在 GPU 上通过 CUDA 实现的功能，在昇腾上可能没有直接对应算子。例如把 SAM 模型迁移到昇腾时，发现 NPU 丢失了 `image_embedding` 的梯度，原因是 `torch_npu` 版本与 PyTorch 不匹配，导致 `repeat_interleave_backward_tensor` 调用失败。**解决方案**：用 Ascend 开源仓的 **msprobe** 工具做精度对比，定位缺失或异常的算子，再通过算子替换或手工实现解决。

**坑 2：混合精度训练的适配**。PyTorch 生态中 NVIDIA Apex 是混合精度训练的核心工具；迁移到昇腾后需要 **Apex for Ascend**，适配过程涉及算子映射、编译配置等环节。

**坑 3：Triton 算子的 Block Size 限制**。GPU 上 `BLOCK_SIZE` 可以设到 1024，但昇腾受 **UB（Unified Buffer）** 内存大小限制，过大的 Block 会让中间变量撑爆 UB，导致报错或性能急剧下降。**解决方案**：先把 Block Size 减小（如从 1024 降到 256 或 128），跑通后再优化。

**坑 4：原子操作的差异**。`tl.atomic_add` 在不同硬件上实现机制不同，昇腾对某些数据类型或场景的原子操作支持仍在完善。**解决方案**：尽量避免过度依赖 `atomic_add`，用 `tl.reduce` 等更通用的指令替代。

**坑 5：非连续内存访问**。Ascend C 底层**偏好连续、对齐的数据**。GPU 上鲁棒的 Mask 机制，在 NPU 上可能导致搬运指令效率低下。**解决方案**：尽量保证 `tl.load`/`tl.store` 的地址连续，复杂 Mask 逻辑尽量简化或 Padding 成对齐的 Shape。

### 2.3 迁移的最佳实践

**实践一：先跑通、再优化**。不要一开始就追求极致性能，先用自动迁移或工具迁移跑通流程、确认 loss 正常收敛，再逐步调优。

**实践二：版本配套至关重要**。昇腾软件栈高度依赖版本配套，MindSpeed-LLM 的文档明确列出了依赖的版本组合（CANN、驱动、PyTorch、torch_npu、框架套件的对应关系）。版本不匹配是导致迁移失败的**最常见原因**。

**实践三：善用精度对比工具**。迁移后 loss 不收敛时，用 **msprobe** 等工具做精度对比，逐层定位偏差来源。

**实践四：关注生态适配清单**。迁移前检查昇腾已适配的模型套件与第三方库列表，已适配的库直接使用适配版本可大幅降低成本。

## 3. 多厂商芯片混合训练的技术挑战

单厂商适配是「从 0 到 1」，多厂商混合训练是「从 1 到 N」——把不同厂商的 AI 芯片（昇腾、寒武纪、壁仞、天数智芯等）**混合部署在同一训练集群**中协同训练。

### 3.1 为什么需要混合训练

**第一，算力供给的结构性矛盾**。高端 GPU 获取受限，国产芯片产能正在爬坡，单一厂商无法满足全部算力需求。

**第二，存量资产的最大化利用**。许多企业已部署不同厂商的芯片——可能是 NVIDIA 与国产芯片并存，也可能是多家国产芯片并存，整合使用是降本增效的必然选择。

**第三，供应链安全**。过度依赖单一供应商存在风险，混合训练可实现**算力来源多样化**。

### 3.2 三大核心挑战

**挑战一：通信协议的不兼容**。不同厂商使用**不同的集合通信库**——NVIDIA 用 NCCL，昇腾用 HCCL，寒武纪用 CNCL，这些库**互不兼容**，无法直接做跨芯片的 AllReduce。**解决方案**：构建**异构通信抽象层**，主动检测、适配异构芯片，实现异构算力间的集合通信。商汤大装置的 **DeepLink** 方案是代表——实现多种国产芯片之间的协同通信与统一调度，自动进行并行策略优化与负载均衡，做到「不同芯片，同一平台」。

**挑战二：算力不均衡导致的拖尾效应**。不同厂商芯片的单卡算力、显存容量、通信带宽差异巨大；数据并行中**最慢的芯片决定整个批次速度**——木桶效应。**解决方案**：采用**异构感知的并行策略**，例如流水线并行中把计算量更大的 Stage 分配给算力更强的芯片，数据并行中按各芯片算力动态调整批次大小。

**挑战三：软件栈的碎片化**。NVIDIA 有 CUDA，昇腾有 CANN，寒武纪有 Neuware，壁仞有 BIRENSUPA；同一训练任务集成多套软件栈会带来依赖冲突、环境管理、调试复杂等工程问题。**解决方案**：容器化封装 + 统一调度层——用 Docker 把不同芯片的软件栈封装在独立容器中，通过 Kubernetes 统一管理与调度。

### 3.3 混合训练的最新进展

**异构流水线并行（Heterogeneous PP）**：研究表明，异构流水线并行场景下**英伟达与壁仞的最优混训效率达 99.77%**，英伟达、天数智芯、壁仞三种芯片的最优混训效率可达 **99.03%**——通过合理调度，异构芯片在流水线并行中的效率损失可控制在 **1% 以内**。

**异构数据并行（Heterogeneous DP）**：该场景下英伟达与壁仞的最优混训效率达 **92.88%**。数据并行的效率损失比流水线并行更大，因为对芯片间同步要求更高。

**RoCEv2 网络的异构互通**：中国电信上海公司在 RoCEv2 网络互通集群中实现了 **3 种异构算力**的混合训练，通过软件栈适配、通信协议优化、任务调度机制等方面的攻关，**训练效率达到单一芯片集群的 90%**。

### 3.4 面向未来的异构计算趋势

**趋势一：从「被动兼容」到「主动适配」**。早期异构计算以兼容为主——让不同芯片在同一框架下勉强工作；新一代系统追求**主动适配**：自动检测异构芯片的性能特征，动态选择最优并行策略与负载分配。

**趋势二：统一编程接口**。DeepLink 等方案尝试建立**统一编程接口**，让开发者用同一套代码在不同芯片上运行——理念类似 CUDA 的「write once, run anywhere」，但面向**多厂商、多架构**的异构环境。

**趋势三：十万卡级异构集群**。在算力多元化与异构化趋势下，跨生态异构算力协同能力将成为**十万卡级训练**的关键支撑。未来的 AI 训练集群不会是单一厂商的芯片集群，而是**多厂商、多架构、多世代**芯片的混合体。
