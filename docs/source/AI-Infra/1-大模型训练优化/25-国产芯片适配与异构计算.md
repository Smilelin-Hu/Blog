# 国产芯片适配与异构计算

### 1.1. CANN：昇腾的“CUDA”
**CANN**（Compute Architecture for Neural Networks，神经网络异构计算架构）是华为昇腾AI处理器的**异构计算架构**，它的角色是将上层AI训练框架（如PyTorch、TensorFlow、MindSpore）与底层昇腾芯片连接起来。通俗地说，**CANN之于昇腾，就像CUDA之于NVIDIA GPU**。

CANN通过**AscendCL**（Ascend Computing Language，昇腾计算语言）对外提供Device管理、Context管理、Stream管理、内存管理、模型加载与执行等API。开发者通过这些API，可以在昇腾软硬件平台上开发和运行AI业务，**无需关心芯片底层的细节**。
截至2025年，CANN已升级到**8.0版本**，新增了200多个深度优化的基础算子、80多个融合算子、100多个Ascend C API，典型算子开发周期从**2人月缩短至1.5人周**。
### 1.2. CANN的生态开放战略
2025年8月，华为宣布CANN全面开源开放。这一战略的核心目标是**扩大生态、降低开发者迁移成本**。
目前，CANN已支持包括**PyTorch、MindSpore、TensorFlow、飞桨、ONNX、计图、OpenCV和OpenMMLab**等深度学习框架与第三方库。开发者将应用迁移到昇腾平台时，**无需对原有代码进行大规模修改，只需做少量适配乃至“零改动”**。
但不可否认，与发展了18年的CUDA生态相比，刚起步六七年的CANN在易用性和生态丰富度上仍存在差距。华为正在效仿英伟达最初推广CUDA的策略，向百度、科大讯飞和腾讯等头部企业派遣工程团队，帮助他们在CANN环境中重现和优化现有的基于CUDA的训练代码。
### 1.3. MindSpeed：昇腾生态的大模型训练套件
**MindSpeed**是昇腾生态中的**大语言模型分布式训练套件**，旨在为昇腾芯片生态合作伙伴提供**端到端的大语言模型训练方案**。
**MindSpeed-LLM**（原ModelLink）的核心能力包括：
- **分布式预训练**：支持在昇腾集群上进行大规模预训练
- **分布式指令微调**：支持SFT等微调任务
- **分布式偏好对齐**：支持RLHF/DPO等对齐训练
- **开发工具链**：数据预处理、权重转换、在线推理、基线评估
MindSpeed-LLM已内置支持**百余个业界常用稠密和MoE大模型**的预训练、微调和偏好对齐。DeepSeek-V3-671B、DeepSeek-R1系列等主流模型均已支持。
**MindSpeed MM**是针对**多模态大模型**的训练套件。它兼容了**FSDP（全分片数据并行）、TP（张量并行）、PP（流水线并行）和CP（上下文并行）** 等主流分布式训练策略。在Lumina-DiMOO多模态模型的训练中，MindSpeed MM采用了npu_fusion_attention（性能优化5%）、RoPE融合算子（性能优化4%）、RMSNorm融合算子（性能优化7.6%）等融合算子，**总计显存占用减少27.7%**。
### 1.4. 昇腾硬件与训练优化
昇腾AI处理器是**NPU（神经网络处理单元）** 架构，与NVIDIA GPU的架构有本质不同。昇腾硬件与CANN形成软硬双引擎。
在实际训练中，昇腾平台需要针对其架构特点进行专门的优化。例如，华为团队通过算法与系统的深度协同优化，成功将MoE模型训练中的Host-Bound占比控制在**2%以下**。Hermes系统——一套面向昇腾芯片的大模型训练性能诊断与优化系统——源于团队3年、面向40多个客户、解决223个性能问题、沉淀135个关键案例的**真实战场经验**。
## 2. 从NVIDIA到昇腾的代码迁移实战
将训练代码从NVIDIA GPU迁移到昇腾NPU，是AI Infra工程师最常面对的实战任务。下文从迁移路径、常见问题和最佳实践三个维度展开。
### 2.1. 三条迁移路径
将基于PyTorch的训练脚本迁移到昇腾AI处理器上训练，目前有**三种方式**：自动迁移（推荐）、工具迁移、手工迁移。迁移前需要保证该脚本能在GPU/CPU上正常运行。
**路径一：自动迁移（推荐）**
在训练脚本中**导入自动迁移的库代码**，即可完成迁移：
```python
import torch_npu
from torch_npu.contrib import transfer_to_npu
```
这两行代码会自动将PyTorch的GPU操作映射到昇腾NPU上。迁移完成后，脚本即可在昇腾NPU环境上直接运行。这是**最轻量、成本最低**的迁移方式。
**路径二：工具迁移（PyTorch GPU2Ascend）**
PyTorch GPU2Ascend工具可以将基于GPU的训练脚本**自动分析并转换**为支持昇腾NPU环境的脚本。它适用于代码量较大、自动迁移无法完全覆盖的场景。
**路径三：手工迁移**
对于包含自定义CUDA算子或深度依赖特定GPU库的代码，需要**手工重写**。手工迁移有两种子路径：
- **硬核路**：将CUDA代码重写为**Ascend C**（昇腾的底层编程语言）。性能最强，但工作量巨大，相当于重写
- **偷懒路**：使用**Triton**。昇腾官方的策略是“拥抱生态”——只要Triton代码符合规范，昇腾的编译器后端就能将其翻译成NPU能懂的指令
### 2.2. 迁移中的常见“坑”
从CUDA迁移到昇腾并非“一键完成”，硬件架构的差异会带来一系列工程问题。
**坑1：算子不兼容**
这是最核心的问题。某些在GPU上通过CUDA算子实现的功能，在昇腾上可能没有直接对应的算子。例如，在将SAM模型迁移到昇腾平台时，发现NPU丢失了`image_embedding`的梯度，原因在于`torch_npu`版本与PyTorch不匹配，导致`repeat_interleave_backward_tensor`函数调用失败。
**解决方案**：使用Ascend开源仓的**msprobe工具**进行精度对比，定位缺失或异常的算子，然后通过算子替换或手工实现来解决。
**坑2：混合精度训练的适配**
在PyTorch生态中，NVIDIA Apex是混合精度训练（AMP）的核心工具。迁移到昇腾后，需要使用**Apex for Ascend**——将NVIDIA Apex适配到昇腾平台。适配过程涉及算子映射、编译配置等多个环节。
**坑3：Triton算子的Block Size限制**
在GPU上，Triton的`BLOCK_SIZE`可以设到1024。但在昇腾上，由于**UB（Unified Buffer）内存大小**的限制，过大的Block会导致中间变量撑爆UB，程序报错或性能急剧下降。
**解决方案**：迁移时**先减小Block Size**（如从1024降到256或128），跑通后再优化。
**坑4：原子操作的差异**
Triton的`tl.atomic_add`在不同硬件上的实现机制不同。昇腾目前对某些特定数据类型或场景的原子操作支持可能还在完善中。
**解决方案**：尽量避免过度依赖`atomic_add`，用`tl.reduce`等更通用的指令替代。
**坑5：非连续内存访问**
Ascend C底层**喜欢连续、对齐的数据**。在GPU上鲁棒的Mask机制，在NPU上可能导致生成的搬运指令效率低下。
**解决方案**：尽量保证`tl.load`和`tl.store`的地址是连续的，复杂Mask逻辑尽量简化或Padding成对齐的Shape。
### 2.3. 迁移的最佳实践
**实践一：先跑通、再优化**
不要一开始就追求极致性能。先用自动迁移或工具迁移**跑通**训练流程，确认loss正常收敛，再逐步进行性能调优。
**实践二：版本配套至关重要**

**实践三：善用精度对比工具**
当迁移后loss不收敛时，使用**msprobe**等工具进行精度对比，逐层定位精度偏差的来源。
**实践四：关注生态适配清单**
在迁移前，检查昇腾已适配的模型套件和第三方库列表。对于已适配的库，直接使用适配版本可大幅降低迁移成本。
## 3. 多厂商芯片混合训练的技术挑战
如果说单厂商适配是“从0到1”，那么多厂商混合训练就是“从1到N”——将不同厂商的AI芯片（昇腾、寒武纪、壁仞、天数智芯等）**混合部署在同一训练集群中**，协同完成大模型的训练。
### 3.1. 为什么需要混合训练
混合训练的需求源于三个现实：
**第一，算力供给的结构性矛盾。** 高端GPU的获取受限，而国产芯片的产能正在爬坡。单一厂商的芯片无法满足全部算力需求。
**第二，存量资产的最大化利用。** 许多企业已经部署了不同厂商的AI芯片——可能是NVIDIA GPU与国产芯片并存，也可能是多家国产芯片并存。将这些存量资产**整合使用**，是降本增效的必然选择。
**第三，供应链安全。** 过度依赖单一芯片供应商存在风险。混合训练可以实现**算力来源的多样化**，降低供应链风险。
### 3.2. 三大核心挑战
**挑战一：通信协议的不兼容**
不同厂商的芯片使用**不同的集合通信库**——NVIDIA使用NCCL，昇腾使用HCCL，寒武纪使用CNCL。这些通信库之间**互不兼容**，无法直接实现跨芯片的AllReduce等集合通信操作。
**解决方案**：构建一个**异构通信抽象层**，主动检测、适配异构AI芯片，实现异构算力间的集合通信。商汤大装置发布的**DeepLink**方案就是这一方向的代表——它实现了多种国产芯片之间的协同通信与统一调度，自动进行并行策略优化和负载均衡，真正做到 **“不同芯片，同一平台”**。
**挑战二：算力不均衡导致的拖尾效应**
不同厂商芯片的单卡算力、显存容量、通信带宽差异巨大。在数据并行中，**最慢的芯片决定了整个批次的速度**——这就是“木桶效应”。
**解决方案**：通过**异构感知的并行策略**来缓解。例如，在流水线并行中，将计算量更大的Stage分配给算力更强的芯片；在数据并行中，根据各芯片的算力动态调整分配给它们的批次大小。
**挑战三：软件栈的碎片化**
每一家芯片厂商都有自己的软件栈——NVIDIA有CUDA，昇腾有CANN，寒武纪有Neuware，壁仞有BIRENSUPA。在同一训练任务中集成多套软件栈，带来了依赖冲突、环境管理、调试复杂等一系列工程问题。
**解决方案**：容器化封装 + 统一调度层。通过Docker将不同芯片的软件栈封装在独立的容器中，通过Kubernetes等调度系统进行统一管理和调度。
### 3.3. 混合训练的最新进展
**异构流水线并行（Heterogeneous PP）**
研究表明，在异构流水线并行场景下，**英伟达与壁仞的最优混训效率达到99.77%**，英伟达、天数智芯、壁仞三种芯片的最优混训效率可达**99.03%**。这意味着，通过合理的调度策略，异构芯片在流水线并行中的效率损失可以控制在**1%以内**。
**异构数据并行（Heterogeneous DP）**
在异构数据并行场景下，英伟达与壁仞的最优混训效率达到**92.88%**。数据并行的效率损失比流水线并行更大，因为数据并行对芯片间的同步要求更高。
**RoCEv2网络的异构互通**
中国电信上海公司在RoCEv2网络互通集群中，实现了**3种异构算力**的混合训练。通过在软件栈适配、通信协议优化、任务调度机制等方面的持续攻关，**训练效率达到单一芯片集群的90%**。
### 3.4. 面向未来的异构计算趋势
**趋势一：从“被动兼容”到“主动适配”**
早期的异构计算以“兼容”为主——让不同芯片能在同一框架下勉强工作。新一代系统则追求 **“主动适配”** ——系统能够自动检测异构芯片的性能特征，动态选择最优的并行策略和负载分配。
**趋势二：统一编程接口**
DeepLink等方案正在尝试建立一个**统一的编程接口**，让开发者用同一套代码在不同芯片上运行。这与CUDA的“write once, run anywhere”理念类似，但面向的是**多厂商、多架构**的异构环境。
**趋势三：十万卡级异构集群**
在算力多元化和异构化趋势下，跨生态异构算力协同能力将成为**十万卡级训练**的关键支撑。未来的AI训练集群不会是单一厂商的芯片集群，而是**多厂商、多架构、多世代**芯片的混合体。
