# CPU/NPU卸载（Offloading）

### 1.1. 为什么需要卸载：显存瓶颈的最后一公里
在后文中我们学过，ZeRO-3将参数、梯度和优化器状态在GPU间分片存储，单卡显存占用降至4P/N（P为参数量，N为GPU数）。当N足够大时，模型状态已经不再是瓶颈。
但在**单卡或小规模集群**场景下（比如个人开发者只有1-2张GPU），ZeRO-3的显存节省仍然不够。以一张80GB显存的A100为例，训练一个100亿（10B）参数的模型，ZeRO-3将模型状态降至约`4 × 10B / 1 = 40GB`（单卡场景），加上激活值（约20-30GB）和CUDA上下文开销，已经接近80GB的上限。
**ZeRO-Offload**正是为解决这个问题而生的。它的核心思想是：**将优化器状态和计算从GPU卸载到主机CPU**，利用CPU内存和算力来分担GPU的压力。
### 1.2. ZeRO-Offload：优化器状态与计算的卸载
**核心设计**
ZeRO-Offload的设计围绕三个核心目标：**效率优先、高可扩展性、易用性**，同时需要平衡显存节约、通信开销和计算延迟三者的关系。
**GPU侧保留的内容**：
- FP16模型参数（用于前向和反向计算）
- 当前批次的激活值（可通过激活值重计算进一步优化）
- 少量临时计算缓冲区
**CPU侧承载的内容**：
- FP32模型参数（用于高精度参数更新）
- FP16梯度（从GPU传输而来）
- 优化器状态（如Adam的动量和方差）
**关键优化：DeepSpeedCPUAdam**
为了防止CPU成为瓶颈，ZeRO-Offload使用了DeepSpeed高度优化的CPU版Adam——**DeepSpeedCPUAdam**，它比标准的PyTorch CPU实现**快5到7倍**。
**一步延迟参数更新策略**
ZeRO-Offload还采用**一步延迟参数更新**策略：GPU在完成当前批次的计算后，不等待CPU完成参数更新，而是立即开始下一批次的计算。CPU的参数更新与GPU的下一轮计算**并行进行**，从而隐藏了部分CPU计算延迟。
**性能数据**
ZeRO-Offload使得**多达130亿参数的大型模型能够在单张GPU上高效训练**。以单张32GB显存的V100为例，原本只能训练几亿参数的模型，通过ZeRO-Offload可以**训练100亿参数的GPT-2模型**。
### 1.3. ZeRO-Infinity：从CPU到NVMe的“无限内存”
ZeRO-Offload将优化器状态卸载到CPU内存，解决了单卡训练百亿参数模型的问题。但当模型规模达到**千亿甚至万亿参数**时，CPU内存也可能不够用——毕竟一台服务器的CPU内存通常只有几百GB到1TB。
**ZeRO-Infinity**（ZeRO-∞）是DeepSpeed的下一代卸载技术，它将卸载的边界从CPU内存**进一步扩展到了NVMe SSD**。
**核心创新**
ZeRO-Infinity引入了几个关键策略：
1. **新的卸载引擎**：同时利用CPU内存和NVMe SSD作为GPU显存的扩展层
2. **以内存为中心的平铺**：在不依赖模型并行的情况下处理大规模算子
3. **以带宽为中心的分区**：减少带宽成本
4. **以重叠为中心的设计**：调度数据通信，实现计算与I/O的重叠
**工作流程**
ZeRO-Infinity结合了ZeRO-3的分区与NVMe异步I/O：
- **分区**：像ZeRO-3一样，将参数、梯度、优化器状态切分为N份（N=GPU数），每个GPU管理1/N
- **卸载（Swap Out）**：在空闲时（如前向传播后），异步将数据写入NVMe，不阻塞计算
- **拉取（Swap In）**：在需要时（如下一层前向传播前），异步读回GPU缓冲区，计算完即释放
**形象比喻**：GPU像一张小书桌（80GB显存），模型参数像100本大百科（4TB）。ZeRO-3是“分书到多张桌子”（8张桌子各12本）。ZeRO-Infinity是 **“书放仓库（NVMe），用时快递取回”** ——书桌上只放当前正在看的一本，仓库无限大。
**性能数据**
在64个DGX-2节点上，ZeRO-Infinity可访问超过**3TB/s的CPU内存带宽**和超过**1.5TB/s的NVMe带宽**。理论上，NVMe SSD的读写速度可达**3-7GB/s**，这使得“近乎无限模型大小”成为可能。
**局限性**
ZeRO-Infinity也有其局限：**它只能将激活值卸载到CPU内存，而不能进一步卸载到NVMe SSD**。这意味着对于长序列训练，CPU内存仍可能成为瓶颈。
此外，在实际训练负载中，NVMe的读写带宽往往达不到理论峰值。测试表明，libaio在参数加载与卸载阶段的SSD平均读写带宽约为**5.2GB/s和3.6GB/s**，仅达到带宽上限的75%；在读写较小张量时，带宽甚至衰减至**1.2GB/s**。
### 2.1. 卸载的代价：为什么训练会变慢
卸载的核心权衡是 **“用速度换显存”**。为什么卸载会让训练变慢？主要有三个层面的瓶颈。
**瓶颈一：PCIe带宽**
GPU与CPU之间的数据传输通过PCIe总线完成。传统的PCIe Gen5 x16提供**128 GB/s的双向带宽**。相比GPU内部显存带宽（H100为3.35 TB/s），PCIe带宽**慢了约26倍**。
这意味着，当数据需要在GPU和CPU之间频繁搬运时，PCIe总线会成为**严重的瓶颈**。训练过程中，每一轮迭代都需要将梯度从GPU传输到CPU、将更新后的参数从CPU传输回GPU——这些传输占用了大量的PCIe带宽。
**瓶颈二：CPU计算能力**
优化器更新（如Adam的参数更新）涉及大量的数学运算。虽然ZeRO-Offload使用了高度优化的DeepSpeedCPUAdam，但CPU的计算速度仍远低于GPU。当CPU成为瓶颈时，GPU不得不**空闲等待**CPU完成参数更新。
实际测试表明，在4张A100上训练Llama 2-7B时，启用ZeRO-Offload后，**每步训练时间从0.5秒膨胀到超过7秒——14倍的 slowdown**。其中GPU的空闲时间**超过60%**。
**瓶颈三：NVMe I/O延迟**
当使用ZeRO-Infinity将数据卸载到NVMe SSD时，I/O延迟进一步加剧。NVMe SSD的读写速度（3-7GB/s）比CPU内存（几十GB/s）**慢一个数量级**，比GPU显存（TB/s级别）**慢两到三个数量级**。
读写带宽的限制导致了**显著的I/O瓶颈**：GPU在完成每一层梯度计算后需要等待梯度卸载、参数与优化器状态加载等I/O操作，导致计算资源长期处于闲置状态。
### 2.2. 瓶颈的量化分析
**PCIe传输的量化**
假设一个100亿参数的模型，梯度大小为`10B × 2字节（FP16）= 20GB`。每轮迭代需要：
- 将20GB梯度从GPU传输到CPU（D2H）
- 将20GB更新后的参数从CPU传输回GPU（H2D）
- 总传输量：**40GB**
在PCIe Gen5 x16（128GB/s）下，理论传输时间为`40GB / 128GB/s = 0.3125秒`。但实际有效带宽通常只有理论值的**60-70%**，实际传输时间约为**0.45-0.52秒**。如果前向+反向计算本身只需1秒，那么卸载带来的额外开销就占了**30%以上**。
**CPU计算的量化**
Adam优化器对每个参数需要更新两个动量（m和v）。对于100亿参数，CPU需要处理：
- 20GB的梯度（FP16）
- 40GB的优化器状态（FP32的m和v，共80GB）
- 20GB的FP32参数副本
总计约**120GB的数据**需要在CPU上进行读写和计算。即使DeepSpeedCPUAdam比标准PyTorch实现快5-7倍，仍然可能成为瓶颈。
### 2.3. 优化卸载性能的前沿技术
**ZenFlow：消除GPU停顿**
2025年夏季，DeepSpeed团队发布了**ZenFlow**，一种全新的无停顿卸载引擎。
ZenFlow的核心创新是**将GPU和CPU的更新解耦**：
- 优先将**重要性高的梯度**在GPU上立即更新
- 将**低优先级的梯度**异步交给CPU处理
通过将CPU工作和PCIe传输与GPU计算**完全重叠**，ZenFlow实现了：
- **超过85%的GPU停顿减少**
- **相比ZeRO-Offload最高5倍的端到端加速**
- **相比ZeRO-Infinity最高6.3倍的加速**
ZenFlow只需修改DeepSpeed JSON配置，**无需修改代码**。
**NVLink-C2C：硬件层面的突破**
在硬件层面，NVIDIA的**NVLink-C2C**（芯片到芯片互联）技术正在改变卸载的格局。传统PCIe Gen5 x16提供128GB/s的双向带宽，而NVLink-C2C（如GB200）提供**900 GB/s的双向带宽**。
当CPU和GPU通过NVLink-C2C互联时，卸载的带宽瓶颈被**大幅缓解**，使得卸载在大规模训练中变得更加可行。
### 3.1. 一个决策框架
卸载不是“万金油”——它有显著的性能代价。在决定是否启用卸载之前，需要先回答一个问题：**我面临的到底是“显存问题”还是“速度问题”？**
**决策树**：
```text
第1步：模型能否在不启用卸载的情况下放入显存？
├── 能 → 不启用卸载（速度优先）
└── 不能 → 进入第2步

第2步：能否通过增加GPU数量（ZeRO分片）来解决？
├── 能（有更多GPU可用）→ 优先增加GPU，而非启用卸载
└── 不能（GPU数量固定）→ 进入第3步

第3步：能否通过激活值重计算进一步降低显存？
├── 能 → 先启用激活值重计算，再评估显存
└── 不能或仍不够 → 进入第4步

第4步：启用卸载
├── 优化器状态是主要瓶颈 → ZeRO-Offload（卸载到CPU内存）
├── 参数也是瓶颈 → ZeRO-Infinity（卸载到NVMe）
└── 对速度有更高要求 → 考虑ZenFlow（无停顿卸载）
```
### 3.2. 什么时候应该使用卸载
**场景一：单卡训练超大模型**
如果只有**1-2张GPU**，但需要训练或微调**数十亿到百亿参数**的模型，卸载几乎是**唯一的选择**。ZeRO-Offload使得单张32GB显存的V100可以训练100亿参数的模型。
**场景二：显存刚好差一点**
如果模型在启用ZeRO-3和激活值重计算后，显存占用仍然**略高于**单卡显存（比如差10-20GB），那么启用卸载可能是最经济的选择——不需要额外购买GPU，只需要牺牲一些训练速度。
**场景三：长序列训练**
对于**长上下文**（如128K token）的训练，激活值的显存占用会急剧增加。此时即使模型参数不大，显存也可能爆掉。将部分激活值卸载到CPU内存，可以**有效缓解显存压力**。
**场景四：成本敏感的场景**
在云环境中，GPU实例的价格远高于CPU实例。如果通过卸载可以用**更少的GPU**完成训练任务，即使训练时间延长，**总成本可能更低**。
### 3.3. 什么时候不应该使用卸载
**场景一：训练速度是首要目标**
如果目标是**最快的训练速度**（比如在学术研究中追求SOTA），卸载带来的性能损失可能不可接受。在这种情况下，应该优先考虑增加GPU数量或使用更高显存的GPU。
**场景二：多卡大规模集群**
在**数百张GPU**的大规模集群中，卸载通常不是最优解。因为：
- 多卡场景下，ZeRO-3的分片已经将显存需求降到了很低的水平
- 卸载引入的PCIe传输会在大规模集群中造成**严重的通信拥塞**
- 此时**通信优化**（第8-10课）比卸载更重要
**场景三：CPU内存不足**
ZeRO-Offload需要**大量的CPU内存**来存储优化器状态和梯度。如果服务器CPU内存不足（比如只有64GB），启用卸载可能导致**CPU内存溢出（OOM）**。
**场景四：NVMe速度不够**
ZeRO-Infinity依赖高速NVMe SSD。如果使用普通SATA SSD（读写速度仅500MB/s），卸载的I/O延迟会**严重拖慢训练**，甚至比不训练更糟。
### 3.4. 卸载配置实战
**ZeRO-Offload配置示例**：
```json
{
    "zero_optimization": {
        "stage": 2,
        "offload_optimizer": {
            "device": "cpu",
            "pin_memory": true
        },
        "offload_param": {
            "device": "cpu",
            "pin_memory": true
        }
    },
    "fp16": {
        "enabled": true
    },
    "activation_checkpointing": {
        "partition_activations": true,
        "cpu_checkpointing": true
    }
}
```
**关键参数解读**：
- `offload_optimizer.device`：优化器状态卸载目标（"cpu"或"nvme"）
- `offload_param.device`：参数卸载目标（ZeRO-3下可用）
- `pin_memory`：使用锁页内存，加速CPU-GPU数据传输
- `cpu_checkpointing`：将激活值检查点也卸载到CPU，进一步节省显存
**ZeRO-Infinity配置示例**（卸载到NVMe）：
```json
{
    "zero_optimization": {
        "stage": 3,
        "offload_optimizer": {
            "device": "nvme",
            "nvme_path": "/local_nvme"
        },
        "offload_param": {
            "device": "nvme",
            "nvme_path": "/local_nvme"
        },
        "stage3_prefetch_bucket_size": 5e8,
        "stage3_param_persistence_threshold": 1e6
    }
}
```
**调优建议**：
1. **优先使用CPU卸载，而非NVMe卸载**：CPU内存比NVMe快10-100倍，尽量先用CPU内存
2. **启用pin_memory**：锁页内存可显著加速CPU-GPU数据传输
3. **配合激活值重计算使用**：将激活值也卸载到CPU，可进一步节省显存
4. **注意PCIe带宽上限**：如果PCIe带宽成为瓶颈，考虑使用NVLink-C2C的硬件
