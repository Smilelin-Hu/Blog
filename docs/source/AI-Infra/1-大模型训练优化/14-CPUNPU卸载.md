# CPU/NPU 卸载（Offloading）

## 1. ZeRO-Offload 与 ZeRO-Infinity 的原理

### 1.1 为什么需要卸载：显存瓶颈的最后一公里

ZeRO-3 把参数、梯度和优化器状态在 GPU 间分片存储，单卡显存占用降至 $16\Phi/N$（$\Phi$ 为参数量，$N$ 为 GPU 数）。当 $N$ 足够大时，模型状态已经不再是瓶颈。

但在**单卡或小规模集群**场景下（比如只有 1–2 张 GPU），ZeRO-3 的显存节省仍然不够。以一张 80 GB 显存的 A100 为例，训练一个 100 亿（10B）参数的模型，ZeRO-3 在单卡场景下模型状态仍需约 160 GB（按 $16\Phi$ 计），加上激活值（约 20–30 GB）和 CUDA 上下文开销，早已超出 80 GB 上限。

**ZeRO-Offload** 正是为解决这个问题而生的。它的核心思想是：**将优化器状态和计算从 GPU 卸载到主机 CPU**，利用 CPU 内存和算力来分担 GPU 的压力。

### 1.2 ZeRO-Offload：优化器状态与计算的卸载

**核心设计**：ZeRO-Offload 的设计围绕三个核心目标——**效率优先、高可扩展性、易用性**，同时需要平衡显存节约、通信开销和计算延迟三者的关系。

**GPU 侧保留的内容**：

- FP16 模型参数（用于前向和反向计算）。
- 当前批次的激活值（可通过激活值重计算进一步优化）。
- 少量临时计算缓冲区。

**CPU 侧承载的内容**：

- FP32 模型参数（用于高精度参数更新）。
- FP16 梯度（从 GPU 传输而来）。
- 优化器状态（如 Adam 的动量和方差）。

**关键优化：DeepSpeedCPUAdam**。为防止 CPU 成为瓶颈，ZeRO-Offload 使用了 DeepSpeed 高度优化的 CPU 版 Adam——**DeepSpeedCPUAdam**，它比标准的 PyTorch CPU 实现**快 5 到 7 倍**。

**一步延迟参数更新策略**：GPU 在完成当前批次的计算后，不等待 CPU 完成参数更新，而是立即开始下一批次的计算。CPU 的参数更新与 GPU 的下一轮计算**并行进行**，从而隐藏了部分 CPU 计算延迟。

**性能数据**：ZeRO-Offload 使得**多达 130 亿参数的大型模型能够在单张 GPU 上高效训练**。以单张 32 GB 显存的 V100 为例，原本只能训练几亿参数的模型，通过 ZeRO-Offload 可以**训练 100 亿参数的 GPT-2 模型**。

### 1.3 ZeRO-Infinity：从 CPU 到 NVMe 的「无限内存」

ZeRO-Offload 将优化器状态卸载到 CPU 内存，解决了单卡训练百亿参数模型的问题。但当模型规模达到**千亿甚至万亿参数**时，CPU 内存也可能不够用——一台服务器的 CPU 内存通常只有几百 GB 到 1 TB。

**ZeRO-Infinity**（ZeRO-∞）是 DeepSpeed 的下一代卸载技术，它将卸载的边界从 CPU 内存**进一步扩展到了 NVMe SSD**。

**核心创新**：

1. **新的卸载引擎**：同时利用 CPU 内存和 NVMe SSD 作为 GPU 显存的扩展层。
2. **以内存为中心的平铺**：在不依赖模型并行的情况下处理大规模算子。
3. **以带宽为中心的分区**：减少带宽成本。
4. **以重叠为中心的设计**：调度数据通信，实现计算与 I/O 的重叠。

**工作流程**：ZeRO-Infinity 结合了 ZeRO-3 的分区与 NVMe 异步 I/O：

- **分区**：像 ZeRO-3 一样，将参数、梯度、优化器状态切分为 $N$ 份（$N$ 为 GPU 数），每个 GPU 管理 $1/N$。
- **卸载（Swap Out）**：在空闲时（如前向传播后）异步将数据写入 NVMe，不阻塞计算。
- **拉取（Swap In）**：在需要时（如下一层前向传播前）异步读回 GPU 缓冲区，计算完即释放。

**形象比喻**：GPU 像一张小书桌（80 GB 显存），模型参数像 100 本大百科（4 TB）。ZeRO-3 是「分书到多张桌子」（8 张桌子各 12 本）；ZeRO-Infinity 是**「书放仓库（NVMe），用时快递取回」**——书桌上只放当前正在看的一本，仓库近乎无限大。

**性能数据**：在 64 个 DGX-2 节点上，ZeRO-Infinity 可访问超过 **3 TB/s 的 CPU 内存带宽**和超过 **1.5 TB/s 的 NVMe 带宽**。理论上 NVMe SSD 的读写速度可达 **3–7 GB/s**，这使得「近乎无限模型大小」成为可能。

**局限性**：ZeRO-Infinity 只能将激活值卸载到 CPU 内存，而不能进一步卸载到 NVMe SSD——这意味着对于长序列训练，CPU 内存仍可能成为瓶颈。此外，实际训练负载中 NVMe 的读写带宽往往达不到理论峰值：测试表明 libaio 在参数加载与卸载阶段的 SSD 平均读写带宽约为 **5.2 GB/s 和 3.6 GB/s**，仅达带宽上限的 75%；读写较小张量时带宽甚至衰减至 **1.2 GB/s**。

## 2. 卸载策略的带宽瓶颈分析

### 2.1 卸载的代价：为什么训练会变慢

卸载的核心权衡是**「用速度换显存」**。训练变慢主要有三个层面的瓶颈。

**瓶颈一：PCIe 带宽**。GPU 与 CPU 之间的数据传输通过 PCIe 总线完成。PCIe Gen5 x16 提供 **128 GB/s 的双向带宽**，相比 GPU 内部显存带宽（H100 为 3.35 TB/s）**慢了约 26 倍**。这意味着，当数据需要在 GPU 和 CPU 之间频繁搬运时，PCIe 总线会成为**严重的瓶颈**：每一轮迭代都需要将梯度从 GPU 传输到 CPU、将更新后的参数从 CPU 传回 GPU。

**瓶颈二：CPU 计算能力**。优化器更新（如 Adam 的参数更新）涉及大量数学运算。虽然用了 DeepSpeedCPUAdam，CPU 的计算速度仍远低于 GPU，当 CPU 成为瓶颈时 GPU 只能**空闲等待**。实测在 4 张 A100 上训练 Llama 2-7B，启用 ZeRO-Offload 后**每步训练时间从 0.5 秒膨胀到超过 7 秒——14 倍的 slowdown**，其中 GPU 的空闲时间**超过 60%**。

**瓶颈三：NVMe I/O 延迟**。当使用 ZeRO-Infinity 将数据卸载到 NVMe SSD 时，I/O 延迟进一步加剧：NVMe SSD 的读写速度（3–7 GB/s）比 CPU 内存（几十 GB/s）**慢一个数量级**，比 GPU 显存（TB/s 级别）**慢两到三个数量级**。GPU 在完成每一层梯度计算后需要等待卸载与加载，计算资源长期闲置。

### 2.2 瓶颈的量化分析

**PCIe 传输的量化**。假设一个 100 亿参数的模型，梯度大小为 $10\text{B} \times 2\ \text{字节（FP16）} = 20\ \text{GB}$。每轮迭代需要：

- 将 20 GB 梯度从 GPU 传输到 CPU（D2H）。
- 将 20 GB 更新后的参数从 CPU 传输回 GPU（H2D）。
- 总传输量：**40 GB**。

在 PCIe Gen5 x16（128 GB/s）下，理论传输时间为 $40 / 128 = 0.3125$ 秒。但实际有效带宽通常只有理论值的 **60%–70%**，实际传输时间约为 **0.45–0.52 秒**。如果前向 + 反向计算本身只需 1 秒，那么卸载带来的额外开销就占了 **30% 以上**。

**CPU 计算的量化**。Adam 对每个参数需要更新两个动量。对于 100 亿参数，CPU 需要处理：

- 20 GB 的梯度（FP16）。
- 40 GB 的优化器状态（FP32 的 $m$ 和 $v$）。
- 20 GB 的 FP32 参数副本。

总计约 **80 GB 的数据**需要在 CPU 上读写与计算。即使 DeepSpeedCPUAdam 比标准 PyTorch 实现快 5–7 倍，仍然可能成为瓶颈。

### 2.3 优化卸载性能的前沿技术

**ZenFlow：消除 GPU 停顿**。2025 年夏季 DeepSpeed 团队发布了 **ZenFlow**，一种无停顿卸载引擎。核心创新是**将 GPU 和 CPU 的更新解耦**：

- 优先将**重要性高的梯度**在 GPU 上立即更新。
- 将**低优先级的梯度**异步交给 CPU 处理。

通过把 CPU 工作和 PCIe 传输与 GPU 计算**完全重叠**，ZenFlow 实现了：**超过 85% 的 GPU 停顿减少**、**相比 ZeRO-Offload 最高 5 倍的端到端加速**、**相比 ZeRO-Infinity 最高 6.3 倍的加速**。它只需修改 DeepSpeed JSON 配置，**无需修改代码**。

**NVLink-C2C：硬件层面的突破**。NVIDIA 的 **NVLink-C2C**（芯片到芯片互联）技术正在改变卸载的格局：传统 PCIe Gen5 x16 提供 128 GB/s 的双向带宽，而 NVLink-C2C（如 GB200）提供 **900 GB/s 的双向带宽**。当 CPU 和 GPU 通过 NVLink-C2C 互联时，卸载的带宽瓶颈被**大幅缓解**。

## 3. 何时使用卸载：显存不足时的最优解

### 3.1 一个决策框架

卸载不是「万金油」——它有显著的性能代价。在决定是否启用卸载之前，需要先回答一个问题：**面临的是「显存问题」还是「速度问题」？**

```text
第1步：模型能否在不启用卸载的情况下放入显存？
├── 能 → 不启用卸载（速度优先）
└── 不能 → 进入第2步

第2步：能否通过增加GPU数量（ZeRO分片）来解决？
├── 能（有更多GPU可用）→ 优先增加GPU，而非启用卸载
└── 不能（GPU数量固定）→ 进入第3步

第3步：能否通过激活值重计算进一步降低显存？
├── 能 → 先启用激活值重计算，再评估显存
└── 不能或仍不够 → 进入第4步

第4步：启用卸载
├── 优化器状态是主要瓶颈 → ZeRO-Offload（卸载到CPU内存）
├── 参数也是瓶颈 → ZeRO-Infinity（卸载到NVMe）
└── 对速度有更高要求 → 考虑ZenFlow（无停顿卸载）
```

### 3.2 什么时候应该使用卸载

**场景一：单卡训练超大模型**。如果只有 **1–2 张 GPU**，但需要训练或微调**数十亿到百亿参数**的模型，卸载几乎是**唯一的选择**。ZeRO-Offload 使得单张 32 GB 显存的 V100 可以训练 100 亿参数的模型。

**场景二：显存刚好差一点**。如果模型在启用 ZeRO-3 和激活值重计算后，显存占用仍然**略高于**单卡显存（比如差 10–20 GB），那么启用卸载可能是最经济的选择——不需要额外购买 GPU，只需牺牲一些训练速度。

**场景三：长序列训练**。对于**长上下文**（如 128K token）的训练，激活值的显存占用会急剧增加。此时即使模型参数不大，显存也可能爆掉。将部分激活值卸载到 CPU 内存，可以**有效缓解显存压力**。

**场景四：成本敏感的场景**。在云环境中，GPU 实例的价格远高于 CPU 实例。如果通过卸载可以用**更少的 GPU** 完成训练任务，即使训练时间延长，**总成本可能更低**。

### 3.3 什么时候不应该使用卸载

**场景一：训练速度是首要目标**。如果目标是**最快的训练速度**，卸载带来的性能损失可能不可接受。这种情况下应优先考虑增加 GPU 数量或使用更高显存的 GPU。

**场景二：多卡大规模集群**。在**数百张 GPU** 的大规模集群中，卸载通常不是最优解，因为：多卡场景下 ZeRO-3 的分片已经把显存需求降到很低；卸载引入的 PCIe 传输会在集群中造成**严重拥塞**；此时**通信优化**比卸载更重要。

**场景三：CPU 内存不足**。ZeRO-Offload 需要**大量 CPU 内存**来存储优化器状态和梯度。如果服务器 CPU 内存不足（比如只有 64 GB），启用卸载可能导致**CPU 内存溢出（OOM）**。

**场景四：NVMe 速度不够**。ZeRO-Infinity 依赖高速 NVMe SSD。如果使用普通 SATA SSD（读写速度仅 500 MB/s），卸载的 I/O 延迟会**严重拖慢训练**。

### 3.4 卸载配置实战

**ZeRO-Offload 配置示例**：

```json
{
  "zero_optimization": {
    "stage": 2,
    "offload_optimizer": {
      "device": "cpu",
      "pin_memory": true
    },
    "offload_param": {
      "device": "cpu",
      "pin_memory": true
    }
  },
  "fp16": {
    "enabled": true
  },
  "activation_checkpointing": {
    "partition_activations": true,
    "cpu_checkpointing": true
  }
}
```

**关键参数解读**：

- `offload_optimizer.device`：优化器状态卸载目标（`cpu` 或 `nvme`）。
- `offload_param.device`：参数卸载目标（ZeRO-3 下可用）。
- `pin_memory`：使用锁页内存，加速 CPU-GPU 数据传输。
- `cpu_checkpointing`：将激活值检查点也卸载到 CPU，进一步节省显存。

**ZeRO-Infinity 配置示例**（卸载到 NVMe）：

```json
{
  "zero_optimization": {
    "stage": 3,
    "offload_optimizer": {
      "device": "nvme",
      "nvme_path": "/local_nvme"
    },
    "offload_param": {
      "device": "nvme",
      "nvme_path": "/local_nvme"
    },
    "stage3_prefetch_bucket_size": 5e8,
    "stage3_param_persistence_threshold": 1e6
  }
}
```

**调优建议**：

1. **优先使用 CPU 卸载，而非 NVMe 卸载**：CPU 内存比 NVMe 快 10–100 倍，尽量先用 CPU 内存。
2. **启用 `pin_memory`**：锁页内存可显著加速 CPU-GPU 数据传输。
3. **配合激活值重计算使用**：将激活值也卸载到 CPU，可进一步节省显存。
4. **注意 PCIe 带宽上限**：如果 PCIe 带宽成为瓶颈，考虑使用 NVLink-C2C 的硬件。
