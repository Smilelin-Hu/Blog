# 混合并行（Hybrid Parallelism）

## 1. 3D 并行：数据并行 + 张量并行 + 流水线并行的组合策略

### 1.1 为什么要 3D 并行

在大模型训练中，面临三重压力：

1. **显存压力**：GPT-3 175B 在混合精度下，仅模型参数、梯度和优化器状态就需要约 **2.8 TB** 显存（$16\Phi$ 字节），远超单卡 H100 的 80 GB。
2. **算力压力**：训练 GPT-3 需要约 3640 PF-days 的计算量，单卡 A100 需要 130 天以上。
3. **通信压力**：随着 GPU 数量增加，梯度同步的通信量线性攀升。

单一策略无法同时解决这三个问题。3D 并行的本质是：**用 TP 解决「单层太大」的问题，用 PP 解决「层数太多」的问题，用 DP 解决「训练太慢」的问题**。

### 1.2 组合逻辑：从 GPU 到「超级工厂」

理解 3D 并行最好的方式，是把它想象成一个**三层嵌套的组织结构**。

**第一层：张量并行（TP）——「车间小组」**。假设有 4 台服务器、每台 8 张 GPU，总共 32 张卡。首先将每 **4 张卡**捆绑成一个「TP 小组」：

- 这 4 张卡利用 **NVLink 高速互联**，共同计算同一个 Transformer 层。
- 权重矩阵被切分成 4 份，每张卡负责一部分。
- 每层计算结束时，通过 **All-Reduce** 拼装结果。
- 对外表现：这 4 张卡仿佛「合体」成了一张拥有超大显存和算力的「超级显卡」。

通过 TP，32 张独立的显卡转化为 **8 个 TP 小组**（每组 4 卡）。

**第二层：流水线并行（PP）——「接力流水线」**。8 个 TP 小组算力很强，但显存仍然有限，无法一次性装下完整的 80 层模型。于是将 80 层模型切分为 **4 个阶段（Stage）**，每个阶段 20 层，分别放在 4 个 TP 小组上：

![PP 层：80 层模型切为 4 个阶段接力](https://raw.gitcode.com/weixin_42917352/image-host/raw/main/images/aiinfra_y1_l06_01.png)

通过 PP，解决了「模型太深、装不下」的问题。

**第三层：数据并行（DP）——「多条产线并行」**。4 个 PP Stage，每个 Stage 由 1 个 TP 小组（4 卡）负责，总共用了 16 张卡。剩下的 16 张卡组成**另一条完全相同的流水线**（DP 副本），两条流水线同时处理不同的数据批次，梯度通过 AllReduce 同步。

最终，32 张卡的 3D 并行拓扑为：**TP=4，PP=4，DP=2**。

![3D 并行拓扑：TP=4、PP=4、DP=2](https://raw.gitcode.com/weixin_42917352/image-host/blobs/357af0c9a1ce3bf72712f22526909a5dc911a597/images/aiinfra_y1_l06_02.png)

校验：$\mathrm{TP} \times \mathrm{PP} \times \mathrm{DP} = 4 \times 4 \times 2 = 32$。画拓扑时容易把 DP 写成 4，那与「剩 16 卡 → DP=2」矛盾，以乘法校验为准。

### 1.3 通信层次与拓扑感知

3D 并行的一个关键设计原则是**拓扑感知映射**——将通信最密集的维度放在物理上最靠近的位置。三种并行策略的通信密集程度不同，部署原则相应为：

1. **TP 组优先放在同一节点内**：TP 通信最密集，必须利用 NVLink 的高带宽（900 GB/s），否则性能会急剧下降。
2. **PP 可以跨节点**：PP 通信量小，跨节点部署影响不大。
3. **DP 也可以跨节点**：DP 的梯度同步可以容忍一定的网络延迟。

这解释了为什么在实际部署中，**TP 通常不超过 8**（因为单机最多 8 卡），而 PP 和 DP 可以扩展到成百上千张卡。

### 1.4 显存与通信收益

3D 并行的核心价值在于**显存和通信的双重优化**。

**显存方面**：

- PP 将模型按层切分，每个设备只存部分层 → 参数显存线性降低。
- TP 将单层权重切分，每个设备只存部分权重 → 单层显存进一步降低。
- 两者组合，使得**千亿参数模型的训练成为可能**。

**通信方面**：

- 通过 PP 和 TP，**每个 DP 组内的模型规模变小了**，梯度的大小也相应减小。
- 数据并行通信的梯度大小**线性减少**，总通信量比纯 DP 大幅降低。
- 每个 DP 组在**部分本地 Worker 之间独立且并行地执行通信**，有效带宽被放大。

**硬件门槛**：完整的 3D 并行至少需要 **8 张 GPU**（TP≥2、PP≥2、DP≥2）。实际生产中，3D 并行通常部署在**数十到数千张 GPU** 的集群上。

## 2. 并行策略的选型指南：不同规模模型的最优配置

在实际工作中经常需要回答一个问题：**给定一个模型和一批硬件，应该怎么配置 TP、PP 和 DP？** 没有放之四海而皆准的答案，但有一些经过实践检验的**经验法则**。

### 2.1 选型的核心原则

**原则一：TP 优先解决「单层放不下」的问题**。TP 的作用是**横向扩展**——让多张卡共同计算一个超大层。但 TP 的通信开销最大，因此：

- **只有当单层参数超过单卡显存时，才启用 TP**。
- TP 大小通常**不超过单机 GPU 数量**（一般为 2、4、8）。
- 在单机 8 卡 H100 上，常见的 TP 配置为 4 或 8。

**原则二：PP 解决「整体放不下」的问题**。PP 的作用是**纵向切分**——将模型按层切分到多个设备上。PP 的通信开销较小，但存在气泡问题：

- **当模型总参数超过单卡显存时，启用 PP**。
- PP 大小通常为 4–16，取决于模型层数和集群规模。
- PP 越大，气泡越多（气泡率 ≈ $(\mathrm{PP}-1)/$ 微批次数量），需要增加微批次来稀释。

**原则三：DP 解决「训练不够快」的问题**。DP 的作用是**水平扩展**——用更多数据副本并行训练。DP 的通信开销随卡数线性增长：

- **在 TP 和 PP 确定后，剩余的 GPU 都用于 DP**。
- $\mathrm{DP} = \text{总 GPU 数} / (\mathrm{TP} \times \mathrm{PP})$。
- DP 越大，每个迭代处理的样本越多，吞吐量越高。

**原则四：总 GPU 数 = TP × PP × DP**。这是 3D 并行的基本约束。给定总 GPU 数和 TP、PP，DP 也就确定了。

### 2.2 不同规模模型的推荐配置

**小规模模型（< 10B 参数，如 GPT-2、BERT-large）**

- **硬件**：1–8 张 GPU。
- **推荐配置**：DP only（TP=1，PP=1，DP=GPU 数）。
- **理由**：模型单卡放得下，不需要 TP 和 PP 增加通信开销。

**中等规模模型（10B–100B 参数，如 LLaMA-70B）**

- **硬件**：32–128 张 GPU。
- **推荐配置**：TP=4，PP=4，DP=2–8。
- **理由**：单层可能放不下（需要 TP），整体也放不下（需要 PP），剩余卡做 DP 提升吞吐。

**大规模模型（100B–1T 参数，如 GPT-3、GPT-4）**

- **硬件**：256–2048 张 GPU。
- **推荐配置**：TP=8，PP=8–16，DP=4–32。
- **理由**：TP 开到单机上限（8 卡），PP 跨节点切分层数，DP 大规模扩展吞吐。

**超大规模 MoE 模型（> 1T 参数）**

- **硬件**：数千张 GPU。
- **推荐配置**：TP=4–8，PP=8–16，DP=32–128，另加**专家并行（EP）**。
- **理由**：MoE 模型的专家网络需要额外的 EP 维度。

### 2.3 一个实战选型流程

拿到一个训练任务时，可以按以下步骤确定并行配置。

**第 1 步：计算模型的基础显存需求**

```text
显存需求 ≈ 16 × 参数量（FP16 混合精度 + Adam）
```

例如 70B 模型 ≈ $16 \times 70 \times 10^9$ ≈ 1.12 TB。

**第 2 步：确定 TP 大小**

- 如果**单层参数**（如 Attention 的 QKV 权重）> 单卡显存 → 启用 TP。
- TP 大小 = $\min($单机 GPU 数, 单层参数 / 单卡可用显存向上取整$)$。
- 通常 TP ∈ {2, 4, 8}。

**第 3 步：确定 PP 大小**

- 如果**总模型参数** > 单卡显存 × TP 的显存节省 → 启用 PP。
- PP 大小 = $\lceil$总显存需求 / (单卡显存 × TP 节省系数)$\rceil$。
- 通常 PP ∈ {4, 8, 16}。

**第 4 步：确定 DP 大小**

- $\mathrm{DP} = \text{总 GPU 数} / (\mathrm{TP} \times \mathrm{PP})$。
- 如果 DP < 1 → 硬件不足，需要减少 TP 或 PP。
- 如果 DP 太大（> 64）→ 通信开销可能过大，考虑增加 TP 或 PP。

**第 5 步：验证与调优**

- 用 profiler 测量实际训练速度。
- 如果通信占比过高 → 减小 TP 或增加 DP。
- 如果气泡占比过高 → 增加微批次数量。
- 如果 GPU 利用率低 → 检查数据加载或调整 batch size。

### 2.4 选型中的常见误区

**误区一：TP 越大越好**。TP 增加虽然降低了显存，但**通信开销也急剧增加**。在跨节点场景下，TP>8 会导致严重的通信瓶颈。一般建议 **TP 不超过 8**。

**误区二：PP 越大越好**。PP 增加会引入更多**流水线气泡**。虽然可以通过增加微批次来稀释，但微批次太多又会增加显存压力。一般建议 **PP 不超过 16**。

**误区三：DP 越多越好**。DP 增加虽然提升了吞吐，但**梯度同步的通信量也线性增加**。当 DP>64 时，通信可能成为主要瓶颈。

## 3. Megatron-LM 的并行架构解析

### 3.1 概述

**Megatron-LM** 是 NVIDIA 开源的大规模语言模型训练框架，旨在将 Transformer 模型扩展到数十亿到万亿参数规模。它是目前工业界**最成熟、最广泛使用**的大模型训练框架之一，与 DeepSpeed 并称为大模型训练的两大支柱。

Megatron-LM 的核心优势体现在三个方面：

1. **混合并行架构**：支持 DP、TP、PP 的灵活组合，可根据硬件资源动态调整。
2. **通信优化设计**：通过重叠计算与通信、梯度压缩等技术，将通信开销占比从 30%+ 降低至 15% 以下。
3. **显存高效利用**：采用激活检查点与动态批处理策略，单卡显存利用率提升 40% 以上。

### 3.2 核心设计理念：层内模型并行

Megatron-LM 最核心的设计理念是 **「层内模型并行」（Intra-layer Model Parallelism）**——将 Transformer 每一层内部的计算拆分到多个 GPU 上并行执行。

这种设计的关键在于**最小化通信**：

- 不依赖特殊编译器或定制框架。
- 仅在现有 PyTorch 的自动求导图中**插入少量 NCCL 通信操作**。
- 每个 Transformer 块的前向和反向**只需各两次 AllReduce**。

### 3.3 张量并行的实现：与前一篇的对应关系

MLP 层的切分方式是第一层全连接**按列拆分**、GeLU 各卡独立计算、第二层全连接**按行拆分**、输出做一次 **AllReduce**；Attention 层的切分方式是 Q/K/V 投影**按注意力头拆分**、注意力输出投影**按行划分**、同样在输出处 **AllReduce**。这与前一篇《模型并行》中的切分策略完全一致，此处不再重复推导。

精妙之处在于：**各 GPU 无需在非线性激活前频繁同步，只需在层输出时进行少量 AllReduce**，大幅减少了跨设备通信开销。

### 3.4 流水线并行的实现：1F1B 调度

Megatron-LM 实现了 **1F1B（One Forward One Backward）** 调度策略：

- 将输入数据切分为**微批次（Micro-batch）**。
- 采用 **「前向 1 批—反向 1 批」** 的交错执行模式。
- 硬件利用率从传统流水线的 **60% 提升至 85%+**。

在 PP 实现中，每个微批次完成前向传播后**立即**将激活值传递给下一个 Stage，当前设备**立即**开始处理下一个微批次。反向传播也以类似方式沿流水线反向传递。

### 3.5 数据并行的实现：分层梯度聚合

在数据并行维度，Megatron-LM 采用**分层梯度聚合策略**：

- **局部聚合**：同一节点内 GPU 通过 **NVLink** 高速互联完成梯度同步。
- **全局聚合**：跨节点梯度通过 **RDMA 网络**进行 AllReduce。

这种分层设计使得带宽利用率较传统方案提升 **3 倍**。

### 3.6 3D 并行的统一调度：PTD-P

Megatron-LM 将三种并行策略统一在 **PTD-P**（Pipeline-Tensor-Data Parallelism）框架下：

- **P（Pipeline）**：流水线并行维度。
- **T（Tensor）**：张量并行维度。
- **D（Data）**：数据并行维度。

在 PTD-P 框架下，可以独立配置 TP、PP 和 DP 的大小。Megatron-LM 会自动：

1. 根据 TP 大小，将每个 Transformer 层内的权重切分到 TP 组内的 GPU 上。
2. 根据 PP 大小，将模型层切分到不同的 PP Stage 上。
3. 根据 DP 大小，复制整个流水线到多个 DP 副本上。

### 3.7 Megatron-LM 与 DeepSpeed 的分工

在实际工程中，Megatron-LM 经常与 **DeepSpeed** 配合使用或互为补充。前者强在 TP/PP 的模型切分与通信重叠，后者强在 ZeRO 的显存分片与卸载；在大厂实践中两者经常**结合使用**——用 Megatron-LM 的 TP/PP 切分模型，用 DeepSpeed 的 ZeRO 进一步优化显存。

## 4. 量化补充：设备坐标与万亿级组合变化

组合多种并行时先给每张卡标坐标，再对每个算子写出输入、权重、输出分片与通信卡组：DP2×PP2×TP4 占 $2\times2\times4=16$ 张卡；同一 TP4 组内启用 SP 卡数不变，不再乘一个 SP4。TP 与 PP 组合还要写清阶段间传的是完整向量还是分片：两卡阶段各持完整 8 KiB 隐藏向量分别交给下一阶段对应卡，阶段间共发 16 KiB；传分片则由下一阶段按需拼合。

专家并行也可与专家内部 TP 组合，且有一种省 dispatch 的布局：TP2×EP4 八卡，四个专家组都对同一请求执行注意力、各存一份 KV，注意力算完后各组本地就有完整专家输入，不必跨组 dispatch，结果两步归约汇合（组内两卡相加、再四组同编号卡相加）。代价是重复：每卡权重约 64.8 GB、八卡 518.6 GB 比每参数一份的 470.2 GB 多 48.4 GB，8K 上下文每卡 KV 752 MiB 是实际的 4 倍，注意力重复执行四遍。通信账：FP32 归约单 token 完整向量 16 KiB，每层注意力组内、专家组内、跨组三次汇合，每卡发 $16+16+24=56$ KiB，8192 token prefill 每卡 448 MiB——**省 dispatch 是用存储与重复计算换的，要逐项算过再选**。

批内复用与负载要一起看：64 token 各选 8 专家共 512 次分派，均匀覆盖 128 专家读 4.5 GiB、集中 8 专家只读 288 MiB（16 倍），但集中时若 8 个热点同在一组，该组计算量是均匀时 4 倍、其余三组等待；把热点分散到四组则读取维持 288 MiB、四组各 128 次。均匀随机路由的活跃专家期望 $\mathbb E[E_{\mathrm{active}}]=E[1-(1-k/E)^m]$，$E=128,k=8,m=8$ 约 52 个、读约 1.8 GiB；decode 小矩阵受读取限制、prefill 大矩阵受最重组计算限制（skew 随 EP 规模的量化见主题二 28 篇第 11 节）。

模型继续增大时先重查总容量再定组合：Qwen3-235B BF16 约 470 GB、V4-Flash 约 568 GB，一台 HGX H100 640 GB 已所剩无几；V4-Pro 1.6T 即使半字节也约 800 GB、Kimi K3 2.8T 约 1.4 TB，超单机总容量——增 EP 组数把专家摊到更多卡、增专家内 TP 减小每卡矩阵、增 PP 阶段减少每阶段层数。计算图也改通信量：K3 路由专家在 3584 维潜空间工作（主干 7168 维），**先投影再发送 BF16 向量从 14 KiB 降到 7 KiB**，投影放发送前还是接收后决定跨卡传输维度。权重增多决定至少动用多少资源，计算图不同决定这些资源如何连接。
