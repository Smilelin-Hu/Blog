# 训练可观测性体系建设

## 1. 训练指标监控：Loss、Learning Rate、梯度范数

训练指标是模型健康的「体温计」，直接反映模型在学习过程中的状态变化，是判断训练是否正常的第一依据。

### 1.1 损失函数（Loss）：最直接的「健康信号」

Loss 是训练监控中最基础、最直观的指标，直接反映模型在当前数据上的拟合程度。

**监控维度**：一个完整的 Loss 监控体系需要同时关注三个维度——**绝对值**（是否在合理量级）、**趋势**（下降斜率是否符合预期）、**波动**（异常尖峰与抖动）。只看其中任一维度都会漏掉问题。

**训练 Loss vs. 验证 Loss**：同时监控训练与验证 Loss 是发现过拟合的关键手段。如果训练 Loss 持续下降但验证 Loss 上升，提示模型正在**过拟合**，需要及时调整正则化策略或提前终止训练。

**异常波动的应对**：当 Loss 突然飙升，按以下顺序排查：检查 GPU 内存使用情况 → 验证当前数据批次质量 → 确认学习率设置 → 考虑是否从检查点重启。

### 1.2 梯度范数（Gradient Norm）：训练稳定性的「预警雷达」

梯度范数衡量模型参数在每一步训练中的变化幅度。

**监控价值**：

- **梯度爆炸预警**：梯度范数**突然增大 10 倍以上**，提示可能发生梯度爆炸；若不干预，可能导致 Loss Spike 甚至训练崩溃。
- **梯度消失检测**：梯度范数**持续接近 0**，提示梯度消失，参数几乎不更新，需要调整学习率或优化器配置。
- **数据质量指示**：梯度范数与 Loss 同步跳变，说明该阶段学习不平稳，可能源于数据质量较差。

**实践建议**：设置梯度范数的动态阈值告警。固定阈值容易误报，因为不同训练阶段、不同模型规模下范数的正常范围差异很大。ZClip 这类方法通过**动态跟踪梯度范数的均值与标准差**实现自适应异常检测。

### 1.3 学习率（Learning Rate）：训练的「油门踏板」

学习率调度策略直接影响收敛速度与稳定性，监控实际值可判断当前是否处于预期调度轨迹上。

**监控要点**：

- **实际学习率 vs. 调度目标**：确认优化器实际使用的学习率与调度器计划一致。
- **预热阶段**：检查是否按计划从 0 逐步上升到目标值。
- **衰减阶段**：确认衰减时机与幅度符合预期。

**进阶指标：Spectral Alignment（谱对齐）**。传统标量指标（Loss、梯度范数）只能在灾难性退化**发生后**检测到问题。2025 年的研究提出 **Spectral Alignment（SA）**——通过监控层输入与权重矩阵主奇异向量之间的分布对齐程度，在 Loss 爆炸**之前**提供更早、更清晰的预警，代表训练监控从「事后发现」向「事前预警」演进。

### 1.4 采集频率：实时性的硬约束

大模型训练单步迭代时间常达 100 ms 到 1 秒。如果监控数据采集延迟超过 10 秒，问题发现就会严重滞后。**最佳实践**是训练指标与迭代同步采集——**每完成 1 步采集 1 次**，延迟控制在 100 ms 以内。通用监控工具（如每 5 分钟采集一次）的延迟远高于此需求，无法满足实时干预。

## 2. 资源监控：GPU 利用率、显存、网络带宽

训练指标回答「模型学得怎么样」，资源监控回答「硬件用得怎么样」，两者缺一不可。

### 2.1 GPU 利用率：算力是否被充分利用

GPU 利用率反映计算单元在单位时间内的活跃程度。

**问题诊断**：

- **利用率 > 90%**：计算密集，GPU 全力工作——理想状态。
- **利用率长期 < 70%**：存在瓶颈，需要排查。常见原因有三类：
  - **数据加载慢**（GPU 等数据）→ 优化 DataLoader。
  - **通信开销大**（GPU 等 AllReduce）→ 优化并行策略。
  - **算子效率低**（大量小 kernel）→ 算子融合。

**一个真实案例**：某百亿参数模型训练中，GPU 利用率长期低于 50%，但 Loss 下降正常。如果监控只看 Loss，就会漏掉「算力浪费」，导致 7 天训练周期多消耗 10 万元算力成本。

### 2.2 显存监控：容量与带宽的双重关注

**容量维度**：

- **显存占用（GB）**：接近上限时需警惕 OOM 风险。
- **显存碎片化**：总显存有剩余，但没有足够大的连续内存块。

**带宽维度**：显存带宽利用率。如果计算单元在等待数据从 HBM 搬运，即使显存占用不高，训练也可能被带宽限制。

在大规模训练中，显存带宽往往比算力更早成为瓶颈。GPU 利用率 95% 但显存带宽打满，说明训练是**访存密集型**的，优化方向应是减少全局内存访问（如算子融合、FlashAttention）。

### 2.3 网络带宽：分布式训练的「血脉」

集群规模扩展到数百甚至数千张 GPU 时，网络带宽往往成为主要瓶颈。**监控指标**包括：集合通信带宽（AllReduce、AllGather 的实测带宽）、通信持续时间（每次集合操作的实际耗时）、网络延迟（跨节点端到端延迟）。

**NCCL Inspector：通信可观测性的专用工具**。NVIDIA 的 **NCCL Inspector** 提供针对分布式训练通信的深度可观测能力，可回答：

- 不同并行域（Tensor Parallel 与 Data Parallel）中的集合操作性能如何？
- 网络拥塞是否导致了集合操作性能下降？
- 整体计算性能下降是否由网络性能下降引起？

它通过 NCCL 2.23 引入的插件接口实现**始终开启的低开销性能追踪**，可在生产环境持续启用；会定期记录通信器中每个 Rank 的集合带宽与持续时间，作业结束后生成结构化 JSON 输出用于分析可视化。

**RDMA 网络监控**：使用 InfiniBand 或 RoCE 的集群还需监控 RDMA 网络的细粒度性能，百舸等平台提供**最高 10 ms 精度**的 RDMA 网络监控能力。

### 2.4 监控系统的技术实现

一个生产级资源监控系统通常组合使用：GPU 侧 `DCGM`/`nvidia-smi` 采集利用率与显存、`NVLink`/`PCIe` 计数器；网络侧 `NCCL Inspector` 与 RDMA 计数器；软件侧 CUDA/PyTorch Profiler 与 `eBPF`。这套方案覆盖**从硬件（GPU、网络）到软件（CUDA、Python、PyTorch）的全栈监控**。

## 3. 使用 TensorBoard、W&B、MLflow 进行可视化

有了指标与资源数据，下一步是让它们「可见」。可视化把海量数值转化为直观图表，极大提升问题发现与诊断效率。

### 3.1 TensorBoard：开源生态的「标准配置」

TensorBoard 是 TensorFlow 生态中的经典可视化工具，目前已广泛用于 PyTorch 等框架的训练监控。

**核心功能**：标量仪表盘（Loss、Accuracy、Learning Rate 曲线）、直方图（权重、梯度、激活值分布）、图可视化（计算图结构）、嵌入投影（高维向量降维）、超参数对比。

**与 PyTorch 的集成**：通过 `torch.utils.tensorboard` 无缝集成。

```python
from torch.utils.tensorboard import SummaryWriter

writer = SummaryWriter("runs/experiment_001")
for step, batch in enumerate(train_loader):
    loss = train_step(batch)
    writer.add_scalar("Loss/train", loss, step)
    writer.add_scalar("LR", optimizer.param_groups[0]["lr"], step)
    if step % 100 == 0:
        writer.add_histogram("Gradients/layer1", model.layer1.weight.grad, step)
```

**适用场景**：个人开发者或小团队的实验跟踪、需要快速可视化训练过程的场景。免费、开源、与 PyTorch 原生集成；但在**大规模实验管理、团队协作、模型版本管理**方面能力较弱。

### 3.2 Weights & Biases（W&B）：工业级实验管理平台

W&B 是目前 AI 工业界**最流行的实验跟踪与可视化平台**，被领先的 AI 实验室广泛采用。

**核心优势**：

- **云端协作**：实验数据自动同步到云端，团队可实时查看与对比。
- **丰富的可视化**：除标量曲线外，还支持图像、音频、视频、3D 点云。
- **超参数搜索**：内置 Sweep 支持自动化调参。
- **模型版本管理**：通过 Artifacts 管理数据集与模型版本。
- **与训练框架深度集成**：PyTorch、TensorFlow、Hugging Face 均无缝对接。

NVIDIA 的模型定制训练任务也支持把指标通过 API Key 发送到 W&B 项目可视化。

```python
    wandb.log({
        "loss": loss,
        "learning_rate": optimizer.param_groups[0]["lr"],
        "grad_norm": grad_norm,
        "gpu_util": gpu_utilization,
    }, step=step)
```

**适用场景**：团队协作、大规模实验管理、需要长期追踪与对比实验的场景。生产级大模型训练中 W&B 几乎是标配；需注意其核心服务是**商业产品**，免费层级之外的部分需要付费。

### 3.3 MLflow：开源的全生命周期管理平台

MLflow 是 Databricks 开源的 MLOps 平台，覆盖从实验跟踪到模型部署的完整流程。**核心组件**：

- **MLflow Tracking**：记录参数、指标、代码版本与模型产物。
- **MLflow Projects**：打包可复现的 ML 代码。
- **MLflow Models**：标准化模型格式，支持多种部署工具。
- **MLflow Model Registry**：集中化模型生命周期管理。

**自动记录（Autolog）**：只需调用 `mlflow.autolog()`，框架会自动记录相关指标、参数与模型信息；对 PyTorch、TensorFlow、XGBoost 等主流框架都有原生支持。

```python
        loss = train_step(batch)
        mlflow.log_metric("loss", loss, step=step)

    mlflow.pytorch.log_model(model, "model")
```

**适用场景**：需要开源方案、完整 MLOps 生命周期管理、对数据隐私有严格要求的场景。MLflow 3.0 增强了 GenAI 场景支持，提供模型、运行、追踪与评估指标之间的完整血缘关系；AWS 等云平台已提供全托管服务。

### 3.4 三类工具的选型对比

| 工具 | 部署 | 协作 | MLOps 覆盖 | 成本 |
|---|---|---|---|---|
| TensorBoard | 本地 | 弱 | 仅可视化 | 免费 |
| W&B | SaaS/私有化 | 强 | 实验管理 + 制品 | 商业（有免费层） |
| MLflow | 自托管/云托管 | 中 | 全生命周期 | 开源免费 |

**选型建议**：

- **个人/小团队快速实验** → **TensorBoard**（免费、轻量、即开即用）。
- **工业级大模型训练团队** → **W&B**（协作、可视化、生态完整）。
- **需要完整 MLOps 生命周期的企业** → **MLflow**（开源、自托管、全链路）。
- **混合方案**：许多团队用 **TensorBoard 本地快速查看** + **W&B/MLflow 长期实验管理**。

### 3.5 可观测性的未来：从仪表盘到智能分析

传统可观测性依赖人工看仪表盘、手动设告警阈值。大模型训练的复杂性使这种模式越来越难以为继。发展趋势包括：

1. **智能告警**：不再用固定阈值，而是基于历史数据动态判断异常。
2. **根因分析**：自动关联指标异常与系统事件，快速定位源头。
3. **零侵扰可观测性**：基于 eBPF 等技术，在不修改代码的前提下实现全栈可观测。
4. **模型感知的 SLI**：不仅监控 GPU 利用率，更监控「模型质量」相关的指标。
