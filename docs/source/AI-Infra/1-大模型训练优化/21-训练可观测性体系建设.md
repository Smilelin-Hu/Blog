# 训练可观测性体系建设

## 1. 训练指标监控：Loss、Learning Rate、梯度范数
训练指标是模型健康的“体温计”。它们直接反映模型在学习过程中的状态变化，是判断训练是否正常进行的首要依据。
### 1.1. 损失函数（Loss）：最直接的“健康信号”
Loss是训练监控中最基础、最直观的指标。它直接反映了模型在当前数据上的拟合程度。

**训练Loss vs. 验证Loss**：
同时监控训练Loss和验证Loss是发现过拟合的关键手段。如果训练Loss持续下降但验证Loss上升，提示模型正在**过拟合**。这种情况下，需要及时调整正则化策略或提前终止训练。
**异常波动的应对**：
当Loss出现突然飙升时，需要立即按以下顺序排查：
1. 检查GPU内存使用情况
2. 验证当前数据批次的质量是否异常
3. 确认学习率设置是否合理
4. 考虑是否需要从检查点重启训练
### 1.2. 梯度范数（Gradient Norm）：训练稳定性的“预警雷达”
梯度范数是监控训练稳定性的关键指标。它衡量了模型参数在每一步训练中的变化幅度。
**监控价值**：
- **梯度爆炸预警**：如果梯度范数**突然增大10倍以上**，提示可能发生梯度爆炸。若不及时干预，可能导致Loss Spike甚至训练崩溃。
- **梯度消失检测**：如果梯度范数**持续接近0**，提示梯度消失，模型参数几乎不更新。此时需要调整学习率或优化器配置。
- **数据质量指示**：如果梯度范数与Loss同步发生跳变，说明模型在此阶段的学习不平稳，可能是因为训练数据质量较差。
**实践建议**：
设置梯度范数的动态阈值告警。传统固定阈值方法容易产生误报，因为梯度范数在不同训练阶段、不同模型规模下的正常范围差异很大。ZClip等先进方法通过**动态跟踪梯度范数的统计特性（均值和标准差）**，实现了自适应的异常检测。
### 1.3. 学习率（Learning Rate）：训练的“油门踏板”
学习率调度策略直接影响训练的收敛速度和稳定性。监控学习率的实际值，可以帮助判断当前训练阶段是否处于预期的调度轨迹上。
**监控要点**：
- **实际学习率 vs. 调度目标**：确认优化器实际使用的学习率与调度器计划一致
- **预热阶段**：检查学习率是否按计划从0逐渐上升到目标值
- **衰减阶段**：确认衰减时机和幅度符合预期
**进阶指标：Spectral Alignment（谱对齐）**
传统的标量指标（Loss、梯度范数）只能在灾难性退化**发生后**检测到问题。2025年的研究发现了一种新的监控指标——**Spectral Alignment（SA）**，它通过监控层输入与权重矩阵主奇异向量之间的分布对齐程度，能够在Loss爆炸发生**之前**提供更早、更清晰的预警。这代表了训练监控从“事后发现”向“事前预警”演进的前沿方向。
### 1.4. 采集频率：实时性的硬约束
大模型训练单步迭代时间常达100ms到1秒。如果监控数据采集延迟超过10秒，问题发现就会严重滞后。
**最佳实践**：训练指标应与训练迭代同步采集，**每完成1步迭代采集1次**，延迟控制在100ms以内。通用监控工具（如每5分钟采集一次）的延迟远高于此需求，无法满足大模型训练的实时干预需求。
## 2. 资源监控：GPU利用率、显存、网络带宽
训练指标告诉了“模型学得怎么样”，资源监控告诉了“硬件用得怎么样”。两者缺一不可。
### 2.1. GPU利用率：算力是否被充分利用
GPU利用率是衡量训练效率最直接的资源指标。它反映了GPU计算单元在单位时间内的活跃程度。
**问题诊断**：
- **利用率 > 90%**：计算密集，GPU在全力工作——这是理想状态
- **利用率长期 < 70%**：存在瓶颈，需要排查
- 可能原因1：**数据加载慢**（GPU在等待数据）→ 优化DataLoader
- 可能原因2：**通信开销大**（GPU在等待AllReduce）→ 优化并行策略
- 可能原因3：**算子效率低**（大量小kernel）→ 算子融合
**一个真实案例**：某百亿参数模型训练中，GPU利用率长期低于50%，但Loss下降正常。如果通用监控仅关注Loss，就会遗漏“算力浪费”问题，导致7天训练周期多消耗10万元算力成本。
### 2.2. 显存监控：容量与带宽的双重关注
显存监控需要同时关注两个维度：
**容量维度**：
- **显存占用（GB）**：当前已使用的显存量。接近上限时需警惕OOM风险
- **显存碎片化**：虽然总显存有剩余，但没有足够大的连续内存块
**带宽维度**：
- **显存带宽利用率**：如果计算单元在等待数据从HBM搬运过来，即使显存占用不高，训练也可能被内存带宽限制
在大规模训练中，显存带宽往往是比算力更先达到瓶颈的资源。GPU利用率95%但显存带宽打满，说明训练是**访存密集型**的，优化方向应该是减少全局内存访问（如算子融合、FlashAttention）。
### 2.3. 网络带宽：分布式训练的“血脉”
在分布式训练中，网络通信是影响训练效率的关键因素之一。当集群规模扩展到数百甚至数千张GPU时，网络带宽往往成为主要瓶颈。
**监控指标**：
- **集合通信带宽**：AllReduce、AllGather等操作的实测带宽
- **通信持续时间**：每次集合操作的实际耗时
- **网络延迟**：跨节点通信的端到端延迟
**NCCL Inspector：通信可观测性的专用工具**
NVIDIA的**NCCL Inspector**提供了针对分布式训练通信的深度可观测能力。它可以回答以下关键问题：
- 不同并行域（Tensor Parallel vs. Data Parallel）中的集合操作性能如何？
- 网络拥塞是否导致了集合操作性能下降？
- 整体计算性能下降是否由网络性能下降引起？
NCCL Inspector通过NCCL 2.23引入的插件接口实现**始终开启的低开销性能追踪**，可在生产环境中持续启用。它会定期记录通信器中每个Rank的集合带宽和持续时间，作业结束后生成结构化的JSON输出用于分析和可视化。
**RDMA网络监控**：
对于使用InfiniBand或RoCE的集群，还需要监控RDMA网络的细粒度性能。百舸平台等方案提供了**最高10ms精度**的RDMA网络监控能力，为故障诊断和性能调优提供数据支撑。

## 3. 使用TensorBoard、W&B、MLflow进行可视化
有了监控指标和资源数据，下一步就是让它们“可见”。可视化工具将海量的数值转化为直观的图表，极大地提升了问题发现和诊断的效率。
### 3.1. TensorBoard：开源生态的“标准配置”
TensorBoard是TensorFlow生态中的经典可视化工具，目前已广泛应用于PyTorch等框架的训练监控中。
**核心功能**：
- **标量仪表盘**：展示Loss、Accuracy、Learning Rate等随时间变化的曲线
- **直方图**：展示权重、梯度、激活值的分布变化
- **图可视化**：展示模型的计算图结构
- **嵌入投影**：高维向量的降维可视化
- **超参数对比**：不同实验配置下的性能对比
**与PyTorch的集成**：
PyTorch通过`torch.utils.tensorboard`提供了与TensorBoard的无缝集成。只需在训练循环中记录指标：
```text
from torch.utils.tensorboard import SummaryWriter

writer = SummaryWriter("runs/experiment_001")
for step, batch in enumerate(train_loader):
    loss = train_step(batch)
    writer.add_scalar("Loss/train", loss, step)
    writer.add_scalar("LR", optimizer.param_groups[0]["lr"], step)
    if step % 100 == 0:
        writer.add_histogram("Gradients/layer1", model.layer1.weight.grad, step)
```
**适用场景**：TensorBoard适合**个人开发者或小团队**的实验跟踪，以及需要快速可视化训练过程的场景。它免费、开源、与PyTorch原生集成。但TensorBoard在**大规模实验管理、团队协作、模型版本管理**方面能力较弱。
### 3.2. Weights & Biases（W&B）：工业级实验管理平台
W&B是目前AI工业界**最流行的实验跟踪与可视化平台**，被领先的AI实验室广泛采用。
**核心优势**：
- **云端协作**：实验数据自动同步到云端，团队成员可以实时查看和对比实验结果
- **丰富的可视化**：除了标量曲线，还支持图像、音频、视频、3D点云等多种数据类型
- **超参数搜索**：内置的Sweep功能支持自动化的超参数调优
- **模型版本管理**：通过Artifacts管理数据集和模型的版本
- **与训练框架深度集成**：与PyTorch、TensorFlow、Hugging Face等无缝对接
**在NVIDIA平台上的集成**：NVIDIA的模型定制训练任务支持将训练指标通过API Key发送到W&B项目中进行可视化。
**快速上手**：
```text
    wandb.log({
        "loss": loss,
        "learning_rate": optimizer.param_groups[0]["lr"],
        "grad_norm": grad_norm,
        "gpu_util": gpu_utilization,
    }, step=step)
```
**适用场景**：W&B适合**团队协作、大规模实验管理、需要长期追踪和对比实验**的场景。对于生产级的大模型训练项目，W&B几乎是标配。需要注意的是，W&B的核心服务是**商业产品**，虽然提供免费层级，但大规模使用需要付费。
### 3.3. MLflow：开源的全生命周期管理平台
MLflow是Databricks开源的全生命周期MLOps平台，覆盖从实验跟踪到模型部署的完整流程。
**核心组件**：
- **MLflow Tracking**：记录参数、指标、代码版本和模型产物
- **MLflow Projects**：打包可复现的ML代码
- **MLflow Models**：标准化模型格式，支持多种部署工具
- **MLflow Model Registry**：集中化的模型生命周期管理
**自动记录（Autolog）**：
MLflow的一个特色功能是**自动记录**——只需调用`mlflow.autolog()`，框架会自动记录所有相关的指标、参数和模型信息。对于PyTorch、TensorFlow、XGBoost等主流框架都有原生支持。
**与PyTorch的集成**：
```text
        loss = train_step(batch)
        mlflow.log_metric("loss", loss, step=step)

    mlflow.pytorch.log_model(model, "model")
```
**适用场景**：MLflow适合**需要开源方案、需要完整MLOps生命周期管理、对数据隐私有严格要求**的场景。MLflow 3.0增强了GenAI场景的支持，提供了模型、运行、追踪和评估指标之间的完整血缘关系。AWS等云平台已提供全托管的MLflow服务。

### 3.5. 可观测性的未来：从仪表盘到智能分析
传统可观测性依赖人工查看仪表盘、手动设置告警阈值。但大模型训练的复杂性使得这种模式越来越难以为继。
**发展趋势**：
1. **智能告警**：不再使用固定阈值，而是基于历史数据动态判断异常
2. **根因分析**：自动关联指标异常与系统事件，快速定位问题源头
3. **零侵扰可观测性**：基于eBPF等技术，在不修改代码的情况下实现全栈可观测
4. **模型感知的SLI**：不仅监控GPU利用率，更要监控“模型质量”相关的指标
