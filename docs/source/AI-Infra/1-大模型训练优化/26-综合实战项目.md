# 综合实战项目

主题一的收尾是三个综合实战项目，难度递进：

- **项目一**：基于 DeepSpeed/Megatron 完成一个 7B 模型的分布式训练——「入门级」综合实践，目标是完整跑通一个分布式训练任务。
- **项目二**：对训练任务进行端到端的性能分析并优化至目标 MFU——「进阶级」性能调优实践，目标是用数据驱动优化。
- **项目三**：模拟千卡集群场景下的通信瓶颈分析与优化方案设计——「专家级」系统设计实践，目标是具备大规模集群的规划与优化能力。

每个项目都包含明确的目标、步骤指引与验收标准，建议按顺序完成，因为后者建立在前者基础之上。

## 1. 项目一：基于 DeepSpeed/Megatron 完成 7B 模型的分布式训练

### 1.1 项目背景

7B（70 亿）参数是目前开源大模型中最常见的规模之一——LLaMA-2-7B、Qwen-7B、DeepSeek-V2-Lite 都属于这一量级。在 2–8 张 A100/H100 上完成一个 7B 模型的分布式训练，是 AI Infra 工程师最基础、最日常的工作场景。

本项目要求从零完成 7B 模型分布式训练的全流程——从环境配置、数据准备，到 DeepSpeed/Megatron 的配置与启动，再到训练过程的监控与验证。

### 1.2 项目目标

1. 在 **2–8 张 GPU** 上完成一个 7B 模型的分布式训练（预训练或微调）。
2. 使用 **DeepSpeed ZeRO-3** 或 **Megatron-LM** 作为训练框架。
3. 训练稳定运行至少 **1000 步**，无 OOM、无 Loss Spike。
4. 达到合理的训练吞吐量（MFU > 35%）。

### 1.3 第一步：环境准备（1 天）

**硬件要求**：最低配置 2 张 A100 80GB（7B 模型）；推荐 4–8 张 A100/H100 + NVLink 互联。

**软件依赖**：

```bash
# 创建conda环境
conda create -n llm_train python=3.10 -y
conda activate llm_train

# 安装核心库（以PyTorch + DeepSpeed为例）
pip install torch==2.1.0 --index-url https://download.pytorch.org/whl/cu118
pip install transformers==4.36.0 datasets accelerate deepspeed
pip install flash-attn --no-build-isolation  # 可选，提升Attention性能
```

**框架选择**：首次接触分布式训练建议从 **DeepSpeed** 开始；已有一定基础可以挑战 **Megatron-LM**。前者配置化程度高、改代码少，后者对 TP/PP 的控制更精细。

### 1.4 第二步：数据准备（0.5 天）

**数据格式**：准备 JSON Lines 格式的训练数据，每条包含 `instruction` 与 `output` 字段：

```json
{"instruction": "解释什么是机器学习", "output": "机器学习是人工智能的一个分支..."}
{"instruction": "写一首关于秋天的诗", "output": "秋风萧瑟天气凉..."}
```

**数据加载**：

```python
from datasets import load_dataset

dataset = load_dataset("json", data_files={"train": "train.jsonl", "eval": "eval.jsonl"})
```

预训练场景需要使用大规模纯文本语料（如 The Pile、C4），并完成**预分词（Pre-tokenization）**——这是把每 epoch 的预处理时间降低 2–5 倍的关键优化。

### 1.5 第三步：DeepSpeed 配置（0.5 天）

创建 `ds_config.json`：

```json
{
  "train_batch_size": 32,
  "micro_batch_size_per_gpu": 4,
  "gradient_accumulation_steps": 1,
  "steps_per_print": 50,
  "wall_clock_breakdown": false,
  "bf16": { "enabled": true },
  "zero_optimization": {
    "stage": 3,
    "offload_optimizer": { "device": "cpu", "pin_memory": true },
    "overlap_comm": true,
    "contiguous_gradients": true,
    "stage3_prefetch_bucket_size": 5e8,
    "stage3_param_persistence_threshold": 1e6,
    "stage3_gather_16bit_weights_on_model_save": true
  },
  "optimizer": {
    "type": "AdamW",
    "params": { "lr": 2e-5, "betas": [0.9, 0.999], "eps": 1e-8, "weight_decay": 0.01 }
  },
  "scheduler": {
    "type": "WarmupLR",
    "params": { "warmup_min_lr": 0, "warmup_max_lr": 2e-5, "warmup_num_steps": 100 }
  }
}
```

**关键参数解读**：

- `stage: 3`：启用 ZeRO-3，参数、梯度、优化器状态全分片，显存占用最小化。
- `offload_optimizer.device: "cpu"`：把优化器状态卸载到 CPU，进一步节省 GPU 显存。
- `micro_batch_size_per_gpu: 4`：7B 模型建议 2–4，按显存调整。
- `overlap_comm: true`：启用通信与计算重叠。

### 1.6 第四步：训练脚本（1 天）

基于 DeepSpeed + Hugging Face Transformers 的微调脚本骨架：

```python
from transformers import TrainingArguments
from trl import SFTTrainer

training_args = TrainingArguments(
    output_dir="./output",
    per_device_train_batch_size=4,
    gradient_accumulation_steps=8,
    learning_rate=2e-5,
    num_train_epochs=3,
    logging_steps=10,
    save_steps=500,
    fp16=True,  # 或 bf16=True
    deepspeed="ds_config.json",  # 引用DeepSpeed配置文件
    report_to="tensorboard",
)

# 4. 启动训练
trainer = SFTTrainer(
    model=model,
    tokenizer=tokenizer,
    args=training_args,
    train_dataset=dataset["train"],
    max_seq_length=2048,
)
trainer.train()
```

**启动命令**：

```bash
# 单机多卡（8卡）
deepspeed --num_gpus=8 train.py --deepspeed ds_config.json

# 多机多卡（2节点 × 8卡）
deepspeed --num_gpus=8 --num_nodes=2 --master_addr=<node0_ip> train.py --deepspeed ds_config.json
```

### 1.7 第五步：Megatron-LM 配置（可选，进阶）

若选择 Megatron-LM，需要更精细的并行策略配置。

**并行度设计原则**：7B 模型在 2 节点 × 8 卡（共 16 卡）上训练，推荐配置为 `TP=2`（单层权重切到 2 卡，通信量可控）、`PP=4`（模型分 4 个 Stage）、`DP=2`（两条流水线处理不同数据）。校验：$2 \times 4 \times 2 = 16$，等于总 GPU 数。

**显存估算**（关键步骤）：7B 模型在 BF16 混合精度下——参数 7B × 2 字节 = 14 GB、梯度 14 GB、优化器状态（Adam）7B × 8 字节 = 56 GB，**总计约 84 GB**，单卡 80 GB 无法容纳，必须使用 ZeRO-3 或模型并行。按上述 TP=2/PP=4/DP=2 配置，单卡显存可降至约 **25–35 GB**（含激活值）。

**Megatron 启动命令示例**：

```bash
    --num-layers 32 \
    --hidden-size 4096 \
    --num-attention-heads 32 \
    --seq-length 2048 \
    --micro-batch-size 4 \
    --global-batch-size 64 \
    --train-iters 10000 \
    --lr 3e-4 \
    --fp16
```

### 1.8 第六步：训练监控与验证（持续）

- 用 **TensorBoard** 监控 Loss 曲线与学习率变化。
- 用 **`nvidia-smi`** 实时监控 GPU 利用率与显存占用。
- 每 500 步保存一次 Checkpoint，确保可断点续训。
- 训练完成后在验证集上评估（Perplexity、下游任务准确率等）。

### 1.9 验收标准

| 验收项 | 标准 |
|---|---|
| 分布式运行 | 2–8 卡上完成训练，进程组正常建立 |
| 稳定性 | 连续 1000 步无 OOM、无 Loss Spike |
| 效率 | MFU > 35%，吞吐量逐卡可比 |
| 可恢复性 | 从 Checkpoint 恢复后 loss 连续 |
| 交付物 | 配置文件、启动脚本、Loss 曲线与 MFU 计算过程 |

## 2. 项目二：端到端性能分析并优化至目标 MFU

### 2.1 项目背景

「训练能跑」只是第一步，「训练跑得快」才是 AI Infra 工程师的核心价值。MFU 是衡量训练效率的最核心指标。在千卡集群上，MFU 从 71% 提升到 89% 意味着**节省约 20% 的训练时间与算力成本**；在单卡或小规模集群上同样意义重大——一次 7 天的训练任务，MFU 从 30% 提升到 45%，可以**节省约 2 天与数十万元算力成本**。

本项目要求对运行中的训练任务做**端到端性能分析**，识别瓶颈并实施优化，最终把 MFU 提升到目标值。

### 2.2 项目目标

1. 用 `torch.profiler` 与 `nsys` 做**全链路性能分析**。
2. 识别训练中的**三大瓶颈**（计算、显存、通信至少各一个）。
3. 针对每个瓶颈实施**至少一项优化**。
4. 把 MFU 从基线提升**至少 10 个百分点**（如从 30% 提升到 40%+）。

### 2.3 第一步：建立基线（0.5 天）

**选择训练任务**：使用项目一训练好的 7B 模型，或选择中等规模任务（1B–7B，4–8 卡）。

**采集基线数据**：

```python
from torch.profiler import profile, record_function, ProfilerActivity

with profile(
    activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
    record_shapes=True,
    profile_memory=True,
    with_stack=True,
) as prof:
    for step in range(100):  # 采集100步的数据
        # 训练代码...
        if step == 50:
            prof.export_chrome_trace("baseline_trace.json")

# 打印详细统计
print(prof.key_averages().table(sort_by="cuda_time_total", row_limit=20))
```

**计算基线 MFU**：

$$
\mathrm{MFU} = \frac{\text{Model FLOPs per iteration}}{\text{Hardware Peak FLOPs} \times \text{Time per iteration}}
$$

- **Model FLOPs per iteration**：每步前向 + 反向的理论计算量（可用公式估算或 `ptflops` 等工具）。
- **Hardware Peak FLOPs**：GPU 理论峰值（如 A100 FP16/BF16 约 312 TFLOPS）。
- **Time per iteration**：profiler 测量的每步实际耗时。

**记录基线指标**：每步耗时、MFU、GPU 利用率、显存峰值、通信时间占比、数据加载耗时占比。

### 2.4 第二步：瓶颈识别（1 天）

**维度一：计算瓶颈**。在 profiler 输出中查找耗时最长的 CUDA kernel：

```python
# 按CUDA耗时排序
print(prof.key_averages().sort_by("cuda_time_total").table(row_limit=10))
```

判断标准：

- Top 10 主要是矩阵乘法（`aten::mm`、`aten::bmm`）→ **计算密集**，优化方向为混合精度、Tensor Core、算子融合。
- Top 10 主要是逐元素操作（`aten::add`、`aten::mul`、`aten::layer_norm`）→ **访存密集**，优化方向为算子融合、减少中间结果。

**维度二：显存瓶颈**。检查显存占用是否接近上限（>90%）：

- 显存接近上限但 GPU 利用率不高 → 可能**激活值占用过多** → 启用激活值重计算。
- 显存碎片化严重 → 调整 `PYTORCH_CUDA_ALLOC_CONF`。

**维度三：通信瓶颈**。检查通信时间占比：

```python
# 在profiler中查找NCCL kernel
print(prof.key_averages().table(sort_by="cuda_time_total", row_limit=20))
# 筛选包含"nccl"的行
```

判断标准：

- 通信时间 > 总时间的 20% → **通信瓶颈严重**，需要优化。
- 检查是否有跨节点通信导致的尾延迟（P99/P50 > 2×）。

**维度四：数据加载瓶颈**。检查 GPU 利用率波动模式：

- GPU 利用率周期性下降 → **数据加载瓶颈** → 优化 `num_workers`、`pin_memory`、`prefetch_factor`。
- 用 `ProfilerActivity.CPU` 检查数据加载耗时。

### 2.5 第三步：实施优化（2–3 天）

| 瓶颈类型 | 可选优化 |
|---|---|
| 计算密集 | 开启 BF16/FP16 混合精度；启用 FlashAttention；用 `torch.compile` 做算子融合；检查是否走到 Tensor Core 路径 |
| 显存密集 | 激活值重计算（K=2–4）；ZeRO-1/2 分片；降低 micro-batch 并提高梯度累积；合并小算子减少中间张量 |
| 通信密集 | 梯度分桶调参；`overlap_comm` 打开；拓扑感知摆放（TP 不跨节点）；层次化 AllReduce；梯度压缩 |
| 数据加载 | 提高 `num_workers` 与 `prefetch_factor`；开启 `pin_memory` + `non_blocking`；预分词；换 SSD/NVMe 或按 tar 打包 |

### 2.6 第四步：验证与迭代（1 天）

**重新采集 profiler 数据**：应用所有优化后，重新运行 profiler 采集 100 步。

**对比优化前后**：逐项比较每步耗时、MFU、显存峰值、通信占比、GPU 利用率曲线。

**迭代调优**：如果 MFU 未达目标，回到第二步重新分析瓶颈、实施新一轮优化。通常需要 2–3 轮迭代才能达到最优。

### 2.7 验收标准

| 验收项 | 标准 |
|---|---|
| 基线可信 | 基线数据可复现，MFU 计算过程可核验 |
| 瓶颈覆盖 | 计算、显存、通信三类瓶颈各至少识别一个，并有数据支撑 |
| 优化有效 | 每项优化都有前后对比数据，MFU 提升 ≥ 10 个百分点 |
| 副作用评估 | 说明优化带来的精度、稳定性或复杂度代价 |
| 交付物 | 分析报告 + 优化前后的 trace 文件 |

## 3. 项目三：千卡集群通信瓶颈分析与优化方案设计

### 3.1 项目背景

集群规模从 8 卡扩展到千卡时，通信瓶颈从「次要问题」变成「主要矛盾」。在 1024 卡集群上，如果通信优化不到位，训练效率可能从预期的 85% 骤降到 **71% 甚至更低**。

千卡集群的通信优化是**系统性工程**——涉及网络拓扑设计、NCCL 调优、并行策略配置、梯度压缩等多个层面。本项目要求在**模拟环境**中分析通信瓶颈，并设计一套完整的优化方案。

### 3.2 项目目标

1. 理解千卡集群的**网络拓扑**及其对通信性能的影响。
2. 使用 **NCCL 拓扑感知**技术优化通信路径。
3. 设计一套**层次化 AllReduce** 方案，把跨节点通信量最小化。
4. 输出一份**完整的千卡集群通信优化方案文档**。

### 3.3 第一步：理解网络拓扑（0.5 天）

一个 1024 卡集群通常采用 **Fat-Tree** 拓扑：

![1024 卡 Fat-Tree 拓扑：Server→Leaf→Spine→Core](https://raw.gitcode.com/weixin_42917352/image-host/raw/main/images/aiinfra_y1_l26_01.png)

**关键洞察**：Fat-Tree 中**同一 Leaf 下的 GPU 通信延迟最低**，跨 Spine 通信延迟显著增加。

**模拟环境搭建**（无法实际使用千卡时的三种方式）：

1. **多节点模拟**：用 4–8 台物理机（每台 8 卡）模拟千卡集群的通信模式。
2. **NCCL 测试工具**：用 `nccl-tests` 测量不同拓扑配置下的 AllReduce 性能。
3. **软件模拟**：用 NVIDIA 的 NCCL 拓扑模拟器或自写通信模拟脚本。

**测量基线**：

```bash
# 使用nccl-tests测量AllReduce性能
mpirun -np 32 ./all_reduce_perf -b 8 -e 128M -f 2 -g 1
```

记录不同消息大小下的 AllReduce 带宽（GB/s）、延迟（μs）、P50/P99 尾延迟比。

### 3.4 第二步：识别通信瓶颈（1 天）

**瓶颈一：NCCL 默认拓扑探测的问题**。NCCL 默认拓扑探测可能把 32 卡的 pipeline group 直接放到一个 spine 下，导致 AllReduce **频繁跨 spine 通信**，产生严重尾延迟。

```bash
# 导出NCCL拓扑图
export NCCL_GRAPH_DUMP_FILE=./topology.xml
# 运行训练任务，检查拓扑图
```

**瓶颈二：AllReduce 的协议头开销**。在 128 卡集群中，单次 AllReduce 的**协议头占比可达 37%**；通信数据量较小时，协议头开销成为主要瓶颈。

**瓶颈三：跨节点通信带宽不足**。千卡集群中跨节点通信依赖 InfiniBand 或 RoCE；带宽不足或配置不当会使 AllReduce 成为主要瓶颈。

### 3.5 第三步：设计优化方案（2 天）

**方案一：NCCL 拓扑感知调度**。手写 `NCCL_TOPO_FILE`，把 DP/TP/PP 三层映射到 Leaf/Spine/Superspine：

```xml
<!-- 简化示例 -->
<system version="1">
  <cpu numaid="0" affinity="0-63" arch="x86_64" vendor="GenuineIntel">
    <pci busid="0000:01:00.0" class="0x030200" vendor="0x10de" device="0x2330">
      <gpu dev="0" sm="80" rank="0"/>
    </pci>
    <!-- ... 更多GPU ... -->
  </cpu>
</system>
```

**关键原则**：**TP 组**必须放在**同一 Leaf 下**（最密集通信走最短路径）；**PP 组**尽量放在**同一 Spine 下**；**DP 组**可以跨 Spine。

**预期效果**：AllReduce 时延降到原来的 **60%**，MFU 从 71% 提升到 **82%**。

**方案二：层次化 AllReduce**。

两层方案（适合 1024 卡）：

1. **第一层（节点内）**：8 卡通过 NVLink 做 AllReduce → 每个节点得到聚合梯度。
2. **第二层（节点间）**：128 个节点的代表通过 InfiniBand 做 AllReduce → 得到全局梯度。

三层方案（适合 4096+ 卡）：

1. **第一层（节点内）**：8 卡 NVLink AllReduce。
2. **第二层（Leaf 内）**：32 个节点通过 Leaf 交换机 AllReduce。
3. **第三层（Spine 间）**：所有 Leaf 代表通过 Spine 交换机 AllReduce。

**方案三：通信与计算重叠**。在模型并行（TP/PP）中通过精细化调度实现重叠：

- **前向传播**：计算当前层的同时预取下一层参数。
- **反向传播**：计算当前层梯度的同时同步上一层梯度。

**方案四：梯度压缩**。对数据并行的梯度同步可采用：**1-bit 压缩**（通信量减少 32 倍）、**Top-K 稀疏化**（只传最重要的 5%–10%，通信量减少 90%+）、**误差补偿**（保证压缩不损害收敛性）。

### 3.6 第四步：评估优化效果（0.5 天）

逐项记录每项优化的通信量、时延、MFU 变化，并给出综合方案预期：把上述方案组合使用，预期可将千卡集群训练效率从 **71% 提升至 89% 以上**。

### 3.7 第五步：输出方案文档（1 天）

方案文档应包含以下章节：

1. **现状分析**：当前集群拓扑、通信瓶颈数据。
2. **优化目标**：明确的 MFU 目标与关键指标。
3. **优化方案**：NCCL 拓扑感知配置（含配置文件）、层次化 AllReduce 设计（含通信量计算）、通信-计算重叠策略（含调度流程图）、梯度压缩方案（含压缩率与精度影响分析）。
4. **实施计划**：分阶段实施步骤、风险与回退方案。
5. **验收标准**：可量化的验收指标。

### 3.8 验收标准
