# 综合实战项目

本篇程最后包含三个综合实战项目，难度递进：
- **项目一**：基于DeepSpeed/Megatron完成一个7B模型的分布式训练——这是“入门级”的综合实践，目标是让完整跑通一个分布式训练任务
- **项目二**：对训练任务进行端到端的性能分析并优化至目标MFU——这是“进阶级”的性能调优实践，目标是让学会用数据驱动优化
- **项目三**：模拟千卡集群场景下的通信瓶颈分析与优化方案设计——这是“专家级”的系统设计实践，目标是让具备大规模集群的规划与优化能力
每个项目都包含明确的目标、步骤指引和验收标准。建议按顺序完成，因为每个项目都建立在前一个项目的基础之上。
### 1.1. 项目背景
7B（70亿）参数是目前开源大模型中最常见的规模之一——LLaMA-2-7B、Qwen-7B、DeepSeek-V2-Lite等都属于这一量级。在2-8张A100/H100 GPU上完成一个7B模型的分布式训练，是AI Infra工程师最基础、最日常的工作场景。
本项目要求从零开始，完成一个7B模型的分布式训练全流程——从环境配置、数据准备，到DeepSpeed/Megatron的配置与启动，再到训练过程的监控与验证。
### 1.2. 项目目标
1. 在**2-8张GPU**上完成一个7B模型的分布式训练（预训练或微调）
2. 使用**DeepSpeed ZeRO-3**或**Megatron-LM**作为训练框架
3. 训练能够稳定运行至少**1000步**，无OOM、无Loss Spike
4. 达到合理的训练吞吐量（MFU > 35%）

#### 1.3.5. 第五步：Megatron-LM配置（可选，进阶）
如果选择使用Megatron-LM，需要更精细的并行策略配置。
**并行度设计原则**：
对于7B模型在2节点×8卡（共16卡）上训练，推荐配置：
- `TP=2`（张量并行）：将单层权重切分到2卡，通信量可控
- `PP=4`（流水线并行）：将模型分为4个Stage，每Stage 4层
- `DP=2`（数据并行）：2条流水线并行处理不同数据
验证：`TP × PP × DP = 2 × 4 × 2 = 16`（等于总GPU数）
**显存估算**（关键步骤）：
7B模型在BF16混合精度下：
- 模型参数：7B × 2字节 = 14GB
- 梯度：14GB
- 优化器状态（Adam）：7B × 8字节 = 56GB（ZeRO分片后分摊）
- **总计约84GB**，单卡80GB无法容纳 → 必须使用ZeRO-3或模型并行
使用上述TP=2, PP=4, DP=2的配置，单卡显存可降至约**25-35GB**（含激活值）。
**Megatron启动命令示例**：
```bash
    --num-layers 32 \
    --hidden-size 4096 \
    --num-attention-heads 32 \
    --seq-length 2048 \
    --micro-batch-size 4 \
    --global-batch-size 64 \
    --train-iters 10000 \
    --lr 3e-4 \
    --fp16
```

### 2.1. 项目背景
“训练能跑”只是第一步，“训练跑得快”才是AI Infra工程师的核心价值所在。MFU（Model FLOPs Utilization，模型算力利用率）是衡量训练效率的最核心指标。
在千卡集群上，MFU从71%提升到89%意味着**节省了约20%的训练时间和算力成本**。在单卡或小规模集群上，MFU的优化同样意义重大——一次7天的训练任务，如果MFU从30%提升到45%，可以**节省约2天的训练时间和数十万元的算力成本**。
本项目要求对一个正在运行的训练任务进行**端到端的性能分析**，识别瓶颈并实施优化，最终将MFU提升到目标值。
### 2.2. 项目目标
1. 使用`torch.profiler`和`nsys`对一个训练任务进行**全链路性能分析**
2. 识别训练中的**三大瓶颈**（计算、显存、通信至少各一个）
3. 针对每个瓶颈实施**至少一项优化**
4. 将MFU从基线提升**至少10个百分点**（如从30%提升到40%+）

#### 2.3.2. 第二步：瓶颈识别（1天）
使用profiler的数据，按以下维度逐一分析：
**维度一：计算瓶颈**
在profiler输出中，查找耗时最长的CUDA kernel：
```python
# 按CUDA耗时排序
print(prof.key_averages().sort_by("cuda_time_total").table(row_limit=10))
```
**判断标准**：
- 如果Top 10中主要是矩阵乘法（`aten::mm`、`aten::bmm`）→ **计算密集**，优化方向：混合精度、Tensor Core、算子融合
- 如果Top 10中主要是逐元素操作（`aten::add`、`aten::mul`、`aten::layer_norm`）→ **访存密集**，优化方向：算子融合、减少中间结果
**维度二：显存瓶颈**
检查显存占用是否接近上限（>90%）：
- 如果显存接近上限但GPU利用率不高 → 可能是**激活值占用过多** → 启用激活值重计算
- 如果显存碎片化严重 → 调整`PYTORCH_CUDA_ALLOC_CONF`
**维度三：通信瓶颈**
在分布式训练中，检查通信时间占比：
```python
# 在profiler中查找NCCL kernel
print(prof.key_averages().table(sort_by="cuda_time_total", row_limit=20))
# 筛选包含"nccl"的行
```
**判断标准**：
- 通信时间 > 总时间的20% → **通信瓶颈严重**，需要优化
- 检查是否有跨节点通信导致的尾延迟（P99/P50 > 2x）
**维度四：数据加载瓶颈**
检查GPU利用率的波动模式：
- 如果GPU利用率周期性下降 → **数据加载瓶颈** → 优化DataLoader的`num_workers`、`pin_memory`、`prefetch_factor`
- 使用`torch.profiler`的`ProfilerActivity.CPU`检查数据加载耗时

### 3.1. 项目背景
当集群规模从8卡扩展到千卡时，通信瓶颈从“次要问题”变成了“主要矛盾”。在一个1024卡的集群上，如果通信优化不到位，训练效率可能从预期的85%骤降到**71%甚至更低**。
千卡集群的通信优化是一个**系统性工程**——涉及网络拓扑设计、NCCL调优、并行策略配置、梯度压缩等多个层面。本项目要求在**模拟环境**中分析千卡集群的通信瓶颈，并设计一套完整的优化方案。
### 3.2. 项目目标
1. 理解千卡集群的**网络拓扑**及其对通信性能的影响
2. 使用**NCCL拓扑感知**技术优化通信路径
3. 设计一套**层次化AllReduce**方案，将跨节点通信量最小化
4. 输出一份**完整的千卡集群通信优化方案文档**
#### 3.3.1. 第一步：理解网络拓扑（0.5天）
**典型千卡集群拓扑**：
一个1024卡集群通常采用**Fat-Tree**拓扑：
```text
[GPU Server] × 128 (每台8卡)
    ↓ 接入
[Leaf Switch] × 32 (每台连接4台Server)
    ↓ 汇聚
[Spine Switch] × 8 (全互联)
    ↓ 核心
[Core Switch] (可选，用于更大规模)
```
**关键洞察**：在Fat-Tree中，**同一Leaf下的GPU通信延迟最低**，跨Spine通信延迟显著增加。
**模拟环境搭建**：
由于无法实际使用千卡集群，可以使用以下模拟方式：
1. **多节点模拟**：使用4-8台物理机（每台8卡），模拟千卡集群的通信模式
2. **NCCL测试工具**：使用`nccl-tests`测量不同拓扑配置下的AllReduce性能
3. **软件模拟**：使用NVIDIA的**NCCL拓扑模拟器**或自行编写通信模拟脚本
**测量基线**：
```bash
# 使用nccl-tests测量AllReduce性能
mpirun -np 32 ./all_reduce_perf -b 8 -e 128M -f 2 -g 1
```
记录不同消息大小下的：
- AllReduce带宽（GB/s）
- AllReduce延迟（μs）
- P50/P99尾延迟比
#### 3.3.2. 第二步：识别通信瓶颈（1天）
**瓶颈一：NCCL默认拓扑探测的问题**
NCCL默认拓扑探测可能将32卡的pipeline group直接放到一个spine下，导致AllReduce**频繁跨spine通信**，产生严重的尾延迟。
**验证方法**：
```bash
# 导出NCCL拓扑图
export NCCL_GRAPH_DUMP_FILE=./topology.xml
# 运行训练任务，检查拓扑图
```
观察拓扑图中各GPU的物理位置和通信路径。
**瓶颈二：AllReduce的协议头开销**
在128卡集群中，单次AllReduce操作的**协议头占比可达37%**。当通信数据量较小时，协议头开销成为主要瓶颈。
**瓶颈三：跨节点通信带宽不足**
千卡集群中，跨节点通信依赖InfiniBand或RoCE网络。如果网络带宽不足或配置不当，AllReduce会成为训练的主要瓶颈。
#### 3.3.3. 第三步：设计优化方案（2天）
**方案一：NCCL拓扑感知调度**
手写`NCCL_TOPO_FILE`，将DP/TP/PP三层映射到Leaf/Spine/Superspine：
```xml
<!-- 简化示例 -->
<system version="1">
  <cpu numaid="0" affinity="0-63" arch="x86_64" vendor="GenuineIntel">
    <pci busid="0000:01:00.0" class="0x030200" vendor="0x10de" device="0x2330">
      <gpu dev="0" sm="80" rank="0"/>
    </pci>
    <!-- ... 更多GPU ... -->
  </cpu>
</system>
```
**关键原则**：
- **TP组**必须放在**同一Leaf下**（最密集通信走最短路径）
- **PP组**尽量放在**同一Spine下**
- **DP组**可以跨Spine
**预期效果**：AllReduce时延降到原来的**60%**，MFU从71%提升到**82%**。
**方案二：层次化AllReduce**
设计两层或三层的层次化AllReduce方案：
**两层方案**（适合1024卡）：
1. **第一层（节点内）**：8卡通过NVLink做AllReduce → 每个节点得到聚合梯度
2. **第二层（节点间）**：128个节点的代表通过InfiniBand做AllReduce → 得到全局梯度
**三层方案**（适合4096+卡）：
1. **第一层（节点内）**：8卡NVLink AllReduce
2. **第二层（Leaf内）**：32个节点通过Leaf交换机AllReduce
3. **第三层（Spine间）**：所有Leaf代表通过Spine交换机AllReduce
**方案三：通信与计算重叠**
在模型并行（TP/PP）中，通过精细化调度实现通信与计算的重叠：
- **前向传播**：在计算当前层的同时，预取下一层的参数
- **反向传播**：在计算当前层梯度的同时，同步上一层的梯度
**方案四：梯度压缩**
对于数据并行的梯度同步，可以采用：
- **1-bit压缩**：将梯度压缩到1-bit，通信量减少32倍
- **Top-K稀疏化**：只传输最重要的5-10%梯度，通信量减少90%+
- **误差补偿**：保证压缩不损害模型收敛性
