# 训练硬件基础与性能指标

上一课我们认识到，大模型训练的核心矛盾是算力需求的指数级增长与硬件供给的相对滞后。要理解这个矛盾、进而找到优化的突破口，我们首先需要深入理解 **“算力”从何而来**。
本篇将带走进大模型训练的硬件世界。我们将以NVIDIA GPU为线索，从微观的SM（流式多处理器）和Tensor Core开始，逐层理解GPU的计算与存储体系；然后建立衡量硬件性能的关键指标——FLOPS、显存带宽、MFU/HFU；最后把视野从单卡扩展到集群，理解NVLink、InfiniBand和RoCE这三种互联技术如何将成千上万张GPU连接成一个整体。
学完本篇，将能够：
- 读懂一张GPU的“性能参数表”，理解每个数字背后的硬件含义
- 用MFU和HFU准确评估一个训练任务的硬件利用效率
- 理解从单卡到集群的互联层次，为后续学习分布式通信打下基础
### 1.1. CPU vs. GPU：两种设计哲学
在深入GPU架构之前，我们先理解一个根本问题：**为什么AI训练要用GPU，而不是CPU？**
CPU和GPU的设计目标截然不同。CPU擅长处理**复杂的逻辑控制和串行计算**——操作系统调度、数据库查询、分支预测密集的程序，这些都是CPU的强项。因此CPU的芯片面积中，**缓存单元约占50%，控制单元约占25%，运算单元仅占25%**。
GPU则走了另一条路。它的设计目标是**大规模并行计算**——同时处理成千上万个相似的计算任务。因此GPU将**约90%的芯片面积给了运算单元**，缓存和控制单元各仅占5%。这种“放弃复杂性、追求吞吐量”的设计，使得GPU在处理矩阵乘法、卷积等AI核心运算时，效率远超CPU。
在实际的大模型训练中，CPU和GPU是**协同工作**的：CPU负责数据加载、任务调度和指令下发；GPU负责执行大规模并行计算。理解这个分工，就理解了为什么训练优化既要关注GPU的计算效率，也要关注CPU与GPU之间的数据传输效率。
### 1.2. GPU的层级化架构：从GPC到SM
以NVIDIA H100（Hopper架构）为例，GPU内部是一个高度层级化的结构：
**顶层：GPC（图形处理集群）** —— H100包含**8个GPC**，每个GPC是一个独立的大型计算单元。
**中层：TPC（纹理处理集群）** —— 每个GPC包含9个TPC，H100共计**72个TPC**。
**核心层：SM（流式多处理器）** —— 每个TPC包含2个SM，H100完整版共计**144个SM**。从A100到H100，SM数量从108个增加到132个（完整版为144个），增幅约22%。
SM是GPU执行计算的最小独立单元，理解SM的内部结构是理解GPU性能的关键。
### 1.3. SM内部：计算单元与缓存系统
每个SM内部包含四个模块，主要包括以下计算单元：
**CUDA Core（通用计算核心）**：负责执行标量计算（如加法、乘法）。H100的每个SM包含**128个FP32 CUDA Core**和**64个FP64 CUDA Core**。以144个SM计算，H100完整版共有**18,432个FP32 CUDA Core**。
**Tensor Core（张量计算核心）**：这是专门为矩阵乘法设计的**专用硬件单元**。H100搭载**第四代Tensor Core**，每个SM包含4个，全卡共**576个**。Tensor Core支持**FP8、FP16、BF16、TF32**等多种精度格式的混合精度计算，其吞吐量是A100的2倍。
除了计算单元，SM还配备了多级缓存：
- **寄存器文件**：每个SM有65,536个32位寄存器，总大小256KB
- **L1数据缓存/共享内存**：SM内部的高速缓存，供同一SM内的线程共享
- **L2缓存**：所有SM共享，H100的L2缓存达到**60MB**
### 1.4. 显存层次：从HBM3到五级缓存
GPU的存储体系是一个从“快而小”到“慢而大”的金字塔结构：
**第一层：寄存器** —— 最快，但容量最小（每SM仅256KB），由编译器分配。
**第二层：L0/L1缓存与共享内存** —— 程序员可显式控制的片上高速缓存，延迟极低。
**第三层：L2缓存** —— 60MB（H100），所有SM共享，用于缓存频繁访问的全局内存数据。
**第四层：HBM3高带宽显存** —— H100 SXM版本配备**80GB HBM3显存**，带宽高达**3.35 TB/s**。相比之下，PCIe版本的H100使用HBM2e，带宽仅为2TB/s。
**第五层：CPU主内存（系统内存）** —— 通过PCIe 5.0连接，带宽仅128GB/s，远低于HBM3。
理解这个五级存储层次，对于后续学习**显存优化**（第11-14课）至关重要——优化的本质，就是在不同存储层级之间寻找最优的数据放置与移动策略。

## 2. 关键性能指标：FLOPS、显存带宽、算力利用率（MFU/HFU）
了解了硬件架构之后，我们需要建立一套**衡量硬件性能的语言**。大厂AI Infra团队的日常工作中，最常讨论的就是下面这些指标。
### 2.1. FLOPS：硬件的“理论极速”
**FLOPS**（Floating Point Operations Per Second，每秒浮点运算次数）是衡量GPU计算能力的最基本指标。
不同精度下的FLOPS含义不同：
- **FP32（单精度）**：传统科学计算的标准精度，H100约120 TFLOPS
- **TF32**：专为AI设计的精度格式，H100约500 TFLOPS
- **FP16/BF16**：混合精度训练的主流格式，H100约1,000-1,979 TFLOPS
- **FP8**：最新的低精度格式，H100高达3,958 TFLOPS
需要注意的是，这些数字是**理论峰值**——即硬件在理想条件下能够达到的最高算力。实际训练中，几乎不可能达到100%的理论峰值，这就引出了下一个关键指标。
### 2.2. 显存带宽：往往比算力更先成为瓶颈
在大模型训练中，**显存带宽**（Memory Bandwidth）的重要性不亚于算力本身。
为什么？因为大模型训练是**访存密集型**（Memory-Bound）和**计算密集型**（Compute-Bound）的混合体。Transformer架构中的很多操作（如LayerNorm、Softmax、Dropout）对算力要求不高，但需要频繁读写显存。当显存带宽不足时，GPU的计算单元就会“饿死”——等待数据从显存中搬运过来。
H100 SXM的显存带宽高达**3.35 TB/s**，是A100（约1.55 TB/s）的两倍多。即便如此，在大规模训练中，显存带宽仍然常常是主要瓶颈。
一个粗略的判断标准：**如果GPU利用率（通过**`nvidia-smi`**查看）低于90%，但显存带宽利用率接近100%，说明训练是访存密集型的，优化方向应该是减少显存访问**（如算子融合、减少中间结果的落盘）。
### 2.3. MFU与HFU：衡量“算得有多好”的核心指标
FLOPS衡量的是“硬件能算多快”，但实际训练中，硬件往往没有被充分利用。**MFU**（Model FLOPs Utilization，模型算力利用率）和**HFU**（Hardware FLOPs Utilization，硬件算力利用率）就是用来量化“硬件被用得好不好”的两个关键指标。
**MFU（模型算力利用率）** 的定义是：
MFU = 模型理论需要的计算量（预估FLOPS）/ 硬件理论FLOPS
这里的“预估FLOPS”指的是模型前向+反向传播所必需的计算量，**不包括**因优化技术（如激活值重计算）而额外引入的计算量。MFU衡量的是**算法层面的效率**——模型本身对硬件的利用程度。
**HFU（硬件算力利用率）** 的定义是：
HFU = 实际发生的所有计算量（实际FLOPS）/ 硬件理论FLOPS
HFU**包括**了所有实际发生的计算，包括激活值重计算等优化技术引入的额外计算。因此，**HFU ≥ MFU**恒成立。
**两者关系的实际意义**：
- 如果**MFU和HFU都很低**（如都低于30%），说明硬件本身没有被充分利用，问题可能在数据加载、通信瓶颈或并行策略不当
- 如果**MFU低但HFU高**（如MFU=40%，HFU=70%），说明大量的算力被“浪费”在了重计算等额外操作上——这是激活值重计算等显存优化技术的代价
- 如果**MFU和HFU都很高**（如都接近50-60%），说明训练任务对硬件的利用已经相当充分
那么，什么样的MFU/HFU算“好”？这取决于模型规模和硬件配置。对于千亿参数级别的模型在千卡集群上训练，**MFU达到40-50%已经是非常优秀的水平**；而小规模模型在单卡上训练，MFU可以达到60-70%甚至更高。
在大厂AI Infra团队中，**提升MFU是训练优化工程师的核心KPI之一**。每一次并行策略调整、每一次通信优化、每一次算子融合，最终都要体现在MFU的提升上。
## 3. 从单卡到集群：NVLink、InfiniBand、RoCE
单张H100固然强大（3.35 TB/s显存带宽、近2000 TFLOPS算力），但对于千亿、万亿参数的大模型来说，**单卡远远不够**。我们需要将成百上千张GPU连接成一个整体——这就涉及到三种关键的互联技术。
理解这三种技术，需要先建立一个**层次化的认知**：
- **NVLink**：GPU与GPU之间的**芯片级直连**，用于服务器内部的多卡互联
- **InfiniBand（IB）**：服务器与服务器之间的**专用高速网络**，为高性能计算（HPC）而设计
- **RoCE（RDMA over Converged Ethernet）**：**基于以太网的RDMA方案**，成本更低、兼容性更好
### 3.1. NVLink：GPU的“专属高速公路”
NVLink是NVIDIA开发的**专有高速互联技术**，用于GPU之间的直接通信。
**核心特点**：
- **极高的带宽**：第四代NVLink（H100）提供**900 GB/s**的双向带宽，是PCIe 5.0（128 GB/s）的**7倍以上**
- **极低的延迟**：延迟在微秒（µs）级别
- **直接内存访问**：GPU可以直接读写另一个GPU的显存，无需CPU介入
- **范围受限**：NVLink是**芯片级互联**，通常只能在同一服务器内部（同一物理节点）使用
在实际的8卡H100服务器（如NVIDIA DGX H100）中，8张GPU通过NVSwitch实现**全互联拓扑**，总带宽可达**7.2 TB/s**。
**适用范围**：NVLink主要用于**张量并行（TP）** 和**专家并行（EP）** 等需要**高频、大量数据交换**的并行策略。在这些场景中，GPU之间每轮迭代都要交换大量数据，NVLink的高带宽至关重要。
### 3.2. InfiniBand：集群的“专用骨干网”
当我们需要连接**不同服务器**（不同节点）上的GPU时，NVLink就不够用了——它无法跨越物理节点的边界。这时就需要**集群级互联**。
InfiniBand（简称IB）是专门为高性能计算和AI集群设计的**专用网络技术**。
**核心特点**：
- **高带宽**：最新的NDR规格支持**400 Gbps**（即50 GB/s）的单端口带宽
- **超低延迟**：延迟在**1微秒（µs）** 级别
- **无损传输**：通过基于信用的流量控制（Credit-based Flow Control），实现**零丢包**传输
- **RDMA支持**：支持**远程直接内存访问（RDMA）**，数据可以直接从一个GPU的内存传输到另一个GPU的内存，**完全绕过CPU**，大幅降低延迟和CPU开销
- **GPUDirect支持**：与NVIDIA的GPUDirect技术配合，实现GPU到GPU的直接通信
**适用范围**：InfiniBand是构建**大规模AI集群**的首选方案。NVIDIA的DGX SuperPOD等参考架构都基于InfiniBand构建。
**局限性**：InfiniBand的生态系统相对封闭，配置和维护较为复杂，且成本较高。
### 3.3. RoCE：以太网上的RDMA
**RoCE**（RDMA over Converged Ethernet）是在**标准以太网**上实现RDMA的技术方案。
**核心特点**：
- **兼容性好**：基于标准以太网，可以利用现有的网络基础设施
- **成本较低**：以太网交换机的价格通常低于InfiniBand交换机
- **带宽与IB相当**：在相同速率下，RoCE和IB的带宽相同
- **延迟略高**：RoCE的延迟通常在**2微秒（µs）** 左右，比IB略高
- **需要无损网络配置**：RoCE需要依赖**PFC（优先级流控制）** 和**ECN（显式拥塞通知）** 等机制来实现无损传输
**适用范围**：RoCE适合**成本敏感**或**需要与现有以太网基础设施兼容**的AI集群部署场景。

**实际部署中的层次结构**：
在一个典型的AI训练集群中，这三种技术是**分层协作**的：
1. **服务器内部**：8张GPU通过**NVLink + NVSwitch**全互联，实现7.2 TB/s的超高带宽
2. **服务器之间**：通过**InfiniBand或RoCE**网络连接，实现跨节点的GPU通信
3. **整个集群**：通过InfiniBand/RoCE构建的胖树（Fat-Tree）或混合拓扑，连接成百上千个节点
**选型建议**：
- **追求极致性能**：选择InfiniBand，它是目前AI训练集群的**黄金标准**
- **平衡性能与成本**：选择RoCE，在性能损失可控的前提下大幅降低网络成本
- **单机多卡场景**：NVLink是**必须的**，没有NVLink的多卡训练性能会严重下降
