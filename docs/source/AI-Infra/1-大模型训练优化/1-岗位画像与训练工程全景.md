# 岗位画像与训练工程全景

AI Infra 不是单一岗位，而是一组围绕模型训练、推理与平台建设的工程能力：它连接算法、框架、加速器、网络、存储、集群调度与可观测系统，把「论文里的模型」变成能稳定运行、能规模化扩展、能控制成本的生产系统。

这一篇先看岗位要求，再看「为什么必须优化」（算力供需矛盾），然后是训练全流程与硬件底座，最后落到三个日常指标：FLOPS、带宽、MFU/HFU。

## 1. 岗位画像：技术栈的六个维度

### 1.1 编程语言与基础能力

| 技能 | 定位 |
|---|---|
| Python | 必备：训练脚本、数据 pipeline、自动化工具 |
| C++ / CUDA | 高频：Kernel 与算子开发、推理引擎优化、底层性能调优 |
| Go | 加分：基础设施服务开发 |

头部大厂普遍把「精通 PyTorch + C++/CUDA」当作核心门槛——前者说明能写模型，后者说明能改底层。

### 1.2 训练优化方向

- **分布式框架**：DeepSpeed（ZeRO-1/2/3、Offload）、Megatron-LM（TP/PP）、FSDP、3D 并行组合；
- **训练加速**：混合精度（BF16/FP8）、FlashAttention 及其变体、梯度/激活重计算、长序列优化（Ring Attention、YaRN）、MoE 路由与专家并行；
- **集群与数据**：万卡级集群经验、检查点与故障恢复、数据加载 pipeline。

分布式训练经验在招聘里既是高频也是硬性项，因为它很难「速成」——需要真的在集群上踩过坑。

### 1.3 推理优化方向

| 方向 | 具体内容 |
|---|---|
| KV Cache | PagedAttention、Radix Tree、Prefix Caching |
| 批处理 | Continuous Batching、Dynamic Batching |
| 量化 | GPTQ、AWQ、FP8/INT8/INT4、SmoothQuant |
| 投机解码 | Speculative Decoding、Medusa、Lookahead Decoding |
| Serving 框架 | vLLM、TensorRT-LLM、Triton Inference Server |
| PD 分离 | Prefill-Decode 分离架构设计 |

近两年推理优化是面试的绝对核心：它同时考察算法理解（KV Cache 的显存账）、系统设计（批处理与调度）与工程实现（框架源码）。

### 1.4 系统与底层

- **GPU 与硬件**：GPU 架构（Hopper/Blackwell、昇腾达芬奇核心）、CUDA 编程与 Kernel 优化、NCCL 通信、RDMA/InfiniBand 网络调优；
- **集群调度**：K8s + GPU 调度（Volcano、Kubeflow）、Slurm、Ray、弹性扩缩容；
- **存储与 I/O**：JuiceFS、Alluxio、Ceph 等高性能存储，TFRecord/Parquet/LMDB 等格式，检查点读写优化；
- **Profiling**：Nsight Systems/Compute、PyTorch Profiler，以及从指标反推瓶颈的能力。

### 1.5 云平台与工程化

容器化（Docker/K8s）、CI/CD、IaC（Terraform/Pulumi）、主流云平台（SageMaker、Vertex AI、PAI）与实验管理（MLflow、TensorBoard、W&B）。

### 1.6 加分项与面试重点

加分项集中在四类：核心框架的开源贡献（PyTorch/vLLM/DeepSpeed 的 PR）、异构芯片适配（昇腾、TPU、自研）、多模态与 Agent 场景的基础设施、RLHF/端侧部署经验。

面试通常四道关：**系统设计**（设计百万 QPS 推理服务、长上下文训练基础设施）、**手撕代码**（CUDA Kernel、并行算法、通信逻辑）、**工程深挖**（vLLM 源码、PagedAttention 细节、量化原理）、**性能分析**（给训练日志定位瓶颈并给方案）。

## 2. 规模增长与算力供需矛盾

### 2.1 从 GPT-3 到万亿参数

2020 年 GPT-3 以 1750 亿参数刷新认知：训练数据约 4000 亿 token，总算力约 \(3.15\times10^{8}\) PFLOPS（相当于 3640 PF-days），单次训练成本约 500 万美元。

此后规模继续跃升：GPT-4 据信在 2.5 万张 A100 上训练 90–100 天，算力比 GPT-3 增长近 70 倍；Llama 3.1 为 4050 亿参数、3.67 万亿 token；DeepSeek-V3 Base 6710 亿参数、14.8 万亿 token，而训练成本仅约 557.6 万美元。

这里要区分两类口径：**官方披露**（如 GPT-3、Llama 3、DeepSeek 的技术报告）与**业内推测**（如 GPT-4 的参数量与算力，OpenAI 从未确认）。工程讨论里引用后者时必须标注「推测」。

### 2.2 算力需求 vs 硬件供给

需求侧的增速是可量化的：大模型训练所需算力大约每 3–4 个月翻倍，而摩尔定律的历史节奏是 18 个月翻倍——需求增速是工艺红利的 4–6 倍。

供给侧则有四重瓶颈：

1. **高端芯片受限**：以 H20 为例，其 FP16 算力约 148 TFLOPS，与 H100 的差距是数量级的；
2. **成本高企**：多种场景下国产算力的单位训练成本仍显著高于 NVIDIA 方案；
3. **结构性错配**：一边是园区上架率不足，一边是一线城市「一柜难求」；
4. **生态不成熟**：芯片、框架、算子库三者尚未同时就位。

矛盾的本质是**增长速度错配**：需求每 3–4 个月翻倍，供给受制于工艺、产能与地缘因素，跟不上。这正好解释了训练优化的价值——在硬件相对固定的前提下，从系统层「榨」出每一份算力。

### 2.3 规模定律的反思

「更大即更好」正在被修正。行业观察认为，参数超过 5000 亿之后，推理与常识等核心指标的边际提升明显收窄，而训练成本与能耗仍按指数增长（此类结论多为行业测算，具体幅度需按模型与数据单独验证）。

共识正从「更大」转向「更聪明、更高效、更实用」——这恰好把优化技术推到台前。

## 3. 训练全流程与算力分布

```text
海量原始数据 → 清洗与分词 → 预训练（基础模型）
                                ↓
                         有监督微调（SFT）
                                ↓
                          奖励模型训练
                                ↓
                         PPO 强化学习（对齐）
                                ↓
                            部署与推理
```

### 3.1 数据工程

预训练数据常达 PB 级，任务包括采集（CommonCrawl、维基、书籍、论文）、清洗（去 HTML、去噪）、质量评估（困惑度、重复率）、分词（BPE/WordPiece）。数据质量与规模直接决定模型上限。

### 3.2 预训练

算力主战场（通常占全流程 90% 以上）。核心机制是自回归语言建模：通过预测下一个 token 优化参数，需要数千卡并行，典型配置是 DP + PP + TP 的组合。一个千亿模型的预训练往往需要数周到数月。

### 3.3 微调

把通用模型适配到具体用途。三条常见路线：

- **全参数微调**：效果最好，资源消耗最大；
- **LoRA**：冻结基座、只训练低秩矩阵，显存需求大幅下降；
- **Prompt/Adapter 类方法**：几乎不动模型参数。

### 3.4 对齐

让行为符合人类期望。RLHF 三步走：SFT 建基准策略 → 训奖励模型 → 用 PPO 按奖励优化。它带来的是「更有帮助、更无害、更诚实」，也是对话模型能被广泛使用的关键。

### 3.5 算力分布

预训练消耗绝大部分算力，是优化的主战场；微调算力小但频率高；对齐阶段算力不及预训练，但流程复杂（多模型、生成与训练交替），系统挑战最大——这一点在后面的 RLHF 训练专篇里展开。

## 4. 硬件底座：从 SM 到集群

### 4.1 CPU 与 GPU 的设计哲学

CPU 把芯片面积大量给缓存（约 50%）与控制（约 25%），只留约 25% 给运算，追求单线程低延迟；GPU 把约 90% 面积给运算单元，缓存与控制各约 5%，追求吞吐。

大模型训练里两者协同：CPU 负责数据加载与调度，GPU 负责并行计算。这也解释了为什么「GPU 利用率上不去」经常是 CPU 侧与 I/O 侧的问题。

### 4.2 GPC / TPC / SM 的层级

以 Hopper 为例：GH100 完整 die 为 8 个 GPC × 9 个 TPC × 2 个 SM = **144 个 SM**；而 H100 SXM 实际启用 **132 个 SM**（A100 为 108 个）。报规格时要说明是「完整 die」还是「产品实例」，否则很容易对不上账。

### 4.3 SM 内部

- **CUDA Core**：每个 SM 128 个 FP32 核（另有 64 个 FP64）；
- **Tensor Core**：每个 SM 4 个，第四代，支持 FP8/FP16/BF16/TF32；
- **寄存器文件**：每个 SM 65,536 × 32-bit，共 256 KB；
- **L1/共享内存**：SM 内共享，程序员可显式管理；
- **L2**：全卡共享，H100 为 **50 MB**（A100 为 40 MB）。

### 4.4 五级存储层次

寄存器 → L1/共享内存 → L2 → HBM → 主机内存，容量递增、带宽递减。H100 SXM 配 80 GB HBM3，带宽 **3.35 TB/s**；PCIe 版本用 HBM2e，约 2 TB/s；主机内存走 PCIe 5.0，约 128 GB/s，比 HBM 低两个数量级。

后续所有显存优化（ZeRO、重计算、Offload）本质上都是在这一金字塔里重新安排「谁放哪、搬几次」。

## 5. 三个指标：FLOPS、带宽、MFU/HFU

### 5.1 FLOPS 的口径陷阱

同一个 H100，不同精度的峰值差两个数量级（SXM，Dense 口径）：

| 精度 | 计算路径 | 峰值（约） |
|---|---|---|
| FP32 | CUDA Core 向量 | 67 TFLOPS |
| TF32 | Tensor Core | 495 TFLOPS |
| BF16 / FP16 | Tensor Core | 989 TFLOPS |
| FP8 | Tensor Core | 1,979 TFLOPS |

很多宣传数字是**稀疏加速后**的峰值（上表 ×2），或者是张量核与非张量核混算。比较算力必须先对齐三件事：精度、是否稀疏、是否 Tensor Core。

### 5.2 显存带宽常比算力更早成为瓶颈

Transformer 里有大量访存密集操作（LayerNorm、Softmax、Dropout、逐元素运算），它们对算力要求很低但需要频繁读写 HBM。带宽不够时，计算单元会「饿死」。

一个可用的判据：**GPU 利用率低于 90% 而显存带宽接近饱和** → 访存受限，优化方向是减少访存（算子融合、减少中间张量、混合精度）。

### 5.3 MFU 与 HFU

$$
\text{MFU} = \frac{\text{模型理论 FLOPs}}{\text{硬件理论峰值 FLOPs}},\qquad
\text{HFU} = \frac{\text{实际执行的 FLOPs}}{\text{硬件理论峰值 FLOPs}}
$$

两者的差别只有一处：**HFU 把重计算等额外开销算进去，MFU 不算**。因此恒有 \(\text{HFU} \ge \text{MFU}\)。

判读方式：

| 观察 | 含义 | 行动 |
|---|---|---|
| MFU 与 HFU 都低（<30%） | 硬件没被喂饱 | 查数据加载、通信、并行切分 |
| MFU 低、HFU 高（如 40% / 70%） | 算力花在重计算上 | 权衡显存收益与算力损失 |
| MFU 与 HFU 都高 | 系统利用充分 | 继续做通信/算子级微调 |

量级参考：千亿模型在千卡集群上 MFU 40%–50% 已属优秀；小模型单卡训练可以到 60%–70%。

## 6. 互联：NVLink、InfiniBand、RoCE

### 6.1 NVLink：机内的专属高速路

第四代 NVLink（H100）提供 900 GB/s 双向带宽，是 PCIe 5.0（128 GB/s）的 7 倍以上，延迟微秒级，且支持 GPU 直接读写对端显存。8 卡 DGX H100 通过 NVSwitch 全互联，整机聚合带宽可达 7.2 TB/s。

它只覆盖节点内部，因此承载的是通信最密集的 TP 与 EP。

### 6.2 InfiniBand：集群骨干

NDR 单端口 400 Gbps（约 50 GB/s），延迟约 1 μs，基于信用的流控保证无损，配 RDMA 与 GPUDirect 可绕过 CPU 直接搬数据。它是大规模训练集群的黄金标准，代价是生态封闭、成本高、运维复杂。

### 6.3 RoCE：以太网上的 RDMA

在标准以太网上实现 RDMA，兼容现有网络、成本更低；延迟约 2 μs，略高于 IB。它依赖 PFC + ECN 做无损，配置不当会出现「无损不无损、时延不稳定」的老问题。

### 6.4 分层协作与选型

| 层次 | 技术 | 承载的并行 |
|---|---|---|
| 节点内 | NVLink + NVSwitch | TP、EP（高频大流量） |
| 节点间 | InfiniBand / RoCE | PP、DP（中低频） |
| 集群级 | Fat-Tree / 多级交换 | 全局 AllReduce、All-to-All |

选型逻辑：追求极致性能上 IB；成本敏感或要复用既有以太网选 RoCE；单机多卡场景 NVLink 不是可选项，而是前提。
