# 并行策略：DP、TP、PP 与专家并行

并行不是「卡越多越快」，而是把模型与计算按维度切开后重新装配。切分维度决定通信发生在哪里、通信量多大，也决定了这套配置能不能长期稳定运行。

## 1. 先有可信基线，再谈并行

### 1.1 工业级训练循环比「能跑」多了什么

```python
for epoch in range(num_epochs):
    for batch in dataloader:
        outputs = model(batch)
        loss = criterion(outputs, labels)
        loss.backward()
        optimizer.step()
```

这段代码能跑，但缺了设备管理、梯度裁剪、学习率调度、验证评估、日志，也没有为性能分析留接口。工业级模板的关键细节有五处：

| 细节 | 作用 |
|---|---|
| `pin_memory=True` | 用锁页内存让 GPU 直接 DMA 读取，不开时 H2D 传输可能慢 30%–50% |
| `non_blocking=True` | 让 H2D 拷贝与计算重叠 |
| `zero_grad(set_to_none=True)` | 梯度直接置 None，比逐元素清零更快，也能释放显存 |
| `autocast` + `GradScaler` | 前向/反向用低精度、累加与更新用 FP32 |
| `clip_grad_norm_` | 防止梯度爆炸，大模型训练标配 |

### 1.2 用 profiler 拿证据

```python
from torch.profiler import profile, ProfilerActivity, schedule

my_schedule = schedule(skip_first=10, wait=1, warmup=2, active=3, repeat=5)

with profile(
    activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
    schedule=my_schedule,
    on_trace_ready=torch.profiler.tensorboard_trace_handler("./profiler_logs/"),
) as prof:
    for step in range(num_steps):
        train_step()
        prof.step()
```

三个参数最容易踩坑：

- `activities` 必须同时包含 `CPU` 与 `CUDA`，否则只看得到 kernel 启动，看不到 GPU 执行；
- `skip_first` / `warmup` 用来跳过初始化抖动，`active` 才是真正统计的步数；
- `prof.step()` 必须调用，否则 schedule 不会前进。

输出可以走 Chrome Trace（`export_chrome_trace`，在 `chrome://tracing` 里看时间线）或 TensorBoard 的 Performance Profile。

### 1.3 计算密集还是访存密集

| 类型 | 特征 | 典型算子 | 优化方向 |
|---|---|---|---|
| 计算密集 | Tensor Core 满负荷，带宽不高 | `aten::mm`、`aten::bmm`、大卷积 | 混合精度、更好的 Attention 实现 |
| 访存密集 | 计算单元等数据，带宽接近上限 | `aten::add`、`layer_norm`、`softmax` | 算子融合、减少中间张量 |

还有一类常被忽略：如果 `cuda_time_total` 与 `cpu_time_total` 差距很大，说明 GPU 在等 CPU 下发，瓶颈在 Python 侧或同步调用。

一个必须纠正的直觉：**GPU 利用率不高，绝大多数时候是软件问题**（数据加载、小算子碎片、频繁 `.item()` 同步、日志打印太密），而不是「卡不够强」。

## 2. 数据并行：DDP

### 2.1 原理

每张卡保留完整模型，各自算梯度，然后同步：

$$
g_{\text{avg}} = \frac{1}{N}\sum_{i=1}^{N} g_i
$$

工程上必须用 `DistributedSampler` 而不是 `shuffle`，并且每个 epoch 调 `sampler.set_epoch(epoch)`，否则各 rank 的切分顺序在 epoch 间不变，等于每轮都看同一批顺序：

```python
sampler = DistributedSampler(dataset, num_replicas=world_size, rank=rank, shuffle=True)
dataloader = DataLoader(dataset, batch_size=bs, sampler=sampler, num_workers=4, pin_memory=True)
model = DDP(model, device_ids=[rank])

for epoch in range(num_epochs):
    sampler.set_epoch(epoch)
    for inputs, labels in dataloader:
        ...
        loss.backward()   # 钩子在这里触发 AllReduce
        optimizer.step()
```

DDP 的精妙之处在于非侵入：训练循环与单卡几乎一致，梯度同步由 autograd hook 自动完成。

### 2.2 AllReduce 与 Ring 算法

AllReduce 让所有参与方得到相同的归约结果。Ring 实现分两阶段，各 \(N-1\) 轮：

1. **Scatter-Reduce**：梯度切成 \(N\) 块，边传边累加，结束后每卡持有一块的全局和；
2. **AllGather**：把已归约的块继续沿环传递，结束后每卡拥有完整结果。

每卡通信量：

$$
V \approx 2(N-1)\cdot\frac{K}{N} \approx 2K
$$

其中 \(K\) 是梯度总大小。这里有个常见误读：**通信量几乎与卡数无关（≈2K），随卡数增长的是轮数 \(2(N-1)\)，也就是延迟**。所以大规模下 Ring 的问题是延迟与长距离链路，而不是「总量爆炸」。

另一个细节：即使训练用 FP16/BF16，梯度归约通常仍建议用 FP32 累加——数千张卡的累加会放大舍入误差。

### 2.3 梯度分桶

反向传播逐层算梯度，如果每个张量一算完就发一次 AllReduce，小张量会被固定开销（kernel launch、NCCL 初始化）吃掉。

`bucket_cap_mb` 把相邻的小梯度打包成桶，一个桶触发一次通信：

```python
model = DDP(model, device_ids=[rank], bucket_cap_mb=25)   # 默认 25MB
```

调参方向：小模型可降到 10MB 左右以减少桶内等待；千亿模型可提高到 50–100MB 以减少通信次数。

### 2.4 通信与计算重叠

DDP 不等整个反向结束：某个桶的梯度都算完就立刻发通信，同时继续算下一层的梯度。

```text
不重叠：| 前向 | 反向 | AllReduce | 优化器 |
重叠：  | 前向 | 反向(层N) | 反向(层N-1) | ... |
                | AllReduce(桶1) |
                        | AllReduce(桶2) |
```

代价是权衡：`bucket_cap_mb` 太大时，桶要等最后一层梯度才触发，重叠机会反而变少。验证方式是看 profiler 时间线里 NCCL kernel 与计算 kernel 是否真的交叠。

其余两个常用开关：`gradient_as_bucket_view=True`（梯度直接复用桶内存，减少拷贝）、`find_unused_parameters=False`（默认关闭，避免每步遍历全部参数；只有存在未参与反传的参数时才需要打开）。

## 3. 张量并行：切单层

### 3.1 行并行与列并行

对线性层 \(Y = XW\)：

- **列并行**：\(W\) 按列切，每卡持有部分列，输出是结果的**部分列**；
- **行并行**：\(W\) 按行切，每卡持有部分行，输出需要**求和**才能得到完整结果。

### 3.2 MLP：列并行接行并行

$$
Y = \mathrm{GeLU}(XA)B
$$

第一层 \(A\) 按列切：\(A = [A_1, \ldots, A_N]\)，各卡算 \(Z_i = XA_i\)，非线性激活前**不需要通信**。

第二层 \(B\) 按行切：\(B = [B_1; \ldots; B_N]\)，各卡算 \(Y_i = Z_iB_i\)，最后 AllReduce 求和。

这样组合的价值是：**两层之间只通信一次**。反过来（行并行接列并行）需要两次通信，或者要在激活前同步，效率更低。

### 3.3 Attention：按 Head 切

多头注意力天然可切：各卡负责 \(H/N\) 个 Head，独立完成该 Head 的 QKV 投影与注意力计算，最后拼接并经输出投影（行并行）+ AllReduce。

Megatron 的设计原则很克制：**只对线性层做张量并行**，LayerNorm、Dropout 等逐元素操作各卡独立算——它们计算量小，且各卡输入一致。

### 3.4 边界

TP 通信最密集（每层多次 AllReduce），因此必须放在 NVLink 域内，通常 **TP ≤ 8**（不超过单机卡数）。跨节点做 TP 会让带宽降一个数量级，收益基本被吃掉。

另外要纠正一个常见口误：TP 切分的是**投影权重矩阵**，不是「注意力分数的 \(O(n^2)\) 矩阵」——后者是激活，属于序列维度的问题，靠序列并行解决。

## 4. 流水线并行：切层

### 4.1 朴素切分的问题

24 层切 4 段，每段 6 层：数据从 GPU0 流入、GPU3 流出。但同一时刻只有一张卡在工作，其余空等，利用率约 \(1/N\)。

### 4.2 微批次与 GPipe

把一个大 batch 切成 \(M\) 个微批次依次流过流水线，不同 Stage 就能同时处理不同微批次。GPipe 的策略是「先全部前向，再全部反向」，最后累加梯度。

- 优点：实现简单，只在 Stage 边界传激活与梯度；
- 缺点：必须保存所有微批次的激活，显存压力大；气泡也大。

### 4.3 1F1B：前向一步、反向一步

不等全部前向结束，每完成一个微批次的前向就尽快排入它的反向：

```text
GPipe:  GPU0: F1 F2 F3 F4 | B1 B2 B3 B4
        GPU1:    F1 F2 F3 F4 | B1 B2 B3 B4
        GPU2:       F1 F2 F3 F4 | B1 B2 B3 B4

1F1B:   GPU0: F1 F2 F3 F4 | B1 B2 B3 B4
        GPU1:    F1 F2 F3 | B1 B2 B3 B4
        GPU2:       F1 F2 | B1 B2 B3 B4
        GPU3:          F1 | B1 B2 B3 B4
```

收益是显存峰值显著下降（「算一个、存一个、反传一个、释放一个」），并且更早启动反向。Megatron 实现 1F1B 后，硬件利用率可从传统调度的 60% 左右提升到 85% 以上。

### 4.4 气泡：量化与三种优化

Stage 数 \(P\)、微批次数 \(M\)，则：

$$
\text{总时间} = (M + P - 1)T_{\text{micro}},\qquad
\text{气泡率} = \frac{P-1}{M+P-1} \approx \frac{P-1}{M}
$$

\(P=8, M=64\) 时约 10.9% 的算力被浪费。三种优化：

1. **加大 \(M\)**：最直接，工程经验取 \(M \ge 4P\)（8 个 Stage 至少 32 个微批次）；代价是激活缓存与边界通信增多；
2. **减小 \(P\)**：每个 Stage 装更多层，但会加剧 Stage 间的负载不均；
3. **交错式流水线（Interleaved）**：把层按「虚拟 Stage」交错分配，让空闲时间被打散，通常能再降低 30%–40% 的气泡。

### 4.5 负载均衡

Embedding 与 Attention/MLP 的计算量不同，切分不均就会制造「结构性气泡」。做法是按 profiler 实测耗时确定切分边界，或者用**虚拟流水线**：Stage 数大于物理卡数，把多个虚拟 Stage 映射到同一张卡上，让计算量更均匀。

## 5. 3D 并行与选型

### 5.1 三层嵌套的一次演算

32 卡（4 台 × 8 卡）、TP=4 的话：

1. **TP 组**：每 4 卡组成一个「超级卡」，32 卡 → 8 个 TP 组；
2. **PP Stage**：80 层模型切成 4 段，每段 20 层，用 4 个 TP 组 = 16 卡；
3. **DP 副本**：剩下 16 卡组成另一条同样的流水线，DP=2；
4. 校验：\(\mathrm{TP} \times \mathrm{PP} \times \mathrm{DP} = 4 \times 4 \times 2 = 32\)。

画拓扑时容易把 DP 写成 4，与前面的「剩 16 卡 → DP=2」矛盾——以乘法校验为准。

### 5.2 四条原则

1. **TP 解决「单层放不下」**，只在单层超显存时启用，且 \(\mathrm{TP} \le\) 单机卡数；
2. **PP 解决「整体放不下」**，通信量小可跨机，但要接受气泡；
3. **DP 解决「训练不够快」**，TP/PP 定完后余量全给 DP；
4. **总卡数 = TP × PP × DP**，这是硬约束。

### 5.3 按规模给配置

| 模型规模 | 硬件 | 配置 | 理由 |
|---|---|---|---|
| < 10B | 1–8 卡 | DP only | 单卡放得下，别引入并行通信 |
| 10B–100B | 32–128 卡 | TP=4, PP=4, DP=2–8 | 单层与整体都放不下 |
| 100B–1T | 256–2048 卡 | TP=8, PP=8–16, DP=4–32 | TP 打满单机，PP 跨机，DP 扩吞吐 |
| > 1T（MoE） | 数千卡 | TP=4–8, PP=8–16, DP=32–128 + EP | 专家需要独立维度 |

### 5.4 五步选型流程

1. **算显存**：\(16\Phi\)（含 FP32 主参的保守口径），70B ≈ 1.12 TB；
2. **定 TP**：单层权重大于单卡可用显存才开，常见 2/4/8；
3. **定 PP**：总需求除以「单卡显存 × TP 节省」向上取整，常见 4/8/16；
4. **定 DP**：总卡数 / (TP × PP)，若小于 1 说明硬件不够；
5. **验证**：看通信占比调 TP、看气泡调 M、看利用率查数据加载。

三个典型误区：TP 越大越好（跨机就崩）、PP 越大越好（气泡与激活显存一起涨）、DP 越多越好（梯度同步线性增长，DP > 64 后通信易成主瓶颈）。

## 6. Megatron-LM 的实现要点

- **层内并行**：不靠编译器或定制框架，只在 autograd 图里插入少量 NCCL 调用；每个 Transformer 块前向、反向各两次 AllReduce；
- **1F1B 调度**：前向反向交错，利用率 85%+；
- **分层梯度聚合**：节点内走 NVLink，跨节点走 RDMA 网络做 AllReduce；
- **PTD-P 统一视角**：Pipeline / Tensor / Data 三个维度独立配置，框架负责切权重、切层、复制流水线。

工程上 Megatron 与 DeepSpeed 常组合：用 Megatron 的 TP/PP 切模型，用 ZeRO 处理优化器状态与参数的进一步分片。

## 7. 专家并行与 MoE

### 7.1 Dense 的天花板

Dense 模型每一层都激活全部参数——参数涨多少，计算涨多少，线性绑定。万亿参数 Dense 的计算成本几乎不可承受。

MoE 用**稀疏激活**解耦这一点：每个 token 只走少数专家，总参数可以极大，而单次前向的计算量只相当于一个小模型。1.6 万亿参数的 Switch Transformer，训练计算量约等于百亿级 Dense。

### 7.2 专家与路由

MoE 把单个 FFN 换成多个并行 FFN（每个是一个专家），由路由网络决定 token 去向：

$$
z = W_r x,\qquad p = \mathrm{softmax}(z)
$$

Top-K 取概率最高的 K 个专家（K 通常 1 或 2）。专家数 \(N_E\) 从几十到几千：DeepSeek-V3 用 256 个，Switch Transformer 某些配置用到 2048 个。\(N_E = 2048, K = 2\) 时，每个 token 只激活不到 0.1% 的专家参数。

部署上通常**交错放置**：只在每 P 层插一个 MoE 层（如 80 层模型中第 1、3、5… 层），浅层保持 Dense、深层专业化。

### 7.3 专家并行的四步

1. **专家分布**：\(N_E\) 个专家均匀分到各卡；
2. **Dispatch**：路由算出目标专家，用 All-to-All 把 token 发到对应卡；
3. **本地计算**：各卡算自己负责的专家；
4. **Combine**：再一次 All-to-All 把结果收回原卡并加权求和。

EP 的核心开销就是这两次 All-to-All。DeepSeek-V3 的训练中，All-to-All 相关的通信耗时可占整体训练时长的一半以上——这也是 EP 必须限制在超节点内的原因。

### 7.4 负载均衡：MoE 最棘手的问题

路由是学出来的，容易退化成少数专家吃掉大部分 token：轻则计算拖尾，重则 OOM，极端情况是**专家坍塌**（所有 token 涌向同一专家）。

三种主流手段：

| 方案 | 机制 | 代价 |
|---|---|---|
| 辅助损失（LBL） | 用「选中频率 × 平均门控分数」的乘积惩罚不均衡 | 与主任务目标存在张力，权重难调 |
| 专家容量（Capacity） | 每个专家设 token 上限，溢出丢弃或转投 | 容量小会丢信息，容量大则不均衡照旧 |
| 动态重分配 | 运行时迁移过载设备上的专家与 token（如 LLEP） | 实现复杂，迁移本身有开销 |

### 7.5 工程实践

- **DeepSpeed-MoE**：提供 `MoE(hidden_size, num_experts, ep_size, k)` 这样的层 API，支持多种并行组合；官方数据称训练成本降低 5 倍、推理延迟与成本最多降低 7.3 倍、模型可压缩至 1/3.7。
- **Switch Transformer**：把 K 从 2 降到 1，路由计算量减半、每专家批更大、跨设备通信更少；同时证明稀疏模型可以稳定地用 BF16 训练，配合容量与辅助损失的精细调参，在 T5 上取得最高 7 倍预训练加速。
- **GShard**：首次把 MoE 与 Transformer 深度结合的分布式系统，用条件计算 + 自动分片把 6000 亿参数翻译模型拆到多节点训练，为后续工程化铺路。

## 写在最后

三维并行加专家并行，本质上是在「单层太大 / 层数太多 / 训练太慢 / 专家太散」四个约束下做取舍：TP 换通信，PP 换气泡，DP 换梯度同步，EP 换 All-to-All。下一篇把这些通信真正跑快——集合通信原语、NCCL 的算法选择，以及集群拓扑与通信亲和性。
