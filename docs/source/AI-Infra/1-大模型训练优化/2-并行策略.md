# 并行策略：从数据并行到专家并行

并行不是「卡越多越快」，而是把模型与计算按维度切分后重新装配。切分维度决定了通信发生在哪里、通信量有多大，也决定了这套配置能否长期稳定运行。

## 1. 先建立可信的基线

在动任何并行配置之前，需要一个可重复的单机基线，否则优化前后无法比较。

### 1.1 一个训练 Step 的关键路径

标准 Step 包含：数据加载 → H2D 拷贝 → 前向 → Loss → 反向 → 梯度同步 → 优化器更新 → 清梯度。

```python
for batch in dataloader:
    input_ids = batch["input_ids"].to(device, non_blocking=True)
    labels = batch["labels"].to(device, non_blocking=True)

    optimizer.zero_grad(set_to_none=True)
    outputs = model(input_ids=input_ids, labels=labels)
    loss = outputs.loss
    loss.backward()
    optimizer.step()
```

分布式训练中，梯度同步通常由 DDP、FSDP 或 DeepSpeed 的 Hook 插入反向图。因此性能分析必须覆盖完整 Step，而不是只测 `model()` 那一段。

### 1.2 固定实验变量

需要固定：模型权重、数据样本、序列长度、global batch、micro batch、梯度累积、精度、并行配置、随机种子。任何一项变化都可能让对比失效。

三者关系必须写清：

$$
\text{global\_batch} = \text{micro\_batch\_per\_gpu} \times \text{grad\_accum} \times \text{DP size}
$$

改并行度时，DP size 变化会直接改变 global batch——这是最常见的「优化后结果不可比」的原因。

### 1.3 Warmup 与同步计时

首次运行包含 CUDA 上下文创建、内核加载、通信器初始化、缓存与编译开销，应当跳过 Warmup 再测稳定区间。计时必须同步：

```python
torch.cuda.synchronize()
start = time.perf_counter()

train_step(batch)

torch.cuda.synchronize()
elapsed = time.perf_counter() - start
```

CUDA 默认异步提交，不同步时测到的只是 CPU 提交时间，host 侧测出的「提速」经常是假象。

### 1.4 基线要记录什么

- 每步耗时与 tokens/s；
- 峰值显存，以及 `reserved` / `allocated` 两个口径；
- GPU Util、SM 效率、Tensor Core 活动、HBM 带宽；
- NCCL 集合通信耗时；
- 数据加载等待时间。

## 2. 数据并行（DP）

### 2.1 原理

每张 GPU 保留一份完整模型副本，把不同数据子集分给各 Rank。每个 Rank 独立前向与反向，然后同步梯度，用相同的全局梯度更新参数：

$$
g_{\text{global}} = \frac{1}{N}\sum_{i=1}^{N} g_i
$$

只要初始化一致、梯度同步一致、优化器状态一致，更新后各 Rank 的模型必然一致。

### 2.2 单进程 DP 的局限与 DDP 的流程

`torch.nn.DataParallel` 由主进程控制多卡，存在主卡聚合、Python 线程与负载不均的问题，生产训练基本不用。生产标准是一进程一卡的 `DistributedDataParallel`（DDP），执行流程是：

1. 每个进程绑定一张 GPU；
2. 各 Rank 加载相同模型参数；
3. `DistributedSampler` 为每个 Rank 分配不同数据；
4. 每个 Rank 独立前向与反向；
5. 梯度 Bucket 就绪后发起 AllReduce；
6. 所有 Rank 用同步后的梯度更新参数。

「Bucket 就绪就发」是 DDP 的关键设计：梯度按反向量产顺序分桶，边算边通信，把通信藏在计算后面。

### 2.3 代码骨架

```python
import os
import torch
import torch.distributed as dist

dist.init_process_group(backend="nccl")
local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)
device = torch.device("cuda", local_rank)

model = model.to(device)
model = torch.nn.parallel.DistributedDataParallel(
    model,
    device_ids=[local_rank],
    output_device=local_rank,
)
```

### 2.4 边界

DP 的前提是「单卡装得下一整份模型」。7B 模型在混合精度下光模型状态就要 112 GB 以上（16Φ 口径），单卡 80 GB 装不下——于是必须切模型。

## 3. 张量并行（TP）

TP 切分同一层内部的矩阵，解决的是「单层太大」的问题。

### 3.1 MLP 的列并行与行并行

Transformer 的 MLP 可写成：

$$
Y = \mathrm{GeLU}(XA)B
$$

第一层权重 \(A\) 按列切分：

$$
A = [A_1, A_2, \ldots, A_p],\qquad XA = [XA_1, XA_2, \ldots, XA_p]
$$

每个 Rank 独立计算自己的列分片并各自过 GeLU，**非线性激活前不需要同步**。

第二层权重 \(B\) 按行切分：

$$
B = \begin{bmatrix} B_1 \\ B_2 \\ \vdots \\ B_p \end{bmatrix},\qquad
Y = \sum_{i=1}^{p}\mathrm{GeLU}(XA_i)B_i
$$

每个 Rank 算出局部结果后，通过一次 AllReduce 求和得到完整输出。这正是 Megatron 的「列并行接行并行」模式：一对 TP 层只需两次同步（反向一次、前向一次），而不是每层多次。

### 3.2 Attention 的 Head 切分

Q、K、V 的投影按 Attention Head 切分，每个 Rank 只计算部分 Head；输出投影按行切分并 AllReduce。要求 Head 数量能被 TP 大小整除——这也是 TP 常见取 2/4/8 的原因。

### 3.3 边界

TP 每层都要通信，通信量大且频繁，必须放在 NVLink 域内（通常不跨机）。TP 越大，单卡计算量越小，通信占比越高，因此存在收益拐点。

## 4. 流水线并行（PP）

PP 按层切分模型深度，解决「层数太多」的问题：模型被切成若干 Stage，每个 Stage 放在不同设备上，微批次沿 Stage 依次流动。

它带来两个必须处理的问题：

- **气泡（Bubble）**：流水线填充与排空阶段部分设备空闲，气泡比例约为 \((P-1)/(M+P-1)\)，\(P\) 为 Stage 数、\(M\) 为微批次数。因此必须让微批次数远大于 Stage 数。
- **显存不均**：第一个 Stage 通常要处理 embedding、最后一个要处理 loss 与输出层，切分时要刻意做负载均衡。

## 5. 3D 并行：把三个维度组合起来

### 5.1 为什么必须组合

大模型训练同时面临三重压力：

1. **显存**：175B 混合精度仅模型状态约 2.8 TB（16Φ），远超单卡 80 GB；
2. **算力**：GPT-3 量级需要约 3640 PF-days，单卡 A100 要跑 130 天以上；
3. **通信**：GPU 数量增加，梯度同步通信量线性攀升。

一句话概括分工：**TP 解决「单层太大」，PP 解决「层数太多」，DP 解决「训练太慢」**。

### 5.2 一个具体的组合演算

假设 4 台服务器、每台 8 卡，共 32 卡：

1. **先划 TP 小组**：每 4 张卡组成一个 TP 组，组内靠 NVLink 计算同一个 Transformer 层。32 卡变成 8 个「超级卡」。
2. **再划 PP Stage**：8 个组分成若干 Stage，每个 Stage 负责一段连续的层，微批次接力通过。
3. **剩下的维度给 DP**：若 TP=4、PP=2，则 DP = 32 / (4×2) = 4，即 4 份数据副本。

经验约束：

- TP 必须在节点内（NVLink）；
- PP 可以跨节点，但要接受气泡；
- DP 放最外层，跨机柜通信量相对可控。

## 6. 专家并行与 MoE

### 6.1 从 Dense 到 Sparse

Dense 模型的根本问题是：每一层前向都会激活全部参数——参数增加多少，计算量就增加多少，两者线性绑定。万亿参数 Dense 模型的计算成本几乎不可承受。

MoE（混合专家）用**稀疏激活**改变了这个关系：每个 Token 只激活一小部分参数，从而把参数量与计算量解耦。1.6 万亿参数的 Switch Transformer，其训练计算量大致相当于百亿参数级 Dense 模型。

### 6.2 专家与路由

MoE 用多个并行 FFN 取代原来的单一 FFN，每个 FFN 是一个**专家（Expert）**；由一个**路由网络（Router / Gating）**决定 Token 交给哪几个专家。

对 Token 表征 \(x\)，路由先算 logits：

$$
z = W_r x
$$

再取 Top-k 专家的加权和作为输出：

$$
y = \sum_{i \in \mathrm{TopK}(z)} \frac{\exp(z_i)}{\sum_{j \in \mathrm{TopK}(z)}\exp(z_j)}\, E_i(x)
$$

专家数量的量级在几十到几千：DeepSeek-V3 用 256 个专家，Switch Transformer 某些配置用到 2048 个。

### 6.3 工程上真正难的三件事

- **负载均衡**：路由是学出来的，容易退化成「少数专家吃掉大部分 Token」。需要辅助损失（load balancing loss）或容量因子/丢弃策略来约束。
- **All-to-All 通信**：EP 要把 Token 按专家分发再收回，是训练中最昂贵的一类通信，必须限制在超节点内。
- **专家并行与 TP/PP 的组合**：EP 通常替代 TP 在 FFN 上的角色，形成「Attention 走 TP、FFN 走 EP」的混合切分。

## 写在最后

并行方案的三个维度已经摆开：DP 便宜但吃显存，TP 省显存但吃节点内带宽，PP 省显存但吃气泡，EP 靠稀疏性换规模但吃 All-to-All。下一步是把这些通信真正跑快——集合通信原语、NCCL 的算法选择，以及集群拓扑与通信亲和性。
