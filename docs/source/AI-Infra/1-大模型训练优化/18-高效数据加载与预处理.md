# 高效数据加载与预处理

### 1.1. 问题根源：同步数据加载的“停等”效应
在理解优化之前，先看一个最朴素的数据加载方式：
```text
train_loader = DataLoader(dataset, batch_size=32)
```
此时`num_workers=0`，数据加载是**同步**的——主进程在每次迭代时从磁盘读取数据、进行预处理（如图像解码、数据增强），然后才能将数据送到GPU进行计算。在数据加载和预处理完成之前，**GPU完全空闲**。
这就是“停等（Stall）”效应：GPU的高速计算能力被低速的I/O和CPU预处理拖累。
### 1.2. num_workers：用多进程“预加载”数据
**核心原理**
`num_workers`指定了用于数据加载的子进程数量。当`num_workers > 0`时，DataLoader会启动多个独立的worker子进程，**异步**地在后台预加载和预处理数据。主训练进程不再需要等待数据——它直接从worker准备好的队列中取数据即可。
这种设计的本质是**用CPU时间换GPU等待时间**——利用多核CPU的并行能力，让数据准备与模型计算重叠。
**如何设置num_workers**
`num_workers`的设置没有唯一的“正确答案”，它取决于CPU核心数、数据集大小、预处理复杂度等多个因素。以下是几条经验法则：
- **通用建议**：设置为CPU物理核心数，或按经验设为`4 × num_gpu`
- **数据集的特性**：当数据集很大或预处理较重时，增加`num_workers`可以显著提升性能；当数据集很小或预处理极轻时，过大的`num_workers`反而会带来调度与内存开销
- **监控与调优**：如果GPU利用率低于70%，需增加`num_workers`或`prefetch_factor`；如果CPU使用率过高，需减少`num_workers`或优化预处理代码
**注意事项**
`num_workers`并非越大越好。每个worker子进程都会消耗内存——当worker数量过多时，内存占用会急剧上升。此外，在分布式训练中，`num_workers`需要在所有进程中累加考虑，避免总进程数过多导致系统过载。
### 1.3. pin_memory：加速CPU到GPU的数据搬运
**核心原理**
`pin_memory=True`指示DataLoader使用**固定内存（Pinned Memory，也称锁页内存）**。固定内存是操作系统不会交换到磁盘的物理内存区域，GPU的DMA（直接内存访问）引擎可以直接从固定内存中读取数据，而无需CPU的介入。
对比一下：
- **普通内存（Pageable Memory）**：数据需要先从普通内存复制到固定内存（由CPU完成），再由GPU读取——两步操作，CPU参与
- **固定内存（Pinned Memory）**：GPU直接通过DMA读取——一步操作，CPU不参与
因此，`pin_memory=True`可以实现**从主机到GPU更快且异步的内存复制**。
**最佳实践**
当使用GPU训练时，**强烈建议设置**`pin_memory=True`。配合`non_blocking=True`，还可以实现数据传输与GPU计算的重叠：
```text
inputs = inputs.to(device, non_blocking=True)
labels = labels.to(device, non_blocking=True)
```
### 1.4. prefetch_factor：控制预取深度
**核心原理**
`prefetch_factor`定义了**每个worker预先加载的批次数量**。默认值为2，意味着每个worker会在当前批次被消费之前，预先准备好2个批次。
预取的逻辑是：在当前批次进行前向和反向传播的同时，DataLoader会尽可能多地准备后续批次，直到达到`prefetch_factor`所限制的预取数量。
**调优建议**
- **增加**`prefetch_factor`：可以更充分地利用数据加载的并行能力，减少GPU等待——但会**增加内存占用**
- **权衡**：需要在“减少GPU等待”和“控制内存占用”之间找到平衡
- **诊断**：如果GPU利用率周期性下降，可能意味着预取深度不足，可以尝试增大`prefetch_factor`
### 1.5. 一个优化的DataLoader配置
综合以上三个参数，一个经过优化的DataLoader配置如下：
```text
from torch.utils.data import DataLoader

train_loader = DataLoader(
    dataset,
    batch_size=256,              # 根据显存调整
    shuffle=True,
    num_workers=8,               # 建议≈CPU物理核心数或4×num_gpu
    pin_memory=True,             # 必须开启，加速CPU→GPU传输
    prefetch_factor=4,           # 每个worker预取4个batch
    persistent_workers=True,     # 长时训练减少worker重建开销
)
```
`persistent_workers=True` 是一个容易被忽视但很有用的参数——它让worker进程在epoch之间保持存活，避免每个epoch重新创建worker的开销。
### 2.1. 从DataLoader到数据流水线
DataLoader的`num_workers`和`prefetch_factor`已经实现了一定程度的预取，但它们只是数据流水线的第一层。在大规模训练中，我们需要一个**多级数据流水线**，每一级都在为下一级“预取”数据。
一个完整的数据流水线通常包含以下层级：
```text
[磁盘/NVMe] → [操作系统页缓存] → [进程级缓存] → [GPU显存]
```
每一级都有其独特的优化策略。
### 2.2. 第一级：存储介质与文件格式
**存储介质的选择**：将数据集放在SSD/NVMe而非HDD，可显著降低读取延迟。在云端训练时，使用本地NVMe临时存储而非网络存储（如EBS），可以避免网络I/O成为瓶颈。
**减少小文件开销**：海量小文件（如图像数据集中的每个样本单独存储）会导致大量的文件系统元数据操作和寻道开销。解决方案包括：
- 将数据打包为**容器格式**，如TFRecord、LMDB、HDF5
- 使用**WebDataset的tar归档格式**（将在18.3节详述）
- 使用**FFCV的.beton格式**（将在18.3节详述）
### 2.3. 第二级：内存级缓存
对于体量可控的数据集，可以将整个数据集**加载到内存**中：
```text
# Linux下使用tmpfs挂载
sudo mount -t tmpfs -o size=30G tmpfs /path/to/data
```
这种方式将数据集放在内存文件系统中，**极大降低I/O等待**。但需要注意：重启后数据清空，且会占用物理内存，可能触发swap。
更精细的内存缓存策略包括**进程级缓存**——每个worker进程在内存中缓存已读取的数据，避免重复从磁盘读取。
### 2.4. 第三级：CUDA流级预取
这是最接近GPU的一级预取。核心思想是：**在独立的CUDA流中执行 pinned memory → GPU的拷贝**，使“下一批数据的拷贝”与“当前批次的前向计算”并行。
实现方式是实现一个`DataPrefetcher`类：
```python
class DataPrefetcher:
    def __init__(self, loader, device):
        self.loader = iter(loader)
        self.device = device
        self.stream = torch.cuda.Stream()
        self.preload()

    def preload(self):
        try:
            self.next_data = next(self.loader)
        except StopIteration:
            self.next_data = None
            return
        with torch.cuda.stream(self.stream):
            self.next_data = [d.to(self.device, non_blocking=True) 
                              for d in self.next_data]

    def next(self):
        torch.cuda.current_stream().wait_stream(self.stream)
        data = self.next_data
        self.preload()
        return data
```
使用方式：
```text
prefetcher = DataPrefetcher(train_loader, device)
batch = prefetcher.next()
while batch is not None:
    # 训练步骤
    # ...
    batch = prefetcher.next()
```
这种模式使得**数据传输与计算完全重叠**——当GPU在执行当前批次的前向/反向传播时，下一批数据已经在后台拷贝到显存中了。
### 2.5. 多级缓存的设计原则
设计高效的数据流水线，核心原则是**让每一级都“超前”为下一级准备数据**：
1. **存储层** → **内存缓存**：将频繁访问的数据提前加载到内存
2. **内存缓存** → **worker进程**：worker从内存中读取并预处理
3. **worker进程** → ** pinned memory**：预处理后的数据放入固定内存
4. **pinned memory** → **GPU显存**：通过CUDA流异步拷贝
每一级的“预取深度”都需要根据实际 workload 调优——预取太少会导致GPU等待，预取太多会耗尽内存。
## 3. 大数据场景下的WebDataset与FFCV
当数据集规模达到TB级别时，传统的DataLoader即使经过上述优化，也可能力不从心。**WebDataset**和**FFCV**是两种专门为超大规模数据集设计的数据加载方案。
### 3.1. WebDataset：以tar应对海量小文件
**核心思想**
WebDataset的核心思想非常简洁：**将成千上万个小文件打包成少量的tar归档文件**。
为什么这能加速？文件系统的随机访问（打开、读取、关闭海量小文件）会产生巨大的元数据开销和寻道延迟。而tar归档文件是**顺序存储**的——读取一个tar文件时，数据在磁盘上是连续的，可以实现**顺序I/O**。顺序I/O的吞吐量通常是随机I/O的**3-10倍**。
**基本用法**
```python
import webdataset as wds

dataset = (
    wds.WebDataset("dataset-{0000..0016}.tar")
    .decode("pil")
    .to_tuple("jpg", "cls")
    .batched(64)
)

dataloader = DataLoader(dataset, num_workers=4, batch_size=None)
```
WebDataset将每个tar文件中的样本按basename分组，将同名的不同扩展名文件（如`image.jpg`和`label.txt`）聚合为一个字典。
**分布式训练支持**
WebDataset在设计时就考虑了分布式训练场景：
- **分片机制**：数据集可以分割成多个shard，每个worker处理不同的shard
- **数据并行**：自动处理数据在多个GPU间的分配
- **确定性洗牌**：确保分布式环境下数据顺序的一致性
在视频等大规模数据处理场景中，直接使用WebDataset内置的解码功能（如`wds.torch_video`）往往比外部工具更稳定高效。
**性能数据**
在CC12M数据集上的实验表明，**WebDataset与NVIDIA DALI结合使用，平均可获得1.20倍的训练加速**，同时GPU利用率维持在92-97%的高位。
### 3.2. FFCV：全链路数据加载优化
如果说WebDataset主要解决了**存储格式**的问题，那么**FFCV（Fast Forward Computer Vision）** 则是从**全链路**的角度重新设计了数据加载系统。
**核心方法**
FFCV通过多种技术的组合来消除数据瓶颈：
1. **改进的文件格式（.beton）**：FFCV引入了新的二进制格式`.beton`，专门为高吞吐量数据加载优化，减轻文件系统压力，提高灵活性和搜索/索引性能
2. **JIT编译数据处理管道**：FFCV通过即时编译将用户提供的Python数据处理管道编译成优化的机器码，平衡了效率与灵活性
3. **线程级并行而非进程级**：由于编译后的代码不受Python GIL限制，FFCV可以使用线程而非子进程，并在训练循环中**异步并行**运行数据准备操作
4. **多级缓存策略**：FFCV提供了操作系统缓存、进程缓存和准随机采样等多种高吞吐量读取策略
**性能数据**
FFCV的性能提升非常显著：
- 在单台机器上，使用FFCV可以在**20分钟内将ImageNet ResNet-50训练到75%的准确率**，而PyTorch DataLoader需要**超过1小时**
- 在数据加载吞吐量测试中，FFCV从RAM加载512px JPEG图像时达到**31,278 images/sec**的吞吐量
- FFCV在**性能上显著优于PyTorch DataLoader、WebDataset和DALI**，同时**使用和扩展都更加简单**
**快速上手**
使用FFCV只需几行代码：
```python
import ffcv

# 1. 将数据集转换为FFCV格式
ffcv.writer.DatasetWriter(...).from_indexed_dataset(dataset)

# 2. 使用FFCV的DataLoader替换原有loader
loader = ffcv.Loader(
    dataset_path,
    batch_size=256,
    num_workers=8,
    distributed=True,  # 分布式训练支持
)
```
对于分布式训练，FFCV的`Loader`类提供了`distributed`标志，行为与PyTorch的`DistributedSampler`类似——**替换数据加载器即可，无需修改其他代码**。
### 3.3. 三种方案的对比与选型

**选型建议**：
- **中小规模数据集**（< 100GB）：优化PyTorch DataLoader的`num_workers`、`pin_memory`和`prefetch_factor`即可
- **海量小文件**（如数百万张图像）：使用**WebDataset**将文件打包为tar，大幅提升I/O效率
- **追求极致训练速度**（如ImageNet基准测试）：使用**FFCV**，它从存储格式到数据处理管道进行了全链路优化
- **云存储训练**：WebDataset天然支持从S3等对象存储流式读取
