# 高效数据加载与预处理

## 1. PyTorch DataLoader 的深度优化

### 1.1 问题根源：同步数据加载的「停等」效应

先看一个最朴素的数据加载方式：

```python
train_loader = DataLoader(dataset, batch_size=32)
```

此时 `num_workers=0`，数据加载是**同步**的——主进程在每次迭代时从磁盘读取数据、进行预处理（如图像解码、数据增强），然后才能把数据送到 GPU 计算。在数据加载和预处理完成之前，**GPU 完全空闲**。

这就是「停等（Stall）」效应：GPU 的高速计算能力被低速的 I/O 和 CPU 预处理拖累。

### 1.2 num_workers：用多进程「预加载」数据

`num_workers` 指定用于数据加载的子进程数量。当 `num_workers > 0` 时，DataLoader 会启动多个独立的 worker 子进程，**异步**地在后台预加载和预处理数据；主训练进程不再等待数据，直接从 worker 准备好的队列里取。本质是**用 CPU 时间换 GPU 等待时间**——利用多核 CPU 的并行能力，让数据准备与模型计算重叠。

设置经验：

- **通用建议**：设为 CPU 物理核心数，或按经验设为 `4 × num_gpu`。
- **数据集特性**：数据集很大或预处理较重时，增加 `num_workers` 可显著提升性能；数据集很小或预处理极轻时，过大的 `num_workers` 反而带来调度与内存开销。
- **监控与调优**：GPU 利用率低于 70% 时增加 `num_workers` 或 `prefetch_factor`；CPU 使用率过高时减少 `num_workers` 或优化预处理代码。

**注意**：`num_workers` 并非越大越好。每个 worker 子进程都会消耗内存，worker 太多内存占用会急剧上升；分布式训练中还要按「每进程 worker 数 × 进程数」累计考虑，避免总进程数过多导致系统过载。

### 1.3 pin_memory：加速 CPU 到 GPU 的数据搬运

`pin_memory=True` 指示 DataLoader 使用**固定内存（Pinned Memory，也称锁页内存）**。固定内存是操作系统不会交换到磁盘的物理内存区域，GPU 的 DMA 引擎可以直接从中读取数据，无需 CPU 介入。

- **普通内存（Pageable Memory）**：数据需要先从普通内存复制到固定内存（CPU 完成），再由 GPU 读取——两步，CPU 参与。
- **固定内存（Pinned Memory）**：GPU 直接通过 DMA 读取——一步，CPU 不参与。

因此 `pin_memory=True` 可以实现**从主机到 GPU 更快且异步的内存复制**。配合 `non_blocking=True`，还能让数据传输与 GPU 计算重叠：

```python
inputs = inputs.to(device, non_blocking=True)
labels = labels.to(device, non_blocking=True)
```

### 1.4 prefetch_factor：控制预取深度

`prefetch_factor` 定义**每个 worker 预先加载的批次数**，默认值 2，意味着每个 worker 会在当前批次被消费前预先准备好 2 个批次。预取逻辑是：在当前批次做前向和反向的同时，DataLoader 尽可能多地准备后续批次，直到达到 `prefetch_factor` 限制的数量。

调优建议：

- **增加** `prefetch_factor`：更充分利用数据加载并行能力、减少 GPU 等待，但会**增加内存占用**。
- **权衡**：在「减少 GPU 等待」和「控制内存占用」之间找平衡。
- **诊断**：GPU 利用率周期性下降，往往意味着预取深度不足。

### 1.5 一个优化的 DataLoader 配置

```python
from torch.utils.data import DataLoader

train_loader = DataLoader(
    dataset,
    batch_size=256,              # 根据显存调整
    shuffle=True,
    num_workers=8,               # 建议≈CPU物理核心数或4×num_gpu
    pin_memory=True,             # 必须开启，加速CPU→GPU传输
    prefetch_factor=4,           # 每个worker预取4个batch
    persistent_workers=True,     # 长时训练减少worker重建开销
)
```

`persistent_workers=True` 是容易被忽视但很有用的参数——它让 worker 进程在 epoch 之间保持存活，避免每个 epoch 重新创建 worker 的开销。

## 2. 数据预取（Prefetch）与多级缓存设计

### 2.1 从 DataLoader 到数据流水线

`num_workers` 和 `prefetch_factor` 只是数据流水线的第一层。大规模训练需要一条**多级数据流水线**，每一级都在为下一级「预取」数据：

```text
[磁盘/NVMe] → [操作系统页缓存] → [进程级缓存] → [GPU显存]
```

### 2.2 第一级：存储介质与文件格式

**存储介质的选择**：把数据集放在 SSD/NVMe 而非 HDD 可显著降低读取延迟；云端训练时使用本地 NVMe 临时存储而非网络存储（如 EBS），可避免网络 I/O 成为瓶颈。

**减少小文件开销**：海量小文件（如图像数据集中每个样本单独存储）会造成大量文件系统元数据操作和寻道开销。解决方案包括：

- 打包为**容器格式**，如 TFRecord、LMDB、HDF5。
- 使用 **WebDataset 的 tar 归档格式**。
- 使用 **FFCV 的 .beton 格式**。

### 2.3 第二级：内存级缓存

对于体量可控的数据集，可以把整个数据集**加载到内存**：

```bash
# Linux下使用tmpfs挂载
sudo mount -t tmpfs -o size=30G tmpfs /path/to/data
```

这种方式把数据集放到内存文件系统，**极大降低 I/O 等待**；但要注意重启后数据清空，且会占用物理内存、可能触发 swap。更精细的策略是**进程级缓存**——每个 worker 在内存中缓存已读取的数据，避免重复从磁盘读取。

### 2.4 第三级：CUDA 流级预取

这是最接近 GPU 的一级预取。核心思想是**在独立的 CUDA 流中执行 pinned memory → GPU 的拷贝**，使「下一批数据的拷贝」与「当前批次的前向计算」并行：

```python
class DataPrefetcher:
    def __init__(self, loader, device):
        self.loader = iter(loader)
        self.device = device
        self.stream = torch.cuda.Stream()
        self.preload()

    def preload(self):
        try:
            self.next_data = next(self.loader)
        except StopIteration:
            self.next_data = None
            return
        with torch.cuda.stream(self.stream):
            self.next_data = [d.to(self.device, non_blocking=True)
                              for d in self.next_data]

    def next(self):
        torch.cuda.current_stream().wait_stream(self.stream)
        data = self.next_data
        self.preload()
        return data
```

使用方式：

```python
prefetcher = DataPrefetcher(train_loader, device)
batch = prefetcher.next()
while batch is not None:
    # 训练步骤
    # ...
    batch = prefetcher.next()
```

这种模式使**数据传输与计算完全重叠**——当 GPU 执行当前批次的传播时，下一批数据已经在后台拷贝到显存。

### 2.5 多级缓存的设计原则

设计高效数据流水线的核心原则是**让每一级都「超前」为下一级准备数据**：

1. **存储层 → 内存缓存**：把频繁访问的数据提前加载到内存。
2. **内存缓存 → worker 进程**：worker 从内存读取并预处理。
3. **worker 进程 → pinned memory**：预处理后的数据放入固定内存。
4. **pinned memory → GPU 显存**：通过 CUDA 流异步拷贝。

每一级的「预取深度」都需要按实际 workload 调优——预取太少导致 GPU 等待，预取太多耗尽内存。

## 3. 大数据场景下的 WebDataset 与 FFCV

当数据集规模达到 TB 级别时，传统 DataLoader 即使经过上述优化也可能力不从心。**WebDataset** 和 **FFCV** 是两种专门为超大规模数据集设计的数据加载方案。

### 3.1 WebDataset：以 tar 应对海量小文件

**核心思想**：**把成千上万个小文件打包成少量 tar 归档文件**。

为什么这能加速？文件系统的随机访问（打开、读取、关闭海量小文件）会产生巨大的元数据开销和寻道延迟；而 tar 归档文件是**顺序存储**的，读取时数据在磁盘上连续，可实现**顺序 I/O**。顺序 I/O 的吞吐量通常是随机 I/O 的 **3–10 倍**。

```python
import webdataset as wds

dataset = (
    wds.WebDataset("dataset-{0000..0016}.tar")
    .decode("pil")
    .to_tuple("jpg", "cls")
    .batched(64)
)

dataloader = DataLoader(dataset, num_workers=4, batch_size=None)
```

WebDataset 把每个 tar 文件中的样本按 basename 分组，将同名的不同扩展名文件（如 `image.jpg` 和 `label.txt`）聚合成一个字典。

**分布式训练支持**：数据集可分割成多个 shard，每个 worker 处理不同 shard；自动处理数据在多个 GPU 间的分配；提供确定性洗牌以保证分布式环境下数据顺序一致。在视频等大规模场景中，直接使用内置解码（如 `wds.torch_video`）往往比外部工具更稳定高效。

**性能数据**：在 CC12M 数据集上，WebDataset 与 NVIDIA DALI 结合平均可获得 **1.20 倍的训练加速**，同时 GPU 利用率维持在 92%–97% 的高位。

### 3.2 FFCV：全链路数据加载优化

WebDataset 主要解决**存储格式**问题，而 **FFCV（Fast Forward Computer Vision）** 则从**全链路**角度重新设计数据加载系统。它通过多种技术的组合消除数据瓶颈：

1. **改进的文件格式（.beton）**：专为高吞吐量加载优化的二进制格式，减轻文件系统压力，提高检索/索引性能。
2. **JIT 编译数据处理管道**：把用户提供的 Python 预处理管道即时编译成优化的机器码，兼顾效率与灵活性。
3. **线程级并行而非进程级**：编译后的代码不受 Python GIL 限制，FFCV 可以使用线程而非子进程，并在训练循环中**异步并行**运行数据准备。
4. **多级缓存策略**：提供操作系统缓存、进程缓存和准随机采样等多种高吞吐读取策略。

**性能数据**：

- 单机上使用 FFCV 可在 **20 分钟内把 ImageNet ResNet-50 训练到 75% 准确率**，而 PyTorch DataLoader 需要**超过 1 小时**。
- 数据加载吞吐量测试中，FFCV 从 RAM 加载 512px JPEG 图像达到 **31278 images/sec**。
- FFCV 在性能上显著优于 PyTorch DataLoader、WebDataset 和 DALI，同时使用与扩展更简单。

**快速上手**：

```python
import ffcv

# 1. 将数据集转换为FFCV格式
ffcv.writer.DatasetWriter(...).from_indexed_dataset(dataset)

# 2. 使用FFCV的DataLoader替换原有loader
loader = ffcv.Loader(
    dataset_path,
    batch_size=256,
    num_workers=8,
    distributed=True,  # 分布式训练支持
)
```

分布式训练时，FFCV 的 `Loader` 提供 `distributed` 标志，行为与 PyTorch 的 `DistributedSampler` 类似——**替换数据加载器即可，无需修改其他代码**。

### 3.3 三种方案的对比与选型

| 方案 | 解决的核心问题 | 适用规模 | 迁移成本 |
|---|---|---|---|
| 优化 DataLoader | 进程并行与锁页内存 | < 100 GB | 无（改参数） |
| WebDataset | 海量小文件、顺序 I/O、云存储流式读取 | TB 级、百万级小文件 | 低（改数据集封装） |
| FFCV | 格式 + 解码 + 预处理全链路 | 追求极致吞吐（如 ImageNet 基准） | 中（需转换格式） |

**选型建议**：

- **中小规模数据集**（< 100 GB）：优化 `num_workers`、`pin_memory` 和 `prefetch_factor` 即可。
- **海量小文件**（如数百万张图像）：用 **WebDataset** 打包为 tar，大幅提升 I/O 效率。
- **追求极致训练速度**（如 ImageNet 基准测试）：用 **FFCV**，它从存储格式到数据处理管道做了全链路优化。
- **云存储训练**：WebDataset 天然支持从 S3 等对象存储流式读取。
