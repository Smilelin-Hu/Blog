# 专家并行（Expert Parallelism）与 MoE 训练

前几篇系统讲过 3D 并行——数据并行（DP）、张量并行（TP）和流水线并行（PP）的组合。这套体系在训练 Dense（密集型）模型时非常有效，但当模型参数突破万亿级别时，3D 并行也遇到了天花板。

原因在于 Dense 模型有一个根本性的效率问题：**每一层的前向传播都会激活全部参数**。这意味着模型参数增加多少，计算量就增加多少——两者是线性绑定的。训练一个万亿参数的 Dense 模型，计算成本高到几乎不可承受。

**MoE（混合专家模型）** 的出现改变了这个游戏规则。它通过**「稀疏激活」**——每个输入只激活模型中的一小部分参数——实现了**「参数规模与计算成本的有效解耦」**。一个 1.6 万亿参数的 Switch Transformer，训练所需的计算量仅相当于一个 100 亿参数的 Dense 模型。

## 1. MoE（混合专家）模型架构概述

### 1.1 从 Dense 到 Sparse：一个根本性的架构转变

在理解 MoE 之前，先回顾标准 Transformer 的结构。在标准的仅解码器（Decoder-only）Transformer 中，每个 token 依次通过多头注意力（MHA）和前馈网络（FFN）。FFN 层由两个线性层构成，中间插入一个非线性激活函数（如 ReLU 或 GeLU）。**所有 token 都通过同一个 FFN 处理**——这就是「Dense」的含义：每个输入都激活全部参数。

MoE 对这一设计进行了关键修改：**将单一的 FFN 替换为多个并行的 FFN，每个 FFN 称为一个「专家」（Expert）**。每个专家拥有独立的权重参数。当 token 到达 MoE 层时，由一个**路由机制（Router，也叫门控网络）**决定该 token 应该由哪几个专家来处理。

这就是「Sparse」的含义：**每个输入只激活全部专家中的一小部分**。用一句话概括：**Dense 模型是「全员上阵」，MoE 模型是「按需调度」**。

### 1.2 MoE 的核心组成：专家网络 + 路由机制

MoE 架构由两大核心组件构成。

**组件一：专家网络（Experts）**。专家网络就是一组并行的 FFN。每个专家本身就是一个标准的 FFN 结构——两个线性层加一个非线性激活函数。不同的是，在 MoE 层中部署了**多个**这样的 FFN 单元，每个单元有自己独立的权重参数。专家的数量（记为 $N_E$）通常在**几十到几千**不等。例如 DeepSeek-V3 使用了 256 个专家，而 Switch Transformer 的某些配置使用了多达 **2048 个专家**。

**组件二：路由机制（Router / Gating Network）**。路由机制是 MoE 的「大脑」——它决定每个 token 应该交给哪些专家处理。路由机制本质上是一个可训练的网络层，输入是 token 的 embedding，输出是该 token 与每个专家的匹配分数（logits）。

对于输入 token 的表征 $x$，路由网络通过权重 $W_r$ 计算 logits：

$$
h(x) = x W_r
$$

再通过 softmax 得到每个专家的选择概率：

$$
p_i = \mathrm{softmax}(h(x))_i = \frac{\exp(h_i(x))}{\sum_{j=1}^{N_E} \exp(h_j(x))}
$$

**Top-K 路由**是最主流的策略：选择概率最高的 K 个专家（K 通常为 1 或 2）来处理该 token。当 K=1 时，每个 token 只路由到 1 个专家——这就是 Switch Transformer 的核心设计。

### 1.3 稀疏激活：为什么 MoE「参数多但算得省」

理解了专家和路由之后，MoE 的效率奥秘就清晰了。

**参数规模大**：MoE 模型的总参数量 = 基础层参数 + 所有专家的参数之和。当专家数量很大时（如 2048 个），总参数量可以轻松达到万亿级别。

**计算成本低**：但每个 token **只激活 K 个专家**（K 通常为 1 或 2）。如果专家总数是 $N_E$，每个 token 只用了 $K/N_E$ 的专家参数。当 $N_E=2048$、$K=2$ 时，每个 token 只激活了**不到 0.1%** 的专家参数。

这就是「参数规模与计算成本解耦」的核心含义——**模型可以拥有海量参数，但每次前向传播的计算量却只相当于一个小得多的模型**。

### 1.4 MoE 在 Transformer 中的部署方式

在实际的大模型架构中，MoE 层并不是替换所有的 FFN 层。大多数模型采用**交错部署**的策略——仅在每 P 层中使用 MoE 层。例如一个 80 层的模型可能只在第 1、3、5、7… 层使用 MoE，其余层仍使用标准 FFN。

这种设计的原因是：并非所有层都需要专家化。浅层可能处理通用特征，深层才需要专业化。交错的部署方式在获得专家优势的同时，避免了模型过度复杂化。

## 2. 专家并行的原理与负载均衡挑战

### 2.1 为什么 MoE 需要第四种并行维度

在 MoE 出现之前，三维并行（DP + TP + PP）已经能够覆盖 Dense 模型的训练需求。但 MoE 引入了新的挑战：**专家参数是独立且不可复制的**。

在数据并行中，每张 GPU 都有一份完整的模型副本——这在 MoE 场景下行不通。因为 MoE 的总参数量可能高达万亿，如果每个 DP 副本都复制一份完整的专家集合，显存会瞬间爆掉。

更关键的是，**专家参数必须在训练过程中独立更新**——每个专家的梯度只能由分配给它的 token 计算得出，不能简单地 AllReduce 共享。

因此 MoE 催生了第四种并行维度——**专家并行（Expert Parallelism，EP）**。EP 的核心思想是：**将不同的专家分布到不同的 GPU 上，每个 token 通过路由机制被发送到对应专家所在的 GPU 上进行计算**。

### 2.2 专家并行的工作原理

EP 的完整工作流程如下。

**第 1 步：专家分布**——在模型初始化阶段，将 $N_E$ 个专家通过哈希算法**均匀分配**到多张 GPU 上。每张 GPU 负责存储和计算分配给它的那部分专家。

**第 2 步：Token 分发（Dispatch）**——当一批 token 到达 MoE 层时，路由机制计算每个 token 应该分配给哪些专家，然后通过 **All-to-All 通信**将每个 token 发送到其目标专家所在的 GPU 上。

**第 3 步：专家计算**——每张 GPU 在本地完成分配给它的专家的前向/反向计算。

**第 4 步：结果聚合（Combine）**——通过另一次 All-to-All 通信，将各专家的输出结果收集回原始 token 所在的 GPU，进行加权求和。

EP 中最重要的通信原语是 **All-to-All**——每个 GPU 都需要向所有其他 GPU 发送数据，同时也从所有其他 GPU 接收数据。这是 EP 通信开销的主要来源。

### 2.3 负载均衡：MoE 训练的最大挑战

负载均衡是 MoE 训练中**最核心、最棘手**的工程挑战。

**问题本质**：在 MoE 训练中，路由机制会根据 token 的特征动态选择专家。如果某些专家因为「擅长」某类 token 而被频繁选中，另一些专家几乎不被使用，就会出现**严重的负载不均**。

**负载不均带来的后果**：

- **计算拖尾（Straggler）**：被频繁选中的专家所在的 GPU 计算量远超其他 GPU，成为整个训练的「木桶短板」。
- **显存压力**：过载的 GPU 可能因显存溢出（OOM）而崩溃。
- **专家坍塌（Routing Collapse）**：最极端的情况下，所有 token 都路由到同一个专家，其他专家完全「饿死」。

**量化影响**：在极端负载不均的情况下，EP 可能导致过载设备上的计算和内存故障。在 DeepSeek-V3 的训练过程中，通信耗时（主要来自 All-to-All）占整体训练时长的比例可达 **50% 以上**。

### 2.4 负载均衡的解决方案

工业界主要采用以下手段解决负载均衡问题。

**方案一：辅助损失（Auxiliary Loss）**。这是最经典的解决方案：在训练目标函数中添加一个**辅助负载均衡损失（Load-Balancing Loss，LBL）**，惩罚路由的不均衡。LBL 的常见定义如下：

$$
\mathcal{L}_{\mathrm{LBL}} = N_E \sum_{i=1}^{N_E} f_i \, p_i
$$

其中 $N_E$ 是专家总数，$f_i$ 是专家 $i$ 被选中的频率，$p_i$ 是专家 $i$ 的平均门控分数。当 $f_i$ 与 $p_i$ 的乘积在所有专家上均匀分布时，LBL 最小。这个损失项会**鼓励路由机制更均匀地分配 token**。

**方案二：专家容量（Expert Capacity）**。为每个专家设置一个**「容量上限」**——即每个专家每批最多能处理的 token 数量。当一个专家达到容量上限后，多余的 token 会被**溢出（Overflow）**到其他专家或丢弃。容量设计需要在「负载均衡」和「信息损失」之间取得平衡：容量太小会丢弃过多 token，容量太大又无法有效限制负载。

**方案三：动态负载重分配**。在训练过程中实时监控各专家的负载，当偏差超过阈值时触发**动态重分配**。例如将过载设备上的部分专家参数和 token 迁移到空闲设备上。最新的研究提出了 **Least-Loaded Expert Parallelism（LLEP）**，它动态地将多余的 token 和相关专家参数从过载设备重路由到未充分利用的设备，可实现**最高 5 倍加速和 4 倍峰值显存降低**。

## 3. DeepSpeed-MoE 与 Switch Transformer 的工程实践

### 3.1 DeepSpeed-MoE：工业级 MoE 训练框架

**DeepSpeed-MoE** 是微软 DeepSpeed 库中专为 MoE 模型设计的训练和推理解决方案。它提供了从训练到推理的端到端支持，是目前最成熟的 MoE 工程框架之一。

**核心能力：多种并行配置**。DeepSpeed-MoE 支持多种并行形式的组合（数据并行、专家并行、张量并行、流水线并行），可以根据模型规模和硬件资源灵活搭配，从而适应从单机到千卡集群的各种部署场景。

**MoE 层 API**。DeepSpeed MoE 提供了简洁的 MoE 层 API，通过指定 `num_experts`（专家数量）和 `ep_size`（专家并行度）来配置 MoE 层：

```python
from deepspeed.moe.layer import MoE

moe_layer = MoE(
    hidden_size=hidden_size,
    num_experts=32,        # 32个专家
    ep_size=4,             # 4路专家并行（4张GPU分摊32个专家）
    k=2,                   # 每个token路由到2个专家
)
```

**性能数据**：DeepSpeed-MoE 在自回归语言模型上实现了 **5 倍训练成本降低**，推理延迟和成本相比现有 MoE 推理方案降低了**最高 7.3 倍**。模型压缩技术可将 MoE 模型尺寸缩小**最高 3.7 倍**。

### 3.2 Switch Transformer：简化路由，极致扩展

**Switch Transformer** 是 Google 在 2021 年提出的 MoE 模型，核心理念是**「极简主义」**——通过简化 MoE 路由机制，实现万亿参数模型的高效训练。

**核心创新：Switch Routing（K=1）**。传统 MoE 采用 Top-K 路由（K 通常为 2），每个 token 需要选择多个专家。Switch Transformer 做了一个看似简单但影响深远的改动：**将 K 从 2 降为 1**——每个 token 仅路由到 **1 个专家**。这个改动带来了三重收益：

1. **路由计算量减半**：从 $O(K \cdot N)$ 降至 $O(N)$。
2. **批处理效率提升**：每个专家获得的 token 批处理量至少翻倍，内存利用率更高。
3. **通信成本降低**：跨设备通信仅需传递单个专家的输出。

**训练稳定性优化**。Switch Transformer 的另一个重要贡献是解决了 MoE 训练的不稳定性问题。此前 MoE 模型在大规模训练中经常出现损失震荡甚至发散。Google 团队提出的解决方案包括：

- **选择性精度**：首次证明了大规模稀疏模型可以**使用 BF16 低精度格式**进行稳定训练，此前业界普遍认为稀疏模型需要更高精度。
- **专家容量与辅助损失的精细调优**：通过系统化的超参数搜索，找到了稳定训练的最佳配置。

**性能数据**：Switch Transformer 在 T5 架构上实现了**最高 7 倍的预训练加速**（同等计算资源下）。基于 T5-XXL 的万亿参数版本实现了 **4 倍加速**。在多语言场景下，在所有 101 种语言上都取得了显著提升。

### 3.3 从 GShard 到 MoE 的工业化之路

MoE 从学术概念到工业落地，经历了一个重要的里程碑——**GShard**。

GShard 是 Google 在 2020 年提出的分布式训练系统，**首次将 MoE 与 Transformer 架构深度结合**。它通过**「专家并行」策略**将 **6000 亿参数的翻译模型**拆分到不同计算节点上训练。GShard 的核心创新包括：

- **条件计算（Conditional Computation）**：只在需要时激活部分专家。
- **自动分片（Automatic Sharding）**：自动将专家参数分布到不同设备。
- **多维度并行**：结合数据并行、模型并行和专家并行。

GShard 的成功证明了 MoE + EP 的技术路线在大规模工业场景中是可行的，为后续的 DeepSpeed-MoE 和 Switch Transformer 铺平了道路。
