# 数据存储与格式优化

## 1. 数据格式选型：TFRecord、Lance、Parquet

### 1.1 为什么文件格式如此重要

在大规模 AI 训练中，数据加载往往成为被忽视的瓶颈。一个朴素但关键的事实是：**选对文件格式可以削减 30%–50% 的训练时间，降低 1%–5% 的存储成本**。

格式的影响之所以这么大，是因为不同格式在**存储布局、压缩方式、读取模式**上有根本差异：

- **行式存储 vs. 列式存储**：行式存储（如 CSV、JSON）适合整行读取，但过滤特定字段时需要扫描全部数据；列式存储（如 Parquet、Lance）按列组织数据，读取特定字段时只需访问对应的列，I/O 效率大幅提升。
- **随机访问 vs. 顺序访问**：训练时通常需要随机打乱数据，这要求格式支持高效随机访问；而传统列式格式（如 Parquet）主要为分析型负载设计，随机访问性能较差。
- **流式就绪**：能够顺序读取而无需随机寻址的格式（如 TFRecord、WebDataset）可以直接从 S3/GCS 进行训练，无需本地副本。

### 1.2 TFRecord：TensorFlow 生态的二进制容器

**TFRecord** 是 Google 为 TensorFlow 设计的二进制数据格式，用于高效存储和读取序列数据。它把数据序列化为二进制记录（Record），每条记录包含一个字节串和若干特征。

**核心优势**：

- **内置压缩**：支持 GZIP、ZSTD 等算法，可显著减少存储空间。
- **流式读取**：设计为顺序读取，适合大规模数据集的流式训练。
- **生态集成**：与 TensorFlow、PyTorch（通过 torchdata）、HuggingFace datasets 集成。

**局限性**：

- **TF-centric**：深度绑定 TensorFlow 生态，在纯 PyTorch 栈中使用略显「隔阂」。
- **隐式 Schema**：模式信息需要通过 `tf.io.parse_example` 解析，不如自描述格式直观。
- **随机访问弱**：本质是顺序存储格式，随机访问效率不高。

**适用场景**：TensorFlow 生态内的生产级训练，尤其是在 Google Cloud 上运行的大规模工作负载。以 PyTorch 为主的团队，WebDataset（基于 tar）通常更自然。

### 1.3 Parquet：数据湖的事实标准

**Apache Parquet** 是当前数据湖生态中使用最广泛的列式存储格式，在 AWS、Azure 和 Google 数据湖中占据主导地位。

**核心优势**：

- **列式存储**：按列组织数据，读取特定字段只需访问对应列，I/O 效率远高于行式格式。
- **自描述 Schema**：文件内部嵌入字段名称和类型，保证跨代码版本的兼容性。
- **丰富的压缩支持**：Snappy、ZSTD、LZ4 等。
- **生态广泛**：与 Spark、Pandas、PyArrow、HuggingFace datasets 集成。

**Parquet 在 LLM 训练中的崛起**：近年来 Parquet 在 LLM 数据管道中的地位显著提升。一份行业报告指出，**Parquet 的使用并不限于强化学习（RLHF）阶段，而是贯穿 LLM 数据生命周期的所有阶段——预训练、监督微调（SFT）和 RLHF**。把训练数据集存为 Parquet 并配合本地 SSD 缓存热点数据，可以显著提升加载速度。

**局限性**：Parquet 的设计初衷是服务批处理 SQL 分析，面对 AI 场景时暴露短板：

- **随机访问性能差**：它需要连续读取数据范围，对「搜索与检索」这类随机访问很不友好。
- **大数据类型效率低**：对多模态数据（长文本、嵌入向量、图像、视频），row group 布局在写入大规模数据时会耗尽内存。
- **版本控制能力弱**：缺乏原生数据版本管理。

**适用场景**：结构化数据的批处理分析，以及 LLM 训练数据管道中的中间存储（如预处理后的数据湖）。对频繁随机访问的 AI 训练场景，Parquet 正被新一代格式挑战。

### 1.4 Lance：为 AI 而生的新一代列式格式

**Lance** 是专为 AI 工作负载设计的开源列式数据格式，由 LanceDB 公司开发维护。其核心理念是：**Parquet 在 AI 与机器学习场景下已经显得过时，需要一个额外的、互补的格式**。Lance 不只是一层文件格式，它同时提供**文件格式层、表格式层和二级索引**。

**关键优势**：

1. **高性能随机访问**：既保证比 Parquet 更快的扫描，也保证极快的随机访问，官方宣称随机访问比 Parquet **快 100 倍**。
2. **多模态数据友好**：能高效存储并随机访问大规模多模态数据（文本、图像、音视频、向量嵌入）。
3. **向量检索原生支持**：内置向量搜索，可在 1 毫秒内找到最近邻居，并把 OLAP 查询与向量搜索结合。
4. **版本控制**：提供类似 Apache Iceberg 的数据湖管理能力，包括原子事务和多版本控制。

**定位与生态**：Lance 的目标不是替代 Parquet 和 Iceberg，而是与之协同——「Lance for AI, Iceberg for BI」：分析型工作负载仍存于 Iceberg/Parquet，AI 密集型数据集（搜索、训练、推理）使用 Lance。

**适用场景**：多模态 AI 训练、向量检索、需要频繁随机访问的大规模数据集。纯文本的 LLM 预训练，Parquet + WebDataset 的组合仍然成熟；图像-文本、视频-音频等多模态场景，Lance 优势更明显。

### 1.5 三种格式的对比总结

| 格式 | 布局 | 随机访问 | 多模态 | 定位 |
|---|---|---|---|---|
| TFRecord | 二进制记录、顺序 | 弱 | 一般 | TensorFlow 生态 |
| Parquet | 列式、row group | 差 | 弱 | 数据湖、批处理分析 |
| Lance | 列式 + 索引，含表格式 | 强（官方称快 100×） | 强 | AI 训练、向量检索 |

**选型建议**：

- **TensorFlow 生态** → **TFRecord**。
- **结构化数据湖 + 批处理** → **Parquet**。
- **多模态 AI 训练 + 向量检索** → **Lance**。
- **PyTorch + 大规模预训练** → **WebDataset（tar）+ Parquet（元数据）** 的组合。

## 2. 数据去重与质量清洗对训练效率的影响

数据格式决定数据「怎么存」，数据质量决定数据「值不值得存」。在大模型时代，**数据质量和模型性能之间的关系已经从「锦上添花」变成「生死攸关」**。

### 2.1 重复数据的三大危害

**危害一：浪费资源**。冗余数据会增加训练时间、成本和能耗。如果一个数据集中有 10% 的重复内容，意味着 10% 的计算资源被浪费在重复学习上；在千卡集群上，这可能是每天数万美元的额外成本。

**危害二：降低模型泛化能力**。模型可能过度拟合重复内容，限制对新信息的泛化——就像教孩子时反复重复同样的课程，却跳过了其他重要主题。

**危害三：记忆效应与隐私风险**。重复内容会增加模型逐字记忆和复制特定文本的机会，可能导致隐私泄露或版权问题；训练集与测试集之间的重复还会意外夸大性能指标，误导评估。

### 2.2 去重技术的演进

面对 TB 甚至 PB 级语料库，传统成对比较在计算上不可行。业界发展出三个层次的去重方法：

**精确匹配（Exact Matching）**：通过哈希算法（如 MD5、SHA）识别完全相同的重复数据。最基础、计算效率高，但只能识别完全一致的重复。

**近似匹配（Approximate Matching）**：使用 **MinHash LSH（位置敏感哈希）** 和 Jaccard 相似度查找「接近重复」的内容。MinHash 把每个文档拆成重叠的单词或字符序列（k-shingles），通过多个哈希函数生成紧凑的「指纹」（签名），从而在大规模数据集上高效估计相似性。它平衡了召回率与精度，使大规模去重切实可行。

**语义匹配（Semantic Matching）**：用向量嵌入识别含义相似的内容。精度最高，但计算开销也最大。

实践中，**精确匹配 + MinHash LSH 近似匹配**的组合是目前大规模预训练数据去重的主流方案。

### 2.3 数据质量筛选：从人工规则到自动化评估

去重解决「重复」，质量筛选解决「低质量」——网页抓取的数据中充斥着广告、破碎的 HTML 标签、无意义的乱码。

**传统方法**：人工筛选数据源，或对不同来源编写启发式规则（基于长度、特殊字符比例、困惑度等）。工作量大且难以规模化。

**基于分类器的质量过滤（CQF）**：目前最广泛采用的方法，已纳入 GPT-3、LLaMA、PaLM 等模型的预训练流程。核心思路是训练一个二元分类器区分预训练数据与一个小规模高质量数据集，为每个文档打质量分，只保留高分文档。

但 2025 年的研究对这一方法提出了质疑：Apple 的研究表明，**CQF 虽然提升了下游任务性能，但并不一定增强在高质量数据集上的语言建模能力**——它在过滤低质量数据的同时，也隐式过滤了高质量数据集本身。这提醒我们：**质量筛选不是简单地「过滤掉坏的」，而是要理解什么数据对模型学习真正有价值**。

**自动化数据评估的新范式**：Google DeepMind 的 **DataRater** 代表了新方向——用**元学习**自动学习筛选或混合数据流的标准，通过元梯度（依据数据与性能之间的联系计算）训练。实验表明，经 DataRater 筛选的数据可**减少高达 46.6% 的训练计算量**，同时提高最终性能。

### 2.4 质量清洗对训练效率的量化影响

**维度一：算力节省**。高质量筛选可直接减少训练所需浮点运算次数。DataRater 的实验表明，优化后的筛选可**减少高达 46.6% 的净计算量**——同样的模型可以在不到一半的时间内训练完成。

**维度二：模型性能提升**。预训练数据质量直接决定模型的知识深度与推理能力上限。中科院与阿里 Qwen 团队提出的 RefineX 框架，通过对预训练数据做程序化精炼，使从头预训练的模型在下游任务上**平均提高 7.2%**。

更深层的洞察是：**数据筛选正在从「静态过滤」走向「动态评估」**。传统离线筛选通过硬过滤或重采样改变数据集大小，往往牺牲多样性、损害泛化能力；最新研究提出**在线重加权（Online Reweighting）** 范式——在训练过程中通过损失加权动态调整样本重要性，而不是静态预处理。这种方法在指令微调和大型预训练中均取得了比离线方法更强的跨基准泛化能力。

## 3. 在线数据增强与离线预处理的权衡

数据增强是提升泛化能力的重要手段，但工程上一个经典权衡是：**增强操作应该在数据加载时在线执行，还是在数据存储前离线完成？**

### 3.1 离线预处理（Offline Preprocessing）

**定义**：训练开始前，把所有数据增强操作（图像旋转、裁剪、色彩抖动；文本回译、同义词替换等）应用到原始数据上，将增强后的数据**直接存储**，训练时直接加载。

**优点**：训练时零开销；可复现性强（数据集固定）；便于调试。

**缺点**：存储成本高（每个样本生成 5 个版本，存储增加 5 倍）；灵活性差（策略定下难调整）；多样性受限（每个 epoch 看到相同的增强样本）。

### 3.2 在线数据增强（Online Data Augmentation）

**定义**：训练过程中每次读取批次时**实时**应用增强。

**优点**：无限多样性（每个 epoch 每个样本都可不同）；灵活性高（随时调整策略）；存储效率高（只存原始数据）。

**缺点**：CPU/GPU 开销（实时执行可能成为新瓶颈）；不确定性（影响实验可复现性）；需要优化（复杂增强如随机裁剪 + 旋转 + 色彩抖动容易拖慢训练）。

### 3.3 混合策略：预计算 + 在线轻量增强

实际大规模训练中，纯粹的离线或在线往往都不是最优解，业界普遍采用**混合策略**。

**第一步：离线预处理「重」操作**。把计算密集型增强预先完成并存储：

- 图像的**解码、缩放、裁剪**到固定尺寸。
- 文本的**分词（Tokenization）**，把文本转成整数 ID 序列。
- 多模态数据的**对齐和打包**。

这些操作的共同特点是计算量大、每个样本只需执行一次、结果可复用。

**第二步：在线执行「轻」操作**。训练时实时执行轻量级随机增强：

- 图像的**随机翻转、色彩抖动**。
- 文本的**随机掩码（Masking）** 或**丢弃（Dropout）**。
- 批次的**随机打乱（Shuffle）**。

这种混合策略把 **80% 的预处理成本前置到离线阶段**，训练时只承担 20% 的轻量操作开销，既保证训练效率，又保留了增强的随机性。

### 3.4 预分词（Pre-tokenization）：一个关键的最佳实践

在 LLM 训练中，**预分词**是离线预处理里最重要的一项优化。

**做法**：在数据准备阶段，把原始文本通过分词器转换为整数 ID 序列，再将 ID 序列存入数据文件。

**收益**：可以把每个 epoch 的预处理时间**降低 2–5 倍**。不做预分词时，每次 epoch 都要重新运行分词器——对数万亿 token 的数据集，这是巨大的计算浪费。

**工程实践**：

- 在 WebDataset 中，把分词后的 token IDs 作为 `.npy` 或 `.bin` 文件存进 tar 包。
- 在 Parquet 中，把 token IDs 存为数组类型的列。
- 在 Lance 中，向量化的 token 序列是原生支持的数据类型之一。

### 3.5 决策框架

```text
第1步：增强操作的计算成本高吗？
├── 高（如图像解码、分词、特征提取）→ 离线预处理
└── 低（如随机翻转、轻微色彩抖动）→ 在线执行

第2步：存储成本是否可接受？
├── 可接受 → 可以离线生成多个增强版本
└── 不可接受 → 在线执行增强，或采用混合策略

第3步：是否需要实验灵活性？
├── 是（频繁调整增强策略）→ 偏向在线
└── 否（策略已稳定）→ 偏向离线

第4步：训练时的CPU资源是否充裕？
├── 是 → 可以在线执行更多增强
└── 否 → 尽可能将操作前置到离线
```
