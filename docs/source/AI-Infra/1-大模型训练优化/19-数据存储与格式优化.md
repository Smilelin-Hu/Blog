# 数据存储与格式优化

### 1.1. 为什么文件格式如此重要
在大规模AI训练中，数据加载往往成为被忽视的瓶颈。一个朴素但关键的事实是：**选择的文件格式可以削减30-50%的训练时间，降低1%-5%的存储成本**。
为什么格式的影响如此之大？因为不同的格式在**存储布局、压缩方式、读取模式**上有根本性差异：
- **行式存储 vs. 列式存储**：行式存储（如CSV、JSON）适合整行读取，但过滤特定字段时需要扫描全部数据；列式存储（如Parquet、Lance）按列组织数据，读取特定字段时只需访问对应的列，I/O效率大幅提升。
- **随机访问 vs. 顺序访问**：训练时通常需要随机打乱数据，这就要求格式支持高效的随机访问；而传统的列式格式（如Parquet）主要为分析型工作负载设计，随机访问性能较差。
- **流式就绪**：能够顺序读取而无需随机寻址的格式（如TFRecord、WebDataset）可以直接从S3/GCS进行训练，无需本地副本。
### 1.2. TFRecord：TensorFlow生态的二进制容器
**TFRecord**是Google为TensorFlow设计的二进制数据格式，用于高效地存储和读取序列数据。它将数据序列化为二进制记录（Record），每个记录包含一个字节串和若干特征。
**核心优势**：
- **内置压缩**：支持GZIP、ZSTD等压缩算法，可显著减少存储空间
- **流式读取**：设计为顺序读取，适合大规模数据集的流式训练
- **生态集成**：与TensorFlow、PyTorch（通过torchdata）、HuggingFace datasets无缝集成
**局限性**：
- **TF-centric**：设计上深度绑定TensorFlow生态，在纯PyTorch栈中使用略显“隔阂”
- **隐式Schema**：模式信息需要通过`tf.io.parse_example`解析，不如自描述格式直观
- **随机访问弱**：本质上是顺序存储格式，随机访问效率不高
**适用场景**：
TFRecord最适合**TensorFlow生态内的生产级训练**，尤其是在Google Cloud上运行的大规模工作负载。对于PyTorch为主的团队，WebDataset（基于tar）通常是更自然的选择。
### 1.3. Parquet：数据湖的事实标准
**Apache Parquet**是当前数据湖生态中使用最广泛的列式存储格式，在AWS、Azure和Google数据湖中占据主导地位。
**核心优势**：
- **列式存储**：按列组织数据，读取特定字段时只需访问对应的列，I/O效率远高于行式格式
- **自描述Schema**：文件内部嵌入字段名称和类型，保证跨代码版本的兼容性
- **丰富的压缩支持**：支持Snappy、ZSTD、LZ4等多种压缩算法
- **生态广泛**：与Spark、Pandas、PyArrow、HuggingFace datasets等无缝集成
**Parquet在LLM训练中的崛起**
近年来，Parquet在LLM训练数据管道中的地位显著提升。一份行业报告指出，**Parquet的使用并不仅限于强化学习（RLHF）阶段，而是贯穿LLM数据生命周期的所有阶段——包括预训练、监督微调（SFT）和RLHF**。
在实践中，将训练数据集存储为Parquet格式，结合本地SSD缓存热点数据，可以显著提升数据加载速度。
**局限性**：
Parquet的设计初衷是服务批处理SQL分析，面对AI场景时暴露出明显的短板：
- **随机访问性能差**：Parquet不是为随机访问设计的。LanceDB的创始人指出，Parquet“对于搜索和检索来说真的很糟糕”，因为它需要随机访问，而Parquet的设计适合“读取连续的数据范围”。
- **大数据类型效率低**：对于多模态数据（长文本、嵌入向量、图像、视频），Parquet的row group布局会导致在写入大规模数据时耗尽内存。
- **版本控制能力弱**：缺乏原生的数据版本管理能力。
**适用场景**：
Parquet适合**结构化数据的批处理分析**，以及**LLM训练数据管道中的中间存储**（如预处理后的数据湖）。对于需要频繁随机访问的AI训练场景，Parquet正在被新一代格式挑战。
### 1.4. Lance：为AI而生的新一代列式格式
**Lance**是专为AI工作负载设计的开源列式数据格式，由LanceDB公司开发并维护。其创始人是pandas库的原始贡献者之一。
**核心设计理念**：
Lance的核心理念是：**Parquet在AI和机器学习场景下已经显得过时，需要一个额外的、互补的格式来更好地满足这些需求**。Lance不只是一种文件格式，它同时提供了**文件格式层、表格式层和二级索引**，三位一体地解决AI数据管理问题。
**关键优势**：
1. **高性能随机访问**：Lance针对AI工作负载的访问模式进行了优化——既保证比Parquet更快的扫描，也保证极快的随机访问。官方宣称Lance的随机访问比Parquet**快100倍**。
2. **多模态数据友好**：Lance能够高效存储和随机访问大规模、多模态的数据（文本、图像、音视频、向量嵌入等），而Parquet对此“根本没有优化”。
3. **向量检索原生支持**：Lance内置了对向量搜索的支持，可在1毫秒内找到最近邻居，并将OLAP查询与向量搜索相结合。
4. **版本控制**：Lance提供了类似Apache Iceberg的数据湖管理功能，包括原子事务和多版本控制。
**定位与生态**：
Lance的创始人明确表示，Lance的目标**不是替代Parquet和Iceberg，而是与之协同工作**：“Lance for AI, Iceberg for BI”——分析型工作负载仍存储在Iceberg/Parquet中，而AI密集型的数据集（搜索、训练、推理）则使用Lance。
**适用场景**：
Lance最适合**多模态AI训练、向量检索、以及需要频繁随机访问的大规模数据集**。对于纯文本的LLM预训练，Parquet+WebDataset的组合仍然是成熟的选择；但对于图像-文本、视频-音频等多模态场景，Lance的优势更加明显。

## 2. 数据去重与质量清洗对训练效率的影响
数据格式决定了数据“怎么存”，而数据质量决定了数据“值不值得存”。在大模型时代，**数据质量和模型性能之间的关系，已经不再是“锦上添花”，而是“生死攸关”**。
### 2.1. 重复数据的三大危害
原始训练数据往往包含大量冗余。当重复内容出现在训练数据中时，会产生几个严重问题：
**危害一：浪费资源**
冗余数据会增加训练时间、成本和能耗。如果一个数据集中有10%的重复内容，意味着10%的计算资源被浪费在了重复学习上。在千卡集群上，这可能是每天数万美元的额外成本。
**危害二：降低模型泛化能力**
模型可能会过度拟合重复内容，从而限制了对新信息的泛化能力。就像教孩子时一遍又一遍地重复同样的课程，却跳过了其他重要的主题。
**危害三：记忆效应与隐私风险**
重复内容会增加模型逐字记忆和复制特定文本的机会，可能导致隐私泄露或版权问题。此外，训练集和测试集之间的重复内容会意外夸大性能指标，误导评估。
### 2.2. 去重技术的演进
面对TB甚至PB级别的预训练语料库，传统的成对比较方法在计算上完全不可行。业界发展出了三种层次的去重方法：
**精确匹配（Exact Matching）**
通过哈希算法（如MD5、SHA）识别完全相同的重复数据。这是最基础的去重手段，计算效率高，但只能识别完全一致的重复。
**近似匹配（Approximate Matching）**
使用**MinHash LSH（位置敏感哈希）** 和Jaccard相似度等算法查找“接近重复”的内容。MinHash将每个文档拆分为重叠的单词或字符序列（k-shingles），通过多个哈希函数生成紧凑的“指纹”（签名），从而在大规模数据集中高效估计文档相似性。这种方法在平衡召回率和精度的同时控制了成本，使得大规模重复数据删除切实可行。
**语义匹配（Semantic Matching）**
使用向量嵌入识别含义相似的内容。这种方法精度最高，但计算开销也最大——通过嵌入模型生成向量增加了大量开销。
在实践中，**精确匹配 + MinHash LSH近似匹配**的组合是目前大规模预训练数据去重的主流方案。
### 2.3. 数据质量筛选：从人工规则到自动化评估
去重解决的是“重复”问题，而质量筛选解决的是“低质量”问题——网页抓取的数据中充斥着广告、破碎的HTML标签、无意义的乱码等噪声。
**传统的质量筛选方法**：
人工筛选数据源，或对不同数据源编写启发式规则（如基于长度、特殊字符比例、语言模型困惑度等）筛选出高质量数据。这种方法工作量巨大，且难以规模化。
**基于分类器的质量过滤（CQF）**：
CQF是目前最广泛采用的数据质量筛选方法，已被纳入GPT-3、LLaMA、PaLM等模型的预训练流程中。其核心思路是：训练一个二元分类器来区分预训练数据和一个小的、高质量的数据集，为每个文档分配质量分数，只保留得分最高的文档。
然而，2025年的研究对这一方法提出了质疑。Apple的研究表明，**CQF虽然提升了下游任务性能，但并不一定增强在高质量数据集上的语言建模能力**——CQF在过滤低质量数据的同时，也隐式地过滤了高质量数据集本身。这提醒我们：**质量筛选不是简单地“过滤掉坏的”，而是要理解什么数据对模型学习真正有价值**。
**自动化数据评估的新范式**：
Google DeepMind开发的**DataRater**代表了数据质量筛选的新方向。DataRater使用**元学习**自动学习筛选或混合数据流的标准，通过元梯度（根据数据与性能之间的联系进行计算）进行训练。实验表明，经过DataRater筛选的数据可以**减少高达46.6%的训练计算量**，同时提高语言模型的最终性能。
### 2.4. 质量清洗对训练效率的量化影响
数据质量清洗对训练效率的影响可以从两个维度量化：
**维度一：算力节省**
高质量的数据筛选可以直接减少训练所需的浮点运算次数。DataRater的实验表明，经过优化的数据筛选可以**减少高达46.6%的净计算量**。这意味着同样的模型可以在不到一半的时间内完成训练。
**维度二：模型性能提升**
预训练数据的质量直接决定了模型的知识深度与推理能力上限。中科院与阿里Qwen团队提出的RefineX框架，通过对预训练数据进行程序化精炼，使得从头预训练的模型在下游任务上**平均提高了7.2%**。
一个更深层的洞察是：**数据筛选正在从“静态过滤”走向“动态评估”**。传统的离线筛选方法通过硬过滤或重采样改变数据集大小，往往牺牲数据多样性、损害泛化能力。而最新的研究提出了**在线重加权（Online Reweighting）** 的范式——在训练过程中通过损失加权动态调整样本重要性，而不是静态的预处理。这种方法在指令微调和大型预训练中均取得了比离线方法更强的跨基准泛化能力。
## 3. 在线数据增强与离线预处理的权衡
数据增强是提升模型泛化能力的重要手段。但在工程实践中，我们面临一个经典的权衡：**增强操作应该在数据加载时在线执行，还是在数据存储前离线完成？**
### 3.1. 离线预处理（Offline Preprocessing）
**定义**：在训练开始之前，将所有数据增强操作（如图像旋转、裁剪、色彩抖动；文本的回译、同义词替换等）应用到原始数据上，将增强后的数据**直接存储**，训练时直接加载增强后的样本。
**优点**：
- **训练时零开销**：数据加载管道只需要读取已增强的数据，不消耗额外的CPU/GPU计算资源
- **可复现性强**：增强后的数据集是固定的，每次训练使用相同的数据
- **便于调试**：可以直观地检查增强后的数据质量
**缺点**：
- **存储成本高**：增强会成倍增加数据集的存储大小（如每个原始样本生成5个增强版本，存储增加5倍）
- **灵活性差**：一旦增强策略确定，难以在训练过程中调整
- **多样性受限**：增强后的数据集是固定的，模型在每个epoch看到的是相同的增强样本
### 3.2. 在线数据增强（Online Data Augmentation）
**定义**：在训练过程中，每次从数据加载器读取一个批次时，**实时**应用数据增强操作。
**优点**：
- **无限多样性**：每个epoch每个样本都可以看到不同的增强版本，相当于拥有无限大的数据集
- **灵活性高**：可以随时调整增强策略，无需重新生成数据集
- **存储效率高**：只存储原始数据，不额外占用存储空间
**缺点**：
- **CPU/GPU开销**：增强操作需要在训练过程中实时执行，可能成为新的瓶颈
- **不确定性**：每次训练的数据不完全相同，可能影响实验的可复现性
- **需要优化**：如果增强操作复杂（如图像的随机裁剪+旋转+色彩抖动），需要仔细优化以避免拖慢训练
### 3.3. 混合策略：预计算 + 在线轻量增强
在实际的大规模训练中，纯粹的“离线”或“在线”往往都不是最优解。业界普遍采用的是一种**混合策略**：
**第一步：离线预处理“重”操作**
将计算密集型的增强操作**预先完成并存储**。例如：
- 图像的**解码、缩放、裁剪**到固定尺寸
- 文本的**分词（Tokenization）** 将文本转换为整数ID序列
- 多模态数据的**对齐和打包**
这些操作的特点是：计算量大、对每个样本只需执行一次、结果可复用。
**第二步：在线执行“轻”操作**
在训练时实时执行轻量级的随机增强：
- 图像的**随机翻转、色彩抖动**（计算量小，可实时完成）
- 文本的**随机掩码（Masking）** 或**丢弃（Dropout）**
- 批次的**随机打乱（Shuffle）**
这种混合策略的优势在于：**将80%的预处理成本前置到离线阶段，训练时只承担20%的轻量操作开销**，既保证了训练效率，又保留了数据增强的随机性。
### 3.4. 预分词（Pre-tokenization）：一个关键的最佳实践
在LLM训练中，**预分词**是离线预处理中最重要的一项优化。
**做法**：在数据准备阶段，将原始文本通过分词器（Tokenizer）转换为整数ID序列，然后将这些ID序列存储在数据文件中。
**收益**：这可以将每个epoch的预处理时间**降低2-5倍**。如果不做预分词，每次epoch都需要重新运行分词器——对于数万亿token的数据集，这是巨大的计算浪费。
**工程实践**：
- 在WebDataset中，可以将分词后的token IDs作为`.npy`或`.bin`文件存储在tar包中
- 在Parquet中，可以将token IDs存储为数组类型的列
- 在Lance中，向量化的token序列是其原生支持的数据类型之一
### 3.5. 决策框架
在选择预处理策略时，可以遵循以下决策树：
```text
第1步：增强操作的计算成本高吗？
├── 高（如图像解码、分词、特征提取）→ 离线预处理
└── 低（如随机翻转、轻微色彩抖动）→ 在线执行

第2步：存储成本是否可接受？
├── 可接受 → 可以离线生成多个增强版本
└── 不可接受 → 在线执行增强，或采用混合策略

第3步：是否需要实验灵活性？
├── 是（频繁调整增强策略）→ 偏向在线
└── 否（策略已稳定）→ 偏向离线

第4步：训练时的CPU资源是否充裕？
├── 是 → 可以在线执行更多增强
└── 否 → 尽可能将操作前置到离线
```
