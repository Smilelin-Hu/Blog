## 1. 理解性能指标与 MFU

### 1.1 为什么 MFU 比 GPU 利用率更重要

传统监控显示的 GPU 利用率只反映设备是否在工作，却无法区分有效计算与无效等待。例如：

- GPU 利用率 95%，但大量时间花在数据搬运上 → 有效计算占比低。
- GPU 利用率 60%，但实际在高效执行矩阵乘法 → 有效计算占比可能反而更高。

**MFU（Model FLOPs Utilization，模型算力利用率）**直接衡量硬件资源在训练任务中的有效利用率。它的核心价值是：回答的不是「GPU 忙不忙」，而是「GPU 忙得有没有价值」。

### 1.2 MFU 的计算方法

**方法一：基于每步耗时**

$$
\mathrm{MFU} = \frac{\text{Model FLOPs per iteration}}{\text{Hardware Peak FLOPs} \times \text{Time per iteration}}
$$

- **Model FLOPs per iteration**：每步前向 + 反向的理论计算量。
- **Hardware Peak FLOPs**：GPU 理论峰值算力。
- **Time per iteration**：profiler 测量的每步实际耗时。

**方法二：基于吞吐量**

$$
\mathrm{MFU} = \frac{\text{实测吞吐（tokens/s）} \times \text{每 token 前反向 FLOPs}}{\text{Hardware Peak FLOPs} \times \text{GPU 数}}
$$

**7B 模型的 FLOPs 估算**。对 Transformer，每 token 每层的前向 FLOPs 近似为 $2 \times \text{hidden\_size} \times (12 \times \text{hidden\_size} + 4 \times \text{hidden\_size})$，反向约为前向的 2 倍。更实用的方式是使用 `ptflops` 或直接查阅模型文档。对 Llama-2-7B，在序列长度 2048、batch size 等配置下，单步 Model FLOPs 约为 **1.5–2 × 10¹⁴**。

**A100 的理论峰值**：

| 精度 | 稠密 | 稀疏 |
|---|---|---|
| FP16/BF16 | 312 TFLOPS | 624 TFLOPS |
| FP32 | 19.5 TFLOPS | — |

稀疏峰值只在结构化稀疏真正被利用时才可达，算 MFU 时通常用稠密值。

### 1.3 MFU 的行业参考值

| 场景 | 一般水平 | 优秀水平 |
|---|---|---|
| 单卡/小规模微调 | 25%–35% | 40%–50% |
| 百亿参数、百卡级 | 35%–45% | 50%–60% |
| 千亿参数、千卡级 | 40%–50% | 55% 左右 |
| 万亿/MoE 大规模 | 30%–40% | 45%+ |

```python
from torch.profiler import profile, ProfilerActivity, record_function, schedule

WAIT, WARMUP, ACTIVE = 1, 2, 3
SCHEDULE = schedule(wait=WAIT, warmup=WARMUP, active=ACTIVE, repeat=1)

profiler = profile(
    activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
    schedule=SCHEDULE,
    on_trace_ready=torch.profiler.tensorboard_trace_handler("./output/profiler_logs"),
    record_shapes=True,
    with_stack=True,

global_step = 0
for epoch in range(args.num_train_epochs):
    for batch in dataloader:
        with profiler:
            inputs = batch["input_ids"].to(local_rank)
            labels = batch["labels"].to(local_rank)

            with record_function("forward"):
                outputs = model(inputs)
                loss = criterion(outputs, labels)

            with record_function("backward"):
                loss.backward()

            with record_function("optimizer"):
                optimizer.step()
                optimizer.zero_grad(set_to_none=True)

        profiler.step()
        global_step += 1

        if global_step >= args.profiling_steps + 10:  # wait+warmup+active
            break

profiler.export_chrome_trace(f"{args.output_dir}/trace.json")
print(f"Profiling完成！结果保存在 {args.output_dir}/profiler_logs")
```

### 2.4 计算基线 MFU

```python
def estimate_llama2_7b_flops(batch_size, seq_len, hidden_size=4096, num_layers=32):
    # 每层Attention的FLOPs（QKV投影 + 注意力 + 输出投影）
    attn_flops = 2 * batch_size * seq_len * hidden_size * hidden_size * 4
    attn_flops += 2 * batch_size * seq_len * seq_len * hidden_size  # QK^T 与 AV

    # 每层FFN的FLOPs（Llama用SwiGLU，约3个投影）
    ffn_flops = 2 * batch_size * seq_len * hidden_size * hidden_size * 3

    per_layer_flops = attn_flops + ffn_flops
    total_flops = num_layers * per_layer_flops * 3  # 前向+反向 ≈ 3倍前向
    return total_flops


def calculate_mfu(model_flops, step_time, gpu_count, peak_flops):
    return model_flops / (peak_flops * gpu_count * step_time)


# 示例
model_flops = 1.8e14  # 7B模型单步FLOPs（示例值）
step_time = 0.85      # 每步耗时（秒）
gpu_count = 8
peak_flops = 312e12   # A100 FP16理论峰值（312 TFLOPS）

mfu = calculate_mfu(model_flops, step_time, gpu_count, peak_flops)
print(f"Baseline MFU: {mfu:.1%}")
```

## 3. 瓶颈识别

### 3.1 使用 PyTorch Profiler 分析


典型输出长这样（列有 CPU 自身耗时、CPU 总耗时、CUDA 自身耗时、CUDA 总耗时、调用次数）：

```text

```

### 3.2 识别四大类瓶颈

**类别一：计算瓶颈（Compute-Bound）**

- **判断标准**：`aten::mm`、`aten::bmm` 在 CUDA 总时间中占比超过 50%；GPU SM 效率 > 80%。
- **典型特征**：计算密度高，计算单元满负荷运转。
- **优化方向**：混合精度、Tensor Core 优化、算子融合。

**类别二：访存瓶颈（Memory-Bound）**

- **判断标准**：`aten::add`、`aten::mul`、`aten::layer_norm`、`aten::dropout` 等逐元素操作占比高；SM 效率低（<60%）但显存带宽利用率高。
- **典型特征**：大量小算子频繁读写 HBM，计算单元等数据。
- **优化方向**：算子融合（`torch.compile`）、减少中间结果、FlashAttention。

**类别三：通信瓶颈（Communication-Bound）**

- **判断标准**：`nccl:all_reduce`、`nccl:all_gather` 等占比超过 15%–20%；多卡时 GPU 利用率随卡数增加显著下降。
- **典型特征**：梯度同步成为主要耗时。
- **优化方向**：梯度分桶调优、NCCL 配置优化、通信与计算重叠。

**类别四：数据瓶颈（Data-Bound）**

- **判断标准**：CPU 侧（数据加载、预处理）耗时显著；GPU 利用率周期性下降。
- **典型特征**：GPU 在等 CPU 准备数据。
- **优化方向**：增加 `num_workers`、开启 `pin_memory`、预分词。

## 4. 实施优化

根据识别出的瓶颈类型选择对应策略。**每次只实施一项优化，重新测量效果，再继续下一项**——这是科学调优的核心原则。

### 4.1 计算密集型瓶颈的优化

**优化 1：启用 BF16 混合精度**。在 DeepSpeed 配置中切换：

```json
{
    "fp16": { "enabled": false },
    "bf16": { "enabled": true }
}
```

**预期收益**：训练速度提升 1.5–2.5 倍，显存占用降低约 40%。

**优化 2：使用 FlashAttention**。它把 Attention 的 HBM 访问从 $O(N^2)$ 降到 $O(N^2/M)$，显著加速长序列训练。

```bash
pip install flash-attn --no-build-isolation
```

```python
model = AutoModelForCausalLM.from_pretrained(
    args.model_name_or_path,
    torch_dtype=torch.bfloat16,
    attn_implementation="flash_attention_2",  # 启用FlashAttention
    use_cache=False,
)
```

**预期收益**：Attention 计算加速 2–4 倍（序列越长收益越大）。

**优化 3：用 `torch.compile` 做算子融合**。它会把相关操作组合成单个高效的 Triton 内核，让数据保留在快速寄存器中并减少内核启动开销。

```python
# 在模型加载后
model = torch.compile(model, mode="reduce-overhead")
```

三种模式：`default`（平衡编译时间与运行性能）、`reduce-overhead`（减少 Python 开销，适合训练）、`max-autotune`（极致优化，编译最慢）。**预期收益**：10%–30% 端到端加速。

**优化 4：确保矩阵维度是 8 的倍数**。Tensor Core 要求矩阵维度为 8 的倍数才能发挥最大效率，检查 `hidden_size`、`num_heads` 等配置。

### 4.2 访存密集型瓶颈的优化

**优化 1：算子融合（手动或自动）**。除 `torch.compile` 的自动融合，也可手动实现融合算子，例如把 GeLU 与 Dropout 合成一个内核：

```python
# 未融合版本
def gelu_dropout(x, p=0.1):
    x = F.gelu(x)
    x = F.dropout(x, p=p)
    return x

# 融合版本：用Triton或自定义CUDA kernel把两步写进一个kernel
```

垂直融合把前一个操作的输出直接送入下一个操作，消除中间结果的全局内存读写。**预期收益**：访存密集型操作加速 20%–50%。

**优化 2：启用激活值重计算**。

```json
{
    "activation_checkpointing": {
        "partition_activations": true,
        "cpu_checkpointing": false,
        "contiguous_memory_optimization": true,
        "number_checkpoints": 4
    }
}
```

**预期收益**：显存占用降低 30%–50%，端到端时间增加 15%–25%。

### 4.3 通信密集型瓶颈的优化

**优化 1：调整梯度分桶大小**。

```json
{
    "reduce_bucket_size": 5e8,
    "allgather_bucket_size": 5e8,
    "overlap_comm": true
}
```

更大的桶 → 更少的通信次数 → 更低的延迟开销；但桶过大会延迟通信触发时机、减少重叠机会。

**优化 2：启用通信与计算重叠**。确保 `overlap_comm: true`，让 GPU 在等通信完成的同时继续计算。

**优化 3：NCCL 环境变量调优**。

```bash
export NCCL_IB_DISABLE=0          # 启用InfiniBand
export NCCL_SOCKET_IFNAME=eth0    # 指定网络接口
export NCCL_DEBUG=INFO            # 调试模式（生产环境关闭）
export NCCL_MIN_NCHANNELS=4       # 增加通道数
```

**优化 4：层次化 AllReduce**。数据并行中先用节点内 NVLink 高速聚合，再在节点间用 InfiniBand 同步；这需要把 TP 组限制在同一节点内。

### 4.4 数据瓶颈的优化

**优化 1：调整 DataLoader 参数**。

```python
dataloader = DataLoader(
    dataset,
    batch_size=per_device_batch_size,
    num_workers=8,           # 建议≈CPU物理核心数
    pin_memory=True,         # 加速CPU→GPU传输
    prefetch_factor=4,       # 增加预取深度
    persistent_workers=True, # 跨epoch复用worker
)
```

**优化 2：预分词（Pre-tokenization）**。在数据准备阶段完成分词，训练时直接加载 token IDs：

```python
tokenized_dataset.save_to_disk("data/tokenized")
```

**预期收益**：每个 epoch 的预处理时间降低 2–5 倍。

### 4.5 优化实施顺序建议

```text
第1轮：BF16/FlashAttention（计算路径，收益最大、风险最低）
    ↓ 重新测量
第2轮：torch.compile 或算子融合（访存路径）
    ↓ 重新测量
第3轮：通信桶与 overlap_comm 调参
    ↓ 重新测量
第4轮：激活值重计算（若显存是约束）
    ↓ 重新测量
第5轮：DataLoader 与预分词
    ↓ 最终MFU
```

1. **检查新的 Profiler 输出**：哪些操作现在占比最高？

- 通信占比仍然很高 → 尝试增加 TP 或减少 DP。
- 显存仍有余量 → 可以增加 batch size 提升吞吐。

## 6. 常见问题与排查

### 6.1 Profiler 不输出 CUDA 数据

**现象**：只显示 CPU 操作，没有 CUDA 操作。

**原因与解决**：未正确设置 `activities`，或 CUDA 上下文未初始化。务必同时包含 CPU 与 CUDA：

```python
profiler = profile(
    activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],  # 必须同时包含
    ...
)
```

### 6.2 torch.compile 编译失败

**现象**：报错或训练速度下降。

**解决**：

1. 检查 PyTorch 版本（≥ 2.0）。
2. 尝试 `mode="reduce-overhead"` 而非默认模式。
3. 用 `TORCH_LOGS=+dynamo` 查看编译日志。
4. 识别导致图断裂的操作（如第三方库调用）。

### 6.3 MFU 计算不准确

**现象**：MFU 异常高或低。

**解决**：

1. 确认 GPU 理论峰值是否正确（注意稀疏/稠密差异）。
2. 确认 Model FLOPs 估算是否准确。
3. 确保 profiler 采集的是稳定状态的数据（跳过前 10–20 步）。
4. 用 `torch.cuda.synchronize()` 确保计时准确。

### 6.4 优化后 Loss 不收敛

**现象**：应用优化后出现 NaN 或训练不稳定。

**解决**：

1. 检查 BF16/FP16 的数值稳定性，必要时调整损失缩放。
2. 确认 `torch.compile` 没有改变计算逻辑。
3. 回退优化，逐个启用以定位根源。
