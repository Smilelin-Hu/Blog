# 实战项目：从跑通到调优到方案设计

前五篇是知识，这一篇是交付。三个项目难度递进：先把 7B 训练跑通，再用数据把 MFU 拉起来，最后给千卡集群写一份通信优化方案。

| 项目 | 层次 | 核心能力 | 验收指标 |
|---|---|---|---|
| 项目一 | 入门 | 跑通分布式训练 | 稳定 1000 步，无 OOM、无 Spike，MFU > 35% |
| 项目二 | 进阶 | 数据驱动的性能优化 | 定位至少三类瓶颈，MFU 提升 ≥ 10 个百分点 |
| 项目三 | 专家 | 大规模集群方案设计 | 输出可执行的通信优化方案与验收口径 |

## 1. 项目一：7B 模型的分布式训练

### 1.1 为什么选 7B

7B 是开源模型最常见的一档（LLaMA-2-7B、Qwen-7B、DeepSeek-V2-Lite 等），在 2–8 张 A100/H100 上就能完整跑通，是 AI Infra 最日常的场景。

### 1.2 目标与硬件

目标：

- 在 2–8 张 GPU 上完成 7B 模型的分布式训练（预训练或微调）；
- 使用 DeepSpeed ZeRO-3 或 Megatron-LM；
- 稳定运行至少 1000 步，无 OOM、无 Loss Spike；
- MFU > 35%。

硬件：

- 最低：2 × A100 80 GB；
- 推荐：4–8 × A100/H100 + NVLink；
- 替代：2 张以上 24 GB 卡配合 ZeRO-3 + CPU Offload（能跑，但吞吐会大幅下降）。

### 1.3 环境

```bash
conda create -n llm_train python=3.10 -y
conda activate llm_train

pip install torch==2.1.0 torchvision==0.16.0 torchaudio==2.1.0 \
    --index-url https://download.pytorch.org/whl/cu118
```

要点：PyTorch 版本要和 CUDA 驱动匹配；要用 FlashAttention 一类特性时建议 PyTorch ≥ 2.0；昇腾平台需要装对应的 `torch_npu`。

### 1.4 配置与启动

ZeRO-3 的核心配置项就四组：

```json
{
  "train_batch_size": 64,
  "gradient_accumulation_steps": 4,
  "zero_optimization": {
    "stage": 3,
    "offload_optimizer": { "device": "none" },
    "stage3_gather_16bit_weights_on_model_save": true
  },
  "fp16": { "enabled": false },
  "bf16": { "enabled": true }
}
```

启动脚本的关键是 `--num_processes` 与 `--num_machines` 要和实际拓扑一致，`--mixed_precision=bf16` 要与 config 里的 `bf16` 对齐——两处不一致是新手最常踩的坑。

### 1.5 常见失败原因

1. **OOM 但账算得下**：显存碎片或峰值出现在反向开始（激活全在）；
2. **训练卡在第一步**：NCCL 初始化超时，往往是网卡名、`NCCL_SOCKET_IFNAME` 或防火墙；
3. **Loss 立即 NaN**：BF16/FP16 配置冲突，或数据里有空标签；
4. **MFU 只有个位数**：`num_workers` 太小、数据在机械盘上、或 micro batch 小到 launch 开销占主导；
5. **多机跑不动单机正常**：跨机带宽不足 + TP 放到了节点外。

## 2. 项目二：端到端性能分析并优化到目标 MFU

### 2.1 为什么 MFU 比 GPU Util 更可信

GPU 利用率只反映设备是否在工作，不区分有效计算与无效等待：

- Util 95%，但大量时间在搬数据 → 有效算力占比低；
- Util 60%，但一直在跑高效 GEMM → 有效算力占比可能更高。

MFU 直接衡量硬件在训练任务里的有效利用率：

$$
\text{MFU} = \frac{\text{模型理论 FLOPs}}{\text{实际训练时间} \times \text{GPU 数量} \times \text{单卡峰值 FLOPS}}
$$

理论 FLOPs 用 \(6 \times \text{参数量} \times \text{Token 数}\) 估算，峰值必须声明精度口径（BF16 Dense、是否按稀疏折算）。口径不声明，MFU 就没有可比性。

### 2.2 分析流程

1. **建基线**：固定变量、跳过 Warmup、同步计时，记录 step time / tokens/s / 峰值显存 / NCCL 耗时 / 数据等待；
2. **抓时间线**：`torch.profiler` 看算子级分布，`nsys` 看 Kernel 与通信的时间重叠；
3. **归类瓶颈**：计算受限（SM 忙、Tensor Core 高）、访存受限（HBM 打满、SM 空转）、通信受限（AllReduce 与计算不重叠）、数据受限（GPU 周期性空转）；
4. **单项优化 + 回归**：一次只改一个变量，改完回到第 1 步。

### 2.3 三类瓶颈各一项典型手段

| 瓶颈类型 | 判据 | 典型手段 |
|---|---|---|
| 计算 | Tensor Core 活动高、SM 占用高 | 换更高效的 Attention 实现、提高 micro batch、算子融合 |
| 访存 | HBM 带宽接近峰值、SM 空等 | 提高数据复用（Tiling）、混合精度、减少中间张量 |
| 通信 | AllReduce 占 step 时间比例高 | 调 NCCL 通道数与算法、DP 梯度分桶重叠、改用 ZeRO-1 减少通信 |
| 数据 | GPU 利用率周期性掉坑 | 加 worker、`pin_memory`、预取、把数据搬到本地 NVMe |

### 2.4 验收

MFU 从基线提升至少 10 个百分点，并且**每项优化都要写清「改善了哪个区间、损害了哪个区间」**——只报峰值吞吐的优化报告是不合格的。

## 3. 项目三：千卡集群通信方案设计

### 3.1 规模跃迁带来的质变

8 卡时通信是次要问题，1024 卡时通信是主要矛盾。即使所有硬件指标达标，NCCL 默认的拓扑探测也可能把 32 卡的 pipeline group 放到同一个 Spine 下，导致 AllReduce 频繁跨 Spine、尾延迟飙升。

一个真实复盘：1024 张 H800A 跑 Megatron-LM（DP=8 / TP=4 / PP=32），首次上线 MFU 只有 71%，而预期 85%。Profiler 显示 25% 时间花在 AllReduce 上，P99 尾延迟是 P50 的 4 倍。

### 3.2 要理解的两种拓扑

- **Fat-Tree**：Leaf-Spine 两层（或多层），任意两点的对分带宽一致，但跨 Spine 跳数多、拥塞时尾延迟明显；
- **Dragonfly+**：分组全互联 + 组间光互联，直径更短，但需要全局自适应路由与更精细的负载均衡。

方案设计要回答的是：哪类通信落在哪一层、每层的带宽与延迟预算各是多少、拥塞时靠什么手段保住 P99。

### 3.3 方案要素

1. **拓扑感知放置**：TP 不跨机、EP 限制在超节点内、PP 允许跨机、DP 放最外层；
2. **层次化 AllReduce**：节点内先归约（NVLink/NVLS），节点间只传一次，避免「每个 Rank 都发一份」；
3. **算法选择**：小消息用 Tree、大消息用 Ring/NVLS，按消息大小设阈值；
4. **通信与计算重叠**：梯度分桶、反向即通信、避免同步点把流水线掐断；
5. **辅助手段的适用性**：梯度压缩（如 FP8/量化 AllReduce、Top-k 稀疏）能省带宽，但会引入精度风险与额外计算，千卡场景要先算清「省下的带宽是否大于压缩开销」；
6. **可验收的指标**：MFU、AllReduce 占 step 时间比例、P99/P50 尾延迟比、集合通信带宽利用率。

### 3.4 交付物

- 拓扑与并行映射图（哪个维度落在哪一层网络）；
- 通信瓶颈的测量证据（时间线、带宽曲线、尾延迟分布）；
- 优化项清单与预期收益、风险与回滚方式；
- 验收标准与复现实验脚本。
