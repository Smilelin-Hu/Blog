# 数据并行（Data Parallelism）

## 1. 数据并行的原理与实现（DP/DDP）

### 1.1 核心思想：把数据切开，模型复制

数据并行的思路非常直观：**在多张 GPU 上各保存一份完整的模型副本，将训练数据切分成多份，每张 GPU 处理一份数据，然后同步梯度来更新所有副本。**

整个过程可以分解为三个步骤：

1. **前向传播**：每张 GPU 独立计算自己那份数据的损失（Loss）。
2. **反向传播**：每张 GPU 独立计算梯度。
3. **梯度同步**：将所有 GPU 的梯度汇总（通常是求平均），得到全局梯度，用于统一更新模型参数。

这个模式的核心优势是**实现简单**——模型代码完全不需要改动，只需要把数据切分一下，再加一个梯度同步的环节。但代价是**显存冗余**——每张卡上都存了一份完整的模型参数、梯度和优化器状态，大模型训练时显存压力极大（这个问题由后文的 ZeRO 一篇解决）。

### 1.2 PyTorch 的 DP（DataParallel）：最早的实现，但已过时

PyTorch 最早提供的数据并行实现是 `torch.nn.DataParallel`（简称 DP）。

**DP 的工作原理**：

- 使用**单进程、多线程**模式。
- 有一个**主卡（GPU 0）**承担额外职责：接收输入数据并将其**分发（Scatter）**到所有 GPU，收集所有 GPU 的输出和梯度，在主卡上更新模型参数后再**广播（Broadcast）**到其他 GPU。
- 代码实现极其简单——只需一行 `model = nn.DataParallel(model)`。

**DP 的主要问题**：

- **主卡负载过重**：模型参数更新、梯度汇总等都在主卡上完成，导致主卡的显存和计算压力远大于其他卡。
- **通信效率低**：主卡需要与所有其他卡通信，形成**参数服务器（PS）架构**的单点瓶颈。
- **Python GIL 限制**：单进程多线程模式下，多卡训练受 GIL 锁影响，无法充分利用并行性。
- **不支持模型并行**：DP 与模型并行不兼容。

**结论**：DP 已经**被 PyTorch 官方标记为过时（deprecated）**，**不推荐在生产环境中使用**。DDP（DistributedDataParallel）是取而代之的标准方案。

### 1.3 DDP（DistributedDataParallel）：工业界的标准方案

`torch.nn.DistributedDataParallel`（简称 DDP）是 PyTorch 官方推荐的数据并行方案。

**DDP 的核心设计**：

- 采用**多进程**模式：每个 GPU 对应一个独立的 Python 进程，互不干扰，天然绕过 GIL。
- 每个进程拥有独立的模型副本、优化器和数据采样器。
- 梯度同步通过 **AllReduce** 集体通信完成，所有 GPU 地位平等，**没有主卡瓶颈**。

**DDP 的启动方式**：在现代 PyTorch（1.10+）中，推荐使用 `torchrun`（原生支持）来启动分布式训练。

```bash
# 在一台机器上使用8张GPU
torchrun --nproc_per_node=8 train.py

# 在多台机器上使用16张GPU（每台8张）
# 节点0
torchrun --nnodes=2 --nproc_per_node=8 --rdzv_endpoint="10.0.0.1:29500" train.py
# 节点1
torchrun --nnodes=2 --nproc_per_node=8 --rdzv_endpoint="10.0.0.1:29500" train.py
```

**DDP 的标准代码模板**：

```python
    dataset = MyDataset()
    sampler = DistributedSampler(
        dataset,
        num_replicas=world_size,
        rank=rank,
        shuffle=True
    )
    dataloader = DataLoader(
        dataset,
        batch_size=batch_size,
        sampler=sampler,  # 使用sampler，不要用shuffle
        num_workers=4,
        pin_memory=True
    )

    # 5. 优化器、损失函数
    optimizer = torch.optim.AdamW(model.parameters(), lr=1e-4)
    criterion = torch.nn.CrossEntropyLoss()

    # 6. 训练循环
    for epoch in range(num_epochs):
        # 【关键】每个epoch开始时设置sampler的epoch，确保不同epoch的shuffle不同
        sampler.set_epoch(epoch)

        for batch_idx, (inputs, labels) in enumerate(dataloader):
            inputs = inputs.to(rank)
            labels = labels.to(rank)

            optimizer.zero_grad()
            outputs = model(inputs)      # DDP模型自动处理前向
            loss = criterion(outputs, labels)
            loss.backward()              # DDP的钩子在这里触发AllReduce
            optimizer.step()

    cleanup()

if __name__ == "__main__":
    # 假设通过torchrun传递了RANK、WORLD_SIZE等环境变量
    rank = int(os.environ["LOCAL_RANK"])  # torchrun自动注入
    world_size = int(os.environ["WORLD_SIZE"])
    train(rank, world_size)
```

**DDP 设计的精妙之处**：从用户代码的角度看，除了额外的 `DistributedSampler` 和进程初始化，训练循环的代码**几乎和单卡一模一样**。`loss.backward()` 之后，DDP 通过**自动注册的反向传播钩子（Autograd Hook）**悄悄完成了梯度同步——这种非侵入式设计是 DDP 成功的重要原因。

## 2. AllReduce 的梯度同步机制

### 2.1 什么是 AllReduce

**AllReduce** 是分布式计算中的一种**集体通信（Collective Communication）**原语。它的功能是：**所有参与方（GPU）各自持有一个值（或一组值），经过 AllReduce 操作后，所有参与方都得到相同的结果——通常是这些值的和或平均值。**

在数据并行中，AllReduce 的作用就是**跨 GPU 同步梯度**：

- 每张 GPU 独立计算出自己那份数据的梯度，记为 $g_1, g_2, \dots, g_N$。
- AllReduce 将这些梯度**求和并取平均**（通常求和后除以 `world_size`）。
- 所有 GPU 都得到相同的平均梯度，然后各自用这个平均梯度更新自己的模型副本。

数学上，AllReduce 需要实现：

$$
g_{\mathrm{avg}} = \frac{1}{N} \sum_{i=1}^{N} g_i
$$

并将 $g_{\mathrm{avg}}$ 广播到所有节点。

![DDP 梯度同步：各卡独立求梯度，AllReduce 后一致更新](https://raw.gitcode.com/weixin_42917352/image-host/raw/main/images/aiinfra_y1_l04_01.png)

### 2.2 Ring-AllReduce：最经典的实现算法

NCCL（NVIDIA Collective Communications Library）底层采用的最核心算法之一是 **Ring-AllReduce**。理解它有助于理解通信开销从哪里来。

Ring-AllReduce 将 N 个 GPU 逻辑上排列成一个**环（Ring）**，数据沿环单向传递。整个过程分为两个阶段。

**第一阶段：Scatter-Reduce（分散-归约）**

- 将每张 GPU 上的待同步数据（梯度张量）切分成 N 块（每块大小相等）。
- 在第 k 步，第 i 张 GPU 将自己持有的第 k 块数据发送给环上的下一个 GPU，同时从上一个 GPU 接收一块数据并累加。
- 经过 N-1 步后，每张 GPU 上都有一个数据块包含了**所有 GPU 在该块上的累加和**。

**第二阶段：AllGather（全收集）**

- 在第 k 步，第 i 张 GPU 将自己持有的已累加完成的第 k 块数据发送给下一个 GPU。
- 经过 N-1 步后，所有 GPU 上都持有所有数据块的完整结果。

**通信量分析**：

- 在 Ring-AllReduce 中，每一步每个 GPU 发送和接收的数据量相同。
- 总通信量为 $2 \times (N-1) \times \dfrac{K}{N} \approx 2K$，其中 K 是梯度总大小。
- 通信时间约为 $\dfrac{2K}{B} \times \dfrac{N-1}{N}$，其中 B 是带宽。

**关键结论**：Ring-AllReduce 的通信开销**随 GPU 数量的增加而增加**（虽然不是线性增加，但 $2K$ 的系数意味着带宽利用率受限于环的大小）。这就是为什么数据并行在扩展到成百上千张卡时通信会成为严重瓶颈。

### 2.3 AllReduce 的数学等价性与数值精度

在实际实现中，AllReduce 通常**先求和、后取平均**。这是因为求和是线性操作，可以先在环上累加完成后再统一除以 N。

但需要注意：当 N 极大（如数千张卡）时，大数值的累加可能带来**浮点数精度问题**。NCCL 通常使用 FP32 进行梯度累加以保证精度，这也是为什么即便用 FP16/BF16 训练，梯度同步仍推荐用 FP32 的原因之一。

## 3. DDP 的性能瓶颈与优化：梯度分桶、通信与计算重叠

DDP 虽然在单机 8 卡场景下性能卓越，但当扩展到大规模集群时（如 32 卡以上），通信开销会显著拖慢训练速度。这一节聚焦大厂 AI Infra 团队优化 DDP 性能的**两大核心技术**。

### 3.1 瓶颈一：小梯度带来的通信开销

**问题描述**：PyTorch 的 `autograd` 引擎在反向传播时，每计算完一个参数的梯度，就会立即触发该参数的 AllReduce。如果一个模型有成千上万个参数张量（层数多、参数小），那么每轮迭代就会触发**成千上万次**小规模的 AllReduce 操作。

每次 AllReduce 都有固定的**启动开销**（Kernel Launch、NCCL 初始化、同步等）。当张量很小（如几十 KB）时，启动开销可能**大于**实际数据传输的时间，导致通信效率极低。

**解决方案：梯度分桶（Gradient Bucketing）**。DDP 提供了一个关键优化参数 `bucket_cap_mb`，用于将多个小梯度张量**打包**成一个大的桶（Bucket），每个桶触发一次 AllReduce，而不是每个张量触发一次。

```python
model = DDP(
    model,
    device_ids=[rank],
    bucket_cap_mb=25  # 默认值25MB，可调整
)
```

**工作原理**：

- DDP 在反向传播开始前，将所有参数按照**模型定义顺序**倒序排列（因为反向传播是逆序进行的）。
- 将连续的小张量填充到同一个桶中，直到桶大小达到 `bucket_cap_mb`（默认 25 MB）。
- 每个桶独立触发一次 AllReduce。

**调优建议**：

- 对于小模型（参数少），可以适当**降低** `bucket_cap_mb`（如 10 MB），以避免桶内参数过多导致「等待」延迟。
- 对于大模型（千亿参数），可以适当**提高** `bucket_cap_mb`（如 50–100 MB），以进一步减少 AllReduce 次数。
- 需要**实测调优**，找到一个平衡点。

### 3.2 瓶颈二：串行执行带来的时间浪费

**问题描述**：在朴素的实现中，训练循环是严格串行的：前向传播 → 反向传播 → AllReduce 同步 → 优化器更新。这意味着**通信期间 GPU 的计算单元完全空闲**，造成浪费。

**解决方案：通信与计算重叠（Overlap）**。DDP 利用 PyTorch `autograd` 引擎的**异步特性**，实现了通信与计算的重叠。

**具体机制**：

- 反向传播是逐层进行的（从输出层到输入层）。
- DDP 将参数分组到桶中。当某个桶内的所有参数都完成梯度计算后，DDP 会**立即**触发该桶的 AllReduce，**不需要等待整个反向传播结束**。
- 在 AllReduce 进行的同时，反向传播继续计算其他层的梯度。

**直观理解**：

![梯度分桶重叠：AllReduce 藏进反向计算](https://raw.gitcode.com/weixin_42917352/image-host/raw/main/images/aiinfra_y1_l04_02.png)

- 桶 1 的梯度算完 → 立即开始通信。
- 通信的同时，模型继续算桶 2、桶 3 的梯度。
- **通信开销被有效地「隐藏」在了计算时间中**。

**验证重叠效果**：通过 `torch.profiler` 可以验证重叠是否生效。在 profiler 的**时间线视图**中，如果看到 CUDA kernel（计算）和 NCCL kernel（通信）在时间轴上有**重叠**，说明重叠生效了。

**需要注意的坑**：如果 `bucket_cap_mb` 设置过大，桶内包含太多层，那么该桶的 AllReduce 必须等**最后一层**的梯度计算完成才能开始。这会**延迟**通信的触发时机，**减少重叠**的机会。因此，合理的 `bucket_cap_mb` 需要在「减少 AllReduce 次数」和「提前触发通信」之间取得平衡。

### 3.3 其他 DDP 优化技巧

`gradient_as_bucket_view=True`：该参数（DDP 默认开启）让梯度张量直接引用桶的内存视图，避免梯度同步时的额外内存拷贝。

```python
model = DDP(model, device_ids=[rank], gradient_as_bucket_view=True)
```

`find_unused_parameters=False`（默认值）：如果模型中存在在某些训练步骤中不参与反向传播的参数，需要设置 `find_unused_parameters=True`。否则，保持默认 `False` 可以减少 DDP 在反向传播开始时遍历所有参数的额外开销。

## 4. 量化补充：通信等待、扩展效率与容量因子

第 3 节的分桶重叠可以算出收益上限。桶越大越要等桶内最后生成的梯度，桶越小启动次数越多；数据依赖给最早开始时刻，资源争用把它推迟，无法重叠而延长训练步的部分才是**通信等待**：归约 3 ms、其后有 5 ms 无关计算，链路空闲时全能藏住；若链路先被 4 ms 专家交换占用，归约延到 4-7 ms，多出的 2 ms 延长整步。反向中先算 dX 让前一层更早反向、先算 dW 让本层梯度更早通信，两者争用同一计算资源时改顺序就是重新分配通信窗口。ZeRO-3 每 micro-batch 三次集合（前向前/反向前 AllGather 权重、反向后 ReduceScatter 梯度），每步通信量 $V=3m\cdot\frac{d-1}{d}\cdot2N$：48 卡 m=8 约 385 GB，4090 无 NVLink 无 P2P、全部收发穿 PCIe 4.0 x16（32 GB/s）链路时间约 12 s——但逐层预取与归约后，大部分藏在每 micro-batch 6.53 s 计算内，**藏不住的只剩第一次 AllGather 与最后一次 ReduceScatter（都作用于约 1.24 GB 词嵌入），合计约 0.08 s**。若 1.3 s 归约只有 0.2 s 延到计算后，消除通信等待整步至多短 0.2 s。扩展效率同样有账：MegaScale 175B 全局 batch 6144 不变、卡数 3072→12288，每步 23.7→6.3 s 而非理想 5.9 s，约 3.7 倍/93% 效率——多出的 0.4 s 先归跨组同步与负载不均（扩展本身的工作），解释不了的才归实现开销。

MoE 与长上下文让每步耗时再看两个变量。其一是路由不均下的**容量因子**：每专家容量 $\lfloor c\times\text{token数}\times k/E\rfloor$ 行，超出丢弃（表示经残差直传下层）、未满补零（仍占计算与通信）。Qwen3-235B 形状（E=128、k=8、8192 token、一半专家 1.5 倍热）下：c=1.0 丢 25% 补零 25%，c=1.25 丢 12.5% 补零 30%，c=1.5 起不丢但补零 33%，c=2.0 补零 50%——**丢弃与补零是一笔交换，路由越均衡所需 c 越接近 1**，辅助损失与 DeepSeek-V3 无辅助损失偏置都把分布推向均衡。其二是梯度桶与空闲窗口的匹配：72 MiB FP32 专家梯度四成员环归约每卡发 108 MiB，整桶 4.55 ms 塞不进 2 ms 空闲；切三个 24 MiB 子桶各 1.53 ms 能分别藏进三个空闲段，总处理时间反增到 4.59 ms——**通信处理总量变长但计算后等待变短，值得**；换 400 Gbit/s 网卡整桶 2.28 ms 仍塞不进，切桶依然必要。长上下文另有一层：同总 token 数下 4096+4096 改 7168+1024，因果配对从约 1680 万增到 2620 万（+56%），长序列的三角形面积无法靠删 padding 消除——打包减无效工作、按长分组均衡各卡面积、CP 把长序列分到多卡（见 24 篇），三者分别改无效工作、工作分配与数据到达路径；比较时保持长度分布、掩码与损失权重不变，才能把调度收益与任务变化分开。
