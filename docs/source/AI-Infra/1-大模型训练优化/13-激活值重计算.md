# 激活值重计算（Activation Recomputation）

激活值是什么？在前向传播过程中，每一层都会产生输出张量，这些输出需要在反向传播时用于计算梯度——因此它们必须被保存下来，直到对应的反向传播完成。对于Transformer模型，激活值的显存占用与**批量大小（Batch Size）** 和**序列长度（Sequence Length）** 成正比。
有多夸张？训练一个GPT-3 175B模型时，如果使用较大的batch size，**激活值可能占用超过30%的显存**。而在长序列训练（如上下文窗口达到128K）中，这个比例甚至会超过50%。
**激活值重计算（Activation Recomputation，也称为梯度检查点 Gradient Checkpointing）** 的核心思想是：**以时间换空间**——不再保留所有激活值，而是在反向传播需要时重新计算它们。这是一项经典的显存优化技术，在Transformer训练中尤其有效。
### 1.1. 为什么激活值占用这么多显存？
在标准的前向-反向传播中，每一层的激活值必须被保留，直到反向传播完成。对于一个N层的Transformer模型：
- **前向传播**：第1层 → 第2层 → ... → 第N层，每层产生激活值并存储在显存中
- **反向传播**：第N层 → 第N-1层 → ... → 第1层，逐层读取对应的激活值计算梯度
- **释放时机**：某一层的反向传播完成后，该层的激活值才能被释放
这意味着，在反向传播的早期（从最后一层开始），**所有层的激活值都还驻留在显存中**——这就是激活值显存占用的峰值。
对于Transformer模型，单层激活值的显存占用为：
```text
每层激活值 ≈ batch_size × seq_len × hidden_dim × 4（可拆分为Q/K/V/中间结果）
```
当 `batch_size = 64`、`seq_len = 2048`、`hidden_dim = 4096` 时，**单层激活值就可能超过1GB**。70层的模型就是70GB以上——这比模型参数本身还要大。
### 1.2. 核心思想：丢弃并重新计算
激活值重计算的思路非常直接：
**传统方式（存储所有激活值）**：
```text
前向: 计算Layer1→保存A1→计算Layer2→保存A2→...→计算LayerN→保存AN
反向: 读取AN→计算梯度→读取A(N-1)→计算梯度→...
峰值显存: A1 + A2 + ... + AN（全部保留）
```
**重计算方式（不保存激活值）**：
```text
前向: 计算Layer1→丢弃A1→计算Layer2→丢弃A2→...→计算LayerN→丢弃AN
反向: 重新计算Layer1→得到A1→计算梯度→丢弃A1→重新计算Layer2→...
峰值显存: 仅1层激活值（或0层，取决于实现）
```
这就是“时间换空间”的含义：**前向传播时不保存激活值，反向传播时重新计算它们**。代价是**额外的前向计算时间**——每一层在反向时都被重新计算了一次。

### 1.4. 为什么在Transformer中尤其有效？
Transformer的架构特点使得激活值重计算特别有效：
1. **层数深**：GPT-3有96层，Llama 3 405B有126层。层数越深，保存所有激活值的显存压力越大，重计算的相对收益越高。
2. **计算密集**：Transformer的每一层主要由矩阵乘法（Attention和FFN）构成，计算速度远快于显存访问。重计算增加的是“计算”而不是“显存访问”——对GPU利用率反而是有利的。
3. **激活值占比高**：在长序列训练中，激活值显存占用超过模型参数。重计算可以将这部分显存开销降低到可忽略的水平。
实践中的经验数据表明，启用激活值重计算后，**显存占用可以减少30%-50%**，而**训练时间仅增加15%-25%**——这是一个非常划算的交易。
### 2.1. 全重算（Full Recomputation）
**策略描述**：在反向传播过程中，**重新计算所有层的激活值**。前向传播时不保存任何激活值（除了最后一层的输出）。
**优点**：
- **显存节省最大**：激活值显存占用从

**缺点**：
- 时间开销最大：约增加33%-40%的训练时间
- 在某些极端场景下，重计算可能与反向传播形成串行依赖，导致GPU利用率下降
**适用场景**：
- 显存极度受限，无法容纳完整激活值
- 模型极深（层数 > 100），保存所有激活值不现实
- 训练目标受限于显存而非计算（例如需要更大批量大小或更长序列）
### 2.2. 选择性重算（Selective Recomputation / Checkpointing）
**策略描述**：仅对模型的一部分层进行重计算，其他层的激活值仍然保存。**仅在特定“检查点”（Checkpoint）层之间进行重计算**。
具体做法是：在前向传播时，每隔K层**保存**一次激活值（称为Checkpoint），然后丢弃这两层之间的所有激活值。反向传播时，从最近的Checkpoint开始，重新计算这K层的激活值。
**图示**（以K=2为例）：
```text
前向传播:
Layer1→保存A1→Layer2→丢弃A2→Layer3→保存A3→Layer4→丢弃A4→...

反向传播:
从A1开始→重算Layer2→计算梯度→从A3开始→重算Layer4→计算梯度→...
```
**优点**：
- **可调节的权衡**：通过调整K值（每K层保存一次），在显存和时间之间平滑调节
- **更灵活**：可以根据模型结构选择性地对计算密集的层启用重算
- 时间开销可控：通常为10%-20%
**缺点**：
- 实现比全重算复杂
- 需要手动选择Checkpoint的位置
**适用场景**：
- 显存有一定余量，但不足以保存全部激活值
- 希望在显存节省和时间开销之间取得平衡
- 是工业界最常用的策略

### 2.4. 基于模型结构的非均匀Checkpoint
更精细化的策略是**根据层的重要性或计算量进行非均匀分配**：
- **Self-Attention层**：激活值占用大（需要保存Q/K/V中间结果），但计算密集，重计算的时间开销相对较小 → 优先重计算
- **FFN层**：激活值占用也大，但计算相对简单 → 可根据情况选择
- **Embedding层**：激活值占用较小，且只在前向开始时使用 → 通常保存
在这种策略下，激活值重计算的开销可以减少至**15-20%**。

### 3.2. 重计算对MFU的影响
在后文中我们学过**MFU（Model FLOPs Utilization）**。激活值重计算会增加**实际FLOPs**而不改变**模型FLOPs**（模型本身的FLOPs不变，只是重复计算了前向部分）。因此：
- **MFU降低**：因为分母（硬件FLOPS）不变，分子（模型FLOPs）不变，但实际执行时间增加 → MFU下降
- **HFU不变或上升**：因为实际FLOPs增加了（重算的部分）
**这意味着什么？** MFU下降了，但硬件利用率（HFU）可能并没有下降——计算资源一直在忙。这是“时间换空间”在MFU指标上的体现。
### 3.3. 重计算与ZeRO的协作
激活值重计算和ZeRO是**互补的**优化技术：
- **ZeRO**：解决**模型状态**（参数、梯度、优化器状态）的显存问题，通过分片存储
- **激活值重计算**：解决**激活值**的显存问题，通过丢弃并重新计算
两者组合使用，可以将大模型训练所需的总显存**降低到原来的1/3到1/4**。在DeepSpeed中，可以同时启用：
```json
{
    "zero_optimization": {
        "stage": 3
    },
    "activation_checkpointing": {
        "partition_activations": true,
        "cpu_checkpointing": true,
        "contiguous_memory_optimization": true,
        "number_checkpoints": 4,
        "synchronize_checkpoint_boundary": false,
        "profile": false
    }
}
```
**关键参数**：
- `partition_activations`：将激活值分片到多张GPU（与ZeRO-3配合）
- `cpu_checkpointing`：将Checkpoint保存到CPU内存，进一步减少显存
- `contiguous_memory_optimization`：优化显存布局，减少碎片
### 3.4. 调优实战：找到最佳Checkpoint配置
**步骤1：基线测量**
使用 `torch.profiler` 在不启用重计算的情况下，测量训练的时间分布和显存占用：
```text
with torch.profiler.profile(activities=[...]) as prof:
    for batch in dataloader:
        loss = model(inputs)
        loss.backward()
        optimizer.step()
```
记录：
- 每步训练时间（秒）
- 峰值显存占用（GB）
- 前向/反向的时间占比
**步骤2：启用重计算并逐步调整**
从K=8开始，逐步减小K值（8→4→2→1），观察：
- K=8时，显存占用最低，但时间开销最大
- K=4时，显存和时间达到较好的平衡
- K=2时，显存占用接近全保存，时间开销较小
找到**满足显存约束的最小时间开销**的K值。
**步骤3：验证精度**
重计算完全可复现（因为计算逻辑完全相同），不会影响模型精度。但需要验证实现是否正确——确保中间结果的数值误差在可接受范围内。
**步骤4：性能分析**
启用重计算后，使用profiler检查：
- 重计算是否与反向传播重叠？理想情况下，重计算和梯度计算应尽量并行
- 是否存在GPU空闲等待？检查是否有同步点导致性能下降
- Checkpoint的保存位置是否影响了通信效率（在多卡场景下）
