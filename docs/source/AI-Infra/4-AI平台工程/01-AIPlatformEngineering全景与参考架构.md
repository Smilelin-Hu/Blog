# AI Platform Engineering 全景与参考架构

企业明明已经买了 GPU、搭了 Kubernetes，也能把训练程序跑起来，为什么不同团队仍然每天在群里抢卡、找管理员开权限、询问作业为什么没有启动？为什么一个模型训练成功后，还要靠人复制文件、登记版本、申请上线，出了事故却找不到完整责任链？

![AI 平台全景与参考架构](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l01_01.png)

问题通常不在于“少安装了一个工具”，而在于机器、集群和工具还没有被组织成稳定能力。有人要临时开一台 Notebook，有人要占用八张卡训练三天，有人要把模型发布到线上，还有人要求模型必须经过审批、能够追溯来源，并把每一笔成本归到具体项目。GPU 仍然是那些 GPU，但系统已经需要同时处理身份、策略、配额、排队、生命周期、制品、观测、故障和成本。

AI Platform Engineering 解决的就是这段落差：把“机器可以运行程序”变成“不同角色可以在明确规则下反复获得 AI 能力”。判断一套系统是否已经成为平台，可以先检查四件事：请求是否有稳定入口，期望状态是否有人持续协调，失败与成本是否能够定位，底层组件变化时用户契约是否仍然成立。

## 这篇先解决什么问题

这篇文章先建立整个系列的系统地图。从一个团队的资源混乱出发，沿三条线推进：

- 第一条线解释平台是什么。它会区分基础设施、集群、工具和平台，并说明平台为什么是一组能力、体验与治理契约，而不是软件清单。
- 第二条线解释平台怎样工作。它会把期望状态、控制面、数据面、七层架构和一次完整请求生命周期连接起来。
- 第三条线解释平台怎样被长期拥有。它会落到角色、事实源、故障域、质量指标、成本和常见反模式。

读完后，应能够面对一个陌生组织，画出可评审的 AI 平台参考架构；能够解释每个组件承接哪项能力、保存什么状态、由谁负责、失败影响谁；也能够通过实验发现需求悬空、能力无主、组件缺失或责任重叠。

## 1. 从一个团队的真实混乱开始

### 1.1 同一张 GPU 被五种方式使用

假设一家互联网公司刚开始建设大模型团队。公司有一个四节点 GPU 集群，每个节点八张卡。研究团队希望在 Notebook 里交互式试验；训练团队希望提交八机任务；推荐团队每天跑特征和训练流水线；在线业务希望部署低延迟服务；评测团队希望定期批量生成结果。表面上看，这些请求都可以归结为“申请 GPU”，但它们对系统的要求完全不同。

Notebook 的用户关心的是几分钟内进入环境、能够保存代码和结果、长时间无操作后不会无止境占卡。分布式训练关心的是所有进程能否同时获得匹配的 GPU、网络和存储，任意一个进程失败后整个作业怎样恢复。流水线关心步骤之间的依赖、缓存、重试和制品传递。在线服务关心连续可用、版本切换、流量隔离、自动扩缩和回滚。批量评测关心数据版本、模型版本、评价配置和结果血缘。若平台只提供一个“GPU 数量”字段，它并没有真正表达这些差异。

同一块物理 GPU 还可能以不同资源形态出现。它可能整卡分配给一个 Pod，也可能通过时间切片让多个低负载进程共享，还可能在支持 MIG 的设备上切成具有独立显存和计算单元的实例。资源形态决定隔离强度、可观测性、调度方式和故障范围。把它们都显示成“1 GPU”会让用户误判能力，也会让容量管理员无法解释为什么名义上还有卡，新的作业却无法进入。

真正的平台需要理解请求的意图，而不仅是数量。用户说“我要八张卡”时，系统至少还需要知道：是否必须同一时间启动，是否必须在同一高速互联域，能否等待，能否抢占，失败后从头重跑还是从检查点恢复，最长运行时间是多少，数据从哪里来，结果写到哪里，谁承担成本，以及这次运行是否允许访问敏感数据。请求中的这些语义，最终会落到队列、准入、调度、存储、身份、策略和可观测性系统中。

因此，AI 平台的第一条设计原则是：不要用一种资源申请表伪装所有工作负载相同。平台应当提供少量清晰的工作负载产品，每种产品都有稳定输入、默认策略、生命周期和服务承诺。例如“交互式工作空间”“分布式训练作业”“批处理流水线”“在线模型服务”可以共享底层集群，却不应该共享一套含义模糊的启动脚本。

### 1.2 训练成功为何仍然不能称为平台

一位工程师登录服务器，手工选择空闲 GPU，运行训练脚本并得到模型，这证明训练代码和机器可以工作，却没有证明组织拥有平台。第二个人是否能够在不询问这位工程师的情况下复现过程？同一环境能否在下周重建？资源冲突时是否有一致规则？模型来自哪个数据版本？失败由谁处理？使用成本记到哪个项目？这些问题若依赖口头沟通，系统仍然停留在个人操作层。

“能跑”是单次执行属性，“平台化”是重复交付属性。一次成功可以依赖幸运的时间窗口、临时修改过的环境和某个专家的记忆；平台则要求不同用户在可预期的规则下反复获得能力。它不保证每个作业都成功，但必须让提交、等待、失败、恢复和退出都有可观察、可解释的状态。用户不应通过在群里追问管理员来了解作业为什么没启动。

平台还必须处理并发。只有一名用户时，人工协调看似高效；有几十个项目时，所有特殊请求都会成为队列外的暗箱操作。某个高优任务插队，可能让已经等待两天的团队继续等待；某个长期 Notebook 忘记关闭，可能阻塞整卡训练；某次驱动升级没有记录，可能让所有环境在同一天失效。如果规则没有编码进系统，资源越昂贵，组织内的博弈越强。

最后，平台要处理变化。模型框架、GPU 代际、驱动、容器运行时、调度扩展和安全要求都会升级。单个训练脚本只关心当前环境；平台需要提供版本化模板、兼容窗口、迁移路径和弃用策略。平台工程不是把环境永远固定，而是让环境可以在受控条件下演进。

判断一个系统是否具备平台属性，可以问四个问题。第一，用户是否能够通过稳定接口获得能力，而不是依赖某个管理员？第二，系统是否能持续把声明的需求协调成实际资源？第三，失败、成本和责任是否能定位？第四，底层组件替换时，用户接口和核心语义能否保持相对稳定？若四个问题多数无法回答，组织拥有的通常是工具或集群，而不是平台。

### 1.3 脚本堆积、人工审批和隐性知识的代价

平台建设前最常见的资产是一组“非常重要但没人敢改”的脚本。脚本 A 创建命名空间，脚本 B 复制 Secret，脚本 C 生成训练 YAML，脚本 D 从共享盘加载模型。每个脚本都可能在局部解决了问题，但它们通常缺少统一状态模型。执行者不知道上一步是否真的完成，也不知道重复执行会不会创建两份资源。失败后，现场只剩一段终端输出，无法回答系统最终处于什么状态。

人工审批本身并非错误。敏感数据访问、大额 GPU 预算和高风险线上变更确实可能需要人作决定。问题在于审批如果存在于聊天消息、电子表格和口头许可中，就不能成为机器可验证的准入条件。平台看不到审批结论，审计人员也无法把某次运行与批准记录关联起来。于是团队要么绕开流程追求速度，要么让每个普通请求都排在人工队列中。

隐性知识的成本常被低估。一个训练任务因挂载路径错误而失败，资深工程师几分钟就能修复，新同事可能排查半天。如果同类故障反复出现，说明组织只在修复实例，没有把知识沉淀成默认值、校验规则、错误消息或自动修复。平台的价值之一就是把高频、稳定、可编码的专家判断固化成产品行为，让专家把时间留给真正的新问题。

脚本堆积还会产生所有权真空。用户认为平台团队提供了脚本，所以运行失败应由平台负责；平台团队认为脚本只是示例，模型代码和数据由用户负责；基础设施团队认为节点在线就已经完成职责。没有明确的服务边界时，每次事故都会先争论归属，再开始恢复。恢复时间因此不只是技术故障时间，还包括寻找负责人的组织延迟。

把这些代价量化后，平台投入就更容易讨论。可以统计首次成功运行需要多少人工步骤、每月有多少重复工单、作业因环境或权限失败的比例、平均排队时间、资源空闲而用户仍在等待的时间、一次版本升级影响多少项目，以及事故中用于定位责任的时间。平台不是为了“看起来现代”，而是为了系统性减少这些摩擦和风险。

### 1.4 从“机器可用”到“能力可自助使用”

机器可用意味着电源、网络、操作系统和 GPU 驱动正常；能力可用意味着目标用户能够在权限范围内完成任务。两者之间隔着很长的交付链。用户需要身份和项目空间，需要可选择的运行模板，需要数据和模型的访问路径，需要队列与配额，需要可理解的状态和日志，需要结果保存与成本记录。任何一环缺失，都可能出现“集群没有故障，但用户无法工作”。

自助不等于没有治理。成熟的自助服务是在预先定义的护栏内快速完成常规请求。平台用默认值覆盖常见场景，用策略阻止明显危险的配置，用配额限制最大影响范围，用审批处理少数高风险例外。用户不必理解驱动 DaemonSet、调度插件和存储拓扑，却仍需明确知道申请了多少资源、能等待多久、哪些数据可访问，以及运行失败时谁负责什么。

自助也不等于只有网页。网页、命令行、SDK 和声明式 API 可以是同一能力的不同入口。真正稳定的是后台契约：请求字段的含义、状态机、权限规则、版本策略和审计记录。如果平台只有一个漂亮表单，而后台仍然由人复制参数运行脚本，它只是工单前端。反过来，一个具有清晰 API、良好错误信息和自动协调能力的系统，即使最初只有命令行，也已经具备平台骨架。

从机器到能力的转变，可以用四层结果检验。第一层是资源结果：GPU、CPU、内存、网络和存储按约束被分配。第二层是运行结果：工作负载完成启动、执行、终止和清理。第三层是业务结果：模型、指标或在线服务被正确交付。第四层是治理结果：整个过程能够说明谁在何时以何种权限使用了什么资源、产生什么版本和多少成本。企业平台必须把四层结果连接起来。

## 2. AI 平台究竟是什么

### 2.1 基础设施、集群、MLOps 工具和平台的区别

基础设施提供计算、网络、存储和物理设备。它回答“资源是否存在、是否连通、是否健康”。GPU 服务器、交换机、对象存储、云账户和机房属于这一层。基础设施非常重要，但用户通常不能直接把业务意图表达给它。服务器不会理解“这是一个可抢占的训练试验”，对象存储也不会自动判断某个模型是否已通过发布门禁。

集群把若干资源组织成统一管理域。Kubernetes 或 Slurm 可以发现节点、分配资源、启动任务、报告状态。集群回答“某个资源对象如何被安排和运行”。它提供的平台原语很强，但这些原语通常仍然面向基础设施工程师。例如用户需要知道 Pod、Job、Deployment、PriorityClass 或 Slurm partition，才能准确提交工作负载。企业 AI 平台会使用这些原语，却不要求所有用户直接操作全部底层细节。

工具解决某一段具体问题。实验跟踪工具保存参数和指标，模型注册中心管理版本，流水线引擎编排步骤，服务控制器管理模型部署，监控系统采集遥测。单个工具可能非常完整，但它只拥有局部状态。用户从实验工具看到的“完成”，不一定代表模型已经注册；注册中心中的“候选版本”，也不一定代表线上容量已经准备好。工具之间若没有共同身份、事件、权限和生命周期，用户仍需人工拼接流程。

MLOps 常用来描述机器学习从开发到交付的工程实践，包括数据、实验、训练、验证、注册、部署和监控。它强调流程和自动化，但在不同组织中范围差异很大。有些 MLOps 系统聚焦流水线和模型生命周期，有些也包含资源调度和平台门户。为了避免术语争论，这里使用更可操作的定义：AI 平台是面向内部用户、以稳定接口交付 AI 工作负载能力，并持续协调资源、生命周期、治理和运营状态的内部产品。

这个定义有三个关键词。第一是“面向用户”，说明平台必须从用户任务而非组件出发。第二是“稳定接口”，说明底层实现可以演进，用户契约不能随意破坏。第三是“持续协调”，说明平台不是执行一次安装，而是不断比较期望与实际并纠正偏差。只要抓住这三个关键词，组织采用 Kubernetes、Slurm、云服务还是混合技术栈，都可以用同一套框架分析。

### 2.2 平台作为内部产品而不是组件清单

组件清单的写法通常是：“安装 Kubernetes、Kubeflow、Kueue、KServe、Prometheus 和 Argo CD。”这句话只能说明候选实现，不能说明用户获得了什么。用户无法从清单判断如何提交训练、等待多久、怎样访问数据、模型怎样晋级、出现故障找谁。更严重的是，同一能力可能由多个组件重叠实现，而关键能力仍然缺失。

产品视角从用户任务开始。例如“在受控项目空间中提交一次分布式训练”是一项产品能力。它的输入包含镜像、代码、数据、资源规模、优先级和恢复策略；输出包含运行状态、日志、指标、检查点、模型制品与成本；限制包含可用 GPU 型号、最大运行时间、配额和数据权限；服务承诺包含提交接口可用性、排队状态可见性和故障响应方式。具体由哪个控制器创建 Pod，是实现细节。

内部产品同样需要版本、文档、支持和反馈。平台 API 的字段会演进，默认镜像会升级，旧 GPU 池会退役，安全策略会收紧。平台团队需要公布兼容范围、弃用时间和迁移方案，而不是把变化作为突发通知发给用户。用户也需要能够报告阻塞、申请例外并参与优先级判断。没有产品管理，平台团队容易按照自身技术兴趣扩充组件，却无法证明使用价值。

“平台即产品”不意味着平台必须商业化，也不意味着用户可以无限定制。它意味着平台团队要明确客户、问题、能力、质量和路线图。平台可以拒绝低频且高成本的需求，也可以要求用户在标准路径之外自行承担更多责任。关键是这种边界必须可见，而不是等事故发生后才临时解释。

评审平台方案时，可以暂时遮住所有产品名称，只保留能力框。若架构仍能说明用户怎样完成任务、状态怎样流转、策略怎样执行、谁拥有故障，它就是能力驱动的设计。若遮住产品名后只剩空白，说明方案主要是在罗列技术，而不是设计平台。

### 2.3 平台提供的能力、体验和治理契约

平台能力描述系统能做什么，例如创建工作空间、提交训练、管理队列、注册模型、发布服务和查询成本。每项能力都应有明确输入、输出、状态和所有者。能力不是一个界面按钮，也不是某个组件名字。一个按钮可能触发多项能力，一个组件也可能承载多项能力；相反，一项能力可能跨越门户、控制器、队列和存储多个组件。

平台体验描述用户怎样感知这些能力。好的体验不是把所有底层选项全部暴露，而是在关键决策点提供恰当信息。用户提交训练时，需要看到可选资源类型、预计等待、预算影响和配置校验；等待期间，需要知道处于审批、配额不足、等待同组资源还是节点供给阶段；失败后，需要得到面向行动的原因，而不是只有一个 Pod 名称。体验的目标是降低完成任务所需的组织和技术认知负担。

治理契约规定哪些事情必须发生、哪些事情不能发生，以及证据如何保留。例如镜像必须来自受信仓库，敏感项目不能把数据复制到公共桶，线上模型必须关联已批准版本，团队不能超过月度 GPU 预算。治理如果只写在制度文档里，执行就依赖人工；如果直接硬编码在某个脚本里，又缺少版本和解释。平台应将规则转换为可版本化、可测试、可审计的策略，并向用户返回明确拒绝原因。

三者必须共同设计。只有能力没有体验，用户会被复杂接口淹没；只有体验没有可靠能力，门户会成为工单包装；只有治理没有标准能力，安全规则会被视为阻碍。平台产品的完整契约可以表达为：“在给定身份、项目和政策条件下，用户通过稳定接口请求某项能力，系统以可观察的状态协调底层资源，并留下可追溯证据。”

这个契约还需要处理失败。平台不能承诺所有作业永不失败，但可以承诺失败状态可见、原因有分类、可重试条件明确、数据不因单点故障丢失、关键事件可审计。失败契约往往比成功路径更能区分工具拼装与成熟平台。

### 2.4 平台不应该替用户隐藏的复杂性

平台要降低无关复杂性，却不能删除会改变结果的关键语义。例如平台可以隐藏 Device Plugin 的安装方式，但不能隐藏 GPU 型号与显存差异；可以隐藏队列控制器内部对象，但不能隐藏作业可能等待和被抢占；可以提供训练模板，但不能替用户决定检查点是否正确；可以自动发布服务，但不能假装流量迁移没有容量成本。

判断某个细节是否应被隐藏，可以看它是否会改变用户的风险、成本或结果。驱动容器的名字通常不会；GPU 拓扑可能会。监控后端的分片方案通常不会；日志保留期限可能会。控制器的重试实现通常不会；一个失败是否会自动重跑并产生额外费用会。平台应该把前一类封装在内部，把后一类变成清楚的产品参数或状态。

过度抽象会制造“惊讶”。用户只选择“高性能训练”，平台默默申请昂贵 GPU 和专用网络，月底才看到成本；用户只点击“自动恢复”，平台从旧检查点反复重跑，造成数据重复写入；用户选择“共享 GPU”，却误以为具备强隔离。平台接口若用模糊的营销词代替工程语义，短期看起来简单，长期会失去信任。

另一种错误是完全不抽象，要求每个用户理解上百个 Kubernetes 字段。这样做把平台团队的集成成本转移给每个业务团队，形成大量复制粘贴配置。合理做法是提供 Golden Path：为高频场景定义少量意见明确的模板，暴露真正影响结果的参数，并保留受控的扩展出口。平台既不是黑盒，也不是裸集群，而是有边界的抽象层。

## 3. AI 工作负载为什么特殊

### 3.1 Notebook、批处理、训练、Pipeline 和在线服务

交互式 Notebook 的核心特点是有人在等待。用户对启动延迟敏感，使用过程却可能呈现突发计算和长时间空闲。它需要持久化工作目录、身份代理、会话超时和资源回收策略。Notebook 内可以运行训练，但从平台角度，它仍然是一个交互式环境：生命周期由人驱动，资源预测较弱，空闲检测重要，开放网络和凭证带来的安全风险也更高。

批处理作业有明确开始和结束，输入输出通常可枚举。它适合排队、重试和成本核算。单机批处理可以独立获得资源后运行，多角色分布式作业则要求若干成员共同启动。批处理的关键状态不只是 Running 和 Failed，还包括等待准入、资源不足、镜像拉取、数据准备、执行、保存结果和清理。把所有等待都显示成 Pending，会让用户和运维同时失去判断依据。

训练作业是一类资源重、持续时间长、失败代价高的批处理。它可能包含不同角色，如协调进程、参数服务和工作进程；可能需要同构 GPU、高速互联和本地缓存；可能通过检查点恢复。训练代码内部如何切分张量、同步梯度属于工作负载实现，平台则要确保请求的资源集合、拓扑、存储和失败语义被正确表达。两者接口不清时，平台会把算法错误误判为基础设施故障，训练团队也会把调度等待误判为集群坏了。

Pipeline 是任务之间的有向依赖图。每个步骤可能是 CPU 预处理、GPU 训练、批量评测或模型注册。它的难点不只在启动容器，还在参数传递、制品寻址、缓存命中、步骤重试、条件分支和元数据血缘。Pipeline 引擎管理流程状态，底层调度系统管理每个工作负载的资源准入，两者不能互相替代。

在线模型服务没有自然结束时间。平台要维持副本、健康、路由和版本，处理扩缩容与滚动变更。服务可能在没有流量时仍占用昂贵 GPU，也可能在突发流量到来时因模型加载过慢而无法及时扩容。推理引擎内部如何批处理请求、管理 KV Cache 属于数据面；平台控制面负责让正确版本以正确资源、策略和容量进入运行状态。

这些形态可以共享身份、镜像、制品、GPU 节点和遥测基础，但它们需要不同的生命周期控制器与产品契约。平台架构的目标不是把所有对象压成同一类型，而是统一共同语义，同时保留关键差异。

### 3.2 短作业、长作业、长驻服务和交互式环境

工作负载持续时间会直接改变调度和运营策略。几分钟的短作业适合高吞吐排队，启动开销占总时长比例很高；运行数天的训练更关心中断概率、检查点和节点稳定性；长驻服务更关心变更期间的连续可用；交互式环境则要在即时体验与闲置浪费之间取平衡。一个统一的超时值无法合理服务四类负载。

短作业数量多，控制面吞吐和镜像拉取容易成为瓶颈。每个作业只计算两分钟，却等待三分钟创建 Pod，GPU 有效工作比例就很低。平台需要缓存镜像和数据、合并过细任务，或者提供常驻执行池。此时单看作业运行期间的 GPU 利用率会误导，因为等待和启动成本被排除在统计之外。

长作业占用资源时间长，任何硬件故障、维护和抢占都会放大损失。平台需要明确维护窗口、节点排空、检查点验证和恢复策略。不是所有长作业都适合自动重试：如果程序没有幂等输出，重跑可能破坏数据；如果检查点本身损坏，反复恢复只会浪费更多卡时。平台能够触发重试，但工作负载所有者必须声明并验证恢复语义。

长驻服务的资源计划由请求流量驱动。GPU 服务的扩容比普通无状态 Web 服务慢，因为节点供给、驱动就绪、模型下载和显存装载都需要时间。平台必须区分控制面看到的“副本已创建”和业务看到的“模型已经可服务”。容量不足时，滚动发布可能同时保留新旧版本，瞬间需要双倍资源；若没有发布前容量检查，标准发布动作本身就会造成事故。

交互式环境的所有权最模糊。用户可能把 Notebook 当作临时终端，也可能在里面保存唯一代码和结果。平台若强制回收，可能导致数据损失；永不回收，则会积累僵尸资源。正确做法是把计算与持久数据分离，提前提示空闲策略，保存必要状态，并提供延期或恢复机制。资源回收应是产品契约的一部分，而不是管理员夜间执行的秘密脚本。

### 3.3 稀缺加速器、重型制品与长启动时间

GPU 与普通 CPU 资源的一个显著差异是稀缺且异构。不同代际、显存容量、互联方式和虚拟化形态可能决定任务能否运行。一个需要 80GB 显存的模型不能因为“集群还有很多 GPU”就安排到 24GB 卡上；一个需要节点内高速互联的训练也不能随意分散。平台必须让资源类别与拓扑成为可调度语义，而不是依靠用户记住节点名字。

稀缺资源使排队成为正常状态，而不是异常状态。平台若试图让所有请求立即启动，只能过度采购或允许资源争抢。成熟平台会定义配额、借用、公平共享、优先级、抢占和准入顺序，并向用户解释等待原因。队列不是降低体验的障碍；不可见、不可预测、可以被人情绕开的队列才是问题。

AI 制品通常很重。容器镜像可能包含大型框架与驱动用户态库，模型权重可能达到数百 GB，训练数据可能远大于节点本地磁盘。即使调度器快速找到 GPU，镜像拉取、数据准备和模型加载仍会让启动延迟达到分钟级。若所有副本同时从远端对象存储读取同一模型，还可能形成带宽尖峰，拖慢整个集群。

因此，平台需要把“资源已分配”和“工作负载已就绪”分开测量。前者由调度与节点状态决定，后者还受制品分发、存储、网络和应用初始化影响。优化启动时间也不能只做一件事：镜像分层与预拉取解决镜像，节点缓存解决重复模型下载，拓扑约束避免跨域访问，制品校验保证缓存内容正确。每项优化都要保留版本一致性和回收机制。

长启动时间还改变自动扩缩容。普通 Web Pod 可以在数秒启动，按当前负载扩容可能足够；GPU 模型服务若需要十几分钟才能就绪，就必须提前预测、保留热容量或接受更高排队延迟。平台产品应把这种约束体现为服务等级与成本选择，而不是承诺不现实的即时弹性。

### 3.4 Gang、拓扑、失败恢复和成本敏感性

分布式训练常要求多个成员一起获得资源。如果先启动七个进程，第八个因资源不足长期等待，已经启动的七个既不能有效训练，又持续占卡。Gang Scheduling 的核心不是“同时创建 Pod”，而是只有当整个最小资源集合可满足时才允许工作负载进入。它减少部分占用死锁，却可能让大作业等待更久，因此还要结合公平共享、优先级和回填策略。

拓扑描述资源之间的物理或逻辑关系。节点内 GPU 可能通过高速互联连接，机架内节点共享较低延迟网络，跨机架带宽可能更有限。调度器若只满足 GPU 数量，可能得到一个能启动但性能极差的放置结果。平台需要让工作负载声明“必须同域”“优先同域”或“可跨域”，并在资源不可满足时给出可解释状态。强约束提高性能确定性，却降低可调度性；软约束更灵活，却可能带来性能波动。

失败恢复也具有跨层语义。节点掉线由基础设施发现，调度系统可能重新创建 Pod，训练控制器可能重启某个角色，训练框架可能从检查点恢复。若每一层都独立重试，可能形成重试风暴；若所有层都等待别人处理，作业会卡住。平台需要明确每类失败由哪一层检测、何时重试、重试预算是多少、终态如何报告。检查点可用性不能仅凭文件存在判断，还应验证完整性和与代码版本的兼容性。

成本敏感性贯穿所有决策。等待一小时可能损失工程师时间，立即启动可能需要保留昂贵闲置容量；高优任务抢占低优任务可以提升关键业务速度，也会浪费被中断作业的已用卡时；复制模型到每个节点能加快启动，却增加存储和网络成本。平台不能替组织决定价值，但必须提供数据和策略，让这些权衡可以被明确选择。

AI 工作负载之所以特殊，并不是因为每个概念都前所未有，而是多个苛刻条件同时出现：资源昂贵而异构，任务规模大且持续久，制品重，启动慢，分布式成员相互依赖，失败代价高，治理要求又贯穿生命周期。平台架构必须把这些条件作为一等语义，而不是在通用容器平台上临时增加几个 GPU 标签。

## 4. 控制面与数据面

### 4.1 期望状态、实际状态和持续协调

用户通过平台提交的不是一串应当只执行一次的命令，而是一个期望。例如“项目 recommendation 需要一个使用四张指定型号 GPU 的训练作业，最多运行十二小时，失败时从检查点恢复，产物写入指定位置”。这个期望会被保存为资源对象或数据库记录。它应当有唯一身份、版本、创建者、策略上下文和生命周期状态。

实际状态是系统当前观察到的事实：配额是否充足，作业是否已准入，节点是否存在，GPU 是否健康，Pod 是否创建，数据是否准备，进程是否运行，检查点是否写入。期望与实际之间经常存在差异，这种差异并不必然是故障。一个新提交作业处于等待队列，就是合理差异；一个应当有三个副本的在线服务暂时只有两个健康副本，则需要控制系统继续协调。

协调循环反复执行四个动作：读取期望，观察实际，计算差异，采取一步可恢复的动作。完成后它不会假定世界从此不变，而会继续观察。节点可能下线，用户可能修改规格，策略可能拒绝新版本，外部存储可能暂时不可用。持续协调使系统能够面对变化，而不是要求操作者每次从头运行脚本。

协调必须幂等。所谓幂等，是同一个期望被处理多次，不会无意创建多个作业或重复扣减预算。控制器收到重复事件很正常，进程崩溃后也可能不知道上一步响应是否送达。可靠实现通常先查询目标资源是否存在、其版本和所有权是否匹配，再决定创建、更新或等待。把“我已经调用过一次”当成完成证据，是分布式控制面常见错误。

期望状态还需要与观察结果分开。Spec 表达用户想要什么，Status 表达控制器看到了什么。如果控制器直接修改用户期望来适应现实，用户就无法知道请求是否被悄悄降级。可以通过默认值或策略在准入阶段明确变换，但变换必须可见。例如用户请求八张卡，平台只能提供四张卡时，合理结果是等待、拒绝，或让用户选择弹性规模，而不是静默改成四张。

状态设计决定可操作性。只提供 Pending、Running、Failed 太粗。Pending 可能是等待审批、等待配额、等待队列准入、等待节点扩容、等待镜像或等待数据；每种状态的负责人和处理动作不同。平台应该报告阶段、原因、消息、最近转换时间和观测版本，让用户知道系统正在处理哪个期望，也让 SRE 能够区分拥塞、策略和故障。

### 4.2 用户请求怎样变成集群资源

一次自助请求通常先进入平台 API。平台解析用户身份与项目，验证字段，补充默认值，把高层产品参数转换为内部资源声明。例如“标准四卡训练”可能映射为训练运行时、队列、资源类别、存储挂载、遥测标签和安全上下文。这里的转换不是简单模板替换，因为它还要结合租户策略、区域、预算和平台版本。

请求随后经过策略与准入。身份系统回答“你是谁”，授权系统回答“你是否可以在这个项目请求该能力”，策略系统回答“这个具体声明是否符合规则”，配额系统回答“组织是否允许它进入资源竞争”。这些判断应当分层：拥有提交权限不等于拥有无限 GPU 配额；通过安全策略不等于资源现在足够；资源足够也不代表发布质量门禁已经满足。

被接受的高层对象由生命周期控制器展开成更底层对象。一个训练请求可能产生分布式作业对象、若干角色模板、配置、服务发现和检查点挂载；一个模型服务请求可能产生部署、网络路由、自动扩缩策略和版本状态。父对象应记录子对象身份，子对象应能追溯父对象。这样用户删除高层请求时，系统可以安全清理派生资源，也能避免不同控制器同时争夺同一对象。

队列控制器与实际调度器承担不同职责。队列系统从组织角度决定某个工作负载何时获得准入以及占用哪类名义配额；调度器从集群当前状态决定具体 Pod 放到哪个节点。一个作业可能已经通过队列准入，却因节点刚刚故障而暂时无法绑定；也可能节点看似有零散 GPU，但作业未获组织配额。把两种等待混为一谈会导致错误扩容和错误告警。

设备与节点层最终把容器的资源请求关联到真实 GPU、网络和存储。驱动、容器运行时、设备发现和健康上报必须协同。若设备插件只报告数量，不报告健康与拓扑，调度结果可能无法满足运行要求。节点准备完成后，容器启动、加载数据和模型，工作负载进入数据面执行。

整条路径需要关联标识。用户请求 ID、项目、工作负载 UID、队列记录、Pod、模型版本、遥测和成本条目应能够串联。否则门户显示一个作业失败，SRE 只能在数十万 Pod 中猜测；成本系统看到 GPU 使用，也无法归到业务结果。关联标识不是为了日志美观，而是平台跨组件可解释性的基础。

### 4.3 工作负载运行路径和管理路径

数据面是实际完成计算或服务请求的地方。训练进程读取数据、执行前向与反向计算、通信并写出检查点；推理进程加载权重、接受请求并返回结果；流水线步骤转换数据和生成制品。这些过程承载业务数据，通常对带宽、延迟和设备性能敏感。它们应尽量沿最短路径访问数据与网络，不应让每次张量通信都经过平台门户或管理数据库。

控制面是创建、配置、观察和改变数据面的路径。门户、API、控制器、策略、队列、注册中心和发布系统属于控制面。它们处理的主要是元数据和状态，例如谁请求了什么、当前版本是什么、资源是否准入、服务是否健康。控制面的吞吐通常远低于数据面，但其错误可能影响大量工作负载，所以要重视幂等、权限、备份和升级兼容。

管理路径还包括人类操作。平台管理员修改资源池，安全人员更新策略，SRE 响应告警，FinOps 调整预算。成熟平台会让这些动作也通过版本化接口进入控制面，并留下审计记录。直接登录节点修改驱动或手工改数据库，可能暂时解决问题，却让声明状态与实际状态分离，下一次协调又会覆盖手工修改。

区分两条路径有助于设计网络和权限。用户请求平台 API 不需要直接访问 GPU 节点管理端口；训练容器访问对象存储不应获得修改平台配额的凭证；遥测采集器可以读取运行指标，但不应能够发布模型。权限遵循最小化后，单个工作负载被攻破时不容易横向控制整个集群。

区分两条路径也有助于性能判断。训练变慢可能来自数据面网络、存储或 GPU；提交变慢可能来自控制面 API、策略或队列。若所有指标都汇总为“平台延迟”，团队无法分派问题。平台应分别定义控制面服务等级与数据面工作负载目标，并建立从用户症状到组件信号的关联。

### 4.4 控制面故障为何不应直接破坏数据面

理想情况下，已运行工作负载不应因为门户短暂不可用而停止。门户只是请求入口，训练进程已经获得资源并在数据面执行。类似地，模型注册中心暂时不可用应阻止新版本晋级，但不应让当前线上服务立即退出。这个性质称为故障隔离：控制面故障影响管理能力的范围，应尽量小于数据面业务影响范围。

要实现隔离，首先不能把高频数据路径强制经过中央控制服务。若每个推理请求都要同步查询模型注册中心，注册中心故障就会直接中断推理；更好的方式是在发布时解析不可变模型版本，把运行所需信息下发到数据面。若每个训练批次都要向门户确认配额，门户延迟就会进入训练关键路径；更合理的是在准入时授予资源，运行期间通过异步遥测核算。

其次，需要区分控制平面一致性与数据面连续性。控制器重启后可以从持久状态重建缓存，短期内停止创建新资源，却让现有 Pod 继续运行。策略服务不可用时，高风险新请求可采用失败关闭，已批准对象则继续执行。不同能力的故障策略不应一刀切：安全准入可能宁可拒绝新变更，成本报表则可以暂时延迟更新。

状态存储是隔离设计的关键。平台数据库、集群 API 状态、模型注册元数据、对象存储和遥测后端分别保存不同事实。架构必须说明哪个是每类信息的事实源，备份和恢复目标是什么，缓存是否可重建。若同一“模型当前版本”被同时手工维护在门户数据库、Git 和服务配置中，控制面恢复后就会产生冲突。
