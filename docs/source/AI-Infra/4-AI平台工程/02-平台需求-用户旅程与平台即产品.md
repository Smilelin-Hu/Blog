# 平台需求、用户旅程与平台即产品

一家公司的平台团队收到一句很常见的要求：“我们也要做一个像大厂那样的 AI 平台。”接下来，所有人开始列工具。有人建议安装 Kubeflow，有人希望引入 Slurm，有人主张先做门户，还有人认为应该购买一套商业 MLOps 产品。三个月后，集群里多了十几个组件，用户提交训练仍然要在群里找管理员，模型上线仍靠复制配置，平台团队每天仍被重复工单淹没。

![平台需求与用户旅程](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l02_01.png)

问题不一定是工具选错了，而是团队一开始没有把“平台”翻译成用户任务、服务契约和可验证结果。用户说“提交训练太麻烦”，背后可能同时包含环境不稳定、权限审批慢、队列不可见、作业状态难懂和结果无法登记。只购买一个训练 Operator，最多解决其中一段；如果平台把整句话当成一个需求，交付之后双方必然对“完成”有不同理解。

平台需求工程要完成一次关键转换：把模糊愿望转换为角色、旅程、痛点、能力、接口、服务等级、配额和指标。转换后的结果必须能同时回答三类问题：用户通过什么路径完成工作，系统承诺哪些可观察行为，平台团队怎样判断投入是否真正改善了结果。

判断一份平台需求能否进入架构设计，可以先检查五件事：

- 是否说清楚了谁在什么情况下发起请求，而不是只写“用户需要”。
- 是否描述了从触发到结果的完整旅程，包括等待、失败和人工决策。
- 是否把痛点映射成稳定能力，而不是直接映射到产品名称。
- 是否为能力规定输入、输出、限制、状态、所有者和服务等级。
- 是否定义了能够证明问题改善的指标，而不是把“上线某组件”当作成功。

这篇文章沿着这五个问题展开。最后的实验会输入三类用户旅程、十五个痛点和十二项平台能力，自动检查每个痛点是否有能力承接、每项能力是否有 API、SLO、指标和负责人，并生成可以进入路线图评审的 MVP 能力清单。

## 1. 为什么从工具选型开始通常会失败

### 1.1 工具能力与用户问题为什么不是一一对应

工具文档通常按自身对象组织。Kubernetes 讲 Pod、Deployment、Job 和调度；队列系统讲配额、准入和公平共享；流水线引擎讲步骤、制品和缓存；模型注册中心讲模型版本、标签和血缘。用户不会按这些对象表达问题，他们说的是“我不知道作业为什么没启动”“这个模型到底来自哪次训练”“能不能今天上线”“为什么这个月用了这么多卡”。

一项用户问题往往跨越多个组件。以“训练启动太慢”为例，提交 API 可能花一秒，队列等待两小时，节点供给十分钟，镜像拉取五分钟，数据准备又花十五分钟。门户、队列、自动扩缩、镜像仓库和存储都参与结果。若团队只安装更快的训练控制器，却没有分解延迟，用户体感几乎不会变化。

反过来，一个工具也可能实现多项能力。策略控制器既可以校验特权容器，也可以检查资源上限、镜像签名和数据区域；平台门户既可以提供能力发现，也可以承载项目申请、状态查询与支持入口。把“一个工具”等同“一项需求”，会导致能力重复、状态冲突和所有权不清。

因此，需求与实现之间需要一层能力模型。能力用用户和组织能够理解的语言描述稳定结果，例如“版本化运行环境”“工作负载提交与状态”“队列与等待原因”“不可变模型版本”“发布与回滚”“成本归属”。组件只是当前实现。架构可以更换组件，但不能在替换时丢失能力语义。

能力模型还有一个作用：暴露空白。如果架构图上已经有 Kubernetes、Kubeflow、Prometheus 和对象存储，却没有人负责把成本归属到项目，那么“成本归属”就应作为未实现能力出现，而不是假设监控系统会自动解决。只有先列能力，团队才能发现“装了很多工具，但关键旅程仍有断点”。

需求评审时，可以做一个简单测试：暂时遮住所有产品名称，只保留用户、动作、能力和状态。如果方案仍能解释请求怎样完成，它是能力驱动的；如果遮住产品名称后只剩空框，团队讨论的其实是采购和安装，不是平台产品。

### 1.2 平台团队的客户究竟是谁

平台的直接客户通常不是购买公司产品的外部消费者，而是组织内部需要训练、评测、发布和运营 AI 工作负载的人。内部并不意味着需求可以模糊。相反，内部用户拥有绕开平台的可能：他们可以直接申请云账户、登录服务器、维护自己的脚本。如果平台不能比自建路径更快、更稳定或更安全，用户只会在制度要求下被动使用。

“算法工程师”也不是一个足够精确的客户定义。进行交互探索的数据科学家、维护大规模训练的训练工程师、交付在线服务的推理工程师，虽然都写 Python，却有不同触发点、风险和成功标准。数据科学家希望十分钟内进入环境；训练工程师更关心多机作业能否一起启动和恢复；推理工程师关心版本、容量、流量和回滚。

平台还有治理型客户。安全人员需要知道谁访问了什么数据、哪些镜像能够运行、哪个模型通过了什么规则。FinOps 负责人需要把 GPU、存储、网络和共享服务成本归到项目。SRE 需要从一个用户请求关联到控制器、Pod、节点和告警。这些角色可能不直接提交模型，却决定平台是否能在企业环境长期运行。

客户识别的关键不是列职位，而是列责任。一个小团队里，同一个人可能既训练又部署；大型公司可能把数据、训练、服务、SRE 和安全分成多个部门。平台需求应该写成“负责将候选模型交付生产的人需要……”，而不是假设某个固定岗位名称在所有组织都相同。

每项能力还要区分主要用户、决策者、被影响者和运营者。训练提交的主要用户是训练工程师，配额决策可能由平台和 FinOps 共同制定，被抢占的其他团队会受影响，队列控制器由平台团队运营。只访谈提交者，容易忽略公平与成本；只听管理者，又容易做出流程完整但使用困难的系统。

平台团队自己也是平台客户。控制器升级是否可回滚，策略变更是否能预检，事故能否定位，容量是否可预测，决定了平台能否持续交付。内部运营需求不应压过用户旅程，但必须与产品功能一起进入路线图，否则每次新增能力都在扩大不可维护的系统。

### 1.3 需求列表为什么无法直接变成架构

常见需求列表会写：“需要支持 Notebook、分布式训练、模型部署、权限、监控和成本。”它列出了名词，却没有说明对象怎样连接。Notebook 里的代码怎样变成训练作业？训练结果怎样进入模型版本？什么条件允许模型部署？权限在哪一步检查？成本按申请、分配还是实际使用核算？这些关系决定控制面，而名词清单看不出来。

需求还经常混合不同层级。“支持 GPU”是资源能力，“训练三小时内开始”是服务等级，“安装 Kueue”是实现选择，“提升研发效率”是业务目标，“用户可以查看等待原因”是产品体验。若把它们放在同一优先级列表里，团队无法判断依赖关系，也无法验收。

从需求到架构至少要经过四次翻译。第一次把愿望翻译成用户旅程；第二次把旅程中的痛点翻译成能力；第三次把能力翻译成平台 API、状态与服务契约；第四次才把 API 和能力映射到组件、集群与组织。跳过中间层，架构会过早绑定实现，也无法解释为何选择它。

例如“训练团队需要八张 GPU”还不是完整需求。旅程中可能发现团队真正需要的是：一次声明整组资源、在等待期间看见原因、预计开始时间可供安排工作、成员必须同一时间进入、失败能从检查点恢复、结果自动登记成本。架构因此需要的不只是设备分配，还包括队列、Gang 准入、拓扑、状态、恢复和成本关联。

需求之间还会冲突。业务希望所有请求立即启动，财务希望减少闲置，安全希望高风险变更经过审核，研发希望完全自助。平台不可能让所有目标同时最大化。需求工程必须把冲突转化为可选择的服务等级和产品档位，例如高优保留容量、普通公平队列、低价可抢占资源，而不是用一句“兼顾效率与成本”掩盖。

需求列表只有在包含触发、结果、约束、状态、指标和所有者后，才具备进入设计的条件。架构不是把需求名词摆进方框，而是为整条旅程建立持续工作的控制关系。

## 2. 建立真正有用的用户角色

### 2.1 数据科学家的探索路径

数据科学家的工作通常从一个不确定问题开始。他们需要查看样本、尝试特征、运行小模型、比较指标，并不断修改代码。此时“最优资源利用率”不是首要目标，快速获得可用环境和保存思路更重要。若每次试验都要提交工单等待一天，团队会回到个人电脑或长期占用服务器。

探索路径的第一个平台问题是环境。用户希望打开工作空间后就有版本明确的 Python、框架、数据访问方式和持久目录。平台不能只承诺 Pod 已创建，还要承诺交互环境何时可使用。工作空间启动时间、首次成功率、空闲回收与数据持久化共同构成产品契约。

第二个问题是从交互到可重复。Notebook 允许随时安装包、修改变量和手工执行单元，这些状态很难复现。平台应提供把代码、依赖、参数和数据标识转成批作业的路径。转换不一定完全自动，但必须让临时探索逐步进入版本化环境，而不是把 Notebook 快照当作生产制品。

第三个问题是数据权限。数据科学家通常需要访问多个数据集，平台不能把长期个人密钥放进环境。更合理的方式是根据项目和工作负载签发短期身份，显示允许的数据范围并记录访问。数据申请的等待和拒绝原因也属于用户旅程，不应被当作外部流程忽略。

第四个问题是结果比较。一次实验至少要关联代码、数据、参数、环境、指标和制品。平台可以使用实验跟踪或元数据系统实现，但对用户提供的是“这个结果怎样重现”的能力。若指标很好却找不到对应代码和数据，探索并没有形成可交付知识。

因此，数据科学家的成功指标可以从“拥有 Notebook”改成“首次有意义实验时间”“从交互转为可重复作业的比例”“环境导致的失败率”和“结果血缘完整率”。这些指标更接近用户价值，也能指导平台改进。

### 2.2 训练工程师的规模化路径

训练工程师接手的是已经较明确的模型和数据方案，他们要把试验扩展到更多设备、更长运行和更严格恢复。训练作业可能持续数天，一次失败损失大量卡时。平台产品不能只提供资源申请，还要把队列、拓扑、环境、检查点和成员状态组织成可操作生命周期。

规模化路径从声明开始。训练工程师应描述角色、资源、最小规模、拓扑、镜像、入口、数据和恢复策略，而不是复制数百行底层 YAML。平台模板封装稳定默认值，同时保留会影响训练结果和成本的参数。模板版本必须可追溯，否则同一声明在不同日期可能产生不同运行环境。

等待是训练旅程的重要组成。资源昂贵且稀缺，大作业等待很正常。用户真正无法接受的是不知道为什么等待、能否插队、预计多久、是否因为自己的配置永远无法满足。队列状态应区分配额不足、等待公平份额、缺少特定 GPU、缺少同拓扑资源和等待节点供给。

运行阶段要连接平台与训练信号。平台能够看到 Pod、节点和设备，训练应用知道步数、吞吐、损失与检查点。两类信号需要用同一个运行标识关联。节点故障后平台可以重建成员，训练工程师则要保证检查点可用；职责只有在请求和状态中明确，事故时才不会互相等待。

训练结束并不等于旅程结束。结果需要写入受管理制品位置，登记模型版本与血缘，释放资源和短期凭证，记录等待、运行、重试与成本。若最后一步仍靠人复制文件，平台只自动化了计算，没有自动化交付。

训练工程师的产品指标包括高分位排队时间、首次启动成功率、有效检查点比例、故障恢复时间、失败重跑卡时和模型血缘完整率。只看 GPU 利用率无法判断训练路径是否可靠。

### 2.3 推理工程师的交付路径

推理工程师从候选模型版本出发，目标是让它以明确容量和风险进入某个环境。交付路径包含版本选择、策略与评测门禁、资源准备、健康检查、流量迁移、观测和回滚。任何一步依赖人工记忆，都会让发布难以重复。

第一个要求是不可变版本。用户可以使用“候选”“生产”等别名选择模型，但发布系统最终必须解析为不可变制品摘要。评测结论、镜像、模型和配置要锁定同一版本，避免别名移动后发布一个没有验证的对象。

第二个要求是容量与就绪。推理容器进程启动不代表模型已经加载，副本创建也不代表可以接流量。平台需要读取应用级就绪，评估发布期间新旧版本是否会同时占用 GPU，并在容量不足时阻止或改变策略。发布前置时间应从用户请求到新版本真正可服务计算。

第三个要求是可控流量和回滚。平台可以提供 Canary 或蓝绿发布，但推理团队需要声明业务指标、观察窗口和回滚条件。平台执行状态机并留下证据，不能替业务决定质量阈值。异常时，回滚对象应是已知不可变版本，而不是重新寻找某个路径下的旧文件。

第四个要求是长期运营。在线服务没有自然结束，会持续占用 GPU。平台需要关联项目、模型、环境、容量、流量和成本，支持扩缩与退役。推理工程师关心延迟和吞吐，平台还要看到副本就绪、资源等待、发布状态与设备健康。

推理路径的成功指标包括发布前置时间、变更失败率、自动回滚时间、版本与评测证明匹配率、目标 SLO 达成率和保留容量成本。门户中出现“部署成功”不等于这些结果已经成立。

### 2.4 管理员、安全和财务的治理路径

平台管理员需要维护项目、模板、资源池和控制器。他们的旅程常被隐藏在用户功能之后：创建一个新项目要改多少系统，模板升级怎样灰度，节点维护怎样避免中断，控制器失败怎样恢复。若每项能力都增加新的手工操作，用户越多，平台团队越无法扩展。

安全人员的任务不是给每个请求盖章，而是定义威胁、规则、证据和例外。他们需要知道哪些请求可以自动通过，哪些必须人工接受风险，规则变更怎样测试，误拒绝怎样回滚。平台提供统一策略入口后，安全团队才可能从重复审批转向治理设计。

财务和 FinOps 需要把资源消耗转化为可理解的成本。他们关心项目、成本中心、资源类别、使用时间、共享成本和预算。若平台对象没有稳定身份和标签，月底只能按节点粗略分摊；如果只按 GPU 分配时间收费，又可能忽略等待、重试、存储与长期保留。

治理角色还需要查看例外。哪些团队绕过了标准模板，哪些作业超出预算，哪些策略被豁免，哪些资源长期无所有者。例外不是一定要消灭，但必须有范围、批准者、期限和退出方式。没有例外流程的严格平台会把特殊需求逼到系统之外。

这些角色的成功标准与研发不同。管理员关心自动化覆盖、变更失败与恢复；安全关心策略覆盖、误拒绝、审计完整和例外到期；FinOps 关心成本归属、预算偏差、闲置与预测准确性。平台路线图必须同时容纳这些结果，不能把治理需求永远排在“核心功能完成以后”。

## 3. 把一次工作拆成可以观察的旅程

人物画像只回答“谁在使用”，用户旅程才回答“他怎样得到结果”。很多需求访谈停留在愿望层：用户想要更快、管理员想要更稳定、安全希望更可控。这样的词无法直接指导接口、控制器或值班手册。旅程分析必须把愿望落到事件、状态、等待、失败与责任转移上。

一条可用于平台设计的旅程至少包含六类信息：触发条件、用户提交的声明、系统生成的状态、外部依赖、完成证据和异常出口。它不是一张营销流程图，而是一份从产品语言通往工程状态机的中间模型。只要其中某一项无法说明，平台团队就还不能断言自己理解了需求。

### 3.1 不要只画顺利路径

以“提交分布式训练”为例。顺利路径看起来很短：选择环境、提交作业、等待启动、查看日志、得到模型。但真实用户经历还包括镜像拉取失败、配额不足、同拓扑 GPU 不足、某个成员迟迟未就绪、数据凭证过期、检查点损坏和制品登记失败。恰恰是这些分支决定平台有没有价值。

旅程中的每一步应记录一个可观察事件。用户按下提交按钮只是入口事件；随后还应有请求被接受、策略已评估、配额已保留、调度已准入、资源已绑定、成员已就绪、训练开始、检查点已落盘、作业完成和制品已登记。事件之间的时间差就是平台性能，而不是只记录最后一个总耗时。

等待状态也要成为一等产品对象。`Pending` 对 Kubernetes 来说可能足够，对训练工程师却没有解释力。平台应把底层条件翻译为“项目并发上限已满”“等待八张同一高速互联域内的 H100”“所选模板不允许该安全上下文”或“数据访问审批尚未完成”。可行动的等待原因比一个不断旋转的图标有价值得多。

失败需要区分可重试、需修改声明和需人工处置三类。临时控制器超时可以自动重试；请求四张 GPU 而配额只有两张，需要用户修改或申请；数据源被认定为受限数据，则可能需要数据所有者参与。若所有失败都返回同一个错误码，支持团队只能依靠经验重新诊断。

完成证据同样不能省略。实验完成要有不可变结果位置、运行参数、代码版本、环境版本和成本归属；训练完成还应包含检查点与模型血缘；发布完成则要有流量状态、健康窗口、门禁结论和回滚对象。没有证据的“成功”无法进入下一条自动化链路。

设计旅程时可以反向提问：如果用户明天投诉这一步很慢，用哪个时间戳证明？如果控制器重启，哪一条声明能够重建状态？如果操作失败，谁能根据事件判断下一动作？如果半年后审计，什么对象能够还原当时的决策？这些问题会自然暴露出单纯功能列表看不到的缺口。

### 3.2 用户动作与控制器循环不是一回事

平台门户常把许多底层动作包装成一个按钮，因此团队容易误以为一次点击对应一次同步调用。实际上，AI 工作负载通常跨越多个控制器和较长时间。用户提交的是期望，控制面不断观察实际状态并推进，两者应通过稳定对象和状态字段连接。

用户动作应尽量是声明式的。例如用户声明“为项目 A 运行模板版本 3 的八卡训练，在失败时从最近检查点恢复，预算上限为某值”。用户不应负责按顺序创建 ServiceAccount、PVC、PodGroup、Job、监控规则和制品目录。后者是平台内部实现，可能随版本改变。

控制器循环则需要回答三个问题：现在观察到什么，距离期望还差什么，本轮采取什么动作。每次动作都应幂等，重复执行不会产生第二份资源；状态写回要包含条件、原因、消息和观测版本；外部调用要能够在超时后判断是否已经成功。否则一次网络抖动就可能产生重复训练或重复发布。

用户旅程与控制器旅程可以并排描述。用户看到“等待资源”，调度控制器可能先后经历配额检查、公平队列排序、Gang 准入、节点过滤和设备分配。用户不需要阅读所有原始事件，却需要稳定的解释层。平台产品的职责不是隐藏一切，而是把复杂度压缩成与用户决策相关的信息。

这也决定了界面设计。长任务不能让浏览器请求一直等待，而应立即返回稳定的运行标识，再通过查询、事件流或通知获得进展。命令行、SDK 和门户都操作同一个资源对象；门户关闭后，控制器仍继续推进。把浏览器会话当成工作流引擎，是许多内部平台脆弱的根源。

取消也应被设计为状态转换，而不是强制删除。用户发出取消意图后，平台可能先阻止新成员、请求应用保存检查点、终止计算、回收设备、撤销临时凭证、保留必要日志，最终进入已取消状态。紧急终止可以是另一种动作，但必须说明可能丢失哪些证据和数据。

同理，“重试”不能简单复制按钮行为。平台要说明重用哪个输入版本、是否沿用原请求身份、预算怎样累计、检查点是否兼容、旧运行与新运行怎样关联。一次重试产生新的运行实例，但应保留共同的逻辑工作负载身份，便于计算失败成本和恢复成功率。

### 3.3 人工批准应该放在哪里

企业平台不可能消除所有人工判断，但可以把人工判断放到正确的位置。适合自动化的条件应编码为策略；只有缺少确定规则、风险需要明确接受或法律流程要求签字时，才进入人工批准。把每个训练作业都送给管理员审批，只是把排队从调度器搬到了工单系统。

一个批准点需要明确批准对象。是批准某项目可访问一类数据，批准某模板版本可进入生产，还是批准一次具体运行？对象范围越宽，使用越方便，但潜在影响越大；范围越窄，重复劳动越多。通常应优先批准可复用且有版本的能力，例如“项目 A 在九十天内可使用数据集版本 D 的脱敏视图”，而不是逐 Pod 审批。

批准还要有输入证据。安全审查可能需要镜像扫描结果、制品签名、数据分类、运行身份和网络目的地；发布审查需要离线评测、负载测试和回滚演练。平台应自动收集并绑定这些证据，审批者只对例外和风险作判断，而不是手工搜索多个系统。

审批结果必须机器可读。允许或拒绝之外，还要有适用范围、条件、批准者、理由、时间和到期日。控制器根据结果推进，审计系统可以还原，通知系统提醒到期。若批准只存在聊天消息里，平台无法安全复用，也无法在条件变化后自动失效。

人工环节的 SLO 也不能忽略。某个审批平均耗时两天，会直接成为交付前置时间。平台产品经理应测量进入审批的比例、等待时长、被拒原因、补充材料次数和过期量。若大量请求都以同样理由通过，说明该判断可能已经具备策略化条件。

对于高风险的紧急变更，可以设计“先受控执行、后补充审查”的破窗流程，但它必须比正常路径留下更多证据：调用人、事件编号、影响范围、自动到期、实时告警和事后复盘。破窗不是绕开平台，而是平台提供的一种被严格约束的例外产品。

### 3.4 例外不是备注栏，而是有生命周期的对象

任何成熟平台都会遇到标准路径无法满足的需求。研究团队可能需要尚未纳入模板的新驱动，训练团队可能需要跨区域数据，推理团队可能因活动临时保留过量容量。完全拒绝会促使团队搭建影子系统；无条件接受则会让平台失去标准。

正确做法是把例外显式建模。例外请求需要关联主体、资源、规则、业务理由、风险、补偿措施、批准人、开始时间和到期时间。它还应说明结束后是撤销、迁移到正式能力，还是延长。这样平台能区分“暂时特殊”与“已经成为普遍需求”。

例外的默认期限应短于资源和项目生命周期。到期前通知所有者；未续期则自动停止新使用，在不会造成数据损坏的前提下撤销；无法自动撤销时至少产生升级事件。没有到期的例外会逐渐成为永久后门，而且团队往往已忘记最初理由。

例外数据是路线图的重要输入。如果五个团队分别申请同一种 GPU 拓扑，说明标准资源产品缺了一档；如果某个模板不断因同类依赖被绕过，说明模板演进太慢；如果所有发布都需要人工豁免某规则，可能是策略不符合实际风险。平台应按类型、频率、影响和持续时间回顾例外。

但高频不意味着必须产品化。某类例外也可能暴露不应支持的工作方式，例如绕开数据保留规则或使用无法获得安全更新的运行环境。此时平台需要明确拒绝，并给出替代路径。产品管理的责任不仅是增加能力，也包括清晰划定不提供的能力。

## 4. 从旅程抽出能力，而不是反向推销组件

完成旅程后，下一步不是立即选择项目，而是提炼平台能力。能力描述一种稳定结果，例如“提交可恢复的分布式工作负载”“获得可解释的排队状态”“把模型版本安全迁移到生产”。Kueue、Volcano、Slurm、Argo、MLflow 或 KServe 都只是实现某些能力的候选组件。
