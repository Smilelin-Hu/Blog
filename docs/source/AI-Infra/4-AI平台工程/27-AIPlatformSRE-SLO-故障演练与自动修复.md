# AI Platform SRE：SLO、故障演练与自动修复

AI 平台的可靠性不能只用“集群是否在线”来描述。对模型训练用户而言，提交成功却长期无法准入仍然是不可用；对在线推理用户而言，接口返回成功但首 Token 延迟持续越界也不能算作良好服务；对平台团队而言，GPU 节点看似 Ready，却不断产生设备错误、通信异常或作业重试，同样意味着有效容量正在下降。AI Platform SRE 的目标，是把用户可感知结果、平台控制面状态、算力基础设施健康和变更风险连接为一套能够计算、告警、演练、修复与复盘的可靠性系统。

![AI Platform SRE 与可靠性控制面](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l27_01.png)

本文以 Kubernetes v1.36、Prometheus 3.12.0、Alertmanager 0.32.1、Chaos Mesh 2.8.3 和 NVIDIA DCGM 4.6.1 的官方语义为核验基线。版本用于固定接口与能力边界，不表示这些组件能够自动构成完整 SRE 平台。OpenTelemetry Collector 延续前一篇的 0.159.0 基线，用于说明遥测证据质量；当真实 Kubernetes、Prometheus、Alertmanager、Chaos Mesh 或 NVIDIA GPU 环境缺失时，相应路径必须记录 `SKIPPED`，不能用模拟输出替代生产证据。

## 1. 课程定位

本文讨论 AI 平台如何建立可靠性目标，并让观测、决策、演练和恢复互相验证。重点不是背诵 SLI、SLO 和 SLA 的定义，也不是把任意故障都交给脚本自动重启，而是回答五个工程问题：平台承诺什么用户结果；这些结果怎样从可信事件中计算；错误预算如何约束发布和运维；故障演练怎样控制爆炸半径；自动修复如何做到有证据、有边界、可回滚并能证明恢复。

这里将训练、推理、流水线、调度、制品和 GPU Fleet 放入同一框架，但不会用一个全局可用率覆盖所有服务。不同用户旅程需要不同 SLI，不同故障域需要不同修复权限。可靠性控制面必须允许差异化目标，同时保持统一的身份、证据、审批和审计契约。

## 2. 学习目标

完成后应能够独立完成以下工作：

- 从用户旅程定义可观测、可计算、可行动的 SLI，并明确分子、分母、窗口和排除项。
- 为在线推理、训练准入、流水线、模型发布、制品读取和 GPU 节点建立分层 SLO。
- 计算误差预算、预算消耗率与多窗口燃尽率，区分分页告警、工单告警和趋势预警。
- 设计告警分组、抑制、静默、所有权、Runbook 和升级路径，降低告警风暴。
- 用稳态假设、目标选择器、最大影响量、时长、停止条件和恢复验证约束故障演练。
- 区分 Kubernetes 自愈、应用控制器恢复、平台自动修复和人工事件响应的责任边界。
- 为自动修复建立证据门禁、动作预算、冷却时间、幂等键、互斥锁、验证和回滚。
- 正确处理 PDB、节点隔离、GPU 被动健康观察与主动诊断，避免修复动作扩大事故。
- 运行确定性模拟、真实只读发现和受控破坏性实验，并对每条结果给出真实边界。

## 3. 前置知识与环境

需要理解 Kubernetes Pod、Deployment、StatefulSet、Job、Node、Probe、Event、Condition、PDB、Eviction API 和控制器调和；能够阅读 PromQL、YAML、JSON 与 Python；知道 Counter、Gauge、Histogram、Trace 和资源身份的基本语义。默认机制模拟只需要 Python 标准库。真实只读路径需要 `kubectl` 上下文和可选 Prometheus HTTP API。故障注入路径还需要受控集群、Chaos Mesh、隔离命名空间、可恢复测试负载、审批和持续观测。GPU 诊断路径需要受支持的 NVIDIA 驱动、DCGM、目标设备与独占维护窗口。

## 4. 知识串讲

### 1. 可靠性是用户结果，不是组件存活

组件存活是必要条件，却不是用户结果。API Server 可访问，并不代表训练用户获得配额；调度器运行，并不代表八卡作业能够整体准入；推理 Pod Ready，并不代表请求延迟、正确率和模型版本满足承诺。平台要从用户旅程反向选择信号，而不是从现有 Dashboard 正向拼凑一个可用率。

最实用的方法是为每种关键旅程写出“用户发起什么动作、何时认为成功、允许等待多久、失败由谁负责”。训练提交旅程可以从平台 API 接受请求开始，以 Workload 被准入并创建运行对象为成功；推理旅程从 Gateway 接收合法请求开始，以正确模型在时限内返回可用响应为成功。只要成功条件含糊，后续指标就会被实现细节绑架。

### 2. 服务边界必须先于 SLO

一个 SLO 的分母必须知道服务边界。若把用户错误、平台错误、上游身份服务故障、云厂商中断和计划维护全部混在一起，指标虽可计算，却无法推动任何单一团队行动。边界不是为了把失败排除掉，而是为了明确哪些失败计入用户承诺、哪些需要单独建立依赖 SLO、哪些只能作为解释维度。

AI 平台常见边界包括提交 API、队列准入、工作负载启动、运行时控制器、模型服务、制品存储、可观测性管线和 GPU 节点池。每个边界应有稳定所有者、依赖列表、故障域和变更入口。跨边界的端到端 SLO 用于表达用户结果，分层 SLO 用于定位责任，两者不能互相替代。

### 3. SLI 是经过语义约束的测量

SLI 不是任意指标名，而是对服务水平的数值表达。事件型可用性通常写成良好事件数除以有效事件总数；延迟 SLI 可写成在阈值内完成的有效请求数占比；训练准入 SLI 可写成在规定时间内进入 Admitted 状态的有效工作负载占比。分子和分母必须来自同一身份空间、同一时间语义和同一去重规则。

若请求在 Gateway 重试三次，服务端记录三条失败而客户端最终成功，分母如何计算取决于承诺对象。面向用户请求的 SLI 应按逻辑请求去重；面向服务端尝试的容量指标则保留每次尝试。把两者混用会让重试既掩盖故障又夸大流量。

### 4. 良好事件要可执行地定义

“请求成功”至少需要协议状态、业务状态、模型身份和时延共同判定。HTTP 200 但返回降级兜底文本，是否算良好要在产品契约中决定；流式推理已输出部分 Token 后中断，不能简单按连接建立成功；训练任务被准入后立即因镜像无权限失败，也不应被准入 SLI 吞掉，而应进入启动或执行 SLI。

良好事件定义要足够稳定，避免每次事故后临时改口径。变更定义时必须版本化并回算历史，否则趋势断点会被误认为可靠性变化。平台可在事件中保存 `sli_contract_version`，让同一窗口内的口径可以被追踪。

### 5. 有效分母决定指标可信度

分母应排除无法形成用户请求的探测噪声、已被明确拒绝的非法输入和内部健康检查，但不应排除平台容量不足、依赖故障或发布错误。若系统在故障时停止产生成功日志，只按已写入成功日志计算，指标会在最坏时刻变得更好。可靠分母通常来自入口计数、消息接收确认或控制面创建事件，并与出口结果进行核对。

缺失结果不能默认成功。超过最大观察时间仍无终态的事件，应进入超时或未知桶，并根据契约计入坏事件。未知比例本身应成为证据质量 SLI，超过门禁时 SLO 只能判为不确定，而不能宣称通过。

### 6. 可用性不等于正确性

AI 服务的响应可能协议成功、延迟正常，却使用了错误模型、错误租户适配器、过期配置或不满足质量门禁的版本。本文聚焦平台控制面，因此不重新展开模型评测方法，但会要求发布身份和评测结论进入可靠性事件。平台可用性 SLO 应至少验证实际模型 Digest、服务修订与路由策略是否符合期望。

模型质量属于评测闭环，平台可靠性负责确保被批准的质量结论没有在发布、路由和回滚过程中丢失。若运行版本与批准版本不一致，即使请求全部返回，也应视作平台正确性故障。

### 7. 延迟 SLI 要按旅程拆分

在线推理可拆为网关排队、路由、模型队列、批处理等待、首 Token、Token 间隔和端到端完成；训练可拆为提交、配额等待、调度、镜像拉取、数据准备和框架启动。端到端延迟表达用户体验，分段延迟定位瓶颈。只对端到端做 SLO 会让团队知道坏了却不知道从哪里行动。

阈值不能只取平均值。事件型延迟 SLI 可直接计算“在两秒内获得首 Token 的请求占比”，避免只看 P99 在低样本下的剧烈变化。Histogram 仍适合聚合与趋势，但桶边界应围绕产品阈值设计，不能事后从过粗的桶恢复精确分布。

### 8. 训练可靠性有排队与运行两种时钟

训练任务可能因团队主动选择低优先级队列而等待，这与平台故障不同。准入 SLO 要结合优先级、ResourceFlavor、配额和承诺级别。对保障型队列可承诺一定时间内准入；对机会型队列只能报告等待分布与中断率，不能借用同一目标。

运行时钟从资源实际交付后开始。多卡作业需要所有必要角色就绪，单个 Worker Pending 仍未形成可训练状态。作业重试要区分用户代码、数据、平台、节点和设备原因，否则平台会为用户代码失败承担错误预算，或反过来把基础设施故障归为用户错误。

### 9. 控制面 SLI 需要观察 Generation

![控制面状态与调和证据](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l27_02.png)

Operator 型平台的核心结果是期望状态被调和。仅统计 Reconcile 成功次数会被高频空转放大。更可靠的 SLI 是对象 `observedGeneration` 追上 `generation`，关键 Condition 在时限内达到期望状态，并且对应执行对象真实可用。控制器返回无错误不代表外部资源已经完成。

对于 KServe、Trainer、KubeRay、Pipeline 或自研 CRD，应保存提交 Generation、首次观察时间、关键状态转移和最终结果。对象被删除或替换时使用 UID 区分生命周期，不能以名称串接不同运行。

### 10. GPU Fleet 可靠性关注有效容量

节点 Ready 只说明 kubelet 与控制面关系，不能证明 GPU 可用。设备可能未被发现、资源未发布、XID 错误增加、显存出现不可纠正错误、NVLink 异常、温度或功耗受限，也可能被错误配置为可调度。GPU SLI 应包含设备发现率、健康设备数、分配成功率、作业因设备原因失败率和节点恢复时间。

有效容量是能够接受目标工作负载并完成验证的 GPU 数，而不是资产清单数。一个被 cordon 的故障节点应从可服务容量扣除，但仍保留在资产和维护视图。容量告警必须区分需求上升和健康容量下降，二者的修复动作不同。

### 11. SLO 是目标，不是愿望

SLO 应基于用户价值、系统能力和改进成本共同确定。把所有服务写成五个九并不会提高可靠性，只会制造长期违约和无意义告警。目标过低则无法推动工程质量。合理过程是先测量基线，识别关键旅程和失败模式，再选择能支持产品承诺的目标，并为依赖、容量和维护制定配套策略。

一个平台可同时拥有服务级目标与内部目标。外部目标关注用户结果，内部目标通常更严格，为检测和修复留下余量。内部目标不能对外冒充承诺，外部目标也不能成为停止优化的上限。

### 12. SLA 是业务后果，SLO 是工程控制

SLA 通常包含服务承诺、例外、测量方式和违约后果；SLO 是团队用于工程决策的目标；SLI 是测量。三者相关但不等同。平台团队应避免把每个内部控制指标都写入 SLA，也不能用法律文本代替可执行 SLO。

实验只计算工程 SLO，不模拟赔偿。若企业存在 SLA，SLO 定义应比 SLA 留出安全边际，测量链路要经审计，并明确时区、窗口、数据迟到和修订政策。

### 13. 时间窗口改变决策含义

滚动窗口持续反映最近一段时间，适合运维；自然月窗口便于业务结算，但月初和月末的预算含义不同。短窗口捕捉快速故障，长窗口抑制瞬时噪声。一个 30 天目标不能只在月底计算一次，否则发现超支时已无法恢复预算。

平台应同时保留窗口类型和评估时间。数据迟到时可以在限定期内修订历史，但已经触发的事件响应不能被静默删除。告警使用当前可用证据，报表使用最终校正数据，两者要有版本与差异说明。

### 14. 误差预算把目标转成可消费资源

目标为 99.9% 时，允许坏事件比例为 0.1%。在某窗口内，允许坏事件数等于有效事件总数乘以允许错误比例；实际坏事件除以允许坏事件得到预算消耗比。预算不是允许团队故意制造故障，而是承认绝对可靠成本无限，并将风险选择显式化。

预算剩余充足时可以加快受控变更；预算快速消耗时应收紧发布、优先修复可靠性缺陷；预算耗尽时只允许降低风险或恢复服务的变更。策略要在事故前写好，避免业务压力出现后临时解释。

### 15. 低流量服务不能机械计算比例

当窗口只有几个请求，一个失败就会产生巨大错误率。比例数学正确，却不一定支持分页。解决方法不是忽略低流量，而是设置最小事件数、结合合成探测、延长窗口，并对关键服务增加绝对失败条件。样本不足应返回 `INCONCLUSIVE`，同时触发观测或流量覆盖工单。

训练队列天然低频，更适合用完成时间、绝对失败数、分位数和状态机持续时间联合判断。所有 SLI 都应记录样本量，Dashboard 不能只显示百分比。

### 16. 燃尽率描述预算消耗速度

燃尽率等于观测错误比例除以 SLO 允许错误比例。目标 99.9% 时允许错误比例是 0.1%；若当前错误比例为 1%，燃尽率就是十倍。含义是若该速度持续，预算会以正常速度的十倍耗尽。燃尽率让不同目标的服务可以使用一致风险语言。

单窗口阈值容易被短尖峰或慢性退化欺骗。高阈值短窗口可快速捕捉严重故障，低阈值长窗口可识别缓慢消耗。告警应同时要求短窗口和对应长窗口超过同一阈值，既保留灵敏度，也减少瞬时噪声。

### 17. 多窗口告警需要成对评估

快速分页规则可以组合五分钟与一小时窗口，慢速工单规则可以组合三十分钟与六小时窗口。具体时长和阈值取决于目标、值班响应时间和预算周期，不应照抄固定数字。实验使用两对窗口说明算法，不宣称这些阈值适用于所有平台。

每个窗口必须使用一致 SLI 口径，且长窗口数据完整。若短窗口超过而长窗口未超过，可能是刚出现的尖峰，需要继续观察或由绝对严重度规则补充；若长窗口超过而短窗口恢复，说明近期可能已缓解，不应重复分页，但仍需调查已消耗预算。

### 18. 遥测质量是 SLO 判定前置条件

采集缺失、时间戳漂移、身份无法关联或查询结果过期时，SLO 数字可能看似正常。平台必须先评估遥测完整率、时效性、未知序列比例和时钟偏差。证据不达标时，业务 SLO 状态应标记不确定，同时由可观测性团队接手数据质量事件。

不能把“没有错误样本”直接解释为“没有错误”。入口与出口计数差异、Collector 拒收、Exporter 失败和后端摄取延迟都应进入证据门禁。前一篇建立的可观测性自身 SLI，在这里成为所有自动决策的信任基础。

### 19. 告警的目标是触发行动

能够展示异常但没有明确行动的信号适合 Dashboard 或工单，不适合叫醒值班人员。分页告警必须满足紧急、用户影响显著、值班者可以立即行动三个条件。否则告警越多，真正事故越容易被忽略。

每条分页告警应携带服务、环境、故障域、严重度、当前值、目标、窗口、开始时间、Runbook 和主要证据链接。标签用于路由和分组，注释用于人类上下文；无界请求 ID 不应成为告警标签。

### 20. Alertmanager 负责通知语义

Prometheus 告警规则判断条件何时 active、pending 和 firing；Alertmanager 负责分组、去重、路由、静默和抑制。把所有逻辑塞入 PromQL 会让通知关系难以治理，把告警条件交给 Alertmanager 又会丢失时序计算。二者职责需要清晰分开。

`for` 可以要求条件持续一段时间后再 firing，`keep_firing_for` 可降低数据短暂缺失造成的抖动。它们不是故障修复，也不能替代多窗口门禁。时长过长会延迟真实事故，过短会放大噪声，应通过历史重放和演练校准。

### 21. 分组要围绕共同处置单元

网络分区可能让数百个 Pod 同时告警。若每个 Pod 都通知一次，值班者无法看到根因。分组键应围绕集群、服务、环境、故障域和严重度，使同一处置动作对应一个通知组。分组过粗会把不同事故合并，过细会重新制造风暴。

告警指纹要稳定，同一实例的持续事件不应每次评估生成新通知。动态值放在注释而不是指纹标签。版本变化是否形成新事件取决于是否需要不同处置，一般发布修订应保留为定位维度，但不能导致每个 Pod 重启都建立全新分页。

### 22. 抑制表达因果优先级

当 NodeUnavailable 已 firing，同一节点上的 Pod 延迟、GPU Exporter Down 和训练 Worker Missing 很可能是派生症状。抑制规则可以在根因告警存在时不发送这些通知，同时保留其状态供调查。抑制必须使用共同标签连接，避免一个集群故障误抑制其他集群。

抑制不是删除证据。被抑制告警仍应在事件时间线可见，并在根因解除后重新评估。若根因判断错误，值班者需要能够查看派生信号。规则本身应测试缺失标签语义，防止空值相等造成意外抑制。

### 23. 静默不是修复

静默适合计划维护、已知事件和短期降噪，应有创建者、原因、匹配范围和过期时间。永久静默会把未解决问题变成不可见风险。维护结束前应验证服务恢复并让静默自动到期，不应依靠人工记忆删除。

错误预算耗尽时更不能用静默让 Dashboard 变绿。静默只影响通知，不改变 SLI、SLO 或事故事实。所有静默操作应进入审计，并检测范围过宽和持续时间异常。

### 24. Runbook 是告警契约的一部分

Runbook 应先说明用户影响和安全边界，再给出验证步骤、常见原因、最小风险动作、升级人和恢复标准。只写“重启服务”不是 Runbook。对于 GPU 节点，要区分被动健康检查、节点 cordon、工作负载迁移、主动诊断和硬件维修；对于训练队列，要区分配额耗尽、拓扑不足和控制器故障。

命令要默认只读，破坏性步骤必须显式标注前置条件和回滚。Runbook 链接失效应由持续测试发现。告警没有 Runbook 时可以先进入工单，不能直接接入高风险自动修复。

### 25. 事件响应要有角色和时间线

事故处理至少需要事件指挥、操作执行、沟通和记录角色，小团队可以一人兼任，但责任仍要明确。时间线应记录首次用户影响、首次信号、告警触发、确认、缓解、恢复、验证和关闭。没有统一时钟与身份，复盘会陷入互相矛盾的截图。

平台事件可能同时影响多个租户。沟通内容应说明受影响能力、已知范围、当前缓解和下一次更新时间，不泄露其他租户数据。技术团队内部可以保留更细节点和工作负载证据，但访问要按职责控制。

### 26. 严重度由影响和紧迫性决定

一个 GPU 故障若有冗余且未影响作业，可以是维护事件；同样故障发生在容量临界点并导致核心推理不可用，就需要分页。严重度不能只根据组件名称固定。应结合用户影响、受影响租户、持续时间、数据风险、容量余量和恢复路径。
