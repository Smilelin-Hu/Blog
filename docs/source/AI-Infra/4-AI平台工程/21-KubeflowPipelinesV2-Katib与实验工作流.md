# Kubeflow Pipelines V2、Katib 与实验工作流

一个训练脚本能够在开发者笔记本中跑通，并不等于它已经成为平台可交付的实验工作流。数据可能在对象存储中被原地替换，容器镜像标签可能指向新内容，评估逻辑可能依赖一个未记录的配置文件，失败后的手工重跑还可能重复注册同一个模型。流水线表面上是四个绿色节点，实际上却无法回答“这个候选模型究竟由哪份数据、哪个环境和哪套门禁产生”。

![Kubeflow Pipelines 与实验工作流](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l21_01.png)

还有一类平台把超参搜索理解为“多启动几个训练任务”。当搜索空间、并发 Trial 数、单 Trial GPU 需求和失败上限都没有边界时，Katib 就会成为一个绕过资源治理的任务放大器。正确设计不是删掉自动搜索，而是让 Experiment、Trial、TrainJob、Kueue 配额、指标收集与候选模型注册共同形成可预测的产品合同。

本文以 2026 年 8 月 22 日核验的官方一手资料为事实基线。Kubeflow Pipelines 后端与 SDK 采用 2.17.0，Katib 采用 v0.19.0。这里将一条“数据检查—TrainJob 训练—外部评估结果读取—候选模型注册”的流程展开为任务图、类型合同、缓存合同、血缘合同、恢复合同和资源预算合同，最后用可运行模拟路径和只读真实环境路径验收。

## 1. ML Pipeline 表达的是实验语义

ML Pipeline 与普通软件 CI Pipeline 都有有向图、失败状态和重试，但两者的核心对象不同。CI 主要围绕源代码、构建产物、测试证据和环境晋级；ML Pipeline 还必须把数据集、特征、训练配置、模型、指标和评估策略当成一等输入与输出。源代码未变时，数据版本或门禁版本变化仍应产生新实验结果。

所以平台不应用“节点是否成功”作为唯一交付。完整记录至少要包含输入身份、组件身份、运行环境、输出 URI、内容摘要、执行状态、资源归属和上下游边。只有这些信息共同存在，一次训练才能被重现、对比、审计和有条件地晋级。

## 2. KFP 是实验编排面，不是训练运行时

Kubeflow Pipelines 负责定义、编译、提交、观察和记录任务图。它可以运行容器化组件，也可以由组件向 Kubernetes 提交 TrainJob 等高层工作负载。对于多节点 GPU 训练，让 KFP 的某个 Pod 自己管理多角色子 Pod，会重复实现训练控制器的职责。更清晰的边界是由 KFP 组件创建 TrainJob，再等待其 Condition 与输出合同。

这种分层让每个控制面保持专注。KFP 管数据检查、训练、评估、注册之间的依赖与制品；Trainer 管分布式角色、启动、重试和完成语义；Kueue 管队列与配额；对象存储管大对象；模型注册表管版本与晋级状态。一条 Pipeline 是它们的编排与证据索引，不应变成吞掉所有控制面的巨型程序。

## 3. Component 是可复用的类型化合同

KFP Component 把一段代码、容器基础镜像、依赖与输入输出约束包装成可组合单元。官方推荐使用 `@dsl.component` 定义 Python 组件。函数签名不只是编程便利，它会进入编译后规格，使编译器可以在提交前发现部分类型错误。

平台组件库应按业务能力组织，例如“校验数据合同”、“创建受队列管理的 TrainJob”、“读取评估证据”和“幂等注册候选版本”。组件不应暗中读取开发者主目录、不受版本管理的 ConfigMap 或公共路径。任何能改变输出的东西都应成为显式输入或被固定在镜像摘要中。

## 4. Task 是 Component 在图中的一次调用

在 Pipeline 函数中调用 Component 会构造 PipelineTask，不会立即执行函数体。Task 持有组件、输入绑定、输出通道、缓存、重试与资源等执行选项。同一组件可以在图中出现多次，每个 Task 都应有稳定且可解释的名字。

运维观察的是 Task 实例，复用和发布的是 Component 定义。如果平台把两者混在一起，修复某次运行的配置就可能意外改变全局组件；反之，如果每个 Pipeline 都复制组件代码，安全修复与观测标准又无法统一。合理模式是发布版本化组件，Pipeline 只对其明确版本或摘要做引用。

## 5. Pipeline 是有向图而不是顺序脚本

KFP Pipeline 由 Task 及其依赖构成有向图。没有数据依赖或显式顺序约束的任务默认可并行。这与普通 Python 函数从上到下执行的直觉不同。在 Pipeline 函数中先写数据检查，后写训练，不能单凭代码位置保证顺序；必须把前者输出传给后者，或显式使用依赖。

设计时要优先使用数据边，因为它同时说明顺序与原因。仅用 `.after()` 可以表达顺序，却不会自动产生制品血缘。如果训练必须在检查后运行，就应传递经过检查的 Dataset Artifact 或数据合同摘要，而不是只用一条无语义的控制边。

## 6. IR YAML 是编译交付物

KFP 2.x 编译器把 Pipeline 转换为 IR YAML。官方将其定义为 PipelineSpec protobuf 的 YAML 表示，核心是平台无关的中间表示。文件通常包含 components、deployment_spec、root、pipeline_info、sdk_version、schema_version 和可选的 default_pipeline_root。

IR 应由 SDK 生成并进入版本管理，而不是由人长期直接编辑。手工修改很容易破坏类型、通道引用和编译器不变式，也使源代码与发布产物不一致。平台 CI 应在固定 SDK 版本和锁定依赖的环境中编译，对 IR 做 Schema 校验与策略扫描，再以摘要识别实际提交物。

## 7. 平台无关不等于后端行为完全相同

IR 把高层图与特定执行引擎解耦，但运行时能力仍受 KFP 后端和版本限制。官方文档说明，开源 KFP 默认路径会将 IR 编排为 Argo Workflow 相关执行；KFP 2.17 的编译能力又支持输出 Kubernetes 原生 API 清单模式。这两条路径不应被混写成一个没有条件的默认承诺。

每个发布环境都应记录 KFP 后端版本、SDK 版本、编译模式和执行引擎。如果从一种后端迁移到另一种，需要重新验证退出处理、缓存、重试、并行循环、安全上下文和制品上传，不能只因 IR 相同就推导语义等价。

## 8. Parameter 用于可 JSON 序列化的小值

KFP Parameter 支持 str、int、float、bool、list 和 dict 等可 JSON 序列化类型，适合学习率、数据版本号、评估阈值、开关或简短配置。它们可以出现在 UI、运行参数和缓存输入中，是实验可比较性的重要维度。

不要把大型数据集、模型二进制或长篇报告塞进 Parameter。即使某个小数组能序列化，也要考虑 API 负载、数据库、UI 和日志暴露。敏感信息更不应作为明文 Parameter；应通过受控的 Secret 引用与短期凭证注入，并确保它们不进入制品元数据或缓存键。

## 9. Artifact 表达大对象及其身份

KFP 将 Artifact 作为对象存储中大对象的一等引用。官方 SDK 提供 dsl.Artifact、Dataset、Model、Metrics、HTML 和 Markdown 等类型。运行时元数据保存 Artifact 的 URI、类型与自定义属性，真正字节位于 Pipeline Root 指向的存储。

只记 URI 还不足以保证重现，因为可变路径的内容可被覆盖。平台应为制品生成不可变版本 URI 或对象版本 ID，同时记录内容摘要、字节数、生成者与数据合同版本。Artifact 类型解决“这是什么类别”，摘要解决“这是哪份确切内容”，两者不能互相替代。

## 10. Pipeline Root 是制品命名空间的根

Pipeline Root 定义运行产生的 Artifact 字节默认写入哪个对象存储根。官方文档列出 SeaweedFS、S3 与 GCS 等由 Go CDK 支持的路径，并允许在安装、Pipeline 或单次 Run 层级配置。运行数据库中的 Artifact 元数据与对象字节是分离保存的。

生产平台不能允许用户任意把 Root 指向公共桶根或他人前缀。应根据租户、项目、环境与数据等级生成允许前缀，用工作负载身份授予最小读写权限，并配置加密、版本、保留和生命周期。否则一个 Pipeline 可以覆盖另一个 Pipeline 的制品，血缘图完整也无法防止数据越权。

## 11. 类型检查应在编译阶段失败

KFP 编译器能检查组件输入输出的静态类型兼容性。把 Metrics 输出连到需要 Model 的输入，或把字符串参数连到整数输入，应当在 CI 编译时被拒绝，而不是浪费 GPU 配额后才由 Python 抛异常。

静态类型不能替代内容合同。两个 Dataset 都是同一 Artifact 类型，但列名、数据时间窗、标签含义和隐私级别可能完全不同。数据检查组件应对 Schema、质量、许可与时效做运行时校验，并输出经过签名的数据合同证据。类型检查与内容检查是两道不同门禁。

## 12. 依赖边同时是血缘边

当训练 Task 读取数据检查 Task 的 Dataset 输出时，KFP 不仅知道训练应等待检查，还知道该 Model 源自该 Dataset。评估 Task 同时读取 Model 与评估策略版本，其 Metrics 就应具有两条显式上游边。这些边会进入 ML Metadata 的执行与制品关系。

“我们都知道评估读取了那个桶”不是血缘。如果 URI 在组件内部硬编码，Pipeline 图无法知道该依赖，缓存也不会因其变化而失效。所有外部输入都应以 Parameter、Artifact 或明确的环境合同进入图，这是可追踪和正确缓存共享的前提。

## 13. 无依赖节点默认并行

一条 Pipeline 可以同时执行多个独立数据检查、训练不同候选或生成多种报告。这是有向图相对顺序脚本的优势，但并行不是免费的。每个并行分支都可能创建 Pod、TrainJob 或外部 API 请求，对 GPU、对象存储、数据库与模型注册表形成瞬时压力。

平台要同时设置图内扇出上限、Run 级并发上限、命名空间配额、Kueue 队列配额和外部服务速率限制。只限制 Pod 数不能防止单个 Task 创建大型 TrainJob；只限制 GPU 也不能防止千个 CPU 数据任务压垮对象存储。并发是跨控制面的预算问题。

## 14. ParallelFor 需要显式扇出上限

`dsl.ParallelFor` 可以为列表中每个元素构造循环体 Task。官方 Artifact 文档还支持通过列表类型与 Collected 汇集循环分支产物。这适合分片数据处理、多数据集评估或一组经过审批的候选配置。

反例是把一个由外部输入控制的任意长列表直接传给 ParallelFor。一次误操作可以在几秒内生成大量 Task 与 Pod，给 KFP 数据库和 Kubernetes API 带来控制面压力。应在编译或准入中定义最大列表长度，并在业务上将超大集合分批，而不是盲目提高控制面上限。

## 15. If、Elif 与 Else 表达数据驱动分支

KFP 控制流支持 `dsl.If`、`dsl.Elif` 与 `dsl.Else`。官方已将旧 `dsl.Condition` 标记为弃用路径，新 Pipeline 应使用当前接口。分支条件应源自显式 Parameter 或上游输出，例如数据质量是否达标、评估结果是否满足候选注册阈值。

不应用分支隐藏一套无法审计的模型晋级策略。阈值、指标方向、分组约束和例外批准都应由版本化评估策略提供，Pipeline 只消费其结果。这样评估语义与编排语义才能分层，更换门禁时不必重写工作流拓扑。

## 16. ExitHandler 保证收尾路径被调度

`dsl.ExitHandler` 用于无论包围的任务图成功或失败，都运行指定退出任务。它可以用来释放外部租约、关闭临时服务、上传运行摘要或发出最终状态。收尾任务本身必须幂等，因为后端重试、控制器恢复或人工重运可能使它执行多次。

ExitHandler 不是分布式事务。当 Kubernetes 集群或存储完全不可用时，退出任务也可能无法运行；外部资源还需要 TTL、所有者引用、对账作业或垃圾回收器作为第二道保障。正确承诺是“在工作流可继续调度时执行收尾”，而不是“任何灾难下都一定成功清理”。

## 17. 本地执行不是远程语义的替身

KFP SDK 提供本地执行能力，官方推荐 DockerRunner 作为本地路径。它非常适合快速发现组件入参、镜像依赖、文件输出和基本逻辑问题。但官方同时明确说明，本地执行缺少缓存、重试、资源限制和认证等远程能力。

当前本地路径还不支持 Condition、ParallelFor 和 ExitHandler 等控制流。因此本地跑通只能证明某些组件逻辑或简化图可执行，不能证明 KFP 后端缓存、MLMD 血缘、Kubernetes 身份、Kueue 准入或 Katib 控制器已工作。这里将本地模拟标记为可携带证据，真实控制面必须另行验收。

## 18. 缓存默认开启是优化也是责任

KFP 官方缓存文档说明，任务缓存默认开启。当一个 Task 的输入参数与制品等符合后端判定，且之前输出仍可用时，后端可复用已存输出而不重新执行容器。对昂贵的数据预处理和训练，正确缓存能大幅降低时间与成本。

然而缓存的前提是任务在给定显式输入和固定环境下具有可重放语义。如果组件暗中读取“最新数据”、当前时间、可变镜像或未记录模型，同一表面输入可产生不同结果。此时缓存命中会将旧结果伪装成当前结果，比不使用缓存更危险。

## 19. 缓存键要覆盖所有可观测输入

一个工程上可解释的缓存键应至少受组件版本或摘要、容器镜像摘要、显式 Parameter、上游 Artifact 身份与必要环境合同影响。具体后端如何构造内部键应以其当前实现为准，但平台仍要在组件设计层保证没有隐藏依赖。

环境合同不应简单收集所有环境变量，否则随机 Pod 名或追踪 ID 会导致永不命中。应只纳入会改变业务输出的部分，例如预处理引擎版本、特征合同版本和确定性模式。对于 GPU 类型、驱动或底层算子会影响数值结果的任务，是否纳入也应由风险和重现要求决定。

## 20. 外部副作用任务默认禁用缓存

候选模型注册、发送消息、开通资源、更改权限或创建外部工单都会改变 Pipeline 之外的世界。如果这类 Task 使用缓存，某次新 Run 可能被标记为已注册，实际外部注册表中没有对应本次 Run 的记录。因此这里的合同要求所有副作用任务显式关闭缓存。

关闭缓存不等于可以重复产生副作用。注册组件应以模型内容摘要、评估策略版本和目标阶段构造幂等键；重试时先查询，已存在则返回同一版本，不存在才创建。这样即使后端或网络在响应返回前中断，新的尝试也不会生成重复候选。

## 21. 任务级和 Run 级缓存开关要分开

KFP SDK 允许在 Task 上调用 `.set_caching_options(False)` 禁用缓存。官方文档还说明，提交 Run 时的 `enable_caching` 可在运行级对任务设置产生覆盖效果。因此平台门户若暴露“全局开启缓存”按钮，就必须防止它把明确禁用的副作用任务变成可缓存。

运维上应区分两种需求。“我怀疑上游缓存被污染，要强制重算”适合在 Run 级关闭缓存；“这个 Task 语义上不允许缓存”应写入组件或 Pipeline 策略，不允许提交者改写。缓存是正确性策略，不只是一个性能开关。

## 22. 缓存污染需要可定位的根因

常见缓存污染来自三类问题：制品 URI 可变，镜像标签可变，或组件有隐藏依赖。表面上的输入没有变，缓存合理命中；但业务期待的实际输入已变。如果只删除缓存而不修复身份合同，下一次还会重现。

事故处理应先隔离受影响组件版本和制品，保留 Run、Task、输入、镜像摘要与缓存来源证据，然后修复隐藏依赖。受污染结果不应继续参与候选模型注册或下游缓存。必要时通过新的数据或组件身份强制整条下游链重算，不要手工修改旧 Run 的结果来掩盖问题。

## 23. Run 是一次不可变执行记录

KFP 官方将 Run 定义为 Pipeline 的一次执行。它保存提交时使用的 Pipeline、参数、Task 状态、制品与日志索引。即使后来用新参数发起类似执行，也应产生新 Run，不应把旧 Run 改写成当前状态。

不可变性使得审计者可以回答当时发生了什么。这并不意味着日志和制品可以永久保留；保留策略可以删除大字节，但应保留身份、摘要、删除时间和策略证据。否则 Run 虽在 UI 中存在，却无法重现或证明其输出。

## 24. Experiment 是 Run 的逻辑工作区

KFP Experiment 用于将相关 Run 和 Recurring Run 组织在一起。它可按用例、团队、模型或一次研究问题分组，但并不替代模型版本、制品身份或环境晋级状态。一个 Experiment 可以包含任意相关 Run，不应把它误解为强隔离或安全边界。

平台门户应自动为 Experiment 增加项目、成本中心、所有者、数据分类和保留策略等可查询标识。命名只是人类可读索引，计费和审计应使用不可变 ID 与结构化标签。删除 Experiment 前还要区分是否删除 Run 元数据、对象制品和外部 TrainJob 证据。

## 25. Recurring Run 是带触发器的运行模板

KFP Recurring Run 保存 Pipeline、参数和触发设置，可根据周期或 Cron 表达式创建新 Run，并可设置最大并发 Run 数。它适合每日数据质量检查、周期重训练或定期回归，但每次触发仍应生成独立不可变 Run。

定时并不能保证数据已就绪。对于外部数据到达，应在 Pipeline 开头校验完整性、时间窗与水位，不满足时以明确类型结束。并发上限要防止前一次长跑与后一次重叠将资源放大；是选择跳过、排队还是取消旧 Run，必须由业务时效和幂等性决定。

## 26. 重试只适用于明确的短暂失败

KFP Task 可设置重试策略。这对短时网络中断、对象存储限流或可恢复的节点中断有用，但重试次数、间隔和退避必须有上限。对于确定性数据 Schema 错误、镜像不存在或配额策略拒绝，自动重试只会增加控制面与资源压力。

组件要输出可分类的错误，例如短暂不可用、不可重试的合同违反、超过预算与用户取消。同一 Task 内的外部操作必须幂等，因为进程可能已完成外部写入，却在回传成功前被终止。平台还要把每次尝试与最终 Task 状态分开观测，否则一个经过五次重试才成功的节点会被绿色状态掩盖。

## 27. 恢复不是修改旧 Run 继续往前

工程上应将恢复理解为基于已保存输入、制品和缓存创建一次新执行，或者由后端在同一 Task 的重试语义中完成尝试。不要宣称 KFP 对任意失败图都有“原地从精确节点续跑”的通用魔法。具体 UI 或后端提供的克隆、重试与恢复行为需按当前版本验证。

一条可恢复 Pipeline 需要满足更强的不变式：上游成功制品不可变且仍存在，组件可由摘要重新获取，隐藏依赖不存在，副作用任务幂等，下游可识别制品是重用还是新产生。只有这些条件成立，新 Run 利用旧结果才是恢复，而不是将不确定状态带入新实验。

## 28. 取消语义要覆盖外部工作负载

当一个 KFP 组件创建 TrainJob 后等待，用户取消 Run 不一定自动删除该 TrainJob，除非组件或外部对账控制器明确实现了所有权和取消传播。如果只终止等待 Pod，分布式训练可继续消耗 GPU，最后还向存储写入一个没有活跃 Run 拥有的模型。

设计时应在 TrainJob 标签或注解中写入 Run ID、Task ID、项目和所有者，并定义取消传播、宽限期、强制终止与制品处理。部分完成的检查点可以按策略保留，但必须标记为未完成运行产物，不得进入候选模型注册。对账器要定期查找没有活跃 Run 的 TrainJob 并按政策回收。

## 29. 运行证据要跨越多个控制面

一次实验的时间线可能同时出现在 KFP Run、Argo 或 Kubernetes 执行对象、TrainJob、JobSet、Pod、Kueue Workload、Katib Trial、对象存储和 MLMD 中。如果每层只保留自己的随机名字，事故时就无法快速从候选模型追回某个 GPU Pod 的中断。

平台应定义跨层关联字段，至少包括租户、项目、Pipeline ID、Run ID、Task ID、Experiment ID、Trial ID、TrainJob UID 与成本归属。标签长度和字符集有 Kubernetes 限制时，可使用稳定短摘要并在元数据库中保存完整映射。日志、指标和追踪也应注入相同关联维度，但要控制高基数标签成本。

## 30. ML Metadata 把执行、制品与上下文连起来

Kubeflow Pipelines 使用 Google ML Metadata 的模型记录运行时信息。其中 Execution 表示一次组件或任务执行，Artifact 表示数据集、模型、指标等输入输出，Context 用来把执行与 Run、Pipeline 等范围组织起来。输入与输出关系形成可查询的血缘图。

MLMD 是血缘与运行元数据基础，但它不会自动替平台理解每个业务字段。如果组件只输出一个无类型文件，血缘图只能显示文件边，无法知道它是未通过门禁的评估结果还是可晋级模型。平台需要定义类型、属性、摘要与状态的一致语义。

## 31. 血缘图不等于制品本身可用

KFP 数据库可能仍有 Artifact URI，但对象存储中字节已因生命周期被删除；反之，对象字节可能仍存在，但 MLMD 数据库损坏后失去生成关系。因此运行元数据、Artifact 字节、制品注册表与审计日志必须有相互协调的保留和备份策略。

验收一条血缘时，不只查图上有边，还要随机抽取制品，校验 URI 可访问、摘要一致、权限不越界且保留策略符合分类。对已合规删除的制品，图上应显示删除原因和时间，而不是给出一个看似可点击、实际永久失效的链接。

## 32. MLMD 数据库升级必须先备份

KFP 近期版本的后端数据库变更不应被当成无风险的容器替换。官方发布说明在 2.15 相关升级中引入了重大 Gorm 后端与数据库索引迁移，并明确提醒没有回滚路径。从早于 2.15 的部署升级到当前基线前，必须按官方说明保存可恢复数据库备份。

升级验收要包含完整恢复演练，而不是只看备份作业成功。应在隔离环境恢复数据库，比较 Experiment、Run、Task、Artifact 和血缘查询，再测试新版本的编译与执行。回退方案不能假设新 Schema 可由旧二进制直接读取，而应在未执行不可逆迁移前完成快照和变更门禁。

## 33. 多用户隔离不能超出官方承诺

KFP 多用户文档将该模式限定在 Kubeflow Community Distribution 的集成上下文中。其中 Experiment、Run 和 Recurring Run 可按 Kubernetes Namespace 隔离，而 Pipeline 定义并没有同样按命名空间隔离，可在不同命名空间之间共享。官方还提醒，这不提供超出 Kubernetes Namespace 的强安全保证。

因此平台不应在敌对租户场景中仅依靠 KFP 界面过滤。需要结合 Profile、Namespace、ServiceAccount、RBAC、NetworkPolicy、对象存储前缀策略、密钥隔离与底层集群边界。共享 Pipeline 定义还要做供应链签名与准入，防止一个团队更新的组件在另一团队权限下运行未审核代码。

## 34. Pipeline ServiceAccount 应使用最小权限

每个 Run 中的组件通过 Kubernetes ServiceAccount 访问 API、Secret 和存储。一个可以创建 TrainJob 的账号不需要创建 ClusterRole，一个只读评估结果的组件不需要列出所有 Secret。将所有 Pipeline 都绑定到管理员账号是最常见也最危险的快捷方式。

平台可为数据读取、训练提交、评估读取和候选注册设计不同组件身份，或使用经审核的中介服务以将权限与任意用户代码隔离。工作负载身份应换取短期云凭证，不把长期密钥写入参数、镜像或对象存储配置。验收时必须做负向权限测试，证明该身份无法访问他租户资源。

## 35. 镜像必须由摘要固定

使用 `latest` 或可重用版本标签会同时破坏重现、缓存和供应链审计。两个 Run 的 IR 看起来完全相同，节点拉取到的镜像字节却可能不同。正确做法是在构建阶段生成签名镜像，在 Pipeline 发布时将其解析为不可变摘要，并在准入策略中禁止可变引用。
