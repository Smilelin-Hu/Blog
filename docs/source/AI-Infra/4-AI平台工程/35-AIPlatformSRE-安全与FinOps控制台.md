# AI Platform SRE、安全与 FinOps 控制台

本项目把前序可观测性、SRE、安全与 FinOps 四篇整合为一套 AI 平台运营控制台。它不只是把若干图表放在一个页面，而是用稳定请求身份关联 Kubernetes 对象、遥测信号、策略判定、故障事件、恢复动作和 GPU 成本。平台团队由此能够从一次用户请求追到资源与设备，从 SLO 燃烧追到具体影响域，从准入拒绝追到策略证据，并把每一笔 GPU 成本归属到租户、项目和 Owner。

![AI 平台运营控制台](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l35_01.png)

参考场景包含三个请求和两次受控事件。实验计算 SLO 达成率、最大检测时间、最大恢复时间、成本归属率与策略违规阻断率；同时验证身份缺口、跨租户访问、特权工作负载、签名缺失、遥测陈旧、故障半径越界、恢复未验证、审计延迟和成本重复计算等反例。真实数据源未提供时返回 SKIPPED，不以模拟结果代替生产证据。

## 1. 知识体系与架构原理

### 1. 运营控制台责任边界

运营控制台责任边界必须从同一个请求身份出发。门户、准入控制器、调度器、训练或推理控制器、Pod、GPU 设备、遥测和成本记录都要携带稳定关联键。名称可以重用，UID 和不可变 request_id 才适合做关联。控制台如果只用 namespace 与 Pod 名称拼接数据，在对象重建、跨集群迁移和同名项目出现时会把不同事实错误合并，最终既影响故障判断，也影响成本归属。

运营控制台责任边界的状态不能只有绿灯和红灯。数据不足应标 INCONCLUSIVE，身份无法解析的成本应标 UNALLOCATED，策略违规应 REJECTED，超出自动化安全边界应 ESCALATE，遥测被基数预算丢弃应 DROPPED，环境条件缺失应 SKIPPED。显式状态可防止平台把未知当作正常，也让责任人知道下一步是补证据、修策略、人工处置还是恢复数据源。

FinOps 视角下，运营控制台责任边界需要把 GPU 占用时间、设备类型价格、共享平台成本、闲置成本与请求身份连接。分配率只计算身份完整且价格有效的记录，未分配成本要保留为一等对象，不能为了报表漂亮而均摊给现有租户。总分配成本与账单输入还要对账，任何差额都应形成可追踪的异常。

实现运营控制台责任边界时要明确谁拥有原始事实。Kubernetes API 拥有对象与事件，遥测后端拥有指标、日志和 Trace，策略引擎拥有准入判定，事件系统拥有响应时间线，成本系统拥有价格与分配结果。控制台负责查询、规范化和展示，不应改写来源含义。任何推导结果都要保存查询窗口、输入版本、计算规则和产生时间，才能在事后重放。

验收运营控制台责任边界应沿请求、策略、调度、运行、信号、事件、处置和成本八段取证。每段至少包含稳定身份、Owner、状态、Reason、时间与来源。正向案例证明链路贯通，反例证明缺身份、跨租户、遥测不足、运行手册缺失、影响域越界和成本重复计算会得到预期处置，不能只验证页面能够渲染。

安全评审运营控制台责任边界时，需要检查身份从可信控制面注入，而不是相信工作负载自报的 tenant 或 owner。跨租户请求必须在执行前阻断；特权容器、hostPath、未签名镜像和超预算请求也应由确定性策略拒绝。控制台显示的拒绝必须包含策略摘要、主体、输入对象 UID、Reason 与时间，避免只有一条难以取证的文本消息。

运营运营控制台责任边界还需要持续校准阈值和数据质量。SLO 目标、燃烧率窗口、故障半径、GPU 价格、共享成本规则与策略版本都应变更受控。每次复盘不仅统计恢复耗时，也要检查检测是否及时、自动化是否扩大影响、告警是否有行动价值、成本是否可解释，并把结论转成新的可执行门禁或测试。
