# Kubernetes 调度器与 AI 资源碎片

集群监控显示还有二十张空闲 GPU，一个申请八张 GPU 的训练 Pod 却连续 Pending。值班人员把各节点余量相加，认定调度器出了故障；扩大集群后，作业仍然没有落位，因为新增的是另一种 GPU，训练请求还同时要求同一节点具备足够 CPU、内存、可挂载的卷、正确机型标签和匹配的污点容忍。后来团队把小作业平均摊到所有节点，单卡利用率看起来更均匀，却把原本完整的八卡节点切成许多小洞，大作业只能继续等待。

![调度器与资源碎片](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l10_01.png)

这个事故的第一条结论是：集群“总量足够”和 Pod“存在一个可行位置”是两个不同命题。调度器选择的是一个具体 Node，不会把四台节点各剩的两张整卡拼成一台八卡机器，也不会把若干 `1g.10gb` MIG 实例自动合成为 `3g.40gb`。CPU、内存、GPU、设备形态、卷拓扑、端口、亲和性、污点和故障域共同构成一个多维放置问题，任一硬约束失败都足以让节点退出候选集。

第二条结论是：Filter 决定“能不能放”，Score 只在可行节点之间决定“更愿意放到哪里”。调高 Binpack 权重不能让一个不满足八卡请求的节点突然可行；Spread 也不是安全性的同义词。Binpack 往往能保留完整节点、提高装箱密度和缩容机会，Spread 往往能降低故障域集中、邻居干扰与单节点损失范围。策略必须对负载形态、未来到达分布和服务目标负责，而不是追求一个抽象的平均利用率。

第三条结论是：`Pending` 只是 Pod 生命周期阶段，不是根因。正确排障要还原某一次调度尝试的资源快照，区分没有进入活跃队列、所有节点在过滤阶段失败、评分或绑定插件报错、抢占受害者仍在退出、卷尚未绑定、外部调度器没有处理等状态。事件、Condition、失败插件和调度指标必须串成时间线，不能只看一条被聚合过的 `FailedScheduling` 文本。

本文从单 Pod 调度的输入输出开始，拆解 Scheduling Framework 的队列、调度周期与绑定周期；随后建立 Request、Allocatable、多维资源、Extended Resource 和位置约束模型；再分析优先级、抢占、整卡与 MIG Shape 碎片、CPU／内存／GPU 交叉碎片、拓扑碎片、Binpack、Spread、队头阻塞、Backfill 与扩展机制。最后用可重复的状态回放实验比较三种评分策略，并让真实集群路径在缺少专用环境时如实返回 `SKIPPED`。

## 1. 调度问题的输入不是一串 GPU 数字

Kubernetes 调度是把尚未指定 `.spec.nodeName` 的 Pod 与某个 Node 匹配，并把选择结果写回 API 的过程。这个定义看似简单，关键在“某个”二字。默认调度器不是给 Pod 分配抽象资源池中的份额，而是判断一个具体节点在当前快照与全部约束下是否能够承载该 Pod。

### 1.1 Pod 描述的是不可拆分的放置单元

一个普通 Pod 内的多个容器共享调度位置。调度器会聚合应用容器、Init Container、Pod Overhead 以及适用的 Pod 级资源请求，形成这个放置单元的资源需求。Pod 申请四张 `nvidia.com/gpu`，含义是同一节点要提供四个这种扩展资源，而不是任选四张分散设备。

训练框架把八个 Worker 表达成八个 Pod 时，单个 Pod 可以分别调度；把一个八卡进程表达成一个 Pod 时，八卡必须来自同一节点。两种建模方式对应不同通信、故障和资源形状。调度器只忠实执行对象表达的边界，不会推断训练框架原本想要什么。

Pod 还携带 NodeSelector、NodeAffinity、PodAffinity、PodAntiAffinity、TopologySpreadConstraints、Toleration、Priority、SchedulerName、Volume、HostPort 等信息。它们不是附加说明，而是放置合同。合同中的硬要求会进入可行性判断，软偏好才进入评分。

### 1.2 Node 是容量、状态与拓扑的组合

Node 对调度器不是一台只有“八张卡”的服务器。它包含 Capacity、Allocatable、标签、污点、Condition、已有 Pod 请求、可访问卷、已占 HostPort、设备资源、镜像状态以及拓扑域等事实。

Capacity 是节点报告的总资源，Allocatable 是扣除系统与 Kubernetes 保留后可供 Pod 使用的上界。调度时通常比较 Pod Request 与 Allocatable 中尚未被已调度 Pod Request 占用的部分，而不是读取实时 GPU 利用率或 `free` 命令显示的瞬时内存。

节点标签把机型、Zone、Rack、GPU 产品、网络等级或合规域表达给调度。标签若来自人工维护，漂移会直接造成错误放置；关键硬件事实应由受控发现组件写入，并配合准入和审计。标签既是调度输入，也是安全边界的一部分，不能允许普通工作负载随意伪造节点身份。

### 1.3 调度器使用的是一个资源快照

调度尝试发生时，集群仍在变化。新 Pod 到达、旧 Pod 结束、节点心跳更新、卷绑定完成、设备变健康。调度器维护缓存，并在一次调度周期中基于快照计算。这个快照不是永恒真相，选择后还要通过 Reserve、Permit、PreBind 和 Bind 等阶段处理竞争与外部条件。

“刚才明明有资源”可能在绑定前被另一个调度上下文占用。调度器通过 Assume 与 Reserve 一类机制减少并发冲突，但外部系统仍可能失败。平台排障记录必须带时间、资源版本或至少带完整节点请求快照，不能把一分钟后的 `kubectl describe node` 当成失败瞬间的证据。

### 1.4 输出不是启动容器，而是绑定决定

调度器成功的核心输出是 Pod 与 Node 的绑定关系。之后由目标节点上的 Kubelet 处理镜像、卷挂载、Sandbox、设备注入和容器启动。Pod 已有 `nodeName` 但仍 Pending，常见原因是镜像拉取、卷挂载或运行时准备，不应继续归因于调度器。

反过来，没有 `nodeName` 且有 `FailedScheduling`，才重点调查调度阶段。若使用调度门控、外部 SchedulerName 或 Permit 等待，可能没有普通的 FailedScheduling。先判断生命周期停在哪个控制面，再选择日志和指标。

### 1.5 调度不会创建资源

默认调度器能在现有节点中寻找位置，也能通过抢占尝试释放低优先级 Pod，但它不会制造 GPU、扩大 MIG Profile、创建匹配的 Node Pool 或立刻完成卷跨区迁移。节点自动扩缩器可能根据不可调度 Pod 触发扩容，这是另一个控制回路。

因此 Pending 的处置不一定是修改 Scheduler。资源形状不存在时要改变供应；请求不合理时要修改工作负载；策略造成碎片时要调整评分和队列；标签或健康漂移时要修复事实；容量正在扩展时要显示“等待供应”而不是“调度器异常”。

## 2. 先把一次调度尝试拆成阶段

Scheduling Framework 把调度行为组织为扩展点。理解扩展点的价值不在于背插件名称，而在于知道一个 Pod 在哪里被挡住、哪个组件能改变决定、失败是否可以通过集群事件重新排队。

### 2.1 内部队列不是简单先进先出

Pod 被调度器观察后，不一定立即进入同一条队列。活跃队列保存准备尝试的 Pod，退避队列保存失败后等待重试的 Pod，不可调度集合保存已尝试且当前事件没有明显改变其可行性的 Pod，门控 Pod 还可能尚未进入正常尝试。

优先级会影响排序，但高优先级 Pod 不可行时，调度器不会永远停在它身上。失败 Pod 会进入不可调度或退避路径，其他可行 Pod 仍有机会调度。这一点与某些批处理系统的严格队头阻塞不同。

队列设计要同时控制吞吐和无效重试。每个节点心跳都唤醒所有失败 Pod，会造成调度风暴；永不唤醒又会错过变得可行的时刻。Queueing Hint 类机制让插件根据具体事件判断是否值得重新进入活跃队列。

### 2.2 PreEnqueue 与 QueueSort 解决不同问题

PreEnqueue 在 Pod 进入内部活跃队列前判断它是否准备好。例如一个外部准入系统尚未给出批准，Pod 可以被保留而不是反复执行完整过滤。它回答“现在是否值得尝试”。

QueueSort 提供待尝试 Pod 的顺序。默认思路会考虑优先级和到达顺序，但批处理平台可能需要队列、公平份额或作业级语义。一个调度器实例的某个 Profile 只能形成一致的队列排序合同，不能让多个互相矛盾的 QueueSort 插件同时主导顺序。

排序只决定谁先尝试，不保证谁先运行。排在前面的八卡 Pod 没有可行节点时会失败重排，而后面的单卡 Pod 可能成功。用户看到的等待时间由排序、可行性、退避、资源释放、抢占和供应共同决定。

### 2.3 PreFilter 准备一次 Pod 级计算

PreFilter 适合预处理只与 Pod 或全局状态有关的信息，避免对每个节点重复昂贵计算。插件可以检查某些前置条件，也可以把中间结果放入本次 CycleState，供后续 Filter 使用。

如果 PreFilter 直接判定条件不满足，整个调度周期可以提前结束。此时不是“所有节点分数低”，而是还没有进入逐节点评分。排障系统应保留扩展点和插件身份，不能把所有失败压成 `0/N nodes are available`。

### 2.4 Filter 构造可行节点集合

Filter 对候选节点执行硬约束。资源是否足够、NodeSelector 与 required NodeAffinity 是否匹配、NoSchedule 污点是否被容忍、HostPort 是否冲突、卷拓扑是否可满足、必需的 Pod 亲和与拓扑分布是否成立，都可能在这里淘汰节点。

设节点集合为 $N$，某 Pod 的第 $j$ 个硬约束为 $C_j(n,p)$，结果取零或一。可行集合写成：

$$F(p)=\{n\in N\mid \forall j,\ C_j(n,p)=1\}$$

读法是：Pod 的可行节点集合，包含所有同时满足每一个硬约束的节点。任何一个约束为零，节点就不在集合中。这个公式有用，因为它揭示“总资源足够”只检查了若干资源约束的集群和，没有证明存在一个节点让所有约束同时为真。

例如节点甲剩四卡但内存只剩一百 GiB，节点乙剩两卡且内存五百 GiB，Pod 请求四卡和三百 GiB。GPU 维度看甲可行、内存维度看乙可行，但没有交集，所以 $F(p)$ 为空。

### 2.5 PostFilter 处理没有可行节点的情况

当 Filter 后可行集合为空，PostFilter 扩展点可以尝试恢复策略，默认抢占逻辑就是重要例子。它寻找是否能通过移除低优先级 Pod，让待调度 Pod 在某节点上变得可行。

PostFilter 不是万能修复。若失败来自节点机型标签、不可访问卷、硬反亲和、缺失 MIG Profile 或更高优先级 Pod 占用，移除低优先级受害者可能仍然无效。跨节点抢占也有明确限制，不能假定整个集群任意重排。

### 2.6 PreScore 与 Score 只处理可行节点

当 $F(p)$ 非空，PreScore 可准备评分数据，Score 插件为每个可行节点给分。不同插件分数规范化并乘权重，形成总分。调度器从最高分节点中选择一个，平分时采用受控的选择逻辑。

设第 $k$ 个评分插件对节点 $n$ 的归一化分数为 $s_k(n,p)$，权重为 $w_k$，总分可概念化为：

$$S(n,p)=\sum_k w_k s_k(n,p),\quad n\in F(p)$$

读法是：对每个已经可行的节点，把各评分插件分数乘以权重后相加。权重改变偏好，不改变可行集合。若某节点因缺 GPU 在 Filter 被淘汰，再高的 Binpack 分也不会复活它。

### 2.7 Reserve 是调度器内部的承诺点

选择节点后，Reserve 插件可以在调度器内部状态中为 Pod 保留资源，防止其他并发绑定周期重复使用同一份逻辑资源。Reserve 成功不等于 API 已绑定，也不等于设备在节点上已配置完成。

后续阶段失败时，Unreserve 必须撤销相应状态。自定义插件如果只实现保留、不实现幂等回滚，会产生幽灵占用。平台测试扩展插件时要注入 Permit 拒绝、PreBind 超时和 Bind 失败，确认所有内部与外部 Reservation 都能清理。

### 2.8 Permit 可以批准、拒绝或等待

Permit 插件允许 Pod 进入等待状态，常用于作业组协调等语义。等待有超时，超时相当于拒绝并触发回滚。处于 Permit Wait 的 Pod 可能已经有提名或内部选择，但还没有最终绑定。

把“已选节点”展示成“正在运行”会误导用户。门户至少区分 Queued、Scheduling、Reserved、WaitingOnPermit、Bound 和 NodePreparing。每个状态给出 Owner、超时和可行动作。

### 2.9 PreBind、Bind 与 PostBind 连接 API 世界

PreBind 在写绑定前执行必要准备，例如确保某些外部条件。Bind 插件真正完成绑定；某个 Bind 插件成功后，后续 Bind 插件不再执行。PostBind 是成功绑定后的通知扩展点，不应承载必须决定正确性的关键事务。

绑定周期可以并行，提高吞吐；调度周期按设计串行处理选择。插件若持有全局锁或在扩展点执行慢外部请求，会放大尾延迟。性能问题要看具体扩展点耗时，而不是只看 kube-scheduler 进程 CPU。

## 3. Request 与 Allocatable 是默认可行性的资源语言

AI 平台最常见的误区，是拿实时使用率解释调度。调度器主要以声明的 Request 进行容量承诺，因为瞬时使用率会抖动、无法提前保证，也不能表达未来峰值。

### 3.1 CPU Request 与实际 CPU 使用不是同一数值

Pod 请求八核，表示调度时预留八个 CPU 单位的份额；实际某时刻可能只用两核。NodeResourcesFit 仍按请求计算，因为其他 Pod 也有权在随后使用各自承诺。

如果团队普遍把 Request 写成峰值的数倍，调度显示满而机器实际空；如果长期低报，调度密度很高，运行时却会争抢、节流或 OOM。平台需要用历史分位数和业务风险给出推荐，但更改 Request 是容量合同变更，不能由调度器偷偷按实时值替换。

### 3.2 内存不可像 CPU 一样安全超卖

CPU 是可压缩资源，竞争时可分时；内存压力可能触发回收与 OOM。调度仍按 Request 判断，Kubelet 和内核在运行期处理限制、QoS 与驱逐。调度成功只证明声明请求可容纳，不证明实际峰值一定安全。

AI 任务常同时需要大量 Host Memory 用于数据加载、Pinned Memory、模型映射和通信缓冲。只申请 GPU 不写合理内存 Request，会让节点在调度视角显得宽裕，运行期却发生内存压力。CPU、内存和 GPU Request 要作为一套 Profile 管理。

### 3.3 Init Container 与 Pod Overhead 也进入计算

Init Container 通常顺序运行，资源计算不是简单把所有 Init 与应用容器全部相加。调度器会根据 Kubernetes 的 Pod 资源规则计算有效请求，使初始化阶段和稳定运行阶段都可容纳。Sandbox 或 RuntimeClass 引入的 Pod Overhead 也可能计入。

大模型下载 Init Container 若需要一百 GiB 内存解压，应用只需三十 GiB，平台不能只记录应用态。反过来，初始化下载结束后大量内存释放，节点会出现声明保留但瞬时空闲，这属于合同与阶段峰值的取舍。

### 3.4 Extended Resource 通常不可超卖

设备插件暴露的 `nvidia.com/gpu` 或 MIG 资源属于节点扩展资源。它们以整数请求，通常 Request 与 Limit 一致，也不进行普通 CPU 式超卖。调度器看到的是资源名与数量，不天然理解两张卡是否 NVLink 相连、显存多少或健康降级。

这些语义需要通过不同资源名、标签、DRA 设备属性、拓扑插件或额外约束表达。把所有加速器都叫同一个 `nvidia.com/gpu`，会简化消费接口，却失去机型和形态选择；把每个型号都变成资源名，会增加平台目录与迁移复杂度。需要明确产品抽象。

### 3.5 Pod Request 是容器请求的聚合合同

普通应用容器并行运行，因此同类资源请求通常相加。两个容器各请求一核和两 GiB，Pod 稳定态至少请求两核和四 GiB。Init Container 按规则取能覆盖各阶段的有效值，再与应用态比较。

平台门户显示 Pod 级有效请求，同时允许展开容器来源。只显示 YAML 原字段，用户很难理解调度器为何认为请求更大；只显示聚合值，又无法找到哪个 Sidecar 把内存抬高。

### 3.6 Allocatable 不是 Capacity

一台节点物理有八百 GiB 内存，Capacity 接近该数值，Allocatable 会扣除系统、Kubernetes 保留和驱逐阈值。GPU 也可能因驱动、健康或分区配置只暴露一部分可分配实例。

调度容量应以 Allocatable 为基线，再扣除已绑定 Pod 有效 Request 和调度假定量。资产系统显示物理设备数，调度系统显示可分配设备数，两者不一致并非一定故障，但差异必须有 Reason，如健康隔离、MIG 重配置、维护保留或驱动未就绪。

## 4. 多维资源让“总量”失去解释力

调度可行性本质上是多维装箱。每个 Node 是一个容量向量，每个 Pod 是一个请求向量，还要叠加离散标签和关系约束。只看单一 GPU 平均利用率，会漏掉决定可行性的其他维度。

### 4.1 用向量读一个节点

把节点剩余资源写成 $r_n=(c_n,m_n,g_n)$，分别表示 CPU、内存 GiB 和整卡数；Pod 请求写成 $d_p=(c_p,m_p,g_p)$。仅考虑资源时，节点可行要求每一维都满足：

$$c_n\ge c_p,\quad m_n\ge m_p,\quad g_n\ge g_p$$

读法是节点剩余 CPU 不小于请求、剩余内存不小于请求、剩余 GPU 不小于请求。三个不等式必须同时成立。若任何一项失败，资源过滤不通过。

例子中节点甲余量为四十八核、一百九十二 GiB、四卡，Pod 需要三十二核、二百五十六 GiB、四卡。CPU 和 GPU 通过，内存失败；该节点不可行。另一个节点余量十六核、五百 GiB、八卡，CPU 失败，仍不可行。全局看资源都很多，交集却为空。

### 4.2 主导资源会随负载改变

大语言模型训练可能 GPU 主导，数据预处理可能 CPU 和本地盘主导，模型服务可能显存与 Host Memory 主导。一个统一权重无法对所有负载最优。

## 5. 量化补充：成组碎片与抢占的账

第 4 节的多维资源可以落到一个具体碎片：作业要同节点 4 张 H100＋16 核，节点 1（DGX H100，112 核）已被占 4 卡 104 核只剩 4 卡 8 核，节点 2（DGX A100）空 4 张 A100＋32 核——池里既有 4 张空闲 H100 也有足够核，但没有一个节点同时满足。三种方案的完成时间：等原任务结束 12 s＋本地执行 20 s＝32 s；迁移占 8 核的 CPU 任务 4 s＋执行 20 s＝24 s；跨节点分散准备 1 s＋执行 32 s＝33 s——迁移比等待早 8 s、比分散早 9 s；迁移耗时涨到 12 s 就与等待打平，**调度器可直接拿预测迁移耗时与原任务剩余时间比**。阿里 ASI 生产集群研究同样发现配套 CPU 不足、成组启动与网络位置限制让空闲 GPU 用不上，加入可抢占低优先级作业后 GPU 分配比例从 68% 升到 93%。

突发与均匀到达的排队完全不同：十项各 1 s 的工作每隔 1 s 到达排队全零，同时到达则平均排 4.5 s——总工作量决定执行多久，到达时刻决定先等多久。80 次突发调用落 48 核：前 48 立即执行、余 32 等 1 s，平均 0.4 s、2 s 内完成；96 核则 1 s 内完成。环境内存也要够：80 个 2 GiB 环境要 160 GiB，始终驻留方案平均 600 GiB 超容量，每轮重建方案 180 GiB 才腾得出余量（环境策略见 40 篇）。突发分到多节点时，调度器视图是定期汇总的，总挑当前最空闲节点会让同批请求挤同一节点：DSec（峰值每秒 5000 沙箱、160 节点）用 power-of-k-choices 随机抽几个选最低、本地补记自己刚放的、节点自查容量不够就拒绝再换——全局视图可以过时，不超容量由节点检查保证，调度器无需持久状态。

抢占的代价要算进决策：在线任务最多等 2 s 而离线作业保存状态要 30 s，即使可抢占也要 30 s 后才交还——**需另行预留能在 2 s 内分配的资源**。优先级在硬件上未必分得开：BE 任务放 `SCHED_IDLE` 只管同一硬件线程谁先跑，开 SMT 后 LS 与 BE 仍可同物理核争执行单元；DSec 实测 BE 占半容量时 LS 每步耗时 +45%，单靠 SCHED_IDLE 几乎无改善，加 core scheduling 降到 +17%，剩余干扰来自降频与共用内存带宽/末级缓存。公平性也要定标准：两任务各得两张 GPU 看似份额相同，卡速差一倍则进度不同——DRF 按主导资源份额分配，Gavel/Pollux 进一步按处理能力或训练进度，限最长等待避免长期饿死（RL 作业的动态配比见 13 篇第 6 节）。
