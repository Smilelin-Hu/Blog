# KServe 模型服务控制面与声明式生命周期

把前一篇已经注册并批准的模型版本交给生产，并不是创建一个长期运行的容器那么简单。模型字节需要以固定摘要下载，Runtime 镜像需要与格式、GPU 和协议兼容，工作负载要通过调度和健康探针，Service、Gateway、TLS 与认证要形成完整请求路径，扩缩器还必须获得真实信号。任何一层失败，用户看到的都可能只是一个无法访问的 URL 或长期为 False 的 Ready。

![KServe 控制面与声明式生命周期](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l23_01.png)

本文以 2026 年 8 月 27 日核验的 KServe 官方一手资料为事实基线。KServe v0.20.0 已于 2026 年 8 月 6 日发布并被官方标记为 Latest。内容覆盖 InferenceService、ServingRuntime、Standard 与 Knative 模式、Storage Initializer、LocalModel、LLMInferenceService、HPA、KEDA、WVA 与 Condition 排障；不展开 KV Cache、Continuous Batching、推理引擎内部路由算法或 CUDA 性能优化。

知识讲解先于实验。实验使用确定性模拟验证声明式控制面合同，并提供只读真实 Kubernetes 路径。没有集群上下文时真实部分明确为 SKIPPED；提供上下文却无法读取 KServe 对象时返回 FAIL，模拟成功不能替代真实控制面证据。

## 1. KServe 的控制面定位

KServe 把预测模型和生成式模型转换为 Kubernetes 声明式服务对象，控制器负责把期望状态协调为工作负载、Service、入口和扩缩资源。

工程实现上，平台应把模型注册版本、运行时、网络、身份和容量策略组合成受控规格，而不是让用户直接拼接底层 Deployment。这项能力要同时回答期望状态由谁提交、控制器生成哪些子资源、当前状态如何观察、失败由哪个团队处理以及变更怎样回滚。平台把这些答案固化为 Schema、策略、Condition 和运行手册，用户才能在不理解全部底层对象的情况下获得可预测服务。

控制面正确不等于数据面正确。KServe 可以创建资源并报告中间 Condition，但模型服务器是否真的加载了固定字节、入口是否执行 TLS 与认证、请求是否到达正确修订，仍要用对象状态、日志、指标和真实请求联合验证。验收记录必须携带模型 Digest、Runtime Digest 和 Generation。

反例是：把 KServe 当推理引擎会混淆控制面与请求执行面；吞吐、KV Cache 和 Kernel 优化不由这个控制器自动完成。这种错误在单机实验中可能被手工修复，在多租户平台中会转化为不可复现、越权或容量事故。这里要求负面测试产生稳定 Reason，并让真实依赖缺失时显示 SKIPPED 而非假装通过。

## 2. 控制面与数据面分离

控制面观察 CR、生成子资源并更新 Condition；数据面由 Runtime Pod 和网络代理实际加载模型与处理请求。

从声明式生命周期看，为两条路径分别定义 SLO：控制面关注调和延迟和状态正确性，数据面关注可用性、延迟、错误与资源效率。发布器只写期望状态，不应直接操纵控制器拥有的 Deployment、Service 或 Route。控制器反复对账，status 与 Condition 提供观察接口，运维再沿 OwnerReference 和事件定位实际资源。任何人工热修都要回写配置源，否则下一次调和会覆盖。

从平台产品看，这项能力还要被包装为有界自助合同。租户选择模型版本、服务档位和暴露等级，平台注入 Runtime、身份、网络、扩缩和观测默认值；超出白名单的配置在创建前拒绝。这样既减少使用门槛，也把安全和成本责任放在正确控制面。

需要验证的反例是：控制器健康不代表模型 Pod 已 Ready，模型 Pod Ready 也不代表外部 Gateway 可达。页面显示对象存在不能作为验收，必须检查当前 Generation、第一处 False Condition、子资源状态和外部请求。缺少专用集群或 GPU 时，只能证明模拟规则和静态对象，不能声称真实吞吐或可用性。

## 3. Reconcile 循环

声明式控制器反复比较 spec 与实际资源，创建、更新或删除子对象，并把观察结果写入 status。

落地时，变更应通过 spec 与版本化配置进入，控制器操作要幂等，并以 generation 和 observedGeneration 区分新旧观察。每个外部引用都要固定身份，每个可变选择都要经过策略，每个子资源都要有明确 Owner，每个 Condition 都要能导向下一步检查。平台还需为超时、重试、并发更新和依赖升级定义边界，避免控制器无限等待或重复创建。

可观测性要覆盖控制器、初始化容器、Runtime、Gateway 与 Autoscaler。日志关联服务、修订和 Digest，指标区分调和、加载、启动、路由和扩缩，事件保留足够长以支持事故分析。若只聚合 Runtime 请求日志，控制面失败会成为盲区。

典型错误是：把一次 kubectl apply 成功当成服务完成，会忽略后续拉取、调度、启动和路由失败。验收应先重现错误，再确认 Reason、Condition、诊断建议和拒绝阶段都符合合同。修复后重新提交新 Generation，不能通过手工改子资源绕过平台。

## 4. Runtime Pod

Runtime Pod 承载模型服务器、必要的存储初始化、队列代理或可观测性组件，是请求真正执行的地方。

工程实现上，固定容器镜像 Digest、模型 Digest、资源请求、探针和 ServiceAccount，分别观测初始化与持续服务状态。这项能力要同时回答期望状态由谁提交、控制器生成哪些子资源、当前状态如何观察、失败由哪个团队处理以及变更怎样回滚。平台把这些答案固化为 Schema、策略、Condition 和运行手册，用户才能在不理解全部底层对象的情况下获得可预测服务。

反例是：只看 Pod 处于 Running 会错过容器未 Ready、模型未加载和路由未建立。这种错误在单机实验中可能被手工修复，在多租户平台中会转化为不可复现、越权或容量事故。这里要求负面测试产生稳定 Reason，并让真实依赖缺失时显示 SKIPPED 而非假装通过。

## 5. 请求数据路径

请求通常经 DNS、Gateway 或 Ingress、Service 与 Pod 端口到达 Runtime，不同部署模式可能插入 Knative 代理或其他组件。

从声明式生命周期看，绘制实际数据路径并在每一跳配置 TLS、认证、超时、大小限制和遥测关联。发布器只写期望状态，不应直接操纵控制器拥有的 Deployment、Service 或 Route。控制器反复对账，status 与 Condition 提供观察接口，运维再沿 OwnerReference 和事件定位实际资源。任何人工热修都要回写配置源，否则下一次调和会覆盖。

需要验证的反例是：入口返回 503 时直接重启模型 Pod，可能掩盖 Gateway、Service 选择器或 Endpoint 故障。页面显示对象存在不能作为验收，必须检查当前 Generation、第一处 False Condition、子资源状态和外部请求。缺少专用集群或 GPU 时，只能证明模拟规则和静态对象，不能声称真实吞吐或可用性。

## 6. 独立故障域

模型字节、Runtime、Kubernetes 调度、网络入口、扩缩指标和业务协议彼此独立，Condition 只能提供分层线索。

落地时，排障先找第一个未满足 Condition，再检查其所有者资源和事件，避免从最显眼日志开始猜测。每个外部引用都要固定身份，每个可变选择都要经过策略，每个子资源都要有明确 Owner，每个 Condition 都要能导向下一步检查。平台还需为超时、重试、并发更新和依赖升级定义边界，避免控制器无限等待或重复创建。

典型错误是：所有失败都映射成 PredictorNotReady 会降低可操作性，团队无法快速分派责任。验收应先重现错误，再确认 Reason、Condition、诊断建议和拒绝阶段都符合合同。修复后重新提交新 Generation，不能通过手工改子资源绕过平台。

## 7. InferenceService 对象

InferenceService 是 KServe 预测推理的核心声明式 API，spec 表达 Predictor 及可选的 Transformer 和 Explainer，status 暴露 URL 与 Condition。

工程实现上，平台模板只开放业务必要字段，Runtime、存储、网络和安全由策略补全与验证。这项能力要同时回答期望状态由谁提交、控制器生成哪些子资源、当前状态如何观察、失败由哪个团队处理以及变更怎样回滚。平台把这些答案固化为 Schema、策略、Condition 和运行手册，用户才能在不理解全部底层对象的情况下获得可预测服务。

反例是：让租户完整提交任意 PodSpec，等于绕过平台运行时白名单和安全基线。这种错误在单机实验中可能被手工修复，在多租户平台中会转化为不可复现、越权或容量事故。这里要求负面测试产生稳定 Reason，并让真实依赖缺失时显示 SKIPPED 而非假装通过。

## 8. Predictor

Predictor 加载模型并提供推理协议，是 InferenceService 的必需职责。

从声明式生命周期看，模型 URI 必须来自注册表固定版本和摘要，资源、运行时、协议与探针共同组成可部署合同。发布器只写期望状态，不应直接操纵控制器拥有的 Deployment、Service 或 Route。控制器反复对账，status 与 Condition 提供观察接口，运维再沿 OwnerReference 和事件定位实际资源。任何人工热修都要回写配置源，否则下一次调和会覆盖。

需要验证的反例是：只记录模型名 latest 而不固定摘要，同一 InferenceService 可在无 spec 变更时加载不同字节。页面显示对象存在不能作为验收，必须检查当前 Generation、第一处 False Condition、子资源状态和外部请求。缺少专用集群或 GPU 时，只能证明模拟规则和静态对象，不能声称真实吞吐或可用性。

## 9. Transformer

Transformer 位于 Predictor 前后执行预处理或后处理，会增加独立工作负载、网络跳数与故障面。

落地时，只有在预处理需要独立扩缩、依赖或复用时使用；其输入输出 Schema、超时和资源单独治理。每个外部引用都要固定身份，每个可变选择都要经过策略，每个子资源都要有明确 Owner，每个 Condition 都要能导向下一步检查。平台还需为超时、重试、并发更新和依赖升级定义边界，避免控制器无限等待或重复创建。

典型错误是：把轻量字段转换也拆成远程服务，会无谓增加延迟和发布复杂度。验收应先重现错误，再确认 Reason、Condition、诊断建议和拒绝阶段都符合合同。修复后重新提交新 Generation，不能通过手工改子资源绕过平台。

## 10. Explainer

Explainer 为部分模型提供解释请求路径，但它不是所有模型和 Runtime 的通用能力。

工程实现上，把解释能力视为显式可选合同，验证 Runtime 支持、数据权限和额外容量。这项能力要同时回答期望状态由谁提交、控制器生成哪些子资源、当前状态如何观察、失败由哪个团队处理以及变更怎样回滚。平台把这些答案固化为 Schema、策略、Condition 和运行手册，用户才能在不理解全部底层对象的情况下获得可预测服务。

反例是：默认开启解释端点可能暴露敏感特征或显著放大计算成本。这种错误在单机实验中可能被手工修复，在多租户平台中会转化为不可复现、越权或容量事故。这里要求负面测试产生稳定 Reason，并让真实依赖缺失时显示 SKIPPED 而非假装通过。

## 11. Status 与 URL

status 是控制器对当前观察的汇总，URL 只是入口声明，不等于端到端请求成功。

从声明式生命周期看，自动化等待 observedGeneration 追上目标且 Ready 为真，再用受控探针验证 DNS、TLS、认证与推理响应。发布器只写期望状态，不应直接操纵控制器拥有的 Deployment、Service 或 Route。控制器反复对账，status 与 Condition 提供观察接口，运维再沿 OwnerReference 和事件定位实际资源。任何人工热修都要回写配置源，否则下一次调和会覆盖。

需要验证的反例是：旧一代 Ready 状态在新 spec 提交后短暂保留时，发布器可能提前宣布成功。页面显示对象存在不能作为验收，必须检查当前 Generation、第一处 False Condition、子资源状态和外部请求。缺少专用集群或 GPU 时，只能证明模拟规则和静态对象，不能声称真实吞吐或可用性。

## 12. Condition 思维

Condition 表达某方面状态、Reason、Message 和转换时间，应按第一处失败建立诊断树。

落地时，平台保存 Condition 历史与事件，发布流水线依据明确 Reason 决定重试、拒绝或人工处理。每个外部引用都要固定身份，每个可变选择都要经过策略，每个子资源都要有明确 Owner，每个 Condition 都要能导向下一步检查。平台还需为超时、重试、并发更新和依赖升级定义边界，避免控制器无限等待或重复创建。

典型错误是：不停轮询一个布尔 Ready 而丢弃 Reason，会把可修复配置错误变成超时。验收应先重现错误，再确认 Reason、Condition、诊断建议和拒绝阶段都符合合同。修复后重新提交新 Generation，不能通过手工改子资源绕过平台。

## 13. ServingRuntime 职责

ServingRuntime 描述模型服务器容器模板、支持的模型格式与协议，使多个 InferenceService 复用受控运行环境。

工程实现上，运行时由平台团队发布，镜像按 Digest 固定，声明支持格式、资源假设、端口和健康合同。这项能力要同时回答期望状态由谁提交、控制器生成哪些子资源、当前状态如何观察、失败由哪个团队处理以及变更怎样回滚。平台把这些答案固化为 Schema、策略、Condition 和运行手册，用户才能在不理解全部底层对象的情况下获得可预测服务。

反例是：每个用户复制一份 Runtime 清单会造成版本漂移和安全修复困难。这种错误在单机实验中可能被手工修复，在多租户平台中会转化为不可复现、越权或容量事故。这里要求负面测试产生稳定 Reason，并让真实依赖缺失时显示 SKIPPED 而非假装通过。

## 14. ClusterServingRuntime

## 19. Runtime 白名单

白名单把可用 Runtime 限制为经过扫描、性能验证和维护的集合，是多租户平台基础策略。

工程实现上，以名称加镜像 Digest 和策略版本判断，禁止只按易被复用的名称授权。这项能力要同时回答期望状态由谁提交、控制器生成哪些子资源、当前状态如何观察、失败由哪个团队处理以及变更怎样回滚。平台把这些答案固化为 Schema、策略、Condition 和运行手册，用户才能在不理解全部底层对象的情况下获得可预测服务。

反例是：名称 vllm-runtime 合法但镜像被改成未知 Tag，简单白名单会失效。这种错误在单机实验中可能被手工修复，在多租户平台中会转化为不可复现、越权或容量事故。这里要求负面测试产生稳定 Reason，并让真实依赖缺失时显示 SKIPPED 而非假装通过。

## 21. Standard 模式

官方 v0.20 文档说明 Standard 模式以 Deployment、Service、Ingress 或 Gateway API 和 HPA 等标准 Kubernetes 资源实现。

落地时，适合希望减少 Knative 依赖、使用常规调度与卷能力的环境，扩缩与入口仍需明确组件。每个外部引用都要固定身份，每个可变选择都要经过策略，每个子资源都要有明确 Owner，每个 Condition 都要能导向下一步检查。平台还需为超时、重试、并发更新和依赖升级定义边界，避免控制器无限等待或重复创建。

典型错误是：把 Standard 理解为没有控制器，只手写 Deployment，会失去 InferenceService 生命周期。验收应先重现错误，再确认 Reason、Condition、诊断建议和拒绝阶段都符合合同。修复后重新提交新 Generation，不能通过手工改子资源绕过平台。

## 22. Knative 模式

## 24. 模式选择

部署模式不是简单功能多寡，而是依赖、启动特性、网络路径、卷需求和运维能力的选择。

落地时，平台按工作负载类提供预设：稳定在线 GPU 服务倾向保留最小副本，短小 CPU 模型可评估 Knative。每个外部引用都要固定身份，每个可变选择都要经过策略，每个子资源都要有明确 Owner，每个 Condition 都要能导向下一步检查。平台还需为超时、重试、并发更新和依赖升级定义边界，避免控制器无限等待或重复创建。

典型错误是：每个租户自由选择模式会增加支持矩阵和排障成本。验收应先重现错误，再确认 Reason、Condition、诊断建议和拒绝阶段都符合合同。修复后重新提交新 Generation，不能通过手工改子资源绕过平台。

## 25. 生成式模型的稳定资源
