# AI 数据与模型制品的存储和分发

一个百 GB 模型部署到四台 GPU 节点，四个 Pod 同时从对象存储下载，源站出口被打满，GPU 空闲等待十几分钟。平台随后增加节点缓存，第二次启动很快，却有一台节点加载了旧权重；另一个训练任务每小时生成 Checkpoint，控制器先更新 `latest` 指针，数据分片尚未全部上传，故障恢复读取到一个不可用版本。

![AI 数据与模型制品分发](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l09_01.png)

这些事故看似都叫“存储慢”或“缓存问题”，实际包含访问模式、存储语义、发布原子性、不可变身份、分发拓扑、容量和恢复目标。数据集、Checkpoint、模型权重、容器镜像和 Pipeline Artifact 不能因为都是文件，就使用同一个 PVC 或同一种缓存策略。

核心判断先给出来：平台先按读写模式、一致性、生命周期、共享范围、恢复目标和分发规模定义制品产品，再选择对象、文件、块、本地 NVMe、内存、OCI Registry 与缓存。持久化解决“数据能留下”，Digest 解决“读到哪一版”，快照解决某个存储时点的复制，应用一致性仍由写入协议保证；缓存解决重复传输，但必须以不可变身份、容量预算、校验和回收为前提。

本文先拆开五类制品，解释对象、文件、块、本地盘和内存的语义，再进入 CSI、StorageClass、PV/PVC、动态供给、延迟绑定、快照、克隆与数据填充。随后用 Rook/Ceph 说明 RBD、CephFS、对象网关、故障域与副本；再讲 S3 Multipart、版本与校验，OCI 层与 Digest、Kubernetes Image Volume、KServe LocalModel、本地缓存、分层缓存和 P2P。最后用启动时间、源站流量、RPO/RTO 与跨区成本收口。

实验模拟 120GiB 模型分发到四台节点，比较远程冷加载、节点缓存命中、预热和 P2P。所有时间都是由场景带宽计算的容量模型，不是假装实际测出的性能。实验还验证 RWO 多节点挂载、未完成 Multipart、Checkpoint 发布顺序、Mutable Tag 旧缓存、Digest 损坏、缓存空间不足、源站风暴和快照应用一致性边界。没有专用 Kubernetes 和对象存储时，真实路径明确标记 `SKIPPED`。

## 1. 先问制品怎样被读写，不要先问用哪家存储

“需要保存 120TB 数据”不足以选存储。训练数据可能被数千 Worker 并行顺序读取，Checkpoint 由每个 Rank 写入后整体提交，模型权重发布后只读，容器镜像按层复用，Pipeline Artifact 既有小元数据又有大文件。容量相同，IO 模式与一致性完全不同。

### 1.1 六个问题定义存储需求

第一，读多还是写多，是顺序大对象还是随机小 IO？第二，一个消费者还是许多节点共享？第三，内容能否修改，怎样标识版本？第四，失败后允许丢多少数据，即 RPO？第五，需要多久恢复，即 RTO？第六，数据是否跨 Zone、Region 或租户？

回答后才讨论存储后端。一个只读模型权重适合对象源加节点缓存，一个需要 POSIX 共享目录的旧训练框架可能使用 CephFS，一个数据库式元数据服务需要块卷，一个 Shuffle 临时文件适合本地 NVMe。没有万能“AI 存储”。

### 1.2 路径比介质名称更重要

用户说使用对象存储，实际路径可能是 SDK 直接读 S3 API，也可能由 Init Container 下载到 `emptyDir`，或由 FUSE 把 Bucket 挂成目录，再由模型服务复制到本地缓存。语义和性能都不同。

平台记录从源制品到 Pod 可见路径：来源、协议、缓存层、挂载、校验、解压、最终目录。下载慢时才知道是源站、网络、FUSE、小文件、解压还是本地盘。

### 1.3 成功打开文件不等于读到正确制品

路径存在只能证明某个内容可读。若引用 `production` 或 `latest` 等可变名称，节点缓存可能保留旧内容；如果没有校验，传输损坏也可能到加载阶段才失败。

平台把不可变 Digest 或 Version ID 作为运行时身份。人可以用 Tag 表达意图，但部署控制器先解析为 Digest，并把解析结果写入 Spec 和审计。运行期间不再次解析 Tag。

## 2. 五类制品的访问模式从根上不同

制品分类不是文件扩展名，而是生命周期和消费协议。一个 `.safetensors` 文件是模型权重，一组 Parquet 文件是数据集，一个 `.tar` 也可能是 OCI 层或 Pipeline 输出。平台目录按用途定义产品。

### 2.1 训练数据集是大规模读多与版本集合

数据集通常由许多 Shard 组成，被多个 Epoch、Job 和 Worker 重复读取。读取可能顺序扫描，也可能随机采样。吞吐、并发和小文件数量比单文件延迟更重要。

数据发布要有 Manifest，列出 Shard、大小、校验和、Schema 与版本。训练 Job 引用 Manifest Digest，不直接枚举一个会变化的目录。新增数据产生新版本，不原地覆盖旧 Shard。

数据集缓存可按 Shard，热门 Shard 留本地，冷数据从对象源读取。随机采样若跨大量小对象，会增加请求开销；预先合并 Shard 可提升吞吐，但改变 Shuffle 粒度。平台给数据团队反馈真实访问分布。

### 2.2 Checkpoint 是周期写入与一致恢复点

Checkpoint 保存模型参数、优化器、调度器、随机状态和分布式训练进度。它的价值不是“文件写完”，而是故障后能够恢复到一致 Step。多 Rank 分别写文件时，任一缺失都会让整体不可用。

正确发布通常先写临时版本，所有分片上传并校验，生成 Manifest，最后原子或条件更新 `latest` 指针。读者只读取已提交 Manifest。不能边写固定目录边让恢复任务扫描。

保留策略按 RPO 和成本。每十分钟写一次意味着最多丢约十分钟进度，但写入本身消耗网络与存储。近版本放热层，较老版本转温或冷层，达到期限后删除；删除前确认没有活跃恢复与合规保留。

### 2.3 模型权重是大对象、读多和不可变发布

模型权重在部署后应只读。同一 Digest 可能被数百副本消费，冷启动流量巨大。本地缓存、预热和 P2P 价值很高，但缓存键必须是 Digest。

权重经常由多个 Shard、Tokenizer、配置与 Adapter 构成。平台用 Manifest 表达完整集合，单个文件校验通过不足以证明模型版本完整。加载前验证所有 Required 对象、总大小和 Digest。

模型 Tag 可指向新 Digest，用于发布入口；已运行 Pod 继续使用旧 Digest，灰度 Pod 使用新 Digest。回滚只需重新引用旧 Digest，不覆盖对象。这使缓存与审计可预测。

### 2.4 容器镜像按层分发并由运行时管理

容器镜像由 Manifest、配置和有序 Layer 组成，Registry 以 Digest 标识 Blob。多个镜像共享基础层时，节点 Runtime 可以复用，减少传输。大模型直接塞进应用镜像虽然实现简单，却让代码小改也可能重建和重新分发巨大层。

代码镜像与模型权重分离通常更灵活：运行时镜像按软件版本发布，模型作为独立 OCI Artifact、对象或缓存制品挂载。二者分别 Digest 固定，再由部署记录组合。

镜像拉取和模型加载有不同事件。`ImagePullBackOff` 属于容器镜像，模型 Init Container 失败或 Image Volume 拉取失败属于制品路径。平台状态不要混成“启动失败”。

### 2.5 Pipeline Artifact 既是数据也是血缘节点

Pipeline 步骤输出指标、模型、图表、数据切片和中间文件。Artifact 需要 URI、Digest、类型、Schema、生产步骤、输入与运行身份。存储保存字节，元数据系统保存血缘。

把大对象直接写进 Pipeline 数据库会让控制面膨胀；更常见是对象写存储，元数据只记引用和校验。删除 Pipeline 运行时要区分元数据删除与共享制品垃圾回收。

## 3. 用访问模式轴选择，而不是背“优缺点”

任何制品都可沿七个轴定位：对象大小、文件数量、读写比例、并发消费者、共享范围、一致性和寿命。存储选择是这些轴的组合结果。

### 3.1 大对象和海量小文件不是同一种吞吐

读取一个 120GiB 连续对象主要受带宽和并行分段影响；读取一百万个 128KiB 文件会产生大量 Open、Metadata 与请求开销。总容量相同，性能可差几个数量级。

数据格式设计是存储工程的一部分。合并小文件、建立索引、使用适合随机访问的 Shard 格式，可减少 Metadata 压力。平台不能只加缓存掩盖上游文件布局。

### 3.2 读放大与写放大都要计算

四个节点各下载 120GiB 模型，源站流量 480GiB。三副本存储写入 120GiB 逻辑数据，后端可能消耗约 360GiB 原始容量，还包括元数据、校验和和日志。纠删码比例不同，CPU 与恢复代价也不同。

对用户展示逻辑容量，对平台容量规划使用物理放大。缓存又增加一份或多份副本，但可以降低网络与启动时间。成本比较要包含源、持久层、缓存和跨区流量。

### 3.3 一致性不是一个开关

对象写入后的可见性、目录列举、Tag 解析、缓存更新、文件锁和快照语义属于不同一致性。即使底层提供强读后写一致性，应用分多对象发布模型仍需 Manifest 与提交协议。

一致性目标应写成用户动作：部署引用某 Digest 时所有节点读取相同字节；恢复读取 `latest` 时得到完整 Checkpoint；Pipeline 运行重放时输入版本不变。具体后端机制服务这些目标。

### 3.4 生命周期决定谁负责清理

容器临时文件随 Pod 删除，本地模型缓存随节点维护可丢，Checkpoint 要按保留策略，训练数据可能长期保存，法规数据还有 Legal Hold。没有 Owner 和过期策略，存储只会增长。

清理引用可达性与保留规则。Digest 对象可能被多个 Tag、部署和实验引用，不能看到某个 Tag 删除就清 Blob。垃圾回收先计算活跃引用，再设延迟删除窗口。

## 4. 对象、文件、块、本地盘和内存提供不同语义

存储后端不是性能高低的线性排序。对象提供 Key 到 Blob 的 API，文件提供目录、路径和 POSIX 类操作，块提供裸设备或文件系统基础，本地盘靠近节点但缺少天然迁移，内存最快却易失且昂贵。

### 4.1 对象存储适合不可变大制品与规模共享

对象通过 Bucket、Key 与 API 访问，天然适合大规模命名空间、版本、生命周期和跨集群消费。训练数据、模型权重、Checkpoint 与 Pipeline 大对象常以对象为 Source of Truth。

对象不是普通文件系统。Rename 通常不是本地元数据原子操作，随机小写与频繁 Append 不自然。通过 FUSE 挂载可以兼容文件接口，却不自动获得完整 POSIX 语义与本地文件性能。

发布多对象制品时使用不可变 Prefix 加 Manifest，再更新小指针。不要依赖把整个目录 Rename 为正式版，除非具体系统明确提供所需原子性。

### 4.2 共享文件系统适合需要目录和多 Pod 读写

CephFS、NFS 和并行文件系统向应用提供目录、权限、文件操作与共享挂载。旧训练代码直接遍历目录或多个 Pod 共享输出时方便。

Metadata Server、目录热点和小文件会成为瓶颈。大量 Worker 同时 `stat` 同一目录，数据带宽未满，元数据已过载。优化要考虑目录分片、缓存和数据格式。

共享写需要应用协调。文件系统允许多个客户端写，不表示 Checkpoint 自动一致。锁、临时文件和 Manifest 协议仍需要。

### 4.3 块存储适合单工作负载的持久文件系统或数据库

块卷呈现设备，Pod 通常在其上格式化文件系统。RWO 块卷适合单节点训练状态、数据库、缓存索引或需要低延迟随机 IO 的服务。它不天然给多节点同时挂载。

块存储的 Attach、Detach 与拓扑影响 Pod 调度。卷位于某 Zone，Pod 必须能在兼容节点运行。节点故障后 Detach 可能等待 Fencing，RTO 不只取决于数据是否存在。

Raw Block 可让应用直接使用设备，但要求应用理解块语义，运维复杂。普通模型文件不因“块性能高”就应改用 Raw Block。

### 4.4 本地 NVMe 适合缓存、Shuffle 和可重建临时数据

本地盘延迟低、带宽高、靠近 GPU 节点，适合模型缓存、数据 Shard 缓存、编译缓存和 Shuffle。节点故障或重建时数据可能丢失，调度迁移不会自动带走。

Source of Truth 必须在持久层，缓存通过 Digest 可重建。若 Checkpoint 只写本地 NVMe，节点故障时无法恢复，除非后台复制在 RPO 内完成且有明确状态。

本地盘与容器镜像、日志、`emptyDir` 可能共享容量。缓存占满会触发 Ephemeral Storage 压力与 Pod 驱逐。平台分区、设置配额与保留水位。

### 4.5 内存适合极热、短命和可重建数据

内存盘或进程缓存适合小型索引、Tokenizer 状态、编译结果或极热数据。它占用节点内存，可能与 Pinned Memory、数据加载和系统组件竞争。

模型权重最终进入 GPU 显存，但这不表示 Host 缓存应无限保留。容量模型同时考虑 GPU 显存、Host 内存和本地盘，避免三层复制使节点 OOM。

## 5. 数据集产品要把版本、Shard 和读取计划绑在一起

平台发布数据集时，至少生成 Dataset Version、Manifest、Schema、Shard 列表、Digest、统计和访问策略。训练请求引用 Version ID，数据加载器按 Worker 数量与拓扑分配 Shard。

### 5.1 Manifest 是数据集的提交点

生产过程先写所有 Shard，每个对象包含大小与校验；质量检查通过后生成 Manifest。只有 Manifest 发布，版本才 Ready。失败的生成任务留下临时对象，由生命周期规则清理，不进入用户目录。

Manifest 可以包含总行数、字段 Schema、分区、许可与敏感等级。训练记录 Manifest Digest，实现重放。只记录 Bucket Prefix 无法证明当时有哪些对象。

### 5.2 Shard 大小在并行度与请求开销间权衡

Shard 太大，Worker 数量多时无法均匀分配，单个失败重传代价高；Shard 太小，请求与 Metadata 开销大。合理大小取决于对象存储吞吐、样本大小、压缩、随机性和 Worker 数。

先测代表性数据加载，记录每秒样本、请求数、CPU 解压与网络。不能套用固定“每 Shard 若干 GB”作为行业真理。

### 5.3 缓存按不可变 Shard 复用

缓存键使用对象 Version 或 Digest。两个数据集版本共享相同 Shard 时，只保留一份 Blob。Manifest 到 Blob 的引用决定可达性。

预热不必把整个数据集复制到每个节点，可按首个 Epoch 或本地 Rank 计划预取。长尾 Shard 在访问前到达即可，减少启动等待和缓存占用。

### 5.4 数据权限必须传递到缓存

源对象按项目授权，缓存若跨租户共享，需要证明内容不可被未授权用户枚举或读取。Digest 本身不是访问凭据；知道 Hash 不应自动获得 Blob。

缓存服务在每次请求校验调用方权限，或按安全域分池。节点上文件权限、容器挂载和清理也要隔离。数据撤销后，缓存副本进入删除或隔离流程。

## 6. Checkpoint 的正确性来自提交协议

分布式 Checkpoint 可能有数百分片。若 `latest` 仅指一个目录，写入过程中的目录可被恢复任务看到。正确协议把未完成和已提交版本分离。
