# GPU 资源抽象：Device Plugin、CDI、DRA 与设备健康

一个 Pod 声明 `nvidia.com/gpu: 1`，调度器为什么知道哪台节点还有卡；Pod 绑定后，谁决定分配 GPU 0 还是 GPU 3；容器运行时又怎样把正确的设备文件和驱动库放进容器？如果这张卡在任务运行中失效，Kubernetes 会不会自动换一张继续运行？

![GPU 资源抽象与设备健康](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l06_01.png)

把这些问题全部回答成“Device Plugin 负责”，会漏掉最关键的边界。传统 Device Plugin 把厂商设备发布为整数扩展资源，并在容器创建时返回设备注入信息；CDI 用跨运行时规范描述“获得某个设备意味着对容器做哪些修改”；Dynamic Resource Allocation 让设备类别、属性、Claim、分配结果和节点可达性进入 Kubernetes API 与调度过程。

三者不是简单的新旧替代关系。Device Plugin 可以在 Allocate 响应中返回 CDI 设备名；DRA 驱动也可以依赖 CDI 完成节点侧注入。CDI 不负责判断谁有权使用设备，也不负责调度；DRA 不自动安装内核驱动；Device Plugin 发布两个整数资源，也不意味着调度器理解两张卡的型号、显存、互联或共享关系。

本文从一次 Pod 资源请求出发，沿 API Server、调度器、kubelet、设备管理器、厂商插件和容器运行时走到容器内设备文件。然后比较传统整数模型与 DRA 的表达能力，处理属性选择、优先候选、Claim 生命周期、设备健康、节点绑定冲突、安全和迁移。

实验会构造三个节点、五个逻辑 GPU 设备、传统扩展资源和 DRA ResourceSlice。它同时验证两卡整数分配、高显存属性选择、H200 不可用时回退 H100、插件未注册、资源耗尽、没有匹配设备、节点约束冲突、CDI 规范陈旧、已分配设备失效和 Claim 回收。模拟只证明状态语义，真实设备路径必须连接明确的实验集群。

## 1. 从一个整数 GPU 请求说起

传统 Kubernetes 资源调度擅长可加总数量。CPU 可以用毫核表示，内存用字节数量表示，GPU 等厂商设备通过扩展资源名表示。Device Plugin 向 kubelet 报告两张健康设备后，Node Status 可能出现 `vendor.example/gpu: 2`，调度器据此完成数量装箱。

这个抽象刻意简单。调度器看到的是资源名和整数，不需要链接厂商 SDK，也不需要知道设备文件。厂商逻辑留在节点插件，Kubernetes 核心保持通用。简单性让 Device Plugin 稳定支撑大量 GPU、NIC、FPGA 与其他设备。

代价也来自同一个抽象。若两张 GPU 型号不同却发布为相同资源名，调度器把它们视为可互换单位；若一张 GPU 和一张高速 NIC 必须配对，两个独立整数请求不能天然表达“来自同一拓扑域”；若设备需要先按请求动态配置，静态健康列表不够。

### 1.1 扩展资源名是产品接口

扩展资源采用厂商域名加资源类型，例如 `nvidia.com/gpu`。域名降低不同实现重名风险，资源类型由提供者定义。对用户而言，这个字符串直接进入 Pod 模板、配额、队列、成本和监控，因而已经是一种 API。

平台不能随意把测试资源名替换成生产资源名。改名后旧 Pod 会继续请求不存在资源并保持 Pending，ResourceQuota 与成本规则也可能失效。资源名迁移需要并行支持、准入转换或工作负载版本升级。

不同型号可以发布不同资源名，例如把高显存卡与通用卡拆开，能在传统模型里增加一部分表达能力。但资源名数量会迅速增长：型号、显存、MIG 形态、共享模式和拓扑若做笛卡尔积，用户需要理解大量字符串，配额也变得碎片化。

稳定平台通常对外提供少量资源产品，再把产品映射到底层资源名和节点约束。这个映射应版本化，并告诉用户性能与隔离承诺；不能只给一个 `gpu` 字段，后台随机选择任何卡。

### 1.2 扩展资源只允许整数且不可超额承诺

传统扩展资源请求为整数。一个容器请求一张 GPU 时，调度器为它记一个单位；不能像 CPU 那样写 0.5。Kubernetes 也不默认对扩展资源超卖，已被 Pod 请求的单位不会再次分配给另一个 Pod。

整数不一定等于物理整卡。MIG 插件可以把实例作为资源单位，时间切片插件可以发布多个逻辑副本，vGPU 实现也可发布虚拟设备。调度器只知道单位数，不知道背后隔离和性能。因此资源产品必须解释“一单位”实际是什么。

厂商通过发布十个逻辑副本实现共享时，从 Kubernetes 账本看仍是十个不可超卖的整数；物理 GPU 却被多个工作负载共享。这不是 Kubernetes 自动理解了分数 GPU，而是插件先定义新的逻辑设备集合。共享的显存、故障和性能边界由实现承担。

传统文档中的设备不能在容器间共享，描述的是 Device Manager 把同一个插件设备 ID 独占分配。若厂商要共享，通常发布不同逻辑 ID 或使用额外机制。平台不要把物理共享事实和 Kubernetes 逻辑独占混为一谈。

### 1.3 Request、Limit 与设备资源

扩展资源通常写在容器 Limits 中。Kubernetes 要求设备资源请求与限制满足特定关系，实践里常只声明 Limit，由系统将相应 Request 用于调度。不要把 GPU 只写在环境变量或节点标签中，那样调度器没有所有权账本。

GPU 请求属于容器级分配。一个 Pod 里有两个容器分别请求 GPU，设备管理器按各自请求分配。把主程序与需要访问同一 GPU 的辅助容器分开时，要检查实现是否支持共享或管理容器路径，不能假定 Pod 内自动共享设备。

Init Container 对设备请求也会影响资源计算和生命周期。若初始化阶段需要 GPU 而应用阶段不需要，传统模型是否能在同一 Pod 内高效复用要按当前 Kubernetes 语义和插件实现验证。平台模板应避免隐藏设备占用。

调度器按声明数量工作，不看实时利用率。一个请求 GPU 却只做 CPU 预处理的 Pod 仍占有设备；这保障所有权，却可能降低利用。解决方法是优化工作流阶段、拆分任务或选择合适共享产品，而不是从账本中强行回收“看起来空闲”的卡。

### 1.4 资源数量与具体设备身份分离

调度阶段通常只决定节点，具体设备 ID 由目标节点上的 kubelet Device Manager 在容器创建前选择。调度器知道节点还有两个单位，不一定知道最后是 UUID-A 还是 UUID-B。

这种分离减少控制面细节，但限制了全局属性选择。插件可通过 GetPreferredAllocation 帮助 kubelet 在本节点选择更合适设备，例如尽量同一 NUMA；它只是偏好提示，不能替代跨节点调度决策，也不保证最终采用。

设备身份必须在分配后可观察。监控系统通过 kubelet PodResources API 等来源关联 Pod、容器与设备 ID，DCGM 一类采集器再按 UUID 归因。仅有“请求一张 GPU”的 PodSpec 不能告诉事故人员是哪张卡发生错误。

## 2. Device Plugin 从注册到分配的生命周期

Device Plugin 是节点侧 gRPC 服务。它先完成厂商初始化，在固定插件目录提供 Unix Socket 服务，再向 kubelet Registration 服务注册 API 版本、Socket 名称和扩展资源名。注册顺序很重要：必须先监听自己的服务，再通知 kubelet 连接。

注册成功后，插件通过 ListAndWatch 持续报告设备列表与健康。kubelet 据此更新 Node 的 Capacity 与 Allocatable。容器即将创建时，kubelet 调用 Allocate；可选的 GetPreferredAllocation 和 PreStartContainer 为拓扑偏好或启动前准备提供扩展点。

### 2.1 Registration 只是建立合作关系

kubelet 在 `/var/lib/kubelet/device-plugins/kubelet.sock` 提供 Registration 服务。插件提交自己的 Socket、Device Plugin API 版本和资源名。注册成功不代表发现了任何设备，也不代表 Allocate 一定成功。

插件通常以 DaemonSet 运行并挂载固定主机目录，因此需要较高权限。该路径不随 kubelet 普通 root 目录配置改变，部署清单必须使用官方规定位置。Socket 未创建、目录权限错误或 API 不兼容都会阻止注册。

kubelet 重启时会清理插件目录里的既有 Socket。插件必须监测 Socket 删除并重新注册。只在进程启动时注册一次的实现，遇到 kubelet 重启后可能仍 Running，却不再向新 kubelet 提供资源。

实验的 `plugin-unregistered` 把状态停在 RegistrationBlocked，Reason 为 PluginSocketUnavailable。此时节点可能有健康硬件，后续 ListAndWatch 与 Allocate 却没有控制通道。

### 2.2 ListAndWatch 发布设备列表与健康

ListAndWatch 是服务端流。插件发送当前设备 ID 和 Healthy 或 Unhealthy 状态；设备变化或消失时继续发送新列表。kubelet 聚合健康设备，把扩展资源写入 Node Status。

设备 ID 由插件定义，可能是 UUID、路径或逻辑实例标识。它应在合理生命周期内稳定，否则监控、分配恢复与故障关联困难。设备重配置后 ID 是否改变，要进入迁移和回收逻辑。

某设备变为 Unhealthy 时，kubelet 减少 Allocatable，Capacity 通常保持不变。这个差异很重要：Capacity 表示节点设备总量，Allocatable 表示可用于新 Pod 的健康量。二者差值可以触发设备故障告警。

已分配到故障设备的 Pod 不会因为 ListAndWatch 更新就自动换卡。分配关系继续存在，应用可能失败或 CrashLoop。静默把同一运行中容器切到另一张 GPU 会破坏上下文、显存和结果语义，因此恢复要由工作负载重建与检查点协调。

### 2.3 Allocate 发生在容器创建路径

Pod 已经调度到节点后，kubelet 为每个请求设备的容器调用 Allocate。请求包含要分配的设备 ID，插件可以执行设备准备，并返回容器访问设备所需修改。

响应可以包含设备节点、挂载、环境变量、Annotation 和完整 CDI 设备名。kubelet 把这些信息交给容器运行时。Allocate 成功说明插件构造了注入计划，不等于容器运行时已经执行，也不等于应用初始化成功。

Allocate 必须幂等或至少能安全处理重试。kubelet 与运行时故障可能造成调用边界不清，如果重复准备会泄漏设备配置或破坏前一次状态，节点难以恢复。插件开发者需要保存或重建分配状态。

失败日志应区分设备不再健康、准备失败、CDI 名称无法生成和内部错误。平台看到 ContainerCreating 时，要下钻 kubelet 和插件日志，不能只看调度事件。

### 2.4 GetPreferredAllocation 只提供本地偏好

当节点还有多张可选设备时，kubelet 可以询问插件首选集合。GPU 插件可能根据 NVLink、PCIe 交换机或 NUMA 选择彼此更近的设备。返回值帮助 Device Manager 作更知情决策，但官方接口明确不保证最终采用。

它发生在节点已选择之后，无法修复调度器选错节点。例如 Pod 同时请求 GPU 和高速 NIC，两者在不同 NUMA，两个插件各自给出局部偏好，未必形成全局最佳组合。Topology Manager 可以协调一部分节点级资源对齐，但表达仍有限。

业务不能把正确性建立在 Preferred 结果上。如果必须拿到特定拓扑，否则无法运行，应使用可验证硬约束、资源池或 DRA 等更丰富模型。偏好适合性能优化，不适合安全与兼容底线。

### 2.5 PreStartContainer 用于启动前准备

插件在注册选项中声明支持后，kubelet 可在每次容器启动前调用 PreStartContainer。厂商可用它重置设备或执行必要初始化。它不是所有插件必需方法，也不是 Pod Init Container。

PreStart 失败会阻止容器启动。重试时要考虑操作是否可重复、设备上是否残留进程、准备是否改变共享状态。高耗时初始化还会增加 Pod 启动长尾，应有超时和指标。

不能用 PreStart 偷偷执行全局设备重配置，却不让调度器知道。若一项配置影响其他 Pod 或改变资源形态，必须在分配和节点准入中协调，避免一个新容器破坏已运行工作负载。

### 2.6 Device Plugin 的 API 与部署也需要升级策略

Device Manager 功能已经长期稳定，但 Device Plugin API 版本仍需关注 Kubernetes 发布兼容。节点升级前，插件应先支持新旧 kubelet 需要的 API 范围，避免升级期间资源发布中断。

DaemonSet 滚动插件时，现有 GPU 容器通常不会立即丢失设备文件，但新分配和健康更新会受影响。平台在批次中观察 Node Allocatable 和新 Pod 启动，不能只看 DaemonSet Ready。

插件进程属于节点容量控制面。为它设置合适 Priority、资源请求和容忍，避免普通节点压力把插件驱逐；同时限制权限与镜像来源。它体积小，却掌握昂贵设备的分配入口。

## 3. kubelet 怎样保存和观察设备分配

kubelet Device Manager 维护节点设备状态与容器分配关系，调用插件并向运行时提供结果。调度器的资源账、kubelet 的设备账和监控系统的实际使用账属于三个视角，必须能互相对照。

Node Status 中的已分配资源来自 Pod 请求聚合，不列出每个设备 ID。具体 Pod 与设备关系可通过 PodResources gRPC 服务查询。监控代理可以读取分配给 Pod 和容器的设备，给利用率指标添加 namespace、pod 和 container 标签。

### 3.1 Checkpoint 帮助 kubelet 在重启后恢复

kubelet 需要在本地持久化设备分配信息，避免进程重启后把正在被容器使用的设备重新分配。实现通常维护设备管理 checkpoint，并结合 Pod 与容器状态恢复。

本地状态损坏、磁盘丢失或管理员手工删除 checkpoint 可能造成资源账异常。修复不能简单伪造文件，应先隔离节点、清空或确认现有 GPU 任务，再让 kubelet 与插件从干净状态重建。

节点被重建时原有 Pod 通常不应假设获得同一物理 UUID。训练检查点要保存业务状态，而不是依赖设备身份。只有确实与设备绑定的许可或拓扑场景，才需要上层显式协调。

### 3.2 PodResources API 连接分配与监控

PodResourcesLister 提供 List、GetAllocatableResources 等接口，让节点监控组件查看 Pod 和容器使用哪些设备。它解决的是观察与归因，不是让普通业务申请设备。

访问该 Socket 能够看到节点工作负载与设备元数据，应限制给受信任监控代理。把 Socket 挂入任意 Notebook 会暴露其他租户信息，并可能扩大节点攻击面。

监控采集的设备映射要处理 Pod 快速重建。旧 Pod UID 与新 Pod 同名时不能混淆，指标标签至少保留 namespace、pod、container，诊断系统最好关联 UID 和运行 ID。

### 3.3 调度账与利用率账可能不一致

一个 Pod 已分配 GPU 却利用率为零，可能正在拉模型、等待数据、执行 CPU 阶段或僵死。一个没有 GPU 请求的容器产生 GPU 利用率，可能是管理组件，也可能绕过 Device Plugin 获得设备权限。

平台定期做对账：扩展资源已请求的容器应出现在设备映射，非管理容器不应访问未分配设备，每个健康设备最多属于允许数量的逻辑所有者。共享模式使用不同规则，不能套用整卡独占断言。

异常对账不能立即杀进程。先确认监控延迟、Pod 终止窗口与管理容器白名单，再隔离。对账系统输出证据和置信度，避免把短暂状态传播成大规模误杀。

## 4. CDI 描述“把设备放进容器”

Container Device Interface 是一种开放规范。设备提供者生成 CDI 规范文件，里面为命名设备定义容器修改，例如添加设备节点、环境变量、挂载、hook 和其他编辑；支持 CDI 的容器运行时收到完整设备名后解析并应用。

CDI 把设备注入从某个运行时专用配置中抽离。Device Plugin Allocate 可以返回完整 CDI 设备名，kubelet 交给运行时；DRA 节点插件也可以在准备设备后使用 CDI。上层只传一个规范化名称，不必重复拼装所有 Mount 和 Device 规则。

### 4.1 完整设备名连接分配结果和规范条目

CDI 设备通常以厂商、类别和名称形成完整标识，例如 `gpu.training.invalid/device=a100-0`。运行时在本机规范目录找到匹配 kind 和 device 条目，读取 containerEdits。

名称必须和当前设备配置一致。GPU 重配置、MIG 变化或节点替换后，旧 CDI 条目可能引用不存在的设备文件。Allocate 返回名称成功，运行时解析时仍会失败，这就是实验 `stale-cdi-spec` 的边界。

CDI 文件由高权限工具生成，普通租户不能写。否则攻击者可创建同名条目，把宿主敏感文件或设备注入自己的容器。运行时应从受控目录读取，生成器镜像与节点文件权限进入安全基线。

### 4.2 Device Node 不是全部设备能力

Linux 设备通常通过 `/dev` 下的字符或块设备节点访问，容器还需要 cgroup 设备权限。GPU 应用又依赖驱动用户态库、配置和可能的 hook。只把 `/dev/nvidia0` 挂入容器并不能保证框架可用。

CDI 把相关编辑放在一个设备定义中，减少漏配和不同运行时实现差异。示例 `cdi-spec.yaml` 为模拟设备声明 deviceNode、只读库 Mount 和可见设备环境变量；它不对应真实 NVIDIA 路径，不能用于生产 GPU。

环境变量适合告诉框架可见身份，但不是安全隔离。用户可以修改环境，真正访问控制由设备节点、cgroup、运行时与驱动决定。用 `CUDA_VISIBLE_DEVICES` 隐藏其他卡，不等于阻止进程打开设备。

### 4.3 CDI 不负责资源所有权

只要高权限容器或管理员把某个 CDI 设备名直接交给运行时，运行时可以注入设备，却没有经过 Kubernetes 调度和配额。CDI 解决可移植注入，不建立谁能申请、是否空闲和如何计费。

标准工作负载应通过 Device Plugin 资源请求或 DRA Claim 获得设备，再由受信任链生成 CDI 名。管理容器确实可能需要绕过普通分配访问所有设备，例如监控代理，但必须使用专用 ServiceAccount、RuntimeClass 和策略。

NVIDIA 当前 Operator 文档已把 CDI 作为推荐与默认注入路径之一，但不同 Operator 版本和升级路径存在差异。这里绑定概念，实施时读取目标版本配置，不能把“当前默认”当成永远不变。

### 4.4 运行时支持和刷新时机决定最终结果

containerd、CRI-O 等运行时需要启用并支持 CDI。文件生成成功但运行时版本过旧或配置未加载，容器仍会创建失败。验收要通过 CRI 实际启动请求设备的 Pod。

运行时可能扫描规范目录并缓存。设备配置改变后，生成器更新文件的时机、原子写入与运行时刷新要协调。写到一半的规范被读取会造成瞬时错误，通常采用临时文件加原子替换。

节点上保留两个生成器可能互相覆盖文件。升级从 legacy NVIDIA runtime 迁到 CDI 时，要盘点旧 hook、RuntimeClass 和环境路径，金丝雀比较容器最终 OCI 规范，避免重复注入。

## 5. 传统静态资源模型在哪里遇到边界

Device Plugin 非常适合“节点有 N 个同质、启动前选择一个并注入”的设备。AI 平台开始要求型号偏好、显存下限、GPU 与 NIC 联合选择、动态 MIG 配置、共享容量和持久 Claim 时，单一整数资源名会承受越来越多补丁。

这些限制不是 Device Plugin 设计失败，而是需求超出原始抽象。判断是否引入 DRA，应看平台是否真正需要设备属性和生命周期，而不是因为 DRA 更新就重写所有稳定工作负载。

### 5.1 属性被压进资源名和标签

传统路径常用节点标签表达型号，用资源名表达数量。Pod 同时请求 `nvidia.com/gpu: 2` 并选择 A100 节点。调度器能找到 A100 节点，却不掌握节点内每张设备属性；异构设备混在同一节点时标签只能描述整体或复杂集合。

把每种属性组合做成资源名能够区分，却让 ResourceQuota、队列和模板成倍增长。一个设备配置变化可能使资源名改变，运行任务和新任务看到不同接口。

属性选择也缺少优先回退。用户希望 H100 优先、不可用时 A100，传统模板通常依赖多个队列、Webhook 修改或应用重试。硬编码一种型号降低利用，完全不选型号又可能得到不兼容设备。

### 5.2 多种设备联合选择困难

分布式训练可能同时请求 GPU 和 RDMA NIC，并希望二者位于同一 NUMA 或 PCIe 根。传统调度先根据两个整数资源选择节点，kubelet 的 Topology Manager 再在节点内尝试对齐。

若节点上的可用 GPU 与 NIC 分别位于不同拓扑域，数量满足但性能目标失败。插件各自只看到本类设备，难以表达跨资源约束。平台可能通过预先划分节点、拓扑资源名或自定义调度器弥补，维护成本很高。

DRA 允许设备以属性和 Claim 参与更丰富选择，但跨驱动联合语义仍需对应驱动与 Kubernetes 能力支持，不能假设声明两个 Claim 就自动获得最佳拓扑。后续网络与调度篇目会继续处理。

### 5.3 动态配置改变可用设备集合

MIG 把物理 GPU 划为实例，配置前后逻辑设备数和属性不同。传统插件通常要求管理员预先配置节点，再发布静态资源。用户 Claim 无法自然表达“为我创建这种形状，任务结束后还原”。

共享设备也可能有容量而不是离散个数，例如显存、带宽或时间配额。插件可预造固定逻辑单位，但难以覆盖连续组合，并可能产生碎片。DRA 的新能力为可消费容量、可分区设备和配置提供统一演进位置，不过各特性成熟度不同。
