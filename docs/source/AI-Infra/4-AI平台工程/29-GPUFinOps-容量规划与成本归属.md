# GPU FinOps、容量规划与成本归属

## 1. 课程定位

![GPU FinOps 与成本归属](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l29_01.png)

本文把 GPU 成本从月末报表提升为平台控制面的工程对象。目标不是教会一种固定计价公式，而是建立可复算、可对账、可解释、可治理的成本与容量系统：工作负载为什么产生费用，费用如何归属，空闲与共享成本如何保持可见，容量缺口如何由需求、提前期、目标利用率和故障域共同计算，优化建议如何在不破坏 SLO、安全和交付期限的前提下进入执行。

文中的费率是教学场景参数，不代表任何云厂商、采购合同或机房的真实价格。模拟只证明归属恒等式、容量公式、治理门禁和状态语义；真实 Kubernetes、OpenCost、Kueue 与 GPU 遥测需要在目标环境收集证据。没有真实环境时，实验必须返回 SKIPPED，不能把模拟结果写成真实成本结论。

## 2. 学习目标

完成后应能够：

- 建立从租户、项目、控制器、Pod、设备到成本中心的稳定身份链。
- 区分直接、共享、空闲、未分配和机会成本，并用总账恒等式对账。
- 解释 OpenCost Allocation API 的窗口、聚合、步长、分辨率和空闲参数。
- 为云 GPU 与自建 GPU 分别建立可版本化价格画像。
- 把 GPU 小时、有效 GPU 小时、训练或推理单位经济性与服务目标联合分析。
- 使用需求分位数、增长率、采购提前期、目标利用率和最大故障域制定容量情景。
- 建立价格新鲜度、账单覆盖、身份映射、共享规则和预算所有者门禁。
- 运行确定性模拟、反例测试与真实环境只读采集，并正确解释 PASS、REJECTED、INCONCLUSIVE、FAIL 和 SKIPPED。

## 3. 前置知识与环境

需要理解 Kubernetes Pod、资源 requests 与 limits、扩展资源、Namespace、控制器和基本 Prometheus 指标。模拟路径只要求 Python 3.10 及以上版本，使用标准库，不需要 GPU、Kubernetes 或外部服务。真实路径需要 kubectl、目标集群只读权限，以及按需部署的 OpenCost、Kueue 指标和 DCGM Exporter。

真实采集应先在只读环境完成。OpenCost 端口转发、Prometheus 查询和 Kubernetes API 读取不会自动改变资源；采购、缩容、抢占和自动终止属于有影响动作，不进入默认运行器。任何真实价格、折扣、折旧、电价和税费都必须来自组织认可的数据源。

## 4. 知识串讲

### 成本不是一个数字

GPU 成本至少同时存在资源数量、时间、价格、身份和业务单位五个维度。缺少任一维度，都只能得到局部估算。平台工程的价值是把这些维度接到同一控制面，使财务总额与工程行为可以相互解释。

### 容量不是设备清单

已安装 GPU 数量只描述库存。真正可承诺容量还要扣除故障、维护、升级和拓扑限制，并考虑队列等待、工作负载形状、需求增长和供应提前期。高利用率、低等待和强冗余不能同时无限提升，必须通过服务目标确定平衡。

### 归属先于优化

如果成本无法可靠归属，所谓优化很可能只是把费用从一个桶移动到另一个桶。平台应先保证身份覆盖、总账对账和价格可追溯，再讨论资源右配、共享、承诺和采购。

## 5. 原理与工程分析

### 1. FinOps 的工程边界

FinOps 不是把云账单换成按团队分组的报表，而是让资源申请、资源消耗、成本分配、容量承诺和业务价值进入同一套可验证决策循环。它连接财务、平台、工程和业务所有者，但不替代财务记账、采购审批或模型效果评估。

从数据模型看，FinOps 的工程边界必须绑定统一时间窗口、稳定资源身份、价格或策略版本以及计算状态。平台既保存输入事实，也保存派生结果，避免仪表盘只能展示最终金额却不能重放计算。任何缺失都应落入显式未知状态；补齐证据后可以重新计算，但不能悄悄覆盖已经关闭的账期。

从控制面看，FinOps 的工程边界需要与工作负载申请、队列准入、Pod 调度、设备分配、运行时遥测和完成结果建立关联。GPU 是一种不可超卖或按特定方式共享的稀缺设备，名称相同不代表拓扑、显存、健康、供应来源和服务等级相同。成本模型应保留这些差异，而不是只用一个集群平均单价。

反例是：只在月末导出一张总账，会让等待、空闲、碎片和容量短缺的原因全部丢失。这类做法通常能快速得到一个看似完整的数字，却不能回答数字为什么变化、由谁负责、是否可逆，也不能为采购、调度或发布决策提供可信依据。工程评审时应要求最小反例和失败语义，避免把缺失证据解释为零成本或正常状态。

实现时先定义数据契约，再选择 OpenCost、Prometheus、资产系统、云账单或自建 TCO 等数据源。契约至少包含主键、时间语义、单位、来源、版本、新鲜度、覆盖率和 Reason。数据源可以替换，合同不能随仪表盘实现漂移；展示层只消费已验证对象，不在页面中重复发明分摊逻辑。

验收平台是否能从任一成本条目回到工作负载、租户、资源池、价格版本和时间窗口。验收不能只检查页面是否有数值，还要随机抽取明细进行正向重算，并注入身份缺失、价格过期、重复分摊、采样中断和容量样本为空等反例。只有正例、反例、总账恒等式和真实环境边界同时成立，FinOps 的工程边界才进入可运营状态。

反例是：在标签覆盖率不足时直接做 Chargeback，会把平台数据缺口转化为错误账单。这类做法通常能快速得到一个看似完整的数字，却不能回答数字为什么变化、由谁负责、是否可逆，也不能为采购、调度或发布决策提供可信依据。工程评审时应要求最小反例和失败语义，避免把缺失证据解释为零成本或正常状态。

### 4. 时间窗口与采样粒度

成本是时间积分，窗口决定回答的是实时异常、日度归属还是月度结算。采样分辨率越细，短作业越不容易被漏掉，但查询开销和时序存储成本越高；步长决定返回分段，分辨率决定底层查询精度。

从数据模型看，时间窗口与采样粒度必须绑定统一时间窗口、稳定资源身份、价格或策略版本以及计算状态。平台既保存输入事实，也保存派生结果，避免仪表盘只能展示最终金额却不能重放计算。任何缺失都应落入显式未知状态；补齐证据后可以重新计算，但不能悄悄覆盖已经关闭的账期。

反例是：用三十分钟分辨率核算只运行两分钟的 GPU 任务，可能把短作业压缩成不可解释的缺口。这类做法通常能快速得到一个看似完整的数字，却不能回答数字为什么变化、由谁负责、是否可逆，也不能为采购、调度或发布决策提供可信依据。工程评审时应要求最小反例和失败语义，避免把缺失证据解释为零成本或正常状态。

### 5. 请求量与实际使用量

Kubernetes 调度主要依据资源请求判断是否可放置，实际使用量反映运行时消费。成本归属若只按使用量，低利用但长期占卡的工作负载可能逃避机会成本；若只按请求量，又无法发现程序没有真正使用设备。

从数据模型看，请求量与实际使用量必须绑定统一时间窗口、稳定资源身份、价格或策略版本以及计算状态。平台既保存输入事实，也保存派生结果，避免仪表盘只能展示最终金额却不能重放计算。任何缺失都应落入显式未知状态；补齐证据后可以重新计算，但不能悄悄覆盖已经关闭的账期。

反例是：把低 GPU 利用率直接解释为资源浪费，会忽略通信等待、数据加载、显存驻留和服务低负载保障。这类做法通常能快速得到一个看似完整的数字，却不能回答数字为什么变化、由谁负责、是否可逆，也不能为采购、调度或发布决策提供可信依据。工程评审时应要求最小反例和失败语义，避免把缺失证据解释为零成本或正常状态。

### 6. GPU 小时的基本口径

GPU 小时等于分配 GPU 数量乘以占用时长，是最容易跨工作负载比较的数量口径。它不包含 GPU 型号、分区、功耗、拓扑和服务等级，因此只能作为成本计算的一个乘数，不能等同业务产出。

从数据模型看，GPU 小时的基本口径必须绑定统一时间窗口、稳定资源身份、价格或策略版本以及计算状态。平台既保存输入事实，也保存派生结果，避免仪表盘只能展示最终金额却不能重放计算。任何缺失都应落入显式未知状态；补齐证据后可以重新计算，但不能悄悄覆盖已经关闭的账期。

反例是：把一小时旧型号 GPU 与一小时新型号 GPU 视作相同成本和相同性能，会扭曲优化决策。这类做法通常能快速得到一个看似完整的数字，却不能回答数字为什么变化、由谁负责、是否可逆，也不能为采购、调度或发布决策提供可信依据。工程评审时应要求最小反例和失败语义，避免把缺失证据解释为零成本或正常状态。

每条 GPU 小时记录必须绑定设备类型、资源池、计费率版本、开始结束时间和分配方式。验收不能只检查页面是否有数值，还要随机抽取明细进行正向重算，并注入身份缺失、价格过期、重复分摊、采样中断和容量样本为空等反例。只有正例、反例、总账恒等式和真实环境边界同时成立，GPU 小时的基本口径才进入可运营状态。

反例是：只把服务器采购价除以三年小时数，会忽略停机、功耗、网络和运维。这类做法通常能快速得到一个看似完整的数字，却不能回答数字为什么变化、由谁负责、是否可逆，也不能为采购、调度或发布决策提供可信依据。工程评审时应要求最小反例和失败语义，避免把缺失证据解释为零成本或正常状态。

为每个资产批次保留购置日期、折旧期、残值、实际可用小时和共享设施分摊。验收不能只检查页面是否有数值，还要随机抽取明细进行正向重算，并注入身份缺失、价格过期、重复分摊、采样中断和容量样本为空等反例。只有正例、反例、总账恒等式和真实环境边界同时成立，自建 GPU 的总拥有成本才进入可运营状态。

### 18. 云 GPU 账单

云成本应区分按需、承诺、竞价、存储、网络和管理服务费用。列表价可用于快速估算，结算必须与账单或成本使用报告对账，并明确折扣如何分配到工作负载。
