# AI 平台统一可观测性与资源归因

AI 平台的可观测性不是把 Prometheus、日志系统和链路追踪系统安装起来，也不是给每块 GPU 放一张利用率图。真正的问题是：一次训练、一次批处理、一次在线推理请求和一次模型发布，究竟消耗了哪些资源，经历了哪些控制面状态，在哪个环节失去效率，影响了哪个租户，证据是否足以支持告警、扩缩、容量决策和事故复盘。只有同一份资源身份能够贯穿工作负载对象、Pod、容器、节点、GPU、模型版本、服务版本和租户项目，多种信号才可能被解释为一条工程事实链。

![统一可观测性与资源归因](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l26_01.png)

本文以 OpenTelemetry Collector 0.159.0、Prometheus 3.12.0、NVIDIA DCGM Exporter 4.6.0-4.8.3 与 Kubernetes v1.36 的官方语义为核验基线。版本号用于固定实验接口，不表示每个企业必须使用相同组合。OpenTelemetry 的资源语义约定仍包含不同稳定级别，DCGM 字段是否出现取决于 GPU、驱动、DCGM、权限、实体类型和采集配置，Kubernetes Metrics API 只提供支撑自动扩缩的基础 CPU 与内存指标。这里会把稳定概念、当前实现和环境依赖分开说明。

## 1. 课程定位

本文关注 AI 平台的统一可观测性控制面，而不是重新讲解某一种数据库的安装运维。统一的含义不是把所有数据硬塞进一个后端，而是让指标、日志、追踪、事件和资源账本使用可连接的身份、明确的时间语义与可审计的处理策略。后端可以是 Prometheus 兼容存储、日志存储、Trace 存储或企业自研系统，平台契约仍应保持稳定。

资源归因也不等于财务结算。归因先回答“哪一个工作负载在什么时间窗占用了哪些资源”，后续 GPU FinOps 一篇再把资源量映射为价格、共享成本、预算和容量计划。本文的重点是建立可信计量底座：没有稳定身份、采样窗口和未分配桶，任何精确到小数点后的成本数字都可能只是伪精确。

## 2. 学习目标

完成后应能够独立完成以下工作：

- 为集群、命名空间、工作负载、Pod、容器、节点、GPU、服务、模型和租户设计稳定身份。
- 区分指标、日志、追踪、事件、Baggage 和 Profile 的信息能力与成本边界。
- 设计 Agent 与 Gateway 两层 OpenTelemetry Collector 拓扑，并解释单写者、队列、批处理、内存限制和背压。
- 为 Prometheus 指标设计名称、类型、单位、标签与基数预算，识别高基数和错误聚合。
- 将 DCGM GPU 指标可靠映射到 Pod、工作负载、项目与团队，并保留无法归因的数据。
- 建立 Trace、Log、Metric、Kubernetes Event 和控制器 Condition 的关联路径。
- 定义遥测完整性、时效性、关联率、归因覆盖率和查询成本等数据质量指标。
- 运行确定性机制模拟，并在真实 Kubernetes、Prometheus 与 GPU 环境中进行只读发现和证据采集。

## 3. 前置知识与环境

需要理解 Kubernetes Namespace、UID、Label、OwnerReference、Pod、Node、Deployment、DaemonSet 和 RBAC；知道 Counter、Gauge 与 Histogram 的基本差别；能够阅读 JSON、YAML、PromQL 和 Python。默认模拟只需要 Python 标准库。真实路径需要可读取目标集群的 `kubectl` 上下文，可选 Prometheus HTTP API，以及安装了 DCGM Exporter 的 NVIDIA GPU 节点。没有这些条件时真实路径必须返回 `SKIPPED`。

## 4. 知识串讲

### 1. 可观测性首先是决策能力

监控通常围绕已知故障预先设置指标和阈值，可观测性更强调依据系统外部信号推断内部状态。二者不是互斥关系。生产平台既需要稳定的 SLO 指标和告警，也需要事故发生后能够用未预先设想的维度追查。把所有原始数据都保存下来并不自动产生可观测性；数据缺少身份、时间、语义和查询路径时，数量越多，噪声越大。

平台团队应先列出必须回答的问题，再选择信号。训练为什么等待，可能需要 Kueue Workload Condition、Pod 调度事件、节点资源、存储吞吐和框架日志；推理延迟为什么上升，可能需要请求 Trace、队列深度、批处理大小、GPU 利用率、KV Cache 指标和部署修订；某团队用了多少 GPU，需要 Pod 生命周期、设备分配和时间窗口。若一个 Dashboard 无法支持任何操作决策，它只是装饰。

### 2. 从四个黄金信号到 AI 平台信号

延迟、流量、错误和饱和度仍然适用于 AI 服务，但需要扩展。训练平台的流量可以是每小时准入作业数、样本数或 Token 数，延迟要分排队、调度、镜像拉取、数据加载、训练和检查点，错误要区分用户配置、容量、基础设施、框架与数据，饱和度则覆盖队列配额、GPU、网络、存储和控制器工作队列。

在线推理还要区分首 Token 延迟、每 Token 延迟、端到端延迟、队列等待、批处理形成时间和模型执行时间。只看平均值会掩盖尾部，只有 P99 也可能在低流量时不稳定。正确做法是保存可聚合分布、请求量和错误分类，并让版本、路由、模型 Digest 与硬件档位成为受控维度。

### 3. 平台可观测性有三类消费者

工作负载所有者关心运行是否成功、为什么慢、是否达到模型与业务目标；平台运维者关心集群健康、控制器、调度、容量和故障域；治理与财务角色关心租户、项目、环境、预算和审计。三类消费者共享底层事实，但查询粒度和权限不同。把管理员级节点日志直接开放给所有租户会泄露邻居信息，把所有数据只做集群聚合又无法自助排障。

因此数据产品要有多层视图。租户视图只展示其授权工作负载与经过聚合的共享资源；平台视图保留节点、设备和控制器细节；治理视图依据不可伪造的项目归属计算用量。身份与权限在采集、处理、存储和查询四个环节都要执行，不能只依靠 Dashboard 隐藏按钮。

### 4. 统一不是单一后端

指标适合聚合、告警和趋势，日志适合离散事件和上下文，Trace 适合请求路径与因果，Kubernetes Event 与 Condition 适合控制面状态，Profile 适合代码级资源热点。每种信号的数据模型、成本与查询方式不同。统一平台应提供共同资源属性、关联键、保留策略、查询入口和治理规则，而不是强迫一种后端承担全部工作。

将所有日志转换成 Metric 会丢失上下文，把每个请求 ID 放进 Metric 标签会制造序列爆炸，把全部指标复制成日志会让聚合成本失控。一个成熟架构允许后端替换，同时保持 OpenTelemetry 资源属性、Prometheus 指标契约和平台身份映射不变。

### 5. 观测对象必须有稳定边界

平台对象不断变化：Deployment 创建 ReplicaSet，ReplicaSet 创建 Pod，Pod 重启后名称可能相近但 UID 改变；训练控制器可能重建 Job 和 Worker；模型服务会同时运行稳定版和候选版。名称适合人看，UID 才能区分对象生命周期。资源账本必须同时保存稳定业务身份与运行时 UID。

推荐把身份分为三层。业务层包含租户、项目、运行 ID、模型 Digest 和环境；控制层包含 Workload UID、TrainJob UID、InferenceService UID 或 PipelineRun UID；执行层包含 Pod UID、Container、Node UID、GPU UUID 或 DRA Device 名称。查询时从任意层都能沿映射边回到其他层，删除对象后映射仍按保留策略保存。

### 6. 为什么不能只依赖标签

Kubernetes Label 便于筛选，但值可能由用户提交、控制器改写或在对象重建时变化。如果费用和审计完全信任用户标签，租户可以把工作负载标到其他成本中心；如果只信 Namespace，又无法区分一个团队的多个项目。平台应在准入时根据已认证主体、项目空间和平台 API 生成归属，并由受信控制器写入不可随意覆盖的字段。

遥测处理器随后用 Kubernetes API 元数据补齐这些属性，而不是信任应用自己宣称的 `team`。应用可提供低风险业务维度，租户、项目、环境和安全级别应来自控制面。冲突时保留原始声明用于排障，但计量选择受信来源并记录冲突事件。

### 7. 集群身份为何要使用 UID

多个集群可能都叫 `production`，名称在重建、复制与灾备切换时也可能复用。OpenTelemetry Kubernetes 资源语义建议使用 `kube-system` Namespace 的 UID 作为当前集群 UID 代理，因为该 Namespace 与集群生命周期一致。平台还可保存企业定义的集群名称、区域和资源池，但不能只凭这些可变字符串去重。

如果集群重建后仍沿用旧 UID，历史数据会被错误拼接；如果每次 Collector 重启都生成随机集群 ID，同一集群会裂成大量资源。身份获取要由部署配置或 Kubernetes 属性处理器稳定完成，并在数据进入后端前检查缺失率。

### 8. 工作负载身份比 Pod 名称更重要

Pod 是执行载体，不是平台产品对象。一个训练运行可能有多个角色、多个 Pod 和多次重启；一个推理修订会横向扩容；一个 PipelineRun 会创建多个 TaskRun。归因若只按 Pod 聚合，用户看到的是碎片，重试还可能重复计费。平台需要把 Pod UID 映射到拥有者链，最终归到稳定运行 UID。

映射必须有时间区间。Pod A 在十点占用 GPU-1，十一点结束，Pod B 随后占用同一 GPU。只保存“GPU-1 当前属于 B”会把 A 的历史样本归给 B。每条分配边至少包含开始、结束、来源和观察时间；边界缺失时进入未分配桶，而不是猜测。

### 9. GPU 身份不是节点加序号

节点上的设备序号会随可见设备、驱动和容器映射变化，MIG、DRA、vGPU 与时间切片还会引入不同实体。优先使用 GPU UUID、MIG 实例身份或 DRA 分配结果，并保存节点与设备池作为属性。一个指标只带 `gpu="0"`，跨节点聚合后没有唯一意义。

DCGM Exporter 能在 Kubernetes Pod Resources 映射成功时添加 Pod、Namespace 和 Container 标签，当前版本还可选择 Pod UID、Pod Label 与 DRA 相关属性。但增加标签不保证字段存在，也不保证标签适合长期存储。平台仍需校验 GPU UUID、Pod UID 和采样时间窗，并对映射失败保留独立计数。

### 10. 模型身份必须绑定不可变制品

服务名只能说明逻辑组件，`champion`、`latest` 和 Tag 会移动。定位某个延迟或显存回归时，需要知道请求实际使用的模型 Digest、运行时镜像 Digest、配置版本和服务修订。`service.version` 可以使用版本字符串或 Git hash，AI 平台通常还需要独立 `ai.model.digest` 与 `deployment.revision`。

这些高价值属性适合放在资源或 Span 上，但是否进入 Metric 标签要经过基数评估。模型 Digest 的取值通常受发布数量限制，可以作为聚合维度；完整请求 ID、Prompt 和用户 ID 是无界维度，不应成为指标标签。

### 11. Service 资源属性的计算优先级

OpenTelemetry 对 Kubernetes 上 `service.namespace`、`service.name`、`service.version` 和 `service.instance.id` 给出非规范性计算建议。显式 `resource.opentelemetry.io/` 注解优先，然后可读取约定 Label，最后依据 Deployment、StatefulSet、Job、Pod 或 Container 等资源推导。目标是让同一横向扩展服务共享 `service.name`，不同运行实例拥有稳定可区分的 `service.instance.id`。

平台不应让每种语言 SDK 自由生成不同规则。最好在准入模板中写入明确注解，在 Collector 的 Kubernetes 属性处理器中补齐资源元数据，并用测试验证不同语言、Sidecar 和自动注入路径的结果一致。缺少 `service.name` 时 SDK 可能退回 `unknown_service`，这会把大量无关数据混在一起。

### 12. 资源属性和事件属性要分开

资源属性描述产生信号的实体，如服务、Pod、集群和版本；事件或 Span 属性描述本次操作，如路由、状态码、批大小和 Token 数。如果把请求级字段放在 Resource 上，每次请求都会创建新资源，后端压缩和查询都会恶化；如果把稳定服务身份只放在日志正文里，跨信号连接又很困难。

判断方法是询问：同一进程发出的许多信号是否共享该值。共享且稳定的值更适合资源属性；随操作变化的值属于信号属性。归属字段若在进程生命周期内不变，可以作为资源；运行中允许切换项目或模型时，应拆分实例或显式记录变更时间。

### 13. 身份图需要双向可追踪

排障从业务请求向下追踪资源，审计则常从节点或 GPU 向上追踪租户。只建立单向索引会让另一种查询依赖全表扫描。平台可以把资源映射保存在元数据服务、事件流或可查询账本中，至少支持 `run_uid -> pod_uid -> gpu_uuid` 与反向关系。

边的来源同样重要。OwnerReference、Pod Resources API、DRA ResourceClaim、调度器状态和平台准入记录的可信度不同。发生冲突时要能够解释采用哪一个来源，而不是静默覆盖。删除后的墓碑、重试关系和替代关系应有明确保留周期。

### 14. 缺失身份必须成为一等状态

常见做法是对缺失标签填 `unknown`，然后继续聚合。这样会把不同原因混在同一桶里。至少应区分采集器未获得 RBAC、Pod 已删除、Pod Resources Socket 不可用、GPU 字段不支持、应用未注入、处理器丢弃和后端查询窗口不完整。

未分配资源不是失败数据，应保留并告警。归因覆盖率等于已可靠映射资源量除以总资源量；覆盖率低于门禁时，财务、容量和租户报表应标记不完整，而不是把未分配量按比例摊给已知团队。

### 15. 指标回答“有多少”和“怎样变化”

Metric 以时间序列描述数值。Counter 表示累计且只增加或重置的量，Gauge 表示可上可下的当前值，Histogram 保存观测分布。请求总数、训练 Step 总数适合 Counter；队列深度、GPU 温度和显存使用适合 Gauge；延迟、批大小和样本处理时间适合 Histogram。

类型选错会直接产生错误结论。对 Gauge 使用 `rate()` 不具备累计变化语义，把当前 GPU 利用率声明为 Counter 会在重启与下降时失真。Exporter 的配置类型也不是自动推断的真理。NVIDIA 官方说明 DCGM Exporter 的 CSV 类型按配置使用，不会替用户验证字段语义，因此平台要审核自定义字段。

### 16. 日志回答“发生了什么”

结构化日志应包含 Timestamp、ObservedTimestamp、Severity、Body、Resource、Attributes，以及可用时的 TraceId 与 SpanId。事件发生时间和采集器观察时间不能混为一谈；二者差值可揭示缓冲、网络、时钟或背压问题。正文适合人读，稳定字段适合机器筛选。

日志不是无限上下文仓库。Prompt、样本、Token 和用户输入可能包含隐私、商业秘密或安全载荷。默认采集原文既昂贵又危险。平台应使用字段白名单、哈希或分类标签，必要的原始内容进入独立受控证据系统，不与普通运维日志混存。

### 17. Trace 回答“调用如何经过系统”

Trace 由具有共同 Trace ID 的 Span 构成，每个 Span 表示一段操作并通过 Parent Span 建立因果树。在线推理可以从 Gateway、路由、队列、批处理、模型执行到下游工具；训练控制面可以从提交、准入、调度、启动、数据准备到检查点。并非所有异步关系都适合父子结构，消息队列和批处理还可使用 Span Link。

Trace 的价值取决于传播正确性。只在入口生成 Trace ID、下游丢失上下文，会产生孤岛；把随机日志 ID 当作 Trace ID 也不能恢复因果。采样决策需要传播，否则上游保留、下游丢弃会形成残缺 Trace。

### 18. Event 和 Condition 描述控制面状态

Kubernetes Event 是有限保留的诊断记录，不适合充当永久审计日志；Condition 表示对象当前或最近观察到的状态，但不同控制器的 Type、Reason 与更新策略不同。平台应把关键 Condition 变更转换为带对象 UID、Generation、ObservedGeneration 和控制器版本的结构化事件。

一次 Pod Pending 可能只是正常排队，也可能是配额、拓扑、PVC、镜像或设备问题。只采集 Pod Phase 无法解释。应关联 Kueue Workload、调度事件、ResourceClaim、Node Condition 与控制器 Reconcile 指标，同时避免每次无意义重复 Reconcile 都产生大量日志。

### 19. Baggage 不是可信身份来源

OpenTelemetry Baggage 能把键值随上下文跨服务传播，但它与 Span、Metric 或 Log 属性并不会自动关联，需要显式复制。Baggage 可能随网络请求离开信任边界，也没有内置完整性保证。把 `tenant_id` 放入 Baggage 可帮助应用上下文，但计费和授权不能直接信任它。

平台应限制 Baggage 键、大小与目标域，禁止 Secret、Token、Prompt 和个人信息。受信 Gateway 可以把认证结果转换为内部签名上下文，Collector 仍要将计量身份与控制面元数据核对。客户端提供的租户字段只能作为声明，不能覆盖受信资源属性。

### 20. Profile 是补充而不是默认全采

Profile 描述代码级资源消耗，适合定位 CPU、内存或 GPU Kernel 热点，但采样、符号和存储成本与 Metric 不同。OpenTelemetry Profiles 仍处于演进阶段，平台不应因为“统一信号”就默认对所有租户持续高频采集。

推荐按事件触发或时间窗口开启，记录触发条件、采样率、版本与权限。Profile 可能暴露函数名、路径和代码结构，跨租户访问要严格控制。实验不伪装生成真实 Profile，只说明它在证据链中的位置。

### 21. 跨信号关联依赖共同资源和上下文

最稳健的关联有两类。第一类是资源关联：Metric、Log 与 Span 都带相同 `k8s.pod.uid`、`service.name` 和版本；第二类是请求关联：Log 保存 TraceId 与 SpanId，Histogram 的 Exemplar 可指向代表性 Trace。资源关联适合聚合，Trace 关联适合定位单次异常。

不要把每个 Trace ID 变成 Metric 标签。那会为每个请求创建新序列。Exemplar 或后端关联索引可以把分布中的异常样本链接到 Trace，同时保持指标基数可控。若后端不支持 Exemplar，也可在日志或事件中保存 Trace 链接。

### 22. 关联率是可观测性自身的 SLI

平台需要测量“有多少错误日志能找到 Trace”“有多少 Span 带完整资源属性”“有多少 GPU 样本映射到 Pod UID”“有多少工作负载能连接到项目”。这些是遥测数据质量 SLI，而不是业务 SLO。没有它们，Dashboard 为空时无法区分业务正常、采集失败和查询错误。

关联率的分母必须明确。只计算成功进入后端的数据会忽略入口丢失；因此还需要 SDK 导出、Collector 接收、处理、拒收、发送与后端摄取的分段计数。各段计数存在采样与重试差异，不能机械要求完全相等，但应定义允许偏差和时间窗。

## 5. 原理与工程分析

### 23. OpenTelemetry Collector 是遥测管线而不是数据库

Collector 的核心结构是 Receiver、Processor、Exporter 和 Connector。Receiver 接收 OTLP、Prometheus 或其他协议，Processor 批处理、限内存、过滤、变换和补充资源，Exporter 将数据发送到一个或多个后端，Connector 可以把一条管线的输出连接到另一条管线。Collector 不替代长期存储，它负责在信号离开工作负载后执行一致治理。

配置中定义组件并不代表组件已经参与管线。每个 `service.pipelines` 必须显式引用 Receiver、Processor 与 Exporter；一个 Processor 被声明却未接入任何 Pipeline，不会处理数据。上线前应以配置测试和自监控指标验证有效图，而不是只检查 Pod Ready。

### 24. Agent 和 Gateway 两层分别解决什么

Agent 通常以 DaemonSet 或 Sidecar 靠近数据源，适合读取节点日志、Kubelet 数据、主机指标和本地 OTLP；Gateway 以 Deployment 暴露集群级入口，适合集中执行路由、采样、治理和后端出口。二者组合可以减少应用凭据、统一网络出口并隔离后端变化。

Agent 不应保存全局状态，Gateway 也不能无条件把所有信号随机分发。Tail Sampling 需要同一 Trace 的 Span 到达同一处理实例，某些 Metric 转换要求单写者；因此可能需要 Trace ID 或服务名感知的负载均衡。OpenTelemetry 官方 Gateway 模式明确提醒同一 Metric 数据流要保持单写者和全局唯一身份，否则会出现覆盖、间隙与乱序样本。

### 25. DaemonSet 不是所有接收器的唯一答案

Kubelet Stats、文件日志和主机指标适合每节点一个 Agent，但 Kubernetes Cluster Receiver、集群事件和某些控制面抓取若在每个副本同时运行，会重复产生同一数据。需要单实例、Leader Election 或显式分片。把 Cluster Receiver 放入每个 DaemonSet 而不去重，是常见的重复 Metric Writer 来源。

设计时为每个 Receiver 写出数据所有权：谁负责哪个节点、Namespace、Target 或资源范围，故障转移后如何避免并发双写，扩容是否改变数据身份。仅凭 Helm 模式名无法替代这个分析。

### 26. Sidecar 的优点与隐性成本

Sidecar 与应用生命周期一致，能访问本地文件和 Unix Socket，故障域清晰；但每个 Pod 多一个容器会增加 CPU、内存、镜像拉取和升级成本。训练集群有成千上万个短生命周期 Worker 时，Sidecar 还会放大启动延迟和调度资源。
