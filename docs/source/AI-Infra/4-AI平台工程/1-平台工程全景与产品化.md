# 平台工程全景：从脚本堆积到平台即产品

AI Platform Engineering 的对象不是某个集群，而是「一群人如何稳定地获得 AI 能力」。这一篇建立判断框架：什么才算平台、平台为什么容易退化成脚本堆、以及怎么把需求翻译成架构。

## 1. 四个问题：这是平台还是工具堆

1. 用户能否通过**稳定接口**获得能力，而不是依赖某个管理员？
2. 系统能否**持续把声明的需求协调成实际资源**？
3. 失败、成本和责任**能否定位**？
4. 底层组件替换时，**用户接口与核心语义能否保持稳定**？

四个问题多数答不上来，组织拥有的就是工具或集群，不是平台。

## 2. 平台建设前最常见的资产：没人敢改的脚本

```text
脚本 A 建命名空间 → 脚本 B 复制 Secret → 脚本 C 生成训练 YAML → 脚本 D 从共享盘加载模型
```

每个脚本都可能局部解决问题，但它们缺少**统一状态模型**：执行者不知道上一步是否真的完成，也不知道重复执行会不会创建两份资源；失败后只剩一段终端输出，无法回答「系统最终处于什么状态」。

三类隐性成本：
- **审批**：敏感数据、大额 GPU、高风险变更确实需要人决定。但审批如果只活在聊天、表格与口头许可里，就无法成为机器可验证的准入条件——平台看不见审批结论，审计也无法把某次运行与批准记录关联；
- **隐性知识**：挂载路径错误，资深工程师几分钟修好，新人查半天。同类故障反复出现，说明组织只在修实例，没把知识沉成默认值、校验规则、错误消息或自动修复；
- **所有权真空**：用户认为脚本是平台给的、失败该平台负责；平台认为脚本只是示例；基础设施认为节点在线就完事。没有明确服务边界，每次事故都先争论归属再恢复。

把这些摩擦量化，平台投入才谈得清：首次成功运行需要多少人工步骤、每月多少重复工单、因环境或权限失败的作业比例、平均排队时间、资源空闲而用户仍在等待的时间、一次版本升级影响多少项目、事故中用于定位责任的时间。

## 3. 从「机器可用」到「能力可自助使用」

机器可用 = 电源、网络、OS、GPU 驱动正常。能力可用 = 目标用户能在权限范围内完成任务。中间隔着很长的交付链：身份与项目空间、可选的运行模板、数据与模型访问路径、队列与配额、可理解的状态与日志、结果保存与成本记录。

四层结果必须连起来：

| 层 | 结果 | 证据 |
|---|---|---|
| 资源 | GPU/CPU/内存/网络/存储按约束分配 | 分配记录、配额 |
| 运行 | 工作负载完成启动、执行、终止、清理 | 状态机、事件 |
| 业务 | 模型、指标或在线服务被正确交付 | 版本、评测、SLO |
| 治理 | 谁在何时以何种权限用了什么资源、产生什么版本和多少成本 | 审计、账目 |

## 4. 基础设施、集群、工具、MLOps 与平台

- **基础设施**：计算、网络、存储、设备。回答「资源是否存在、是否连通、是否健康」；
- **集群**：Kubernetes / Slurm 把资源组织成管理域，回答「对象如何被安排和运行」，但原语仍面向基础设施工程师（Pod、Job、PriorityClass、partition）；
- **工具**：只拥有局部状态。实验工具里的「完成」不代表模型已注册；注册中心的「候选」不代表线上容量已就绪；
- **MLOps**：强调流程与自动化，但范围因组织而异；
- **平台**（本系列的使用定义）：**面向内部用户、以稳定接口交付 AI 工作负载能力，并持续协调资源、生命周期、治理与运营状态的内部产品**。

三个关键词：面向用户（从任务出发）、稳定接口（实现可换、契约不破）、持续协调（不断比较期望与实际）。抓住它们，用 K8s、Slurm 还是云服务，都能用同一套框架分析。

## 5. 平台即产品：能力、体验、治理契约

**组件清单式写法**（「装 Kubernetes、Kubeflow、Kueue、KServe、Prometheus、Argo CD」）只能说明候选实现，不能说明用户获得了什么。

产品视角从用户任务出发。以「在受控项目空间提交一次分布式训练」为例：

- 输入：镜像、代码、数据、资源规模、优先级、恢复策略；
- 输出：运行状态、日志、指标、检查点、模型制品、成本；
- 限制：可用 GPU 型号、最大运行时间、配额、数据权限；
- 承诺：提交接口可用性、排队状态可见性、故障响应方式。

内部产品也需要版本、文档、支持与反馈：API 字段会演进、默认镜像会升级、旧 GPU 池会退役、安全策略会收紧。**没有产品管理，平台团队容易按技术兴趣扩组件，却证明不了使用价值。**

评审方案时可以做一次「遮住产品名」测试：若架构仍能说明用户怎样完成任务、状态怎样流转、策略怎样执行、谁拥有故障，就是能力驱动；若只剩空白，就只是罗列技术。

### 5.1 平台不该隐藏的复杂性

平台要降低无关复杂性，但不能删掉会改变结果的关键语义：

| 可以隐藏 | 不能隐藏 |
|---|---|
| Device Plugin 的安装方式 | GPU 型号与显存差异 |
| 队列控制器内部对象 | 作业可能等待与被抢占 |
| 控制器的重试实现 | 失败自动重跑会不会产生额外费用 |
| 监控后端的分片方案 | 日志保留期限 |

判断标准是：**它是否改变用户的风险、成本或结果。**

过度抽象会制造「惊讶」：只选「高性能训练」却被默默申请了昂贵 GPU 和专用网络，月底才看到账单；只点「自动恢复」却从旧检查点反复重跑，造成数据重复写入。另一种错误是完全不抽象，要求每个用户理解上百个 K8s 字段，把平台集成成本转移给每个业务团队。

合理做法是 **Golden Path**：为高频场景定义少量意见明确的模板，只暴露真正影响结果的参数，保留受控的扩展出口。

## 6. AI 工作负载为什么特殊

| 形态 | 生命周期 | 平台关注的痛点 |
|---|---|---|
| Notebook | 人驱动，长空闲 | 启动延迟、持久目录、身份代理、超时回收 |
| 批处理 | 明确开始结束 | 排队、重试、成本核算；分布式作业要同时启动 |
| 训练 | 数小时到数天 | 拓扑、检查点、故障恢复、成员状态 |
| Pipeline | DAG | 参数传递、制品寻址、缓存、分支、血缘 |
| 在线服务 | 无自然结束 | 副本、健康、路由、版本、扩缩容 |

把「所有等待」都显示成 Pending，会让用户与运维同时失去判断依据——**等待原因必须分类**（配额不足 / 等公平份额 / 缺特定 GPU / 缺同拓扑 / 等节点供给）。

持续时间也改变策略：几分钟的短作业，启动开销占大头（单看运行期 GPU 利用率会误导）；数天的训练怕中断，需要维护窗口、drain、检查点验证；长驻服务在滚动发布时会短暂双倍占卡，**没有发布前容量检查，标准发布动作本身就会造成事故**；交互式环境所有权最模糊，要「计算与持久数据分离 + 明确空闲策略」。

### 6.1 稀缺加速器让排队成为常态

一个 80 GB 显存的模型，不会因为「集群还有很多 GPU」被安排到 24 GB 卡上；一个需要节点内高速互联的训练，也不能随意分散。资源的**类别与拓扑必须成为可调度语义**，而不是靠用户记节点名。

稀缺资源下，排队是正常状态。平台若想让所有请求立即启动，只能过度采购或放任争抢。成熟做法是配额、借用、公平共享、优先级、抢占与准入顺序，并**向用户解释等待原因**。队列不是体验障碍；不可见、不可预测、能被人情绕开的队列才是。

## 7. 客户是责任，不是岗位

「算法工程师」不是精确的客户定义。数据科学家、训练工程师、推理工程师都写 Python，但触发点、风险和成功标准不同；此外还有治理型客户（安全、FinOps、SRE）。

| 角色 | 真实需求 | 成功指标 |
|---|---|---|
| 数据科学家 | 十分钟进环境、结果可复现、数据权限可控 | 首次有意义实验时间、交互转可重复比例、环境失败率、血缘完整率 |
| 训练工程师 | 整组资源一次声明、等待原因可见、能恢复 | P95 排队时间、首次启动成功率、有效检查点比例、恢复时间、重跑卡时 |
| 推理工程师 | 不可变版本、容量就绪、可控流量与回滚 | 发布前置时间、变更失败率、回滚时间、评测匹配率、SLO 达成率 |
| 平台/安全/FinOps | 自动化覆盖、策略覆盖、成本归属 | 变更失败与恢复、误拒绝、审计完整性、预算偏差与闲置 |

一个团队里同一个人可能既训练又部署；大公司则可能拆成四个部门。需求应写成「**负责把候选模型交付生产的人需要……**」，而不是假设岗位名称。

## 8. 需求到架构：四次翻译

需求列表常写成「需要支持 Notebook、分布式训练、模型部署、权限、监控和成本」——只有名词，没有关系：Notebook 的代码怎样变成训练作业？训练结果怎样进入版本？什么条件允许部署？权限在哪一步检查？成本按申请、分配还是实际使用核算？

至少四次翻译：

1. 愿望 → **用户旅程**；
2. 旅程痛点 → **能力**；
3. 能力 → **API、状态与服务契约**；
4. API 与能力 → **组件、集群与组织**。

需求还混了层级：「支持 GPU」是资源能力，「三小时内开始」是服务等级，「安装 Kueue」是实现选择，「提升研发效率」是业务目标，「能看到等待原因」是产品体验。放在同一优先级列表里，既排不出依赖也无法验收。

需求之间还会冲突（业务要立即启动、财务要减少闲置、安全要审核、研发要自助）。正确做法是把它转成**可选的服务档位**（高优保留容量 / 普通公平队列 / 低价可抢占），而不是用「兼顾效率与成本」一句话糊过去。
