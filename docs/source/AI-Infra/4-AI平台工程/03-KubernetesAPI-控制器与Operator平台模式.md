# Kubernetes API、控制器与 Operator 平台模式

平台团队写了一个脚本：先创建项目，再创建训练 Job，最后登记模型。脚本在演示环境中运行成功，于是团队把它接到门户按钮上。一个月后，网络超时导致用户重复点击，集群出现两份昂贵训练；管理员手工删除 Job，门户仍显示运行中；控制面重启后，半完成流程无人接管；项目删除时，对象存储里的检查点长期残留。

![Kubernetes 控制器与 Operator 模式](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l03_01.png)

问题不是脚本语法，而是它只执行一次命令，没有持续拥有系统状态。AI 工作负载运行时间长、子资源多、外部依赖多，失败可能出现在任何两步之间。平台必须能够在重复事件、进程重启、并发修改和部分失败下，继续把实际状态推向用户声明的期望状态。

Kubernetes 控制器模式提供了这种工程基础：用户提交资源对象，API Server 保存期望与状态，控制器反复观察差异并执行幂等动作。它不保证每一步立即完成，而是通过可重试调和达到最终一致。Operator 则把安装、升级、备份、恢复和故障处理等运维知识编码进控制循环。

判断一个平台控制器是否可靠，可以先检查五件事：同一事件重复到达会不会创建第二份资源；控制器重启后能否只依赖 API 中的事实继续工作；用户修改规范后状态能否说明观察的是哪一代；删除父对象时集群内外资源能否正确清理；失败状态是否足够让用户采取下一动作。

本文从一次重复训练事故出发，逐层拆开 API Machinery、Reconcile、CRD、Condition、OwnerReference、Finalizer 和 Admission，最后实现一个最小 AIJob 控制器仿真。实验会故意制造创建与清理的瞬时失败，并验证重复调和、乐观并发、状态更新、子资源更新和终结清理。

## 1. 为什么“一次执行成功”不是平台保证

命令式脚本描述动作顺序：创建 A，等待 A，再创建 B。声明式系统描述期望：对象应该具有某些属性，控制器持续确保这些属性成立。二者都能创建资源，但面对失败和时间时，责任模型完全不同。

### 1.1 一条命令只能证明一个瞬间

假设脚本向集群创建训练 Job，API 返回成功。这个响应只证明 API Server 在那个时刻接受并持久化了对象，不证明调度成功、镜像可拉取、所有训练成员就绪，更不证明运行会一直健康。Job 之后可能被人删除、被另一个工具修改，或因节点故障重建。

若平台把 API 200 当作“训练已启动”，状态会提前。用户看到成功，却在数小时后发现没有任何训练进展。可靠系统必须区分请求已接受、策略已通过、资源已准入、成员已形成、应用已运行和结果已交付，每个阶段由观察事实驱动。

命令执行也会在两步之间失败。脚本创建 Job 后、写入数据库前崩溃，重启时不知道 Job 是否存在；如果再次创建可能冲突，跳过则数据库永远缺记录。把进度只放在进程内存或日志里，控制器无法从故障中恢复。

长任务放大了这个问题。一个六小时训练期间，门户、平台 API、控制器、节点和网络都可能重启。平台不能要求发起请求的 HTTP 连接持续存在，也不能依赖最初处理请求的进程活着。期望和进度必须存放在具有一致性与持久性的资源对象中。

### 1.2 期望状态与实际状态必须分开

期望状态是用户想要系统维持的语义，例如使用四个成员、某个镜像和高显存资源产品完成训练。实际状态是系统此刻观察到的事实，例如子 Job 已创建、三个成员运行、一个成员等待镜像、最新检查点在某个位置。

把两者放在一个可被双方随意修改的字段里会产生冲突。用户可能把 phase 改成 Running，控制器则无法区分这是声明还是事实；控制器为了补默认值修改用户输入，也会让审计无法还原原始意图。Kubernetes 资源通常用 `spec` 表达期望，用 `status` 表达控制面观察。

差异就是控制器的工作队列。期望四个成员而实际没有子资源，创建子资源；期望镜像版本二而实际仍为版本一，更新或替换；期望对象删除而外部检查点仍存在，执行清理。没有差异时，调和也应安全结束，不产生新的副作用。

实际状态不一定直接等于某个底层对象。AIJob 的运行状态可能由 Kueue 准入、JobSet 成员、Pod 就绪、训练框架指标和制品登记共同决定。平台控制器需要聚合这些事实，生成稳定、可解释的上层状态，同时保留下钻链接。

### 1.3 持续协调意味着系统会自我修复

控制器不是“收到创建事件后执行一次”的回调。事件只提醒某个对象可能需要检查；真正逻辑应读取最新对象与依赖，重新计算差异。即使事件重复、合并、延迟或控制器重启后重新列表，结果都应一致。

持续协调让系统能够应对漂移。管理员误删由 AIJob 管理的子 Job，Owner 控制器收到子资源删除事件，再次调和父对象并按策略重建；用户修改副本数，Generation 增加，控制器观察新规范后更新子资源；外部依赖暂时不可用，控制器退避后再次尝试。

自我修复有边界。若训练已经产生副作用，简单重建可能重复写数据；若用户手工修改由控制器拥有的字段，控制器会改回；若外部 API 操作缺少幂等键，重试可能重复扣费。控制器模式不会自动消除这些问题，它要求设计者明确所有权、幂等与恢复语义。

### 1.4 最终一致不是无限等待

最终一致表示系统允许期望与实际在一段时间内不同，并通过调和收敛。它不是对延迟和失败不作承诺。平台仍要为校验、控制器调和、资源准入和状态新鲜度定义服务水平，并在无法收敛时提供明确 Condition。

控制循环的收敛可以用一个概念函数表示：

$$x_{t+1}=R(d,x_t,e_t)$$

其中 $d$ 是期望状态，$x_t$ 是当前实际状态，$e_t$ 是本轮观察到的外部事实，$R$ 是调和函数。可靠设计希望重复应用 $R$ 后，系统进入满足期望的稳定集合；对同一稳定输入再次调用，不能不断产生新对象或改变结果。

有些状态不会自动收敛。例如用户请求不存在的设备类型，继续重试不能创造资源；镜像签名被策略拒绝，只有修改规范或批准例外才能推进。控制器应把这类错误标记为不可重试或等待用户动作，避免无意义地高速重排队。

最终状态也不总是成功。Succeeded、Failed、Cancelled 都可以是终态，关键是它们由确定证据产生，并说明结果与清理是否完成。若失败后允许用户修改规范重试，需要定义是同一对象进入新一代，还是创建新运行对象；两种选择影响审计与历史。

## 2. 一个资源对象怎样穿过 Kubernetes API

理解控制器之前，先要理解它依赖的事实系统。API Server 是资源操作入口，负责认证、授权、准入、验证、版本转换和持久化；etcd 保存规范化状态；客户端和控制器通过 List、Watch、Get、Create、Patch、Update 等 API 观察与修改对象。

这不是一个让所有组件直接读写数据库的架构。API Server 统一并发、版本、策略和审计。控制器只通过 API 操作对象，不能把本地缓存当成权威，也不应绕过 API 直接修改 etcd。这样不同控制器才能围绕共享资源安全协作。

### 2.1 API Server、etcd 与资源事实

当客户端提交 AIJob 时，请求先经过身份认证，得到调用主体；授权判断主体能否在目标 Namespace 创建该资源；准入阶段可能补默认或拒绝；模式验证检查字段；版本转换将外部版本转为存储版本；成功后对象写入 etcd，并返回包含 UID、ResourceVersion 等服务端元数据的结果。

etcd 保存的是 Kubernetes API 的持久事实，不是训练数据仓库。模型、检查点和大日志不应塞入资源对象。对象保存引用、摘要、状态和必要证据；大制品存放在适合的数据系统。否则对象过大、更新频繁会拖累整个控制面。

API Server 的高可用不等于每次读取都看到未来。并发客户端通过 ResourceVersion 协调，Watch 从某个版本继续事件流。客户端必须按照 API 语义处理过期版本、重新列表与断线恢复，不能把网络连接本身当成一致性保证。

资源对象的身份由 API Group、Version、Kind、Namespace、Name 和 UID 等共同描述。Name 可以在对象删除后重用，UID 对一次对象生命唯一。OwnerReference 必须引用 UID，不能只凭名字，否则新对象可能错误继承旧对象的子资源。

### 2.2 Metadata、Spec 与 Status 各自保存什么

Metadata 保存对象身份、版本、标签、注解、所有权、终结器和删除时间等控制信息。标签用于选择与组织，应保持短小、可索引和有稳定语义；注解可保存非识别性元数据，但也不适合塞入无限增长日志。

Spec 是用户或上层控制器声明的期望。AIJob 的 Spec 可以包含镜像摘要、命令、成员数、资源产品、检查点引用和重试策略。字段应表达产品语义，使用 OpenAPI 模式验证。控制器读取 Spec，却不把运行事实写回 Spec。

Status 是控制器观察到的结果。它可以包含 Phase、ObservedGeneration、Conditions、成员摘要、准入引用、开始与完成时间、制品引用。启用 Status 子资源后，更新 Status 不应改变 Spec 的 Generation，也可以通过 RBAC 单独授权控制器写状态。

Metadata 里的 Generation 通常在期望状态发生有意义变化时增加。控制器处理某一代 Spec 后，把该值写入 Status 的 ObservedGeneration 或 Condition 的 observedGeneration。用户看到 Ready=True 时，必须结合代数判断它是否对应最新规范。

### 2.3 Generation 与 ObservedGeneration 防止陈旧成功

假设 AIJob 第一次运行成功，Generation 为一，Status Ready=True。用户把成员数从四改成八，Generation 变为二，但控制器尚未处理。若界面只看 Ready=True，会错误宣布八卡任务已经就绪；实际上这个状态来自旧规范。

控制器开始处理新一代时，应更新 Progressing 或其他 Condition，并在完成观察后写入 `observedGeneration: 2`。客户端判断最新状态时验证 ObservedGeneration 是否等于 Metadata.Generation。两者不等时，旧状态仍有历史价值，但不能代表新声明已经兑现。

并非每次 Metadata 变化都提高 Generation。标签或注解的变化是否影响它取决于资源实现；设计者不能用 ResourceVersion 代替 Generation。ResourceVersion 表示对象存储版本，任何更新都可能变化；Generation 表示期望语义代数，两者解决不同问题。

Condition 自身带 observedGeneration 更精确。一个对象的 Available、Progressing 和 Degraded 可能由不同控制器或不同阶段更新，分别说明各自观察的代数。顶层 ObservedGeneration 可以作为摘要，但不能让 Condition 丢失语义。

### 2.4 Watch、Informer 和缓存解决规模问题

控制器不能每秒全量扫描所有对象，也不能为每个事件都直接向 API Server 做大量读取。典型客户端先 List 得到对象集合与 ResourceVersion，再 Watch 后续变化；Informer 维护本地缓存、事件处理和索引，把相关对象键放入工作队列。

Watch 是有版本的事件流，不是永久可靠消息队列。连接会断、版本会过期、事件可能合并，客户端需要重新 List 并恢复。控制器逻辑因此不能依赖“恰好收到某个中间事件”，而要根据最新状态计算正确结果。

缓存读取通常具有短暂延迟。刚创建子资源后立即从缓存读取，可能还看不到它；如果控制器因此再创建一次，会产生冲突或重复外部操作。常见策略是使用确定名称让第二次创建得到 AlreadyExists，再在后续调和读取；对外部 API 则必须传幂等键或持久记录操作身份。

Informer 可以为父资源和子资源建立索引。子 Job 状态变化时，通过 OwnerReference 或标签找到对应 AIJob，把父对象键入队。队列只保存“需要重新检查”的键，不要求保存完整事件历史。调和开始时总是获取最新对象。

本地缓存不是数据库。控制器重启后可以重新 List 重建，因此任何无法从 API 或外部权威系统恢复的进度都不应只放在内存。性能缓存可以丢，业务事实必须可重建。这条规则是 Operator 能否真正自愈的分水岭。

## 3. Reconcile 循环怎样写得可重复

一个典型调和函数接收 Namespace 和 Name，读取 AIJob；对象不存在则结束；检查删除流程；计算期望子资源；创建或更新差异；读取子资源状态；更新父对象 Status；根据需要立即、延时或在事件到来时再次入队。

这看起来简单，真正难点在边界：每一步之后进程都可能退出，同一个键可能并发或重复处理，缓存可能陈旧，写入可能冲突，外部调用可能成功但响应丢失。可靠调和不是把命令脚本放进循环，而是让每个中间状态都可恢复。

### 3.1 获取、比较、执行、报告与重排队

获取阶段读取父对象和必要依赖。若 API 返回 NotFound，通常表示对象已经删除，本轮成功结束。其他读取错误按瞬时或永久分类。不要在还没读取最新 Spec 时依赖事件附带旧对象执行。

比较阶段构造期望子资源并与实际对象比较。比较只关注控制器拥有的字段，忽略服务端默认、其他控制器拥有的 Status 和无关 Metadata。整对象深度比较容易因时间戳、默认值或字段顺序造成无休止更新。

执行阶段使用 Create、Patch 或 Update 改变实际状态。每个动作都要可重复：确定子资源名称，设置 OwnerReference，使用资源版本处理并发，对外部系统使用幂等请求标识。成功后不必在同一轮完成所有步骤，可以结束并等待新事件。

报告阶段更新 Status 与 Event。Status 表达当前稳定事实，Event 记录值得用户注意的离散变化。不能每次调和都生成相同 Event，否则事件系统和用户都会被淹没。日志则用于诊断本轮行为，并携带控制器、Namespace、Name、UID 和 Reconcile ID。

重排队有三种来源。相关对象变化触发事件入队；瞬时错误由限速队列退避重试；需要周期检查但没有事件源时使用延时重排队。优先建立 Watch，而不是用短周期轮询弥补缺少依赖观察。

### 3.2 幂等不是“先查再创建”这么简单

幂等意味着相同意图和事实下，重复调和不会产生额外业务副作用。先查询再创建只是一个开始，因为查询与创建之间存在竞态：另一个工作者可能已经创建，缓存也可能暂时看不到。创建操作必须能够安全处理 AlreadyExists，并确认现有对象是否属于当前父对象。

子资源采用确定名称最容易去重，例如父名加角色。若需要多个运行历史，可以把不可变运行 UID 或代数加入名称，并把映射写入父 Status。随机名称配合 GenerateName 很方便，却要求额外机制识别“上次请求已创建但响应丢失”的对象。

更新也要幂等。控制器只在拥有字段有差异时写入；若每轮都无条件更新时间戳或重排列表，会触发自己的 Watch，形成热循环。Status Condition 的 transition time 只在状态真正变化时更新，而不是每次观察都更新。

外部副作用最危险。调用云 API 创建桶、发送消息、登记模型或扣费时，HTTP 超时无法说明服务端有没有执行。请求要携带由对象 UID 和动作构造的幂等键，或先创建 Kubernetes 操作记录，再由单独控制器完成。绝不能仅因没有收到响应就换随机名字重试。

删除同样要幂等。外部对象已不存在应视为清理完成；重复撤销权限不产生新错误；移除 Finalizer 只发生在所有必要清理确认后。这样控制器在清理中途重启，下一轮仍可继续。

### 3.3 ResourceVersion 与乐观并发保护别人

多个客户端可能同时更新同一对象。Kubernetes 使用 ResourceVersion 支持乐观并发：客户端读取版本，基于它提交 Update；若对象已被别人修改，API 返回冲突，客户端重新读取、重新计算，而不是覆盖最新内容。

冲突不是基础设施异常，而是正常并发信号。控制器不应盲目重复相同旧对象写入，也不应去掉 ResourceVersion 强行覆盖。正确做法是让当前调和返回，再从缓存或 API 获取新版，重新应用仅属于自己的变更。

Patch 可以减少覆盖范围，但仍需要理解字段所有权。Server-Side Apply 通过 field manager 跟踪字段所有者，适合多个管理者协作，但冲突应被认真处理。控制器声明拥有的字段要少而清晰，避免管理整个对象模板导致用户或其他控制器的合法字段被抹掉。
