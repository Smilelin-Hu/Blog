# 六项平台实验：把能力写成可验收的合同

第四期最后六篇不是「再讲一遍组件」，而是六次**验收演练**。它们共享同一个模板：任何一项平台能力，都必须能说清输入、观察方式、成功条件、失败 Reason 与负责团队。

## 1. 六项实验全景

| # | 实验 | 核心问题 | 关键证据 |
|---|---|---|---|
| 1 | GPU Ready 集群基线 | 这台节点凭什么能接 GPU 任务 | 宿主机 + API + 测试 Pod 三视角 |
| 2 | 多租户 GPU 批处理与配额平台 | 配额怎么分、怎么结算、怎么隔离 | 队列准入记录 + 租户账目 + 隔离验证 |
| 3 | 声明式分布式训练平台 | 一次训练从声明到制品的全链路 | Workload 状态 + 检查点 + 制品提交 |
| 4 | 模型持续交付与安全发布平台 | 上线的是不是批准的那一份 | Digest 绑定 + 门禁 + 灰度/回滚 |
| 5 | SRE / 安全 / FinOps 控制台 | 故障、审计、成本能否归因 | SLO + 审计事件 + 成本对账 |
| 6 | 企业级自助 AI 平台 | 门户聚合是否能代表真相 | 权威状态划分 + 跨系统 generation |

## 2. 共同模板：能力写成合同

每项能力都要回答五件事：

1. **输入**：谁提交、带什么字段、经过哪些校验；
2. **观察**：从哪个来源看状态（CR Condition / 事件 / 遥测）；
3. **成功条件**：不是「对象存在」，而是「真实路径可用」；
4. **失败 Reason**：稳定、可分类、能指向下一步动作；
5. **Owner**：出问题找谁，回滚由谁执行。

**「组件已安装」永远不能替代合同。** 节点只有同时满足软件、设备、网络、存储、制品与健康条件，才对外发布对应 Profile；某一子条件失效时，控制器应撤销受影响能力或隔离节点，而不是继续依赖人工记忆避免调度。

## 3. 三视角证据：只查一层一定漏

| 视角 | 能看到 | 看不到 |
|---|---|---|
| 宿主机 | 内核模块、设备节点、驱动版本 | 调度账本、运行时注入 |
| Kubernetes API | Capacity/Allocatable、Claim、Condition | 容器内真实可见性 |
| 测试 Pod | Runtime 注入、CUDA 初始化、真实可用性 | 宿主侧健康细节 |

两个经典断点正是「只查一层」造成的：

- **主机可见 GPU，容器不可见**（Toolkit/运行时配置没生效）；
- **Capacity 正确，但健康设备已从 Allocatable 扣除**（ListAndWatch 报了 Unhealthy）。

所以每次验证都要保存：节点 UID、Profile 摘要、探针版本、起止时间、原始证据 URI、结果。

## 4. 正向探针 + 最小反例

只有绿灯不能证明门禁生效——**检查脚本可能一直返回成功**。必须同时注入反例：

| 反例 | 期望 |
|---|---|
| 版本漂移（镜像/驱动与矩阵不符） | 节点进入 Quarantined |
| 资源数量不符（声明 8 卡实际 7 卡） | 拒绝发布 Profile |
| 设备不健康（Xid/ECC） | Allocatable 扣减 + 告警 |
| 几何漂移（拓扑变化导致 TP 无法落位） | 撤销对应 Profile |
| Rail / NIC 故障 | 移除网络 Profile，阻止跨机大任务 |
| 存储能力缺失 | 阻断 Admission |
| 制品 Digest 错误 | 隔离缓存条目 |
| 检测超时 | 记 SLOViolated，不静默通过 |

**每个反例都要断言具体的 phase 与 reason**，这样自动化与人员才能区分「修正输入 / 等待容量 / 补充证据 / 人工升级」，而不是对所有故障执行同一种重启。

## 5. 节点准入的失败语义

```text
配置漂移        → Quarantined（隔离，等修复或重建）
活动设备故障    → Draining（排空后下线）
硬网络能力丢失  → 撤销 Profile
存储能力缺失    → 阻断 Admission
制品摘要错误    → 隔离缓存条目
探测延迟越界    → SLOViolated（保留可用但记违约）
```

不可变版本矩阵是这一切的基础：**服务器 SKU、GPU/NIC 型号、固件、OS Digest、内核、驱动、Runtime、Operator、关键配置**共同构成一个矩阵；标签只是矩阵引用，**不是矩阵本身**。任何变量变化都要生成候选 Profile 并重新验证，否则同名标签在不同节点会代表不同组合。

## 6. 实验二：多租户批处理与配额平台

验收关注四件事：

1. **准入可解释**：每次拒绝都有 QuotaFeasible / PlacementFeasible / Provisionable 的分层原因；
2. **结算完整**：成功、失败、取消三条路径的预留都要结清；
3. **隔离有效**：不同租户的工作负载不能读到对方数据/设备；
4. **公平可观测**：加权公平的排程序列与交错证据可复现。

## 7. 实验三：声明式分布式训练平台

一条完整链路：

```text
提交（模板+队列）→ 准入 → Gang 放行 → 启动 → 运行 → 检查点 → 制品提交 → 成本归属
```

验收要点：Gang 语义（成员是否同时进入）、检查点可恢复、**制品提交与成功判定一致**（Manifest 写完才算成功）、成本能归到运行 UID。

## 8. 实验四：持续交付与安全发布

- 每份制品以 Digest 引用，别名只是入口；
- 门禁覆盖：评测、SBOM、漏洞、许可证、签名身份、策略版本；
- 灰度：按请求 ID 哈希分桶，候选与稳定版**并行 shadow 对比**；
- 回滚：切回旧 Digest，有证据；
- **拒绝必须发生在晋级或 Pod 创建之前**。

## 9. 实验五：SRE / 安全 / FinOps 控制台

三块看板，共享同一套身份：

- **SRE**：分层 SLO、错误预算余量、故障演练结果、自动修复动作与判据；
- **安全**：关键动作审计、策略版本、例外（范围/批准者/到期）；
- **FinOps**：请求/分配/有效 GPU 小时、归因覆盖率、总账恒等式、随机明细重算。

共同要求：每个数字都能下钻到**具体对象 + 时间窗口 + 版本**。

## 10. 实验六：企业级自助平台

### 10.1 权威状态划分

| 系统 | 权威状态 |
|---|---|
| 管理面 | 模板、策略、项目与集群清单 |
| 队列系统 | 准入与配额 |
| 工作集群控制器 | 实际执行状态 |
| GitOps | 环境期望状态 |
| 遥测与成本后端 | 运行证据 |

**门户只聚合这些来源，不凭本地缓存推断成功。** 跨系统状态必须携带 generation、UID、Reason 与时间，才能发现陈旧与冲突。

### 10.2 默认安全

普通用户只能提交业务参数、资源意图与批准模板；不能拿到 cluster-admin、工作集群凭据、任意 ServiceAccount 或策略豁免。数据驻留、GPU 类型、队列、环境批准、制品摘要一律**失败关闭**。管理员紧急权限也要短时、可审计、与日常操作分离。

### 10.3 升级与灾备

API 与模板变化要兼容存量请求；集群控制面失联要有明确降级；恢复后要对账「期望 vs 实际」。责任边界通过审计事件连接：平台团队负责产品合同与公共能力，业务团队负责工作负载与模型质量，安全/财务/SRE 分别负责门禁、成本规则与可靠性目标。

### 10.4 可量化目标

- 首次成功时间（提交 → 第一个可用结果）
- 自助完成率（无需人工介入的比例）
- 跨集群派发率（能力选择是否有效）
- 平台请求 SLO（控制面延迟）
- 单位工作负载成本（模板/集群对比）

指标必须带窗口、样本、来源与版本——**单次演示不能代替持续观测**。

## 11. 上线评审清单

- [ ] 每项能力都有输入/观察/成功/失败 Reason/Owner
- [ ] 关键能力有三视角证据，不只查一层
- [ ] 门禁同时有正向探针与最小反例
- [ ] 节点准入有稳定状态机与 Reason
- [ ] 版本矩阵以 Digest 固化，标签只作引用
- [ ] 配额/预留三路结算完整
- [ ] 发布以 Digest 绑定，拒绝发生在晋级前
- [ ] 门户不缓存推断成功，跨系统状态带 generation
- [ ] 成本与审计可反向追到租户与运行
- [ ] 升级与灾备有降级与对账流程

## 写在最后

这份清单其实就是「平台即产品」的最小实现：**能力要能被验收，验收要有反例，反例要能落到具体 Reason 与 Owner。**

第四期到此收尾。第五期转向数据与后训练：语料度量、数据湖与来源、清洗与去重、混合与课程、SFT/偏好/奖励、RL 与 RLVR、以及可恢复的后训练平台——把「模型能力从哪来」这条线补完。
