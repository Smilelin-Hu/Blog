# GitOps、环境晋级与渐进式发布

一个模型在预发环境已经通过评测，工程师把生产工作负载的镜像改成新摘要，几分钟后延迟上升，于是又把镜像改回旧版。用户流量似乎恢复了，但 Git 仍指向新版，模型注册别名已经前移，自动同步很快再次部署故障组合。这不是回滚操作不够快，而是发布过程没有唯一事实源，也没有把审批、容量、流量、指标和制品组织成同一条控制链。

![GitOps 与渐进式发布](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l24_01.png)

本文的核心判断是：生产发布不是一条命令，而是一个可审查、可重放、可暂停、可证伪的状态机。Git 保存经过批准的期望状态，Argo CD 把提交调和到集群，Argo Rollouts 把新旧版本的变化拆成 5%、25%、50% 和 100% 四个阶段，AnalysisRun 用延迟与质量证据决定继续或中止。发生退化时，流量先自动回到稳定版本，再通过 Git 反向提交和注册别名的并发安全更新收敛长期状态。

本文以 2026 年 8 月 22 日核验的官方一手资料为事实基线，采用当时可确认的 Argo CD v3.4.2 和 Argo Rollouts v1.9.1。知识讲解先于实验；模拟路径验证控制合同，不声称替代真实 Argo 控制器、真实 GPU 容量或真实流量。没有 Kubernetes 上下文时真实路径输出 SKIPPED，提供上下文但对象读取失败时输出 FAIL。

最容易发生的问题是状态来源互相覆盖。人工热修改变集群，Git 仍保留旧意图；流量已经回退，模型别名仍指向候选；PR 通过评测，生产却重新构建出不同字节。下一次 selfHeal、扩容或重启会把这些不一致重新暴露。修正方式不是关闭调和，而是让每个可变状态都有明确所有者，并规定紧急操作怎样回写长期事实源。

工程验证应记录输入、阈值、时间窗、第一失败 Reason 和恢复动作。重复同一反例必须得到稳定结果，修复输入后才允许重新推进。模拟只能证明确定性状态机，真实环境还要核对控制器版本、权限、路由、GPU 和端到端请求，两类证据不得互相冒充。

这项能力必须同时回答四个问题：期望由谁提交，控制器改变哪些对象，当前事实从哪里读取，失败后回到哪个稳定身份。落地时要把提交摘要、模型摘要、运行时摘要、目标环境、审批结果、容量结论和发布标识写进同一证据链。任何一步只保存可变名称，下一次调和、扩容或灾难恢复就无法证明重建的是同一服务。

反例是把工具动作当成能力完成：命令退出码为零、对象处于 Running 或界面显示 Synced，都不能单独证明用户正在获得正确版本和正确质量。系统需要先找出第一处不一致，再区分声明错误、控制器错误、基础设施不足、指标缺失和业务退化。证据缺失时应暂停或标记 SKIPPED，不能用一个总 PASS 覆盖未知事实。

验收要从两个方向闭环。正向从 PR 沿 Git Revision、Application、Rollout、AnalysisRun、路由和 Pod 到用户请求；反向从运行中的模型和镜像摘要追到批准提交。两条路径得到的 Revision 与 Digest 一致，负面输入又能在有害改变之前被拒绝，才说明控制合同真实存在。
