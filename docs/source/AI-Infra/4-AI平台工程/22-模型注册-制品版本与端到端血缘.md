# 模型注册、制品版本与端到端血缘

模型训练完成后，把一个对象存储 URI 写进页面，并不等于模型已经具备可交付身份。URI 可能指向可覆盖路径，权重与分词器可能来自不同版本，运行时镜像可能仍是可变标签，评估报告也可能无法证明对应这份制品。生产故障发生时，如果平台只能看到“模型版本二”，却不能回答它由哪份数据、哪次训练、哪个代码提交、哪套评估和谁的审批产生，注册表就没有完成治理职责。

![模型注册与端到端血缘](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l22_01.png)

本文以 2026 年 8 月 22 日核验的官方一手资料为事实基线。MLflow 采用当时官方最新稳定版 3.13.0 的文档语义；Kubeflow 部分采用已更名为 Kubeflow Hub 的官方文档、Model Registry v1alpha3 REST 说明和 Kubeflow SDK 0.4.0 接口；制品部分采用 OCI Image Specification 与 Distribution Specification 1.1.1。知识讲解先于实验，所有产品能力都与模拟证据分开陈述。

本文的目标不是演示一次点击注册，而是建立可审计的模型生命周期控制面：不可变 Model Version 与 Artifact Digest 保存事实，可变 Alias 承载候选、生产与回滚决策，类型化血缘连接数据、代码、作业、运行时、评估、审批和制品，发布门禁在改变 Champion 之前验证整套证据。

## 1. 模型注册不是文件上传器

模型注册表首先索引模型身份、版本、元数据与晋级关系，模型字节通常仍在对象存储或制品仓库中。Kubeflow 官方 SDK 文档明确说明其注册表保存元数据，制品保留在原始 S3 或 GCS 位置。

工程上要把这段概念拆成可验证合同。在平台边界上分别定义元数据事务与对象字节事务，以摘要和位置把两者连接，任何一侧成功都不能自动证明另一侧完整。每个写入动作都应明确主体、前置条件、幂等键和审计事件，每个读取动作都要说明解析的是固定身份还是可变选择。这样故障发生时，团队可以区分元数据错误、制品错误、权限错误和发布决策错误，不会把所有问题都归结为“模型平台异常”。

平台实现还要考虑时间与并发。训练流水线、评估服务、审批门户和部署控制器可能同时读写同一模型对象，因此任何会改变生产选择的字段都不能依赖最后写入者获胜。身份性字段一旦发布就锁定，可变字段用修订号、条件更新或单一控制器治理，并把前后值写入追加事件。

反例是：只检查注册 API 返回成功就发布，会让已经删除、被覆盖或无权读取的 URI 进入生产。这类做法在规模较小时往往看似省事，因为操作者可以靠记忆补足上下文；当模型、团队和环境增多后，隐含假设会变成不可追踪的生产风险。验收必须同时检查正常路径、拒绝路径和恢复路径，缺少真实环境条件时明确标记 SKIPPED。

## 2. 实验跟踪的职责

实验跟踪记录 Run、参数、指标、日志和执行上下文，主要回答一次尝试如何运行以及结果如何。它提供候选产生过程，却不自动等价于可部署模型目录。

从控制面角度看，把 Run 标识、Logged Model 标识与评估证据写入模型版本来源字段，保留从注册版本返回实验的稳定边。这不是单纯的数据建模问题，还涉及谁有权创建事实、谁有权改变指针、谁负责验证外部字节以及失败后由谁对账。平台应为每一种对象和关系设置 Schema、访问控制、状态转换和保留期限，避免同一个自由字段承担多种语义。

从数据面角度看，注册记录中的名称与 URI 都不是内容本身。消费者在部署、回滚和审计时要解析到固定版本与摘要，再验证实际读取字节。若产品只展示当前状态而不保留产生过程，用户得到的是方便的目录，却得不到可重现、可比较和可追责的证据链。

需要专门验证的反例是：将最优指标 Run 直接视作生产版本，会跳过制品封装、审批、兼容性和回滚合同。验收不以页面上是否出现记录为终点，而以固定身份可验证、血缘必需节点齐全、变更事件可回放、并发冲突被拒绝和旧版本可恢复为准。任何一项无法证明，都不应把版本推进到生产别名。

## 3. 制品存储的职责

制品存储负责保存权重、配置、分词器、报告和其他大对象，关键能力是字节持久性、内容摘要、访问控制与生命周期。

把它落成平台能力时，使用内容摘要、对象版本和不可变前缀定位实际字节，注册记录仅保存可验证引用，读取端必须重新校验摘要。控制器先读取当前状态与固定证据，再根据版本化策略做决定，最后通过带前置条件的写入提交结果。若中间外部依赖失败，状态应停留在可重试或需人工处理的位置，不能用一个模糊成功标志覆盖部分完成。

可观测性也必须围绕对象关系设计。日志要携带模型、版本、摘要、作业和请求标识；指标要区分注册延迟、制品校验失败、Alias 冲突、血缘缺失与审批拒绝；审计事件要能还原前后状态。这样团队才能判断是系统不可用、策略主动拒绝还是输入证据不合格。

典型失败方式是：只用 latest 路径或可覆写对象键，历史注册记录会在内容变化后失去真实性。反例测试必须稳定地产生预期拒绝原因，不能只得到笼统异常。通过这种方式，实验把抽象原则转换为可执行合同；真实环境仍需以官方 API、实际对象存储和目标身份重新验收，不能由模拟结果代替。

## 4. 模型注册表的职责

注册表组织 Registered Model、Model Version、标签、别名和描述，使团队能发现、比较、治理和选择具体版本。

工程上要把这段概念拆成可验证合同。把同一业务能力归入稳定模型名，每次可复现制品生成一个新版本；不允许在原版本上替换字节。每个写入动作都应明确主体、前置条件、幂等键和审计事件，每个读取动作都要说明解析的是固定身份还是可变选择。这样故障发生时，团队可以区分元数据错误、制品错误、权限错误和发布决策错误，不会把所有问题都归结为“模型平台异常”。

反例是：把模型名同时当环境名、团队名和实现名，名称变化会破坏引用，权限与晋级也难以表达。这类做法在规模较小时往往看似省事，因为操作者可以靠记忆补足上下文；当模型、团队和环境增多后，隐含假设会变成不可追踪的生产风险。验收必须同时检查正常路径、拒绝路径和恢复路径，缺少真实环境条件时明确标记 SKIPPED。

## 5. 元数据存储的职责

元数据存储保存执行、制品、数据和关系图，侧重血缘与查询。注册表可以消费其结果，但不必吞并所有训练事件。

从控制面角度看，以稳定标识连接数据版本、代码提交、训练作业、运行时、评估、审批和模型制品，控制每类节点的 Schema。这不是单纯的数据建模问题，还涉及谁有权创建事实、谁有权改变指针、谁负责验证外部字节以及失败后由谁对账。平台应为每一种对象和关系设置 Schema、访问控制、状态转换和保留期限，避免同一个自由字段承担多种语义。

需要专门验证的反例是：把所有事实塞入一段自由文本，表面信息丰富却无法做反向查询、完整性校验和自动门禁。验收不以页面上是否出现记录为终点，而以固定身份可验证、血缘必需节点齐全、变更事件可回放、并发冲突被拒绝和旧版本可恢复为准。任何一项无法证明，都不应把版本推进到生产别名。

## 6. 四类系统的组合边界

实验跟踪、制品存储、模型注册表与元数据存储可以由一个产品提供，也可以是多个服务；逻辑职责仍应分开。

把它落成平台能力时，为每条跨系统边定义所有者、写入顺序、幂等键、失败补偿和对账任务，避免依赖某个 UI 中的偶然跳转。控制器先读取当前状态与固定证据，再根据版本化策略做决定，最后通过带前置条件的写入提交结果。若中间外部依赖失败，状态应停留在可重试或需人工处理的位置，不能用一个模糊成功标志覆盖部分完成。

典型失败方式是：采购一个全栈工具后取消边界设计，故障时仍会遇到数据库成功而对象失败、版本存在而血缘缺失。反例测试必须稳定地产生预期拒绝原因，不能只得到笼统异常。通过这种方式，实验把抽象原则转换为可执行合同；真实环境仍需以官方 API、实际对象存储和目标身份重新验收，不能由模拟结果代替。

## 7. Registered Model

MLflow 官方定义中，Registered Model 拥有唯一名称，并包含版本、别名、标签及其他元数据；它表达一个长期业务模型集合。

工程上要把这段概念拆成可验证合同。名称应稳定、可授权并避免把临时阶段写死；描述中记录用途、输入输出合同、所有者和风险等级。每个写入动作都应明确主体、前置条件、幂等键和审计事件，每个读取动作都要说明解析的是固定身份还是可变选择。这样故障发生时，团队可以区分元数据错误、制品错误、权限错误和发布决策错误，不会把所有问题都归结为“模型平台异常”。

反例是：每次训练都创建新 Registered Model，会失去版本序列、别名语义和跨版本比较能力。这类做法在规模较小时往往看似省事，因为操作者可以靠记忆补足上下文；当模型、团队和环境增多后，隐含假设会变成不可追踪的生产风险。验收必须同时检查正常路径、拒绝路径和恢复路径，缺少真实环境条件时明确标记 SKIPPED。

## 8. Model Version

Model Version 是 Registered Model 下的一个具体版本。MLflow 为同名注册模型新增版本时递增编号，Kubeflow 则允许按模型名与版本检索。

从控制面角度看，版本记录一旦发布应视作不可变快照，允许补充非身份性注释，但不能更换其制品摘要、训练来源或关键合同。这不是单纯的数据建模问题，还涉及谁有权创建事实、谁有权改变指针、谁负责验证外部字节以及失败后由谁对账。平台应为每一种对象和关系设置 Schema、访问控制、状态转换和保留期限，避免同一个自由字段承担多种语义。

需要专门验证的反例是：把版本号当可覆盖目录名，回滚到旧编号时得到的却可能是新字节。验收不以页面上是否出现记录为终点，而以固定身份可验证、血缘必需节点齐全、变更事件可回放、并发冲突被拒绝和旧版本可恢复为准。任何一项无法证明，都不应把版本推进到生产别名。

## 9. Logged Model 与注册版本

MLflow 3 把模型提升为一等 Logged Model 实体，模型可不依赖活动 Run 直接记录；注册版本则提供共享目录和生命周期治理。

把它落成平台能力时，显式保存 Logged Model 到 Registered Model Version 的映射，注册动作要有幂等键，重复执行不能产生无意的新版本。控制器先读取当前状态与固定证据，再根据版本化策略做决定，最后通过带前置条件的写入提交结果。若中间外部依赖失败，状态应停留在可重试或需人工处理的位置，不能用一个模糊成功标志覆盖部分完成。

典型失败方式是：只存模型 URI 字符串而不存 Logged Model 标识，会让 MLflow 3 的模型级指标、参数与来源难以关联。反例测试必须稳定地产生预期拒绝原因，不能只得到笼统异常。通过这种方式，实验把抽象原则转换为可执行合同；真实环境仍需以官方 API、实际对象存储和目标身份重新验收，不能由模拟结果代替。

## 10. 模型标签

标签是键值元数据，可描述任务、风险等级、验证状态、硬件兼容性或数据地域。标签适合查询和策略输入，但本质上可变。

工程上要把这段概念拆成可验证合同。定义受控键名、值域、写权限和变更事件；身份性事实使用不可变字段，不能靠任意标签替代。每个写入动作都应明确主体、前置条件、幂等键和审计事件，每个读取动作都要说明解析的是固定身份还是可变选择。这样故障发生时，团队可以区分元数据错误、制品错误、权限错误和发布决策错误，不会把所有问题都归结为“模型平台异常”。

反例是：允许任何人写 validation_status=passed，会让展示信息越权成为发布凭证。这类做法在规模较小时往往看似省事，因为操作者可以靠记忆补足上下文；当模型、团队和环境增多后，隐含假设会变成不可追踪的生产风险。验收必须同时检查正常路径、拒绝路径和恢复路径，缺少真实环境条件时明确标记 SKIPPED。

## 11. 模型别名

MLflow 官方将 Alias 定义为指向特定模型版本的可变命名引用，可通过 models:/模型名@champion 加载，重指后调用方获得新版本。

从控制面角度看，把别名更新设计为受门禁、审计和并发控制的控制面操作，消费方还要决定何时解析与缓存。这不是单纯的数据建模问题，还涉及谁有权创建事实、谁有权改变指针、谁负责验证外部字节以及失败后由谁对账。平台应为每一种对象和关系设置 Schema、访问控制、状态转换和保留期限，避免同一个自由字段承担多种语义。

需要专门验证的反例是：把 champion 当成不可变版本号写入审计报告，会掩盖它随后已经指向其他版本的事实。验收不以页面上是否出现记录为终点，而以固定身份可验证、血缘必需节点齐全、变更事件可回放、并发冲突被拒绝和旧版本可恢复为准。任何一项无法证明，都不应把版本推进到生产别名。

## 12. 阶段语义迁移

MLflow 官方工作流建议用版本标签与别名替代旧阶段模型，以便表达多别名、独立环境和更灵活的发布流程。

把它落成平台能力时，新平台直接围绕 Alias 与 Tag 建模，旧平台迁移时先映射现有阶段，再逐步改写加载 URI 与权限。控制器先读取当前状态与固定证据，再根据版本化策略做决定，最后通过带前置条件的写入提交结果。若中间外部依赖失败，状态应停留在可重试或需人工处理的位置，不能用一个模糊成功标志覆盖部分完成。

典型失败方式是：同时让 Stage 和 Alias 都能独立决定生产版本，会形成两个冲突的真相源。反例测试必须稳定地产生预期拒绝原因，不能只得到笼统异常。通过这种方式，实验把抽象原则转换为可执行合同；真实环境仍需以官方 API、实际对象存储和目标身份重新验收，不能由模拟结果代替。

## 13. 不可变版本引用

内容摘要或固定版本用于证明具体对象身份，适合部署清单、审计、回放和供应链验证。

工程上要把这段概念拆成可验证合同。发布控制器应把别名解析为版本与摘要，将解析结果写入部署修订，然后以摘要拉取。每个写入动作都应明确主体、前置条件、幂等键和审计事件，每个读取动作都要说明解析的是固定身份还是可变选择。这样故障发生时，团队可以区分元数据错误、制品错误、权限错误和发布决策错误，不会把所有问题都归结为“模型平台异常”。

反例是：运行中每次请求都重新解析可变别名，会让同一 Replica 集合在无发布事件时得到不同字节。这类做法在规模较小时往往看似省事，因为操作者可以靠记忆补足上下文；当模型、团队和环境增多后，隐含假设会变成不可追踪的生产风险。验收必须同时检查正常路径、拒绝路径和恢复路径，缺少真实环境条件时明确标记 SKIPPED。

## 14. 可变业务引用

Champion、Challenger、Candidate 和环境 Alias 把人可读的角色映射到具体版本，降低业务流程与数字版本的耦合。

从控制面角度看，将别名视为小型状态机，其写入必须携带期望旧值或修订号，并记录操作者、原因、证据和前后目标。这不是单纯的数据建模问题，还涉及谁有权创建事实、谁有权改变指针、谁负责验证外部字节以及失败后由谁对账。平台应为每一种对象和关系设置 Schema、访问控制、状态转换和保留期限，避免同一个自由字段承担多种语义。

需要专门验证的反例是：简单的读取后写入在两个发布者并发时会丢失更新，最后指向谁取决于时序。验收不以页面上是否出现记录为终点，而以固定身份可验证、血缘必需节点齐全、变更事件可回放、并发冲突被拒绝和旧版本可恢复为准。任何一项无法证明，都不应把版本推进到生产别名。

## 15. Champion 语义

Champion 表示当前获准承担主要生产职责的版本，而不是全局上任何指标最高的模型。

把它落成平台能力时，门禁应同时检查评估策略、审批、制品完整性、运行时兼容和环境约束，再用原子更新改变指针。控制器先读取当前状态与固定证据，再根据版本化策略做决定，最后通过带前置条件的写入提交结果。若中间外部依赖失败，状态应停留在可重试或需人工处理的位置，不能用一个模糊成功标志覆盖部分完成。

典型失败方式是：只按单一离线分数自动设置 Champion，可能绕过延迟、资源、安全或分组退化约束。反例测试必须稳定地产生预期拒绝原因，不能只得到笼统异常。通过这种方式，实验把抽象原则转换为可执行合同；真实环境仍需以官方 API、实际对象存储和目标身份重新验收，不能由模拟结果代替。

## 16. Challenger 语义

Challenger 表达与 Champion 比较的候选版本，可用于影子、少量流量或离线复核；它不天然拥有生产权限。

工程上要把这段概念拆成可验证合同。允许同一版本有多个角色别名，但每个别名的消费者、流量语义和撤销条件要明确。每个写入动作都应明确主体、前置条件、幂等键和审计事件，每个读取动作都要说明解析的是固定身份还是可变选择。这样故障发生时，团队可以区分元数据错误、制品错误、权限错误和发布决策错误，不会把所有问题都归结为“模型平台异常”。

反例是：把 Challenger 直接暴露为公共默认 URI，调用者可能在未意识到实验状态时加载它。这类做法在规模较小时往往看似省事，因为操作者可以靠记忆补足上下文；当模型、团队和环境增多后，隐含假设会变成不可追踪的生产风险。验收必须同时检查正常路径、拒绝路径和恢复路径，缺少真实环境条件时明确标记 SKIPPED。

## 17. 环境别名

环境 Alias 可表达 dev、staging、prod 中的选择，但成熟平台常用独立注册模型或独立注册表配合访问控制。

从控制面角度看，跨环境晋级应复制或提升固定摘要，再由目标环境受权主体设置本地别名，不直接共享无限写权限。这不是单纯的数据建模问题，还涉及谁有权创建事实、谁有权改变指针、谁负责验证外部字节以及失败后由谁对账。平台应为每一种对象和关系设置 Schema、访问控制、状态转换和保留期限，避免同一个自由字段承担多种语义。

需要专门验证的反例是：从开发环境直接修改生产别名，会破坏职责分离与变更窗口。验收不以页面上是否出现记录为终点，而以固定身份可验证、血缘必需节点齐全、变更事件可回放、并发冲突被拒绝和旧版本可恢复为准。任何一项无法证明，都不应把版本推进到生产别名。

## 18. 回滚指针

回滚不是重新训练旧模型，而是把可变选择恢复到一个已验证且仍可读取的固定版本。

把它落成平台能力时，保存别名变更历史和上一稳定版本，回滚前重新检查制品存在、密钥、运行时与数据合同，随后原子重指。控制器先读取当前状态与固定证据，再根据版本化策略做决定，最后通过带前置条件的写入提交结果。若中间外部依赖失败，状态应停留在可重试或需人工处理的位置，不能用一个模糊成功标志覆盖部分完成。

典型失败方式是：假设旧版本永远可用而提前清理镜像、权重或依赖，事故时会出现有编号但无法部署。反例测试必须稳定地产生预期拒绝原因，不能只得到笼统异常。通过这种方式，实验把抽象原则转换为可执行合同；真实环境仍需以官方 API、实际对象存储和目标身份重新验收，不能由模拟结果代替。

## 19. 模型包的权重边界

权重是模型行为的核心字节，但单独的权重文件通常不足以恢复可运行模型。

工程上要把这段概念拆成可验证合同。权重必须有内容摘要、分片清单、总字节数、格式、张量精度和必要的索引文件，下载后逐项校验。每个写入动作都应明确主体、前置条件、幂等键和审计事件，每个读取动作都要说明解析的是固定身份还是可变选择。这样故障发生时，团队可以区分元数据错误、制品错误、权限错误和发布决策错误，不会把所有问题都归结为“模型平台异常”。

反例是：只比较目录名或文件数量不能发现单个分片被替换、截断或跨版本混入。这类做法在规模较小时往往看似省事，因为操作者可以靠记忆补足上下文；当模型、团队和环境增多后，隐含假设会变成不可追踪的生产风险。验收必须同时检查正常路径、拒绝路径和恢复路径，缺少真实环境条件时明确标记 SKIPPED。

## 20. 分词器与配置

大语言模型的分词器、特殊 Token、架构配置、生成配置会改变输入编码和输出行为，应与权重共同版本化。

从控制面角度看，把配置与分词器纳入模型包清单或 OCI 层，并分别记录媒体类型与摘要，推理加载前校验组合兼容性。这不是单纯的数据建模问题，还涉及谁有权创建事实、谁有权改变指针、谁负责验证外部字节以及失败后由谁对账。平台应为每一种对象和关系设置 Schema、访问控制、状态转换和保留期限，避免同一个自由字段承担多种语义。

需要专门验证的反例是：权重固定却从公共仓库读取 latest 分词器，可能造成词表尺寸和特殊 Token 不一致。验收不以页面上是否出现记录为终点，而以固定身份可验证、血缘必需节点齐全、变更事件可回放、并发冲突被拒绝和旧版本可恢复为准。任何一项无法证明，都不应把版本推进到生产别名。

## 21. 运行时与镜像

模型格式并不保证任意 Serving Runtime 都能正确加载；CUDA、框架、算子、驱动能力和启动参数共同形成运行合同。

把它落成平台能力时，以镜像 Digest 而非 Tag 记录运行时，附加支持的加速器、计算能力、精度、并行策略和服务协议。控制器先读取当前状态与固定证据，再根据版本化策略做决定，最后通过带前置条件的写入提交结果。若中间外部依赖失败，状态应停留在可重试或需人工处理的位置，不能用一个模糊成功标志覆盖部分完成。

典型失败方式是：registry/runtime:latest 即使名字不变也可指向新 Manifest，旧模型的回放因此失去确定性。反例测试必须稳定地产生预期拒绝原因，不能只得到笼统异常。通过这种方式，实验把抽象原则转换为可执行合同；真实环境仍需以官方 API、实际对象存储和目标身份重新验收，不能由模拟结果代替。

## 22. 许可证与模型卡

许可证、使用限制、来源说明和模型卡决定模型是否可以在某环境与用途部署，属于模型包治理边界。

工程上要把这段概念拆成可验证合同。注册门禁检查许可证标识、文本摘要、限制标签和责任人；模型卡引用要固定版本并可随版本审计。每个写入动作都应明确主体、前置条件、幂等键和审计事件，每个读取动作都要说明解析的是固定身份还是可变选择。这样故障发生时，团队可以区分元数据错误、制品错误、权限错误和发布决策错误，不会把所有问题都归结为“模型平台异常”。

反例是：把许可证只放在外部网页，网页变化或失效后无法证明发布时遵循了什么条件。这类做法在规模较小时往往看似省事，因为操作者可以靠记忆补足上下文；当模型、团队和环境增多后，隐含假设会变成不可追踪的生产风险。验收必须同时检查正常路径、拒绝路径和恢复路径，缺少真实环境条件时明确标记 SKIPPED。

## 23. 签名与输入输出 Schema

输入列、张量形状、数据类型、必填字段与输出含义属于服务兼容合同。MLflow 模型可包含 Signature，目标注册后端也可能强制要求。

从控制面角度看，发布前用真实样例和反例验证 Signature，部署控制器比较新旧版本 Schema 是否向后兼容。这不是单纯的数据建模问题，还涉及谁有权创建事实、谁有权改变指针、谁负责验证外部字节以及失败后由谁对账。平台应为每一种对象和关系设置 Schema、访问控制、状态转换和保留期限，避免同一个自由字段承担多种语义。

## 24. SBOM 与依赖证据

模型包还应关联软件物料清单、漏洞扫描、构建来源和签名，因为风险常来自运行时与依赖而非权重。
