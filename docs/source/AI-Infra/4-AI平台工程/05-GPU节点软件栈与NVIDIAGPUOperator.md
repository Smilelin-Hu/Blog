# GPU 节点软件栈与 NVIDIA GPU Operator

一台新 GPU 服务器已经加入 Kubernetes，`nvidia-smi` 在宿主机上也能输出型号和显存。训练 Pod 提交后却一直 Pending，节点的 `Allocatable` 里没有 `nvidia.com/gpu`。另一台节点能够分配 GPU，容器启动后却看不到 `/dev/nvidia0`。还有一批节点升级内核后突然失去 GPU，平台团队只看到 GPU Operator 的多个 Pod 在反复重启。

![GPU 节点软件栈](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l05_01.png)

这些故障不能统一归结为“驱动有问题”。GPU 成为 Kubernetes 可调度资源，要连续穿过内核驱动、用户态库、容器运行时、设备发现、kubelet 设备注册、资源发布、容器设备注入、健康监控与工作负载验证。任何一层没有兑现，上一层的“正常”都不能证明下一层可用。

本文建立 GPU 节点的软件栈与运维模型，并用 NVIDIA GPU Operator 说明 Operator 如何把多个节点级组件组织成声明式系统。重点不在背诵 Helm 参数，而在回答四个工程问题：平台究竟在管理哪些状态；每一层用什么证据判定；升级怎样避免同时击穿整个资源池；出现故障时怎样沿依赖链定位，而不是重启所有 DaemonSet。

先给出本文最重要的结论：GPU 节点 Ready、宿主机 `nvidia-smi` 成功、Device Plugin Running、节点出现 `nvidia.com/gpu`、GPU 容器完成一次计算，这五个结论彼此不等价。生产平台至少应把它们显示为五个独立检查点。

实验有两条路径。确定性模拟会让两个 GPU 节点依次经过驱动、Toolkit、Device Plugin、GFD、DCGM、Exporter 与 Validator，并注入 nouveau 冲突、内核头文件缺失、Secure Boot 拒绝签名、运行时未配置、设备资源未发布和验证工作负载失败。真实路径只做只读集群检查；没有真实 GPU 集群 context 时必须明确记为 SKIPPED，不能用模拟结果冒充硬件验收。

## 1. “GPU 节点可用”是一组条件，不是一个布尔值

CPU 节点加入集群后，kubelet 通常可以直接发布处理器和内存。GPU 则是厂商设备，内核需要识别 PCIe 设备并加载匹配模块，容器运行时需要把设备文件和用户态库注入容器，kubelet 还需要一个设备管理组件把可分配数量公开给调度器。因此，服务器有 GPU 不等于 Kubernetes 有 GPU 资源。

平台常把节点健康压成绿色或红色。绿色掩盖部分降级，红色又无法说明责任边界。更合适的状态模型是按依赖链输出 Condition，例如 HardwareDetected、DriverReady、RuntimeReady、ResourceAdvertised、TelemetryReady 和 WorkloadValidated。每个 Condition 都带 Reason、最近转换时间和证据来源。

如果 PCIe 枚举根本没有设备，继续排查容器运行时没有意义；如果驱动模块没有加载，Device Plugin 日志中的 NVML 初始化失败只是后果；如果资源已经发布但验证容器失败，则调度链正常，问题可能在设备注入、用户态兼容或硬件健康。依赖顺序决定排障顺序。

### 1.1 硬件存在、内核可控、容器可用是三件事

硬件存在通常由 PCIe 枚举、带外管理或云实例规格确认。它回答的是“操作系统能否看到这个设备”。设备可能存在，却因 BIOS 设置、IOMMU、PCIe 链路、虚拟化直通或硬件故障无法被正确驱动。

内核可控要求 NVIDIA 内核模块成功构建或安装、加载并绑定设备，同时创建设备节点。`nvidia-smi` 通过管理库与内核驱动通信，因此它成功是很强的驱动证据，却仍只发生在宿主机环境。它没有证明某个 OCI 容器能得到设备文件、驱动库和权限。

容器可用要求运行时在创建容器时解析 GPU 请求，把选定设备和所需库暴露给容器。容器里的 CUDA Toolkit 版本与宿主驱动存在兼容边界。镜像可以自带 CUDA 用户态运行库，但内核驱动必须来自宿主机；不能指望在普通容器中加载另一个不匹配的内核驱动。

Kubernetes 可调度还要增加第四层：Device Plugin 或相应设备资源驱动需要向 kubelet 注册资源，kubelet 把 Capacity 与 Allocatable 写入 Node Status，调度器再根据 Pod 请求完成装箱。宿主机计算成功但 Node Status 没有资源时，训练仍会 Pending。

### 1.2 节点 Ready 只说明 kubelet 主链路，不说明加速器就绪

Node Condition 中的 Ready 主要反映 kubelet 是否健康上报以及节点基础运行条件。GPU 驱动损坏时，CPU 容器可能继续运行，kubelet 也能保持 Ready。若平台只把 Node Ready 作为 GPU 池准入依据，新的训练会被调度到功能不完整的节点。

反过来，GPU Operator 的组件全是 Running 也不等于节点通过验收。Pod Running 只表示容器进程存在；某个组件可能在循环重试，Exporter 可能无法读取指标，Validator 可能尚未完成计算验证。需要读取组件自身状态、日志、节点资源和实际工作负载结果。

生产系统可以设置独立的 GPUReady 标签或 Condition，并由受控控制器维护。调度入口只允许通过验收的节点进入可用池；驱动升级中的节点、硬件告警节点和验证失败节点应先被隔离。这个标签不能由普通租户或节点上的不可信进程随意修改，否则隔离边界会失效。

### 1.3 可用性要从用户请求反向定义

用户请求一张指定类别 GPU，真正需要的是 Pod 按时获得一台符合属性的健康设备，框架能够初始化 CUDA，数据路径和互联满足任务要求，并持续运行到结果完成。节点层的每个检查都应服务于这条用户链路。

因此，平台 SLI 不能只有“GPU 节点在线率”。还应测量资源可发布率、从请求到绑定时间、从绑定到 GPU 初始化时间、验证任务成功率、因设备健康导致的重试率和升级期间可用容量。单节点绿灯很多，队列仍可能长时间无容量。

验收也不应只在安装当天执行。内核更新、容器运行时更新、驱动升级、GPU Operator 升级、节点镜像重建和云厂商维护都可能改变链路。持续验证比一次性脚本更接近平台工程。

## 2. GPU Operator 管理的是一张依赖图

GPU Operator 使用 Kubernetes Operator 模式声明并协调 GPU 节点所需组件。管理员安装 Operator 并提交 ClusterPolicy 等配置，控制器根据节点能力与策略创建驱动、Container Toolkit、Device Plugin、GPU Feature Discovery、DCGM、Exporter 和 Validator 等工作负载。

它的价值不是把几个 YAML 放在一个 Helm Chart 里，而是持续观察期望状态和实际状态：新节点出现时补齐组件，节点不需要某个组件时避免错误安装，配置改变时滚动协调，组件失败时通过状态和事件暴露偏差。

Operator 也不是魔法兼容层。主机操作系统、内核、GPU 型号、容器运行时和 Kubernetes 版本必须落在支持矩阵内。网络、镜像仓库、代理、Secure Boot 密钥、内核头文件和云厂商节点镜像仍是平台责任。安装命令执行成功，只说明对象被 API 接受。

### 2.1 ClusterPolicy 描述期望，Operand 执行节点任务

Operator 本身是控制面控制器。它读取 ClusterPolicy 一类自定义资源，根据字段决定哪些 Operand 启用、使用什么镜像与参数、选择哪些节点。真正接触主机驱动、运行时配置与设备的通常是节点上的 DaemonSet Pod 或相关控制器。

这种分工非常重要。Operator Deployment Running 只能证明协调进程存在；Driver DaemonSet 没有覆盖目标节点时，驱动不会自动出现；Toolkit Pod 成功但运行时配置没有生效时，GPU 容器仍无法启动；Device Plugin 没有向 kubelet 注册时，调度器仍看不到资源。

排障时应先查看 ClusterPolicy 的状态与 Conditions，再查看目标 Operand 工作负载的 Desired、Current、Ready、Unavailable 数量，最后落到特定节点 Pod 日志和宿主状态。直接从一条业务 Pod 错误跳到重装 Operator，会丢失故障层次。

一个集群通常只有一套全局 GPU 策略，但节点池可能不同：部分节点预装驱动，部分由 Operator 管理；不同代际 GPU 可能要求不同分支；测试池需要先升级。若单一 ClusterPolicy 无法安全表达差异，应使用受支持的 Driver CRD 或分池、分集群方案，而不是在同一节点上让两套管理器竞争。

### 2.2 DaemonSet 为什么适合节点组件

驱动、Toolkit、Device Plugin 与监控代理的职责和物理节点绑定。DaemonSet 会为每个满足选择条件的节点创建一个 Pod，新节点加入时自动补齐，节点离开时对象随之消失。这比管理员逐台 SSH 安装更容易审计期望覆盖范围。

但 DaemonSet 的“一节点一份”不等于同时更新安全。默认滚动策略、最大不可用数、节点数量和工作负载占用共同决定升级冲击。GPU 节点价值高、单节点设备多，一次不可用一台可能就损失八张卡；一次按百分比更新可能让大池瞬间失去大量容量。

DaemonSet Pod 往往需要特权、HostPath、主机 PID 或访问容器运行时 Socket。这些权限来自任务本身，也扩大供应链风险。平台要锁定镜像来源与摘要、限制谁能修改 ClusterPolicy、审计主机挂载，并让安全团队理解每个 Operand 为什么需要权限。

节点选择同样要谨慎。GPU 发现标签尚未建立时，驱动组件如何找到目标节点；CPU 节点是否被误装；带有虚拟 GPU 或直通设备的节点是否走不同路径，都需要预先设计。常见做法是结合 NFD 发现、云节点池标签和 Operator 自己的标签完成引导。

### 2.3 状态聚合不能替代底层证据

Operator 会把多个组件状态聚合成 Ready 或 Error 一类高层结论，适合总览，却可能滞后或丢失节点差异。一百台节点中九十九台完成，剩下一台因内核头文件缺失失败，集群级状态不能告诉用户他的 Pod 为什么恰好落在问题节点。

平台应保留三层证据：策略级 Condition 用于判断整体协调；DaemonSet 或 Deployment 状态用于判断覆盖；节点级检查用于判断具体硬件。告警需要带 node、pool、GPU model、driver branch、kernel、operator version 和最近变更批次。

不要把标签当作永远真实的数据库。GFD 生成的标签来自当前发现结果，设备不可访问或组件停机后，旧标签可能暂时残留。资源数量来自 kubelet 状态，也可能在插件重启窗口内变化。重要准入需要结合新鲜度与主动验证。

### 2.4 Operator 的边界要写进平台契约

GPU Operator 能够管理容器化驱动生命周期，但不会替平台决定何时驱逐用户训练、怎样保存检查点、怎样扩容替代容量，也不会自动证明某个业务框架在特定 NCCL 拓扑上性能正常。它提供组件与状态，不提供完整产品承诺。

对于宿主机预装驱动的模式，Operator 通常只管理其余组件，驱动的升级、回滚和节点镜像一致性由镜像流水线或云节点服务承担。若责任边界未写清，平台团队会以为 Operator 负责，节点团队又以为 Helm 负责，故障窗口内无人拥有驱动。

对 MIG、时间切片、MPS、RDMA 和 GDS 等高级能力，也需要额外策略、兼容矩阵和验收。它们不应因为 Operator 有相应开关就默认成为已支持产品。这里只建立基础整卡节点链路，高级资源形态在后续篇目单独处理。

## 3. NVIDIA 驱动把内核与硬件连接起来

NVIDIA 驱动包含内核模块与用户态组件。内核模块需要与正在运行的内核及相关配置兼容，管理 GPU 设备、内存和命令提交；用户态的管理库与计算接口通过设备文件调用驱动。容器中的 CUDA 应用最终仍依赖宿主机这套内核能力。

这解释了为什么“镜像里安装 CUDA”不能修复宿主驱动。CUDA 镜像提供编译器、运行库或工具，不能在无权限的普通容器里替换主机内核模块。驱动失败时反复改业务镜像，只会制造更多变量。

### 3.1 内核模块必须匹配当前内核环境

驱动模块可能在节点上预编译，也可能安装时针对当前内核构建。构建路径依赖正确的内核头文件、编译器与工具链。节点自动升级到新内核后重启，如果对应模块没有准备好，原本正常的 GPU 节点会在重启后失效。

版本号相同也不总能消除差异。发行版补丁、内核配置、实时内核、云厂商定制内核和安全策略都会影响模块。支持矩阵是生产前提，实验集群的“碰巧能加载”不能取代厂商支持组合。

平台应记录每个节点的 OS 镜像、内核版本、驱动分支、模块类型与构建来源，并把组合当作不可随意拆开的节点基线。扩容新节点时先做基线验证，再进入资源池；不要让用户任务成为第一批测试。

预编译驱动容器可以避免每台节点安装时下载头文件并本地编译，降低编译峰值和网络依赖，也让已验证的内核与驱动组合更明确。但它要求所用内核拥有对应预编译产物；自定义内核或版本漂移仍可能没有匹配镜像。

### 3.2 nouveau 冲突发生在内核控制权层

Linux 发行版可能加载开源 nouveau 驱动并绑定 NVIDIA 设备。专有或 NVIDIA 开放内核模块随后尝试接管同一设备时会失败。此时 Driver Pod 日志、内核日志和已加载模块能够指出冲突。

解决方案通常是在节点镜像或启动配置中禁用冲突模块，重建 initramfs 并重启，而不是在业务 Pod 里删除文件。是否必须重启取决于模块占用与系统状态；生产节点应先停止工作负载、隔离并按变更流程处理。

实验中的 `nouveau-conflict` 故障被设计为在 Driver 阶段停止，Reason 为 NouveauLoaded。后续 Toolkit、Device Plugin 与 Validator 都不再假装执行。这种因果短路比同时产生六个红灯更适合排障，因为它明确指出第一个未兑现前置条件。

### 3.3 Secure Boot 要求模块可信

启用 Secure Boot 的主机只允许符合信任策略的内核代码加载。驱动模块没有由主机信任的密钥签名时，即使文件存在、版本匹配，内核也可能拒绝。日志往往表现为签名、密钥或验证失败。

生产选择不是简单关闭 Secure Boot。平台可以使用受支持的已签名模块、建立密钥注册和签名流程，或在安全评审后调整节点策略。关键是把安全选择纳入节点基线，而不是安装当天临时执行不可审计命令。

如果驱动由容器化安装，签名与信任仍由宿主内核裁决，容器特权不能绕过可信启动模型。Operator 负责尝试安装和报告，平台负责提前准备密钥、固件与主机策略。

实验中的 `secure-boot-unsigned` 保留“设备存在、头文件存在”的事实，只让模块签名条件失败。这样可以验证状态机能否区分普通构建失败与安全策略拒绝。

### 3.4 开放与专有内核模块是兼容选择，不是价值判断

NVIDIA 提供开放内核模块与专有内核模块路径，具体支持取决于 GPU 代际、驱动版本、平台能力和附加功能。当前 Operator 配置应使用受支持的 `driver.kernelModuleType` 等字段选择或自动判断，而不是继续依赖已经弃用的旧开关。

“open”描述内核模块许可和实现路径，不意味着整套用户态都变成同一种开源边界，也不意味着所有旧 GPU 都支持。平台模板必须绑定当前官方支持矩阵，不应把一次成功组合推广到所有节点。

自动选择方便异构节点，但生产变更仍需记录最终解析出的模块类型。发生回归时，如果只保存 values 中的 `auto`，就无法快速知道某一批节点实际加载了什么。资产清单应采集解析结果。

涉及 GH200、GDS 或特定内存一致性能力时，模块类型可能成为硬要求。平台在提供这类资源产品前应建立单独验收，而不是把高级功能悄悄叠在基础 GPU 池上。

### 3.5 `nvidia-smi` 是必要检查，不是完整验收

宿主机 `nvidia-smi` 能列出设备、驱动版本与基础健康，说明 NVML 能够与驱动通信。它适合验证驱动层和采集资产，但不会创建 Kubernetes 资源，也不会测试容器注入。

在 Driver Pod 或宿主运行 `nvidia-smi`，还要注明执行环境。容器可能通过 HostPath 看到主机库与设备，结果不代表普通租户容器获得相同挂载。验收应增加一个按平台标准请求 GPU 的非特权 Pod，并运行最小 CUDA 计算。

对于多 GPU 节点，不能只看命令退出码。要确认预期设备数量、UUID、型号、持久化与错误状态，必要时逐设备运行诊断。八卡节点只剩七卡可见时，简单“命令成功”会把部分故障节点放回资源池。

ECC、Xid、温度与功耗告警也可能在命令成功时存在。驱动就绪和硬件健康是相邻但独立的 Condition，监控部分会继续展开。

## 4. NVIDIA Container Toolkit 连接 OCI 运行时与驱动

驱动在宿主机工作后，容器运行时仍需要知道怎样把 GPU 设备和兼容的驱动用户态组件放入容器。NVIDIA Container Toolkit 提供运行时集成，使 containerd 或 CRI-O 创建 GPU 容器时能够按请求配置设备、库和环境。

这层失败的典型现象是节点 `nvidia-smi` 正常，Device Plugin 可能也在运行，但业务容器创建失败，或进入容器后没有设备。此时问题发生在 CRI 与 OCI 创建链，不应重新编译驱动。

### 4.1 Kubernetes 不直接启动容器

kubelet 通过 CRI 调用 containerd、CRI-O 等容器运行时。运行时根据镜像与 Pod 配置生成 OCI 规范，再由低层 runtime 创建进程、命名空间和 cgroup。GPU 注入要进入这条链，通常通过 NVIDIA 运行时、OCI hook 或 CDI 设备规范表达。

平台首先要确认 kubelet 实际使用哪个 CRI endpoint 和 runtime 配置文件。节点上安装了 Docker 或某个 CLI 并不说明 kubelet 使用它。修改错误的配置文件后重启无关服务，是 GPU 运行时排障中非常常见的无效操作。

Operator Toolkit Operand 通常以特权 DaemonSet 修改目标运行时配置并触发必要重载。成功条件不是 Toolkit Pod Completed，而是运行时加载新配置，并能用相应 handler 或 CDI 设备启动 GPU 容器。

配置变更可能影响节点上全部容器。生产升级需要确认重载是否无损、是否要重启运行时、现有 Pod 是否受影响，并先在空节点或金丝雀池验证。把 runtime Socket 挂给容器的组件必须执行严格的供应链和权限控制。

### 4.2 RuntimeClass 是选择运行处理器的显式接口

Kubernetes RuntimeClass 允许 Pod 选择一个已配置的运行时 handler。某些安装把 NVIDIA runtime 设为默认，另一些要求 Pod 指定 RuntimeClass。两种模式都可工作，但平台必须统一，否则同样的 Pod 在不同节点池表现不同。

设为默认能减少用户字段，却扩大配置错误影响面；显式 RuntimeClass 边界清楚，却需要模板、准入和调度约束保证目标节点存在对应 handler。平台产品通常隐藏底层名字，由资源模板自动注入并验证。

RuntimeClass 还可以带调度和开销语义，但不能自动证明 GPU 资源存在。用户同时需要扩展资源请求和正确运行时。只指定 NVIDIA runtime 而不请求 GPU，可能得到带驱动能力但未分配独占设备的容器，具体行为取决于配置，容易突破资源治理。

排障时可以比较普通 CPU 容器、显式 RuntimeClass 容器和请求 GPU 的容器，逐步缩小范围。一次改变镜像、RuntimeClass、资源请求、权限和命令，会让结果无法归因。

### 4.3 CDI 把设备注入描述标准化

Container Device Interface 使用标准化设备描述让运行时按设备名称注入节点、挂载、环境和 hook。它减少每个上层编排系统为每种设备重复实现注入逻辑，也为更丰富的设备管理机制提供共同接口。

CDI 文件通常在宿主机生成并由运行时读取。文件存在不代表内容新鲜；GPU 重配置、驱动变化或 MIG 布局改变后，旧规范可能引用不存在的设备。平台要把 CDI 刷新与设备配置变更协调，并监控解析错误。

传统环境变量和 NVIDIA runtime 路径仍可能存在。迁移期最危险的是两套机制同时作用，导致重复注入或行为依赖节点历史。节点镜像与 Operator 配置应明确主路径，清理遗留配置，并在验收报告中记录实际机制。

CDI 解决的是描述和注入，不负责 Kubernetes 调度数量、队列公平或 GPU 性能隔离。它是数据面接口之一，不应被包装成完整 GPU 共享方案。
