# 运营面：可观测性、SRE、安全、FinOps 与多集群

平台上线只是开始。运营层要回答四类问题：**出了什么事、该谁负责、花了多少钱、能不能扩到下一个集群。**

## 1. 可观测性：先列问题，再选信号

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l26_01.png" width="78%" alt="统一可观测性" />
  <p>图 1：三类消费者共享同一批事实，但视图与权限不同</p>
</div>

### 1.1 三类消费者

| 消费者 | 关心 | 视图 |
|---|---|---|
| 工作负载所有者 | 为什么慢、为什么失败、是否达 SLO | 只到自己的 Namespace/运行 |
| 平台运维 | 集群健康、控制器、调度、容量、故障域 | 节点/设备/控制面细节 |
| 治理与财务 | 租户、项目、环境、预算、审计 | 受信归属 + 聚合用量 |

把管理员级节点日志直接开放给租户会泄露邻居信息；只做集群聚合又无法自助排障。**身份与权限要在采集、处理、存储、查询四个环节都执行，不能只靠 Dashboard 隐藏按钮。**

### 1.2 四个黄金信号的 AI 版

- **延迟**：训练要拆成排队、调度、镜像拉取、数据加载、训练、检查点；推理要拆 TTFT / ITL / E2E / 队列 / 批形成 / 模型执行；
- **流量**：每小时准入作业数、样本数、Token 数；
- **错误**：区分用户配置、容量、基础设施、框架、数据；
- **饱和度**：队列配额、GPU、网络、存储、控制器工作队列。

**只看平均值会掩盖尾部，只看 P99 在低流量时也不稳定**——要保存可聚合分布 + 请求量 + 错误分类，并把版本、路由、模型 Digest、硬件档位做成受控维度。

### 1.3 统一不是单一后端

| 信号 | 擅长 |
|---|---|
| Metrics | 聚合、告警、趋势 |
| Logs | 离散事件与上下文 |
| Traces | 请求路径与因果 |
| Events / Conditions | 控制面状态 |
| Profiles | 代码级资源热点 |

三种典型反模式：把所有日志转成指标（丢上下文）、把请求 ID 放进指标标签（序列爆炸）、把所有指标复制成日志（聚合成本失控）。

正确做法：统一的是**资源属性 + 关联键 + 保留策略 + 查询入口 + 治理规则**，后端可以替换（OpenTelemetry 资源属性、Prometheus 指标契约、平台身份映射保持不变）。

## 2. 归因：身份要分三层，且不能用标签

### 2.1 三层身份

```text
业务层：租户 / 项目 / 运行 ID / 模型 Digest / 环境
控制层：Workload UID / TrainJob UID / InferenceService UID / PipelineRun UID
执行层：Pod UID / Container / Node UID / GPU UUID / DRA Device
```

任意层都能沿映射边回到其他层；对象删除后映射按保留策略留存。

### 2.2 为什么不能只信标签

- 只信用户标签 → 租户可以把负载标到别的成本中心；
- 只信 Namespace → 无法区分一个团队下的多个项目；
- 只信 Pod 名称 → 重启后名称相似、UID 已变，指标会串。

平台的正确做法：**准入时根据已认证主体 + 项目空间 + 平台 API 生成归属，由受信控制器写入不可覆盖字段**；应用自报的 `team` 只作为低风险业务维度，冲突时保留原始声明用于排障，但**计量选择受信来源并记录冲突事件**。

### 2.3 几个必须用 UID 的地方

- **集群**：多个集群都叫 `production`，重建/复制/灾备切换会复用名字。OpenTelemetry 建议用 `kube-system` Namespace 的 UID 作为集群 UID 代理；
- **GPU**：节点内序号会随可见设备、驱动、MIG、vGPU 变化。要优先用 GPU UUID / MIG 实例身份 / DRA 分配结果；只有 `gpu="0"` 的指标跨节点聚合后没有意义；
- **模型**：`champion` / `latest` 会移动，定位回归需要模型 Digest + 运行时镜像 Digest + 配置版本 + 服务修订。

### 2.4 映射边必须有时间区间

Pod A 在 10:00 占用 GPU-1，11:00 结束；Pod B 随后占用同一 GPU。若只保存「GPU-1 当前属于 B」，A 的历史样本会被错记到 B。每条分配边至少包含**开始、结束、来源、观察时间**；边界缺失进入「未分配桶」，而不是猜测。

### 2.5 缺失身份是一等状态

别把缺失标签填成 `unknown` 就完事——要把原因分开：采集器无 RBAC、Pod 已删除、PodResources 不可用、GPU 字段不支持、应用未注入、处理器丢弃、查询窗口不完整。

定义**归因覆盖率** = 已可靠映射资源 / 总资源。覆盖率低于门禁时，财务、容量、租户报表应标记「不完整」，而不是把未分配量摊给已知团队。

## 3. SRE：SLO、错误预算与自动修复的边界

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l27_01.png" width="78%" alt="平台 SRE" />
  <p>图 2：SLO 分层、错误预算与故障演练构成平台可靠性闭环</p>
</div>

四条实践：

1. **SLO 要分层**：入口（请求成功率/延迟）、控制面（提交接口可用性/排队可见性）、数据面（模型加载成功率）、平台自身（控制器调和延迟）；
2. **错误预算驱动决策**：预算耗尽时优先修稳定性，而不是继续加功能；
3. **故障演练要有剧本**：副本崩溃、节点失联、共享存储变慢、权重下载失败、控制器重启、镜像仓库不可达；
4. **自动修复要有验证**：自动重启/重建只是「恢复手段」，真正可服务要由**真实请求探针**确认——否则会把 CrashLoop 变成「看起来在自愈」。

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l27_02.png" width="78%" alt="故障演练与自动修复" />
  <p>图 3：自动动作必须绑定可验证的恢复判据</p>
</div>

一条纪律：**自动化的每一步都要留下「为什么做这个动作」的证据**（触发条件、目标对象、结果），否则事后无法复盘。

## 4. 安全与审计：策略即代码

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l28_01.png" width="78%" alt="多租户安全" />
  <p>图 4：身份、策略、隔离与审计四层共同构成多租户安全</p>
</div>

四个层次：

| 层 | 控制点 |
|---|---|
| 身份与权限 | 租户身份标签受 Admission 保护，普通用户不能改；工作负载用短期身份而非长期密钥 |
| 策略即代码 | 镜像来源白名单、特权容器禁止、HostPath 限制、网络策略、资源上限；策略本身要有版本与测试 |
| 隔离 | Namespace + 网络策略 + 设备隔离（整卡/MIG/vGPU）；高风险租户独立节点或集群 |
| 审计 | 谁在何时以什么身份做了什么；证据保留期限；例外有范围、批准者、到期与退出方式 |

关键认知：**审计不是日志越多越好，而是关键动作可回答**——创建/删除工作负载、修改配额、发布模型、绑定集群角色、访问敏感数据。

## 5. FinOps：归属先于优化

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l29_01.png" width="78%" alt="GPU FinOps" />
  <p>图 5：成本 = 稳定身份 × 价格版本 × 时间窗口，缺一项就不可重放</p>
</div>

### 5.1 顺序不能颠倒

**如果成本无法可靠归属，所谓优化很可能只是把费用从一个桶移到另一个桶。** 先保证身份覆盖、总账对账、价格可追溯，再谈右配、共享、承诺与采购。

### 5.2 Showback → Chargeback

- **Showback**：展示可归属成本但不结算，用来建立数据质量与行为反馈；
- **Chargeback**：计入预算/利润中心，需要更严格的身份、价格、分摊与对账证据。

建议先用 Showback 跑通三个结算周期，再按覆盖率、争议率与对账差异决定是否进入 Chargeback。**标签覆盖率不足时直接 Chargeback，会把数据缺口变成错误账单。**

### 5.3 成本对象的稳定身份

至少包含：集群、节点、Namespace、控制器、Pod、容器、租户、项目、成本中心、所有者。显示名可变，**结算主键必须稳定**；控制器创建的下游 Pod 还要保留「入口请求 → 最终执行对象」的关联。

反例：只用 Namespace 文本名归属，迁移/重命名/多环境复制时就会漂移。

### 5.4 窗口与粒度

成本是时间积分：

- 30 分钟分辨率核算只跑 2 分钟的 GPU 任务 → 短作业被压成不可解释的缺口；
- 步长决定返回分段，分辨率决定底层精度，两者不要混。

要用「短作业 / 跨日作业 / 持续服务」三类样本验证窗口边界、时区与采样误差。

### 5.5 三种 GPU 小时要一起看

$$
\text{请求 GPU 小时} \ge \text{分配 GPU 小时} \ge \text{有效 GPU 小时}
$$

- 只看**请求量**：低利用但长期占卡的工作负载逃避机会成本；
- 只看**使用量**：无法发现「占着卡但没算」；
- 只看**利用率百分比**：会把通信等待、数据加载、服务保底容量都误判为浪费。

**GPU 小时必须带型号**：一小时旧卡与一小时新卡不是同一个成本也不是同一个性能。

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l29_02.png" width="78%" alt="成本对账" />
  <p>图 6：总账恒等式 + 随机明细重算 + 反例注入，才叫「成本可信」</p>
</div>

### 5.6 验收方式

- **总账恒等式**：各维度求和 = 云账单/资产总额（在允许误差内）；
- **随机明细重算**：抽一条成本，正向重算回工作负载、租户、资源池、价格版本、时间窗口；
- **反例注入**：身份缺失、价格过期、重复分摊、采样中断、容量样本为空——都要落入显式未知状态，而不是静默变 0。

## 6. 多集群：控制面与数据面的分工

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l30_01.png" width="78%" alt="多集群架构" />
  <p>图 7：单集群有硬上限，多集群解决规模、隔离与灾备，但引入身份与制品的一致性成本</p>
</div>

为什么要多集群：

- **规模上限**：单集群的 etcd、调度吞吐、故障半径都有边界；
- **隔离**：不同业务/合规域需要独立故障域；
- **地域与灾备**：数据驻留与跨区切换；
- **异构硬件**：不同型号/厂商的池难以在单集群内统一治理。

代价是四个一致性问题：**身份一致**（谁能做什么）、**制品一致**（哪个 Digest 在哪个集群）、**策略一致**（准入规则是否同版本）、**观测一致**（同一套资源属性与指标口径）。

常见架构：**中心控制面 + 区域数据面**——控制面负责注册、策略、发布与账本，数据面负责实际运行；跨集群的发布用 GitOps 引用同一 Digest，观测用统一资源属性汇聚。

## 7. 运营四张表

| 表 | 内容 | 频率 |
|---|---|---|
| SLO 表 | 分层 SLO、当前达成率、错误预算余量 | 实时/日 |
| 容量表 | 请求/分配/有效 GPU 小时、队列等待、碎片率 | 日/周 |
| 成本表 | 按租户/项目/型号的 Showback、覆盖率 | 周/月 |
| 审计表 | 关键动作、例外、策略版本 | 按需 |

四张表都依赖同一件事：**稳定身份 + 可重放计算**。缺了它，报表只是好看的数字。

## 写在最后

运营层的核心不是「多接几个监控」，而是**让每个结论都能回到身份、版本、时间与证据**。下一篇是第四期的收口：六个实验与项目——把这一整套东西做成可交付、可验收的平台。
