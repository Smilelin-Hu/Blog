# 云原生 CI/CD、制品供应链与发布证明

一份镜像已经通过漏洞扫描并被签名，部署时仍然被拒绝；另一份镜像没有发现高危漏洞，却不应该进入生产。前者可能因为签名身份不在允许集合、Provenance 没有绑定当前 Digest 或模型评测指向另一版本；后者可能来自未审查源码、可变 Task 或无法证明身份的构建器。供应链安全不是把“签名”“SBOM”和“扫描”三个勾打上，而是证明从源码到生产引用的每一跳都没有换对象。

本文建立一条完整可信交付链：PR 只触发受限构建，Tekton Pipeline 把源码、Task、依赖和输出 Digest 组织成一次 PipelineRun；CycloneDX SBOM 描述最终镜像组件；Tekton Chains 从完成的 Run 生成 in-toto/SLSA Provenance 并签名；Cosign 验证制品主张、身份、OIDC 签发者与信任根；policy-controller 在生产命名空间执行 Fail Closed 准入；只有测试、模型评测、安全和来源证据全部指向同一镜像与模型组合，发布机器人才能提交 GitOps 晋级 PR。

## 知识串讲与原理工程分析

## 1. CI/CD 与 ML Pipeline 为何必须分工

构建链生产可部署字节，数据与训练链生产模型及评测证据，发布链只提升经过批准的不可变制品。

### 1. 构建链解决什么问题

工程实现不应让一个脚本同时拥有源码合并、构建、签名、Registry 写入、生产仓库写入和集群管理员权限。构建链生产可部署字节，数据与训练链生产模型及评测证据，发布链只提升经过批准的不可变制品。每个边界使用独立身份和最小权限，交接物是不可变 Digest 与经过认证的 Attestation，而不是共享工作目录中的临时文件或聊天消息中的结论。

如果忽略边界，攻击者只需控制流水线中的一个 Step，就可能读取所有 Secret、替换输出、伪造评测或直接部署。即使没有攻击，任务重试、控制器重启和并发构建也会让可变 Tag 或共享目录产生竞态。正确状态机要求生成者不能批准自己的结果，验证者从 Registry 重新解析并校验制品，发布者只消费通过策略的证明。

验证报告要保存策略 Digest、Builder ID、Signer Identity、OIDC Issuer、Subject Digest、PipelineRun UID 和时间。缺少真实依赖时只能说明哪一段 SKIPPED；网络错误、证明查询失败和证据不充分应分别进入 FAIL、Error 或 Inconclusive，不能统一转换成绿色。

### 2. 数据与训练链为何不是普通编译

理解这项能力要分三个问题。第一，构建声称使用了什么输入；第二，构建服务实际产出了什么字节；第三，谁以什么信任根认证这份声明。构建链生产可部署字节，数据与训练链生产模型及评测证据，发布链只提升经过批准的不可变制品。Provenance 负责描述，签名负责认证，准入策略负责判断，三者缺一都无法把“有一份报告”提升为“允许这个 Digest 运行”。

平台在合并前检查源码审查与流水线定义，在执行前解析所有远程引用，在执行后依据真实输出生成 SBOM 和 Provenance，再从独立验证身份读取 Registry 内容。只有验证成功且模型评测绑定同一 Digest，才生成 GitOps 更新。发布仓库的签名提交继续承载环境审批，不让构建控制面越过交付边界。

失败设计往往表面完整：证明字段齐全却由工作负载自己填写 Builder ID；SBOM 组件很多却绑定构建中间层；签名合法却来自任意企业账号。反例测试必须修改一个变量并命中唯一 Reason，证明策略检查的是语义而不是文件存在。

### 3. 发布链从哪里开始

从产品角度，用户不应手工组合几十个命令。他只选择源码提交、模型版本、服务档位和目标环境，平台模板固定 Task、Builder、SBOM、Provenance、签名与准入策略。构建链生产可部署字节，数据与训练链生产模型及评测证据，发布链只提升经过批准的不可变制品。高级例外通过独立审批进入，正常用户不能关闭验证、替换 ServiceAccount 或把 Tag 伪装成 Digest。

最危险的错误是把“可信”压缩成一个布尔值。某次构建可能来源可信但评测失败，也可能模型质量通过却镜像含严重漏洞；透明日志可用但 Signer 不在允许身份；所有证据有效但策略版本已经被撤销。状态页要展示每个门禁的 Subject、版本、时间和 Reason，并定义过期与重算规则。

工程验收既跑成功链，也注入未审查源码、未固定 Task、非 Hermetic 网络、空 SBOM、严重漏洞、禁止许可证、错误 Subject、未受信 Builder、签名篡改、透明记录缺失、策略 Digest 漂移和无匹配策略。拒绝必须发生在 GitOps 晋级或 Pod 创建之前。

### 4. 三条链怎样用 Digest 交接

把这一判断落到平台，需要同时固定输入、执行者、输出和验证策略。输入包括源码提交、远程 Task、基础镜像、依赖锁、模型数据引用与配置生成器；执行者通过 Kubernetes ServiceAccount、工作负载身份和 Builder ID 被识别；输出用 Digest 表示；策略本身也用版本或摘要保存。只有四者都可追踪，发布证明才不是一份脱离对象的报告。

常见反例是工具分别显示成功：PipelineRun 为 Succeeded，扫描器显示零严重漏洞，签名命令返回验证成功，部署系统却无法证明它们讨论的是同一个 Digest。平台必须先核对 Subject，再解释 Predicate 和结果。任何证据只引用 Tag、别名、任务名称或可编辑 URL，都不能作为生产放行依据。

验收从运行中的 Pod 反向追踪镜像 ID、模型 Digest、GitOps 提交、准入策略、签名 Bundle、Provenance、PipelineRun UID 和源码提交；也从 PR 正向追踪到最终请求。两条路径闭合，反例又能在有害状态发生前被拒绝，才说明控制链真实成立。

## 2. Tekton 对象怎样表达构建图

### 7. Task 与 Step 怎样划分

Task 是一组按顺序执行的 Step，Task 在运行时通常对应一个 Pod；Step 共享任务级执行环境但仍应通过明确文件和 Result 交接。

### 9. TaskRun 和 PipelineRun 为何是证据对象

TaskRun 和 PipelineRun 是一次执行的 Kubernetes 对象，包含 Spec、状态、Result 与 Condition，证明要绑定其 UID 而不是只保存名称。

Workspace 适合源码、缓存和凭据挂载，但共享可写目录会引入隐式依赖；任务接口优先用 Result 传递 Digest 和小型元数据。

### 11. Result 怎样成为任务接口

Result 把一个任务的输出传给后续参数或条件，制品结果应返回完整 Digest，不能只返回可变 Tag。

### 12. finally 任务能否改变主结论

finally 会在主任务结束后运行清理或通知，但不能把已经失败的构建重新解释成成功。
