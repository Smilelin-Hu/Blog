# GPU Ready Kubernetes 集群基线

集群里有 GPU、`nvidia.com/gpu` 数量也正确，为什么仍不能把节点交给训练和推理团队？因为可见设备只证明资源发现的一段。生产节点还需要 GPU 驱动与 Runtime 一致、设备分配可用、共享模式符合合同、高速网络 Profile 通过、存储和制品路径 Ready、故障能被发现并从调度池摘除。

![GPU Ready 集群基线](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l31_01.png)

本项目把前序 GPU 节点软件栈、资源抽象、分区共享、网络拓扑与存储分发几篇组合成一套 GPU Ready 验收基线。最终输出不是一张安装清单，而是一份不可变版本矩阵、两个节点 Profile、六类前置能力证据、四个量化指标、八类故障动作、模拟报告和真实集群只读检查入口。

模拟环境可以证明控制逻辑、状态聚合、阈值和失败语义。它不能证明真实 CUDA、MIG、RDMA、GPUDirect、Ceph 或对象存储性能。真实环境未提供时报告必须为 `SKIPPED`；提供专用 Context 后先只读观察，任何驱动、网络、共享或存储变更另行审批。

## 1. 项目交付目标

项目结束后，一台 GPU 节点只有同时满足九个门禁才能进入正式资源池：GPU 软件栈、设备数量、设备健康、共享模式、网络 Profile、存储 Profile、制品 Digest、健康发现 SLO 和版本 Profile。

两台参考节点分别使用整卡与 MIG 产品，但都要求双 Rail GPUDirect 网络和 Digest 模型缓存。这个组合说明共享模式可以不同，基础可靠性合同必须一致。

验收指标包括 GPU 节点就绪率、设备发现正确率、节点健康检测时间和缓存制品 Ready 时间。参考阈值由场景文件定义，不作为所有硬件的通用性能承诺；真实集群应根据基线调整并经过评审。

## 2. GPU Ready 基线的工程原理

这一部分在实验目录之前展开集群基线的完整工程逻辑。每个能力都先定义产品合同、权威证据、失败语义和运营方式，再在后文通过场景、脚本、反例和真实环境路径验收。

### 2.1 节点准入边界

节点准入边界是 GPU Ready 基线中的一项独立合同。它不能用“组件已安装”代替，而要定义输入、观察方式、成功条件、失败 Reason 和负责团队。节点只有同时满足软件、设备、网络、存储、制品和健康条件，才对外发布对应 Profile。某一子条件失效时，控制器应撤销受影响能力或隔离节点，不能继续依赖人工记忆避免调度。

节点准入边界的权威证据需要从宿主机、Kubernetes API 和测试 Pod 三个视角交叉取得。宿主机能看到模块和设备，API 能看到 Capacity、Allocatable、Claim 与 Condition，Pod 能证明 Runtime 注入和真实可用性。只检查其中一层会遗漏常见断点，例如主机可见 GPU 但容器不可见，或 Capacity 正确而健康设备已经从 Allocatable 扣除。

安全上，节点准入边界由受信控制器管理。租户不能修改 GPU Ready 标签、Taint、共享几何、网络 Profile 或验证结果；诊断容器默认不使用特权，确需宿主访问时采用短期授权和审计。镜像与配置使用 Digest 和签名策略，测试数据与凭据不写入场景文件，节点跨安全域迁移前清理设备状态和本地制品。

评审节点准入边界时首先冻结版本与硬件身份。服务器 SKU、GPU 与 NIC 型号、固件、操作系统 Digest、内核、驱动、Runtime、Operator 和关键配置都要形成不可变矩阵。标签只是矩阵引用，不是矩阵本身。任何变量发生变化都生成候选 Profile 并重新验证，避免同名标签在不同节点代表不同实际组合。

验收节点准入边界要同时包含正向探针和最小反例。正向探针证明目标合同确实可用，反例则故意制造版本漂移、资源数量不符、设备不健康、几何漂移、Rail 故障、存储缺失、Digest 错误或检测超时，并断言节点进入预期阶段。没有反例的绿灯无法证明门禁真正生效，可能只是检查脚本始终返回成功。

可靠性上，节点准入边界必须有失败语义和恢复动作。配置漂移进入 Quarantined，活动设备故障进入 Draining，硬网络能力丢失移除 Profile，存储能力缺失阻止 Admission，制品摘要错误隔离缓存条目，探测延迟越界记为 SLOViolated。稳定 Reason 使自动化和人员能够选择修复、排空、重建或升级，而不是对所有故障执行同一种重启。

运营节点准入边界需要保存时间序列与变更记录。每次验证都关联节点 UID、Profile 摘要、探针版本、开始结束时间、原始证据 URI 和结果。平台持续观察就绪率、设备发现正确率、健康发现时间和制品 Ready 时间，并按服务器 SKU、Rack 和 Profile 分组。聚合指标下降后仍能下钻到具体门禁和 Owner，才具有处置价值。

CDI 设备注入是 GPU Ready 基线中的一项独立合同。它不能用“组件已安装”代替，而要定义输入、观察方式、成功条件、失败 Reason 和负责团队。节点只有同时满足软件、设备、网络、存储、制品和健康条件，才对外发布对应 Profile。某一子条件失效时，控制器应撤销受影响能力或隔离节点，不能继续依赖人工记忆避免调度。

可靠性上，CDI 设备注入必须有失败语义和恢复动作。配置漂移进入 Quarantined，活动设备故障进入 Draining，硬网络能力丢失移除 Profile，存储能力缺失阻止 Admission，制品摘要错误隔离缓存条目，探测延迟越界记为 SLOViolated。稳定 Reason 使自动化和人员能够选择修复、排空、重建或升级，而不是对所有故障执行同一种重启。

### 2.13 DRA 资源声明

验收 DRA 资源声明要同时包含正向探针和最小反例。正向探针证明目标合同确实可用，反例则故意制造版本漂移、资源数量不符、设备不健康、几何漂移、Rail 故障、存储缺失、Digest 错误或检测超时，并断言节点进入预期阶段。没有反例的绿灯无法证明门禁真正生效，可能只是检查脚本始终返回成功。
