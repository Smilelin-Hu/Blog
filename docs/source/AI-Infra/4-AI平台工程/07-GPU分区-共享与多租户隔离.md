# GPU 分区、共享与多租户隔离

一个 Notebook 用户只占用 6GiB 显存，GPU 利用率大部分时间不到 10%，却独占一张 80GiB 卡；四个小模型推理服务各自申请整卡，成本无法接受。平台团队把一张 GPU 发布成八个 Time-Slicing 副本后，利用率上升了，但一个容器突然申请全部显存，其他七个服务同时失败。另一个团队使用 MIG，以为切片数相加够用，三份空闲小实例却无法满足一份大实例请求。

![GPU 分区与共享形态](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l07_01.png)

“共享 GPU”不是一种技术，而是五种不同资源产品：整卡独占、MIG 硬件分区、Time-Slicing 时间复用、MPS 进程并发和 vGPU 虚拟机设备。它们在显存隔离、故障隔离、性能保证、安全边界、重配置成本和许可上差异巨大。把这些模式都叫“0.25 张卡”，会让调度、计费和 SLO 失去真实含义。

本文先建立四维隔离模型，再逐一解释五种形态，重点分析 MIG 的 GPU Instance 与 Compute Instance、Profile 与 Shape、single 与 mixed 策略、MIG Manager 重配置；解释 Time-Slicing 副本为什么不是算力份额；说明 MPS 的 active thread percentage 和显存限制能做什么、不能做什么；把 vGPU 放回 Hypervisor、VM 和许可证边界。

结论先给出来：未知或不互信租户需要硬件或虚拟化边界，不能使用没有显存与故障隔离的 Time-Slicing 冒充；大规模训练默认整卡；小模型推理和受控服务可评估 MIG 或 MPS；交互式开发可在可信项目内使用 Time-Slicing，但必须接受邻居干扰与 OOM 风险；vGPU 适合必须以 VM 交付、需要虚拟化生命周期和企业许可的环境。

实验用 CPU 模拟五类产品、五种工作负载和八类故障。它会证明三份空闲 MIG 小 Shape 不等于一份 3g 大 Shape，Time-Slicing 请求两个副本不获得两倍算力，MPS 显存限制会拒绝越界客户端，MIG 重配置前必须处理活动 GPU Pod，vGPU 许可证不可用会阻塞交付。真实路径只有在明确 GPU 实验集群与显式变更许可下才允许修改共享配置。

## 1. 共享的目标不是把利用率数字变高

GPU 价格高、显存大、计算并行度强，许多交互式或小模型负载无法持续占满。把多个工作负载放在一张卡上可以减少空闲、提高单位成本产出，也能让更多用户获得实验资源。但共享同时把原本独立的故障域和性能域连接起来。

平台目标应是满足业务 SLO 与隔离条件下，提高有效利用和完成量，而不是追求 DCGM 利用率接近 100%。推理服务为低尾延迟保留空闲是容量保险，训练数据加载阶段 GPU 低利用可能来自存储瓶颈。强行塞入邻居会增加尾延迟或让诊断更难。

### 1.1 小任务为什么浪费整卡

一个 2B 参数模型以半精度加载可能只需要数 GiB 显存，单请求推理的 Kernel 也无法占满高端 GPU 全部 SM。独占 80GiB 设备意味着剩余显存和计算不能被其他 Pod 使用，即使调度账显示“已分配”。

Notebook 更明显。用户编辑代码、读取结果和开会时，GPU 上下文仍存在，利用率长时间为零。空闲回收能释放整卡，但频繁停止会破坏交互；共享让多个低占用会话在同一物理卡上交错。

小任务不一定适合共享。如果它包含突发显存峰值、对延迟敏感、处理不可信代码或需要特定 GPU 功能，整卡仍可能是正确产品。浪费要相对于产品目标衡量，而不是只看平均使用。

### 1.2 利用率和完成量不是同一指标

两项任务串行各运行十分钟，GPU 平均利用率可能很高，总完成时间二十分钟；并发后它们争用，利用率仍高，却各运行十八分钟，平均延迟恶化。共享是否有收益要比较单位时间完成的有效工作和 SLO。

训练看 samples per second、tokens per second 和完成时间；在线推理看吞吐、P95/P99 延迟和错误；Notebook 看获取时间、交互响应与可用会话数。设备利用率是解释指标，不是最终目标。

能量和成本也要算。多租户并发使 GPU 保持高功耗，完成量提升若小于功耗增幅，单位任务成本可能没有改善。MIG 或 MPS 的固定限制还会让空闲份额不能被邻居完全借用，隔离与弹性之间存在交换。

### 1.3 共享把容量规划变成概率问题

整卡独占时，一单位请求对应一张卡，性能较可预测。Time-Slicing 四副本意味着一张物理卡可以接受四个 Pod，但每个 Pod 实际获得多少计算取决于其他客户端是否繁忙，显存总需求也可能同时峰值。

若四个 Notebook 平时各占 10%，共享效果好；若它们在同一时段运行训练，全部同时满载，性能和显存冲突出现。副本数不能只按平均利用率设定，要分析同时峰值、工作负载相关性和故障影响。

MIG 把资源切成硬 Shape，概率更低但碎片更高。3g 实例空闲时，两个 1g 任务不能自动借用全部计算；三个 1g 空闲也不能在不重配置时合成 3g。可预测性来自预先保留，代价是灵活性。

### 1.4 多租户首先是信任模型

同一研发团队的多个服务共享，与两个互不信任客户共享，不是同一安全问题。前者可以接受共同故障与性能干扰，后者需要显存、地址空间、管理权限和数据残留的强边界。

平台 API 先要求租户与数据敏感等级，再推荐模式。不能让用户只选“便宜 GPU”，后台用 Time-Slicing 承载任何工作负载。安全敏感等级应强制整卡、MIG、vGPU 或更强节点/VM 隔离。

即使 MIG 提供硬件分区，也共享物理卡、驱动、节点内核、电源和 PCIe。高风险租户可能仍需独占节点或虚拟机。隔离从进程、GPU 实例、设备、主机到集群是层级，不是一个开关。

## 2. 用四种隔离评价任何共享方案

“隔离好不好”过于模糊。至少拆成显存隔离、故障隔离、性能隔离和安全隔离。某技术可以限制显存，却不保证延迟；可以提供 VM 边界，却仍共享物理功耗和故障域。

平台产品描述应逐项写保证与非保证。用户看到“共享 4 份”时，必须知道其他三份能否占用自己的显存、一个客户端错误是否影响自己、忙邻居是否拖慢、租户是否共享进程或内核。

### 2.1 显存隔离

显存隔离回答一个工作负载能访问和分配多少 GPU 内存，以及是否能读到他人数据。MIG GPU Instance 拥有专用内存 slice 和相关缓存、控制器，提供容量与带宽隔离；整卡独占天然只给一个租户设备。

Time-Slicing 多个 Pod 看到同一物理 GPU 和同一总显存池，没有每副本硬额度。任一客户端可以先占大量显存，让其他客户端 OOM。调度器发布四副本不代表自动把 48GiB 分成四份 12GiB。

MPS 可以设置客户端 pinned device memory limit，让超额 CUDA 分配返回 OOM，从而为调度建立显存上限。但配置、进程信任和实现边界要严格控制；它和 MIG 的独立内存 slice 不是同一种硬件隔离。

vGPU Profile 通常定义 VM 可见显存与能力，隔离由 vGPU 软件和 Hypervisor 实现，还依赖主客驱动与许可证。具体保证以所选 Profile 与产品文档为准。

### 2.2 故障隔离

故障隔离回答一个客户端触发的 GPU 错误、Reset 或驱动问题会影响多少邻居。整卡独占时应用故障主要影响自己，但物理设备或节点驱动故障仍影响同节点相关工作。

MIG 实例具有更强故障隔离设计，多个实例有独立资源与地址空间；某些物理级或驱动级故障仍可能波及整卡。不能把“实例隔离”宣传为硬件永不共故障。

Time-Slicing 明确没有故障隔离。所有副本复用同一设备，一个非法访问、Xid 或需要 Reset 的事件可能影响所有 Pod。MPS 客户端通过同一服务协调，服务或设备故障也可能扩大。

vGPU 把客户机隔离在 VM，客户端进程崩溃通常只影响该 VM；Hypervisor、vGPU Manager 和物理 GPU 故障仍是共同域。平台 SRE 要按物理设备关联所有逻辑租户。

### 2.3 性能隔离

性能隔离回答邻居负载能否显著改变自己的吞吐和延迟。MIG 为实例分配固定 SM slice、内存 slice 与部分引擎，提供较强可预测性；具体 Profile 拥有的引擎不同，不能只看显存。

Time-Slicing 只让上下文交替使用 GPU，副本不是固定算力百分比。所有客户端繁忙时各自速度下降，切换与缓存干扰增加尾延迟。请求两个副本也不会获得两倍时间份额。

MPS 把多个 CUDA 上下文的工作并发送入 GPU，可以用 active thread percentage 限制客户端可用线程或 SM 范围。官方说明限制不是专用资源预留，不同客户端 Kernel 仍可能在同一 SM 执行，性能保证需要实测。

vGPU 性能取决于 Profile 与调度策略，可提供较明确份额，也可能采用时间调度。平台不能仅凭“VM 隔离”承诺稳定吞吐。

### 2.4 安全隔离

安全隔离包括设备地址空间、主机内核、驱动、管理接口、数据残留和权限。Time-Slicing 的多个容器共享同一主机和物理 GPU，适合可信或低风险工作负载，不作为强多租户边界。

MIG 提供独立地址空间与硬件分区，是更强 GPU 级边界；Pod 仍共享节点内核和 GPU 驱动。高安全需求再叠加独占节点、沙箱或 VM。

MPS 由控制守护进程与客户端连接，客户端归属、Server 生命周期和日志目录需要保护。跨不信任租户共享 MPS 服务会扩大控制面和故障面，通常按同一信任域运行。

vGPU 以 VM 为主要隔离边界，适合不同操作系统或强虚拟化治理，但引入 Hypervisor、Host Driver、Guest Driver、License Service 和镜像供应链。边界更强不等于运营更简单。

## 3. 五种资源形态的核心语义

选型前先把每种模式还原成“调度器分配的单位是什么”。整卡单位是物理 GPU；MIG 单位是硬件 Profile 实例；Time-Slicing 单位是插件发布的逻辑副本；MPS 单位通常是受控客户端配额或平台自定义资源；vGPU 单位是 Hypervisor 创建并交给 VM 的虚拟设备 Profile。

名称相似不能相互替换。一个 `gpu.shared` 副本不是 MIG 1g 实例；一个 MPS 25% 限制也不是固定四分之一性能；一个 8GiB vGPU 也不是容器内 8GiB MIG。

### 3.1 整卡独占

Pod 请求一个传统 GPU 资源或 DRA 整卡 Claim，获得整个设备。显存和计算不与其他普通租户共享，性能最可预测，调试最简单。多卡训练还能保留完整 NVLink 与拓扑能力。

成本是小负载浪费、并发用户少、长时间 Notebook 空闲。可用空闲回收、排队、短租约和自动停止改善，而不改变隔离。

整卡仍不是节点独占。两个 Pod 可各自使用同节点不同 GPU，共享 CPU、内存、网络、PCIe 和驱动。若安全或性能要求更高，资源产品再加独占节点。

### 3.2 MIG 硬件分区

Multi-Instance GPU 在支持的 GPU 上把物理资源划成多个 GPU Instance。每个 GI 组合 GPU slices 与引擎，拥有专用内存资源和地址空间；GI 的 SM 还能进一步划为 Compute Instance，CI 共享父 GI 内存与部分引擎但拥有专用 SM 资源。

Kubernetes 通常把 MIG 设备 Profile 发布成扩展资源，如某种 `mig-1g.*`。用户请求一个 Profile，获得固定 Shape。Profile 名称随 GPU 型号和显存规格不同，不能把 A100 40GB 示例永久套到 H100 或其他设备。

MIG 提供硬件级分区和较强 QoS，适合多租户小推理、受控 Notebook 和需要显存保证的任务。限制是只有支持 MIG 的硬件可用，Profile 组合有限，重配置会影响 GPU 上现有工作负载，碎片需要运营。

### 3.3 Time-Slicing 时间复用

Device Plugin 为每张物理 GPU 发布多个逻辑 replica，Kubernetes 把每个 replica 当作可分配整数。多个 Pod 最终访问同一 GPU，驱动在不同上下文之间时间复用。

它几乎不需要硬件分区，适用范围广，能快速提高 Notebook 和低占用任务的并发。代价是没有显存隔离和故障隔离，计算份额是 Best Effort，用户请求数量与实际比例不成正比。

配置 `renameByDefault=true` 时可把共享资源发布为 `.shared` 名称，让用户和配额明确区分整卡。`failRequestsGreaterThanOne=true` 可拒绝一个容器请求多个副本，防止用户误以为两个 replica 获得双倍算力。

### 3.4 MPS 进程并发

CUDA Multi-Process Service 通过 MPS Server 协调多个客户端，把 Kernel 和操作更高效地并发提交给 GPU。它可减少多进程上下文切换与提高小 Kernel 并行，适合同一信任域的服务或批量小任务。

active thread percentage 可限制客户端上下文可使用的执行线程或 SM 范围。官方强调限制不是专用资源保留，实际调度仍有共享。还可配置 pinned device memory limit，超额分配返回 OOM，为显存配额提供执行约束。

MPS 引入控制守护进程、Server、客户端连接数、日志、用户和故障处理。它不像 MIG 天然成为 Kubernetes 标准资源 Shape，平台需要封装生命周期、配额和监控。

### 3.5 vGPU 虚拟设备

vGPU 让多个 VM 同时直接访问同一物理 GPU。Hypervisor 侧 vGPU Host Driver 或 Manager 创建虚拟设备，VM 内运行匹配 Guest Driver；Profile 决定可见资源与能力，企业部署还涉及 NVIDIA License System。

它适合需要 VM 边界、不同 Guest OS、虚拟桌面或基于 KubeVirt/OpenShift Virtualization 的 GPU 虚拟机。容器平台若只需要共享 CUDA，vGPU 的 Hypervisor、许可和驱动矩阵可能过重。

GPU Operator 在 vGPU 环境管理 Guest 侧或 KubeVirt 相关组件，但物理 Hypervisor 和 vGPU Manager 仍是另一层责任。发生故障时要跨 VM、节点与 Hypervisor 定位。

## 4. MIG 的资源层次与 Profile

理解 MIG 不能只记 `1g.10gb` 名字。GPU 硬件包含内存 slice、SM slice 与复制、编码、解码等引擎。Profile 把一定数量的这些资源组合成 GI，决定可见显存、带宽、SM 与引擎。

### 4.1 GPU Instance 拥有内存 QoS

GPU memory slice 包含对应显存容量、内存控制器和缓存份额。GI 组合若干 memory slice 与 GPU slice，获得相对独立的地址空间、显存容量和带宽。不同 GI 之间不是在同一个全局显存池先到先得。

这正是 MIG 相对 Time-Slicing 的关键优势。一个 1g 实例的应用不能因为邻居空闲就无限申请整个 80GiB，也不会被邻居先申请显存挤出自己的固定容量。代价是空闲显存不能透明借用。

Profile 还包含引擎差异。一些小 Profile 可能没有编码器，带 `+me` 一类扩展的 Profile 拥有媒体引擎。推理若依赖 NVDEC/NVENC，只检查显存会选择错误 Shape。

### 4.2 Compute Instance 进一步划分 SM

一个 GI 的 SM slice 可以分成多个 CI。CI 拥有父 GI 的一部分 SM，与同 GI 其他 CI 共享显存与引擎。它适合在一个内存边界内进一步分计算，但隔离语义不同于两个独立 GI。

平台通常优先向用户暴露清晰、经过验证的 Profile，不让普通租户直接组合 GI 和 CI。高级细分会增加资源名、监控与故障关联，用户也难以理解共享父 GI。

无论暴露哪一层，资产系统都要记录物理 GPU、GI、CI 和 Kubernetes 资源之间关系。物理卡故障会影响全部子实例，成本与事件不能只停在逻辑资源名。

### 4.3 Profile 不是任意连续容量

支持 Profile 由 GPU 型号和驱动定义。1g、2g、3g、4g、7g 一类组合对应特定 slice 和 Placement，并非用户写任意“25GiB”就能创建。不同 GPU 的显存后缀和最大实例数不同。

Profile 放置还有几何约束。总空闲 slice 数量等于请求 slice，不代表当前位置能形成目标 Profile；驱动只允许特定 Placement。实验用“3 个 1g 空闲不能直接当作一个 3g”表达 Shape 碎片，实际 Placement 以目标 GPU 官方支持表和工具为准。

资源产品不要用 `0.14 GPU` 命名 1g 实例。它的显存、SM 和引擎比例不一定完全相同，用户更需要明确 Profile 能力。

### 4.4 MIG 模式改变整卡可见形态

GPU 启用 MIG 并创建实例后，Device Plugin 发布 MIG 资源而不是普通整卡，具体取决于策略。工作负载必须请求正确资源名。一个仍请求 `nvidia.com/gpu` 的 Pod 可能在 MIG 池 Pending。

MIG 模式与实例几何是节点配置，不应由普通用户随 Pod 任意切换。重配置可能需要终止该 GPU 上的所有任务，某些平台或设备还涉及重启。平台把它当维护与容量变更。

## 5. single 与 mixed MIG 策略

GPU Operator 的 MIG 策略控制 Device Plugin 与 GFD 怎样暴露实例。single 策略要求节点上所有 GPU 采用一致 MIG 设备形态，并以相对统一资源方式发布；mixed 策略允许多种 Profile 并为每种 Profile 发布独立资源名。
