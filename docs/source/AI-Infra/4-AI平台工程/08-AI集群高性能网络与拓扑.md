# AI 集群高性能网络与拓扑

八台 GPU 在一台服务器里训练正常，两台服务器各用八台 GPU 后，任务却在 NCCL 初始化阶段停住；另一个任务能够启动，但吞吐只有单机的六成。节点都显示 Ready，网卡也都是 Up，400Gb/s 链路没有任何一条断开。平台团队先调 NCCL 参数，又换训练框架，最后才发现一组 Pod 走了管理网，另一组虽然用了 RoCE 网卡，却跨 NUMA 连接了 GPU 和 NIC。

![AI 集群网络与拓扑](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l08_01.png)

AI 集群的网络问题很少属于某一层。业务看到的是训练慢，通信库看到的是接口或拓扑，容器看到的是网络设备，Kubernetes 看到的是 CNI、资源和节点标签，宿主机看到的是驱动、PCIe 与 RDMA 设备，交换网络看到的是队列、拥塞和丢包。任何一层把“可用”误当“高性能”，都会让问题在别处表现。

核心判断先给出来：高性能网络不是给 Pod 增加一张网卡，而是把流量平面、设备能力、数据路径、GPU 与 NIC 亲和、机架与 Rail 拓扑、调度约束、端到端配置和验收证据做成一个资源产品。基础 Pod 网络负责通用连接，高速辅助网络承载训练或存储；RDMA 不自动等于 GPUDirect RDMA；400Gb/s 端口不自动等于应用能获得 400Gb/s；节点内 NUMA 对齐也不自动解决跨节点 Rail 选择。

本文从五类流量开始，先解释 CNI、Pod IP、Service、NetworkPolicy、MTU 和多网络，再进入 RDMA、InfiniBand、RoCE、SR-IOV、GPUDirect 与 NVIDIA Network Operator。随后把 PCIe、NUMA、NVLink、NIC、Switch、Rack、Rail 和 Zone 翻译成调度语义，最后建立连通性、带宽、延迟、RDMA、GPUDirect、多节点一致性和故障演练的分层验收。

实验使用 CPU 模拟四个 GPU 节点、两个机架、双 Rail、三种网络和三类工作负载。它验证十六卡训练必须选择同机架、双 Rail 且具备 RDMA 与 GPUDirect 能力的节点集合，高可用推理应跨机架放置；同时注入辅助网络缺失、MTU 不一致、RoCE 拥塞控制缺失、RDMA 资源缺失、GPUDirect 路径缺失、GPU-NIC 跨 NUMA、Rail 故障、驱动代际漂移和错误接口选择。模拟只证明控制面与拓扑语义，真实带宽和延迟必须在专用硬件上测量。

## 1. 网络快不快，先看数据究竟走哪条路

“节点有 400G 网卡”是一条资产事实，不是工作负载事实。一个 Pod 可能只有 Overlay 主网络，数据先通过 veth、主机协议栈和封装，再从另一张 25G 管理网卡离开；400G 网卡即使 Up，也没有进入该 Pod 的网络命名空间。即使辅助网卡已经注入，应用仍可能按路由或接口自动发现选择错误路径。

因此排查顺序不从端口标称速率开始，而从一笔数据开始：它从哪块 GPU 或内存产生，经过哪个进程和通信库，使用哪个容器接口，映射到哪个 VF 或物理 NIC，通过哪条 Rail 和哪些交换机，到达远端哪张 NIC 与 GPU。只要路径中的一个环节没有被证实，就不能把带宽上限写成平台承诺。

### 1.1 链路带宽只是最窄瓶颈的上界

一条数据路径包含 GPU 内存、PCIe、CPU 内存、NIC、交换网络和远端反向路径。理想吞吐不会超过最慢环节：

$$B_{path} \leq \min(B_{gpu}, B_{pcie}, B_{host}, B_{nic}, B_{fabric}, B_{remote})$$

$B_{path}$ 是端到端有效带宽，后面的变量分别是 GPU、PCIe、主机内存、网卡、网络 Fabric 和远端路径能提供的带宽。公式从左到右表达：应用最终吞吐最多等于所有环节中最小的那一个，而且真实值还要扣除协议、拥塞、同步和软件开销。

例如端口为 400Gb/s，理论字节速率约 50GB/s；若 GPU 到 NIC 跨 NUMA 并经过只能有效提供 28GB/s 的 PCIe 路径，应用不可能得到 50GB/s。若两条 400G Rail 配置正确但通信只选中一条，聚合上限仍不是 800Gb/s。标称值适合资产目录，实测值才进入 SLO。

### 1.2 延迟由固定成本和传输成本共同组成

传输一段大小为 $S$ 的数据，可用一个简化模型理解：

$$T \approx L_{fixed} + \frac{S}{B_{effective}} + T_{queue} + T_{sync}$$

$L_{fixed}$ 包括软件栈、设备和交换转发的固定延迟；$B_{effective}$ 是有效带宽；$T_{queue}$ 是拥塞排队；$T_{sync}$ 是集合通信等待慢 Rank 的时间。小消息主要受固定延迟影响，大消息更受带宽影响，拥塞与慢 Rank 会让两者都恶化。

这解释了为什么单跑大包带宽正常，训练仍可能慢。梯度通信包含多种消息大小，集合操作还要等待所有参与者。某个节点 GPU-NIC 错位、多一跳交换或有重传，整个 AllReduce 阶段都被最慢 Rank 拖住。平均端口利用率不能显示同步等待。

### 1.3 连通、可用和高性能是三种状态

连通表示两个端点能交换包，例如 Ping 成功或 TCP 端口可达。可用表示应用能建立所需通道，权限、设备和路由正确。高性能表示在规定拓扑、消息大小、并发和持续时间下达到带宽与延迟门槛。

Ping 通不能证明 RDMA Verbs 可用，`ibv_devinfo` 能看到设备不能证明 Pod 拥有它，RDMA 测试通过不能证明数据直接进入 GPU 内存，单流带宽通过不能证明双 Rail 与多节点集合通信通过。平台健康状态应保留这些层级，而不是一个绿色“网络正常”。

## 2. 五类流量为什么不应挤在同一个网络平面

AI 平台至少面对管理、Pod 与 Service、存储、训练或推理互联、可观测性五类流量。它们在吞吐、延迟、安全、突发模式和故障影响上不同。物理网络可以共享部分设备，但逻辑上必须能识别、治理和验收。

### 2.1 管理面优先稳定而不是极限带宽

管理流量包括节点访问、Kubernetes API、镜像与配置控制、DNS、证书、Operator 协调和远程运维。它通常不需要数百 Gb/s，却必须在训练网络拥塞或重配置时仍可用。

如果管理 SSH、kubelet 心跳和大规模训练共享同一无隔离队列，训练突发可能让节点 NotReady，控制面开始驱逐工作负载，进一步放大事故。管理路径应有独立路由或服务等级，至少不能依赖待维修的高速辅助网络才能执行修复。

管理面还承担逃生通道。修改 RoCE PFC、重建 VF 或升级网卡驱动时，高速接口可能短暂不可用；若节点管理也依赖它，运维动作会失去反馈。高性能不是牺牲可恢复性换来的。

### 2.2 Pod 与 Service 网络承载通用应用语义

Kubernetes 为 Pod 提供集群内网络身份，Service 提供稳定访问入口与后端发现，Ingress 或 Gateway 连接外部流量。控制器、Webhook、Notebook UI、推理 Gateway 和业务 API 通常依赖这张主网络。

主网络强调普适、策略与可运维性，可能采用 Overlay、隧道、eBPF 或路由方案。它不必承担训练集合通信的所有流量。让训练数据走主网可以降低接入复杂度，但封装开销、共享带宽和不可控路径可能无法满足大规模训练。

不能因引入辅助网络就绕过主网络。Pod 仍需要 DNS、API 和健康检查；训练进程可能用主网完成 Bootstrap，再用 RDMA 网传输数据。两张网络的职责与路由必须明确，避免默认路由被辅助网络夺走后，Pod 反而访问不到 Kubernetes 服务。

### 2.3 存储流量具有持续吞吐和突发汇聚

数据集读取、Checkpoint 写入、模型制品下载和缓存填充会形成存储流量。训练启动时数百 Pod 同时拉取数据，周期性 Checkpoint 又在短窗口写入大量内容。它与梯度通信叠加时，容易互相争抢 NIC、PCIe 或交换缓存。

将存储和训练拆到不同 NIC 或不同 Traffic Class，可以减少干扰；若共享物理端口，则需要容量、QoS 和峰值错开策略。只从平均带宽规划会低估同步 Checkpoint 的汇聚峰值。

GPUDirect Storage 可以优化存储到 GPU 的数据路径，但它不取消存储系统、文件系统、驱动和拓扑要求。模型加载慢时，不能因为安装了 GDS 相关组件就直接归因于 GPU；仍要分解对象存储、缓存、文件系统、NIC 与 PCIe。

### 2.4 训练与推理互联对尾部最慢节点敏感

分布式训练的 AllReduce、AllGather、ReduceScatter、AllToAll 和点对点传输需要节点同步。通信量与并行策略有关，数据并行、张量并行、流水线并行和专家并行对消息模式要求不同。这里不重复 NCCL 算法调优，但平台必须提供算法可以正确发现和使用的网络拓扑。

在线推理也可能跨节点通信，例如张量并行模型或预填充与解码分离。它比批训练更敏感于尾延迟，网络抖动会直接映射到请求 P99。训练追求长期有效带宽，在线推理还要求稳定的小消息延迟与故障快速摘除。

### 2.5 可观测性流量不能成为隐藏的竞争者

指标、日志、Trace、Profiling 与核心转储会消耗网络。正常时比例不高，事故时日志量可能突然放大。如果所有 GPU 节点同时上传 Profile 或 Core Dump，可能与业务恢复流量竞争。

可观测性应有速率控制、采样与本地缓冲。监控网络拥塞时，不要让采集本身进一步制造拥塞。高性能链路的端口计数、RDMA 计数和队列状态可以由节点代理采集，但聚合频率要与故障定位价值匹配。

## 3. Kubernetes 基础网络解决什么，又故意不解决什么

Kubernetes 网络模型给 Pod 可通信的网络身份，但不规定必须使用哪种物理 Fabric，也不保证 RDMA、固定带宽、NUMA 亲和或 GPU 直连。CNI 是容器运行时调用的网络配置接口，具体插件负责创建接口、地址、路由和必要的主机规则。

### 3.1 CNI 发生在 Pod Sandbox 创建期间

Kubelet 让容器运行时创建 Pod Sandbox，运行时调用已配置的 CNI 插件。插件根据网络配置在 Pod 网络命名空间中创建接口，分配 IP，设置路由，并返回结果。CNI 失败时，业务容器通常还没有开始运行，事件表现为 Sandbox 创建失败。

这个顺序对诊断很重要。若 Pod 停在 ContainerCreating 且事件提示网络插件失败，反复检查训练框架没有意义；若主接口已创建而 Multus 辅助接口失败，则问题属于 NetworkAttachmentDefinition、辅助 CNI、IPAM 或设备资源。

CNI 本身不长期控制数据面。接口创建成功后，包如何转发由内核、eBPF、硬件、路由和交换网络决定。安装成功也不等于运行路径健康。

### 3.2 Pod IP 与 Service 地址不是一回事

Pod IP 属于具体 Pod 实例，Pod 重建后可能改变。Service 提供稳定虚拟地址或 DNS 名称，将流量导向一组 Endpoint。训练 Rank 之间常使用 Pod 或 Host 网络地址建立直连，而用户访问推理服务通常经过 Service 或 Gateway。

高速辅助接口分配的 IP 一般不会自动成为 Service 后端语义的一部分。应用需要明确用哪个地址 Bootstrap、哪个地址传输数据。若把辅助 IP 写进临时环境变量却没有稳定发现机制，Pod 重建或 IPAM 变化后会失效。

多网络场景下，`eth0` 常是主接口，额外接口名称和 IP 来自 Multus 配置。接口名不应成为跨集群唯一假设；更稳妥的是由平台注入网络选择、地址清单和可验证的通信配置。

### 3.3 NetworkPolicy 保护主网，不自动保护所有辅助网

NetworkPolicy 是否作用于某张网络取决于使用的网络插件和实现。主 CNI 支持策略，不代表 SR-IOV VF 或 MacVLAN 辅助网络自动受到相同策略约束。绕过主机软件数据面的高性能路径尤其需要单独验证隔离能力。

平台安全评审必须逐网络回答：谁可连接，地址如何分配，租户能否伪造源地址，VLAN、PKey、VF Trust 与 Spoof Check 怎样配置，交换机 ACL 或 Fabric 分区由谁管理。不能在门户显示“NetworkPolicy 已启用”就概括所有数据平面。

对于训练集群，辅助网络常在受控 Namespace 和节点池中开放，工作负载通过准入策略才能引用对应 NAD。网络对象、设备资源和租户权限要绑定，否则用户可能只声明网络却未申请设备，或申请设备却接入错误网络。

### 3.4 Overlay 增加了路径和 MTU 约束

Overlay 把 Pod 包封装在另一个外层包中，便于跨节点建立虚拟网络，但会增加头部开销并降低有效 MTU。例如底层物理 MTU 为 1500，叠加封装后 Pod MTU 需要更小，避免外层包超过链路能力。

Jumbo Frame 可减少大流量的包数与每字节处理开销，但只有端到端每一跳都支持并配置一致时才有效。Pod 接口、VF、PF、Bond、交换端口和路由路径中任何一处仍是 1500，发送大帧都可能分片、丢弃或依赖路径 MTU 发现。

“所有网卡显示 MTU 9000”还不够，必须验证真实路径。某个跨机架链路或中间 VLAN 可能不同。实验中的路径 MTU 取各跳最小值；真实验收可用带 DF 标志的 Ping 逐步增大载荷，再用业务协议验证。

## 4. 多网络让通用控制与高速数据各走合适路径

单一 Pod 网络的优点是简单：身份、策略、Service 和故障面都集中。高性能集群引入多网络，是因为训练或存储需要直接接近物理 NIC、专用地址域或 RDMA 设备。代价是接口、路由、IPAM、安全和生命周期复杂度上升。

### 4.1 Multus 是元插件，不是另一张物理网络

Multus CNI 读取 Pod 上的网络选择，将主 CNI 与一个或多个辅助 CNI 组合起来。它协调“给这个 Pod 再增加接口”，实际怎样创建接口仍由 SR-IOV、MacVLAN、IPoIB 或其他插件完成。

把 Multus 安装成功描述为“RDMA 已就绪”是不准确的。Multus 可以附加一个普通 MacVLAN 接口，也可以协调 SR-IOV VF；是否有 RDMA 取决于设备、驱动、插件、权限和网络 Fabric。它解决多网络编排，不创造硬件能力。

### 4.2 NetworkAttachmentDefinition 是网络产品的 API 入口

`NetworkAttachmentDefinition` 简称 NAD，是由多网络生态定义的 Kubernetes 自定义资源。它保存辅助网络的 CNI 配置，Pod 通过注解或更高层控制器引用。NAD 的 Namespace 作用域也构成授权边界：不同项目可以暴露不同网络产品。

一份 NAD 可能声明 CNI 类型、VLAN、MTU、IPAM、资源名和安全参数。资源名把网络附件与 Device Plugin 或 DRA 发布的设备连接起来。两者必须一致，否则 Pod 可能得到 IP 接口却没有对应 VF，或者占用 VF 却没有正确网络配置。

实验中的配置把 `train-roce` 绑定到 `nvidia.com/sriov_rdma`。Pod 同时请求 GPU 和 RDMA 资源，并通过节点标签限定到已验证的双 Rail GPUDirect 节点。示例使用保留测试地址与无效镜像域名，只用于解释对象关系，不应直接部署到生产。

```yaml
metadata:
  annotations:
    k8s.v1.cni.cncf.io/networks: train-roce
spec:
  nodeSelector:
    ai.training.invalid/network-profile: roce-gdr-dual-rail
  containers:
    - name: trainer
      resources:
        limits:
          nvidia.com/gpu: 1
          nvidia.com/sriov_rdma: 1
```

注解选择网络，Limit 请求设备，两者承担不同职责。只复制注解可能导致资源没有被调度器计数；只请求资源则不一定创建应用需要的网络接口。平台模板应成对生成并在准入阶段校验。

### 4.3 主接口和高速接口需要明确路由责任

通常主接口保留默认路由，用于 API、DNS、镜像和普通服务；辅助接口只承载指定训练网段。若辅助 CNI 写入第二条默认路由，Linux 策略路由可能选择意外出口，回包从另一接口返回，产生非对称路由或连接失败。

训练通信库常按接口名、地址范围或路由自动选择。平台应把可用接口写进工作负载环境，并限制不应选择的 Docker Bridge、Loopback 或管理接口。NCCL 官方故障文档指出，处于 Up 但节点间不可通信的接口可能被自动选中，导致初始化失败或挂起；这类问题不能靠增加超时解决。

路由验收至少包含源地址、目标网段、出接口、下一跳和回程路径。多 Rail 环境还要确认每条 Rail 是否连接到预期交换 Fabric，不能只看接口都 Up。

### 4.4 IPAM 失败会把设备问题伪装成网络问题

IPAM 负责为接口分配地址。Host-local、Whereabouts、DHCP 或厂商 IPAM 具有不同作用域和一致性模型。多节点辅助网络通常需要集群范围避免地址冲突，也要处理 Pod 异常删除后的地址回收。

若 VF 已分配但 IPAM 耗尽，Pod 会停在网络附加阶段；若 IP 先分配而后续 CNI 失败，回滚不完整可能泄漏地址。平台需要同时观察设备分配和 IP 租约，而不是只看 Pod 事件。

地址池应按 Rack、Rail 或 Subnet 规划。双 Rail 使用相同子网可能让路由无法稳定区分路径；按 Rail 分网段便于验证与故障隔离。规划还要预留网关、基础设施和扩容地址，不能把可用地址数等同于 GPU 数，因为每个 Pod 可能使用多个接口。

## 5. RDMA 减少的不是网络距离，而是 CPU 参与和软件开销

RDMA 是 Remote Direct Memory Access，允许一台机器的设备通过网络直接读写远端注册内存，减少传统 Socket 路径中的内核参与、数据复制和上下文切换。它需要 RNIC、驱动、RDMA Core、用户态库、内存注册与双方队列资源共同工作。

### 5.1 Kernel Bypass 的准确含义

传统 TCP Socket 发送通常经过系统调用、内核协议栈、缓冲和调度。RDMA 应用通过 Verbs 接口准备 Queue Pair、Completion Queue 和注册内存，数据面操作由 RNIC 执行，完成事件由应用轮询或通知获取。控制面仍需要操作系统与驱动，Kernel Bypass 不表示内核完全无关。

减少 CPU 参与可以把 CPU 留给数据预处理与框架控制，也能降低抖动。但内存注册、队列创建和小消息处理仍有成本。错误的队列数量、Pinned Memory 压力或 NUMA 放置会让 RDMA 方案表现不佳。

### 5.2 RDMA 设备可见不代表应用已获得可用通道

宿主机 `ibv_devices` 能列出设备，说明用户态栈至少发现 HCA；Pod 内是否可见取决于设备插件、设备节点、权限和网络命名空间。端口状态还要检查 Link Layer、Active MTU、GID、LID 或 RoCE 地址、速率和物理状态。

建立通道需要远端同样配置。单节点看到设备不能证明跨节点 Fabric 路由正确。InfiniBand 需要 Subnet Manager 与正确分区，RoCE 需要以太网 VLAN、路由和拥塞配置。任何一端的 GID 索引、地址族或 MTU 不一致，都可能让测试失败。

### 5.3 Send/Receive 与 Read/Write 不是同一语义

RDMA Send/Receive 需要接收端提前发布 Receive 缓冲，适合消息语义；RDMA Read/Write 直接访问远端已授权的内存区域，依赖 Remote Key 等访问控制。上层通信库选择合适操作，平台不需要替用户手写 Verbs，但必须理解资源与故障。

例如 Completion Queue 没有被及时处理，会表现为通信停滞；注册内存不足会在建立通道或传输前失败；队列资源耗尽可能只在大规模 Rank 数出现。两节点微测通过不代表千卡规模的连接数量和交换 Fabric 状态通过。
