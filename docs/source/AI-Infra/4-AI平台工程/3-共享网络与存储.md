# 共享、网络与存储：平台的三块硬约束

资源能不能共享、网络能不能跑满、数据能不能及时到位——这三件事决定了平台的上限。它们的共同特征是：**技术选项很多，但每个选项都带着不可隐藏的语义。**

## 1. 五种 GPU 资源形态：先问「分配单位是什么」

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l07_01.png" width="78%" alt="GPU 共享与隔离" />
  <p>图 1：整卡、MIG、Time-Slicing、MPS、vGPU 的隔离强度与灵活性互为代价</p>
</div>

| 形态 | 调度器分配的单位 | 关键特征 |
|---|---|---|
| 整卡独占 | 物理 GPU | 最可预测，保留完整 NVLink 与拓扑 |
| MIG | 硬件 Profile 实例（如 `mig-1g.*`） | 硬件分区，显存/地址空间独立，碎片高 |
| Time-Slicing | 插件发布的逻辑副本 | 多 Pod 共享同一 GPU，无硬额度 |
| MPS | 受控客户端配额或自定义资源 | 并发上下文，可设线程/显存上限 |
| vGPU | Hypervisor 给的虚拟设备 Profile | VM 级隔离，依赖主客驱动与许可 |

**名称相似不能相互替代**：

- 一个 `gpu.shared` 副本 **不是** MIG 1g 实例；
- 一个 MPS 25% 限制 **不是** 固定四分之一性能；
- 一个 8 GiB vGPU **不是** 容器内 8 GiB 的 MIG。

## 2. 四维隔离：把「隔离好不好」拆开

| 维度 | 整卡 | MIG | Time-Slicing | MPS | vGPU |
|---|---|---|---|---|---|
| 显存 | 独占 | 独立 slice 与带宽 | **共享总池，可被抢占到 OOM** | 可设 pinned 上限 | Profile 定义 |
| 故障 | 影响自身 | 实例级更强，物理故障仍共担 | **无隔离**，Xid/Reset 波及全部 | 服务级共担 | VM 内隔离，宿主共担 |
| 性能 | 最可预测 | 固定 SM/内存 slice | 取决于邻居，副本≠算力百分比 | 可限线程，但非专用预留 | 取决于 Profile 与调度 |
| 安全 | 单租户 | GPU 级边界，仍共享节点内核 | **仅适可信负载** | 需保护守护进程 | VM 边界更强，但运营更复杂 |

平台产品描述必须**逐项写「保证」与「不保证」**：用户看到「共享 4 份」时，必须知道别人能不能吃掉我的显存、一个客户端崩了会不会影响我、忙邻居会不会拖慢我、是否共享进程与内核。

## 3. 共享让容量规划从确定性变成概率

- **Time-Slicing 四副本**：若四个 Notebook 平时各占 10%，共享效果很好；若它们在同一时段跑训练，四个同时满载，性能与显存冲突立刻出现。副本数不能按平均利用率定，要分析**同时峰值、工作负载相关性与故障影响**。
- **MIG 的硬 Shape**：可预测性来自预先保留，代价是灵活性——3g 实例空闲时，两个 1g 任务不能自动借用它的全部计算；三个 1g 空闲也不能在不重配置的情况下合成 3g。重配置还会影响该卡上现有工作负载。

一句话：**共享把「我有多少卡」变成「我大概能同时跑几个」，这个「大概」必须写进 SLO。**

## 4. 多租户首先是信任模型

同一研发团队的多个服务共享，与两个互不信任的客户共享，不是同一个安全问题。前者可以接受共同故障与性能干扰；后者需要显存、地址空间、管理权限与数据残留的强边界。

正确顺序：**平台 API 先要租户与数据敏感等级，再推荐资源形态**。不能让用户只勾「便宜 GPU」，后台就用 Time-Slicing 承载任何负载。敏感等级高的强制整卡、MIG、vGPU 或更强的节点/VM 隔离。

而且要记住隔离是层级：进程 → CUDA 上下文 → GPU 实例 → 设备 → 主机 → 集群。即使 MIG 提供硬件分区，也仍共享物理卡、驱动、节点内核、电源与 PCIe；高风险租户可能仍需独占节点或 VM。

## 5. 网络与拓扑

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l08_01.png" width="78%" alt="AI 集群网络与拓扑" />
  <p>图 2：机内 NVLink、机间 IB/RoCE、多 rail 拓扑共同决定集合通信效率</p>
</div>

三条原则（和前面几期一致，但在平台层要落到调度）：

1. **TP / EP 留在节点或超节点内**：它们通信最密集，跨层就崩；
2. **PP 可跨机，DP 放最外层**：通信量相对小，能容忍更高延迟；
3. **GPU 与 NIC 的亲和性是调度输入**：不是部署后的偶然结果。

平台要做的事：

- 把 GPU 型号、互联能力、NIC 与 rail 暴露成**可调度属性**（标签或 DRA 参数），而不是让用户记节点名；
- 多网卡机器必须显式配置 `NCCL_SOCKET_IFNAME` / `NCCL_IB_HCA`，否则 NCCL 可能选到 docker 网卡；
- 明确 IB 与 RoCE 的差异：IB 延迟更低、生态封闭；RoCE 便宜但依赖 PFC/ECN 调好；
- **网络是共享故障域**：一个租户的大流量可能拖慢另一个租户的集合通信，多租户平台要有带宽隔离或独立网络面。

## 6. 存储与制品：按访问模式选，而不是背优缺点

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l09_01.png" width="78%" alt="制品存储与分发" />
  <p>图 3：数据集、Checkpoint、权重、镜像、Pipeline Artifact 的访问模式完全不同</p>
</div>

### 6.1 五类制品

| 制品 | 访问模式 | 发布语义 |
|---|---|---|
| 训练数据集 | 大规模读多、多 Epoch 多 Worker 重复读 | Shard + Manifest（大小、校验、Schema、版本） |
| Checkpoint | 周期写、需要一致恢复点 | 先写临时版本 → 校验 → 生成 Manifest → 原子更新 `latest` |
| 模型权重 | 大对象、读多、不可变 | 按 Digest 固定；Tag 只是发布入口 |
| 容器镜像 | 按层分发、运行时复用 | Manifest + Digest，代码镜像与权重分离 |
| Pipeline Artifact | 数据 + 血缘节点 | URI + Digest + 类型 + 生产步骤 + 输入 |

三条推论：

- **数据集引用 Manifest Digest**，不要枚举一个会变的目录；
- **Checkpoint 的价值是「能恢复到一致 Step」**，不是「文件写完」；多 Rank 分片任一缺失整体不可用；
- **单文件校验通过 ≠ 模型版本完整**，要校验所有必需对象、总大小与 Digest。

### 6.2 七个轴

任何制品都能沿七个轴定位：**对象大小、文件数量、读写比例、并发消费者、共享范围、一致性要求、寿命**。存储选型是这些轴的组合结果，不是「对象存储 vs 文件系统」的站队。

两个必须算的放大：

- **读放大**：4 个节点各下载 120 GiB 模型 → 源站流量 480 GiB；
- **写放大**：三副本写入 120 GiB 逻辑数据 → 后端约 360 GiB 原始容量（还没算元数据、校验与日志）。

对用户展示逻辑容量，做容量规划时用物理放大。

### 6.3 一致性不是一个开关

对象写入可见性、目录列举、Tag 解析、缓存更新、文件锁与快照语义，属于不同的「一致性」。即使后端提供强读后写，**应用分多对象发布仍需 Manifest 与提交协议**。

一致性目标要写成用户动作：部署引用某 Digest 时所有节点读到相同字节；恢复读 `latest` 时得到完整 Checkpoint；Pipeline 重放时输入版本不变。

### 6.4 生命周期与垃圾回收

- 容器临时文件随 Pod 删除；本地模型缓存随节点维护可丢；
- Checkpoint 按 RPO 与成本定保留策略（每 10 分钟写一次 ⇒ 最多丢约 10 分钟）；
- 训练数据可能长期保存，法规数据还有 Legal Hold；
- **GC 要按引用可达性**：Digest 可能被多个 Tag、部署、实验引用，不能看到某个 Tag 删除就清 Blob；先算活跃引用，再设延迟删除窗口。

### 6.5 不要把对象存储当文件系统

对象是 Key→Blob，**Rename 通常不是本地元数据原子操作**，随机小写与频繁 Append 也不自然。FUSE 挂载能兼容文件接口，但不自动获得完整 POSIX 语义与本地性能。

发布多对象制品的正确姿势：**不可变 Prefix + Manifest + 小指针更新**，而不是把整个目录 Rename 成「正式版」。

## 7. 一个选型速查

| 需求 | 建议 |
|---|---|
| 多租户小推理、显存要保证 | MIG（注意 Profile 组合与碎片） |
| 内部 Notebook、负载相关性低 | Time-Slicing（明确无隔离） |
| 同一信任域内多进程共享 | MPS（限流 + 显存上限，实测性能） |
| 强隔离、不同 OS | vGPU / 独占节点 |
| 大模型权重与数据集 | 对象存储 + Manifest + 本地/节点缓存 |
| 多 Pod 读写同一份目录 | 共享文件系统（注意 POSIX 语义与性能） |

## 写在最后

共享、网络、存储是平台的物理现实：**每个「更便宜」的选项都在某个维度上放弃保证**。平台的价值不是隐藏这些取舍，而是把它们变成可选择、可解释、可验收的产品档位。
