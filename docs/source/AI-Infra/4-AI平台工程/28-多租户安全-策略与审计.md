# 多租户安全、策略与审计

## 1. 课程定位

![多租户安全与策略边界](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l28_01.png)

AI Platform 的多租户安全不是给 Namespace 加几条标签，也不是安装一个策略控制器后查看绿色状态。本文围绕控制面授权、工作负载约束、网络与数据边界、GPU 节点信任、供应链准入和审计证据建立完整模型。目标是让平台能够说明谁以什么身份，在什么条件下，对什么资源执行了什么动作；当动作越过租户边界时，系统能够在准入、运行或检测阶段做出可解释处置。

本文采用 Kubernetes v1.36 作为平台基线，Gatekeeper 使用 v3.23.0 稳定发行语义，Sigstore Policy Controller 使用 v0.15.1 稳定发行语义。版本锁定只用于保证配置和实验可复现，不代表任何未连接的真实集群已经安装这些组件。模拟实验验证确定性策略逻辑；真实路径只读采集对象与控制面证据。缺少真实上下文时结果必须是 SKIPPED，不能用模拟 PASS 替代。

## 2. 学习目标

完成后应能够独立完成以下工作：

- 根据租户是否互信、数据敏感度和攻击者能力选择 Namespace、虚拟控制面、专用节点或独立集群。
- 展开 Kubernetes RBAC 的有效权限，识别通配符、子资源、bind、escalate、impersonate 和工作负载创建形成的隐式提权。
- 使用 Pod Security Admission 的 enforce、audit、warn 和固定版本标签建立可渐进升级的工作负载基线。
- 把 NetworkPolicy、Secret、GPU 节点、存储和供应链准入组合成可验证的数据面边界。
- 区分 Gatekeeper 校验、变更、审计与 Sigstore 镜像签名、Attestation 策略的执行语义。
- 设计 Kubernetes Audit Policy、后端、留存、防篡改、检测和事件取证闭环。
- 运行本地机制模拟、23 个反例契约和真实集群只读发现，并解释 PASS、REJECTED、INCONCLUSIVE、FAIL 与 SKIPPED。

## 3. 前置知识与环境

需要理解 Kubernetes API 对象、Namespace、Pod、ServiceAccount、容器镜像和基本网络概念。模拟路径只要求 Python 3.10 及以上版本，全部逻辑使用标准库。真实路径需要 kubectl、可读取目标 Namespace 的上下文，以及按需安装的 Gatekeeper 或 Sigstore Policy Controller。真实路径不会创建、修改或删除集群对象。

建议先准备一个非生产测试集群验证负例。生产策略应从审计、警告、分批强制逐步晋级；破坏性网络隔离、权限回收和 Webhook 失败演练不进入默认批处理。tenant-baseline.yaml 是审查与 Server-side Dry Run 输入，不由运行器自动 apply。

## 4. 知识串讲

### 安全模型的四个基本问题

平台先回答资产、主体、边界和证据四个问题。资产包括数据、模型、凭证、GPU、网络身份、发布制品和日志；主体包括人、ServiceAccount、控制器、CI 系统和外部服务；边界决定共享到哪一层；证据说明策略是否真的执行。没有这四项，权限清单再长也只是零散配置。

多租户安全还要区分预防、检测和响应。RBAC、准入和 NetworkPolicy 主要预防已知越界；审计、遥测和异常检测发现未被预防的行为；凭证吊销、节点隔离和事件响应负责控制损失。平台不能要求任何一个工具独自覆盖三类能力。

## 5. 原理与工程分析

### 1. 安全问题不是权限清单

平台安全从资产、主体、信任边界、攻击路径和可接受风险开始。训练数据、模型权重、GPU 节点、服务凭证、流水线制品与审计记录的价值和暴露面不同，不能只用一份通用权限模板。

从控制面看，这一主题必须还原为主体、对象、动作和上下文。主体不能只保留显示名称，还要保留稳定身份、所属租户和委托链；对象要区分名字空间资源、集群资源、子资源与外部系统；动作要展开为真实 API 动词；上下文包括环境、策略版本、请求来源和时间。平台默认拒绝无法归属的请求，并将未知状态与明确拒绝分开。

在 AI 平台中，该问题会同时穿过 Notebook、Pipeline、训练控制器、队列、模型注册、发布控制面和 GPU 节点。租户提交的高层对象往往由高权限控制器展开成 Pod、Service、PVC 或外部云资源，因此不能只审查入口 CR。平台需要保存入口身份、控制器身份、最终工作负载身份和制品 Digest 之间的关联，使任何资源都能回到原始租户请求。

只统计已经创建的 Role 会漏掉工作负载创建、节点访问、镜像投毒和网络侧移等隐式能力。

工程实现应优先提供安全默认值和受控模板，再用准入策略阻止绕过。策略的每个拒绝都返回稳定 Reason，并记录策略 ID、版本和匹配字段。例外不是删除规则，而是带主体、范围、原因、所有者和到期时间的风险对象。未知依赖、遥测缺口或执行器不可达时，状态必须保留为 INCONCLUSIVE 或 FAIL，不能为了面板变绿而放行。

验收时从具体用户旅程逆向列出每次身份转换、资源访问、策略决策和证据落点。

落地时先在隔离环境构造允许样例和最小反例，再用 Server-side Dry Run 验证 API Server 链路，随后对少量非关键 Namespace 开启 warn 或 dryrun。观察误报、延迟和控制器兼容性后再提升到 deny。回滚是恢复上一份已验证策略和作用域，而不是临时关闭全部 Webhook。

### 2. 先定义租户

租户可以是团队、项目、客户、环境或某个工作负载。平台必须确定资源所有权、数据边界、预算边界和故障责任是否由同一租户标识承载。

把 Namespace 名称直接等同组织身份，会在项目拆分、人员流动和跨环境复制时产生漂移。

验收租户目录、身份组、Namespace 标签、队列、成本中心和审计字段是否由稳定 ID 贯通。

运行期还要监控覆盖率而不仅是拒绝数。拒绝数为零可能表示没有攻击，也可能表示策略未匹配、Namespace 未启用、Webhook 失联或审计中断。报告应同时展示请求分母、匹配率、允许率、拒绝率、未知率、策略延迟、版本和最近负例验证时间。

### 3. 多团队与多客户威胁不同

企业内部多团队常以误操作和资源争用为主，多客户场景则必须假定租户不互信并考虑主动攻击。两者对控制面、节点、网络和数据隔离强度的要求不同。

用内部协作模型承载外部不可信代码，会高估 Namespace 和容器边界能提供的保护。

验收威胁模型是否明确攻击者能力、可访问接口、敏感资产、容忍后果和升级条件。

权限和策略变化都要进入 GitOps 与发布治理。提交记录说明期望状态，API 审计说明谁把状态送入集群，控制器状态说明是否接受，负例测试说明保护是否有效。只有四类证据能够互相对应，团队才可以把声明提升为已执行控制。

### 4. 共享集群的价值与代价

共享集群提高 GPU 利用率、缩短供给时间并减少控制面数量，但扩大共同故障域与策略配置的影响范围。安全收益不能只按机器数量衡量。

为了装箱率把高信任推理服务与不可信训练代码放在同一节点，可能让节点内核成为共同攻击面。

验收共享决定是否记录信任等级、硬件隔离能力、数据敏感度、性能需求和退出路径。

当该控制与可用性发生冲突时，决策必须由预先定义的风险等级驱动。安全关键边界可以 Fail Closed，但要有高可用、容量和 Break-glass 恢复；低风险建议可先 warn。任何 Fail Open 都要产生显式事件、限定持续时间，并在恢复后复查期间放行的对象。

### 5. Namespace 是逻辑边界

Namespace 隔离对象名称并承载 Role、RoleBinding、ResourceQuota 和 NetworkPolicy 等名字空间级策略，是租户治理的基础单元。

Namespace 不会自动隔离集群级对象、节点内核、网络通信、存储后端或 API 发现能力。

验收新 Namespace 是否原子获得身份、配额、Pod 安全、网络默认拒绝、审计标签和生命周期策略。

### 6. 虚拟控制面模型

每租户虚拟控制面可隔离 API 对象、集群级扩展和部分控制面负载，适用于需要近似集群管理体验但仍共享节点池的场景。

虚拟控制面不会自动解决共享工作节点上的内核、设备、网络和存储风险。

验收同步器权限、宿主控制面边界、租户 CRD 能力、节点映射、日志归属和故障传播路径。

### 7. 独立集群模型

当法规、客户合同、内核攻击面、专属网络或升级节奏要求强隔离时，独立集群通常比层层补丁更容易证明边界。

把独立集群当成绝对安全会忽略供应链、云账号、集中 GitOps 和共享身份提供方等共同依赖。

验收集群账户、密钥、网络、日志、镜像仓库和运维权限是否也按租户或信任域隔离。

### 8. 分层隔离决策

隔离可分为逻辑、控制面、节点、设备、网络、存储和组织流程多个层次。平台应按风险组合，而非在共享与独占之间二选一。

没有升级规则的分层模型会让例外不断积累，最终所有高风险工作负载仍留在默认共享池。

验收是否存在从共享 Namespace 升级到专用节点、虚拟控制面或独立集群的可执行门槛。

### 9. 身份先于授权

认证回答调用者是谁，授权回答该身份可做什么。人类、服务账号、控制器、CI 系统和外部工作负载要有可区分身份。

多个自动化共用一个长期 ServiceAccount 令牌，会让审计无法定位责任并扩大凭证泄漏影响。

验收每个运行时身份的签发者、受众、有效期、绑定对象、轮换和撤销路径。

### 10. 人类身份联邦

人类访问宜通过统一身份提供方、组织组和短期凭证进入集群，避免在各集群维护静态用户证书。

离职或调岗只在单个 RoleBinding 中修补，容易留下其他集群和工具中的孤儿权限。

验收身份组到平台角色的映射、强认证、会话时长、紧急访问和离职回收证据。

### 11. 工作负载身份

工作负载身份应与 Namespace、ServiceAccount 和具体控制器绑定，并限制令牌受众与寿命。没有 API 需求的 Pod 应关闭自动挂载令牌。

把默认 ServiceAccount 当作便利凭证，会让同一 Namespace 内所有 Pod 共享不必要的 API 能力。

验收 TokenRequest、受众、轮换、投射卷、外部云身份映射和默认账号权限。

### 12. 身份传播与代理

Gateway、Notebook、Pipeline 和训练控制器常代表用户执行后续请求。平台必须区分原始用户、代理服务和最终工作负载身份。

把用户令牌直接传入所有容器会增加泄漏面；完全丢弃原始身份又会破坏归责。

验收委托链是否使用受限令牌或结构化声明，并在审计事件中保留原始主体与执行主体。

### 13. 紧急访问

Break-glass 权限用于身份系统或策略控制面失效时恢复服务，应独立审批、短期生效、强审计并在使用后复核。

把 cluster-admin 永久绑定给日常运维组，会把紧急通道变成普通路径。

验收紧急凭证是否离线保护、双人批准、自动过期、实时告警并具备事后回收证明。

### 14. RBAC 纯加法语义

Kubernetes RBAC 规则只增加允许能力，没有显式拒绝规则。多个 RoleBinding 和 ClusterRoleBinding 的权限会合并。

试图用一个较小 Role 覆盖既有大权限不会收回能力，容易造成错误安全感。

验收应计算主体的有效权限集合，而不是只审查最近一次提交的 Role。

### 15. Role 与 ClusterRole 边界

Role 只能描述某个 Namespace 内的权限；ClusterRole 既可描述集群级资源，也可被 RoleBinding 限制在单一 Namespace 授予名字空间资源权限。

为了复用规则直接创建 ClusterRoleBinding，会把原本希望局部授权的能力扩展到所有 Namespace。

验收绑定类型、作用域、主体和规则资源范围是否与租户合同一致。

### 16. 通配符权限

资源、API 组或动词中的通配符会自动覆盖未来新增能力，在平台快速演进时尤其危险。

今天看似只包含普通资源的 API 组，明天新增高权限子资源后，旧通配符会静默获得能力。

验收策略应拒绝租户通配符，并定期将有效权限与允许清单做差异分析。

### 17. 子资源权限

pods/log、pods/exec、pods/attach、serviceaccounts/token 和资源 status 等子资源具有独立安全含义。

只看到 pods 的 get 权限就认为无法执行命令，会漏掉单独授予的 pods/exec。

验收以 API 请求路径展开资源与子资源，并对交互执行、端口转发和令牌签发单列门禁。

## 6. Pod 安全标准与运行时隔离

### 18. Pod Security Standards 三档与命名空间分级

Kubernetes 内置 Pod Security Admission（PSA）定义三档累积策略：Privileged（不设限）、Baseline（禁已知特权升级：hostNetwork/hostPID、privileged、危险 capabilities）、Restricted（在 Baseline 之上强制 runAsNonRoot、seccomp RuntimeDefault、drop ALL capabilities、只读根文件系统等）。通过命名空间标签 `pod-security.kubernetes.io/enforce|audit|warn` 按档执行，enforce 拒绝、audit/warn 只记录——先用 audit 模式跑一个观察期再切 enforce，避免一刀切打挂存量作业。

AI 平台不能全集群一刀 Restricted：GPU 诊断（Nsight/DCGM profiling）、RDMA 与 hostPath 数据挂载常需要 Baseline 甚至豁免。合理做法是命名空间分级——租户业务命名空间 Restricted，平台组件与诊断专用命名空间 Baseline/Privileged 并单独审批，豁免清单带过期时间。

验收租户命名空间 enforce=restricted 覆盖率、豁免清单是否全部带审批与过期、audit 事件是否有人消费。

### 19. Seccomp、AppArmor 与 capabilities 治理

seccomp 限制系统调用面（RuntimeDefault 屏蔽约 40+ 高危调用），AppArmor/SELinux 限制文件与能力访问，capabilities 把 root 拆成细粒度权限。三者与「非 root 运行」叠加才构成纵深：只设 runAsNonRoot 不 drop capabilities，容器仍可能持有 NET_RAW 等能力。

AI 镜像的常见反模式：为了装包方便以 root 构建并运行、为了 profiling 申请 privileged、为了「兼容老代码」放开 seccomp Unconfined。profiling 需求应走专用诊断通道（短期、单节点、强审计），而不是给业务容器常驻特权。

验收 privileged 容器计数为零（平台豁免除外）、seccomp 非 Unconfined 比例、capabilities 允许清单与镜像扫描结果交叉核对。

### 20. gVisor 与 Kata：不可信代码的运行时隔离

普通容器共享宿主内核，一个内核漏洞即可击穿所有租户。Notebook、Agent 沙箱、用户自定义训练代码属于不可信执行面，需要更强边界：gVisor 用用户态内核（Sentry）拦截系统调用，Kata Containers 用轻量 microVM 提供独立内核。代价是性能与兼容性——系统调用密集型负载开销明显，且 GPU 直通支持受限（gVisor 对 CUDA 栈支持不完整，Kata 需 VFIO 直通且与 MIG/时间片共享方案组合复杂），GPU 训练主链路通常仍用 runc + PSA + 网络策略组合，把 gVisor/Kata 留给 CPU 侧不可信代码。

验收不可信执行面（notebook/sandbox）是否全部落在强隔离运行时、隔离运行时清单与租户合同一致、逃逸演练（容器内探测宿主资源）被阻断。

### 21. 特权治理的闭环

PSA 是准入时检查，运行期仍可能被绕过（如先准入后 mutate、webhook 失效 fail-open）。需要周期性扫描实际 Pod spec 与准入策略做差异分析，把「准入时合规、运行时漂移」纳入 27 的故障演练科目。

验收运行态扫描与准入策略差异为零、webhook 失效策略为 fail-close 或有告警兜底、每次豁免都有到期回收记录。

## 7. 网络策略与东西向隔离

### 22. 默认互通是缺口，default-deny 是起点

Kubernetes 网络默认全通：任何 Pod 可访问任何命名空间的任何 Pod。NetworkPolicy 是**加法**语义——选中某 Pod 的策略生效后才转为默认拒绝，未选中任何策略的 Pod 仍然全通。因此多租户基线是每个租户命名空间先落 ingress + egress 双向 default-deny，再逐条放行；只写 ingress 不写 egress，被攻陷的 Pod 仍可外连与横向移动。

default-deny 之后必须显式放行的公共依赖：DNS（kube-system 53）、API Server/控制面回调、监控抓取、镜像拉取走节点侧不受影响但 init 容器的外部下载受影响。漏放 DNS 是最常见的「上了策略全挂」事故。

验收租户命名空间 default-deny（双向）覆盖率、跨租户连通性渗透测试（从租户 A Pod 探测租户 B Service）全部被拒。

### 23. 选择器边界与作业内通信

NetworkPolicy 用 namespaceSelector + podSelector 组合表达边界。AI 场景的特殊性：分布式训练作业内部需要全互通（AllReduce/参数面），策略要按「作业标签」放行组内东西向，而不是按命名空间整体放开——同命名空间可能混跑多个租户作业（12 的队列混部）。标签由平台控制器注入而非用户自填，否则租户可伪造标签越界。

ipBlock 适合放行集群外固定网段，但 Pod IP 漂移使 ipBlock 不适合表达 Pod 间策略；对节点网段的放行要警惕覆盖到别的租户 hostNetwork Pod。

验收作业内通信正常、跨作业/跨租户被拒、策略选择器标签来源为平台注入且用户不可篡改。

### 24. Cilium、mTLS 与高性能网络的取舍

原生 NetworkPolicy 止于 L3/L4。Cilium 基于 eBPF 提供身份（identity）级策略、L7 规则（HTTP path/method、DNS 域名）与策略审计日志，CiliumNetworkPolicy 支持显式 DENY 与 ServiceAccount 维度选择器；2026 年 Cilium 还把 mTLS 做进数据路径（无 sidecar 的原生双向认证加密）。sidecar 网格（Istio/Linkerd）同样提供 mTLS 与 L7 授权，代价是每 Pod 注入代理的延迟与资源开销。

与 08 的高性能网络存在硬冲突：hostNetwork Pod（RDMA 训练常用）绕过 Pod 网络栈，NetworkPolicy 对其不生效——这类作业的隔离要靠节点级隔离（专用节点池 + taint）、交换机 ACL 与作业准入审查兜底，不能宣称「上了 NetworkPolicy 就隔离了」。mTLS 加密也与 RDMA 内核旁路路径不兼容，训练参数面通常不做 mTLS，以物理/节点边界替代。

验收 L7 策略覆盖敏感服务、hostNetwork 作业有替代隔离措施并记录在租户合同、策略拒绝事件进审计（§8）。

### 25. 策略即代码与漂移

网络策略与 RBAC 一样进 GitOps（24），按租户合同生成、评审后合入；手工 kubectl 改策略属于漂移，周期性 diff 告警。策略数量增长后需要连通性矩阵测试（谁该通谁该拒）作为回归，防止一条新放行规则悄悄打通租户边界。

验收策略全部来自 Git、连通性矩阵测试进 CI、漂移 diff 为零或有审批记录。

## 8. 审计日志与合规留存

### 26. Audit 阶段与级别：记什么、记多细

Kubernetes API Server 审计按阶段（RequestReceived / ResponseStarted / ResponseComplete / Panic）与级别（None / Metadata / Request / RequestResponse）组合。Metadata 记谁在何时对什么资源做了什么动词；RequestResponse 连请求与响应体一起记。关键红线：**secrets、configmaps、tokenreviews 等敏感资源禁止 RequestResponse 级别**，否则审计日志本身成为秘密泄漏面（与 37 的秘密管理呼应）；pods/exec、pods/attach 的响应体含终端流，也需评估。

### 27. 分级策略与容量账

全量 RequestResponse 的日志量可达每请求数 KB，千节点集群日均 TB 级，成本与检索都不可持续。分级基线：高危动词（exec/attach/portforward、serviceaccounts/token、clusterrolebindings 的 create/update、secrets 的写操作）记 Metadata 或受限 Request；普通写操作 Metadata；只读与健康检查（get/list/watch 高频路径）None 或聚合。策略用审计 Policy 文件声明，按 user/group/verb/resource/namespace 精细匹配，并定期用真实流量回放验证覆盖率。

验收高危操作 100% 留痕、敏感资源无 RequestResponse、日志量在预算内且策略变更走评审。

### 28. 留存、防篡改与取证

合规留存期按法规与合同定（常见 180 天热存 + 1–3 年冷存），审计日志写入 append-only 存储（对象存储 Object Lock / WORM），与业务日志分账户隔离，防止入侵者清痕。取证依赖三件事：时钟同步（NTP 偏差会打乱事件序列）、auditID 全链关联（API 请求 → 控制器 → Pod 事件）、原始主体保留（12 的委托链中同时记原始用户与执行服务账号）。跨租户查询审计必须脱敏与授权——租户 A 的合规团队不应看到租户 B 的请求体。

验收留存期与合同一致、WORM 写入验证（尝试删除被拒）、取证演练能凭 auditID 重建一次 exec 全链、跨租户查询有脱敏与审批。

### 29. 审计的消费侧：检测与告警

日志只有被消费才有价值。基线检测规则：非工作时间的 cluster-admin 绑定、批量 secrets 读取、exec 进入非本人命名空间、break-glass 凭证使用（13）、策略 webhook 被绕过。规则命中接 26 的可观测性告警通道，定期用攻击模拟（atomic red team 类演练）验证检出率。

验收检测规则覆盖高危清单、演练检出率达标、告警到处置的 MTTR 有记录。

## 9. 供应链准入与镜像策略执行

### 30. 从生成证明到强制验证

25 负责在 CI 侧生成签名与证明（cosign 签名、SLSA provenance、SBOM），准入侧则负责强制执行——证明只有被验证才构成控制。两条主流路线：Kyverno verifyImages 规则（策略即 YAML，支持 keyless 按 identity + issuer 匹配、attestation 条件校验）与 sigstore policy-controller（专注镜像准入的轻量 webhook）。关键配置是**按 digest 而非 tag 验证**：tag 可被重推，签名必须绑定不可变 digest，准入时把 tag 解析为 digest 再校验。

验收未签名/签名不匹配镜像在全部租户命名空间被拒（含 init 容器与 ephemeral containers）、验证按 digest 执行、keyless 的 identity/issuer 白名单与 CI 身份一致。

### 31. 证明内容校验：不止「有签名」

签名只证明「谁签的」，attestation 才证明「怎么构建的」。准入策略可进一步要求：provenance 中的 builder 身份在可信清单、源码仓库与分支匹配发布合同、SBOM 存在且无高危未豁免漏洞。这把 25 的发布证明从「档案」变成「门禁」，也是模型制品（22）之外容器侧的对应控制。

验收 attestation 校验规则覆盖可信 builder 清单、绕过尝试（伪造 provenance）被拒、SBOM 门禁与漏洞平台联动。

### 32. 例外审批与失效语义

例外必须显式、短期、可审计：Kyverno PolicyException / 命名空间豁免标签都要带过期时间与审批记录，到期自动回收；紧急放行（break-glass 镜像）走 13 的双人审批通道并事后复核。另一个常被忽略的失效语义：验证 webhook 不可用时 admission 是 fail-open 还是 fail-close——failurePolicy=Ignore 意味着 webhook 挂掉期间未签名镜像长驱直入，生产应 Fail 并配 webhook 高可用，或至少对 fail-open 窗口实时告警。

验收例外全部带过期与审批、过期例外自动清零、webhook failurePolicy 与高可用配置核查、fail-open 窗口有告警。

### 33. 策略漂移与闭环

准入策略本身进 GitOps（24），与 RBAC、网络策略同一评审通道；周期性用「已知坏镜像」做准入回归（类似 27 的故障演练），确认策略没有被静默放宽。签名密钥/identity 轮换时同步更新验证白名单，避免轮换日全集群拒绝或全集群放行两个极端。

验收坏镜像回归进 CI、策略 diff 为零或有审批、密钥轮换演练通过。
