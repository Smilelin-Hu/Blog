# 多租户安全、策略与审计

## 1. 课程定位

![多租户安全与策略边界](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l28_01.png)

AI Platform 的多租户安全不是给 Namespace 加几条标签，也不是安装一个策略控制器后查看绿色状态。本文围绕控制面授权、工作负载约束、网络与数据边界、GPU 节点信任、供应链准入和审计证据建立完整模型。目标是让平台能够说明谁以什么身份，在什么条件下，对什么资源执行了什么动作；当动作越过租户边界时，系统能够在准入、运行或检测阶段做出可解释处置。

本文采用 Kubernetes v1.36 作为平台基线，Gatekeeper 使用 v3.23.0 稳定发行语义，Sigstore Policy Controller 使用 v0.15.1 稳定发行语义。版本锁定只用于保证配置和实验可复现，不代表任何未连接的真实集群已经安装这些组件。模拟实验验证确定性策略逻辑；真实路径只读采集对象与控制面证据。缺少真实上下文时结果必须是 SKIPPED，不能用模拟 PASS 替代。

## 2. 学习目标

完成后应能够独立完成以下工作：

- 根据租户是否互信、数据敏感度和攻击者能力选择 Namespace、虚拟控制面、专用节点或独立集群。
- 展开 Kubernetes RBAC 的有效权限，识别通配符、子资源、bind、escalate、impersonate 和工作负载创建形成的隐式提权。
- 使用 Pod Security Admission 的 enforce、audit、warn 和固定版本标签建立可渐进升级的工作负载基线。
- 把 NetworkPolicy、Secret、GPU 节点、存储和供应链准入组合成可验证的数据面边界。
- 区分 Gatekeeper 校验、变更、审计与 Sigstore 镜像签名、Attestation 策略的执行语义。
- 设计 Kubernetes Audit Policy、后端、留存、防篡改、检测和事件取证闭环。
- 运行本地机制模拟、23 个反例契约和真实集群只读发现，并解释 PASS、REJECTED、INCONCLUSIVE、FAIL 与 SKIPPED。

## 3. 前置知识与环境

需要理解 Kubernetes API 对象、Namespace、Pod、ServiceAccount、容器镜像和基本网络概念。模拟路径只要求 Python 3.10 及以上版本，全部逻辑使用标准库。真实路径需要 kubectl、可读取目标 Namespace 的上下文，以及按需安装的 Gatekeeper 或 Sigstore Policy Controller。真实路径不会创建、修改或删除集群对象。

建议先准备一个非生产测试集群验证负例。生产策略应从审计、警告、分批强制逐步晋级；破坏性网络隔离、权限回收和 Webhook 失败演练不进入默认批处理。tenant-baseline.yaml 是审查与 Server-side Dry Run 输入，不由运行器自动 apply。

## 4. 知识串讲

### 安全模型的四个基本问题

平台先回答资产、主体、边界和证据四个问题。资产包括数据、模型、凭证、GPU、网络身份、发布制品和日志；主体包括人、ServiceAccount、控制器、CI 系统和外部服务；边界决定共享到哪一层；证据说明策略是否真的执行。没有这四项，权限清单再长也只是零散配置。

多租户安全还要区分预防、检测和响应。RBAC、准入和 NetworkPolicy 主要预防已知越界；审计、遥测和异常检测发现未被预防的行为；凭证吊销、节点隔离和事件响应负责控制损失。平台不能要求任何一个工具独自覆盖三类能力。

## 5. 原理与工程分析

### 1. 安全问题不是权限清单

平台安全从资产、主体、信任边界、攻击路径和可接受风险开始。训练数据、模型权重、GPU 节点、服务凭证、流水线制品与审计记录的价值和暴露面不同，不能只用一份通用权限模板。

从控制面看，这一主题必须还原为主体、对象、动作和上下文。主体不能只保留显示名称，还要保留稳定身份、所属租户和委托链；对象要区分名字空间资源、集群资源、子资源与外部系统；动作要展开为真实 API 动词；上下文包括环境、策略版本、请求来源和时间。平台默认拒绝无法归属的请求，并将未知状态与明确拒绝分开。

在 AI 平台中，该问题会同时穿过 Notebook、Pipeline、训练控制器、队列、模型注册、发布控制面和 GPU 节点。租户提交的高层对象往往由高权限控制器展开成 Pod、Service、PVC 或外部云资源，因此不能只审查入口 CR。平台需要保存入口身份、控制器身份、最终工作负载身份和制品 Digest 之间的关联，使任何资源都能回到原始租户请求。

只统计已经创建的 Role 会漏掉工作负载创建、节点访问、镜像投毒和网络侧移等隐式能力。

工程实现应优先提供安全默认值和受控模板，再用准入策略阻止绕过。策略的每个拒绝都返回稳定 Reason，并记录策略 ID、版本和匹配字段。例外不是删除规则，而是带主体、范围、原因、所有者和到期时间的风险对象。未知依赖、遥测缺口或执行器不可达时，状态必须保留为 INCONCLUSIVE 或 FAIL，不能为了面板变绿而放行。

验收时从具体用户旅程逆向列出每次身份转换、资源访问、策略决策和证据落点。

落地时先在隔离环境构造允许样例和最小反例，再用 Server-side Dry Run 验证 API Server 链路，随后对少量非关键 Namespace 开启 warn 或 dryrun。观察误报、延迟和控制器兼容性后再提升到 deny。回滚是恢复上一份已验证策略和作用域，而不是临时关闭全部 Webhook。

### 2. 先定义租户

租户可以是团队、项目、客户、环境或某个工作负载。平台必须确定资源所有权、数据边界、预算边界和故障责任是否由同一租户标识承载。

把 Namespace 名称直接等同组织身份，会在项目拆分、人员流动和跨环境复制时产生漂移。

验收租户目录、身份组、Namespace 标签、队列、成本中心和审计字段是否由稳定 ID 贯通。

运行期还要监控覆盖率而不仅是拒绝数。拒绝数为零可能表示没有攻击，也可能表示策略未匹配、Namespace 未启用、Webhook 失联或审计中断。报告应同时展示请求分母、匹配率、允许率、拒绝率、未知率、策略延迟、版本和最近负例验证时间。

### 3. 多团队与多客户威胁不同

企业内部多团队常以误操作和资源争用为主，多客户场景则必须假定租户不互信并考虑主动攻击。两者对控制面、节点、网络和数据隔离强度的要求不同。

用内部协作模型承载外部不可信代码，会高估 Namespace 和容器边界能提供的保护。

验收威胁模型是否明确攻击者能力、可访问接口、敏感资产、容忍后果和升级条件。

权限和策略变化都要进入 GitOps 与发布治理。提交记录说明期望状态，API 审计说明谁把状态送入集群，控制器状态说明是否接受，负例测试说明保护是否有效。只有四类证据能够互相对应，团队才可以把声明提升为已执行控制。

### 4. 共享集群的价值与代价

共享集群提高 GPU 利用率、缩短供给时间并减少控制面数量，但扩大共同故障域与策略配置的影响范围。安全收益不能只按机器数量衡量。

为了装箱率把高信任推理服务与不可信训练代码放在同一节点，可能让节点内核成为共同攻击面。

验收共享决定是否记录信任等级、硬件隔离能力、数据敏感度、性能需求和退出路径。

当该控制与可用性发生冲突时，决策必须由预先定义的风险等级驱动。安全关键边界可以 Fail Closed，但要有高可用、容量和 Break-glass 恢复；低风险建议可先 warn。任何 Fail Open 都要产生显式事件、限定持续时间，并在恢复后复查期间放行的对象。

### 5. Namespace 是逻辑边界

Namespace 隔离对象名称并承载 Role、RoleBinding、ResourceQuota 和 NetworkPolicy 等名字空间级策略，是租户治理的基础单元。

Namespace 不会自动隔离集群级对象、节点内核、网络通信、存储后端或 API 发现能力。

验收新 Namespace 是否原子获得身份、配额、Pod 安全、网络默认拒绝、审计标签和生命周期策略。

### 6. 虚拟控制面模型

每租户虚拟控制面可隔离 API 对象、集群级扩展和部分控制面负载，适用于需要近似集群管理体验但仍共享节点池的场景。

虚拟控制面不会自动解决共享工作节点上的内核、设备、网络和存储风险。

验收同步器权限、宿主控制面边界、租户 CRD 能力、节点映射、日志归属和故障传播路径。

### 7. 独立集群模型

当法规、客户合同、内核攻击面、专属网络或升级节奏要求强隔离时，独立集群通常比层层补丁更容易证明边界。

把独立集群当成绝对安全会忽略供应链、云账号、集中 GitOps 和共享身份提供方等共同依赖。

验收集群账户、密钥、网络、日志、镜像仓库和运维权限是否也按租户或信任域隔离。

### 8. 分层隔离决策

隔离可分为逻辑、控制面、节点、设备、网络、存储和组织流程多个层次。平台应按风险组合，而非在共享与独占之间二选一。

没有升级规则的分层模型会让例外不断积累，最终所有高风险工作负载仍留在默认共享池。

验收是否存在从共享 Namespace 升级到专用节点、虚拟控制面或独立集群的可执行门槛。

### 9. 身份先于授权

认证回答调用者是谁，授权回答该身份可做什么。人类、服务账号、控制器、CI 系统和外部工作负载要有可区分身份。

多个自动化共用一个长期 ServiceAccount 令牌，会让审计无法定位责任并扩大凭证泄漏影响。

验收每个运行时身份的签发者、受众、有效期、绑定对象、轮换和撤销路径。

### 10. 人类身份联邦

人类访问宜通过统一身份提供方、组织组和短期凭证进入集群，避免在各集群维护静态用户证书。

离职或调岗只在单个 RoleBinding 中修补，容易留下其他集群和工具中的孤儿权限。

验收身份组到平台角色的映射、强认证、会话时长、紧急访问和离职回收证据。

### 11. 工作负载身份

工作负载身份应与 Namespace、ServiceAccount 和具体控制器绑定，并限制令牌受众与寿命。没有 API 需求的 Pod 应关闭自动挂载令牌。

把默认 ServiceAccount 当作便利凭证，会让同一 Namespace 内所有 Pod 共享不必要的 API 能力。

验收 TokenRequest、受众、轮换、投射卷、外部云身份映射和默认账号权限。

### 12. 身份传播与代理

Gateway、Notebook、Pipeline 和训练控制器常代表用户执行后续请求。平台必须区分原始用户、代理服务和最终工作负载身份。

把用户令牌直接传入所有容器会增加泄漏面；完全丢弃原始身份又会破坏归责。

验收委托链是否使用受限令牌或结构化声明，并在审计事件中保留原始主体与执行主体。

### 13. 紧急访问

Break-glass 权限用于身份系统或策略控制面失效时恢复服务，应独立审批、短期生效、强审计并在使用后复核。

把 cluster-admin 永久绑定给日常运维组，会把紧急通道变成普通路径。

验收紧急凭证是否离线保护、双人批准、自动过期、实时告警并具备事后回收证明。

### 14. RBAC 纯加法语义

Kubernetes RBAC 规则只增加允许能力，没有显式拒绝规则。多个 RoleBinding 和 ClusterRoleBinding 的权限会合并。

试图用一个较小 Role 覆盖既有大权限不会收回能力，容易造成错误安全感。

验收应计算主体的有效权限集合，而不是只审查最近一次提交的 Role。

### 15. Role 与 ClusterRole 边界

Role 只能描述某个 Namespace 内的权限；ClusterRole 既可描述集群级资源，也可被 RoleBinding 限制在单一 Namespace 授予名字空间资源权限。

为了复用规则直接创建 ClusterRoleBinding，会把原本希望局部授权的能力扩展到所有 Namespace。

验收绑定类型、作用域、主体和规则资源范围是否与租户合同一致。

### 16. 通配符权限

资源、API 组或动词中的通配符会自动覆盖未来新增能力，在平台快速演进时尤其危险。

今天看似只包含普通资源的 API 组，明天新增高权限子资源后，旧通配符会静默获得能力。

验收策略应拒绝租户通配符，并定期将有效权限与允许清单做差异分析。

### 17. 子资源权限

pods/log、pods/exec、pods/attach、serviceaccounts/token 和资源 status 等子资源具有独立安全含义。

只看到 pods 的 get 权限就认为无法执行命令，会漏掉单独授予的 pods/exec。

验收以 API 请求路径展开资源与子资源，并对交互执行、端口转发和令牌签发单列门禁。
