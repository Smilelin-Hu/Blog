# 多集群控制面、自助门户与平台最终架构

## 1. 课程定位

![多集群控制面与最终架构](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l30_01.png)

本文完成本系列的最终架构收束：把单集群 GPU 底座、队列与配额、AI 工作负载 API、模型交付、SRE、安全和 FinOps 连接成企业级多集群自助平台。重点不是再罗列工具，而是说明 Cluster API、Argo CD、MultiKueue、Backstage 与平台自有 API 分别承担什么职责，状态如何跨控制面传播，用户如何在不持有集群管理员权限的前提下完成训练和部署。

这里采用管理集群与工作集群分层模型。模拟路径验证集群目录、自助请求、硬约束过滤、软评分、GitOps 收敛、门户权限和二十七个反例；真实路径只读多个 Kubernetes 上下文与 Backstage Catalog。未提供真实环境时返回 SKIPPED，不把场景选择结果写成真实多集群派发结果。

## 2. 学习目标

完成后应能够：

- 设计管理集群、工作集群和平台 API 之间的责任边界。
- 解释 Cluster API 核心对象、Provider、v1beta2 合同和集群生命周期。
- 使用 Argo CD 集群注册、AppProject 和 ApplicationSet 建立 Fleet 基线。
- 解释 MultiKueue 管理集群、工作集群、managedBy、Namespace 与 LocalQueue 前置条件。
- 设计 GPU 类型、容量、驻留、能力、成本、等待与碎片联合放置策略。
- 使用 Backstage Catalog、Software Templates 和 Permission Framework 提供受控自助入口。
- 建立异步状态机、幂等、凭证最小化、观测、SLO、FinOps 和灾难恢复。
- 运行模拟、反例和真实只读发现，并正确解释 PASS、REJECTED、PENDING、DEGRADED、INCONCLUSIVE、FAIL 与 SKIPPED。

## 3. 前置知识与环境

需要理解 Kubernetes API 与控制器、队列准入、GitOps、RBAC、GPU 资源、模型交付、可观测性和成本归属。模拟只要求 Python 3.10 及以上版本，使用标准库，不需要 Kubernetes 或 GPU。真实路径需要 kubectl 以及至少一个管理集群和一个工作集群的只读上下文；可选读取 Backstage Catalog。

多集群真实实验默认不创建、升级、派发或删除资源。集群生命周期、凭证写入和工作负载派发都是有影响动作，必须在隔离环境按组织审批执行。运行器只读取 Nodes、Namespaces、CRDs 和可选 Catalog；无法访问时返回 FAIL 或 SKIPPED，不把模拟状态替代真实证据。

## 4. 知识串讲

### 统一入口不等于单一控制器

统一入口让用户用一致的产品语言表达意图，但后端仍由多个专门控制面协作。生命周期、GitOps、队列派发、训练控制器、模型服务和成本系统拥有不同调和对象与失败语义。平台通过稳定 API、事件和身份关联它们，而不是把所有职责塞进一个进程。

### 多集群首先是治理问题

集群数量增加会同时放大凭证、版本、策略、成本、故障域和数据驻留问题。没有稳定集群身份、能力库存、注册状态和 Owner 时，多集群只是更多 kubeconfig，而不是可运营 Fleet。

### 自助必须受控

自助不是把 cluster-admin 交给用户。用户选择经过审核的模板和业务参数，平台先执行身份、策略、配额、预算与能力检查，再生成声明式变更并派发。所有拒绝、等待和不确定状态都应可解释。

## 5. 原理与工程分析

### 1. 最终架构的目标

企业级自助 AI 平台要把集群生命周期、资源准入、工作负载派发、模型交付、可观测性、安全和成本归属组合成一条用户可理解的路径。架构图不是组件清单，而是对责任、状态、证据和失败边界的承诺。

在最终架构中，最终架构的目标必须落到明确的权威对象。期望状态放在声明 API 或 Git 中，实际状态来自负责调和的控制器，用户可见状态由平台聚合但不篡改原始语义。对象需要稳定 ID、Generation、ObservedGeneration、Condition、Reason、Owner 和证据引用，避免多个系统对同一事实各自给出不同答案。

跨集群实现还要区分硬约束和软偏好。身份、权限、数据驻留、模板许可、GPU 类型、Namespace 和队列前置条件属于硬约束，任一不满足就不能进入评分；等待、成本、碎片和故障风险可以在可行候选中评分。最终架构的目标相关数据若过期或映射缺失，平台返回 INCONCLUSIVE 或 PENDING，不能为了提高派发率静默放宽。

反例是：把所有系统放进一个门户页面并称为统一平台，实际仍要求用户逐个理解底层工具。这种做法通常在演示环境能工作，却在并发、网络分区、版本升级或权限变化时暴露问题。工程评审应问清控制器重启、重复请求、部分成功、远端失联和凭证撤销后的行为，而不是只验证一次成功点击。

实现最终架构的目标时，应先定义合同与状态机，再选择 Cluster API、Argo CD、MultiKueue、Backstage 或其他实现。工具提供特定能力，不自动承担平台产品责任。接口层保存用户意图和治理结果，编排层创建受控下游对象，观测层把请求 ID、租户、集群 UID、远端对象 UID、设备与成本串联起来。

从一个训练请求和一个模型服务请求出发，证明它们能经同一入口完成身份、策略、配额、派发、交付和审计。验收除正向路径外，还应注入重复 ID、模板可变、权限过宽、能力过期、驻留不匹配、工作集群前置对象缺失、GitOps 未收敛和真实上下文缺失等反例。只有 Reason 稳定、没有越权副作用、状态可恢复且证据能回放，最终架构的目标才可以进入生产平台。
