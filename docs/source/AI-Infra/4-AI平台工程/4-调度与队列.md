# 调度与队列：把一堆机器变成一个资源池

调度器的输出不是「容器起来了」，而是**一个绑定决策**。理解这一点，能避免一大类误判：Pod 有 `nodeName` 却仍 Pending，问题在镜像、卷或运行时；没有 `nodeName` 且有 `FailedScheduling`，才该看调度。

## 1. 调度器的三个边界

1. **它只做绑定**：选定 Pod 与 Node 的关系，之后由 kubelet 处理镜像、卷、Sandbox、设备注入与容器启动；
2. **它看的是快照**：调度周期基于缓存快照，「刚才明明有资源」可能在绑定前被另一个周期占用；排障要带时间与快照，别把一分钟后的 `describe node` 当证据；
3. **它不创造资源**：不会凭空造 GPU、不会扩 MIG Profile、不会建节点池、不会跨区搬卷。节点自动扩缩器是**另一个**控制回路。

所以 Pending 的处置不一定是改 Scheduler：资源形状不存在要改供应，请求不合理要改工作负载，碎片要靠评分与队列，标签漂移要修事实，扩容中要显示「等待供应」。

## 2. 一次调度尝试的阶段

```text
内部队列 → PreEnqueue → QueueSort → PreFilter → Filter → PostFilter(抢占)
        → PreScore/Score → Reserve → Permit → PreBind → Bind
```

几个容易被压平的失败点：

- **内部队列不是 FIFO**：活跃队列、退避队列、不可调度集合分开；高优 Pod 不可行时会退避，不会永远堵住队头。每个节点心跳都唤醒全部失败 Pod 会造成调度风暴，**Queueing Hint** 让插件判断值不值得重新入队；
- **PreEnqueue 回答「现在值不值得试」**（例如外部准入还没批），周期可以直接不开始；
- **PreFilter 失败 ≠ 所有节点分数低**，而是还没进入逐节点评分——排障要保留扩展点与插件身份，别把一切压成 `0/N nodes are available`。

### 2.1 Filter：可行集合的定义

设节点集合为 \(N\)，Pod \(p\) 的第 \(j\) 个硬约束为 \(C_j(n,p)\in\{0,1\}\)：

$$
F(p) = \{\, n \in N \mid \forall j,\ C_j(n,p) = 1 \,\}
$$

**任一约束为 0，该节点就不在集合中。** 这个式子最有用的地方是揭示一个常见误判：

> 节点甲剩 4 卡但内存只剩 100 GiB；节点乙剩 2 卡但内存 500 GiB。Pod 要 4 卡 + 300 GiB。
> 按 GPU 看甲可行，按内存看乙可行——**但交集为空**。

「总资源足够」只证明了若干资源在集群层面的和，没有证明**存在一个节点让所有约束同时为真**。

### 2.2 PostFilter 与 Score

可行集合为空时，PostFilter 尝试恢复（默认是抢占）：能否移除低优先级 Pod 让目标变得可行。但机型标签、不可访问卷、硬反亲和、缺失 MIG Profile、更高优先级占用这些原因，**移除受害者也无效**。

可行集合非空后：

$$
S(n,p) = \sum_k w_k\, s_k(n,p),\qquad n \in F(p)
$$

权重改变**偏好**，不改变**可行集合**——一个因缺 GPU 被 Filter 淘汰的节点，Binpack 分再高也复活不了。

### 2.3 Reserve 只是内部承诺

Reserve 在调度器内部为 Pod 保留逻辑资源，防止并发周期重复使用；它**不等于** API 已绑定，也不等于设备已配置完成。

## 3. 碎片：AI 集群的常态

碎片的三个来源：

- **组不可拆**：TP=8 的副本需要同节点 8 卡，节点剩 7 卡就是废的；
- **形状不匹配**：小任务把大卡填满，大任务排不进来；
- **跨代混插**：不同显存/互联的卡混在同一池，账本上都是 `nvidia.com/gpu`。

主要手段：按组装箱（前面第 3 篇）、按型号分池（ResourceFlavor）、评分偏向紧凑（Binpack）或分散（Spread）、以及允许小任务借用但可被抢占。

## 4. Gang Scheduling：作业级原子性

分布式训练的成员必须**同时进入**，否则先到的成员占着卡等不到对端，既浪费又可能死锁。

Gang Scheduling 的语义是：整个作业的 `minMember` 都满足时才一起放行，否则一起等待。代价是「为了等一个成员，所有成员都在等」，所以需要：

- 队列层面的准入顺序（避免大作业永远等不到）；
- 超时与回退（等太久就放弃，释放已保留资源）；
- 与优先级、抢占、配额配合。

### 5.1 六个对象的分工

| 对象 | 归属 | 作用 |
|---|---|---|
| Job / JobSet / TrainJob / RayJob | Namespace | 用户提交的业务对象 |
| Workload | 集群 | **准入单位**，含一个或多个 PodSet |
| LocalQueue | Namespace | 团队提交入口，引用 ClusterQueue |
| ClusterQueue | 集群 | 配额与政策（Flavor 名义额度、借用、抢占、公平） |
| ResourceFlavor | 集群 | 资源品类（型号/池/拓扑） |
| Cohort | 集群 | 多 ClusterQueue 间的额度共享 |

要点：**Workload 不等于运行 Pod 清单**，它是准入合同与状态载体（QuotaReserved、Admitted、Evicted、Finished）。

### 5.2 三种「配额」不要混

| 机制 | 作用时间 | 约束什么 |
|---|---|---|
| ResourceQuota | 创建对象时 | Namespace 内资源请求总量的安全上界 |
| ClusterQueue Quota | 准入时 | **同时**保留/使用的资源量 |
| 累计预算（GPU·小时） | 跨时间 | 月度/项目预算，需 FinOps 或 AdmissionCheck |

所以「每月一万 GPU 小时」**不能**写成 `nominalQuota: 10000`——名义额度的单位是资源数量，不是时间。

### 5.3 三个 Feasible 要分别显示

用户提交 8 卡训练，门户至少给三个判断：

- **QuotaFeasible**：队列与 Cohort 能否给出对应 Flavor 的额度；
- **PlacementFeasible**：当前节点形状与拓扑放得下吗；
- **Provisionable**：自动供给能在期限内补齐吗。

只显示 Pending 会让用户无从行动——额度不足找队列管理员，碎片找调度团队，售罄找供应团队。

### 5.4 长驻服务需要不同的预算语义

训练 Job 有完成点，释放额度后下一个 Workload 才能跑；推理 Deployment 长期存在，直接塞进同一等待模型会永久占用名义额度。

常见做法：给在线服务独立 ClusterQueue 或 Flavor，批作业只能借用可回收部分；服务声明「最低副本保底 + 弹性副本借用」。**不能让开发训练抢占生产最小副本，也不能让过度保守的服务配额让夜间 GPU 永久空闲。**

### 5.5 Cohort：共享的收益与风险

同一 Cohort 内的 ClusterQueue 可借用彼此闲置额度，回收时按策略与优先级。共享提高利用率，也扩大策略影响面：一个队列的高借用上限可能吃掉整棵树的闲置资源，错误的回收策略会直接终止别人的作业。**Cohort 设计必须由资源所有者共同确认。**

### 5.6 字段所有权：避免双重控制

父 Job 由它的 Operator 管，Kueue 管 Suspend 与 Workload 准入，kube-scheduler 管绑定。每个字段要有单一权威。不能另写控制器同时改 Job 的 Suspend，也不能让两个 ClusterQueue 控制同一个 Workload——双控制会产生状态震荡与配额泄漏。

集成升级时应做「字段所有权合同测试」：谁创建 Workload、谁更新 Admission、谁解挂 Job、谁在 Evicted 后重新挂起、谁写 Finished。

## 6. Volcano 与混部

Volcano 面向批处理与 AI：作业级调度、Gang、队列权重与公平、以及在线/离线混部。

混部的核心是**资源超卖与隔离**：离线任务用低优先级填谷，在线任务高峰时抢占。三条纪律：

1. 抢占必须能真正释放（检查点、可中断点）；
2. 在线侧要留 headroom，否则抢占会变成事故；
3. 混部必须有性能隔离证据（同卡共享、NUMA、网络带宽都可能互相伤害）。

## 7. 拓扑感知与 DRA

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l14_01.png" width="78%" alt="拓扑感知调度" />
  <p>图 4：Flavor 把「同名 GPU」拆成真实品类，拓扑约束决定组能否凑齐</p>
</div>

- **ResourceFlavor**：用节点标签/污点把配额绑到品类（`a100-on-demand`），扣减的仍是 `nvidia.com/gpu`——它是「配额分类」，不是新资源名；
- **拓扑约束**：同节点、同机架、同超节点等要求要在准入与放置阶段同时表达；
- **DRA**：用 ResourceClaim + 结构化参数表达「显存 ≥ X、需要 NVLink、允许共享」，比「整数 + 偏好」更精确。

判断标准：需要**跨节点属性选择**或**受控共享**时，用 DRA 类模型；只是简单整卡分配，传统扩展资源更省心。

## 8. 弹性与 Spot：容量是时间的函数

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiinfra_y4_l15_01.png" width="78%" alt="弹性容量" />
  <p>图 5：节点自动扩缩、Spot 中断与中断治理共同决定「有效容量」</p>
</div>

四件事必须一起设计：

1. **扩容有延迟**：节点供给 + 驱动就绪 + 镜像/权重下载 + 模型加载，任何一段都可能几十秒到几分钟；
2. **缩容要排空**：摘流 → 等在途完成 → 释放；直接删 Pod 会造成中断；
3. **Spot 中断治理**：提前通知（若有）→ 保存检查点 → 迁移或重建 → 记录中断原因；
4. **预算与预热联动**：warm pool 的 idle 成本与冷启动违约成本比较（前面第三期的经济模型）。

**容量规划要按「分钟级可用容量」而不是「名义节点数」**：扩容中的节点不产生吞吐。

## 9. Slurm 与 Kubernetes 的边界

| 维度 | Slurm | Kubernetes |
|---|---|---|
| 强项 | 紧耦合 HPC、拓扑与配额表达成熟 | 生态、声明式、服务与作业统一 |
| 弱项 | 云原生服务编排弱 | 批调度语义需额外组件补齐 |
| 典型分工 | 大训练集群的作业调度 | 推理服务、平台入口、周边生态 |

不少企业是「Slurm 跑训练 + K8s 跑服务」，此时平台层要解决的是**统一身份、统一制品、统一成本归属**，而不是强行把两边合并成一个调度器。

## 写在最后

调度这一层的结论可以写成三句：**资源够 ≠ 放得下**（碎片是形状问题）、**排队是产品**（原因要分类、状态要可行动）、**容量是时间函数**（扩容有延迟、缩容要排空）。
