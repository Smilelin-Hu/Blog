# AI 资产的发现与管理：从公共资源到可回放执行

Agent 的行为不只取决于模型：一次调用看到哪些指令、可用哪些方法、能连接哪些外部能力，都会改变执行过程与结果。当 Agent 数量、团队与运行环境增多，Prompt 被复制到不同仓库、Skill 散落在本地目录、MCP 的工具说明与运行端点分别维护、协作 Agent 由不同平台发布——能力资产从局部内容演变为**多 Agent 共同依赖的公共资源**。团队不仅要知道资源存在哪里，还要回答：哪个版本可以用、一次任务实际用了什么、一次变更影响哪些 Agent、运行中如何找到当前任务需要的能力。核心判断：**Prompt、Skill、MCP 与 Agent 不只是开发阶段的配置，而是运行时改变 Agent 行为与能力边界的依赖；它们需要符合各自特点的内容建模与验证方法，同时共用稳定标识、版本、生命周期、发布记录与权限管理**。承载注册、版本、治理、发现与分发的基础设施称为 Agentic Resource Registry，源文以 Nacos 为参考实现（官方产品名 AI Registry，实践基线 Nacos 3.3）。

## 1. Registry 定位与五类资源

定位演进是三段线：Config 回答「应用怎样运行」，Naming 回答「服务实例在哪里」，AI Registry 回答「Agent 当前有哪些经过治理的能力可以使用」。

| 资源 | 核心内容 | 验证与消费 |
| --- | --- | --- |
| Prompt | 指令、模板、变量与输出约束 | 渲染校验、Schema、固定评测集；Prompt Resolver 渲染 |
| Skill | SKILL.md、脚本、资料与依赖构成的能力包 | 包完整性、来源、脚本与依赖安全；Skill Loader 按需加载 |
| MCP Server | 服务说明、Tool、Resource 与协议信息 | Schema 差异、协议兼容、认证与调用样例；MCP Client 调用 |
| Agent | 版本化调用接口、协议原生描述与声明端点 | 内容校验、接口协议、安全要求，运行行为由外部评测补充；协议客户端交互 |
| AgentSpec | Agent 组装配置、资源引用与附属文件 | Manifest、依赖解析、版本锁定、构建验证；构建部署启动阶段解析 |

五类共用名称、版本、生命周期、可见范围与发布记录，但**不能因此忽略各自的验证方法与运行方式**。通用标识 `namespaceId + resourceType + resourceName`，版本再加 `version`；逻辑资源存描述、可见范围、业务标签，资源版本存内容、作者、状态、发布信息；有运行地址的资源关联端点状态，但**地址变化不覆盖已发布的能力版本**。

## 2. Prompt：结构化模板、变更分类与有效 Prompt

可发布的 Prompt 是结构化内容而非完整字符串，五个组成：指令层（来源明确、顺序稳定，**低优先级不能覆盖高优先级规则**）、模板与变量 Schema（名称/类型/必填/默认值/长度限制）、输入输出要求（格式与结构化 Schema，用于判断兼容性）、运行依赖（适用模型、所需工具、知识来源）、验证材料（正向与边界样例、评测集、评价标准）。变量替换须在受控渲染中完成：用户输入、检索结果、工具返回值作为数据经长度类型转义进入指定位置，**不应先与模板随意拼接再交由模型判断哪些属于指令**。依赖须显式记录——要求调用 `query_order` 并按指定 Schema 输出时，工具名、参数定义、输出 Schema 都是运行条件，缺依赖则正文完整也不可运行。

变更分三类：**文字修订**（预期不改目标与输出结构，仍需评测确认）、**接口变化**（增必填变量、改输出 Schema、调工具名，直接影响调用方适配）、**行为变化**（改判断规则、处理步骤、拒绝范围，形式不变也可能改变实际行为）。分类帮助理解风险但不能代替评测：**版本号首先承担唯一标识作用，兼容性不能凭语义化版本推断**。共用 Prompt 须维护反向引用，发布前查看使用方、生产绑定方式与历史调用规模。评测看三层：结构（变量完整、输出过 Schema、引用工具存在）、任务（固定样例比准确性完整性拒绝行为与边界）、运行（延迟、Token、模型工具版本影响）。**评测记录必须关联 Prompt 版本 + 模型版本 + 推理参数 + 工具定义 + 评测集版本，只记总分无法说明变化来自 Prompt 修改还是环境变化**；结构化输出单独统计格式通过率，含判断规则的看错误类别分布而非平均分，高风险场景人工抽查。**评测结果是评审输入，不是自动发布指令**。

发布可固定精确版本，或绑定 `stable`、`canary` 标签由平台调整指向；**历史版本内容始终不变，变的是标签与版本的指向关系**。灰度须按业务关系划分：输出字段改了而调用方未适配，少量随机请求也可能造成完整链路失败。回滚把标签指回最近已验证版本并记录原因执行人影响范围；**长任务不宜执行中换 Prompt，较稳妥的是任务或会话开始时解析一次版本，在该执行边界内不变**。资产库存的是模板，模型实际接收的是渲染装配后的结果，由此引出「有效 Prompt」：

```text
有效 Prompt = Prompt 版本 + 变量快照 + 模型与参数
              + 工具定义版本 + 策略版本 + Context 来源
```

运行系统为该组合生成可查询指纹并保存各部分精确版本或摘要，敏感变量记受保护值、摘要或引用位置，但须能判断两次执行是否条件相同；记录最终进入 Context Manifest。Nacos 以 `namespaceId -> prompt -> promptKey` 唯一标识，标签查询时解析使内容独立于代码发布，**运行记录仍须保存解析后的精确版本，不能只留后来可能移动的标签**。Registry 管模板的权威版本与获取，变量取值、模型参数、检索内容仍由 Harness 装配——区分两层才不会把「模板相同」误认为「最终输入完全相同」。

## 3. Skill：完整能力包、摘要覆盖与可信准入

管理对象是**完整能力包而非一份说明文件**：SKILL.md、manifest.yaml、scripts、templates、references、tests、LICENSE。Manifest 含名称版本维护者、能力描述与触发条件、输入输出、兼容环境、依赖与所需工具、权限范围与资源限制、来源许可证；脚本声明入口、解释器版本与依赖锁定；参考资料区分开始加载与按需读取；**凭据不能保存在 Skill 包中**。描述须表达能力边界（「数据分析助手」过于宽泛），发现元数据本身也是发布内容。发布后**包内容与依赖锁定不可覆盖，摘要必须覆盖完整包**——只对 SKILL.md 算摘要会漏掉脚本变化。兼容性看依赖条件（要求 Python 3.10 而环境 3.12、或依赖未开放工具即不可用）；依赖其他 Skill 时声明版本范围加锁定清单，**避免上游标签移动使下游未发新版就改变行为**，同一版本号对应相同摘要。验证三步（结构/依赖/受控环境任务验证）另加脚本危险命令与敏感路径、运行时下载、混淆内容、已知漏洞与自然语言诱导检查；**检查系统不直接修改待发布内容，发现问题退回草稿**。

废弃分三档：普通废弃（留迁移时间）、停止分发（不再新安装）、安全撤回（阻止新加载并通知）。外部 Skill 可信准入六阶段：来源核实 → 完整性校验（签名与摘要）→ 静态检查 → 隔离验证（无生产数据、无长期凭据）→ 人工评审 → 内部发布（固定版本与摘要后才进发现范围）。**签名与摘要证明来源与未被替换，不证明内容无风险**。运行时不继承 Agent 全部能力：实际权限不超过 Manifest 声明，默认禁网按需开放指定服务，文件限任务目录，短期凭据由运行环境注入。发布后定期重检，关联 Skill 摘要 + 依赖摘要 + 工具版本 + 策略版本；风险处置先停新安装与新解析，再按严重度通知、停加载或中止实例，反向引用列出受影响 Agent。Nacos Skill Registry 自 3.2.0 起，状态 draft/reviewing/online/offline，上线版本不可改须 Fork 新草稿，skill-scanner 作为 Pipeline 节点——**Pipeline 的意义不是宣称绝对安全，而是让扫描工具、检查结果与发布版本进入同一可审计流程**。

## 4. MCP：能力定义、运行端点与治理信息分开

三类信息变化节奏不同：**能力定义随版本发布，运行端点随部署变化，治理信息独立维护**。MCP 协议自带 Prompt 跟随 Server 版本，与企业 Prompt Registry 的独立资源不同，**不因同名视为同一版本**；端点扩缩容不产生新能力版本，Tool 参数、返回结构或说明改变才形成新版本。三种进入方式：启动自动注册；存量 HTTP/RPC 经声明与参数映射转换——**管理链路管描述发布，数据链路管转发执行，二者不混**；外部导入须补齐内部治理信息。最终形成内部唯一逻辑资源，**Agent 经内部 Registry 取治理后的引用，而非绕过直用来源地址**。

Tool 接口 = 名称 + 参数 Schema + 必填项 + 类型 + 返回结构。两点易被低估：**新增 Tool 也改变模型看到的候选能力，须评测**；**Tool 描述修改不是无行为影响**——模型靠名称与描述选工具，须比较 Schema 差异并跑代表性任务看工具选择结果。启用停用开关进审计但不改历史版本，长期移除则创新版本留迁移时间。**在线状态、端点健康、版本状态分别表达**：资源在线不等于端点健康，也不等于当前身份有访问权限。稳态 Agent 在 AgentSpec 声明名称加精确版本或标签，开放任务经 MCP Router / ARD 按任务找候选，**只把相关 Tool 说明放进 Context**。Registry 不代替 Server 执行工具，调用结果是外部数据，不自动获得高优先级指令地位；认证由运行环境按身份注入，描述中不存可用密钥。Nacos MCP Router 本身是标准 MCP Server：router 模式提供 `search_mcp_server`、`add_mcp_server`、`use_tool`，proxy 模式把 stdio/SSE 转为 Streamable HTTP。

## 5. Agent Registry 与 RAD：发现与调用分层

核心对象是**带版本的 Agent 调用描述**（公共部分 + 协议原生描述如 A2A AgentCard），**不是完整实现，不含全部 Prompt、Skill 与模型配置**。逻辑版本与运行端点分开：改能力描述、输入输出、安全要求形成新版本；加实例、迁区域、换故障端点只是运行状态变化。自动注册须处理「版本已发布但无可用端点」「端点在跑但版本已撤回」两种错位，**查询须同时考虑 AgentCard 状态 + 端点状态 + 调用权限，不能凭存在记录就认为可调用**。订阅适合长期协作，任务执行中保持已选版本稳定，端点故障在同版本健康实例间切换并记 Trace。

两个 Registry 面向不同问题：**Agent Registry 回答哪些 Agent 可被发现调用**（面向 Multi-Agent 应用与协议客户端），**AgentSpec Registry 回答一个 Agent 应如何描述、组装与分发**（面向平台、开发工具与构建部署）；先按 AgentSpec 构建再注册 AgentCard，**两者不共用版本号**。Nacos A2A Registry 自 3.1.0 起，RAD 0.1.0 在 3.3 初步完成协议无关发现：**「协议无关」不是取消协议，而是发现层用公共模型表达，调用接口保留协议名称版本与原生描述，实际消息仍由 A2A 等客户端完成**。五操作：Search（轻量候选目录，不承诺健康端点）、Discover（精确在线版本 + 摘要 + 协议原生描述 + 端点的完整快照）、Watch（复用 Discover，完整替换快照，可轮询实现）、Register（发布者提交完整 Endpoint Batch、运行版本与兼容版本范围）、Deregister（移除后注销整份运行发布）。**「可能适合」与「当前可以调用」是两个判断**；运行端点记录部署实现版本及其可服务的 Agent 版本范围，避免升级期返回不兼容实例。RAD 是 ARD 发现 Agent 的可选专门路径而非平行竞争体系；版本上下线改发现投影，Register/Deregister 维护运行地址，**不通过端点变更覆盖已发布定义**。

## 6. 统一变更评审与资源中心

草稿不被运行时查询返回；提交评审即固定候选内容与摘要，检查针对同一份内容；要求修改回草稿，已发布版本不变。**评审通过、发布形成不可变版本、在线状态与标签决定可发现获取——三者须区分**。Pipeline 是有序节点：格式元数据与引用完整性 → 安全扫描与依赖检查 → 任务评测，拒绝即停止并返回可理解原因。**检查过程不修改候选内容**——自动修复会使发布内容与提交评测时查看的不一致。自动结果不代替人工判断（负责人确认目的、业务影响、权限、迁移与限制，跨团队资产须主要使用方参与）。评测记录关联资源类型、名称、候选版本、内容摘要、评测集版本、模型与运行时版本、策略版本、工具版本、时间，以及人工评审结论与例外。**内容依赖的关键条件变化则原评测不能沿用；版本号未变但摘要不一致也停止发布**。紧急强制发布须记录原因、风险接受人、影响范围与恢复目标，上线后提高观察强度补验证。发布后以灰度与 A/B 比较成功率、修正率、延迟、成本与安全事件；**运行反馈生成改进建议与候选草稿，不直接修改在线内容**。Nacos 3.3 已把五类资源纳入通用 Pipeline，Agent 以 AGENT 类型进审核；资源校验与远程行为评测区分，后者可由外部系统完成后关联同一版本。**「资源已登记」与「允许进入生产范围」是两个状态**。

资源中心提供统一标识、生命周期、权限、评审与运行时入口，**不是把资源改造成同一种内容，也不是用一种协议替代各自使用方式**。逻辑资源（稳定名称/Namespace/类型/负责人）与资源版本（版本号/摘要/提交记录/状态）分开；**结构化引用（Namespace + 类型 + 名称 + 版本选择方式）替代偶然文件路径或固定地址**；Resolver 解析为唯一版本加摘要，**运行记录保存解析结果不能只记标签**；已发布内容不可覆盖；生命周期草稿/评审中/已评审/在线/离线，下线不等于删除；**可见范围（是否出现在列表搜索）与鉴权（能否读取修改发布）承担不同作用**；双向引用支撑影响分析。内部六部分：权威 Registry、AI 资源内容存储（大体量包，经摘要与版本关联）、发布 Pipeline、发现索引、Policy Engine（按身份/Namespace/环境/权限/风险等级判断）、Resolver。职责须清晰：**检索结果不能替代版本解析，存储中有文件不表示该版本仍可用，端点健康不表示当前身份有调用权限**。索引属派生数据可重建，版本状态权限摘要以 Registry 为准；索引任务记录来源版本、分段策略与向量模型，靠增量、重试、Backfill 与定期核对收敛；**旧索引检索到已下线资源，返回前仍须按 Registry 当前状态再判断；描述与正文来自不同版本时拒绝生成混合索引**。管理链路（编辑评审扫描索引）与运行链路（查询解析下载端点发现变更通知）在接口与容量上分开；运行链路缓存项绑定精确版本与摘要，Registry 暂不可用时按策略继续用已验证版本，不允许旧版本的高风险任务则停止并说明原因——**不能把一次查询失败解释为「使用任意可用内容」**。

## 7. 稳态声明式依赖与动态 ARD/RAD 发现

稳态 Agent 的职责与主要依赖发布前已明确，「稳态」不表示全写进代码，而是用哪些 Prompt、Skill、MCP 与协作 Agent 可由配置或 AgentSpec 预先声明（客服分类、合规审核、固定流程数据处理属此类）。无论高代码框架还是通用智能体，获取过程都是「声明引用、解析版本、校验内容、加载或连接、记录结果」，框架差异只在接入位置。三种绑定时机：**构建期绑定**（与 Agent Release 一起固定、离线可用、复现清晰，更新依赖须重新构建发布）、**部署期解析**（同一 AgentSpec 按环境解析、发布物存 Lock Manifest，CI/CD 须能访问资源中心并校验依赖）、**启动期拉取**（资源独立更新交付快，依赖 Registry 可用性，需缓存与一致性策略）。Resolver 先按身份与环境检查可见范围，再解析版本或标签、验证生命周期兼容条件与依赖，返回内容位置摘要或端点；Loader 取得后再次校验并把实际结果写入 Lock Manifest。**重点是确定性而非搜索范围**：即使用标签，运行记录仍存当时解析出的版本，MCP 与 Agent 还记录实际端点，使版本变化与实例变化可分别分析。集成上高代码经 SDK 初始化调 Resolver、CI/CD 用 CLI 生成锁定清单、多运行时共享走 Sidecar；通用智能体由同步组件把已解析版本放入原生目录并存来源摘要——**接入不应要求框架放弃原有使用方式，而是在加载或连接前补充统一的版本、权限与完整性检查**；须避免同名本地文件静默覆盖 Registry 版本，本地调试修改标记为未发布内容并在记录中区分。更新先在旁路下载校验，确认运行时工具依赖端点均满足再切换；**任务开始后 Prompt 与 Skill 版本原则上稳定**，跨小时或天的工作流可在阶段边界重新解析并在 Trace 记切换点。失败按资源性质处理：非关键说明可继续用本地已验证版本并告警，涉及安全策略或法规的 Prompt 可能不允许过期缓存，此时暂停新任务；**缓存同样校验摘要与有效状态，不能因位于本地就绕过撤回信息**。生产 Agent 不应每轮调用前重新解析标签，**在构建、部署、启动或任务开始等明确边界解析一次**；端点可在同版本内按健康切换，内容版本不变。

动态 Agent 任务范围随请求与状态变化（通用运维 Agent 可能先处理容器异常再转向数据库性能），无法预先列出所有能力；全部预先绑定会使配置膨胀、无关说明占用 Context 并增加选错概率。ARD（Agentic Resource Discovery）在调用之前按当前任务发现可能需要的资源，位于意图判断与资源使用之间，回答「当前任务适合使用什么」，**不负责执行 Skill、调用 Tool 或代替另一个 Agent 完成工作**（社区 ARD v0.9 为开放提案，Nacos 3.3 在 AI Registry 之上提供按意图发现）。输入不应只有一条未经处理的用户原文，而是结合目标、已有信息与运行限制形成结构化 Capability Requirement（任务描述、期望结果、数据类型、业务领域、环境、时效、允许风险等级、可用权限、成本限制）：「分析刚刚发布后订单接口延迟升高的原因」比单独搜「延迟分析」更有区分度；**须保留用户原始意图，不能为匹配资源而增加未经确认的业务事实**；敏感字段用类型范围或受保护摘要表达，**ARD 的目标是找到能力，不是取得任务全部数据**。检索侧资源形成 Document 再拆 Chunk，关键词召回处理名称产品名错误码等确定术语，向量召回补语义匹配，资源关系补充「某 Skill 依赖某 MCP Server」类信息；**向量与大模型增强属可选，未启用时基础关键词检索仍应工作**；**相关性分数只表达匹配程度，不是安全评分，也不代表平台为资源质量作保**。

相关性与使用资格是两个问题：前者决定排序，后者判断有权使用、是否在线、版本是否允许进入当前环境、风险成本是否符合限制。**高度相关但已撤回或超出授权范围的资源，不应因得分高而出现在可用候选中**。治理分阶段：检索前按身份、Namespace、类型缩小可见范围，得到候选后再结合版本状态、显式授权、环境兼容性、风险等级与任务权限终判；**过滤须在最终分页之前完成，避免页数与总量泄露不可见资源信息**；结果说明匹配依据、来源、版本状态与使用条件，匿名访问同样服从公开范围与最小权限。层次上 ARD 面向广义资源可跨类型发现并直接取得 Agent 资源，需要把候选转为可远程调用对象时问题收窄到版本接口协议端点，再按需使用 RAD；**两者不是平行或竞争关系**，已知目标是远程 Agent 可直接用 RAD Search/Discover，两条路径复用同一资源版本可见范围与权限语义。动态发现不表示可自由获取任何外部内容：候选限于已发布且符合当前身份环境要求的资源，**外部 Skill/MCP/Agent 只有完成内部准入并形成确定版本后才进入发现范围**；选择候选不自动获得额外权限，加载调用仍经当前任务授权。生产通常混合——决定身份、基本行为与安全边界的核心 Prompt 与高频基础 Skill 固定版本或稳定标签，业务长尾能力、领域工具与临时协作 Agent 按任务发现；高风险操作可要求人工确认或只返回能力说明不允许自动加载。**灵活性由可发现资源范围提供，边界仍由资源状态、权限与运行策略共同确定**。Nacos 链路为 ARD Client → ARD Adapter → 协议无关的 AI Resource Search → 关系索引与可选向量能力，权威数据仍是 Registry 标准资源，对外接口与内部模型分开使协议、检索策略与版本治理独立演进；当前主要聚焦本地或私有 Registry，**未配置上游 Registry 时不能把本地查询表述为已完成公共互联网的 Federation 或 Referral**。

## 8. 从发现结果到运行时 Context

发现只确定可能需要哪些能力，**不能把所有候选的完整内容直接拼进系统提示**：不同资源有不同的指令优先级、信任程度与加载方式，Context 还受长度限制；缺少统一装配，动态发现越灵活越容易出现指令冲突、无关信息占位与外部内容改变系统规则。MCP Server 与远程 Agent 本身不作为大段文本进入 Context，进入的是当前任务可用的能力说明、必要参数与调用结果，连接交互由相应客户端完成。**发现摘要与执行内容分离**：发现阶段只用名称、简要能力描述、适用场景、版本状态、风险等级与匹配原因比较候选；选定后 Resolver 解析精确版本，Context Compiler 按类型取执行内容（Prompt 加载正文与变量 Schema，Skill 先加载主要说明、执行到特定步骤再读模板资料，MCP 只呈现授权范围内必要工具，远程 Agent 给筛选后的能力描述）。摘要与完整内容必须指向同一逻辑版本；索引未更新、版本已撤回或端点不满足环境要求时，**Resolver 应拒绝继续加载并触发重新发现，不能用名称相近的其他内容替代**。

优先级按来源分类：系统策略与核心 Prompt（受信发布、优先级稳定、不允许被后续内容覆盖）、任务 Prompt（经版本解析与变量校验、与当前任务绑定）、已批准 Skill（按需加载、仅在声明能力与权限范围内生效）、MCP 与远程 Agent 能力说明（运行时按当前授权生成、与实际可用端点一致）、Knowledge/RAG/Memory（作为数据来源，保留出处时间相关性）、用户输入与调用结果（外部数据，不自动改变更高层级指令）。**优先级不只由文本排列位置决定**，Compiler 以结构化方式保留指令层级并在发送前做冲突检查：Skill 要求忽略系统策略、Tool 返回含类似系统指令的文本，仍保持原有层级，**不能因措辞强烈而获得更高优先级**。低信任内容以引用数据形式进入并加边界标记；确需把外部内容转为内部规则时先形成新的 Prompt 或 Skill 候选版本，经评审发布后再用。**能力说明须与实际授权一致**：看到却无权调用产生无效规划，具备能力但 Context 无说明则无法正确使用；Compiler 按身份任务环境端点状态生成最终能力集合并记录候选被排除原因。

Token 预算与渐进装配：**Context 变长并不必然带来更好结果**，过多规则样例资料分散注意力并增加成本延迟。先按类别分配预算再在类别内按相关性必要性选择：核心策略与任务指令完整保留，Skill 先留步骤与必要限制、大体量资料延迟到相关步骤，检索材料留最相关片段附来源，历史与 Memory 按阶段摘要淘汰，重复背景去重留权威来源。Tool Schema 按需披露（工具多时先按任务权限分类选较小集合，需扩展再重新发现加载），远程 Agent 先给摘要、确定协作对象后才取完整 AgentCard 与端点。**每次新增内容都经相同的版本、权限与预算判断，不能首轮检查通过后允许后续文件不受限制进入**；超预算时裁剪须可解释，记录保留/摘要/省略片段与原因，**重要限制不应仅因位于长文末尾而被截断**，Skill 包可用 Manifest 标记必须完整加载的安全说明与可延迟资料。一致性上，一项资源获取失败不能随意混合新旧版本——新 Prompt 依赖更新后的 Schema 而节点仍缓存旧 Skill，分别取最新可能比整体用上一组已验证组合风险更大；任务开始把已验证组合存为 Lock Manifest，部分不可用或校验失败则整体退回上一组或停止任务说明缺失依赖，长尾能力可重新 ARD、明确指向远程 Agent 可直接 RAD 找同需求候选，**替换必须重新通过版本权限风险判断**。**端点故障不应修改历史版本，故障转移也不应静默改变能力定义**，备用端点须满足相同版本协议环境权限并记录实际连接目标；紧急撤回按风险级别决定立即终止、阻止下一步或只读操作结束后停止，处置写入 Trace。

Context Manifest 不是完整 Context 的副本，而是**可定位来源并恢复装配过程的结构化记录**：Agent Release、模型版本、各资源精确版本与摘要、策略版本、ARD/RAD 发现请求标识、实际解析端点、Context 指纹，另加变量快照受保护引用、匹配理由、实际授予权限、裁剪结果、缓存状态与装配时间。Trace 经 Manifest 关联具体资源，回答一次执行用了什么、为何选择、哪些候选因权限或风险未被采用。**回放不保证模型生成逐字相同的结果，但应能重建当时的输入条件，区分资源变化、模型变化、端点变化与外部数据变化**；敏感内容存摘要、访问引用与保留期限，原始数据已按规定删除时明确说明缺失项，**不能用当前数据替代历史输入**。职责边界：Registry 提供资源身份、精确版本、标签解析结果、发布状态与内容端点信息，Compiler 决定这些信息如何进入模型调用（Prompt 是否位于系统策略层、Skill 哪些文件延迟加载、Tool Schema 保留多少、远程 Agent 结果如何作为数据引用），二者以 Manifest 为稳定接口；标签、在线状态或端点集合变化时**不应在正在执行的一轮任务中静默替换内容**，先重新解析校验再在任务或阶段边界生成新 Manifest。

## 9. 端到端案例、运营指标与演进路线

生产故障诊断 Agent 把各环节连成一条路径：核心 Prompt、故障分级 Skill 与基础可观测性 MCP 由 AgentSpec 声明，业务日志规则、领域知识与协作 Agent 作为长尾能力按任务发现。一次发布后订单接口延迟与错误率同时升高，执行分八阶段——加载稳定依赖（基础 Lock Manifest）、形成能力需求（保留原始意图，订单与日志原文留在任务环境）、ARD 发现非固定能力、RAD 解析远程 Agent（协议与端点快照）、执行治理判断（Registry 按身份 Namespace 授权在线状态过滤，Runtime 再按协议兼容风险与任务权限终判）、解析版本与端点、装配并使用能力（Context Manifest 与调用 Trace）、输出带不确定性说明的诊断结果。边界明确后，问题发生时才能判断是候选不准、资源不可用、权限判断不当、Context 装配错误还是实际调用失败。已发布 Skill 出现风险（某版本把样例数据发往未申报外部服务）时：下线该版本必要时禁用整个 Skill，运行时查询不再返回、ARD 资格判断排除，节点按风险策略停新加载、清待用缓存、中止尚未执行外部请求的任务；再经 Lock Manifest、Context Manifest 与历史 Trace 找出使用该版本的任务，确认哪些执行获得过网络权限、是否产生实际外部请求、是否含敏感数据；修正后以新版本重走 Pipeline、隔离验证与人工评审才恢复标签与发现范围。**版本撤回不是简单删除文件，有效处置依赖确定的内容摘要、运行权限记录、消费者列表与可替代版本**。

运营指标五方面：资源治理（无负责人资源数、已发布版本覆盖率、版本漂移率、恢复稳定版本耗时）、变更评审（自动检查通过率、评测集退化率、人工评审时长、发布后回退率）、发现质量（Top-K 命中率、无结果率、候选采用率、误匹配率、理由可解释率）、运行效率（版本解析延迟、内容加载时间、端点选择成功率、缓存命中率、Context Token 消耗、装配失败率）、安全治理（未检查外部 Skill 数、风险版本发现数、受控外部请求数、撤回版本新加载次数、处置完成时间）。**指标须结合业务结果解释**：候选采用率高不一定表示发现质量好，也可能是 Agent 总接受第一个结果；外部请求被限制次数增加可能来自风险上升，也可能说明控制覆盖面扩大。演进六阶段：L0 分散维护（盘点关键资源、定名称与负责人）→ L1 版本留存（区分工作副本、不可变版本与实际运行版本）→ L2 统一 Registry（完善 Lock Manifest、反向引用与跨资源影响分析）→ L3 统一评估与可信供应链 → L4 受控动态发现 → L5 持续改进。**阶段判断以实际能力为准而非是否部署了某产品**：仅建资源列表但仍允许覆盖历史内容不算 L2，部署语义检索但没有权限过滤与精确版本解析不算受控动态发现。落地顺序先纳管少量被多 Agent 共用、变更频繁的 Prompt/Skill/MCP，建立 Namespace、版本、标签、在线状态与运行记录，为协作 Agent 建版本化调用描述与端点登记、为需标准化分发的 Agent 建 AgentSpec；再启用匹配 Pipeline，把评估结果、影响分析与本地缓存接入交付流程；外部 Skill 多的组织优先建内部接收区域与运行权限限制；**权威资源、版本解析与治理规则稳定后，再扩展 ARD 发现范围并按需使用 RAD**。
