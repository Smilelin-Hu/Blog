# 状态存储与语义资产：从 Event Log 到本体的一体化治理

状态外置之后，存储层不再只保存数据，还要连接推理、执行、协作与学习：任务在跨节点、跨时间、跨角色流转时始终拥有同一份可信连续的上下文。本文沿「分层地图 → 运行状态与工作区 → 记忆/知识/本体 → 平台治理」提炼持久化、版本、一致性与生命周期的工程要求，参考架构以 Lakebase（一体化 Agent 数据库路线）为例。核心判断：**不是让所有状态落入同一种存储，而是每类状态获得匹配的物理承载，同时在上层拥有一致的身份、元数据、版本、权限和生命周期**。

## 1. 分层地图：四类状态对象与各自的正确性边界

| 对象类 | 内容 | 核心要求 |
|---|---|---|
| 运行时状态 | 事件日志、检查点、任务进度、执行租约、状态指针 | 写入顺序、原子更新、幂等、可恢复历史 |
| 工作区与产物 | 文件、代码、图表、快照、版本、分支 | 版本、快照、稳定引用、可回滚 |
| 记忆与知识 | 会话摘要、偏好、经验、文档、向量索引、知识图谱 | 可检索、时效、来源可信、权限过滤 |
| 业务语义与治理 | 本体对象、关系、规则、租户、权限、审计 | 对象身份、关系完整性、规则边界、审计证据 |

把任务事实仅当可检索文本会丢失顺序与原子性；把工作成果当无版本附件难以回滚复用；把记忆知识权限混为同一份上下文会让过期或越权内容持续影响决策。**正确起点不是先选引擎，而是先定义各对象的正确性边界，再匹配存储能力，用统一契约组织为整体**。统一访问契约减少重复集成，但各对象的一致性与恢复保证仍需分别验证。

## 2. 运行时状态：Event Log、Checkpoint 与 Durable Execution

**Event Log** 只追加记录有业务意义的事实变化（生成计划/申请租约/发起调用/收到返回/等待确认/提交结果），按顺序还原任务演进。顺序在边界上最关键：审批请求已成功但结果事件没记牢就会重复发请求，子任务完成事件父任务没看到就会错误等待。**强一致不等于全局一条日志**——合理边界是任务/会话/业务对象：同一任务内状态变化有明确先后，独立任务并发执行。事件与当前状态同事务提交或经 Outbox 保证最终同步、按事件标识去重；**诊断日志和模型输出不能替代事件记录作重放依据**。保留策略平衡审计与成本：近期任务细粒度事件、稳定完成任务形成可验证快照、按合规设保留期——关键不是永久保存每段模型输出，而是影响正确性与外部动作的事实始终可追溯。

**Checkpoint** 记录「某可信时刻任务处于什么状态」，不是模型上下文的拷贝，应含任务阶段、已完成/未完成步骤、工具结果引用、工作区版本、子任务状态、等待条件、状态版本。频率与任务成本匹配：秒级可低成本重试的查询不必频繁快照；调外部系统、长链路、需人工介入的任务在关键边界主动打点——**外部调用发起前后、长计算完成后、人工确认前后、工作区重要变更后、交接给其他 Agent 时**。增量快照基于状态版本存变化集，恢复时组合最近完整快照+后续增量。

**Durable Execution**：执行实例是可替换计算单元，不是任务事实的唯一拥有者。恢复 = 读最新 Checkpoint + 按需回放其后事件，不重执行已确认步骤。三个配套机制：**执行租约**定「谁有权继续执行」（接力棒：只有持最新租约的实例能提交状态变化，写入附版本或围栏标识，旧实例仍在跑也不能覆盖新结果）；**状态指针**定「当前可信状态在哪」（关联任务、事件序列、Checkpoint、工作区快照与产物引用，也是审计运营统一入口）；**外部副作用不天然 exactly-once**——平台保证的是任务状态变化有明确事实边界，模型调用/消息发送/审批提交/数据写入还要幂等标识+结果确认+补偿，所以必须同时保存调用意图、调用标识与调用结果，不能只记一句「正在执行」。

Agent 负载天然脉冲式（批量请求、子任务扇出、超时集中恢复）。状态外置后计算与状态分别弹性：执行层按任务数扩缩，状态层按任务分区/热点/持久化等级保吞吐——关键不是每条事件最低延迟，而是高负载与实例切换下**不丢失、不乱序、不被旧副本覆盖**。冷热分层：在跑任务低延迟读写、完成任务可检索历史、不活跃事件治理后归档，避免历史任务挤占实时资源。

## 3. 工作区与产物：分层、CoW 快照与 Artifact Store

工作区不是执行实例上的临时目录——**实例只是工作区的一个临时挂载点**，工作区有独立身份、权限、版本历史与生命周期，可被新实例重挂、被协作者有选择共享。底层三形态对 Agent 呈现为统一任务空间：共享文件存储（目录结构+频繁小文件读写）、对象存储（大文件/不可变成果/长期归档）、近端加速层（热点低延迟）。分层结构「共享不变部分，隔离变化部分」：只读基础层（运行环境/依赖/模板，平台维护防 Agent 乱改）、任务或租户共享数据层、当前任务独占可写层——既是性能优化也是治理边界，**试错在私有可写层，交付须显式提升进产物库**。

**Copy-on-Write** 让快照不复制整份工作区：未变内容复用，只有新写入形成新数据块，短时间建多个实验分支不成倍复制数据。可信快照能回答「哪个任务、哪个阶段、基于什么输入、由谁生成、后续产生哪些变化」；**环境回滚不撤销已提交到外部系统的操作**。关键阶段的运行时 Checkpoint 应记录对应工作区快照引用，避免「任务状态恢复了但文件状态已变」的不一致。

并发写入要独立约束：执行租约解决「谁有权推进任务状态」，工作区还要解决「谁有权修改可写层」——支持围栏的写接口验证执行代次，普通文件系统用独占挂载、撤销旧端访问或写私有分支仅当前持有者可发布；**仅更新任务表租约阻止不了仍持文件句柄的旧实例写入**。多 Agent 协作显式区分共享与私有：各自可写分支完成工作，经稳定快照或 Artifact 引用读对方结果，合并走明确版本合并与审批，不退化为不可审计的文件覆盖竞争。**进入 Artifact Store 的产物不可原地修改，变更生成新版本**。Artifact 元数据：来源任务、创建时间、版本、生成 Agent、输入依据、审批状态、权限范围、保留策略——后续任务引用「经审批的第三版报告」而非易变临时路径。规模化四要点：冷热分层防成本超线性增长、并发下各层保持正确、存储层基于身份与任务的租户隔离、**独立元数据索引**（不能只存运行时上下文或产物文件里）。

## 4. 长期记忆：两个正交维度与全生命周期

记忆分层用两个正交维度，避免把「来源」与「稳定性」混为一轴。**来源三类**：用户显式表达（偏好要求反馈）、Agent 行为归纳（调用模式/执行路径/错误处理经验）、外部业务事实（订单状态/审批结论，由业务系统写入记忆服务承接）。**稳定性三层**：人设与身份层（角色/行为规范/长期边界）、画像层（角色偏好习惯，周月级更新）、事件偏好层（具体场景交互，最细最易变）。同一条显式表达可落画像层也可落事件偏好层。**Persona 不是经验性记忆**，由构建方或治理方显式维护、受版本权限控制，构成记忆基底但不来自 Agent 经历。物理承载匹配逻辑分层：高频召回进向量索引与缓存，低频历史沉低成本持久层。

写入管线：从对话与行为日志抽取有长期价值的信息（偏好声明/事实陈述/重复行为模式），寒暄、临时调试指令、一次性查询不进长期记忆；新记忆与已有做语义匹配、合并、去重——多次独立交互指向同一结论则可信度增强，冲突按时效性、来源可靠度与上下文覆盖或保留待确认。检索是多路混合召回：语义向量 + BM25 关键词 + 实体关系（发现文本不相似但实际关联的历史），Rerank 精排后结合时间衰减与类别过滤。**时间衰减不适用于所有信息**：长期有效的约束不应因少被调用而淡出；引用频率不等于正确性，要与来源和验证结果共同使用。

遗忘与记住同等重要：空闲时增量合并、冲突消解、摘要压缩（多次「少放辣」可成候选偏好但不宜推断为所有饮食习惯；压缩保留来源引用，不确定的概括留待确认）。**归档、降召回权重与删除是不同操作**：用户要求删除要同步处理原始记录、摘要、索引、缓存并防后续重建重新引入；依法依约保留的隔离用途按明确策略处理。多模态记忆（截图/语音/视频）统一持久化与语义检索，共享权限生命周期，返回保留模态来源与原始资源引用。治理贯穿写入检索使用删除全链路：分类分级、权限隔离、访问审计、合规脱敏、标准化接口凭证接入、全链路可视化追踪一条记忆从写入到淘汰。规模化验证要同时报告活跃用户/条目数/并发/规模/召回质量/P95-P99 延迟，并验证记忆纠正、权限撤回、索引延迟与故障恢复对后续回答的影响——**不能仅凭「记住了更多」推导质量提升**。

## 5. RAG 知识库与本体：事实与语义骨架

记忆是 Agent 自己「经历」的，知识库是外部「引入」的（企业文档/手册/报告/业务数据，知识管理员维护）；**知识不因被导入而自动权威，记忆不因来自真实交互而必然正确**，都需来源核验。工程链路：深度文档解析（保留标题层级/段落关系/表格/实体/时间/数值，**解析深度决定检索质量上限**，避免「海外退货政策用于国内业务」式断章取义）→ 智能切片（标题/段落/语义转折为边界，保留父级标题；过大引噪声过小丢上下文）→ 向量化与增量索引（变更检测只处理变化部分，记录源版本/解析版本/索引水位，**新版本构建验证后再切查询入口**，时效按实际规模设定不能由「增量」推导固定生效时间）。

混合检索按查询特征动态调配权重：语义向量懂概念相似但可能忽略产品型号，关键词精确匹配但难懂同义表达，结构化过滤（类型/时间/部门）严格限范围。业务事实补全走受控数据探查（自然语言转查询，**只读账号 + 授权 Schema 范围**）。多路候选统一 Rerank，综合语义相关性、权威性与时效性。**GraphRAG** 解决答案不在单段文本而在跨文档关系推理的问题（股权穿透/供应链关联/跨法规审查）：双层索引——语义层召回片段、图谱层关系遍历与模式匹配，融合为有事实依据和推理链路的回答；抽取关系与模型推断均需保留来源并验证。治理三维度：权限过滤覆盖检索到生成全链路（**防推理过程成为受限信息旁路**）、答案溯源到文档段落版本、标准管线从网盘/CMS/Wiki 持续同步配版本快照回滚时效检测。规模化用冷热分层（热点驻内存索引与 SSD 缓存、低频迁低成本层按访问模式透明回温）与湖库一体承载。

**本体（Ontology）**回答「找到文本不等于理解它」：检索到「订单已逾期」还要理解订单-客户-产品关系、逾期对应什么规则、触发什么动作。四要素建模：对象（实体属性约束）、关系（方向/基数/业务语义）、动作（触发条件/执行逻辑/权限约束，把「知道」变「能做」）、规则（专家经验显式化，约束自主决策边界）；三层组织：语义层 → 数据流转层 → 智能决策层。**责任分离**：本体承担语义建模，动作执行生命周期归 Runtime，权限与 Agent 绑定的授权决策归治理方——本体才能版本化独立演进。实例数据更新与 Schema/规则变更分开处理，后者走版本管理与影响评估；核心概念稳定、外围属性灵活演进，同步水位与校验发现本体与业务数据的差异。推理是规则与 LLM 协同：确定性规则依赖规则与输入正确，LLM 推断也要校验，**不因采用本体就默认可解释或准确**；关键结论附关系遍历、规则应用与上下文参考的推理路径。运维关注**本体覆盖率**——大量业务数据不能被现有概念描述，说明语义盲区，Agent 在这些区域难以形成可靠结构化理解。三者协同：本体为知识提供骨架（故障文档组织为「设备类型—故障模式—解决方案」链路）、知识为记忆赋业务语义（「上次交付延迟」置于订单与交付规则下才可理解）、记忆驱动知识与本体演进（交互暴露新关联时提示补充）——**反馈经受控更新：候选事实由维护者验证后生效，不得把模型推测直接写成组织规则**。并非所有应用都要三者齐备，按跨会话复用、知识检索与关系推理的实际需要选择。

## 6. 平台化：隔离、一致性、元数据、成本与容灾

多租户身份边界六级：组织（业务合规边界）→ 工作空间（协作共享资产）→ Agent（角色可访问范围）→ 用户（交互授权主体）→ Task（跨会话持续的业务目标与权威状态）→ execution（一次具体执行实例），映射为可传播可校验的上下文，每次读写检索执行都带归属。隔离三层组合而非互斥：物理隔离（强监管高敏专属环境）、逻辑隔离（独立库/Schema/索引命名空间/对象目录，多数企业空间）、行级隔离（大规模共享服务按租户角色标签控制）。**语义数据必须检索前过滤**——先跨租户召回再过滤结果，候选生成阶段已引入暴露风险；租户与权限约束前置到索引空间、检索条件与重排序策略。隔离也保护行为边界：不同租户的偏好记忆规则不因共享模型或工具链相互影响。

一致性按对象定级，不追求所有组件同时成功：**权威事实**（执行租约/支付确认/工具结果/关键检查点/事件日志/对象元数据）以强一致或可验证提交为目标；**派生视图**（向量索引/全文检索/图谱投影/缓存/读副本/统计聚合）可接受短暂最终一致，但必须明确新鲜度与对应源数据版本。写入先可靠提交权威事实再异步增量推索引；读取按任务重要性选最新权威状态或高性能派生视图。跨组件流程用幂等标识、版本号、提交水位与补偿管理（文档更新：新版本 → 解析切分向量化 → 索引达可用水位才切流量，失败重放或回退旧版本），避免把分布式事务扩展到所有操作。**回答要可解释**：标注引用的对象版本、索引时间与数据来源，答案过期时能区分模型推理、数据源更新还是索引未同步，而不是都归因幻觉。

统一元数据把异构对象组织成可发现可治理的资产目录：类型与唯一标识、租户空间、创建主体、来源系统、摘要、敏感级、版本、位置、访问策略、生命周期状态、关联关系——记忆追溯到来源对话，知识切片关联原文档版本，本体关系说明来源数据与生效范围。**血缘让静态目录变动态治理**：源文档更新/权限变更/规则调整时识别受影响的索引、图谱、摘要与下游任务，触发重算、失效或人工审核；但跨系统删除未必同步传播，法律保留与不可变审计要留显式例外策略。策略（访问/保留期/地域/脱敏/审批/删除）声明为对象治理属性而非散落在业务代码。成本治理三原则：**按数据价值而非技术类型分层**（访问频率+业务价值+合规+恢复成本定位置）、**保留期是显式策略**（临时状态任务完成即清、检查点留到可恢复窗口结束、记忆支持撤销删除、知识历史版本按审计长存）、**减少无效复制**（去重/增量索引/摘要压缩/失效检测/按需物化，记忆不因「未来或许有用」无限累积）。成本按租户/空间/Agent/任务类型/对象归因——分清上升来自模型调用、频繁重建索引、过度保留工作区还是跨区复制。

选型两条路线：组件组合（复用既有设施按负载扩展，代价是自维护跨组件身份版本更新恢复契约）vs 一体化 Agent 数据库（契约收敛统一服务减少集成，代价是产品能力/迁移路径/故障边界依赖）。Lakebase 走一体化：统一对象模型、服务接口与治理控制面，**统一指数据模型与治理界面而非单一底层引擎**。逐项验证：关键状态能否原子提交、产物引用是否稳定、权限撤回是否及时、各层能否独立备份恢复、数据能否完整导出——验收落到实际任务与故障场景而非产品名称；短会话低敏轻量应用组件组合仍是合理起点。容灾按对象定 RPO/RTO：运行时事件与检查点要更低恢复点目标，工作区产物保版本可溯引用不失效，记忆知识区分权威源与可重建派生（先恢复业务正确性再恢复检索性能）。**高可用不只是数据库不宕机**：恢复流程要定位最后已确认事件、加载检查点、校验租约与幂等标识、确认外部调用状态，再决定继续/重试/补偿/转人工——避免数据恢复了但业务重复错乱。定期演练：主区域不可用能否切换、损坏索引能否依源重建、误删记忆产物能否在权限边界内恢复、跨组件任务恢复后是否幂等可追溯，并与 Runtime 故障演练联动。
