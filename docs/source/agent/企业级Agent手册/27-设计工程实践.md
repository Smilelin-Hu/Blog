# 设计工程实践：GenUI 与 Vibe Designing

设计需要把结果交付到真实界面，也从表达意图开始。本文按源章顺序整理阿里云设计工程的两项实践：GenUI 讨论生成式用户界面怎样补上结果交付的最后一公里，Vibe Designing 讨论意图驱动的设计工作方式怎样进化。两者共同回答一个问题：**当 Vibe Coding 让更多人可以把意图变成结果之后，怎样让这些结果成为高质量的产品体验**——从意图到体验，中间不是一个 Prompt 也不是一个模型，而是一套能力系统。

## 1. GenUI：补上结果交付的最后一公里

在 Agentic 用云管云场景里，用户对结果的要求不止「读懂」：需要横向比较几组证据、判断某个操作的风险、然后在当前上下文里直接把动作执行掉。**真正卡住体验的不是模型答得好不好，而是结果交付的最后一公里**——用户拿到的是一段文字，需要做的却是比较证据、判断风险、动手操作。现有两种表达方式都有局限：纯文本擅长解释和开放表达，但对比多组指标、定位异常时间点、发起带确认的操作时组织能力和操作能力都不够；固定页面擅长承载稳定高频流程，但必须提前设计，而 Agent 运行时产出的结果形态是长尾的，无法提前穷举对应页面。GenUI（Generative UI）是一套机制：让 Agent 在运行时依据任务上下文和业务结果，在受约束范围内动态组织内容、组件与操作，交由客户端渲染成界面——**产物是界面，但本身是「生成 + 约束 + 渲染」的一条链路，而不是某一张具体页面**。三者分工清晰：自然语言负责开放表达与解释，固定页面负责稳定高频的既定流程，GenUI 把富表达和富操作延伸到无法提前穷举的长尾任务。

## 2. 共享设计资产与声明式原则：灵活性归 Agent，确定性归客户端

Agent 的生成自由度需由资产约束，否则一致性无从谈起。CloudAI GenUI 把约束沉淀为一套与具体协议无关的**共享设计资产**，由适配层翻译成各协议的数据契约：**Catalog 约束「能用什么」**（本次任务可用的组件清单及其数据与操作契约，是生成的硬边界，含通用基础组件、业务组件、语义组合组件 Block）；**Template 约束「通常怎么组织」**（按常见任务意图给出推荐信息结构与示例，帮助 Agent 收敛组织方式）；**使用规则约束「该怎么用」**（信息层级、组件选择、风险提示与操作确认等规则，避免随意拼装）。「动态」不等于「不可控」，因为确定性并不来自生成过程，而来自三重约束：**Catalog 白名单限定可用元素、Schema 校验拦截非法结构、客户端可信组件独占渲染实现**——灵活性归 Agent，确定性归客户端。核心选择是声明式而非生成界面代码：不是让模型直接产出 HTML/JavaScript/JSX，而是用结构化数据声明「需要呈现什么」，由客户端决定「具体如何呈现」。直接生成代码有两个绕不过去的问题——输出空间开放，品牌一致性和交互边界难以约束；模型生成内容被直接送进可执行边界。声明式遵循三项解耦原则：**业务结果与界面表达解耦**（业务结果是事实源，协议数据只负责呈现，可随上下文重新组织）、**表达语义与视觉实现解耦**（Agent 选择指标证据风险操作等语义，品牌布局样式交互由客户端可信组件实现）、**设计知识与技术框架解耦**（Component 语义、Block、Template 意图和规则作为共享知识，适配层转成不同协议契约）。仅有协议和基础组件时（json-render、A2UI 提供生成渲染机制，shadcn 提供基础组件），信息层级、组件组合与操作边界仍依赖 Agent 临时组织；接入 Block、增量 Catalog、Template 与使用规则后，设计经验进入生成过程，结构更清晰、体验更一致、操作边界更明确。GenUI 还不只展示结果：任务需要用户继续参与时，界面提供输入、选择、确认和操作入口，用户操作回传 Agent 继续驱动业务执行与界面更新，无需离开当前上下文就能从理解结果进入下一步。

## 3. 运行机制与应用场景：界面确认不等于授权

运行时由两条方向相反的数据通道形成闭环：**通道 A（Server → Client）交付界面数据**——Agent Server 依据业务结果、共享设计资产和目标协议生成界面数据（json-render 交付 UI Spec，A2UI 交付协议消息），Client 校验解析状态，Renderer 按 Registry 映射渲染 CloudAI 组件；**通道 B（Client → Server）回传交互事件**——用户操作组装为 Action Event 连同必要状态回传，**鉴权、执行与审计一律发生在服务端，界面上的确认只是意图表达，不构成授权**，执行结果若改变界面再经通道 A 回流。输出可校验、问题可追踪：结构化协议数据先经 Schema 校验再映射可信组件，未知组件、字段类型错误、引用缺失在渲染前就被拦下，脚本注入与不可预期交互风险显著降低，协议数据本身可记录可比对，为回放和问题定位留出接口；流式场景下校验按消息、按节点进行，渲染器逐条消费增量消息边校验边渲染，未通过校验的节点降级或跳过，而不是等整屏数据齐备。落地场景以数据库 AIDBS 产品为例：**诊断与运维**呈现诊断摘要、异常指标、证据、方案对比与高风险操作确认；**数据查询与业务分析**动态组织结论、数据对象、知识依据、指标、图表和查询入口；**售卖**在对话中完成需求澄清、方案选择、参数调整、确认和下单全流程。

## 4. 边界限制与技术路线：资产稳定，适配层承接变化

GenUI 的价值域是长尾任务——**用到不该用的地方，代价是稳定性和成本；对能力做过强假设，代价是信任**。三类场景不该用：稳定高频强流程的操作走固定页面（最优形态可提前设计，没必要运行时重新组织）；纯解释性开放式回答走自然语言（为一段解释套组件只会增加噪声）；强合规强事务字段极多的复杂配置走控制台（校验规则和状态机要求超出生成式组织的可靠区间）。能力边界五条：**结构可校验，事实不可校验**——Schema 拦得住未知组件与字段错误，拦不住被编造的数值或不成立的结论，数值必须来自业务系统返回、结论需要可溯源证据、必要时业务侧二次核对；**界面确认不等于授权**——所有鉴权执行审计在服务端完成；**成本与延迟是真实约束**——Spec 体积直接影响首屏时间与 Token 成本，复杂界面依赖流式生成与增量更新才有可接受的感知性能；**跨协议不可直接互换**——共享的是设计语义与使用规则，不是同一份可互换的 JSON，数据契约由适配层各自生成；**依赖的协议本身仍在演进**——A2UI 处于活跃演进阶段（稳定线 v0.9 系列，v1.0 为候选版本），OpenUI 生态同样在迭代，因此采取「资产稳定、适配层承接变化」策略，把协议波动隔离在业务语义之外。技术路线共享资产、兼容多路径：json-render（UI Spec + 渲染器）已打通生成校验渲染闭环，下一步拓展真实业务验证；A2UI（声明式 UI 协议、流式 JSON 消息）进行中，已在业务场景完成验证、设计资产适配中；OpenUI Lang（生成式 UI 框架 + 面向 LLM 的行式 DSL）规划中，尚未接入。后续重点评估四个维度：生成与体验（结构有效率、业务完整度、组件选择、任务完成体验）、交互与性能（流式生成、增量更新、多轮状态、首屏时间、Token 成本）、安全与可观测（Schema 校验、权限审计、容错降级、链路追踪回放）、兼容与接入（资产覆盖度、适配维护成本、跨端复用、业务接入成本）。

## 5. Vibe Designing：AI Coding 成为通识性的创造能力

GenUI 解决运行态的结果交付，而它调用的设计规则、组件与审美判断从哪里来——Vibe Designing 从设计工作方式一侧回答。AI Coding 正从开发者专属能力变成更普遍的创造能力：一个人用自然语言表达意图和判断，参与软件、工具、页面、体验和服务的创造。对设计师而言，变化不是「设计师也会写代码了」，而是**终于可以更快地把脑子里的想法变成可以运行、可以验证、可以被别人使用的东西**。三个层面的信号：个人层面，阿里云设计师借助 AI Coding 自己做小工具发布到 npm，两天获得 150 多次下载——设计师不再只是等待工具，也可以为解决问题创造工具；团队层面，阿里云设计中心全员 Vibe Designing Jam 比赛涌现 40 多个作品，覆盖产品设计、市场传播、体验度量，AI Coding 进入设计现场后开始重新组织团队工作流、重新发现业务创新机会；教育层面，浙江大学将 AI Coding 引入文化计算课程，学生围绕傩文化、传统乐器把文化研究、视觉表达和交互体验连接起来——过去想象一个互动体验需要技术同学深度参与，现在传统文化创造性转化不再停留在图像风格化，而能进入动态叙事、交互体验和数字系统层面。

## 6. 意图驱动的新范式：设计师转向能力系统构建者

技术平权之后，一个人说出意图，Agent 就有机会把它变成代码、界面、工具和产品。但深入使用会发现：**Agent 并不天然懂业务语境，也不天然懂设计语言**——反复对话纠正，生成结果仍容易像模板、像默认审美、没有具体语境。当意图可以被更快表达，谁来定义什么是好的体验、谁把好的体验变成可持续生产的系统、谁让 Agent 真正理解业务文化组件审美和判断？真正的问题是**一个意图如何被 Agent 高质量地实现为产品体验**。设计师要从工具使用者转向设计能力系统的构建者。阿里云的实践中这套系统称为 CloudAI Design，含三个相互支撑的层面：**设计工程（Design Foundation）**解决研发态和创作态的能力构建，**动态交互（Generative Runtime）**解决运行态的体验组织（GenUI 正是这一层的落地），**自我进化（Evolution Loop）**让体验持续向上生长——对应三句判断：Design is the New Code，GenUI is the New Interface，Taste is the New Engine。

## 7. 设计工程：设计声明控制质量，执行契约控制过程

设计工程把设计经验、组件规范、业务知识、文化素材、设计方法和验收标准转化为 Agent 可调用、可执行、可复用的工程资产，让 Agent 生成产品体验时**不再裸生成，而是在真实语境和设计系统中生成**。第一件事不是继续堆 Prompt，而是主动打开 Agent 的黑盒理解它到底怎么生成——过程都交给裸模型，它就按通用经验生成；把设计能力工程化地提供给它，它才有机会按业务语义、组件体系和体验标准生成。能力拆两类：**设计声明回答什么是好的设计**（产品结构、业务语义、设计风格、交互逻辑、组件约束和通用体验原则，让 Agent 不在抽象空间而在真实业务语境里生成）；**执行契约回答怎么做出好的设计**（不是让 Agent 自由发挥，而是把设计师的经验、流程和判断变成 Agent 的能力）。设计声明控制质量、执行契约控制过程，设计不再只是一个交付物，而开始成为一种新的工程能力。这套能力已在阿里云 AI Native 产品研发中应用，覆盖 Agent 构建、运维、观测、安全等商业化场景：Agent 读取 CloudAI 能力快速完成高质量 Baseline 设计，复杂交互和高审美场景中设计师借助 Figma MCP 等工具基于生成结果精修，并把新规则、组件和经验回流到系统中。

## 8. 动态交互与自我进化：体验随意图被实时组织

传统软件的交互界面是预设的，用户要理解菜单在哪、功能在哪、路径怎么走；AI Native 产品从「人如何理解系统」转向「Agent 如何理解人的意图并帮助人完成目标」——**从 UX 到 AX（Agent eXperience）的转变**。动态交互发生在产品运行态：Agent 在用户表达意图后，根据场景上下文调用设计规则和组件动态组织一段交互过程。例如用户想在云上部署机械臂训练模型，传统方式要理解平台入口、选算法框架、配算力、设参数一步步部署；GenUI 场景中用户只表达意图，Agent 结合平台能力、社区最佳实践和任务上下文自动推荐算法类型、训练方案和资源配置，在关键节点生成临时界面让用户确认、调整或推进——**UI 不再是固定页面，而是 Agent 为完成当前任务动态组织出来的过程界面**，界面不再只是被设计出来，也可以在意图中被组织出来。但光有设计工程和动态交互还不够：AI 能很快给出不错的 Baseline，却常需一轮轮对话纠正补充才接近想要的结果，这个过程不应长期依赖人的反复提醒。真正优秀的体验需要 Taste 牵引和质量兜底——质量关注语义准确、场景合理、业务合规、交互可用和视觉一致，Taste 不仅是视觉审美，更包含对文化、叙事、产品气质和交互细节的综合判断。自我进化的关键是**把质量规则和 Taste 判断沉淀为 Agent 可执行的评价机制**：生成完成后系统通过 evaluator 和体验巡检验收效果、识别问题、提出修正，并将修正结果反哺下一轮生成——这不是把审美机械化，而是让 Agent 在反馈中逐渐理解什么只是完整、什么才是真正好的体验。设计师仍然用作品说话，只是作品形态变了：可能是一个可交互的动态网站、一套可被 Agent 调用的 Design Skill、一组持续巡检体验质量的 evaluator，或一套把业务数据组件规则组织成体验的 Runtime 机制。真正的机会是把专业能力、业务理解、审美判断和创造方法变成 Agent 时代新的设计基础设施。

## 写在最后

GenUI 把动态结果变成可理解可操作的界面，设计工程把专业能力变成 Agent 可调用的资产——两者都在回答「意图如何高质量落地」。下一篇整理 [运维安全与企业IT实践](/source/agent/企业级Agent手册/28-运维安全与企业IT实践)，看吉利汽车、塔斯汀、畅捷通的大规模生产业务怎样把观测、知识和受控行动连接成持续工作的系统。
