# 异步任务与自动化流程：可靠接收、调度、等待与恢复

同步请求-响应模式在简单问答下足够高效，但数据采集分析、跨系统流程自动化、周期巡检这类长时间、跨请求、需操作外部环境的任务会暴露根本局限：请求超时、上下文溢出、用户必须在线等待、等待外部事件期间进程持续占用资源。本文提炼异步任务、定时触发、工作流与运行治理的生产要求。核心判断：**关键不在堆叠组件，而在分清责任边界——执行生命周期与请求生命周期解耦，完成语义分层判定，恢复与幂等不能外包给任何单一组件**。

## 1. 任务模型：权威关系与完成语义

Task 是异步执行的最小业务单元，有独立持久标识与业务 State，可跨等待、恢复、审批持续存在，也可跨多个 Session 续跑；Session 只是其中一段执行视图，边界不等同于一次进程拉起。**跨 Session 续跑须 Runtime 显式装载经授权的 Task State**（业务参数、Checkpoint、待恢复等待对象、副作用记录）并建立关联，不是两个 Session 天然共享上下文；真正的隔离取决于租户、运行身份、凭证、Environment 与资源边界。

| 对象 | 权威来源 | 生命周期 |
|---|---|---|
| Task | 业务应用/任务模型 | 跨 Session、跨等待、跨恢复 |
| 业务 State | 业务应用 | 与 Task 同寿 |
| Session Context | Harness/Runtime | 按应用定义的会话持续 |
| Checkpoint | 工作流引擎/Runtime | 按恢复契约保存 |
| Runtime State | Runtime | 一次执行租约 |
| 外部副作用 | 业务系统 | 与外部系统同寿 |

完成语义五层各答不同问题：**执行状态**（succeeded/failed，答「跑完没有」）、**节点运维状态**（Worker 在线/租约有效，影响调度不等于 Task 结论）、**候选证据**（日志/Trace/快照/Artifact/LLM 原始响应，须核验来源完整性）、**Evidence**（被成功标准明确引用的候选证据）、**业务 Outcome**（业务应用或获授权 Verifier 判定）。**LLM-as-a-Judge 是 Evaluation 的实现方式，不是 Outcome 的天然权威**；人工审核也须被授权。运维「强制标记成功」只能在授权范围内改执行状态并留完整审计（谁/何时/原因/原状态/新状态），不能跨层判定 Outcome。

恢复与幂等责任划分：外置调度仍可能重复投递，执行端按业务操作标识核对结果，**不把调度成功当作恰好一次的保证**；Checkpoint 复用计算结果但不等同副作用幂等——外部写入已提交而 Checkpoint 未落盘时重跑仍会重复副作用。幂等机制（唯一键/幂等键/去重账本/事务性 outbox-inbox/租约与 fencing/对账补偿）按交付语义与外部系统能力组合选择，**是设计选择而非默认堆叠**。新实例恢复须重新取得有效执行权，不能恢复一份旧心跳就继续提交。

## 2. 异步任务核心架构：队列、调度器与状态机

异步模型核心：客户端提交得到可靠接收确认与 Task ID，后台排队、执行、重试，完成后经 Webhook/消息推送/轮询通知。**请求超时只表示调用方未在期限内取得结果，不证明执行已停止**；异步也不扩大上下文窗口，选择与压缩仍归 Harness。Task 属性至少含名称、内容、优先级、Agent/池、可选关联 Session、成功标准（引用 Evidence 与 Verifier）、重试策略、超时、计划调度时间、数据业务时间（如每天 00:30 处理前一天数据）、实际开始时间。

三类组件协同：**任务队列**按优先级排序、同级 FIFO，积压降级（拒绝入队返回结构化错误/低优先级限速/告警扩容），队列深度是核心可观测指标；**调度器**投递 Task 给合适 Worker（轮询/按活动任务或槽位/加权/亲和路由须配恢复契约）并维护租约，**背压本质是让消费速率自适应执行速率**——生产常见组合：每 Worker 并发配额、队列水位线暂停拉取、消费速率自适应、租约超时防失联卡死、按心跳动态调整槽位；**执行状态机**九态：waiting（等依赖满足）→ queued（等资源）→ running → succeeded/failed/killed，hold（等审批/输入/外部条件）可回 waiting，skipped 可取消跳过，succeeded/failed/killed 可手动重跑回 queued，mark_succeeded 为终态。状态存储以数据库为权威源、内存缓存加速——内存重启即丢、文件抗进程重启但机器不可用即不可达。

状态监听三方案不互斥，生产组合「**回调为主、轮询/租约兜底、共享存储做权威持久化**」：轮询控制权集中但有频率与实时性取舍，**单次轮询失败不能推断 Task 异常**（网络分区/GC 暂停都可能查询失败而执行仍在），判异常应基于租约失效再转 unknown 对账；回调实时但依赖 Worker 诚实回报，事件须带 Task ID、序号/版本、Worker 标识、租约 token，幂等消费丢弃迟到事件；共享存储 + Watch 有持久化保障但通知会丢——Redis Keyspace Notification 默认关闭且断连丢事件，etcd Watch 落后超 compaction 阈值被取消须重建并重读全量。**轮询/回调/Watch 都是变化信号不是事实源，信号缺失必须以权威 Task State 重新对账**。

## 3. HITL 等待与内置/外置调度

人工介入使 Task 进入 hold，等待从分钟级到数天级。**是否常驻取决于恢复能力，不由「内置」这一部署位置单独决定**：内置调度若状态只在内存则等待期须保留进程，支持持久化等待恢复也可释放资源；外置调度在 Agent 完成当前步骤后保存恢复状态与引用、按环境能力释放 Worker，审批事件到达后校验任务/授权/等待条件再重新分配——等待期仍承担调度、状态存储、通知及可能保留环境的成本。外置适合大规模、等待时长不可预测、需要资源弹性的场景。

HITL 也可借工作流引擎人工节点（Airflow 3.1.0 引入 HITL 能力，MSE-XXLJOB 人工节点支持暂停/恢复），但**流程引擎负责暂停恢复协调，不自动拥有业务审批授权**。审批回传须明确：载荷含 Task ID、审批版本号、授权主体、决策结论；接收方是 Runtime 或调度器，验证事件未过期、未重复、与 Task 当前状态兼容——「审批通过→回调唤醒」画成无标注箭头会掩盖这些必要校验。

## 4. 定时任务：触发统一与错过策略

定时任务是 Agent 从被动工具走向主动数字员工的关键：按用户或业务**预授权**的时间规则创建 Task。时间触发（Cron 周期/ScheduledAt 未来一次/FixedRate 固定频率）与事件触发（Webhook 业务方推送/MQ 订阅/内部 Task 状态变化）**在执行层走同一条路径——都是向队列投递 Task**，共用调度、并发控制、重试、对账。定时属性须明确：并发数（1 即串行）、阻塞处理策略（排队/跳过/合并为最新）、失败重试、超时与未知结果处理、时区与夏令时、以调度 ID+计划发生时间识别同一次触发。错过策略四种：run_latest（只补最新一次）、run_all（限额内补跑全部）、skip（只按未来时间点继续）、prompt（挂起交人工选择）。

外置到专用调度系统（XXL-JOB/SchedulerX/Airflow）须明确三点：**触发统一**（时间与事件共享执行链路）；**外置调度不接管业务 State 权威**（调度系统持有的是 Runtime State 与触发计划）；**幂等是业务设计责任**——failover 期间子任务可能执行多次，业务代码必须保证幂等。内置调度多实例触发去重需自行实现分布式锁或 Leader 选举。

## 5. 工作流：DAG 节点模型与汇聚语义

编排结构未收敛到两种方案：单 Task 内 Agent 自主决策（ReAct）、预定义工作流（计划固化为图）、Multi-Agent 协调（Planner 动态分解）及其组合——工作流节点内可以是完整 Agent 循环，Multi-Agent 也可被确定性流程约束。预定义工作流减少重复规划、控制路径易测试，但**不消除节点内模型错误、工具开销与失败重试**。

DAG 型工作流按拓扑序驱动，节点分业务节点（Agent 调用/工具/代码执行/知识检索/人工审批/通知）与逻辑节点（条件分支/并行/汇聚/循环/等待/错误处理/子工作流）。**循环语义靠运行时有界展开**（ForEach 按集合展开 N 个实例、Loop 子工作流递归设最大迭代），图本身保持无环；真需要带环流转（审批驳回回起草）应改用状态机模型而非把环硬塞进 DAG。仅业务节点+依赖边也能表达并行与汇聚，不能据此判断图必然线性。

节点就绪条件三类边须明确衔接：**普通依赖边**上游 succeeded 或 skipped 即就绪；**AND Join** 所有入边分支到终态且满足策略（全部成功/至少 N 个成功）；**OR Join** 任一满足即就绪，**未选分支必须显式取消**——否则继续消耗资源、产生副作用，与下游基于先到结果的决策冲突；迟到结果进审计日志不参与下游计算。

## 6. 工程能力与横切治理

**状态持久化与断点恢复**：节点完成即持久化步骤级 Checkpoint，后续节点输入从 Checkpoint 读取，进程崩溃后从最后成功 Checkpoint 继续——执行进程无状态化，但业务 State 权威仍在业务应用。**幂等与局部重跑区分两件事**：步骤计算结果复用是 Checkpoint 天然能力；外部副作用幂等不是——外部调用先存意图、执行后存结果，故障窗口按后端能力用事务/Outbox/幂等键/对账处理；围栏拒绝过期执行者提交但不能替代跨系统事务；邮件、扣款等已发生操作只能确认或补偿，**不能由恢复检查点撤销**。

可视化运维在 DAG 上标注节点状态/耗时/重试，支持重跑、跳过、强制标记成功、暂停、终止。**可观测采集不是无条件全量**：默认最小必要、敏感字段脱敏或散列、凭证禁止入库、RBAC 访问、留存有期限、审计只追加防篡改；「查看任意节点输入输出与 LLM 原始响应」须按需授权——无人值守任务上下文常携带客户数据与商业敏感信息，默认全量记录显著扩大攻击面。责任分层：Observability 输出材料、Evaluation 输出评分诊断、Outcome 由业务或获授权 Verifier 判定，各记来源与方法。

无人值守安全补充四维度：运行身份（以哪个账号执行、凭证获取与轮转）、租户隔离（Task State/Checkpoint/Artifact 边界）、网络出口（可访问域名与审计代理）、**审批超时默认行为须预定义（拒绝/继续等待/升级），超时本身不构成批准**。成本至少七项：模型 Token、工具与外部 API、计算资源、存储、网络、重试与补偿、人工审批时间；预算维度扩展到调用次数、执行时长、并发数、副作用次数、总费用，配单次上限、周期累计预算、耗尽自动暂停告警、基于历史的异常检测——**无人在场时死循环 Agent 数小时累积非预期账单是真实风险**，阈值按实际价格与历史负载设定。

## 写在最后

异步、定时与工作流分别描述执行方式、触发方式与编排结构，可自由组合。当任务需要多个 Agent 分工协调时，编排之上还有协作语义。下一篇整理 [Multi-Agent 协作与编排](/source/agent/企业级Agent手册/12-MultiAgent协作与编排)：委派与交接如何设计，协作系统如何不失控。
