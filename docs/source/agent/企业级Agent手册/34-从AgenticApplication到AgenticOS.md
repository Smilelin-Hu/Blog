# 从 Agentic Application 到 Agentic OS：全书结论与系统层展望

当同一家企业同时运行多个 Agent、使用多种框架、服务多个租户时，前面每一篇提出的工程要求都会在每个应用里被重复实现一次，且实现方式互不一致。这类重复不是某个应用的实现缺陷，而是缺少一个位于应用之下、被所有 Agent 共享的层。本文作为全系列收尾，回答哪些能力应该从应用层下沉到系统层、下沉之后可能长成什么形态——这一形态称为 Agentic OS，但它现在还不是一个已经存在的产品类别，也不必然对应一个新的内核，更接近一组正在成形的系统职责。核心判断是：**自治程度的上限不由模型能力决定，而由可撤销范围与可证明范围决定；系统层能力是否成立，取决于它在被约束方不配合时能否仍然生效**。

## 1. 全书回顾：五项架构共识

前面各篇技术细节各异，但收敛到五项相对稳定的结论。**架构对象是系统，不是一次模型调用**：Agent 拆解为 Model 与广义 Harness，模型之外的工程系统划分为业务与应用层、Agent 构建与编排层、生产运行层、治理与控制层、调优层五个能力责任域，意义在于责任归属——模型升级不应变成应用重构，任务语义不应与基础设施强绑定。**任务是需要被长期管理的对象**：任务状态机、Session 与 Task State、长时任务与会话亲和、Checkpoint 与状态分层处理的是同一件事——任务生命周期长于一次请求、宽于一个进程、可能跨越多个副本与区域，状态必须外置且可暂停恢复。**能力是动态接入的，能力发现与执行授权必须分开**：Skill、工具与 MCP、MCP Gateway 与 Registry 共同说明，模型知道某个工具存在与模型有权执行该操作，是两件必须分别设计的事。**自主性必须与权限、可撤销范围和可验证性匹配**：沙箱与工作区隔离、统一治理与审批、身份安全与出站控制反复强调同一判断——授予的自主权越大，影响半径越大，匹配的边界与证据要求也越高。**证据是变更能否发布的前提**：Trace 与指标体系、行为生成与质量验证、黄金数据集、Badcase 评估与修复闭环共同构成一条要求——任何一次 Agent Release，无论改动的是 Prompt、Skill、工具、模型还是 Harness，都需要以可复现的评估结果作为发布依据，这也是全书「生产事实驱动改进」的落点。

## 2. 六类跨篇反复出现的工程约束

上述结论在单个应用内可以落地，困难出现在组织层面。**任务缺少统一的标识与状态归属**：各框架对「一次运行」的语义不同——有的以会话为单位、有的以图执行为单位、有的以进程为单位，跨框架汇总成本、排查故障或统一限流时，第一步往往是把不同来源的运行对象强行对齐。**执行环境成为一等资源，其成本决定并发经济性**：任务在模型等待、数据检索与工具执行之间交替，平均资源占用与瞬时峰值差距很大，且多个任务可能同时结束等待、集中启动工具；按峰值预留留下大量空闲配额，按平均值部署则在集中编译、测试或读取数据时拥塞——环境的创建、空载占用、暂停恢复与销毁成本直接决定平台能支撑多少并发任务。**能力元数据不足以支撑自动化决策**：生产中真正稀缺的是三类声明——该操作是否有外部副作用、是否幂等、失败后是否可安全重试；缺少它们，重试与补偿只能靠人工约定，自动修复闭环也难以覆盖写操作。**上下文与状态的边界容易被侵蚀**：压缩、摘要与续行会不断把「不完整的对话历史」当成「可恢复的任务事实」，单应用内可靠代码规范控制，跨框架接入时缺少强制手段。**授权难以随任务派生与收回**：任务会派生子任务、子 Agent 与后台调用，授权需随之派生并在任务终止时级联收回；当身份、权限收回与执行中止分散在应用代码、Gateway 配置与运行时策略中时，「任务已终止」与「该任务的凭证已失效」并不总是同时成立。**证据的采集点分散，口径不统一**：采集点分布在模型调用、工具调用、状态变更与审批环节，各应用自行埋点时，跨应用的成本核算、故障定位与质量回归都缺少可比性。六类约束的共同特征：都不是某个应用的实现缺陷，而是缺少一个位于应用之下、被所有 Agent 共享的层。

## 3. 三条下沉判据与 Agentic OS 的窄定义

并非所有共性能力都应该下沉——把任务语义、业务规则或评估口径塞进系统层，只会得到一个更难替换的框架。三条判据：**复用性**（多个应用会重复实现且实现方式差异不产生业务价值——工作区快照、沙箱创建、Trace 采集属于此类，任务的终止条件与验收标准不属于）；**强制性**（必须由被约束方之外的组件执行才能真正生效——权限校验、网络出站控制、预算上限、审计记录属于此类；约束只写在提示词里或由被约束的 Agent 自己调用，就不是强制的）；**可验证性**（需要独立于执行方的证据来源才能被采信——关联观测、工作区状态独立校验、评估可复现性属于此类，Agent 自行上报的执行结果不构成独立证据）。一项能力只有同时满足判据一、且至少满足判据二或三，才具备下沉理由。回看六类约束：二、五、六应当下沉；一与三是接口与元数据的标准化问题，需要跨厂商约定而非由某一层独占实现；四介于两者之间——边界规范可下沉为运行服务的接口约定，具体的上下文策展策略仍应留在应用侧。据此给出窄定义：**Agentic OS 是为 Agent 任务提供公共运行对象、公共能力接入、可强制边界与统一证据的系统层，以任务、环境、能力、授权与证据为核心管理对象，不持有任务语义**。定义包含三条同样重要的否定：**不替代 Harness**——编排层决定模型看到什么、能调用什么、什么时候停止、结果如何验收，这些属于任务语义应留在应用侧，系统层提供的是任务对象的生命周期管理而不是任务该怎么做；**不等于又一个 Agent 框架**——框架通过 SDK 约束开发方式，约束在不使用该框架时即失效，系统层通过接口与强制点约束运行行为，约束应在被约束方不配合时仍然成立；**不必然意味着修改内核**——下沉的目标是让能力位于被约束方之外，而不是位于尽可能低的层次，同一项能力可以由平台控制面、宿主运行服务、容器运行时或内核机制提供，选择取决于强制性与成本而不是层次高低，与「最低充分架构」的取舍标准一致。

## 4. 两条演进线与 AI 操作系统的四种产品形态

操作系统产品侧的变化通常划分为四种形态：**交互层重构**（系统之外，独立助手或代理通过既有接口使用 OS——命令行助手、计算机操作 Agent，宿主不做改动）；**内核与服务增强**（系统之内，按 AI 与 Agent 负载改进内核、驱动与运行服务——异构适配、缓存管理、沙箱承载优化，决定并发成本上限）；**功能层融合**（系统之内，模型、上下文与工具调用融入系统功能与任务流程——系统智能服务、系统级 Agent、任务管理，与平台控制面职责高度重叠）；**底层架构颠覆**（计算、执行、保护或状态管理的基础机制重构——原生内核、专用执行域、研究原型，尚无成熟通用实现）。Agentic OS 不是从零开始的构想，而是两条已在推进的演进线在同一组对象上会合。**自上而下是平台能力下沉**：Gateway、Registry、身份与策略、任务与配额管理在 OS 产品侧表现为功能层融合——openEuler Intelligence 将本地知识库、语义接口、MCP 服务与运维工作流集成为系统智能服务；Red Hat 通过 RHEL MCP Server 把系统诊断工具开放为可调用能力（开发者预览）；Microsoft 将 Agent 的独立标准账户与 Agent workspace 纳入系统功能（相关 Copilot Actions 为实验预览），共同点是把原本每个应用自建的能力变成系统接口。阿里巴巴开源的 **ANOLISA** 是组织方式最接近的实例：定位面向 Agent 负载的操作层，按三个域组织能力——Agent 入口（cosh-ng 终端、OS Skills 系统与运维技能、ktuner 内核调优）、上下文效率（Token-less 工具输出压缩、Agent Memory 跨会话记忆、AgentSight 轨迹与 Token 可见性）、运行与安全（ws-ckpt 检查点与回滚、SkillFS 技能视图、Agent Sec Core 沙箱与校验、Blaze 沙箱生命周期）；边界声明明确保留使用者已有的 Shell、Agent 框架与沙箱，各项能力可独立启用——不要求换框架也不要求换内核，而是在既有 Linux 底座上补一层；成熟度需同时说明：截至 v1.1（2026-08-08），除 copilot-shell 外的组件多处于 0.x 版本，引用它是作为组织方式的样本而不是已经稳定的实现基线。**自下而上是系统承载增强**：轻量创建、模板预热、写时复制、按需加载、空闲回收与基于压力反馈的资源调节；Linux 的 PSI 与 cgroup v2 提供资源等待观测与配额调整的基础机制，CPU 厂商已将 Agent 沙箱密度与批量创建吞吐列为明确产品场景；这条线不改变应用的调用方式，只改变同等服务质量下能承载的任务数量与单位成本。两条线会合的位置正是环境、授权与证据——Agentic OS 雏形最先成型的地方。第四类形态当前仍以研究为主，现有公开工业实践更准确的归类是「第二类与第三类的组合」：在既有 Linux 底座上扩展 Agent 运行时与控制面，用系统机制提供强制与观测，但不重构基础机制；把它称作「操作系统」，指的是职责归属，不是实现层次。

## 5. 九类核心管理对象

操作系统的形态由其核心管理对象决定：传统 OS 管理进程、地址空间、文件与设备，Agentic OS 归纳为九类。**Agent 身份**（可被授权、可被审计的执行主体，长于单次任务；缺失时无法区分 Agent 与用户的操作责任）；**Run**（一次有目标、可暂停、可恢复的执行，分钟到数天；缺失时跨框架无法统一计量、限流与排障）；**Session**（交互与上下文的连续性载体，与 Run 交叉但不等价；缺失时上下文历史被误当作任务事实）；**Workspace**（任务可读写的文件与制品空间，随 Run 派生与回收；缺失时并发任务互相污染、失败后无法回退）；**Skill**（可复用、可发布、可校验的行动方法，独立版本化；缺失时能力沉淀不可审计也无法回滚）；**Tool 与 MCP 端点**（可发现、可调用的外部能力，独立注册与授权；缺失时能力发现与执行授权混同）；**Budget Lease**（有上限、有期限、可收回的资源与调用额度，随 Run 派生、可级联撤销；缺失时预算失控且子任务无法被约束）；**Policy**（可强制执行的边界声明，集中定义、分布判定；缺失时约束只存在于提示词中）；**Evidence**（计划、已发出操作与已确认结果的记录，长于 Run、供审计与评估；缺失时无法证明变更改进也无法安全重试）。三个对象与传统 OS 对象差异最大，值得单独说明：**Run 与进程不是同一层次的对象**——一个 Run 可能跨越多个进程、副本、区域，也可能中途长时间挂起等待人工审批，正确性依据不是「进程是否存活」而是「任务事实是否完整且一致」，Run 的身份必须独立于承载它的执行实例。**Budget Lease 最容易被忽略、但对可控自治最关键**——配额与最小权限在实现上通常分离，租约模型把它们合并为同一件事：一次授权同时限定可用资源、可执行操作、有效期限与撤销方式，并可随子任务派生；缺少这个对象时，「终止任务」与「收回该任务的全部权限」只能靠多处配置协同保证。**Evidence 必须区分三种状态**——计划中的操作、已发出的操作、已确认结果的操作，这一区分直接决定恢复策略：以「修改配置后重启远程服务」为例，恢复本地工作区文件并不会把远程服务恢复到原状态，若之前的调用已发出但结果未返回，直接重试还可能重复产生影响；工作区快照只能恢复其覆盖的文件状态，跨系统的副作用需要依靠操作记录与实时查询决定是否重试或补偿。

## 6. 三层结构与职责分界

九类对象的管理职责组织为三层，表达的是责任边界而不是调用顺序：上层解决复用性，中层解决成本与密度，下层解决强制性与可验证性；最重要的一条边界是**任务语义不下沉**。**Agent 运行服务层**承担任务对象的生命周期管理：Run 的创建、挂起、恢复与终止，Session 与 Workspace 的派生与回收，上下文、记忆与技能的读写接口，并在这些操作上绑定预算租约——接口对象是任务与状态而不是函数调用细节。研究侧已有对应探索：AIOS 将模型调度、上下文、记忆、存储与访问控制抽取为多个 Agent 共享的公共服务，其 kernel 位于宿主内核之上；IBM 研究团队在《Towards an Agent Operating System》中借鉴经典操作系统与云平台，讨论生命周期、工具调用、上下文、记忆、授权与恢复等基础能力。工业侧 ANOLISA 以系统组件形式提供了这一层的多数能力：Agent Memory 承担跨会话记忆，SkillFS 控制当前可见的技能视图并保留其余技能的可发现性，ws-ckpt 为工作区变更保留恢复点，Token-less 压缩进入模型的工具 schema 与工具响应——其中 Token-less 的放置方式值得单列：压缩发生在 Agent 与模型之间，不需要修改 Agent 框架代码，被丢弃的数组项通过标记保留可检索性使压缩可逆；按三条判据看这是一次典型的合格下沉（多个框架会重复实现同一件事，放在调用路径上而非框架内部使它无需被约束方配合），也提示上下文成本本身可以是系统层的优化对象，而不只是应用侧的提示词技巧。**系统承载层**决定同等服务质量下的成本与密度：沙箱与工作区的轻量创建、模板共享与及时回收，按任务活跃状态分配容量，模型服务与缓存的数据路径，需要时提供机密执行环境；ANOLISA 的 Blaze 管理沙箱生命周期、ktuner 负责内核参数调优。这一层的收益不体现为新功能，而体现为承载量、启动与恢复时间、尾延迟与资源成本；代价也要注意：模板共享、暂停恢复与动态调节本身都有开销，集中唤醒可能造成争用，过度回收会拖慢恢复，部署密度受任务完成时间、尾延迟与相邻任务干扰共同约束，单纯增加沙箱数量可能使整体服务质量下降。**治理与证据层**决定任务是否被允许发生、事后能否被证明：集中定义身份、策略与授权，在请求路径上分布判定点，采集模型调用与系统行为的关联证据，提供恢复与补偿所需的操作记录。工业形态：NVIDIA OpenShell 在 Agent 之外设置独立执行控制，通过沙箱、声明式策略、Landlock、seccomp 与网络代理管理文件、网络与进程访问（文档标注 alpha 状态，部分控制具有兼容降级配置）；Windows 365 for Agents 将按任务分配的执行环境与任务生命周期结合，任务结束后重置环境。ANOLISA 的两个机制可对照九类对象：AgentSight 在 Linux 上基于 eBPF 观测 Agent 行为，不要求修改 Agent 代码，把用户输入、模型调用、工具调用、Token 消耗与子 Agent 分支关联在同一视图中——正是 Evidence 要求的「独立于执行方的证据来源」；Agent Sec Core 的 Skill Ledger 给 Skill 补上状态机：已签名的技能发生变化时，Agent 在再次使用前报告 drifted，重新扫描会把阻断性发现记为 deny——「Skill 可校验」不是形容词，需要签名、漂移检测与阻断状态三样东西同时存在才成立。职责分界补充一条工程约束：**跨层调用的成本不应超过它所换取的强制性收益**。倾向由宿主与内核提供：沙箱与工作区的创建回收机制、基于压力反馈的资源调节、进程与网络的强制隔离、可信启动与机密执行、eBPF 等低干扰观测——共同特征是必须位于被约束方之外且无法通过应用层协作达成。倾向由平台控制面提供：Run 与 Session 的语义定义、评估口径与准入基线、审批流程、跨租户配额与成本核算、技能与工具的注册与版本管理——需要与组织流程对齐且在多种宿主环境上保持一致。明确留在应用侧的是任务语义：终止条件、上下文策展策略、验收标准与业务规则——一旦系统层开始规定任务该如何完成，它就从操作系统退化为框架。

## 7. 四个解耦面与解耦的代价

Agentic OS 能否成立，取决于四个解耦面上是否存在稳定接口——可以在不重写任务语义的前提下替换实现，并用同一套评估证明替换前后的能力等价。**模型与 Harness**：请求响应格式、工具调用协议、结构化输出的接口形态已相对收敛，长上下文中的指令遵循与多步稳定性无法用协议表达；破坏解耦的典型做法是把补偿模型缺陷的提示词与循环控制固化进业务代码；必须防范的失败模式是**协议兼容不等于能力等价**——降级模型可以在协议层正常返回工具调用，却在多步任务中丢失中间约束，产生一次结构合法而结果错误的执行，模型替换的验证只能通过完整 Harness 的回归评估完成，不能通过接口测试完成。**Harness 与运行时**：Run、Session、Checkpoint、Workspace 的状态语义，状态外置的必要性已成共识，但各框架对「一次运行」的定义不一致；破坏做法是编排层直接依赖某个运行时的内存结构或进程模型。**能力与协议**：工具描述、能力发现、调用与错误语义，MCP 已承担工具发现与调用协议的角色，副作用、幂等性与风险等级缺少可机读声明；破坏做法是用协议兼容代替权限设计、把「能发现」当成「可执行」——Windows App Actions 让应用声明可复用操作及其输入输出与内容类型，接口描述越清楚模型越容易选择工具并判断操作是否完成，但描述清楚不等于授权正确。**运行时与承载环境**：沙箱契约、文件与网络边界、快照与恢复接口，多后端可配置已有实践（OpenSandbox 提供环境生命周期接口并支持配置 gVisor、Kata 等运行后端），真正缺失的是快照语义的边界声明——内部快照能恢复什么、不能恢复什么需要成为接口的一部分而不是使用方的默认假设；破坏做法是假定内部快照可以撤销外部副作用。解耦不是免费的，它把复杂度从代码转移到版本组合与验证上，三项代价：**版本组合矩阵**——模型、框架、协议实现、运行时与硬件驱动独立演进时，可用组合的验证与维护成本上升；NVIDIA 围绕 DGX 硬件维护驱动、通信与操作系统的配套关系并列出硬件与最低软件版本，Red Hat 把快速硬件适配与企业 Linux 维护分开安排，面向新硬件的专用组件持续升级、仅支持最新版本、不保证向后兼容——「可支持的组合、支持周期与升级路径」本身就是交付能力的一部分，企业设计 Agent Platform 时面临同类问题，只是对象换成模型版本、框架版本与协议版本。**隐式行为变更**——系统或模型更新可能在不改变接口的情况下改变输出行为，Apple 在 Foundation Models 更新说明中提醒开发者在系统更新带来模型变化后重新验证提示词行为；兼容性讨论已从传统 API 扩展到模型版本与输出行为，后者无法用接口签名描述，只能用评估集覆盖。**评估成本**——证明替换前后能力等价需要在相同负载、相同权限与相同服务目标下运行同一套评估，这把评估体系从「质量保障手段」提升为「解耦的前提条件」：没有可复现的评估，解耦只是把风险从设计阶段推迟到生产阶段。解耦的判据：不取决于是否存在接口定义，而取决于能否在不重写任务语义的前提下完成替换，并用同一套评估证明替换后的行为在可接受范围内。

## 8. 标准化与生态化

标准化的对象应当来自多家产品的共性问题，而不是某一实现的内部结构。当前具备标准化条件的六类接口：**任务与运行对象模型**（Run、Session、Checkpoint、Workspace 的语义、状态机与相互关系，特别是「一次运行」的边界，直接决定跨框架计量、限流、排障与成本核算能否统一）；**身份与授权**（Agent 身份的表达、委派链的传递与验证、租约的授予与撤销语义，跨组织协作下缺失会使责任归属无法确定）；**能力描述与发现**（在现有工具描述之外补充副作用、幂等性、风险等级与前置条件的可机读声明——当前最欠缺且收益最直接的一类元数据，决定重试与补偿能否自动化、审批策略能否按风险分级而不是按工具名单配置）；**可观测事件语义**（模型调用、工具调用、状态变更与审批四类事件的最小字段与因果关联方式，使跨厂商 Trace 可以合并分析）；**评估与指标口径**（数据集组织、评估器接口、指标定义与门禁表达，使不同产品的评估结果具备可比性）；**执行环境契约**（工作区、快照、网络出站、文件与进程边界的声明方式，以及快照能够恢复与不能恢复的范围）。形成机制不是先写规范再等实现，而是从多方实现中提炼共性，操作系统领域有三种可借鉴：**上游贡献**——龙芯将矩阵乘法、卷积、转置等核心算子的向量优化提交到 ONNX Runtime 上游，从 1.17.0 版起原生支持，减少各发行版重复适配与长期维护独立补丁的成本；对应做法是把通用的运行对象与观测语义推入被广泛使用的开源实现，而不是维护各自的私有扩展。**多方共建**——Mooncake 由清华大学、月之暗面、阿里云、华为存储等共同开发，龙蜥社区的 SysOM 通过社区组件支持不同产品的运维集成；特征是企业负责具体产品的适配与交付，社区协作提供可共享的源码、接口与开发工具。**可复现测评**——厂商、开源社区与测评机构结合不同实现制定测试方法，在相同负载、权限与服务目标下评价性能、功能与安全；这对 Agent 生态尤其重要，因为 Agent 系统的收益高度依赖任务分布与权限设置，脱离这些条件的指标缺少可比性。ANOLISA 对 Token-less 效果的披露提供了可参照的口径样本：区分组件级基准（分别给出工具响应、工具 schema 与全链路的压缩率及处理耗时）与单次观测值（某个编码任务节省约 31.7 万 Token、约 40.5%，由 AgentSight 测得），并同时声明三条边界——节省只作用于进入上下文的工具响应、不等于整场会话账单，结果随负载变化，效果估算方法另有文档说明；这种「数字 + 适用范围 + 测量来源」的三段式披露应当成为 Agent 效能指标的默认口径，缺少适用范围与测量来源的单一百分比无论数值多高都不具备跨实现比较的价值。生态化三个递进层次：**协议兼容**（不同实现可以互相调用，MCP 在工具接入上已达到）；**语义一致**（相同调用在不同实现上产生相同的可观察后果——错误分类、重试语义与状态变更范围，目前普遍未达到，副作用与幂等性声明缺失是主因）；**证据可比**（不同实现的运行记录与评估结果可以放在同一口径下比较，达到这一层企业才能真正实现多来源 Agent 的纳管与替换）。标准化不应先于共性问题的收敛：过早把当前实现固化为规范，会把某一阶段的工程折中变成长期负担；语义尚未清晰的领域，更务实的做法是先约定可观测字段与声明格式，让不同实现的差异变得可以被度量，再讨论行为标准。

## 9. 自治阶梯与强制边界

把可靠性与完成验证、权限与审批放在一起，得到一条自治阶梯——作用不是鼓励尽快向上走，而是明确每一级必须同时具备的边界与证据：**L1 建议**（生成命令或方案由人执行，无需执行权限，建议内容可追溯）；**L2 单步获准执行**（每次变更前请求批准，操作与资源一一对应的授权，每次执行的输入输出与批准记录）；**L3 有界自主**（在限定资源、预算与操作集内连续执行，预算租约、工作目录限定、读写分离，完整调用轨迹与预算消耗）；**L4 长任务自主**（跨会话长期执行、可暂停恢复，可级联撤销的授权、可回退的工作区，计划/已发出操作/已确认结果的区分）；**L5 组织级自治**（跨系统、跨团队委派与协作，可验证的委派链、跨域强制点，跨组织可审计的责任归属证据）。隐含判断：**自治程度的上限不由模型能力决定，而由可撤销范围与可证明范围决定**——一项操作既不能撤销也不能证明其结果时，无论模型多可靠，交给自主执行都缺少工程依据。纳管多来源 Agent 时最容易出现的表述问题是把「能观测到」说成「能控制住」。一项边界只有同时满足三个条件才能称为**强制边界**：覆盖全部可用路径（任务入口、凭证获取、网络与 DNS 访问、文件与进程间通信、子进程创建、原生工具调用、后台任务与子 Agent、交互控制台）；判定组件不可用时采取失败即拒绝（fail-closed）；通过负向测试证明绕过尝试确实被拒绝。任何一条不满足，只能称为**观测边界**——能发现越界行为但不能阻止它。同理，「只读接入」是需要证明的结论而不是可以声明的属性：只有通过「写路径不可达」的负向测试才能称只读，缺少该测试时准确的表述是「未观察到写操作」。异构 Agent 接入能力分四类：**外部边界强制**（在被接入方之外建立强制点，覆盖已证明的路径集合——「已覆盖路径」表达的是已证明的子集而不是全部路径，每一项都应有独立的策略来源与独立的采集来源相互印证）；**包装器中介**（替换入口、代理或钩子实现中介，强制性依赖被接入方是否绕过包装器）；**仅观测**（只能采集行为并事后告警，需负向测试确认确实不具备写能力）；**不支持**（既不能强制也不能可靠观测，只应进入治理与认证范围，不应对外声明为受控）。描述接入能力时建议同时给出四个维度：强制属性还是观测属性、覆盖的操作语义、覆盖的执行路径、证据质量——使「我们已纳管某类 Agent」成为一句可以被检验的话。ANOLISA 说明了为什么必须逐项标注而不是整体声明：Agent Sec Core 通过 hook 接入 Qoder CLI、Qwen Code、Codex 等外部 Agent 运行时，在提示词、工具调用、技能与输出环节施加策略，属于包装器中介——策略确实在被接入方之外定义，但强制性取决于该运行时是否绕过 hook，需要负向测试界定覆盖范围；AgentSight 基于 eBPF 观测、不要求修改被观测方、证据质量高，但本身不阻断行为，属于仅观测。同一产品的两项能力落在不同类别，「是否受控」不能按产品整体回答，只能按能力、路径与证据分别回答。

## 10. 不可逆操作、补偿与撤销

可控自治的最后一块是失败处理。工作区快照解决的是文件状态回退，不解决跨系统副作用：数据库写入、消息发送、工单创建与远程服务重启在快照之外，不会随内部回滚自动撤销。长任务的恢复需要三样东西配合：区分计划、已发出与已确认三种状态的操作记录；能够识别重复提交的幂等键；针对不可逆操作的显式补偿动作。一次调用已发出但结果未返回时，正确做法是先查询实际状态再决定重试或补偿，而不是直接重放——Evidence 不只是审计材料，而是恢复逻辑的输入。共享状态还带来一类容易被忽视的失效：长期记忆或共享知识中可能保留已经失效的结论，软件更新、配置变更或环境迁移之后，此前正确的结论会变成误导；恢复任务时需要重新查询当前状态，而不是直接采信记忆中的历史结论，系统层对记忆服务的要求是必须支持更新、删除与访问控制。此外，模型参与决策后，日志、网页与工具输出既是诊断材料，也可能包含诱导操作的文本：系统需要把这些内容视为待分析的数据，不能据此扩大权限，工具端仍应按调用身份检查可执行的变更。这类风险的性质是新的，但放大的往往是传统问题——过大的权限、错误的配置与可重复执行的危险操作，在自动执行范围扩大后后果更严重。

## 11. 七个开放问题与基础机制重构

以下问题目前没有公认答案，每个都给出判断进展的标志，便于在后续一到两年内自行校准。**Run 对象应该落在哪一层**（平台控制面、宿主运行服务还是执行域基础机制；标志：是否出现被多个框架共同采用的任务状态语义，且该语义在框架不配合时仍能被宿主观测与约束）。**Agent 身份与委派链如何跨组织传递**（标志：是否出现可被独立第三方验证的委派凭证格式及配套撤销机制）。**副作用与幂等性能否成为可机读的能力元数据**（自动化重试、补偿与风险分级审批的前提；标志：主流工具协议是否引入这些字段，且运行时确实依据字段改变重试行为）。**沙箱与工作区的成本隔离曲线在 Agent 负载下的最优点**（进程级隔离、应用内核、轻量虚拟机与容器运行时各有不同的启动成本、空载占用与隔离强度——gVisor 通过用户态应用内核处理沙箱应用的系统调用，Occlum 在可信执行区内实现库操作系统，Asterinas 以 Rust framekernel 架构在保持 Linux ABI 兼容的同时缩小可信基础；标志：是否出现在 Agent 典型负载下同时公开创建吞吐、空载占用、恢复时延与隔离强度的可复现测评）。**共享状态如何既复用又不越界**（KV Cache、长期记忆与技能库的复用显著降低成本，但把原本局限于单个请求的状态带入共享环境；现有做法是按租户与任务限制访问范围——推理服务通过可选的缓存分域参数控制前缀缓存复用范围，由可信入口把租户身份绑定到相应共享域；标志：分域机制是否成为默认配置而非可选项，是否有对应的越权检测手段）。**评估如何从离线数据集走向系统级基准**（Agentic OS 的收益体现在承载量、恢复时间、干扰与单位成本上；标志：是否形成在相同负载、权限与服务目标下同时评价质量、成本与安全的公开方法）。**自进化的变更边界**（Agent 能否修改自身的 Skill、Prompt 与 Harness、在什么证据下允许；标志：是否出现被广泛接受的变更分级与准入规则，使部分自动变更可在无人审批下发布同时保留可回滚能力）。七个问题之外还有更基础的一个：面向 AI 负载的基础机制重构能否成立。研究侧已有具体方向：LithOS 针对机器学习负载重新设计 GPU 资源管理，提出细粒度调度与算子核函数的执行拆分；Agent libOS 在运行时中管理授权上限、预算与操作记录，区分外部调用的准备、派发与结算，以减少恢复时的盲目重放。共同特征是把九类核心对象直接纳入基础机制，而不是由上层反复映射到既有系统对象；但目前都限定在特定范围内，尚未形成通用实现。判断是：这类重构更可能先在专用执行域内被验证——代码修改与测试、数据分析、工具执行这类依赖与权限范围明确的任务——再逐步扩大兼容范围。

## 12. 结论：三个判断问题

回到全书起点：模型是认知核心，但可靠性不能寄托于模型本身。前面各篇沿着这一判断，把「模型之外还需要什么」展开为架构设计、构建、运行、治理与调优五个阶段的工程要求。本文补充的判断是：当同一组织中运行多个 Agent、使用多种框架、服务多个租户时，这些工程要求会从「每个应用各自实现」变为「需要被共享的系统能力」。这一变化正在两个方向同时发生——平台能力向下沉为系统接口，操作系统向上承载 Agent 负载，两者会合的对象是任务、环境、授权与证据，归纳为九类核心管理对象与三层责任结构，并给出复用性、强制性、可验证性三条下沉判据。下一阶段的工作重点不在于提出新的架构名词，而在于把已经识别的限制转化为可强制、可验证、可维护的机制。一项能力是否真正成立，判断依据始终是三个具体问题：**它能否在被约束方不配合时仍然生效；它的效果能否用独立证据证明；它能否在版本演进中被持续维护**。Agentic OS 是否会成为一个稳定的产品品类，取决于这三个问题在多少条路径上得到了肯定回答。
