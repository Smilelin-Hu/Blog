# Agent Infra 前沿探索：GOAI 赛道上的多 Agent 协同

前面四篇记录的是企业在生产环境中已经跑通的实践，本文记录的是另一种探索：当一批开发者被放在同一道命题下、面向企业内部真实的高风险流程设计多 Agent 系统时，他们会做出什么选择。2026 年 GOAI 世界人工智能开源大赛 Agent Infra 新智基座赛道的 15 项决赛作品给出了密集的答案，它们共同证明了一件事：**把 Agent 放进企业真正重要的流程里，这条路走得通，而且已经有人走出了具体的方法**——靠的不是更强的模型，而是更清楚的工程设计。

## 1. 命题、工程要求与参赛结构

赛道命题是「企业级复杂任务下的多 Agent 基础设施与协同系统，推动 Agent 从 Demo 走向 Production」，工程要求明确：系统中至少包含三个职能不同的 Agent，以 AgentTeams 作为多 Agent 协同的设计基点，Skill 作为能力封装的必选项；作品需覆盖从任务输入、任务拆解、上下文传递、工具调用、结果验证、执行证据沉淀、审批与回滚直到经验沉淀的完整链路。评审五维度：场景价值与行业可复制性、多 Agent 协同与自主闭环、Skill 工程体系与生态复用、工程落地运行验证与安全可审计、开放开源贡献。开放式选题自 2026 年 7 月启动，吸引 **7802 支队伍、8346 名选手报名，提交作品 847 个，覆盖全球 38 个国家/地区**，9 月产生 15 项决赛晋级作品。15 支队伍由 30 位选手组成，覆盖 11 所高校与 7 家企业及科研机构，高校队 7 支、企业与科研机构队 5 支、个人开发者队 3 支，比例约 5:3:2。两个结构特征值得记录：**成绩不由机构背景决定**——三类主体平均成绩接近，前五名中高校、企业、个人开发者各占其位，三支个人开发者队伍全部进入决赛，作品分别面向 IT 运维、金融数据治理与跨平台故障恢复，都是需要相当行业经验才能提出的命题；**跨单位组队成为常态**——15 支队伍中 6 支为跨单位组合占四成，「逐光」队由吉利控股与 OPPO 两家企业工程师组成，「星河引擎」队来自昆山杜克、深圳大学与上海大学，「helloworld」队由高校、科研机构与独立开发者共同构成；产业侧 8 位选手分散在 7 家单位，基本是工程师带着本岗位的实际痛点单人参赛。

## 2. 场景版图：11 个互不重合的领域，全部指向高风险流程

15 项作品涉及 11 个互不重合的行业或技术领域，没有扎堆：垂直行业 5 项（能源电力 EnergyMesh-Agents、金融 FinFlux、建筑工程设计总工之眼、零售连锁店巡 Agent、数字内容 SceneGuard），企业职能 2 项（组织治理 OrgRebase 知变、财务与渠道佣金结算 RevGuard），研发与 IT 8 项（软件工程与交付 4 项：CodeNotary、MergePilot、RepoMesh、DevOrbit；IT 运维与故障恢复 2 项：OpsKeeper、OpenXnet；网络安全运营 CyberGuard；数据工程 DataFlow-Agent）。即 33.3% 进入垂直行业专业流程、53.3% 服务研发与 IT 自身、其余为可跨行业平移的企业职能场景。一个共同点贯穿全部 15 项：**选择的都是企业内部的高风险流程**——安全处置、生产变更、资金结算、食品安全、工程出图、数据准入。这类流程的共同特征是**一次错误动作的代价远高于一次响应延迟**，因此对 Agent 的要求不止「能完成任务」，还包括权限是否受控、结果是否可验证、出错后能否退回——这也解释了为什么 15 项作品在架构上都把「谁来执行」与「谁来确认」分给了不同的角色。

## 3. 能源与金融：治理层叠加与语义准入闸门

**EnergyMesh-Agents（能源电力）** 回答园区与算力中心怎样协调用电、光伏、储能和生产负荷：现有 EMS 已具备监测控制和部分优化能力，但生产计划、设备状态和运行约束持续变化时，还需要状态确认、计划更新、独立复核和授权执行。设计是在现有 EMS 与确定性优化器**之上增加 Multi-Agent 治理层**：感知角色确认现场状态，规划角色调用优化器生成计划，审计角色独立检查关键约束并可拒绝失效计划，执行角色只执行已授权版本；实际功率曲线和成本计算由确定性优化器完成，BMS、PCS 及现场保护系统继续承担设备级控制与安全保护。已跑通状态快照、计划版本、独立审计、人工审批、模拟执行、结果回读与回退，基于公开园区运行数据、数字孪生和模拟设备验证，以原有 EMS 策略为对照基线并提供独立复算入口——让能源调度从「自动优化」走向「可信自治」。**FinFlux（金融，独立开发者作品）** 针对交易与行情数据字段定义与统计口径频繁变更：最危险的情形不是接口报错，而是**接口正常返回、数据结构校验通过，业务含义却已经改变**——这类语义漂移沿数据血缘传导进计算、风控与分析环节，直到结果出错才被发现，影响范围已难以界定。作品把数据变更准入做成一条责任链：三类 Agent 分别负责证据采集、影响评估与结论签署，五个核心 Skill 承担资产画像、血缘追溯与口径比对等可复用能力，全过程沉淀不可篡改证据；准入结论不是简单的通过/不通过，而是**放行、暂缓、拦截三条路径，每条都要说清依据**——为什么可以放行、在等什么条件、因为哪一处漂移而拦截。一次完整运行把三个角色的产物、模型调用记录与人工决定关联在一起，事后可逐步回放；以期货行情资产完成完整链路验证，三条路径均有可复现运行记录。

## 4. 工程与零售：分歧不平均，设备修好不等于商品安全

**总工之眼（建筑工程设计）** 针对设计企业出图前的多专业会审：真正的难点不在单个专业能否独立发现问题，而在**多个专业条件放在同一个工程对象上后能否同时成立**——各专业分别审查合规不意味着项目整体不存在冲突，跨专业条件遗漏、审查依据不完整最终转化为返工、沟通成本和工期风险。系统基于 AgentTeams 由协调角色组织任务，把可追溯的工程事实与审查依据分派给多个专业审查角色，汇总跨专业关系后由独立证据核验角色复核关键结论。一项重要设计是**跨专业分歧不做平均处理**：不同专业对同一工程对象意见不一致或证据不足以支持结论时，系统不强行折中、不替代专业人员作最终判断，而是保留不同专业意见及其依据，提交真人总工程师复核、裁决并留痕；专业结论、运行事件与人工决定关联在同一条证据链上。**店巡 Agent（零售连锁）** 针对门店冷柜异常处理：从停售遏制、故障诊断、维修处置到商品批次判断和恢复销售涉及多个系统与角色，最容易出的问题是维修工单已完成、设备温度恢复正常，但柜内商品是否仍然安全并不能直接得出结论。核心约束是**执行者不能自行确认自己的处置成功**：设备恢复与商品安全是两条独立确认路径，独立 Auditor 必须重新查询设备状态、商品批次、维修工单与审批记录，两条路径都通过才允许恢复销售并关闭事件；覆盖设备故障、传感器误报、审批超时、维修查询异常等六类正常与异常场景，证据不足、处置未完成或商品仍有风险时系统继续保持停售并阻止事件关闭——**这是设计中的正确结果，而不是流程失败**。

## 5. 内容与财务：原件只读零发布，金额不由模型产生

**SceneGuard（数字内容，三所高校跨单位组队）** 针对游戏、XR 与电商团队批量发布三维资产：格式、材质、网格与贴图缺陷往往在导入或上线后才暴露，修复依赖技术美术在设计工具中手工处理，难以追溯复现。一个协调角色拆分任务，四类执行角色分别负责审计、制定修复计划、执行修复与回归验证，各持独立权限边界；资产处理三条约束：**原始文件只读、修复动作限定白名单范围、每一步留存检查点**；高风险操作先行暂停经批准后续跑，回归验证未通过自动回滚并保持零发布状态——**宁可不发布，也不发布未验证通过的资产**。代码层面已打通缺陷检出、受控修复到回归复验的完整主链，具备内容寻址的证据记录与发布结论。**RevGuard（财务与渠道佣金结算）** 针对佣金结算涉及订单、合同、回款、激励政策、渠道等级与台账分散多系统靠人工核对：最常见的差错不是算错公式，而是**取用错误的政策版本、弄错等级生效时间点、漏算激励组件**——少付引发渠道争议，多付产生追偿成本，手工改账还会丢失审计依据。一名 Leader 与九类 Worker 分工完成受理、取证、政策匹配、金额计算、台账写入与结果验证；最值得记录的判断是**金额不由模型产生**：计算交给专用十进制规则引擎按政策条款精算，模型只负责组织流程、匹配政策版本与解释差异，不直接触碰数字；台账写入等高风险动作须持有审批令牌方可执行，写入失败走反向冲销，最终由独立验证角色复核账目。八个标准用例覆盖政策版本错配、等级时点冲突、激励组件漏算等典型佣金异议，审批、写入、回滚与运行轨迹均有完整记录。

## 6. 数据、安全与运维：算子复用优先，授权四项匹配

**DataFlow-Agent（数据工程，北京大学）** 针对 AI 团队持续生产训练数据：AI 可以按需求生成处理脚本，但脚本难沉淀、难修改、难稳定复跑，依赖关系不透明，运行失败说不清哪个环节失效。需求解析、算子检索与实际执行分派给不同 Agent，明确优先级是**先在平台已有算子中检索复用，确实缺少能力时才生成新算子**；Agent、可视化界面与后端围绕同一份流水线状态协作，任何修改前后都经校验；最终交付的不是对话答案，而是一条可编辑的流水线、完整运行记录与明确数据出口——让非平台专家也能搭起能保存、能修改、能复跑的数据流水线。**CyberGuard（网络安全运营）** 针对海量入侵告警下证据有限而安全动作很「重」：未经充分授权的封禁、隔离或账号禁用可能造成业务中断与证据污染。七类职能角色承担分诊、情报、取证、遏制、验证、恢复与审计，两处设计值得记录：**高风险动作与人工授权严格绑定**——每次授权对应一个具体处置提案与明确目标对象，执行角色不能自行扩大权限范围；**独立复测有权推翻上一轮结论**——发现处置目标有误则退回规划阶段重新走授权。完整运行记录串起七角色与四次人工审批，演示了模型服务异常恢复、处置目标修正、已执行动作回滚与两轮独立复测。**OpsKeeper（IT 运维，独立开发者作品）** 针对生产故障处置中告警、定位、审批、修复、复盘散落在不同的人、群聊与控制台，谁定位谁批准谁动手谁确认恢复不在同一条证据链上——修错目标、扩大影响、以「命令执行成功」冒充「业务已恢复」都会把小故障拖成生产事故。通过插件接入 AgentTeams，控制层与执行层分离：调查角色只做只读定位，修复角色须取得精确授权后执行，验证角色独立判断业务是否真正恢复；授权精确性由一组标识共同保证——**故障工单、处置提案、目标对象与具体指令必须全部匹配，任何一项不符即拒绝执行**。演示的数据库连接池耗尽故障处置中，先对错误目标拒绝执行，再经人工批准对正确目标重新派发，连接数归零、健康探针成功，全程进入审计记录与故障时间线。

## 7. 赛道要求之外的五个一致选择

角色分工与审批留痕在 15 项作品中普遍存在，这是命题设定的结果；更值得记录的是**赛道未作规定的地方，多支队伍给出了方向一致的答案**。**一是执行者不为自己的结果签字**——赛道只要求「结果验证」存在，没规定由谁执行，多支队伍不约而同把验证权从执行角色手中拿走：MergePilot 的修复角色不能为自己的修复签字，店巡 Agent 的执行角色不能确认自己的处置，CodeNotary 让作者看不到盲测、测试者不接触实现，OpsKeeper 与 RevGuard 都设独立验证角色——场景差异极大，却都判断出**自证的验证结论没有价值**。**二是授权精确到具体动作与目标**——通用做法是「高风险操作需要审批」，进一步的做法是把授权与动作本身绑定：CyberGuard 每次审批对应具体提案与明确目标，OpsKeeper 要求四项标识全部匹配，RevGuard 台账写入须持对应审批令牌——**授权不再是一张可复用的通行证，而是一次一用的具体许可**。**三是关键计算不交给模型**——EnergyMesh 把调度计算与安全边界交给确定性优化器，RevGuard 金额由专用规则引擎精算，模型只负责组织流程与解释过程：**模型擅长处理语义与流程，不擅长承担必须精确的数值责任**。**四是「拒绝」被设计成正确结果**——店巡 Agent 处置未达标保持遏制，SceneGuard 验证未通过回滚保持零发布，MergePilot 对严重风险变更永久阻断，FinFlux 拦截路径与放行路径同等完整：不把「必须给出结论」当成功标准，**证据不足时停住本身就是正确输出**。**五是一次运行留下可回放的完整证据**——同一次运行内的角色协作、能力调用、人工决定与最终状态可关联、可回放，作为交付标准的一部分而非事后补写的日志，验证方式从「演示一遍」变成「可以复查」。

## 8. 这批探索留下了什么

15 项作品不是产品，多数还没进入企业日常生产，价值在别处。**其一，把多 Agent 协同的讨论推进到了具体场景**：关于多 Agent 架构的讨论长期停留在通用层面——如何拆解任务、传递上下文、互相通信；这批作品把同样的问题放进 11 个互不重合的领域，答案立刻具体起来：园区调度的难点是计算精度与安全边界，佣金结算的难点是政策版本与时间点，门店食品安全的难点是两条独立确认路径必须都通过——**多 Agent 系统的设计难点不在协同机制本身，而在场景对「正确」的定义**。**其二，验证了高风险流程可以交给 Agent，前提是权限设计到位**：15 项作品全部选择了一年前还被普遍规避的高风险方向，共同答案不是提升模型能力而是重新组织权限——执行与验证分离、授权绑定具体动作、关键计算交给确定性引擎、拒绝作为合法终态，四条都不需要更强的模型，需要更清楚的工程设计。**其三，展示了一批可迁移的工程模式**：OpenXnet 用同一套控制面覆盖三个不同平台的故障场景，只替换平台工具、阈值与场景能力；SceneGuard 的原件只读加白名单修复适用于任何「不能损坏原始数据的受控修改」场景；FinFlux 的三路径准入结论适用于所有需要在变更进入生产前做判断的环节——模式的适用范围明显超出作品各自的原始场景。从 7 月报名到 9 月决赛，企业工程师带着本岗位痛点、高校团队从零搭起完整工程链路、独立开发者独自完成企业级系统设计，两个月密集探索的意义不在某一项作品最终走多远，而在共同证明了这条路的可行性与具体方法。
