# Agent 可观测性：从执行语义到审计与基础设施的全链路观测

一次任务的结果由 Agent 编排、模型推理、上下文处理、知识检索、工具执行与运行环境共同决定，任何环节偏差都可能表现为响应变慢、成本增加、任务失败或输出看似合理实际不可用。生产运行不能只回答「服务是否可用」，还要回答「实际执行了什么、问题在哪一步、异常由哪次调用引起」。本文提炼观测接入、执行语义、指标体系、审计与 AI 基础设施观测。核心判断：**「请求成功」不等于「任务成功」；观测记录系统能直接观察验证的事实，不把无法稳定获得的模型内部思维当必要字段**。

## 1. 观测挑战与维度对象

AI 可观测性在传统指标/日志/Trace/事件之上引入 Agent、模型、工具、上下文、任务语义，覆盖应用及其依赖的模型服务、AI 网关、推理引擎与沙箱；不等同模型训练监控，也不同于用 AI 分析运维数据的 AIOps。六大挑战：**异常与任务质量难界定**（同输入不同输出，错误规划/无效检索/工具误用/表面完成）、**动态执行路径难还原**（步骤数量运行前不确定，固定拓扑或单层调用链不够）、**外部依赖可见性受限**（托管服务只暴露有限信息，须结合多层遥测判断来源）、**跨步骤跨会话难关联**（单次调用无异常但放在任务中是重复调用或异常循环）、**异构场景难统一纳管**（语言/框架/SDK/运行形态各异）、**完整性成本安全难平衡**（Prompt 与响应既是高成本数据也是高敏数据）。

四维度：运行表现（任务是否完成、输出是否符合预期）、稳定性与性能（错误/超时/重试/异常循环/延迟）、成本与效率（Token/调用成本/资源效率）、行为审计（关键操作可追溯主体过程结果）。三层对象：任务与交互层（请求/轮次/会话/任务）、Agent 执行层（Agent/工作流/模型/检索/工具）、AI 基础设施层（网关/推理引擎/沙箱/Pod/GPU）。OTel GenAI 语义约定已纳入模型调用与 Agent 操作但仍在演进，平台须兼容开放标准并具备语义扩展能力。

## 2. 采集架构：多入口并存，统一语义汇聚

一种探针覆盖不了全部对象，统一架构允许多种采集入口并存、在汇聚中统一传输协议/执行语义/关联标识。四层：**被观测对象层**（应用侧最懂任务语义，服务端提供请求处理与调度状态，运行时采集证明进程/文件/网络实际行为）；**采集接入层**（显式埋点/SDK 自动插桩/进程探针/Hook 适配器/Daemon/服务端遥测/日志解析/K8s 接收器/eBPF 可组合，**组合采集按原生调用 ID、时间边界与来源去重**，避免同一操作重复建 Span 或累计 Token）；**统一处理层**（OTLP 统一入口，协议适配/批处理/语义规范化/采样/过滤/脱敏，保留来源与实际值/估算值标识）；**存储与分析层**（Trace/Metrics/日志/事件各进适合的存储，经共同标识联合查询，**不必强行写入同一种数据模型**；原始内容与聚合指标可用不同保存周期与访问范围）。三类数据互补：Trace 记因果（沙箱内命令还要关联子进程/文件/网络，**不让链路停在「命令执行成功」表面**）、Metrics 看聚合趋势（标签用模型/工具类型/服务/环境/结果等可控维度，不用 Session/Trace/tool-call ID 高基数字段）、日志事件存细节（经标识在 Trace 视图下钻）。

**高代码应用三方式**按语义强度与改造成本选择：GenAI Utils 手动埋点（语义最强，Entry/Agent/ReAct Step/LLM/Tool/Embedding/Retrieval/Rerank/Memory 统一封装，默认不采集消息正文，完成分类脱敏权限评估后才按需启用；流式与后台任务不能在返回迭代器时就结束 Span；框架回调接入须按 run_id/parent_run_id 关联而非线程号）、进程级自动插桩（改造少，覆盖受探针/依赖版本/导入顺序约束，**能识别「调了什么」却无法推断「为什么调、属于哪个业务阶段、结果是否达标」**）、K8s Operator 自动注入（解决探针交付与配置治理，注入后采集仍由进程内探针完成，兼容边界与方式二相同）。生产常用「探针采通用依赖 + Utils 补业务语义」混合，**手动与自动组合须避免重复建模**——探针已建 LLM/Tool Span 时手动只补 Entry/Agent/Step 与业务属性；进程内只保留一套有效 TracerProvider。建议层级 `ENTRY → AGENT/WORKFLOW → STEP → LLM/RETRIEVAL/TOOL`，跨步骤字段入口写 Baggage 传播，单操作字段写在对应 Span。

**Coding 与通用 Agent**（CLI/IDE/桌面形态，难改内部实现）走适配器 + 独立 Daemon 协同（LoongSuite Pilot 路线）：三类入口组合——原生插件回调（结构化事件，覆盖取决于版本与 API）、生命周期 Hook（记录活动或唤醒解析 transcript，**不能假定每个 Hook 都含模型用量**）、本地 transcript/日志/数据库（偏移/游标增量读取，处理延迟写入与轮转）。多来源融合**按字段确定权威来源，优先原生调用 ID 配对，时间接近只是受约束的辅助证据**；缺失与估算明确标识，不用零值或猜测补齐。tool-call 只是意图，实际执行由匹配的执行回调或结果记录确认；轮次结束依据运行级终止证据，不等同单次模型结束；LLM 耗时用原生请求开始与完整流结束，只有 transcript 时间时须说明它表示记录/首可见输出/持久化时刻。Token 优先实际用量，**输入总量已经含缓存读写时汇总不能再次相加**，累计快照换算新增，缺失不记零。采集游标与去重状态须持久化且只推进到完整记录边界；**游标已保存不代表后端已收到**——读取恢复与远端交付是两种保证，更强交付须另设待发送队列/确认/幂等。

**eBPF 无侵入观测**（AgentSight 路线）：模型调用落到系统层是一次网络请求+响应（承载提示词/输出/工具意图/用量，结合流式增量到达时刻得 TTFT/TPOT），工具调用对应进程/文件/网络三类事件；统一携带进程标识与内核时间戳，按进程关系与时序把**模型输出的调用意图与随后真实发生的系统行为对应起来**。链路：内核事件 → 解析（字节流还原 HTTP 报文）→ 关联（连接配对往返、父子串进程树）→ 输出进程事件树与会话级 Agent 轨迹。

## 3. 观测模型与执行语义

**Session/Trace/Span 三层边界**：Session 是连续会话的关联范围，可跨多次请求多条 Trace 与较长时间间隔，**不宜把整个 Session 记为一条长时间不结束的 Trace**；Trace 记录一次外部输入触发的活跃执行（用户消息/审批结果/回调/恢复事件），返回结果、转入跨请求等待或错误中断时结束——**跨请求等待恢复时创建新 Trace，经相同 Session 标识与前序关系/Trace Link 保留因果**；内部重试/模型回退/流式输出未结束活跃执行则留在同一 Trace。Span 是有明确起止与结果的操作单元，划分优先覆盖对结果/延迟/成本有实际影响的操作，过粗无法定位、过细引入噪声。三者是逻辑层级，Session 不必创建为 Span。

统一执行语义解决跨框架「同类行为不同名称」问题，十二类：ENTRY（一次外部请求的完整处理）、AGENT（一次实际 Agent 调用，子 Agent 独立记录并关联发起方）、WORKFLOW（编排结构）、STEP（**只在框架能可靠识别 ReAct 轮次时记录**，不把任意内部操作统称 STEP）、LLM（一次真实发往模型的请求，回退与实际重试分别记录）、RETRIEVAL（外部召回，LLM 自主发起的检索位于对应 TOOL 下）、MEMORY（明确的记忆读写管理，**模型读取已组装上下文不算 MEMORY**）、TOOL（一次实际执行而非调用意图，**审批等待不计入工具耗时**）、GUARDRAIL（校验对象/阶段/判定/处置，关联被保护操作）、COMPACTION（压缩触发原因与前后规模，摘要 LLM 调用位于其下，不重复保存被替换历史）、HITL（区分等待/恢复/拒绝/终止）、INTERRUPT（保留发起方/原因/位置/已有有效结果，**预期用户打断不算系统错误但也不标记正常完成**）。父子结构反映真实调用关系而非人为拼成固定树：派发工具启动的子 Agent 位于对应 TOOL 下，并行工具是同父并列 Span，Guardrail 紧邻被保护操作。ReAct 典型结构只是示例不是强制模板，Workflow 型按实际编排记录，操作仍映射到统一语义支持跨框架查询。

## 4. 错误、延迟、成本与质量观测

错误须区分类型（模型/检索/工具/参数校验/权限拒绝/超时/人工终止），记录**首次出现步骤与传播情况**；工具失败但 Agent 继续执行时，同时保留工具步骤失败状态与任务最终状态。延迟分请求端到端与步骤两层：端到端 P50/P95/P99 + 首个用户可见输出延迟（**用户可见首输出与模型首响应分开统计**）；步骤耗时识别关键路径/串行等待/慢工具/重复调用；模型性能分整体耗时、TTFT、TPOT、输出速率——区分「调用慢、首 Token 慢、持续生成慢」。稳定性问题常表现为错误率/超时率/长尾持续升高：先聚合指标发现趋势，再下钻 Trace 定位。

Token 分别记输入/输出/缓存并关联调用与执行过程；服务端返回准确用量时以服务端为准，估算须标注口径并与计费数据区分。成本从单次调用汇总到 Trace/Agent/Session/任务层，**保留模型、供应商、Token 类型、计价版本与币种以便重算审计**。效率指标（调用次数/缓存使用/无效步骤占比/完成前平均步骤数）须与任务结果结合——才能区分合理的高成本任务与重复调用/异常重试/低效路径造成的浪费。缓存命中率按缓存读取占输入比例计算，不同供应商口径不一致须按实际返回语义统计。

任务效果不能由基础运行指标推断，须在 Trace 数据上执行规则校验/模型评估/人工判断，三层评价：**最终结果**（正确完整满足要求）、**关键步骤**（检索内容/工具选择/参数/子 Agent 路由合理性）、**执行轨迹**（路径是否支持结果、有无偏离与冗余）。评估结果关联到 Session/Trace/Span，**不保存与运行链路割裂的总分**。九类通用评估器：正确性、相关性、完整性、有据性（事实能否被检索/工具结果支持）、指令遵循、检索质量、工具调用正确性、轨迹质量、安全合规。实现选择：有明确答案/格式/业务状态的优先确定性规则与业务校验，语义质量用 LLM-as-a-Judge，高风险主观结果结合专家复核与人工标注；评估记录保留评估器名称版本/对象/分数/理由/证据。**通用评估器只是基础质量信号，不能替代面向业务目标的效果评价**——业务价值、替代路径允许度、错误影响程度须代表性样本+评价标准+校准评估器+专家反馈迭代。

## 5. Agent 审计：证据链、风险检测与处置闭环

审计回答「谁在什么权限下通过哪个 Agent 发起什么任务、调用了什么、实际影响了哪些对象、是否越过意图与策略边界、结论能否复核」。职责区分：可观测性还原「发生了什么」，评测衡量「效果是否达预期」，审计判断「行为是否合规、责任如何归因、证据是否完整」，Guardrail 在执行前/中实施控制；**事后审计能推动策略改进，但不能撤销已发生的文件修改、外部请求或数据泄露**。

最小证据链四要素：**主体与范围**（用户/Agent/子 Agent/服务身份及租户/会话/任务/Trace/轮次标识）、**意图与授权**（目标/指令来源/可用工具/权限范围/审批/当时生效的策略版本）、**执行事实**（模型请求响应/检索记忆/工具参数结果/进程文件网络凭证等实际副作用）、**结果与证据**（状态/受影响对象/风险命中位置/原始事件引用/时间戳/规则或模型版本）。应用埋点表达业务语义，运行时遥测验证真实副作用，经稳定标识关联；**eBPF 补充「实际发生」的证据但缺少用户目标与业务授权，对加密流量可见性有限，须与应用埋点/网关日志/策略记录互证，不能单独据此认定越权**。原始事实追加写入保留稳定标识，检测结论以引用形成派生记录，**不为修正结论改写原始事件**；审计数据本身是高敏资产，最小采集/脱敏/独立存储/访问控制/加密/租户隔离/保留期限——完整审计不等于无边界保存全部内容。

风险检测围绕信任边界、授权范围与实际后果组织，**不只是搜索危险关键词**：敏感数据流转（进上下文/出输出/写记忆/发未授权目标）、提示词注入与目标劫持（不可信指令被采纳并改变计划产生越权副作用）、工具误用与危险操作、身份与权限滥用（委托不清/权限扩大/共享凭证/审批绕过）、上下文与供应链污染（记忆/知识库/Skill/工具描述被污染持续影响后续会话）。OWASP Agentic Top 10 是威胁建模起点而非认证标准或穷尽清单——同一命令在不同主体/环境/授权下风险等级完全不同。

分层链路「**原始事实 → 候选信号 → 上下文研判 → 已确认事件**」兼顾召回与可处置性：规则/敏感识别/异常检测先产生候选，再按会话/任务/主体回捞上下文核实指令来源/授权/是否真正执行/副作用/扩散。研判三状态：确认风险、风险链不成立或在授权内、**关键证据缺失暂无法判断——第三种不能当成安全结论**。严重性与置信度分别记录，不进同一优先级队列。模型可辅助理解长上下文与降噪但不作唯一证据来源：审计材料本身可能含注入，须数据指令隔离/限制工具/结构化输出/保留规则版本与证据引用，**模型解释也是待验证输出**。交付物不是增长的告警列表而是可调查/可分派/可验证的风险工作队列：按严重性/置信度/资产/传播/趋势/业务重要性排序，支持 Session 时间线回放与实体反查影响面；处置走带负责人/状态/动作/证据/关闭原因的流程，关闭后验证旧凭证是否续用、同类行为是否复发、策略是否生效。**检测与拦截分开建模**：实时阻断策略必须确定/低延迟/可解释/可回放并具备影子运行/灰度/快速回滚，开放式语义判断进异步调查——闭环是「观测事实→审计判断→调查处置→策略更新→执行验证」，不是把所有可疑信号直接变成同步阻断。

## 6. AI 基础设施观测：网关、推理引擎与沙箱

**AI 网关**提供跨应用统一稳定的观测入口，补应用侧覆盖不全与语义不一致：Metrics 发现趋势（请求量/错误率/延迟分位/网关处理耗时/上游等待/首 Chunk 时延/Token/缓存命中/成本）、Trace 还原路径（认证授权/策略检查/路由/缓存判断/上游调用，展示切换重试 Fallback，**Agent 传入 Trace 上下文时网关在同一条 Trace 建 Span 并继续向下游传播**）、日志解释细节（身份/请求模型与实际模型/判定结果/拒绝原因）。模型侧七方向：请求与服务状态（协议成功≠任务完成）、性能分段（**网关看到的是外部响应表现，不能替代引擎内部排队/Prefill/Decode 分析**）、模型路由（请求模型 vs 实际模型、命中原因、切换引入的错误延迟成本）、用量成本（实际/估算/计费三口径分开）、身份与策略结果、安全策略执行（优先记风险类型与处置，不默认存完整敏感内容）、Trace 关联。MCP 流量**不应全归为 TOOL**（还有初始化/协商/发现/资源读取/通知），须区分工具业务错误与协议/连接/版本问题。同一次调用 Agent Span 与网关 Span 含义不同：前者描述任务语义，后者描述代理治理过程，经上下文传播串联。

**推理引擎**只看 HTTP 耗时或 GPU 利用率都不够，须模型级指标 + Pod/GPU 资源 + 单请求调用链 + 并发调度现场四层经标识关联。模型级四信号：流量可靠性（QPS/成功率/结束原因）、用户体验（E2E/TTFT/TPOT，TTFT 反映排队与 Prefill，TPOT 接近 Decode 生成速度）、吞吐负载形态（**请求数相同不代表负载相同**，长 Prompt 放大 Prefill、长输出占 Decode 槽位，Token 维度比 QPS 更能描述压力）、调度缓存（Waiting/Running/Swapped、队列时间、KV Cache 使用与命中）。指标联合解读而非逐项设阈值：E2E 与 TTFT 同升而 TPOT 稳 → 查排队与 Prefill；TTFT 正常 TPOT 升 → 查同批 Prefill 干扰/并发/GPU 饱和；吞吐降且缓存命中降 → 查前缀变化/容量/冷实例。下钻 Pod 维度区分路由倾斜（单 Pod 异常）与整体容量不足（全部恶化），再关联 GPU 利用率/SM Active/显存带宽区分排队有余量、计算饱和、访存瓶颈。

**Continuous Batching 使请求相互影响**：单条 Trace 展示该请求的经历但不一定包含变慢的全部原因——同批其他请求共享计算与缓存。并发分析以时间为轴绘制每请求 Wait/Prefill/Decode 时间块，竖线切面即引擎执行快照：大 Prefill 阻塞同批 Decode（TPOT 同步升高，只看单条 Trace 易误判模型生成变慢）、并发突增占满槽位排队（Waiting/Queue Time/TTFT 同升而 TPOT 未必恶化，**盲目提高单实例并发可能进一步恶化尾延迟**）。排障闭环五步：指标发现异常 → Trace 找慢请求归入 Wait/Prefill/Decode/框架网络 → 并发分析还原现场 → Pod/GPU 指标验证根因 → 优化后**在相同流量与 Token 长度分布下对比验证，确认瓶颈没有转移**。

**工具与沙箱**同时记录「计划做什么」与「实际发生什么」：工具调用事实（意图与实际执行分别保留，**不能仅凭模型输出创建「执行成功」的 TOOL Span**）、沙箱生命周期（调度/创建/镜像准备/预热或冷启动/休眠恢复销毁各阶段耗时，区分工具本身慢与沙箱排队冷启动等待）、命令与进程（进程树/退出码/终止信号/OOM，stdout 记大小截断摘要或受控引用）、资源使用（关联到实例与时间窗口，解释异常退出与单次调用成本）、文件网络副作用（**只记命令与退出码无法反映脚本内部真正操作**，重点是识别相关外部影响而非无差别保存全部系统调用）、策略与隔离结果（命中策略/规则版本/处置/拒绝原因；策略拒绝发生在执行前时记判定 Span，**不伪造命令执行 Span**）。三类诊断：变慢区分审批/调度/冷启动/执行/远程依赖，失败区分参数/策略拒绝/创建失败/非零退出/信号/OOM/超时/网络，成本安全问题识别重复调用/异常循环/规格不合理/意外文件修改/越界访问。
