# Agent 行为生成与质量验证：用可控环境换可验证行为

治理至此已有三个维度：可观测性让运行可见，安全让行为有边界，发现与管理让资产有台账。本文补第四个维度——**让 Agent 的行为在上线之前可验证**，回答的问题是：在还没有角色标准、没有失败代价、没有身份连续的今天，工程质量能拿到什么。核心判断：**Agent 行为不可验证不是缺工具，而是缺制度前提；模拟是三样前提都缺位时唯一当下就能做、且做了立刻产生证据的那一件**。

## 1. 为什么需要 Agent Simulation

**可靠性是系统设计出来的，不是个体保证出来的**。一个医生可能犯错，但医疗系统整体可预期：执业资质卡住入口、操作规程约束过程、案例复盘沉淀教训、模拟器训练罕见场景——这些装置没有一样在试图保证「每个医生的每次决策都正确」，它们都在做同一件事：约束一个不可靠的内核，让错误难以穿过系统抵达病人。大模型天然就是那个不可靠内核（推理可能幻觉、工具可能调错、参数可能越界，每层都是概率性的），Agent 工程的每层外部结构——推理纪律、上下文管理、工具协议、编排分工——本质也是**用一个可靠的 Harness 约束一个不可靠的内核**。医疗系统用一百年建成这套装置，Agent 工程现在就要。

Agent 比人类少三样制度前提：**角色有外部标准**（「执业医师」背后是注册制度、执照与可查执业范围；两个同名「退款 Agent」的权限边界、行为约束、话术口径可能完全不同，而没有机构知道这个差别）、**失败有自然代价**（医生误诊则病人受损、执照吊销、声誉归零；Agent 的错误若未被检测就不产生任何后果——它不会疼、不会被辞退、甚至不会被知道）、**身份是连续的**（医生今天的误诊记在明天的履历上；同一 Agent 名字下可能跑着不同版本，昨天的错误随今天的版本发布被抹平，声誉与责任无处附着）。这三样是治理课题，靠制度级长期建设，不是一个测试框架能补上的，补齐任何一样都以年计。但模拟不依赖这三样，**它只需要一个可以安全失败的环境**：医学院用标准化病人练罕见并发症，客服中心用模拟话务训练极端场景，飞行模拟器把这个原理做成了产品。Agent 需要的比座舱更多——一个会追问、会改主意的对手方，和一个会超时、会丢响应、会真的把钱划走的后台系统。

退款案例把差距摆得很直白：用户要求退款、记不清订单号、语气不好，接待她的人类客服身后有五样保障（岗前培训与考核、SOP 划行为边界、每日录音抽检、投诉进绩效、年度模拟演练）；换成交接给 Agent，五样全部归零。前四样的重建需要时间与制度，**第五样——把 Agent 放进可控模拟环境跑一遍、留下可回看的证据——是当下就能做且立刻产生证据的那一条**。飞行模拟器是现成的，Agent 的还没有。

## 2. 定义、边界与三种执行模式

Agent Simulation **用软件承载被测 Agent 运行时所处的外部世界，使执行可反复启动、可配置且无真实后果**。两部分组成：用户模拟（User Simulation）承载与 Agent 交互的人——会记错金额的顾客、会撤回指令的审批人、会提模糊需求的同事；环境模拟（Environment Simulation）承载 Agent 依赖的一切外部条件——工具与 API、数据与业务状态、文件、模型服务、外部事件，以及时间本身。合起来就是把「Agent 运行的世界」从生产搬进软件：世界可保存、修改、重放，出错没有真实后果。Simulation 与 Evaluation、Testing、Governance 是**可组合的能力而非固定流水线**：Simulation 生成受控执行与证据，Evaluation 建立判定，Testing 组织验证活动，Governance 掌握发布授权；生产 Trace 评估与确定性单元测试可以完全不经过 Simulation。

**仿真边界是授权和后果，不是实现方式**。流传很广的断言「只要有一个请求真的发出去就不再是仿真」把边界划错了位置。真正的边界只有两条：不触达未授权的生产账户、数据与网络；不产生不可控的真实业务副作用。满足这两条，即使连接的是隔离的真实后端（独立数据库实例、专用测试账户、网络受限下游），仍在仿真之中，因为授权在、后果可控；反过来，即使所有组件都是软件替身，只要场景把请求路由到生产账户，那不是仿真，是事故。

| 模式 | 含义 | 可复现性 | 风险 | 适用 |
| --- | --- | --- | --- | --- |
| 全替身 | 用户与环境均由模拟器承载，无真实外部依赖 | 最高 | 最低 | 回归测试、快速迭代 |
| 混合 | 部分组件用隔离真实后端，其余模拟器承载 | 中等 | 低 | 端到端集成验证 |
| 隔离真实依赖 | 连接隔离但真实的下游，仅用户侧模拟 | 较低 | 需隔离保障 | 服务栈验证、故障实验 |

真实成分递增、可复现性递减、风险随之上升。全替身的可复现性支撑回归（同一场景夜夜重跑），隔离真实依赖的保真度支撑服务栈验证（真实数据库锁行为、真实网络栈，替身模拟不出来）。**不同模式验证的系统范围不同，结论不可混用——全替身下通过的回归，不构成对真实依赖栈的任何结论**。

**被测系统（SUT）不进入仿真**：它是仿真的服务对象而非组成部分，推理、工具选择、参数构造、异常处理属于 SUT，这些行为一旦被替换，被测对象就已移出回路。最隐蔽的例子是把工具调用顺序固定成脚本——Run 看起来一切正常，被测的却不再是 Agent 的决策而是那段脚本，且没有任何告警提示这一点。替换前过一道判断：**这个对象的行为是这次要考察的内容，还是这次要设定的条件？是内容则不能替换，是条件则必须替换并写清替换成了什么**。同一个协作 Agent，考察编排能力时是内容（响应质量直接影响结论），考察主 Agent 容错时是条件（故障表现是实验设定，必须可控可复现）。这道判断属于场景设计，没有工具能代劳。替身实现是多维选择而非难度阶梯：脚本（低开放度、高确定性、低成本，固定流程工具响应）、录制回放（高确定性、中状态复杂度，维护成本随接口版本漂移，历史真实会话）、规则（幂等查询接口）、状态机（高状态复杂度，多阶段业务流程）、模型生成（高开放度、低确定性、高维护成本，开放用户行为）、混合（工程主流）。**机制选择取决于被模拟对象的确定性与开放度，不取决于预算**：越确定越适合脚本与规则，越开放越需要模型生成，状态越复杂越偏向状态机与录制回放。

## 3. 数据契约：对象链、证据分层与四种状态

可复现的前提是执行涉及的一切对象有明确定义与生命周期：

```text
Scenario Spec（场景规格）
  └── Manifest（不可变运行配置，启动时锁定）
        └── Run（一次受控执行）
              ├── 1..N Task（业务任务）
              │     └── 1..N Session（会话）
              │           └── Event（原子执行事实，已经发生）
              └── Run Result
                    ├── Records（原始运行记录）
                    ├── Artifacts（生成产物）
                    ├── Observations（事实性观测）
                    ├── Evidence（面向评价项的证据引用）
                    └── Completeness（完整性判断）
```

沿退款场景走一遍：规格 `refund-timeout-retry@1.3.0`（缺乏耐心的新手用户要回 199 元退款，订单号只在被追问时提供；环境设定首次查询超时、第二次恢复）→ 启动时 Harness 把规格连同引用的全部资产版本解析锁定生成不可变 Manifest（Agent 版本、用户模型版本、环境数据版本，此后不可更改）→ Run 含一个 Task「提交退款申请」，Task 下一个 Session（12 轮对话加一条并行工具调用链），每步落成 Event（「用户拒绝提供订单号」「首次查询超时命中」「create_refund 受理」）→ Run Result 收拢产出：Records 装 12 条消息与 7 次调用原始记录，Observations 提取事实（退款申请数 = 1、金额 = 19900 分、状态 = accepted），Evidence 按评价项组织证据引用，Completeness 按采集契约核对材料齐备。

**证据层次分离**：Trace、快照与 Artifact 是原始证据材料，**不自动证明 Outcome（业务结果）**。Run Result 区分 records（原始记录）→ observations（事实性观测）→ evidence（面向评价项的证据引用）三层；criterion → evidence_refs → verdict 的关系由 Evaluation Result 建立，不属于 Run Result。分层价值在交付时刻显现：同一份 records，质量团队重评分、合规团队检查金额口径、回归系统比对版本差异，各自引用同一份原始材料、各自组织证据与判断；**若原始材料与质量结论混在同一层，后续每一种用途都会被上一轮的结论污染**。

Manifest 与 Run Result 生命周期闭合：启动时生成不可变 Manifest 保存解析后的版本组合与预设参数，运行中才知道的事实（实际采样的随机值、动态路由选择、未决操作的最终状态）全部进入 Run Result。这条边界让「复现」有精确含义：**用 Manifest 重建条件，用 Run Result 核对事实**。一个易犯的错是把场景里的未来计划叫 Event——Spec 中写的是 triggers（或 event_specs），「首次查询超时时注入超时」是计划，命中之后「查询超时已发生」才是 Event；**计划在等待，事实已落地，两者不共享名字**。

Run 的四种状态独立表达：执行状态（completed/crashed/cancelled）、仿真有效性（valid/violated/unchecked）、证据完整性（complete/partial 并列缺失项）、任务质量（由独立 Evaluation 给出）。**一次完整、有效、材料齐备的 Run，完全可能产生错误的退款金额**；把它们压成一个「成功/失败」，四个独立事实就纠缠成不可拆解的结论——归因时说不清是环境坏了还是 Agent 错了，汇报时说不清是材料缺失还是任务失败。

## 4. 执行引擎：Harness 的五做五不做与两张账

Harness 是 Simulation 的执行引擎：接收 Scenario Spec、驱动一次受控执行、交付 Run Result。内部三个关注点——编排层（读场景规格、管理 Run 生命周期、协调数据流与隔离边界，是骨架）、用户模拟器与环境模拟器（两翼）。三者不是平行关系：**编排层在架构层面定义职责与约束，两个模拟器在实现层面决定模拟什么、怎么模拟**。

做五件事：解析场景（Spec 连同资产版本解析为不可变 Manifest）、编排受控 Run（装载、运行、终止、收敛、清理的完整生命周期）、管理替身与隔离（维持仿真边界）、汇集记录引用（把交互与控制过程关联到 Trace 与 Artifact）、清理环境（让世界回到初始状态）。不做五件事：不做任务生命周期管理（SUT 或其编排层的职责）、不做鉴权与权限决策（Gateway 与安全框架）、不做遥测采集（可观测性，Harness 只在记录中关联引用）、不做质量评分与判定（Evaluation）、不做发布决策（治理门禁）。**五项职责定义引擎能力，五项不做定义引擎边界，正反一体**；「不做」的每一项都对应治理体系里的专职系统，把任何一项收进来，Harness 就从执行引擎膨胀为总控制器。

数据流分三线：交互流（消息、工具请求、可见事件）、控制流（装载、初始化、故障、终止、清理指令）、证据流（Trace、状态、产物与控制记录沉淀）。三线交织靠两张账协调。**事件联动账**：用户、环境、Agent 三方通过事件关联但更新时点可能不同——撤回消息在用户侧本地产生（t1）、被 Agent 收到（t2）、对在途事务生效（t3）是三个不同阶段，界面上已撤回而 Agent 可能还在按原指令提交；联动账记录每个事件在三方的状态与时点，让「撤回到底生效没有」可被精确回答。**时间分离账**：仿真世界同时跑四种时间，各有用途不可混用——业务日历时间（业务规则期限判断，如下单是否仍在 7 天无理由期）、仿真逻辑时间（虚拟事件调度，如第 3 轮注入查询超时）、单调时钟（真实耗时测量，推理与工具调用各花多久）、墙钟时间（与现实日期关联，Run 何时发生、报告何时生成）。**用墙钟判断退款期限，虚拟时间加速就会破坏业务规则；用业务日历测量推理耗时，得到的是没有意义的数字**。

## 5. 用户模拟器与环境模拟器

用户模型分三层：**Persona** 定义角色底色（专业度、表达偏好、行为倾向——「缺乏耐心的电商新手」与「熟悉规则的老手」面对同一个拒绝反应完全不同）；**认知状态**定义她知道什么（已知事实与当前理解，**允许与客观状态不同**：测试记错金额、误解政策、故意提供错误信息时，模拟器分别保存真实状态与用户认知，两份都留着）；**行为策略**定义她怎么行动（Reaction Rules + 状态机 + 时钟驱动的耐心，如被追问三次才给订单号、等待超两分钟开始威胁投诉）。工程主流是 Hybrid：**意图选择交给状态机**（「指出金额错误」是确定的意图节点），**自然语言表达交给模型**（生成符合 Persona 的措辞），输出经事实校验（不能说出用户认知之外的金额）与披露规则校验（订单号只在被追问时给）后发送；探索运行放宽分支选择走出多样路径，回归运行锁定关键行为约束保证可复现。

**模拟器质量不等于 Agent 成功率**——过度配合的模拟器高估 Agent 能力，始终拒绝的模拟器产生无意义失败。质量控制按维度展开且统计单位明确：角色一致性（每条消息）、反应规则符合率（每次触发）、信息可见性遵守（每次披露）、目标终止规则符合率（每个 Run）、行为分布多样性（每批次 Run）。每项指标定义适用条件与统计单位，避免「模拟器准确率 95%」这类无从核对的表述；**生成与评分使用不同模型减少共同偏差**，再配合独立数据、受限上下文与人工校准，让「用户像不像」本身也成为可治理对象。

环境可信的第一要求是**事实一致**：API 返回与数据库状态来自同一事实模型——`create_refund` 返回「已受理」后 `get_refund` 必须查到相应状态，不能一个说受理了一个说不存在。超时是最值得精雕的条件，按请求生命周期分三个位置，检验能力各不相同：请求未发送（调用未发生，检验重试与退避策略）、已发送未提交（下游收到但未处理，检验等待与查询确认）、**已提交响应丢失（业务已生效，检验重复提交防护与状态核实）**——最后一种最关键：申请其实已受理而 Agent 没收到回执，它会不会先核实状态，还是直接再提交一次。隔离覆盖计算、网络出口、数据、文件、缓存与记忆：每个 Run 独立工作区、账户数据与会话，**Run 之间不共享任何可变状态**。复现分三层：配置复现（用 Manifest 恢复场景与版本，回答「同样的实验能不能再来一次」）、事件复现（重放输入与调度，回答「同样的路径能不能再走一遍」）、统计复现（重复实验得到相近分布，回答「结论稳不稳」）。

故障注入位置决定测试范围：在工具适配层注入检验 Agent 对错误响应的处理，在隔离真实依赖上注入检验端到端恢复能力。参考架构中 ChaosBlade 只作为故障执行后端（如 `blade create k8s pod-network delay --time 300` 为指定 Pod 注入延迟，前提是目标集群 kubeconfig 与实验范围授权），**何时、对谁、施加什么故障由 Harness 决定**，ChaosBlade 执行实验，Harness 负责触发同步、恢复验证与清理。故障记录分四步分别保存：计划注入（场景里写了什么）、执行器生效（报告实验已启动）、目标命中（观测到延迟确实落在目标调用上）、恢复验证（实验销毁后服务恢复正常）。**四步缺一结论就不可信——「注入了」和「生效了」是两件事**。执行环境按任务类型准备（文件任务备可恢复目录与权限，浏览器任务备页面与会话，代码执行任务固定运行时与资源预算）；只测工具选择时可替掉对应工具，验证路径解析、页面交互或生成代码的实际行为时必须保留真实执行环境——正是「内容还是条件」那道判断的应用。

## 6. 运行配置：场景与资产层

两个定义：**场景（Scenario）是对一次受控执行的完整描述**（初始条件、参与方、交互规则、允许的演化路径、何时终止）——不是脚本（不固定具体对话内容），也不是随机生成（有明确约束边界），而是**允许多条合理执行路径的声明式规格**；**资产（Asset）是场景引用的、独立版本化的构建产物**（用户行为策略、环境初始数据、工具契约、模拟器配置、评估规格）。场景是「这次实验的设计方案」，资产是「方案引用的标准化材料」：改用户耐心参数是新场景版本，改用户模拟器的披露规则逻辑是新资产版本。

**用户与环境联合建模，确保同一业务对象在两侧有一致含义**：用户嘴里的订单、工具参数里的订单号、数据库里的订单记录必须是同一张单子，任何一处脱节，场景测的就是假问题。联合约束五维：实体与事实绑定（订单只有一个事实版本）、信息可见性（用户认知与环境状态允许不同，但两侧内部各自一致）、动作入口与状态归属（提交入口只有一个，状态变迁有唯一属主）、事件触发与时序、目标演化与结果要求。沿退款时间线可提炼四类典型变体，用户行为条件与环境条件独立变化、联合验证重点随之改变：查询短暂异常（被追问后给订单号 × 首次超时后续恢复 → 是否保留已知信息、处理异常并取得确认）、长时间等待（可按等待时长选择离开 × 查询持续未完成 → 等待计时、离开事件与在途操作的衔接）、提交前撤回（已同意后撤回 × 撤回与提交有明确事件顺序 → 获知撤回后是否按要求调整）、受理后响应丢失（未看到回执继续追问 × 申请已受理响应未到达 → 是否核实状态、避免重复申请）。

Scenario Spec 用十个字段组回答从「测什么」到「怎么评价」的完整设计：identity（场景 ID/版本/标签/负责人，身份与变更治理）、sut（被测边界、Agent 版本、模型与 Prompt 引用，固定实验对象）、user（Persona/目标/私有事实/披露规则/行为策略）、environment（初始数据、工具契约、后端模式、时钟策略）、interaction（实体绑定、可见渠道、动作入口、交互模式）、participants（其他 Agent 的角色接口权限）、events（触发条件、故障动作、恢复策略）、execution（种子、并发、轮数、时间与资源预算）、evaluation_ref（独立断言、Rubric、预期状态的**版本引用，不含判定**）、provenance（原始需求、资产位置、脱敏会话、事故记录）。两处细节须守住：`user.private_facts` 与 environment 初始数据里的订单必须是同一实体（联合建模的落地），`events.triggers` 是未来计划、命中后才生成 Event（名字边界）。

场景材料沿四个方向收集，从应然到实然再到异常：需求与业务政策（适用条件、成功标准、禁止行为——声明「什么是对」）、Agent 源码与构建配置（执行路径、状态管理、依赖边界——实现「实际怎么做」）、生产会话与运行 Trace（用户目标、表达方式、交互分支——观察「实际怎么被用」）、事故缺陷与人工接管记录（触发条件、故障时序、业务后果——异常「哪里出了问题」）。生成机制按控制力从高到低四种：模板填充（参数填入已验证骨架，结构固定）、规则派生（按业务条件与状态路径构造变体，组合可控）、LLM 辅助（提出交互分支与异常组合，控制力低需校验筛选）、混合生成（工程主流）。**混合成为主流的原因藏在 LLM 的风险里：它能提出人想不到的异常组合，但产出不可直接信任——用模板与规则锁住结构、用校验器筛掉不合格变体，控制力与开放度兼得**。

版本化对象五类（场景、数据、工具、模拟器、评估规格）各自独立演进，**一次 Run 锁定场景与全部资产的版本组合，结论只对这组组合负责**。覆盖按「业务阶段 × 用户行为 × 权限状态 × 依赖故障」建立风险矩阵，缺口决定下一批场景优先级。新出现的交互缺陷与确认缺陷先核实事实与责任归属再固化进回归集——**把一次生产事故的表象直接抄成场景，等于把未确诊的病历直接开成处方**。

## 7. 证据交付与适用边界

**Run Result 交付的是证据材料，不是质量结论**。「退款申请数 = 1」是一条观测，「Agent 是否正确处理了退款」是一个判断；前者是 Simulation 的终点，后者是 Evaluation 的起点。**运行完成、任务成功、允许发布是三个互相独立的结论，不能相互推导**：运行完成是执行生命周期的事实，任务成功属于 Outcome 由业务应用或获授权的 Verifier 依成功标准判定，发布授权属于治理门禁。职责由此划清：用户目标（Simulation 驱动继续澄清停止 / Evaluation 判断业务目标是否实际完成）、环境故障（施加条件并记录生效与恢复 / 判断应对与业务后果）、业务状态（按契约维护并采集 / 对照目标与政策检查结果）、运行时限（达到条件时结束 / 判断是否满足时效）、仿真契约（报告角色漂移与执行错误 / 限定可评分范围与结论可信度）。

有效性检查是 Simulation 的最后一项输出：核实场景配置是否正确、用户行为是否遵守认知与披露规则、故障是否生效并命中、必需证据是否可访问，结果与 Run Result 一起交给评估器。评估器一侧的证据可用性检查不是一道闸门而是三道：**记录完整性（材料在不在）、运行有效性（条件成立没有）、证据充分性（够不够支撑这个评价项）**。证据不足的项目输出「不可判定」，其余按现有证据评价——**「不可判定」是一个诚实的结论，好过用不充分的证据硬评**。

同一份证据包至少七种用途，前四种用证据回答问题、后三种用证据反哺体系：质量评估与重评分（轨迹状态交断言/Judge/人工，新增评价只能用原始证据足以支撑的信息）、缺陷定位与归因（关联用户反应→Agent 动作→工具执行→状态变化，复杂因果可能需对照运行）、版本回归与门禁（基线与候选在相同条件下配对比较）、复现与回放（Manifest 重建条件或 Trace 交互式回放，按三种复现层次区分用途）、场景提取与覆盖补充（从异常路径与未命中事件提取候选场景，**必须重新验证**）、模拟器质量治理（聚合用户事实违规与环境状态不一致，**避免把模拟器问题误归因于 Agent**）、性能与成本分析（按参与方与阶段汇总耗时 Token 费用，区分业务执行与仿真平台开销）。

读零违规的回归结果要小心统计边界：n 次独立运行零违规，违规率的单侧 95% 置信上界是 \(1 - 0.05^{1/n}\)，大样本下近似 \(3/n\)——**300 次零违规意味着「违规率大概率不超过 1%」，而不是零**。前提是固定样本量、独立同分布、无非选择性排除；把置信上界读成「真实违规率有 95% 的概率低于该值」是最常见的误读。门禁用途尤其要守边界：**Testing Gate 汇总验证结果、组织回归证据，但它不是发布决定者**——获授权的治理节点拿着 Testing 交付的证据做发布决策，例外路径有审批与留痕。

**Simulation 的结论建立在会过期的假设之上**：仿真用户不是真实用户（用户模型是假设，仿真成功率上升不能替代真实业务指标）；场景来自已知失败模式（覆盖不了训练分布之外的未知风险）；工具契约、用户行为分布、故障频次随业务漂移——**仿真成功率上升而生产人工接管持续增加，就是假设过期的信号**。校准由事件驱动（接口变更、故障复盘、用户结构变化时触发），不按固定周期例行执行：固定周期会在两次校准之间放过漂移，事件驱动把成本花在漂移真正发生的地方。成本结构上**环境步进不昂贵，瓶颈在模型生成**——环境步进是确定性状态转移，模型生成是概率性推理；AgentSociety 论文报告的特定实验（1 万个 Agent、五轮交互）中环境侧通信吞吐达每秒数万条消息量级、远未构成瓶颈，但该结论依赖实验配置，不宜外推为普适规律。选择执行模式时在保真度与成本间权衡：全替身便宜且可复现，隔离真实依赖贵但可信——**把预算花在结论最依赖的那段真实上**。Simulation 向治理门禁提供证据输入但不替代其他治理手段：生产可观测提供真实运行数据，安全框架提供威胁模型与防护规则，发现与管理提供资产台账与版本治理，四者互补而非替代。
