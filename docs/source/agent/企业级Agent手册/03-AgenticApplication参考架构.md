# Agentic Application 参考架构：责任域、平面与生命周期闭环

上一篇把 Agent 拆成 Model + Harness，本文把这套概念落到可施工的架构图上。架构设计的难点不在罗列组件，而在划分责任边界：Model 与 Harness 不分，模型升级就变成应用重构；编排与 Runtime 不分，任务语义就与基础设施强绑定；Context 与 State 不分，不完整的对话历史就被误当成可恢复的任务事实；沙箱、权限和工具描述混在一起，「模型知道某个工具」就被误解为「模型有权执行某个操作」。这四类边界问题演示阶段不暴露，任务变长、工具变多、租户变多之后集中出现。参考架构不要求每个应用建全部组件，而是按任务风险选最低充分架构。

## 1. 三个视图与五个责任域

同一套系统要用三个正交视图描述，**不能互相推导**：组件视图回答由什么组成（避免能力遗漏），平台视图回答在哪运行、由谁负责（避免责任混乱），生命周期视图回答如何从决策走向运行并被持续改进（避免把演示误当可运营系统）。同一个 State Store，在组件视图是任务事实持久化，在平台视图属数据与资源面，在生命周期视图是运行产生、调优反复读取的证据。

组件视图分五个能力责任域（是组织责任不是调用栈）：

| 责任域 | 回答的问题 | 关键边界 |
|---|---|---|
| 业务与应用层 | 系统为什么存在、什么结果可被接受 | 不实现通用 Agent 能力；触发方式与任务形态（Single/Long-Horizon/Multi/Hybrid）在此确定 |
| Agent 构建与编排层 | 如何组合成观察—判断—行动—反馈的任务循环 | 只描述和绑定能力；实际执行与影响范围归生产运行层 |
| 生产运行层 | 任务能否稳定执行 | 调度、状态持久化、工作区、隔离、恢复、流量治理 |
| 治理与控制层 | 哪些版本和动作被允许发生 | 判定点可分布在 Harness/Gateway/Runtime/Sandbox，策略、版本与审计语义集中管理 |
| 调优层 | 问题在哪、改动是否更好 | 不直接改生产 Agent；变更回流构建层出新版本，过准入门禁再上线 |

**Security 横跨五层**而非某层的单一组件：业务定风险边界、构建实现约束、运行提供隔离、治理定义身份策略审计、调优用红队仿真验证有效性。

五项设计原则（源自 AWS/Google/Microsoft/Anthropic/LangChain/OpenAI 2025 下半年以来的公开实践）：① Model 与 Harness 解耦——一起评估但实现不强绑定；② 编排层与 Runtime 解耦——接口是任务与状态而非函数调用细节；③ 状态外置、执行实例可替换——持久事件/Checkpoint/外部工作区是长任务恢复前提；④ 自主性与权限、可验证性匹配——工具凭证越多影响半径越大，用最小权限/短期凭证/出站控制/沙箱/结果校验/审批共同建边界；⑤ 可观测、安全、评估是运行前提不是上线补丁。原则不要求把系统做大：**凡被授予的自主性必须有对等的边界、证据与验证；暂不需要的能力可以不建，但要明确何时必须补齐**。

## 2. Model 与 Harness 编排层

Model 是可替换、可路由的认知核心，评估至少五维：领域任务基础能力、长上下文指令遵循与抗干扰、工具调用稳定性（参数生成/结果理解/错误修正/多步调用）、延迟价格并发与区域可用性、数据保留隐私合规。前三维决定能否完成任务，后两维决定能否规模化。规划/执行/摘要/检索/评审可按任务类型、预算、数据边界经 Model Router 路由，但**每条路由降级策略都要与完整 Harness 一起回归——协议兼容不等于能力等价**。典型失败模式：降级模型协议层正常返回工具调用，却在多步任务中丢失中间约束，产出「结构合法、结果错误」的执行。

Harness 编排层是广义 Harness 中直接组织任务循环的子域：**位于模型与运行环境之间，构造上下文、组织任务循环、提供能力、约束行为并验证中间结果的代码、配置与执行逻辑**。生产级编排层七项能力及其缺失时的失效模式：

| 能力 | 职责 | 缺失时的失效 |
|---|---|---|
| Agent Loop 与终止条件 | 调用、回送、重试、停止、恢复、预算约束 | 无终止循环、预算失控 |
| Instruction 与 Context Engineering | 指令/历史/工具描述/记忆/检索的选择编排 | 关键信息被淹没、长上下文偏离目标 |
| Planning 与 Delegation | 待办、阶段目标、子 Agent、Handoff、聚合 | 失败后无法定位与续接 |
| Tool 与 Skill 管理 | 注册、渐进披露、参数校验、结果截断外置、失败分类 | 描述挤占上下文、工具错误被当模型错误 |
| Middleware 与 Policy Hook | 调用/变更/输出前后的权限审批审计过滤 | 策略只靠提示词、模型可绕过约束 |
| Compaction 与 Continuation | 压缩、重置、文件式交接、跨窗口续行 | 上下文耗尽中断、压缩改变任务事实 |
| Steering / HITL / Verification | 运行中修正、关键动作审批、结束前测试评审验证 | 任务「看起来完成」但结果不可信 |

编排层本身是可评估对象，需与模型共同演进：模型增强后，为弥补旧模型缺陷的复杂脚手架可能反而限制新模型（Anthropic 经验，需重估甚至简化）；模型固定时，Trace 分析、错误聚类、完成前验证、循环检测同样能改变完成质量（LangChain 经验）。**不能一次定型，也不能默认越复杂越好**。

## 3. 五类信息对象：不要用一个上下文包含一切

| 对象 | 回答的问题 | 生命周期与治理要求 |
|---|---|---|
| Context | 这次模型调用该看到什么 | 单次调用级、持续重建，**不作为事实来源** |
| State | 任务已发生什么、从哪恢复 | 任务级，强一致事实记录与持久化 |
| Memory | 过去哪些经验对当前有用 | 跨任务跨会话，需写入策略、更新、遗忘与隐私治理 |
| Knowledge | 组织已有哪些可检索知识 | 与组织内容同步，需权限过滤、时效管理、来源可溯 |
| Skill | 某类任务应该怎么做 | 版本化能力资产，可发布复用回滚 |

Memory 与 Knowledge 必须分列：Memory 由 Agent 运行中生成，风险是错误经验被反复沿用，需写入门槛与遗忘机制；Knowledge 来自组织既有内容，风险是权限越界与信息过期，需与源系统权限模型和更新周期对齐。**放进同一个向量库，往往同时失去这两类治理能力**。Context Engineering 的本质不是塞进更长窗口，而是在正确时间选正确信息（摘要、结果卸载、按需检索、渐进披露、子 Agent 隔离、文件式交接）；可恢复任务的真实状态必须在模型上下文之外——压缩、截断或模型误读若能改变任务事实，任务就失去可恢复性。

Tool（可请求的能力）、Protocol（能力如何被描述发现调用）、Environment（能力真正产生影响的空间）失效方式各不同。Function Calling / MCP / A2A / Browser Use / Shell 逐级扩大能力与影响半径，但三个不等式要记住：**能力被发现 ≠ 已被授权；参数符合 Schema ≠ 意图符合目标；沙箱内运行成功 ≠ 结果可安全影响生产**。一次受控行动至少六环节：能力选择 → 身份权限判定 → 参数校验 → 隔离执行 → 结果校验 → 状态与审计记录，分布在编排层、Gateway、Sandbox 与控制面，缺任何一环都会把模型建议直接变成系统事实。

## 4. 生产运行：三平面、Runtime/Sandbox 与 Gateway

任务从秒级延长到小时/天级、从单用户到多租户、从只读到持有文件网络数据库凭证后，问题就从进程内循环扩展为分布式系统 + 安全隔离 + 企业治理。平台分三个平面（不沿用易混淆的「数据面」译法）：

| 平面 | 责任 | 关键性质 |
|---|---|---|
| 执行面 | 真实运行 Agent Loop 与工具环境操作 | 可弹性、可失败、需隔离，尽量不持有唯一真实状态 |
| 数据与资源面 | 保存可恢复事实、提供可访问能力 | 须定义一致性、所有权、保留期、隐私与租户边界 |
| 控制面 | 版本、身份、策略、部署、配额与改进 | 集中定义、版本化、可审计可回滚，判定点可分布 |

控制面不应成为每次调用的强同步依赖：**策略集中定义、判定分布执行**——Middleware/Gateway/Runtime/Sandbox 按已下发策略在请求路径判定，审计事件异步回传。代价是传播延迟，高风险策略（凭证吊销、租户封禁）需强制刷新、短期凭证或集中校验兜底。

Runtime 管任务生命周期（排队、并发、暂停取消、超时重试、Checkpoint 恢复），必须假设任何执行都可能在任意步骤中断、保证从外部状态续行而非从头重试；Sandbox 管行动影响范围（文件/进程/资源/网络/Secrets/出站），隔离粒度按风险选：进程级便宜但边界弱、容器适合多数任务、microVM/独立账号适合不可信代码与高敏数据。**Sandbox 只是技术可达范围的基础隔离，不回答是否授权、是否符合业务意图、结果是否正确**——分别由权限判定、业务审批、结果校验承担。

State Store 与 Workspace 使任务脱离单实例，各对象一致性要求不同：Event Log/Checkpoint 要强一致与顺序，Workspace 要可快照可回滚，Artifact 要可寻址可保留，Memory/Knowledge 要可检索可治理——全塞进同一个向量库等于放弃大部分要求。AI Gateway 按治理粒度分三层：**LLM Gateway 管模型调用**（协议适配/路由/限流/降级/Token 成本）、**MCP Gateway 管工具调用**（Registry/凭证托管/工具级 ACL/审计）、**Agent Gateway 管任务**（Agent 路由/会话连续性/租户配额预算）。可以是同一产品的不同能力，但粒度必须区分，否则模型成本、工具权限与任务预算在同一处策略中互相覆盖。

四种部署形态：内嵌 SDK 直连（原型低风险，状态密钥观测易分散）、托管 Harness+Runtime（快速进生产，厂商绑定与数据边界需逐项确认）、托管控制面+私有执行面（管理执行解耦，跨域连通审计更复杂）、全自托管/混合云（高合规大规模完全可控，建设运营成本最高需专门平台团队）。选型先分差异化资产与横切能力：业务 Prompt/Skill/Tool/评估标准/人机流程属应用；模型接入/任务托管/沙箱/状态/身份/观测/评估/安全策略适合平台化。**平台提供安全可运营的默认路径，应用保留组合选择权**——封装所有差异会退化为最低共同需求平台被业务绕过，只给计算不给策略观测则每个应用重复解决同一批治理问题。

## 5. 生命周期：Agent Release 与五阶段闭环

Agent 行为取决于模型、Prompt、Context、Memory、Knowledge、Skill、Tool、编排逻辑、预算与环境的组合，任一项变化都可能改变轨迹与结果。因此最小发布单元不是应用代码，而是绑定六要素的 **Agent Release**：① 模型版本/参数/推理预算/路由策略；② 编排代码/配置/循环控制/Middleware/终止条件；③ Prompt 与 Context/Memory Policy、Skill/Knowledge 版本；④ Tool/MCP/Agent 能力清单、权限策略、凭证范围；⑤ Runtime/Sandbox/资源/网络/数据保留配置；⑥ 评估数据集、Evaluator、基线、准入阈值与已知风险。要素可追踪，才能回答某任务用了哪个 Release、复现失败、证明质量「提升」而非仅仅「变化」；Prompt 可在线随手改不留版本，任何评估结论只对那一刻成立。

| 阶段 | 核心问题 | 准入/反馈机制 |
|---|---|---|
| 架构设计 | 什么形态、多大自主性、什么边界 | 架构评审、威胁建模、影响半径评估、最低充分判断 |
| 构建 | 实现为可复现 Agent Release | 离线评估、安全检查、人工评审 → Approved Release |
| 运行 | 可靠隔离可恢复地执行 | Runtime 状态机、Sandbox、Gateway、实时策略与恢复 |
| 治理 | 看见、约束、审批、追责 | 最小权限、在线检查、行为监测、人类监督、应急处置 |
| 调优 | 复现证实问题、生成改进、安全发布 | 回归、对比实验、红队、仿真、灰度、审批、回滚 |

不是瀑布而是闭环，两条关键回流：**治理/调优可指回架构设计**——形态选择与权限边界一旦确定就锁定后续成本区间，风险来自架构本身时正确动作是重新设计而非叠补丁；**调优变更必须回流构建过门禁**——模型/反馈/轨迹生成的 Prompt、Memory、Skill、Harness 补丁都是候选变更，经可复现评估、安全检查、版本化、灰度与可回滚发布才进生产，调优直连运行只是在线评估的观测通道。治理既是阶段也是横切约束，自检标准：**只能在上线后靠流程人工补齐、落不到策略接口数据结构上的治理要求，规模化后很可能失效**。没有结构化 Trace 与版本化发布单元，调优只能靠主观印象，观测—评估—发布缺一环，闭环就退化为一次性人工调参。
