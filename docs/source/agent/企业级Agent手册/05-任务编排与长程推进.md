# 任务编排与长程推进：Loop、状态机、委派与完成验证

模型的一次输出只是离散判断，企业任务却是持续过程：理解环境 → 制定计划 → 连续调工具 → 关键动作前等审批 → 委派子任务 → 经历失败恢复 → 用环境事实证明目标达成。本文提炼 Harness 执行内核如何把这些判断组织成有状态、可控制、可恢复的任务过程。贯穿案例用「生产服务漏洞修复与变更发布」：定位受影响代码、制定升级方案、分析/修改/评审分派给不同执行者、隔离环境改代码跑测试、生成变更单、发布等审批、最终以代码差异/测试报告/安全扫描/发布状态验收。

## 1. Agent Loop 与权威任务状态

Loop 是 Harness 最稳定的内核，五阶段循环：**Prepare**（读权威状态、定本轮目标、请求 Context）→ **Model**（判断行动/委派/询问/等待/申请完成）→ **Act**（交 Action Plane 完成参数、身份、策略、审批、执行）→ **Observe**（结果转结构化 Observation、更新任务事实）→ 回到 Prepare；模型申请完成则进 **Verify**，未通过产生新缺口继续循环。浏览文件、执行代码、查业务系统、调远程 Agent 都是 Act 的不同实现——**核心 Loop 保持稳定，具体能力通过扩展点加入**。

消息历史不应成为任务状态的唯一来源。权威状态是可机读对象：目标、当前阶段、Plan/Todo、已确认事实、阻塞项、子任务、Artifact、剩余预算、等待原因、完成依据。状态机至少十态：CREATED / RUNNING / WAITING_INPUT / WAITING_APPROVAL / WAITING_EVENT / PAUSED / VERIFYING / COMPLETED / FAILED / CANCELLED。**WAITING 不是失败，PAUSED 不是结束**——状态显式化，Runtime 才能在等待期释放算力并准确恢复，界面才能说明在等什么，观测才能区分执行慢、审批慢还是工具慢。模型看到的是由权威状态生成的当前任务视图，而不是从几百条历史里猜进度；安全扫描未过时即使模型说「修复完成」，状态也只能进 VERIFYING。

Loop 必须有外部终止边界：步骤数、总时长、Token 费用、工具调用次数、子任务并发、高风险动作次数都进预算。接近阈值时要求模型收敛范围、停止新委派、优先完成可交付部分或请用户选择；耗尽时产生明确终态与未完成清单，**不是悄然截断**。

## 2. Planning、Todo 与阶段门禁

Planning 的价值不是展示模型的思考过程，而是**把任务结构外部化为 Harness 和用户都能读取、修改、验证的控制对象**。按复杂度选三种模式：轻量 Todo（目标明确步骤少反馈快）、Plan Mode（只读探索 → 形成计划 → 确认后执行，适合影响面大需审阅）、Planner–Executor（Planner 维护阶段依赖、Executor 逐项执行，适合长任务多依赖可并行）。计划必须允许修订：每次重规划说明触发事实、保留已完成项，**不能通过改写目标掩盖失败**；Todo 只记改变可交付状态的事项，保持唯一当前进行项或明确并行分组。

长任务不应到最后才验证，用阶段门禁切分（案例五阶段）：影响分析（门禁：影响范围可追溯、版本事实已核验）→ 修复规划（计划获批、写权限放开）→ 变更实施（修改仅在授权工作区）→ 独立验证（强制检查全过或缺口被显式接受）→ 发布准备（责任人审批）。门禁既降低错误方向的继续投入，也为 Context 压缩、人工接管、跨窗口续行提供稳定边界。**有效阶段描述必须回答「输出是什么、证据在哪里、谁来确认」**，而不是「分析问题」「确保质量」。

Plan Mode 的关键是权限而非提示词：探索阶段只开放只读工具与计划工具（plan_enter/plan_write/plan_exit/todo_write），plan_exit 触发人工确认，获批才进入可写阶段；计划落盘 PLAN.md、Todo 存 Agent 状态，均可跨调用恢复。Prompt 可以要求「先规划再修改」，但只有权限模式、工具白名单、持久状态与 HITL 共同生效，系统才真正具备「计划获批前不可写」的约束。

## 3. Subagent：受控委派而非角色扮演

委派只解决三个具体问题：**上下文隔离**（子任务只加载相关文件工具历史，不占满主窗口）、**能力隔离**（不同模型/指令/Skill/工具/权限）、**并行执行**（互不依赖的工作同时推进）。任务很短、步骤高度依赖或共享对象频繁变化时，委派的通信合并成本超过收益，不值得用。

主 Agent 保留全局目标、计划、预算、依赖与最终结果责任，**不把「任务完成」的责任一并交出去**。每个子任务携带可机读契约七项：目标与边界、已知上下文（哪些决定不可自行改变）、能力与权限、预算、输出与证据结构、失败语义、验收条件。两个概念要分清：**Delegation 是父任务保留责任的有界委派**，结果返回仍由父整合验收；**Handoff 是控制权转移**，接收者成为责任人并获得目标、状态与恢复位置——都不能只靠一条自然语言消息，至少要有任务关系与责任变更记录。

案例协同：依赖分析（只读、可并行）与修复（隔离分支、可写）分派不同 Subagent，评审基于固定差异只读进行、不与执行者共享未提交的中间判断；多执行者同改一个工作区要用隔离分支、对象级锁或补丁合并，不能靠「大家小心」。子代理可声明为工作区中的版本化规格（description/workspace mode/steps/tools + 指令），**默认不继承父任务全部上下文与权限——父有权委派不等于子自动获得同等授权**。失败策略显式定义：关键分析 FAIL_FAST、非关键探索 BEST_EFFORT、瞬时故障 RETRY_OR_REASSIGN、需业务决定 ESCALATE；合并时校验输入版本与证据时间，避免采用基于旧状态的结论。子任务产物不是可直接复述的答案，而是新的 Observation，经 Schema 校验、版本检查与父验收才进权威状态。

## 4. 异步任务与长程续行

任务经常超过一次 HTTP 请求、一个进程或一个上下文窗口的生命周期，**任务身份必须与当前连接分离**：提交后获得稳定 task_id 与事件游标，可断开；等待或后台运行时 Runtime 释放算力；条件满足从权威状态恢复，不依赖原进程还在。后台任务/事件/恢复共用一套契约：任务 ID、父 ID、状态、创建执行者、输入与 Artifact 引用、事件序号、超时取消与幂等语义、结果位置、错误分类、Continuation。

暂停前停止创建新行动、处理可中断操作、保存最新状态；恢复时重查目标、外部条件、**工具是否实际执行过**、权限是否仍有效、工作区是否变化、剩余预算。取消沿父子任务传播，但已发生的外部副作用不能假装消失——保留事实、必要时补偿。Context Reset 只管控制语义：旧窗口结束前形成一致继续点，新窗口从权威状态重建视图；Continuation 含目标、Plan、已确认事实、失败尝试、Artifact、等待项、剩余预算与权限模式。多实例环境下 Session 存共享存储，凭 session_id 在任意实例 resume；但 Session Store 只解决会话接续，任务队列、并发控制与业务幂等仍归企业服务层。

## 5. Middleware 与执行内核测试

常见演进陷阱：每加一个能力（压缩/计划/权限/路由/观测）就往 Loop 里塞条件分支，长期状态迁移不可预测。稳健结构是**稳定内核 + 可插拔能力**：Loop 只定义阶段与状态迁移，Middleware/Hook 在明确生命周期点读 Runtime Context，返回放行、修改、短路或追加。扩展点各有禁区：Task 创建前后不得隐式改用户目标；Prepare 前后不得把持久状态只写进 Prompt；Model 调用前后不得记录不应保留的敏感推理；Action 前后不得绕过统一 Action Plane；State 变化前后不得多处各自维护权威状态；Verify 前后不得仅凭模型自述标记完成。扩展返回结构化 Decision/Patch 由核心统一提交，而非任意改共享对象；扩展自身也要有顺序、读写范围、冲突规则与失败语义。

Harness 测试不能只看最终回答，四类确定性契约测试：**状态迁移**（每态只接受合法事件，暂停取消失败正确传播）、**扩展顺序**（时机确定、冲突短路稳定）、**恢复**（任意安全点中断后可重建且不重复副作用——如「补丁已写入但测试未返回」时强制中断，恢复后应先查原测试任务而不是再改文件）、**预算边界**（阈值到达后按设计收敛）。模型输出用固定样本、录制回放或模拟器替代，把确定性控制与真实模型端到端效果分开验证。

## 6. 失败恢复与证据化完成

「Agent 失败」不是可执行的诊断，按类型选策略：瞬时模型/网络错误 → 有界退避；参数错误 → 修正；环境缺失 → 重建；权限拒绝 → 等待或终止；重复探索 → 重新规划；业务条件不满足 → 明确缺口。**有副作用的行动重试前必须先回答「上一次究竟有没有发生」**：发布/通知/写库的超时可能只是响应丢失，要生成幂等键、记录请求结果、优先查状态，无法证明未执行就不直接重复；降级切换模型/工具/环境也要记录，能力权限与结果质量可能已变。无进展检测比最大步数更早发现问题：连续同工具同参数、反复同一错误、Plan 长期不变、工作区无新增事实、少数行动间循环——先要求基于结构化证据重新规划，再缩小任务、切换能力、独立评审或转人工。

**模型只能提出完成申请，Harness 才能提交完成状态**。验证强度与风险匹配，五层递进：结构验证（Schema/必填/文件存在，低风险产物）→ 环境验证（查真实系统/文件差异/执行结果）→ 确定性验证（测试/规则/静态检查/业务校验）→ 独立模型验证（独立 Context 查质量遗漏，开放式分析）→ 人工验收（高影响/主观/合规）。Verifier 返回结构化缺口、失败证据与可修复性；验证失败不是结束而是新 Observation。案例的完成条件：依赖清单证明旧版本已替换且无传递依赖重新引入、差异仅落授权目录且与批准计划一致、测试与扫描有可寻址报告强制项全过、评审无未关闭阻断问题、变更单含影响范围回滚方案证据引用——**目标只到「形成可审批变更」时，不得把「尚未发布」误判为未完成**。最终结果是一组目标相关事实（outcome + evidence 引用 + remaining_actions），不是一句「已完成」。这套结构可迁移：合同审查以条款覆盖与签署为证据、数据修复以影响行数与回滚点为证据、工单以系统状态与用户确认为证据——变化的是 Verifier，稳定的是「模型申请、Harness 依事实提交」原则。Verifier 是单次任务的完成门禁，跨版本判断 Harness 是否更好属于 Evaluation。
