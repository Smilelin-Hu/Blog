# Agent 分布式通信：四个通信面与四档交互语义的选型地图

任务、信息、行动三类工程契约都隐含一个前提——参与执行的各方能够互相通达。Agent 从单进程走向分布式后，这个前提本身成为需要设计的对象：同一任务包含耗时差异很大的步骤，跨越多次连接与多个实例，经历较长外部等待。本文讨论的不是该用哪个中间件，而是通信语义的选择及其后果。核心判断：**让业务标识、必要状态和结果获取独立于当前连接与执行实例；协议无状态不等于业务无状态，流式输出也不直接决定任务能否离线运行**。

## 1. 四个需要重新检查的假设与状态承载主线

**调用耗时是否有界**（超时针对具体调用设置，长任务不能只靠延长同一个 HTTP 请求）；**会话是否依赖当前连接**（会话跨多次连接存在，连接只是当前传输路径，节点更替后须重新定位任务与订阅位置）；**等待期间占用哪些资源**（异步 I/O 减线程占用、持久化等待释放执行资源，但连接/内存/保留环境/存储成本仍分别测量）；**通信端点是否会变化**（扩缩容/故障接管/沙箱重建改变物理地址，契约须把业务标识与物理端点分开）。

主线是状态由谁保存、断连后如何继续，三类承载位置不能互相替代：

| 承载位置 | 常见内容 | 失效影响 | 恢复条件 |
|---|---|---|---|
| 连接与进程内存 | 当前响应、临时调用状态 | 断连或退出后未持久化内容丢失 | 查持久任务或重发允许重试的调用 |
| 外部状态存储 | 任务记录、检查点、结果引用 | 依赖存储可用性与提交一致性 | 按任务标识取可信状态按契约继续 |
| 持久消息通道 | 消息、序号、确认位置 | 超保留期或消费位置丢失形成缺口 | 保留范围内补读、按规则去重更新状态 |

任务表维护当前业务状态、通道保存交互事件，**只有采用完整事件溯源契约时通道事件日志才能成为重建业务状态的权威来源**；消息重播不自动恢复进程，也不自动撤销或去重外部操作。

## 2. 参考模型：四个通信面 × 四档语义

第一轴按通信双方身份划分，决定**契约由谁定义**（分析框架非行业标准分层）：

| 通信面 | 通信双方 | 协议层 | 核心矛盾 |
|---|---|---|---|
| 人机面 | 用户/前端 ↔ Agent | AG-UI | 要求增量可见与随时打断，而前端连接最不可靠 |
| 能力面 | Agent ↔ 工具/数据 | MCP | 毫秒级查询与分钟级任务共用一套协议 |
| 协作面 | Agent ↔ Agent | A2A | 任务天然长跑，点对点拓扑下集成与信任随数量组合增长 |
| 内构面 | 服务端组件之间 | 无标准协议 | 海量会话通道的元数据成本与多租户隔离 |

第二轴按时间与空间耦合度划分，决定**失效模式是什么**（四档非成熟度等级，可同时使用多档）：**S1 请求-响应**（响应期内耦合，短调用直接反馈，不自带长任务查询与续传）、**S2 请求域流式**（当前流依赖连接，增量可见，单凭流不保证断连补齐）、**S3 任务句柄**（执行与首次请求解耦，凭标识查询订阅，不自动保证事件重播或业务恢复）、**S4 持久通道**（生产消费解耦，消息日志+消费位置，仍需应用状态/幂等/运维机制）。

**Token 流和 SSE 只说明结果如何逐步到达，不说明任务是否独立于连接存在**。须分别检查两个条件：有无独立于连接的任务句柄（支持稍后查询）、有无事件续传位置（支持补齐保留范围内事件）——有句柄不一定有完整重播，有序号不自动保证业务可恢复。MCP 2026-07-28 移除传输层 SSE 续传，断流后新请求须应用处理幂等；A2A 允许流式更新关联持久 Task。**流结束与业务任务结束是不同边界**。

生产级通信契约六要素：**标识**（会话/任务/轮次/消息分别保留显式关联，任务标识直接绑消息线程标识会限制后台执行与跨渠道续接）、**顺序**（保序作用域通常限任务或会话内，不承诺跨会话全局序）、**投递保证**（至少一次/至多一次/恰好一次+去重键，不同通道可取不同强度）、**续传点**（与任务查询能力分开声明）、**生命周期**（临时通道设保留期，回收前核对活跃任务/未确认消息/恢复窗口）、**背压**（协议限流信号、客户端重试、网关准入、队列共同参与，明确各层流控与积压边界）。

## 3. 同步的边界与异步的代价

请求-响应四项难替代的优势：控制路径直接（但跨进程仍会超时/重复/结果未知，**不因同步接口就省略幂等和追踪**）；进程内调用栈连续（仅限无跨进程边界的调用段，跨进程同步同样需要分布式追踪）；运维复杂度低（没有保留策略/消费者组/DLQ/重投风暴等新失效模式）；成本结构简单（是否占线程取决于编程模型）。三项选择依据：调用能否在约定时限内完成（客户端/网关/服务端协调连接、空闲、总截止）；链路是否需要独立伸缩削峰（同步也能扩容熔断限流，队列进一步分离生产消费速率，值不值得引入要比较突发负载与新增成本）；失败结果是否可确认（同步也可用幂等键与状态查询，**异步化不消除外部副作用的确认责任**）。原则：**只在实际需要的链路增加机制**——短且可控用 S1，需持续进度加 S2，需执行与连接解耦加 S3，需补读削峰消费治理再加 S4。

异步三形态：**任务句柄**（结果持久性/查询保留期/故障恢复能力须服务端分别承诺，**不能仅凭返回 Task ID 推导**；配轮询/回调/订阅，结果查询有明确保留与授权规则）、**事件驱动**（围绕已发生状态变化触发后续，可与事件溯源组合但不要求；引入消息中间件不自动得到可重放审计或业务恢复）、**持久通道**（四条最小语义：以业务标识命名通道、(通道,序号) 构成续传点、保留期内可重复读取、未确认按约定重投且消费者仍须幂等——**恢复指补读消息，不等于业务执行自动恢复**）。代价清单：每跳延迟（与端到端时延目标一起测量）、幂等要求（每步骤定义幂等键，恢复前核对外部状态）、保留策略（按容灾回溯与审计需求设定）、故障传播（无超时的编排边放大失败）、可观测缺口（调用栈不连续，须全链路追踪统一关联）。

## 4. 能力面：MCP 四代传输与无状态化

| 版本 | 传输形态 | 状态位置 | 主要代价 |
|---|---|---|---|
| 2024-11-05 | stdio 与 HTTP 双端点 | 会话级常驻推送通道 | 管理服务端推送连接 |
| 2025-03-26 | Streamable HTTP 单端点 | 会话标识头+可选重放标识 | 负载均衡后需粘性会话或共享存储 |
| 2025-11-25 | 保留会话与握手 | 同上 | 首次引入实验性 Tasks |
| 2026-07-28 | 无状态核心 | 逐请求元数据+应用层显式任务句柄 | 重放责任下沉应用层 |

2026-07-28 移除协议会话标识与初始化握手，请求携带版本与能力元数据，`server/discover` 按需发现；反向调用改多轮往返（服务端返回需要输入的结果，客户端携输入再请求），变更通知经 `subscriptions/listen` 按类型订阅——**无状态核心不等于没有持续通知连接**；Roots/Sampling/Logging 进入弃用流程。核心传输与 Tasks 扩展分别协商验证，**不能把扩展能力视为所有端点的默认保证**。最易误读的一点：**协议放弃承担状态不意味着状态消失，而是责任转移到应用层显式句柄**，由应用选择持久化后端；无会话依赖的请求更容易分配到不同实例，但能否直接轮询负载均衡仍取决于工具的业务状态与持久化契约。

## 5. 协作面：A2A 异步优先与两协议的反向演进

A2A 指导原则直接写明「为可能非常长时间运行的任务与人在回路交互而设计」：核心工作单元是有状态可长跑的任务（已提交/执行中/需要输入/需要授权/完成/失败/取消/拒绝），简单交互可直接返回 Message 不建 Task，状态与结果保留由服务端契约约束、不依赖当前输出连接。两种异步机制分属不同档位，**混用会导致恢复语义不明**：流式消息属 S2（响应体即事件流，作用域限单次请求，适合进度可见，不适合作结果送达的唯一保证）；推送通知属 S3 的通知增强（载荷与流式事件同构，但规范给出的客户端做法是**收到通知后按任务标识查询拉取完整结果**——推送是「去拉取」的触发器，可寻址性由任务查询保证）。三者按需组合，关键是断连后仍有明确的结果获取路径。

MCP 削弱会话状态、A2A 强化任务生命周期，不是路线优劣之争而是通信形态使然：MCP 垂直面向工具资源访问，会话收敛利于请求在实例间分配；A2A 水平面向任务交接，长任务需要可查询的生命周期。对照：核心单元（单次工具调用 vs 有状态任务）、能力发现（按需 discover vs Agent Card 预发布可签名）、状态管理（无状态核心上推应用 vs 完整任务状态机）、传输绑定（Streamable HTTP vs JSON-RPC/gRPC/REST 三绑定）。两者组合使用：编排 Agent 经 A2A 委派，专业 Agent 经 MCP 调工具，**不宜按「有状态/无状态」为整个应用划分路线**。

## 6. 内构面：通道键、手脑分离与规模化

**通道键影响治理粒度**——通道以什么业务标识命名，隔离、限流、观测与回收就以什么粒度进行。三个公开案例：智能语音交互以会话标识为键（请求侧分区键保会话内有序，响应侧每节点只订阅相关通道集合，断连删订阅/新会话增/重启续订），收益是长会话连续性、**路由逻辑下沉消息中间件使应用节点更接近无状态计算单元**、降低无效重试的 Token 成本，按通道堆积量告警使故障定位从全局排查变为按通道定位。百炼网关限流以「用户×模型」为键：几十万并发下进程内漏桶会在突发时灌爆网关内存，方案把漏桶搬到进程外——网关固定窗口管硬上限、通道阵列管节奏、消费回调挂起指令做单通道细粒度调速，到期自动恢复；资产中心以「用户」为键，**消息只带元数据与对象存储索引不传文件本体**，通道按需创建按存活时间回收，单用户堆积不阻塞他人。共享队列也能靠分区/公平调度/应用配额做隔离，但须验证活跃通道数、每通道积压、消费公平性与管理成本，**不由队列名称推导隔离能力**。

**手脑分离**把决策循环与工具执行拆到不同进程、以会话通道相连，分别伸缩。Anthropic Managed Agents 的出发点是 **Harness 老化**：Harness 编码的是对当前模型局限的假设，模型升级后假设从优化变负担（为上一代「上下文焦虑」加的重置机制在下一代成了多余负重）。三个抽象解耦：会话=追加式事件日志、Harness=调模型路由工具的循环、沙箱=执行环境。三条通信契约：沙箱降级为普通工具（失败表现为工具层错误而非会话中断，按需申请新环境）；Harness 无状态（新实例凭会话标识唤醒拉事件历史续跑）；**会话不等于模型上下文窗口**（压缩裁剪是不可逆决策，日志侧完整保留，取用变换留给 Harness）——扩展方向是「多大脑多双手」。Qoder Cloud Agent 落到通道层：脑（Agent Runtime 决策推进）—路（RocketMQ 保序投递、Session 内有序 Session 间并行、承担等待背压）—手（Sandbox Worker 按需计算完成即释放）—底（Session State 持久化事实支撑挂起恢复重放）；同一通道体系承载三类语义不同的信息流（任务指令要削峰解耦、执行事件要保序重试死信、异步工作项要按路由弹性消费），总结为「**会话常驻、计算流动、状态可续**」——任务不属于某台机器，机器只负责当前这一棒。分离后须明确调用标识/接收确认/进度结果/取消与未知状态，**只有保存了必要工作区与操作事实后执行实例才可安全替换**。

规模化代价：会话进入万级十万级时「一会话一通道」的便宜假设失效。三种直觉方案的失效点：每会话一个标准主题（元数据/路由同步/创建回收成本压垮控制面）、广播消息（全节点重复投递过滤，单节点处理能力成整体上限）、每 Session 独立消费组（数量爆炸，动态过滤等于在消息系统外重建路由）。并列反模式是**会话与常驻工作进程一对一绑死**——把工作进程「当成宠物」：有名字、有状态、不能替换。解法是轻量通道（如 RocketMQ LiteTopic）：通道运行时按业务标识声明挂到少量预置父主题下，服务端内存中仅是字符串键，物理消息共享父主题存储；配套机制——首次发送自动创建、双向索引精准点对点投递（无需应用维护路由表）、就绪集合公平排空（调度复杂度从订阅总数降到活跃数）、空闲存活时间自动回收、单通道挂起立即释放线程不牵连他人、通配符与显式两种订阅模式。验收关注持久性/保序/隔离/恢复/规模成本，不限定某一产品机制。

## 7. 人机面与选型决策

人机面需求与可靠性倒挂：对增量可见与打断要求最高，前端连接却最易中断。**契约不应把前端连接当任务边界**：任务在服务端独立存在，前端连接只是当前观察视图，断开只影响可见性不影响推进，重连经续传点补齐（Claude Code Remote Control 即此结构：多客户端看同一会话视图，断开只是关闭观察窗口）。人在回路分两类：执行期间引导可走请求域流式（只在会话活跃时有意义），**阻塞式审批必须走持久化机制**（等待时间跨度不可预测，如待办收件箱按「需要输入/错误/已完成」组织）。AG-UI 把界面交互表达为事件（文本/工具调用/状态同步），规范仍在演进须固定版本并区分已实现与草案；前端持有的状态副本不成为任务权威；**事件格式、运行中断与消息续传是不同能力**——支持快照或人工输入不代表断连后能无缺口重播，精确补读须额外约定事件标识/保留窗口/重复处理，只恢复当前视图可重新取快照。

选型起点是**为每个通信面选择成本与风险可接受的最低充分语义，而非统一最高档**：人机面默认 S2（阻塞审批或跨设备续看升 S3/S4）、能力面默认 S1（工具耗时超网关超时或需跨实例恢复升 S3）、协作面持续交接 S3 简单交互 S1（需补读扇出消费治理组合 S4）、内构面按组件职责 S1/S3（需削峰与通道治理组合 S4 并验证规模成本）。四档可按链路组合，不构成必须逐级升级的路线。
