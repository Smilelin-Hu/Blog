# 受控执行与验证反馈：Action Plane、Sandbox、HITL 与效果闭环

模型输出的工具调用只是行动意图：没有自动获得用户身份、不等于策略允许执行、不能证明远程系统已产生预期结果。把意图转化为行动的是 Harness 的行动与反馈系统，两条链路：**Action Plane** 连接外部世界并限制影响范围，**Feedback Plane** 把进度、状态、结果与质量信号反馈给用户和下一个 Agent 版本。Tool、MCP、A2A、Sandbox、HITL、AG-UI、Trace、Evaluation 在这套架构中各有位置，不是一组并列的协议名词。本文沿用漏洞修复案例观察最后一公里：变更单为什么可自动创建而生产发布必须等审批、断线后如何继续看任务、一次失败怎样从 Trace 进入下一版 Harness。

## 1. Action Plane：统一行动契约

完整行动链不从「调用 Tool」开始也不在「返回文本」结束：**Model Intent → Schema 校验 → 身份绑定 → Policy 判定（ALLOW/DENY/ASK）→ 必要时审批 → 隔离执行 → 结构化 Observation → State/Trace → 回到模型**。三个必须区分的事实：模型看见某工具（描述进了 Context）、Harness 注册某工具（系统知道如何调用解析）、当前用户与任务获得执行授权（这次行动可以发生）。**若「出现在 Tool Schema 中」等价于「可以调用」，最小权限、用户委派和阶段性只读模式都无法成立**。

Function Calling、Shell、浏览器、Computer Use、远程 Agent 的不同表达先转换为统一 Action Request：action/task/parent_event ID、capability 及版本、参数与期望输出 Schema、actor 身份、purpose 与任务阶段、环境与资源范围、副作用/可逆性/风险分级、幂等键与超时、审批审计要求——预算、权限、审计、重试、Trace 不必为每种连接方式重新实现。**模型自由文本只能作 purpose 候选，能力名、参数类型、影响范围、身份必须由确定性代码解析校验**。Action 有自己的生命周期（REQUESTED → VALIDATED → AUTHORIZED/WAITING_APPROVAL → RUNNING → SUCCEEDED/FAILED/CANCELLED，异步系统另有 ACCEPTED/WAITING_RESULT），与 Task 状态相关但不能混同：Tool 失败不一定使 Task 失败，Task 取消可能要等已提交 Action 返回再补偿。

Action Result 不只给模型可读文本：成功/失败/未知/部分完成状态、结构化数据与紧凑 Observation、原始结果稳定引用、错误类别与可重试性、**是否已产生副作用**、实际执行身份环境时间版本成本、对 Task State 的候选 Patch、可供 Verifier 使用的环境证据。State Patch 由 Harness 统一提交，避免每个 Tool 任意改权威状态。案例要点：**「创建变更单」与「发布生产」是两个 Action**——前者 risk medium、可逆、ALLOW；后者引用已批变更单、risk high、ASK 进 WAITING_APPROVAL。即使调用同一变更平台也能分别授权审计重试验证；企业 Tool 应优先暴露业务语义，而不是让模型用通用 HTTP/Shell 自行拼接生产操作。

## 2. 协议分层与能力边界

三层职责：**Function Calling 是模型与 Harness 之间的意图接口**（结构化表达想调什么、参数是什么）；**MCP 是 Harness 与能力提供方之间的连接协议**（标准方式发现连接工具资源）；**A2A 面向拥有独立任务循环、状态与自主性的远程 Agent**（传递任务/消息/状态/Artifact，不只执行函数）。协议不替 Harness 完成授权、租户隔离、业务语义验证与效果评估——MCP Server 能描述工具不代表调用方有权访问底层数据，A2A Agent 声明完成仍需委派方按契约验收。

面向 Agent 的 Tool 设计六条：名称描述说明业务目的/适用条件/非目标；输入 Schema 用明确类型枚举边界示例；输出区分结构化结果/模型摘要/原始证据引用；标明只读性/副作用/可逆性/预览/幂等；错误稳定分类（可重试/需修参/转人工）；**认证与 Secret 留在执行侧，不进 Tool 描述与模型 Context**。粒度对应一个可描述、可授权、可观察、可验证的业务动作——过粗影响面大难审批，过细迫使模型编排大量低级步骤。

五个对象的边界（避免两种混淆：把固定 API 包装成「Agent」不会自动获得规划恢复能力；把远程 Agent 当同步 Tool 会丢失任务状态、异步事件与 Artifact 语义）：

| 对象 | 独立 Loop | 封装 | 责任 |
|---|---|---|---|
| Tool | 否 | 一个可执行动作 | 调用方组合验收 |
| MCP Server | 否 | 一组工具资源能力 | Server 实现，Host 选择授权集成 |
| Skill | 否 | 某类任务的方法脚本文献 | 当前 Agent 仍负责 Loop 与结果 |
| Subagent | 是（同一 Harness/平台） | 有界子任务执行者 | 父保留总体责任，本地 Delegation |
| Remote Agent | 是（独立部署治理） | 可持续执行的外部任务能力 | 远程对任务承诺负责，委派方负责最终采用 |

跨系统委派的互操作契约：远程身份/能力声明/版本/服务边界、目标输入与数据使用限制、remote_task_id 与本地 task_id 关联、状态进度 Artifact 错误映射、超时取消幂等重试回调、凭证委派与可审计代表关系、结果 Schema 与验收标准。**远程 Agent 不获得父的全部 Context，只发最小必要信息；返回的消息与 Artifact 都是外部输入，须过 Schema/权限/内容安全检查，不因来源是另一个 Agent 就视为可信指令**。协议选择由能力是否拥有独立任务循环、是否需要异步状态与 Artifact 决定，不由新旧流行度决定：读依赖清单用本地 Tool、连企业扫描平台用 MCP、委派独立安全团队的审计 Agent 用 A2A。Registry 管元数据/所有者/版本/健康/作用域，Gateway 管入口/身份/凭证/路由/限流/审计，Harness 按任务渐进披露；能力少信任边界简单可直连，多团队共享大量能力时 Registry+Gateway 避免凭证与治理逻辑重复。

## 3. Environment Contract 与 Sandbox

File/Shell/Code Interpreter/Browser/Computer Use 提供通用操作空间也扩大攻击面，各有必要控制：File 限根目录与读写范围（防路径穿越/敏感泄漏）、Shell 配命令策略与资源网络隔离、Code Interpreter 用临时环境+包策略+资源时限、Browser 配域名策略/下载隔离/操作确认/内容信任标记（防 Prompt Injection 与会话劫持）、Computer Use 限应用范围+预览人工确认。**能用窄 Tool 完成的高风险动作，不应优先开放通用 Shell 或 Computer Use**；长尾应用与非结构化工作区再用 Sandbox 把通用能力限在可接受边界。

Harness 不假定「本机一定有某目录某依赖可访问公网」，而是提交 Environment Contract：镜像/OS/架构、挂载与读写范围、网络出入站策略、Secret 引用与委派身份、所需工具包版本、CPU/内存/存储/GPU 配额、超时空闲与并发、持久化快照要求、审计清理策略。Runtime 按契约选环境，Sandbox 落实隔离；**环境无法满足时 Action 应在执行前失败或请求降级，而不是让模型进入不确定状态自行猜测**。四形态：本地工作区（真实文件低延迟，环境差异大难集中治理）、共享远程（复用基础设施，租户隔离与残留数据风险高）、托管隔离（按 Session/Task 快速创建生命周期清晰，数据边界需评估）、企业自托管（数据工具留在内网，自担容量补丁隔离质量）。托管 Harness + 自托管 Sandbox 可组合，关键是稳定事件状态身份契约，**不把长期 Secret 或完整企业数据复制到托管控制侧**。隔离粒度按 Agent/Session/Task/Action 递细：越细污染与横向移动风险越低、创建与状态传递成本越高；在线多租户至少按 Task/Session 隔离，长期工作区把共享基础镜像与私有可写层分开。销毁前确认 Artifact 证据已转存、临时凭证已撤销；恢复时验证镜像依赖文件版本与 Checkpoint 一致。

Secret 纪律：不出现在 System Prompt、Tool Schema、Task State 或模型可见环境变量；执行侧按 Action/身份/目的取短时凭证，只注入目标工具进程，记录使用不记录密文。网络默认限制出站目标协议数据量；网页/下载/工具返回标记不可信；高敏数据出站需额外策略或审批。**Sandbox 防进程越界，Policy 决定业务是否允许，缺一不可**——案例中 Sandbox 允许改 payment-service 副本跑构建但不给生产凭证，即使恶意文件诱导模型执行部署命令，网络与 Secret 边界仍阻止绕过 Action Plane。

## 4. Permission、HITL 与注入防护

三类身份同时记录：发起任务的用户/服务身份、发起行动的 Agent 版本、实际执行的 Runtime 身份——数据访问与副作用最终归属必须明确。权限决策综合主体、租户、任务目的、能力、参数、目标资源、环境、阶段、数据敏感度、影响范围、可逆性、预算与历史审批；**仅按 Tool 名称做静态白名单，无法区分「读一条测试记录」和「导出整个生产库」**。策略结果三类：ALLOW（记录决策依据）、DENY（模型如何解释都不执行，返回结构化原因与允许替代项）、ASK（需指定人或系统确认）。**ASK 不是默认兜底**——过多审批让用户机械确认、Agent 失去连续性，优先用更窄 Tool、参数约束、预览、资源范围与 Sandbox 降风险。默认策略参考：项目内非敏感读取 ALLOW；有权业务数据 ALLOW 或按等级 ASK；工作区修改未提交 ALLOW+Diff 可撤销；外发消息/发布/支付/删除/改生产 ASK 或 DENY 且要求预览；跨租户数据/绕过安全控制/索取长期 Secret 一律 DENY。

HITL 三层次：Plan 审批（执行前确认目标范围方案影响面）、Action 审批（批准拒绝修改某次调用）、结果验收（高影响 Artifact 最终签署）。审批请求包含想做什么/为什么/以谁身份/作用对象/预计影响/参数差异/可逆性/失败处理/批准范围（仅本次、当前 Task 还是一类受限动作）；**批准后 Harness 仍要重校验对象版本与策略，防止等待期间环境已变**。不可逆高影响动作统一 **Preview—Approve—Commit—Verify**：Preview 展示接近实际提交的内容与影响（无法回滚必须明说）、Approve 绑定身份范围对象版本、Commit 用幂等键、Verify 查真实系统状态；验证失败进 Repair/Compensate/Escalate，不把已发送请求当成功。SDK 的 canUseTool 回调只是交互入口，企业后端仍按登录身份/租户/资源版本/Policy 再做确定性判断；生产发布审批生成短时限定目标的授权，**不是把整个 Session 切成无条件放行**。

Steering 是高优先级任务事件，由状态机在安全点处理；紧急中断取消可中断行动并阻止新 Action。恢复前把用户新要求提交 Task State、判断现有 Plan/权限/后台任务是否仍有效再重建 Context——**直接把消息追加到长历史末尾，可能覆盖不了已进执行队列的旧计划**。Guardrail 可部署在输入/Context/Action/结果/输出各阶段但不是唯一边界：可编码的权限资源限制用 Policy 与 Sandbox，模型分类器识别复杂语义风险作额外信号。Prompt Injection 关键防线是**区分指令与数据**：网页邮件文档工具结果远程返回都是不可信输入，不能改变平台政策、授权范围或 Tool Set；保留来源、限制外部文本进高优先级指令层、数据外传与高风险 Action 独立授权、必要时隔离读取与执行阶段。

## 5. Streaming、Channel 与交互协议

长任务只在结束返回一段文本，用户无法知道在做什么、是否等审批、能否纠偏。外部语义事件八类：Text（可见输出增量）、Progress（阶段/Todo/里程碑）、Tool（意图/状态/紧凑结果，不泄 Secret）、State（驱动界面与业务状态机）、Approval（预览/风险/选项）、Artifact（文件/Diff/版本）、Error（分类/可重试性/下一步）、Usage（Token/费用/预算）。**模型隐藏推理不需要通过 Streaming 暴露**，用户要的是状态、说明、行动、证据与可操作选项。

Channel 是入口适配层不重写 Harness：外部身份映射平台身份、消息线程映射 Session 并选择创建 Task、附件按钮转统一输入事件、Harness 事件转渠道消息卡片、跨入口保持任务连续、渠道级限制脱敏审计。IM 线程可查看后台 Task、IDE 创建的任务可在 Web 继续审批——**Channel 不应成为唯一状态存储**。AG-UI 承载 Agent 与应用间双向流式事件（生命周期/文本/工具/状态/中断），A2UI 让 Agent 输出声明式界面（表单卡片列表），客户端用本地受信组件目录渲染而非执行模型生成的任意代码；A2UI 描述「界面是什么」、AG-UI 处理「如何交换事件」，Payload 可经 AG-UI 传输，两者不互替。

事件流假定会断线重连、消费速度不同：每事件单调序号或可恢复游标，重连从最后确认位置续传、服务端去重；快消费者收增量，慢消费者先读快照再补关键事件。高频 Token 与细粒度日志可合并采样或仅调试发送，**状态/审批/Artifact/终态事件不能因背压丢弃**。Cancel 要区分「已收到取消」与「底层 Action 已安全停止」。同一 Task 按接收者身份与 Channel 能力生成视图：开发控制台看 Tool 与 Trace、客户应用只看业务进度、审批人看影响对象、观察者只见等待状态——不能把内部 Trace 原样广播。先稳定 Task/Event/Approval/Artifact 语义模型，再选 AG-UI/A2UI/WebSocket/SSE 作承载。托管路径的一个细节：QCA 等待工具确认时返回 session.status_idle 且 stop_reason.type 为 requires_action，**不能仅凭 idle 判定完成**，要读 stop_reason.event_ids 处理待响应动作，用 user.tool_confirmation（关联 tool_use_id）回传确认，普通 user.message 不能代替工具确认。

## 6. Trace 与 Evaluation：从失败到 Harness Patch

质量来自模型与 Harness 的组合，问题可能在 Context/计划/工具/权限/环境/状态/验证任一环节，**Trace 不能只记模型输入输出**。Task Trace 至少关联：Agent/Model/Harness 版本、Session/Task 与父子拓扑、Context Manifest 与压缩决策、Plan 与状态迁移、模型调用延迟 Token 成本、Action Request 与策略审批、工具环境远程结果、Workspace 变更与 Artifact、重试降级与失败分类、Verifier 结果与完成证据、业务 Outcome 与用户反馈。**Trace 要因果关系而非按时间排列的日志**：哪份 Context 产生哪个 Action、更新哪些状态、触发哪次验证都要能关联。敏感原文可脱敏加密只存引用，核心元数据与决策事实不能缺。Build 时就要为每个 Loop 阶段/Middleware/Tool/Subagent/Verifier 定义 Span，明确默认与调试记录范围、敏感字段处理、版本关联、Outcome 写回来源、采样后如何保留错误与长尾、跨系统 Trace Context 传递——**Build 时没有稳定事件版本关联 ID，后续平台补不出可信 Trace**。

两套系统分清：**Agent Harness** 完成一次任务（输出轨迹/Artifact/证据/Outcome），**Evaluation Harness** 以一致方式运行回放比较版本（输出指标/失败聚类/版本差异/发布建议），必须固定或披露模型、推理设置、工具版本、预算、重试、环境与评分规则，否则分差可能来自运行条件而非被评的 Patch。Verifier 是单次完成门禁，Evaluation 是跨版本质量判断；Verifier 可作 Evaluation 数据来源，但不应把昂贵的发布评估器嵌进每次线上任务。三层评测对象：**单步**（工具选对没有/参数正确没有/检索含关键证据没有——规则/Schema/标注/局部模型评分）、**轨迹**（绕路/重复/越权/错误委派/过度消耗——轨迹规则/序列比较/评审）、**最终结果**（目标真正达成没有——测试/业务查询/人工验收/独立 Evaluator）。只评结果掩盖高成本高风险轨迹，只评单步惩罚有效探索；人工反馈也不是天然真值，要区分用户偏好、业务结果与操作便利性。

效果闭环不从单条失败直接改 Prompt：**Trace+Outcome → 失败聚类 → 根因诊断 → 最小针对性 Patch → 回归 → 发布门禁 → 新版本**。Patch 与根因一一对应：缺事实调 Context/Knowledge、错误经验反复修 Memory、不会稳定方法增修 Skill、工具误用改 Schema 或权限、无进展调 Loop/Plan/模型、环境不一致修 Environment Contract、完成误判强化 Verifier——**只有确定模型能力本身不足才换模型或路由**。回归集同时含原失败用例、相邻正常用例与安全对抗用例；模型升级后重查旧补偿逻辑，删除失效或阻碍新模型的规则。案例：Agent 把用户对草稿的同意误解为允许生产发布，沿因果链定位到 Policy 仅按 Tool 名称匹配错误返回 ALLOW——正确 Patch 不是 Prompt 加一句「谨慎发布」，而是拆分 change.create 与 production.deploy、发布策略校验审批类型/对象版本/目标环境/短时授权，并加「草稿获批不得推导为发布获批」的确定性回归用例，再跑原失败/正常/合法发布/注入对抗四类样本确认修复没有让所有任务陷入无效审批。
