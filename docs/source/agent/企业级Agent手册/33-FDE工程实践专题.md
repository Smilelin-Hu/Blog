# FDE 工程实践专题：AI Coding 全生命周期的规格驱动交付

本专题整理自某国企数科公司「IPO 板块符合性对标平台」项目的全生命周期复盘（客户与数据已脱敏，方法论、流程与量化指标为真实项目还原），是笔者长期基于 Qoder 产品多个 AI Coding 项目的实践经验沉淀。核心论点：**AI Coding 走进企业级交付的深水区，瓶颈已从「能不能生成」转移到「能不能对齐、能不能验证」；破局之道不是更强的模型，而是一套工程规范——以 Spec-Driven Development 为主线，用「三阶段·三产物·三闸门」把 AI 的高产出锁定在可追溯、可验收、可信的轨道上**。

## 1. 真问题不在代码生成：项目全景与成果看板

编码阶段的问题大多是局部的、可验证的——测试跑不过、编译报错，反馈链路以秒计；需求-设计阶段的问题都是系统性的：口径歧义、跨文档不一致、业务规则遗漏、依赖信息缺失，一旦流入编码阶段返工成本放大一个数量级，传统上恰恰是最难标准化、最容易「带病流转」的环节。AI 的介入没有消除反而放大了它——**AI 生成的产物「长得太像真的」**：格式规范、编号完整、逻辑自洽，只有对照原始材料逐条核验才能发现偏差；当产出的边际成本趋近于零，质量的边际成本反而成了主要矛盾。项目起点是老板一句话交办：把公司经营现状与各上市板块（沪深主板/科创板/创业板/北交所）的发行上市要求做符合性对比，输出可观测报表。业务复杂度是规则密集加强合规加可追溯的理想检验场景：四个板块 × 多套财务/创新/合规标准 × 数十项指标要素（56 个财务要素、27 个上行要素，收敛为 43 项内置指标），且有多层 AND/OR 嵌套条件组（北交所某标准嵌套达 4 层）。实践中迭代出两代产物：一代「分析平台」（诊断引擎 + 评分推荐 + 报表导出）与二代「观测平台」（可观测报表 + 指标大屏 + 资格对比矩阵），共享同一套方法论内核。成果看板：代码生成实现率 **88.3%**（达到进入联调门槛，AI 承担近九成代码产出）、整体完成度 **97.4%**、SRS 基线五轮升版（V1.0→V1.5，每版都有评审输入与修订记录）、EARS 用户故事 **120 条**（全编号、可测试、与验收标准双向追溯）、PRD 联合评审拦下 **7 阻断 + 16 重要**（若在编码期发现均为数天返工）、联调前静态拦截 **13 个接口缺陷**、团队规模仅 **2 人**（完成以往多人项目工作量，但无法靠加人并行提速）。

## 2. 方法论总纲：三阶段·三产物·三闸门

SDD 的做法是先以结构化规格把「要做什么、怎么做、分几步做」固化下来再驱动 AI 编码，让 AI Coding 从「凭感觉生成」转为「照规格实现、可追溯、可验收」。骨架是三阶段三产物三道闸门：**Requirement** 产出 requirement.md（EARS 用户故事 + 验收标准，回答做什么/为谁/怎样算对），过闸门 G1 需求评审；**Design** 产出 design.md（架构/数据模型/API/决策 DD，回答用什么实现），过闸门 G2 设计评审；**Task** 产出 tasks.md（可勾选任务清单 + 每任务验证，回答分几步/每步验什么），过闸门 G3 任务可执行已排期；之后实现、验证、变更回灌规格。贯穿全程三条铁律：**单一基线**（requirement 是权威源，design/task 的变更若触及需求必须回灌 requirement，不允许下游私自圆场）；**可追溯**（需求编号 → 设计条目 → 任务 → 验收/测试全链路双向可追溯，编号体系 FR/BR/US/DD/TC/AC）；**闸门不放水**（每阶段产物过评审闸门才进下一阶段，带阻断项不进入编码）。SDD 三阶段主要覆盖编码前，完整交付延伸为九步流水线：产品脑暴/功能清单 → 需求规格 SRS（G1）→ EARS 用户故事 + 验收标准（覆盖矩阵评审）→ 详细设计 + 开发 SPEC（G2）→ 任务拆解（G3）→ 编码实现（模板示例 + AI 填充、Plan 前置）→ 测试验证（左移 + 极端案例 + 验证三件套）→ 联调部署（静态排查 → 去 Mock → Docker → UAT）→ 复盘回灌（决议/勘误/遗留进基线、经验进标准），经验再沉淀回脑暴。AI Coding 不是「把提示词写好让 AI 多生成点代码」，而是一套有阶段、有闸门、有追溯、有回灌的工程体系——这些规范不是繁琐的形式，而是把 AI 的高产出转化为可信交付的「变压器」。

## 3. 需求阶段：用锚点、权威源与留白堵住编造空间

核心结论：AI 在需求阶段的幻觉不是「能力问题」而是「输入结构问题」，与其反复提示「不要编造」，不如用结构化锚点和权威源把编造的空间堵死。AI 会「善意地编造」业务口径，实际踩过的坑：**连接词之差结论相反**（北交所创新性组合条件 AI 按 AND 理解，监管原文实际是 OR，一个连接词让判定引擎输出完全相反）；**自造公式**（为符合性评分自造加权公式，业务真实需要的是二元达标判定——达标即满分否则 0 分）；**分支混淆**（混淆某板块标准一的 A/B 分支条件）；**术语混用**（「业务板块」与「上市板块」指向不同层级）。五条最佳实践：**结构化输入约束理解**——不把原始 PDF 丢给 AI 自由发挥，先抽离成结构化表格（上市标准矩阵：板块→标准套→指标三层结构）作为理解锚点，56 个财务要素、27 个上行要素全部进受控要素表；**要素级权威源 + 强制出处**——唯一权威附录，每个要素强制携带源材料原文、条件组、指标编码、阈值、出处页码，并声明生效顺序（正文与附录冲突以附录为准）；**留白纪律**——未获签认的参数（性能指标、并发规模、RPO/RTO）一律留白标注「待技术签认」，明令禁止 AI 臆造填充，**宁可文档有遗漏，也不可出现文档有假**（遗漏可以后补，有假会带问题流入生产）；**上游歧义回提不在下游消化**——发现 SRS 歧义走「确认→勘误→升基线」流程，不在详设、代码里擅自解释圆场，衍生物私自消化歧义是一致性腐化最常见的起点；**AI 补全需人工裁剪**——让 AI 模拟用户审查 PRD 补全场景遗漏时它会「过度补全」（给 MVP 阶段补全完整的版本化管理），AI 找遗漏很强，但取舍必须人来决策。需求细化用 EARS（Easy Approach to Requirements Syntax）五种句式生成用户故事：普遍型「系统应〔动作〕」、事件驱动「当〔触发〕时，系统应〔动作〕」、异常型「如果〔异常条件〕，则系统应〔处理〕」、状态驱动「在〔状态〕下，系统应〔动作〕」、可选型「当〔功能可用〕时，系统应〔动作〕」。生成 120 条后执行「产出即校准」：脚本清点条目数、编号连续性、模块分布并与汇总表交叉核对，**发现旧统计表少计了 5 条**（115→120），当轮勘误并在修订记录注明来源——人工目测「差不多 115 条」会放过偏差，机器清点不靠目测。团队原话值得铭记：「PRD 里一个字的描写有差异，都会直接导致后面的结果偏差被放大。」AI 时代需求文档的重要性不是下降而是上升——它现在是机器直接消费的「源代码的源代码」。

## 4. 设计阶段：跨文档一致性是最大的系统性风险

核心结论：设计阶段的交付物是一张网而非一条线，AI 单点修改能力极强，但不会自动知道「还有哪些地方引用了旧口径」。SRS 改一个评分规则，用户故事、详细设计、DDL、权限种子数据、API 定义、前端页面、测试用例、原型 mock 数据全要联动——「评分二元化」一次业务决议，仅详细设计一份文档就有**约 25 处**引用需要回灌；靠记忆或「顺手改掉」几乎必然遗漏，且遗漏是静默的，直到联调或上线才暴露。受控变更回灌的流程：全库检索（Grep）定位所有受影响落点形成清单 → 先改源头（SRS 升版 V1.5 + 用户故事）→ 再改衍生物（详设→DDL 种子→权限→API→前端→测试映射）→ 改原型（评分逻辑与 mock 同源修改）→ 跨角色×跨状态浏览器实测加控制台零报错 → diff 自证（改动仅限决议项、保留旧版）→ 更新项目记忆、登记遗留项（如 tie-break 待确认）。配套纪律：单一基线（所有衍生物声明自己的基线版本「本文档基于 SRS V1.5」）、先源头后衍生（绝不反过来在下游顺手改）、全库定位（不凭记忆）、diff 自证（越界一目了然）；版本治理细节是文档内版本号与文件名解耦（文件名标 -V1.4.md 但内含 V1.5，历史版本独立留存），版本演进连续可查。两个实用做法：**「执行用详设、归档含概设」双轨文档**——AI 一次生成 12 章大文档会截断，且写到后半部分时前文的编号约定、口径定义开始漂移（长上下文衰减），对策是分章生成追加、每章生成前先通读全部上游，给 AI 执行用的详设和给人审计用的含概设版本分开维护；**SPEC 以真实源码为准**——AI 编写开发规范依据的往往是 README 或历史印象，而脚手架实际版本、依赖清单、包名约定可能早已变化，项目通过代码仓库 API 直接抓脚手架配置、依赖清单、目录树、关键类源码逐条比对 SPEC 声明，校验结论分级标注（一致/已修正偏差并注明采集日期与来源路径），据此修正包名、FeignClient 命名、依赖清单等多处偏差，还发现文档从未覆盖的真实依赖（Lombok、knife4j、flowable 等）——**规范的生命力在于它描述的是「真实」而不是「应该」**。角色化联合评审不能省：不同阶段配不同评审团，提示词里显式赋予角色和评审标准，产出是「问题清单（严重度/角色/位置，分阻断/重要）+ 覆盖矩阵」而不是一句「看起来不错」——PRD 联合评审（产品/架构/高管/财务/开发五角色）拦下 7 阻断 + 16 重要后升 V1.2；EARS 故事评审（业务/需求分析/架构/测试/安全）产出覆盖矩阵与问题清单 F1~F4 回灌 SRS 勘误；业务联合评审定下评分二元化回灌全链；统一方案复核用**只读子代理独立复核**——让另一个只有读权限的 AI 会话做独立复核，与主作业会话形成**写审分离**，二代 SRS 升版时正是子代理发现一处高严重度规则遗漏（否决优先条件缺失会导致判定结果错误落位），当轮修复；子代理天然不会越界改文件，复核结论更客观。评审还有诚实性纪律：**区分「文档核验」与「系统测试」**，只读一致性核对不能表述为「已通过测试」，未执行的验证层级必须显式标注——AI 倾向于给积极结论，验证的诚实性要靠流程强制不能靠自觉。设计阶段的价值不在「AI 写得快」而在「变更可证明完整」：AI 让「改」变得极其便宜，于是「改哪里、按什么顺序改、改到什么边界」就成了新的稀缺能力。

## 5. 任务阶段：为 AI 写的施工组织设计

任务阶段是 SDD 从文档走向代码的关键转换层。设计文档写得完备，直接让 AI「照着实现」往往出问题：不知道先做哪个、每个改动的影响边界在哪、做完怎么算验证通过——要么一次改太多引入冲突，要么「报告成功」但实际没跑验证。任务拆解四要素：每个任务必带**关联需求**（FR/BR/US/AC）、**关联设计**（章节/DD 决策）、**影响文件**（改动边界）、**验证方式**（完成定义）；粒度上一个任务等于一个可独立提交、可独立验证的最小工作单元，过大必拆过小合并；依赖显式化（blockedBy 标顺序、能并行的标注可并行）；可勾选（checkbox，状态 pending→in_progress→completed，未验证通过不得标完成）。每个任务必带验证方式是关键：任务完成的定义等于代码写完**且**验证通过，验证分三层按任务类型选用——静态（lint/typecheck/build/语法校验，所有代码任务）、单元/接口（单测、接口用例、算例回归，逻辑/算法/API）、端到端（浏览器实测 + 控制台零报错、跨角色×跨状态走查，前端/页面）。还有专门为「AI 作为执行者」设计的风险对策表：单会话上下文过长导致遗忘约定——**步骤间以设计文档为唯一记忆源，不依赖会话上下文**；数据库迁移脚本冲突——单写者约定，迁移脚本只由当前步骤生成；工具链缺失导致静默跳过测试——即停不绕过，缺什么装什么；实现与设计冲突——**先改设计文档再改代码，不允许改代码绕过设计**。最后一条是整个 Spec-Driven 的灵魂：设计文档是唯一契约源，代码与文档冲突时解决方向永远是「文档先行升版」而不是「代码悄悄跑偏」。没有任务层的约束，AI 编码就是「随机执行」；有了任务层，才是「计划实施」。

## 6. 编码阶段：给 AI 修护栏而不是放开跑

AI 编码失控的根源不是模型能力，而是缺乏「变更前置约束」。典型事故：**AI 修改代码时误删了核心功能页签**——单看是低级错误，揭示的却是结构性问题：AI 的修改范围感知基于上下文，而上下文是有损的，改动越大、文件越多「顺带破坏」概率越高，且这类破坏往往不报错，只在运行时表现为「某个入口不见了」。从此立规：**AI 改代码前必须先产出 Plan MD**——改哪些文件、每个文件改什么、不改什么——人工审核变更边界后才执行，越界就驳回收窄范围；这相当于把「变更边界受控」从文档阶段延伸到代码阶段，成本极低（多一次确认）、收益极高（误删类事故归零）。第二类难点是规范、模板、生成代码的三方冲突：AI 引入的 CSS 写法违反规范（如 npm 引入 CSS 包）、旧模板遗留写法与规则文件互相矛盾、枚举拼写歧义（MET/MEET）、死代码、文档声明与实现不一致（文档写分页对象 PageResult、代码返回 List+Total）。对策是 **「示例代码模板拷贝 + AI 填充」**：工程骨架、依赖版本、目录结构、构建配置全部来自验证过的模板壳，AI 的自由度限制在业务实现层，多规范冲突大幅收敛；前端约定单一 UI 出口（禁用其他组件库直接引入）、单一 HTTP 出口，后端约定分层单向依赖、防腐层、错误码分段，约束写进 rules 文件，再加 AI 按规范自查重生成。对隐蔽问题团队有真实心态记录：「这种问题很隐蔽的……关关难过关关过。」AI 生成代码的审查重点不是逐行读，而是**验证功能行为 + 核心逻辑实现 + 静态排查一致性**（枚举、命名、分页、接口契约）。两条务实判断：**允许 AI 前后端联动修改**——只约束单端会导致接口不匹配的循环修改（前端改完对不上后端、后端改完又对不上前端），让 AI 在同一次变更里协调两端接口契约反而更稳；**承认能力边界**——指标大屏（重展示、重视觉还原）形成明确共识：展示型模块不要让 AI 端到端负责视觉还原，先人工锁定视觉样式定型、AI 只负责数据接口联调，功能性模块优先、展示型模块后置精调成为模块排序默认策略。FDE 原话：「它肯定不是万能的，一定要找到合适的边界……不到这个力度你是还原不出来的。」三道护栏的共同逻辑：把 AI 的自由度约束在它擅长且可验证的范围内，剩下的交给人和模板。

## 7. 测试阶段：左移、极端案例与诚实报告

AI 时代测试用例的生成成本趋近于零，测试的价值重心从「写用例」转移到「设计可测性」和「保证验证诚实」。**测试左移**：用户故事和验收标准确定后测试用例立即生成、与代码生成并行推进，测试人员提前介入验收标准评审；一个细节是用户故事有多个版本时选**逻辑拆分更清晰的版本**作为用例生成基础——选型标准不是「写得好」而是「可测试」。**极端案例法**：业务规则测试选「最复杂 + 最简单」双向覆盖，本项目选北交所某标准（4 层 AND/OR 嵌套条件组）作最复杂案例配最简单案例，两端覆盖能暴露大部分边界逻辑问题；测试数据请行业专家评审——AI 可以生成用例，但用例的业务正确性要靠领域专家背书；实践中发现 AI 初版用例偏重失败场景、缺成功场景的正向验证，用 AI 结合 PRD 补全，生成后必须做一次「正反覆盖」审查并进 checklist。**为 AI 测试而设计的基础设施**是很少被讨论但极其重要的一层——AI 跑自动化测试最大的干扰不是测试逻辑而是环境，三件沉淀：人工预验证环境（AI 测试前人工先在专用电脑把前后端完整跑通一遍，避免 AI 陷入环境调试死循环，团队原话「环境是个比较大的问题，它一测发现环境有问题就去处理环境问题，正式任务完不成」）、Mock SSO 免登（开发期模拟两个角色账号，端到端测试不依赖真实集团鉴权）、浏览器插件图形化测试（插件读页面结构按用例自动输入点击验证，替代脆弱的手工点击）——**环境确定性是 AI 测试的前置条件，不是 AI 的责任**。前端与端到端验证统一走**验证三件套**：浏览器实测（全路由 × 跨角色 × 跨状态）、JS 语法/结构校验、控制台零报错；截图能力不可用时降级为结构化 DOM 校验（断言关键节点的存在、文本、类名），调试页面改动给 URL 加查询参数强制重载避免沿用上一轮 state 误判。最终输出逐条对照验收标准的结论表并如实分层：通过（附验证证据）、有缺口（说明具体问题）、未覆盖（说明原因），诚实标注已知缺口（真实集团 SSO 免登在测试环境不可测、个别性能/并发参数待技术签认）——**报告的可信度恰恰来自它承认了什么没测**。问题追踪 SOP：每个问题必须附截图 + Request ID 发到协作群作为后台排查的唯一凭证，在「AI 改得快、人看得不过来」的节奏下，可复现的凭证链就是排查效率的生命线。

## 8. 联调与部署：把不确定性前移消化

联调阶段是「文档一致性问题」的集中暴露阶段：即便详细设计经过评审，正式联调前的静态排查仍发现 **13 个接口**存在字段缺失/折叠问题，还有 message 字段命名在多个调用点不一致的风险——**评审通过不等于文档-代码完全一致，联调前必须再做一次机器化的一致性排查**。联调路径：开发期 Mock SSO 多角色（权限逻辑可在无真实鉴权环境下开发测试，真实 SSO 对接上线前由主项目统筹）→ 联调前全接口静态排查（**每提前发现一个问题，联调会上就少一次现场调试**）→ 去 Mock 开关一键切真实接口（标准库预置三个财年的初始化数据，保证切真后有数可查）→ Docker 镜像 + docker-compose 一键启动全套服务（nginx/app/mysql/redis）→ UAT 环境域名切换。环境配置进 dev 配置文件加 rules 约束，长期方案是镜像分发统一环境。分支纪律：禁推主干、功能拉独立分支；踩过一次坑——某分支前端代码推送失败为空，差点在空目录上联调，**分支完整性检查应进部署 checklist**。这个阶段的效率取决于前面阶段沉淀的一致性质量——它是整条交付链的「验收关口」而非独立环节。

## 9. 组织协作：AI Coding 是团队工程不是个人技巧

AI Coding 落地失败的组织原因远多于技术原因。五项组织级实践：**文档统一入 Git**——禁止散落个人电脑，所有 AI 可消费的基线（SRS、SPEC、设计文档）必须版本化、可检索、可 diff，这不仅是管理要求更是 AI 作业的技术前提（AI 需要读到「唯一真源」而非各人本地的私有副本），代码修改必须同步更新文档；**需求宣讲全员参与**——不再是产品经理对开发单向传递，AI 时代每个角色都要能把自己的专业口径写进基线；**多人交叉审 AI 产物**——质量控制前置到文档层；**AI 初审 + 人工复核分层**——应对「AI 生成速度大于人工审查速度」这一所有团队都会遇到的核心矛盾，让只读子代理做形式审查（一致性、覆盖度、编号完整性），人只做判断性审查（业务口径、取舍决策），**人的审查带宽是稀缺资源，要花在刀刃上**；**首批骨干→操作标准→第二批推广**——踩坑经验沉淀为 Plan MD 模板、质量门清单、问题追踪 SOP，通过分享会培养第二批成员，经验不沉淀为标准，AI Coding 就永远是「高手的个人技巧」无法变成组织能力。成本结构需要重新认识：显性成本从人力工时大头变为 Token 消耗（单次深度调用可观，但对比人力仍有数量级优势）；隐性成本从沟通/返工变为**人花时间审文档**（新的最大隐性成本）；2 人小团队完成以往多人工作量，但**无法靠加人并行提速**——阶段间严格依赖，瓶颈在决策带宽不在产出带宽。这决定了团队人员画像：需要的是有判断力的资深角色（能审、能拍板），而不是更多的执行者；前期文档规范投入增加、后期编码时间大幅缩短，成本曲线整体前移。技术决定单点效率，组织决定规模上限。

## 10. 度量体系与适用边界

没有度量就没有改进，每个项目收尾用同一套指标才能横向比较。五维度量框架（本项目实测）：**规格质量**（评审阻断项数/需求返工次数/歧义勘误次数——PRD 评审 7 阻断 + 16 重要、SRS 五轮升版）；**可追溯性**（FR→AC 覆盖率/design→需求回链完整率——120 条故事全编号可追溯）；**一致性**（跨文档版本引用不一致数/统计漂移次数——勘误统计少计 5 条、1 处版本引用漂移待勘误）；**实现验证**（一次通过验证的任务占比/控制台报错数/「文档核验 vs 实现测试」混淆次数——实现率 88.3%、完成度 97.4%）；**协作纪律**（越界改动次数/并发写冲突次数/待签认参数臆造次数——检测到 1 次 HTML 并发写冲突并保留他方变更、参数留白未臆造）。闭环是项目收尾按统一指标度量、横向比较历史项目、新踩的坑补进反模式清单、有效的提示词与闸门补进模板库、更新团队记忆供下一个项目复用。关键洞察：**88.3% 的实现率不是终点指标而是过程健康度的体现**，真正值得盯的是「评审阻断项在编码前的拦截率」和「联调前静态排查的缺陷数」——这些前置指标才决定下游的返工成本。适用边界也要诚实划定：中大型功能/系统、金融/合规/内部管理系统、多人/多 Agent 协作强适用（多轮迭代、可追溯硬要求、需要单一基线与变更边界控制）；一次性脚本、纯探索性 demo、极小改动不适用（直接对话式编码即可，需求本身在流动时过早固化规格反而束缚，重规格是负担）。AI 能力边界的务实结论：展示型模块慎用 AI 全流程；AI 会过度补全需求需人工裁剪；存量项目先让 AI 读旧代码生成基准理解再迭代，避免不了解存量就「想当然」；严格前后依赖的任务无法加人并行。

## 11. 结论：工程纪律的胜利

五点体会：**AI 改变的是瓶颈位置而不是消灭瓶颈**——从「写得慢」到「对得齐」再到「审得过来」，围绕新瓶颈重建流程（单一基线、编号追溯、Plan 前置、写审分离）收益远大于单纯提升生成速度；**人的角色从「执笔者」变成「基线守护者」**——全程人没有逐字写过一份文档、一行行敲过业务代码，但每个关键决策（评分二元化、矩阵方案、模板壳策略、大屏边界）都由人拍板、每次变更边界都由人声明，AI 负责产出与自检、人负责决策与守门；**把纪律写进流程而不是指望自觉**——产出即校准、Plan 前置审核、哈希写保护、验证诚实性、留白不臆造、质量门即停不绕过，单看都是小事，但没有它们 AI 的高产出会同时放大正确和错误，88.3% 的实现率是纪律的产物不是运气的产物；**基础设施要为 AI 而设计**——人工预验证环境、Mock SSO、浏览器插件测试、结构化输入锚点、模板代码壳在传统模式下未必划算，在 AI 模式下是决定成败的前置条件，AI 的作业质量上限由它所处环境的确定性决定；**组织能力建设与工具落地同等重要**。给准备落地团队的三条起步建议：选对场景（从规则密集、可追溯要求高的中大型功能切入，不要拿一次性脚本或探索 demo 试水——后者会得出「规格太重」的错误结论）；建最小闭环（先跑通需求→设计→任务三产物 + 三闸门的最小链，用度量指标验证效果，不追求一上来全流程完美）；沉淀再推广（首批骨干把踩坑经验固化为操作标准再分享会规模化，避免「人走方法走」）。可复用资产清单：SDD 流程与标准规范、需求工程作业手册、三产物模板骨架、6 类提示词模板库、13 项反模式清单、5 维复盘度量框架、Plan MD 模板。反模式清单来自真实踩坑，典型如：原型/实现细节写进需求（硬编码日期、「第 2 条」）导致需求绑死实现；口径缺口（时间窗/精度/单位/空值/历史覆盖）导致系统性误判，需求应专设「计算口径」节；超长 design 单次 Write 内容截断，应分章追加；差异在下游静默消化导致需求与设计分叉，应备案加勘误升版；截图工具不可用就跳过 UI 验证，应结构化 DOM 校验兜底；多 Agent 并行互相覆盖，应写前检测哈希/mtime 不覆盖他方改动；待签认参数臆造默认值会带病上线，应留白加标注负责人。项目还在路上——SRS 正式评审签署、性能参数签认、两代产物基线关系确认都在遗留项清单里，但它已完整验证了一件事：**AI Coding 的企业级落地是一场工程纪律的胜利，而非模型能力的炫技**。契约源、编号可追溯、质量门自动化、验证报告诚实——这些传统软件工程的「老规矩」在 AI 时代不是过时了，而是从「最佳实践」升级成了「生存必需」；生成能力每半年迭代一次，工程规范一旦建成却是长期资产。
