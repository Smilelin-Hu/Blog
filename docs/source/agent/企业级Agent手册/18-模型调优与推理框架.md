# 模型调优与推理框架：决策上限与单位成本

模型是 Agent 理解任务、选择工具、组织多步行动并根据反馈调整策略的决策核心。在 Harness 与执行环境满足运行要求的前提下，**模型能力主要决定 Agent 的决策上限**，并显著影响任务效果与单位成功任务成本。但模型优化不是所有问题的统一答案：工具协议含混、上下文缺失、权限失效或外部服务异常属于 Harness 或执行环境问题，不能靠训练补偿。本文前半整理模型侧的归因、三类训练方法与验收上线，后半整理承接每次调用的推理框架。核心判断：**训练决定模型能达到什么水平，推理决定这份能力每用一次要花多少钱**。

## 1. 先归因：模型、Harness 与执行环境

端到端能力由三层共同形成：模型在给定信息与动作空间内理解任务、作出决策、生成动作并解释反馈；Harness 负责上下文组织、工具协议、任务状态、调用路由、反馈传递与重试停止等运行支撑；执行环境（业务系统、数据服务、算力、外部服务）实际承载动作并返回结果。以失败恢复为例，模型判断错误是否可恢复属决策能力，Harness 决定是否重试停止或请求授权属运行控制，环境因服务不可用无法完成动作属环境故障——**三者可能表现为相似的失败现象，但优化手段不同**。

归因原则：先看模型作出错误决策时是否已获得准确充分的信息、清晰可用的动作接口，环境是否正常。信息缺失、协议含混、状态不可见或反馈被截断则优先修 Harness；工具不可用、资源不足或外部服务异常则修环境；**只有信息、动作空间与反馈均明确稳定时，同类决策错误仍跨任务变体反复出现，才有充分理由列为模型优化目标**。验证方式对应三层：绕过模型直接调工具仍复现故障归因环境，固定模型与环境修正上下文协议后问题明显减少归因 Harness，固定 Harness 与环境重复测试或换模型后错误稳定出现或显著改善归因模型。排查顺序是先排除能独立复现的环境故障，再查 Harness，最后判断模型缺口——**避免用模型训练弥补本应由系统工程解决的问题**。数据分析 Agent 反复生成错误 SQL 即例：没获得字段含义则改善字典检索，工具对时间范围有歧义则修协议，查询服务不可用则处理环境，字段口径与反馈都清楚而模型仍混淆去重关联逻辑才评估模型优化。边界不清时在环境稳定前提下组织四组对照（原/候选模型 × 原/候选 Harness），在一致任务集与预算下比较各自及交互收益；候选模型若需专门提示或协议适配，应把适配纳入配置记录，避免把组合变化全归因于模型。模型优化也可由成本驱动：高频任务已能靠长提示、反复纠错或多模型复核完成但开销超预算，且任务分布稳定、有效行为可学习时，可评估用 SFT 或蒸馏减少开销，同时保留权限控制、执行约束与独立验证。

## 2. 能力要求、优化目标与方法选择

归因到模型后，在「接收观察—作出决策—获得反馈—调整决策」循环中把问题归纳为四类决策能力：**任务理解与约束识别**（把自然语言转为可执行目标，识别完成标准、前置条件与允许操作范围，条件不明时提出澄清也是有效推进）、**工具使用与反馈理解**（选对工具、生成合法动作、判断返回能否支持下一步——**调用成功仅说明接口完成了请求**，还需识别结果是否完整、口径是否一致）、**多步决策与状态利用**（理解已完成工作、未解决问题与可用信息并调整行动顺序，涉及用户协作时确认用户是否完成必要操作；τ²-Bench 把用户与 Agent 都能操作共享环境的情形纳入评估，用消融区分推理错误与沟通协调错误）、**失败恢复与合理终止**（报错后判断修正参数、补充信息、切换路径还是求助，满足完成条件后判断能否终止）。这些是模型的决策表现而非 Agent 完整运行能力——工具实际执行、状态持久化、权限校验与动作放行仍由 Harness 与环境承担。

优化动因两类：效果驱动（质量稳定性不足）、效率驱动（任务已能完成但依赖过长提示、反复重试、多模型复核或高推理成本）。两类都从三维评估：**质量**（除最终答案外检查关键动作是否正确、结果是否满足业务口径、约束是否遵守，局部指标可辅助定位但**最终验收仍应回到完整任务**）、**可靠性**（同任务多次运行，覆盖输入变化、长交互、工具异常与用户补充条件，平均成功率提高时仍需确认关键场景没有回退，权限边界被违反应单独报告）、**成本**（模型调用、工具执行、失败重试与人工介入的总投入，同时观察端到端时延及高分位）。成本口径用**单位成功任务成本 = 统计期内全部任务执行成本 ÷ 成功完成任务数，失败任务消耗的资源也计入分子**；比较时固定任务构成并同时报告成功率，**避免因放弃困难任务而形成表面上的成本下降**。效率驱动不意味着训练必然降本：SFT 只有在减少提示长度、降低重试复核或使更小模型胜任时才可能降低端到端成本，否则一次性投入可能抵消运行节省——**低频或变化快的任务轻量 Harness 调整可能更经济，高频且相对稳定的任务训练或蒸馏的单次节省才更可能形成累计收益**。指标之外须设安全护栏：模型识别约束并提出动作，但不能仅依赖模型自行遵守，Harness 负责调用侧权限校验、放行、重试上限、停止与独立验证，环境负责资源侧强制校验；训练前明确目标、基线、门槛、预算、约束与回归范围，训练后同口径复测，确认没有以可靠性或安全性换取局部指标改善。

方法按学习信号与目的选择：**有明确示范时选 SFT**（有效行为可稳定示范而模型执行不稳定，样本应含产生目标动作所需的上下文、工具反馈与任务变化）；**需要交互探索且环境能提供可靠反馈时选 Agentic RL**（存在多种执行路径、优劣需实际执行才能判断，前提是环境可运行、反馈与真实目标一致、探索成本可承担）；**教师已具备能力且目标是迁移压缩部署时选蒸馏**（用教师在目标任务分布上的输出或轨迹训练学生，学生实际执行可能进入教师未覆盖的状态，仍需检验偏差累积与失败恢复）。三类不互斥：轨迹蒸馏通常通过教师数据上的 SFT 实现，SFT 后也可继续 RL；**是否组合与如何排序由基础模型能力、信号质量、目标 Harness 与预算共同决定，而不是固定流水线**。训练阶段应尽可能覆盖生产中的上下文组织、工具协议与反馈方式，或验证训练与生产条件的差异可被可靠适配。

## 3. SFT：把已验证的行为变成稳定倾向

SFT 不是替代 Harness 或环境，也不是自动发现未知最优策略，而是**让经过验证的理解、决策与响应方式更容易在相似任务中被采用**。监督对象不只是最终答案，还包括过程中的关键决策：是否调用工具、选哪个、如何生成参数、如何解释反馈、何时澄清求助或终止；学习单位是「在当前可见信息与动作空间下应当生成什么响应或行动」，改变的是**模型的条件行为分布**。数据分析的例子：即使去重与新增口径已明确，模型仍可能先筛季度内订单再算首次付费时间导致老客户被计入新增，SFT 的目标不是记住某条查询语句，而是通过多样化示范稳定学会「先在全量有效付费记录上确定企业首次付费时间，再按目标季度统计」的执行方法。适用边界：除确认问题属于模型外，还要判断目标行为能否被可靠示范——**若路径优劣只能通过环境交互判断，或同一状态下缺少可信目标动作，不应把不确定结果直接作为监督标签**，应先完善验证条件或考虑 RL。监督目标从已识别的能力缺口出发而非笼统「提升能力」：工具调用失败可拆为时机、选择、参数语义、反馈理解错误，多轮失败可定位为约束遗失、状态利用不足、终止判断错误。

**轨迹本身不等于监督目标**：一条轨迹含系统指令、用户请求、工具定义、模型动作、环境反馈与后续修正，只有经过验证值得复用的模型行为才应参与监督；样本构造本质是在保持决策因果关系的前提下把完整轨迹转化为若干「可见上下文—目标行为」样本。**每个目标行为只能依赖该决策时刻已可见的信息**：某次调用尚未返回时目标动作不能用其结果，用户后续轮次补充的条件不能提前进入早期决策输入，否则离线信息条件优于真实运行条件，模型即使拟合了监督数据上线也难以复现。系统指令、用户请求、工具定义作为输入上下文通常不作生成目标，工具结果与环境观察保留在输入中通常不计损失，经验证的调用澄清修正与最终答复才计算监督损失。**任务最终成功不意味着每一步都值得模仿**：成功轨迹可能含多余查询或错误后偶然正确的步骤，失败轨迹中也可能含有价值的恢复过程；纠错场景可把错误动作保留在历史上下文中使模型理解为何需要修正，但**屏蔽该错误动作对应的训练损失，只监督经过验证的后续行为**。**角色级掩码与质量级掩码解决不同问题**：仅对模型生成内容计损失可排除用户消息与工具返回，但错误调用本身也可能由模型生成，仍需更细粒度的行为标记，实施时应抽查实际参与损失计算的内容。样本配比同时反映生产分布与已确认缺口，**原本可直接完成的简单任务也应保留样本，防止训练后普遍增加工具调用或交互轮次**；**重复复制少量同质示范只能提高这些示范的权重，不能替代对任务变化、状态分支与异常条件的真实覆盖**。训练与推理须用兼容的对话模板、工具格式与结束标记，长样本检查截断位置避免保留目标动作却丢失其依赖的约束——否则损失正常下降但生成的动作无法被运行时解析。全量微调与 LoRA 各有取舍，**二者都不能替代数据质量控制，也不能天然避免能力回退**。

验收：**训练损失下降只说明模型更容易生成监督样本中的目标内容，不能证明它能在真实交互中完成任务**。应让候选模型在固定 Harness、工具接口与预算下自主运行，由环境返回实际反馈，观察早期决策如何影响后续执行；**若每一步都提供标准历史、只检查能否续写下一条标准响应，就无法暴露错误累积与恢复失败**。测试集按任务族、模板或来源分组，避免同一任务的近似改写同时进入训练与测试集；改变季度范围、字段表达与数据分布，加入历史客户再次付费等条件，覆盖工具描述变化、用户中途改要求与可恢复执行错误，验证学的是执行方法而不是固定表达。比较版本时保持 Harness、任务条件与预算一致，同时修改提示词协议或上下文策略则作为组合变更单独记录，有采样随机性的任务重复运行并报告波动范围。

## 4. Agentic RL：以环境反馈优化决策策略

Agentic RL 用模型在环境中执行任务产生的轨迹作为学习样本，依结果、过程状态或验证器反馈更新策略，优化的不是某条固定回答而是**连续决策中选择动作的倾向**。与 SFT 的区别在信号来源：SFT 从固定示范学习、要求目标行为能被可靠示范，RL 让策略产生轨迹再用结果反馈优化期望收益、允许多种可行路径但要求**路径优劣能被稳定评价**。退款任务中模型可能正确查询订单却跳过政策核验，逐步标注唯一正确动作并不容易，但任务是否完成、金额是否正确、政策是否满足、是否越权通常可验证，这就具备进入 RL 的基本条件。**RL 不是对 Harness 或环境缺陷的补偿**：上下文没进模型、工具定义有歧义、权限可被绕过或环境无法稳定复现时，训练只会把错误的观察与反馈固化进策略。准入须同时回答「值不值得用 RL」与「系统是否具备训练条件」，六个维度：失败确实来自模型的动作选择反馈利用或恢复策略（否则先修上下文协议权限环境）、有效路径不唯一难以逐点标注（可稳定示范则优先 SFT）、结果或关键中间状态可由规则测试或可靠评审稳定判断（否则先建验证器）、环境可重复执行状态可重置探索可隔离过程可追踪（否则先建 Sandbox 或模拟器）、已具备基本指令遵循与工具调用能力能产生一定比例有效轨迹（否则先用提示 SFT 或更强基座建立起点）、预期改善能覆盖 Rollout 与环境维护成本。**「结果可验证」比「过程能被完整标注」更重要**：若退款验证器只检查是否生成退款记录而不检查政策金额权限，模型就可能学会更快地创建不合规退款。

任务建模为部分可观测序列决策：外部系统存在模型无法直接观察的真实状态 \(s_t\)，模型只能看到局部观察 \(o_t\)，因此依据交互历史 \(h_t=(o_0,a_0,\dots,o_t)\) 选择动作，策略写作 \(\pi_\theta(a_t|h_t)\)，目标是最大化期望累计回报 \(J(\theta)=\mathbb{E}[\sum_t \gamma^t r_t]\)。四要素须明确：观察（每步能看到什么，**必须与生产一致，避免训练时获得线上不可用的信息**）、动作（回复、调用工具、写入记忆、请求澄清、等待或结束）、转移（调用可能成功失败超时或返回不完整，用户与外部系统也可能改变后续状态）、任务结束（区分终止与截断：任务成功、业务失败或预算耗尽被明确建模为失败状态时记为终止，仅因外部采样时限或基础设施中断等与目标无关的原因停止才属截断；**只有截断后仍能获得有效后继观察、且价值函数能基于后继历史估计后续回报时才适合价值 bootstrap，不能把所有未完成轨迹一律当失败**）。训练环境五要求：可执行、可重置（每次 rollout 恢复明确初始状态避免样本互相污染）、可复现（记录任务、种子、工具版本、Prompt 与环境快照）、可审计（完整保存观察动作返回时延成本与终止原因）、可隔离（探索不得直接作用于真实生产数据或高风险系统）；**环境版本、工具协议或停止规则变化，模型面对的决策问题也随之变化，必须作为训练版本的一部分记录**。

奖励设计原则不是「让奖励更丰富」，而是**尽可能贴近真实任务目标，并减少模型利用评价漏洞获得高分的空间**。四类信号：结果奖励（与业务目标最接近，应作核心）、过程奖励（关键中间状态是否满足要求，可缓解终局稀疏但**不应强制模型复制唯一流程**）、成本信号（调用次数、Token、时延、重试与人工介入，**应在任务成功的前提下优化，不能诱导模型提前终止规避困难任务**）、约束信号（权限隐私格式与操作边界，**高风险约束不能只依赖负奖励，必须由 Harness 设置不可绕过的系统控制**）；组合形式 \(R(\tau)=w_1R_{task}+w_2R_{process}-\lambda C_{execution}-\mu P_{violation}\)，权重应通过离线回放、人工抽检与消融校准。验证器三类：规则验证器（结构校验、数据库状态、单元测试，稳定低成本）、模型验证器（评价开放式结果，需检查偏见、长度偏好与自洽性偏差）、人工反馈（校准复杂偏好、审查边界案例，适合构建高质量标尺集而非覆盖全部 rollout）。三类风险：奖励投机、代理目标偏移、评审器漂移；控制原则是**把训练奖励、独立评测指标与系统约束分开**——奖励提供学习信号，独立评测判断能力是否真实提升，系统控制保证任何模型版本都不能越过操作边界。

基本循环是任务采样 → 策略 Rollout → 轨迹存储 → Verifier 评分 → 回报与 Advantage → 策略更新 → 新版本，开发集失败分析与验证集评测回流到任务采样，候选冻结后走固定留出集一次性评测。一轮六步中任务采样应**避免简单任务占据主要训练预算**，策略更新用 PPO、组相对策略优化或其他策略梯度方法并以裁剪目标与 KL 正则抑制过大漂移。PPO 的 Rollout 通常由更新前的行为策略生成，用概率比率裁剪限制变化并通过价值函数估计优势，**属近似 on-policy，轨迹跨多个策略版本反复复用会增加离策略偏差**；组相对方法改变的主要是优势基线——同一任务生成多条轨迹用组内相对回报替代单独训练的价值模型，适合能并行采样且同任务存在明显回报差异的场景，**若组内结果几乎相同，优势信号趋近于零而多轨迹 Rollout 仍增加执行成本**。**算法不能弥补任务与奖励设计缺陷**：无论何种优势估计，都应先确认奖励有区分度、Rollout 覆盖有效路径、环境可重置，且收益能在独立任务集上复现。工程上执行系统与训练系统通常解耦，两侧通过标准化模型调用接口与轨迹协议连接，但**工具版本、Prompt、环境、验证器与策略版本必须共同登记**才能回放收益与定位退化。长程任务的困难不只是步骤更多，而是**反馈更晚、有效路径更少，且早期错误会改变后续状态**，四个入手点：课程式任务采样（从短轨迹强反馈开始逐步增加跨度）、只在能客观验证的阶段性状态提供过程反馈（**而不是为每一步自然语言推理打分**）、同任务多轨迹用相对结果识别更优路径、显式覆盖参数修正/工具切换/状态回滚/请求澄清/合理终止使恢复行为进入可探索分布。**轨迹分段本身不会自动改善信用分配**——只有分段同时对应可验证子目标、阶段奖励或价值估计时才可能缩短信号传播距离。RL 不要求把某条成功路径的每一步定义为唯一标准答案，而是用结果约束反馈提高产生合规成功路径的概率，**另一条路径若同样满足结果约束与成本目标也应被视为有效策略**；失败轨迹可用于错误分析或经验证后转为 SFT 恢复样本，但**将历史失败轨迹无限回放并不会自然产生有效的策略梯度**。

独立评测四步。**训练奖励上升只说明策略更擅长获得当前奖励，不能证明真实任务能力已提升**。一是冻结候选并建立可比基线，保持 Prompt、Harness、协议、预算与环境版本一致，避免把 Prompt 调整、权限放宽或环境简化的收益误判为策略能力提升。二是隔离评测数据与机制：开发集用于设计奖励可反复迭代，验证集用于选版本，**锁定留出集仅用于候选冻结后的发布验收**并按任务模板、业务实体、环境种子与工具版本与训练数据隔离；训练验证器与独立评测器尽量分离，高分轨迹人工抽检以排除评分漏洞与隐藏状态利用；**即使没有直接用留出集调参，长期依据同一留出集的通过结果选择版本也会产生间接过拟合**，需定期更新私有任务或轮换种子。三是四维报告端到端结果：质量（成功率，确认高分不是来自环境捷径或验证器漏洞）、可靠性（多次 Rollout 报告波动与置信区间）、成本（单位成功任务的 Token、调用次数、时延，而非只比单次调用成本）、安全（**既评价模型产生违规动作的频率，也单独验证 Harness 与环境能否可靠拦截**）。四是解释收益来源：通过消融分别移除过程奖励、成本信号、课程采样或特定验证器，观察端到端指标变化；**训练回报提高而独立成功率没有同步改善时**，优先检查奖励是否鼓励代理目标或捷径、验证器是否有系统性偏差、环境是否泄漏答案、训练与生产是否存在分布差异。由此构成 RL 落地的最终边界：**Agentic RL 既是模型优化问题，也是环境工程、反馈工程与评测工程的联合问题**。

## 5. 模型蒸馏：迁移任务能力，降低执行成本

目标不是让小模型「说得像」强模型，而是**把强模型在任务执行中表现出的有效决策迁移给目标模型**，使其以更低成本独立承担可界定可评测的工作，并在超出能力边界时主动交还教师。两个相互约束的问题：哪些能力可以稳定迁移（要求数据覆盖交互决策而不只是最终答案），迁移后是否真正降低每个成功任务的总成本（要求把失败、重试、工具调用与教师兜底一并核算）。设计从线上职责出发而非模型尺寸：**教师在某类任务上本身不稳定，蒸馏只会更高效地复制其错误；学生容量过小，增加示范数量也未必弥补表示与长程规划能力的不足**。先建「任务—职责—风险」矩阵，划分为学生独立执行、学生执行且教师校验、教师直接执行三类，任务边界至少含输入分布、允许工具、最大步数、成功判定与不可接受的失败类型；**高风险或不可逆操作即使学生离线成功率较高，也不宜仅凭平均分取消教师校验**。迁移范围两种：完整 Agent 行为迁移与技能级迁移（只承担工具路由、查询生成、参数抽取、结果核验等一个稳定环节）——后者更容易定义成功标准与故障边界，**更适合作为首次落地切入点**。AgentDistill 的实验表明蒸馏 Thought—Action—Observation 轨迹可让较小模型学习工具组合使用，训练损失覆盖教师的思考与动作 Token、**不把环境返回的 observation 作为预测目标**，但仅在固定协议有限步数特定任务集上验证，不能据此推断任意复杂 Agent 能力都能完整迁移。**先用候选学生完成小规模可教性测试，再决定数据规模与训练投入**。

教师信号沿四层递进：最终输出（结果级模仿，成本低适合黑盒教师，难学工具时机与失败恢复）、标签与理由（更密集但理由可能事后合理化）、结构化动作（可直接评测合法性，需稳定协议与校验器）、多轮轨迹（最接近真实执行分布但昂贵且错误沿多轮累积）；另有概率信号（保留教师不确定性，依赖概率接口与词表对齐）。按教师可见信息分硬目标与软目标：硬目标只需教师生成文本或动作序列，适用闭源 API、跨架构与不同词表，但丢失候选 Token 间的相对偏好；软目标用概率分布告诉学生「哪些替代行为也合理」，通常要求访问教师概率接口，师生 tokenizer 不一致时需额外对齐——**是否用概率蒸馏不是单纯的算法偏好，而是由教师访问方式与训练基础设施共同决定的工程约束**。教师示范进训练集前必须验证（最终答案用标准答案或裁判器、工具动作用 schema 权限与执行结果、多轮轨迹同时检查成功合法效率与安全），**过滤错误轨迹并保留失败原因，比单纯扩大未经验证的教师样本更重要**。三条路线的差别在训练状态来源与监督形态：Off-policy SFT 用教师或历史轨迹作状态、监督教师文本动作，稳定易实现适合冷启动但学生状态分布偏移容易较早进入平台期；On-policy RL 用当前学生轨迹、监督环境结果奖励，可直接优化任务成功但奖励稀疏信用分配困难；On-policy Distillation（OPD）用当前学生轨迹、监督教师逐 Token 或逐动作评价，**使训练集中处理学生「真正会犯的错」，而不是重复学习教师已熟练覆盖的状态**，但依赖教师打分接口、可能压低探索并继承教师偏差。OPD 目标是最小化学生到教师的反向 KL \(\mathcal{L}_{OPD}=\mathbb{E}_{\tau\sim\pi_\theta}[\sum_t D_{KL}(\pi_\theta(\cdot|s_t)\,\|\,\pi_T(\cdot|s_t))]\)，对学生已采样 Token 可用 \(\hat d_t=\log\pi_\theta(a_t|s_t)-\log\pi_T(a_t|s_t)\) 估计局部差异（**该量是目标函数的蒙特卡洛估计项，不等同于完整训练梯度**）；教师可在 teacher forcing 下对学生已生成序列打分只返回归一化 log-prob，**只有文本生成接口而没有 log-prob 能力时无法直接采用**。学生容量受限时反向 KL 常表现「模式寻求」（mode-seeking），有助于收敛到一条连贯的高概率决策路径、减少在互斥方案间平均化，但 **「教师高概率」不等同于「任务正确」**，仍可能复制教师偏差、压低必要探索，必须与任务成功验证和异常覆盖联合使用。

能力补强的重点是**定位学生相对于有效路径的首个关键偏离**——多轮失败通常不是最后一步突然发生，而是早期偏差逐步放大。四类缺口对应不同数据：知识缺口（目标或约束理解错误，增加解释与对照样本）、决策缺口（工具选择或步骤顺序错误，增加相邻候选动作及选择依据）、执行缺口（参数格式权限或协议不合法，加入结构化校验）、恢复缺口（面对空结果超时冲突或报错时继续重复原动作，显式提供「发现异常—诊断原因—更换路径—重新验证」的纠错轨迹）。补强闭环：按首错位置与失败原因聚类 → 补充困难任务反例与局部纠错示范 → 让新学生自主执行 → 同时检查成功率、恢复率、调用步数与新引入的失败模式；**只有学生在独立保留集与分布外压力集上都改善，才应把专项补强视为有效，而不是对训练集的记忆**。收益核算须在同一任务集、工具环境、成功判定与流量条件下比较教师、学生与原有线上模型三类系统，记录成功率、一次通过率、行动步数、调用与重试次数、教师兜底率、端到端高分位时延与全链路成本——**只比较 Token 单价会忽略学生因规划能力下降而产生的额外步骤与失败重试**。单位成功任务成本按所有任务实际总成本除以成功任务数：

\[C_{success}=\frac{\sum_{i=1}^{N}\sum_{a=1}^{A_i}(C_{student}+C_{teacher}+C_{verifier}+C_{tool}+C_{runtime})_{i,a}}{\sum_{i=1}^{N}\mathbf{1}(task_i\ success)}\]

其中 \(A_i\) 是任务 \(i\) 实际发生的全部尝试，**重试成本已通过对各次尝试求和计入，无需另设可能重复计费的 \(C_{retry}\)**；教师兜底、验证器、工具与编排运行时都按真实调用路径计入。只有当单任务期望成本已完整包含这些条件成本时才能简写为 \(C_{success}=\mathbb{E}[C_{task}]/P(success)\)，因此「单次推理成本 × 平均重试次数 ÷ 成功率」只能作极简近似，**在多模型多工具 Agent 中通常不成立**。学生在低风险高频任务达标而在长程或高风险任务不稳定时可采用路由或级联——学生先执行，置信度或校验不足时调用教师；**收益可以来自「减少教师调用」，而不一定要求一次训练后完全替代教师**。最终 ROI 还要加入一次性投入：设固定投入为 \(F\)，质量与业务价值近似不变时盈亏平衡任务量 \(N^*=F/(\bar C_{old}-\bar C_{new})\)；若成功率不同，应先把成功价值与失败损失纳入单任务净收益 \(g=pV-(1-p)L-\bar C\)，则 \(N^*=F/(g_{new}-g_{old})\)，**若新方案单任务净收益不高于旧方案就不存在有限的正向盈亏平衡点**——该表达能避免「成本下降但失败损失上升」的伪收益。对仍需教师兜底的系统，**应把兜底看作目标架构的一部分，而不是蒸馏失败的例外**。

工程实现按数据、训练、推理、部署四环节。**第一步不是选框架，而是确认教师能提供的信号形态**：黑盒序列级只依赖教师生成的文本或动作，流程「生成轨迹 → 验证 → SFT」，对教师无权重或概率接口要求、跨厂商跨 tokenizer 都能用，是企业落地主流——DeepSeek-R1 的蒸馏阶段明确「只做 SFT、不包含 RL 阶段」，Qwen3 长思维链冷启动同样是「教师对每题生成多个候选、仅保留通过验证的样本再做 SFT」；白盒分布级能拿到 logits 或 log-prob 做逐 Token KL/JSD 对齐，监督更稠密但通常要求师生共享 tokenizer 并需额外概率缓存与对齐工程。数据管线既是成本中心也是质量上限：生成阶段对每个任务采样多个候选（R1 做拒绝采样，Qwen3 用 Pass@N 保留可解样本）；**验证分层设计，优先用可自动化的规则校验**（数学要求可解析 box 格式、代码用编译器跑测试），无法规则化的再交给生成式裁判——R1 明确不使用神经奖励模型，理由是其易被 reward hacking；去污染与去重是防止评测虚高的关键（Tulu 3 用 8-gram 匹配，单条样本与测试集重叠超 50% 即剔除、整个数据集重叠超 2% 直接弃用，规模化可借助 NeMo Curator 的 MinHash+LSH 与语义去重）；配比尽量参数化（PAI EasyDistill 按认知难度分箱设定冗长度目标与每箱样本上限）。训练框架已把路线沉淀为可配置组件：TRL 提供 `GKDTrainer`（`lmbda` 控制学生自生成占比、`beta` 在前向与反向 KL 间插值）、`DistillationTrainer`（分块 JSD 省显存）、`MiniLLMTrainer`（反向 KL）、`AsyncDistillationTrainer`（教师以独立 vLLM server 提供，硬性要求师生共享 tokenizer）；NeMo-Aligner 让学生匹配教师 top-K logits 并建议离线缓存，**缓存必须按降序保存否则影响收敛**，`top_k` 常取约 100。参数高效蒸馏已是优选项（**LoRA 学习率通常取全参微调的约 10 倍**）。**on-policy 路线的真正瓶颈是学生 rollout 采样而非梯度计算**，工程上把生成交给高吞吐推理引擎、训练交给训练后端并行解耦：TRL 与 vLLM server 协同（每个优化步后经 NCCL 把最新权重推回推理引擎，server 与 trainer 须位于不同 CUDA 设备）；verl 用 3D-HybridEngine 解耦，生成后端支持 vLLM 与 SGLang、训练后端支持 FSDP 与 Megatron-LM，并提供 Rollout Correction 用重要性采样与拒绝采样修正推理引擎策略与训练策略间的分布漂移；OpenRLHF 以 Ray+vLLM 把 Actor/Reward/Reference/Critic 分布到不同 GPU。两个务实提醒：**框架与推理引擎的版本矩阵往往很严格**，生产应锁定并记录版本组合；**异步与解耦必然引入一定 off-policy 偏差**，需配套修正否则训练容易不稳定。教师打分服务部署为无状态「只前向、不采样」的服务并按序列长度分桶，vLLM 的 `prompt_logprobs` 天然适配 teacher-forcing 打分，但**推理引擎并不总保证 log-prob 在版本间完全稳定，用于训练监督前应先做一致性校验并锁定引擎版本**。师生词表不一致时可用跨 tokenizer 方法（ULD 用最优传输在分布层面对齐、DSKD 用双空间投影、MultiLevelOT 在 Token 级与序列级用 Sinkhorn 距离对齐），让「用不同家族的强模型当教师」成为可能，但复杂度更高应在确有需求时再引入。部署不必是一次性全量替换：FrugalGPT 的 LLM 级联报告在保持精度的同时最高降低约 98% 成本，落到 Agent 就是路由/级联；蒸馏出的小模型还有第二个高价值用途——**作为投机解码的 draft model**，核心要求是「与目标模型分布高度一致且足够快」，KL 对齐的蒸馏正是训练这种高接受率小模型的主流手段，vLLM 用拒绝采样保证输出分布无损。放量遵循灰度纪律：先影子流量验证，再按 1%→10%→25%→50%→90%→100% 逐档放量，每档设最短观察窗与自动回滚阈值；线上持续监控时延、TTFT、成功率、教师兜底率、投机解码接受率与师生一致性，同时维护固定黄金数据集加线上采样回流的回归评测集，**防止学生模型在长尾场景悄悄退化**——这也是把监控数据回流到数据管线、驱动下一轮蒸馏的闭环起点。

## 6. 模型验收与上线：在完整 Agent 中验证收益

训练完成不等于具备上线条件：训练改变的是模型参数，真实效果由模型、Harness 与环境共同决定。**先定义「比较的对象」**：候选模型若同时用了新 Prompt、更宽松的工具权限或更简单的任务环境，即使成功率提高也无法判断收益来自训练还是系统条件变化。发布前冻结并关联四类配置——模型配置（基础模型、检查点或适配器、训练方法、数据版本、超参数、对话模板、Tokenizer 版本、推理参数）、Harness 配置（System Prompt、Skill、上下文裁剪与记忆策略、工具 Schema、调用路由、重试上限、停止条件、权限校验、人工介入规则）、执行环境配置（工具与业务服务版本、Sandbox 镜像、测试数据快照、外部依赖、资源规格、可读写范围）、评测配置（任务集版本、环境种子、预算、验证器版本、重复次数、指标口径、准入阈值）。这些共同构成可追溯的**候选发布单元**——用显式依赖关系记录「哪个模型在什么应用和环境条件下通过了验收」，**Prompt、工具协议或环境版本变化时原有结论不能自动沿用**。至少保留两组对照：纯模型对照（相同 Harness 环境与预算，判断参数更新本身的变化）、部署组合对照（候选用上线所需的适配后 Harness 与当前生产版本比较，判断最终发布组合是否真正改善业务结果）；**若候选只有经过大幅 Prompt 扩写、额外重试或放宽权限才能取得更高分，应把这些变化作为应用成本与风险单独报告**。

系统适配的目标不是继续「调分」，而是确认候选能在既有运行边界内稳定工作——直接替换端点可能出现离线分数提高但 Agent 无法解析工具调用、重复执行动作或不能正确终止。五项兼容性检查：工具协议（函数名、参数类型、必填字段、枚举值与结构化输出能否被 Harness 稳定解析）、上下文（对话模板、System Prompt、工具返回、历史轨迹、长上下文裁剪与记忆注入是否保留决策所需信息）、执行行为（成功失败权限不足信息缺失时能否正确继续修正求助终止，避免无限规划重复调用与过早结束）、预算（Token、调用次数、并行度、超时、重试与端到端时延能否在现有上限内完成）、安全边界（模型产生越权或高风险动作时 Harness 与环境仍能独立拦截，**不能因模型表现改善而取消系统护栏**）。测试顺序由局部到闭环：固定输入检查消息与工具 Schema → 标准历史前缀验证单步动作 → Sandbox 中自主运行完整任务 → 故障注入验证恢复；**只有闭环执行稳定，局部格式正确率才具有上线意义**。**若适配改变了任务难度、可见信息或动作权限，应建立新的评测基线而不是继续沿用原分数**。准入不能依赖一个加权总分，而应采用 **「硬门槛 + 目标收益」**，五道门禁：接口兼容（不依赖大量解析修复）、目标收益（锁定测试集与一致预算下达到预设最小改善幅度，报告重复运行结果与置信区间）、能力回归（核心通用能力、既有高价值任务与关键长尾场景满足非劣效界值，**不能用局部任务提升掩盖其他能力退化**）、运行预算（单位成功任务成本、超时率、重试率与高分位时延满足上线预算）、安全硬门禁（**关键约束穿透不得由其他指标抵消**）；门槛、界值、最低样本量与观察窗口应在查看候选结果前确定。安全门禁区分两个对象：**模型产生违规动作的频率衡量策略风险，违规动作穿透系统边界并被实际执行的频率衡量 Harness 与环境的防护有效性**。发布判断三种结果：全部硬门禁通过且收益达标进入灰度；硬门禁通过但样本量或长尾覆盖不足只能在限定范围继续验证；任一硬门禁失败退回对应责任层修复（信息充分仍选错工具修模型，工具描述遗漏约束修 Harness，正确动作因服务异常未执行修环境）。

灰度前先建立离线指标与线上结果的映射（离线成功率→真实业务完成率，失败恢复→人工接管率，工具与 Token 消耗→单位成功任务成本）；线上 A/B 固定分流单元，**避免同一长程任务在新旧模型间切换**。四步扩大影响范围：影子验证（只读任务可把脱敏真实请求复制给候选双跑，依赖状态变更的多步任务应在隔离 Sandbox 或状态副本中重放，**不能把「未产生副作用」误认为完成了端到端验证**）→ 低风险灰度（只读工具、低风险任务、内部用户承接少量真实流量，验证完整调用链与告警链路）→ 分阶段扩量（**高风险写操作应晚于一般问答与只读任务开放**）→ 稳定替换（全量后继续保留旧版本与配置快照，在一个完整业务周期内观察）。每阶段预定义三类条件：扩大（收益达门槛、核心回归非劣效、成本时延在预算内、无关键安全事件）、暂停（样本量不足、波动过大或归因不清，保持当前比例补充观察）、回滚（关键约束穿透、持续性任务退化、异常成本增长或核心业务指标超过劣化阈值）。**回滚对象应是完整的候选发布单元而不只是模型权重**：新模型若依赖新 Prompt、工具 Schema 或上下文策略，仅回退模型可能形成不兼容组合；**回滚只能阻止后续请求继续使用故障版本，不能撤销已在外部系统中完成的写操作**——涉及资金账户或业务状态的任务还需独立的幂等、审计与补偿机制。平台上可用 PAI-EAS 服务组与流量权重组织新旧模型共存，模型服务之外的 Prompt、Skill、Harness 与工具协议仍由应用侧独立版本化并与对应 EAS 服务版本共同登记，**避免只有模型端可回退、应用端无法恢复**。上线不是终点而是下一轮证据收集的起点：新版本产生的轨迹、Badcase、用户反馈、成本变化与回滚事件应与候选发布单元绑定并重新按三层归因，**只有被持续观察到、影响明确且可验证的问题才应进入下一轮优化，单个偶发失败不应自动触发训练**。下一轮路径由剩余问题性质决定：可明确示范而不稳定选 SFT，需通过可重复环境探索多步策略且结果可验证选 RL，教师稳定领先而重点是降规模成本选蒸馏，问题来自信息供给上下文组织工具描述状态管理或权限控制则改 Harness，正确动作因服务可用性数据状态或外部依赖失败则修环境——**此时继续训练模型不会消除根因**。在具备轨迹连接器与版本元数据映射的前提下可接入 Trace2Optimizers 使优化提案追溯到具体任务、模型版本与系统条件，**目标不是把所有线上数据自动回灌训练，而是建立明确触发机制**。由此形成「运行—观测—归因—训练或系统修复—独立验收—灰度发布—再运行」的链路，**避免将持续迭代演变为不可解释、不可复现的线上试错**。

## 7. 推理框架：定位、负载与基础概念

模型一生四阶段：预训练（海量文本学会语言与知识）、后训练（SFT/RL/蒸馏学会遵循指令、使用工具、完成特定任务）、评测、部署上线。「推理」指用训练好的模型根据输入计算输出，推理框架负责把模型加载到各类硬件与软件环境、接收请求、组织计算、返回结果。前提是能跑起来（支持要部署的模型与所用硬件），在此基础上「好」含五方面：**快**（尽快看到第一个字、生成流畅）、**多**（同样硬件同时服务尽可能多请求）、**省**（显存算力用足、算过的不重复计算）、**稳**（流量高峰超长请求或硬件故障时服务仍可用且能扩展）、**准**（部署后输出与模型本来能力一致、格式符合要求、需要时可复现）。**五者常常相互牵制**：塞进更多请求让「多」更好但每个请求生成变慢，精度压更低让「省」更好但可能影响「准」——框架要做的就是按业务需要找平衡。推理框架不止出现在上线阶段：后训练中 RL 需要反复生成大量轨迹，**「生成」这一步往往是整个训练流程中最耗时的部分**，所以主流 RL 训练框架普遍嵌入成熟推理引擎专门负责批量生成，评测与合成数据同样如此。成本结构上有一个根本差异：**训练是一次性投入，推理是持续性支出**。

Agent 负载与聊天不同：一次任务更像连续多轮对话（理解问题、拟计划、调工具、读返回、判断下一步……可能调用模型十几到几十次），且每次调用都要把系统提示词、工具、此前每步思考与返回连同新内容一起发给模型，上下文越滚越长而**每次请求中绝大部分内容在上一次请求里已经出现过**。三个特点：输入很长、输出相对较短、前后请求高度重复；端到端耗时是每步累加，每次调用多等一秒几十步就是几十秒。**聊天场景主要比拼谁算得快，Agent 场景还要比拼谁能少算**。与训练框架的差别在核心目标（练出来 vs 用起来）、计算内容（前向+反向更新权重 vs 只做前向权重固定）、负载（批量备好按计划跑 vs 请求随机到达随时进出）、时间要求（几天几周可接受 vs 秒级响应）、显存用途（权重梯度优化器状态激活 vs 权重与 KV Cache）、指标（训练吞吐收敛算力利用率 vs 首字延迟生成速度吞吐单位成本）。**推理框架更像一个在线服务系统**，面对的问题与数据库、Web 服务器相似：请求排队、资源调度、缓存命中、负载均衡、故障恢复，只不过调度的不是 CPU 与磁盘而是昂贵的 GPU 与显存。分层关系是 Harness → 模型服务（API 或自部署）→ 推理框架（模型与硬件之间的中间件层）→ GPU 等硬件；日常只用 API 一般不会关注它，但自行部署模型的企业，成本、首字等多久、每秒吐多少字、并发上来会不会变慢都由这一层决定。几个易混名词一层套一层：推理引擎（把模型跑起来的核心程序，负责调度、显存管理与计算执行）是心脏，推理框架（还含 API 接入、分布式部署、缓存系统等配套）是整套动力系统，推理服务（额外含网关鉴权计费监控扩缩容）是可上路运营的车队，模型服务平台 MaaS（按调用量付费）是面向公众售票的客运公司，本地运行工具则是一条命令在笔记本上跑起模型。

基础概念串起账单上的疑问。**Token** 是模型读写与计费的最小单位，输入输出分开计价且输出通常贵好几倍。**Prefill 与 Decode**：Prefill 相当于「读题」，一次性读入全部输入、所有输入 Token 并行计算、GPU 计算单元被充分调动，结束时产出第一个输出 Token；Decode 相当于「作答」，每次只生成一个 Token 接到已有内容后再生成下一个，**每生成一个 Token 都要把整个模型权重从显存读一遍却只做很少计算**——好比为写一个字把整本参考书从头翻一遍，所以瓶颈不在算力而在显存带宽。**Prefill 吃算力，Decode 吃带宽**，这也解释了输出为何更贵：必须串行生成，单位时间内占用 GPU 更久。既然最大开销是「翻书」，翻一次书能不能同时帮很多请求各写一个字？这就是批处理：处理 1 个与 64 个请求 Decode 一步耗时相差不大，产出 Token 却相差几十倍；**连续批处理（Continuous Batching）以每一步生成为单位调度，写完的随时下车、新来的随时上车**，如今已是主流框架标配。**KV Cache 是模型的草稿纸**：生成每个新 Token 都要回头看前面所有内容（注意力机制），把前面每个 Token 的中间结果 Key 与 Value 保存下来直接取用、只计算新 Token 本身；草稿纸并不免费——大小与上下文长度及并发请求数成正比，**在实际推理服务中 KV Cache 往往是显存里最紧张的资源，其容量直接决定一张卡能同时服务多少请求**。让草稿纸与模型「变薄」的常用办法是量化：16 位降 8 位在多数通用任务上影响较小已是生产常见选择，降到 4 位甚至更低压缩更明显但效果影响更依赖具体模型与任务、需用自己的业务数据验证；不少新模型在设计时就采用压缩 KV Cache 的注意力结构从源头变薄。**模型能不能部署先看权重的显存账，能服务多少人主要看 KV Cache 的账**。三个性能指标此消彼长：**TTFT**（首 Token 时延，主要由 Prefill 决定）、**TBT/TPOT**（Token 间时延，决定「语速」，主要由 Decode 决定）、**吞吐**（单位时间处理的 Token 数或请求数，决定一套硬件能服务多少用户与单位成本）；框架的大量工作就是**在用户能接受的延迟范围内把吞吐推到尽可能高**，业内用「有效吞吐」（Goodput）描述满足延迟要求的那部分吞吐。**推理优化的本质，是在用户能接受的等待时间内让每张卡多服务几个人**。**MoE** 则是参数很多每次只用一小部分：DeepSeek-V3 总参数 6710 亿而每个 Token 实际只激活约 370 亿，知识容量大而单 Token 计算量相对小，代价是所有专家必须常驻显存、一台机器往往装不下，需把专家分散到多张卡，跨卡通信与负载均衡成为新问题。

## 8. 生态格局与一个请求的旅程

开源推理框架发展只有三年多，已形成四条脉络：服务器端通用推理引擎、面向个人电脑与端侧的本地运行工具、管理整个集群的编排层、模型厂商与互联网企业开源的自家推理系统。通用引擎中 vLLM（伯克利，2023 年 6 月，提出 PagedAttention 分页管理 KV Cache，2025 年 5 月成为 PyTorch 基金会托管项目）、SGLang（LMSYS，2024 年 1 月，提出 RadixAttention 自动复用请求间公共前缀、重视结构化生成）、TensorRT-LLM（英伟达，面向其 GPU 深度优化）、LMDeploy（上海人工智能实验室 InternLM 团队）；更早的 Hugging Face TGI 已于 2025 年 12 月进入维护模式并建议转向 vLLM、SGLang。两个明显特点：**学术研究与工程实践距离非常近**——连续批处理来自 2022 年 Orca 论文、分页 KV Cache 来自 2023 年 PagedAttention、FlashAttention 发表于 2022 年、PD 分离代表研究 DistServe 与 Splitwise 发表于 2024 年，几乎都在发表后很短时间内进入主流引擎；**各项目相互借鉴、核心功能日益趋同**——连续批处理、分页 KV Cache、前缀缓存、分块预填充、投机解码、结构化输出如今已是共同配置，竞争焦点转向新模型发布后能多快支持、能覆盖多少种硬件、大规模集群部署表现如何，**从「谁的功能多」转向「谁跟得上模型和硬件的变化」**。本地与端侧：llama.cpp（C/C++ 实现，可在普通 CPU 与苹果芯片运行，GGUF 成为本地量化模型最常用格式之一）、Ollama（把下载运行与简易 API 封装成一条命令，2025 年起逐步转向基于 GGML 的自研引擎）、MLC-LLM（通过机器学习编译部署到手机浏览器等设备）。2025 年以后出现的集群编排层不替代引擎而是架在其上管理整个集群：把请求路由到合适实例、实现 PD 分离部署、管理传输跨机器 KV Cache、按负载自动扩缩容，代表项目有英伟达 Dynamo、红帽等发起的 llm-d（基于 vLLM 原生运行在 Kubernetes 上）、月之暗面 Mooncake（以 KV Cache 为中心的 PD 分离架构，相关论文获 2025 年 FAST 最佳论文奖）——**当单机引擎优化逐渐趋同，推理效率的差距越来越多地拉开在集群调度上**。厂商侧，DeepSeek 2025 年开源周陆续开源 FlashMLA、DeepEP、DeepGEMM、EPLB、3FS 等组件，其内部引擎源自 vLLM 早期分支、与内部基础设施耦合较深，因此选择把独立组件贡献社区并在新模型发布前提前同步，2026 年 10 月正式开源推理框架 DeepInfer；此外京东 xLLM（以支持国产芯片为重点）、阿里 RTP-LLM、百度 FastDeploy 2.0 各有路径，共同认识是**模型结构越复杂、部署规模越大，推理侧实现就越成为模型能力的一部分**。新模型为什么要等框架「适配」：要实现模型结构（新注意力机制、新专家路由需编写高效算子）、对齐对话模板与工具调用格式、支持新量化格式与新多模态输入；2025 年 9 月 DeepSeek 发布稀疏注意力的 V3.2-Exp 时 vLLM 当天宣布支持，同月 Qwen3-Next 混合注意力结构 vLLM 第二天支持——**能做到这么快是因为模型厂商在发布前就与框架社区提前合作**，**模型与推理框架越来越像是一起设计、一起发布的**。硬件多元化同样在推进：vLLM 2025 年推出硬件插件机制让芯片厂商在主项目外独立维护后端（昇腾 vllm-ascend、昆仑芯 vLLM-Kunlun、沐曦适配版本），DeepInfer 同时支持英伟达 GPU 与华为昇腾 NPU，Triton、TileLang 等更高层算子编程语言降低移植成本；可选方案变多但不同芯片与框架组合下的支持范围与性能差异仍较大，部署前需逐一验证——**硬件越多元，推理框架作为模型与芯片之间适配层的价值就越大**。三个方向归结为：从单机引擎走向集群系统、从通用实现走向与模型协同设计、从单一硬件走向多种硬件。

跟着一个请求走一遍（客服 Agent 把系统提示词、十几个工具定义、前几轮对话与新问题打包成约 8000 Token 的请求），六站各司其职：**入口**（协议转换、对话模板、分词、输出解析，决定效果一致性与安全性）、**调度**（连续批处理、分块预填充、显存准入、负载均衡，决定吞吐与首字延迟）、**执行**（并行策略、算子、低精度计算，决定单卡性能）、**缓存**（分页管理、前缀复用、多级缓存，决定成本）、**集群**（PD 分离、大规模并行、扩缩容与容错，决定规模化稳定性）、**采样与输出**（采样策略、确定性推理、结构化输出、投机解码，决定可靠性与生成速度）。入口的核心是对话模板：系统提示词、用户消息、助手回复、工具调用与返回需按模型训练时约定的格式用特殊标记拼成完整序列再转成编号，**模板拼错了模型照样能输出但效果可能明显下降、工具调用频繁出错**；模板中的特殊标记相当于「控制指令」，**若用户输入或工具返回中恰好包含与特殊标记相同的字符串，必须当作普通文本处理，否则可能被利用来伪造角色或注入指令**——**接入层决定了同一个模型部署在不同地方表现能否保持一致**。调度是指挥中心，每步计算前决定处理哪些请求、新请求要不要现在开始 Prefill、KV Cache 空间够不够；8000 Token 的请求一口气 Prefill 完则批次里正在生成的其他请求要停下来等，常见做法是**分块预填充（Chunked Prefill）** 把长请求切成小块与其他请求的 Decode 混算；显存不足时新请求排队，极端情况下暂停一些生成中的请求把 KV Cache 换出到内存或丢弃重算；调度本身有 CPU 开销，普遍采用**异步调度**让 CPU 在 GPU 计算当前步时提前准备下一步；多机部署时集群负载均衡器先决定分给哪个实例（综合排队长度、显存占用与前缀缓存位置），实例内调度器再决定在哪一步以什么方式计算——**调度器要回答的永远是同一个问题：下一步，让 GPU 算什么**。执行层先解决装不下的问题，四种并行：张量并行 TP（把每层大矩阵切开分给多卡）、流水线并行 PP（不同层分给不同卡接力）、数据并行 DP（多卡各自完整处理不同请求）、专家并行 EP（针对 MoE 把不同专家分散到不同卡）；大规模 MoE 往往组合 DP 与 EP，**某些专家特别「热门」所在的卡会拖慢整体，框架通常把热门专家多复制几份**；每层计算最终落到算子（Kernel），**同样的计算任务算子写得好不好性能可以差出数倍**（如 FlashAttention），GPU 每启动一个算子都有固定开销，框架会把一整步的算子调用「录制」下来一次性回放——**模型结构决定要算什么，算子决定算得多快**。

缓存是 Agent 场景的关键：8000 Token 里系统提示词与工具定义每次都一样、前几轮对话上次已算过，若 KV Cache 还保存着就可直接复用只算新增部分，这就是前缀缓存。高效复用的前提是管理好它——早期为每个请求预留一整块连续显存造成大量浪费，**分页管理借鉴操作系统内存思路把 KV Cache 切成固定大小的页、按需分配、页间不必连续**，大幅减少浪费也让不同请求共享相同前缀变得容易；显存有限于是构建多级缓存（最常用放显存、次常用放主机内存、更多放 SSD 甚至独立分布式存储集群，阿里云 Tair KVCache 把资源池化管理并适配 vLLM、SGLang、TensorRT-LLM）。这就解释了账单上的「缓存命中」价格：**命中部分跳过了 Prefill 计算，服务商成本大幅降低，所以很多厂商对缓存命中的输入 Token 大幅打折，常见是原价的一到两折**。对 Agent 开发者有一条非常实用的经验：**尽量让每次请求的开头保持稳定，把固定不变的系统提示词与工具定义放最前面、新增内容追加在末尾；如果在系统提示词开头插入当前时间这类每次都变的信息，后面所有内容的缓存都会失效——在 Agent 场景里，缓存命中率就是成本**。集群阶段三个变化：一是 PD 分离部署（两阶段脾气完全不同，放同一组 GPU 难免互相干扰，用一组机器专做 Prefill、另一组专做 Decode，完成后把 KV Cache 经高速网络传过去继续生成，两组各自选择最合适的并行方式与规模；PAI-EAS 部署 MoE 的 PD 分离模板中 Prefill 实例默认 8 卡张量并行、Decode 实例默认 8 路专家并行加 8 路数据并行，多模态模型的图片视频编码环节也可再拆出来单独部署）；二是更大规模并行与更复杂负载均衡（大规模 MoE 的 Decode 可能几十上百张卡组成一个实例，专家负载是否均衡、卡间通信是否高效直接决定整体吞吐）；三是弹性与容错（**规模越大硬件故障越是常态，上百张卡组成的实例任何一张出问题都可能导致整个实例不可用**，框架要能把受影响请求迅速转移并尽快用剩余健康硬件恢复服务）——**单机推理比的是算得快，集群推理比的是调度得好**。采样与输出是最后一站：模型每步输出的是词表中每个 Token 被选中的概率，温度越高越随机、越低越倾向选概率最高的，Top-p、Top-k 限定只从概率最高的一部分中挑选；**即便温度设为 0，很多推理服务中两次结果仍可能有细微差别**——GPU 浮点运算对计算顺序敏感，同一请求与不同请求拼批时算子内部顺序可能不同，偶尔就让模型在某步选出不同 Token，为此一些框架提供「批不变」或确定性推理模式，**这对评测结果可复现性很重要，对 RL 训练也很重要，因为训练时需要推理阶段与训练阶段对同一段内容算出一致的概率**。采样环节还能做两件有价值的事：结构化输出（把格式要求编译成语法规则，每步采样前先算出哪些 Token 合法、把不合法的直接排除，**从根本上保证输出格式正确**）；投机解码（先用小而快的草稿模型一口气猜出后面几个 Token，再让大模型一次性并行验证，猜对保留猜错从出错位置重新生成，**数学上可保证最终输出的概率分布与大模型逐个生成完全一致**）。

谁在用：模型厂商与云厂商把推理框架当核心基础设施（**同样一批 GPU 效率高一倍就能服务多一倍用户或把价格降一半，API 价格竞争很大程度上就是推理效率竞争**），通常有专门团队基于开源深度定制或完全自研；金融政务医疗能源制造等需私有化部署的企业出于数据安全与合规是自己选型部署调优运维的直接使用者，且越来越多需要在国产芯片上完成部署；大多数 Agent 与应用团队通过 API 间接使用却直接受益——选服务商时首字延迟生成速度缓存命中价格都是重要考量，设计提示词与上下文结构时是否有利于缓存命中会让成本相差数倍，也有越来越多团队在意图分类信息抽取等环节自部署小模型以降本降时延；后训练与科研团队是另一类重度用户（RL 大量生成轨迹、蒸馏批量生成示范或打分、评测跑大量测试题），更看重离线批量吞吐同时对推理与训练的一致性要求更高；个人开发者随本地工具成熟在笔记本台式机上跑模型用于学习调试或处理不便上传的私人数据。智能体越普及，模型被调用次数越多、每次上下文越长，**在这道乘法题里推理效率的每一点提升都会被调用量成倍放大**。

## 写在最后

模型侧的优化解决「决策上限」，推理侧的工程解决「每次调用的成本与等待」，两者都要在完整 Agent 系统中验收才算收益。而模型只是调优对象之一——Harness、上下文、工具与经验资产同样需要持续改进，这就需要一个把运行数据变成优化动作的闭环。下一篇整理 [Agent 调优与数据飞轮](/source/agent/企业级Agent手册/19-Agent调优与数据飞轮)。
