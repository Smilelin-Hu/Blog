# 研发效能实践：从编码提效到端到端交付

AI 辅助编程普及后，代码产出呈指数级增长，但审查与交付的人力并未同步扩张。DORA 年度报告显示 AI 深度参与开发的同时代码 Bug 率 +9%、代码评审时间 +91%、平均 PR 体积 +154%（相关性口径而非因果结论）；Linux 内核上游修复 CVE 的数量从各版本四五百跳升到逼近两千。一个复杂 Feature 从需求到上线约需 20 个工作日，其中代码实现约 2 天——即使 Coding Agent 把编码速度提升 10 倍，端到端周期也只是从 20 天降到 18.2 天。云通信团队走过三段演进（2024 年铺开补全与生成式 IDE、2025 年把规范与领域知识沉淀为宪法和 Skill、2026 年全面 Agent 化作业）后得到同样的反直觉结果：AI 生成代码量翻了数倍，交付周期只被压缩了很小一截。堵点在编码之外仍由人衔接的节点：需求澄清对齐、代码评审跟不上产出、测试排期堵住。核心判断：**只要交付链路里存在由人衔接的节点，该节点就决定了吞吐上限**——产能瓶颈正从「写」转移到「审」和「交付」。本文按源章顺序整理八项实践：先看智能体在内核补丁测试、代码审查、补丁交付和运维评测中的应用，再看安全产品、数据库、云通信团队与多 Agent 研发小队怎样组织协作。

## 1. ABACI：面向内核补丁的定向测试与缺陷检测

传统内核动态测试以覆盖率引导的模糊测试为主流，为广度探索而设计；当测试目标被限定为「本次变更涉及的代码」，效率问题立刻显现——实测统计中**主流工具累计生成的测试用例里与指定目标相关的仅占 5% 左右**，其余算力构成「用例执行幻象」：测试系统高强度运转、覆盖率曲线上升，而变更代码始终停留在执行范围之外，合入前报告标记的「通过」缺少支撑。从广度探索转向定向抵达要跨越三个挑战：如何造出语义有效的用例（内核用例是受严格约束的系统调用序列，须同时满足调用间语义关系与执行前状态条件；大模型读得懂代码意图，但把完整用例生成整体交给模型走不通——幻觉恰恰在细节层面集中爆发）、如何引导用例收敛到目标（大量数值参数只能靠反复执行与观察反馈逼近，传统覆盖率衡量的是代码区域的新鲜程度而非「离目标还有多远」）、如何高效识别真实缺陷（**绝大多数新缺陷是历史缺陷的变体**，机制与触发模式已隐含在历史报告与修复提交中）。设计第一原则是职责分离：语义理解与全局推理交给大模型，精确性与确定性交给程序化机制和运行时反馈。三层能力对应三个挑战：**语义驱动的定向用例构建**以变更位置为起点反向推理，把搜索空间从近乎无穷压缩到可枚举规模，参数上关键约束优先——只有被目标语义真正钉住的少数参数由模型决策，其余交给确定性机制与运行时探索，幻觉暴露面从全部参数收缩到少数关键取值；**目标导向的运行时收敛引导**用方向性反馈取代纯覆盖率——靠近趋势的用例优先深挖、原地踏步的降级淘汰、方向性信号难以区分时覆盖率才作辅助判据，演进遵循结构保持原则（已确认的序列骨架与关键约束稳定，只演进待探索的自由部分）；**经验驱动的缺陷模式筛查**从历史修复提交与问题报告蒸馏缺陷机制与触发模式，同机制聚类抽象、专家抽查确认后入库，形成全局与子系统两级知识库，流水线新发现经归纳回灌入库，把模型推理预算从理解代码重新分配到定位问题。服务链路四阶段全自动：目标识别 → 目标分析与环境准备 → 隔离虚拟化环境并行执行定向测试与缺陷筛查 → 结果归集与报告，端到端小时级预算、每个缺陷附复现材料。在 100 个真实合入变更的评测集上，**目标函数到达率 54.1% 对比 Syzkaller 的 4.5%（12 倍）**，变更行覆盖率 48.4%、目标函数覆盖率 66.8%（对照组贴近零值）；线上已发现上百个可复现真实缺陷并向上游贡献多个修复补丁。四条实践经验：目标粒度直接影响收益（定在变更行反馈信号最锐利，定在函数覆盖面宽而收敛慢，按变更类型混合使用）；语义分析与运行时探索的预算比例按子系统调整；知识库冷启动依赖专家投入、入库抽查必须保留；**报告的可复现性决定闭环成败——附带复现材料的缺陷才推得动修复，只有可疑描述的报告很难走出评审环节**。

## 2. Kitta：把通用 Code Review Agent 领域化

通用 AI Review 工具在核心业务里达不到专家级审查需求，局限在两个维度：**工程行为约束不足**（变更较大时只评审部分文件导致遗漏、报告问题与实际代码位置对不上、质量随提示词细微差异大幅波动）和**检查深度不足**（对每个项目一视同仁，只能扫描代码本身缺陷，感知不到项目特有的审查需求）。拆成三个深层挑战：领域知识匮乏（通用模型未必懂内核的锁语义、编译器的中间表示约定）、业务理解不足（社区开源项目、企业内部仓库、发行版维护对「什么算问题、有多严重」的标准截然不同）、信任边界模糊（用户说「好」不一定是真的好，Agent 自我感觉良好更靠不住）。一句话：**AI 能「看懂」代码，却未必「看懂」项目**。Kitta 的解法是三步走把通用 Agent 领域化。第一步项目级专家资产管理：从真实评审与缺陷记录出发，经采集关联、规整去噪、语义解析、隔离复现沉淀为专家资产——隔离复现让每条缺陷模式与预期结论可验证、经得起追问，而不是把噪音当经验；资产含两类内容，评判标准（评审原则、缺陷模式、项目惯例）回答「按什么标准判」，验证样本（问题样本、正常样本、预期结论）回答「判得对不对如何度量」，换新项目同样管线可重新提炼——**让「懂行」从个人经验变成组织能力**。第二步双轮驱动定制：流程定义看哪里（语义一致性、回合完整性、发行版规范、集成风险四个维度确保不漏项），知识决定怎么看（按子系统组织专用知识库，引入「有罪推定—全栈调用链分析—自我辩论」的深度审查流程）；在龙蜥 ANCK 重点是回合补丁——语义一致性检查先微观溯源比对补丁级差异再宏观评估整体功能，避免「逐行都对、整体变了」的漏判，完整性检查智能追踪上游依赖链、自动识别 Fixes 补丁杜绝已知漏洞回归。第三步在线离线协同进化：离线用验证样本隔离评测、反思进化校准判断标准；线上基于 Review 意见与研发后续代码行为分析意见有效性，结合采纳率持续监控、知识更新与阈值调整。落地为五阶段流水线：PR 分类（自研还是回合，分类决定检查范围避免不必要开销）→ Message 规范性检查 → 补丁完整性检查（无遗漏/已合入/遗漏三类结果）→ 回合一致性检查（基础、上下文、语义三层对比，分层输出差异性质）→ 代码质量审查（Critical 内联评论定位到行，无风险给 LGTM）。运行数据：**累计审查 7 万+ 补丁、门禁准确率 97%、合入率 62%**；回合补丁一致性意见采纳率 70.4%、准确率 99.8%，自研 PR 意见采纳率 41.8%、准确率 73.6%；方法论在内核、编译器、文件系统、网络、云原生、AI 计算框架六大领域验证，审查质量提升 17.0%–31.6%。Benchmark 评估体系基于 LKML 真实评审、sashiko 单 commit 单 issue 映射、龙蜥社区数据三类来源，与多个 SOTA 方案横向对比把差距转化为 Skill 迭代优先级；服务过程沉淀的数据还在反哺基座模型——专家标注反哺漏洞发现、思维链轨迹反哺指令跟随、用户偏好反哺对话表达、后续 Coding 动作反哺代码生成，形成「数据向下沉淀、能力向上反哺」的飞轮。人机信任边界三条原则：**精准分级、克制打扰**（安全漏洞和破坏坚决拦截 CI 是底线，其余分级呈现仅作提示）；**行为作证、拒绝自嗨**（不把开发者的默默无视当成认可，不看用户说什么、看代码改了什么，置信度熔断加追踪真实变更）；**人类兜底、适时退场**（AI 是探照灯照亮风险给出证据，Maintainer 是方向盘握最终决策权）——最好的 AI 门禁不是替代 Maintainer，而是让他们只把精力花在真正需要人类智慧的地方。

## 3. PatchPilot：让补丁交付具备可追踪的过程与可验证的结果

上游补丁进入下游产品版本时，失败原因往往不是单一 Git 冲突：同一函数可能已被重构、结构体字段或函数签名可能已演化、修复依赖的前置提交可能尚未进入目标分支。难点不在于「能不能生成一段修改」，而在于**能否让一次补丁交付具备可追踪的过程、可验证的结果和可持续优化的机制**。PatchPilot 把过程组织为多阶段工作流：补丁获取 → 冲突分类与意图理解 → 可行性分流 → 依赖分析 → AI 解冲突 → 语义审查 → 交付回检，每阶段有明确输入、产出和状态，复杂任务可观测、可暂停、可恢复、可复盘。五项机制各有工程要点：**可行性分流**先以启发式规则快速评估冲突规模、缺失符号、危险变更和复杂度，仅对模糊区间的任务调用 LLM 精判，形成「快筛 + 精判」双层漏斗，把昂贵推理投入真正复杂的问题，并为高风险改动设人工升级出口；**依赖分析**是 State-First 的——以「代码状态偏离」而非单纯缺失符号为线索，函数实现、结构体字段和签名的演化都纳入判断，递归识别必要依赖，避免只按缺失符号补丁导致依赖链膨胀；**AI 解冲突**按 hunk 推理，每轮记录处理方案、失败原因和改动范围，结构化失败记忆让下一次尝试避开已验证的无效路径；**质量守护**检查残留冲突标记、代码漂移和语义偏差，**不把「能合入」误判为「可交付」**；**人机协同**让证据充分且风险可控的任务自动处理、不确定或高风险任务升级工程师。工具约束推理是另一条硬规则：依赖提交必须由 Git 命令精确枚举 commit SHA、以工具输出为事实依据，避免模型凭直觉补全不存在的前置变更。成功以端到端交付定义：回合成功后自动创建检测轮次、回检 PR 与交付状态，任务从入队到合入的状态连续记录、持久化管理，异常中断可恢复或重新调度——**以「是否完成交付」而非「是否完成一次执行」衡量效果，只统计命令执行成功会高估自动化价值**。可复用方法论五条：从高频、证据充分的问题开始（输入明确的场景优先，不一开始追求全自动决策）；先建立工作流再引入 Agent（没有状态、上下文和回检的 Agent 难以在生产中稳定运行）；以质量门禁约束生成（每个自动化动作定义可验证结果与人工升级条件）；以端到端结果度量价值（同时观察效率、成本、交付率、人工升级率和返工率）；让失败成为资产（失败原因、尝试过程和人工决策结构化沉淀，反哺规则、提示词和评测）。这套方法同样适用于 SDK 大版本升级、跨分支移植、fork 同步等代码迁移场景。

## 4. STAROps：运维评测数据的要求与构成

阿里云 STAROps 是服务上千家客户的 Agentic Ops 平台，其评测实践回答一个问题：考核延伸到执行过程之后，一条评测数据要保存什么。运维评测的方式正在变化——早期基于日志指标等离线数据只看最终答案，像考场答题；现在越来越多把 Agent 放进可执行环境完成任务，像放进真实猎场，考核从答案延伸到证据和能不能把问题修好。一次根因分析可抽象为输入、多轮「Agent 判断、工具取证」循环和诊断结论：每轮先定范围、再提假设、用证据排除、定下一步，各轮靠上下文衔接。评一次根因分析要看每轮判断和取证站不站得住，因为**结论正确不等于过程可信**——要评分析思路能否通用（评测集覆盖足够多场景）、结果错在哪一步（数据能对照每步调了什么工具、返回什么、据此做了什么判断）、执行效率（保留完整调用过程看无效调用与上下文堆积）。还有一类更难发现的错误是**时间窗查错**：工具调用成功、返回真实数据、推理前后自洽、结论甚至碰巧正确，但数据对应的不是故障发生的时间段——评测数据必须记下真实时间窗供对照。评测数据三条基本要求：**覆盖要足够广**（公开数据集的覆盖面不能代表自己的真实环境）、**能重复执行**（一项研究中同一 Agent 同一场景跑 10 次只有 6 次诊断成功，只跑一次只留成功那次不够）、**每条证明自己有效**（某研究从九千多次注入里只保留 1430 条——执行了注入不等于产生了可用数据，缺乏清晰因果关系的题目考核的推理并不存在）。一条数据的核心是**能还原一次完整分析轨迹**：目标、观测、工具、动作、结果五要素，只保存答案只能比结论，保存轨迹才能看出哪一步查错数据、哪一步做错判断；轨迹不要求固定路径，但关键判断、关键证据和关键动作必须明确，否则答案对了也可能是碰巧。轨迹之外必须一起保存**配套条件**（环境、工具、观测手段——不保存则下一版本跑同题已换环境不可比）和**核验依据**（评价标准——不固定则分数变化说不清是 Agent 变了还是判分的人变了）。运维场景另有四个约束：环境绑定（故障要在真实服务、流量和观测里发生，数据与环境一起保存）、时间绑定（调用链和日志有保留期，时间窗与当时证据要及时保全）、完整因果链（每步有证据，原因、传播和影响分开写）、低频高风险（生产故障不能线上反复试，用故障注入在评测环境按同一机制反复造出来）。

## 5. STAROps：构建方法、质量检查与成本结构

单条数据的构建流程十二步分四段：**设计**由 Agent 判断（选场景、设计故障——注入什么、注入在哪、沿哪条链传播）；**注入验证恢复**由工具执行（确认环境处于干净基线、注入命令执行成功只说明命令跑完了、故障是否生效要看信号、告警要等真的出现、最后恢复环境）；**取证与写答案**回到 Agent（故障期间和恢复之后两个阶段都要取证，才能完整还原注入点、根因、传播链、影响面）；**检查与入库**由程序和人把关（程序门禁查字段齐全、每个数字附可执行查询且重跑一致；准入复核查因果链说不说得通、相似候选排除干净——Agent 先审、人终审）。持续构建拆给四个 Agent：ScenarioAgent 管题目（缺口识别、变更分析、架构还原、现场回流），EnvironmentAgent 管环境（拓扑构建、业务仿真、流量注入、观测接入），BuildAgent 管构建（注入、信号捕获、证据提取、准入复核——**复核不沿用构建时的上下文，重新取证据核对，否则会顺着已有答案走**），SupervisorAgent 管监督（质量体检、失效识别、回归复测、难度进阶）；人定目标、定验收、终审，不退出但不再逐条梳理。**构建评测集本身是对组织 Agent 工程能力的一次压力测试**：同时考验 Agent 自身能力、Agent 间协同（前一角色产出必须是后一角色可靠输入）、基础设施（工具标准化、环境可重建、状态保存、长任务恢复）和治理质量机制（Agent 自己说完成了不算数）。题目两个来源：一是按**能力地图**主动规划——横轴八个能力域（代码与变更、应用运行时、数据库、容器、中间件、云产品、主机、网络），纵轴四档难度（单点故障、有传播链、多故障并发、告警风暴），纵轴表示要排除多少干扰才能定位，空着的格子就是未覆盖的，由人确认优先级；二是**线上问题回流**，顺序是「先保全，再还原」——先用工具保全轨迹、调用链和时间窗（证据保留期短，处理晚了取不回来），再经机制还原（Agent 弄清因果关系和必要条件，同样报错可能来自不同原因）、等价重放（工具用同一机制重新执行，只复现报错不够）、重建验证（程序对齐线上与重放的信号时序，对不上退回重建），最后与注入构建的数据用同一套七字段标准核验。环境扩展由覆盖需求触发而非规模变大，人确定能力域和隔离边界；流量分常态加场景化两层（常态让故障发生时有业务被影响，场景化让待验证的传播路径真有请求经过），告警阈值用历史数据回放校准；基线检查卡得严——基线本身有异常时注入信号会与原异常混在一起；产出可复刻的环境配置代码，稳定承载故障、流量接近真实、观测完整三者里**优先保证观测**。构建循环四步中，信号捕获六项必查（告警源头、环境变更、指标异常、调用链路、影响范围、噪音干扰——同一时间窗有别人的故障在跑，这条数据直接作废）；标准答案组织成**七个字段**：根因实体（具体到资源或服务）、故障类型（可验证的机制而非表面现象）、因果链（原因传播影响分开）、鉴别点（为什么排除相似候选）、告警锚点（实际触发事件和时间窗）、关键数字（附原查询）、评分规则（按字段独立打分，根因对传播链错能如实反映）。**数字必须单独核验**——曾有答案写错误率约 25%，人工阅读没发现异常，工具重查连续五个时间窗错误数均为零；写不出查询的数字不能进入标准答案。入库后还要持续做五项质量检查：质量、覆盖、区分度、规模、新鲜度，**按短板检查，不能用平均分抵消局部问题**；新鲜度看抽样原样重跑能否跑通而非数据年龄（镜像、告警规则或观测配置一变，昨天建好的数据也可能跑不出来）；失效数据下架（否则被评 Agent 答不对会被记成能力问题，研发去修一个并不存在的缺陷），修复后在仍有效的数据上复测。**分数接近满分时主动提高难度**——强弱曲线重合说明数据已分不出能力，加难后分差重新出现才说明原有数据难以区分；加难后分数下降是题目变难，不能读成能力退步。规模上截至 9 月积累 1400 多条，根因分析 838 条覆盖 100 多类故障（3 月还只有 58 条，半年增长 10 倍以上），另有取数 500 多条。成本结构三段演进：起步以人工为主 → 补齐环境与判据时环境投入快速追上人工 → 复用构建路径后重复人工回落、模型调用超过人工，最终**环境成为最高的一块——用了 Agent 总成本不一定下降，真正减少的是重复的人工操作**。三条原则收尾：标准答案只能来自证据；复核的独立性来自证据的独立；评测集本身也要被持续评估、持续演进。

## 6. Agentic SOC：评测驱动产品进化与组织重构

Agentic SOC 是以多 Agent 协作为核心的安全运营产品，把多云多产品的分散告警归并为可调查可处置的安全事件，再由不同 Agent 分工完成调查、研判、响应与阻断。产品改进闭环是：生产问题形成失败样本 → 评测定位能力差距 → Agent 提交候选修改 → 验证与审批决定变更是否生效 → 新的生产结果进入下一轮。一次角色识别错误展示了闭环怎样运转：实际是 A 攻击 B，报告却把角色写反，且几个模块各自判断、即使报告修正时间线和处置建议仍可能沿用另一套结论；根因是三个模块缺少共享判定，修复从「改正一段报告」扩展为统一生成攻击者、受害者及判定结果字段，让报告、时间线、处置建议复用；复测重跑原场景并核对三模块输出一致，回归用例纳入评测基线——**一次修复留下两份结果：生效的产品能力，以及可以反复运行的验证样本**，团队不必每次依赖某个人记得这个问题。统一评测 SOCBench 含 211 个真实调查任务、覆盖 16 类事件、从 9 个维度评估 5 个调查阶段，题集、执行配置和评分规范都纳入版本管理；安全调查是长程任务，只检查最后结论会遗漏很多问题，还要看环境定位、入口确认、攻击主链还原、影响范围检查和结论的证据支撑，同时结合查询量与耗时理解效果——查询更多不必然调查更充分，耗时更短不代表任务完成。发布关注三件事：原问题复测通过、约定评测范围内无退化、风险可接受，结合独立测试集、生产任务重放和灰度验证。Agent 自主工作的边界在任务开始前明确四类：**目标边界**（允许解决什么问题，超范围重新确认）、**质量边界**（原问题必须复测通过、评测范围不得退化、证据不足不能输出确定结论）、**权限边界**（数据工具环境限定、高风险操作预授权、生产变化可追踪可回滚）、**停止边界**（异常、越权、关键指标恶化、达到重试或资源上限、无法可靠判断都触发暂停）——约束越清楚，Agent 可自主推进的空间越清楚。组织侧的对比更直观：分段交接方式（诉求澄清、设计、安全口径、后端、前端、集中验收依次展开）合计 51 天；另一种方式先确定 12 条验收条件、由一个结果负责人贯穿全过程、把产品体验工程交付安全效果组织为并行任务，周期 14 天。关键在验收与责任的位置：末端集中判断的标准放到任务开始时，随交付物逐段转移的责任由一个 Owner 从目标确认跟到结果验证。四个协作要求：统一客户结果、统一结果标准（指标和证据口径提前确定）、贯穿结果责任（并行可以由多人多 Agent 承担，结果仍需有人负责）、按风险安排专家介入。岗位融合表现为责任范围扩大：产品经理向实现延伸交付可运行原型、安全工程师把专业经验转化为场景判定标准与效果验证、研发向全栈闭环和客户业务理解延伸；但要**把「能够多做一些工作」和「所有人都承担所有工作」区分开**——标准明确可评测可回滚的任务由 Agent 执行人审批，跨领域风险可控的由结果负责人借助 Agent 闭环，高风险高歧义不可逆的仍由专业人员主导。阶段统计：需求平均周期 50.9 天降至 13.8 天（约 72.9%），窗口内吞吐率 63.9% 提升至 98.9%；仍要验证的是机制能否复制到更多模块、能否从依赖个人主动性沉淀为团队稳定能力。

## 7. PolarDB-X：从报警到自动修复的端到端实践

数据库研发任务分两类，协作方式不同：新功能开发与优化需求明确但方案难以一次确定，采用研发主导、Agent 执行；报警工单与缺陷修复是长期效率痛点——**一次修复最终可能只涉及几行代码，但前期问题分析、根因定位和后期验证需要大量投入**，仅让 Agent 协助编码节省的时间非常有限。好在第二类任务有具体故障现象，可通过复现验证原因假设、通过修复前后对照检验效果，稳定复现和测试结果提供明确验收依据，因此选择从它入手让 Agent 端到端自主处理。任务起点从「接收人工整理的修复需求」前移到「直接接收报警或工单」——实践中 Agent 在现场信息梳理上往往比人工更好：时间线更清楚、更擅长海量日志检索、能发现人工遗漏的关键线索。整个流程中**稳定复现是最重要的一步**，贯穿三个阶段：分析阶段用复现检验自己的分析，修复阶段将复现过程固化为测试用例，评审阶段研发以复现用例和验证结果为依据检查是否真正修复了最初的问题。三个工程环节支撑落地。其一让研发系统可被 Agent 调用：日志集中管理、提供结构化接口或 CLI（如 aliyun CLI 查节点性能返回 JSON，Agent 按需扩大查询范围持续推进分析）；缺少维护的存量平台没有现成 CLI，就让 Agent 参考已有实现、自主操作浏览器分析接口请求和认证方式，约一周把监控、日志、拓扑查询封装成 polardbx CLI；诊断方法、工具说明和排查经验整理为 Skills，配套采集脚本、指标字典、日志查询模板。其二让分析结论可运行验证：一个五年未解的 MDL 锁泄漏低概率并发问题中，Agent 静态推演出的线程时序解释被人工约两小时验证推翻——**仅阅读代码容易把可能发生的路径误判为实际执行的路径**，于是把调试能力交给 Agent：基于 JDI 重新实现 JDB CLI（后台进程持续维护调试会话、前台命令独立调用，指定线程断点只暂停目标线程，可控制线程执行顺序验证特定时序）；Heap Dump 放到大内存 ECS 集中加载，Agent 通过 HTTP 接口发起 OQL 查询对象字段与引用关系（平台累计两千多份处理任务）；两类复现环境按需选择（Zero 临时实例做简单问题初步复现，K8s 完整环境按问题实例版本拓扑搭建、配合调试工具控制并发时序）。Agent 经几轮迭代找到遗漏的关键条件——在连接进入语句执行状态之前发起 KILL，用线程断点把相关线程停在关键位置再按序恢复，**把依赖偶然调度的线程交错转化为可主动构造的操作步骤**，稳定复现锁泄漏与后续 DDL 阻塞。其三以稳定复现作为交付门禁：**复现用例修复前必须能触发原问题、修复后必须能正常通过，加上完整回归测试，代码才能进入评审**；研发先审查复现证据再审查代码修改。云端沙箱承载 7×24 持续运行，环境隔离保护本地开发环境、权限最小化限制访问范围。半年实践中所有报警先由 Agent 首轮处理，从上万次报警中识别记录两百多个缺陷，**超过 70% 稳定复现并由 Agent 完成修复进入代码评审**。三条可迁移经验：让研发系统可以被 Agent 调用、让研发过程可以验证、让任务能够持续运行；其他团队可从具有明确验证方法的任务入手。

## 8. 云通信：数字分身与契约链流水线

全流程 Agent 协作要解决三个问题，答案分别是流水线、数字分身和渐进式落地。**协作问题**是多智能体公认的上下文丢失——技术 Agent 输出架构与选型，下游测试 Agent 关心系统边界与错误定位，各自产出看起来完整，协作起来「下游需要的信息上游没有产出」；解法是定义标准化作业流水线，为协作建立统一契约，每环输入输出交接方式以规范固化。**边界问题**本质是组织问题而非技术问题：把 Agent 当独立 AI 工程师就要回答权限怎么定、责任怎么追、谁负责迭代；选择**数字分身**（Agent 作为负责人在数字世界里的延伸）一次性解决三者——直接复用被延伸人的权限、每次提交每份产出与该人挂钩、被延伸人负责分身初始化与迭代。**落地问题**上因噎废食与急于求成（跳过工程体系把质量押注模型能力、靠反复重试兜底）都不可取，以稳定优先渐进放开：需求评估风险等级 R（模块跨度、是否核心链路、高性能要求、资金等高风险场景），物料与 Harness 完备度决定分身能力等级 L，**R ≤ L 才接单，R > L 转交人工**；连续成功提升等级，多次交付不符预期降低等级收紧门禁。体系四层：工具层（钉钉机器人 IM 入口、云端执行平台独立工作区、状态图描述九阶段拓扑的交付引擎）、应用物料层（规则、项目宪法、应用描述、架构文档、历史经验、编码规范六类，统一索引按需加载，完备度直接决定能力等级）、流水线层（产品、研发、测试、质检、审计数字分身协同，研发负责人 Agent 统筹，能力载体是可插拔 Skill）、知识库与审计平台（原始物料蒸馏为结构化知识单元，审计发现问题经归因路由扩充物料，让体系越用越强）。分身装载三步（接消息通道、建执行环境、填领域物料）单人 2-3 天；人退到需求确认与技术方案确认两个决策点。九道工序以契约链串联：需求门控 → 需求对焦（spec.md）→ 技术方案（plan.md 独立评审加人工确认，确认覆盖完整性、架构约束符合性、风险与回滚路径三件事，方案级偏差锁定在编码之前）→ 编码（tasks.md 分批，步频与上下文复杂度控制在模型稳定处理范围内）→ 研发自检 → 测试 → 平台质检 → 审计归档 → 人工放行。契约链两条硬约束：**强制交付物**（每道工序必须有正式交付物，缺失即视为未完成不允许推进）和**交付物驱动的运行时校验**（每次交接做标签格式、修饰符、发送者身份三重校验，防止 Agent 以口头声明自行推进流水线，被打回即触发上游返工）。契约链是随交付经验生长的活约束——审计曾发现某类需求在技术方案环节反复回改，根因是物料规则模板缺少对应章节，补齐后同类返工显著减少。交叉质检针对模型偏见：研发分身审查自身产出天然倾向判定符合预期，因此产品、研发、测试、安全四个分身各自开启独立会话与工作区、不共享上下文、只加载 diff/spec/规则/知识库，分别核对需求完成度、代码健壮性、修改合规性、功能可靠性，输出带证据的结论；技术负责人 Agent 汇总后对照声明式检查点逐项核验收口，打回触发编码分身返工——人工逐行评审和手动测试的瓶颈被机制正面解开。审计做三层正交扫描（数据层核对规格方案齐全、产物层跨文件联合分析检测工序配合度、过程层从会话日志还原轨迹回看 Token 消耗与人工介入次数），**输出不是打分而是归因**，三条路由：规则模板缺陷到物料迭代、技能工具问题到工具链整改、知识缺口进知识库台账分批建设；检测、归因、修正、验证四步循环，每次问题沉淀为一条防止复发的规则。未来三个方向：能力边界持续外扩（复杂需求拆成子需求交给分身）、成本治理（**底线是端到端做一个需求不能比人工更贵**——模型分档、上下文管理、错峰执行）、组织形态演进（工程师带若干数字分身组成人机混编小团队，吞吐不再受限于人头数）。底层判断：**真正靠得住的不是模型能力，而是围绕模型建起的一整套交付体系与资产**——领域知识非标、私有，架构演进、历史遗留、术语黑话，通用大模型不可能一次就知道。

## 9. AgentTeam：多 Agent 研发小队与数据飞轮

目标从「让 Agent 写代码」调整为「让一支 AgentTeam 交付结果」：15 个面向不同工序的 Agent 组成能力池，AgentCore 作为 Leader 按任务状态调度——Researcher 理解需求与代码库构建证据地图、Explorer 寻找同构实现形成候选方案（Reference Anchor）、Spec 把目标边界验收条件结构化、Code Worker 在独立分支和会话中实现、Test/Harness 产出可复现测试证据、Judge/Verify 独立做候选选优语义验收和对抗审查、Deploy 准备环境执行发布验证。AgentCore 负责整个团队的运行：拆解任务、调度角色、保存状态、共享上下文，并按失败类型选择下一步——测试失败回同一 Code Session 继续修复，方案方向错误带失败证据重新进入 Research/Explore，持续不收敛触发 Human Gate 请人补充判断。核心 Coding Loop 是两层回环：内层解决「代码能不能跑」（Code Worker 与 Test/Harness 循环，测试失败保留上下文继续修复），外层判断「方案是不是对」（独立 Judge 不仅查测试通过，还判断需求语义是否满足、是否偏离架构、是否存在「测试绿了但实现方向错误」）；验证通过才交付 PR，边界缺陷增量修复，方案级错误回 Research/Explore 重选路径。四个关键设计：**参考锚定**（先找同构实现和架构约束再设计方案，已有代码不是绝对真理但通常是最精确最新鲜的工程参照）、**Produce/Verify 分离**（作者与 Judge 独立会话，避免同一个 Agent 用自己定义的标准证明自己正确）、**带记忆迭代**（同一方案续接 Code Session，Research 保留历轮失败反馈，返工不从零理解）、**分级验证**（正确性安全架构偏离必须修复，非阻塞改进记录留档，连续不收敛及时转人工）。跑通一次只证明流程可用，持续进化靠 AgentLoop 承接数据飞轮，两条调优路径：**离线 Meta-Loop** 从人类专家历史 Commit 反向整理题目，让 AgentTeam 看不到答案独立解题，比较 Diff 和执行轨迹定位 Skill、Tool、状态流转或 Harness 的问题，调整后用同题和留出题回测；**在线 Experience Loop** 自动上报真实任务 Trace，从成功失败轨迹提炼 SOP、工具调用路径、修复规则和反模式，经来源、适用边界和效果验证后在相似任务中按语义召回注入上下文。阶段性结果保持克制：两个真实任务完成需求到上线闭环；24 道内部基线题中 19 道盲测，对照专家代码 10 道等价、5 道接近、4 道部分完成、0 道方向错误——**这是内部题集对照结果，不等同于生产环境通过率**；少量 Feature 样本交付节奏约一周，样本量小且未按复杂度分组，只作阶段性观察。**只有执行闭环和数据飞轮同时建立，Coding Agent 的局部速度才可能真正转化为端到端交付效率**；AgentTeam 的目标不是取代研发，而是重新分配人的注意力——可执行可验证可回放的工作交给 Agent，目标、架构、风险和最终放行留给人。

## 写在最后

八项实践共同指向一件事：单点智能不足以改变交付，把 Agent 放进有契约、有验证、有门禁、有归因闭环的工程与组织体系里，效率才会端到端兑现。下一篇整理 [设计工程实践](/source/agent/企业级Agent手册/27-设计工程实践)，看 GenUI 与 Vibe Designing 怎样让 Agent 从给出答案走向交付结果。
