# Multi-Agent 协作与编排：把独立执行能力组织成团队

把多个 Agent 放在一起并不会自然形成团队：缺少清晰分工、协作方式和状态管理时，参与者越多越容易重复执行、信息不一致、任务遗漏、责任不清。本文沿「异构接入 → 团队组织 → 任务协作 → 共享信息 → 通信 → 治理」提炼多成员共同运行时的责任交接、状态一致性与成果接受。核心判断：**只有专业分工、并行执行、故障隔离和过程治理的收益覆盖沟通协调成本时，Agent 团队才有价值；目标单一、上下文高度集中或严格串行的任务，单 Agent 更简单有效**。

## 1. 编排层的价值与边界

团队 = 围绕共同目标组织起来的一组 Agent 与人：成员有稳定身份与能力边界，内部有明确分工协作关系，过程可追踪、结果可验证。编排层把宽泛目标转化为可执行可验收的任务，建立依赖、汇集状态与产物、安排并行与等待。**显式记录协作过程对长任务尤其重要**——只靠对话历史维持进度，成员变化、环境重启或中断后隐含信息难以恢复；沉淀目标/任务/依赖/状态/产物后，团队连续性不再依赖某个 Agent 始终在线。

边界：Harness 组织单 Agent 执行，Runtime 管生命周期与恢复，Gateway/A2A/MCP 提供连接，编排层串联团队工作，**最终交付是否达标仍由发起人或获授权验收者确认**。编排层不介入每个执行细节：所有信息都汇总到主管 Agent 再由它决定每步，系统就退回单点决策，主管成为新的上下文与执行瓶颈。合理平衡是日常由成员独立推进，只在阻塞、结果冲突、资源不足或高风险操作时协调或引入人工。

## 2. 异构接入：保留原有执行方式

框架 Agent、Coding Agent、托管服务、个人工作区助手并非互斥分类：构建方式决定能怎样扩展执行逻辑，运行位置影响资源访问、在线时间与维护责任。接入按可控范围选择：

| 已有条件 | 接入方式 | 需要准备 |
|---|---|---|
| 能修改应用代码 | 现有框架加协作 SDK/任务接口 | 接收任务、反馈状态、提交成果 |
| 能装插件或控制启动 | 插件 + 适配程序 | 配置环境、关联会话与执行状态 |
| 只能调远程 API | 外部适配程序 | 记录远端任务编号、取状态与结果 |

**能逐步返回文本不代表支持任务查询或中断恢复**，按实际能力安排工作；只返回最终结果的接口无法提供实时进度。框架 Agent 不必为加入团队整体迁移，协作能力可用指令+工具+Skill 组合进原有 Harness，也可用确定性代码完成，不要求全交模型。Coding Agent 经插件/适配保留原生任务循环；**任务与会话分别标识按需关联，不要求一一对应**；关闭输出连接后后台命令可能仍在跑，取消须确认生效；其内部子代理仍归当前 Harness 管理，不自动成为团队成员。

个人工作区接入的是运行实例：团队任务用个人工具须用户明确选择，**不自动继承个人目录全部配置**；允许某 Agent 处理项目代码不意味着其他成员可借此用该用户全部账号权限。仅设工作目录参数不足以阻止访问其他文件，限制须由权限控制或沙箱实施。本地成员受休眠/断网/登录失效影响，适配程序如实报告可观察状态。**文件交付最易被忽略**：只回一个本机绝对路径其他成员读不到，共享文件走约定交付通道附可访问引用，不默认同步整个工作目录；本地执行也不代表数据留本机（远程模型/工具/交付都在外传）。接入后用小任务验证五项：任务到达（正确输入/身份/环境）、连续交互（不混无关任务）、状态反馈（区分执行/等待/失败/结束）、成果交付（接收方可读且核对归属）、控制恢复（声明支持的取消/重试/恢复逐一验实际行为）。

## 3. 组织拓扑：三种模式不是演进阶段

主管—执行（集中协调分散执行）、对等协作（直接协商）、分层编排（专业小组）是对决策/委派/汇报关系的不同安排，按工作特点选择而非按 Agent 数量加层级。**专业能力与组织角色分开**：能力强的不一定当主管，主管不必比所有成员更擅长业务；同一 Agent 可在不同团队承担不同角色。团队成员关系、任务参与关系、执行责任、审核责任分别记录——加入团队不必参与每项任务，能查看不等于负责执行或审核。角色须说明可自主决定什么、交付什么、何时寻求协调；人承担需求澄清/专业判断/关键决策角色，不只是 Agent 卡住时的兜底。

主管—执行要避免所有局部决定等主管确认（决策瓶颈）与主管分派前提前解题、交付后重复验证（重复执行）；对等协作须预先约定分歧解决、共同决策事项、产物整合者与最终交付责任——**对等不意味着责任模糊或决定权均等**；分层只在小组能承担相对完整交付责任时才有意义，代价是逐层信息损耗与汇报延迟。组织关系不决定所有消息路径：执行成员可直接讨论，直接沟通不改变任务归属也不赋予相同决策权。

## 4. 协作机制：分解、调度与结果聚合

Task 是围绕目标的持续工作约定（目标/范围/输入/交付物/验收条件/负责人/约束），Subtask 承载可明确分派、独立负责的局部交付；**Task Run 是一次实际执行**，重试/恢复/重新分派产生多个 Run；Session 是具体 Agent 的交互上下文，与 Run 关联但不一一对应。**只有存在独立交付、不同责任或明确依赖时才拆子任务**，同一成员连续完成的内部步骤不必逐项建任务；消息发送成功不代表任务已被承接。

计划回答如何划分交付单元、选执行者、安排依赖与安全并行；**创建顺序不等于执行顺序**，依赖与可用条件才决定何时开始（测试 Agent 可并行准备环境用例，完整验证等补丁产物可用，且明确验证哪个版本）。子任务引用父 Task 的共同目标约束，只补充自己的责任与特有条件，避免多份描述漂移。需求变化时计划更新保留有效进展：标明哪些分析可复用、旧产物对应哪个版本、哪些必须返工，不直接覆盖旧状态。调度以 Task State 的负责人/依赖/有效版本为准，通知只是提醒——延迟或重复消息不能重新触发已结束的工作。测试失败须把失败用例、产物版本、修订要求关联回实现子任务；V2 提交后旧结果作为历史事实保留，**后续验证只对当前有效版本判断**。

**团队级停止条件在根 Task 开始前约定**：总时间/成本预算、最大委派深度、派生任务数、单任务重试次数、返工轮次、连续多轮无有效进展的处理——不在编排过程中无限追加，单 Agent 重试上限不能替代团队约束。触及后暂停新委派与自动返工，保留已完成结果/阻塞/剩余预算，根 Task 标记失败/阻塞/待人工，由发起人终止、调范围、补资源或授权继续。

结果聚合三层不互相替代：**执行者提交**（候选成果产生）→ **Leader/审核成员接受**（具备用于下游的条件）→ **根 Task 完成条件**（当前有效版本成果共同覆盖目标）。代码/日志/成员报告最初只是候选材料，与验收条件建立关联后才成为 Evidence；内部接受不等于最终业务验收。「已完成」表示执行阶段结束、产物具备交付条件，**不是生命周期终态**——用户或人工验收者取得产物、按约定规则确认接受后归档才真正完结；未通过验收沿用原 Task 关系修订，不另建一套任务。已接受结果可直接复用，只在需要统一口径/解决冲突/综合判断时才额外整合，不必固定增加「聚合执行阶段」。

## 5. 最小充分共享：Context、Memory、State、Artifact

共享不足导致重复探索与错误依赖，共享过多让噪声挤占上下文并把局部错误扩散给其他成员。**团队共享的是上下文来源，不是完全相同的 Context**：统一维护目标/约束/任务状态/已确认事实/产物，每个 Agent 按角色、任务、权限、执行阶段选择所需信息——Context 是团队状态在某成员某时刻的局部视图。选择遵循「最小充分」：含完成任务所需的目标约束依赖结果，不注入完整项目历史、无关工具输出与其他成员全部推理。Handoff 按四类组织：**目标**（范围与交付要求）、**已知事实**（已确认信息与已完成工作）、**待处理事项**（未解决问题/依赖/关键约束）、**可用引用**（Task/数据/Artifact）；完整搜索过程与未验证中间推理通常不原样传递。

团队记忆不等于共用一个向量库或永久保存对话历史：**只沉淀经过任务结果、外部数据、其他成员或人工确认的信息**（领域事实、有效或失败的方法、决策及背景、工作约定、可复用策略），未验证假设直接进长期记忆会被后续任务当事实反复引用。记忆保留来源与边界（谁产生/经何验证/适用团队场景/何时写入/是否仍有效），随业务变化更新降级淘汰——**决定什么能成为记忆、由谁维护、何时失效，比存储技术更影响长期可靠性**。

| 对象 | 回答的问题 | 生命周期 |
|---|---|---|
| Context | 当前 Agent 此刻需要知道什么 | 当前步骤或任务 |
| Memory | 团队过去积累了什么 | 跨任务跨 Session |
| Task State | 当前工作推进到哪里 | 随 Task 持续 |
| Artifact | 团队实际产出了什么 | 由业务应用定义 |
| Workspace | 在哪些工作文件与获准资源上开展任务 | 按持久化策略可跨实例重挂 |
| Environment | 当前执行采用哪些运行条件 | 随运行实例或部署配置 |

**消息说明「发生了什么」，Task State 与 Artifact 记录「当前事实是什么」**：通知任务完成后其他成员仍应读任务当前状态，通知报告生成后接收方应经可访问引用取报告本身而非只依赖消息摘要。共享事实载体不等于全员可读可改，访问范围按角色任务权限控制。

## 6. 通信与协议：A2A、MCP 与混合路由

A2A 为异构 Agent 建立共同协作语义：Agent Card 描述能力接口（**声明不能单独建立可信身份**，须结合签名验证/信任来源/授权策略）、Task/Message/Artifact 解决互操作（与业务同名对象须经适配层明确映射，同名不代表生命周期与权威相同）、contextId 关联协议交互（不替代业务 Task/Session）。长任务三种更新方式按运行条件组合：Streaming（连接保持期间收事件）、轮询（稍后查状态）、Push Notification（不维持连接收更新），**不应统一描述为「不占用连接」**。分工：A2A 管 Agent 间任务交接与结果交换，MCP 管模型应用连接工具资源提示（可选 Tasks 扩展须双方显式支持，句柄不自动等同业务任务），内部消息系统管状态通知广播与组件解耦。

通信模式按任务组合：Direct/Handoff（边界清晰直接交接，目标状态引用须完整）、Shared Message Space（探索讨论复核，订阅与角色过滤控噪声）、Event-driven（大规模异步，处理重复投递/乱序/消费恢复）。成员增多后路由从「调用 Agent B」转向「找能处理某类任务的 Agent」：**混合路由——模型参与语义理解与候选建议，确定性规则校验团队边界/权限/数据范围/可用性/成本/安全并完成执行留痕**。消息平面与协作状态分离：普通通知不作为任务完成唯一依据；事件溯源须具备完整事件/顺序/保留/重建契约才能形成权威状态，**不能把任意消息队列等同于任务账本**，也不能把对话历史当 Team State。开放协议解决互操作，Identity/Delegation/Policy/Data Boundary/Audit 决定连接是否可以发生——能发现调用某 Agent 不代表默认可信其能力声明与数据处理方式。

## 7. 团队治理：身份六类、权限交集与出入站分离

**主体、凭证、委托三者分离**：主体回答谁在行动，委托回答为什么可以代表他人行动，凭证只是证明载体。六类对象各有生命周期：人员主体（随企业账号，SSO/停用同步/强认证）、服务主体（独立于人员账号，轮换撤销最小权限）、Agent/工作负载主体（每个 Agent 唯一，**不与模型或临时容器实例绑定**）、执行主体（随运行实例，须关联 Agent/版本/Task Run/环境）、临时凭证（限定资源动作时段，不落盘长期密钥）、委托授权（保留授权方/受托方/范围/目的/审批证据/到期时间）。审计关联主体标识、委托关系与凭证指纹，**不记录凭证秘密**。

权限 =「稳定角色 + 动态策略」，按组织/团队/Agent/运行/资源/观测六层组织。**有效权限取人员权限、团队边界、Agent 策略、资源策略、委托范围的交集，显式拒绝优先**；资源访问在每次实际访问前重新决策，禁止只在入口检查；Agent 间交接不扩大权限，接收方只获当前任务所需且双方都被允许的最小范围。每次 Task Run 固化策略版本与关键决策，策略变化不改写历史事实；拒绝返回可理解原因（缺角色/委托过期/超边界/需审批）而非通用「无权限」。**入站与出站权限独立配置分别校验**：入站管谁能调用 Agent 发起什么任务，出站管 Agent 可代表谁访问什么资源；入站鉴权不能转化为出站权限，Agent 不得持有复用用户长期凭证；任一环节校验失败即拒绝，**不得降级为共享账号或平台默认权限**。

观测以根 Task 关联各 Task Run/成员运行/交接/模型工具调用：长任务跨多条 Trace，不强制整段生命周期一条追踪，任务标识与产物引用承担跨恢复关联；W3C Trace Context 传播 + teamId/taskId/taskRunId/sessionId 业务关联，连续传播用父子 Span，跨 Trace/并行汇合用 Span Links，**不把动态执行图强行简化为一棵调用树**。五类数据（运行/模型/工具/资源指标 + 治理事件）经统一标识关联；日志不直接记凭证、完整提示词与敏感数据。可观测还要回答协作是否有效：完成度、结果质量、交接有效性、记忆相关性、工具选择合理性、策略一致性——**评估结论与事实记录分开保存**，明确方法版本时间，不把模型判断当不可质疑的运行事实；告警基于稳定运行状态与聚合指标而非高基数字段。

## 写在最后

团队把独立执行能力组织成有序协作，成员间的发现、委派与消息传递还依赖底层通信机制。下一篇整理 [Agent 分布式通信](/source/agent/企业级Agent手册/13-Agent分布式通信)：协议传输形态、版本演进与断线续传如何支撑跨实例协作。
