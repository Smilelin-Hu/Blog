# 上下文状态与能力资产：Context、State、Memory、Knowledge、Skill

模型窗口有限，任务世界持续增长，两者之间必须有独立的信息组织机制。全塞进窗口会让关键约束被重复信息和低可信内容淹没，只留最近几轮又会丢失目标变更、已确认事实、外部副作用与恢复位置。本文提炼 Harness 信息工程的四项工作：多来源信息如何编译成本轮 Context、增长的历史如何压缩卸载、任务事实如何保存在窗口之外、长期 Memory/Knowledge/Skill 如何在正确权限下按需供给。物理存储与索引选型归运行篇，这里聚焦逻辑模型、构建管线与资产契约。

## 1. Context 构建管线：每轮输入是一次编译

System Prompt 不应是仓库里的长字符串，每轮 System Context 按 Agent 版本、任务阶段、用户身份、工作区规则、剩余预算、可用工具与选中 Skill 动态编译。分层解决的是责任问题：

- **System Context**：Platform Policy（不可覆盖）→ Agent Contract → Tenant/Project Rule → Runtime Reminder（阶段/预算/等待项）→ Selected Skill → Tool Descriptors；
- **Task Context**：User Goal/Steering → Plan/Todo → Recent Interaction → Compacted History → Retrieved Memory → Retrieved Knowledge → Workspace References。

**平台策略不能被项目文档覆盖；用户最新要求可以改任务方向但不能突破安全边界；Memory 历史偏好不能替代当前业务事实；工具返回的外部内容不能自动升级为系统指令**。拼成同一层文本，冲突无法定位，也无法独立版本与回归。

Context Builder 每次调用前跑确定性管线：读 Task State → 解析身份作用域 → 收集候选 → **权限与可信度过滤（先于相关性排序，不能为排序方便先把跨租户内容交给检索器）** → 排序去重 → 分配 Token 预算 → 压缩截断引用化 → 按层级编译 → 生成 Manifest。优先级不只看相似度，综合七因素：约束强度、任务相关性、时间有效性、来源可信度、执行依赖（即将调用的工具说明与验收条件优先保留）、信息增量、Token 成本。预算分区动态调整：不可覆盖规则与当前状态保固定下限，工具密集阶段工具定义权重上升，最终综合阶段证据与验收条件更重要，并预留输出与 Observation 空间。

每次调用生成 **Context Manifest**，记录模型究竟看到了什么：source_type/id、scope、version、trust_level、permission_basis、selected_reason、token_count、transform（原文/摘要/截断/引用化）、content_hash，以及 omitted 项与排除原因。它支撑三类工作：开发时解释信息为何遗漏、评估时比较版本间 Context 差异、审计时确认敏感内容为何进入输入——只存 Prompt 文本做不到，同一文本片段的来源权限版本可能完全不同。层级、检索范围、预算、压缩阈值、工具披露与敏感处理统一定义为 **Context Policy 并与 Agent 版本绑定**，把「偶然看见了什么」变成可测试可回放的工程行为。出错时先查「模型是否看见了正确材料」，再判断推理或工具执行。

## 2. 压缩与续行：事实先落权威状态，再退出窗口

Active Context 六区：稳定目标约束、当前任务状态、需精确理解的最近交互、更早过程的结构化摘要、本轮相关检索事实、Artifact 引用。**「最近」不只按时间定义**：最新目标修改、未解决工具错误、待审批动作、验收失败证据即使产生更早已是活动状态；已完成且可由 Artifact 证明的探索可退出窗口。

对话压缩不是普通摘要，要支持下一轮继续执行，至少保留：原始目标与不可变约束、已确认事实及来源（区分事实/假设/模型建议）、已做决定与被否决方案、已执行行动与副作用、当前 Plan/Todo/阻塞、Artifact 路径与外部对象 ID、审批结果与权限模式、失败尝试及避免重复的原因。**高风险事实从 Task State/工具结果/审批记录确定性提取，模型只压缩叙述性内容**；摘要用结构化 Schema，带覆盖事件范围、生成版本与来源引用。

大结果（数万行日志/扫描/搜索）卸载到 Workspace 或 Artifact Store，Context 只留摘要、关键片段、类型大小、生成工具、权限范围与可继续读取的引用；引用必须稳定且受权限保护（临时 URL 恢复时可能失效），随时间变化的结果记录读取时版本或快照标识。**任何影响后续行动的事实先进权威状态，才允许从活动上下文移除**——否则一次不准确摘要就能改变任务真实状态。生命周期四步：**Commit**（事实提交状态/资产库）→ **Compact**（叙述转摘要）→ **Rebuild**（重构 Context 并检查关键约束仍在）→ **Validate**（目标/未解决项/权限/证据完整性检查 + 续行用例验证无漂移）。多次压缩仍不够或进入新大阶段时 Context Reset，前提是 Continuation 已形成一致继续点，表达为可重新加载的信息包：目标与验收标准、Plan/Todo/阻塞、结构化事实与决定、Workspace/Artifact Manifest、活跃异步任务与审批、相关 Memory/Knowledge 引用、权限预算快照、下一步简报。文件式交接特别适合工作区 Agent——人和 Agent 都能检查，不因窗口结束而消失。

压缩质量不能只看省了多少 Token，五指标：**事实保留率、继续成功率（不重复大量探索）、矛盾率（摘要与工具事实/状态/最新指令冲突）、引用可用率、成本收益**。压缩器、摘要 Schema 与阈值都要版本化进回归范围。案例：完整安全扫描存 evidence/security-scan.sarif，窗口只留漏洞数量、阻断项摘要与文件引用——省的不是一次输入长度，而是后续每轮不再重复携带同一大结果。

## 3. Call / Session / Task 与 Workspace

三个常被合并为「会话」的边界：**Call** 是一次请求或恢复动作（秒到分钟，请求 ID/临时凭证/游标）；**Session** 是用户与 Agent 的连续交互边界（分钟到数天，参与者/Channel/消息/偏好）；**Task** 是围绕可验收目标持续存在的执行对象（可跨 Call/Session/进程/节点）。一个 Session 可发起多个 Task，一个长 Task 可在多个 Session 中被查看干预恢复。**把 Task ID 绑成消息线程 ID，会限制后台执行、多人协作与跨渠道续接**——两者分别保留、显式记录关联。

状态三种互补表示，不能互替：**Event Log** 记发生过什么（因果/审计/重建）、**Snapshot** 记某时刻聚合状态（快速读当前视图）、**Checkpoint** 记可安全恢复的位置（Snapshot + Continuation + 幂等 + 环境依赖）。只有 Event Log 恢复成本随任务长度增长；只有 Snapshot 无法解释状态如何形成；把每次保存都叫 Checkpoint 会掩盖工具事务仍在进行、不能安全重放的事实。Harness 面向逻辑状态接口编程（append_event / load_task_state / commit_task_patch / save_snapshot / put_artifact / create_checkpoint / resume_checkpoint / search_workspace / read_range），本地映射到文件与进程内状态、分布式映射到外置状态服务——语义一致，三条构建路径就能接同一企业状态平台。

Workspace 是服务当前任务的显式工作空间（用户可直接查看编辑），与跨任务选择性保留的 Memory 不同。逻辑分区：inputs（保来源）/ scratch（任务结束可清理）/ state（Harness 管理）/ artifacts（可交付结果）/ evidence（证明完成）/ manifest——**不能因为都在文件系统里就用同样的保留与权限策略**。对象至少记录稳定 ID、引用、类型、创建者、来源、版本、权限、所属任务、状态、校验摘要、保留期。Artifact 生命周期 Draft → Validating → Ready → Published/Rejected → Archived/Deleted：**模型写出文件不等于产物完成**，Ready 前过格式测试业务验收，Published 往往还需审批与提交动作。窗口重置、节点替换后，新 Worker 凭 Task State + Continuation + Artifact 引用即可恢复。

## 4. Memory 与 Knowledge：经验与事实分治

Memory 不是无限增长的历史库，是有选择写入、检索、更新、遗忘的信息。四类：**Working**（当前任务临时事实，来自 Task State/Workspace，不必长期保留）、**Episodic**（过去任务经验片段，须保留当时条件与 Outcome，避免把偶然成功当普遍规律）、**Semantic**（稳定事实偏好实体关系，需来源与更新时间）、**Procedural**（已验证方法步骤，稳定后应升级为受版本治理的 Skill 而非停留在自由文本）。

「每次任务结束自动总结写入」很容易造成污染，写入前六问：未来是否有可预期价值？是环境验证的事实还是模型推测/临时表达？属于哪个用户项目租户与保留周期？是否含敏感或依法不应长存的数据？已存在时新增/合并/更新/标冲突？未来错误谁能纠正删除、派生索引如何清理？高价值 Memory 带元数据：来源事件、证据、可信度、适用条件、作用域、最近验证时间、使用反馈、过期策略、版本。检索综合考虑语义、实体、时间、作用域、可信度与历史效果；**被检索到不等于可直接进 Context**，还要按当前身份任务目的过滤，并标记为历史经验而非当前事实。冲突不静默覆盖：保留多版本来源、按时间权威性选当前值、高影响场景请求确认；长期未用未验证或持续致错的衰减、复核或遗忘。**遗忘不是只删向量**——原文、摘要、索引、缓存、派生实体关系、引用它的 Skill 与评估样本都要处理。

Knowledge 是组织维护、有来源时效的业务事实，与 Memory 治理责任不同：来源（权威文档/数据库 vs Agent 任务与反馈）、权威责任（内容所有者 vs Harness/用户/项目责任人）、更新方式（同步发布索引刷新 vs 写入合并纠正衰减遗忘）、风险（过期/权限泄漏/来源冲突 vs 污染/错误固化/跨用户混淆）。知识接口返回结构化证据而非拼接文本：内容、来源与稳定标识、版本/生效时间、所有者与权威级别、ACL 作用域、检索原因与分数、新鲜度、引用或查询轨迹。**实时经营数据优先查权威工具而非离线索引；权限过滤必须在进模型前完成，不能靠向量库里的自然语言标签推断**。实用双层记忆：当日抽取事实追加流水文件（保留来源过程），周期性合并去重到长期记忆文件（按策略进 System Context）；压缩前先 Flush 关键事实。案例分流：当前补丁与待审批项 → Task State；某依赖特殊兼容约束 → Project Memory 候选（需来源与验证时间）；企业升级发布制度 → Knowledge（Agent 不得自行改写）；已验证的分析测试步骤 → Skill 候选；模型未验证的「不兼容」猜测 → 不写入。

## 5. Skill：可复用方法的资产化

Tool 说「能做什么动作」，Skill 说「某类任务中如何正确使用若干动作」——由指令、脚本、模板、示例、检查清单、参考资料组成，封装经过验证的任务方法。Skill 不是 Prompt 也不只是 Tool 别名，**不直接拥有额外权限**，只在当前用户任务环境允许时相关能力才可执行。包结构：manifest（name/version/owner、适用条件、所需工具权限环境、输入输出验收契约）+ instructions + scripts + templates + examples + references + tests。

数百 Skill 全注入会耗尽窗口并导致误选，**渐进式披露三层**：发现层（只见名称/简述/适用条件/主要风险）→ 选择层（Harness 按任务权限环境解析候选、加载完整 Manifest）→ 执行层（真正需要某步才读详细指令脚本）。选择不只靠模型语义匹配，还检查模型兼容性、工具依赖、环境条件、租户许可、数据范围、版本状态——要求写生产的 Skill 在只读探索阶段可被发现但不可执行。确定性边界：稳定重复可编码且失败代价高的步骤沉淀为脚本/工具/规则，模糊目标理解、方案比较、异常解释留给模型指令；**脚本不能藏在说明文本里不受控运行，仍要过 Action Plane 与权限契约**。

一次任务成功不等于成为可复用能力：从 Trace 提取稳定步骤、移除特定任务 ID/临时路径/一次性判断、为脚本模板补测试，再形成 Skill。发布链 Draft → Test → Review（安全权限领域）→ Publish → Observe（使用率/成功率/失败模式）→ Update/Deprecate/Rollback。评估不只看是否被选中，还要比较启用前后成功率、步骤数、工具错误、人工修改量、成本与安全事件；很少被采用或持续降效的调整描述、缩小范围或下线。**线上 Trace 必须能定位到具体 Skill 版本，latest 指针适合开发不适合生产**；Agent 版本锁定允许的 Skill 集与版本范围，紧急修复走新版本或受控热补丁并触发回归。

## 6. 多租户资产治理与反退化

作用域模型六级：Global（平台策略/通用 Skill，通常只读）、Tenant（企业制度/租户知识）、Project（项目规则/规范/Memory）、User（个人偏好经验）、Session（临时交互）、Task（Plan/Scratch/Artifact/证据）。**先确定身份租户项目任务再查允许作用域——不要先跨作用域召回再在生成端「提醒模型不要泄漏」，内容进入模型输入时隔离已经失败**。每项资产带最小治理元数据（来源/所有者/作用域/版本/时间/权限/敏感级/保留期/摘要/派生关系/状态），Memory 加可信度与适用条件，Knowledge 加生效时间与权威来源，Skill 加依赖与评估基线——统一元数据让同一套 Policy 决定能否读写、如何引用、何时过期、如何删除。

三类污染：记忆污染（错误推测/失败轨迹/恶意输入被长期写入当经验）、指令污染（外部文档/工具结果/Memory 文字被提升为高优先级规则）、跨租户污染（索引/缓存/摘要/Artifact/评估数据串租户）。防护覆盖两端：写入时来源识别、验证、敏感检测、作用域绑定、冲突检查；读取时身份过滤、信任标记、指令与数据分离、最小披露、输出审查；高风险 Memory 先进候选区验证后发布。删除要能从稳定资产 ID 追踪派生链（切片/向量/摘要/实体/上层总结/Skill 引用）：禁新读取注入 → 删或隔离原文 → 清理派生 → 更新引用方 Manifest 与 Skill → 保留最小化审计证明 → 触发受影响 Agent 版本验证或重发布。**「遗忘」有时是权重衰减有时是彻底删除，须在策略中区分；需要撤回的数据不能只降检索分数**。

资产变更与代码走同一发布链：结构权限校验 → 受影响 Agent/用例分析 → 离线回放与安全评估 → 灰度进新版本 → Trace/Outcome 监测 → 保留修订或回滚。反退化不只防成功率下降，还监测成本、延迟、引用准确性、跨租户泄漏、错误 Memory 使用、Skill 误选、上下文膨胀；一个资产可能提升某类任务却损害另一类，**评估必须按场景、租户、风险与任务复杂度分层**。三条构建路径责任不同：Framework 由企业为 Context 选择与状态正确性负责；SDK 复用成熟 Harness 但多租户隔离、共享存储、业务验收仍要补齐；Managed Agents 托管 Session 与执行基础，但不替企业决定哪些知识可见、哪些记忆可写、哪些 Skill 可在某租户使用。
